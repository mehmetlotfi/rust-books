    همروندی

    همروندی (concurrency) هر زمانی پیش می‌آید که بخش‌های مختلف برنامهٔ شما ممکن است در زمان‌های متفاوت یا خارج از ترتیب اجرا شوند. در یک بستر توکار، این شامل موارد زیر است:

    • کنترل‌کنندهٔ وقفه‌ها (interrupt handler)، که هر بار رخ دادن وقفهٔ مربوط به خود اجرا می‌شوند،
    • انواع گوناگون چندنخی (multithreading)، که در آن ریزپردازندهٔ شما به‌طور منظم میان بخش‌های برنامه جابه‌جا می‌شود،
    • و در برخی سیستم‌ها، ریزپردازنده‌های چندهسته‌ای، که در آن‌ها هر هسته می‌تواند به‌طور مستقل و هم‌زمان بخش دیگری از برنامهٔ شما را اجرا کند.

    از آن‌جا که بسیاری از برنامه‌های توکار باید با وقفه‌ها سروکار داشته باشند، همروندی معمولاً دیر یا زود پیش می‌آید و جایی است که بسیاری از باگ‌های ظریف و دشوار هم رخ می‌دهند. خوشبختانه Rust تعدادی انتزاع و تضمین ایمنی فراهم می‌کند که به ما کمک می‌کنند کد درست بنویسیم.

    بدون همروندی

    ساده‌ترین همروندی برای یک برنامهٔ توکار این است که اصلاً همروندی نباشد: نرم‌افزار شما از یک حلقهٔ اصلی تشکیل می‌شود که فقط به اجرا ادامه می‌دهد و هیچ وقفه‌ای در کار نیست. گاهی این رویکرد برای مسئلهٔ پیش رو کاملاً مناسب است! معمولاً حلقهٔ شما چند ورودی را می‌خواند، مقداری پردازش انجام می‌دهد و چند خروجی را می‌نویسد.

    #[entry]
fn main() {
    let peripherals = setup_peripherals();
    loop {
        let inputs = read_inputs(&peripherals);
        let outputs = process(inputs);
        write_outputs(&peripherals, outputs);
    }
}

    از آن‌جا که همروندی وجود ندارد، لازم نیست نگران اشتراک داده میان بخش‌های برنامه یا همگام‌سازی دسترسی به دستگاه‌های جانبی باشید. اگر می‌توانید با چنین رویکرد ساده‌ای کارتان را راه بیندازید، این می‌تواند راه‌حل بسیار خوبی باشد.

    دادهٔ سراسری تغییرپذیر

    برخلاف Rust غیرتوکار، معمولاً این امکان را نداریم که تخصیص‌های heap بسازیم و ارجاع‌هایی به آن داده را به نخی که تازه ساخته شده بدهیم. در عوض، کنترل‌کنندهٔ وقفه‌های ما ممکن است در هر لحظه فراخوانی شوند و باید بدانند به هر حافظهٔ اشتراکی‌ای که استفاده می‌کنیم چگونه دسترسی پیدا کنند. در پایین‌ترین سطح، این یعنی باید حافظهٔ تغییرپذیری داشته باشیم که به‌صورت ایستا تخصیص داده شده باشد و هم کنترل‌کنندهٔ وقفه و هم کد اصلی بتوانند به آن اشاره کنند.

    در Rust، چنین متغیرهای static mut همیشه خواندن یا نوشتنشان ناایمن (unsafe) است، زیرا اگر مراقبت ویژه‌ای نکنید، ممکن است یک شرایط رقابتی (race condition) پدید آورید که در آن دسترسی شما به متغیر در میانه‌اش با وقفه‌ای قطع می‌شود که آن هم به همان متغیر دسترسی دارد.

    برای نمونه‌ای از اینکه این رفتار چگونه می‌تواند خطاهای ظریفی در کد شما ایجاد کند، یک برنامهٔ توکار را در نظر بگیرید که لبه‌های صعودی یک سیگنال ورودی را در هر بازهٔ یک‌ثانیه‌ای می‌شمارد (یک فرکانس‌شمار):

    static mut COUNTER: u32 = 0;

#[entry]
fn main() -> ! {
    set_timer_1hz();
    let mut last_state = false;
    loop {
        let state = read_signal_level();
        if state && !last_state {
            // DANGER - Not actually safe! Could cause data races.
            unsafe { COUNTER += 1 };
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    unsafe { COUNTER = 0; }
}

    هر ثانیه، وقفهٔ تایمر شمارنده را دوباره روی 0 می‌گذارد. در همین حال، حلقهٔ اصلی پیوسته سیگنال را اندازه می‌گیرد و هر وقت تغییر از پایین به بالا ببیند، شمارنده را افزایش می‌دهد. ناچار شده‌ایم برای دسترسی به COUNTER از unsafe استفاده کنیم، چون static mut است و این یعنی به کامپایلر قول می‌دهیم که هیچ رفتار تعریف‌نشده‌ای ایجاد نخواهیم کرد. می‌توانید شرایط رقابتی را پیدا کنید؟ تضمینی وجود ندارد که افزایش COUNTER اتمی (atomic) باشد؛ در واقع در بیشتر پلتفرم‌های توکار، این عمل به یک بارگذاری (load)، سپس افزایش، و بعد یک ذخیره‌سازی (store) شکسته می‌شود. اگر وقفه بعد از بارگذاری و پیش از ذخیره‌سازی رخ دهد، بازنشانی به 0 پس از بازگشت از وقفه نادیده گرفته می‌شود — و ما در آن بازه دو برابرِ تعداد گذارهای واقعی را خواهیم شمرد.

    بخش‌های بحرانی

    پس برای رقابت‌های داده‌ای چه می‌توانیم بکنیم؟ یک رویکرد ساده استفاده از بخش‌های بحرانی (critical section) است، یعنی بستری که در آن وقفه‌ها غیرفعال هستند. با پیچیدن دسترسی به COUNTER در main درون یک بخش بحرانی، می‌توانیم مطمئن باشیم که وقفهٔ تایمر تا وقتی افزایش COUNTER را تمام نکرده‌ایم رخ نخواهد داد:

    static mut COUNTER: u32 = 0;

#[entry]
fn main() -> ! {
    set_timer_1hz();
    let mut last_state = false;
    loop {
        let state = read_signal_level();
        if state && !last_state {
            // New critical section ensures synchronised access to COUNTER
            cortex_m::interrupt::free(|_| {
                unsafe { COUNTER += 1 };
            });
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    unsafe { COUNTER = 0; }
}

    در این مثال از cortex_m::interrupt::free استفاده می‌کنیم، اما پلتفرم‌های دیگر سازوکارهای مشابهی برای اجرای کد در یک بخش بحرانی دارند. این کار همچنین با غیرفعال کردن وقفه‌ها، اجرای مقداری کد و سپس فعال کردن دوبارهٔ وقفه‌ها یکی است.

    توجه کنید که لازم نبود درون وقفهٔ تایمر بخش بحرانی بگذاریم، به دو دلیل:

    • نوشتن 0 در COUNTER نمی‌تواند تحت تأثیر رقابت قرار بگیرد، چون آن را نمی‌خوانیم
    • به‌هر حال هرگز نخ main آن را قطع نخواهد کرد

    اگر COUNTER میان چند کنترل‌کنندهٔ وقفه به اشتراک گذاشته می‌شد که ممکن است یکدیگر را پیش‌دستی (preempt) کنند، آنگاه هر کدام از آن‌ها هم ممکن بود به یک بخش بحرانی نیاز داشته باشد.

    این کار مشکل فوری ما را حل می‌کند، اما هنوز مجبوریم مقدار زیادی کد ناایمن بنویسیم که باید با دقت دربارهٔ آن استدلال کنیم، و ممکن است بخش‌های بحرانی را بی‌دلیل به کار ببریم. چون هر بخش بحرانی پردازش وقفه را موقتاً متوقف می‌کند، هزینه‌ای همراه آن است: اندازهٔ کد کمی بیشتر و تأخیر (latency) و لرزش (jitter) بالاتر برای وقفه‌ها (پردازش وقفه‌ها ممکن است بیشتر طول بکشد و زمان تا پردازش آن‌ها متغیرتر باشد). اینکه این موضوع مشکل‌ساز باشد یا نه به سیستم شما بستگی دارد، اما به‌طور کلی دوست داریم از آن اجتناب کنیم.

    شایان ذکر است که اگرچه بخش بحرانی تضمین می‌کند هیچ وقفه‌ای رخ نمی‌دهد، در سیستم‌های چندهسته‌ای تضمین انحصار فراهم نمی‌کند! هستهٔ دیگر می‌تواند بی‌هیچ مشکلی و حتی بدون وقفه به همان حافظه‌ای دسترسی داشته باشد که هستهٔ شما به آن دسترسی دارد. اگر از چند هسته استفاده می‌کنید، به اولیه‌های همگام‌سازی (synchronisation primitive) قوی‌تری نیاز خواهید داشت.

    دسترسی اتمی

    در برخی پلتفرم‌ها دستورهای اتمی ویژه‌ای در دسترس است که برای عملیات خواندن-تغییر-نوشتن (read-modify-write) تضمین‌هایی فراهم می‌کنند. به‌طور مشخص برای Cortex-M: thumbv6 (Cortex-M0 و Cortex-M0+) فقط دستورهای بارگذاری و ذخیره‌سازی اتمی دارد، در حالی که thumbv7 (Cortex-M3 و بالاتر) دستورهای کامل Compare and Swap (CAS) را فراهم می‌کند. این دستورهای CAS جایگزینی برای غیرفعال کردن سنگین‌دستانهٔ همهٔ وقفه‌ها به دست می‌دهند: می‌توانیم افزایش را امتحان کنیم؛ در بیشتر مواقع موفق می‌شود، اما اگر قطع شده باشد، به‌طور خودکار کل عملیات افزایش را دوباره تلاش می‌کند. این عملیات اتمی حتی روی چند هسته هم ایمن‌اند.

    use core::sync::atomic::{AtomicUsize, Ordering};

static COUNTER: AtomicUsize = AtomicUsize::new(0);

#[entry]
fn main() -> ! {
    set_timer_1hz();
    let mut last_state = false;
    loop {
        let state = read_signal_level();
        if state && !last_state {
            // Use `fetch_add` to atomically add 1 to COUNTER
            COUNTER.fetch_add(1, Ordering::Relaxed);
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    // Use `store` to write 0 directly to COUNTER
    COUNTER.store(0, Ordering::Relaxed)
}

    این بار COUNTER یک متغیر static ایمن است. به لطف نوع AtomicUsize، COUNTER را می‌توان هم از کنترل‌کنندهٔ وقفه و هم از نخ اصلی بدون غیرفعال کردن وقفه‌ها به‌طور ایمن تغییر داد. در صورت امکان، این راه‌حل بهتری است — اما ممکن است در پلتفرم شما پشتیبانی نشود.

    یک نکته دربارهٔ Ordering: این پارامتر بر نحوهٔ جابه‌جایی ترتیب دستورها توسط کامپایلر و سخت‌افزار اثر می‌گذارد و پیامدهایی هم برای دیده‌شدن در حافظهٔ نهان (cache) دارد. با فرض اینکه هدف یک پلتفرم تک‌هسته‌ای است، Relaxed در این مورد خاص کافی و کارآمدترین انتخاب است. ترتیب سخت‌گیرانه‌تر باعث می‌شود کامپایلر پیرامون عملیات اتمی مانع‌های حافظه (memory barrier) تولید کند؛ بسته به اینکه از عملیات اتمی برای چه کاری استفاده می‌کنید، ممکن است به این موضوع نیاز داشته باشید یا نداشته باشید! جزئیات دقیق مدل اتمی پیچیده است و بهتر است در جای دیگری توضیح داده شود.

    برای جزئیات بیشتر دربارهٔ عملیات اتمی (atomics) و ترتیب (ordering)، به nomicon نگاه کنید.

    انتزاع‌ها، Send و Sync

    هیچ‌یک از راه‌حل‌های بالا چندان رضایت‌بخش نیستند. آن‌ها به بلوک‌های unsafe نیاز دارند که باید با دقت بسیار زیاد بررسی شوند و ارگونومیک نیستند. حتماً در Rust می‌توانیم بهتر عمل کنیم!

    می‌توانیم شمارندهٔ خود را در یک رابط ایمن انتزاع کنیم که در هر جای دیگر کدمان بتوان با خیال راحت از آن استفاده کرد. برای این مثال از شمارندهٔ مبتنی بر بخش بحرانی استفاده می‌کنیم، اما می‌توانید با عملیات اتمی هم کاری بسیار مشابه انجام دهید.

    use core::cell::UnsafeCell;
use cortex_m::interrupt;

// Our counter is just a wrapper around UnsafeCell<u32>, which is the heart
// of interior mutability in Rust. By using interior mutability, we can have
// COUNTER be `static` instead of `static mut`, but still able to mutate
// its counter value.
struct CSCounter(UnsafeCell<u32>);

const CS_COUNTER_INIT: CSCounter = CSCounter(UnsafeCell::new(0));

impl CSCounter {
    pub fn reset(&self, _cs: &interrupt::CriticalSection) {
        // By requiring a CriticalSection be passed in, we know we must
        // be operating inside a CriticalSection, and so can confidently
        // use this unsafe block (required to call UnsafeCell::get).
        unsafe { *self.0.get() = 0 };
    }

    pub fn increment(&self, _cs: &interrupt::CriticalSection) {
        unsafe { *self.0.get() += 1 };
    }
}

// Required to allow static CSCounter. See explanation below.
unsafe impl Sync for CSCounter {}

// COUNTER is no longer `mut` as it uses interior mutability;
// therefore it also no longer requires unsafe blocks to access.
static COUNTER: CSCounter = CS_COUNTER_INIT;

#[entry]
fn main() -> ! {
    set_timer_1hz();
    let mut last_state = false;
    loop {
        let state = read_signal_level();
        if state && !last_state {
            // No unsafe here!
            interrupt::free(|cs| COUNTER.increment(cs));
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    // We do need to enter a critical section here just to obtain a valid
    // cs token, even though we know no other interrupt could pre-empt
    // this one.
    interrupt::free(|cs| COUNTER.reset(cs));

    // We could use unsafe code to generate a fake CriticalSection if we
    // really wanted to, avoiding the overhead:
    // let cs = unsafe { interrupt::CriticalSection::new() };
}

    کد unsafe خود را به درون انتزاعی که با دقت طراحی شده منتقل کرده‌ایم، و اکنون کد برنامهٔ ما هیچ بلوک unsafeای ندارد.

    این طراحی لازم می‌کند که برنامه یک توکن CriticalSection را بفرستد: این توکن‌ها فقط توسط interrupt::free به‌صورت ایمن تولید می‌شوند، پس با الزام به ارسال یکی از آن‌ها، مطمئن می‌شویم که درون یک بخش بحرانی عمل می‌کنیم، بی‌آنکه واقعاً خودمان قفل را بگیریم. این تضمین به‌صورت ایستا توسط کامپایلر فراهم می‌شود: هیچ سربار زمان اجرایی‌ای برای cs وجود نخواهد داشت. اگر چند شمارنده داشتیم، همه‌شان می‌توانستند همان cs را بگیرند، بدون اینکه به چند بخش بحرانی تو در تو نیاز باشد.

    این موضوع همچنین یک مبحث مهم برای همروندی در Rust را پیش می‌کشد: traitهای Send و Sync. برای خلاصه‌کردن کتاب Rust، یک نوع وقتی Send است که بتوان آن را با خیال راحت به نخ دیگری منتقل کرد، و وقتی Sync است که بتوان آن را با خیال راحت میان چند نخ به اشتراک گذاشت. در بستر توکار، وقفه‌ها را نخی جدا از کد برنامه در حال اجرا در نظر می‌گیریم، بنابراین متغیرهایی که هم وقفه و هم کد اصلی به آن‌ها دسترسی دارند باید Sync باشند.

    برای بیشتر نوع‌ها در Rust، هر دوی این صفت‌ها به‌طور خودکار توسط کامپایلر برایتان مشتق می‌شوند. اما چون CSCounter یک UnsafeCell دارد، Sync نیست و بنابراین نمی‌توانستیم یک static CSCounter بسازیم: متغیرهای static باید Sync باشند، چون ممکن است چند نخ به آن‌ها دسترسی داشته باشند.

    برای اینکه به کامپایلر بگوییم مراقب بوده‌ایم و CSCounter در واقع برای اشتراک میان نخ‌ها ایمن است، صفت Sync را به‌صراحت پیاده‌سازی می‌کنیم. مانند استفادهٔ قبلی از بخش‌های بحرانی، این فقط روی پلتفرم‌های تک‌هسته‌ای ایمن است: با چند هسته باید برای تضمین ایمنی به تدابیر بیشتری متوسل شوید.

    میوتکس‌ها

    یک انتزاع مفید مختص مسئلهٔ شمارندهٔ خودمان ساخته‌ایم، اما انتزاع‌های رایج بسیاری برای همروندی وجود دارند.

    یکی از این اولیه‌های همگام‌سازی (synchronisation primitive) میوتکس (mutex) است که مخفف mutual exclusion، یعنی انحصار متقابل، است. این ساختارها دسترسی انحصاری به یک متغیر، مانند شمارندهٔ ما، را تضمین می‌کنند. یک نخ می‌تواند تلاش کند میوتکس را قفل کند (lock) یا به دست آورد (acquire)، و یا بی‌درنگ موفق می‌شود، یا مسدود می‌شود و منتظر می‌ماند تا قفل به دست آید، یا خطایی برمی‌گرداند مبنی بر اینکه میوتکس قابل قفل شدن نبود. تا زمانی که آن نخ قفل را نگه می‌دارد، به دادهٔ محافظت‌شده دسترسی دارد. وقتی نخ کارش تمام شد، میوتکس را باز می‌کند (unlock) یا رها می‌کند (release) تا نخ دیگری بتواند آن را قفل کند. در Rust معمولاً بازکردن قفل را با صفت Drop پیاده‌سازی می‌کنیم تا اطمینان یابیم هر وقت میوتکس از محدوده خارج شود، همیشه رها می‌شود.

    استفاده از میوتکس با کنترل‌کنندهٔ وقفه‌ها می‌تواند پیچیده باشد: معمولاً قابل‌قبول نیست که کنترل‌کنندهٔ وقفه مسدود شود، و به‌ویژه فاجعه‌بار خواهد بود اگر برای منتظر ماندن تا نخ اصلی قفلی را رها کند مسدود شود، چون در آن صورت دچار بن‌بست (deadlock) می‌شویم (نخ اصلی هرگز قفل را رها نخواهد کرد چون اجرا در کنترل‌کنندهٔ وقفه می‌ماند). بن‌بست ناایمن به حساب نمی‌آید: حتی در Rust ایمن هم ممکن است رخ دهد.

    برای اجتناب کامل از این رفتار، می‌توانیم میوتکسی پیاده‌سازی کنیم که برای قفل شدن به یک بخش بحرانی نیاز دارد، دقیقاً مانند مثال شمارندهٔ خودمان. تا وقتی بخش بحرانی باید به‌اندازهٔ قفل دوام بیاورد، می‌توانیم مطمئن باشیم دسترسی انحصاری به متغیر پیچیده‌شده داریم، بدون اینکه حتی نیاز باشد وضعیت قفل/بازکردن میوتکس را ردیابی کنیم.

    این کار در واقع برایمان در crate به نام cortex_m انجام شده است! می‌توانستیم شمارندهٔ خود را با آن بنویسیم:

    use core::cell::Cell;
use cortex_m::interrupt::Mutex;

static COUNTER: Mutex<Cell<u32>> = Mutex::new(Cell::new(0));

#[entry]
fn main() -> ! {
    set_timer_1hz();
    let mut last_state = false;
    loop {
        let state = read_signal_level();
        if state && !last_state {
            interrupt::free(|cs|
                COUNTER.borrow(cs).set(COUNTER.borrow(cs).get() + 1));
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    // We still need to enter a critical section here to satisfy the Mutex.
    interrupt::free(|cs| COUNTER.borrow(cs).set(0));
}

    اکنون از Cell استفاده می‌کنیم که همراه هم‌خانوادهٔ خود RefCell برای فراهم کردن تغییرپذیری درونی (interior mutability) ایمن به کار می‌رود. پیش‌تر UnsafeCell را دیده‌ایم که لایهٔ پایه‌ای تغییرپذیری درونی در Rust است: به شما اجازه می‌دهد چند ارجاع تغییرپذیر به مقدارش به دست آورید، اما فقط با کد ناایمن. یک Cell مانند UnsafeCell است اما رابطی ایمن فراهم می‌کند: فقط اجازه می‌دهد یک کپی از مقدار فعلی بگیرید یا آن را جایگزین کنید، نه اینکه ارجاعی بگیرید، و چون Sync نیست، نمی‌توان آن را میان نخ‌ها به اشتراک گذاشت. این محدودیت‌ها یعنی استفاده از آن ایمن است، اما نمی‌توانستیم مستقیماً آن را در یک متغیر static به کار ببریم، چون یک static باید Sync باشد.

    پس چرا مثال بالا کار می‌کند؟ Mutex<T> برای هر T ای که Send باشد — مانند یک Cell — صفت Sync را پیاده‌سازی می‌کند. این کار را می‌تواند با ایمنی انجام دهد چون فقط در طول یک بخش بحرانی به محتویاتش دسترسی می‌دهد. بنابراین می‌توانیم یک شمارندهٔ ایمن بدون هیچ کد ناایمنی به دست آوریم!

    این برای نوع‌های ساده مانند u32 شمارندهٔ ما عالی است، اما دربارهٔ نوع‌های پیچیده‌تری که Copy نیستند چه؟ یک نمونهٔ بسیار رایج در بستر توکار ساختار دستگاه جانبی است که معمولاً Copy نیست. برای آن می‌توانیم به RefCell روی بیاوریم.

    اشتراک‌گذاری دستگاه‌های جانبی

    crateهای دستگاه که با svd2rust و انتزاع‌های مشابه تولید می‌شوند، با اِعمال این قاعده که در هر زمان فقط یک نمونه از ساختار دستگاه جانبی می‌تواند وجود داشته باشد، دسترسی ایمن به دستگاه‌های جانبی را فراهم می‌کنند. این ایمنی را تضمین می‌کند، اما دسترسی به یک دستگاه جانبی از هر دو نخ اصلی و کنترل‌کنندهٔ وقفه را دشوار می‌کند.

    برای اشتراک‌گذاری ایمن دسترسی به دستگاه جانبی، می‌توانیم از Mutexای که پیش‌تر دیدیم استفاده کنیم. همچنین باید از RefCell استفاده کنیم که از یک بررسی در زمان اجرا بهره می‌برد تا مطمئن شود در هر زمان فقط یک ارجاع به دستگاه جانبی داده می‌شود. این سربار بیشتری از Cell ساده دارد، اما چون ارجاع می‌دهیم نه کپی، باید مطمئن باشیم در هر لحظه فقط یکی وجود دارد.

    در نهایت، باید به نحوی هم تدبیری بیندیشیم تا دستگاه جانبی پس از مقداردهی اولیه در کد اصلی به درون متغیر مشترک منتقل شود. برای این کار می‌توانیم از نوع Option استفاده کنیم که با None مقداردهی اولیه می‌شود و بعداً با نمونهٔ دستگاه جانبی تنظیم می‌شود.

    use core::cell::RefCell;
use cortex_m::interrupt::{self, Mutex};
use stm32f4::stm32f405;

static MY_GPIO: Mutex<RefCell<Option<stm32f405::GPIOA>>> =
    Mutex::new(RefCell::new(None));

#[entry]
fn main() -> ! {
    // Obtain the peripheral singletons and configure it.
    // This example is from an svd2rust-generated crate, but
    // most embedded device crates will be similar.
    let dp = stm32f405::Peripherals::take().unwrap();
    let gpioa = &dp.GPIOA;

    // Some sort of configuration function.
    // Assume it sets PA0 to an input and PA1 to an output.
    configure_gpio(gpioa);

    // Store the GPIOA in the mutex, moving it.
    interrupt::free(|cs| MY_GPIO.borrow(cs).replace(Some(dp.GPIOA)));
    // We can no longer use `gpioa` or `dp.GPIOA`, and instead have to
    // access it via the mutex.

    // Be careful to enable the interrupt only after setting MY_GPIO:
    // otherwise the interrupt might fire while it still contains None,
    // and as-written (with `unwrap()`), it would panic.
    set_timer_1hz();
    let mut last_state = false;
    loop {
        // We'll now read state as a digital input, via the mutex
        let state = interrupt::free(|cs| {
            let gpioa = MY_GPIO.borrow(cs).borrow();
            gpioa.as_ref().unwrap().idr.read().idr0().bit_is_set()
        });

        if state && !last_state {
            // Set PA1 high if we've seen a rising edge on PA0.
            interrupt::free(|cs| {
                let gpioa = MY_GPIO.borrow(cs).borrow();
                gpioa.as_ref().unwrap().odr.modify(|_, w| w.odr1().set_bit());
            });
        }
        last_state = state;
    }
}

#[interrupt]
fn timer() {
    // This time in the interrupt we'll just clear PA0.
    interrupt::free(|cs| {
        // We can use `unwrap()` because we know the interrupt wasn't enabled
        // until after MY_GPIO was set; otherwise we should handle the potential
        // for a None value.
        let gpioa = MY_GPIO.borrow(cs).borrow();
        gpioa.as_ref().unwrap().odr.modify(|_, w| w.odr1().clear_bit());
    });
}

    این مطلب زیادی برای هضم کردن است، پس بیایید خطوط مهم را بشکافیم.

    static MY_GPIO: Mutex<RefCell<Option<stm32f405::GPIOA>>> =
    Mutex::new(RefCell::new(None));

    متغیر مشترک ما اکنون یک Mutex است که یک RefCell را در بر می‌گیرد که خود یک Option دارد. Mutex تضمین می‌کند که فقط در طول یک بخش بحرانی دسترسی داریم، و بنابراین متغیر را Sync می‌کند، هرچند یک RefCell ساده Sync نخواهد بود. RefCell تغییرپذیری درونی را همراه با ارجاع‌ها به ما می‌دهد، که برای استفاده از GPIOA خود به آن نیاز خواهیم داشت. Option به ما اجازه می‌دهد این متغیر را با چیزی خالی مقداردهی اولیه کنیم و فقط بعداً متغیر واقعی را در آن منتقل کنیم. نمی‌توانیم به‌صورت ایستا به singleton دستگاه جانبی دسترسی پیدا کنیم، فقط در زمان اجرا می‌توانیم، پس این لازم است.

    interrupt::free(|cs| MY_GPIO.borrow(cs).replace(Some(dp.GPIOA)));

    درون یک بخش بحرانی می‌توانیم borrow() را روی میوتکس صدا بزنیم که ارجاعی به RefCell به ما می‌دهد. سپس replace() را صدا می‌زنیم تا مقدار جدید خود را به درون RefCell منتقل کنیم.

    interrupt::free(|cs| {
    let gpioa = MY_GPIO.borrow(cs).borrow();
    gpioa.as_ref().unwrap().odr.modify(|_, w| w.odr1().set_bit());
});

    سرانجام، از MY_GPIO به شیوه‌ای ایمن و همروند استفاده می‌کنیم. بخش بحرانی طبق معمول مانع رخ دادن وقفه می‌شود و به ما اجازه می‌دهد میوتکس را قرض بگیریم. سپس RefCell یک &Option<GPIOA> به ما می‌دهد و پیگیری می‌کند که چه مدت قرض‌گرفته‌شده می‌ماند — وقتی آن ارجاع از محدوده خارج شود، RefCell به‌روز می‌شود تا نشان دهد دیگر قرض گرفته نشده است.

    چون نمی‌توانیم GPIOA را از درون &Option بیرون بکشیم، باید آن را با as_ref() به یک &Option<&GPIOA> تبدیل کنیم، که سرانجام می‌توانیم unwrap() کنیم تا &GPIOAای را به دست آوریم که به ما اجازه می‌دهد دستگاه جانبی را تغییر دهیم.

    اگر به یک ارجاع تغییرپذیر به یک منبع مشترک نیاز داشته باشیم، باید به‌جای آن‌ها از borrow_mut و deref_mut استفاده کرد. کد زیر نمونه‌ای را با استفاده از تایمر TIM2 نشان می‌دهد.

    use core::cell::RefCell;
use core::ops::DerefMut;
use cortex_m::interrupt::{self, Mutex};
use cortex_m::asm::wfi;
use stm32f4::stm32f405;

static G_TIM: Mutex<RefCell<Option<Timer<stm32::TIM2>>>> =
	Mutex::new(RefCell::new(None));

#[entry]
fn main() -> ! {
    let mut cp = cm::Peripherals::take().unwrap();
    let dp = stm32f405::Peripherals::take().unwrap();

    // Some sort of timer configuration function.
    // Assume it configures the TIM2 timer, its NVIC interrupt,
    // and finally starts the timer.
    let tim = configure_timer_interrupt(&mut cp, dp);

    interrupt::free(|cs| {
        G_TIM.borrow(cs).replace(Some(tim));
    });

    loop {
        wfi();
    }
}

#[interrupt]
fn timer() {
    interrupt::free(|cs| {
        if let Some(ref mut tim)) =  G_TIM.borrow(cs).borrow_mut().deref_mut() {
            tim.start(1.hz());
        }
    });
}

    اوف! این ایمن است، اما کمی هم دست‌وپاگیر است. آیا کار دیگری هست که بتوانیم بکنیم؟

    RTIC

    یک جایگزین چارچوب RTIC است که مخفف Real Time Interrupt-driven Concurrency (همروندی بلادرنگ مبتنی بر وقفه) است. این چارچوب اولویت‌های ایستا را اِعمال می‌کند و دسترسی‌ها به متغیرهای static mut («منابع») را ردیابی می‌کند تا به‌صورت ایستا تضمین کند منابع مشترک همیشه به‌طور ایمن در دسترس قرار می‌گیرند، بدون اینکه سربار ورود دائم به بخش‌های بحرانی و استفاده از شمارش ارجاع (مانند RefCell) لازم باشد. این رویکرد مزایای متعددی دارد، از جمله تضمین نبود بن‌بست و سربار بسیار کم زمانی و حافظه‌ای.

    RTIC همراه با یک اجراکنندهٔ ناهمگام (asynchronous executor) عرضه می‌شود، پس وظایف نرم‌افزاری شما توابع async هستند که در آن‌ها می‌توانید افزون بر APIهای همگام معمولی از APIهای async هم استفاده کنید.

    این چارچوب قابلیت‌های دیگری هم دارد، مانند ارسال پیام، که نیاز به حالت مشترک صریح را کاهش می‌دهد، و امکان زمان‌بندی اجرای وظایف در زمانی مشخص، که می‌توان از آن برای پیاده‌سازی وظایف دوره‌ای استفاده کرد. برای اطلاعات بیشتر مستندات را ببینید!

    Embassy

    Embassy اکوسیستمی از کتابخانه‌هاست که بر استفاده از نحو async / await موجود در Rust برای همروندی تمرکز دارد. هستهٔ embassy اجراکنندهٔ ناهمگام آن است که از بیشتر معماری‌های رایج MCU پشتیبانی می‌کند.

    embassy همچنین رویکرد «باتری‌ها همراه آن است» را دارد و مؤلفه‌های دیگر فراوانی عرضه می‌کند، برای مثال:

    • کتابخانهٔ زمان
    • کتابخانه‌های HAL گوناگون که پشتیبانی از کتابخانهٔ زمان را هم فراهم می‌کنند.
    • embassy-sync برای اولیه‌های همگام‌سازی

    برای اطلاعات بیشتر می‌توانید وب‌سایت و کتاب آن را ببینید.

    سیستم‌عامل‌های بلادرنگ

    مدل رایج دیگری برای همروندی در سیستم‌های توکار، سیستم‌عامل بلادرنگ (RTOS) است. اگرچه در حال حاضر در Rust کمتر کاویده شده‌اند، در توسعهٔ توکار سنتی به‌طور گسترده به کار می‌روند. نمونه‌های متن‌باز شامل FreeRTOS و ChibiOS هستند. این RTOSها از اجرای چند نخ برنامه پشتیبانی می‌کنند که CPU میان آن‌ها جابه‌جا می‌شود، یا وقتی نخ‌ها کنترل را واگذار می‌کنند (چندوظیفگی همکارانه یا cooperative multitasking) یا بر پایهٔ یک تایمر منظم یا وقفه‌ها (چندوظیفگی پیش‌دستانه یا preemptive multitasking). RTOS معمولاً میوتکس (mutex) و دیگر ابزارهای پایهٔ همگام‌سازی (synchronisation primitives) را فراهم می‌کند و اغلب با قابلیت‌های سخت‌افزاری مانند موتورهای DMA همکاری می‌کند.

    در زمان نگارش، نمونه‌های چندانی از RTOS در Rust نیست که به آن‌ها اشاره کنیم، اما این حوزه جذاب است، پس آن را زیر نظر داشته باشید!

    چندهسته‌ای

    داشتن دو یا چند هسته در پردازنده‌های توکار رایج‌تر می‌شود، که لایهٔ پیچیدگی اضافه‌ای به همروندی می‌افزاید. همهٔ مثال‌هایی که از بخش بحرانی استفاده می‌کنند (از جمله cortex_m::interrupt::Mutex) فرض می‌کنند تنها نخ اجرایی دیگر، نخ وقفه است، اما در یک سیستم چندهسته‌ای دیگر چنین نیست. در عوض، به اولیه‌های همگام‌سازی‌ای نیاز خواهیم داشت که برای چند هسته طراحی شده‌اند (که SMP، مخفف symmetric multi-processing یا چندپردازشی متقارن، هم نامیده می‌شود).

    این‌ها معمولاً از همان دستورهای اتمی‌ای استفاده می‌کنند که پیش‌تر دیدیم، چون سیستم پردازشی تضمین می‌کند که اتمی بودن در همهٔ هسته‌ها حفظ شود.

    پوشش جزئیات این موضوعات در حال حاضر خارج از دامنهٔ این کتاب است، اما الگوهای کلی همان الگوهای حالت تک‌هسته‌ای هستند.
