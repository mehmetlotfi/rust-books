    نکاتی برای توسعه‌دهندگان C نهفته

    این فصل مجموعه‌ای از نکات گوناگون را گرد آورده است که ممکن است برای توسعه‌دهندگان باتجربهٔ C نهفته که می‌خواهند نوشتن Rust را آغاز کنند مفید باشد. تأکید ویژهٔ آن بر این است که چیزهایی که شاید در C به آن‌ها عادت کرده باشید، در Rust چه تفاوتی دارند.

    پیش‌پردازنده

    در C نهفته استفاده از پیش‌پردازنده (preprocessor) برای مقاصد گوناگون بسیار رایج است، مانند:

    • انتخاب بلوک‌های کد در زمان کامپایل با #ifdef
    • اندازه‌ها و محاسبات آرایه در زمان کامپایل
    • ماکروهایی برای ساده‌کردن الگوهای رایج (برای پرهیز از سربار فراخوانی تابع)

    در Rust پیش‌پردازنده وجود ندارد و به همین دلیل بسیاری از این موارد استفاده به شیوه‌ای دیگر پوشش داده می‌شوند. در ادامهٔ این بخش جایگزین‌های مختلفی را برای استفاده از پیش‌پردازنده بررسی می‌کنیم.

    انتخاب کد در زمان کامپایل

    نزدیک‌ترین معادل #ifdef ... #endif در Rust، featureهای Cargo هستند. این featureها از پیش‌پردازندهٔ C کمی رسمی‌تر هستند: همهٔ featureهای ممکن برای هر crate به‌صراحت فهرست می‌شوند و تنها می‌توانند روشن یا خاموش باشند. featureها هنگامی روشن می‌شوند که یک crate را به‌عنوان وابستگی فهرست می‌کنید و جمع‌پذیرند: اگر هر crate در درخت وابستگی‌های شما یک feature را برای crate دیگری فعال کند، آن feature برای همهٔ کاربران آن crate فعال خواهد شد.

    برای مثال، ممکن است crateای داشته باشید که کتابخانه‌ای از اجزای پایهٔ پردازش سیگنال فراهم می‌کند. هر کدام از این اجزا ممکن است زمان کامپایل بیشتری بگیرد یا جدول بزرگی از ثابت‌ها اعلام کند که دوست دارید از آن پرهیز کنید. می‌توانید برای هر جزء یک feature در Cargo.toml خود اعلام کنید:

    [features]
FIR = []
IIR = []

    سپس در کد خود از #[cfg(feature="FIR")] برای کنترل آنچه شامل می‌شود استفاده کنید.

    /// In your top-level lib.rs

#[cfg(feature="FIR")]
pub mod fir;

#[cfg(feature="IIR")]
pub mod iir;

    به‌طور مشابه می‌توانید بلوک‌های کد را فقط در صورتی شامل کنید که یک feature فعال نباشد، یا هر ترکیبی از featureهای فعال و غیرفعال برقرار باشد.

    افزون بر این، Rust تعدادی شرط خودکار فراهم می‌کند که می‌توانید از آن‌ها استفاده کنید، مانند target_arch برای انتخاب کدهای متفاوت بر اساس معماری. برای جزئیات کامل پشتیبانی از کامپایل شرطی، به فصل کامپایل شرطی در مرجع Rust مراجعه کنید.

    کامپایل شرطی فقط بر دستور یا بلوک بعدی اعمال می‌شود. اگر در دامنهٔ فعلی نتوان از بلوک استفاده کرد، attribute cfg باید چندین بار به کار برود. شایان ذکر است که در بیشتر موارد بهتر است همهٔ کد را شامل کنید و بگذارید کامپایلر هنگام بهینه‌سازی کد مرده را حذف کند: این کار برای شما و کاربرانتان ساده‌تر است و معمولاً کامپایلر در حذف کدهای استفاده‌نشده خوب عمل می‌کند.

    اندازه‌ها و محاسبات در زمان کامپایل

    Rust از const fn پشتیبانی می‌کند: توابعی که تضمین می‌شود در زمان کامپایل قابل ارزیابی هستند و بنابراین می‌توان در جاهایی که ثابت لازم است، مانند اندازهٔ آرایه‌ها، از آن‌ها استفاده کرد. این قابلیت را می‌توان همراه featureهای یادشده به کار برد، برای مثال:

    const fn array_size() -> usize {
    #[cfg(feature="use_more_ram")]
    { 1024 }
    #[cfg(not(feature="use_more_ram"))]
    { 128 }
}

static BUF: [u32; array_size()] = [0u32; array_size()];

    این قابلیت‌ها از نسخهٔ 1.31 به Rust پایدار (stable) افزوده شده‌اند، بنابراین مستندات آن‌ها هنوز اندک است. قابلیت‌های در دسترس const fn نیز در زمان نگارش بسیار محدود است؛ انتظار می‌رود در نسخه‌های آیندهٔ Rust آنچه در const fn مجاز است گسترش یابد.

    ماکروها

    Rust یک سامانهٔ ماکرو بسیار قدرتمند فراهم می‌کند. در حالی که پیش‌پردازندهٔ C تقریباً مستقیماً روی متن کد منبع شما کار می‌کند، سامانهٔ ماکروی Rust در سطحی بالاتر عمل می‌کند. دو گونه ماکروی Rust وجود دارد: ماکروهای مبتنی بر مثال (macros by example) و ماکروهای رویه‌ای (procedural macros). گونهٔ نخست ساده‌تر و رایج‌تر است؛ شبیه فراخوانی تابع به نظر می‌رسد و می‌تواند به یک عبارت، دستور، آیتم یا الگوی کامل گسترش یابد. ماکروهای رویه‌ای پیچیده‌ترند اما افزودن قابلیت‌های بسیار قدرتمند به زبان Rust را ممکن می‌کنند: آن‌ها می‌توانند نحو دلخواه Rust را به نحو جدیدی از Rust تبدیل کنند.

    به‌طور کلی، هرجا ممکن بود از یک ماکروی پیش‌پردازندهٔ C استفاده کنید، احتمالاً بهتر است ببینید آیا یک ماکروی مبتنی بر مثال می‌تواند همان کار را انجام دهد. این ماکروها را می‌توان در crate خودتان تعریف کرد و به‌سادگی در همان crate استفاده یا برای کاربران دیگر صادر کرد. توجه داشته باشید که چون آن‌ها باید به عبارت، دستور، آیتم یا الگوی کامل گسترش یابند، برخی موارد استفاده از ماکروهای پیش‌پردازندهٔ C کار نخواهند کرد؛ برای مثال ماکرویی که به بخشی از نام یک متغیر یا مجموعه‌ای ناقص از آیتم‌ها در یک فهرست گسترش می‌یابد.

    مانند featureهای Cargo، ارزش دارد که بررسی کنید اصلاً به ماکرو نیاز دارید یا نه. در بسیاری از موارد یک تابع معمولی آسان‌تر فهمیده می‌شود و به همان کدی inline می‌شود که ماکرو تولید می‌کرد. attributeهای #[inline] و #[inline(always)] کنترل بیشتری بر این فرایند به شما می‌دهند، هرچند در اینجا نیز باید احتیاط کرد — کامپایلر به‌طور خودکار توابع هم‌crate را در جاهای مناسب inline می‌کند، بنابراین مجبور کردن آن به inline کردن در جای نامناسب ممکن است در واقع به کاهش کارایی بینجامد.

    توضیح کامل سامانهٔ ماکروی Rust از حوصلهٔ این صفحهٔ نکات خارج است، بنابراین توصیه می‌شود برای جزئیات کامل به مستندات Rust مراجعه کنید.

    سامانهٔ ساخت

    بیشتر crateهای Rust با Cargo ساخته می‌شوند (هرچند الزامی نیست). Cargo بسیاری از مشکلات دشوار سامانه‌های ساخت سنتی را حل می‌کند. با این حال ممکن است بخواهید فرایند ساخت را سفارشی کنید. Cargo برای این منظور اسکریپت‌های build.rs را فراهم می‌کند. این‌ها اسکریپت‌های Rust هستند که در صورت نیاز می‌توانند با سامانهٔ ساخت Cargo تعامل داشته باشند.

    موارد استفادهٔ رایج اسکریپت‌های ساخت عبارت‌اند از:

    • فراهم‌کردن اطلاعات زمان ساخت، برای مثال درج ایستای تاریخ ساخت یا هش commit در Git درون فایل اجرایی شما
    • تولید اسکریپت‌های لینکر (linker) در زمان ساخت، بسته به featureهای انتخاب‌شده یا منطق دیگر
    • تغییر پیکربندی ساخت Cargo
    • افزودن کتابخانه‌های ایستای اضافی برای پیوند (link) شدن

    در حال حاضر از اسکریپت‌های پس از ساخت (post-build) پشتیبانی نمی‌شود؛ اسکریپت‌هایی که شاید به‌طور سنتی برای کارهایی مانند تولید خودکار فایل‌های باینری از اشیای ساخت یا چاپ اطلاعات ساخت از آن‌ها استفاده می‌کردید.

    کامپایل متقابل

    استفاده از Cargo به‌عنوان سامانهٔ ساخت، کامپایل متقابل (cross-compiling) را نیز ساده می‌کند. در بیشتر موارد کافی است --target thumbv6m-none-eabi را به Cargo بدهید و فایل اجرایی مناسب را در target/thumbv6m-none-eabi/debug/myapp پیدا کنید.

    برای پلتفرم‌هایی که Rust به‌طور بومی از آن‌ها پشتیبانی نمی‌کند، باید خودتان libcore را برای آن هدف بسازید. در چنین پلتفرم‌هایی می‌توان از Xargo به‌جای Cargo استفاده کرد که libcore را به‌طور خودکار برای شما می‌سازد.

    iteratorها در برابر دسترسی به آرایه

    در C احتمالاً به دسترسی مستقیم به آرایه‌ها با اندیس آن‌ها عادت دارید:

    int16_t arr[16];
int i;
for(i=0; i<sizeof(arr)/sizeof(arr[0]); i++) {
    process(arr[i]);
}

    در Rust این کار یک ضدالگو (anti-pattern) است: دسترسی با اندیس می‌تواند کندتر باشد (چون باید مرزها بررسی شوند) و ممکن است از بهینه‌سازی‌های مختلف کامپایلر جلوگیری کند. این تفاوت مهمی است و ارزش تکرار دارد: Rust برای تضمین ایمنی حافظه، دسترسی خارج از محدوده را هنگام اندیس‌گذاری دستی آرایه بررسی می‌کند، در حالی که C با کمال میل بیرون از آرایه اندیس می‌زند.

    به‌جای آن از iteratorها استفاده کنید:

    let arr = [0u16; 16];
for element in arr.iter() {
    process(*element);
}

    iteratorها مجموعهٔ قدرتمندی از قابلیت‌ها را فراهم می‌کنند که در C باید خودتان به‌صورت دستی پیاده‌شان کنید، مانند زنجیره‌کردن (chaining)، zip‌کردن، شمارش‌گذاری (enumerating)، یافتن کمینه یا بیشینه، جمع‌زدن و موارد دیگر. متدهای iterator را نیز می‌توان زنجیر کرد و کدی بسیار خوانا برای پردازش داده نوشت.

    برای جزئیات بیشتر تکرارگرها در کتاب و مستندات Iterator را ببینید.

    ارجاع‌ها در برابر اشاره‌گرها

    در Rust اشاره‌گرها (که اشاره‌گرهای خام نامیده می‌شوند) وجود دارند اما فقط در شرایط خاص به کار می‌روند، زیرا ارجاع‌زدایی از آن‌ها همیشه unsafe به حساب می‌آید – Rust نمی‌تواند تضمین‌های معمول خود را دربارهٔ آنچه پشت اشاره‌گر قرار دارد ارائه دهد.

    در بیشتر موارد به‌جای آن از ارجاع‌ها (references) استفاده می‌کنیم که با نماد & نشان داده می‌شوند، یا ارجاع‌های تغییرپذیر که با &mut نشان داده می‌شوند. ارجاع‌ها از این نظر شبیه اشاره‌گرها رفتار می‌کنند که می‌توان با ارجاع‌زدایی به مقادیر زیرین دسترسی یافت، اما آن‌ها بخش کلیدی سامانهٔ مالکیت Rust هستند: Rust به‌شدت اعمال می‌کند که در هر لحظه برای یک مقدار فقط می‌توانید یک ارجاع تغییرپذیر یا چند ارجاع غیرتغییرپذیر داشته باشید.

    در عمل این یعنی باید بیشتر دقت کنید که آیا به دسترسی تغییرپذیر به داده نیاز دارید یا نه: در C حالت پیش‌فرض تغییرپذیر است و باید const را صریحاً بنویسید، اما در Rust برعکس است.

    یک وضعیت که هنوز ممکن است از اشاره‌گرهای خام استفاده کنید، تعامل مستقیم با سخت‌افزار است (برای مثال نوشتن اشاره‌گر به یک بافر درون ثبات یک پیرامونی DMA)، و همچنین آن‌ها در پشت صحنهٔ همهٔ crateهای دسترسی به پیرامونی به کار می‌روند تا بتوانید ثبات‌های نگاشت‌شده به حافظه را بخوانید و بنویسید.

    دسترسی Volatile

    در C می‌توان متغیرهای منفرد را volatile علامت زد تا به کامپایلر بگوید مقدار متغیر ممکن است بین دسترسی‌ها تغییر کند. متغیرهای volatile معمولاً در زمینهٔ سیستم‌های نهفته برای ثبات‌های نگاشت‌شده به حافظه به کار می‌روند.

    در Rust به‌جای علامت‌زدن یک متغیر به‌عنوان volatile، از متدهای مشخصی برای دسترسی volatile استفاده می‌کنیم: core::ptr::read_volatile و core::ptr::write_volatile. این متدها یک *const T یا *mut T (اشاره‌گرهای خام، همان‌گونه که در بالا گفته شد) می‌گیرند و یک خواندن یا نوشتن volatile انجام می‌دهند.

    برای مثال، در C ممکن است چنین بنویسید:

    volatile bool signalled = false;

void ISR() {
    // Signal that the interrupt has occurred
    signalled = true;
}

void driver() {
    while(true) {
        // Sleep until signalled
        while(!signalled) { WFI(); }
        // Reset signalled indicator
        signalled = false;
        // Perform some task that was waiting for the interrupt
        run_task();
    }
}

    معادل آن در Rust در هر دسترسی از متدهای volatile استفاده می‌کند:

    static mut SIGNALLED: bool = false;

#[interrupt]
fn ISR() {
    // Signal that the interrupt has occurred
    // (In real code, you should consider a higher level primitive,
    //  such as an atomic type).
    unsafe { core::ptr::write_volatile(&mut SIGNALLED, true) };
}

fn driver() {
    loop {
        // Sleep until signalled
        while unsafe { !core::ptr::read_volatile(&SIGNALLED) } {}
        // Reset signalled indicator
        unsafe { core::ptr::write_volatile(&mut SIGNALLED, false) };
        // Perform some task that was waiting for the interrupt
        run_task();
    }
}

    چند نکته در نمونه کد بالا شایان توجه است:

    • می‌توانیم &mut SIGNALLED را به تابعی که *mut T می‌خواهد بدهیم، زیرا &mut T به‌طور خودکار به *mut T تبدیل می‌شود (و همین‌طور برای *const T)
    • برای متدهای read_volatile/write_volatile به بلوک‌های unsafe نیاز داریم، زیرا آن‌ها توابع unsafe هستند. مسئولیت اطمینان از استفادهٔ ایمن بر عهدهٔ برنامه‌نویس است: برای جزئیات بیشتر مستندات این متدها را ببینید.

    نیاز مستقیم به این توابع در کد شما نادر است، زیرا معمولاً کتابخانه‌های سطح بالاتر آن‌ها را برایتان مدیریت می‌کنند. برای پیرامونی‌های نگاشت‌شده به حافظه، crateهای دسترسی به پیرامونی دسترسی volatile را به‌طور خودکار پیاده‌سازی می‌کنند، و برای ابزارهای پایهٔ همروندی انتزاع‌های بهتری در دسترس است (فصل همروندی را ببینید).

    نوع‌های فشرده و ترازشده

    در C نهفته معمول است که به کامپایلر بگویند یک متغیر باید تراز (alignment) مشخصی داشته باشد یا یک struct باید به‌جای ترازشده، فشرده (packed) باشد، معمولاً برای برآورده‌کردن الزامات سخت‌افزار یا پروتکل.

    در Rust این موضوع با attribute به نام repr روی یک ساختار یا union کنترل می‌شود. نمایش پیش‌فرض هیچ تضمینی دربارهٔ چیدمان نمی‌دهد، بنابراین نباید برای کدی که با سخت‌افزار یا C تعامل دارد از آن استفاده کرد. کامپایلر ممکن است اعضای ساختار را بازچینی کند یا padding درج کند و این رفتار ممکن است با نسخه‌های آیندهٔ Rust تغییر کند.

    struct Foo {
    x: u16,
    y: u8,
    z: u16,
}

fn main() {
    let v = Foo { x: 0, y: 0, z: 0 };
    println!("{:p} {:p} {:p}", &v.x, &v.y, &v.z);
}

// 0x7ffecb3511d0 0x7ffecb3511d4 0x7ffecb3511d2
// Note ordering has been changed to x, z, y to improve packing.

    برای اطمینان از چیدمانی سازگار با C، از repr(C) استفاده کنید:

    #[repr(C)]
struct Foo {
    x: u16,
    y: u8,
    z: u16,
}

fn main() {
    let v = Foo { x: 0, y: 0, z: 0 };
    println!("{:p} {:p} {:p}", &v.x, &v.y, &v.z);
}

// 0x7fffd0d84c60 0x7fffd0d84c62 0x7fffd0d84c64
// Ordering is preserved and the layout will not change over time.
// `z` is two-byte aligned so a byte of padding exists between `y` and `z`.

    برای اطمینان از نمایش فشرده، از repr(packed) استفاده کنید:

    #[repr(packed)]
struct Foo {
    x: u16,
    y: u8,
    z: u16,
}

fn main() {
    let v = Foo { x: 0, y: 0, z: 0 };
    // References must always be aligned, so to check the addresses of the
    // struct's fields, we use `std::ptr::addr_of!()` to get a raw pointer
    // instead of just printing `&v.x`.
    let px = std::ptr::addr_of!(v.x);
    let py = std::ptr::addr_of!(v.y);
    let pz = std::ptr::addr_of!(v.z);
    println!("{:p} {:p} {:p}", px, py, pz);
}

// 0x7ffd33598490 0x7ffd33598492 0x7ffd33598493
// No padding has been inserted between `y` and `z`, so now `z` is unaligned.

    توجه کنید که استفاده از repr(packed) تراز نوع را نیز روی 1 تنظیم می‌کند.

    سرانجام، برای تعیین یک تراز مشخص از repr(align(n)) استفاده کنید، که n تعداد بایت‌هایی است که باید روی آن‌ها تراز شود (و باید توانی از دو باشد):

    #[repr(C)]
#[repr(align(4096))]
struct Foo {
    x: u16,
    y: u8,
    z: u16,
}

fn main() {
    let v = Foo { x: 0, y: 0, z: 0 };
    let u = Foo { x: 0, y: 0, z: 0 };
    println!("{:p} {:p} {:p}", &v.x, &v.y, &v.z);
    println!("{:p} {:p} {:p}", &u.x, &u.y, &u.z);
}

// 0x7ffec909a000 0x7ffec909a002 0x7ffec909a004
// 0x7ffec909b000 0x7ffec909b002 0x7ffec909b004
// The two instances `u` and `v` have been placed on 4096-byte alignments,
// evidenced by the `000` at the end of their addresses.

    توجه کنید که می‌توانیم repr(C) را با repr(align(n)) ترکیب کنیم تا چیدمانی ترازشده و سازگار با C به دست آوریم. ترکیب repr(align(n)) با repr(packed) مجاز نیست، زیرا repr(packed) تراز را روی 1 تنظیم می‌کند. همچنین مجاز نیست که یک نوع repr(packed) شامل یک نوع repr(align(n)) باشد.

    برای جزئیات بیشتر دربارهٔ چیدمان نوع‌ها، به فصل چیدمان نوع در مرجع Rust مراجعه کنید.
