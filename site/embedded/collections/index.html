    مجموعه‌ها

    سرانجام در برنامهٔ خود به ساختارهای داده‌ای پویا (که مجموعه یا collection هم نامیده می‌شوند) نیاز پیدا خواهید کرد. std مجموعه‌ای از collectionهای رایج را فراهم می‌کند: Vec، String، HashMap و غیره. همهٔ collectionهایی که در std پیاده‌سازی شده‌اند از یک تخصیص‌دهندهٔ سراسری حافظهٔ پویا (که هیپ یا heap هم نامیده می‌شود) استفاده می‌کنند.

    از آن‌جا که core طبق تعریف از تخصیص حافظه عاری است، این پیاده‌سازی‌ها در آن در دسترس نیستند، اما می‌توان آن‌ها را در crate به نام alloc یافت که همراه کامپایلر عرضه می‌شود.

    اگر به collection نیاز دارید، پیاده‌سازی مبتنی بر heap تنها گزینهٔ شما نیست. می‌توانید از collectionهای با ظرفیت ثابت نیز استفاده کنید؛ یکی از این پیاده‌سازی‌ها در crate به نام heapless یافت می‌شود.

    در این بخش این دو پیاده‌سازی را بررسی و با هم مقایسه می‌کنیم.

    استفاده از alloc

    crate به نام alloc همراه توزیع استاندارد Rust عرضه می‌شود. برای وارد کردن این crate می‌توانید آن را مستقیماً با use به کار ببرید، بدون آن‌که آن را به‌عنوان وابستگی در فایل Cargo.toml خود اعلام کنید.

    #![feature(alloc)]

extern crate alloc;

use alloc::vec::Vec;

    برای استفاده از هر مجموعه‌ای (collection)، ابتدا باید از attribute با نام global_allocator استفاده کنید تا تخصیص‌دهندهٔ سراسری‌ای را که برنامه‌تان به کار می‌برد تعریف کنید. لازم است تخصیص‌دهنده‌ای که انتخاب می‌کنید trait با نام GlobalAlloc را پیاده‌سازی کند.

    برای کامل بودن مطلب و مستقل نگه‌داشتن هرچه بیشتر این بخش، یک تخصیص‌دهندهٔ ساده از نوع اشاره‌گر bump پیاده‌سازی می‌کنیم و آن را به‌عنوان تخصیص‌دهندهٔ سراسری به کار می‌بریم. با این حال، قویاً توصیه می‌کنیم در برنامهٔ خود به‌جای این تخصیص‌دهنده از یک تخصیص‌دهندهٔ آزموده‌شده از crates.io استفاده کنید.

    // Bump pointer allocator implementation

use core::alloc::{GlobalAlloc, Layout};
use core::cell::UnsafeCell;
use core::ptr;

use cortex_m::interrupt;

// Bump pointer allocator for *single* core systems
struct BumpPointerAlloc {
    head: UnsafeCell<usize>,
    end: usize,
}

unsafe impl Sync for BumpPointerAlloc {}

unsafe impl GlobalAlloc for BumpPointerAlloc {
    unsafe fn alloc(&self, layout: Layout) -> *mut u8 {
        // `interrupt::free` is a critical section that makes our allocator safe
        // to use from within interrupts
        interrupt::free(|_| {
            let head = self.head.get();
            let size = layout.size();
            let align = layout.align();
            let align_mask = !(align - 1);

            // move start up to the next alignment boundary
            let start = (*head + align - 1) & align_mask;

            if start + size > self.end {
                // a null pointer signal an Out Of Memory condition
                ptr::null_mut()
            } else {
                *head = start + size;
                start as *mut u8
            }
        })
    }

    unsafe fn dealloc(&self, _: *mut u8, _: Layout) {
        // this allocator never deallocates memory
    }
}

// Declaration of the global memory allocator
// NOTE the user must ensure that the memory region `[0x2000_0100, 0x2000_0200]`
// is not used by other parts of the program
#[global_allocator]
static HEAP: BumpPointerAlloc = BumpPointerAlloc {
    head: UnsafeCell::new(0x2000_0100),
    end: 0x2000_0200,
};

    افزون بر انتخاب تخصیص‌دهندهٔ سراسری، کاربر باید با attribute ناپایدار alloc_error_handler مشخص کند که خطاهای کمبود حافظه (Out Of Memory یا OOM) چگونه مدیریت شوند.

    #![feature(alloc_error_handler)]

use cortex_m::asm;

#[alloc_error_handler]
fn on_oom(_layout: Layout) -> ! {
    asm::bkpt();

    loop {}
}

    وقتی همهٔ این موارد برقرار شد، کاربر سرانجام می‌تواند از مجموعه‌های موجود در alloc استفاده کند.

    #[entry]
fn main() -> ! {
    let mut xs = Vec::new();

    xs.push(42);
    assert!(xs.pop(), Some(42));

    loop {
        // ..
    }
}

    اگر از collectionهای crate به نام std استفاده کرده باشید، این‌ها برایتان آشنا خواهند بود، چون دقیقاً همان پیاده‌سازی هستند.

    استفاده از heapless

    heapless به هیچ راه‌اندازی‌ای نیاز ندارد، چون collectionهای آن به تخصیص‌دهندهٔ سراسری حافظه وابسته نیستند. کافی است collectionهای آن را با use وارد کنید و نمونه‌سازی‌شان کنید:

    // heapless version: v0.4.x
use heapless::Vec;
use heapless::consts::*;

#[entry]
fn main() -> ! {
    let mut xs: Vec<_, U8> = Vec::new();

    xs.push(42).unwrap();
    assert_eq!(xs.pop(), Some(42));
    loop {}
}

    دو تفاوت میان این collectionها و collectionهای alloc را متوجه خواهید شد.

    نخست، باید ظرفیت collection را از قبل اعلام کنید. collectionهای heapless هرگز تخصیص مجدد نمی‌شوند و ظرفیت ثابت دارند؛ این ظرفیت بخشی از امضای نوع collection است. در این مثال اعلام کرده‌ایم که xs ظرفیت 8 عنصر دارد، یعنی بردار حداکثر می‌تواند 8 عنصر نگه دارد. این موضوع با U8 (به typenum نگاه کنید) در امضای نوع نشان داده می‌شود.

    دوم، متد push و بسیاری از متدهای دیگر یک Result برمی‌گردانند. از آن‌جا که collectionهای heapless ظرفیت ثابت دارند، همهٔ عملیاتی که عنصری را به collection اضافه می‌کنند ممکن است شکست بخورند. API این مشکل را با برگرداندن یک Result بازتاب می‌دهد که نشان می‌دهد عملیات موفق بوده یا نه. در مقابل، collectionهای alloc برای افزایش ظرفیت خود را روی heap تخصیص مجدد می‌کنند.

    از نسخهٔ v0.4.x به بعد، همهٔ collectionهای heapless همهٔ عناصر خود را به‌صورت درون‌خطی (inline) ذخیره می‌کنند. این یعنی عملیاتی مانند let x = heapless::Vec::new(); collection را روی پشته (stack) تخصیص می‌دهد، اما می‌توان collection را روی یک متغیر static یا حتی روی heap (Box<Vec<_, _>>) نیز تخصیص داد.

    مبادله‌ها

    هنگام انتخاب میان collectionهای تخصیص‌یافته روی heap و جابه‌جاپذیر (relocatable) و collectionهای با ظرفیت ثابت، این نکات را در نظر داشته باشید.

    کمبود حافظه و مدیریت خطا

    در تخصیص‌های heap، کمبود حافظه (Out Of Memory) همیشه یک امکان است و می‌تواند در هر جایی رخ دهد که یک collection ممکن است نیاز به رشد پیدا کند: برای مثال، همهٔ فراخوانی‌های alloc::Vec.push به‌طور بالقوه می‌توانند وضعیت OOM ایجاد کنند. بنابراین برخی عملیات می‌توانند به‌طور ضمنی شکست بخورند. برخی collectionهای alloc متدهای try_reserve را ارائه می‌دهند که به شما اجازه می‌دهند هنگام رشد collection وضعیت‌های بالقوهٔ OOM را بررسی کنید، اما باید در استفاده از آن‌ها پیش‌دستانه عمل کنید.

    اگر فقط از collectionهای heapless استفاده کنید و از تخصیص‌دهندهٔ حافظه برای هیچ کار دیگری استفاده نکنید، وضعیت OOM غیرممکن است. در عوض باید موضوع تمام‌شدن ظرفیت collectionها را مورد به مورد مدیریت کنید. یعنی باید با همهٔ Resultهایی که متدهایی مانند Vec.push برمی‌گردانند سروکار داشته باشید.

    اشکال‌زدایی خطاهای OOM می‌تواند دشوارتر از مثلاً unwrap کردن همهٔ Resultهایی باشد که heapless::Vec.push برمی‌گرداند، چون محل مشاهده‌شدهٔ خطا ممکن است با محل علت مشکل مطابقت نداشته باشد. برای مثال، حتی vec.reserve(1) هم می‌تواند OOM ایجاد کند اگر تخصیص‌دهنده تقریباً تمام شده باشد، چون collection دیگری حافظه را نشت داده است (نشت حافظه در Rust ایمن هم ممکن است).

    مصرف حافظه

    استدلال دربارهٔ مصرف حافظهٔ collectionهای تخصیص‌یافته روی heap دشوار است، چون ظرفیت collectionهای بلندعمر می‌تواند در زمان اجرا تغییر کند. برخی عملیات ممکن است collection را به‌طور ضمنی تخصیص مجدد کنند و مصرف حافظه‌اش را افزایش دهند، و برخی collectionها متدهایی مانند shrink_to_fit را ارائه می‌دهند که به‌طور بالقوه می‌توانند حافظهٔ مصرفی collection را کاهش دهند – در نهایت تخصیص‌دهنده تصمیم می‌گیرد که واقعاً تخصیص حافظه را کوچک کند یا نه. افزون بر این، ممکن است تخصیص‌دهنده مجبور شود با تکه‌تکه‌شدن حافظه (fragmentation) کنار بیاید که می‌تواند مصرف حافظهٔ ظاهری را افزایش دهد.

    از سوی دیگر، اگر فقط از collectionهای با ظرفیت ثابت استفاده کنید، بیشتر آن‌ها را در متغیرهای static نگه دارید و حداکثر اندازه‌ای برای پشتهٔ فراخوانی (call stack) تعیین کنید، آن‌گاه لینکر تشخیص خواهد داد که آیا می‌کوشید از حافظه‌ای بیش از آنچه به‌طور فیزیکی در دسترس است استفاده کنید.

    افزون بر این، collectionهای با ظرفیت ثابتی که روی stack تخصیص یافته‌اند با پرچم -Z emit-stack-sizes گزارش می‌شوند، یعنی ابزارهایی که مصرف stack را تحلیل می‌کنند (مانند stack-sizes) آن‌ها را در تحلیل خود لحاظ خواهند کرد.

    با این حال، collectionهای با ظرفیت ثابت را نمی‌توان کوچک کرد، که می‌تواند به ضرایب بار (load factor؛ نسبت اندازهٔ collection به ظرفیتش) پایین‌تری نسبت به آنچه collectionهای جابه‌جاپذیر به دست می‌آورند بینجامد.

    بدترین زمان اجرا (WCET)

    اگر برنامه‌های حساس به زمان یا برنامه‌های بی‌درنگ سخت (hard real time) می‌سازید، آن‌گاه شاید بسیار به بدترین زمان اجرای بخش‌های مختلف برنامه‌تان اهمیت می‌دهید.

    collectionهای alloc می‌توانند تخصیص مجدد شوند، بنابراین WCET عملیاتی که ممکن است collection را رشد دهند زمان تخصیص مجدد collection را نیز شامل می‌شود، که خودش به ظرفیت زمان اجرای collection بستگی دارد. این موضوع تعیین WCET عملیاتی مانند alloc::Vec.push را دشوار می‌کند، چون هم به تخصیص‌دهندهٔ مورد استفاده و هم به ظرفیت زمان اجرای آن بستگی دارد.

    از سوی دیگر، collectionهای با ظرفیت ثابت هرگز تخصیص مجدد نمی‌شوند، بنابراین همهٔ عملیات زمان اجرای قابل پیش‌بینی دارند. برای مثال، heapless::Vec.push در زمان ثابت اجرا می‌شود.

    سهولت استفاده

    alloc نیاز به راه‌اندازی یک تخصیص‌دهندهٔ سراسری دارد، در حالی که heapless ندارد. با این حال، heapless از شما می‌خواهد ظرفیت هر collection را که نمونه‌سازی می‌کنید انتخاب کنید.

    API مربوط به alloc تقریباً برای هر توسعه‌دهندهٔ Rust آشناست. API مربوط به heapless می‌کوشد از نزدیک از API مربوط به alloc تقلید کند، اما به‌دلیل مدیریت صریح خطا هرگز دقیقاً مثل آن نخواهد بود – ممکن است برخی توسعه‌دهندگان احساس کنند مدیریت صریح خطا زیاده‌روی یا بیش از حد دست‌وپاگیر است.
