    استثناها

    استثناها (exception) و وقفه‌ها (interrupt) سازوکاری سخت‌افزاری‌اند که پردازنده به کمک آن رویدادهای ناهمگام و خطاهای مهلک (مثلاً اجرای یک دستور نامعتبر) را مدیریت می‌کند. استثنا مستلزم پیش‌دستی (preemption) است و شامل کنترل‌گرهای استثنا می‌شود؛ زیرروال‌هایی که در پاسخ به سیگنالی که رویداد را برانگیخته است اجرا می‌شوند.

    crate با نام cortex-m-rt یک attribute به نام exception برای تعریف کنترل‌گرهای استثنا (exception handlers) فراهم می‌کند.

    // Exception handler for the SysTick (System Timer) exception
#[exception]
fn SysTick() {
    // ..
}

    جدا از attribute با نام exception، کنترل‌گرهای استثنا شبیه تابع‌های معمولی‌اند، اما یک تفاوت دیگر هم وجود دارد: کنترل‌گرهای exception را نرم‌افزار نمی‌تواند فراخوانی کند. با ادامهٔ مثال قبلی، دستور SysTick(); به خطای کامپایل می‌انجامد.

    این رفتار تقریباً عمدی است و برای فراهم کردن یک قابلیت لازم است: متغیرهای static mut که داخل کنترل‌گرهای exception تعریف می‌شوند، استفادهٔ امن دارند.

    #[exception]
fn SysTick() {
    static mut COUNT: u32 = 0;

    // `COUNT` has transformed to type `&mut u32` and it's safe to use
    *COUNT += 1;
}

    همان‌طور که شاید می‌دانید، استفاده از متغیرهای static mut در یک تابع آن را غیرقابل‌بازورود (non-reentrant) می‌کند. فراخوانی یک تابع غیرقابل‌بازورود، چه مستقیم و چه غیرمستقیم، از بیش از یک کنترل‌گر استثنا / وقفه، یا از main و یک یا چند کنترل‌گر استثنا / وقفه، رفتار تعریف‌نشده (undefined behavior) است.

    Rust ایمن هرگز نباید به رفتار تعریف‌نشده منجر شود، بنابراین توابع غیرقابل‌بازورود باید با unsafe علامت‌گذاری شوند. با این حال همین الان گفتم که کنترل‌گرهای exception می‌توانند به‌صورت ایمن از متغیرهای static mut استفاده کنند. این چگونه ممکن است؟ ممکن است چون کنترل‌گرهای exception را نمی‌توان از سوی نرم‌افزار فراخوانی کرد و در نتیجه بازورود امکان‌پذیر نیست. این کنترل‌گرها را خود سخت‌افزار فراخوانی می‌کند که فرض می‌شود از نظر فیزیکی غیرهمروند است.

    در نتیجه، در بافت کنترل‌گرهای استثنا در سیستم‌های توکار، نبودِ فراخوانی‌های همروند از یک کنترل‌گر واحد تضمین می‌کند که مشکل بازورود پیش نمی‌آید، حتی اگر کنترل‌گر از متغیرهای ایستای تغییرپذیر استفاده کند.

    در یک سیستم چندهسته‌ای، که در آن چند هستهٔ پردازنده کد را به‌طور همزمان اجرا می‌کنند، احتمال بروز مشکلات بازورود دوباره اهمیت پیدا می‌کند، حتی درون کنترل‌گرهای استثنا. هر هسته ممکن است مجموعهٔ کنترل‌گرهای استثنای خودش را داشته باشد، اما همچنان ممکن است سناریوهایی پیش بیاید که در آن چند هسته بخواهند همزمان یک کنترل‌گر استثنای یکسان را اجرا کنند. برای رفع این نگرانی در محیط چندهسته‌ای، باید درون کنترل‌گرهای استثنا از سازوکارهای همگام‌سازی مناسب استفاده کرد تا دسترسی به منابع مشترک بین هسته‌ها به‌درستی هماهنگ شود. این کار معمولاً شامل استفاده از تکنیک‌هایی مانند قفل‌ها (lock)، سمافورها (semaphore) یا عملیات اتمی (atomic) است تا از رقابت داده‌ای (data race) جلوگیری شود و یکپارچگی داده حفظ گردد.

    توجه کنید که attribute با نام exception تعریف متغیرهای ایستا درون تابع را تغییر می‌دهد: آن‌ها را درون بلوک‌های unsafe قرار می‌دهد و متغیرهای جدید و مناسبی از نوع &mut با همان نام در اختیار ما می‌گذارد. بنابراین می‌توانیم با * ارجاع را از ارجاع‌زدایی کنیم و به مقدار متغیرها دسترسی پیدا کنیم، بدون آنکه نیازی به قرار دادن آن‌ها در یک بلوک unsafe باشد.

    یک مثال کامل

    مثال زیر از تایمر سیستم استفاده می‌کند تا تقریباً هر ثانیه یک استثنای SysTick ایجاد کند. کنترل‌گر استثنای SysTick در متغیر COUNT نگه می‌دارد که چند بار فراخوانی شده است و سپس مقدار COUNT را با semihosting روی کنسول میزبان چاپ می‌کند.

    توجه: می‌توانید این مثال را روی هر دستگاه Cortex-M اجرا کنید؛ همچنین می‌توانید آن را روی QEMU اجرا کنید.

    #![deny(unsafe_code)]
#![no_main]
#![no_std]

use panic_halt as _;

use core::fmt::Write;

use cortex_m::peripheral::syst::SystClkSource;
use cortex_m_rt::{entry, exception};
use cortex_m_semihosting::{
    debug,
    hio::{self, HostStream},
};

#[entry]
fn main() -> ! {
    let p = cortex_m::Peripherals::take().unwrap();
    let mut syst = p.SYST;

    // configures the system timer to trigger a SysTick exception every second
    syst.set_clock_source(SystClkSource::Core);
    // this is configured for the LM3S6965 which has a default CPU clock of 12 MHz
    syst.set_reload(12_000_000);
    syst.clear_current();
    syst.enable_counter();
    syst.enable_interrupt();

    loop {}
}

#[exception]
fn SysTick() {
    static mut COUNT: u32 = 0;
    static mut STDOUT: Option<HostStream> = None;

    *COUNT += 1;

    // Lazy initialization
    if STDOUT.is_none() {
        *STDOUT = hio::hstdout().ok();
    }

    if let Some(hstdout) = STDOUT.as_mut() {
        write!(hstdout, "{}", *COUNT).ok();
    }

    // IMPORTANT omit this `if` block if running on real hardware or your
    // debugger will end in an inconsistent state
    if *COUNT == 9 {
        // This will terminate the QEMU process
        debug::exit(debug::EXIT_SUCCESS);
    }
}

    کنترل‌گر پیش‌فرض استثنا

    کاری که attribute با نام exception در واقع انجام می‌دهد، بازنویسی (override) کنترل‌گر پیش‌فرض استثنا برای یک استثنای مشخص است. اگر کنترل‌گر یک استثنای خاص را بازنویسی نکنید، آن استثنا را تابع DefaultHandler مدیریت می‌کند که به‌طور پیش‌فرض چنین است:

    fn DefaultHandler() {
    loop {}
}

    این تابع را crate با نام cortex-m-rt فراهم می‌کند و با #[no_mangle] علامت‌گذاری شده است، بنابراین می‌توانید روی «DefaultHandler» یک نقطهٔ توقف (breakpoint) بگذارید و استثناهای رسیدگی‌نشده را بگیرید.

    می‌توان این DefaultHandler را با attribute با نام exception بازنویسی (override) کرد:

    #[exception]
fn DefaultHandler(irqn: i16) {
    // custom default handler
}

    آرگومان irqn نشان می‌دهد کدام استثنا در حال سرویس‌دهی است. مقدار منفی نشان می‌دهد که یک استثنای Cortex-M در حال سرویس‌دهی است؛ و مقدار صفر یا مثبت نشان می‌دهد که یک استثنای مختص دستگاه، که به آن وقفه (interrupt) هم می‌گویند، در حال سرویس‌دهی است.

    کنترل‌گر hard fault

    استثنای HardFault کمی خاص است. این استثنا وقتی رخ می‌دهد که برنامه وارد یک حالت نامعتبر شود، بنابراین کنترل‌گر آن نمی‌تواند برگردد، چون این کار می‌تواند به رفتار تعریف‌نشده منجر شود. همچنین crate مربوط به runtime پیش از فراخوانی کنترل‌گر HardFault که کاربر تعریف کرده است کمی کار انجام می‌دهد تا قابلیت اشکال‌زدایی بهتر شود.

    نتیجه این است که کنترل‌گر HardFault باید امضای زیر را داشته باشد: fn(&ExceptionFrame) -> !. آرگومان کنترل‌گر اشاره‌گری به ثبات‌هایی است که استثنا آن‌ها را روی پشته push کرده است. این ثبات‌ها تصویری لحظه‌ای از وضعیت پردازنده در لحظهٔ برانگیخته شدن استثنا هستند و برای تشخیص hard fault مفیدند.

    در اینجا مثالی می‌بینید که یک عملیات غیرمجاز انجام می‌دهد: خواندن از یک مکان حافظهٔ ناموجود.

    توجه: این برنامه روی QEMU کار نمی‌کند، یعنی خراب (crash) نمی‌شود، چون qemu-system-arm -machine lm3s6965evb بارگذاری‌های حافظه را بررسی نمی‌کند و با کمال میل در خواندن از حافظهٔ نامعتبر مقدار 0 را برمی‌گرداند.

    #![no_main]
#![no_std]

use panic_halt as _;

use core::fmt::Write;
use core::ptr;

use cortex_m_rt::{entry, exception, ExceptionFrame};
use cortex_m_semihosting::hio;

#[entry]
fn main() -> ! {
    // read a nonexistent memory location
    unsafe {
        ptr::read_volatile(0x3FFF_0000 as *const u32);
    }

    loop {}
}

#[exception]
fn HardFault(ef: &ExceptionFrame) -> ! {
    if let Ok(mut hstdout) = hio::hstdout() {
        writeln!(hstdout, "{:#?}", ef).ok();
    }

    loop {}
}

    کنترل‌گر HardFault مقدار ExceptionFrame را چاپ می‌کند. اگر این برنامه را اجرا کنید، چیزی شبیه این را در کنسول OpenOCD خواهید دید.

    مقدار pc مقدار شمارندهٔ برنامه (Program Counter) در لحظهٔ وقوع استثنا است و به دستورالعملی اشاره می‌کند که استثنا را برانگیخته است.

    اگر به کد اسمبلی (disassembly) برنامه نگاه کنید:

    $ cargo objdump --bin app --release -- -d --no-show-raw-insn --print-imm-hex
(..)
ResetTrampoline:

    می‌توانید مقدار شمارندهٔ برنامه یعنی 0x0800094a را در disassembly جست‌وجو کنید. خواهید دید که یک عملیات بارگذاری (ldr r0, [r0] ) استثنا را ایجاد کرده است. فیلد r0 در ExceptionFrame به شما می‌گوید مقدار ثبات r0 در آن زمان 0x3fff_fffe بوده است.
