    سخت‌افزار

    تا اینجا باید با ابزارها و فرایند توسعه تا حدی آشنا شده باشید. در این بخش به سخت‌افزار واقعی می‌رویم؛ فرایند کار تقریباً همان می‌ماند. بیایید شروع کنیم.

    سخت‌افزار خود را بشناسید

    پیش از شروع، باید چند ویژگی دستگاه هدف را مشخص کنید، چون از آن‌ها برای پیکربندی پروژه استفاده می‌شود:

    • هستهٔ ARM، مثلاً Cortex-M3.

    • آیا هستهٔ ARM شامل FPU است؟ هسته‌های Cortex-M4F و Cortex-M7F دارند.

    • دستگاه هدف چقدر حافظهٔ Flash و RAM دارد؟ مثلاً 256 KiB حافظهٔ Flash و 32 KiB حافظهٔ RAM.

    • حافظهٔ Flash و RAM در کجای فضای آدرس نگاشت شده‌اند؟ مثلاً RAM معمولاً در آدرس 0x2000_0000 قرار دارد.

    این اطلاعات را در برگهٔ داده (data sheet) یا راهنمای مرجع (reference manual) دستگاه خود پیدا می‌کنید.

    در این بخش از سخت‌افزار مرجع خودمان، یعنی STM32F3DISCOVERY، استفاده می‌کنیم. این برد یک میکروکنترلر STM32F303VCT6 دارد. این میکروکنترلر این مشخصات را دارد:

    • یک هستهٔ Cortex-M4F که شامل یک FPU با دقت یگانه (single precision) است

    • 256 KiB حافظهٔ Flash در آدرس 0x0800_0000.

    • 40 KiB حافظهٔ RAM در آدرس 0x2000_0000. (ناحیهٔ RAM دیگری هم هست، اما برای سادگی آن را نادیده می‌گیریم.)

    پیکربندی

    کار را از صفر و با یک نمونهٔ تازه از قالب شروع می‌کنیم. برای مرور این‌که چطور بدون cargo-generate این کار را انجام دهید، به بخش قبلی دربارهٔ QEMU مراجعه کنید.

    $ cargo generate --git https://github.com/rust-embedded/cortex-m-quickstart
 Project Name: app
 Creating project called `app`...
 Done! New project created /tmp/app

$ cd app

    گام اول، تعیین یک هدف کامپایل پیش‌فرض در .cargo/config.toml است.

    tail -n5 .cargo/config.toml

    # Pick ONE of these compilation targets
# target = "thumbv6m-none-eabi"    # Cortex-M0 and Cortex-M0+
# target = "thumbv7m-none-eabi"    # Cortex-M3
# target = "thumbv7em-none-eabi"   # Cortex-M4 and Cortex-M7 (no FPU)
target = "thumbv7em-none-eabihf" # Cortex-M4F and Cortex-M7F (with FPU)

    ما از thumbv7em-none-eabihf استفاده می‌کنیم، چون هستهٔ Cortex-M4F را پوشش می‌دهد.

    توجه: همان‌طور که شاید از فصل قبل به یاد داشته باشید، باید همهٔ هدف‌ها را نصب کنیم و این یکی جدید است. پس فراموش نکنید که برای این هدف فرایند نصب rustup target add thumbv7em-none-eabihf را اجرا کنید.

    گام دوم، وارد کردن اطلاعات ناحیهٔ حافظه در فایل memory.x است.

    $ cat memory.x
/* Linker script for the STM32F303VCT6 */
MEMORY
{
  /* NOTE 1 K = 1 KiBi = 1024 bytes */
  FLASH : ORIGIN = 0x08000000, LENGTH = 256K
  RAM : ORIGIN = 0x20000000, LENGTH = 40K
}

    توجه: اگر به هر دلیلی فایل memory.x را بعد از اولین ساخت برای یک هدف ساخت مشخص تغییر دادید، پیش از cargo build دستور cargo clean را اجرا کنید، چون ممکن است cargo build تغییرات memory.x را دنبال نکند.

    دوباره با مثال hello شروع می‌کنیم، اما ابتدا باید یک تغییر کوچک بدهیم.

    در examples/hello.rs، مطمئن شوید فراخوانی debug::exit() به‌صورت توضیح درآمده یا حذف شده باشد. این فراخوانی فقط برای اجرا روی QEMU به کار می‌رود.

    #[entry]
fn main() -> ! {
    hprintln!("Hello, world!").unwrap();

    // exit QEMU
    // NOTE do not run this on hardware; it can corrupt OpenOCD state
    // debug::exit(debug::EXIT_SUCCESS);

    loop {}
}

    اکنون می‌توانید برنامه‌ها را با cargo build برای معماری دیگر کامپایل متقابل (cross compile) کنید و مثل قبل با cargo-binutils فایل‌های دودویی را بررسی کنید. crate با نام cortex-m-rt همهٔ جادوی لازم برای راه‌اندازی تراشهٔ شما را انجام می‌دهد، چون تقریباً همهٔ پردازنده‌های Cortex-M به یک شیوه بوت می‌شوند.

    cargo build --example hello

    اشکال‌زدایی

    اشکال‌زدایی کمی متفاوت به نظر می‌رسد. در واقع گام‌های اول هم بسته به دستگاه هدف می‌توانند متفاوت باشند. در این بخش گام‌های لازم برای اشکال‌زدایی برنامه‌ای را که روی STM32F3DISCOVERY اجرا می‌شود نشان می‌دهیم. این بخش فقط به‌عنوان مرجع در نظر گرفته شده است؛ برای اطلاعات مختص دستگاه دربارهٔ اشکال‌زدایی، Debugonomicon را ببینید.

    مثل قبل اشکال‌زدایی از راه دور انجام می‌دهیم و کلاینت یک فرایند GDB خواهد بود. اما این بار سرور OpenOCD است.

    همان‌طور که در بخش تأیید نصب انجام دادید، برد discovery را به لپ‌تاپ / رایانهٔ خود وصل کنید و بررسی کنید که هدر ST-LINK لحیم شده باشد.

    در یک ترمینال openocd را اجرا کنید تا به ST-LINK روی برد discovery وصل شود. این دستور را از ریشهٔ قالب اجرا کنید؛ openocd فایل openocd.cfg را برمی‌دارد که مشخص می‌کند از کدام فایل interface و کدام فایل target استفاده شود.

    cat openocd.cfg

    # Sample OpenOCD configuration for the STM32F3DISCOVERY development board

# Depending on the hardware revision you got you'll have to pick ONE of these
# interfaces. At any time only one interface should be commented out.

# Revision C (newer revision)
source [find interface/stlink.cfg]

# Revision A and B (older revisions)
# source [find interface/stlink-v2.cfg]

source [find target/stm32f3x.cfg]

    توجه: اگر در بخش تأیید نصب متوجه شدید که برد discovery شما نسخهٔ قدیمی‌تری است، باید در این مرحله فایل openocd.cfg را تغییر دهید تا از interface/stlink-v2.cfg استفاده کند.

    در ترمینال دیگری GDB را اجرا کنید، آن هم از ریشهٔ قالب.

    gdb-multiarch -q target/thumbv7em-none-eabihf/debug/examples/hello

    توجه: مثل قبل، بسته به این‌که در فصل نصب کدام نسخهٔ gdb را نصب کرده‌اید، ممکن است به‌جای gdb-multiarch به نسخهٔ دیگری از gdb نیاز داشته باشید. این نسخه می‌تواند arm-none-eabi-gdb یا فقط gdb هم باشد.

    سپس GDB را به OpenOCD وصل کنید؛ OpenOCD روی پورت 3333 منتظر یک اتصال TCP است.

    (gdb) target remote :3333
Remote debugging using :3333
0x00000000 in ?? ()

    حالا با دستور load برنامه را روی میکروکنترلر فلش (بارگذاری) کنید.

    (gdb) load
Loading section .vector_table, size 0x400 lma 0x8000000
Loading section .text, size 0x1518 lma 0x8000400
Loading section .rodata, size 0x414 lma 0x8001918
Start address 0x08000400, load size 7468
Transfer rate: 13 KB/sec, 2489 bytes/write.

    برنامه اکنون بارگذاری شده است. این برنامه از semihosting استفاده می‌کند، بنابراین پیش از هر فراخوانی semihosting باید به OpenOCD بگوییم semihosting را فعال کند. با دستور monitor می‌توانید به OpenOCD دستور بفرستید.

    (gdb) monitor arm semihosting enable
semihosting is enabled

    با اجرای دستور monitor help می‌توانید همهٔ دستورهای OpenOCD را ببینید.

    مثل قبل می‌توانیم با یک breakpoint و دستور continue مستقیم به main برویم.

    (gdb) break main
Breakpoint 1 at 0x8000490: file examples/hello.rs, line 11.
Note: automatically using hardware breakpoints for read-only addresses.

(gdb) continue
Continuing.

Breakpoint 1, hello::__cortex_m_rt_main_trampoline () at examples/hello.rs:11
11      #[entry]

    توجه: اگر پس از اجرای دستور continue بالا، GDB به‌جای رسیدن به breakpoint ترمینال را مسدود کرد، بهتر است دوباره بررسی کنید که اطلاعات ناحیهٔ حافظه در فایل memory.x برای دستگاه شما درست تنظیم شده باشد (هم آغاز و هم طول ناحیه‌ها).

    با step وارد تابع main شوید.

    (gdb) step
halted: PC: 0x08000496
hello::__cortex_m_rt_main () at examples/hello.rs:13
13          hprintln!("Hello, world!").unwrap();

    پیام فقط یک بار نمایش داده می‌شود، چون برنامه در شرف ورود به حلقهٔ بی‌نهایتی است که در خط 19 تعریف شده است: loop {}

    اکنون می‌توانید با دستور quit از GDB خارج شوید.

    (gdb) quit

    اشکال‌زدایی اکنون به چند گام بیشتر نیاز دارد، به همین دلیل همهٔ آن گام‌ها را در یک اسکریپت GDB به نام openocd.gdb گردآوری کرده‌ایم. این فایل در مرحلهٔ cargo generate ساخته شده است و باید بدون هیچ تغییری کار کند. بیایید نگاهی به آن بیندازیم:

    cat openocd.gdb

    target extended-remote :3333

# print demangled symbols
set print asm-demangle on

# detect unhandled exceptions, hard faults and panics
break DefaultHandler
break HardFault
break rust_begin_unwind

monitor arm semihosting enable

load

# start the process but immediately halt the processor
stepi

    اکنون اجرای <gdb> -x openocd.gdb target/thumbv7em-none-eabihf/debug/examples/hello بلافاصله GDB را به OpenOCD وصل می‌کند، semihosting را فعال می‌کند، برنامه را بارگذاری می‌کند و فرایند را شروع می‌کند.

    از طرف دیگر، می‌توانید <gdb> -x openocd.gdb را به یک runner سفارشی تبدیل کنید تا cargo run هم برنامه را بسازد و هم یک نشست GDB را شروع کند. این runner در .cargo/config.toml گنجانده شده است، اما به‌صورت توضیح درآمده است.

    head -n10 .cargo/config.toml

    [target.thumbv7m-none-eabi]
# uncomment this to make `cargo run` execute programs on QEMU
# runner = "qemu-system-arm -cpu cortex-m3 -machine lm3s6965evb -nographic -semihosting-config enable=on,target=native -kernel"

[target.'cfg(all(target_arch = "arm", target_os = "none"))']
# uncomment ONE of these three option to make `cargo run` start a GDB session
# which option to pick depends on your system
runner = "arm-none-eabi-gdb -x openocd.gdb"
# runner = "gdb-multiarch -x openocd.gdb"
# runner = "gdb -x openocd.gdb"

    $ cargo run --example hello
