    QEMU

    نوشتن برنامه‌ای برای LM3S6965، یک میکروکنترلر Cortex-M3، را شروع می‌کنیم. این را به‌عنوان هدف اولیهٔ خود برگزیده‌ایم، چون با QEMU قابل شبیه‌سازی است؛ بنابراین در این بخش لازم نیست با سخت‌افزار سروکله بزنید و می‌توانیم روی ابزارها و فرایند توسعه تمرکز کنیم.

    مهم در این آموزش از نام «app» برای نام پروژه استفاده می‌کنیم. هر جا واژهٔ «app» را دیدید، باید آن را با نامی که برای پروژهٔ خود انتخاب کرده‌اید جایگزین کنید. یا می‌توانید پروژهٔ خود را هم «app» نام‌گذاری کنید و از این جایگزینی‌ها بی‌نیاز شوید.

    ساخت یک برنامهٔ Rust غیراستاندارد

    از قالب پروژهٔ cortex-m-quickstart برای تولید یک پروژهٔ جدید استفاده می‌کنیم. پروژهٔ ساخته‌شده یک برنامهٔ حداقلی (barebone) خواهد داشت: نقطهٔ شروع خوبی برای یک برنامهٔ جدید Rust توکار. افزون بر این، پروژه یک پوشهٔ examples دارد که چند برنامهٔ مجزا در آن هست و برخی از قابلیت‌های کلیدی Rust توکار را برجسته می‌کنند.

    استفاده از cargo-generate

    ابتدا cargo-generate را نصب کنید

    cargo install cargo-generate

    سپس یک پروژهٔ جدید تولید کنید

    cargo generate --git https://github.com/knurling-rs/app-template

     Project Name: app
 Creating project called `app`...
 Done! New project created /tmp/app

    cd app

    استفاده از git

    مخزن را کلون کنید

    git clone https://github.com/rust-embedded/cortex-m-quickstart app
cd app

    و سپس جاینگهدارها (placeholder) را در فایل Cargo.toml پر کنید

    [package]
authors = ["{{authors}}"] # "{{authors}}" -> "John Smith"
edition = "2018"
name = "{{project-name}}" # "{{project-name}}" -> "app"
version = "0.1.0"

# ..

[[bin]]
name = "{{project-name}}" # "{{project-name}}" -> "app"
test = false
bench = false

    استفاده از هیچ‌کدام

    آخرین نسخهٔ لحظه‌ای (snapshot) قالب cortex-m-quickstart را بگیرید و از حالت فشرده خارج کنید.

    curl -LO https://github.com/rust-embedded/cortex-m-quickstart/archive/master.zip
unzip master.zip
mv cortex-m-quickstart-master app
cd app

    یا می‌توانید به cortex-m-quickstart بروید، روی دکمهٔ سبز «Clone or download» کلیک کنید و سپس روی «Download ZIP» کلیک کنید.

    سپس جاینگهدارها را در فایل Cargo.toml پر کنید، همان‌طور که در بخش دوم نسخهٔ «استفاده از git» انجام شد.

    مروری بر برنامه

    برای راحتی، مهم‌ترین بخش‌های کد منبع در src/main.rs این‌ها هستند:

    #![no_std]
#![no_main]

use panic_halt as _;

use cortex_m_rt::entry;

#[entry]
fn main() -> ! {
    loop {
        // your code goes here
    }
}

    این برنامه با یک برنامهٔ استاندارد Rust کمی تفاوت دارد، پس بیایید دقیق‌تر نگاهی به آن بیندازیم.

    #![no_std] نشان می‌دهد که این برنامه به crate استاندارد، یعنی std، پیوند نمی‌خورد. در عوض به زیرمجموعهٔ آن، یعنی crate با نام core، پیوند می‌خورد.

    #![no_main] نشان می‌دهد که این برنامه از رابط main استانداردی که بیشتر برنامه‌های Rust استفاده می‌کنند بهره نمی‌برد. دلیل اصلی انتخاب no_main (بدون قصد جناس) این است که استفاده از رابط main در بافت no_std به nightly نیاز دارد.

    use panic_halt as _;. این crate یک panic_handler فراهم می‌کند که رفتار panic برنامه را تعریف می‌کند. این موضوع را در فصل Panic این کتاب با جزئیات بیشتری بررسی می‌کنیم.

    #[entry] یک attribute است که crate با نام cortex-m-rt فراهم می‌کند و برای علامت‌گذاری نقطهٔ ورود برنامه به کار می‌رود. چون از main استاندارد استفاده نمی‌کنیم، به راه دیگری برای مشخص کردن نقطهٔ ورود برنامه نیاز داریم، و آن #[entry] است.

    fn main() -> !. برنامهٔ ما تنها فرایندی خواهد بود که روی سخت‌افزار هدف اجرا می‌شود، پس نمی‌خواهیم تمام شود! از یک تابع واگرا (بخش -> ! در امضای تابع) استفاده می‌کنیم تا در زمان کامپایل مطمئن شویم چنین خواهد بود.

    کامپایل متقابل

    پیش از هر چیز به چیدمان حافظهٔ میکروکنترلر هدف، که در اینجا LM3S6965 است، نیاز داریم. در غیر این صورت، ساخت در پیوند دادن image شکست می‌خورد. فایلی به نام memory.x را در ریشهٔ پروژه بسازید و محتوای زیر را در آن بچسبانید:

    MEMORY
{
  /* NOTE 1 K = 1 KiBi = 1024 bytes */
  /* TODO Adjust these memory regions to match your device memory layout */
  /* These values correspond to the LM3S6965, one of the few devices QEMU can emulate */
  FLASH : ORIGIN = 0x00000000, LENGTH = 256K
  RAM : ORIGIN = 0x20000000, LENGTH = 64K
}

/* This is where the call stack will be allocated. */
/* The stack is of the full descending type. */
/* You may want to use this variable to locate the call stack and static
   variables in different memory regions. Below is shown the default value */
/* _stack_start = ORIGIN(RAM) + LENGTH(RAM); */

/* You can use this symbol to customize the location of the .text section */
/* If omitted the .text section will be placed right after the .vector_table
   section */
/* This is required only on microcontrollers that store some configuration right
   after the vector table */
/* _stext = ORIGIN(FLASH) + 0x400; */

/* Example of putting non-initialized variables into custom RAM locations. */
/* This assumes you have defined a region RAM2 above, and in the Rust
   sources added the attribute `#[link_section = ".ram2bss"]` to the data
   you want to place there. */
/* Note that the section will not be zero-initialized by the runtime! */
/* SECTIONS {
     .ram2bss (NOLOAD) : ALIGN(4) {
       *(.ram2bss);
       . = ALIGN(4);
     } > RAM2
   } INSERT AFTER .bss;
*/

    گام بعدی، کامپایل متقابل برنامه برای معماری Cortex-M3 است. اگر بدانید هدف کامپایل ($TRIPLE) چیست، این کار به سادگی اجرای cargo build --target $TRIPLE است. خوشبختانه فایل .cargo/config.toml در قالب پاسخ را دارد:

    tail -n6 .cargo/config.toml

    [build]
# Pick ONE of these compilation targets
# target = "thumbv6m-none-eabi"    # Cortex-M0 and Cortex-M0+
target = "thumbv7m-none-eabi"    # Cortex-M3
# target = "thumbv7em-none-eabi"   # Cortex-M4 and Cortex-M7 (no FPU)
# target = "thumbv7em-none-eabihf" # Cortex-M4F and Cortex-M7F (with FPU)

    برای کامپایل متقابل برای معماری Cortex-M3 باید از thumbv7m-none-eabi استفاده کنیم. این هدف هنگام نصب toolchain زبان Rust به‌طور خودکار نصب نمی‌شود؛ اگر هنوز این کار را نکرده‌اید، اکنون زمان خوبی است که این هدف را به toolchain اضافه کنید:

    rustup target add thumbv7m-none-eabi

    از آنجا که هدف کامپایل thumbv7m-none-eabi در فایل .cargo/config.toml شما به‌عنوان پیش‌فرض تنظیم شده است، دو دستور زیر یک کار را انجام می‌دهند:

    cargo build --target thumbv7m-none-eabi
cargo build

    بازرسی

    اکنون یک فایل دودویی ELF غیربومی (non-native) در target/thumbv7m-none-eabi/debug/app داریم. می‌توانیم آن را با cargo-binutils بازرسی کنیم.

    با cargo-readobj می‌توانیم سرایندهای ELF را چاپ کنیم تا تأیید کنیم این یک فایل دودویی ARM است.

    cargo readobj --bin app -- --file-headers

    • --bin app میان‌بُری است برای بازرسی فایل دودویی در target/$TRIPLE/debug/app

    مروری سریع بر بخش‌های پیوندگر ELF

    • .text شامل دستورهای برنامه است
    • .rodata شامل مقادیر ثابت مانند رشته‌ها است
    • .data شامل متغیرهای تخصیص‌یافتهٔ ایستا است که مقدار اولیه‌شان صفر نیست
    • .bss هم شامل متغیرهای تخصیص‌یافتهٔ ایستا است که مقدار اولیه‌شان صفر است
    • .vector_table بخشی غیراستاندارد است که برای نگهداری جدول بردار (وقفه) به کار می‌بریم
    • .ARM.attributes و بخش‌های .debug_* فراداده دارند و هنگام فلش کردن فایل دودویی روی هدف بارگذاری نمی‌شوند.

    مهم: فایل‌های ELF فراداده‌هایی مانند اطلاعات اشکال‌زدایی دارند، بنابراین اندازهٔ آن‌ها روی دیسک فضایی را که برنامه هنگام فلش شدن روی دستگاه اشغال می‌کند به‌درستی نشان نمی‌دهد. برای دانستن اندازهٔ واقعی یک فایل دودویی همیشه از cargo-size استفاده کنید.

    cargo-objdump را می‌توان برای دیس‌اسمبل کردن فایل دودویی به کار برد.

    cargo objdump --bin app --release -- --disassemble --no-show-raw-insn --print-imm-hex

    توجه: اگر دستور بالا دربارهٔ Unknown command line argument شکایت کرد، گزارش اشکال زیر را ببینید: https://github.com/rust-embedded/book/issues/269

    توجه: این خروجی ممکن است روی سیستم شما متفاوت باشد. نسخه‌های جدید rustc، LLVM و کتابخانه‌ها می‌توانند اسمبلی متفاوتی تولید کنند. برخی از دستورها را کوتاه کرده‌ایم تا قطعه کد کوچک بماند.

    اجرا

    در ادامه ببینیم چطور یک برنامهٔ توکار را روی QEMU اجرا کنیم! این بار از مثال hello استفاده می‌کنیم که واقعاً کاری انجام می‌دهد. به‌طور پیش‌فرض، این مثال برای چاپ متن از [defmt] و RTT استفاده می‌کند.

    توجه: defmt یک وابستگی شخص ثالث (یعنی غیرهسته‌ای) است که در اکوسیستم Rust توکار به‌طور گسترده استفاده می‌شود.

    برای خواندن و رمزگشایی پیام‌هایی که defmt روی میزبان تولید می‌کند، باید خروجی انتقال RTT را به semihosting تغییر دهیم. در سخت‌افزار واقعی این کار به یک نشست اشکال‌زدایی نیاز دارد، اما در QEMU بی‌دردسر کار می‌کند.

    بیایید وابستگی‌ها را عوض کنیم:

    cargo remove defmt-rtt
cargo add defmt-semihosting

    فایل src/lib.rs را باز کنید و use defmt_rtt as _; را با use defmt_semihosting as _; جایگزین کنید

    اکنون می‌توانیم مثال را بسازیم:

    cargo build --bin hello

    فایل دودویی خروجی در target/thumbv7m-none-eabi/debug/hello قرار می‌گیرد.

    برای اجرای این فایل دودویی روی QEMU، دستور زیر معمولاً کافی است:

    qemu-system-arm \
  -cpu cortex-m3 \
  -machine lm3s6965evb \
  -nographic \
  -semihosting-config enable=on,target=native \
  -kernel target/thumbv7m-none-eabi/debug/hello

    در مورد ما، چون از defmt استفاده می‌کنیم، میزبان نمی‌تواند خروجی را رمزگشایی کند. در عوض به ابزاری از Ferrous Systems با نام qemu-run نیاز داریم:

    git clone git@github.com:knurling-rs/defmt.git
cd defmt/qemu-run/
cargo run -- --machine lm3s6965evb ../qemu-rs/target/thumbv7m-none-eabi/debug/hello

    Hello, world!

    دستور باید پس از چاپ متن با موفقیت خارج شود (کد خروج = 0). در سیستم‌های *nix می‌توانید با دستور زیر این را بررسی کنید:

    echo $?

    0

    بیایید آن دستور QEMU را تکه‌تکه بررسی کنیم:

    • qemu-system-arm. این شبیه‌ساز QEMU است. چند گونه از این فایل‌های دودویی QEMU وجود دارد؛ این یکی شبیه‌سازی کامل سیستم ماشین‌های ARM را انجام می‌دهد و نامش از همین‌جاست.

    • -cpu cortex-m3. این به QEMU می‌گوید یک پردازندهٔ Cortex-M3 را شبیه‌سازی کند. مشخص کردن مدل پردازنده به ما امکان می‌دهد برخی خطاهای کامپایل نادرست را بگیریم: برای مثال، اجرای برنامه‌ای که برای Cortex-M4F، که FPU سخت‌افزاری دارد، کامپایل شده است باعث می‌شود QEMU هنگام اجرا خطا بدهد.

    • -machine lm3s6965evb. این به QEMU می‌گوید LM3S6965EVB را شبیه‌سازی کند، بردی ارزیابی که یک میکروکنترلر LM3S6965 دارد.

    • -nographic. این به QEMU می‌گوید رابط گرافیکی خود را اجرا نکند.

    • -semihosting-config (..). این به QEMU می‌گوید semihosting را فعال کند. semihosting به دستگاه شبیه‌سازی‌شده اجازه می‌دهد، از جمله، از stdout، stderr و stdin میزبان استفاده کند و روی میزبان فایل بسازد.

    • -kernel $file. این به QEMU می‌گوید کدام فایل دودویی را روی ماشین شبیه‌سازی‌شده بارگذاری و اجرا کند.

    تایپ کردن آن دستور بلند QEMU زیادی زحمت دارد! می‌توانیم برای ساده‌تر کردن فرایند یک runner سفارشی تعیین کنیم. فایل .cargo/config.toml یک runner به‌صورت توضیح درآمده دارد که QEMU را فراخوانی می‌کند؛ بیایید آن را از حالت توضیح درآوریم:

    head -n3 .cargo/config.toml

    [target.thumbv7m-none-eabi]
# uncomment this to make `cargo run` execute programs on QEMU
runner = "qemu-system-arm -cpu cortex-m3 -machine lm3s6965evb -nographic -semihosting-config enable=on,target=native -kernel"

    این runner فقط برای هدف thumbv7m-none-eabi اعمال می‌شود، که هدف کامپایل پیش‌فرض ماست. اکنون cargo run برنامه را کامپایل و روی QEMU اجرا می‌کند:

    cargo run --example hello --release

       Compiling app v0.1.0 (file:///tmp/app)
    Finished release [optimized + debuginfo] target(s) in 0.26s
     Running `qemu-system-arm -cpu cortex-m3 -machine lm3s6965evb -nographic -semihosting-config enable=on,target=native -kernel target/thumbv7m-none-eabi/release/examples/hello`
Hello, world!

    اشکال‌زدایی

    اشکال‌زدایی برای توسعهٔ توکار حیاتی است. ببینیم چطور انجام می‌شود.

    اشکال‌زدایی یک دستگاه توکار شامل اشکال‌زدایی از راه دور است، چون برنامه‌ای که می‌خواهیم اشکال‌زدایی کنیم روی ماشینی اجرا نمی‌شود که برنامهٔ اشکال‌زدا (GDB یا LLDB) را اجرا می‌کند.

    اشکال‌زدایی از راه دور شامل یک کلاینت و یک سرور است. در یک راه‌اندازی QEMU، کلاینت یک فرایند GDB (یا LLDB) و سرور فرایند QEMU است که برنامهٔ توکار را هم اجرا می‌کند.

    در این بخش از مثال hello که قبلاً کامپایل کرده‌ایم استفاده می‌کنیم.

    نخستین گام اشکال‌زدایی، اجرای QEMU در حالت اشکال‌زدایی است:

    qemu-system-arm \
  -cpu cortex-m3 \
  -machine lm3s6965evb \
  -nographic \
  -semihosting-config enable=on,target=native \
  -gdb tcp::3333 \
  -S \
  -kernel target/thumbv7m-none-eabi/debug/examples/hello

    این دستور چیزی روی کنسول چاپ نمی‌کند و ترمینال را مسدود می‌کند. این بار دو پرچم اضافی داده‌ایم:

    • -gdb tcp::3333. این به QEMU می‌گوید روی پورت TCP شمارهٔ 3333 منتظر اتصال GDB بماند.

    • -S. این به QEMU می‌گوید ماشین را هنگام راه‌اندازی متوقف کند. بدون آن، برنامه پیش از آن‌که فرصتی برای اجرای اشکال‌زدا داشته باشیم به انتهای main می‌رسید!

    سپس در ترمینال دیگری GDB را اجرا می‌کنیم و به آن می‌گوییم نمادهای اشکال‌زدایی مثال را بارگذاری کند:

    gdb-multiarch -q target/thumbv7m-none-eabi/debug/examples/hello

    توجه: بسته به این‌که در فصل نصب کدام نسخهٔ gdb را نصب کرده‌اید، ممکن است به‌جای gdb-multiarch به نسخهٔ دیگری از gdb نیاز داشته باشید. این نسخه می‌تواند arm-none-eabi-gdb یا فقط gdb هم باشد.

    سپس درون پوستهٔ GDB به QEMU وصل می‌شویم، که روی پورت TCP شمارهٔ 3333 منتظر اتصال است.

    target remote :3333

    Remote debugging using :3333
Reset () at $REGISTRY/cortex-m-rt-0.6.1/src/lib.rs:473
473     pub unsafe extern "C" fn Reset() -> ! {

    می‌بینید که فرایند متوقف شده است و شمارندهٔ برنامه (program counter) به تابعی با نام Reset اشاره می‌کند. این همان کنترل‌گر reset است: چیزی که هسته‌های Cortex-M هنگام بوت اجرا می‌کنند.

    توجه کنید که در برخی راه‌اندازی‌ها، به‌جای نمایش خط Reset () at $REGISTRY/cortex-m-rt-0.6.1/src/lib.rs:473 که در بالا نشان داده شد، ممکن است gdb چند هشدار چاپ کند، مانند core::num::bignum::Big32x40::mul_small () at src/libcore/num/bignum.rs:254 و src/libcore/num/bignum.rs: No such file or directory.

    core::num::bignum::Big32x40::mul_small () at src/libcore/num/bignum.rs:254 src/libcore/num/bignum.rs: No such file or directory.

    این یک مشکل شناخته‌شده است. می‌توانید با خیال راحت این هشدارها را نادیده بگیرید؛ به احتمال زیاد در Reset() هستید.

    این کنترل‌گر reset سرانجام تابع main ما را فراخوانی می‌کند. بیایید با یک breakpoint و دستور continue یک‌راست به آنجا برویم. برای تنظیم breakpoint، ابتدا با دستور list ببینیم در کد خود کجا می‌خواهیم توقف کنیم.

    list main

    این دستور کد منبع را از فایل examples/hello.rs نشان می‌دهد.

    6       use panic_halt as _;
7
8       use cortex_m_rt::entry;
9       use cortex_m_semihosting::{debug, hprintln};
10
11      #[entry]
12      fn main() -> ! {
13          hprintln!("Hello, world!").unwrap();
14
15          // exit QEMU

    می‌خواهیم درست پیش از “Hello, world!” که در خط 13 است، یک breakpoint اضافه کنیم. این کار را با دستور break انجام می‌دهیم:

    break 13

    اکنون می‌توانیم با دستور continue به gdb بگوییم تا تابع main ما اجرا کند:

    continue

    Continuing.

Breakpoint 1, hello::__cortex_m_rt_main () at examples\hello.rs:13
13          hprintln!("Hello, world!").unwrap();

    اکنون به کدی که “Hello, world!” را چاپ می‌کند نزدیک شده‌ایم. بیایید با دستور next جلوتر برویم.

    next

    16          debug::exit(debug::EXIT_SUCCESS);

    در این مرحله باید “Hello, world!” را روی ترمینالی ببینید که qemu-system-arm را اجرا می‌کند.

    $ qemu-system-arm (..)
Hello, world!

    فراخوانی دوبارهٔ next فرایند QEMU را خاتمه می‌دهد.

    next

    [Inferior 1 (Remote target) exited normally]

    اکنون می‌توانید از نشست GDB خارج شوید.

    quit
