    بهینه‌سازی‌ها: مصالحهٔ سرعت و اندازه

    همه می‌خواهند برنامه‌شان بسیار سریع و بسیار کوچک باشد، اما معمولاً نمی‌توان هر دو ویژگی را با هم داشت. این بخش سطوح مختلف بهینه‌سازی‌ای را که rustc فراهم می‌کند و تأثیر آن‌ها بر زمان اجرا و اندازهٔ باینری برنامه را بررسی می‌کند.

    بدون بهینه‌سازی

    این حالت پیش‌فرض است. وقتی cargo build را اجرا می‌کنید از پروفایل توسعه (که به آن dev هم می‌گویند) استفاده می‌کنید. این پروفایل برای اشکال‌زدایی بهینه شده است؛ بنابراین اطلاعات اشکال‌زدایی را فعال می‌کند و هیچ بهینه‌سازی‌ای را فعال نمی‌کند، یعنی از -C opt-level = 0 استفاده می‌کند.

    دست‌کم برای توسعهٔ bare metal، اطلاعات اشکال‌زدایی (debuginfo) از این نظر هزینه‌ای ندارد که فضایی در Flash / ROM اشغال نمی‌کند؛ بنابراین در واقع توصیه می‌کنیم debuginfo را در پروفایل release فعال کنید – به‌طور پیش‌فرض غیرفعال است. این کار به شما اجازه می‌دهد هنگام اشکال‌زدایی ساخت‌های release از نقطهٔ توقف (breakpoint) استفاده کنید.

    [profile.release]
# symbols are nice and they don't increase the size on Flash
debug = true

    نبود بهینه‌سازی برای اشکال‌زدایی عالی است، چون گام‌به‌گام پیش رفتن در کد حس اجرای برنامه دستور به دستور را می‌دهد، و افزون بر آن می‌توانید متغیرهای پشته و آرگومان‌های تابع را در GDB با print چاپ کنید. وقتی کد بهینه شده باشد، تلاش برای چاپ متغیرها باعث می‌شود $0 = <value optimized out> چاپ شود.

    بزرگ‌ترین عیب پروفایل dev این است که باینری حاصل بسیار بزرگ و کند خواهد بود. معمولاً اندازه مشکل بزرگ‌تری است، چون باینری‌های بهینه‌نشده می‌توانند ده‌ها KiB از Flash را اشغال کنند که ممکن است دستگاه هدف شما آن‌قدر نداشته باشد – نتیجه: باینری بهینه‌نشدهٔ شما در دستگاهتان جا نمی‌شود!

    آیا می‌توانیم باینری‌های کوچک‌تر و سازگار با اشکال‌زدا داشته باشیم؟ بله، یک ترفند وجود دارد.

    بهینه‌سازی وابستگی‌ها

    یک قابلیت Cargo با نام profile-overrides وجود دارد که به شما اجازه می‌دهد سطح بهینه‌سازی وابستگی‌ها را بازنویسی کنید. می‌توانید از این قابلیت استفاده کنید تا همهٔ وابستگی‌ها را برای اندازه بهینه کنید و در عین حال crate اصلی را بهینه‌نشده و سازگار با اشکال‌زدا نگه دارید.

    حواستان باشد که کد جنریک (generic) گاهی ممکن است همراه با crate‌ای بهینه شود که در آن نمونه‌سازی می‌شود، نه crate‌ای که در آن تعریف شده است. اگر در برنامهٔ خود نمونه‌ای از یک struct جنریک بسازید و ببینید کدی با ردپای بزرگ را وارد می‌کند، ممکن است افزایش سطح بهینه‌سازی وابستگی‌های مربوط هیچ تأثیری نداشته باشد.

    این یک مثال است:

    # Cargo.toml
[package]
name = "app"
# ..

[profile.dev.package."*"] # +
opt-level = "z" # +

    بدون بازنویسی:

    $ cargo size --bin app -- -A
app  :
section               size        addr
.vector_table         1024   0x8000000
.text                 9060   0x8000400
.rodata               1708   0x8002780
.data                    0  0x20000000
.bss                     4  0x20000000

    با بازنویسی:

    $ cargo size --bin app -- -A
app  :
section               size        addr
.vector_table         1024   0x8000000
.text                 3490   0x8000400
.rodata               1100   0x80011c0
.data                    0  0x20000000
.bss                     4  0x20000000

    این یعنی ۶ KiB کاهش در مصرف Flash بدون هیچ آسیبی به قابلیت اشکال‌زدایی crate اصلی. اگر وارد یک وابستگی شوید، دوباره آن پیام‌های <value optimized out> را خواهید دید، اما معمولاً می‌خواهید crate اصلی را اشکال‌زدایی کنید و نه وابستگی‌ها را. و اگر واقعاً لازم است یک وابستگی را اشکال‌زدایی کنید، می‌توانید با قابلیت profile-overrides یک وابستگی مشخص را از بهینه‌سازی مستثنا کنید. مثال زیر را ببینید:

    # ..

# don't optimize the `cortex-m-rt` crate
[profile.dev.package.cortex-m-rt] # +
opt-level = 0 # +

# but do optimize all the other dependencies
[profile.dev.package."*"]
codegen-units = 1 # better optimizations
opt-level = "z"

    اکنون crate اصلی و cortex-m-rt سازگار با اشکال‌زدا هستند!

    بهینه‌سازی برای سرعت

    تا تاریخ ۲۰۱۸-۰۹-۱۸، rustc از سه سطح «بهینه‌سازی برای سرعت» پشتیبانی می‌کند: opt-level = 1، 2 و 3. وقتی cargo build --release را اجرا می‌کنید از پروفایل release استفاده می‌کنید که به‌طور پیش‌فرض opt-level = 3 دارد.

    هر دو سطح opt-level = 2 و 3 به بهای اندازهٔ باینری برای سرعت بهینه می‌کنند، اما سطح 3 بیش از سطح 2 برداری‌سازی (vectorization) و درون‌خطی‌سازی (inlining) انجام می‌دهد. به‌ویژه می‌بینید که در opt-level برابر یا بیشتر از 2، LLVM حلقه‌ها را باز می‌کند (unroll). بازکردن حلقه از نظر Flash / ROM هزینهٔ نسبتاً بالایی دارد (مثلاً از ۲۶ بایت به ۱۹۴ بایت برای حلقه‌ای که یک آرایه را صفر می‌کند) اما در شرایط مناسب (مثلاً وقتی تعداد تکرارها به‌اندازهٔ کافی زیاد باشد) می‌تواند زمان اجرا را به نصف هم برساند.

    در حال حاضر راهی برای غیرفعال کردن باز کردن حلقه در opt-level = 2 و 3 وجود ندارد، بنابراین اگر نمی‌توانید هزینهٔ آن را بپردازید باید برنامهٔ خود را برای اندازه بهینه کنید.

    بهینه‌سازی برای اندازه

    تا تاریخ ۲۰۱۸-۰۹-۱۸، rustc از دو سطح «بهینه‌سازی برای اندازه» پشتیبانی می‌کند: opt-level = "s" و "z". این نام‌ها از clang / LLVM به ارث رسیده‌اند و چندان گویا نیستند، اما "z" قرار است این مفهوم را برساند که باینری‌های کوچک‌تری از "s" تولید می‌کند.

    اگر می‌خواهید باینری‌های release شما برای اندازه بهینه شوند، تنظیم profile.release.opt-level را در Cargo.toml همان‌طور که در زیر نشان داده شده است تغییر دهید.

    [profile.release]
# or "z"
opt-level = "s"

    این دو سطح بهینه‌سازی آستانهٔ درون‌خطی‌سازی (inline threshold) در LLVM را به شدت کاهش می‌دهند؛ معیاری که برای تصمیم‌گیری دربارهٔ درون‌خطی کردن یا نکردن یک تابع به کار می‌رود. یکی از اصول Rust انتزاع‌های بدون هزینه (zero cost abstractions) است؛ این انتزاع‌ها برای حفظ پایانه‌ها (invariants) تمایل دارند از تعداد زیادی newtype و تابع کوچک استفاده کنند (مثلاً تابع‌هایی که یک مقدار داخلی را قرض می‌گیرند، مانند deref و as_ref)، بنابراین پایین بودن آستانهٔ درون‌خطی‌سازی می‌تواند باعث شود LLVM فرصت‌های بهینه‌سازی را از دست بدهد (مثلاً حذف شاخه‌های مرده یا درون‌خطی کردن فراخوانی closureها).

    هنگام بهینه‌سازی برای اندازه ممکن است بخواهید آستانهٔ درون‌خطی‌سازی را افزایش دهید تا ببینید آیا بر اندازهٔ باینری تأثیری دارد یا نه. روش توصیه‌شده برای تغییر آستانهٔ درون‌خطی‌سازی این است که پرچم -C inline-threshold را به دیگر rustflagها در .cargo/config.toml اضافه کنید.

    # .cargo/config.toml
# this assumes that you are using the cortex-m-quickstart template
[target.'cfg(all(target_arch = "arm", target_os = "none"))']
rustflags = [
  # ..
  "-C", "inline-threshold=123", # +
]

    چه مقداری استفاده کنیم؟ از نسخهٔ 1.29.0، این‌ها آستانه‌های درون‌خطی‌سازی‌ای هستند که سطوح مختلف بهینه‌سازی استفاده می‌کنند:

    • opt-level = 3 uses 275
    • opt-level = 2 uses 225
    • opt-level = "s" uses 75
    • opt-level = "z" uses 25

    هنگام بهینه‌سازی برای اندازه، مقادیر 225 و 275 را امتحان کنید.
