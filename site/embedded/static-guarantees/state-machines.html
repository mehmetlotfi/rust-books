    پیرامونی‌ها به‌عنوان ماشین‌های حالت

    دستگاه‌های جانبی یک میکروکنترلر را می‌توان مجموعه‌ای از ماشین‌های حالت در نظر گرفت. برای مثال، پیکربندی یک پایهٔ GPIO ساده‌شده را می‌توان با درخت حالت‌های زیر نمایش داد:

    • غیرفعال (Disabled)
    • فعال (Enabled)
      • پیکربندی‌شده به‌عنوان خروجی
        • خروجی: بالا
        • خروجی: پایین
      • پیکربندی‌شده به‌عنوان ورودی
        • ورودی: مقاومت بالا
        • ورودی: کشیده‌شده به پایین
        • ورودی: کشیده‌شده به بالا

    اگر دستگاه جانبی در حالت Disabled شروع شود، برای رفتن به حالت Input: High Resistance باید مراحل زیر را انجام دهیم:

    1. غیرفعال
    2. فعال
    3. پیکربندی‌شده به‌عنوان ورودی
    4. ورودی: مقاومت بالا

    اگر بخواهیم از Input: High Resistance به Input: Pulled Low برویم، باید مراحل زیر را انجام دهیم:

    1. ورودی: مقاومت بالا
    2. ورودی: کشیده‌شده به پایین

    به‌طور مشابه، اگر بخواهیم یک پایهٔ GPIO را از حالت Input: Pulled Low به Output: High ببریم، باید مراحل زیر را انجام دهیم:

    1. ورودی: کشیده‌شده به پایین
    2. پیکربندی‌شده به‌عنوان ورودی
    3. پیکربندی‌شده به‌عنوان خروجی
    4. خروجی: بالا

    نمایش سخت‌افزاری

    معمولاً حالت‌های فهرست‌شدهٔ بالا با نوشتن مقادیری در رجیسترهای مشخصی که به یک دستگاه جانبی GPIO نگاشت شده‌اند تنظیم می‌شوند. برای توضیح این موضوع، یک رجیستر پیکربندی GPIO فرضی تعریف می‌کنیم:

    نامشمارهٔ بیت‌هامقدارمعناتوضیحات
    enable00disabledGPIO را غیرفعال می‌کند
    1enabledGPIO را فعال می‌کند
    direction10inputجهت را روی ورودی (Input) تنظیم می‌کند
    1outputجهت را روی خروجی (Output) تنظیم می‌کند
    input_mode2..300hi-zورودی را روی مقاومت بالا تنظیم می‌کند
    01pull-lowپایهٔ ورودی به پایین کشیده می‌شود
    10pull-highپایهٔ ورودی به بالا کشیده می‌شود
    11نداردحالت نامعتبر. تنظیم نکنید
    output_mode40set-lowپایهٔ خروجی در سطح پایین رانده می‌شود
    1set-highپایهٔ خروجی در سطح بالا رانده می‌شود
    input_status5xin-valاگر ورودی کمتر از 1.5v باشد 0 و اگر ورودی بزرگ‌تر یا مساوی 1.5v باشد 1

    ما می‌توانیم ساختار زیر را در Rust برای کنترل این GPIO در اختیار قرار دهیم:

    /// GPIO interface
struct GpioConfig {
    /// GPIO Configuration structure generated by svd2rust
    periph: GPIO_CONFIG,
}

impl GpioConfig {
    pub fn set_enable(&mut self, is_enabled: bool) {
        self.periph.modify(|_r, w| {
            w.enable().set_bit(is_enabled)
        });
    }

    pub fn set_direction(&mut self, is_output: bool) {
        self.periph.modify(|_r, w| {
            w.direction().set_bit(is_output)
        });
    }

    pub fn set_input_mode(&mut self, variant: InputMode) {
        self.periph.modify(|_r, w| {
            w.input_mode().variant(variant)
        });
    }

    pub fn set_output_mode(&mut self, is_high: bool) {
        self.periph.modify(|_r, w| {
            w.output_mode.set_bit(is_high)
        });
    }

    pub fn get_input_status(&self) -> bool {
        self.periph.read().input_status().bit_is_set()
    }
}

    با این حال، این کار به ما اجازه می‌دهد رجیسترهایی را تغییر دهیم که معنایی ندارند. برای مثال، اگر وقتی GPIO ما به‌عنوان ورودی پیکربندی شده است فیلد output_mode را تنظیم کنیم چه اتفاقی می‌افتد؟

    به‌طور کلی، استفاده از این ساختار به ما اجازه می‌دهد به حالت‌هایی برسیم که در ماشین حالت بالا تعریف نشده‌اند؛ مثلاً خروجی‌ای که به پایین کشیده شده است، یا ورودی‌ای که روی بالا تنظیم شده است. برای برخی سخت‌افزارها ممکن است این موضوع اهمیتی نداشته باشد. در سخت‌افزارهای دیگر، می‌تواند رفتار غیرمنتظره یا تعریف‌نشده ایجاد کند!

    هرچند نوشتن این رابط راحت است، قراردادهای طراحی‌ای را که پیاده‌سازی سخت‌افزاری ما تعیین کرده است اعمال نمی‌کند.
