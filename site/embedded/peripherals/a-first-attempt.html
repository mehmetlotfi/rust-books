    نخستین تلاش

    ثبات‌ها

    بیایید به دستگاه جانبی «SysTick» نگاه کنیم، یک زمان‌سنج ساده که همراه هر هستهٔ پردازندهٔ Cortex-M عرضه می‌شود. معمولاً این اطلاعات را در برگهٔ داده (data sheet) یا راهنمای مرجع فنی (Technical Reference Manual) سازندهٔ تراشه جست‌وجو می‌کنید، اما این مثال برای همهٔ هسته‌های ARM Cortex-M مشترک است، پس به راهنمای مرجع ARM نگاه می‌کنیم. می‌بینیم چهار ثبات وجود دارد:

    آفستنامتوضیحعرض
    0x00SYST_CSRثبات کنترل و وضعیت32 بیت
    0x04SYST_RVRثبات مقدار بازنشانی32 بیت
    0x08SYST_CVRثبات مقدار فعلی32 بیت
    0x0CSYST_CALIBثبات مقدار کالیبراسیون32 بیت

    رویکرد C

    در Rust می‌توانیم مجموعه‌ای از ثبات‌ها را دقیقاً مثل C نمایش دهیم، یعنی با یک struct.

    #[repr(C)]
struct SysTick {
    pub csr: u32,
    pub rvr: u32,
    pub cvr: u32,
    pub calib: u32,
}

    مشخص‌کنندهٔ #[repr(C)] به کامپایلر Rust می‌گوید این ساختار را همان‌طور که کامپایلر C می‌چیند در حافظه بچیند. این موضوع بسیار مهم است، چون Rust اجازه می‌دهد ترتیب فیلدهای ساختار تغییر کند، اما C چنین اجازه‌ای نمی‌دهد. می‌توانید تصور کنید اگر کامپایلر بی‌سروصدا این فیلدها را جابه‌جا می‌کرد، چه اشکال‌زدایی‌ای در انتظارمان بود! با این مشخص‌کننده، چهار فیلد 32 بیتی داریم که با جدول بالا متناظرند. اما البته این struct به‌تنهایی فایده‌ای ندارد؛ به یک متغیر نیاز داریم.

    let systick = 0xE000_E010 as *mut SysTick;
let time = unsafe { (*systick).cvr };

    دسترسی‌های volatile

    حالا رویکرد بالا چند مشکل دارد.

    1. هر بار که بخواهیم به دستگاه جانبی دسترسی پیدا کنیم باید از unsafe استفاده کنیم.
    2. راهی نداریم که مشخص کنیم کدام ثبات‌ها فقط‌خواندنی و کدام‌ها خواندنی-نوشتنی‌اند.
    3. هر تکه کدی در هر جای برنامهٔ شما می‌تواند از طریق این ساختار به سخت‌افزار دسترسی پیدا کند.
    4. از همه مهم‌تر اینکه این رویکرد در واقع کار نمی‌کند…

    مشکل این است که کامپایلرها باهوش‌اند. اگر دو بار پشت سر هم در یک نقطهٔ RAM بنویسید، کامپایلر می‌تواند این را تشخیص دهد و نوشتن اول را کاملاً نادیده بگیرد. در C می‌توانیم متغیرها را volatile علامت بزنیم تا مطمئن شویم هر خواندن یا نوشتن دقیقاً همان‌طور که مقصود بوده انجام می‌شود. در Rust، به‌جای آن، دسترسی‌ها را volatile علامت می‌زنیم و نه خود متغیر را.

    let systick = unsafe { &mut *(0xE000_E010 as *mut SysTick) };
let time = unsafe { core::ptr::read_volatile(&mut systick.cvr) };

    پس یکی از چهار مشکلمان را برطرف کرده‌ایم، اما حالا کد unsafe حتی بیشتری داریم! خوشبختانه یک crate شخص ثالث وجود دارد که می‌تواند کمک کند: volatile_register.

    use volatile_register::{RW, RO};

#[repr(C)]
struct SysTick {
    pub csr: RW<u32>,
    pub rvr: RW<u32>,
    pub cvr: RW<u32>,
    pub calib: RO<u32>,
}

fn get_systick() -> &'static mut SysTick {
    unsafe { &mut *(0xE000_E010 as *mut SysTick) }
}

fn get_time() -> u32 {
    let systick = get_systick();
    systick.cvr.read()
}

    اکنون دسترسی‌های volatile به‌طور خودکار از طریق متدهای read و write انجام می‌شوند. نوشتن همچنان unsafe است، اما انصافاً سخت‌افزار مجموعه‌ای از وضعیت تغییرپذیر است و کامپایلر راهی ندارد بفهمد این نوشتن‌ها واقعاً ایمن‌اند یا نه، پس این یک موضع پیش‌فرض خوب است.

    پوششی به سبک Rust

    باید این struct را در یک API سطح بالاتر بپیچیم که فراخوانی آن برای کاربران ما ایمن باشد. ما به‌عنوان نویسندهٔ درایور، درستی کد unsafe را به‌صورت دستی بررسی می‌کنیم و سپس یک API ایمن به کاربران عرضه می‌کنیم تا لازم نباشد نگران آن باشند (البته به شرطی که به ما اعتماد کنند که کار را درست انجام داده‌ایم!).

    یک نمونه می‌تواند این باشد:

    use volatile_register::{RW, RO};

pub struct SystemTimer {
    p: &'static mut RegisterBlock
}

#[repr(C)]
struct RegisterBlock {
    pub csr: RW<u32>,
    pub rvr: RW<u32>,
    pub cvr: RW<u32>,
    pub calib: RO<u32>,
}

impl SystemTimer {
    pub fn new() -> SystemTimer {
        SystemTimer {
            p: unsafe { &mut *(0xE000_E010 as *mut RegisterBlock) }
        }
    }

    pub fn get_time(&self) -> u32 {
        self.p.cvr.read()
    }

    pub fn set_reload(&mut self, reload_value: u32) {
        unsafe { self.p.rvr.write(reload_value) }
    }
}

pub fn example_usage() -> String {
    let mut st = SystemTimer::new();
    st.set_reload(0x00FF_FFFF);
    format!("Time is now 0x{:08x}", st.get_time())
}

    مشکل این رویکرد این است که کد زیر از نظر کامپایلر کاملاً قابل قبول است:

    fn thread1() {
    let mut st = SystemTimer::new();
    st.set_reload(2000);
}

fn thread2() {
    let mut st = SystemTimer::new();
    st.set_reload(1000);
}

    آرگومان &mut self در تابع set_reload بررسی می‌کند که هیچ ارجاع دیگری به همان ساختار SystemTimer وجود نداشته باشد، اما جلوی کاربر را نمی‌گیرد که SystemTimer دومی بسازد که دقیقاً به همان دستگاه جانبی اشاره می‌کند! کدی که به این شیوه نوشته شده باشد، اگر نویسنده آن‌قدر دقیق باشد که همهٔ این نمونه‌های «تکراری» درایور را شناسایی کند، کار می‌کند؛ اما وقتی کد روی چند ماژول، درایور، توسعه‌دهنده و روز پخش شود، ارتکاب این نوع اشتباهات هر چه بیشتر آسان می‌شود.
