    singleton‌ها

    در مهندسی نرم‌افزار، الگوی singleton یک الگوی طراحی نرم‌افزار است که نمونه‌سازی از یک کلاس را به یک شیء محدود می‌کند.

    ویکی‌پدیا: الگوی Singleton

    اما چرا نمی‌توانیم فقط از متغیر(های) سراسری استفاده کنیم؟

    می‌توانیم همه‌چیز را به‌صورت یک static عمومی تعریف کنیم، مثل این:

    static mut THE_SERIAL_PORT: SerialPort = SerialPort;

fn main() {
    let _ = unsafe {
        THE_SERIAL_PORT.read_speed();
    };
}

    اما این کار چند مشکل دارد. این یک متغیر سراسری تغییرپذیر است و در Rust تعامل با این نوع متغیرها همیشه unsafe است. این متغیرها همچنین در سراسر برنامهٔ شما قابل مشاهده‌اند، یعنی بررسی‌گر قرض (borrow checker) نمی‌تواند در ردیابی ارجاع‌ها و مالکیت این متغیرها به شما کمک کند.

    در Rust چگونه این کار را انجام دهیم؟

    به‌جای اینکه دستگاه جانبی را فقط یک متغیر سراسری کنیم، می‌توانیم ساختاری بسازیم، که در اینجا PERIPHERALS نام دارد و برای هر یک از دستگاه‌های جانبی ما یک Option<T> در خود دارد.

    struct Peripherals {
    serial: Option<SerialPort>,
}
impl Peripherals {
    fn take_serial(&mut self) -> SerialPort {
        let p = replace(&mut self.serial, None);
        p.unwrap()
    }
}
static mut PERIPHERALS: Peripherals = Peripherals {
    serial: Some(SerialPort),
};

    این ساختار به ما امکان می‌دهد یک نمونهٔ منفرد از دستگاه جانبی را به دست آوریم. اگر بخواهیم take_serial() را بیش از یک بار فراخوانی کنیم، کد ما panic می‌کند!

    fn main() {
    let serial_1 = unsafe { PERIPHERALS.take_serial() };
    // This panics!
    // let serial_2 = unsafe { PERIPHERALS.take_serial() };
}

    اگرچه تعامل با این ساختار unsafe است، اما وقتی SerialPort درون آن را به دست آوردیم، دیگر نیازی به استفاده از unsafe یا ساختار PERIPHERALS نداریم.

    این رویکرد سربار اندکی در زمان اجرا دارد، چون باید ساختار SerialPort را در یک option بپیچیم و یک بار هم take_serial() را فراخوانی کنیم؛ اما همین هزینهٔ اندکِ اولیه به ما اجازه می‌دهد در بقیهٔ برنامه از بررسی‌گر قرض بهره ببریم.

    پشتیبانی کتابخانه‌های موجود

    اگرچه در بالا ساختار Peripherals خودمان را ساختیم، لازم نیست در کد خودتان این کار را بکنید. crate با نام cortex_m ماکرویی به نام singleton!() دارد که این کار را برای شما انجام می‌دهد.

    use cortex_m::singleton;

fn main() {
    // OK if `main` is executed only once
    let x: &'static mut bool =
        singleton!(: bool = false).unwrap();
}

    مستندات cortex_m

    علاوه بر این، اگر از cortex-m-rtic استفاده کنید، کل فرایند تعریف و به دست آوردن این دستگاه‌های جانبی برای شما انتزاعی می‌شود و در عوض ساختاری به نام Peripherals در اختیارتان قرار می‌گیرد که نسخهٔ غیر-Option<T> همهٔ آیتم‌هایی را که تعریف می‌کنید در خود دارد.

    // cortex-m-rtic v0.5.x
#[rtic::app(device = lm3s6965, peripherals = true)]
const APP: () = {
    #[init]
    fn init(cx: init::Context) {
        static mut X: u32 = 0;
         
        // Cortex-M peripherals
        let core: cortex_m::Peripherals = cx.core;
        
        // Device specific peripherals
        let device: lm3s6965::Peripherals = cx.device;
    }
}

    اما چرا؟

    اما این singleton‌ها چطور تفاوتی محسوس در طرز کار کد Rust ما ایجاد می‌کنند؟

    impl SerialPort {
    const SER_PORT_SPEED_REG: *mut u32 = 0x4000_1000 as _;

    fn read_speed(
        &self // <------ This is really, really important
    ) -> u32 {
        unsafe {
            ptr::read_volatile(Self::SER_PORT_SPEED_REG)
        }
    }
}

    دو عامل مهم در کار است:

    • چون از singleton استفاده می‌کنیم، تنها یک راه یا یک مکان برای به دست آوردن ساختار SerialPort وجود دارد
    • برای فراخوانی متد read_speed() باید مالک ساختار SerialPort باشیم یا ارجاعی به آن داشته باشیم

    کنار هم قرار گرفتن این دو عامل یعنی فقط وقتی می‌توانیم به سخت‌افزار دسترسی پیدا کنیم که بررسی‌گر قرض را به‌درستی راضی کرده باشیم؛ یعنی در هیچ نقطه‌ای چند ارجاع تغییرپذیر به یک سخت‌افزار واحد نداریم!

    fn main() {
    // missing reference to `self`! Won't work.
    // SerialPort::read_speed();

    let serial_1 = unsafe { PERIPHERALS.take_serial() };

    // you can only read what you have access to
    let _ = serial_1.read_speed();
}

    با سخت‌افزارتان مثل داده رفتار کنید

    علاوه بر این، چون برخی ارجاع‌ها تغییرپذیرند و برخی تغییرناپذیر، می‌توان دید که یک تابع یا متد بالقوه می‌تواند وضعیت سخت‌افزار را تغییر دهد یا نه. برای مثال،

    این تابع مجاز است تنظیمات سخت‌افزار را تغییر دهد:

    fn setup_spi_port(
    spi: &mut SpiPort,
    cs_pin: &mut GpioPin
) -> Result<()> {
    // ...
}

    این یکی مجاز نیست:

    fn read_button(gpio: &GpioPin) -> bool {
    // ...
}

    این کار به ما امکان می‌دهد اعمال کنیم که کد باید یا نباید در سخت‌افزار تغییر ایجاد کند، آن هم در زمان کامپایل و نه در زمان اجرا. یادآوری می‌کنیم که این روش عموماً فقط در سطح یک برنامه کار می‌کند، اما در سیستم‌های bare metal نرم‌افزار ما در یک برنامهٔ واحد کامپایل می‌شود، پس معمولاً این یک محدودیت نیست.
