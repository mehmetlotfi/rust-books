راهنمای توسعهٔ rustcrustc Development Guide

    Stability attributes

    این بخش دربارهٔ attributeها و طرح‌های پایداری است که به APIهای پایدار اجازه می‌دهند در کتابخانهٔ استاندارد rustc از APIهای ناپایدار در داخل استفاده کنند.

    نکته: این بخش برای قابلیت‌های کتابخانه است، نه قابلیت‌های زبان. برای دستورالعمل پایدارسازی قابلیت زبان، پایدارسازی قابلیت‌ها را ببینید.

    unstable

    attribute با نام #[unstable(feature = "foo", issue = "1234", reason = "lorem ipsum")] یک آیتم را صراحتاً ناپایدار علامت می‌زند. آیتم‌هایی که «ناپایدار» علامت‌گذاری شده‌اند بدون attribute متناظر #![feature] روی crate قابل‌استفاده نیستند، حتی روی کامپایلر nightly. این محدودیت فقط از مرز crateها اعمال می‌شود؛ آیتم‌های ناپایدار را می‌توان درون crateای که آن‌ها را تعریف می‌کند به‌کار برد.

    فیلد issue شمارهٔ issue مرتبط در GitHub را مشخص می‌کند. این فیلد الزامی است، و همهٔ قابلیت‌های ناپایدار باید issue پیگیری متناظر داشته باشند. در موارد نادری که مقدار معقولی وجود ندارد، issue = "none" استفاده می‌شود.

    attribute با نام unstable همهٔ زیرآیتم‌ها را آلوده می‌کند و لازم نیست دوباره اعمال شود. پس اگر آن را روی یک ماژول اعمال کنید، همهٔ آیتم‌های ماژول ناپایدار می‌شوند.

    اگر نام یک feature را تغییر دهید، می‌توانید old_name = "old_name" را اضافه کنید تا پیام خطای مفیدی تولید شود.

    می‌توانید با استفاده از attribute با نام #[stable] روی زیرآیتم‌های مشخص آن‌ها را پایدار کنید. طرح پایداری مشابه نحوهٔ کار pub است. می‌توانید توابع عمومی از ماژول‌های غیرعمومی داشته باشید، و می‌توانید توابع پایدار در ماژول‌های ناپایدار یا برعکس داشته باشید.

    پیش‌تر، به دلیل یک باگ rustc، آیتم‌های پایدار درون ماژول‌های ناپایدار در آن مکان برای کد پایدار در دسترس بودند. از سپتامبر 2024 ، آیتم‌هایی با مسیرهای تصادفاً پایدارشده با attribute با نام #[rustc_allowed_through_unstable_modules] علامت‌گذاری می‌شوند تا کدی که به آن مسیرها وابسته است نشکند. این attribute را به آیتم‌های بیشتری اضافه نکنید، مگر برای پرهیز از تغییرات شکننده لازم باشد.

    attribute با نام unstable ممکن است مقدار soft هم داشته باشد که آن را به‌جای خطای سخت، یک lint ناسازگار با آینده و پیش‌فرض ممنوع (deny-by-default) می‌کند. این توسط attribute با نام bench به‌کار می‌رود که در گذشته به‌طور تصادفی پذیرفته می‌شد. این با بهره‌گیری از lint capping در Cargo از شکستن وابستگی‌ها جلوگیری می‌کند.

    stable

    attribute با نام #[stable(feature = "foo", since = "1.420.69")] یک آیتم را صراحتاً پایدارشده علامت می‌زند. توجه کنید توابع پایدار ممکن است در بدنهٔ خود از چیزهای ناپایدار استفاده کنند.

    rustc_const_unstable

    #[rustc_const_unstable(feature = "foo", issue = "1234", reason = "lorem ipsum")] همان رابط attribute با نام unstable را دارد. برای علامت‌گذاری const fn به‌عنوان تابعی که const بودنش ناپایدار است به‌کار می‌رود. این فقط در موارد نادر لازم است:

    • اگر const fn از قابلیت‌های زبان یا intrinsicهای ناپایدار استفاده کند. (اگر به این برخورد کنید کامپایلر به شما می‌گوید attribute را اضافه کنید.)
    • اگر const fn با #[stable] است اما هنوز قرار نیست const-stable باشد.
    • برای تغییر feature gate لازم برای فراخوانی intrinsic ناپایدار از نظر const.

    پایداری const با پایداری معمول فرق دارد چون بازگشتی است: تابع #[rustc_const_unstable(...)] حتی به‌طور غیرمستقیم هم نمی‌تواند از کد پایدار فراخوانی شود. این برای پرهیز از نشت تصادفی آرتیفکت‌های پیاده‌سازی ناپایدار کامپایلر به کد پایدار یا قفل‌شدن روی عجیب‌گی‌های تصادفی یک پیاده‌سازی ناقص است. برای تنظیم دقیق این بررسی attributeهای rustc_const_stable_indirect و rustc_allow_const_fn_unstable را در ادامه ببینید.

    rustc_const_stable

    attribute با نام #[rustc_const_stable(feature = "foo", since = "1.420.69")] صراحتاً یک const fn را به‌عنوان تابعی که const بودنش stable است علامت می‌زند.

    rustc_const_stable_indirect

    attribute با نام #[rustc_const_stable_indirect] را می‌توان به تابع #[rustc_const_unstable(...)] اضافه کرد تا از توابع #[rustc_const_stable(...)] قابل‌فراخوانی شود. این نشان می‌دهد تابع از نظر پیاده‌سازی برای پایدار‌شدن آماده است (یعنی از قابلیت ناپایدار کامپایلر استفاده نمی‌کند)؛ تنها دلیل اینکه هنوز const-stable نیست نگرانی‌های API است.

    این باید به lang itemهایی هم اضافه شود که فراخوانی‌های const آن‌ها در کامپایلر سنتز می‌شود، تا مطمئن شویم آن فراخوانی‌ها قواعد بازگشتی پایداری const را دور نمی‌زنند.

    rustc_intrinsic_const_stable_indirect

    روی یک intrinsic، این attribute آن را «آمادهٔ استفاده توسط توابع پایدار عمومی» علامت می‌زند. اگر intrinsic attribute با نام rustc_const_unstable دارد، باید حذف شود. افزودن این attribute به یک intrinsic نیازمند تأیید t-lang و wg-const-eval است!

    rustc_default_body_unstable

    attribute با نام #[rustc_default_body_unstable(feature = "foo", issue = "1234", reason = "lorem ipsum")] همان رابط attribute با نام unstable را دارد. برای علامت‌گذاری پیاده‌سازی پیش‌فرض یک آیتم درون trait به‌عنوان ناپایدار به‌کار می‌رود. یک trait با آیتم default-body-unstable را می‌توان به‌طور پایدار با ارائهٔ بدنهٔ صریح برای هر چنین آیتمی پیاده‌سازی کرد، یا می‌توان با فعال‌کردن #![feature] متناظر از بدنهٔ پیش‌فرض استفاده کرد.

    پایدارسازی یک قابلیت کتابخانه

    برای پایدارسازی یک قابلیت، این گام‌ها را دنبال کنید:

    1. از یکی از اعضای @T-libs بخواهید روی issue پیگیری FCP شروع کند و منتظر تکمیل FCP (با disposition-merge) بمانید.
    2. #[unstable(...)] را به #[stable(since = "CURRENT_RUSTC_VERSION")] تغییر دهید.
    3. #![feature(...)] را از هر تست یا doc-test این API حذف کنید. اگر قابلیت در کامپایلر یا ابزارها استفاده شده، از آنجا هم حذف کنید.
    4. اگر این یک const fn است، #[rustc_const_stable(since = "CURRENT_RUSTC_VERSION")] را اضافه کنید. یا اگر قرار نیست هنوز const-stabilize شود، #[rustc_const_unstable(...)] را برای یک feature gate جدید (با issue پیگیری جدید) اضافه کنید.
    5. Open a PR against rust-lang/rust.
      • برچسب‌های مناسب را اضافه کنید: @rustbot modify labels: +T-libs.
      • به issue پیگیری پیوند دهید و بنویسید «Closes #XXXXX».

    می‌توانید نمونه‌ای از پایدارسازی یک قابلیت را با issue پیگیری #81656 همراه با FCP و PR پیاده‌سازی #84642 مرتبط با آن ببینید.

    allow_internal_unstable

    ماکروها و desugaringهای کامپایلر بدنهٔ خود را در محل فراخوانی نمایان می‌کنند. برای دورزدن ناتوانی در استفاده از چیزهای ناپایدار در ماکروهای کتابخانهٔ استاندارد، attribute با نام #[allow_internal_unstable(feature1, feature2)] هست که اجازه می‌دهد قابلیت‌های داده‌شده در ماکروهای پایدار به‌کار روند.

    توجه کنید که اگر ماکرویی در زمینهٔ const استفاده شود و فراخوانی به تابع #[rustc_const_unstable(...)] تولید کند، حتی با allow_internal_unstable هم همچنان رد می‌شود. #[rustc_const_stable_indirect] را به تابع اضافه کنید تا مطمئن شوید ماکرو نمی‌تواند به‌طور تصادفی بررسی‌های بازگشتی پایداری const را دور بزند.

    rustc_allow_const_fn_unstable

    همان‌طور که بالا توضیح داده شد، هیچ قابلیت const ناپایداری درون const fn پایدار مجاز نیست، حتی به‌طور غیرمستقیم.

    با این حال، گاهی می‌دانیم یک قابلیت پایدار خواهد شد، فقط نه چه زمانی، یا راه‌حل پایدار (اما مثلاً کند در زمان اجرا) وجود دارد، پس همیشه می‌توانستیم اگر قابلیت ناپایدار را کنار می‌گذاشتیم به نسخهٔ پایدار برگردیم. در آن موارد، attribute با نام [rustc_allow_const_fn_unstable(feature1, feature2)] را می‌توان برای مجاز‌کردن برخی قابلیت‌های ناپایدار در بدنهٔ const fn پایدار (یا غیرمستقیم پایدار) به‌کار برد.

    همچنین باید مراقب حفظ پایای const fn باشید که فراخوانی آن در زمان اجرا و زمان کامپایل باید یکسان رفتار کند (این پست وبلاگ را هم ببینید). یعنی ممکن است const fnای نسازید که مثلاً آدرس حافظه را به عدد صحیح transmute کند، چون آدرس چیزها غیرقطعی و اغلب در زمان کامپایل نامعلوم است.

    اگر attributeهای rustc_allow_const_fn_unstable بیشتری به const fnی اضافه می‌کنید همیشه @rust-lang/wg-const-eval را ping کنید.

    staged_api

    هر crateای که از attributeهای stable یا unstable استفاده می‌کند باید attribute با نام #![feature(staged_api)] را روی crate بگنجاند.

    deprecated

    منسوخ‌سازی‌ها (deprecation) در کتابخانهٔ استاندارد تقریباً با منسوخ‌سازی در کد کاربر یکسان‌اند. وقتی #[deprecated] روی آیتمی به‌کار می‌رود، باید attribute با نام stable یا unstable هم داشته باشد.

    deprecated شکل زیر را دارد:

    #[deprecated(
    since = "1.38.0",
    note = "explanation for deprecation",
    suggestion = "other_function"
)]

    فیلد suggestion اختیاری است. اگر داده شود، باید رشته‌ای باشد که می‌تواند به‌عنوان پیشنهاد machine-applicable برای اصلاح هشدار به‌کار رود. این معمولاً وقتی به‌کار می‌رود که شناسه تغییر نام داده می‌شود اما تغییر مهم دیگری لازم نیست. وقتی از فیلد suggestion استفاده می‌شود، باید #![feature(deprecated_suggestion)] را در ریشهٔ crate داشته باشید.

    تفاوت دیگر با کد کاربر این است که فیلد since واقعاً با نسخهٔ فعلی rustc بررسی می‌شود. اگر since در نسخهٔ آینده باشد، lint با نام deprecated_in_future فعال می‌شود که پیش‌فرض allow است، اما بیشتر کتابخانهٔ استاندارد آن را با #![warn(deprecated_in_future)] به هشدار ارتقا می‌دهد.

    unstable_feature_bound

    attribute با نام #[unstable_feature_bound(foo)] را می‌توان همراه attribute با نام #[unstable] برای علامت‌گذاری impl یک نوع پایدار و trait پایدار به‌عنوان ناپایدار به‌کار برد. در std/core، آیتمی که با #[unstable_feature_bound(foo)] annotate شده فقط توسط آیتم دیگری قابل‌استفاده است که آن هم با #[unstable_feature_bound(foo)] annotate شده باشد. بیرون از std/core، استفاده از آیتم با #[unstable_feature_bound(foo)] نیازمند فعال‌شدن قابلیت با attribute با نام #![feature(foo)] روی crate است.

    فعلاً آیتم‌هایی که می‌توان با #[unstable_feature_bound] annotate کرد این‌ها هستند:

    • impl
    • free function
    • trait

    قابلیت‌های تغییرنام‌یافته و حذف‌شده

    قابلیت‌های ناپایدار می‌توانند تغییر نام یابند و حذف شوند. اگر نام یک قابلیت را تغییر دهید، می‌توانید old_name = "old_name" را به attribute با نام #[unstable] اضافه کنید. اگر قابلیتی را حذف کنید، attribute با نام #![unstable_removed(feature = "foo", reason = "brief description", link = "link", since = "1.90.0")] باید برای تولید پیام خطای خوب برای کاربران قابلیت حذف‌شده به‌کار رود.

    فیلد link را می‌توان برای پیوند به مرتبط‌ترین اطلاعات دربارهٔ حذف قابلیت، مثل issue، کامنت یا PR در GitHub به‌کار برد.
