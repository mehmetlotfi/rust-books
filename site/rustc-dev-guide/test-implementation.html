    attribute با نام #[test]

    بسیاری از برنامه‌نویسان Rust به attribute داخلی به نام #[test] تکیه می‌کنند. فقط باید تابعی را علامت بزنید و چند assert مثل زیر بگنجانید:

    #[test]
fn my_test() {
    assert!(2+2 == 4);
}

    وقتی این برنامه با rustc --test یا cargo test کامپایل شود، فایل اجرایی‌ای تولید می‌کند که می‌تواند این و هر تابع تست دیگر را اجرا کند. این روش تست اجازه می‌دهد تست‌ها به‌شکلی طبیعی کنار کد زندگی کنند. حتی می‌توانید تست‌ها را درون ماژول‌های خصوصی بگذارید:

    mod my_priv_mod {
    fn my_priv_func() -> bool {}

    #[test]
    fn test_priv_func() {
        assert!(my_priv_func());
    }
}

    بنابراین آیتم‌های خصوصی را می‌توان به‌آسانی تست کرد بدون اینکه نگران نمایان‌کردنشان برای هر نوع ابزار تست بیرونی باشید. این کلید ergonomics تست در Rust است. اما از نظر معناشناسی کمی عجیب است. چگونه هر نوع تابع main این تست‌ها را فراخوانی می‌کند اگر دیده نمی‌شوند؟ rustc --test دقیقاً چه می‌کند؟

    #[test] به‌صورت تبدیل نحوی درون rustc_ast کامپایلر پیاده‌سازی شده است. اساساً یک macro شیک است که crate را در ۳ گام بازنویسی می‌کند:

    Step 1: Re-Exporting

    همان‌طور که پیش‌تر گفته شد، تست‌ها می‌توانند درون ماژول‌های خصوصی باشند، پس راهی برای نمایان‌کردن آن‌ها به تابع main لازم داریم بدون شکستن کد موجود. برای این منظور، rustc_ast ماژول‌های محلی به نام __test_reexports می‌سازد که تست‌ها را به‌صورت بازگشتی دوباره export می‌کنند. این گسترش مثال بالا را به این ترجمه می‌کند:

    mod my_priv_mod {
    fn my_priv_func() -> bool {}

    pub fn test_priv_func() {
        assert!(my_priv_func());
    }

    pub mod __test_reexports {
        pub use super::test_priv_func;
    }
}

    اکنون تست ما با my_priv_mod::__test_reexports::test_priv_func قابل‌دسترسی است. برای ساختارهای ماژول عمیق‌تر، __test_reexports ماژول‌هایی را که تست دارند دوباره export می‌کند، پس تستی در a::b::my_test به a::__test_reexports::b::__test_reexports::my_test تبدیل می‌شود. هرچند این فرایند کاملاً ایمن به نظر می‌رسد، اگر ماژول __test_reexports از قبل وجود داشته باشد چه می‌شود؟ پاسخ: هیچ.

    برای توضیح، باید بفهمیم درخت نحو انتزاعی Rust شناسه‌ها را چگونه نمایش می‌دهد. نام هر تابع، متغیر، ماژول و غیره به‌صورت رشته ذخیره نمی‌شود، بلکه به‌صورت Symbol مات که اساساً شمارهٔ شناسهٔ هر شناسه است. کامپایلر hashtable جداگانه‌ای نگه می‌دارد که در صورت نیاز اجازه می‌دهد نام قابل‌خواندن برای انسان یک Symbol را بازیابی کنیم (مثلاً هنگام چاپ خطای نحوی). وقتی کامپایلر ماژول __test_reexports را تولید می‌کند، یک Symbol جدید برای شناسه می‌سازد، پس هرچند __test_reexports تولیدشده توسط کامپایلر ممکن است نامی مشابه نسخهٔ دست‌نویس شما داشته باشد، Symbol مشترک ندارد. این تکنیک از تعارض نام هنگام تولید کد جلوگیری می‌کند و پایهٔ hygiene در macro Rust است.

    Step 2: Harness generation

    اکنون که تست‌هایمان از ریشهٔ crate قابل‌دسترسی‌اند، باید کاری با آن‌ها بکنیم. rustc_ast ماژولی مثل زیر تولید می‌کند:

    #[main]
pub fn main() {
    extern crate test;
    test::test_main_env_args(&[&path::to::test1, /*...*/]);
}

    اینجا path::to::test1 ثابتی از نوع test::TestDescAndFn است.

    هرچند این تبدیل ساده است، بینش زیادی دربارهٔ اینکه تست‌ها واقعاً چگونه اجرا می‌شوند به ما می‌دهد. تست‌ها در آرایه‌ای جمع می‌شوند و به test runner با نام test_main_env_args داده می‌شوند. به اینکه TestDescAndFn دقیقاً چیست بازمی‌گردیم، اما فعلاً نکتهٔ کلیدی این است که crateای به نام test هست که بخشی از core در Rust است و همهٔ runtime مربوط به تست را پیاده‌سازی می‌کند. رابط test ناپایدار است، پس تنها راه پایدار تعامل با آن ماکروی #[test] است.

    گام ۳: تولید شیء تست

    اگر پیش‌تر در Rust تست نوشته باشید، ممکن است با برخی attributeهای اختیاری موجود روی توابع تست آشنا باشید. برای مثال، می‌توان تستی را با #[should_panic] annotate کرد اگر انتظار داریم تست باعث panic شود. چیزی شبیه این است:

    #[test]
#[should_panic]
fn foo() {
    panic!("intentional");
}

    یعنی تست‌های ما بیش از توابع ساده‌اند، اطلاعات پیکربندی هم دارند. test این داده‌های پیکربندی را در structای به نام TestDesc کدگذاری می‌کند. برای هر تابع تست در یک crate، rustc_ast attributeهای آن را تجزیه می‌کند و نمونهٔ TestDesc تولید می‌کند. سپس TestDesc و تابع تست را در struct با نام TestDescAndFn ترکیب می‌کند که test_main_env_args روی آن عمل می‌کند. برای تست مشخصی، نمونهٔ TestDescAndFn تولیدشده این‌طور به نظر می‌رسد:

    self::test::TestDescAndFn{
  desc: self::test::TestDesc{
    name: self::test::StaticTestName("foo"),
    ignore: false,
    should_panic: self::test::ShouldPanic::Yes,
    allow_fail: false,
  },
  testfn: self::test::StaticTestFn(||
    self::test::assert_test_result(::crate::__test_reexports::foo())),
}

    پس از ساخت آرایه‌ای از این اشیای تست، آن‌ها از طریق harness تولیدشده در گام ۲ به test runner داده می‌شوند.
