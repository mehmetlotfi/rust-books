راهنمای توسعهٔ rustcrustc Development Guide

    موضوعات پیش‌زمینه

    این بخش تعدادی از اصطلاحات رایج کامپایلر را که در این راهنما پیش می‌آید پوشش می‌دهد. می‌کوشیم تعریف کلی را بیان کنیم و در عین حال زمینه‌ای مختص Rust هم ارائه دهیم.

    گراف جریان کنترل چیست؟

    گراف جریان کنترل (control-flow graph یا CFG) اصطلاحی رایج در کامپایلرهاست. اگر تا به حال از فلوچارت استفاده کرده باشید، مفهوم گراف جریان کنترل برایتان کاملاً آشنا خواهد بود. این گراف نمایشی از برنامهٔ شماست که جریان کنترل زیربنایی را به‌روشنی آشکار می‌کند.

    یک گراف جریان کنترل به‌صورت مجموعه‌ای از بلوک‌های پایه (basic blocks) ساخته می‌شود که با یال‌ها به هم متصل‌اند. ایدهٔ اصلی بلوک پایه این است که مجموعه‌ای از دستورهاست که «با هم» اجرا می‌شوند؛ یعنی هر وقت به یک بلوک پایه شاخه می‌زنید، از اولین دستور شروع می‌کنید و سپس همهٔ باقی‌مانده را اجرا می‌کنید. فقط در انتهای بلوک امکان شاخه‌زدن به بیش از یک مقصد وجود دارد (در MIR به آن دستور پایانی terminator می‌گوییم):

    bb0: {
    statement0;
    statement1;
    statement2;
    ...
    terminator;
}

    بسیاری از عبارت‌هایی که در Rust به آن‌ها عادت دارید به چند بلوک پایه کامپایل می‌شوند. برای مثال، یک دستور if را در نظر بگیرید:

    a = 1;
if some_variable {
    b = 1;
} else {
    c = 1;
}
d = 1;

    این کد در MIR به چهار بلوک پایه کامپایل می‌شود. در شکل متنی چنین به نظر می‌رسد:

    BB0: {
    a = 1;
    if some_variable {
        goto BB1;
    } else {
        goto BB2;
    }
}

BB1: {
    b = 1;
    goto BB3;
}

BB2: {
    c = 1;
    goto BB3;
}

BB3: {
    d = 1;
    ...
}

    در شکل گرافیکی چنین به نظر می‌رسد:

                    BB0
       +--------------------+
       | a = 1;             |
       +--------------------+
             /       \
  if some_variable   else
           /           \
     BB1  /             \  BB2
    +-----------+   +-----------+
    | b = 1;    |   | c = 1;    |
    +-----------+   +-----------+
            \          /
             \        /
              \ BB3  /
            +----------+
            | d = 1;   |
            | ...      |
            +----------+

    هنگام استفاده از گراف جریان کنترل، یک حلقه به‌سادگی به‌صورت یک دور در گراف ظاهر می‌شود و کلیدواژهٔ break به مسیری برای خروج از آن دور ترجمه می‌شود.

    تحلیل جریان داده چیست؟

    Static Program Analysis نوشتهٔ Anders Møller و Michael I. Schwartzbach منبعی فوق‌العاده است!

    تحلیل جریان داده (dataflow analysis) نوعی تحلیل ایستا است که در بسیاری از کامپایلرها رایج است. این اصطلاح یک تکنیک کلی را توصیف می‌کند، نه یک تحلیل خاص.

    ایدهٔ اصلی این است که می‌توانیم روی یک گراف جریان کنترل (CFG) پیمایش کنیم و ردیابی کنیم که یک مقدار چه می‌تواند باشد. در پایان پیمایش، ممکن است نشان داده باشیم که یک ادعا درست است یا لزوماً درست نیست (مثلاً «این متغیر باید مقداردهی اولیه شده باشد»). rustc معمولاً تحلیل‌های جریان داده را روی MIR انجام می‌دهد، چون MIR از قبل یک CFG است.

    برای مثال، فرض کنید می‌خواهیم بررسی کنیم که x پیش از استفاده در این قطعه کد مقداردهی اولیه شده است:

    fn foo() {
    let mut x;

    if some_cond {
        x = 1;
    }

    dbg!(x);
}

    یک CFG برای این کد ممکن است چنین به نظر برسد:

     +------+
 | Init | (A)
 +------+
    |   \
    |   if some_cond
  else    \ +-------+
    |      \| x = 1 | (B)
    |       +-------+
    |      /
 +---------+
 | dbg!(x) | (C)
 +---------+

    تحلیل جریان داده را می‌توانیم این‌گونه انجام دهیم: با یک پرچم init شروع می‌کنیم که نشان می‌دهد آیا می‌دانیم x مقداردهی اولیه شده است یا نه. هنگام پیمایش CFG، این پرچم را به‌روز می‌کنیم. در پایان می‌توانیم مقدارش را بررسی کنیم.

    پس ابتدا در بلوک (A)، متغیر x اعلان شده اما مقداردهی اولیه نشده است، بنابراین init = false. در بلوک (B) مقدار را مقداردهی اولیه می‌کنیم، پس می‌دانیم x مقداردهی اولیه شده است. بنابراین در انتهای (B)، init = true.

    بلوک (C) جایی است که کار جالب می‌شود. توجه کنید که دو یال ورودی وجود دارد، یکی از (A) و یکی از (B)، که مربوط به درست بودن یا نبودن some_cond هستند. اما ما نمی‌توانیم این را بدانیم! ممکن است some_cond همیشه درست باشد، به‌طوری که x در واقع همیشه مقداردهی اولیه شده باشد. همچنین ممکن است some_cond به چیزی تصادفی (مثلاً زمان) بستگی داشته باشد، پس x ممکن است مقداردهی اولیه نشده باشد. در حالت کلی نمی‌توانیم به‌صورت ایستا بدانیم (به دلیل قضیهٔ رایس). پس مقدار init در بلوک (C) باید چه باشد؟

    به‌طور کلی، در تحلیل‌های جریان داده، اگر یک بلوک چند والد داشته باشد (مانند (C) در مثال ما)، مقدار جریان داده‌اش تابعی از همهٔ والدهایش خواهد بود (و البته آنچه در (C) رخ می‌دهد). اینکه کدام تابع را به کار ببریم به تحلیلی که انجام می‌دهیم بستگی دارد.

    در این مورد، می‌خواهیم بتوانیم قطعاً ثابت کنیم که x باید پیش از استفاده مقداردهی اولیه شده باشد. این ما را وادار می‌کند محافظه‌کار باشیم و فرض کنیم some_cond گاهی ممکن است false باشد. بنابراین «تابع ادغام» ما «و» است. یعنی، init = true در (C) است اگر init = true در (A) و در (B) باشد (یا اگر x در (C) مقداردهی اولیه شود). اما چنین نیست؛ به‌ویژه init = false در (A) است و x در (C) مقداردهی اولیه نشده است. بنابراین init = false در (C) است؛ می‌توانیم خطای «x ممکن است پیش از استفاده مقداردهی اولیه نشده باشد» را گزارش کنیم.

    قطعاً دربارهٔ تحلیل‌های جریان داده می‌توان خیلی بیشتر گفت. مجموعهٔ گسترده‌ای از ادبیات پژوهشی دربارهٔ این موضوع وجود دارد، از جمله نظریهٔ فراوان. ما فقط یک تحلیل رو به جلو را بحث کردیم، اما تحلیل جریان داده رو به عقب نیز مفید است. برای مثال، به‌جای شروع از بلوک (A) و حرکت رو به جلو، می‌توانستیم از استفادهٔ x شروع کنیم و رو به عقب حرکت کنیم تا مقداردهی اولیهٔ آن را پیدا کنیم.

    «سورگذاری عمومی» چیست؟ و «سورگذاری وجودی» چه؟

    در ریاضی، یک محمول (predicate) ممکن است عمومی سورگذاری یا وجودی سورگذاری شده باشد:

    • سورگذاری عمومی:
      • محمول برقرار است اگر برای همهٔ ورودی‌های ممکن درست باشد.
      • نمادگذاری سنتی: ∀x: P(x). خوانده می‌شود «برای همهٔ x، P(x) برقرار است».
    • سورگذاری وجودی:
      • محمول برقرار است اگر ورودی‌ای وجود داشته باشد که در آن درست باشد، یعنی فقط کافی است یک ورودی واحد وجود داشته باشد.
      • نمادگذاری سنتی: ∃x: P(x). خوانده می‌شود «x‌ای وجود دارد که P(x) برقرار است».

    در Rust این‌ها در بررسی نوع و حل صفت پیش می‌آیند. برای مثال،

    fn foo<T>()

    این تابع ادعا می‌کند که تابع برای همهٔ نوع‌های T خوش‌نوع (well-typed) است: ∀ T: well_typed(foo).

    مثالی دیگر:

    fn foo<'a>(_: &'a usize)

    این تابع ادعا می‌کند که برای هر طول عمر 'a (که فراخواننده تعیین می‌کند)، خوش‌نوع است: ∀ 'a: well_typed(foo).

    مثالی دیگر:

    fn foo<F>()
where for<'a> F: Fn(&'a u8)

    این تابع ادعا می‌کند که برای همهٔ نوع‌های F که به ازای همهٔ طول عمرهای 'a داریم F: Fn(&'a u8)، خوش‌نوع است: ∀ F: ∀ 'a: (F: Fn(&'a u8)) => well_typed(foo).

    یک مثال دیگر:

    fn foo(_: dyn Debug)

    این تابع ادعا می‌کند که نوعی T وجود دارد که Debug را پیاده‌سازی می‌کند به‌طوری که تابع خوش‌نوع است: ∃ T: (T: Debug) and well_typed(foo).

    شاخص دبروین چیست؟

    شاخص‌های دبروین (De Bruijn) روشی‌اند برای نمایش اینکه کدام متغیرها در کدام بست‌کننده‌ها (binder) مقید شده‌اند، آن هم تنها با استفاده از اعداد صحیح. آن‌ها در ابتدا برای ارزیابی حساب لامبدا ابداع شدند (برای اطلاعات بیشتر این مقالهٔ ویکی‌پدیا را ببینید). در rustc از شاخص‌های دبروین برای نمایش نوع‌های جنریک استفاده می‌کنیم.

    در اینجا مثالی ساده از نحوهٔ استفاده از شاخص‌های دبروین برای closureها آمده است (البته ما در rustc واقعاً این کار را نمی‌کنیم!):

    |x| {
    f(x) // de Bruijn index of `x` is 1 because `x` is bound 1 level up

    |y| {
        g(x, y) // index of `x` is 2 because it is bound 2 levels up
                // index of `y` is 1 because it is bound 1 level up
    }
}

    هم‌وردایی و پادوردایی چیست؟

    فصل زیرنوع‌سازی (subtyping) را در Rust Nomicon ببینید.

    برای اطلاعات بیشتر دربارهٔ اینکه بررسی‌کنندهٔ نوع چگونه با وردایی (variance) برخورد می‌کند، فصل وردایی این راهنما را ببینید.

    «ناحیهٔ آزاد» یا «متغیر آزاد» چیست؟ و «ناحیهٔ مقید» چه؟

    بیایید مفاهیم آزاد در برابر مقید را بر حسب متغیرهای برنامه توضیح دهیم، چون با آن‌ها بیش از همه آشنا هستیم.

    • این عبارت را که یک closure می‌سازد در نظر بگیرید: |a, b| a + b. در اینجا a و b در a + b به آرگومان‌هایی اشاره می‌کنند که closure هنگام فراخوانی دریافت خواهد کرد. می‌گوییم a و b در آنجا به closure مقید (bound) هستند، و امضای closure یعنی |a, b| یک بست‌کننده (binder) برای نام‌های a و b است (چون هر اشاره‌ای به a یا b در درون آن، به متغیرهایی اشاره می‌کند که آن معرفی می‌کند).
    • این عبارت را در نظر بگیرید: a + b. در این عبارت، a و b به متغیرهای محلی‌ای اشاره می‌کنند که بیرون از عبارت تعریف شده‌اند. می‌گوییم آن متغیرها در عبارت آزاد ظاهر می‌شوند (یعنی آزاد هستند، نه مقید (بسته‌شده)).

    پس مسئله این است: یک متغیر در یک عبارت/دستور/هر چیز دیگر «آزاد ظاهر می‌شود» اگر به چیزی اشاره کند که بیرون از آن عبارت/دستور/هر چیز دیگر تعریف شده است. به‌طور معادل، می‌توانیم از «متغیرهای آزاد» یک عبارت صحبت کنیم – که صرفاً مجموعهٔ متغیرهایی است که «آزاد ظاهر می‌شوند».

    حالا این چه ربطی به ناحیه‌ها (regions) دارد؟ خب، می‌توانیم مفهوم مشابهی را برای نوع‌ها و ناحیه‌ها به کار ببریم. برای مثال، در نوع &'a u32، 'a آزاد ظاهر می‌شود. اما در نوع for<'a> fn(&'a u32) چنین نیست.
