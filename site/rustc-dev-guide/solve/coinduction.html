    هم‌استقرا (Coinduction)

    حل‌کنندهٔ صفت ممکن است هنگام اثبات goalها از هم‌استقرا (coinduction) استفاده کند. هم‌استقرا نسبتاً ظریف است، بنابراین فصلی جداگانه به آن اختصاص داده‌ایم.

    هم‌استقرا و استقرا

    در استقرا، اثبات‌ها را به‌صورت بازگشتی اعمال می‌کنیم تا به یک درخت اثبات متناهی برسیم. مثال Vec<Vec<Vec<u32>>>: Debug را در نظر بگیرید که به درخت زیر می‌انجامد.

    • Vec<Vec<Vec<u32>>>: Debug
      • Vec<Vec<u32>>: Debug
        • Vec<u32>: Debug
          • u32: Debug

    این درخت متناهی است. اما همهٔ goalهایی که می‌خواهیم برقرار باشند درخت اثبات متناهی ندارند؛ مثال زیر را در نظر بگیرید:

    struct List<T> {
    value: T,
    next: Option<Box<List<T>>>,
}

    برای اینکه List<T>: Send برقرار باشد، همهٔ فیلدهای آن باید به‌صورت بازگشتی Send را نیز پیاده‌سازی کنند. این به درخت اثبات زیر می‌انجامد:

    • List<T>: Send
      • T: Send
      • Option<Box<List<T>>>: Send
        • Box<List<T>>: Send
          • List<T>: Send
            • T: Send
            • Option<Box<List<T>>>: Send
              • Box<List<T>>: Send
                • …

    این درخت بی‌نهایت بزرگ خواهد بود که دقیقاً موضوع هم‌استقراست.

    برای اثبات استقرایی یک goal باید برایش یک درخت اثبات متناهی ارائه دهید. برای اثبات هم‌استقرایی یک goal، درخت اثبات ارائه‌شده می‌تواند نامتناهی باشد.

    چرا هم‌استقرا درست است

    هنگام بررسی اینکه آیا یک goal صفت برقرار است، می‌پرسیم «آیا implای وجود دارد که این کران را برآورده کند». حتی اگر زنجیره‌های نامتناهی از goalهای تودرتو وجود داشته باشد، باز هم یک impl یکتا داریم که باید از آن استفاده شود.

    چگونه هم‌استقرا را پیاده‌سازی کنیم

    اگرچه پیاده‌سازی ما نمی‌تواند با تلاش برای ساختن یک درخت نامتناهی هم‌استقرا را بررسی کند، چون این کار منابع نامتناهی می‌خواهد، همچنان منطقی است که از این منظر به هم‌استقرا فکر کنیم.

    چون نمی‌توانیم درخت‌های نامتناهی را بررسی کنیم، در عوض به دنبال الگوهایی می‌گردیم که می‌دانیم به درخت اثبات نامتناهی می‌انجامند. در حال حاضر الگویی که تشخیص می‌دهیم چرخه‌های (کانونی) است. اگر T: Send به T: Send وابسته باشد، کاملاً روشن است که این تا ابد ادامه می‌یابد.

    در مورد چرخه‌ها باید مراقب کش کردن باشیم. به‌دلیل کانونی‌سازی نواحی و متغیرهای استنتاج، برخورد با یک چرخه به این معنا نیست که به درخت اثبات نامتناهی می‌رسیم. مثال زیر را ببینید:

    trait Foo {}
struct Wrapper<T>(T);

impl<T> Foo for Wrapper<Wrapper<T>>
where
    Wrapper<T>: Foo
{}

    اثبات Wrapper<?0>: Foo از impl به شکل impl<T> Foo for Wrapper<Wrapper<T>> استفاده می‌کند که ?0 را به Wrapper<?1> مقید می‌کند و سپس Wrapper<?1>: Foo را لازم دارد. به‌دلیل کانونی‌سازی، این به‌صورت یک چرخه تشخیص داده می‌شود.

    ایدهٔ حل این است که هر بار چرخه‌ای تشخیص دادیم یک نتیجهٔ موقت برگردانیم و goalها را مکرراً دوباره امتحان کنیم تا نتیجهٔ موقت با نتیجهٔ نهایی آن goal برابر شود. با استفاده از Yes بدون قید به‌عنوان نتیجه شروع می‌کنیم و هر بار که لازم باشد دوباره اجرا کنیم آن را به نتیجهٔ تکرار قبلی به‌روز می‌کنیم.

    کارهای آینده

    در حال حاضر فقط صفت‌های خودکار، Sized و goalهای WF را هم‌استقرایی می‌دانیم. در آینده تقریباً قصد داریم همهٔ goalها هم‌استقرایی باشند. ابتدا توضیح بدهیم چرا اجازه دادن به اثبات‌های هم‌استقرایی بیشتر اصلاً مطلوب است.

    نوع‌های داده‌ای بازگشتی هم‌اکنون به هم‌استقرا متکی‌اند…

    …فقط تمایل دارند در حل‌کنندهٔ صفت از آن‌ها پرهیز کنند.

    enum List<T> {
    Nil,
    Succ(T, Box<List<T>>),
}

impl<T: Clone> Clone for List<T> {
    fn clone(&self) -> Self {
        match self {
            List::Nil => List::Nil,
            List::Succ(head, tail) => List::Succ(head.clone(), tail.clone()),
        }
    }
}

    در این impl از tail.clone() استفاده می‌کنیم. برای این کار باید Box<List<T>>: Clone را اثبات کنیم، که List<T>: Clone را لازم دارد. اما این به همان impl‌ای وابسته است که اکنون در حال بررسی آن هستیم. با افزودن آن الزام به where-clauseهای impl، کاری که با perfect derive انجام می‌دادیم، آن چرخه را به درون حل‌کنندهٔ صفت می‌بریم و خطا می‌گیریم.

    نوع‌های داده‌ای بازگشتی

    برای استدلال دربارهٔ نوع‌های بازگشتی که projection دارند هم به هم‌استقرا نیاز داریم؛ مثلاً مثال زیر در حال حاضر کامپایل نمی‌شود، هرچند باید معتبر باشد.

    use std::borrow::Cow;
pub struct Foo<'a>(Cow<'a, [Foo<'a>]>);

    این مشکل دست‌کم از سال ۲۰۱۵ شناخته‌شده است؛ برای اطلاعات بیشتر #23714 را ببینید.

    کران‌های ضمنیِ صریحاً بررسی‌شده

    هنگام بررسی یک impl، فرض می‌کنیم نوع‌های موجود در سرایند impl well-formed هستند. یعنی هنگام نمونه‌سازی impl باید ثابت کنیم که واقعاً چنین است. #100051 نشان می‌دهد که چنین نیست. برای رفع این مشکل باید گزاره‌های WF را برای نوع‌های سرایند impl اضافه کنیم. بدون هم‌استقرا برای همهٔ صفت‌ها، این حتی core را خراب می‌کند.

    trait FromResidual<R> {}
trait Try: FromResidual<<Self as Try>::Residual> {
    type Residual;
}

struct Ready<T>(T);
impl<T> Try for Ready<T> {
    type Residual = Ready<()>;
}
impl<T> FromResidual<<Ready<T> as Try>::Residual> for Ready<T> {}

    هنگام بررسی well-formed بودن impl مربوط به FromResidual، به چرخهٔ زیر می‌رسیم:

    impl در صورتی well-formed است که <Ready<T> as Try>::Residual و Ready<T> well-formed باشند.

    • wf(<Ready<T> as Try>::Residual) نیاز دارد به
    • Ready<T>: Try، که به‌دلیل صفت بالادستی (super trait) نیاز دارد به
    • Ready<T>: FromResidual<Ready<T> as Try>::Residual>, به‌دلیل کران‌های ضمنی روی impl
    • wf(<Ready<T> as Try>::Residual) :tada: چرخه

    مشکلات هنگام گسترش هم‌استقرا به goalهای بیشتر

    هنگام گسترش هم‌استقرا چند مشکل اضافی وجود دارد که باید در نظر داشت. مشکلات اینجا به حل‌کنندهٔ فعلی ربطی ندارند.

    کران‌های ضمنی صفت‌های بالادستی

    سامانهٔ صفت ما در حال حاضر با صفت‌های بالادستی، مثلاً trait Trait: SuperTrait، چنین رفتار می‌کند: ۱) الزام می‌کند که SuperTrait برای همهٔ نوع‌هایی که Trait را پیاده‌سازی می‌کنند برقرار باشد، و ۲) فرض می‌کند SuperTrait برقرار است اگر Trait برقرار باشد.

    تکیه بر ۲) هنگام اثبات ۱) ناسالم (unsound) است. این را فقط در مورد چرخه‌های هم‌استقرایی می‌توان مشاهده کرد. بدون چرخه، هر زمان بر ۲) تکیه می‌کنیم باید برای impl به‌کاررفتهٔ Trait ۱) را هم بدون تکیه بر ۲) اثبات کرده باشیم.

    trait Trait: SuperTrait {}

impl<T: Trait> Trait for T {}

// Keeping the current setup for coinduction
// would allow this compile. Uff :<
fn sup<T: SuperTrait>() {}
fn requires_trait<T: Trait>() { sup::<T>() }
fn generic<T>() { requires_trait::<T>() }

    این در واقع ذاتی هم‌استقرا نیست، بلکه ویژگی‌ای موجود است که به‌واسطهٔ آن ناسالم می‌شود.

    راه‌حل‌های ممکن

    ساده‌ترین راه حل این است که ۲) را به‌کلی حذف کنیم و همیشه T: Trait را به T: Trait و T: SuperTrait در بیرون از حل‌کنندهٔ صفت بسط دهیم. این به ما اجازه می‌دهد ۱) را هم حذف کنیم، اما چون هنوز باید where-boundهای معمولی روی صفت‌ها را اثبات کنیم، این صرفاً کار اضافه است.

    هرچند می‌توان راه‌هایی برای غیرفعال کردن کاربردهای چرخه‌ای ۲) هنگام بررسی ۱) تصور کرد، دست‌کم ایده‌های خودم - @lcnr - همگی بسیار پیچیده‌تر از آن‌اند که معقول باشند.

    normalizes_to goalها و پیشرفت

    یک goal از نوع normalizes_to الزام نرمال‌شدن <T as Trait>::Assoc به یک U را نشان می‌دهد. این در عمل با نرمال‌سازی ابتدایی <T as Trait>::Assoc و سپس یکسان‌سازی نوع حاصل با U انجام می‌شود. باید یک نگاشت باشد، زیرا هر projection باید دقیقاً به یک نوع نرمال شود. اگر صرفاً اجازهٔ درخت‌های اثبات نامتناهی را بدهیم، رفتار زیر را خواهیم داشت:

    trait Trait {
    type Assoc;
}

impl Trait for () {
    type Assoc = <() as Trait>::Assoc;
}

    اگر اکنون normalizes_to(<() as Trait>::Assoc, Vec<u32>) را محاسبه کنیم، impl را حل می‌کنیم و نوع وابستهٔ <() as Trait>::Assoc را به دست می‌آوریم. سپس آن را با نوع مورد انتظار یکسان می‌کنیم که باعث می‌شود normalizes_to(<() as Trait>::Assoc, Vec<u32>) را دوباره بررسی کنیم. این تا ابد ادامه می‌یابد و به یک درخت اثبات نامتناهی می‌انجامد.

    یعنی <() as Trait>::Assoc با هر نوع دیگری برابر می‌شد که ناسالم است.

    چگونه این را حل کنیم

    هشدار: این موضوع ظریف است و ممکن است نادرست باشد

    برخلاف goalهای صفت، normalizes_to باید مولد (productive) باشد1. یک goal از نوع normalizes_to وقتی مولد است که projection به یک سازندهٔ نوع صلب (rigid) نرمال شود، پس نرمال شدن <() as Trait>::Assoc به Vec<<() as Trait>::Assoc> مولد خواهد بود.

    یک goal از نوع normalizes_to دو نوع goal تودرتو دارد: الزامات تودرتویی که برای نرمال‌سازی واقعی projection لازم‌اند، و برابری میان projection نرمال‌شده و نوع مورد انتظار. فقط برابری باید مولد باشد. یک شاخه در درخت اثبات مولد است اگر یا متناهی باشد، یا دست‌کم یک normalizes_to داشته باشد که در آن alias به یک سازندهٔ نوع صلب حل شده است.

    به‌عنوان جایگزین، می‌توانیم صرفاً همیشه شاخهٔ یکسان‌سازی normalizes_to را استقرایی در نظر بگیریم. هر چرخه‌ای باید به نوع‌های نامتناهی بینجامد که به‌هرحال پشتیبانی نمی‌شوند و فقط هنگام نرمال‌سازی عمیق برای codegen به سرریز می‌انجامند.

    تلاشی دیگر برای خلاصه‌سازی.

    • یک چرخه فقط در صورتی مجاز است که هنگام یکسان‌سازی دست‌کم یک بار پس از نرمال‌سازی یک نوع صلب در سمت چپ (lhs) داشته باشیم
    • چرخه‌های بیرون از فراخوانی بازگشتی eq در normalizes_to همیشه مشکلی ندارند
