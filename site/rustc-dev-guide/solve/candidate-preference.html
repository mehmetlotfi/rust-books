    ترجیح candidate

    راه‌های متعددی برای اثبات goalهای Trait و NormalizesTo وجود دارد. هر یک از این گزینه‌ها یک Candidate نامیده می‌شود. اگر چند candidate قابل‌اعمال وجود داشته باشد، برخی candidateها را بر برخی دیگر ترجیح می‌دهیم. اطلاعات مرتبط را در CandidateSource آن‌ها ذخیره می‌کنیم.

    این ترجیح ممکن است به استنتاج یا قیدهای ناحیهٔ نادرست منجر شود و بنابراین در طول coherence ناسالم (unsound) خواهد بود. به همین دلیل، در coherence صرفاً می‌کوشیم همهٔ candidateها را ادغام کنیم.

    goalهای Trait

    goalهای صفت، candidateهای قابل‌اعمال خود را در fn merge_trait_candidates ادغام می‌کنند. این سند جزئیات و ارجاعات بیشتری فراهم می‌کند تا توضیح دهد چرا قواعد ترجیح فعلی را داریم.

    CandidateSource::BuiltinImpl(BuiltinImplSource::Trivial))

    implهای داخلی بدیهی (trivial builtin impls) آن implهای داخلی‌ای هستند که برای نوع‌های خوش‌ساخت همیشه قابل‌اعمال‌اند. این یعنی اگر یکی وجود داشته باشد، استفاده از candidate دیگر هرگز نباید قیدهای کمتری داشته باشد. در حال حاضر فقط implهای Sized - و MetaSized - را بدیهی می‌دانیم.

    این برای جلوگیری از یک خطای طول عمر در الگوی زیر لازم است

    trait Trait<T>: Sized {}
impl<'a> Trait<u32> for &'a str {}
impl<'a> Trait<i32> for &'a str {}
fn is_sized<T: Sized>(_: T) {}
fn foo<'a, 'b, T>(x: &'b str)
where
    &'a str: Trait<T>,
{
    // Elaborating the `&'a str: Trait<T>` where-bound results in a
    // `&'a str: Sized` where-bound. We do not want to prefer this
    // over the builtin impl.
    is_sized(x);
}

    این ترجیح در صورتی نادرست است که impl داخلی یک goal تودرتو داشته باشد که به یک بند where غیرپارامتری متکی است

    struct MyType<'a, T: ?Sized>(&'a (), T);
fn is_sized<T>() {}
fn foo<'a, T: ?Sized>()
where
    (MyType<'a, T>,): Sized,
    MyType<'static, T>: Sized,
{
    // The where-bound is trivial while the builtin `Sized` impl for tuples
    // requires proving `MyType<'a, T>: Sized` which can only be proven by
    // using the where-clause, adding an unnecessary `'static` constraint.
    is_sized::<(MyType<'a, T>,)>();
    //~^ ERROR lifetime may not live long enough
}

    CandidateSource::ParamEnv

    به‌محض اینکه دست‌کم یک candidate ‏ParamEnv غیرسراسری وجود داشته باشد، همهٔ candidateهای ParamEnv را بر انواع دیگر candidate ترجیح می‌دهیم. یک قید where سراسری (global) است اگر مرتبهٔ بالاتر (higher-ranked) نباشد و هیچ پارامتر جنریکی نداشته باشد. ممکن است 'static داشته باشد.

    می‌کوشیم قیدهای where را بر candidateهای دیگر ترجیح دهیم، چون کاربران معمولاً بیشترین کنترل را روی آن‌ها دارند و بنابراین در صورت نادرست بودن ترجیح candidate ما، می‌توانند به‌راحتی آن‌ها را تنظیم کنند.

    ترجیح بر candidateهای Impl

    این برای پرهیز از خطاهای ناحیه در مثال زیر لازم است

    trait Trait<'a> {}
impl<T> Trait<'static> for T {}
fn impls_trait<'a, T: Trait<'a>>() {}
fn foo<'a, T: Trait<'a>>() {
    impls_trait::<'a, T>();
}

    به این هم نیاز داریم چون implهای سایه‌خورده (shadowed) می‌توانند به چرخه‌های حل‌گرِ فعلاً مبهم منجر شوند: trait-system-refactor-initiative#76. بدون ترجیح، اگر قید where به قیدهای ناحیه بینجامد، برای پرهیز از ناکامل بودن مجبور می‌شدیم با خطاهای ابهام شکست بخوریم.

    trait Super {
    type SuperAssoc;
}

trait Trait: Super<SuperAssoc = Self::TraitAssoc> {
    type TraitAssoc;
}

impl<T, U> Trait for T
where
    T: Super<SuperAssoc = U>,
{
    type TraitAssoc = U;
}

fn overflow<T: Trait>() {
    // We can use the elaborated `Super<SuperAssoc = Self::TraitAssoc>` where-bound
    // to prove the where-bound of the `T: Trait` implementation. This currently results in
    // overflow.
    let x: <T as Trait>::TraitAssoc;
}

    این ترجیح مشکلات زیادی ایجاد می‌کند. #24066 را ببینید. بیشتر مشکلات از ترجیح قیدهای where بر implها ناشی می‌شود، حتی اگر قید where استنتاج نوع را هدایت کند:

    trait Trait<T> {
    fn call_me(&self, x: T) {}
}
impl<T> Trait<u32> for T {}
impl<T> Trait<i32> for T {}
fn bug<T: Trait<U>, U>(x: T) {
    x.call_me(1u32);
    //~^ ERROR mismatched types
}

    با این حال، حتی اگر این ترجیح را فقط وقتی اعمال کنیم که قید where استنتاج را هدایت نمی‌کند، باز هم ممکن است به قیدهای طول عمر نادرست منجر شود:

    trait Trait<'a> {}
impl<'a> Trait<'a> for &'a str {}
fn impls_trait<'a, T: Trait<'a>>(_: T) {}
fn foo<'a, 'b>(x: &'b str)
where
    &'a str: Trait<'b>
{
    // Need to prove `&'x str: Trait<'b>` with `'b: 'x`.
    impls_trait::<'b, _>(x);
    //~^ ERROR lifetime may not live long enough
}

    ترجیح بر candidateهای AliasBound

    این برای پرهیز از خطاهای ناحیه در مثال زیر لازم است

    trait Bound<'a> {}
trait Trait<'a> {
    type Assoc: Bound<'a>;
}

fn impls_bound<'b, T: Bound<'b>>() {}
fn foo<'a, 'b, 'c, T>()
where
    T: Trait<'a>,
    for<'hr> T::Assoc: Bound<'hr>,
{
    impls_bound::<'b, T::Assoc>();
    impls_bound::<'c, T::Assoc>();
}

    همچنین می‌تواند به قیدهای غیرضروری منجر شود

    trait Bound<'a> {}
trait Trait<'a> {
    type Assoc: Bound<'a>;
}

fn impls_bound<'b, T: Bound<'b>>() {}
fn foo<'a, 'b, T>()
where
    T: for<'hr> Trait<'hr>,
    <T as Trait<'b>>::Assoc: Bound<'a>,
{
    // Using the where-bound for `<T as Trait<'a>>::Assoc: Bound<'a>`
    // unnecessarily equates `<T as Trait<'a>>::Assoc` with the
    // `<T as Trait<'b>>::Assoc` from the env.
    impls_bound::<'a, <T as Trait<'a>>::Assoc>();
    // For a `<T as Trait<'b>>::Assoc: Bound<'b>` the self type of the
    // where-bound matches, but the arguments of the trait bound don't.
    impls_bound::<'b, <T as Trait<'b>>::Assoc>();
}

    چرا برای قیدهای where سراسری ترجیحی وجود ندارد

    قیدهای where سراسری یا کاملاً توسط یک impl مستلزم می‌شوند یا ارضاناپذیرند. اگر ارضاناپذیر باشند، واقعاً اهمیتی ندارد چه اتفاقی می‌افتد. اگر قید where کاملاً مستلزم باشد، استفاده از impl برای اثبات goal صفت نمی‌تواند به قیدهای اضافی بینجامد. برای goalهای صفت، این فقط برای قیدهای whereای مفید است که از 'static استفاده می‌کنند:

    trait A {
    fn test(&self);
}

fn foo(x: &dyn A)
where
    dyn A + 'static: A, // Using this bound would lead to a lifetime error.
{
    x.test();
}

    مهم‌تر اینکه با استفاده از implها در اینجا، از سایه انداختن قیدهای where سراسری بر implها هنگام نرمال‌سازی نوع‌های وابسته جلوگیری می‌کنیم. هیچ مشکل شناخته‌شده‌ای از ترجیح implها بر قیدهای where سراسری وجود ندارد.

    چرا همچنان قیدهای where سراسری را در نظر می‌گیریم

    با توجه به اینکه حتی وقتی قید where سراسری وجود دارد فقط از implها استفاده می‌کنیم، ممکن است بپرسید چرا این قیدهای where سراسری را به‌طور کامل نادیده نمی‌گیریم: از آن‌ها برای تضعیف هدایت استنتاج قیدهای where غیرسراسری استفاده می‌کنیم.

    بدون قید where سراسری، در حال حاضر قیدهای where غیرسراسری را ترجیح می‌دهیم، حتی اگر یک impl قابل‌اعمال هم وجود داشته باشد. با افزودن یک قید where سراسری، این هدایت استنتاج غیرضروری غیرفعال می‌شود و کامپایل شدن مثال زیر را ممکن می‌کند:

    fn check<Color>(color: Color)
where
    Vec: Into<Color> + Into<f32>,
{
    let _: f32 = Vec.into();
    // Without the global `Vec: Into<f32>`  bound we'd
    // eagerly use the non-global `Vec: Into<Color>` bound
    // here, causing this to fail.
}

struct Vec;
impl From<Vec> for f32 {
    fn from(_: Vec) -> Self {
        loop {}
    }
}

    CandidateSource::AliasBound

    candidateهای alias-bound را بر implها ترجیح می‌دهیم. در حال حاضر از این ترجیح برای هدایت استنتاج نوع استفاده می‌کنیم که باعث کامپایل شدن مثال زیر می‌شود. شخصاً فکر نمی‌کنم این ترجیح مطلوب باشد 🤷

    pub trait Dyn {
    type Word: Into<u64>;
    fn d_tag(&self) -> Self::Word;
    fn tag32(&self) -> Option<u32> {
        self.d_tag().into().try_into().ok()
        // prove `Self::Word: Into<?0>` and then select a method
        // on `?0`, needs eager inference.
    }
}
    fn impl_trait() -> impl Into<u32> {
    0u16
}

fn main() {
    // There are two possible types for `x`:
    // - `u32` by using the "alias bound" of `impl Into<u32>`
    // - `impl Into<u32>`, i.e. `u16`, by using `impl<T> From<T> for T`
    //
    // We infer the type of `x` to be `u32` even though this is not
    // strictly necessary and can even lead to surprising errors.
    let x = impl_trait().into();
    println!("{}", std::mem::size_of_val(&x));
}

    این ترجیح همچنین از ابهام ناشی از قیدهای ناحیه جلوگیری می‌کند؛ نمی‌دانم مردم در عمل به این متکی‌اند یا نه.

    trait Bound<'a> {}
impl<T> Bound<'static> for T {}
trait Trait<'a> {
    type Assoc: Bound<'a>;
}

fn impls_bound<'b, T: Bound<'b>>() {}
fn foo<'a, T: Trait<'a>>() {
    // Should we infer this to `'a` or `'static`.
    impls_bound::<'_, T::Assoc>();
}

    CandidateSource::BuiltinImpl(BuiltinImplSource::Object(_))

    implهای داخلی شیء صفت (trait object) را بر implهای نوشته‌شده توسط کاربر ترجیح می‌دهیم. این ناسالم (unsound) است و باید در آینده حذف شود. برای جزئیات بیشتر #57893 و #141347 را ببینید.

    goalهای NormalizesTo

    رفتار ترجیح candidate هنگام نرمال‌سازی در fn assemble_and_merge_candidates پیاده‌سازی شده است.

    همیشه candidateهای AliasBound را در نظر می‌گیریم

    اگر قید where آیتم وابسته را مشخص نکند، به‌جای اینکه alias را صلب (rigid) بدانیم، candidateهای AliasBound را در نظر می‌گیریم، حتی اگر goal صفت از طریق یک candidate ‏ParamEnv اثبات شده باشد.

    trait Super {
    type Assoc;
}
trait Bound {
    type Assoc: Super<Assoc = u32>;
}
trait Trait: Super {}

// Elaborating the environment results in a `T::Assoc: Super` where-bound.
// This where-bound must not prevent normalization via the `Super<Assoc = u32>`
// item bound.
fn heck<T: Bound<Assoc: Trait>>(x: <T::Assoc as Super>::Assoc) -> u32 {
    x
}

    استفاده از چنین aliasی می‌تواند به قیدهای ناحیهٔ اضافی منجر شود، رجوع کنید به #133044.

    trait Bound<'a> {
    type Assoc;
}
trait Trait {
    type Assoc: Bound<'static, Assoc = u32>;
}

fn heck<'a, T: Trait<Assoc: Bound<'a>>>(x: <T::Assoc as Bound<'a>>::Assoc) {
    // Normalizing the associated type requires `T::Assoc: Bound<'static>` as it
    // uses the `Bound<'static>` alias-bound instead of keeping the alias rigid.
    drop(x);
}

    candidateهای ParamEnv را بر AliasBound ترجیح می‌دهیم

    در حالی که اگر قید where نوع وابسته را مشخص نکند از candidateهای AliasBound استفاده می‌کنیم، در صورتی که مشخص کند، قید where را ترجیح می‌دهیم. این برای مثال زیر لازم است:

    // Make sure we prefer the `I::IntoIterator: Iterator<Item = ()>`
// where-bound over the `I::Intoiterator: Iterator<Item = I::Item>`
// alias-bound.

trait Iterator {
    type Item;
}

trait IntoIterator {
    type Item;
    type IntoIter: Iterator<Item = Self::Item>;
}

fn normalize<I: Iterator<Item = ()>>() {}

fn foo<I>()
where
    I: IntoIterator,
    I::IntoIter: Iterator<Item = ()>,
{
    // We need to prefer the `I::IntoIterator: Iterator<Item = ()>`
    // where-bound over the `I::Intoiterator: Iterator<Item = I::Item>`
    // alias-bound.
    normalize::<I::IntoIter>();
}

    همیشه قیدهای where را در نظر می‌گیریم

    حتی اگر goal صفت از طریق یک impl اثبات شده باشد، در صورت وجود، همچنان candidateهای ParamEnv را ترجیح می‌دهیم.

    قیدهای where «یتیم» (orphaned) را ترجیح می‌دهیم

    بندهای Projection «یتیم» را به ParamEnv اضافه می‌کنیم، هنگام نرمال‌سازی قیدهای آیتم GATها و RPITIT در fn check_type_bounds. باید این candidateهای ParamEnv را بر implها و قیدهای where دیگر ترجیح دهیم.

    #![feature(associated_type_defaults)]
trait Foo {
    // We should be able to prove that `i32: Baz<Self>` because of
    // the impl below, which requires that `Self::Bar<()>: Eq<i32>`
    // which is true, because we assume `for<T> Self::Bar<T> = i32`.
    type Bar<T>: Baz<Self> = i32;
}
trait Baz<T: ?Sized> {}
impl<T: Foo + ?Sized> Baz<T> for i32 where T::Bar<()>: Eq<i32> {}
trait Eq<T> {}
impl<T> Eq<T> for T {}

    موارد لزوم واقعی این ترجیح را کاملاً نمی‌فهمم و هنوز نتوانسته‌ام از آن به شیوه‌های جالب سوءاستفاده کنم، ولی 🤷

    قیدهای where سراسری را بر implها ترجیح می‌دهیم

    این برای کامپایل شدن مثال زیر لازم است. نمی‌دانم در عمل چیزی به آن متکی است یا نه 🤷

    trait Id {
    type This;
}
impl<T> Id for T {
    type This = T;
}

fn foo<T>(x: T) -> <u32 as Id>::This
where
    u32: Id<This = T>,
{
    x
}

    این یعنی نرمال‌سازی می‌تواند به قیدهای ناحیهٔ اضافی منجر شود، رجوع کنید به #133044.

    trait Trait {
    type Assoc;
}

impl Trait for &u32 {
    type Assoc = u32;
}

fn trait_bound<T: Trait>() {}
fn normalize<T: Trait<Assoc = u32>>() {}

fn foo<'a>()
where
    &'static u32: Trait<Assoc = u32>,
{
    trait_bound::<&'a u32>(); // ok, proven via impl
    normalize::<&'a u32>(); // error, proven via where-bound
}

    قیدهای where صفت بر implها سایه می‌اندازند

    نرمال‌سازی آیتم‌های وابسته، اگر goal صفت متناظر از طریق یک candidate ‏ParamEnv یا AliasBound اثبات شده باشد، implها را در نظر نمی‌گیرد. این یعنی برای قیدهای whereای که نوع‌های وابسته را مقید نمی‌کنند، نوع‌های وابسته صلب باقی می‌مانند.

    استفاده از implها به قیدهای ناحیهٔ متفاوت می‌انجامد

    این برای پرهیز از قیدهای ناحیهٔ غیرضروری ناشی از اعمال implها لازم است.

    trait Trait<'a> {
    type Assoc;
}
impl Trait<'static> for u32 {
    type Assoc = u32;
}

fn bar<'b, T: Trait<'b>>() -> T::Assoc { todo!() }
fn foo<'a>()
where
    u32: Trait<'a>,
{
    // Normalizing the return type would use the impl, proving
    // the `T: Trait` where-bound would use the where-bound, resulting
    // in different region constraints.
    bar::<'_, u32>();
}

    RPITIT type_of cycles

    در حال حاضر اگر قیدهای where وجود داشته باشند باید از candidateهای impl پرهیز کنیم تا از چرخه‌های query برای RPITIT جلوگیری شود، #139762 را ببینید. به نظر من مطلوب است که برای رفع این مشکل، اتکا به نشت auto-trait هنگام محاسبهٔ RPITIT متوقف شود، #139788 را ببینید.

    use std::future::Future;
pub trait ReactiveFunction: Send {
    type Output;

    fn invoke(self) -> Self::Output;
}

trait AttributeValue {
    fn resolve(self) -> impl Future<Output = ()> + Send;
}

impl<F, V> AttributeValue for F
where
    F: ReactiveFunction<Output = V>,
    V: AttributeValue,
{
    async fn resolve(self) {
        // We're awaiting `<V as AttributeValue>::{synthetic#0}` here.
        // Normalizing that one via the the impl we're currently in
        // relies on `collect_return_position_impl_trait_in_trait_tys` which
        // ends up relying on auto-trait leakage when checking that the
        // opaque return type of this function implements the `Send` item
        // bound of the trait definition.
        self.invoke().resolve().await
    }
}

    تعریف صفت نمی‌تواند از نوع‌های وابستهٔ implهای همیشه قابل‌اعمال استفاده کند

    فرض T: Trait در تعریف صفت از نرمال‌سازی <Self as Trait>::Assoc به T با استفاده از blanket impl جلوگیری می‌کند. این به نظر محدودیتی تا حدی مطلوب است، هرچند نه فوق‌العاده.

    trait Eq<T> {}
impl<T> Eq<T> for T {}
struct IsEqual<T: Eq<U>, U>(T, U);

trait Trait: Sized {
    type Assoc;
    fn foo() -> IsEqual<Self, Self::Assoc> {
        //~^ ERROR the trait bound `Self: Eq<<Self as Trait>::Assoc>` is not satisfied
        todo!()
    }
}

impl<T> Trait for T {
    type Assoc = T;
}
