    Compiletest directives

    directiveها کامنت‌های ویژه‌ای هستند که به compiletest می‌گویند یک تست را چگونه بسازد و تفسیر کند. آن‌ها ممکن است در تست‌های run-make در rmake.rs هم بیایند.

    معمولاً پس از کامنت کوتاهی که هدف تست را توضیح می‌دهد قرار می‌گیرند. مجموعه‌های تست compiletest از //@ برای اعلام اینکه یک کامنت directive است استفاده می‌کنند. برای مثال، این تست از دستور //@ compile-flags برای مشخص‌کردن پرچم سفارشی‌ای استفاده می‌کند که هنگام کامپایل تست به rustc داده می‌شود:

    // Test the behavior of `0 - 1` when overflow checks are disabled.

//@ compile-flags: -C overflow-checks=off

fn main() {
    let x = 0 - 1;
    ...
}

    directiveها می‌توانند مستقل باشند (مثل //@ run-pass) یا مقدار بگیرند (مثل //@ compile-flags: -C overflow-checks=off).

    directiveها به‌صورت یکی در هر خط نوشته می‌شوند: نمی‌توانید چند directive را در یک خط بنویسید. برای مثال، اگر //@ only-x86 only-windows بنویسید، only-windows به‌عنوان کامنت تفسیر می‌شود، نه directive جداگانه.

    فهرست directiveهای compiletest

    در ادامه فهرست directiveهای compiletest آمده است. directiveها در صورت وجود به بخش‌هایی پیوند خورده‌اند که دستور را با جزئیات بیشتر شرح می‌دهند. ممکن است این فهرست جامع نباشد. معمولاً می‌توان directiveها را با مرور ساختار TestProps در directives.rs از منبع compiletest یافت.

    کنترل اینکه تست‌ها چه وقت اجرا شوند

    این directiveها برای نادیده‌گرفتن تست در برخی موقعیت‌ها به‌کار می‌روند، یعنی تست کامپایل یا اجرا نمی‌شود.

    • ignore-X که در آن X جزئیات هدف یا معیار دیگری است که بر اساس آن تست نادیده گرفته می‌شود (در ادامه ببینید)
    • only-X مثل ignore-X است، اما تست را فقط روی آن هدف یا مرحله اجرا می‌کند
    • ignore-auxiliary برای فایل‌هایی است که در یک یا چند فایل تست اصلی دیگر شرکت می‌کنند اما compiletest نباید سعی کند خود آن فایل را بسازد. لطفاً به تست اصلی‌ای که واقعاً از فایل کمکی استفاده می‌کند backlink بدهید.
    • ignore-test همیشه تست را نادیده می‌گیرد. از آن می‌توان برای غیرفعال‌کردن موقت تستی که فعلاً کار نمی‌کند استفاده کرد، اما می‌خواهید آن را درون درخت نگه دارید تا بعداً دوباره فعالش کنید.

    چند مثال برای X در ignore-X یا only-X:

    • یک target triple کامل: aarch64-apple-ios
    • Architecture: aarch64, arm, csky, mips, mips64, wasm32, x86_64, x86, …
    • OS: android, emscripten, freebsd, ios, linux, macos, windows, …
    • محیط (کلمهٔ چهارم target triple): gnu، msvc، musl
    • Pointer width: 32bit, 64bit
    • Endianness: endian-big
    • Stage: stage1, stage2
    • Binary format: elf
    • Channel: stable, beta
    • هنگام cross compile: cross-compile
    • هنگام استفاده از تست راه‌دور: remote
    • هنگام تست دیباگرهای مشخص: cdb، gdb، lldb
    • هنگام تطبیق نسخه‌های مشخص دیباگر: ignore-gdb-version
    • هنگام فعال‌بودن frontend موازی: ignore-parallel-frontend
    • حالت‌های مقایسهٔ مشخص: compare-mode-polonius، compare-mode-next-solver، compare-mode-split-dwarf، compare-mode-split-dwarf-single
    • دو حالت تست متفاوت که تست‌های coverage استفاده می‌کنند: ignore-coverage-map و ignore-coverage-run
    • When testing a dist toolchain: dist
      • این باید با COMPILETEST_ENABLE_DIST_TESTS=1 فعال شود
    • rustc_abi هدف: مثلاً rustc_abi-x86_64-sse2

    directiveهای زیر تنظیمات ساخت rustc و تنظیمات هدف را بررسی می‌کنند:

    • needs-asm-support — اگر معماری میزبان پشتیبانی پایدار از asm! نداشته باشد نادیده می‌گیرد. برای تست‌هایی که با --target به هدف‌های صریح cross-compile می‌کنند، به‌جای آن از needs-llvm-components استفاده کنید تا backend مناسب در دسترس باشد.
    • needs-asm-ret - اگر هدف دستور ret را در نحو assembly خود نداشته باشد نادیده می‌گیرد. بیشتر معماری‌های هدف این دستور را دارند، که برای تست‌های inline-assembly قابل‌حمل راحت است، اما برخی معماری‌ها (مثل ARM ۳۲ بیتی) آن را ندارند.
    • needs-profiler-runtime — اگر runtime مربوط به profiler برای هدف فعال نشده باشد (build.profiler = true در bootstrap.toml) تست را نادیده می‌گیرد
    • needs-sanitizer-support — اگر پشتیبانی از sanitizer برای هدف فعال نشده باشد (build.sanitizers = true در bootstrap.toml) نادیده می‌گیرد
    • needs-sanitizer-{address,hwaddress,leak,memory,thread} — اگر sanitizer متناظر برای هدف فعال نشده باشد نادیده می‌گیرد (به‌ترتیب AddressSanitizer، AddressSanitizer با کمک سخت‌افزار، LeakSanitizer، MemorySanitizer یا ThreadSanitizer)
    • needs-run-enabled — اگر تستی باشد که اجرا می‌شود و اجرا غیرفعال شده باشد نادیده می‌گیرد. اجرای تست‌ها را می‌توان با پرچم x test --run=never یا هنگام اجرا روی fuchsia غیرفعال کرد.
    • needs-unwind — اگر هدف از unwinding پشتیبانی نکند نادیده می‌گیرد
    • needs-rust-lld — اگر پشتیبانی از rust lld فعال نشده باشد (rust.lld = true در bootstrap.toml) نادیده می‌گیرد
    • needs-threads — اگر هدف پشتیبانی از threading نداشته باشد نادیده می‌گیرد
    • needs-subprocess — اگر هدف پشتیبانی از زیرفرایند نداشته باشد نادیده می‌گیرد
    • needs-symlink — اگر هدف از symlink پشتیبانی نکند نادیده می‌گیرد. این می‌تواند در ویندوز رخ دهد اگر توسعه‌دهنده مجوز symlink ممتاز را فعال نکرده باشد.
    • ignore-std-debug-assertions — اگر std با debug assertions ساخته شده باشد نادیده می‌گیرد.
    • needs-std-debug-assertions — اگر std بدون debug assertions ساخته شده باشد نادیده می‌گیرد.
    • ignore-std-remap-debuginfo — اگر std با بازنگاشت منابعش ساخته شده باشد نادیده می‌گیرد.
    • needs-std-remap-debugino — اگر std بدون بازنگاشت منابعش ساخته شده باشد نادیده می‌گیرد.
    • ignore-rustc-debug-assertions — اگر rustc با debug assertions ساخته شده باشد نادیده می‌گیرد.
    • needs-rustc-debug-assertions — اگر rustc بدون debug assertions ساخته شده باشد نادیده می‌گیرد.
    • needs-target-has-atomic — اگر هدف از همهٔ پهناهای atomic مشخص‌شده پشتیبانی نکند نادیده می‌گیرد، مثلاً تستی با //@ needs-target-has-atomic: 8, 16, ptr فقط وقتی اجرا می‌شود که از فهرست جداشده با ویرگول پهناهای atomic پشتیبانی کند.
    • needs-dynamic-linking — اگر هدف از لینک پویا پشتیبانی نکند نادیده می‌گیرد (که مستقل از ناتوانی در ساخت نوع‌های crate با نام dylib و cdylib است)
    • needs-crate-type — اگر پلتفرم هدف از یک یا چند نوع crate در فهرست جداشده با ویرگول پشتیبانی نکند نادیده می‌گیرد. برای مثال، //@ needs-crate-type: cdylib, proc-macro باعث می‌شود تست روی هدف wasm32-unknown-unknown نادیده گرفته شود چون این هدف از نوع crate با نام proc-macro پشتیبانی نمی‌کند.
    • needs-target-std — ignores if target platform does not have std support.
      • #![no_std]/#![no_core] و needs-target-std ضمنی برای تست‌های codegen را هم ببینید.
    • ignore-backends — backendهای فهرست‌شده را که با نویسه‌های فاصله جدا شده‌اند نادیده می‌گیرد. لطفاً توجه کنید این directive را می‌توان با پرچم خط فرمان --bypass-ignore-backends=[BACKEND] بازنویسی کرد.
    • needs-backends — تست را فقط اگر backend تولید کد فعلی فهرست شده باشد اجرا می‌کند.
    • needs-offload — اگر backend ما در LLVM با پشتیبانی offload ساخته نشده باشد نادیده می‌گیرد.
    • needs-enzyme — اگر زیرماژول Enzyme ما ساخته نشده باشد نادیده می‌گیرد.

    directiveهای زیر پشتیبانی LLVM را بررسی می‌کنند:

    • exact-llvm-major-version: 19 — اگر نسخهٔ major در llvm با نسخهٔ major مشخص‌شدهٔ llvm مطابقت نداشته باشد نادیده می‌گیرد.
    • min-llvm-version: 13.0 — اگر نسخهٔ LLVM کمتر از مقدار داده‌شده باشد نادیده می‌شود
    • min-system-llvm-version: 12.0 — اگر از LLVM سیستمی استفاده شود و نسخهٔ آن کمتر از مقدار داده‌شده باشد نادیده می‌شود
    • max-llvm-major-version: 19 — اگر نسخهٔ major در LLVM بالاتر از نسخهٔ major داده‌شده باشد نادیده می‌شود
    • ignore-llvm-version: 9.0 — یک نسخهٔ مشخص LLVM را نادیده می‌گیرد
    • ignore-llvm-version: 7.0 - 9.9.9 — نسخه‌های LLVM در یک بازه (شامل دو سر) را نادیده می‌گیرد
    • needs-llvm-components: powerpc — اگر مؤلفهٔ مشخص LLVM ساخته نشده باشد نادیده می‌گیرد. نکته: اگر مؤلفه وجود نداشته باشد، تست در CI شکست می‌خورد (وقتی COMPILETEST_REQUIRE_ALL_LLVM_COMPONENTS تنظیم شده باشد).
    • needs-forced-clang-based-tests — test is ignored unless the environment variable RUSTBUILD_FORCE_CLANG_BASED_TESTS is set, which enables building clang alongside LLVM
      • این فقط در دو job از CI تنظیم شده است (test-x86_64-gnu-debug و test-aarch64-gnu-debug)، که فقط زیرمجموعه‌ای از تست‌های run-make را اجرا می‌کنند. تست‌های دیگر با این directive اصلاً اجرا نمی‌شوند، که معمولاً چیزی نیست که بخواهید.

    directive با نام edition

    directive با نام //@ edition می‌تواند edition دقیق، بازه‌ای کران‌دار از editionها، یا بازهٔ نیمه‌باز با کران چپ از editionها را بگیرد. این بر اینکه ./x test از کدام edition برای اجرای تست استفاده کند اثر می‌گذارد.

    برای مثال:

    • تستی با directive با نام //@ edition: 2018 فقط تحت edition 2018 اجرا می‌شود.
    • تستی با directive با نام //@ edition: 2015..2021 می‌تواند تحت editionهای 2015 و 2018 اجرا شود، پس کران بالا شامل نمی‌شود، درست مثل Rust (توجه کنید معادلی برای ..= در Rust که کران بالا را شامل می‌شود وجود ندارد). اما CI تست را فقط با پایین‌ترین edition در بازه (در این مثال 2015) اجرا می‌کند.
    • تستی با directive با نام //@ edition: 2018.. تحت edition 2018 یا بالاتر اجرا می‌شود. اما CI تست را فقط با پایین‌ترین edition در بازه (در این مثال 2018) اجرا می‌کند.

    همچنین می‌توانید با دادن آرگومان -- --edition= ./x test را مجبور به استفاده از edition مشخصی کنید. اما تست‌هایی با directive با نام //@ edition مقدار داده‌شده به آرگومان را محدود (clamp) می‌کنند. برای مثال اگر ./x test -- --edition=2015 را اجرا کنیم:

    • تستی با //@ edition: 2018 با edition 2018 اجرا می‌شود.
    • تستی با //@ edition: 2015..2021 با edition 2015 اجرا می‌شود.
    • تستی با //@ edition: 2018.. با edition 2018 اجرا می‌شود.

    Tool-specific directives

    directiveهای زیر بر نحوهٔ فراخوانی برخی ابزارهای خط فرمان اثر می‌گذارند، در مجموعه‌های تستی که از آن ابزارها استفاده می‌کنند:

    • skip-filecheck avoids running LLVM’s FileCheck tool in tests that would normally run it to check output.
      • توسط تست‌های codegen، تست‌های assembly و تست‌های mir-opt استفاده می‌شود.
    • filecheck-flags adds extra flags when running LLVM’s FileCheck tool.
      • توسط تست‌های codegen، تست‌های assembly، و تست‌های MIR-opt استفاده می‌شود.
    • llvm-cov-flags adds extra flags when running LLVM’s llvm-cov tool.
      • توسط تست‌های coverage در حالت coverage-run استفاده می‌شود.

    Tidy specific directives

    directiveهای زیر نحوهٔ اعتبارسنجی تست‌ها توسط اسکریپت tidy را کنترل می‌کنند.

    • ignore-tidy-target-specific-tests بررسی لزوم مؤلفهٔ مناسب LLVM (از طریق directive با نام needs-llvm-components) را وقتی تست برای هدف مشخصی (از طریق پرچم --target در directive با نام compile-flag) کامپایل می‌شود غیرفعال می‌کند.
    • unused-revision-names - بررسی‌های tidy برای ذکر نام‌های ناشناختهٔ revision را سرکوب می‌کند.

    Substitutions

    مقادیر directive از جایگزینی چند متغیر پشتیبانی می‌کنند که با مقدار متناظرشان جایگزین می‌شوند. برای مثال، اگر باید پرچم کامپایلر همراه با مسیر یک فایل مشخص بدهید، چیزی شبیه این می‌تواند کار کند:

    //@ compile-flags: --remap-path-prefix={{src-base}}=/the/src

    که در آن نگهبان {{src-base}} با مسیر مناسب که در ادامه شرح داده شده جایگزین می‌شود:

    • {{cwd}}: The directory where compiletest is run from. This may not be the root of the checkout, so you should avoid using it where possible.
      • Examples: /path/to/rust, /path/to/build/root
    • {{src-base}}: The directory where the test is defined. This is equivalent to $DIR for output normalization.
      • Example: /path/to/rust/tests/ui/error-codes
    • {{build-base}}: The base directory where the test’s output goes. This is equivalent to $TEST_BUILD_DIR for output normalization.
      • Example: /path/to/rust/build/x86_64-unknown-linux-gnu/test/ui
    • {{rust-src-base}}: پوشهٔ sysroot که libstd/libcore/… در آن قرار دارند
    • {{sysroot-base}}: Path of the sysroot directory used to build the test.
      • عمدتاً برای تست‌های ui-fulldeps که کامپایلر را از طریق API اجرا می‌کنند.
    • {{target-linker}}: Linker that would be passed to -Clinker for this test, or blank if no linker override is active.
      • عمدتاً برای تست‌های ui-fulldeps که کامپایلر را از طریق API اجرا می‌کنند.
    • {{target}}: The target the test is compiling for
      • Example: x86_64-unknown-linux-gnu

    برای نمونه‌ای از تستی که از این جایگزینی استفاده می‌کند tests/ui/argfile/commandline-argfile.rs را ببینید.

    افزودن یک directive

    اگر نیاز باشد ویژگی یا رفتار تستی را به‌صورت جداگانه برای هر تست تعریف کنید، directive جدیدی اضافه می‌کنید. یک ویژگی directive در زمان اجرا نقش مخزن پشتیبان directive را دارد (مقدار فعلی دستور را نگه می‌دارد).

    برای افزودن ویژگی directive جدید:

    1. اعلان pub struct TestProps را در src/tools/compiletest/src/directives.rs بیابید و ویژگی عمومی جدید را به انتهای اعلان اضافه کنید.
    2. بلوک پیاده‌سازی impl TestProps را که بلافاصله پس از اعلان struct می‌آید بیابید و ویژگی جدید را با مقدار پیش‌فرضش مقداردهی اولیه کنید.

    افزودن parser جدید برای directive

    وقتی compiletest به یک فایل تست می‌رسد، آن را خط به خط تجزیه می‌کند با فراخوانی هر parser که در بلوک پیاده‌سازی struct با نام Config تعریف شده، که آن هم در src/tools/compiletest/src/directives.rs است (توجه کنید که بلوک اعلان struct با نام Config در src/tools/compiletest/src/common.rs قرار دارد). متد load_from() در TestProps سعی می‌کند خط فعلی متن را به هر parser بدهد، که آن هم معمولاً بررسی می‌کند آیا خط با directive کامنت‌شدهٔ (//@) مشخصی شروع می‌شود، مثل //@ must-compile-successfully یا //@ failure-status. فاصله پس از نشانگر کامنت اختیاری است.

    parserها مقدار پیش‌فرض ویژگی directive را صرفاً با مشخص‌شدن در فایل تست به‌عنوان directive یا با مشخص‌شدن مقدار پارامتر در فایل تست، بسته به directive، بازنویسی می‌کنند.

    parserهایی که در impl Config تعریف می‌شوند معمولاً parse_<directive-name> نام دارند (توجه کنید <directive-command> به شکل kebab-case به snake-case یعنی <directive_command> تبدیل می‌شود). impl Config چند parser «سطح پایین» هم تعریف می‌کند که تجزیهٔ الگوهای رایج را ساده می‌کنند، مثل حضور یا عدم حضور ساده (parse_name_directive())، directive:parameter(s) (parse_name_value_directive())، تجزیهٔ اختیاری فقط اگر attribute با نام cfg مشخصی تعریف شده باشد (has_cfg_prefix()) و بسیاری دیگر. parserهای سطح پایین نزدیک انتهای بلوک impl Config هستند؛ حتماً آن‌ها و parserهای مرتبطی را که بلافاصله بالاتر هستند ببینید تا نحوهٔ استفاده‌شان را بدانید و از نوشتن کد تجزیهٔ اضافی غیرضروری پرهیز کنید.
