    UI tests

    تست‌های UI یک مجموعهٔ تست مشخص از compiletest هستند.

    Introduction

    تست‌های tests/ui مجموعه‌ای از تست‌های همه‌منظوره‌اند که عمدتاً بر اعتبارسنجی خروجی کنسول کامپایلر تمرکز دارند، اما برای بسیاری کارهای دیگر هم می‌توان از آن‌ها استفاده کرد. برای مثال، می‌توان تست‌ها را طوری هم پیکربندی کرد که برنامهٔ حاصل را اجرا کنند تا رفتارش را تأیید کنند.

    برای مرور هدف هر زیرپوشه در tests/ui، README.md را ببینید. این وقتی مفید است که تست جدیدی می‌نویسید و به دنبال دسته‌ای برای قراردادن آن هستید.

    اگر باید با تست‌های cross-compile از نوع #![no_std] کار کنید، فصل تست کمکی minicore را ببینید.

    ساختار کلی یک تست

    یک تست شامل فایل منبع Rust است که در پوشهٔ tests/ui قرار دارد. تست‌ها باید در زیرپوشهٔ مناسب قرار بگیرند بر اساس هدف و دستهٔ تست — قراردادن تست مستقیماً در tests/ui مجاز نیست.

    Compiletest از rustc برای کامپایل تست استفاده می‌کند و خروجی را با خروجی مورد انتظار که در فایل .stdout یا .stderr کنار تست ذخیره شده مقایسه می‌کند. برای اطلاعات بیشتر مقایسهٔ خروجی را ببینید.

    علاوه بر این، خطاها و هشدارها باید با کامنت‌هایی در فایل منبع annotate شوند. برای اطلاعات بیشتر annotationهای خطا را ببینید.

    directiveهای compiletest به شکل کامنت‌های ویژه با پیشوند //@ نحوهٔ کامپایل تست و رفتار مورد انتظار را کنترل می‌کنند.

    انتظار می‌رود تست‌ها در کامپایل شکست بخورند، چون بیشتر تست‌ها خطاهای کامپایلر را می‌آزمایند. می‌توانید این رفتار را با یک directive تغییر دهید، به کنترل انتظارات pass/fail نگاه کنید.

    به‌طور پیش‌فرض، یک تست به‌صورت فایل دودویی اجرایی ساخته می‌شود. اگر نوع crate دیگری لازم دارید، می‌توانید با attribute با نام #![crate_type] آن را مطابق نیاز تنظیم کنید.

    Output comparison

    تست‌های UI خروجی مورد انتظار کامپایلر را در snapshotهای .stderr و .stdout کنار تست ذخیره می‌کنند. معمولاً این فایل‌ها را با گزینهٔ خط فرمان --bless تولید می‌کنید، و سپس دستی بررسی می‌کنید تا ببینید آنچه انتظار دارید را در بر دارند.

    خروجی نرمال‌سازی می‌شود تا تفاوت‌های ناخواسته نادیده گرفته شوند، بخش نرمال‌سازی را ببینید. اگر فایل وجود نداشته باشد، compiletest انتظار دارد خروجی متناظر خالی باشد.

    دلیل رایج استفاده از نرمال‌سازی، revisionها و بیشتر ابزارهای بعدی، در نظر‌گرفتن تفاوت‌های پلتفرم است. جایگزین‌های این ابزارها را در نظر بگیرید، مثلاً استفاده از ABI با نام extern "rust-invalid" که روی هر پلتفرم نامعتبر است، به‌جای اینکه تست را طوری اصلاح کنید که از cross-compilation استفاده کند و هر ABI نامعتبر ممکن را تست کند.

    می‌تواند چند فایل stdout/stderr وجود داشته باشد. شکل کلی آن این است:

    *test-name*`.`*revision*`.`*compare_mode*`.`*extension*
    • test-name نمی‌تواند نقطه داشته باشد. دلیلش این است که شکل کلی نام فایل‌های خروجی تست پیش‌بینی‌پذیر باشد و بتوانیم برای ردیابی فایل‌های خروجی سرگردان تست الگو را تطبیق دهیم.
    • revision نام revision است. اگر از revision استفاده نشود، این بخش گنجانده نمی‌شود.
    • compare_mode حالت مقایسه است. این فقط وقتی بررسی می‌شود که حالت مقایسهٔ داده‌شده فعال باشد. اگر فایل وجود نداشته باشد، compiletest فایل بدون حالت مقایسه را بررسی می‌کند.
    • extension is the kind of output being checked:
      • stderr — compiler stderr
      • stdout — compiler stdout
      • run.stderr — stderr هنگام اجرای تست
      • run.stdout — stdout هنگام اجرای تست
      • 64bit.stderr — stderr کامپایلر با directive با نام stderr-per-bitwidth روی هدف ۶۴ بیتی
      • 32bit.stderr — stderr کامپایلر با directive با نام stderr-per-bitwidth روی هدف ۳۲ بیتی

    یک مثال ساده foo.stderr کنار تست foo.rs است. مثال پیچیده‌تر foo.my-revision.polonius.stderr است.

    چند directive هست که نحوهٔ بررسی فایل‌های خروجی توسط compiletest را تغییر می‌دهند:

    • stderr-per-bitwidth — فایل‌های خروجی جداگانه را بر اساس پهنای اشاره‌گر هدف بررسی می‌کند. استفاده از directive با نام normalize-stderr را به‌جای آن در نظر بگیرید (نرمال‌سازی را ببینید).
    • dont-check-compiler-stderr — stderr کامپایلر را نادیده می‌گیرد.
    • dont-check-compiler-stdout — stdout کامپایلر را نادیده می‌گیرد.
    • compare-output-by-lines — برخی تست‌ها ترتیب خروجی غیرقطعی دارند، پس باید خط به خط مقایسه کنیم.

    تست‌های UI با پرچم -Zdeduplicate-diagnostics=no اجرا می‌شوند، که سازوکار داخلی حذف تکرار پیام‌های تشخیصی در rustc را غیرفعال می‌کند. یعنی ممکن است در خروجی چند پیام تکراری ببینید. این به روشن‌شدن موقعیت‌هایی که پیام‌های تشخیصی تکراری تولید می‌شوند کمک می‌کند.

    Normalization

    خروجی کامپایلر نرمال‌سازی می‌شود تا تفاوت‌های خروجی بین پلتفرم‌ها، عمدتاً دربارهٔ نام فایل‌ها، حذف شود.

    Compiletest جایگزینی‌های زیر را روی خروجی کامپایلر انجام می‌دهد:

    • پوشه‌ای که تست در آن تعریف شده با $DIR جایگزین می‌شود. مثال: /path/to/rust/tests/ui/error-codes
    • پوشهٔ منبع کتابخانهٔ استاندارد با $SRC_DIR جایگزین می‌شود. مثال: /path/to/rust/library
    • شمارهٔ خط و ستون برای مسیرهای درون $SRC_DIR با LL:COL جایگزین می‌شود. این کمک می‌کند تغییر در چیدمان کتابخانهٔ استاندارد باعث تغییرات گسترده در فایل‌های .stderr نشود. مثال: $SRC_DIR/alloc/src/sync.rs:53:46
    • پوشهٔ پایه‌ای که خروجی تست در آن می‌رود با $TEST_BUILD_DIR جایگزین می‌شود. این فقط در چند شرایط نادر پیش می‌آید. مثال: /path/to/rust/build/x86_64-unknown-linux-gnu/test/ui
    • پوشهٔ واقعی منبع کتابخانهٔ استاندارد با $SRC_DIR_REAL جایگزین می‌شود.
    • پوشهٔ واقعی منبع کامپایلر با $COMPILER_DIR_REAL جایگزین می‌شود.
    • tabها با \t جایگزین می‌شوند.
    • بک‌اسلش‌ها (\) درون مسیرها به اسلش (/) تبدیل می‌شوند (با یک heuristic). این به نرمال‌سازی تفاوت‌ها با مسیرهای سبک Windows کمک می‌کند.
    • خطوط جدید CRLF به LF تبدیل می‌شوند.
    • annotationهای خط خطا مثل //~ ERROR some message حذف می‌شوند.
    • هش‌های مختلف نمادهای v0 و legacy با جانگهدارهایی مثل [HASH] یا <SYMBOL_HASH> جایگزین می‌شوند.

    علاوه بر این، کامپایلر با پرچم -Z ui-testing اجرا می‌شود که باعث می‌شود خود کامپایلر برخی تغییرات را روی خروجی تشخیصی اعمال کند تا برای تست UI مناسب‌تر باشد.

    برای مثال، شمارهٔ خطوط را در خروجی ناشناس می‌کند (شمارهٔ خطوطی که قبل از هر خط منبع می‌آیند با LL جایگزین می‌شوند). در موقعیت‌های بسیار نادر، این حالت را می‌توان با directive با نام //@ compile-flags: -Z ui-testing=no غیرفعال کرد.

    هنگام استفاده از -Z ui-testing=no، آرگومان --diagnostic-width هم باید تنظیم شود تا از اینکه تست‌ها بسته به پهنای ترمینالی که مجموعهٔ تست UI در آن اجرا می‌شود بگذرند یا شکست بخورند جلوگیری شود.

    نکته: شمارهٔ خط و ستون در خطوط --> که به تست اشاره می‌کنند نرمال‌سازی نمی‌شوند و همان‌طور که هستند باقی می‌مانند. این تضمین می‌کند کامپایلر همچنان به مکان درست اشاره کند، و فایل‌های stderr خوانا می‌مانند. ایده‌آل این است که همهٔ اطلاعات خط/ستون حفظ شوند، اما تغییرات کوچک در منبع باعث diffهای بزرگ و تعارض‌های merge و خطاهای تست بیشتری می‌شود.

    گاهی این نرمال‌سازی‌های داخلی کافی نیستند. در چنین مواردی، می‌توانید با directiveهای normalize-* قواعد نرمال‌سازی سفارشی بدهید، مثلاً

    //@ normalize-stdout: "foo" -> "bar"
//@ normalize-stderr: "foo" -> "bar"
//@ normalize-stderr-32bit: "fn\(\) \(32 bits\)" -> "fn\(\) \($$PTR bits\)"
//@ normalize-stderr-64bit: "fn\(\) \(64 bits\)" -> "fn\(\) \($$PTR bits\)"

    این به تست می‌گوید روی پلتفرم‌های ۳۲ بیتی، هر وقت کامپایلر fn() (32 bits) را در stderr می‌نویسد، باید به‌جای آن به fn() ($PTR bits) نرمال‌سازی شود. برای ۶۴ بیتی هم مشابه است. جایگزینی با regexها و با نوع regex پیش‌فرض ارائه‌شده توسط crate با نام regex انجام می‌شود.

    فایل مرجع متناظر از خروجی نرمال‌سازی‌شده استفاده می‌کند تا هم پلتفرم‌های ۳۲ بیتی و هم ۶۴ بیتی را تست کند:

    ...
   |
   = note: source type: fn() ($PTR bits)
   = note: target type: u16 (16 bits)
...

    برای یک نمونهٔ کاربرد عینی ui/transmute/main.rs و main.stderr را ببینید.

    Error annotations

    annotationهای خطا خطاهایی را مشخص می‌کنند که انتظار می‌رود کامپایلر صادر کند. آن‌ها به خطی از منبع که خطا در آن است «متصل» می‌شوند.

    fn main() {
    boom  //~ ERROR cannot find value `boom` in this scope [E0425]
}

    هرچند تست‌های UI فایل .stderr دارند که کل خروجی کامپایلر را شامل می‌شود، تست‌های UI لازم دارند خطاها درون منبع هم annotate شوند. این افزونگی به پرهیز از اشتباه کمک می‌کند، چون فایل‌های .stderr معمولاً خودکار تولید می‌شوند. همچنین با نگاه‌کردن به یک فایل به‌جای مقایسهٔ فایل .stderr با منبع، کمک می‌کند ببینیم span خطا کجا باید اشاره کند. در نهایت تضمین می‌کنند هیچ خطای غیرمنتظرهٔ اضافه‌ای تولید نمی‌شود.

    چند شکل دارند، اما عموماً کامنتی هستند با سطح پیام تشخیصی (مثل ERROR) و زیررشته‌ای از خروجی خطای مورد انتظار. لازم نیست کل پیام را بنویسید، اما حتماً بخش مهم پیام را بگنجانید تا مستندسازی خودکار باشد.

    بیشتر annotationهای خطا باید با خط پیام تشخیصی تطبیق داده شوند. چند راه برای تطبیق پیام با خط هست (مثال‌ها را در ادامه ببینید):

    • ~: سطح خطا و پیام را با خط فعلی مرتبط می‌کند
    • ~^: سطح خطا و پیام را با خط annotation خطای قبلی مرتبط می‌کند. هر caret (^) که اضافه کنید یک خط به این می‌افزاید، پس ~^^^ سه خط بالاتر از خط annotation خطاست.
    • ~|: سطح خطا و پیام را با همان خطِ کامنت قبلی مرتبط می‌کند. این وقتی چند پیام با یک خط مرتبط‌اند از استفاده از چند caret راحت‌تر است.
    • ~v: سطح خطا و پیام را با خط annotation خطای بعدی مرتبط می‌کند. هر نماد (v) که اضافه کنید یک خط به این می‌افزاید، پس ~vvv سه خط پایین‌تر از خط annotation خطاست.

    Example:

    let _ = same_line; //~ ERROR undeclared variable
fn meow(_: [u8]) {}
//~^ ERROR unsized
//~| ERROR anonymous parameters

    نویسهٔ فاصله بین //~ (یا شکل‌های دیگر آن) و متن بعدی بی‌اهمیت است (یعنی تفاوت معنایی بین //~ ERROR و //~ERROR وجود ندارد، هرچند اولی در کدبیس رایج‌تر است).

    ~? <diagnostic kind> (مثلاً ~? ERROR) برای تطبیق پیام‌های تشخیصی بدون اطلاعات خط به‌کار می‌رود، یا آن‌هایی که اطلاعات خطشان بیرون از فایل تست اصلی است1. این annotationها را می‌توان روی هر خطی از فایل تست گذاشت.

    Error annotation examples

    در ادامه مثال‌هایی از annotationهای خطا روی خطوط مختلف منبع تست UI آمده است.

    قرارگرفته روی خط خطا

    از اصطلاح //~ ERROR استفاده کنید:

    fn main() {
    let x = (1, 2, 3);
    match x {
        (_a, _x @ ..) => {} //~ ERROR `_x @` is not allowed in a tuple
        _ => {}
    }
}

    قرارگرفته زیر خط خطا

    از اصطلاح //~^ با تعداد caret در رشته برای نشان‌دادن تعداد خطوط بالاتر استفاده کنید. در مثال زیر، خط خطا چهار خط بالاتر از خط annotation خطاست، پس چهار caret در annotation گنجانده شده است.

    fn main() {
    let x = (1, 2, 3);
    match x {
        (_a, _x @ ..) => {}  // <- the error is on this line
        _ => {}
    }
}
//~^^^^ ERROR `_x @` is not allowed in a tuple

    استفاده از همان خط خطای تعریف‌شده در خط annotation خطای بالا

    از اصطلاح //~| برای تعریف همان خط خطای خط annotation خطای بالا استفاده کنید:

    struct Binder(i32, i32, i32);

fn main() {
    let x = Binder(1, 2, 3);
    match x {
        Binder(_a, _x @ ..) => {}  // <- the error is on this line
        _ => {}
    }
}
//~^^^^ ERROR `_x @` is not allowed in a tuple struct
//~| ERROR this pattern has 1 field, but the corresponding tuple struct has 3 fields [E0023]

    قرارگرفته بالای خط خطا

    از اصطلاح //~v با تعداد v در رشته برای نشان‌دادن تعداد خطوط پایین‌تر استفاده کنید. این معمولاً در تست‌های lexer یا parser برای تطبیق خطاهایی مثل delimiter بسته‌نشده یا literal بسته‌نشده که در پایان فایل رخ می‌دهند به‌کار می‌رود.

    // ignore-tidy-trailing-newlines
//~v ERROR this file contains an unclosed delimiter
fn main((ؼ

    خطا بدون اطلاعات خط

    از //~? برای تطبیق خطا بدون اطلاعات خط استفاده کنید. //~? دقیق است و اگر اطلاعات خط خطا در دسترس باشد آن را تطبیق نمی‌دهد. برای تست‌هایی که می‌خواهند پیام‌های تشخیصی کامپایلر را تطبیق دهند باید بر //@ error-pattern ترجیح داده شود، چون //@ error-pattern نادقیق و غیرجامع است.

    //@ compile-flags: --print yyyy

//~? ERROR unknown print request: `yyyy`

    error-pattern

    directive با نام error-pattern را می‌توان برای پیام‌های زمان اجرا که span مشخصی ندارند، یا در موارد استثنایی برای پیام‌های زمان کامپایل به‌کار برد.

    این تست را در نظر بگیرید:

    fn main() {
    let a: *const [_] = &[1, 2, 3];
    unsafe {
        let _b = (*a)[3];
    }
}

    می‌خواهیم مطمئن شویم این «index out of bounds» نشان می‌دهد، اما نمی‌توانیم از annotation با نام ERROR استفاده کنیم چون خطای زمان اجرا span ندارد. آن‌گاه وقت استفاده از directive با نام error-pattern است:

    //@ error-pattern: index out of bounds
fn main() {
    let a: *const [_] = &[1, 2, 3];
    unsafe {
        let _b = (*a)[3];
    }
}

    برای تست سخت‌گیرانهٔ خروجی زمان کامپایل، تا جای ممکن از annotationهای خط //~ استفاده کنید، از جمله annotationهای //~? برای پیام‌های تشخیصی بدون span.

    اگر خروجی زمان کامپایل به هدف وابسته یا بیش‌ازحد مفصل است، از directive با نام //@ dont-require-annotations: <diagnostic-kind> استفاده کنید تا بررسی annotationهای خط غیرجامع شود. در این حالت برخی پیام‌های کامپایلر ممکن است بدون annotation بمانند.

    برای بررسی خروجی زمان اجرا، //@ check-run-results ممکن است ترجیح داده شود.

    فقط وقتی هیچ‌یک از موارد بالا کار نمی‌کند از error-pattern استفاده کنید، مثل وقتی که یک الگوی رشته‌ای مشخص را در خروجی panic زمان اجرا می‌یابید.

    annotationهای خط //~ و error-pattern سازگارند و می‌توان در یک تست با هم به‌کار برد.

    انواع پیام تشخیصی‌ای که می‌توانید داشته باشید این‌هاست:

    • NOTE
    • HELP
    • SUGGESTION
    • RAW

    نوع SUGGESTION برای مشخص‌کردن متن جایگزین مورد انتظار برای یک پیشنهاد تشخیصی به‌کار می‌رود. نوع RAW را می‌توان برای تطبیق خطوط خروجی غیرساختاریافته‌ای به‌کار برد که گاهی کامپایلر به‌جای یا علاوه بر JSON ساختاریافته صادر می‌کند.

    انواع ERROR و WARN به‌طور پیش‌فرض باید با annotationهای خط //~ به‌طور جامع پوشش داده شوند.

    انواع دیگر فقط وقتی باید annotate شوند که دست‌کم یک annotation از آن نوع در فایل تست ظاهر شود. برای مثال، یک //~ NOTE لازم می‌کند همهٔ //~ NOTEهای دیگر در فایل هم صراحتاً نوشته شوند.

    از directive با نام //@ dont-require-annotations برای انصراف از annotationهای جامع استفاده کنید. مثلاً از //@ dont-require-annotations: NOTE برای annotate‌کردن انتخابی noteها استفاده کنید. از استفاده از این directive برای ERRORها و WARNing‌ها پرهیز کنید، مگر اینکه دلیل جدی باشد، مثل خروجی کامپایلر وابسته به هدف.

    برخی پیام‌های تشخیصی هرگز لازم نیست annotate شوند، صرف‌نظر از نوع یا directiveها. نمونه‌ها خطوط ثانویهٔ پیام‌های تشخیصی چندخطی، یا پیام‌های فراگیر مثل aborting due to N previous errors هستند.

    تست‌های UI به‌طور پیش‌فرض از پرچم -A unused برای نادیده‌گرفتن همهٔ هشدارهای unused استفاده می‌کنند، چون هشدارهای unused معمولاً کانون تست نیستند. اما نمونه‌کدهای ساده اغلب هشدار unused دارند. اگر تست به‌طور مشخص هشدار unused را می‌آزماید، فقط attribute با نام #![warn(unused)] مناسب را در صورت نیاز اضافه کنید.

    cfg revisions

    هنگام استفاده از revisionها، می‌توان پیام‌های مختلف را بسته به revision فعلی به‌طور شرطی بررسی کرد. این کار با قرار‌دادن نام cfg مربوط به revision در قلاب انجام می‌شود، مثل این:

    //@ edition:2018
//@ revisions: mir thir
//@[thir] compile-flags: -Z thir-unsafeck

async unsafe fn f() {}

async fn g() {
    f(); //~ ERROR call to unsafe function is unsafe
}

fn main() {
    f(); //[mir]~ ERROR call to unsafe function is unsafe
}

    در این مثال، پیام خطای دوم فقط در revision با نام mir صادر می‌شود. revision با نام thir فقط خطای اول را صادر می‌کند.

    اگر cfg باعث شود کامپایلر خروجی متفاوتی صادر کند، یک تست می‌تواند چند فایل .stderr برای خروجی‌های مختلف داشته باشد. در مثال بالا، یک فایل .mir.stderr و یک فایل .thir.stderr با خروجی‌های متفاوت revisionهای مختلف وجود خواهد داشت.

    نکته: revisionهای cfg درون کد منبع با attributeهای #[cfg] هم کار می‌کنند.

    طبق قرارداد، cfg با نام FALSE برای داشتن پیکربندی همیشه‌نادرست به‌کار می‌رود.

    کنترل انتظارات pass/fail

    به‌طور پیش‌فرض، انتظار می‌رود یک تست UI خطای کامپایل تولید کند چون بیشتر تست‌ها ورودی نامعتبر و پیام‌های تشخیصی خطا را بررسی می‌کنند. اما می‌توانید تست‌های UI‌ای هم بسازید که انتظار می‌رود کامپایل در آن‌ها موفق شود، و حتی می‌توانید برنامهٔ حاصل را اجرا کنید. فقط یکی از directiveهای زیر را اضافه کنید:

    • Pass directives:
      • //@ check-pass — کامپایل باید موفق شود اما codegen را رد می‌کند (که گران است و در بیشتر موارد نباید شکست بخورد).
      • //@ build-pass — کامپایل و لینک باید موفق شوند اما فایل دودویی حاصل را اجرا نمی‌کند.
      • //@ run-pass — کامپایل باید موفق شود و اجرای فایل دودویی حاصل باید با کد 0 خارج شود که نشان‌دهندهٔ موفقیت است.
    • Fail directives:
      • //@ check-fail — کامپایل باید شکست بخورد (فاز codegen رد می‌شود). این پیش‌فرض تست‌های UI است.
      • //@ build-fail — compilation should fail during the codegen phase. This will run rustc twice:
        • بار اول برای اطمینان از موفقیت کامپایل بدون فاز codegen است
        • بار دوم برای اطمینان از شکست کامپایل کامل است
      • //@ run-fail — کامپایل باید موفق شود، اما اجرای فایل دودویی حاصل باید با کدی در بازهٔ 1..=127 خارج شود که نشان‌دهندهٔ شکست عادی است. روی هدف‌های بدون پشتیبانی از unwind، crashها هم پذیرفته می‌شوند.
      • //@ run-crash — compilation should succeed, but running the resulting binary should fail with a crash. Crashing is defined as “not exiting with a code in the range 0..=127”.
        • مثال در لینوکس: خاتمه با SIGABRT یا SIGSEGV.
        • مثال در ویندوز: خروج با کد STATUS_ILLEGAL_INSTRUCTION (0xC000001D).
      • //@ run-fail-or-crash — کامپایل باید موفق شود، اما اجرای فایل دودویی حاصل باید یا run-fail یا run-crash باشد. وقتی مفید است که تستی روی برخی هدف‌ها crash کند اما روی بقیه فقط شکست بخورد.

    برای تست‌های run-pass، run-fail، run-crash و run-fail-or-crash، خروجی خود برنامه به‌طور پیش‌فرض بررسی نمی‌شود.

    اگر می‌خواهید خروجی اجرای برنامه را بررسی کنید، directive با نام check-run-results را بگنجانید. این فایل‌های .run.stderr و .run.stdout را برای مقایسه با خروجی واقعی برنامه بررسی می‌کند.

    تست‌هایی که directiveهای *-pass دارند را می‌توان با گزینهٔ خط فرمان --pass بازنویسی کرد:

    ./x test tests/ui --pass check

    گزینهٔ --pass فقط بر تست‌های UI اثر می‌گذارد. استفاده از --pass check می‌تواند مجموعهٔ تست UI را بسیار سریع‌تر اجرا کند (روی سیستم من تقریباً دو برابر سریع‌تر)، هرچند بدیهی است به همان اندازه چیز را نمی‌آزماید.

    directive با نام no-pass-override را می‌توان برای نادیده‌گرفتن پرچم خط فرمان --pass به‌کار برد اگر تست با آن بازنویسی درست کار نکند.

    Known bugs

    directive با نام known-bug را می‌توان برای تست‌هایی به‌کار برد که باگ شناخته‌شده‌ای را نشان می‌دهند که هنوز رفع نشده است. افزودن تست برای باگ‌های شناخته‌شده به چند دلیل مفید است، از جمله:

    1. نگه‌داشتن تست کارا که وقتی باگ رفع شد به‌راحتی می‌توان دوباره از آن استفاده کرد.
    2. فراهم‌کردن نگهبانی (sentinel) که اگر باگ به‌طور اتفاقی رفع شود شکست می‌خورد. این می‌تواند به توسعه‌دهنده هشدار دهد تا بداند issue مرتبط رفع شده و احتمالاً می‌توان آن را بست.

    این directive شمارهٔ issueهای جداشده با ویرگول را به‌عنوان آرگومان می‌گیرد، یا "unknown":

    • //@ known-bug: #123, #456 (وقتی issueها در rust-lang/rust هستند)
    • //@ known-bug: rust-lang/chalk#123456 (اجازه می‌دهد قبل از # متن دلخواه باشد، که وقتی issue در مخزن دیگری است مفید است)
    • //@ known-bug: unknown (وقتی هنوز issue شناخته‌شده‌ای نیست؛ ترجیحاً اگر وجود ندارد یکی باز کنید)

    در تست دارای known-bug annotationهای خطا نگذارید. تست همچنان باید directiveهای عادی دیگر و فایل‌های stdout/stderr را داشته باشد.

    Test organization

    هنگام تصمیم دربارهٔ محل قرارگرفتن فایل تست، لطفاً سعی کنید زیرپوشه‌ای بیابید که بهترین تطابق را با آنچه می‌آزمایید دارد. تمام تلاش خود را بکنید تا همه‌چیز سازمان‌یافته بماند. باید اذعان کرد که می‌تواند دشوار باشد چون برخی تست‌ها ممکن است با دسته‌های مختلف همپوشانی داشته باشند، و چیدمان موجود ممکن است خوب جور نباشد.

    تست را با توصیف مختصری از آنچه بررسی می‌کند نام‌گذاری کنید. از گنجاندن شمارهٔ issue در نام تست پرهیز کنید. برای بحث عمیق‌تر بهترین روش‌ها را ببینید.

    ایده‌آل این است که تست به پوشه‌ای اضافه شود که به شناسایی اینکه چه بخشی از کد در اینجا تست می‌شود کمک کند (مثلاً tests/ui/borrowck/reject-move-out-of-borrow-via-pat.rs)

    هنگام نوشتن قابلیت جدید، ممکن است بخواهید زیرپوشه‌ای برای ذخیرهٔ تست‌های خود بسازید. برای مثال، اگر RFC 1234 («Widgets») را پیاده‌سازی می‌کنید، شاید منطقی باشد تست‌ها را در پوشه‌ای مثل tests/ui/rfc1234-widgets/ بگذارید.

    در موارد دیگر ممکن است از قبل پوشهٔ مناسبی وجود داشته باشد.

    با گذشت زمان پوشهٔ tests/ui بسیار سریع رشد کرده است. بررسی‌ای در tidy هست که تضمین می‌کند هیچ زیرپوشه‌ای بیش از ۱۰۰۰ ورودی نداشته باشد. داشتن فایل‌های بسیار زیاد مشکل ایجاد می‌کند چون با ویرایشگر/IDE سازگار نیست و رابط GitHub بیش از ۱۰۰۰ ورودی نمایش نمی‌دهد. اما چون tests/ui (پوشهٔ ریشهٔ تست UI) و پوشهٔ tests/ui/issues بیش از ۱۰۰۰ ورودی دارند، برای آن پوشه‌ها حد دیگری تعیین کرده‌ایم. پس لطفاً از قراردادن تست جدید در آنجا پرهیز کنید و سعی کنید مکان مرتبط‌تری بیابید.

    برای مثال، اگر تست شما به closureها مربوط است، باید آن را در tests/ui/closures بگذارید. وقتی به حد رسیدید، می‌توانید با تغییر اینجا آن را افزایش دهید.

    Rustfix tests

    تست‌های UI می‌توانند اعتبارسنجی کنند که پیشنهادهای تشخیصی درست اعمال می‌شوند و تغییرات حاصل درست کامپایل می‌شوند. این کار با directive با نام run-rustfix ممکن است:

    //@ run-rustfix
//@ check-pass
#![crate_type = "lib"]

pub struct not_camel_case {}
//~^ WARN `not_camel_case` should have an upper camel case name
//~| HELP convert the identifier to upper camel case
//~| SUGGESTION NotCamelCase

    تست‌های rustfix باید فایلی با پسوند .fixed داشته باشند که منبع را پس از اعمال پیشنهاد در بر دارد.

    • وقتی تست اجرا می‌شود، compiletest ابتدا بررسی می‌کند lint/هشدار درست تولید شده باشد.
    • سپس پیشنهاد را اعمال می‌کند و با .fixed مقایسه می‌کند (باید مطابق باشند).
    • در نهایت منبع اصلاح‌شده کامپایل می‌شود و این کامپایل باید موفق شود.

    معمولاً هنگام ساخت تست rustfix فایل .fixed را به‌طور خودکار با گزینهٔ x test --bless تولید می‌کنید.

    directive با نام run-rustfix باعث می‌شود همهٔ پیشنهادها اعمال شوند، حتی اگر MachineApplicable نباشند. اگر این مشکل‌ساز است، می‌توانید علاوه بر run-rustfix directive با نام rustfix-only-machine-applicable را هم اضافه کنید. این باید وقتی به‌کار رود که ترکیبی از سطوح مختلف پیشنهاد وجود دارد، و برخی از آن‌هایی که machine-applicable نیستند به‌درستی اعمال نمی‌شوند.

    Compare modes

    حالت‌های مقایسه را می‌توان برای اجرای همهٔ تست‌ها با پرچم‌هایی متفاوت از آنچه معمولاً با آن‌ها کامپایل می‌شوند به‌کار برد. در برخی موارد این می‌تواند باعث خروجی متفاوتی از کامپایلر شود. برای پشتیبانی از این، می‌توان فایل‌های خروجی مختلفی ذخیره کرد که خروجی را بر اساس حالت مقایسه در بر دارند.

    برای مثال، هنگام استفاده از حالت Polonius، تست foo.rs ابتدا خروجی مورد انتظار را در foo.polonius.stderr جست‌وجو می‌کند و اگر پیدا نکند به foo.stderr معمول برمی‌گردد. این مفید است چون حالت‌های مختلف گاهی می‌توانند به پیام‌های تشخیصی و رفتار متفاوتی بینجامند. این می‌تواند به ردیابی اینکه کدام تست‌ها بین حالت‌ها تفاوت دارند، و بررسی بصری آن تفاوت‌های تشخیصی کمک کند.

    اگر در مورد نادری با تستی روبه‌رو شدید که رفتار متفاوتی دارد، می‌توانید چیزی شبیه این را اجرا کنید تا فایل stderr جایگزین تولید شود:

    ./x test tests/ui --compare-mode=polonius --bless

    فعلاً هیچ‌یک از حالت‌های مقایسه برای تست‌های UI در CI بررسی نمی‌شوند.

    rustc_* TEST attributes

    کامپایلر چند attribute با نام #[rustc_*] دائماً ناپایدار تعریف می‌کند که پشت قابلیت داخلی rustc_attrs قرار دارند و اطلاعات اضافی داخلی کامپایلر را dump می‌کنند. برای جزئیات بیشتر زیربخش متناظر در اشکال‌زدایی کامپایلر را ببینید.

    می‌توان از آن‌ها در تست‌ها برای آزمودن دقیق‌تر، خواناتر و آسان‌تر حالت داخلی کامپایلر در مواردی استفاده کرد که انجام همان کار فقط با Rust «رو به کاربر» بسیار دشوار می‌بود. در واقع می‌توان گفت این کار اندکی از اصطلاح «UI» (رابط کاربر) سوءاستفاده می‌کند و چنین تست‌های UI را از جعبه‌سیاه به جعبه‌سفید تبدیل می‌کند. با احتیاط و کم از آن‌ها استفاده کنید.

    سطوح lint از پیش تنظیم‌شده در حالت تست UI

    به‌طور پیش‌فرض، مجموعه‌های تست در حالت تست UI (tests/ui، tests/ui-fulldeps، اما نه tests/rustdoc-ui) این‌ها را مشخص می‌کنند

    • -A unused
    • -W unused_attributes (چون این‌ها معمولاً برای تست‌های UI جالب‌اند)
    • -A internal_features
    • -A incomplete_features
    • -A unused_parens
    • -A unused_braces

    برای جزئیات بیشتر runtest را ببینید.

    If:

    • حالت pass تست UI پایین‌تر از run است (یعنی check یا build).
    • هیچ حالت مقایسه‌ای مشخص نشده است.

    چون در تست‌های UI می‌توانند بسیار پرسروصدا باشند.

    می‌توانید آن‌ها را با پرچم‌های سطح lint در compile-flags یا attributeهای سطح lint درون منبع در صورت نیاز بازنویسی کنید.

    توجه کنید که نسخهٔ rustfix پرچم -A unused را نخواهد داشت، یعنی ممکن است برای سرکوب lintهای unused روی فایل rustfix‌شده مجبور شوید #[allow(unused)] بگذارید (چون ممکن است خود rustfix را روی lintهای unused تست کنیم).
