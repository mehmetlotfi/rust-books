راهنمای توسعهٔ rustcrustc Development Guide

    بهترین روش‌ها برای نوشتن تست

    این فصل بهترین روش‌های مربوط به نوشتن و تغییر تست‌ها را شرح می‌دهد. می‌خواهیم مطمئن شویم تست‌هایی که می‌نویسیم حتی چند سال بعد هم بدون نیاز به مراجعه به نویسندهٔ اصلی و انجام کلی باستان‌شناسی git، آسان فهمیده و تغییر داده می‌شوند.

    روش خوبی است تست خودتان را بازبینی کنید و وانمود کنید مشارکت‌کنندهٔ دیگری هستید که چند سال بعد بدون زمینهٔ زیاد به تستی که شکست خورده نگاه می‌کند (این حتی چند روز یا چند ماه بعد هم به خودتان کمک می‌کند!). سپس از خود بپرسید: چگونه می‌توانم کار خودم و آن‌ها را آسان‌تر کنم؟

    برای اینکه این موضوع در چشم‌انداز قرار بگیرد، با یک حاشیه دربارهٔ اینکه چگونه تستی بنویسیم که زندگی مشارکت‌کنندهٔ دیگر را تا حد ممکن دشوار کند شروع می‌کنیم.

    حاشیه: راهنمای میدانی خرابکاری ساده در تست

    برای دشوارکردن زندگی مشارکت‌کنندهٔ دیگر تا حد ممکن، می‌توان:

    • تست را فقط با شمارهٔ issue و بدون هیچ زمینهٔ دیگری نام‌گذاری کرد، مثلاً issue-123456.rs.
    • هیچ کامنتی دربارهٔ آنچه تست می‌خواهد بیازماید نداشت و هیچ پیوندی به زمینهٔ مرتبط نگذاشت.
    • تستی عظیم (که می‌شد کمینه‌اش کرد) گنجاند که شامل بخش‌های غیرضروری است و حواس را از چیز اصلی‌ای که تست واقعاً می‌خواهد بیازماید پرت می‌کند.
    • مجموعه‌ای از خطاهای نحوی نامرتبط و خطاهای دیگر را گنجاند که برای آنچه تست می‌خواهد بررسی کند حیاتی نیستند.
    • قالب‌بندی تکه‌کدها را عجیب کرد.
    • مجموعه‌ای از featureهای استفاده‌نشده و نامرتبط را گنجاند.
    • مثلاً directiveهای compiletest مثل ignore-windows را داشت اما هیچ توضیحی دربارهٔ اینکه چرا لازم‌اند نداد.

    Test naming

    کاری کنید خواننده فوراً بفهمد تست چه چیزی را می‌آزماید، به‌جای اینکه مجبور باشد شمارهٔ issue را وارد کند و در جست‌وجوی github بگردد تا بفهمد تست چه چیزی را می‌آزماید. این مزیت اضافه‌ای هم دارد: امکان فیلترکردن تست‌ها با --test-args به‌عنوان مجموعه‌ای از تست‌های مرتبط.

    • تست را بر اساس چیزی که می‌آزماید یا از رگرسیون آن جلوگیری می‌کند نام‌گذاری کنید.
    • مختصر نگه دارید.
    • از استفاده از شمارهٔ issue به‌تنهایی به‌عنوان نام تست پرهیز کنید.
    • از شروع‌کردن نام تست با پیشوند issue-xxxxx پرهیز کنید چون تکمیل خودکار را بدتر می‌کند.

    از به‌کاربردن فقط شمارهٔ issue به‌عنوان نام تست پرهیز کنید

    ترجیح دهید آن‌ها را به‌صورت پیوند یا #123456 در کامنت‌های تست بیاورید. یا اگر منطقی است شمارهٔ issue را بگنجانید، کلیدواژه‌های مختصر مثل macro-external-span-ice-123956.rs را هم اضافه کنید.

    tests/ui/typeck/issue-123456.rs                              // bad
tests/ui/typeck/issue-123456-asm-macro-external-span-ice.rs  // bad (for tab completion)
tests/ui/typeck/asm-macro-external-span-ice-123456.rs        // good
tests/ui/typeck/asm-macro-external-span-ice.rs               // good

    issue-123456.rs فوراً چیزی دربارهٔ اینکه تست واقعاً چه چیزی را می‌آزماید نمی‌گوید، یعنی باید جست‌وجوی اضافی کنید. گنجاندن شمارهٔ issue به‌عنوان پیشوند نام تست تکمیل با tab را کم‌فایده می‌کند (اگر ls را روی پوشهٔ تست بزنید و مجموعه‌ای از پیشوندهای issue-xxxxx ببینید). می‌توانیم در کامنت تست به issue پیوند بدهیم.

    //! Check that `asm!` macro including nested macros that come from external
//! crates do not lead to a codepoint boundary assertion ICE.
//!
//! Regression test for <https://github.com/rust-lang/rust/issues/123456>.

    یک استثنا برای این قاعده تست‌های crash است: در آنجا مرسوم است تست‌ها فقط با شمارهٔ issue نام‌گذاری شوند چون هدف آن‌ها پیگیری تکه‌کدهایی است که issueهایشان دیگر ICE/crash نمی‌دهند، و آن‌ها در PRهای رفع یا حذف می‌شوند یا به تست‌های ui/دیگر درست تبدیل می‌شوند.

    Test organization

    • For most test suites, try to find a semantically meaningful subdirectory to home the test.
      • مثلاً برای پیاده‌سازی RFC 2093 به‌طور مشخص، می‌توانیم مجموعه‌ای از تست‌ها را زیر tests/ui/rfc-2093-infer-outlives/ گروه‌بندی کنیم. در نام پوشه، موضوع RFC را بگنجانید.
    • برای مجموعه‌های تست run-make/run-make-support، هر rmake.rs باید در یک زیرپوشهٔ مستقیم زیر tests/run-make/ یا tests/run-make-cargo/ قرار بگیرد. تو در تویی بیشتر فعلاً پشتیبانی نمی‌شود. در اینجا هم از به‌کاربردن فقط شمارهٔ issue برای نام تست پرهیز کنید.

    Test descriptions

    برای اینکه به مشارکت‌کنندگان دیگر کمک کنیم بفهمند اگر تغییراتشان باعث شکست تست شد تست دربارهٔ چیست، باید مطمئن شویم تست مستندات کافی دربارهٔ هدف/منظور خود، پیوند به زمینهٔ مرتبط (از جمله شمارهٔ issue یا بحث‌های دیگر) و احتمالاً منابع مرتبط دارد (مثلاً پیوند دادن به APIهای Win32 برای رفتار مشخص می‌تواند مفید باشد).

    خلاصهٔ یک تست با کامنت‌های خوب

    //! Brief summary of what the test is exercising.
//! Example: Regression test for #123456: make sure coverage attribute don't ICE
//!     when applied to non-items.
//!
//! Optional: Remarks on related tests/issues, external APIs/tools, crash
//!     mechanism, how it's fixed, FIXMEs, limitations, etc.
//! Example: This test is like `tests/attrs/linkage.rs`, but this test is
//!     specifically checking `#[coverage]` which exercises a different code
//!     path. The ICE was triggered during attribute validation when we tried
//!     to construct a `def_path_str` but only emitted the diagnostic when the
//!     platform is windows, causing an ICE on unix.
//!
//! Links to relevant issues and discussions. Examples below:
//! Regression test for <https://github.com/rust-lang/rust/issues/123456>.
//! See also <https://github.com/rust-lang/rust/issues/101345>.
//! See discussion at <https://rust-lang.zulipchat.com/#narrow/stream/131828-t-compiler/topic/123456-example-topic>.
//! See [`clone(2)`].
//!
//! [`clone(2)`]: https://man7.org/linux/man-pages/man2/clone.2.html

//@ ignore-windows
// Reason: (why is this test ignored for windows? why not specifically
// windows-gnu or windows-msvc?)

// Optional: Summary of test cases: What positive cases are checked?
// What negative cases are checked? Any specific quirks?

fn main() {
    #[coverage]
    //~^ ERROR coverage attribute can only be applied to function items.
    let _ = {
        // Comment highlighting something that deserves reader attention.
        fn foo() {}
    };
}

    اینکه چه مقدار زمینه/توضیح لازم است به صلاحدید نویسنده و بازبین است. یک قاعدهٔ سرانگشتی خوب این است که چیزهای غیربدیهی که در تست آزموده می‌شوند سزاوار توضیحی هستند تا به مشارکت‌کنندگان دیگر در فهمیدن کمک کنند. این ممکن است شامل نکاتی دربارهٔ این‌ها باشد:

    • چگونه یک ICE یا باگ فعال می‌شود اگر نسبتاً پیچیده باشد.
    • issueها و تست‌های مرتبط (مثلاً این تست شبیه تست دیگری است اما جدا نگه داشته شده چون…).
    • Platform-specific behaviors.
    • رفتار وابستگی‌ها و APIهای خارجی: syscallها، لینکرها، ابزارها، محیط‌ها و مانند آن.

    Test content

    • سعی کنید تست تا حد ممکن کمینه باشد.
    • کد غیرحیاتی را کمینه کنید و به‌ویژه خطاهای نحوی و نوع غیرضروری را که می‌توانند snapshotهای stderr را شلوغ کنند کمینه کنید.
    • برای خاموش‌کردن هشدارهای نامرتبط از #![allow(...)] یا #![expect(...)] استفاده کنید.
    • در صورت امکان از نام‌های دارای معنای مفهومی استفاده کنید (مثلاً fn bare_coverage_attributes() {}).

    Flaky tests

    همهٔ تست‌ها باید بکوشند بازتولیدپذیر و قابل‌اعتماد باشند. تست‌های flaky بدترین نوع تست‌اند، و می‌توان گفت حتی بدتر از نداشتن تست در وهلهٔ اول.

    • تست‌های flaky می‌توانند در PRهای کاملاً نامرتبط شکست بخورند که ممکن است مشارکت‌کنندگان دیگر را گیج کند و وقتشان را صرف فهمیدن اینکه آیا شکست تست مرتبط است هدر دهد.
    • تست‌های flaky از نتایج تستشان هیچ اطلاعات مفیدی جز این نمی‌دهند که flaky و نامطمئن‌اند: اگر تستی گذشت اما flaky است، آیا فقط شانس آوردم؟ اگر تستی flaky است اما شکست خورد، آیا فقط گذرا بود؟
    • تست‌های flaky اعتماد به کل مجموعهٔ تست را تضعیف می‌کنند. اگر مجموعهٔ تستی بتواند به‌دلیل تست‌های flaky به‌طور تصادفی و گذرا شکست بخورد، آیا کل مجموعهٔ تست گذشت یا فقط خوش‌شانس/بدشانس بودم؟
    • تست‌های flaky می‌توانند در CI کامل به‌طور تصادفی شکست بخورند و منابع گران‌بها را هدر دهند.

    Compiletest directives

    برای فهرست directiveها directiveهای compiletest را ببینید.

    • برای directiveهای ignore-*/needs-*/only-*، مگر اینکه بسیار بدیهی باشد، توضیح کوتاهی بدهید که چرا directive لازم است. مثلاً "//@ ignore-wasi (wasi codegens the main symbol differently)".
    • هنگام استفاده از //@ ignore-auxiliary، فایل‌های تست اصلی متناظر را مشخص کنید، مثلاً //@ ignore-auxiliary (used by `./foo.rs`).

    FileCheck best practices

    برای جزئیات راهنمای FileCheck در LLVM را ببینید.

    • از تطبیق روی شمارهٔ رجیسترهای مشخص یا شمارهٔ basic blockها پرهیز کنید مگر اینکه خاص باشند یا برای تست حیاتی باشند. در صورت مناسب‌بودن، استفاده از الگو (pattern) برای تطبیق آن‌ها را در نظر بگیرید.
