راهنمای توسعهٔ rustcrustc Development Guide

    Compiletest

    Introduction

    compiletest ابزار اصلی اجرای تست (test harness) در مجموعهٔ تست Rust است. به نویسندگان تست اجازه می‌دهد تعداد زیادی تست را سازمان‌دهی کنند (کامپایلر Rust هزاران تست دارد)، اجرای کارآمد تست‌ها (اجرای موازی پشتیبانی می‌شود)، و به نویسندهٔ تست اجازه می‌دهد رفتار و نتایج مورد انتظار هر دو حالت تست‌های جداگانه و گروهی را پیکربندی کند.

    نکته برای کاربران macOS

    برای کاربران macOS، SIP (System Integrity Protection) ممکن است به‌طور مداوم فایل دودویی کامپایل‌شده را با ارسال درخواست‌های شبکه به Apple بررسی کند، پس ممکن است هنگام اجرای تست‌ها افت شدید عملکرد ببینید.

    می‌توانید با تنظیم این گزینه‌ها آن را حل کنید: Privacy & Security -> Developer Tools -> Add Terminal (Or VsCode, etc.).

    compiletest ممکن است کد تست را برای موفقیت/شکست در زمان کامپایل یا زمان اجرا بررسی کند.

    تست‌ها معمولاً به‌صورت فایل منبع Rust با annotationهایی در کامنت‌ها پیش از و/یا درون کد تست سازمان‌دهی می‌شوند. این کامنت‌ها به compiletest می‌گویند آیا و چگونه تست را اجرا کند، چه رفتاری انتظار دارد و موارد بیشتر. برای جزئیات بیشتر دربارهٔ این annotationها directiveها و مستندات مجموعهٔ تست در ادامه را ببینید.

    برای آموزش ساخت یک تست جدید و توصیه‌هایی دربارهٔ نوشتن تست خوب به فصل‌های افزودن تست‌های جدید و بهترین روش‌ها و برای نحوهٔ اجرای مجموعهٔ تست به فصل اجرای تست‌ها نگاه کنید.

    آرگومان‌ها را می‌توان با --test-args یا با قرار‌دادن آن‌ها پس از -- به compiletest داد، مثلاً

    • x test --test-args --force-rerun
    • x test -- --force-rerun

    علاوه بر این، bootstrap چند آرگومان رایج را مستقیماً می‌پذیرد، مثلاً

    x test --no-capture --force-rerun --run --pass.

    خود compiletest سعی می‌کند وقتی آرتیفکت‌های درگیر (عمدتاً کامپایلر) تغییر نکرده‌اند تست‌ها را اجرا نکند. می‌توانید از x test --test-args --force-rerun برای اجرای دوباره یک تست حتی وقتی هیچ ورودی تغییر نکرده استفاده کنید.

    Test suites

    همهٔ تست‌ها در پوشهٔ tests هستند. تست‌ها در «مجموعه‌ها» (suites) سازمان‌دهی شده‌اند، که هر مجموعه در زیرپوشهٔ جداگانه‌ای است. هر مجموعهٔ تست کمی متفاوت رفتار می‌کند، با رفتار کامپایلر و بررسی‌های درستی متفاوت. برای مثال، پوشهٔ tests/incremental شامل تست‌های کامپایل افزایشی است. مجموعه‌های مختلف در src/tools/compiletest/src/common.rs در اعلان pub enum Mode تعریف شده‌اند.

    مجموعه‌های تست زیر در دسترس‌اند، با پیوند برای اطلاعات بیشتر:

    Pretty-printer tests

    تست‌های tests/pretty قابلیت «pretty-printing» در rustc را می‌آزمایند. گزینهٔ خط فرمان -Z unpretty در rustc باعث می‌شود منبع ورودی را به قالب‌های مختلف ترجمه کند، مثل منبع Rust پس از گسترش ماکرو.

    تست‌های pretty-printer چند directive دارند که در ادامه شرح داده شده‌اند. این دستورها می‌توانند رفتار تست را به‌طور قابل‌توجهی تغییر دهند، اما رفتار پیش‌فرض بدون هیچ دستوری این است:

    1. rustc -Zunpretty=normal را روی فایل منبع اجرا می‌کند.
    2. rustc -Zunpretty=normal را روی خروجی گام قبل اجرا می‌کند.
    3. خروجی دو گام قبل باید یکسان باشد.
    4. rustc -Zno-codegen را روی خروجی اجرا می‌کند تا مطمئن شود می‌تواند type check شود (مشابه cargo check).

    اگر هر یک از دستورهای بالا شکست بخورد، تست شکست می‌خورد.

    directiveهای تست‌های pretty-printing این‌ها هستند:

    • pretty-mode حالتی را که تست‌های pretty-print باید در آن اجرا شوند مشخص می‌کند (یعنی آرگومان -Zunpretty). اگر مشخص نشود پیش‌فرض normal است.
    • pretty-compare-only باعث می‌شود یک تست pretty فقط خروجی pretty-print شده را مقایسه کند (پس از گام ۳ بالا متوقف می‌شود). سعی نمی‌کند خروجی گسترش‌یافته را برای type check کامپایل کند. این برای حالت pretty-mode‌ای لازم است که به Rust معتبر گسترش نمی‌یابد، یا برای موقعیت‌های دیگری که خروجی گسترش‌یافته قابل‌کامپایل نیست.
    • pp-exact برای تضمین اینکه تست pretty-print خروجی مشخصی بدهد به‌کار می‌رود. اگر بدون مقدار مشخص شود، یعنی خروجی pretty-print باید با منبع اصلی مطابقت کند. اگر با مقدار مشخص شود، مثل //@ pp-exact:foo.pp، تضمین می‌کند خروجی pretty-print شده با محتوای فایل داده‌شده مطابقت دارد. در غیر این صورت، اگر pp-exact مشخص نشده باشد، خروجی pretty-print شده یک بار دیگر pretty-print می‌شود، و خروجی دو دور pretty-printing مقایسه می‌شود تا تضمین شود خروجی pretty-print شده به حالت پایدار همگرا می‌شود.

    Incremental tests

    تست‌های tests/incremental کامپایل افزایشی را می‌آزمایند. آن‌ها از directive با نام revisions استفاده می‌کنند تا به compiletest بگویند کامپایلر را در یک سری گام اجرا کند.

    Compiletest با یک پوشهٔ خالی و پرچم -C incremental شروع می‌کند، و سپس کامپایلر را برای هر revision اجرا می‌کند و نتایج افزایشی گام‌های قبل را دوباره به‌کار می‌برد.

    نام هر revision باید با یکی از این‌ها شروع شود:

    • cpass - تست باید با موفقیت کامپایل شود (بررسی ساخت، بدون codegen)
    • bfail — تست باید در کامپایل شکست بخورد (ساخت کامل، با codegen)
    • bpass — تست باید با موفقیت کامپایل شود (ساخت کامل، با codegen)
    • rpass — تست باید با موفقیت کامپایل و اجرا شود

    برای یکتا‌کردن revisionها، باید پسوندی مثل rpass1 و rpass2 اضافه کنید.

    برای شبیه‌سازی تغییر منبع، compiletest یک پرچم --cfg با نام revision فعلی هم می‌دهد.

    برای مثال این دو بار اجرا می‌شود و تغییر یک تابع را شبیه‌سازی می‌کند:

    //@ revisions: rpass1 rpass2

#[cfg(rpass1)]
fn foo() {
    println!("one");
}

#[cfg(rpass2)]
fn foo() {
    println!("two");
}

fn main() { foo(); }

    تست‌های افزایشی از directive با نام forbid-output پشتیبانی می‌کنند تا مشخص کنند یک زیررشتهٔ مشخص نباید هیچ‌جای خروجی کامپایلر ظاهر شود. این می‌تواند برای تضمین ظاهرنشدن برخی خطاها مفید باشد، اما می‌تواند شکننده باشد چون پیام‌های خطا با گذر زمان تغییر می‌کنند، و ممکن است تست دیگر چیز درست را بررسی نکند اما همچنان بگذرد.

    تست‌های افزایشی ممکن است از attribute با نام #[rustc_clean(...)] استفاده کنند. این attribute اثر انگشت جلسهٔ کامپایل فعلی را با جلسهٔ قبلی مقایسه می‌کند. اولین revision هرگز نباید attribute فعال rustc_clean داشته باشد، چون همیشه dirty خواهد بود.

    در حالت پیش‌فرض، تضمین می‌کند اثر انگشت‌ها باید یکسان باشند. این attribute آرگومان‌های زیر را می‌گیرد:

    • cfg="<cond>" — شرط cfg با نام <cond> را بررسی می‌کند، و بررسی را فقط وقتی اجرا می‌کند که شرط پیکربندی true باشد. از آن می‌توان برای اجرای attribute با نام rustc_clean فقط در یک revision مشخص استفاده کرد.
    • except="<query1>,<query2>,..." — تضمین می‌کند نتایج کوئری‌های فهرست‌شده باید متفاوت باشند، نه یکسان.
    • loaded_from_disk="<query1>,<query2>,..." — تضمین می‌کند نتایج کوئری‌های فهرست‌شده واقعاً از دیسک بارگذاری شده‌اند (نه فقط سبز علامت‌گذاری شده‌اند). این می‌تواند برای اطمینان از اینکه تست واقعاً منطق deserialization برای نتیجهٔ یک کوئری مشخص را می‌آزماید مفید باشد. می‌توان آن را با except ترکیب کرد.

    مثال ساده‌ای از تستی که از rustc_clean استفاده می‌کند تست hello_world است.

    Debuginfo tests

    Important

    از #159455 به بعد این تست‌ها اختیاری (opt-in) شدند. برای زمینهٔ بیشتر ببینید: پایدارسازی وضعیت مجموعهٔ تست debuginfo

    تست‌های tests/debuginfo بررسی می‌کنند debuginfo چگونه توسط دیباگرهای پشتیبانی‌شده تفسیر می‌شود، و تأیید می‌کنند visualizerهای ما همچنان مطابق انتظار کار می‌کنند. یک برنامه می‌سازند، دیباگر را راه‌اندازی می‌کنند و دستورهایی به دیباگر می‌دهند. یک تست واحد می‌تواند با cdb، gdb و lldb کار کند.

    بیشتر تست‌ها باید directive با نام //@ compile-flags: -g یا چیزی مشابه آن را داشته باشند تا debuginfo مناسب تولید شود.

    برای تنظیم breakpoint روی یک خط، کامنت // #break را به آن خط اضافه کنید.

    تست‌های debuginfo شامل مجموعه‌ای از دستورهای دیباگر به‌علاوهٔ خطوط «check» هستند که خروجی مورد انتظار از دیباگر را مشخص می‌کنند.

    دستورها کامنت‌هایی به شکل //@ $DEBUGGER-command:$COMMAND هستند که در آن $DEBUGGER دیباگر مورد استفاده و $COMMAND دستور دیباگر برای اجراست.

    مقادیر debugger می‌توانند این‌ها باشند:

    • cdb
    • gdb
    • lldb

    دستور بررسی خروجی به شکل //@ $DEBUGGER-check:$OUTPUT است که در آن $OUTPUT خروجی مورد انتظار است.

    برای مثال، موارد زیر تست را می‌سازند، دیباگر را شروع می‌کنند، breakpoint تنظیم می‌کنند، برنامه را اجرا می‌کنند، مقداری را بررسی می‌کنند و آنچه دیباگر چاپ می‌کند را می‌سنجند:

    //@ compile-flags: -g

//@ lldb-command: run
//@ lldb-command: print foo
//@ lldb-check: $0 = 123

fn main() {
    let foo = 123;
    b(); // #break
}

fn b() {}

    علاوه بر این، یک دستور ویژه به نام //@ $DEBUGGER-repr:$VAR_NAME هست که برای تأیید متغیرها (و visualizerهایشان) با جزئیات بیشتر از آنچه با مقایسهٔ ساده رشته‌ها ممکن است طراحی شده است. این directive تا جای ممکن بر -command/-check ترجیح دارد.

    Note

    در زمان نگارش (ژوئیهٔ 2026) این دستور به LLDB محدود است و پیاده‌سازی آن برای GDB به‌زودی می‌آید. برنامهٔ قطعی برای انتقال این منطق به CDB وجود ندارد.

    این دستور در عمل به این بسط داده می‌شود:

    //@ $DEBUGGER-command:repr $VAR_NAME
//@ $DEBUGGER-check:$VAR_NAME ok

    دستور repr $VAR_NAME توسط منطق ویژه‌ای رهگیری می‌شود که از API دیباگرها برای بررسی داده‌هایی استفاده می‌کند که در خروجی چاپ‌شدهٔ متغیر منعکس نمی‌شوند. متغیر در حافظه با داده‌های ورودی ذخیره‌شده در tests/debuginfo/<test_name>/input/<debugger>_input/<target_group>.json مقایسه می‌شود و هنگام شکست پیام‌های خطای مفصل می‌دهد.

    Important

    directiveهای -repr با گزینهٔ --bless سازگارند، برخلاف -command/-check. عمل --bless روی فایلی با دستورهای -repr به‌طور خودکار فایل داده‌های ورودی هدف مناسب را می‌سازد/به‌روز می‌کند.

    جزئیات پیاده‌سازی این دستور بیشتر در بخش تست در فصل Debug Info شرح داده شده است.

    directiveهای زیر برای غیرفعال‌کردن یک تست بر اساس دیباگری که فعلاً استفاده می‌شود در دسترس‌اند:

    • min-cdb-version: 10.0.18317.1001 — اگر نسخهٔ cdb پایین‌تر از نسخهٔ داده‌شده باشد تست را نادیده می‌گیرد
    • min-gdb-version: 8.2 — اگر نسخهٔ gdb پایین‌تر از نسخهٔ داده‌شده باشد تست را نادیده می‌گیرد
    • ignore-gdb-version: 9.2 — اگر نسخهٔ gdb برابر نسخهٔ داده‌شده باشد تست را نادیده می‌گیرد
    • ignore-gdb-version: 7.11.90 - 8.0.9 — اگر نسخهٔ gdb در یک بازه (شامل دو سر) باشد تست را نادیده می‌گیرد
    • min-apple-lldb-version: 1703.0.236.21/min-llvm-lldb-version: 21.1.0 — اگر نسخهٔ lldb پایین‌تر از نسخهٔ داده‌شده باشد تست را نادیده می‌گیرد. نکته: fork شرکت Apple از LLDB (که با Xcode توزیع می‌شود) از طرح نسخه‌گذاری متفاوتی استفاده می‌کند که به‌آسانی به شمارهٔ نسخه‌های LLDB در LLVM نگاشت نمی‌شود. به همین دلیل، دروازه‌های نسخه بر اساس تأمین‌کننده مشخص می‌شوند. اطلاعات بیشتر دربارهٔ بررسی دستی هم‌ارزی نسخه‌ها اینجا موجود است
    • rust-lldb — اگر lldb افزونهٔ Rust را نداشته باشد تست را نادیده می‌گیرد. نکته: نسخهٔ «Rust» از LLDB دیگر وجود ندارد، پس این همیشه نادیده گرفته می‌شود. احتمالاً باید حذف شود.

    با دادن گزینهٔ --debugger به compiletest، می‌توانید یک دیباگر مشخص را برای اجرای تست‌ها تعیین کنید. برای مثال، ./x test tests/debuginfo -- --debugger gdb فقط دستورهای GDB را تست می‌کند.

    نکته دربارهٔ اجرای محلی تست‌های debuginfo در lldb با توزیع از پیش ساخته‌شدهٔ lldb

    اگر می‌خواهید تست‌های debuginfo در lldb را به‌صورت محلی اجرا کنید، فعلاً در ویندوز لازم است:

    LLDB 21

    • Python 3.10 را نصب کرده باشید.
    • python310.dll در متغیر محیطی PATH شما در دسترس باشد. این فایل توسط نصب‌کنندهٔ استاندارد Python از python.org ارائه نمی‌شود؛ باید آن را دستی به PATH اضافه کنید.

    LLDB 22

    • Python 3.11 را نصب کرده باشید.
    • python311.dll در PATH شما در دسترس باشد.
    • توصیه می‌شود نصب Python را از طریق pymanager بگیرید، که اسکریپت‌های نصب بعدی برای کمک به پیکربندی PATH دارد.

    در غیر این صورت تست‌های debuginfo در lldb می‌توانند به شکل‌های مرموزی crash کنند.

    نکته دربارهٔ دریافت cdb.exe در Windows 11

    cdb.exe همراه با «Windows 11 SDK» مناسب دریافت می‌شود که بخشی از پروفایل workload با نام «Desktop Development with C++» در نصب‌کنندهٔ Visual Studio است (مثلاً نصب‌کنندهٔ Visual Studio 2022).

    اما این به‌تنهایی به‌طور پیش‌فرض کافی نیست. اگر به cdb.exe نیاز دارید، باید به Installed Apps بروید، جدیدترین «Windows Software Development Kit» را بیابید (و بله، ممکن است همچنان Windows 10.0.22161.3233 بنویسد، حتی اگر سیستم‌عامل Windows 11 نامیده می‌شود). سپس باید روی «Modify» -> «Change» کلیک کنید و «Debugging Tools for Windows» را انتخاب کنید تا cdb.exe را دریافت کنید.

    Assembly tests

    Codegen-units tests

    تست‌های tests/codegen-units جمع‌کنندهٔ monomorphization و افراز CGU را می‌آزمایند.

    این تست‌ها با اجرای rustc با پرچمی برای چاپ نتیجهٔ گذر جمع‌آوری monomorphization، یعنی -Zprint-mono-items، کار می‌کنند، و سپس annotationهای ویژه در فایل برای مقایسه با آن به‌کار می‌روند.

    سپس تست باید با کامنت‌هایی به شکل //~ MONO_ITEM name annotate شود که در آن name رشتهٔ monomorphize‌شده‌ای است که rustc چاپ می‌کند، مثل fn <u32 as Trait>::foo.

    برای بررسی افراز CGU، کامنتی به شکل //~ MONO_ITEM name @@ cgu که در آن cgu فهرستی از نام CGUها با فاصله و اطلاعات linkage در قلاب است. برای مثال: //~ MONO_ITEM static function::FOO @@ statics[Internal]

    Mir-opt tests

    تست‌های tests/mir-opt بخش‌هایی از MIR تولیدشده را بررسی می‌کنند تا مطمئن شوند درست تولید شده و بهینه‌سازی‌های مورد انتظار را انجام می‌دهد. برای اطلاعات بیشتر فصل بهینه‌سازی‌های MIR را ببینید.

    Compiletest تست را با چند پرچم می‌سازد تا خروجی MIR را dump کند و خط مبنایی برای بهینه‌سازی‌ها تعیین کند:

    • -Copt-level=1
    • -Zdump-mir=all
    • -Zmir-opt-level=4
    • -Zvalidate-mir
    • -Zdump-mir-exclude-pass-number

    تست باید با کامنت‌های // EMIT_MIR annotate شود که فایل‌هایی را مشخص می‌کنند که خروجی MIR مورد انتظار را در بر دارند. می‌توانید از x test --bless برای ساخت فایل‌های اولیهٔ مورد انتظار استفاده کنید.

    کامنت EMIT_MIR چند شکل می‌تواند داشته باشد:

    • // EMIT_MIR $MIR_PATH.mir — این بررسی می‌کند نام فایل داده‌شده با خروجی دقیق dump مربوط به MIR مطابقت داشته باشد. برای مثال، my_test.main.SimplifyCfg-elaborate-drops.after.mir آن فایل را از پوشهٔ تست بارگذاری می‌کند و با dump حاصل از rustc مقایسه می‌کند.

      بررسی فایل «after» (که پس از بهینه‌سازی است) وقتی مفید است که به حالت نهایی پس از یک بهینه‌سازی علاقه‌مندید. برخی موارد نادر ممکن است برای کامل‌بودن بخواهند از فایل «before» استفاده کنند.

    • // EMIT_MIR $MIR_PATH.diff — که در آن $MIR_PATH نام فایل dump مربوط به MIR است، مثل my_test_name.my_function.EarlyOtherwiseBranch. Compiletest فایل‌های .before.mir و .after.mir را diff می‌کند، و خروجی diff را با فایل .diff مورد انتظار از کامنت EMIT_MIR مقایسه می‌کند.

      این وقتی مفید است که می‌خواهید ببینید یک بهینه‌سازی MIR را چگونه تغییر می‌دهد.

    • // EMIT_MIR $MIR_PATH.dot — هنگام استفاده از پرچم‌های مشخصی که داده‌های اضافی MIR را dump می‌کنند (مثلاً -Z dump-mir-graphviz برای تولید فایل‌های .dot)، این بررسی می‌کند خروجی با فایل داده‌شده مطابقت دارد.

    به‌طور پیش‌فرض هدف‌های ۳۲ بیتی و ۶۴ بیتی از فایل‌های dump یکسانی استفاده می‌کنند، که در حضور اشاره‌گرها در ثابت‌ها یا چیزهای دیگر وابسته به پهنای بیت می‌تواند مشکل‌ساز باشد. در آن صورت می‌توانید // EMIT_MIR_FOR_EACH_BIT_WIDTH را به تست خود اضافه کنید، که باعث می‌شود فایل‌های جداگانه برای سیستم‌های ۳۲ بیتی و ۶۴ بیتی تولید شود.

    Important

    چند مورد از این تست‌ها از ignore-std-debug-assertions directive استفاده می‌کنند. اگر rust.debug-assertions-std در bootstrap.toml روی true تنظیم شده باشد (از جمله به‌طور تعدّی از طریق rust.debug یا rust.debug-assertions)، اجرا نخواهند شد!

    run-make tests

    تست‌های tests/run-make و tests/run-make-cargo تست‌های همه‌منظوره با استفاده از دستورپخت‌های (recipes) Rust هستند، که برنامه‌های کوچکی (rmake.rs) هستند و اجازهٔ کد دلخواه Rust مثل فراخوانی rustc را می‌دهند، و کتابخانهٔ run_make_support از آن‌ها پشتیبانی می‌کند. استفاده از recipeهای Rust نهایت انعطاف را فراهم می‌کند.

    اگر مجموعهٔ تست دیگری بهتر نیازهای شما را برآورده نمی‌کند باید از تست‌های run-make استفاده شود.

    مجموعهٔ تست run-make-cargo علاوه بر آن یک cargo درون‌درختی هم می‌سازد تا از مواردی پشتیبانی کند که نیاز به تست cargo درون‌درختی همراه با rustc درون‌درختی دارند. مجموعهٔ تست run-make به cargo درون‌درختی دسترسی ندارد (پس می‌تواند مجموعهٔ تست سریع‌تری برای تکرار باشد).

    build-std tests

    تست‌های tests/build-std بررسی می‌کنند -Zbuild-std کار می‌کند. این فعلاً فقط یک مجموعهٔ تست run-make با یک recipe است. recipe موارد تست را تولید و آن‌ها را به‌صورت موازی اجرا می‌کند.

    استفاده از recipeهای Rust

    هر تست باید در پوشهٔ جداگانه‌ای با برنامهٔ Rust با نام rmake.rs باشد، که recipe نامیده می‌شود. recipe توسط compiletest با کتابخانهٔ run_make_support لینک‌شده کامپایل و اجرا می‌شود.

    اگر به ابزارها یا قابلیت‌های جدید نیاز دارید، گسترش و بهبود کتابخانهٔ run_make_support را در نظر بگیرید.

    directiveهای compiletest مثل //@ only-<target> یا //@ ignore-<target> در rmake.rs پشتیبانی می‌شوند، مثل تست‌های UI. اما revisionها یا ساخت auxiliary با directiveها فعلاً پشتیبانی نمی‌شوند.

    rmake.rs و run-make-support نباید هیچ قابلیت nightly/ناپایداری را به‌کار ببرند، چون باید توسط rustc مرحلهٔ stage 0 قابل‌کامپایل باشند که ممکن است beta یا حتی stable باشد.

    به‌طور پیش‌فرض، تست‌های run-make هر دستور زیرفرایند و stdout/stderr آن را چاپ می‌کنند. هنگام اجرا با --no-capture روی مجموعه‌های تست panic=abort (مثل cg_clif)، این می‌تواند ترمینال را سیل‌زده کند. با حذف --verbose-run-make-subprocess-output این خروجی برای تست‌های موفق سرکوب می‌شود — تست‌های شکست‌خورده همیشه چاپ می‌کنند:

    ./x test tests/run-make --no-capture --verbose-run-make-subprocess-output=false

    بررسی سریع اینکه تست‌های rmake.rs قابل‌کامپایل‌اند

    می‌توانید بدون ساخت rustc مرحلهٔ stage1، سریعاً بررسی کنید تست‌های rmake.rs قابل‌کامپایل‌اند، با اجبار کامپایل rmake.rs توسط کامپایلر stage0:

    $ COMPILETEST_FORCE_STAGE0=1 x test --stage 0 tests/run-make/<test-name>

    البته برخی تست‌ها به این شکل با موفقیت اجرا نخواهند شد.

    استفاده از rust-analyzer با rmake.rs

    مثل برنامه‌های تست دیگر، اسکریپت‌های rmake.rs که در تست‌های run-make استفاده می‌شوند به‌طور پیش‌فرض یکپارچگی با rust-analyzer ندارند.

    برای دور‌زدن این هنگام کار روی یک تست مشخص، موقتاً یک فایل Cargo.toml در پوشهٔ تست بسازید (مثلاً tests/run-make/sysroot-crates-are-unstable/Cargo.toml) با این محتوا:

    مراقب باشید این Cargo.toml یا Cargo.lock آن را به PR واقعی خود اضافه نکنید!

    # Convince cargo that this isn't part of an enclosing workspace.
[workspace]

[package]
name = "rmake"
version = "0.1.0"
edition = "2021"

[dependencies]
run_make_support = { path = "../../../src/tools/run-make-support" }

[[bin]]
name = "rmake"
path = "rmake.rs"

    سپس ورودی متناظر را به "rust-analyzer.linkedProjects" اضافه کنید (مثلاً در .vscode/settings.json):

    "rust-analyzer.linkedProjects": [
  "tests/run-make/sysroot-crates-are-unstable/Cargo.toml"
],

    Coverage tests

    تست‌های tests/coverage بین چند حالت تست که پوشش (coverage) instrumentation را به شکل‌های مختلف می‌آزمایند مشترک‌اند. اجرای مجموعهٔ تست coverage به‌طور خودکار هر تست را در همهٔ حالت‌های مختلف coverage اجرا می‌کند.

    هر حالت یک نام مستعار هم دارد تا تست‌های coverage را فقط در همان حالت اجرا کند:

    ./x test coverage # runs all of tests/coverage in all coverage modes
./x test tests/coverage # same as above

./x test tests/coverage/if.rs # runs the specified test in all coverage modes

./x test coverage-map # runs all of tests/coverage in "coverage-map" mode only
./x test coverage-run # runs all of tests/coverage in "coverage-run" mode only

./x test coverage-map -- tests/coverage/if.rs # runs the specified test in "coverage-map" mode only

    اگر به دلیلی نباید یک تست مشخص در یکی از حالت‌های تست coverage اجرا شود، از directiveهای //@ ignore-coverage-map یا //@ ignore-coverage-run استفاده کنید.

    coverage-map suite

    در حالت coverage-map، این تست‌ها نگاشت‌های بین نواحی کد منبع و شمارنده‌های coverage را که LLVM تولید می‌کند تأیید می‌کنند. آن‌ها تست را با --emit llvm-ir کامپایل می‌کنند، سپس از یک ابزار سفارشی (src/tools/coverage-dump) برای استخراج و pretty-print نگاشت‌های coverage جاسازی‌شده در IR استفاده می‌کنند. این تست‌ها به runtime مربوط به profiler نیاز ندارند، پس در jobهای CI مربوط به PR اجرا می‌شوند و اجرا/bless محلی آن‌ها آسان است.

    این تست‌های نگاشت coverage می‌توانند به تغییرات در lowering یا بهینه‌سازی‌های MIR حساس باشند، و نگاشت‌هایی تولید کنند که متفاوت‌اند اما گزارش‌های coverage یکسانی می‌دهند.

    به‌عنوان قاعدهٔ سرانگشتی، هر PRای که کد مخصوص coverage را تغییر نمی‌دهد آزاد است تست‌های coverage-map را در صورت لزوم دوباره bless کند، بدون نگرانی دربارهٔ تغییرات واقعی، مادامی که تست‌های coverage-run همچنان بگذرند.

    coverage-run suite

    در حالت coverage-run، این تست‌ها یک تست سرتاسری از گزارش‌دهی coverage انجام می‌دهند. یک برنامهٔ تست را با instrumentation مربوط به coverage کامپایل می‌کنند، آن برنامه را اجرا می‌کنند تا داده‌های خام coverage تولید شود، و سپس از ابزارهای LLVM برای پردازش آن داده‌ها به گزارش coverage خوانا برای انسان استفاده می‌کنند.

    فایل‌های دودویی instrument‌شده باید با runtime مربوط به profiler در LLVM لینک شوند، پس تست‌های coverage-run به‌طور خودکار رد می‌شوند مگر اینکه runtime مربوط به profiler در bootstrap.toml فعال شده باشد:

    build.profiler = true

    این همچنین یعنی معمولاً در jobهای CI مربوط به PR اجرا نمی‌شوند، هرچند به‌عنوان بخشی از مجموعهٔ کامل jobهای CI که برای merge به‌کار می‌روند اجرا می‌شوند.

    coverage-run-rustdoc suite

    تست‌های tests/coverage-run-rustdoc هم doctestهای instrument‌شده را اجرا می‌کنند و آن‌ها را در گزارش coverage می‌گنجانند. این از لزوم ساخت rustdoc هنگام اجرای فقط مجموعهٔ اصلی coverage جلوگیری می‌کند.

    Crash tests

    tests/crashes مجموعه‌ای از تست‌هاست که انتظار می‌رود باعث ICE، panic یا crash دیگری در کامپایلر شوند، تا رفع‌های تصادفی پیگیری شوند. پیش‌تر این کار در https://github.com/rust-lang/glacier انجام می‌شد اما انجام آن درون مجموعهٔ تست rust-lang/rust راحت‌تر است.

    ضروری است که یک تست در این مجموعه باعث شود rustc ICE دهد، panic کند یا به شکل دیگری crash کند. تست «می‌گذرد» اگر rustc با کد خروجی غیر از 1 یا 0 خارج شود.

    اگر می‌خواهید stdout/stderr مفصل ببینید، باید COMPILETEST_VERBOSE_CRASHES=1 را تنظیم کنید، مثلاً

    $ COMPILETEST_VERBOSE_CRASHES=1 ./x test tests/crashes/999999.rs --stage 1

    هر کسی می‌تواند crashهای «بدون‌پیگیری» را از issue tracker اضافه کند. قویاً توصیه می‌شود تست‌های چند issue در یک PR گنجانده شوند. وقتی این کار را می‌کنید، شمارهٔ هر issue باید در نام فایل (12345.rs کافی است) و همچنین درون فایل با directive با نام //@ known-bug: #12345 ذکر شود. لطفاً پس از merge شدن PR، issueهای مرتبط را با S-bug-has-test برچسب‌گذاری کنید.

    اگر اتفاقاً یکی از crashها را رفع کردید، لطفاً آن را به زیرپوشهٔ مناسبی در tests/ui منتقل کنید و نام معناداری به آن بدهید. لطفاً در بالای فایل یک doc comment اضافه کنید که توضیح دهد چرا این تست وجود دارد. بهتر از آن این است که بتوانید به‌اختصار توضیح دهید مثال پیش‌تر چگونه rustc را crash می‌داد، و چه کاری برای رفع آن انجام شد.

    Adding

    Fixes #NNNNN
Fixes #MMMMM

    به توضیحات pull request شما باعث می‌شود تیکت‌های متناظر هنگام merge به‌طور خودکار بسته شوند.

    ابتدا مطمئن شوید رفع شما واقعاً علت ریشه‌ای issue را رفع می‌کند نه فقط زیرمجموعه‌ای از آن را. شمارهٔ issueها را می‌توان در نام فایل یا directive با نام //@ known-bug درون فایل تست یافت.

    Building auxiliary crates

    رایج است که برخی تست‌ها به crateهای کمکی (auxiliary) اضافی برای کامپایل نیاز دارند. چند directive برای کمک به این کار هست:

    • aux-build
    • aux-crate
    • aux-bin
    • aux-codegen-backend
    • proc-macro

    aux-build یک crate جداگانه را از فایل منبع نام‌برده می‌سازد. فایل منبع باید در پوشه‌ای به نام auxiliary کنار فایل تست باشد.

    //@ aux-build: my-helper.rs

extern crate my_helper;
// ... You can use my_helper.

    crate کمکی در صورت امکان به‌صورت dylib ساخته می‌شود (مگر روی پلتفرمی که از آن‌ها پشتیبانی نمی‌کند، یا سرایند no-prefer-dynamic در فایل aux مشخص شده باشد). پرچم -L برای پیدا‌کردن crateهای خارجی به‌کار می‌رود.

    aux-crate بسیار شبیه aux-build است. اما از پرچم --extern استفاده می‌کند تا به crate خارجی لینک کند و crate را به‌عنوان extern prelude در دسترس قرار دهد. این به شما اجازه می‌دهد نحو اضافی پرچم --extern را مشخص کنید، مثل تغییر نام یک وابستگی. برای مثال، //@ aux-crate: foo=bar.rs auxiliary/bar.rs را کامپایل می‌کند و آن را با نام foo درون تست در دسترس قرار می‌دهد. این شبیه تغییر نام وابستگی در Cargo است. همچنین می‌توان modifierهای --extern را مشخص کرد. برای مثال، //@ aux-crate: noprelude:foo=bar.rs.

    aux-bin شبیه aux-build است اما به‌جای کتابخانه یک فایل دودویی می‌سازد. فایل دودویی نسبت به پوشهٔ کاری تست در auxiliary/bin در دسترس خواهد بود.

    aux-codegen-backend شبیه aux-build است، اما dylib کامپایل‌شده را هنگام ساخت فایل اصلی به -Zcodegen-backend می‌دهد. این فقط برای تست‌های tests/ui-fulldeps کار می‌کند، چون نیاز به استفاده از crateهای کامپایلر دارد.

    Auxiliary proc-macro

    اگر وابستگی proc-macro می‌خواهید، می‌توانید از directive با نام proc-macro استفاده کنید. این directive درست مثل aux-build رفتار می‌کند، یعنی باید فایل کمکی تست proc-macro را زیر پوشه‌ای به نام auxiliary در همان پوشهٔ والد فایل تست اصلی قرار دهید. اما در مقایسه با aux-build برای فایل کمکی تست proc-macro چهار رفتار از پیش تنظیم‌شدهٔ اضافی هم دارد:

    1. فایل تست کمکی با --crate-type proc-macro ساخته می‌شود.
    2. فایل تست کمکی بدون -C prefer-dynamic ساخته می‌شود، یعنی سعی نمی‌کند برای crate کمکی dylib تولید کند.
    3. crate کمکی از طریق extern prelude با --extern <aux_crate_name> در دسترس فایل تست قرار می‌گیرد. توجه کنید که چون تست‌های UI پیش‌فرضاً edition 2015 دارند، همچنان باید extern <aux_crate_name> را مشخص کنید، مگر اینکه فایل تست اصلی از editionای 2018 یا جدیدتر استفاده کند، اگر می‌خواهید نام crate کمکی را در یک use import به‌کار ببرید.
    4. crate با نام proc_macro به‌عنوان ماژول extern prelude در دسترس قرار می‌گیرد. همان تمایز edition 2015 در برابر editionهای جدیدتر برای extern proc_macro; صادق است.

    برای مثال ممکن است تستی به نام tests/ui/cat/meow.rs و فایل کمکی proc-macro به نام tests/ui/cat/auxiliary/whiskers.rs داشته باشید:

    tests/ui/cat/
    meow.rs                 # main test file
    auxiliary/whiskers.rs   # auxiliary

    // tests/ui/cat/meow.rs

//@ proc-macro: whiskers.rs

extern crate whiskers; // needed as ui test defaults to edition 2015

fn main() {
  whiskers::identity!();
}

    // tests/ui/cat/auxiliary/whiskers.rs

extern crate proc_macro;
use proc_macro::*;

#[proc_macro]
pub fn identity(ts: TokenStream) -> TokenStream {
    ts
}

    نکته: سرایند proc-macro فعلاً با سرایند build-aux-doc در تست‌های rustdoc کار نمی‌کند. در آن صورت باید از سرایند aux-build استفاده کنید، و در proc-macro از #![crate_type="proc_macro"] و سرایندهای //@ force-host و //@ no-prefer-dynamic استفاده کنید.

    Revisions

    revisionها اجازه می‌دهند یک فایل تست برای چند تست به‌کار رود. این کار با افزودن directive ویژه در بالای فایل انجام می‌شود:

    //@ revisions: foo bar baz

    این باعث می‌شود تست سه بار کامپایل (و تست) شود: یک بار با --cfg foo، یک بار با --cfg bar، و یک بار با --cfg baz. بنابراین می‌توانید درون تست از #[cfg(foo)] و مانند آن برای تنظیم هر یک از این نتایج استفاده کنید.

    همچنین می‌توانید directiveها و پیام‌های خطای مورد انتظار را برای یک revision مشخص سفارشی کنید. برای این کار، [revision-name] را بعد از //@ برای directiveها، و بعد از // برای annotationهای خطای UI اضافه کنید، به این شکل:

    // A flag to pass in only for cfg `foo`:
//@[foo]compile-flags: -Z verbose-internals

#[cfg(foo)]
fn test_foo() {
    let x: usize = 32_u32; //[foo]~ ERROR mismatched types
}

    چند revision را می‌توان در فهرستی با ویرگول مشخص کرد، مثل //[foo,bar,baz]~^.

    در مجموعه‌های تستی که از ابزار FileCheck در LLVM استفاده می‌کنند، نام revision فعلی هم به‌عنوان پیشوند اضافی برای directiveهای FileCheck ثبت می‌شود:

    //@ revisions: NORMAL COVERAGE
//@[COVERAGE] compile-flags: -Cinstrument-coverage
//@[COVERAGE] needs-profiler-runtime

// COVERAGE:   @__llvm_coverage_mapping
// NORMAL-NOT: @__llvm_coverage_mapping

// CHECK: main
fn main() {}

    توجه کنید همهٔ directiveها وقتی برای یک revision سفارشی شوند معنا ندارند. برای مثال، directiveهای ignore-test (و همهٔ directiveهای «ignore») فعلاً فقط به کل تست اعمال می‌شوند، نه به revisionهای مشخص. تنها directiveهایی که قرار است واقعاً هنگام سفارشی‌شدن برای یک revision کار کنند الگوهای خطا و پرچم‌های کامپایلر هستند.

    توجه کنید این مجموعه‌های تست از revision پشتیبانی نمی‌کنند:

    • codegen-units
    • run-make
    • rustdoc-html
    • rustdoc-json

    نادیده‌گرفتن نام‌های revisionِ استفاده‌نشده

    معمولاً نام‌های revision که در directiveها و annotationهای خطای دیگر ذکر می‌شوند باید با revision واقعی‌ای که در directive با نام revisions اعلام شده متناظر باشند. این توسط بررسی ./x test tidy اعمال می‌شود.

    اگر نام یک revision به دلیلی باید موقتاً از فهرست revisionها حذف شود، می‌توان بررسی بالا را با افزودن نام revision به سرایند //@ unused-revision-names: سرکوب کرد.

    مشخص‌کردن نام استفاده‌نشدهٔ * (یعنی //@ unused-revision-names: *) اجازه می‌دهد هر نام revisionِ استفاده‌نشده ذکر شود.

    Compare modes

    Compiletest را می‌توان در حالت‌های مختلف اجرا کرد که حالت‌های مقایسه (compare modes) نام دارند، و می‌توان از آن‌ها برای مقایسهٔ رفتار همهٔ تست‌ها با پرچم‌های مختلف کامپایلر استفاده کرد. این می‌تواند به برجسته‌کردن تفاوت‌هایی که با پرچم‌های مشخص ممکن است ظاهر شوند کمک کند، و مشکلات احتمالی را بررسی کند.

    برای اجرای تست‌ها در حالت متفاوت، باید پرچم خط فرمان --compare-mode را بدهید:

    ./x test tests/ui --compare-mode=next-solver

    حالت‌های مقایسهٔ ممکن این‌ها هستند:

    • polonius — با Polonius و -Zpolonius=next اجرا می‌کند.
    • next-solver — با trait solver بعدی و -Znext-solver اجرا می‌کند.
    • next-solver-coherence — coherence را با trait solver بعدی و -Znext-solver=coherence اجرا می‌کند.
    • split-dwarf — با split-DWARF باز (unpacked) و -Csplit-debuginfo=unpacked اجرا می‌کند.
    • split-dwarf-single — با split-DWARF بسته‌بندی‌شده (packed) و -Csplit-debuginfo=packed اجرا می‌کند.

    برای اطلاعات بیشتر دربارهٔ اینکه تست‌های UI چگونه از خروجی متفاوت برای حالت‌های مختلف پشتیبانی می‌کنند، حالت‌های مقایسهٔ UI را ببینید.

    در CI، حالت‌های مقایسه فقط در یک builder لینوکس و فقط با تنظیمات زیر به‌کار می‌روند:

    • tests/debuginfo: از حالت split-dwarf استفاده می‌کند. این کمک می‌کند هنگام فعال‌کردن split-DWARF هیچ‌کدام از تست‌های debuginfo تحت‌تأثیر قرار نگیرند.

    توجه کنید حالت‌های مقایسه جدا از revisionها هستند. هنگام اجرای ./x test tests/ui همهٔ revisionها تست می‌شوند، اما حالت‌های مقایسه باید به‌صورت دستی و جداگانه با پرچم --compare-mode اجرا شوند.

    Parallel frontend

    Compiletest را می‌توان با پرچم --parallel-frontend-threads برای اجرای کامپایلر در حالت موازی اجرا کرد. از این می‌توان برای بررسی اینکه کامپایلر در حالت موازی همان خروجی حالت غیرموازی را تولید می‌کند، و برای بررسی مشکلات احتمالی در حالت موازی استفاده کرد.

    برای اجرای تست‌ها در حالت موازی، باید پرچم خط فرمان --parallel-frontend-threads را بدهید:

    ./x test tests/ui -- --parallel-frontend-threads=N --iteration-count=M

    که در آن N تعداد threadها برای frontend موازی است، و M تعداد دفعاتی است که هر تست در حالت موازی اجرا می‌شود (تا احتمال گرفتن هر نوع عدم‌قطعیت بیشتر شود).

    همچنین هنگام اجرا با --parallel-frontend-threads، directive با نام compare-output-by-lines برای همهٔ تست‌ها ضمنی خواهد بود، چون خروجی frontend موازی از نظر ترتیب خطوط می‌تواند غیرقطعی باشد.

    frontend موازی فعلاً فقط در تست‌های UI در دسترس است، و در مجموعه‌های تست دیگر پشتیبانی نمی‌شود.
