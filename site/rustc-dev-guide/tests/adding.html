راهنمای توسعهٔ rustcrustc Development Guide

    Adding new tests

    به‌طور کلی انتظار داریم هر PR که یک باگ در rustc را رفع می‌کند همراه با یک تست رگرسیون از نوعی باشد. این تست باید در main شکست بخورد اما پس از PR بگذرد. این تست‌ها واقعاً برای جلوگیری از تکرار اشتباهات گذشته مفیدند.

    اولین کار تصمیم‌گیری دربارهٔ نوع تستی است که باید اضافه شود. این به ماهیت تغییر و آنچه می‌خواهید بیازمایید بستگی دارد. چند رهنمود تقریبی:

    • The majority of compiler tests are done with compiletest.
      • بیشتر تست‌های compiletest تست‌های UI در پوشهٔ tests/ui هستند.
    • Changes to the standard library are usually tested within the standard library itself.
      • بیشتر تست‌های کتابخانهٔ استاندارد به‌صورت doctest نوشته می‌شوند، که رفتار معمول API را نشان می‌دهند و می‌آزمایند.
      • تست‌های واحد اضافی باید در library/${crate}/tests قرار بگیرند (که در آن ${crate} معمولاً std است).
      • Tests for the alloc or core crates must go in separate crates: alloctests or coretests respectively.
        • نکته: هنگام افزودن تست‌های واحد برای قابلیت‌های ناپایدار، اعلان #![feature(...)] باید به library/${crate}tests/tests/lib.rs اضافه شود، نه به library/${crate}tests/lib.rs.
    • اگر کد بخشی از یک سیستم ایزوله است و خروجی کامپایلر را تست نمی‌کنید، استفاده از تست واحد یا یکپارچگی را در نظر بگیرید.
    • نیاز به اجرای rustdoc دارید؟ تست rustdoc یا rustdoc-ui را ترجیح دهید. گاهی rustdoc-js هم لازم می‌شود.
    • Other compiletest test suites are generally used for special purposes:
      • نیاز به اجرای gdb یا lldb دارید؟ از مجموعهٔ تست debuginfo استفاده کنید.
      • نیاز به بررسی LLVM IR یا MIR IR دارید؟ از مجموعه‌های تست codegen یا mir-opt استفاده کنید.
      • Need to inspect the resulting binary in some way? Or if all the other test suites are too limited for your purposes? Then use run-make.
        • اگر باید cargo درون‌درختی را همراه با rustc درون‌درختی بیازمایید، از run-make-cargo استفاده کنید.
      • برای مجموعه‌های تست تخصصی‌تر فصل compiletest را ببینید.

    پس از تصمیم دربارهٔ نوع تستی که باید اضافه شود، برای راهنمایی در نوشتن تست‌هایی که کار با آن‌ها آسان است و در برابر زمان مقاومت می‌کنند (یعنی اگر تستی چند سال بعد شکست بخورد یا نیاز به تغییر داشته باشد، چگونه می‌توانیم کار را برایشان آسان‌تر کنیم؟)، بهترین روش‌ها را ببینید.

    UI test walkthrough

    در ادامه راهنمای پایه‌ای برای ساخت یک تست UI آمده است که یکی از رایج‌ترین تست‌های کامپایلر است. در این آموزش تستی برای یک پیام خطای async اضافه می‌کنیم.

    گام ۱: یک فایل تست اضافه کنید

    اولین گام ساخت یک فایل منبع Rust در جایی درون درخت tests/ui است. هنگام ساخت یک تست، تمام تلاش‌تان را بکنید تا مکان و نام خوبی پیدا کنید (برای اطلاعات بیشتر سازمان‌دهی تست‌ها را ببینید). از آنجا که نام‌گذاری سخت‌ترین بخش توسعه است، از اینجا به بعد همه‌چیز سرازیری است!

    بیایید تست async خود را در tests/ui/async-await/await-without-async.rs قرار دهیم:

    // Provide diagnostics when the user writes `await` in a non-`async` function.
//@ edition:2018

async fn foo() {}

fn bar() {
    foo().await
}

fn main() {}

    چند نکته دربارهٔ تست ما:

    • بالای فایل باید یک کامنت کوتاه شروع شود که توضیح می‌دهد تست برای چیست.
    • کامنت //@ edition:2018 یک directive نامیده می‌شود که به compiletest دستور می‌دهد تست را چگونه بسازد. در اینجا باید edition را تنظیم کنیم تا async کار کند (پیش‌فرض edition 2015 است).
    • پس از آن منبع تست می‌آید. سعی کنید مختصر و مفید باشد. اگر می‌خواهید یک مثال را از گزارش باگ کمینه کنید ممکن است کمی تلاش لازم باشد.
    • این تست را با یک تابع خالی fn main تمام می‌کنیم. دلیلش این است که پیش‌فرض تست‌های UI نوع crate از نوع bin است، و نمی‌خواهیم خطای «main not found» در تست‌مان باشد. راه دیگر این است که #![crate_type="lib"] را اضافه کنید.

    گام ۲: خروجی مورد انتظار را تولید کنید

    گام بعدی ساخت snapshotهای خروجی مورد انتظار از کامپایلر است. این کار با گزینهٔ --bless انجام می‌شود:

    ./x test tests/ui/async-await/await-without-async.rs --bless

    این کامپایلر را می‌سازد (اگر قبلاً ساخته نشده باشد)، تست را کامپایل می‌کند و خروجی کامپایلر را در فایلی به نام tests/ui/async-await/await-without-async.stderr قرار می‌دهد.

    اما این گام شکست می‌خورد! باید یک پیام خطا ببینید، چیزی شبیه این:

    error: /rust/tests/ui/async-await/await-without-async.rs:7: unexpected error: ‘7:10: 7:16: await is only allowed inside async functions and blocks E0728’

    دلیلش این است که stderr شامل خطاهایی است که با annotationهای خطا در فایل منبع مطابقت داده نشده‌اند.

    گام ۳: annotationهای خطا را اضافه کنید

    هر خطا باید با یک کامنت در منبع که متن خطا را دارد annotate شود. در این مورد می‌توانیم کامنت زیر را به فایل تست اضافه کنیم:

    fn bar() {
    foo().await
    //~^ ERROR `await` is only allowed inside `async` functions and blocks
}

    کامنت با نماد //~^ (شبیه خط موجی و علامت caret) به compiletest می‌گوید خطا به خط قبلی تعلق دارد (جزئیات بیشتر در بخش annotationهای خطا).

    آن را ذخیره کنید و تست را دوباره اجرا کنید:

    ./x test tests/ui/async-await/await-without-async.rs

    حالا باید بگذرد، آفرین!

    گام ۴: خروجی را بازبینی کنید

    تا حدی در ارتباط با گام قبلی، باید فایل .stderr ساخته‌شده را بررسی کنید تا ببینید آیا آن‌طور که انتظار دارید به نظر می‌رسد. اگر پیام تشخیصی جدیدی اضافه می‌کنید، اکنون زمان خوبی است که خوانایی کلی پیام را هم بررسی کنید، به‌ویژه برای افرادی که تازه با Rust آشنا شده‌اند.

    فایل نمونهٔ ما tests/ui/async-await/await-without-async.stderr باید این‌طور به نظر برسد:

    error[E0728]: `await` is only allowed inside `async` functions and blocks
  --> $DIR/await-without-async.rs:7:10
   |
LL | fn bar() {
   |    --- this is not `async`
LL |     foo().await
   |          ^^^^^^ only allowed inside `async` functions and blocks

error: aborting due to previous error

For more information about this error, try `rustc --explain E0728`.

    ممکن است متوجه شوید برخی چیزها کمی با خروجی معمول کامپایلر متفاوت‌اند.

    • $DIR اطلاعات مسیر را که بین سیستم‌ها فرق می‌کند حذف می‌کند.
    • مقادیر LL جای شمارهٔ خطوط را می‌گیرند. این کمک می‌کند تغییرات کوچک در منبع باعث diffهای بزرگ نشوند. برای اطلاعات بیشتر بخش نرمال‌سازی را ببینید.

    در حوالی این مرحله ممکن است لازم باشد چند بار گام‌های آخر را تکرار کنید تا تست را تنظیم کنید، دوباره bless کنید و خروجی را دوباره بازبینی کنید.

    گام ۵: تست‌های دیگر را بررسی کنید

    گاهی هنگام افزودن یا تغییر یک پیام تشخیصی، این بر تست‌های دیگر در مجموعهٔ تست اثر می‌گذارد. گام آخر پیش از ارسال PR بررسی این است که آیا چیز دیگری را تحت‌تأثیر قرار داده‌اید. اجرای مجموعهٔ UI معمولاً شروع خوبی است:

    ./x test tests/ui

    اگر تست‌های دیگر شروع به شکست‌خوردن کنند، ممکن است لازم باشد بررسی کنید چه چیزی تغییر کرده و آیا خروجی جدید منطقی است.

    ممکن است لازم شود خروجی را با پرچم --bless دوباره bless کنید.

    کامنت توضیح‌دهندهٔ موضوع تست

    اولین کامنت یک فایل تست باید هدف تست را خلاصه کند و آنچه را دربارهٔ آن مهم است برجسته کند. اگر شمارهٔ issueای با تست مرتبط است، شمارهٔ issue را بیاورید.

    این کامنت لازم نیست بسیار مفصل باشد. فقط چیزی شبیه این شاید کافی باشد: «تست رگرسیون برای #18060: بازوهای match به ترتیب نادرست تطبیق داده می‌شدند».

    این کامنت‌ها بعدها وقتی تست شما می‌شکند برای دیگران بسیار مفیدند، چون اغلب می‌توانند مشکل را برجسته کنند. همچنین اگر به دلیلی نیاز به بازآرایی تست‌ها باشد مفیدند، چون به دیگران می‌گویند کدام بخش‌های تست مهم بوده‌اند. اغلب یک تست باید بازنویسی شود چون دیگر آنچه را باید می‌آزمود نمی‌آزماید، و آن‌گاه مفید است بدانیم دقیقاً قرار بود چه چیزی را بیازماید.
