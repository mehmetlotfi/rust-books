راهنمای توسعهٔ rustcrustc Development Guide

    Running tests

    می‌توانید کل مجموعهٔ تست‌ها را با x اجرا کنید. اما توجه کنید که اجرای کل مجموعهٔ تست‌ها تقریباً هرگز چیزی نیست که هنگام توسعهٔ محلی بخواهید، چون زمان بسیار زیادی می‌برد. برای توسعهٔ محلی، زیربخش بعدی دربارهٔ اجرای زیرمجموعه‌ای از تست‌ها را ببینید.

    اجرای ساده ./x test کامپایلر stage 1 را می‌سازد و سپس کل مجموعهٔ تست را اجرا می‌کند. این نه‌فقط tests/ بلکه تست‌های بسته‌های library/، compiler/، src/tools/ و بیشتر را هم شامل می‌شود.

    معمولاً فقط می‌خواهید زیرمجموعه‌ای از مجموعه‌های تست (یا حتی مجموعه‌ای کوچک‌تر از تست‌ها) را اجرا کنید که انتظار دارید تغییرات شما را بیازماید. CI مربوط به PR زیرمجموعه‌ای از مجموعه‌های تست را اجرا می‌کند، و CI صف merge همهٔ مجموعهٔ تست را اجرا می‌کند.

    ./x test

    نتایج تست cache می‌شوند و تست‌هایی که قبلاً موفق بوده‌اند هنگام تست ignored می‌شوند. محتوای stdout/stderr و یک فایل زمان‌سنج برای هر تست را می‌توان زیر build/<target-tuple>/test/ برای <target-tuple> داده‌شده یافت. برای اجبار به اجرای مجدد یک تست (مثلاً اگر اجراکنندهٔ تست تغییری را تشخیص ندهد) می‌توانید از گزینهٔ خط فرمان --force-rerun استفاده کنید.

    نکته دربارهٔ نیازمندی‌های وابستگی‌های خارجی

    برخی مجموعه‌های تست ممکن است به وابستگی‌های خارجی نیاز داشته باشند. این به‌ویژه دربارهٔ تست‌های debuginfo صادق است. برخی تست‌های debuginfo به gdb دارای پشتیبانی Python نیاز دارند. می‌توانید بررسی کنید gdb نصب‌شدهٔ شما از Python پشتیبانی می‌کند یا نه، با استفاده از دستور python در درون gdb. پس از اجرا می‌توانید کد Python (مثلاً print("hi")) بنویسید، سپس return و بعد CTRL+D را برای اجرای آن بزنید. اگر gdb را از منبع می‌سازید، باید با --with-python=<path-to-python-binary> پیکربندی کنید.

    اجرای زیرمجموعه‌ای از مجموعه‌های تست

    هنگام کار روی یک PR مشخص، معمولاً می‌خواهید مجموعهٔ کوچک‌تری از تست‌ها را اجرا کنید. برای مثال، یک «smoke test» خوب که پس از تغییر rustc می‌توان به‌کار برد تا ببینید همه‌چیز عموماً درست کار می‌کند، اجرای مجموعهٔ تست ui است (tests/ui):

    ./x test tests/ui

    البته انتخاب مجموعه‌های تست تا حدی دلبخواه است و ممکن است با کاری که انجام می‌دهید جور نباشد. برای مثال، اگر روی debuginfo کار می‌کنید، شاید مجموعهٔ تست debuginfo بهتر باشد:

    ./x test tests/debuginfo

    اگر فقط نیاز دارید زیرپوشهٔ مشخصی از تست‌ها را برای هر مجموعهٔ تست مشخص اجرا کنید، می‌توانید آن پوشه را به‌عنوان فیلتر به ./x test بدهید:

    ./x test tests/ui/const-generics

    نکته برای MSYS2

    در MSYS2 مسیرها عجیب به نظر می‌رسند و ./x test نه tests/ui/const-generics را می‌شناسد و نه tests\ui\const-generics را. در آن صورت می‌توانید با استفاده از مثلاً ./x test ui --test-args="tests/ui/const-generics" دور بزنید.

    همین‌طور می‌توانید با دادن مسیر یک فایل، آن تک‌فایل را تست کنید:

    ./x test tests/ui/const-generics/const-test.rs

    x هنوز از اجرای تست یک ابزار با دادن مسیر آن پشتیبانی نمی‌کند. باید از آرگومان --test-args استفاده کنید، همان‌طور که در ادامه توضیح داده شده است.

    ./x test src/tools/miri --test-args tests/fail/uninit/padding-enum.rs

    فقط اسکریپت tidy را اجرا کنید

    ./x test tidy

    تست‌های کتابخانهٔ استاندارد را اجرا کنید

    ./x test --stage 0 library/std

    توجه کنید که این فقط تست‌های std را اجرا می‌کند؛ اگر می‌خواهید core یا crateهای دیگر را تست کنید، باید آن‌ها را صراحتاً مشخص کنید.

    اسکریپت tidy و تست‌های کتابخانهٔ استاندارد را اجرا کنید

    ./x test --stage 0 tidy library/std

    تست‌های کتابخانهٔ استاندارد را با کامپایلر stage 1 اجرا کنید

    ./x test --stage 1 library/std

    با فهرست‌کردن مجموعه‌های تستی که می‌خواهید اجرا کنید، از اجرای تست‌های اجزایی که اصلاً تغییرشان نداده‌اید پرهیز می‌کنید.

    توجه کنید که bors تست‌ها را فقط با ساخت کامل stage 2 اجرا می‌کند؛ بنابراین، هرچند تست‌ها معمولاً با stage 1 خوب کار می‌کنند، چند محدودیت وجود دارد.

    همهٔ تست‌ها را با کامپایلر stage 2 اجرا کنید

    ./x test --stage 2
    You almost never need to do this; CI will run these tests for you.

    اجرای تست‌های واحد روی کامپایلر/کتابخانه

    ممکن است بخواهید تست‌های واحد را روی یک فایل مشخص با دستور زیر اجرا کنید:

    ./x test compiler/rustc_data_structures/src/thin_vec/tests.rs

    اما متأسفانه ممکن نیست. به‌جای آن باید این را فراخوانی کنید:

    ./x test compiler/rustc_data_structures/ --test-args thin_vec

    اجرای یک تست جداگانه

    کار رایج دیگری که افراد می‌خواهند انجام دهند اجرای یک تست جداگانه است، اغلب تستی که سعی می‌کنند رفعش کنند. همان‌طور که پیش‌تر گفته شد، می‌توانید مسیر کامل فایل را بدهید، یا می‌توانید x را با گزینهٔ --test-args فراخوانی کنید:

    ./x test tests/ui --test-args issue-1234

    در پشت صحنه، اجراکنندهٔ تست اجراکنندهٔ استاندارد تست Rust را فراخوانی می‌کند (همان که با #[test] دریافت می‌کنید)، پس این دستور در نهایت فقط تست‌هایی را فیلتر می‌کند که «issue-1234» در نامشان باشد. بنابراین --test-args راه خوبی برای اجرای مجموعه‌ای از تست‌های مرتبط است.

    دادن آرگومان به rustc هنگام اجرای تست‌ها

    گاهی می‌تواند مفید باشد برخی تست‌ها را با آرگومان‌های مشخص کامپایلر اجرا کنید، بدون استفاده از RUSTFLAGS (مثلاً هنگام توسعهٔ قابلیت‌های ناپایدار با پرچم‌های -Z).

    این کار با گزینهٔ --compiletest-rustc-args در ./x test ممکن است، که آرگومان‌های اضافی را هنگام ساخت تست‌ها به کامپایلر می‌دهد.

    ویرایش و به‌روزرسانی فایل‌های مرجع

    اگر خروجی کامپایلر را عمداً تغییر داده‌اید، یا تست جدیدی می‌سازید، می‌توانید --bless را به زیردستور test بدهید.

    برای مثال، اگر برخی تست‌های tests/ui شکست می‌خورند، می‌توانید این دستور را اجرا کنید:

    ./x test tests/ui --bless

    این به‌طور خودکار فایل‌های .stderr، .stdout یا .fixed همهٔ تست‌های test/ui را تنظیم می‌کند. البته می‌توانید فقط تست‌های مشخصی را هم با پرچم --test-args your_test_name هدف بگیرید، درست مثل اجرای تست‌ها بدون پرچم --bless.

    Configuring test running

    چند گزینه برای اجرای تست‌ها هست:

    • bootstrap.toml گزینهٔ rust.verbose-tests را دارد. اگر false باشد، هر تست یک نقطه چاپ می‌کند (پیش‌فرض). اگر true باشد، نام هر تست چاپ می‌شود. این معادل گزینهٔ --quiet در test harness در Rust است.
    • متغیر محیطی RUST_TEST_THREADS را می‌توان روی تعداد threadهای همزمان برای تست تنظیم کرد.

    Passing --pass $mode

    تست‌های UI از نوع pass اکنون سه حالت دارند: check-pass، build-pass و run-pass. وقتی --pass $mode داده شود، این تست‌ها مجبور می‌شوند تحت $mode داده‌شده اجرا شوند مگر اینکه دستور //@ no-pass-override در فایل تست وجود داشته باشد. برای مثال، می‌توانید همهٔ تست‌های tests/ui را به‌صورت check-pass اجرا کنید:

    ./x test tests/ui --pass check

    با دادن --pass $mode می‌توانید زمان تست را کاهش دهید. برای هر حالت، لطفاً کنترل انتظارات pass/fail را ببینید.

    اجرای تست‌ها با «حالت‌های مقایسه» مختلف

    تست‌های UI ممکن است بسته به «حالت‌های» مشخصی که کامپایلر در آن است خروجی متفاوتی داشته باشند. برای مثال، هنگام استفاده از حالت Polonius، تست foo.rs ابتدا خروجی مورد انتظار را در foo.polonius.stderr جست‌وجو می‌کند و اگر نیافت به foo.stderr معمول برمی‌گردد. دستور زیر مجموعهٔ تست UI را در حالت Polonius اجرا می‌کند:

    ./x test tests/ui --compare-mode=polonius

    برای جزئیات بیشتر حالت‌های مقایسه را ببینید.

    Running tests manually

    گاهی ساده‌تر و سریع‌تر است که تست را دستی اجرا کنید. بیشتر تست‌ها فقط فایل‌های .rs هستند، پس پس از ساخت یک toolchain در rustup می‌توانید چیزی شبیه این بکنید:

    rustc +stage1 tests/ui/issue-1234.rs

    این بسیار سریع‌تر است اما همیشه کار نمی‌کند. برای مثال، برخی تست‌ها شامل دستورهایی هستند که پرچم‌های مشخص کامپایلر را تعیین می‌کنند یا به crateهای دیگر وابسته‌اند، و ممکن است بدون آن گزینه‌ها به همان شکل اجرا نشوند.

    اجرای تست‌ها روی ماشین راه‌دور

    تست‌ها را می‌توان روی ماشین راه‌دور اجرا کرد (مثلاً برای تست ساخت‌ها برای معماری متفاوت). این با استفاده از remote-test-client روی ماشین ساخت انجام می‌شود تا برنامه‌های تست را به remote-test-server که روی ماشین راه‌دور اجرا می‌شود بفرستد. remote-test-server برنامه‌های تست را اجرا می‌کند و نتایج را به ماشین ساخت برمی‌گرداند. remote-test-server اجرای کد راه‌دور بدون احراز هویت فراهم می‌کند، پس مراقب باشید کجا استفاده می‌شود.

    برای این کار، ابتدا remote-test-server را برای ماشین راه‌دور بسازید (با مثال RISC-V):

    ./x build src/tools/remote-test-server --target riscv64gc-unknown-linux-gnu

    فایل دودویی در ./build/host/stage2-tools/$TARGET_ARCH/release/remote-test-server ساخته می‌شود. آن را به ماشین راه‌دور کپی کنید.

    روی ماشین راه‌دور، remote-test-server را با پرچم --bind 0.0.0.0:12345 (و در صورت تمایل پرچم --verbose) اجرا کنید. خروجی باید به این شکل باشد:

    $ ./remote-test-server --verbose --bind 0.0.0.0:12345
starting test server
listening on 0.0.0.0:12345!

    توجه کنید که bind‌کردن سرور به 0.0.0.0 به همهٔ میزبان‌هایی که به ماشین شما دسترسی دارند اجازه می‌دهد کد دلخواه را روی ماشین شما اجرا کنند. قویاً توصیه می‌کنیم یا firewall راه بیندازید تا دسترسی خارجی به پورت 12345 مسدود شود، یا هنگام bind از آدرس IP محدودتری استفاده کنید.

    می‌توانید با اتصال به remote-test-server و ارسال ping\n بررسی کنید کار می‌کند. باید با pong پاسخ دهد:

    $ nc $REMOTE_IP 12345
ping
pong

    برای اجرای تست‌ها با اجراکنندهٔ راه‌دور، متغیر محیطی TEST_DEVICE_ADDR را تنظیم کنید و سپس مثل همیشه از x استفاده کنید. برای مثال، برای اجرای تست‌های ui روی ماشین RISC-V با آدرس IP برابر 1.2.3.4 از این استفاده کنید

    export TEST_DEVICE_ADDR="1.2.3.4:12345"
./x test tests/ui --target riscv64gc-unknown-linux-gnu

    اگر remote-test-server با پرچم verbose اجرا شده باشد، خروجی روی ماشین تست ممکن است چیزی شبیه این باشد

    [...]
run "/tmp/work/test1007/a"
run "/tmp/work/test1008/a"
run "/tmp/work/test1009/a"
run "/tmp/work/test1010/a"
run "/tmp/work/test1011/a"
run "/tmp/work/test1012/a"
run "/tmp/work/test1013/a"
run "/tmp/work/test1014/a"
run "/tmp/work/test1015/a"
run "/tmp/work/test1016/a"
run "/tmp/work/test1017/a"
run "/tmp/work/test1018/a"
[...]

    تست‌ها روی ماشینی که x را اجرا می‌کند ساخته می‌شوند نه روی ماشین راه‌دور. تست‌هایی که به‌طور غیرمنتظره ساخته نمی‌شوند (یا تست‌های ui که خروجی ساخت نادرست تولید می‌کنند) ممکن است بدون اینکه هرگز روی ماشین راه‌دور اجرا شوند شکست بخورند.

    یک مهلت پیش‌فرض ۳۰ دقیقه‌ای هست برای وقتی که دستور x نتواند به remote-test-server برسد. این مهلت را می‌توان با متغیر محیطی TEST_DEVICE_CONNECT_TIMEOUT_SECONDS تغییر داد.

    تست روی شبیه‌سازها (emulators)

    برخی پلتفرم‌ها برای معماری‌هایی که به‌راحتی در دسترس نیستند با شبیه‌ساز تست می‌شوند. برای معماری‌هایی که کتابخانهٔ استاندارد در آن‌ها به‌خوبی پشتیبانی می‌شود و سیستم‌عامل میزبان از شبکهٔ TCP/IP پشتیبانی می‌کند، دستورالعمل‌های بالا برای تست روی ماشین راه‌دور را ببینید (در این حالت ماشین راه‌دور شبیه‌سازی می‌شود).

    همچنین مجموعه‌ای از ابزارها برای هماهنگ‌کردن اجرای تست‌ها درون شبیه‌ساز هست. پلتفرم‌هایی مثل arm-android و arm-unknown-linux-gnueabihf طوری تنظیم شده‌اند که تست‌ها را به‌طور خودکار تحت شبیه‌سازی در GitHub Actions اجرا کنند. در ادامه نگاهی می‌اندازیم به اینکه تست‌های یک هدف چگونه تحت شبیه‌سازی اجرا می‌شوند.

    ایمیج Docker برای armhf-gnu شامل QEMU برای شبیه‌سازی معماری CPU ARM است. در درخت Rust ابزارهای remote-test-client و remote-test-server قرار دارند که برنامه‌هایی برای ارسال برنامه‌ها و کتابخانه‌های تست به شبیه‌ساز، اجرای تست‌ها درون شبیه‌ساز و خواندن نتایج‌اند. ایمیج Docker طوری تنظیم شده که remote-test-server را اجرا کند و ابزارهای ساخت از remote-test-client برای ارتباط با سرور استفاده می‌کنند تا اجرای تست‌ها را هماهنگ کنند (src/bootstrap/src/core/build_steps/test.rs را ببینید).

    برای اجرا روی شبیه‌ساز iOS/tvOS/watchOS/visionOS، می‌توانیم آن را هم مثل ماشین «راه‌دور» در نظر بگیریم. جزئیات جالب اینجاست که شبکه بین نمونهٔ شبیه‌ساز و macOS میزبان مشترک است، پس می‌توانیم از آدرس loopback محلی 127.0.0.1 استفاده کنیم. چیزی شبیه این باید کار کند:

    # Build the test server for the iOS simulator:
./x build src/tools/remote-test-server --target aarch64-apple-ios-sim

# If you already have a simulator instance open, copy the device UUID from:
xcrun simctl list devices booted
UDID=01234567-89AB-CDEF-0123-456789ABCDEF

# Alternatively, create and boot a new simulator instance:
xcrun simctl list runtimes
xcrun simctl list devicetypes
UDID=$(xcrun simctl create $CHOSEN_DEVICE_TYPE $CHOSEN_RUNTIME)
xcrun simctl boot $UDID
# See https://nshipster.com/simctl/ for details.

# Spawn the runner on port 12345:
xcrun simctl spawn $UDID ./build/host/stage2-tools/aarch64-apple-ios-sim/release/remote-test-server -v --bind 127.0.0.1:12345

# In a new terminal, run tests via the runner:
export TEST_DEVICE_ADDR="127.0.0.1:12345"
./x test --host='' --target aarch64-apple-ios-sim --skip tests/debuginfo
# FIXME(madsmtm): Allow debuginfo tests to work (maybe needs `.dSYM` folder to be copied to the target?).

    تست‌کردن تست‌ها روی wasi (wasm32-wasip1)

    برخی تست‌ها مخصوص اهداف wasm هستند. برای اجرای این تست‌ها، باید --target wasm32-wasip1 را به x test بدهید. علاوه بر این به wasi sdk نیاز دارید. دستورالعمل نصب مخزن wasi sdk را دنبال کنید تا sysroot را روی رایانهٔ خود داشته باشید. در صفحهٔ پشتیبانی از هدف wasm32-wasip1 حداقل نسخه‌ای مشخص شده که sdk شما باید بتواند بسازد. برخی دستورهای cmake که مدتی طول می‌کشند و هشدارهای C++ بسیار نگران‌کننده‌ای می‌دهند… سپس، در bootstrap.toml، sysroot را این‌طور مشخص کنید:

    [target.wasm32-wasip1]
wasi-root = "<wasi-sdk location>/build/sysroot/install/share/wasi-sysroot"
