    تست‌های یکپارچگی Rust for Linux

    Rust for Linux (RfL) تلاشی برای افزودن پشتیبانی از زبان Rust به هستهٔ لینوکس است.

    اگر job مربوط به Rust for Linux شکست خورد چه کنیم؟

    اگر یک PR job در CI مربوط به Rust for Linux را بشکند، آن‌گاه:

    • If the breakage was unintentional and seems spurious, then let RfL know and retry.
      • اگر PR فوری است و تلاش مجدد آن را رفع نمی‌کند، job در CI را موقتاً غیرفعال کنید (job با نام image: x86_64-rust-for-linux را در src/ci/github-actions/jobs.yml کامنت کنید).
    • اگر شکستگی ناخواسته بود، PR را تغییر دهید تا شکستگی رفع شود.
    • If the breakage was intentional, then let RfL know and discuss what will the kernel need to change.
      • اگر PR فوری است، job در CI را موقتاً غیرفعال کنید (job با نام image: x86_64-rust-for-linux را در src/ci/github-actions/jobs.yml کامنت کنید).
      • اگر PR می‌تواند چند روز صبر کند، منتظر بمانید نگه‌دارندگان RfL commit hash جدیدی از هستهٔ لینوکس با تغییرات لازم ارائه دهند و آن را به PR اعمال کنید، که تأیید می‌کند تغییرات کار می‌کنند (متغیر محیطی LINUX_VERSION را در src/ci/docker/scripts/rfl-build.sh به‌روز کنید).

    اگر نیاز دارید با توسعه‌دهندگان RfL تماس بگیرید، می‌توانید گروه ping با نام Rust for Linux را برای درخواست کمک ping کنید:

    @rustbot ping rfl

    ساخت Rust for Linux در CI

    Rust for Linux به‌عنوان بخشی از مجموعهٔ تست‌های bors که پیش از merge شدن pull request اجرا می‌شوند ساخته می‌شود.

    workflow یک sysroot از stage1 کامپایلر Rust می‌سازد، هستهٔ لینوکس را دانلود می‌کند، و سعی می‌کند چند درایور و مثال Rust for Linux را با این sysroot کامپایل کند. RfL از چند قابلیت ناپایدار کامپایلر/زبان استفاده می‌کند، بنابراین این workflow به ما اطلاع می‌دهد اگر تغییری در کامپایلر آن را بشکند.

    اگر نگران هستید یک pull request ممکن است builder مربوط به Rust for Linux را بشکند و می‌خواهید پیش از ارسال آن به صف bors تستش کنید، فقط از bors بخواهید job از نوع try را اجرا کند که یکپارچگی Rust for Linux را می‌سازد: @bors try jobs=x86_64-rust-for-linux.
