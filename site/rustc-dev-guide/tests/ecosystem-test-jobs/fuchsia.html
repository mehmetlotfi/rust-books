راهنمای توسعهٔ rustcrustc Development Guide

    Fuchsia integration tests

    Fuchsia یک سیستم‌عامل متن‌باز با حدود ۲ میلیون خط کد Rust است.1 این پروژه در گذشته تعداد زیادی رگرسیون را گرفته و سپس در CI گنجانده شد.

    اگر job مربوط به Fuchsia شکست خورد چه کنیم؟

    لطفاً با گروه ping با نام fuchsia تماس بگیرید و از آن‌ها کمک بخواهید.

    @rustbot ping fuchsia

    ساخت Fuchsia در CI

    Fuchsia به‌عنوان بخشی از مجموعهٔ تست‌های bors که پیش از merge شدن pull request اجرا می‌شوند ساخته می‌شود.

    اگر نگران هستید یک pull request ممکن است builder مربوط به Fuchsia را بشکند و می‌خواهید پیش از ارسال آن به صف bors تستش کنید، فقط از bors بخواهید job از نوع try را اجرا کند که یکپارچگی Fuchsia را می‌سازد:

    @bors try jobs=test-x86_64-fuchsia

    Building Fuchsia locally

    چون Fuchsia از زبان‌هایی غیر از Rust استفاده می‌کند، از Cargo به‌عنوان سامانهٔ ساخت استفاده نمی‌کند. همچنین لازم است ساخت toolchain به شکل مشخصی پیکربندی شود.

    روش توصیه‌شده برای ساخت Fuchsia استفاده از اسکریپت‌های Docker است که checkout و ساخت Fuchsia را برایتان انجام می‌دهند. اگر قبلاً تست‌های Docker را اجرا کرده‌اید، می‌توانید این دستور را از checkout مربوط به Rust اجرا کنید تا Fuchsia را با toolchain محلی Rust خود دانلود و بسازید.

    src/ci/docker/run.sh test-x86_64-fuchsia

    برای جزئیات بیشتر دربارهٔ نحوهٔ اجرا و اشکال‌زدایی jobها با Docker فصل تست با Docker را ببینید.

    توجه کنید که checkout مربوط به Fuchsia بزرگ است — در زمان نگارش، checkout و ساخت بیش از ۶۷ گیگابایت فضا می‌گیرد — و همان‌طور که می‌توانید تصور کنید، تمام‌شدنش مدتی طول می‌کشد.

    تغییر checkout مربوط به Fuchsia

    دلیل اصلی که می‌خواهید Fuchsia را به‌صورت محلی بسازید این است که باید یک رگرسیون را بررسی کنید. پس از اجرای ساخت Docker، checkout مربوط به Fuchsia را درون پوشهٔ obj/test-x86_64-fuchsia/fuchsia در checkout مربوط به Rust خود می‌یابید. اگر خط KEEP_CHECKOUT را در اسکریپت build-fuchsia.sh به KEEP_CHECKOUT=1 تغییر دهید، می‌توانید checkout را هر طور لازم است تغییر دهید و دستور ساخت بالا را دوباره اجرا کنید. این همهٔ نتایج ساخت قبلی را دوباره به‌کار می‌برد.

    گزینه‌های بیشتری برای سفارشی‌سازی checkout مربوط به Fuchsia را در اسکریپت build-fuchsia.sh می‌یابید.

    سفارشی‌سازی ساخت Fuchsia

    اطلاعات بیشتر دربارهٔ گزینه‌های مورد استفاده برای ساخت Fuchsia در Rust CI را در اسکریپت build_fuchsia_from_rust_ci.sh که توسط build-fuchsia.sh فراخوانی می‌شود می‌یابید.

    سامانهٔ ساخت Fuchsia از GN استفاده می‌کند، یک سامانهٔ metabuild که فایل‌های Ninja تولید می‌کند و سپس کار اجرای ساخت را به Ninja می‌سپارد.

    توسعه‌دهندگان Fuchsia از fx برای اجرای ساخت‌ها و انجام کارهای توسعهٔ دیگر استفاده می‌کنند. این ابزار در .jiri_root/bin در checkout مربوط به Fuchsia قرار دارد؛ ممکن است برای برخی گردش‌کارها لازم باشد آن را به $PATH اضافه کنید.

    چند زیردستور fx مرتبط‌اند، از جمله:

    • fx set آرگومان‌های ساخت را می‌پذیرد، آن‌ها را در out/default/args.gn می‌نویسد و GN را اجرا می‌کند.
    • fx build پروژهٔ Fuchsia را با Ninja می‌سازد. تغییرات آرگومان‌های ساخت را به‌طور خودکار می‌گیرد و GN را دوباره اجرا می‌کند. به‌طور پیش‌فرض همه‌چیز را می‌سازد، اما مسیرهای هدف را هم می‌پذیرد تا هدف‌های مشخص را بسازد (در ادامه ببینید).
    • fx clippy Clippy را روی هدف‌های مشخص Rust (یا همه) اجرا می‌کند. ما از این در ساخت Rust CI برای پرهیز از اجرای codegen روی بیشتر هدف‌های Rust استفاده می‌کنیم. در زیر، مثل fx build Ninja را فراخوانی می‌کند. نتایج clippy پیش از چاپ در فایل‌های json درون پوشهٔ خروجی ساخت ذخیره می‌شوند.

    Target paths

    GN از مسیرهایی مثل زیر برای شناسایی هدف‌های ساخت استفاده می‌کند:

    //src/starnix/kernel:starnix_core

    // ابتدایی یعنی ریشهٔ checkout، و اسلش‌های باقی‌مانده نام پوشه‌ها هستند. رشتهٔ بعد از : نام هدف یک هدف است که در فایل BUILD.gn آن پوشه تعریف شده است.

    اگر نام هدف با نام پوشه یکی باشد می‌توان آن را حذف کرد. به عبارت دیگر //src/starnix/kernel همان //src/starnix/kernel:kernel است.

    این مسیرهای هدف درون فایل‌های BUILD.gn برای ارجاع به وابستگی‌ها به‌کار می‌روند، و در fx build هم می‌توان از آن‌ها استفاده کرد.

    Modifying compiler flags

    می‌توانید پرچم‌های سفارشی کامپایلر را درون config در GN بگذارید که به یک هدف اضافه می‌شود. به‌عنوان مثال ساده:

    config("everybody_loops") {
    rustflags = [ "-Zeverybody-loops" ]
}

rustc_binary("example") {
    crate_root = "src/bin.rs"
    # ...existing keys here...
    configs += [ ":everybody_loops" ]
}

    این پرچم -Zeverybody-loops را هنگام ساخت هدف example به rustc اضافه می‌کند. توجه کنید که می‌توانید از public_configs هم برای افزودن config به هر هدفی که به آن هدف وابسته است استفاده کنید.

    اگر می‌خواهید پرچمی را به هر هدف Rust در ساخت اضافه کنید، می‌توانید rustflags را به config با نام //build/config:compiler یا به configهای مخصوص سیستم‌عامل که در آن فایل ارجاع شده‌اند اضافه کنید. توجه کنید که cflags و ldflags روی هدف‌های Rust نادیده گرفته می‌شوند.

    اجرای مستقیم دستورهای ninja و rustc

    یک لایه پایین‌تر، fx build دستور ninja را فراخوانی می‌کند که آن هم در نهایت rustc را فراخوانی می‌کند. همهٔ اقدامات ساخت درون پوشهٔ out اجرا می‌شوند، که معمولاً out/default درون checkout مربوط به Fuchsia است.

    می‌توانید با اجبار دستور به شکست، ninja را وادار کنید دستور واقعی‌ای را که فراخوانی می‌کند چاپ کند، مثلاً با افزودن خطای نحوی به یکی از فایل‌های منبع هدف. وقتی دستور را داشتید می‌توانید آن را از درون پوشهٔ خروجی اجرا کنید.

    پس از تغییر خود toolchain، تنظیم ساخت rustc_version_string در out/default/args.gn باید تغییر کند تا fx build یا ninja همهٔ هدف‌های Rust را دوباره بسازد. این را می‌توان در یک ویرایشگر متن انجام داد، و محتوای رشته مهم نیست، مادامی که از یک ساخت به ساخت بعدی تغییر کند. اسکریپت build_fuchsia_from_rust_ci.sh این کار را با هش‌کردن پوشهٔ toolchain برایتان انجام می‌دهد.

    وب‌سایت Fuchsia مستندات مفصل‌تری از سامانهٔ ساخت دارد.

    نکات و ترفندهای دیگر

    هنگام استفاده از build_fuchsia_from_rust_ci.sh می‌توانید دستور fx set را پس از اجرای اول کامنت کنید تا GN هر بار دوباره اجرا نشود. اگر این کار را کردید، می‌توانید خط version_string را هم کامنت کنید تا چند ثانیه صرفه‌جویی شود.

    export NINJA_PERSISTENT_MODE=1 را اجرا کنید تا پس از ساخت اولیه، راه‌اندازی ninja سریع‌تر شود.

    Fuchsia target support

    برای آشنایی بیشتر با پشتیبانی از هدف Fuchsia، فصل Fuchsia را در کتاب rustc ببینید.
