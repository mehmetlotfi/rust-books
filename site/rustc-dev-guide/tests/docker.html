    تست با Docker

    پوشهٔ src/ci/docker شامل تعریف ایمیج‌های Docker برای jobهای مبتنی بر لینوکس است که در GitHub Actions اجرا می‌شوند (jobهای غیرلینوکسی خارج از Docker اجرا می‌شوند). می‌توانید این jobها را روی رایانهٔ توسعهٔ محلی خود اجرا کنید، که برای تست محیط‌هایی متفاوت از سیستم محلی‌تان مفید است. باید Docker را روی سیستم لینوکس، ویندوز یا macOS نصب کنید (معمولاً لینوکس بسیار سریع‌تر از ویندوز یا macOS است، چون آن دو برای شبیه‌سازی محیط لینوکس از ماشین‌های مجازی استفاده می‌کنند).

    jobهایی که در CI اجرا می‌شوند با مجموعه‌ای از اسکریپت‌های bash پیکربندی شده‌اند، و بازتولید رفتارشان به‌صورت محلی همیشه ساده نیست. اگر می‌خواهید یک job را در CI به ساده‌ترین شکل ممکن به‌صورت محلی اجرا کنید، می‌توانید از کمک‌ابزار citool استفاده کنید که سعی می‌کند آنچه را در CI رخ می‌دهد تا حد ممکن بازتولید کند:

    cargo run --manifest-path src/ci/citool/Cargo.toml run-local <job-name>
# For example:
cargo run --manifest-path src/ci/citool/Cargo.toml run-local dist-x86_64-linux-alt

    اگر اسکریپت بالا برایتان کار نمی‌کند، می‌خواهید کنترل بیشتری بر اجرای ایمیج Docker داشته باشید، یا می‌خواهید بفهمید دقیقاً هنگام اجرای job در Docker چه رخ می‌دهد، ادامهٔ مطلب را بخوانید.

    اسکریپت run.sh

    اسکریپت src/ci/docker/run.sh برای ساخت یک ایمیج Docker مشخص و اجرای آن، ساخت Rust درون ایمیج، و سپس یا اجرای تست‌ها یا آماده‌کردن مجموعه‌ای از آرشیوها برای توزیع به‌کار می‌رود. این اسکریپت درخت منبع Rust محلی شما را در حالت فقط‌خواندنی و پوشهٔ obj را در حالت خواندن-نوشتن mount می‌کند. همهٔ آرتیفکت‌های کامپایلر در پوشهٔ obj ذخیره می‌شوند. shell از پوشهٔ obj شروع می‌شود. از آنجا، ../src/ci/run.sh را اجرا می‌کند که ساخت را همان‌طور که ایمیج Docker تعریف کرده شروع می‌کند.

    می‌توانید مستقیماً src/ci/docker/run.sh <image-name> را اجرا کنید. چند نکتهٔ مهم دربارهٔ اسکریپت run.sh:

    • وقتی در CI اجرا می‌شود، اسکریپت انتظار دارد همهٔ زیرماژول‌ها checkout شده باشند. اگر زیرماژولی که job به آن دسترسی دارد در دسترس نباشد، ساخت با خطا مواجه می‌شود. بنابراین باید مطمئن شوید همهٔ زیرماژول‌های لازم به‌صورت محلی checkout شده‌اند. می‌توانید این را دستی با git انجام دهید، یا build.submodules = true را در bootstrap.toml تنظیم کنید و دستوری مثل x build را اجرا کنید تا bootstrap مهم‌ترین زیرماژول‌ها را دانلود کند. توجه کنید که ممکن است این برای job مشخص CI که می‌خواهید اجرا کنید کافی نباشد.
    • <image-name> با یک پوشهٔ واحد در یکی از پوشه‌های src/ci/docker/host-* متناظر است. توجه کنید که نام ایمیج لزوماً با نام job یکی نیست، چون برخی jobها همان ایمیج را اجرا می‌کنند اما با متغیرهای محیطی یا آرگومان‌های ساخت Docker متفاوت. این بخشی از پیچیدگی‌ای است که اجرای محلی jobهای CI را دشوار می‌کند.
    • اگر یک job از نوع «dist» (jobای که با dist- شروع می‌شود) را اجرا می‌کنید، باید متغیر محیطی DEPLOY=1 را تنظیم کنید.
    • اگر یک job از نوع «alternative dist» (jobای که با dist- شروع و با -alt تمام می‌شود) را اجرا می‌کنید، باید متغیر محیطی DEPLOY_ALT=1 را تنظیم کنید.
    • برخی تست‌های std به پشتیبانی IPv6 نیاز دارند. Docker روی لینوکس به نظر می‌رسد آن را به‌طور پیش‌فرض غیرفعال دارد. پیش از ساخت container، دستورهای enable-docker-ipv6.sh را اجرا کنید تا IPv6 فعال شود. این فقط یک بار لازم است.

    Interactive mode

    گاهی می‌تواند مفید باشد یک ایمیج Docker مشخص را بسازید و سپس دستورهای سفارشی درون آن اجرا کنید، تا رفتار سیستم داده‌شده را آزمایش کنید. می‌توانید این کار را با حالت تعاملی انجام دهید، که با src/ci/docker/run.sh --dev <image-name> یک shell از نوع bash در container شروع می‌کند.

    وقتی درون container Docker هستید، می‌توانید دستورهای جداگانه‌ای را برای کارهای مشخص اجرا کنید. برای مثال می‌توانید ../x test tests/ui را اجرا کنید تا فقط تست‌های UI اجرا شوند.

    چند نکتهٔ اضافی دربارهٔ استفاده از حالت تعاملی:

    • container هنگام خروج از shell به‌طور خودکار حذف می‌شود، اما آرتیفکت‌های ساخت در پوشهٔ obj باقی می‌مانند. اگر بین ایمیج‌های مختلف Docker جابه‌جا می‌شوید، آرتیفکت‌های محیط‌های قبلی که در پوشهٔ obj ذخیره شده‌اند ممکن است سامانهٔ ساخت را گیج کنند. گاهی لازم می‌شود پیش از ساخت درون container بخش‌هایی از پوشهٔ obj یا همهٔ آن را حذف کنید.
    • container حداقلی است و فقط مجموعهٔ کمینه‌ای از بسته‌ها را دارد. شاید بخواهید چیزهایی مثل apt install less vim را نصب کنید.
    • می‌توانید چند shell درون container باز کنید. ابتدا به نام container (یک هش کوتاه) نیاز دارید که در prompt مربوط به shell نمایش داده می‌شود، یا می‌توانید بیرون از container دستور docker container ls را برای فهرست‌کردن containerهای موجود اجرا کنید. با نام container، دستور docker exec -it <CONTAINER> /bin/bash را اجرا کنید که در آن <CONTAINER> نام container مثل 4ba195e95cef است.
