    Effects، صفت‌های const و بررسی شرط‌های const

    گزاره HostEffect

    HostEffectPredicateها نوعی گزاره هستند که از کران‌های [const] Tr یا const Tr ساخته می‌شوند. هر یک شامل یک ارجاع صفت و یک constness است که بسته به کران می‌تواند Maybe یا Const باشد. از آن‌جا که [const] Tr، یا به بیان دقیق‌تر کران‌های Maybe، بسته به بافتی که در آن قرار دارند به شکل متفاوتی اعمال می‌شوند، رفتارشان با کران‌های معمولی فرق دارد. کران‌های صفت معمولی روی یک تابع، مانند T: Tr، در کوئری clauses_of گردآوری می‌شوند تا هنگام فراخوانی تابع اثبات شوند و درون تابع مفروض گرفته شوند. کران‌هایی مانند T: [const] Tr مانند یک کران صفت معمولی رفتار می‌کنند و T: Tr را به نتیجه clauses_of اضافه می‌کنند، اما علاوه بر آن یک HostEffectPredicate هم به کوئری const_conditions اضافه می‌کنند.

    در مقابل، کران‌های T: const Tr در بافت‌های مختلف معنایشان تغییر نمی‌کند؛ بنابراین به‌جای const_conditions، عبارت HostEffect(T: Tr, const) به clauses_of اضافه می‌شود.

    کوئری const_conditions

    clauses_of مجموعه‌ای از بندها را نشان می‌دهد که برای استفاده از یک آیتم باید اثبات شوند. برای مثال، برای استفاده از foo در مثال زیر:

    fn foo<T>() where T: Default {}

    باید بتوانیم اثبات کنیم که T صفت Default را پیاده‌سازی می‌کند. به همین ترتیب، const_conditions مجموعه‌ای از گزاره‌ها را نشان می‌دهد که برای استفاده از یک آیتم در بافت‌های const باید اثبات شوند. اگر مثال بالا را طوری تغییر دهیم که از کران‌های صفت const استفاده کند:

    const fn foo<T>() where T: [const] Default {}

    آن‌گاه foo در کوئری const_conditions یک HostEffect(T: Default, maybe) خواهد داشت، که نشان می‌دهد برای فراخوانی foo از بافت‌های const باید اثبات کرد که T یک پیاده‌سازی const از Default دارد.

    اعمال const_conditions

    const_conditions در حال حاضر در چند جای مختلف بررسی می‌شوند.

    هر فراخوانی در HIR که از یک بافت const انجام شود (که شامل const fn و آیتم‌های const است) بررسی می‌کند که const_conditions تابعی که فراخوانی می‌شود برقرار باشند. این کار در FnCtxt::enforce_context_effects انجام می‌شود. توجه کنید که اگر تابع فقط ارجاع داده شود و فراخوانی نشود، این بررسی انجام نمی‌شود، زیرا کد زیر باید کامپایل شود:

    const fn hi<T: [const] Default>() -> T {
    T::default()
}
const X: fn() -> u32 = hi::<u32>;

    برای این‌که یک impl صفت well-formed باشد، باید بتوانیم const_conditions صفت را از محیط آن impl اثبات کنیم. این کار در wfcheck::check_impl بررسی می‌شود.

    Here’s an example:

    const trait Bar {}
const trait Foo: [const] Bar {}
// `const_conditions` contains `HostEffect(Self: Bar, maybe)`

impl const Bar for () {}
impl const Foo for () {}
// ^ here we check `const_conditions` for the impl to be well-formed

    متدهای implهای صفت نباید کران‌های سخت‌گیرانه‌تری از متد متناظر در صفتی که پیاده‌سازی می‌کنند داشته باشند. برای بررسی سازگاری متدها، یک محیط ترکیبی از گزاره‌های impl به‌علاوه‌ی گزاره‌های متد صفت ساخته می‌شود و سپس تلاش می‌کنیم گزاره‌های متد impl را اثبات کنیم. همین کار را برای const_conditions هم انجام می‌دهیم:

    const trait Foo {
    fn hi<T: [const] Default>();
}

impl<T: [const] Clone> Foo for Vec<T> {
    fn hi<T: [const] PartialEq>();
    // ^ we can't prove `T: [const] PartialEq` given `T: [const] Clone` and
    // `T: [const] Default`, therefore we know that the method on the impl
    // is stricter than the method on the trait.
}

    این بررسی‌ها در compare_method_clause_entailment انجام می‌شوند. تابع مشابهی که همین بررسی را برای نوع‌های وابسته انجام می‌دهد compare_type_clause_entailment نام دارد. هر دوی این‌ها در بافت‌های const باید const_conditions را هم در نظر بگیرند.

    در MIR، به‌عنوان بخشی از بررسی const، const_conditions آیتم‌هایی که فراخوانی می‌شوند در Checker::revalidate_conditional_constness دوباره اعتبارسنجی می‌شوند.

    explicit_implied_const_bounds روی نوع‌های وابسته و صفت‌ها

    کران‌های روی نوع‌های وابسته، نوع‌های opaque و ابَرصفت‌ها، مانند نمونه‌ی زیر، به شکل متفاوتی نمایش داده می‌شوند:

    trait Foo: [const] PartialEq {
    type X: [const] PartialEq;
}

fn foo() -> impl [const] PartialEq {
    // ^ unimplemented syntax
}

    برخلاف const_conditions که باید برای فراخوانندگان اثبات شوند و درون تعریف می‌توان آن‌ها را مفروض گرفت (مانند کران‌های صفت روی توابع)، این کران‌ها باید در محل تعریف اثبات شوند (در impl یا هنگام بازگرداندن نوع opaque) اما برای فراخوانندگان می‌توان آن‌ها را مفروض گرفت. معادل غیر const این کران‌ها explicit_item_bounds نام دارد.

    این کران‌ها در compare_impl_item::check_type_bounds برای بررسی نوع HIR، در evaluate_host_effect_from_item_bounds برای حل‌کننده‌ی قدیمی و در consider_additional_alias_assumptions برای حل‌کننده‌ی جدید بررسی می‌شوند.

    اثبات HostEffectPredicateها

    HostEffectPredicateها هم در حل‌کننده‌ی قدیمی و هم در حل‌کننده‌ی صفت جدید پیاده‌سازی شده‌اند. به‌طور کلی، وقتی یکی از این شرایط برقرار باشد می‌توانیم یک گزاره‌ی HostEffect را اثبات کنیم:

    • گزاره را بتوان از کران‌های فراخواننده مفروض گرفت؛
    • نوع یک impl از نوع const برای صفت داشته باشد، و شرط‌های const روی آن impl برقرار باشند، و explicit_implied_const_bounds روی صفت برقرار باشد؛ یا
    • نوع در بافت‌های const یک پیاده‌سازی درونی (built-in) برای صفت داشته باشد. برای مثال، Fn ممکن است توسط آیتم‌های تابع پیاده‌سازی شود اگر شرط‌های const آن‌ها برآورده شوند، یا Destruct در بافت‌های const پیاده‌سازی می‌شود اگر نوع بتواند در زمان کامپایل drop شود.

    بیشتر درباره‌ی صفت‌های const

    بعداً تکمیل خواهد شد.

    اتریبیوت #[rustc_non_const_trait_method]

    این اتریبیوت فقط برای استفاده‌ی داخلی (کتابخانه‌ی استاندارد) در نظر گرفته شده است. وقتی این اتریبیوت روی یک متد صفت اعمال شود، کامپایلر بدنه‌ی پیش‌فرض آن متد را از نظر امکان اجرا در زمان کامپایل بررسی نمی‌کند. کاربران صفت نیز اجازه نخواهند داشت از این متد صفت در بافت‌های const استفاده کنند. این اتریبیوت عمدتاً برای const کردن صفت‌های بزرگ مانند Iterator به کار می‌رود، بدون این‌که لازم باشد همه‌ی متدهای آن هم‌زمان const شوند.

    این اتریبیوت نباید هنگام پایدارسازی (stabilize) صفت به‌صورت const وجود داشته باشد.
