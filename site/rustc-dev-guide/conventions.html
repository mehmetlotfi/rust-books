راهنمای توسعهٔ rustcrustc Development Guide

    قراردادهای کدنویسی

    این فصل قالب‌بندی، کدنویسی برای درستی، استفاده از crateها از crates.io و چند نکته دربارهٔ ساختاردهی PR برای بررسی آسان را پوشش می‌دهد.

    قالب‌بندی و اسکریپت tidy

    rustc در حال حرکت به سوی سبک کدنویسی استاندارد Rust است.

    با این حال، فعلاً از rustfmt پایدار استفاده نمی‌کنیم؛ از نسخه‌ای ثابت‌شده (pinned) با پیکربندی ویژه استفاده می‌کنیم، بنابراین ممکن است سبکی متفاوت از rustfmt معمولی تولید شود. از این رو قالب‌بندی این مخزن با cargo fmt توصیه نمی‌شود.

    در عوض، قالب‌بندی باید با ./x fmt انجام شود. عادت خوبی است که پیش از هر commit دستور ./x fmt را اجرا کنید، چون این کار تداخل‌های بعدی را کاهش می‌دهد.

    قالب‌بندی توسط اسکریپت tidy بررسی می‌شود. این اسکریپت هنگام اجرای ./x test به‌طور خودکار اجرا می‌شود و می‌توان آن را به‌تنهایی با ./x fmt --check اجرا کرد.

    نکته: قالب‌بندی و مجموعه‌های آزمون

    بیشتر فایل‌های منبع Rust در دایرکتوری tests/ به دلایلی مانند حساسیت به فاصله‌های خالی، ماهیت آزمون‌های snapshot، توضیحات وابسته به مکان و موارد دیگر قالب‌بندی نمی‌شوند.

    برای دانستن اینکه کدام فایل‌های آزمون قالب‌بندی نمی‌شوند، به مدخل‌های ignore در https://github.com/rust-lang/rust/blob/main/rustfmt.toml مراجعه کنید.

    اگر می‌خواهید در ویرایشگر خود قالب‌بندی هنگام ذخیره را استفاده کنید، نسخهٔ ثابت‌شدهٔ rustfmt در مسیر build/<target>/stage0/bin/rustfmt ساخته می‌شود.

    قالب‌بندی کد C++

    کامپایلر شامل مقداری کد C++ برای ارتباط با بخش‌هایی از LLVM است که API پایدار C ندارند. هنگام تغییر آن کد، برای قالب‌بندی‌اش از این دستور استفاده کنید:

    ./x test tidy --extra-checks cpp:fmt --bless

    این دستور از نسخه‌ای ثابت‌شده از clang-format استفاده می‌کند تا به محیط محلی وابسته نباشد.

    قالب‌بندی و lint کد Python

    مخزن Rust مقدار زیادی کد Python دارد. تلاش می‌کنیم آن را هم با ابزار ruff lint و هم قالب‌بندی کنیم.

    هنگام تغییر کد Python، برای قالب‌بندی از این دستور استفاده کنید:

    ./x test tidy --extra-checks py:fmt --bless

    و برای اجرای lintها از دستور زیر:

    ./x test tidy --extra-checks py:lint

    این دستورها از نسخه‌ای ثابت‌شده از ruff استفاده می‌کنند تا به محیط محلی وابسته نباشند.

    اعلان حق نشر

    در گذشته فایل‌ها با یک اعلان حق نشر و مجوز شروع می‌شدند. لطفاً این اعلان را برای فایل‌های جدیدی که تحت شرایط استاندارد (MIT OR Apache-2.0) مجوز دارند حذف کنید.

    اکنون همهٔ اعلان‌های حق نشر باید حذف شده باشند، اما اگر در مخزن rust-lang/rust به یکی از آن‌ها برخوردید، با خیال راحت یک PR برای حذفش باز کنید.

    طول خط

    خطوط باید حداکثر ۱۰۰ نویسه باشند. اگر بتوانید آن را در ۸۰ نگه دارید حتی بهتر است.

    گاهی، به‌ویژه برای آزمون‌ها، ممکن است لازم باشد خودتان را از این محدودیت معاف کنید. در این صورت می‌توانید نزدیک ابتدای فایل یک توضیح به این شکل اضافه کنید:

    // ignore-tidy-linelength

    Tab در برابر فاصله

    Prefer 4-space indents.

    کدنویسی برای درستی

    فراتر از قالب‌بندی، چند نکتهٔ دیگر هم هست که پیروی از آن‌ها ارزش دارد.

    match جامع را ترجیح دهید

    استفاده از _ در match راحت است، اما به این معناست که وقتی variantهای جدیدی به شمارش اضافه شوند، ممکن است به‌درستی مدیریت نشوند. از خودتان بپرسید: اگر variant جدیدی به این شمارش اضافه شود، چقدر احتمال دارد که بخواهد از کد _ استفاده کند، در برابر اینکه رفتار دیگری داشته باشد؟ مگر آنکه پاسخ «کم» باشد، match جامع را ترجیح دهید.

    همین توصیه دربارهٔ if let و while let هم صدق می‌کند، چون این‌ها عملاً آزمونی برای یک variant واحد هستند.

    برای چیزهایی که نمی‌خواهید فراموش شوند از توضیح “TODO” استفاده کنید

    به‌عنوان ابزاری مفید برای خودتان، می‌توانید برای چیزی که می‌خواهید پیش از land کردن PR به آن برگردید یک توضیح // TODO بگذارید:

    fn do_something() {
    if something_else {
        unimplemented!(); // TODO write this
    }
}

    اسکریپت tidy برای توضیح // TODO خطا گزارش می‌کند، بنابراین این کد تا زمانی که TODO رفع (یا حذف) نشود نمی‌تواند land شود.

    این روش در یک PR نیز می‌تواند مفید باشد تا از یک commit نشان دهید که باگی را باقی گذاشته‌اید که commit بعدی آن را رفع خواهد کرد:

    if foo {
    return true; // TODO wrong, but will be fixed in a later commit
}

    اگر می‌خواهید در codebase یادداشتی بگذارید، به‌جای آن از // FIXME استفاده کنید.

    از سبک کد اطراف پیروی کنید

    از کمکی‌های (helper) موجود استفاده کنید و از تکرار منطق یا اعتبارسنجی بپرهیزید.

    از منابع حقیقت تکراری بپرهیزید

    تلاش برای همگام نگه داشتن داده بین دو جای مختلف نشانهٔ کد بد (code smell) است.

    از نوع‌ها برای اعمال invariantها استفاده کنید

    در صورت امکان، حالت‌های نامعتبر را غیرقابل بیان کنید، نه اینکه فقط هنگام ساخت بررسی شوند.

    توضیحات مفید بنویسید

    توضیحاتی بنویسید که بگویند چرا کاری را انجام داده‌اید، نه اینکه چه کاری کرده‌اید. پرداختن به جزئیات باگ‌های غیرواضح اشکالی ندارد.

    رفتار موجود را حفظ کنید

    تفاوت‌های پلتفرم و حالت‌های خطا را در نظر بگیرید. آزمون‌های مرتبطی را که حالت‌های مرزی را بررسی می‌کنند پیدا کنید.

    در گام‌های کوچک کار کنید

    در گام‌های کوچک و مستقل‌قابل‌آزمون کار کنید. پس از هر تغییر معنادار آزمون‌های مرتبط را اجرا کنید تا بدانید اولین اشتباه کجا رخ داده است.

    استفاده از crateها از crates.io

    بخش وابستگی‌های crates.io را ببینید.

    چگونه PR خود را ساختاردهی کنید

    نحوهٔ آماده‌سازی commitهای PR می‌تواند تفاوت بزرگی برای بررسی‌کننده ایجاد کند. در اینجا چند نکته آمده است.

    «بازآرایی‌های محض» را در commit جداگانه‌ای قرار دهید. برای مثال، اگر نام یک متد را تغییر می‌دهید، آن تغییر نام را همراه با تغییر نام همهٔ استفاده‌های آن در یک commit جداگانه بگذارید.

    commitهای بیشتر معمولاً بهتر است. اگر تغییر بزرگی می‌دهید، تقریباً همیشه بهتر است آن را به گام‌های کوچک‌تری بشکنید که به‌طور مستقل قابل‌فهم باشند. تنها نکته‌ای که باید مراقبش بود این است که اگر کدی را با یک راهبرد معرفی کنید و سپس در commit بعدی آن را به‌شدت تغییر دهید (به‌جای افزودن به آن)، این «رفت‌وبرگشت» می‌تواند گیج‌کننده باشد.

    آزادانه قالب‌بندی کنید. هرچند فقط commit نهایی یک PR باید درست قالب‌بندی شده باشد، قالب‌بندی تک‌تک commitها با ./x fmt هم بررسی را آسان‌تر و هم کم‌نویزتر می‌کند.

    بدون merge. ما commit از نوع merge را در تاریخچه‌مان نمی‌پذیریم، جز آنهایی که bors ایجاد می‌کند. اگر با تداخل merge مواجه شدید، به‌جای آن با دستوری مانند git rebase --interactive rust-lang/main rebase کنید (با فرض اینکه برای remote خود نام rust-lang را به کار برده‌اید).

    commitهای منفرد لازم نیست ساخته شوند (اما خوب است). ما الزام نمی‌کنیم که هر commit میانی با موفقیت ساخته شود – فقط انتظار داریم بتوانیم در سطح PR از bisect استفاده کنیم. با این حال، اگر بتوانید commitهای منفرد را قابل‌ساخت کنید، همیشه مفید است.

    قراردادهای نام‌گذاری

    جدا از سبک و قراردادهای نام‌گذاری معمول Rust، چند قرارداد ویژهٔ کامپایلر هم وجود دارد.

    • cx معمولاً کوتاه‌شدهٔ «context» است و اغلب به‌عنوان پسوند به کار می‌رود. برای مثال، tcx نام رایجی برای Typing Context است.

    • 'tcx به‌عنوان نام طول عمر برای Typing Context استفاده می‌شود.

    • چون crate یک کلمهٔ کلیدی است، اگر به متغیری برای نمایش چیزی مرتبط با crate نیاز داشته باشید، اغلب املای آن به krate تغییر می‌کند.
