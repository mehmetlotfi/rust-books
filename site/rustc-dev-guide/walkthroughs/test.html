راهنمای توسعهٔ rustcrustc Development Guide

    گام‌به‌گام: افزودن یک تست جدید

    این فصل مثالی از یک تغییر کوچک ارائه می‌دهد که می‌توانید به‌عنوان اولین مشارکت خود در Rust انجام دهید، با استفاده از rust#59333 و rust#161442 به‌عنوان مثال.

    یک issue با برچسب E-needs-test برای کار پیدا کنید

    برای فهرستی از کارهای ممکن «روی چه چیزی کار کنم؟» را ببینید. اینجا یک issue با E-needs-test انتخاب کرده‌ایم: rust#59333. این به‌ویژه مناسب است چون یک مثال مستقیماً در issue دارد، بدون اینکه نیاز به کار اضافه از شما برای کمینه‌کردن باگ باشد. البته همیشه بسیار مفید است که issueی با E-needs-test را بردارید که مثال کمینه ندارد و برایش یکی بسازید.

    issue را بازتولید کنید

    مثال اینجا در سال ۲۰۱۹ منتشر شد، یعنی کاملاً ۷ سال پیش (در زمان نگارش). در این بازه چیزهای زیادی در کامپایلر تغییر می‌کند. برای اطمینان از اینکه تست هنوز دقیق است، آن را با جدیدترین کامپایلر بازتولید کنید. راه آسان انجام این کار استفاده از play.rust-lang.org روی شاخهٔ nightly، یا rust.godbolt.org با rustc nightly است. همچنین اگر به راه‌اندازی پیچیده‌ای نیاز دارید که در Playground ممکن نیست می‌توانید به‌صورت محلی از rustc +nightly استفاده کنید.

    issue را به تست تبدیل کنید

    مخزن rust-lang/rust را checkout و راه‌اندازی کنید، همان‌طور که در شروع سریع مستند شده:

    $ git clone https://github.com/rust-lang/rust
$ cd rust
$ ./x setup compiler
$ ./x build library

    اینجا از compiler به‌عنوان profile پیش‌فرض استفاده می‌کنیم، چون باگی که رفع می‌کنیم به کامپایلر مربوط است. اگر تست واحد به کتابخانهٔ استاندارد اضافه می‌کنید، از ./x setup library استفاده می‌کنید.

    این همچنین پیشنهاد می‌کند یک بررسی .git/hooks/pre-push راه‌اندازی شود. این اختیاری اما توصیه‌شده است.

    ما همچنین ساختی را در پس‌زمینه با ./x build library شروع کردیم. متأسفانه ساخت Rust مدتی طول می‌کشد، پس شروع زودهنگام ساخت اجازه می‌دهد در پس‌زمینه اجرا شود در حالی که روی چیزهای دیگر کار می‌کنید.

    برای راهنمای افزودن تست‌های جدید تست‌های UI را ببینید. در موارد نادر ممکن است به تست run-make یا نوع تخصصی‌تری نیاز داشته باشید. برای اطلاعات بیشتر Compiletest را ببینید.

    در مورد ما، تست نسبتاً ساده است:

    // Save this file to `tests/ui/lint/dead-code/type-alias-used-in-impl-59333.rs`.

//@ check-pass
//! Regression test for <https://github.com/rust-lang/rust/issues/59333>.
//! A type alias used only as (part of) the self type of an impl was
//! incorrectly flagged as dead code.

#![deny(dead_code)]

struct Runner;

type RuntimeImpl = Runner;

trait Runtime {
    fn run(&mut self);
}

impl Runtime for &mut RuntimeImpl {
    fn run(&mut self) {}
}

struct Walker;

type WalkerImpl = Walker;

trait Walk {
    fn walk(&self) {}
}

impl Walk for WalkerImpl {}

fn main() {
    let mut runner = Runner;
    (&mut runner).run();
    Walker.walk();
}

    بیشتر جزئیات اینجا چندان اهمیت ندارند، اما به //@ check-pass و #![deny(dead_code)] در بالا توجه کنید. این دو با هم تضمین می‌کنند کامپایلر هنگام کامپایل این فایل lint با نام dead_code صادر نمی‌کند.

    همچنین به کامنت «Regression test for …» توجه کنید. این برای بازبین شما بسیار مفید است، چون کمک می‌کند بفهمد تست چه می‌کند و آیا راه ساده‌تری برای تست آن رفتار هست. لطفاً تمام تلاشتان را بکنید که توضیح کاملی برای تست بنویسید.

    تست خود را اجرا کنید. rust#161442 تست خود را tests/ui/lint/dead-code/type-alias-used-in-impl-59333.rs نام‌گذاری کرد، پس می‌توانید این را اجرا کنید:

    ./x test tests/ui/lint/dead-code/type-alias-used-in-impl-59333.rs

    اگر موفق شد، تست شما آماده است.

    یک PR باز کنید

    دستورالعمل‌های چرخهٔ عمر PR را دنبال کنید.

    ابتدا اگر قبلاً راه‌اندازی نکرده‌اید بررسی pre-push را اجرا کنید:

    ./x test tidy

    سپس PR را باز کنید:

    git switch --create issue-59333-test
git add tests/ui/lint/dead-code/type-alias-used-in-impl-59333.rs
git commit
git remote add personal https://github.com/YOUR_USERNAME_HERE/rust.git
git push --set-upstream personal issue-59333-test
