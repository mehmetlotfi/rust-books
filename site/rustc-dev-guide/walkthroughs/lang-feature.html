    گام‌به‌گام: یک قابلیت جدید زبان، از طراحی تا پایدارسازی

    این فصل طراحی و پیاده‌سازی یک قابلیت جدید زبان را گام‌به‌گام مرور می‌کند. برخی از این گام‌ها مخصوص قابلیت‌های زبان‌اند، اما بسیاری به قابلیت‌های کتابخانه هم تعمیم می‌یابند.

    Overview

    قابلیتی که در این فصل بحث می‌کنم عملگر Kleene با نام ? برای ماکروهاست. اساساً می‌خواهیم بتوانیم چیزی شبیه این بنویسیم:

    macro_rules! foo {
    ($arg:ident $(, $optional_arg:ident)?) => {
        println!("{}", $arg);

        $(
            println!("{}", $optional_arg);
        )?
    }
}

fn main() {
    let x = 0;
    foo!(x); // ok! prints "0"
    foo!(x, x); // ok! prints "0 0"
}

    پس اساساً matcher با نام $(pat)? در ماکرو یعنی «این الگو می‌تواند ۰ یا ۱ بار رخ دهد»، شبیه نحوهای regex دیگر.

    برای رسیدن از یک ایده به قابلیت پایدار Rust چند گام بود. در ادامه فهرست سریعی هست. هر کدام را به ترتیب مرور می‌کنیم. همان‌طور که پیش‌تر گفتم، همهٔ این‌ها برای هر نوع مشارکتی لازم نیستند.

    • بحث ایده/Pre-RFC Pre-RFC پیش‌نویس اولیه یا بحث طراحی یک قابلیت است. این مرحله برای شکل‌دادن به فضای طراحی و درک مزایا و مشکلات مختلف یک ایده است. راه عالی برای گرفتن بازخورد زودهنگام دربارهٔ ایده پیش از ارائه به مخاطبان گسترده‌تر است. بحث اصلی را اینجا می‌یابید.
    • RFC اینجا ایده را رسماً برای بررسی به جامعه ارائه می‌دهید. RFC را اینجا می‌یابید.
    • پیاده‌سازی ایده را به‌صورت ناپایدار در کامپایلر پیاده کنید. پیاده‌سازی اصلی را اینجا می‌یابید.
    • احتمالاً تکرار/پالایش وقتی جامعه با قابلیت شما روی کامپایلر nightly و در std تجربه کسب می‌کند، ممکن است بازخورد بیشتری دربارهٔ انتخاب‌های طراحی بیاید که شاید تعدیل شوند. این قابلیت خاص چندین تکرار را گذراند.
    • پایدارسازی وقتی قابلیت شما به‌اندازهٔ کافی پخته شد، یکی از اعضای تیم Rust ممکن است پیشنهاد پایدارسازی آن را بدهد. اگر اجماع باشد، انجام می‌شود.
    • آسوده باشید قابلیت شما اکنون قابلیت پایدار Rust است!

    Pre-RFC و RFC

    نکته: عموماً اگر قابلیت جدید یا تغییر اساسی در Rust یا اکوسیستم پیشنهاد نمی‌کنید، لازم نیست فرایند RFC را دنبال کنید. به‌جای آن می‌توانید مستقیماً به پیاده‌سازی بروید.

    رهنمودهای رسمی دربارهٔ اینکه چه وقت RFC باز کنید را اینجا می‌یابید.

    RFC سندی است که قابلیت یا تغییر پیشنهادی شما را با جزئیات توصیف می‌کند. هر کسی می‌تواند RFC بنویسد؛ فرایند برای همه یکسان است، از جمله اعضای تیم Rust.

    برای باز‌کردن RFC، یک PR روی مخزن rust-lang/rfcs در GitHub باز کنید. دستورالعمل‌های مفصل را در README می‌یابید.

    پیش از باز‌کردن RFC، باید تحقیق کنید تا ایده‌تان را «شکل دهید». RFCهای شتاب‌زده پیشنهادشده معمولاً پذیرفته نمی‌شوند. عموماً باید توضیح خوبی از انگیزه، اثر، معایب و تعامل‌های بالقوه با قابلیت‌های دیگر داشته باشید.

    اگر این کار زیادی به نظر می‌رسد، به این دلیل است که هست. اما نترسید! حتی اگر هکر کامپایلر نیستید، با انجام یک pre-RFC می‌توانید بازخورد عالی بگیرید. این یک بحث غیررسمی دربارهٔ ایده است. بهترین جا برای این internals.rust-lang.org است. پست شما لازم نیست ساختار خاصی داشته باشد. حتی لازم نیست ایده‌ای منسجم باشد. عموماً بازخورد فراوانی می‌گیرید که می‌توانید برای تولید RFC خوب به آن بازگردانید.

    (نکتهٔ حرفه‌ای دیگر: سعی کنید در مخزن RFCها و internals دنبال ایده‌های مرتبط قبلی بگردید. اغلب ایده‌ای قبلاً بررسی شده و یا رد شده یا برای تلاش مجدد بعدی به تعویق افتاده. این می‌تواند وقت شما و همه را صرفه‌جویی کند)

    در مثال ما، یکی از شرکت‌کنندگان رشتهٔ pre-RFC به یک ابهام نحوی و یک راه‌حل بالقوه اشاره کرد. همچنین بازخورد کلی مثبت به نظر می‌رسید. در این مورد بحث خیلی سریع همگرا شد، اما برای برخی ایده‌ها بحث بسیار بیشتری ممکن است رخ دهد (مثلاً این RFC را ببینید که حدود ۶۸۴ کامنت گرفت!). اگر این رخ داد، ناامید نشوید؛ یعنی جامعه به ایدهٔ شما علاقه‌مند است اما شاید کمی تعدیل لازم دارد.

    RFC مربوط به قابلیت ماکروی ? ما هم در رشتهٔ RFC بحث‌هایی داشت. مثل بیشتر RFCها، چند پرسش بود که نتوانستیم با بحث پاسخ دهیم: برای تصمیم‌گیری به تجربهٔ استفاده از قابلیت نیاز داشتیم. چنین پرسش‌هایی در بخش «پرسش‌های حل‌نشده» RFC فهرست می‌شوند. همچنین در طول بحث RFC احتمالاً می‌خواهید خود سند RFC را به‌روز کنید تا مسیر بحث را منعکس کند (مثلاً جایگزین‌ها یا کار قبلی جدید اضافه شود یا تصمیم بگیرید بخش‌هایی از خود پیشنهاد را تغییر دهید).

    در نهایت، وقتی بحث به اجماع می‌رسد و کمی فروکش می‌کند، یکی از اعضای تیم Rust ممکن است پیشنهاد دهد با یکی از سه حالت ممکن به «دورهٔ نظر نهایی» (FCP) برویم. یعنی می‌خواهند اعضای تیم‌های مناسب دیگر RFC را بازبینی و نظر دهند. ممکن است بحث بیشتری رخ دهد که می‌تواند به تغییرات بیشتر یا پرسش‌های حل‌نشدهٔ بیشتر منجر شود. در نقطه‌ای، وقتی همه راضی‌اند، RFC وارد FCP می‌شود که آخرین فرصت برای مطرح‌کردن اعتراض است. وقتی FCP تمام شد، آن حالت پذیرفته می‌شود. سه حالت ممکن این‌هاست:

    • Merge: پذیرش قابلیت. این پیشنهاد merge برای قابلیت ماکروی ? ماست.
    • Close: این قابلیت به شکل فعلی برای Rust مناسب نیست. اگر این برای RFC شما رخ داد ناامید نشوید و شخصی برداشت نکنید. این بازتابی از شما نیست، بلکه تصمیم جامعه است که Rust مسیر دیگری برود.
    • Postpone: علاقه به این مسیر هست اما نه در حال حاضر. این بیشتر به این دلیل رخ می‌دهد که تیم Rust مناسب ظرفیت هدایت قابلیت را تا پایدارسازی ندارد. اغلب وقتی است که قابلیت در نقشهٔ راه تیم نمی‌گنجد. ایده‌های به‌تعویق‌افتاده ممکن است بعداً دوباره بررسی شوند.

    وقتی RFC merge می‌شود، PR به مخزن RFCها merge می‌شود. یک issue پیگیری جدید در مخزن rust-lang/rust ساخته می‌شود تا پیشرفت قابلیت را پیگیری و پرسش‌های حل‌نشده، پیشرفت پیاده‌سازی و موانع و غیره را بحث کند. این issue پیگیری قابلیت ماکروی ? ماست.

    Experimental RFC (eRFC)

    eRFC گونه‌ای از فرایند RFC است که برای قابلیت‌های پیچیده به‌کار می‌رود که نیاز سطح بالا روشن است اما فضای طراحی آن‌قدر بزرگ است که نمی‌توان از ابتدا روی مشخصات مفصل به توافق رسید. به‌جای ارائهٔ طراحی نهایی، eRFC راهبردی سطح بالا را مشخص می‌کند تا دورهٔ آزمایش فعال را مجاز کند. این به تیم اجازه می‌دهد قابلیت را پشت feature gate پیاده کند و داده‌های عملی جمع کند که سپس RFC رسمی بعدی را برای پایدارسازی آگاه می‌کند. هرچند این فرایند برای قابلیت‌های بزرگی مثل coroutineها به‌کار رفت (RFC 2033 را ببینید)، برچسب صریح «eRFC» امروزه به‌ندرت به‌کار می‌رود. پروژه اکنون عموماً ترجیح می‌دهد RFC استاندارد را برای نسخهٔ اولیه تأیید کند و آن را از طریق کانال nightly تا پایدارسازی نهایی تکرار کند.

    Implementation

    برای تغییر در کامپایلر، یک PR روی مخزن rust-lang/rust باز کنید.

    بسته به قابلیت/تغییر/رفع باگ/بهبود، پیاده‌سازی ممکن است نسبتاً ساده باشد یا کار بزرگی. همیشه می‌توانید از توسعه‌دهندگان باتجربه‌تر کامپایلر کمک یا mentoring بخواهید. همچنین لازم نیست خودتان قابلیت را پیاده کنید؛ اما به یاد داشته باشید اگر نکنید، ممکن است مدتی طول بکشد تا کس دیگری انجام دهد.

    برای قابلیت ماکروی ? لازم بود بخش‌های مرتبط گسترش ماکرو در کامپایلر را بفهمم. شخصاً بهبود کامنت‌ها در کد را راه مفیدی برای اطمینان از درک آن می‌دانم، اما اگر نمی‌خواهید لازم نیست این کار را بکنید.

    سپس قابلیت اصلی را همان‌طور که در RFC توصیف شده پیاده‌سازی کردم. وقتی قابلیت جدیدی پیاده‌سازی می‌شود، پشت یک feature gate قرار می‌گیرد، یعنی برای استفاده از قابلیت باید #![feature(my_feature_name)] را به‌کار ببرید. feature gate هنگام پایدارسازی قابلیت حذف می‌شود.

    بیشتر رفع باگ‌ها و بهبودها نیاز به feature gate ندارند. می‌توانید فقط تغییرات/بهبودهای خود را بدهید.

    برای اطلاعات دربارهٔ نحوهٔ باز‌کردن PR و merge شدن آن چرخهٔ عمر PR را ببینید.

    اگر قابلیت جدید یا چیزی شبیه آن نمی‌سازید (مثلاً اگر باگی را رفع می‌کنید)، همین بود! از مشارکت شما متشکریم :)

    پالایش پیاده‌سازی

    وقتی افراد با قابلیت جدید شما در nightly تجربه کسب می‌کنند، ممکن است تغییرات جزئی پیشنهاد شود و پرسش‌های حل‌نشده حل شوند. تغییرات/به‌روزرسانی‌ها همان فرایند پیاده‌سازی هر تغییر دیگر را طی می‌کنند، همان‌طور که بالا توضیح داده شد (یعنی ارسال PR، بازبینی، انتظار برای @bors و غیره).

    برخی تغییرات ممکن است آن‌قدر عمده باشند که به FCP و بازبینی اعضای تیم Rust نیاز داشته باشند.

    برای قابلیت ماکروی ?، پس از پیاده‌سازی اولیه چند تکرار مختلف داشتیم: ۱، ۲، ۳.

    در طول راه تصمیم گرفتیم ? جداکننده نگیرد، که پیش‌تر پرسش حل‌نشدهٔ فهرست‌شده در RFC بود. همچنین راهبرد رفع ابهام را تغییر دادیم: تصمیم گرفتیم توانایی استفاده از ? به‌عنوان توکن جداکننده برای عملگرهای تکرار دیگر (مثل + یا *) را حذف کنیم. اما چون این تغییر شکننده بود، تصمیم گرفتیم آن را از مرز edition انجام دهیم. پس قابلیت جدید فقط در edition 2018 قابل‌فعال‌شدن است. این انحرافات از RFC اصلی FCP دیگری لازم داشتند.

    Stabilization

    در نهایت، پس از اینکه قابلیت مدتی روی nightly پخته شد، یکی از اعضای تیم زبان برای پایدارسازی آن اقدام کرد.

    گزارش پایدارسازی باید نوشته شود که شامل این‌هاست

    • توضیح مختصر رفتار و هر انحراف از RFC
    • کدام edition(ها) تحت‌تأثیر هستند و چگونه
    • پیوند به چند تست برای نشان‌دادن جنبه‌های جالب

    گزارش پایدارسازی برای قابلیت ما اینجاست.

    پس از این، یک PR ساخته می‌شود تا feature gate را حذف کند و قابلیت را به‌طور پیش‌فرض فعال کند (در edition 2018). یادداشتی دربارهٔ قابلیت به یادداشت‌های انتشار اضافه می‌شود.

    گام‌های پایدارسازی قابلیت را در پایدارسازی قابلیت‌ها می‌یابید.
