    استنتاج capture در Closure

    این بخش توضیح می‌دهد rustc چگونه closureها را مدیریت می‌کند. closureها در Rust عملاً به structهایی «تبدیل (desugar)» می‌شوند که مقادیری را که از قاب پشتهٔ (stack frame) سازندهٔ خود استفاده می‌کنند (یا ارجاع‌هایی به آن مقادیر) در خود نگه می‌دارند. rustc وظیفه دارد بفهمد یک closure از کدام مقادیر و چگونه استفاده می‌کند، تا بتواند تصمیم بگیرد یک متغیر مفروض را با ارجاع مشترک، ارجاع تغییرپذیر یا با move capture کند. rustc همچنین باید تشخیص دهد یک closure قادر به پیاده‌سازی کدام‌یک از صفت‌های closure (Fn، FnMut یا FnOnce) است.

    با چند مثال شروع می‌کنیم:

    مثال ۱

    برای شروع، ببینیم closure در مثال زیر چگونه desugar می‌شود:

    fn closure(f: impl Fn()) {
    f();
}

fn main() {
    let x: i32 = 10;
    closure(|| println!("Hi {}", x));  // The closure just reads x.
    println!("Value of x after return {}", x);
}

    فرض کنیم موارد بالا محتوای فایلی به نام immut.rs است. اگر immut.rs را با دستور زیر کامپایل کنیم، پرچم -Z dump-mir=all باعث می‌شود rustc، MIR را تولید کند و در دایرکتوری‌ای به نام mir_dump بریزد.

    > rustc +stage1 immut.rs -Z dump-mir=all

    پس از اجرای این دستور، یک دایرکتوری تازه‌ساخته به نام mir_dump در دایرکتوری کاری فعلی خود می‌بینیم که چند فایل دارد. اگر به فایل rustc.main.-------.mir_map.0.mir نگاه کنیم، از جمله چیزهای دیگر این خط را هم در آن می‌یابیم:

    _4 = &_1;
_3 = [closure@immut.rs:7:13: 7:36] { x: move _4 };

    توجه کنید که در مثال‌های MIR این فصل، _1 همان x است.

    در اینجا، در خط اول _4 = &_1;، mir_dump به ما می‌گوید x به‌صورت ارجاع تغییرناپذیر قرض گرفته شده است. این همان چیزی است که امید داشتیم، چون closure ما فقط x را می‌خواند.

    مثال ۲

    این هم مثالی دیگر:

    fn closure(mut f: impl FnMut()) {
    f();
}

fn main() {
    let mut x: i32 = 10;
    closure(|| {
        x += 10;  // The closure mutates the value of x
        println!("Hi {}", x)
    });
    println!("Value of x after return {}", x);
}
    _4 = &mut _1;
_3 = [closure@mut.rs:7:13: 10:6] { x: move _4 };

    این بار، در خط _4 = &mut _1; می‌بینیم که قرض به قرض تغییرپذیر تبدیل شده است. منطقی است! closure مقدار x را ۱۰ واحد افزایش می‌دهد.

    مثال ۳

    یک مثال دیگر:

    fn closure(f: impl FnOnce()) {
    f();
}

fn main() {
    let x = vec![21];
    closure(|| {
        drop(x);  // Makes x unusable after the fact.
    });
    // println!("Value of x after return {:?}", x);
}
    _6 = [closure@move.rs:7:13: 9:6] { x: move _1 }; // bb16[3]: scope 1 at move.rs:7:13: 9:6

    در اینجا x مستقیماً به درون closure منتقل (move) می‌شود و دسترسی به آن پس از closure مجاز نخواهد بود.

    استنتاج‌ها در کامپایلر

    حالا وارد کد rustc شویم و ببینیم همهٔ این استنتاج‌ها چگونه توسط کامپایلر انجام می‌شوند.

    با تعریف اصطلاحی شروع می‌کنیم که در ادامهٔ بحث بسیار به کار خواهیم برد - upvar. یک upvar متغیری است که محلی تابعی است که closure در آن تعریف شده است. پس در مثال‌های بالا، x یک upvar برای closure خواهد بود. گاهی به آن‌ها متغیرهای آزاد هم گفته می‌شود، یعنی به بافت closure مقید نیستند. compiler/rustc_passes/src/upvars.rs برای این منظور queryای به نام upvars_mentioned تعریف می‌کند.

    جز فراخوانی تنبل (lazy)، چیز دیگری که closure را از یک تابع عادی متمایز می‌کند این است که می‌تواند از upvarها استفاده کند. این upvarها را از بافت پیرامون خود قرض می‌گیرد؛ بنابراین کامپایلر باید نوع قرض upvar را تعیین کند. کامپایلر با تخصیص نوع قرض تغییرناپذیر شروع می‌کند و بر اساس نحوهٔ استفاده، در صورت لزوم محدودیت را کاهش می‌دهد (یعنی از تغییرناپذیر به تغییرپذیر و سپس به move تغییر می‌دهد). در مثال ۱ بالا، closure فقط از متغیر برای چاپ استفاده می‌کند و آن را به هیچ شکلی تغییر نمی‌دهد و بنابراین در mir_dump، نوع قرض upvar به نام x را تغییرناپذیر می‌یابیم. اما در مثال ۲، closure مقدار x را تغییر می‌دهد و آن را به‌اندازه‌ای افزایش می‌دهد. به‌دلیل این تغییر، کامپایلر که با تخصیص x به‌صورت نوع ارجاع تغییرناپذیر شروع کرده بود باید آن را به ارجاع تغییرپذیر تعدیل کند. به همین ترتیب در مثال سوم، closure بردار را drop می‌کند و بنابراین این ایجاب می‌کند متغیر x به درون closure منتقل (move) شود. بسته به نوع قرض، closure باید صفت مناسب را پیاده‌سازی کند: صفت Fn برای قرض تغییرناپذیر، FnMut برای قرض تغییرپذیر و FnOnce برای معناشناسی move.

    بیشتر کد مرتبط با closure در فایل compiler/rustc_hir_typeck/src/upvar.rs است و ساختارهای داده در فایل compiler/rustc_middle/src/ty/mod.rs اعلام شده‌اند.

    پیش از اینکه جلوتر برویم، بیایید دربارهٔ نحوهٔ بررسی جریان کنترل در کد پایهٔ rustc بحث کنیم. به‌طور ویژه برای closureها، متغیر محیطی RUSTC_LOG را مانند زیر تنظیم کنید و خروجی را در یک فایل جمع کنید:

    > RUSTC_LOG=rustc_hir_typeck::upvar rustc +stage1 -Z dump-mir=all \
    <.rs file to compile> 2> <file where the output will be dumped>

    این دستور از کامپایلر stage1 استفاده می‌کند و لاگ‌گیری debug! را برای ماژول rustc_hir_typeck::upvar فعال می‌کند.

    گزینهٔ دیگر این است که کد را با lldb یا gdb گام‌به‌گام اجرا کنید.

    1. rust-lldb build/host/stage1/bin/rustc test.rs
    2. در lldb:
      1. b upvar.rs:134 // تنظیم breakpoint روی یک خط مشخص در فایل upvar.rs
      2. r // اجرای برنامه تا رسیدن به breakpoint

    با upvar.rs شروع می‌کنیم. این فایل چیزی به نام euv::ExprUseVisitor دارد که روی منبع closure پیمایش می‌کند و برای هر upvarی که قرض گرفته، تغییر داده یا move شود یک callback فراخوانی می‌کند.

    fn main() {
    let mut x = vec![21];
    let _cl = || {
        let y = x[0];  // 1.
        x[0] += 1;  // 2.
    };
}

    در مثال بالا، بازدیدکنندهٔ ما دو بار فراخوانی می‌شود، برای خط‌های علامت‌گذاری‌شده با ۱ و ۲، یک بار برای قرض مشترک و بار دیگر برای قرض تغییرپذیر. همچنین به ما می‌گوید چه چیزی قرض گرفته شد.

    callbackها با پیاده‌سازی صفت Delegate تعریف می‌شوند. نوع InferBorrowKind، Delegate را پیاده‌سازی می‌کند و نگاشتی نگه می‌دارد که برای هر upvar ثبت می‌کند چه حالت captureای لازم بوده است. حالت‌های capture می‌توانند ByValue (move شده) یا ByRef (قرض گرفته‌شده) باشند. برای قرض‌های ByRef، BorrowKindهای ممکن ImmBorrow، UniqueImmBorrow و MutBorrow هستند، همان‌طور که در compiler/rustc_middle/src/ty/mod.rs تعریف شده‌اند.

    Delegate چند متد مختلف (callbackهای مختلف) تعریف می‌کند: consume برای move یک متغیر، borrow برای قرض از نوعی (مشترک یا تغییرپذیر)، و mutate وقتی انتساب چیزی را می‌بینیم.

    همهٔ این callbackها یک آرگومان مشترک به نام cmt دارند که مخفف Category، Mutability و Type است و در compiler/rustc_hir_typeck/src/expr_use_visitor.rs تعریف شده است. به نقل از توضیحات کد، «cmt یک دسته‌بندی کامل از یک مقدار است که نشان می‌دهد از کجا منشأ گرفته و چگونه قرار گرفته است، و همچنین تغییرپذیری حافظه‌ای که مقدار در آن ذخیره شده است». بر اساس callback (consume، borrow و غیره)، adjust_upvar_borrow_kind_for_<something> مرتبط را فراخوانی می‌کنیم و cmt را به آن می‌دهیم. پس از تعدیل نوع قرض، آن را در جدول ذخیره می‌کنیم، که اساساً می‌گوید برای هر closure چه قرض‌هایی انجام شده است.

    self.tables
    .borrow_mut()
    .upvar_capture_map
    .extend(delegate.adjust_upvar_captures);
