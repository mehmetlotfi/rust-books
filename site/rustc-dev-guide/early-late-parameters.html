    پارامترهای early bound در برابر late bound

    نکته: این فصل عمدتاً از early/late bound به‌عنوان چیزی صحبت می‌کند که صرفاً هنگام بحث دربارهٔ نوع‌های آیتم تابع/تعریف‌های تابع مرتبط است. این احتمالاً کاملاً درست نیست؛ بلوک‌های async و closureها احتمالاً باید تا حدی در این فصل بحث شوند.

    همچنین این نوشته‌های وبلاگ را ببینید که در زمان معرفی تمایز میان پارامترهای early و late bound نوشته شدند: Intermingled parameter lists و Intermingled parameter lists, take 2.

    مقید بودن «early» یا «late» به چه معناست

    هر تعریف تابع یک ZST متناظر دارد که صفت‌های Fn* را پیاده‌سازی می‌کند و به نوع آیتم تابع (function item type) معروف است. این بخش از فصل کمی دربارهٔ «desugaring» نوع‌های آیتم تابع صحبت می‌کند، چون بافت مفیدی برای توضیح تفاوت میان پارامترهای جنریک early bound و late bound است.

    با یک مثال بسیار ساده که هیچ پارامتر جنریکی ندارد شروع می‌کنیم:

    fn foo(a: String) -> u8 {
    1
    /* snip */
}

    اگر تعریف‌های نوع آیتم تابع متناظر با foo و impl مربوط به Fn آن را صریحاً می‌نوشتیم، چیزی شبیه این می‌شد:

    struct FooFnItem;

impl Fn<(String,)> for FooFnItem {
    type Output = u8;
    /* fn call(&self, ...) -> ... { ... } */
}

    impl‌های توکار صفت‌های FnMut/FnOnce و نیز impl‌های Copy و Clone برای اختصار حذف شدند (هرچند این صفت‌ها برای نوع‌های آیتم تابع پیاده‌سازی شده‌اند).

    مثالی کمی پیچیده‌تر شامل معرفی پارامترهای جنریک به تابع خواهد بود:

    fn foo<T: Sized>(a: T) -> T {
    a
    /* snip */
}

    نوشتن تعریف‌ها چیزی شبیه این می‌شود:

    struct FooFnItem<T: Sized>(PhantomData<fn(T) -> T>);

impl<T: Sized> Fn<(T,)> for FooFnItem<T> {
    type Output = T;
    /* fn call(&self, ...) -> ... { ... } */
}

    توجه کنید که نوع آیتم تابع FooFnItem نسبت به پارامتر نوعی T که روی تابع foo تعریف شده جنریک است. اما همهٔ پارامترهای جنریک تعریف‌شده روی توابع روی نوع آیتم تابع هم تعریف نمی‌شوند، همان‌طور که اینجا نشان داده شده:

    fn foo<'a, T: Sized>(a: &'a T) -> &'a T {
    a
    /* snip */
}

    که شکل «desugar»شدهٔ آن چنین است:

    struct FooFnItem<T: Sized>(PhantomData<for<'a> fn(&'a T) -> &'a T>);

impl<'a, T: Sized> Fn<(&'a T,)> for FooFnItem<T> {
    type Output = &'a T;
    /* fn call(&self, ...) -> ... { ... } */
}

    پارامتر طول عمر 'a از تابع foo روی نوع آیتم تابع FooFnItem وجود ندارد و در عوض روی impl توکار صرفاً برای نمایش نوع‌های آرگومان معرفی می‌شود.

    اینکه همهٔ پارامترهای جنریک روی نوع آیتم تابع تعریف نمی‌شوند یعنی هنگام فراخوانی یک تابع دو گام وجود دارد که در آن‌ها آرگومان‌های جنریک فراهم می‌شوند.

    1. نام بردن از تابع (مثلاً let a = foo;): آرگومان‌های FooFnItem فراهم می‌شوند.
    2. فراخوانی تابع (مثلاً a(&10);): هر پارامتری که روی impl توکار تعریف شده فراهم می‌شود.

    این سامانهٔ دوگامی منشأ نام‌گذاری early در برابر late است: پارامترهای early bound در زودترین گام (نام بردن از تابع) فراهم می‌شوند، در حالی که پارامترهای late bound در دیرترین گام (فراخوانی تابع).

    با نگاه به desugaring مثال قبلی می‌توانیم بگوییم T یک پارامتر نوع early bound و 'a یک پارامتر طول عمر late bound است، چون T روی نوع آیتم تابع هست اما 'a نیست. این مثال فراخوانی foo را ببینید که با توضیح اینکه هر پارامتر جنریک در کجا آرگومان می‌گیرد حاشیه‌نویسی شده است:

    fn foo<'a, T: Sized>(a: &'a T) -> &'a T {
    a
    /* snip */
}

// Here we provide a type argument `String` to the
// type parameter `T` on the function item type
let my_func = foo::<String>;

// Here (implicitly) a lifetime argument is provided
// to the lifetime parameter `'a` on the builtin impl.
my_func(&String::new());

    تفاوت‌های میان پارامترهای early و late bound

    اشاره‌گرهای تابع و کران‌های صفتِ مرتبه‌بالاتر (higher ranked)

    late bound بودن یک پارامتر جنریک امکان استفادهٔ انعطاف‌پذیرتر از آیتم تابع را می‌دهد. برای مثال، اگر تابعی مانند foo با پارامتر طول عمر early bound و تابعی مانند bar با پارامتر طول عمر late bound به نام 'a داشته باشیم، impl‌های توکار Fn زیر را خواهیم داشت:

    impl<'a> Fn<(&'a String,)> for FooFnItem<'a> { /* ... */ }
impl<'a> Fn<(&'a String,)> for BarFnItem { /* ... */ }

    تابع bar امضایی به‌طور اکید انعطاف‌پذیرتر دارد، چون نوع آیتم تابع را می‌توان با قرضی با هر طول عمر فراخوانی کرد، در حالی که نوع آیتم تابع foo فقط با قرضی با همان طول عمر روی نوع آیتم تابع قابل فراخوانی است. می‌توانیم این را با صرفاً تلاش برای فراخوانی چندبارهٔ نوع آیتم تابع foo با طول عمرهای مختلف نشان دهیم:

    // The `'a: 'a` bound forces this lifetime to be early bound.
fn foo<'a: 'a>(b: &'a String) -> &'a String { b }
fn bar<'a>(b: &'a String) -> &'a String { b }

// Early bound generic parameters are instantiated here when naming
// the function `foo`. As `'a` is early bound an argument is provided.
let f = foo::<'_>;

// Both function arguments are required to have the same lifetime as
// the lifetime parameter being early bound means that `f` is only
// callable for one specific lifetime.
//
// As we call this with borrows of different lifetimes, the borrow checker
// will error here.
f(&String::new());
f(&String::new());

    early bound بودن پارامتر طول عمر روی foo ایجاب می‌کند همهٔ فراخواننده‌های f قرضی با همان طول عمر فراهم کنند. در این مثال، نوع آیتم تابع foo را دو بار فراخوانی می‌کنیم، هر بار با قرضی از یک موقت. این دو قرض نمی‌توانند طول عمرهای هم‌پوشان داشته باشند، چون موقت‌ها فقط در حین فراخوانی تابع زنده‌اند و پس از آن نه، پس خطای کامپایل می‌گیریم.

    اگر پارامتر طول عمر روی foo late bound بود، این کد کامپایل می‌شد، چون هر فراخواننده می‌توانست آرگومان طول عمر متفاوتی برای قرض خود فراهم کند. مثال زیر را ببینید که این را با استفاده از تابع bar تعریف‌شده در بالا نشان می‌دهد:

    fn foo<'a: 'a>(b: &'a String) -> &'a String { b }
fn bar<'a>(b: &'a String) -> &'a String { b }

// Early bound parameters are instantiated here, however as `'a` is
// late bound it is not provided here.
let b = bar;

// Late bound parameters are instantiated separately at each call site
// allowing different lifetimes to be used by each caller.
b(&String::new());
b(&String::new());

    این در توانایی coerce کردن نوع‌های آیتم تابع به اشاره‌گرهای تابع مرتبه‌بالاتر و اثبات کران‌های صفت Fn مرتبه‌بالاتر بازتاب می‌یابد. می‌توانیم این را با مثال زیر نشان دهیم:

    // The `'a: 'a` bound forces this lifetime to be early bound.
fn foo<'a: 'a>(b: &'a String) -> &'a String { b }
fn bar<'a>(b: &'a String) -> &'a String { b }

fn accepts_hr_fn(_: impl for<'a> Fn(&'a String) -> &'a String) {}

fn higher_ranked_trait_bound() {
    let bar_fn_item = bar;
    accepts_hr_fn(bar_fn_item);

    let foo_fn_item = foo::<'_>;
    // errors
    accepts_hr_fn(foo_fn_item);
}

fn higher_ranked_fn_ptr() {
    let bar_fn_item = bar;
    let fn_ptr: for<'a> fn(&'a String) -> &'a String = bar_fn_item;

    let foo_fn_item = foo::<'_>;
    // errors
    let fn_ptr: for<'a> fn(&'a String) -> &'a String = foo_fn_item;
}

    در هر دوی این موارد، borrow checker خطا می‌دهد چون foo_fn_item را با قرضی از هر طول عمری قابل فراخوانی نمی‌داند. این به این واقعیت برمی‌گردد که پارامتر طول عمر روی foo early bound است و باعث می‌شود foo_fn_item نوع FooFnItem<'_> داشته باشد که (همان‌طور که impl ‏Fn در حالت desugar نشان می‌دهد) فقط با قرضی با همان طول عمر '_ قابل فراخوانی است.

    Turbofish در حضور پارامترهای late bound

    همان‌طور که پیش‌تر گفته شد، تمایز میان پارامترهای early و late bound یعنی دو جا وجود دارد که پارامترهای جنریک نمونه‌سازی می‌شوند:

    • هنگام نام بردن از تابع (early)
    • هنگام فراخوانی تابع (late)

    در حال حاضر نحوی برای مشخص کردن صریح آرگومان‌های جنریک برای پارامترهای late bound در گام فراخوانی وجود ندارد؛ آرگومان‌های جنریک را فقط برای پارامترهای early bound هنگام نام بردن از تابع می‌توان مشخص کرد. نحو foo::<'static>(); با اینکه بخشی از یک فراخوانی تابع است، مانند (foo::<'static>)(); رفتار می‌کند و پارامترهای جنریک early bound را روی نوع آیتم تابع نمونه‌سازی می‌کند.

    مثال زیر را ببینید:

    fn foo<'a>(b: &'a u32) -> &'a u32 { b }

let f /* : FooFnItem<????> */ = foo::<'static>;

    مثال بالا خطا می‌دهد چون پارامتر طول عمر 'a late bound است و بنابراین نمی‌تواند به‌عنوان بخشی از گام «نام بردن از تابع» نمونه‌سازی شود. اگر پارامتر طول عمر را early bound کنیم، می‌بینیم این کد شروع به کامپایل شدن می‌کند:

    fn foo<'a: 'a>(b: &'a u32) -> &'a u32 { b }

let f /* : FooFnItem<'static> */ = foo::<'static>;

    هدف پیاده‌سازی فعلی کامپایلر این است که هنگام مشخص کردن آرگومان‌های طول عمر برای تابعی که هم پارامتر طول عمر early bound و هم late bound دارد خطا بدهد. در عمل، به‌دلیل شکستن بیش‌ازحد، برخی موارد در واقع فقط هشدار سازگاری آینده (FCW) هستند (#42868):

    • وقتی تعداد آرگومان‌های طول عمر با تعداد پارامترهای طول عمر early bound برابر باشد، به‌جای خطا یک FCW صادر می‌شود
    • هنگام استفاده از نحو فراخوانی متد، خطا همیشه به FCW تنزل می‌یابد

    برای نشان دادن این، می‌توانیم انواع مختلف توابع را بنویسیم و به همهٔ آن‌ها یک طول عمر late bound و یک early bound بدهیم:

    fn free_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}

struct Foo;

trait Trait: Sized {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ());
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ());
}

impl Trait for Foo {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

impl Foo {
    fn inherent_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn inherent_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

    سپس برای حالت اول، می‌توانیم هر تابع را با یک آرگومان طول عمر (متناظر با تنها پارامتر طول عمر early bound) فراخوانی کنیم و توجه کنیم که فقط به یک FCW می‌انجامد، نه یک خطای سخت.

    #![deny(late_bound_lifetime_arguments)]

fn free_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}

struct Foo;

trait Trait: Sized {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ());
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ());
}

impl Trait for Foo {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

impl Foo {
    fn inherent_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn inherent_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

// Specifying as many arguments as there are early
// bound parameters is always a future compat warning
Foo.trait_method::<'static>(&(), &());
Foo::trait_method::<'static>(Foo, &(), &());
Foo::trait_function::<'static>(&(), &());
Foo.inherent_method::<'static>(&(), &());
Foo::inherent_function::<'static>(&(), &());
free_function::<'static>(&(), &());

    برای حالت دوم هر تابع را با آرگومان‌های طول عمر بیشتر از تعداد پارامترهای طول عمر (چه early و چه late bound) فراخوانی می‌کنیم و توجه می‌کنیم که فراخوانی متد به FCW می‌انجامد، برخلاف توابع آزاد/وابسته که به خطای سخت می‌انجامند:

    fn free_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}

struct Foo;

trait Trait: Sized {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ());
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ());
}

impl Trait for Foo {
    fn trait_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn trait_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

impl Foo {
    fn inherent_method<'a: 'a, 'b>(self, _: &'a (), _: &'b ()) {}
    fn inherent_function<'a: 'a, 'b>(_: &'a (), _: &'b ()) {}
}

// Specifying more arguments than there are early
// bound parameters is a future compat warning when
// using method call syntax.
Foo.trait_method::<'static, 'static, 'static>(&(), &());
Foo.inherent_method::<'static, 'static, 'static>(&(), &());
// However, it is a hard error when not using method call syntax.
Foo::trait_method::<'static, 'static, 'static>(Foo, &(), &());
Foo::trait_function::<'static, 'static, 'static>(&(), &());
Foo::inherent_function::<'static, 'static, 'static>(&(), &());
free_function::<'static, 'static, 'static>(&(), &());

    حتی وقتی آرگومان‌های طول عمر کافی برای هر دو پارامتر طول عمر late و early bound مشخص می‌کنیم، این آرگومان‌ها در واقع برای حاشیه‌نویسی طول عمر داده‌شده به پارامترهای late bound به کار نمی‌روند. می‌توانیم این را با turbofish کردن 'static روی تابعی و در عین حال دادن یک قرض غیر static نشان دهیم:

    struct Foo;

impl Foo {
    fn inherent_method<'a: 'a, 'b>(self, _: &'a (), _: &'b String ) {}
}

Foo.inherent_method::<'static, 'static>(&(), &String::new());

    این کد کامپایل می‌شود با اینکه آرگومان تابع &String::new() طول عمر 'static ندارد؛ دلیلش این است که آرگومان‌های طول عمر «اضافی» هنگام فراخوانی واقعی تابع دور ریخته می‌شوند و برای پارامترهای late bound در نظر گرفته نمی‌شوند.

    زنده بودن (Liveness) نوع‌ها با پارامترهای late bound

    هنگام بررسی کران‌های outlives نوع که نوع‌های آیتم تابع را درگیر می‌کنند، پارامترهای early bound را در نظر می‌گیریم. برای مثال:

    fn foo<T>(_: T) {}

fn requires_static<T: 'static>(_: T) {}

fn bar<T>() {
    let f /* : FooFnItem<T> */ = foo::<T>;
    requires_static(f);
}

    چون پارامتر نوع T early bound است، desugaring نوع آیتم تابع برای foo چیزی شبیه struct FooFnItem<T> خواهد بود. آن‌گاه برای اینکه FooFnItem<T>: 'static برقرار باشد، باید برقراری T: 'static را هم الزام کنیم، وگرنه به باگ‌های سلامت (soundness) می‌رسیم.

    متأسفانه، به‌دلیل باگ‌هایی در کامپایلر، طول عمرهای early bound را در نظر نمی‌گیریم، که علت باگ سلامت باز #84366 است. این یعنی نشان دادن «تفاوت» میان پارامترهای early/late bound برای کران‌های liveness/outlives نوع غیرممکن است، چون تنها نوع پارامتر جنریکی که می‌تواند late bound باشد طول عمرهاست که نادرست مدیریت می‌شوند.

    با این حال، در نظریه مثال کد زیر باید چنین تفاوتی را نشان دهد، پس از اینکه #84366 رفع شود:

    fn early_bound<'a: 'a>(_: &'a String) {}
fn late_bound<'a>(_: &'a String) {}

fn requires_static<T: 'static>(_: T) {}

fn bar<'b>() {
    let e = early_bound::<'b>;
    // this *should* error but does not
    requires_static(e);

    let l = late_bound;
    // this correctly does not error
    requires_static(l);
}

    الزامات late bound بودن یک پارامتر

    باید پارامتر طول عمر باشد

    پارامترهای نوع و Const نمی‌توانند late bound باشند، چون راهی برای پشتیبانی از نوع‌هایی مانند dyn for<T> Fn(Box<T>) یا for<T> fn(Box<T>) نداریم. فراخوانی چنین نوع‌هایی مستلزم توانایی monomorphize کردن تابع زیربنایی است که با غیرمستقیم‌گری از طریق dispatch پویا ممکن نیست.

    نباید در where clause استفاده شده باشد

    در حال حاضر وقتی یک پارامتر جنریک در where clause استفاده شود باید early bound باشد. برای مثال:

    trait Trait<'a> {}
fn foo<'a, T: Trait<'a>>(_: &'a String, _: T) {}

    در این مثال پارامتر طول عمر 'a early bound در نظر گرفته می‌شود چون در where clause به شکل T: Trait<'a> ظاهر می‌شود. این حتی برای where clauseهای «بدیهی» مانند 'a: 'a یا آن‌هایی که از well-formed بودن آرگومان‌های تابع نتیجه می‌شوند صادق است، برای مثال:

    fn foo<'a: 'a>(_: &'a String) {}
fn bar<'a, T: 'a>(_: &'a T) {}

    در هر دوی این توابع، پارامتر طول عمر 'a early bound در نظر گرفته می‌شود، با اینکه where clauseهایی که در آن‌ها به کار رفته است می‌توان گفت در واقع هیچ قیدی بر فراخواننده تحمیل نمی‌کنند.

    دلیل این محدودیت ترکیبی از دو چیز است:

    • نمی‌توانیم کران‌های پارامترهای late bound را پیش از نمونه‌سازی‌شان اثبات کنیم
    • اشاره‌گرهای تابع و شیء‌های صفت راهی برای نمایش where clauseهای هنوز اثبات‌نشدهٔ تابع زیربنایی ندارند

    مثال زیر را در نظر بگیرید:

    trait Trait<'a> {}
fn foo<'a, T: Trait<'a>>(_: &'a T) {}

let f = foo::<String>;
let f = f as for<'a> fn(&'a String);
f(&String::new());

    در نقطه‌ای هنگام بررسی نوع باید برای این کد خطا صادر شود، چون String صفت Trait را برای هیچ طول عمری پیاده‌سازی نمی‌کند.

    اگر طول عمر 'a late bound بود، بررسی این دشوار می‌شد. هنگام نام بردن از foo نمی‌دانیم چه طول عمری باید به‌عنوان بخشی از کران صفت T: Trait<'a> استفاده شود، چون هنوز نمونه‌سازی نشده است. هنگام coerce کردن نوع آیتم تابع به اشاره‌گر تابع راهی برای ردیابی کران صفت String: Trait<'a> که هنگام فراخوانی تابع باید اثبات شود نداریم.

    اگر طول عمر 'a early bound باشد (که در پیاده‌سازی فعلی در rustc چنین است)، کران صفت را می‌توان هنگام نام بردن از تابع foo بررسی کرد. الزام early bound بودن پارامترهای به‌کاررفته در where clauseها جای طبیعی‌ای برای بررسی where clauseهای تعریف‌شده روی تابع فراهم می‌کند.

    سرانجام، اگر طول عمرها در کران‌های ضمنی (implied bounds) به کار روند، الزام نمی‌کنیم early bound باشند، برای مثال:

    fn foo<'a, T>(_: &'a T) {}

let f = foo;
f(&String::new());
f(&String::new());

    این کد کامپایل می‌شود و نشان می‌دهد پارامتر طول عمر late bound است، با اینکه 'a در نوع &'a T به کار رفته که به‌طور ضمنی برقراری T: 'a را ایجاب می‌کند. کران‌های ضمنی را می‌توان به‌طور ویژه رفتار کرد، چون هر نوعی که کران ضمنی ایجاد می‌کند در امضای نوع اشاره‌گر تابع است، یعنی هنگام فراخوانی تابع می‌دانیم باید T: 'a را اثبات کنیم.

    باید توسط نوع‌های آرگومان مقید شده باشد

    مهم است که impl‌های توکار روی نوع‌های آیتم تابع به پارامترهای جنریک مقیدنشده ختم نشوند، چون این می‌تواند به ناسالمی (unsoundness) بینجامد. این همان نوع محدودیتی است که بر impl‌های نوشته‌شده توسط کاربر اعمال می‌شود؛ برای مثال کد زیر به خطا می‌انجامد:

    trait Trait {
    type Assoc;
}

impl<'a> Trait for u8 {
    type Assoc = &'a String;
}

    مثال متناظر برای impl‌های توکار روی آیتم‌های تابع چنین خواهد بود:

    fn foo<'a>() -> &'a String { /* ... */ }

    اگر پارامتر طول عمر 'a late bound می‌شد، به یک impl توکار با طول عمر مقیدنشده می‌رسیدیم؛ می‌توانیم desugaring نوع آیتم تابع و impl‌های آن را با late bound بودن 'a دستی بنویسیم تا این را نشان دهیم:

    // NOTE: this is just for demonstration, in practice `'a` is early bound
struct FooFnItem;

impl<'a> Fn<()> for FooFnItem {
    type Output = &'a String;
    /* fn call(...) -> ... { ... } */
}

    برای پرهیز از چنین وضعیتی 'a را early bound در نظر می‌گیریم که باعث می‌شود طول عمر روی impl توسط نوع self مقید شود:

    struct FooFnItem<'a>(PhantomData<fn() -> &'a String>);

impl<'a> Fn<()> for FooFnItem<'a> {
    type Output = &'a String;
    /* fn call(...) -> ... { ... } */
}
