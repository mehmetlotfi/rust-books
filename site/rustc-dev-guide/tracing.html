    استفاده از tracing برای اشکال‌زدایی کامپایلر

    کامپایلر تعداد زیادی فراخوانی debug! (یا trace!) دارد که در نقاط بسیاری اطلاعات لاگ چاپ می‌کنند. این‌ها دست‌کم برای محدودکردن محل یک باگ، اگر نه یافتن کامل آن، بسیار مفیدند، یا فقط برای اینکه بفهمید چرا کامپایلر کار مشخصی را انجام می‌دهد.

    برای دیدن لاگ‌ها باید متغیر محیطی RUSTC_LOG را روی فیلتر لاگ خود تنظیم کنید. نحو کامل فیلترهای لاگ را در مستندات rustdoc برای tracing-subscriber می‌یابید.

    Environment variables

    این نمای کلی متغیرهای محیطی‌ای است که rustc برای سفارشی‌سازی خروجی tracing می‌پذیرد. تعریف این‌ها را عمدتاً در compiler/rustc_log/src/lib.rs می‌یابید.

    NameUsage
    RUSTC_LOGفیلترهای tracing (بقیهٔ این صفحه را ببینید)
    RUSTC_LOG_COLORalways, never or auto.
    RUSTC_LOG_ENTRY_EXITاگر تنظیم شده و برابر «0» نباشد، ورود/خروج span را لاگ می‌کند.
    RUSTC_LOG_THREAD_IDSاگر تنظیم شده و برابر «1» باشد، شناسهٔ threadها را هم لاگ می‌کند.
    RUSTC_LOG_BACKTRACEاگر یک trace با target منطبق با رشتهٔ داده‌شده صادر شود، backtrace را می‌گیرد و چاپ می‌کند.
    RUSTC_LOG_LINESاگر 1 باشد، خطوط لاگ را بر اساس عمق تو‌رفته می‌کند.
    RUSTC_LOG_FORMAT_JSONاگر 1 باشد، لاگ‌ها را به‌صورت JSON خروجی می‌دهد. پارامترهای دقیق در rustc_log/src/lib.rs هست اما قالب آن ناپایدار است.
    RUSTC_LOG_OUTPUT_TARGETاگر مشخص شود، لاگ‌ها به‌جای stderr به فایلی با نام داده‌شده می‌روند.

    Function level filters

    بسیاری از توابع در rustc با این annotate شده‌اند

    #[instrument(level = "debug", skip(self))]
fn foo(&self, bar: Type) {}

    که به شما اجازه می‌دهد از

    RUSTC_LOG=[foo]

    استفاده کنید تا همهٔ این‌ها را یک‌جا انجام دهید

    • همهٔ فراخوانی‌های foo را لاگ می‌کند
    • آرگومان‌ها را لاگ می‌کند (به‌جز آن‌هایی که در فهرست skip هستند)
    • همه‌چیز (از هر جای دیگر کامپایلر) را تا برگشتن تابع لاگ می‌کند

    همه‌چیز را نمی‌خواهم

    بسته به دامنهٔ تابع، ممکن است نخواهید همه‌چیز در بدنهٔ آن لاگ شود. به‌عنوان مثال: تابع do_mir_borrowck حتی برای کد بی‌اهمیتی که borrowcheck می‌شود صدها خط dump می‌کند.

    چون می‌توانید همهٔ فیلترها را ترکیب کنید، می‌توانید مسیر crate/ماژول اضافه کنید، مثلاً

    RUSTC_LOG=rustc_borrowck[do_mir_borrowck]

    همهٔ فراخوانی‌ها را نمی‌خواهم

    اگر libcore را کامپایل می‌کنید، احتمالاً همهٔ dumpهای borrowck را نمی‌خواهید، بلکه فقط یکی برای تابعی مشخص. می‌توانید فراخوانی‌های تابع را بر اساس آرگومان‌هایشان با regex فیلتر کنید.

    RUSTC_LOG=[do_mir_borrowck{id=\.\*from_utf8_unchecked\.\*}]

    فقط لاگ‌های borrowcheck برای from_utf8_unchecked را می‌دهد. توجه کنید که همچنان برای هر do_mir_borrowck نادیده‌گرفته‌شده یک پیام کوتاه می‌گیرید، اما هیچ‌چیز از درون آن فراخوانی‌ها. این به شما کمک می‌کند فراخوانی‌هایی را که رخ می‌دهند مرور کنید و اگر regex را اشتباه نوشته‌اید آن را اصلاح کنید.

    Query level filters

    هر کوئری به‌طور خودکار با یک span لاگ‌گذاری برچسب می‌خورد تا بتوانید همهٔ پیام‌های لاگ را هنگام اجرای کوئری نمایش دهید. برای مثال، اگر می‌خواهید همه‌چیز را هنگام type checking لاگ کنید:

    RUSTC_LOG=[typeck]

    آرگومان‌های کوئری به‌صورت فیلد tracing گنجانده می‌شوند که یعنی می‌توانید بر اساس نمایش debug آرگومان‌ها فیلتر کنید. برای مثال، کوئری typeck آرگومان key: LocalDefId برای چیزی که بررسی می‌شود دارد. می‌توانید از regex برای تطبیق آن LocalDefId استفاده کنید تا type checking یک تابع مشخص را لاگ کنید:

    RUSTC_LOG=[typeck{key=.*name_of_item.*}]

    کوئری‌های مختلف آرگومان‌های مختلف دارند. فهرست کوئری‌ها و آرگومان‌هایشان را در rustc_middle/src/queries.rs می‌یابید.

    فیلترهای گسترده در سطح ماژول

    همچنین می‌توانید از فیلترهایی شبیه فیلترهای crate با نام log استفاده کنید، که همه‌چیز درون یک ماژول مشخص را فعال می‌کنند. این اغلب بیش‌ازحد پرحرف و بی‌ساختار است، پس توصیه می‌شود از فیلترهای سطح تابع استفاده کنید.

    فیلتر لاگ شما می‌تواند فقط debug باشد تا همهٔ خروجی debug! و بالاتر را بگیرد (مثلاً info! را هم شامل می‌شود)، یا path::to::module تا همهٔ خروجی (از جمله trace!) را از یک ماژول مشخص بگیرد، یا path::to::module=debug تا خروجی debug! و بالاتر را از یک ماژول مشخص بگیرد.

    برای مثال، برای گرفتن خروجی debug! و بالاتر برای یک ماژول مشخص، می‌توانید کامپایلر را با RUSTC_LOG=path::to::module=debug rustc my-file.rs اجرا کنید. آن‌گاه همهٔ خروجی debug! در standard error ظاهر می‌شود.

    توجه کنید که می‌توانید از مسیر جزئی استفاده کنید و فیلتر همچنان کار می‌کند. برای مثال، اگر می‌خواهید خروجی info! را فقط از rustdoc::passes::collect_intra_doc_links ببینید، می‌توانید از RUSTDOC_LOG=rustdoc::passes::collect_intra_doc_links=info یا RUSTDOC_LOG=rustdoc::passes::collect_intra=info استفاده کنید.

    اگر روی rustdoc کار می‌کنید به‌جای آن از RUSTDOC_LOG استفاده کنید. اگر روی Miri کار می‌کنید به‌جای آن از MIRI_LOG استفاده کنید. منظور را گرفتید :)

    برای دیدن نحو کامل قابل‌استفاده، مستندات crate با نام tracing و به‌طور مشخص مستندات debug! را ببینید. (نکته: برخلاف کامپایلر، crate با نام tracing و مثال‌هایش از متغیر محیطی RUSTC_LOG استفاده می‌کنند. rustc، rustdoc و ابزارهای دیگر متغیرهای محیطی سفارشی تنظیم می‌کنند.)

    توجه کنید که مگر اینکه از فیلتر بسیار سخت‌گیرانه‌ای استفاده کنید، logger خروجی زیادی صادر می‌کند، پس از دقیق‌ترین ماژول(ها) که می‌توانید استفاده کنید (با ویرگول جدا شوند اگر چند تا هستند). معمولاً ایدهٔ خوبی است standard error را به فایل pipe کنید و خروجی لاگ را با یک ویرایشگر متن ببینید.

    پس برای جمع‌بندی:

    # This puts the output of all debug calls in `rustc_middle/src/traits` into
# standard error, which might fill your console backscroll.
$ RUSTC_LOG=rustc_middle::traits=debug rustc +stage1 my-file.rs

# This puts the output of all debug calls in `rustc_middle/src/traits` in
# `traits-log`, so you can then see it with a text editor.
$ RUSTC_LOG=rustc_middle::traits=debug rustc +stage1 my-file.rs 2>traits-log

# Not recommended! This will show the output of all `debug!` calls
# in the Rust compiler, and there are a *lot* of them, so it will be
# hard to find anything.
$ RUSTC_LOG=debug rustc +stage1 my-file.rs 2>all-log

# This will show the output of all `info!` calls in `rustc_codegen_ssa`.
#
# There's an `info!` statement in `codegen_instance` that outputs
# every function that is codegen'd. This is useful to find out
# which function triggers an LLVM assertion, and this is an `info!`
# log rather than a `debug!` log so it will work on the official
# compilers.
$ RUSTC_LOG=rustc_codegen_ssa=info rustc +stage1 my-file.rs

# This will show all logs in `rustc_codegen_ssa` and `rustc_resolve`.
$ RUSTC_LOG=rustc_codegen_ssa,rustc_resolve rustc +stage1 my-file.rs

# This will show the output of all `info!` calls made by rustdoc
# or any rustc library it calls.
$ RUSTDOC_LOG=info rustdoc +stage1 my-file.rs

# This will only show `debug!` calls made by rustdoc directly,
# not any `rustc*` crate.
$ RUSTDOC_LOG=rustdoc=debug rustdoc +stage1 my-file.rs

    Log colors

    به‌طور پیش‌فرض، rustc (و ابزارهای دیگر، مثل rustdoc و Miri) هنگام استفاده از رنگ‌های ANSI در خروجی لاگ هوشمندانه عمل می‌کنند. اگر خروجی به ترمینال برود، از رنگ استفاده می‌کنند، و اگر خروجی به فایل برود یا جای دیگری pipe شود، استفاده نمی‌کنند. اما خواندن خروجی لاگ در ترمینال دشوار است مگر فیلتر بسیار سخت‌گیرانه‌ای داشته باشید، پس ممکن است بخواهید خروجی را به pager مثل less pipe کنید. اما آن‌گاه رنگی نخواهد بود که یافتن چیزی را که دنبالش هستید سخت می‌کند!

    می‌توانید با متغیر محیطی RUSTC_LOG_COLOR تعیین کنید خروجی لاگ رنگی باشد یا نه (یا RUSTDOC_LOG_COLOR برای rustdoc، یا MIRI_LOG_COLOR برای Miri و غیره). سه گزینه هست: auto (پیش‌فرض)، always و never. بنابراین اگر می‌خواهید هنگام pipe به less رنگ‌ها فعال باشند، از دستوری شبیه این استفاده کنید:

    # The `-R` switch tells less to print ANSI colors without escaping them.
$ RUSTC_LOG=debug RUSTC_LOG_COLOR=always rustc +stage1 ... | less -R

    توجه کنید که MIRI_LOG_COLOR فقط لاگ‌هایی را که از Miri می‌آیند رنگی می‌کند، نه لاگ‌های توابع rustc که Miri فراخوانی می‌کند. برای رنگی‌کردن لاگ‌های rustc از RUSTC_LOG_COLOR استفاده کنید.

    چگونه فراخوانی‌های debug! و trace! را در فایل دودویی حاصل نگه داریم یا حذف کنیم

    در حالی که فراخوانی‌های error!، warn! و info! در هر ساخت کامپایلر گنجانده می‌شوند، فراخوانی‌های debug! و trace! فقط وقتی در برنامه گنجانده می‌شوند که rust.debug-logging = true را در bootstrap.toml داشته باشید (به‌طور پیش‌فرض خاموش است)، پس اگر لاگ‌های DEBUG را نمی‌بینید، به‌ویژه اگر کامپایلر را با RUSTC_LOG=rustc rustc some.rs اجرا می‌کنید و فقط لاگ‌های INFO می‌بینید، مطمئن شوید rust.debug-logging در bootstrap.toml شما روشن است.

    آداب و قراردادهای لاگ‌گذاری

    چون فراخوانی‌های debug! به‌طور پیش‌فرض حذف می‌شوند، در بیشتر موارد نگران عملکرد افزودن فراخوانی‌های «غیرضروری» debug! و گذاشتن آن‌ها در کدی که commit می‌کنید نباشید — این‌ها عملکرد چیزی را که عرضه می‌کنیم کند نمی‌کنند.

    با این حال، فراخوانی‌های tracing بیش‌ازحد هم می‌توانند وجود داشته باشند، به‌ویژه وقتی با فراخوانی‌های دیگر در نزدیکی یا در توابعی که از اینجا صدا زده می‌شوند تکراری‌اند. تعادل کاملی برای رسیدن به آن نیست، و تصمیم‌گیری دربارهٔ اینکه اجازه دهد دستورهای debug! بمانند یا از شما بخواهد پیش از merge حذفشان کنید با صلاحدید بازبین است.

    برای لاگ‌های بسیار پرسروصدا ممکن است استفاده از trace! به‌جای debug! ترجیح داده شود.

    یک قرارداد که تا حدی رعایت می‌شود استفاده از #[instrument(level = "debug")] است (مستندات attribute را هم ببینید) به‌جای debug!("foo(...)") در ابتدای تابع foo. درون توابع، debug!(?variable.field) را به debug!("xyz = {:?}", variable.field) ترجیح دهید و debug!(bar = ?var.method(arg)) را به debug!("bar = {:?}", var.method(arg)). مستندات این نحو را اینجا می‌یابید.

    یک نکته که باید مراقبش باشید عملیات پرهزینه در لاگ‌هاست.

    اگر در ماژول rustc::foo دستوری داشته باشید

    debug!(x = ?random_operation(tcx));

    آن‌گاه اگر کسی rustc debug را با RUSTC_LOG=rustc::foo اجرا کند، random_operation() اجرا می‌شود. فیلترهای RUSTC_LOG که این دستور debug را فعال نکنند random_operation را اجرا نمی‌کنند.

    یعنی نباید چیزی بسیار پرهزینه یا محتمل به crash را آنجا بگذارید — این کسی را که می‌خواهد از لاگ‌گذاری برای آن ماژول استفاده کند آزار می‌دهد. کسی تا وقتی کسی بخواهد از لاگ‌گذاری برای یافتن باگ دیگری استفاده کند متوجه نمی‌شود.
