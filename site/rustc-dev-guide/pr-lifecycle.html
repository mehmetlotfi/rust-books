راهنمای توسعهٔ rustcrustc Development Guide

    چرخه‌ی عمر یک PR

    پیش از بازبینی

    باز کردن یک PR

    حالا آماده‌اید که یک pull request (PR) ثبت کنید؟ عالی! در اینجا چند نکته هست که باید از آن‌ها آگاه باشید.

    همه‌ی pull requestها باید روی شاخه‌ی main ثبت شوند، مگر این‌که مطمئن باشید باید شاخه‌ی دیگری را هدف بگیرید.

    پیش از ارسال PR چند بررسی سبک (style) اجرا کنید:

    ./x test tidy --bless

    توصیه می‌کنیم این بررسی را پیش از هر pull request (و پیش از هر commit جدید در یک pull request) انجام دهید؛ می‌توانید برای اطمینان از این‌که هرگز این بررسی را فراموش نمی‌کنید، پیش از هر push یک git hook اضافه کنید. CI نیز tidy را اجرا می‌کند و اگر tidy شکست بخورد، شکست خواهد خورد.

    توضیحات PR

    GitHub اجازه می‌دهد issueها را با استفاده از کلیدواژه‌ها ببندید. برای مرتب نگه‌داشتن issue tracker باید از این قابلیت استفاده شود. با این حال، عموماً ترجیح داده می‌شود متن «closes #123» در توضیحات PR قرار بگیرد، نه در پیام commit؛ به‌ویژه در طول rebase، ذکر شماره‌ی issue در commit می‌تواند issue مربوطه را «اسپم» کند.

    با این حال، اگر PR شما یک پسرفت (regression) از stable به beta یا از stable به stable را رفع می‌کند و برای backport به beta و/یا stable پذیرفته شده است (یعنی با beta-accepted و/یا stable-accepted علامت‌گذاری شده است)، لطفاً از هیچ‌یک از این کلیدواژه‌ها استفاده نکنید، چون نمی‌خواهیم issue مربوطه پس از ورود رفع‌کننده به main به‌طور خودکار بسته شود. لطفاً توضیحات PR را به‌روزرسانی کنید، در حالی که issue را همچنان در جایی ذکر می‌کنید. برای مثال، می‌توانید بنویسید Fixes (after beta backport) #NNN..

    CI

    علاوه بر بازبینی توسط یک انسان، pull requestها به‌لطف یکپارچه‌سازی پیوسته (CI) به‌طور خودکار آزمایش می‌شوند. در اصل، هر بار که یک pull request را باز یا به‌روزرسانی می‌کنید، CI کامپایلر را می‌سازد و آن را با مجموعه‌ی آزمون کامپایلر آزمایش می‌کند، و همچنین آزمون‌های دیگری انجام می‌دهد، مانند بررسی این‌که pull request شما با دستورالعمل‌های سبک Rust مطابقت دارد.

    اجرای آزمون‌های یکپارچه‌سازی پیوسته به نویسندگان PR اجازه می‌دهد اشتباهات را زود تشخیص دهند، بدون این‌که از چرخه‌ی بازبینی اول بگذرند، و همچنین به بازبین‌ها کمک می‌کند از وضعیت یک pull request مشخص آگاه بمانند.

    Rust ظرفیت CI فراوانی دارد و هرگز لازم نیست نگران هدر رفتن منابع محاسباتی در هر بار push کردن تغییرات باشید. همچنین کاملاً مجاز است (و حتی تشویق می‌شود!) که اگر به بهره‌وری شما کمک می‌کند، از CI برای آزمایش تغییراتتان استفاده کنید. به‌ویژه، اجرای کامل مجموعه‌ی ./x test را به‌صورت محلی توصیه نمی‌کنیم، چون اجرای آن زمان بسیار زیادی می‌برد. برای استفاده از CI در Rust برای آزمایش تغییراتتان، فصل آزمایش با CI را ببینید.

    بازبینی PR

    r?

    به PR شما به‌طور خودکار یک بازبین اختصاص داده می‌شود. می‌توانید بازبین را با r? @username تغییر دهید. برای جزئیات، PR assignment را ببینید.

    Rebase کردن

    Rust از یک سیاست بدون merge-commit پیروی می‌کند، یعنی وقتی با تعارض‌های merge مواجه می‌شوید، انتظار می‌رود همیشه به‌جای merge از rebase استفاده کنید. برای مثال، هنگام آوردن آخرین تغییرات شاخه‌ی main به شاخه‌ی ویژگی (feature) خود، همیشه از rebase استفاده کنید. اگر PR شما حاوی merge commit باشد، با has-merge-commits علامت‌گذاری می‌شود. وقتی merge commitها را حذف کردید، مثلاً از طریق یک rebase تعاملی، باید این برچسب را دوباره بردارید:

    @rustbot label -has-merge-commits

    برای جزئیات بیشتر این فصل را ببینید.

    اگر با تعارض‌های merge مواجه شوید یا بازبین از شما بخواهد تغییراتی اعمال کنید، PR شما با S-waiting-on-author علامت‌گذاری می‌شود. وقتی آن‌ها را برطرف کردید، باید از @rustbot استفاده کنید تا آن را با S-waiting-on-review علامت‌گذاری کند:

    @rustbot ready

    به‌روز نگه داشتن شاخه‌ی خود

    CI در rust-lang/rust وصله‌های شما را مستقیماً روی main فعلی اعمال می‌کند، نه روی commitی که شاخه‌ی شما بر پایه‌ی آن است. این می‌تواند به شکست‌های غیرمنتظره بینجامد اگر شاخه‌ی شما قدیمی باشد، حتی وقتی تعارض merge صریحی وجود ندارد.

    شاخه‌ی خود را فقط در صورت نیاز به‌روز کنید: وقتی تعارض merge دارید، CI بالادست خراب است و PR سبز شما را مسدود کرده است، یا یکی از نگهدارندگان درخواست کرده است. از به‌روزرسانی PR سبزی که در حال بازبینی است، مگر در صورت لزوم، خودداری کنید. در طول بازبینی، commitهای تدریجی برای رسیدگی به بازخوردها بسازید. ترجیح بدهید squash یا rebase را فقط در پایان یا وقتی بازبین درخواست کرد انجام دهید.

    هنگام به‌روزرسانی، از git push --force-with-lease استفاده کنید و یک نظر کوتاه بگذارید که توضیح دهد چه چیزی تغییر کرده است. برخی مخزن‌ها merge کردن از upstream/main را به rebase ترجیح می‌دهند؛ از قراردادهای پروژه پیروی کنید. برای دستورالعمل‌های مفصل، به‌روز نگه داشتن امور را ببینید.

    پس از rebase، توصیه می‌شود آزمون‌های مرتبط را به‌صورت محلی اجرا کنید تا پیش از اجرای CI مشکلات را تشخیص دهید.

    منتظر بازبینی ماندن

    نکته

    بازبین‌های pull request اغلب با حداکثر ظرفیت کار می‌کنند، و بسیاری از آن‌ها به‌صورت داوطلبانه مشارکت می‌کنند. برای به حداقل رساندن تأخیر در بازبینی، نویسندگان pull request و بازبین‌های منتصب‌شده باید اطمینان حاصل کنند که برچسب بازبینی (S-waiting-on-review و S-waiting-on-author) به‌روز می‌ماند، و در زمان مناسب این دستورها را فراخوانی کنند:

    • @rustbot author: بازبینی تمام شده است، و نویسنده‌ی PR باید نظرات را بررسی کند و بر اساس آن‌ها اقدام کند.

    • @rustbot ready: نویسنده برای بازبینی آماده است، و این PR دوباره در صف بازبین قرار می‌گیرد.

    لطفاً توجه کنید که بازبین‌ها انسان هستند و بیشترشان در اوقات فراغت خود روی rustc کار می‌کنند. این یعنی ممکن است مدتی طول بکشد تا پاسخ دهند و PR شما را بازبینی کنند. همچنین یعنی بازبین‌ها ممکن است برخی PRهای منتصب‌شده به خود را از قلم بیندازند.

    برای تلاش در جهت پیش بردن PRها، Triage WG به‌طور منظم همه‌ی PRهایی را مرور می‌کند که منتظر بازبینی هستند و دست‌کم ۲ هفته است درباره‌شان بحث نشده است. اگر ظرف ۲ هفته بازبینی دریافت نکردید، می‌توانید در Zulip از Triage WG بپرسید (#t-release/triage). آن‌ها می‌دانند چه زمانی باید یادآوری کرد، چه کسی ممکن است در تعطیلات باشد و غیره.

    بازبین ممکن است با استفاده از رابط بازبینی کد GitHub تغییراتی درخواست کند. همچنین ممکن است برای برخی PRها رویه‌های ویژه‌ای درخواست کند. برای نمونه‌هایی از این رویه‌ها، فصل‌های Crater و Breaking Changes را ببینید.

    در پرسیدن سؤال یا بحث درباره‌ی چیزهایی که نمی‌فهمید یا با آن‌ها مخالفید راحت باشید. با این حال، بدانید که PR ادغام نمی‌شود مگر این‌که یکی از اعضای تیم Rust آن را تأیید کند. اگر بازبین نظری مانند r=me after fixing ... بگذارد، یعنی PR را تأیید کرده است و می‌توانید با نظری به شکل @bors r=reviewer-github-id (مثلاً @bors r=eddyb) آن را پس از رفع مشکلات جزئی ادغام کنید. توجه کنید که r=someone به مجوز نیاز دارد و bors ممکن است هنگام نظر دادن با r=someone چیزی مانند «🔑 Insufficient privileges…» بگوید. در آن صورت، باید از بازبین بخواهید PR شما را دوباره مرور کند.

    برای برخی PRها در طول فرایند بازبینی ممکن است چند اتفاق رخ دهد

    • اگر تغییر به اندازه‌ی کافی اساسی باشد، بازبین ممکن است برای PR یک FCP درخواست کند. این به همه‌ی اعضای تیم مربوطه فرصت می‌دهد تغییرات را بازبینی کنند.
    • اگر تغییر ممکن است باعث شکست شود، بازبین ممکن است اجرای crater را درخواست کند. این کار کامپایلر را با تغییرات شما می‌سازد و سپس تلاش می‌کند همه‌ی crateهای crates.io را با کامپایلر تغییریافته‌ی شما کامپایل کند. این یک smoke test عالی است برای بررسی این‌که آیا تغییری در رفتار کامپایلر ایجاد کرده‌اید که بخش بزرگی از اکوسیستم را تحت تأثیر قرار می‌دهد.
    • اگر diff مربوط به PR شما بزرگ باشد یا بازبین مشغول باشد، PR شما ممکن است با PRهای دیگری که زودتر ادغام می‌شوند تعارض merge پیدا کند. باید این تعارض‌های merge را با رویه‌های معمول git برطرف کنید.

    r+

    پس از آن‌که کسی pull request شما را بازبینی کرد، یک یادداشت با r+ روی pull request می‌گذارد. چیزی شبیه این به نظر می‌رسد:

    @bors r+

    این به @bors، ربات یکپارچه‌سازی دوست‌داشتنی ما، می‌گوید که pull request شما تأیید شده است. سپس PR وارد صف ادغام می‌شود، جایی که @bors همه‌ی آزمون‌ها را روی هر پلتفرمی که پشتیبانی می‌کنیم اجرا می‌کند.

    بسته به مقیاس تغییر، ممکن است شکل کمی متفاوتی از r+ ببینید:

    @bors r+ rollup

    rollup اضافی به @bors می‌گوید که این تغییر باید همیشه «rolled up» شود. تغییرات rolled up همراه با PRهای دیگر آزمایش و ادغام می‌شوند تا فرایند سریع‌تر شود. معمولاً فقط تغییرات کوچکی که انتظار می‌رود با یکدیگر تعارض نداشته باشند به‌عنوان «always roll up» علامت‌گذاری می‌شوند.

    صبور باشید؛ این کار ممکن است مدتی طول بکشد و صف گاهی می‌تواند طولانی باشد. همچنین توجه کنید که PRها هرگز به‌صورت دستی ادغام نمی‌شوند.

    اگر همه‌چیز خوب پیش برود، @bors کد شما را در main ادغام می‌کند و pull request را می‌بندد. کد شما در کامپایلر nightly بعدی خواهد بود :)

    پس از ادغام

    Backportها

    برای اقدامات بعدی، لطفاً مراقب PRای باشید که عنوانش با [beta] یا [stable] شروع می‌شود و PR مورد نظر را backport می‌کند. وقتی آن ادغام شد، می‌توان issue مربوطه را بست. نظر بستن باید همه‌ی PRهایی را که دخیل بوده‌اند ذکر کند. اگر مجوز بستن issue را ندارید، لطفاً روی PR اصلی نظری بگذارید و از بازبین بخواهید آن را برای شما ببندد.

    برگرداندن (revert) یک PR

    «Reverts» را در Forge ببینید.

    اگر PR آن‌قدر بزرگ باشد که برگرداندنش دشوار است، مشکلی ندارد که به‌سادگی trigger مربوط به کد مشکل‌دار را غیرفعال کنیم، همان‌طور که در #128271 نشان داده شده است. برای بهینه‌سازی‌های MIR، می‌توانیم از گزینه‌ی -Zunsound-mir-opt هم برای محدود کردن mir-opt استفاده کنیم، همان‌طور که در #132356 نشان داده شده است.
