راهنمای توسعهٔ rustcrustc Development Guide

    استفاده از مخزن‌های خارجی

    مخزن git با نام rust-lang/rust به چند مخزن دیگر در سازمان rust-lang وابسته است. سه روش اصلی برای استفاده از وابستگی‌ها وجود دارد:

    1. به‌عنوان وابستگی Cargo از طریق crates.io (برای مثال rustc-rayon)
    2. به‌عنوان subtree در git (برای مثال clippy) یا josh (برای مثال miri)
    3. به‌عنوان زیرماژول git (برای مثال cargo)

    به‌طور کلی:

    • از crates.io برای کتابخانه‌هایی استفاده کنید که می‌توانند برای دیگران در اکوسیستم مفید باشند
    • از subtreeها برای ابزارهایی استفاده کنید که به درونیات کامپایلر وابسته‌اند و در صورت تغییرهای ناسازگار باید به‌روزرسانی شوند
    • از زیرماژول‌ها برای ابزارهایی استفاده کنید که از کامپایلر مستقل هستند

    وابستگی‌های خارجی (subtreeها)

    پروژه‌های خارجی زیر با نوعی از subtree مدیریت می‌شوند:

    • clippy
    • miri
    • portable-simd
    • rustfmt
    • rust-analyzer
    • rustc_codegen_cranelift
    • rustc_codegen_gcc
    • rustc-dev-guide
    • compiler-builtins
    • stdarch

    برخلاف وابستگی‌های submodule (بعداً درباره‌ی آن‌ها توضیح داده می‌شود)، وابستگی‌های subtree فقط فایل‌ها و پوشه‌های معمولی هستند که می‌توان آن‌ها را درون همین مخزن به‌روزرسانی کرد. با این حال، در صورت امکان، بهبودها، رفع باگ‌ها و موارد مشابه که مخصوص این ابزارها هستند باید مستقیماً در مخزن‌های بالادستی خودشان ثبت شوند. استثنا این است که وقتی برای پیاده‌سازی یک قابلیت یا آزمون جدید در ابزار به تغییرهایی در rustc نیاز باشد، این کار باید در قالب یک PR جامع در rustc انجام شود.

    به همین ترتیب، اگر تغییرهای rustc شما ساخت یکی از وابستگی‌های subtree را خراب کند، باید اصلاح‌های مربوط به آن را هم در همان PR مربوط به rustc بگنجانید.

    وابستگی‌های subtree در حال حاضر با دو رویکرد متفاوت مدیریت می‌شوند:

    • با استفاده از git subtree
      • clippy (راهنمای همگام‌سازی)
      • portable-simd (اسکریپت همگام‌سازی)
      • rustc_codegen_gcc (راهنمای همگام‌سازی)
    • با استفاده از ابزار josh
      • miri
      • rust-analyzer
      • rustc_codegen_cranelift
      • rustc-dev-guide
      • rustfmt
      • compiler-builtins
      • stdarch

    subtreeهای Josh

    ابزار josh جایگزینی برای subtreeهای git است که تاریخچه‌ی git را به شیوه‌ای متفاوت مدیریت می‌کند و برای مخزن‌های بزرگ‌تر بهتر مقیاس می‌پذیرد. کار با josh به ابزار مخصوص نیاز دارد. ما یک ابزار کمکی به نام rustc-josh-sync برای کمک به همگام‌سازی فراهم کرده‌ایم که در ادامه توضیح داده شده است.

    همگام‌سازی یک subtree از نوع Josh

    برای به‌روزرسانی subtreeهای Josh از ابزار اختصاصی rustc-josh-sync استفاده می‌کنیم. دستورهای زیر برای همه‌ی subtreeهای Josh ما قابل استفاده‌اند، هرچند توجه کنید که miri هنگام pull به انجام مراحل اضافی نیاز دارد.

    می‌توانید این ابزار را با دستور زیر نصب کنید:

    cargo install --locked --git https://github.com/rust-lang/josh-sync

    هم pullها (همگام‌سازی تغییرها از rust-lang/rust به subtree) و هم pushها (همگام‌سازی تغییرها از subtree به rust-lang/rust) از داخل مخزن subtree انجام می‌شوند (پس ابتدا در ترمینال به پوشه‌ی checkout آن مخزن بروید).

    انجام pull

    1. یک شاخه‌ی جدید checkout کنید که برای ساخت PR به subtree استفاده خواهد شد
    2. دستور pull را اجرا کنید rustc-josh-sync pull 
      rustc-josh-sync pull
    3. شاخه را به fork خود push کنید و یک PR به مخزن subtree بسازید
      • اگر ابزار خط فرمان gh نصب باشد، rustc-josh-sync می‌تواند PR را برای شما بسازد.

    انجام push

    نکته: پیش از ادامه، راهنمایی‌های مربوط به Git را در README مربوط به josh-sync ببینید.

    1. دستور push را اجرا کنید تا شاخه‌ای با نام <branch-name> در یک fork از rustc زیر حساب <gh-username> ساخته شود rustc-josh-sync push <branch-name> <gh-username> 
      rustc-josh-sync push <branch-name> <gh-username>
    2. از <branch-name> یک PR به rust-lang/rust بسازید

    ساخت یک وابستگی جدید subtree از نوع Josh

    اگر می‌خواهید یک وابستگی مخزنی را از git subtree یا git submodule به josh منتقل کنید، می‌توانید این راهنما را ببینید.

    همگام‌سازی یک subtree از نوع git

    به‌طور دوره‌ای باید تغییرهایی که در وابستگی‌های مبتنی بر subtree ایجاد شده‌اند بین این مخزن و مخزن‌های بالادستی ابزارها همگام شوند.

    همگام‌سازی subtreeها معمولاً توسط نگهدارندگان هر ابزار انجام می‌شود. سایر کاربران نیز می‌توانند PRهای همگام‌سازی ارسال کنند، اما برای این کار لازم است نصب git محلی خود را تغییر دهید و مجموعه‌ای دقیق از دستورالعمل‌ها را دنبال کنید. این دستورالعمل‌ها، همراه با چند نکته و ترفند مفید، در بخش همگام‌سازی تغییرهای subtree در راهنمای مشارکت Clippy مستند شده‌اند. این دستورالعمل‌ها برای هر ابزار مبتنی بر subtree قابل استفاده‌اند، فقط حتماً از پوشه‌ی subtree و مخزن راه دور متناظر درست استفاده کنید.

    فرایند همگام‌سازی در دو جهت انجام می‌شود: subtree push و subtree pull.

    subtree push همه‌ی تغییرهایی را که روی نسخه‌ی موجود در این مخزن رخ داده‌اند می‌گیرد و روی مخزن راه دور کامیت‌هایی منطبق با تغییرهای محلی می‌سازد. هر کامیت محلی که به subtree دست زده باشد یک کامیت در مخزن راه دور ایجاد می‌کند، اما آن کامیت طوری تغییر می‌یابد که فایل‌ها را از پوشه‌ی مشخص‌شده به ریشه‌ی مخزن ابزار منتقل کند.

    subtree pull همه‌ی تغییرهای مخزن ابزار را از آخرین subtree pull به بعد می‌گیرد و این کامیت‌ها را به مخزن rustc اضافه می‌کند، همراه با یک کامیت merge که تغییرهای ابزار را به پوشه‌ی مشخص‌شده در مخزن Rust منتقل می‌کند.

    توصیه می‌شود همیشه ابتدا push انجام دهید و آن را در شاخه‌ی پیش‌فرض ابزار merge کنید. سپس وقتی pull انجام می‌دهید، merge بدون تداخل انجام می‌شود. اگرچه حل تداخل‌ها هنگام pull قطعاً ممکن است، اگر PR شما به‌اندازه‌ی کافی سریع merge نشود و تداخل‌های جدیدی پیش بیاید، شاید مجبور شوید حل تداخل را دوباره انجام دهید. تلاش نکنید نتیجه‌ی git subtree pull را rebase کنید؛ rebase کردن کامیت‌های merge به‌طور کلی ایده‌ی بدی است.

    همیشه باید پیشوند -P را برای پوشه‌ی subtree و مخزن راه دور متناظر مشخص کنید. اگر پوشه یا مخزن اشتباهی مشخص کنید، با merge‌های بسیار «جالبی» روبه‌رو می‌شوید که می‌خواهند پوشه‌ی اشتباه را به مخزن راه دور اشتباه push کنند. خوشبختانه می‌توانید بدون هیچ عواقبی این کار را متوقف کنید، به این صورت که یا کامیت‌های pull‌شده در rustc یا شاخه‌ی push‌شده در مخزن راه دور را دور بیندازید و دوباره تلاش کنید. معمولاً به‌راحتی می‌توان فهمید که چنین اتفاقی افتاده است، چون ناگهان هزاران کامیت می‌خواهند همگام شوند.

    ساخت یک وابستگی جدید subtree

    اگر می‌خواهید از یک مخزن موجود یک وابستگی subtree جدید بسازید، (از پوشه‌ی ریشه‌ی همین مخزن!) دستور زیر را اجرا کنید

    git subtree add -P src/tools/clippy https://github.com/rust-lang/rust-clippy.git master

    این کار یک کامیت جدید می‌سازد که به هیچ عنوان نباید آن را rebase کنید! اگر نیاز به rebase دارید، کامیت را حذف کنید و عملیات را دوباره انجام دهید.

    حالا کار تمام است؛ پوشه‌ی src/tools/clippy طوری رفتار می‌کند که گویی Clippy بخشی از تک‌مخزن rustc است، بنابراین جز شما (یا دیگرانی که subtreeها را همگام می‌کنند) هیچ‌کس واقعاً نیازی به استفاده از git subtree ندارد.

    وابستگی‌های خارجی (زیرماژول‌ها)

    ساخت Rust همچنین از مخزن‌های git خارجی‌ای استفاده می‌کند که با زیرماژول‌های git دنبال می‌شوند. فهرست کامل را می‌توانید در فایل .gitmodules ببینید. برخی از این پروژه‌ها الزامی‌اند (مثل stdarch برای کتابخانه‌ی استاندارد) و برخی اختیاری (مثل src/doc/book).

    استفاده از زیرماژول‌ها در فصل استفاده از Git بیشتر بحث شده است.

    برخی از زیرماژول‌ها مجازند در وضعیت «خراب» باشند، یعنی یا ساخته نمی‌شوند یا آزمون‌هایشان قبول نمی‌شوند، مثلاً کتاب‌های مستندات مانند The Rust Reference. نگهدارندگان این پروژه‌ها وقتی پروژه در وضعیت خراب قرار بگیرد مطلع می‌شوند و باید هرچه سریع‌تر آن را اصلاح کنند. وضعیت فعلی در وب‌سایت toolstate دنبال می‌شود. اطلاعات بیشتر را می‌توانید در فصل Toolstate در Forge ببینید. در عمل، بسیار نادر است که مستندات toolstate خراب داشته باشند.

    خرابی در کانال‌های beta و stable مجاز نیست و باید پیش از merge شدن PR برطرف شود. همچنین مجاز نیست که در هفته‌ی منتهی به برش beta، این پروژه‌ها روی main خراب باشند.
