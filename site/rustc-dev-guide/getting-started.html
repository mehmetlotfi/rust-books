راهنمای توسعهٔ rustcrustc Development Guide

    شروع کار

    از علاقه‌ی شما به مشارکت در Rust سپاسگزاریم! راه‌های زیادی برای مشارکت وجود دارد و ما قدردان همه‌ی آن‌ها هستیم.

    برای اطلاعات عمومی درباره‌ی چگونگی مشارکت در Rust، Forge را ببینید. بقیه‌ی این بخش مخصوص مشارکت در کامپایلر است.

    این مستندات قصد ندارد جامع باشد؛ هدف آن راهنمای سریعی برای مفیدترین موارد است. برای اطلاعات بیشتر، نحوه‌ی ساخت و اجرای کامپایلر را ببینید.

    یافتن کمک

    همچنین “پرسیدن سؤال” را ببینید.

    متخصصان

    همه‌ی اعضای t-compiler در همه‌ی بخش‌های rustc متخصص نیستند؛ این پروژه نسبتاً بزرگ است. برای یافتن این‌که چه کسانی ممکن است در بخش‌های مختلف کامپایلر تخصص داشته باشند، گروه‌های assign در triagebot را بررسی کنید. این‌ها بخش‌هایی هستند که در فایل triagebot.toml با [assign* شروع می‌شوند. اما حتی اگر نمی‌توانید بفهمید باید چه کسی را صدا بزنید، باز هم راحت سؤال بپرسید.

    راه دیگر برای یافتن متخصصان یک بخش مشخص از کامپایلر، این است که ببینید چه کسانی اخیراً کامیت زده‌اند. برای مثال، برای یافتن افرادی که از انتشار 1.68.2 به بعد روی name resolution کار کرده‌اند، می‌توانید git shortlog -n 1.68.2.. compiler/rustc_resolve/ را اجرا کنید. کامیت‌هایی را که با “Rollup merge” شروع می‌شوند یا توسط @bors هستند نادیده بگیرید (برای اطلاعات بیشتر درباره‌ی این کامیت‌ها روال‌های مشارکت در CI را ببینید).

    روی چه چیزی کار کنم؟

    تک‌مخزن rust بسیار بزرگ است و ممکن است دشوار باشد بدانید کدام بخش‌ها به کمک نیاز دارند یا نقطه‌ی شروع خوبی برای مبتدی‌ها هستند. در اینجا چند نقطه‌ی شروع پیشنهادی آمده است.

    issueهای آسان یا دارای مربی

    اگر دنبال جایی برای شروع هستید، جست‌وجوی issue زیر را ببینید. برای توضیح این برچسب‌ها Triage را ببینید. همچنین می‌توانید جست‌وجو را به حوزه‌هایی که به آن‌ها علاقه دارید محدود کنید. برای مثال:

    • label:T-compiler فقط issueهای مربوط به کامپایلر را نشان می‌دهد
    • label:A-diagnostics فقط issueهای مربوط به تشخیص‌ها را نشان می‌دهد

    همه‌ی کارهای مهم یا مناسب مبتدی‌ها برچسب issue ندارند. برای یافتن کارهای بدون برچسب، در ادامه را ببینید.

    کار تکرارشونده

    برخی کارها آن‌قدر بزرگ‌اند که یک نفر نمی‌تواند به‌تنهایی انجام‌شان دهد. در این موارد معمولاً «issueهای پیگیری» (Tracking issues) برای هماهنگی کار بین مشارکت‌کنندگان وجود دارد. در اینجا چند issue پیگیری نمونه آمده که می‌توان بدون صرف زمان زیاد کاری از آن‌ها برداشت:

    • موارد کار تکرارشونده را اینجا اضافه کنید.

    اگر کار تکرارشونده‌ی بیشتری پیدا کردید، با خیال راحت آن را اینجا اضافه کنید!

    issueهای تشخیص‌ها

    بسیاری از issueهای تشخیص‌ها مستقل هستند و به دانش پیش‌زمینه‌ی دقیق از کامپایلر نیاز ندارند. فهرست issueهای تشخیص‌ها را می‌توانید اینجا ببینید.

    برداشتن pull requestهای رهاشده

    گاهی مشارکت‌کنندگان یک pull request می‌فرستند، اما بعداً متوجه می‌شوند که زمان کافی برای کار روی آن ندارند، یا دیگر به آن علاقه‌ای ندارند. چنین PRهایی اغلب در نهایت بسته می‌شوند و برچسب S-inactive می‌گیرند. می‌توانید برخی از این PRها را بررسی کنید و کار را ادامه دهید. فهرست این PRها را می‌توانید اینجا ببینید.

    اگر در این میان PR به شکل دیگری پیاده‌سازی شده باشد، برچسب S-inactive باید از آن برداشته شود. در غیر این صورت، اگر به نظر می‌رسد هنوز به آن تغییر علاقه وجود دارد، می‌توانید pull request را روی آخرین شاخه‌ی main rebase کنید و یک pull request جدید بفرستید و کار روی آن قابلیت را ادامه دهید.

    نوشتن آزمون

    issueهایی که حل شده‌اند اما آزمون پسرفت ندارند با برچسب E-needs-test علامت‌گذاری می‌شوند. نوشتن آزمون واحد کاری کم‌ریسک و کم‌اولویت‌تر است که فرصتی عالی به مشارکت‌کنندگان جدید می‌دهد تا با زیرساخت آزمون و گردش‌کار مشارکت آشنا شوند. فهرست issueهایی که نیاز به آزمون دارند را می‌توانید اینجا ببینید.

    رفع باگ یا تغییرهای «عادی» کد

    برای بیشتر PRها هیچ روال ویژه‌ای لازم نیست. فقط کافی است یک PR باز کنید و آن بازبینی، تأیید و merge خواهد شد. این شامل بیشتر رفع باگ‌ها، بازآرایی‌ها و سایر تغییرهایی است که برای کاربر نامرئی‌اند. چند بخش بعدی درباره‌ی استثناهای این قاعده صحبت می‌کنند.

    همچنین توجه کنید که باز کردن PRهای WIP یا Draft PR در GitHub کاملاً پذیرفتنی است. برخی افراد این کار را ترجیح می‌دهند تا در طول مسیر بازخورد بگیرند یا کد خود را با یک همکار به اشتراک بگذارند. برخی دیگر این کار را می‌کنند تا از CI برای ساخت و آزمون PR خود استفاده کنند (مثلاً هنگام توسعه روی یک دستگاه کند).

    Pull requestها

    Pull requestها (یا به اختصار PRها) سازوکار اصلی ما برای تغییر Rust هستند. خود GitHub مستندات عالی درباره‌ی استفاده از قابلیت Pull Request دارد. ما از مدل «fork و pull» استفاده می‌کنیم، که در آن مشارکت‌کنندگان تغییرها را به fork شخصی خود push می‌کنند و pull request می‌سازند تا آن تغییرها را به مخزن منبع بیاورند. ما فصلی درباره‌ی نحوه‌ی استفاده از Git هنگام مشارکت در Rust داریم.

    توصیه برای تغییرهای بالقوه بزرگ، پیچیده، فراگیر و/یا بسیار تخصصی

    بازبین‌های کامپایلر که به‌صورت نوبتی کار می‌کنند معمولاً هر یک بخش‌هایی از کامپایلر را که خوب می‌شناسند دارند، اما بخش‌هایی هم هستند که با آن‌ها چندان آشنا نیستند. اگر PR شما شامل تغییرهایی باشد که بزرگ، پیچیده، فراگیر و/یا بسیار تخصصی‌اند، پیدا کردن بازبین مناسبی که با بازبینی همه‌ی تغییرهای چنین PRی راحت باشد بسیار دشوار می‌شود. این موضوع زمانی هم صادق است که تغییرها نه‌تنها مخصوص کامپایلر باشند بلکه شامل تغییرهایی باشند که در حوزه‌ی اختیار بازبین‌های تیم‌های دیگر، مانند تیم کتابخانه‌ی استاندارد، قرار می‌گیرند. یک ربات وجود دارد که تیم‌های مربوطه را مطلع می‌کند و افرادی را که بر اساس فایل‌های تغییریافته هشدارهای مشخصی تنظیم کرده‌اند صدا می‌زند.

    پیش از اعمال چنین تغییرهایی، شدیداً توصیه می‌شود تغییرهای پیشنهادی خود را از قبل با تیم کامپایلر مطرح کنید (و با سایر تیم‌هایی که تغییرها به تأیید آن‌ها نیاز دارند)، و با تیم کامپایلر کار کنید تا ببینیم آیا می‌توانیم به شما کمک کنیم یک PR بزرگ و بالقوه غیرقابل بازبینی را به مجموعه‌ای از PRهای کوچک‌تر و جداگانه قابل بازبینی تقسیم کنید.

    می‌توانید با ایجاد یک thread در #t-compiler در Zulip با تیم کامپایلر ارتباط برقرار کنید تا تغییرهای پیشنهادی خود را مطرح کنید.

    ارتباط با تیم کامپایلر از پیش از چند جهت کمک می‌کند:

    1. احتمال بازبینی به‌موقع PRهای شما را بالا می‌برد.
      • می‌توانیم پیش از آن‌که PRهای واقعی را باز کنید به شما کمک کنیم بازبین‌های مناسب را شناسایی کنید، یا مشاوران و رابط‌هایی پیدا کنیم که در مسیر روال‌های تغییر راهنمایی‌تان کنند، یا در صورت لزوم در اجرای try-jobها، اجرای perf و اجرای crater کمک کنیم.
    2. به تیم کامپایلر کمک می‌کند تغییرهای شما را دنبال کند.
    3. تیم کامپایلر می‌تواند زود و مکرر «بررسی حس و حال» (vibe check) تغییرهای شما را انجام دهد تا ببیند آیا جهت تغییرها با آنچه تیم کامپایلر ترجیح می‌دهد ببیند هم‌خوان است یا نه.
    4. از موقعیت‌هایی جلوگیری می‌کند که ممکن است زمان و تلاش قابل‌توجهی را روی تغییرهای بزرگی صرف کرده باشید که تیم کامپایلر شاید حاضر به پذیرش آن‌ها نباشد، یا خیلی دیر بفهمید که تغییرها در جهتی هستند که تیم کامپایلر با آن مخالف است.
