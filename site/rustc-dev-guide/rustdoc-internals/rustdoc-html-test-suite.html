راهنمای توسعهٔ rustcrustc Development Guide

    مجموعهٔ تست rustdoc-html

    این صفحه دربارهٔ مجموعهٔ تست rustdoc-html است که برای تست خروجی HTML در rustdoc به‌کار می‌رود. برای مجموعه‌های تست مخصوص rustdoc دیگر، مجموعه‌های تست Rustdoc را ببینید.

    هر فایل تست در این مجموعه صرفاً یک فایل منبع Rust با نام file.rs است که با اصطلاحاً directiveهایی درون کامنت‌های عادی کد Rust پر شده است. این‌ها دو نوع‌اند: Compiletest و HtmlDocCk.

    برای آشنایی بیشتر با اولی، directiveهای Compiletest را بخوانید. برای دومی، ادامه دهید.

    در داخل، compiletest اسکریپت کمکی بررسی htmldocck.py را فراخوانی می‌کند.

    HtmlDocCk Directives

    directiveهای HtmlDocCk گزاره‌هایی (assertion) هستند که روی HTML تولیدشده قید می‌گذارند. شبیه directiveهای compiletest هستند چون به شکل کامنت //@ می‌آیند اما در نهایت کاملاً متمایزند و توسط برنامه‌های متفاوتی پردازش می‌شوند.

    XPath برای کوئری‌گرفتن از بخش‌های درخت سند HTML به‌کار می‌رود.

    Introductory example:

    //@ has file/type.Alias.html
//@ has - '//*[@class="rust item-decl"]//code' 'type Alias = Option<i32>;'
pub type Alias = Option<i32>;

    اینجا بررسی می‌کنیم مستندات تولیدشده برای crate با نام file صفحه‌ای برای نوع alias عمومی Alias دارد که بلوک کدِ بالای آن شامل رندر مورد انتظار آیتم است. //*[@class="rust item-decl"]//code یک عبارت XPath است.

    طبق قرارداد، این directiveها را درست بالای چیزی که قرار است تست کنند می‌گذارید. از نظر فنی لازم نیست چنین باشند چون HtmlDocCk فقط به دنبال directiveهاست.

    همهٔ directiveها آرگومان PATH می‌گیرند. برای پرهیز از تکرار، می‌توان - را به آن داد تا آرگومان PATH قبلی دوباره استفاده شود. چون مسیر شامل نام crate است، طبق قرارداد attribute با نام #![crate_name = "foo"] به ریشهٔ crate افزوده می‌شود تا مسیر حاصل کوتاه شود.

    همهٔ آرگومان‌ها شکل رشته‌های نقل‌قول‌دار به سبک shell (تک یا دوتایی) دارند، به‌جز COUNT و شکل ویژهٔ - برای PATH.

    همهٔ directiveها (به‌جز files) را می‌توان با گذاشتن ! جلوی نامشان نفی کرد. پیش از افزودن directiveهای نفی‌شده، لطفاً نکات احتیاطی آن‌ها را بخوانید.

    مشابه دستورهای shell، directiveها می‌توانند چند خط ادامه یابند اگر آخرین نویسه‌شان \ باشد. در این حالت، ابتدای خط بعد باید // باشد، بدون @.

    مشابه directiveهای compiletest، علاوه بر فاصله می‌توانید از دونقطه : هم برای جداکردن نام directive و آرگومان‌ها استفاده کنید، اما برای directiveهای HtmlDocCk فاصله ترجیح داده می‌شود.

    از رشتهٔ ویژهٔ {{channel}} در XPathها، آرگومان‌های PATTERN و فایل‌های snapshot استفاده کنید اگر می‌خواهید به نشانی https://doc.rust-lang.org/CHANNEL ارجاع دهید که CHANNEL کانال انتشار فعلی است (مثلاً stable یا nightly).

    در ادامه همهٔ directiveهای ممکن فهرست شده‌اند:

    has

    Usage 1: //@ has PATH

    بررسی می‌کند فایل داده‌شده با PATH وجود دارد.

    Usage 2: //@ has PATH XPATH PATTERN

    بررسی می‌کند متن هر عنصر / attribute / متنی که با XPATH در فایل نرمال‌سازی‌شدهٔ فاصله1 داده‌شده با PATH انتخاب می‌شود با رشتهٔ PATTERN (که آن هم فاصله‌نرمال‌سازی‌شده است) مطابقت دارد.

    نکته: اگر می‌خواهید از نرمال‌سازی فاصله پرهیز کنید و/یا با regex تطبیق دهید، به‌جای آن از matches استفاده کنید.

    hasraw

    Usage: //@ hasraw PATH PATTERN

    بررسی می‌کند محتوای فایل نرمال‌سازی‌شدهٔ فاصله1 داده‌شده با PATH با رشتهٔ PATTERN (که آن هم فاصله‌نرمال‌سازی‌شده است) مطابقت دارد.

    نکته: اگر می‌خواهید از نرمال‌سازی فاصله پرهیز کنید و/یا با regex تطبیق دهید، به‌جای آن از matchesraw استفاده کنید.

    matches

    Usage: //@ matches PATH XPATH PATTERN

    بررسی می‌کند متن هر عنصر / attribute / متنی که با XPATH در فایل داده‌شده با PATH انتخاب می‌شود با regex به سبک Python2 یعنی PATTERN مطابقت دارد.

    matchesraw

    Usage: //@ matchesraw PATH PATTERN

    بررسی می‌کند محتوای فایل داده‌شده با PATH با regex به سبک Python2 یعنی PATTERN مطابقت دارد.

    count

    Usage: //@ count PATH XPATH COUNT

    بررسی می‌کند دقیقاً COUNT تطابق برای XPATH درون فایل داده‌شده با PATH وجود دارد.

    snapshot

    Usage: //@ snapshot NAME PATH XPATH

    بررسی می‌کند عنصر / متنی که با XPATH در فایل داده‌شده با PATH انتخاب می‌شود با زیردرخت یا متن از پیش ضبط‌شده («snapshot») در فایل FILE_STEM.NAME.html مطابقت دارد که FILE_STEM نام پایهٔ فایل تست است.

    گزینهٔ --bless را به compiletest بدهید تا زیردرخت/متن فعلی به‌عنوان مورد انتظار پذیرفته شود. این فایل یادشده را بازنویسی می‌کند (یا اگر وجود نداشته باشد می‌سازد). نشانی وابسته به کانال https://doc.rust-lang.org/CHANNEL را به‌طور خودکار به رشتهٔ ویژهٔ {{channel}} نرمال‌سازی می‌کند.

    has-dir

    Usage: //@ has-dir PATH

    وجود پوشهٔ داده‌شده با PATH را بررسی می‌کند.

    files

    Usage: //@ files PATH ENTRIES

    بررسی می‌کند پوشهٔ داده‌شده با PATH دقیقاً شامل ENTRIES است. ENTRIES فهرستی شبیه Python از رشته‌ها درون یک رشتهٔ نقل‌قول‌دار است.

    Example: //@ files "foo/bar" '["index.html", "sidebar-items.js"]'

    Compiletest Directives (Brief)

    همان‌طور که در مقدمه گفته شد، به directiveهای compiletest هم دسترسی دارید. مهم‌تر از همه، به شما اجازه می‌دهند crateهای کمکی ثبت کنید و پرچم‌هایی به فایل دودویی rustdoc در حال تست بدهید. اگر هنوز چیزی دربارهٔ آن‌ها نمی‌دانید قویاً توصیه می‌شود آن فصل را بخوانید.

    در ادامه چند جزئیات آمده که به‌طور مشخص به این مجموعهٔ تست مربوط‌اند:

    • هرچند می‌توانید برای دادن پرچم به rustdoc هم از //@ compile-flags و هم از //@ doc-flags استفاده کنید، برای نشان‌دادن قصد، دومی را ترجیح دهید. اولی برای rustc است.
    • //@ build-aux-docs را به فایل تستی که crateهای کمکی دارد اضافه کنید تا علاوه بر کامپایل کمکی‌ها با rustc، آن‌ها را با rustdoc هم مستند کند.

    Caveats

    تست‌کردن نبود یک عنصر یا تکه‌ای از متن بسیار شکننده است و برای آینده چندان مناسب نیست.

    غیرمعمول نیست که شکل درخت سند HTML تولیدشده گاه‌به‌گاه تغییر کند. این مثلاً شامل تغییر نام کلاس‌های CSS است.

    هر وقت این رخ دهد، بررسی‌های مثبت یا همچنان با عنصر / attribute / متن مورد نظر مطابقت می‌کنند (اگر عبارت XPathشان به‌اندازهٔ کافی عمومی / آزاد باشد) و در نتیجه همچنان چیز درست را تست می‌کنند یا مطابقت نمی‌کنند که در آن صورت شکست می‌خورند و نویسندهٔ تغییر را مجبور به نگاه‌کردن به آن‌ها می‌کنند.

    این را با بررسی‌های منفی (مثلاً //@ !has PATH XPATH PATTERN) مقایسه کنید که اگر عبارت XPathشان «دیگر» مطابقت نکند شکست نمی‌خورند. نویسنده‌ای که «شکل» را تغییر داده بنابراین مطلع نمی‌شود و در نتیجه شخص دیگری می‌تواند ناخواسته PATTERN را دوباره به مستندات تولیدشده وارد کند بدون اینکه بررسی منفی اصلی شکست بخورد.

    نکته: لطفاً از بررسی‌های نفی‌شده پرهیز کنید!

    نکته: اگر نمی‌توانید از آن پرهیز کنید، لطفاً همیشه آن را با بررسی مثبت مشابهی در مجاورت نزدیک جفت کنید، تا افرادی که «شکل» را تغییر می‌دهند فرصت داشته باشند متوجه شوند و بررسی نفی‌شده را به‌روز کنند!

    Limitations

    HtmlDocCk از پیاده‌سازی XPath در کتابخانهٔ استاندارد Python استفاده می‌کند. این چند محدودیت ایجاد می‌کند:

    • همهٔ آرگومان‌های XPATH به‌دلیل نقص پیاده‌سازی باید با // شروع شوند.
    • بسیاری از قابلیت‌های XPath (توابع، محورها (axis) و غیره) پشتیبانی نمی‌شوند.
    • فقط HTML درست‌ساختار (well-formed) قابل‌تجزیه است (امیدواریم rustdoc تگ‌های ناهمخوان خروجی ندهد).

    علاوه بر این، revisionهای compiletest پشتیبانی نمی‌شوند.
