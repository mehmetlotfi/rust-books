    Panic‌کردن در Rust

    گام ۱: فراخوانی ماکروی panic!.

    در واقع دو ماکروی panic هست - یکی در core و یکی در std تعریف شده. دلیلش این است که کد درون core هم می‌تواند panic کند. core پیش از std ساخته می‌شود، اما می‌خواهیم panicها در زمان اجرا از همان ماشین‌آلات استفاده کنند، چه از core بیایند چه از std.

    تعریف panic! در core

    ماکروی panic! در core در نهایت فراخوانی زیر را انجام می‌دهد (در library/core/src/panicking.rs):

    // NOTE This function never crosses the FFI boundary; it's a Rust-to-Rust call
extern "Rust" {
    #[lang = "panic_impl"]
    fn panic_impl(pi: &PanicInfo<'_>) -> !;
}

let pi = PanicInfo::new(
    &fmt,
    Location::caller(),
    /* can_unwind */ true,
    /* force_no_backtrace */ false,
);
unsafe { panic_impl(&pi) }

    حل واقعی این از چند لایهٔ indirection می‌گذرد:

    1. در compiler/rustc_hir/src/weak_lang_items.rs، panic_impl به‌صورت «weak lang item» با نماد rust_begin_unwind اعلان شده است. این در rustc_hir_analysis/src/collect.rs برای تنظیم نام نماد واقعی به rust_begin_unwind به‌کار می‌رود.

      توجه کنید panic_impl در بلوک extern "Rust" اعلان شده، یعنی core سعی می‌کند نماد خارجی‌ای به نام rust_begin_unwind را فراخوانی کند (که در زمان لینک حل می‌شود)

    2. در library/std/src/panicking.rs این تعریف را داریم:

    /// Entry point of panics from the core crate (`panic_impl` lang item).
#[cfg(not(any(test, doctest)))]
#[panic_handler]
pub fn panic_handler(info: &core::panic::PanicInfo<'_>) -> ! {
    ...
}

    attribute ویژهٔ panic_handler از طریق compiler/rustc_passes/src/lang_items.rs حل می‌شود. تابع extract_ast attribute با نام panic_handler را به lang item با نام panic_impl تبدیل می‌کند.

    اکنون lang item متناظر panic_handler را در std داریم. این تابع همان فرایند تعریف extern { fn panic_impl } در core را طی می‌کند و در نهایت نام نماد rust_begin_unwind می‌گیرد. در زمان لینک، ارجاع نماد در core به تعریف در std حل می‌شود (تابعی که در منبع Rust panic_handler نام دارد).

    بنابراین جریان کنترل در زمان اجرا از core به std منتقل می‌شود. این اجازه می‌دهد panicهای core از همان زیرساختی که panicهای دیگر استفاده می‌کنند بگذرند (hookهای panic، unwinding و غیره)

    پیاده‌سازی panic! در std

    اینجا جایی است که منطق واقعی مربوط به panic شروع می‌شود. در library/std/src/panicking.rs، کنترل به panic_with_hook می‌رسد. این متد مسئول فراخوانی hook سراسری panic و بررسی panicهای دوگانه است. در نهایت، __rust_start_panic را فراخوانی می‌کنیم که توسط runtime مربوط به panic ارائه می‌شود.

    فراخوانی __rust_start_panic بسیار عجیب است - به آن *mut &mut dyn PanicPayload داده می‌شود که به usize تبدیل شده است. بیایید این نوع را تجزیه کنیم:

    1. PanicPayload یک trait داخلی است. برای PanicPayload پیاده‌سازی شده است (wrapperی دور نوع payload داده‌شده توسط کاربر) و متدی دارد به نام fn take_box(&mut self) -> *mut (dyn Any + Send). این متد payload داده‌شده توسط کاربر (T: Any + Send) را می‌گیرد، آن را box می‌کند و box را به اشاره‌گر خام تبدیل می‌کند.

    2. وقتی __rust_start_panic را فراخوانی می‌کنیم، یک &mut dyn PanicPayload داریم. اما این یک اشاره‌گر چاق (fat pointer) است (دو برابر اندازهٔ usize). برای دادن آن به runtime مربوط به panic از مرز FFI، یک ارجاع تغییرپذیر به این ارجاع تغییرپذیر (&mut &mut dyn PanicPayload) می‌گیریم و به اشاره‌گر خام (*mut &mut dyn PanicPayload) تبدیل می‌کنیم. اشاره‌گر خام بیرونی اشاره‌گر باریک (thin) است، چون به نوع Sized (ارجاع تغییرپذیر) اشاره می‌کند. بنابراین می‌توانیم این اشاره‌گر باریک را به usize تبدیل کنیم، که برای دادن از مرز FFI مناسب است.

    در نهایت، __rust_start_panic را با این usize فراخوانی می‌کنیم. اکنون وارد runtime مربوط به panic شده‌ایم.

    گام ۲: runtime مربوط به panic

    Rust دو runtime برای panic فراهم می‌کند: panic_abort و panic_unwind. کاربر در زمان ساخت از طریق Cargo.toml بین آن‌ها انتخاب می‌کند

    panic_abort بسیار ساده است: پیاده‌سازی __rust_start_panic آن فقط abort می‌کند، همان‌طور که انتظار دارید.

    panic_unwind مورد جالب‌تر است.

    در پیاده‌سازی __rust_start_panic، usize را می‌گیریم، به *mut &mut dyn PanicPayload برمی‌گردانیم، dereference می‌کنیم و take_box را روی &mut dyn PanicPayload فراخوانی می‌کنیم. در این نقطه، اشاره‌گر خام به خود payload داریم (*mut (dyn Send + Any)): یعنی اشاره‌گر خام به مقدار واقعی‌ای که کاربر هنگام فراخوانی panic! داده است.

    در این نقطه کد مستقل از پلتفرم تمام می‌شود. اکنون به منطق unwinding مخصوص پلتفرم وارد می‌شویم (مثلاً unwind). این کد مسئول unwind کردن پشته است، اجرای هر «landing pad» مرتبط با هر فریم (فعلاً اجرای destructorها)، و انتقال کنترل به فریم catch_unwind.

    توجه کنید همهٔ panicها یا فرایند را abort می‌کنند یا توسط فراخوانی catch_unwind گرفته می‌شوند. به‌طور خاص، در سرویس runtime در std، فراخوانی تابع main داده‌شده توسط کاربر درون catch_unwind پیچیده شده است.
