    ADTها و آرگومان‌های جنریک

    اصطلاح ADT مخفف «نوع داده جبری» (Algebraic data type) است؛ در Rust به struct، enum یا union اشاره می‌کند.

    نمایش ADTها

    نوعی مانند MyStruct<u32> را در نظر بگیرید که در آن MyStruct این‌گونه تعریف شده است:

    struct MyStruct<T> { x: u8, y: T }

    نوع MyStruct<u32> نمونه‌ای از TyKind::Adt خواهد بود:

    Adt(&'tcx AdtDef, GenericArgs<'tcx>)
//  ------------  ---------------
//  (1)            (2)
//
// (1) represents the `MyStruct` part
// (2) represents the `<u32>`, or "substitutions" / generic arguments

    دو بخش وجود دارد:

    • AdtDef به struct/enum/union اشاره می‌کند، اما بدون مقادیر پارامترهای نوع آن. در مثال ما این همان بخش MyStruct بدون آرگومان u32 است. (توجه کنید که در HIR، structها، enumها و unionها به‌طور متفاوتی نمایش داده می‌شوند، اما در ty::Ty همه با TyKind::Adt نمایش داده می‌شوند.)
    • GenericArgs فهرستی از مقادیر است که قرار است به‌جای پارامترهای جنریک جایگزین شوند. در مثال ما با MyStruct<u32>، به فهرستی مانند [u32] می‌رسیم. کمی بعد بیشتر به جنریک‌ها و جایگزینی‌ها خواهیم پرداخت.

    AdtDef و DefId

    برای هر نوعی که در کد منبع تعریف شده است یک DefId یکتا وجود دارد (این فصل را ببینید). این شامل ADTها و جنریک‌ها هم می‌شود. در تعریف MyStruct<T> که در بالا آوردیم دو DefId وجود دارد: یکی برای MyStruct و یکی برای T. توجه کنید که کد بالا یک DefId جدید برای u32 تولید نمی‌کند، چون در آن کد تعریف نشده است (فقط به آن ارجاع داده شده).

    AdtDef کم‌وبیش یک پوشش (wrapper) دور DefId با کلی متد کمکی مفید است. اساساً میان AdtDef و DefId رابطهٔ یک‌به‌یک وجود دارد. می‌توانید AdtDef یک DefId را با query ‏tcx.adt_def(def_id) به دست آورید. همهٔ AdtDefها interned هستند، همان‌طور که طول عمر 'tcx نشان می‌دهد.

    پرسش: چرا «درون» AdtDef جایگزین نکنیم؟

    به یاد بیاورید که یک struct جنریک را با (AdtDef, args) نمایش می‌دهیم. پس چرا به این طرح زحمت می‌دهیم؟

    خب، راه دیگری که می‌توانستیم برای نمایش نوع‌ها انتخاب کنیم این بود که همیشه یک شکل جدید کاملاً جایگزین‌شده از AdtDef بسازیم که در آن همهٔ نوع‌ها از پیش جایگزین شده‌اند. این کار دردسر کمتری به نظر می‌رسد. با این حال، طرح (AdtDef, args) مزیت‌هایی نسبت به آن دارد.

    اول اینکه طرح (AdtDef, args) از نظر کارایی برتری دارد:

    struct MyStruct<T> {
  ... 100s of fields ...
}

// Want to do: MyStruct<A> ==> MyStruct<B>

    در مثالی مانند این، می‌توانیم MyStruct<A> را بسیار ارزان به MyStruct<B> (و همین‌طور ادامه) نمونه‌سازی کنیم، فقط با جایگزین کردن یک ارجاع A با B. اما اگر همهٔ فیلدها را زودهنگام نمونه‌سازی می‌کردیم، می‌توانست کار بسیار بیشتری باشد، چون ممکن بود مجبور شویم همهٔ فیلدهای AdtDef را مرور کنیم و نوع همهٔ آن‌ها را به‌روز کنیم.

    کمی عمیق‌تر، این با نوع‌های اسمی بودن structها در Rust مطابقت دارد — که یعنی آن‌ها با نام خود تعریف می‌شوند (و محتویاتشان سپس از تعریف آن نام اندیس‌گذاری می‌شود و «درون» خود نوع حمل نمی‌شود).

    نوع GenericArgs

    با داشتن یک نوع جنریک MyType<A, B, …>، باید فهرست آرگومان‌های جنریک MyType را ذخیره کنیم.

    در rustc این کار با GenericArgs انجام می‌شود. GenericArgs یک اشاره‌گر باریک به برشی از GenericArg است که فهرست آرگومان‌های جنریک یک آیتم جنریک را نمایش می‌دهد. برای مثال، با داشتن struct HashMap<K, V> که دو پارامتر نوع K و V دارد، GenericArgs مورد استفاده برای نمایش نوع HashMap<i32, u32> با &'tcx [tcx.types.i32, tcx.types.u32] نمایش داده می‌شود.

    GenericArg از نظر مفهومی یک enum با سه حالت است: یکی برای آرگومان‌های نوع، یکی برای آرگومان‌های ثابت و یکی برای آرگومان‌های طول عمر. در عمل این با GenericArgKind نمایش داده می‌شود و GenericArg نسخه‌ای کم‌حجم‌تر است که متدی برای تبدیل به GenericArgKind دارد.

    struct واقعی GenericArg نوع، طول عمر یا ثابت را به‌صورت یک اشاره‌گر interned ذخیره می‌کند و discriminant در ۲ بیت پایین ذخیره می‌شود. مگر اینکه به‌طور خاص روی پیاده‌سازی GenericArgs کار کنید، معمولاً نباید با GenericArg سروکار داشته باشید و به‌جای آن از انتزاع ایمن GenericArgKind استفاده کنید که از طریق متد GenericArg::unpack() به دست می‌آید.

    در برخی موارد ممکن است لازم باشد یک GenericArg بسازید؛ این کار از طریق Ty/Const/Region::into() یا GenericArgKind::pack ممکن است.

    // An example of unpacking and packing a generic argument.
fn deal_with_generic_arg<'tcx>(generic_arg: GenericArg<'tcx>) -> GenericArg<'tcx> {
    // Unpack a raw `GenericArg` to deal with it safely.
    let new_generic_arg: GenericArgKind<'tcx> = match generic_arg.unpack() {
        GenericArgKind::Type(ty) => { /* ... */ }
        GenericArgKind::Lifetime(lt) => { /* ... */ }
        GenericArgKind::Const(ct) => { /* ... */ }
    };
    // Pack the `GenericArgKind` to store it in a generic args list.
    new_generic_arg.pack()
}

    پس برای جمع‌بندی همهٔ این‌ها:

    struct MyStruct<T>(T);
type Foo = MyStruct<u32>

    برای MyStruct<U> که در نام مستعار نوع Foo نوشته شده است، آن را به این شکل نمایش می‌دهیم:

    • یک AdtDef (و DefId متناظر) برای MyStruct وجود خواهد داشت.
    • یک GenericArgs شامل فهرست [GenericArgKind::Type(Ty(u32))] وجود خواهد داشت
    • و در نهایت یک TyKind::Adt با AdtDef و GenericArgs فهرست‌شده در بالا.

    آرگومان‌های جنریک تودرتو

    struct MyStruct<T>(T);

impl<T> MyStruct<T> {
    fn func<T2, T3>() {}
}

fn main() {
    MyStruct::<u32>::func::<bool, char>();
}

    ساختار MyStruct::<u32>::func::<bool, char> با یک تاپل نمایش داده می‌شود: یک DefId که به func اشاره می‌کند، و سپس یک فهرست GenericArgs که همهٔ پارامترهای جنریک دربرگیرنده را «طی می‌کند» - در این مورد فهرست [u32, bool, char] خواهد بود.

    نوع ty::Generics (که توسط query ‏generics_of برگردانده می‌شود) اطلاعات اینکه یک سلسله‌مراتب تودرتو چگونه به یک فهرست مسطح می‌شود را دارد و به شما امکان می‌دهد بفهمید کدام اندیس در فهرست GenericArgs متناظر با کدام جنریک است. خط کلی نحوهٔ کار از بیرونی‌ترین به درونی‌ترین (در مثال T پیش از T2) و از چپ به راست (T2 پیش از T3) است، اما چند پیچیدگی وجود دارد:

    • صفت‌ها (traits) یک پارامتر جنریک ضمنی Self دارند که اولین (یعنی صفرمین) پارامتر جنریک است. توجه کنید که Self در همهٔ موقعیت‌ها به معنای یک پارامتر جنریک نیست؛ Res::SelfTyAlias و Res::SelfCtor را ببینید.
    • فقط پارامترهای جنریک early-bound شامل می‌شوند؛ جنریک‌های late-bound شامل نمی‌شوند.
    • … و موارد بیشتر…

    برای جزئیات دقیق نحوهٔ مسطح‌سازی، ty::Generics را ببینید.
