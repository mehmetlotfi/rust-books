    MIR (IR سطح میانی)

    MIR بازنمایی میانی سطح میانی (Mid-level Intermediate Representation) در Rust است. از HIR ساخته می‌شود. MIR در RFC 1211 معرفی شد. شکل به‌شدت ساده‌شده‌ای از Rust است که برای برخی بررسی‌های ایمنی حساس به جریان به‌کار می‌رود – به‌ویژه borrow checker! – و همچنین برای بهینه‌سازی و تولید کد.

    اگر مقدمهٔ بسیار سطح بالایی از MIR و برخی مفاهیم کامپایلری که به آن‌ها تکیه دارد (مثل گراف‌های جریان کنترل و desugaring) می‌خواهید، ممکن است پست وبلاگ rust-lang که MIR را معرفی کرد را دوست داشته باشید.

    مقدمه‌ای بر MIR

    MIR در ماژول compiler/rustc_middle/src/mir/ تعریف شده، اما بخش زیادی از کدی که آن را دستکاری می‌کند در compiler/rustc_mir_build، compiler/rustc_mir_transform و compiler/rustc_mir_dataflow است.

    برخی ویژگی‌های کلیدی MIR این‌هاست:

    • بر پایهٔ گراف جریان کنترل است.
    • عبارت‌های تو در تو ندارد.
    • همهٔ نوع‌ها در MIR کاملاً صریح‌اند.

    Key MIR vocabulary

    این بخش مفاهیم کلیدی MIR را معرفی می‌کند که در اینجا خلاصه شده‌اند:

    • Basic blocks: units of the control-flow graph, consisting of:
      • دستورها (statements): اعمالی با یک جانشین (successor)
      • پایان‌دهنده‌ها (terminators): اعمالی با بالقوه چند جانشین؛ همیشه در انتهای یک بلوک
      • (اگر با اصطلاح basic block آشنا نیستید، فصل پیش‌زمینه را ببینید)
    • Localها: مکان‌های حافظه که روی پشته تخصیص یافته‌اند (دست‌کم از نظر مفهومی)، مثل آرگومان‌های تابع، متغیرهای محلی و temporaryها. این‌ها با یک اندیس شناسایی می‌شوند که با زیرخط ابتدایی نوشته می‌شود، مثل _1. یک «local» ویژه (_0) هم برای ذخیرهٔ مقدار بازگشتی تخصیص یافته است.
    • Placeها: عبارت‌هایی که مکانی در حافظه را شناسایی می‌کنند، مثل _1 یا _1.f.
    • Rvalues: expressions that produce a value. The “R” stands for the fact that these are the “right-hand side” of an assignment.
      • Operandها: آرگومان‌های یک rvalue، که می‌توانند ثابت (مثل 22) یا place (مثل _1) باشند.

    می‌توانید با ترجمهٔ برنامه‌های ساده به MIR و خواندن خروجی pretty-print‌شده حسی از نحوهٔ ساخت MIR بگیرید. در واقع playground این را آسان می‌کند، چون دکمه‌ای به نام MIR دارد که MIR برنامهٔ شما را نشان می‌دهد. این برنامه را در play بگذارید (یا روی این پیوند کلیک کنید)، و سپس دکمهٔ «MIR» بالا را بزنید:

    fn main() {
    let mut vec = Vec::new();
    vec.push(1);
    vec.push(2);
}

    باید چیزی شبیه این ببینید:

    // WARNING: This output format is intended for human consumers only
// and is subject to change without notice. Knock yourself out.
fn main() -> () {
    ...
}

    این قالب MIR برای تابع main است. MIR نشان‌داده‌شده توسط پیوند بالا بهینه‌شده است. برخی دستورها مثل StorageLive در بهینه‌سازی حذف می‌شوند. این به این دلیل است که کامپایلر متوجه می‌شود مقدار هرگز در کد دسترسی نمی‌شود. می‌توانیم از rustc [filename].rs -Z mir-opt-level=0 --emit mir برای دیدن MIR بهینه‌نشده استفاده کنیم. این toolchain از نوع nightly لازم دارد.

    اعلان متغیرها. اگر کمی عمیق‌تر شویم، می‌بینیم با مجموعه‌ای از اعلان‌های متغیر شروع می‌شود. این‌طور به نظر می‌رسند:

    let mut _0: ();                      // return place
let mut _1: std::vec::Vec<i32>;      // in scope 0 at src/main.rs:2:9: 2:16
let mut _2: ();
let mut _3: &mut std::vec::Vec<i32>;
let mut _4: ();
let mut _5: &mut std::vec::Vec<i32>;

    می‌بینید متغیرها در MIR نام ندارند، اندیس دارند، مثل _0 یا _1. همچنین متغیرهای کاربر (مثلاً _1) را با مقادیر موقت (مثلاً _2 یا _3) در هم می‌آمیزیم. می‌توانید متغیرهای تعریف‌شده توسط کاربر را از بقیه تشخیص دهید چون debuginfo به آن‌ها متصل است (در ادامه ببینید).

    debuginfo متغیر کاربر. زیر اعلان‌های متغیر، تنها اشاره‌ای را می‌یابیم که _1 متغیر کاربر است:

    scope 1 {
    debug vec => _1;                 // in scope 1 at src/main.rs:2:9: 2:16
}

    هر annotation به شکل debug <Name> => <Place>; متغیر کاربر نام‌دار را توصیف می‌کند، و اینکه دیباگر کجا (یعنی place) می‌تواند داده‌های آن متغیر را بیابد. اینجا نگاشت بدیهی است، اما بهینه‌سازی‌ها ممکن است place را پیچیده کنند، یا به چند متغیر کاربر که یک place مشترک دارند بینجامند. علاوه بر این، captureهای closure هم با همین سامانه توصیف می‌شوند، پس حتی بدون بهینه‌سازی پیچیده‌اند، مثلاً: debug x => (*((*_1).0: &T));.

    بلوک‌های «scope» (مثلاً scope 1 { .. }) ساختار لغوی برنامهٔ منبع را توصیف می‌کنند (کدام نام‌ها در چه زمانی در scope بودند)، پس هر بخشی از برنامه که با // in scope 0 annotate شده باشد، اگر مثلاً در دیباگر گام‌به‌گام کد را طی کنید، vec را نخواهد داشت.

    Basic blockها. با ادامهٔ خواندن، اولین basic block را می‌بینیم (طبیعتاً هنگام مشاهده ممکن است کمی متفاوت باشد و برخی کامنت‌ها را نادیده می‌گیرم):

    bb0: {
    StorageLive(_1);
    _1 = const <std::vec::Vec<T>>::new() -> bb2;
}

    basic block با مجموعه‌ای از دستورها و یک terminator نهایی تعریف می‌شود. در این مورد، یک دستور هست:

    StorageLive(_1);

    این دستور نشان می‌دهد متغیر _1 «زنده» است، یعنی ممکن است بعداً استفاده شود – این تا زمانی که به دستور StorageDead(_1) برسیم ادامه می‌یابد که نشان می‌دهد استفاده از متغیر _1 تمام شده است. این «دستورهای ذخیره‌سازی» توسط LLVM برای تخصیص فضای پشته به‌کار می‌روند.

    terminator بلوک bb0 فراخوانی Vec::new است:

    _1 = const <std::vec::Vec<T>>::new() -> bb2;

    terminatorها با دستورها فرق دارند چون می‌توانند بیش از یک جانشین داشته باشند – یعنی کنترل می‌تواند به جاهای مختلف برود. فراخوانی‌های تابع مثل فراخوانی Vec::new به‌دلیل امکان unwinding همیشه terminator هستند، هرچند در مورد Vec::new می‌توانیم ببینیم unwinding واقعاً ممکن نیست، و بنابراین فقط یک بلوک جانشین را فهرست می‌کنیم، bb2.

    اگر به bb2 نگاه کنیم، می‌بینیم این‌طور است:

    bb2: {
    StorageLive(_3);
    _3 = &mut _1;
    _2 = const <std::vec::Vec<T>>::push(move _3, const 1i32) -> [return: bb3, unwind: bb4];
}

    اینجا دو دستور هست: StorageLive دیگری که temporary با نام _3 را معرفی می‌کند، و سپس یک انتساب:

    _3 = &mut _1;

    انتساب‌ها به‌طور کلی شکل زیر را دارند:

    <Place> = <Rvalue>

    place عبارتی مثل _3، _3.f یا *_3 است – مکانی در حافظه را نشان می‌دهد. Rvalue عبارتی است که مقداری می‌سازد: در این مورد، rvalue عبارت borrow تغییرپذیر است که شبیه &mut <Place> است. پس می‌توانیم گرامری برای rvalueها این‌طور تعریف کنیم:

    <Rvalue>  = & (mut)? <Place>
          | <Operand> + <Operand>
          | <Operand> - <Operand>
          | ...

<Operand> = Constant
          | copy Place
          | move Place

    همان‌طور که از این گرامر می‌بینید، rvalueها نمی‌توانند تو در تو باشند – فقط می‌توانند به placeها و ثابت‌ها ارجاع دهند. علاوه بر این، وقتی place را به‌کار می‌بریم، مشخص می‌کنیم آیا کپی می‌کنیم (که لازم دارد place نوع T با T: Copy داشته باشد) یا move می‌کنیم (که برای place از هر نوعی کار می‌کند). برای مثال، اگر عبارت x = a + b + c را در Rust داشتیم، به دو دستور و یک temporary کامپایل می‌شد:

    TMP1 = a + b
x = TMP1 + c

    (امتحان کنید و ببینید، هرچند ممکن است بخواهید حالت release را بزنید تا بررسی‌های سرریز رد شوند.)

    MIR data types

    نوع‌های داده MIR در ماژول compiler/rustc_middle/src/mir/ تعریف شده‌اند. هر یک از مفاهیم کلیدی ذکرشده در بخش قبل به شکلی نسبتاً سرراست به یک نوع Rust نگاشت می‌شود.

    نوع داده اصلی MIR Body است. داده‌های یک تابع واحد را دارد (به‌همراه زیرنمونه‌های Mir برای «ثابت‌های ارتقایافته (promoted constants)»، اما دربارهٔ آن‌ها در ادامه می‌توانید بخوانید).

    • Basic blockها: basic blockها در فیلد Body::basic_blocks ذخیره می‌شوند؛ این یک بردار از structهای BasicBlockData است. هیچ‌کس هرگز مستقیماً به basic block ارجاع نمی‌دهد: به‌جای آن مقادیر BasicBlock را دست‌به‌دست می‌کنیم که اندیس‌های newtype‌شدهٔ این بردار هستند.
    • دستورها با نوع Statement نمایش داده می‌شوند.
    • Terminatorها با Terminator نمایش داده می‌شوند.
    • Localها با نوع اندیس newtype‌شدهٔ Local نمایش داده می‌شوند. داده‌های متغیر محلی در بردار Body::local_decls یافت می‌شود. همچنین ثابت ویژهٔ RETURN_PLACE هست که «local» ویژه را برای مقدار بازگشتی شناسایی می‌کند.
    • Places are identified by the struct Place. There are a few fields:
      • Local variables like _1
      • Projectionها، که فیلدها یا چیزهای دیگری هستند که از یک place پایه «تصویر (project)» می‌شوند. این‌ها با نوع newtype‌شدهٔ ProjectionElem نمایش داده می‌شوند. مثلاً place با نام _1.f یک projection است، که f «عنصر projection» و _1 مسیر پایه است. *_1 هم projection است، که * با عنصر ProjectionElem::Deref نمایش داده می‌شود.
    • Rvalueها با enum با نام Rvalue نمایش داده می‌شوند.
    • Operandها با enum با نام Operand نمایش داده می‌شوند.

    Representing constants

    وقتی کد به مرحلهٔ MIR رسیده باشد، ثابت‌ها عموماً به دو شکل می‌آیند: ثابت‌های MIR (mir::Constant) و ثابت‌های سامانهٔ نوع (ty::Const). ثابت‌های MIR به‌عنوان operand به‌کار می‌روند: در x + CONST، CONST ثابت MIR است؛ به همین ترتیب، در x + 2، 2 ثابت MIR است. ثابت‌های سامانهٔ نوع در سامانهٔ نوع به‌کار می‌روند، به‌ویژه برای طول آرایه‌ها، و همچنین برای const generics.

    عموماً هر دو نوع ثابت می‌توانند «ارزیابی‌نشده» یا «از قبل ارزیابی‌شده» باشند. ثابت ارزیابی‌نشده فقط DefId چیزی را که باید برای محاسبهٔ این نتیجه ارزیابی شود ذخیره می‌کند. ثابت ارزیابی‌شده («مقدار») از قبل محاسبه شده است؛ نمایش آن‌ها بین ثابت‌های سامانهٔ نوع و ثابت‌های MIR فرق دارد: ثابت‌های MIR به mir::ConstValue ارزیابی می‌شوند؛ ثابت‌های سامانهٔ نوع به ty::ValTree.

    ثابت‌های سامانهٔ نوع برای پشتیبانی از const generics چند variant بیشتر دارند: می‌توانند به پارامترهای const generic محلی ارجاع دهند و در معرض استنتاج‌اند. علاوه بر این، variant با نام mir::Constant::Ty اجازه می‌دهد از ثابت دلخواه سامانهٔ نوع به‌عنوان ثابت MIR استفاده کنیم؛ این هر وقت پارامتر const generic به‌عنوان operand به‌کار رود رخ می‌دهد.

    MIR constant values

    به‌طور کلی، مقدار ثابت MIR (mir::ConstValue) با ارزیابی ثابتی که کاربر نوشته محاسبه شده است. این ارزیابی ثابت نمایش بسیار سطح پایینی از نتیجه برحسب بایت‌های جداگانه تولید می‌کند. این را ثابت «غیرمستقیم (indirect)» (mir::ConstValue::Indirect) می‌نامیم چون مقدار در حافظه ذخیره می‌شود.

    اما ذخیرهٔ همه‌چیز در حافظه بسیار ناکارآمد خواهد بود. بنابراین variantهای دیگری در mir::ConstValue هست که می‌توانند برخی مقادیر ساده و رایج را کارآمدتر نمایش دهند. به‌طور خاص، هر چیزی که مستقیماً به‌صورت literal در Rust قابل‌نوشتن است (عدد صحیح، ممیز شناور، نویسه، بولی، و همچنین "string literals" و b"byte string literals") variant بهینه‌ای دارد که از سربار کامل نمایش درون‌حافظه‌ای پرهیز می‌کند.

    ValTrees

    ثابت ارزیابی‌شدهٔ سامانهٔ نوع یک «valtree» است. ساختار داده ty::ValTree اجازه می‌دهد نمایش دهیم

    • arrays,
    • many structs,
    • tuples,
    • enumها و،
    • most primitives.

    مهم‌ترین قاعدهٔ این نمایش این است که هر مقدار باید به‌طور یکتا نمایش داده شود. به عبارت دیگر، یک مقدار مشخص فقط باید به یک شکل مشخص قابل‌نمایش باشد. برای مثال، فقط یک راه برای نمایش آرایه‌ای از دو عدد صحیح به‌صورت ValTree هست: Branch([Leaf(first_int), Leaf(second_int)]). حتی اگر نظری [u32; 2] را بتوان در یک u64 کدگذاری کرد و در نتیجه فقط Leaf(bits_of_two_u32) بود، این ساخت قانونی ValTree نیست (و انجامش بسیار پیچیده است، پس بعید است کسی وسوسه شود).

    این قواعد همچنین یعنی برخی مقادیر قابل‌نمایش نیستند. union در ثابت‌های سطح نوع نمی‌تواند باشد، چون روشن نیست چگونه باید نمایش داده شوند، چون variant فعالشان ناشناخته است. به همین ترتیب، راهی برای نمایش اشاره‌گرهای خام نیست چون آدرس‌ها در زمان کامپایل ناشناخته‌اند، و بنابراین نمی‌توانیم دربارهٔ آن‌ها فرضی کنیم. ارجاع‌ها از طرف دیگر می‌توانند نمایش داده شوند، چون برابری ارجاع‌ها برابری مقدارشان تعریف شده، پس آدرسشان را نادیده می‌گیریم و فقط به مقدار پشتیبان نگاه می‌کنیم. باید مطمئن شویم مقادیر اشاره‌گر ارجاع‌ها در زمان کامپایل قابل‌مشاهده نیستند. بنابراین &42 را دقیقاً مثل 42 کدگذاری می‌کنیم. هر تبدیل از valtree به مقدار ثابت MIR باید indirection واقعی را دوباره معرفی کند. در زمان codegen، آدرس‌ها ممکن است بین چند استفاده حذف تکرار شوند یا نشوند، که کاملاً به انتخاب‌های دلخواه بهینه‌سازی بستگی دارد.

    در نتیجه، همهٔ دیکد کردن ValTree باید با تطبیق روی نوع ابتدا و تصمیم‌گیری بر آن اساس انجام شود. خود مقدار بدون نوع متعلق به آن اطلاع مفیدی نمی‌دهد.
