    حذف‌ابهام drop (Drop elaboration)

    dropهای پویا

    طبق مرجع Rust:

    وقتی یک متغیر یا مقدار موقت مقداردهی‌شده از محدوده خارج می‌شود، destructor آن اجرا می‌شود، یا به عبارتی drop می‌شود. انتساب نیز در صورتی که عملوند سمت چپ مقداردهی‌شده باشد، destructor آن را اجرا می‌کند. اگر یک متغیر به‌صورت جزئی مقداردهی شده باشد، فقط فیلدهای مقداردهی‌شده‌ی آن drop می‌شوند.

    هنگام ساخت MIR، ترمیناتورهای Drop و DropAndReplace نشان‌دهنده‌ی جاهایی هستند که ممکن است drop رخ دهد. با این حال، در این مرحله، وجود این ترمیناتورها تضمین نمی‌کند که یک destructor اجرا شود. دلیلش این است که هدفِ یک drop ممکن است پیش از رسیدن به ترمیناتور مقداردهی‌نشده باشد (معمولاً چون از آن move شده است). به‌طور کلی نمی‌توانیم در زمان کامپایل بدانیم که یک متغیر مقداردهی شده است یا نه.

    let mut y = vec![];

{
    let x = vec![1, 2, 3];
    if std::process::id() % 2 == 0 {
        y = x; // conditionally move `x` into `y`
    }
} // `x` goes out of scope here. Should it be dropped?

    در این موارد باید به‌صورت پویا پیگیری کنیم که آیا یک متغیر مقداردهی شده است یا خیر. قوانین این کار به‌تفصیل در RFC 320: Non-zeroing dynamic drops بیان شده است.

    تعهدات drop

    از RFC:

    وقتی یک متغیر محلی مقداردهی می‌شود، مجموعه‌ای از «تعهدات drop» ایجاد می‌کند: مجموعه‌ای از مسیرهای ساختاری (برای مثال یک متغیر محلی a، یا مسیری به یک فیلد مانند b.f.y) که باید drop شوند.

    تعهدات drop برای یک متغیر محلی x با نوع ساختاری T از تحلیل ساختار T محاسبه می‌شوند. اگر خودِ T صفت Drop را پیاده‌سازی کند، آنگاه x یک تعهد drop است. اگر T صفت Drop را پیاده‌سازی نکند، آنگاه مجموعه‌ی تعهدات drop اجتماع تعهدات drop فیلدهای T است.

    وقتی از یک مسیر ساختاری move می‌شود (و در نتیجه مقداردهی‌نشده می‌شود)، هر تعهد drop مربوط به آن مسیر یا نوادگانش (path.f، path.f.g.h و غیره) آزاد می‌شود. نوع‌هایی که پیاده‌سازی Drop دارند اجازه‌ی move از فیلدهای منفرد را نمی‌دهند، بنابراین نیازی به پیگیری وضعیت مقداردهی از طریق آن‌ها نیست.

    وقتی یک متغیر محلی از محدوده خارج می‌شود (Drop)، یا وقتی یک مسیر ساختاری با انتساب بازنویسی می‌شود (DropAndReplace)، تعهدات drop مربوط به آن متغیر یا مسیر را بررسی می‌کنیم. مگر اینکه آن تعهد تا این نقطه آزاد شده باشد، پیاده‌سازی Drop مرتبط با آن فراخوانی می‌شود. برای نوع‌های enum، فقط فیلدهای مربوط به نوع «فعال» باید drop شوند. هنگام پردازش تعهدات drop برای چنین نوع‌هایی، ابتدا discriminant را بررسی می‌کنیم تا نوع فعال مشخص شود. تمام تعهدات drop مربوط به نوع‌های غیر از نوع فعال نادیده گرفته می‌شوند.

    در اینجا چند نوع جالب برای روشن‌تر شدن این قوانین آمده است:

    struct NoDrop(u8); // No `Drop` impl. No fields with `Drop` impls.

struct NeedsDrop(Vec<u8>); // No `Drop` impl but has fields with `Drop` impls.

struct ThinVec(*const u8); // Custom `Drop` impl. Individual fields cannot be moved from.

impl Drop for ThinVec {
    fn drop(&mut self) { /* ... */ }
}

enum MaybeDrop {
    Yes(NeedsDrop),
    No(NoDrop),
}

    Drop elaboration

    یک مدل معتبر برای این قوانین این است که برای هر مسیر ساختاری که در هر نقطه‌ای از تابع استفاده می‌شود، یک پرچم بولی (یک «drop flag») نگه داریم. این پرچم هنگام مقداردهی مسیر تنظیم می‌شود و هنگام move شدن از مسیر پاک می‌شود. وقتی یک Drop رخ می‌دهد، پرچم‌های همه‌ی تعهدات مرتبط با هدف Drop را بررسی می‌کنیم و برای آن‌هایی که هنوز معتبرند، پیاده‌سازی Drop مربوط را فراخوانی می‌کنیم.

    این فرایند—تبدیل MIR تازه‌ساخته‌شده با ترمیناتورهای نادقیق Drop و DropAndReplace به MIR‌ای دارای drop flag—به drop elaboration معروف است. وقتی یک دستور MIR باعث می‌شود یک متغیر مقداردهی (یا مقداردهی‌نشده) شود، drop elaboration کدی درج می‌کند که drop flag آن متغیر را تنظیم (یا پاک) کند. ترمیناتورهای Drop را درون شرط‌هایی قرار می‌دهد که drop flagهای تازه‌درج‌شده را بررسی می‌کنند.

    Drop elaboration همچنین ترمیناتورهای DropAndReplace را به یک Drop از هدف و یک نوشتن در مکانِ تازه‌drop‌شده تقسیم می‌کند. این کار تا حدی با آنچه تا اینجا گفتیم نامرتبط است.

    پس از اتمام این کار، ترمیناتورهای Drop در MIR متناظر با فراخوانی «drop glue» یا «drop shim» برای نوع مکانِ drop‌شده هستند. drop glue یک نوع، پیاده‌سازی Drop آن نوع را (در صورت وجود) فراخوانی می‌کند و سپس به‌صورت بازگشتی drop glue همه‌ی فیلدهای آن نوع را فراخوانی می‌کند.

    Drop elaboration در rustc

    رویکرد توصیف‌شده در بالا پرهزینه‌تر از حد لازم است. می‌توان چند بهینه‌سازی را تصور کرد:

    • فقط مسیرهایی که هدف یک Drop هستند (یا هدف پیشوندی از آن‌هاست) به drop flag نیاز دارند.
    • برخی متغیرها هنگام drop شدن مشخصاً مقداردهی‌شده (یا مقداردهی‌نشده) هستند. این‌ها به drop flag نیاز ندارند.
    • اگر مجموعه‌ای از مسیرها فقط از طریق یک پیشوند مشترک drop یا move می‌شوند، آن مسیرها می‌توانند یک drop flag مشترک داشته باشند.

    زیرمجموعه‌ای از این بهینه‌سازی‌ها در rustc پیاده‌سازی شده است.

    در کامپایلر، drop elaboration میان چند ماژول تقسیم شده است. خودِ pass اینجا تعریف شده است، اما منطق اصلی در جای دیگری تعریف شده، چون برای ساخت drop shimها نیز به کار می‌رود.

    Drop elaboration هر Drop در MIR تازه‌ساخته‌شده را یکی از چهار نوع زیر مشخص می‌کند:

    • Static، هدف همیشه مقداردهی‌شده است.
    • Dead، هدف همیشه نامقداردهی‌شده است.
    • Conditional، هدف یا کاملاً مقداردهی‌شده است یا کاملاً مقداردهی‌نشده. به‌صورت جزئی مقداردهی نشده است.
    • Open، هدف ممکن است به‌صورت جزئی مقداردهی شده باشد.

    برای این کار از یک جفت تحلیل جریان داده به نام‌های MaybeInitializedPlaces و MaybeUninitializedPlaces استفاده می‌کند. اگر یک مکان در یکی از این دو باشد ولی در دیگری نباشد، آنگاه وضعیت مقداردهی هدف در زمان کامپایل معلوم است (Dead یا Static). در این حالت، drop elaboration برای هدف پرچمی اضافه نمی‌کند. صرفاً ترمیناتور Drop را حذف می‌کند (Dead) یا حفظ می‌کند (Static).

    برای dropهای Conditional، می‌دانیم که وضعیت مقداردهی متغیر به‌طور کلی با وضعیت مقداردهی فیلدهایش یکسان است. بنابراین، پس از تولید یک drop flag برای هدف آن drop، فراخوانی drop glue آن هدف ایمن است.

    dropهای Open

    dropهای Open پیچیده‌ترین هستند، زیرا باید یک ترمیناتور Drop واحد را به چند ترمیناتور مختلف بشکنیم، یکی برای هر فیلدِ هدف که نوعش drop glue دارد (Ty::needs_drop). نمی‌توانیم drop glue خودِ هدف را فراخوانی کنیم، چون این کار مستلزم مقداردهی‌شدن همه‌ی فیلدهای هدف است. به یاد داشته باشید، متغیرهایی که نوعشان پیاده‌سازی سفارشی Drop دارد، dropهای Open را مجاز نمی‌کنند، چون نمی‌توان از فیلدهایشان move کرد.

    این کار با دسته‌بندی بازگشتی هر فیلد به‌عنوان Dead، Static، Conditional یا Open انجام می‌شود. فیلدهایی که نوعشان drop glue ندارد به‌طور خودکار Dead هستند و لازم نیست در بازگشت بررسی شوند. وقتی به فیلدی می‌رسیم که نوعش Open نیست، آن را مانند حالت‌های بالا مدیریت می‌کنیم. اگر فیلد نیز Open باشد، بازگشت ادامه می‌یابد.

    شایان ذکر است که dropهای Open مربوط به enumها چگونه مدیریت می‌شوند. درون drop elaboration، هر نوعِ enum مانند یک فیلد در نظر گرفته می‌شود، با این پایای ثابت که در هر لحظه فقط یکی از این «فیلدهای نوع» می‌تواند مقداردهی‌شده باشد. در حالت کلی نمی‌دانیم کدام نوع فعال است، بنابراین باید drop glue مربوط به enum را (که discriminant را بررسی می‌کند) فراخوانی کنیم یا discriminant را خودمان به‌عنوان بخشی از یک drop Open بسط‌یافته بررسی کنیم. با این حال، در برخی موارد (برای مثال درون یک بازوی match) می‌دانیم کدام نوعِ enum فعال است. این اطلاعات در تحلیل‌های جریان داده‌ی MaybeInitializedPlaces و MaybeUninitializedPlaces با علامت‌گذاری همه‌ی مکان‌های متناظر با نوع‌های غیرفعال به‌عنوان مقداردهی‌نشده کدگذاری می‌شود.

    نکته‌ی جانبی: drop elaboration و const-eval

    در Rust، توابعی که واجد شرایط ارزیابی در زمان کامپایل هستند باید صراحتاً با کلیدواژه‌ی const علامت‌گذاری شوند. این شامل پیاده‌سازی‌های صفت Drop نیز می‌شود که ممکن است const باشند یا نباشند. کدی که واجد شرایط ارزیابی در زمان کامپایل است فقط می‌تواند توابع const را فراخوانی کند، بنابراین هر فراخوانی پیاده‌سازی‌های غیر-const از Drop در چنین کدی باید ممنوع شود.

    فراخوانی یک پیاده‌سازی Drop در MIR به‌صورت یک ترمیناتور Drop کدگذاری می‌شود. با این حال، همان‌طور که در بالا گفتیم، یک ترمیناتور Drop در MIR تازه‌ساخته‌شده لزوماً به فراخوانی Drop::drop منجر نمی‌شود. هدف drop ممکن است در آن نقطه مقداردهی‌نشده باشد. این یعنی بررسی Dropهای غیر-const روی MIR تازه‌ساخته‌شده می‌تواند به خطاهای کاذب منجر شود. در عوض، منتظر می‌مانیم تا پس از اجرای drop elaboration، که dropهای Dead را (آن‌هایی که هدفشان مشخصاً مقداردهی‌نشده است) حذف می‌کند، این بررسی‌ها را اجرا کنیم.
