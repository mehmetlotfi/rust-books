    استنتاج نوع‌های مبهم (opaque) (impl Trait)

    این صفحه توضیح می‌دهد کامپایلر چگونه نوع پنهان یک نوع مبهم (opaque) را استنتاج می‌کند. این نوع استنتاج نوع به‌طور ویژه پیچیده است، زیرا برخلاف انواع دیگر استنتاج نوع، می‌تواند در میان توابع و بدنهٔ توابع کار کند.

    مثال راهنما

    برای کمک به توضیح نحوهٔ کار، یک مثال را در نظر بگیریم.

    #![feature(type_alias_impl_trait)]
mod m {
    pub type Seq<T> = impl IntoIterator<Item = T>;

    #[define_opaque(Seq)]
    pub fn produce_singleton<T>(t: T) -> Seq<T> {
        vec![t]
    }

    #[define_opaque(Seq)]
    pub fn produce_doubleton<T>(t: T, u: T) -> Seq<T> {
        vec![t, u]
    }
}

fn is_send<T: Send>(_: &T) {}

pub fn main() {
    let elems = m::produce_singleton(22);

    is_send(&elems);

    for elem in elems {
        println!("elem = {:?}", elem);
    }
}

    در این کد، نوع مبهم (opaque type) Seq<T> است. دامنهٔ تعریف‌کنندهٔ آن ماژول m است. نوع پنهان آن Vec<T> است که از m::produce_singleton و m::produce_doubleton استنتاج می‌شود.

    در تابع main، نوع مبهم خارج از دامنهٔ تعریف‌کنندهٔ خود است. وقتی main تابع m::produce_singleton را فراخوانی می‌کند، یک ارجاع به نوع مبهم Seq<i32> دریافت می‌کند. فراخوانی is_send بررسی می‌کند که Seq<i32>: Send. Send در میان قیدهای impl trait فهرست نشده است، اما به‌دلیل نشت auto-trait می‌توانیم استنتاج کنیم که برقرار است. تبدیل (desugaring) حلقهٔ for ایجاب می‌کند که Seq<T>: IntoIterator، که از قیدهای اعلام‌شده روی Seq<T> قابل اثبات است.

    بررسی نوع main

    با نگاه به آنچه هنگام بررسی نوع main رخ می‌دهد شروع می‌کنیم. ابتدا produce_singleton را فراخوانی می‌کنیم و نوع بازگشتی یک نوع مبهم OpaqueTy است.

    بررسی نوع حلقهٔ for

    حلقهٔ for بخش in elems را به IntoIterator::into_iter(elems) تبدیل (desugar) می‌کند. نوع elems برابر Seq<T> است، بنابراین بررسی‌کنندهٔ نوع تعهد (obligation) Seq<T>: IntoIterator را ثبت می‌کند. این تعهد به‌سادگی برآورده می‌شود، چون Seq<T> یک نوع مبهم (impl IntoIterator<Item = T>) است که برای این صفت قید دارد. همان‌طور که قید where به شکل U: Foo به U اجازه می‌دهد به‌سادگی Foo را برآورده کند، قیدهای نوع‌های مبهم برای بررسی‌کنندهٔ نوع در دسترس‌اند و برای برآورده کردن تعهدها به کار می‌روند.

    نوع elem در حلقهٔ for برابر <Seq<T> as IntoIterator>::Item استنتاج می‌شود که همان T است. بررسی‌کنندهٔ نوع در هیچ نقطه‌ای به نوع پنهان علاقه‌ای ندارد.

    بررسی نوع فراخوانی is_send

    هنگام تلاش برای اثبات قیدهای auto trait، ابتدا فرایند بالا را تکرار می‌کنیم تا ببینیم آیا auto trait در فهرست قیدهای نوع مبهم هست یا نه. اگر نبود، نوع پنهان نوع مبهم را آشکار می‌کنیم، اما فقط برای اثبات همین قید صفت خاص، نه به‌طور کلی. آشکارسازی با فراخوانی query ‏type_of روی DefId نوع مبهم انجام می‌شود. این query در داخل، نوع‌های پنهان را از تابع(های) تعریف‌کننده درخواست می‌کند و آن را برمی‌گرداند (برای جزئیات بیشتر بخش مربوط به type_of را ببینید).

    query ‏type_of، وقتی روی یک نوع مبهم O اعمال شود، نوع پنهان را برمی‌گرداند. آن نوع پنهان با ترکیب نتایج هر تابع قیددهنده در دامنهٔ تعریف‌کنندهٔ O محاسبه می‌شود.

    ربط دادن یک نوع مبهم به نوعی دیگر

    یک جای مرکزی وجود دارد که در آن نوع پنهانِ یک نوع مبهم مقید می‌شود و آن تابع handle_opaque_type است. جالب اینکه دو نوع می‌گیرد، پس می‌توانید هر دو نوعی را بدهید، اما یکی از آن‌ها باید نوع مبهم باشد. ترتیب فقط برای تشخیص‌ها (diagnostics) اهمیت دارد.

    تعامل با queryها

    وقتی queryها نوع‌های مبهم را مدیریت می‌کنند، نمی‌توانند تشخیص دهند که در دامنهٔ تعریف‌کننده هستند یا نه، بنابراین فقط فرض می‌کنند که هستند.

    نوع‌های پنهان ثبت‌شده در struct ‏QueryResponse و در فیلد opaque_types ذخیره می‌شوند (تابع take_opaque_types_for_query_response آن‌ها را بیرون می‌خواند).

    وقتی QueryResponse در infcx پیرامون در query_response_substitution_guess نمونه‌سازی می‌شود، هر قید نوع پنهان را با فراخوانی handle_opaque_type (مانند بالا) تبدیل می‌کنیم.

    یک نکتهٔ «عجیب» وجود دارد. نوع‌های مبهم نمونه‌سازی‌شده ترتیبی دارند (اگر یک نوع مبهم با نوع مبهم دیگری مقایسه شود، و ناچار باشیم یکی از نوع‌های مبهم را انتخاب کنیم تا نوع پنهانش تعیین شود). از آنی استفاده می‌کنیم که «مورد انتظار» در نظر گرفته می‌شود. اما در واقع هر دو نوع مبهم ممکن است کاربردهای تعریف‌کننده داشته باشند. وقتی نتیجهٔ query نمونه‌سازی شود، از بافتی که از query استفاده می‌کند دوباره ارزیابی خواهد شد. بافت نهایی (typeck یک تابع، mir borrowck یا بررسی‌های wf) خواهد دانست کدام نوع مبهم را واقعاً می‌توان نمونه‌سازی کرد و سپس آن را درست مدیریت می‌کند.

    درون بررسی‌کنندهٔ قرض MIR

    بررسی‌کنندهٔ قرض MIR چیزها را از طریق nll_relate به هم ربط می‌دهد و فقط به ناحیه‌ها (regions) اهمیت می‌دهد. هر رابطهٔ نوعی، مقیدسازی نوع‌های پنهان را راه می‌اندازد، بنابراین بررسی‌کنندهٔ قرض همان کاری را می‌کند که بررسی‌کنندهٔ نوع می‌کند، اما کد آشکارا مرده را (مثلاً پس از یک panic) نادیده می‌گیرد. بررسی‌کنندهٔ قرض همچنین مرجع حقیقت در مورد نوع‌های پنهان است، چون تنها کسی است که می‌تواند درست بفهمد کدام طول عمرها روی نوع پنهان متناظر با کدام طول عمرها روی اعلان نوع مبهم‌اند.

    هک‌های سازگاری با نسخه‌های قبلی

    impl Trait در جایگاه بازگشتی ویژگی‌های عجیب گوناگونی دارد که بخشی از هیچ RFC نبوده‌اند و احتمالاً پایدارسازی تصادفی بوده‌اند. برای پشتیبانی از این‌ها، replace_opaque_types_with_inference_vars برای بازگرداندن رفتار پیشین به کار می‌رود.

    سه هک سازگاری با نسخه‌های قبلی وجود دارد:

    1. همهٔ نقاط بازگشت یک متغیر استنتاج مشترک دارند، بنابراین برخی نقاط بازگشت فقط در صورتی کامپایل می‌شوند که نقطهٔ بازگشت دیگری از یک نوع مشخص استفاده کند.

      fn foo() -> impl Debug {
    if false {
        return std::iter::empty().collect();
    }
    vec![42]
}

    2. قیدهای برابری نوع وابسته برای impl Trait را می‌توان به کار برد، مادامی که نوع پنهان قیدهای صفت روی نوع وابسته را برآورده کند. امضای مبهم impl Trait لازم نیست آن‌ها را برآورده کند.

      trait Duh {}

impl Duh for i32 {}

trait Trait {
    type Assoc: Duh;
}

// the fact that `R` is the `::Output` projection on `F` causes
// an intermediate inference var to be generated which is then later
// compared against the actually found `Assoc` type.
impl<R: Duh, F: FnMut() -> R> Trait for F {
    type Assoc = R;
}

// The `impl Send` here is then later compared against the inference var
// created, causing the inference var to be set to `impl Send` instead of
// the hidden type. We already have obligations registered on the inference
// var to make it uphold the `: Duh` bound on `Trait::Assoc`. The opaque
// type does not implement `Duh`, even if its hidden type does.
// Lazy TAIT would error out, but we inserted a hack to make it work again,
// keeping backwards compatibility.
fn foo() -> impl Trait<Assoc = impl Send> {
    || 42
}

    3. closureها نمی‌توانند نوع پنهان برای impl Trait تابع والد خود بسازند. این نکته عمدتاً منتفی است، چون مورد ۱ متغیرهای استنتاج را معرفی می‌کند و در نتیجه closure همیشه فقط متغیر استنتاج را می‌بیند، اما اگر مورد ۱ را برطرف کنیم، این به یک مشکل تبدیل خواهد شد.
