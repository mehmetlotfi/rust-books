    کامپایل افزایشی با جزئیات

    طرح کامپایل افزایشی در اصل افزونه‌ای شگفت‌آور ساده بر سامانهٔ کلی کوئری است. بر این واقعیت تکیه دارد که:

    1. کوئری‌ها توابع خالص هستند — با ورودی‌های یکسان، کوئری همیشه نتیجهٔ یکسانی می‌دهد، و
    2. مدل کوئری کامپایل را در گرافی بدون دور ساختار می‌دهد که وابستگی‌های بین محاسبات جداگانه را صریح می‌کند.

    این فصل توضیح می‌دهد چگونه می‌توانیم از این ویژگی‌ها برای افزایشی‌کردن امور استفاده کنیم و سپس دربارهٔ مسائل پیاده‌سازی بحث می‌کند.

    الگوریتم پایه برای ارزیابی افزایشی کوئری

    همان‌طور که در مقدمهٔ مدل ارزیابی کوئری توضیح داده شد، فراخوانی‌های کوئری گراف جهت‌دار بدون دور می‌سازند. دوباره مثال فصل قبل:

      list_of_all_hir_items <----------------------------- type_check_crate()
                                                               |
                                                               |
  Hir(foo) <--- type_of(foo) <--- type_check_item(foo) <-------+
                                      |                        |
                    +-----------------+                        |
                    |                                          |
                    v                                          |
  Hir(bar) <--- type_of(bar) <--- type_check_item(bar) <-------+

    چون هر دسترسی از یک کوئری به کوئری دیگر باید از زمینهٔ کوئری بگذرد، می‌توانیم این دسترسی‌ها را ثبت کنیم و به این ترتیب این گراف وابستگی را در حافظه بسازیم. با فعال‌بودن ردیابی وابستگی، وقتی کامپایل تمام می‌شود، می‌دانیم کدام کوئری‌ها فراخوانی شدند (گره‌های گراف) و برای هر فراخوانی، کدام کوئری‌ها یا ورودی‌های دیگر در محاسبهٔ نتیجهٔ آن کوئری دخیل بوده‌اند (یال‌های گراف).

    اکنون فرض کنید کد منبع برنامه را تغییر دهیم طوری که HIR مربوط به bar با قبل فرق کند. هدف ما این است که فقط کوئری‌هایی را که واقعاً از این تغییر متأثر شده‌اند دوباره محاسبه کنیم و نتایج cache‌شدهٔ همهٔ کوئری‌های دیگر را دوباره استفاده کنیم. با گراف وابستگی دقیقاً می‌توانیم این کار را بکنیم. برای یک فراخوانی مشخص کوئری، گراف دقیقاً به ما می‌گوید چه داده‌ای در محاسبهٔ نتایج آن دخیل بوده، فقط باید یال‌ها را دنبال کنیم تا به چیزی که تغییر کرده برسیم. اگر به چیزی که تغییر کرده برنخوریم، می‌دانیم کوئری همچنان همان نتیجه‌ای را می‌دهد که از قبل در cache داریم.

    فراخوانی type_of(foo) از بالا را مثال بزنیم، می‌توانیم با دنبال‌کردن یال‌ها به ورودی‌هایش بررسی کنیم آیا نتیجهٔ cache‌شده هنوز معتبر است. تنها یال به Hir(foo) می‌رسد، ورودی‌ای که از تغییر متأثر نشده است. پس می‌دانیم نتیجهٔ cache‌شده برای type_of(foo) هنوز معتبر است.

    داستان برای type_check_item(foo) کمی فرق دارد: دوباره یال‌ها را پیمایش می‌کنیم و از قبل می‌دانیم type_of(foo) مشکلی ندارد. سپس به type_of(bar) می‌رسیم که هنوز بررسی‌اش نکرده‌ایم، پس یال‌های type_of(bar) را پیمایش می‌کنیم و به Hir(bar) می‌رسیم که تغییر کرده است. در نتیجه نتیجهٔ type_of(bar) ممکن است با آنچه در cache داریم متفاوت باشد و، به‌صورت تعدّی، نتیجهٔ type_check_item(foo) هم ممکن است تغییر کرده باشد. پس type_check_item(foo) را دوباره اجرا می‌کنیم، که به نوبهٔ خود type_of(bar) را دوباره اجرا می‌کند، که نتیجهٔ به‌روز می‌دهد چون نسخهٔ به‌روز Hir(bar) را می‌خواند. همچنین type_check_item(bar) را دوباره اجرا می‌کنیم چون نتیجهٔ type_of(bar) ممکن است تغییر کرده باشد.

    مشکل الگوریتم پایه: مثبت‌های کاذب

    اگر پاراگراف قبلی را با دقت خوانده باشید، می‌بینید می‌گوید type_of(bar) ممکن است تغییر کرده باشد چون یکی از ورودی‌هایش تغییر کرده است. این احتمال هم هست که با وجود تغییر ورودی همچنان دقیقاً همان نتیجه را بدهد. مثالی با کوئری ساده‌ای که فقط علامت (sign) یک عدد صحیح را محاسبه می‌کند در نظر بگیرید:

      IntValue(x) <---- sign_of(x) <--- some_other_query(x)

    فرض کنید IntValue(x) ابتدا 1000 است و سپس روی 2000 تنظیم می‌شود. هرچند IntValue(x) در دو حالت متفاوت است، sign_of(x) در هر دو حالت نتیجهٔ + می‌دهد.

    اگر الگوریتم پایه را دنبال کنیم، با این حال، some_other_query(x) باید (بی‌دلیل) دوباره ارزیابی شود چون به‌صورت تعدّی به ورودی تغییریافته وابسته است. تشخیص تغییر در این مورد «مثبت کاذب» می‌دهد چون باید محتاطانه فرض کند some_other_query(x) ممکن است از آن ورودی تغییریافته متأثر شده باشد.

    متأسفانه معلوم می‌شود کوئری‌های واقعی در کامپایلر پر از مثال‌هایی مثل این‌اند و تغییرات کوچک در ورودی اغلب بالقوه بخش‌های بسیار بزرگی از فایل‌های دودویی خروجی را تحت‌تأثیر قرار می‌دهند. در نتیجه، مجبور شدیم سامانهٔ تشخیص تغییر را هوشمندتر و دقیق‌تر کنیم.

    بهبود دقت: الگوریتم red-green

    مشکل «مثبت‌های کاذب» را می‌توان با در هم‌آمیختن تشخیص تغییر و ارزیابی مجدد کوئری حل کرد. به‌جای پیمایش گراف تا ورودی‌ها هنگام تلاش برای فهمیدن اینکه آیا نتیجهٔ cache‌شده هنوز معتبر است، می‌توانیم بررسی کنیم آیا نتیجه واقعاً تغییر کرده است، پس از اینکه مجبور به ارزیابی مجدد آن شدیم.

    این الگوریتم را red-green می‌نامیم چون به گره‌ها در گراف وابستگی رنگ سبز داده می‌شود اگر توانستیم ثابت کنیم نتیجهٔ cache‌شدهٔ آن هنوز معتبر است و رنگ قرمز اگر نتیجه پس از ارزیابی مجدد متفاوت از آب درآمده باشد.

    جان ردیابی تغییر red-green در الگوریتم try-mark-green پیاده‌سازی شده است، که، حدس زدید، سعی می‌کند گره داده‌شده را سبز علامت بزند:

    fn try_mark_green(tcx, current_node) -> bool {

    // Fetch the inputs to `current_node`, i.e. get the nodes that the direct
    // edges from `node` lead to.
    let dependencies = tcx.dep_graph.get_dependencies_of(current_node);

    // Now check all the inputs for changes
    for dependency in dependencies {

        match tcx.dep_graph.get_node_color(dependency) {
            Green => {
                // This input has already been checked before and it has not
                // changed; so we can go on to check the next one
            }
            Red => {
                // We found an input that has changed. We cannot mark
                // `current_node` as green without re-running the
                // corresponding query.
                return false
            }
            Unknown => {
                // This is the first time we look at this node. Let's try
                // to mark it green by calling try_mark_green() recursively.
                if try_mark_green(tcx, dependency) {
                    // We successfully marked the input as green, on to the
                    // next.
                } else {
                    // We could *not* mark the input as green. This means we
                    // don't know if its value has changed. In order to find
                    // out, we re-run the corresponding query now!
                    tcx.run_query_for(dependency);

                    // Fetch and check the node color again. Running the query
                    // has forced it to either red (if it yielded a different
                    // result than we have in the cache) or green (if it
                    // yielded the same result).
                    match tcx.dep_graph.get_node_color(dependency) {
                        Red => {
                            // The input turned out to be red, so we cannot
                            // mark `current_node` as green.
                            return false
                        }
                        Green => {
                            // Re-running the query paid off! The result is the
                            // same as before, so this particular input does
                            // not invalidate `current_node`.
                        }
                        Unknown => {
                            // There is no way a node has no color after
                            // re-running the query.
                            panic!("unreachable")
                        }
                    }
                }
            }
        }
    }

    // If we have gotten through the entire loop, it means that all inputs
    // have turned out to be green. If all inputs are unchanged, it means
    // that the query result corresponding to `current_node` cannot have
    // changed either.
    tcx.dep_graph.mark_green(current_node);

    true
}

    نکته: پیاده‌سازی واقعی را می‌توان در compiler/rustc_middle/src/dep_graph/graph.rs یافت

    با استفاده از علامت‌گذاری red-green می‌توانیم از اثر تجمعی ویرانگر داشتن مثبت کاذب در تشخیص تغییر پرهیز کنیم. هر وقت کوئری‌ای در حالت افزایشی اجرا می‌شود، ابتدا بررسی می‌کنیم آیا از قبل سبز است. اگر نه، try_mark_green() را روی آن اجرا می‌کنیم. اگر پس از آن هم سبز نبود، آن‌گاه واقعاً provider کوئری را فراخوانی می‌کنیم تا نتیجه را دوباره محاسبه کند. محاسبهٔ مجدد کوئری ممکن است خودش شامل فراخوانی بازگشتی کوئری‌های بیشتر باشد، که می‌تواند یعنی دوباره به الگوریتم try_mark_green() برای وابستگی‌ها به‌صورت بازگشتی برمی‌گردیم.

    دنیای واقعی: چگونه پایایی (persistence) همه‌چیز را پیچیده می‌کند

    بخش‌های بالا الگوریتم زیربنایی کامپایل افزایشی را توصیف کردند، اما چون فرایند کامپایلر پس از پایان خارج می‌شود و زمینهٔ کوئری را با cache نتایجش به فراموشی می‌برد، باید داده‌ها را روی دیسک ماندگار کنیم تا جلسهٔ کامپایل بعدی بتواند از آن‌ها استفاده کند. این مجموعه‌ای کاملاً تازه از چالش‌های پیاده‌سازی به همراه دارد:

    • cache نتایج کوئری روی دیسک ذخیره می‌شود، پس برای مقایسهٔ تغییر به‌آسانی در دسترس نیست.
    • جلسهٔ کامپایل بعدی با نسخهٔ جدیدی از کد شروع می‌شود که تغییرات دلخواه روی آن اعمال شده است. انواع شناسه‌ها و اندیس‌هایی که از شمارندهٔ سراسری و ترتیبی تولید می‌شوند (مثلاً NodeId، DefId و غیره) ممکن است جابه‌جا شده باشند، که نتایج ماندگار روی دیسک را فوراً غیرقابل‌استفاده می‌کند چون همان شناسه‌ها و اندیس‌های عددی ممکن است در جلسهٔ کامپایل جدید به چیزهای کاملاً تازه اشاره کنند.
    • ماندگارکردن روی دیسک هزینه دارد، پس نباید هر تکهٔ کوچک اطلاعات واقعاً بین جلسه‌های کامپایل cache شود. داده‌های ساده با اندازهٔ ثابت بر چیزهای پیچیده‌ای که باید از گام پرهزینهٔ (de-)serialization بگذرند ترجیح دارند.

    بخش‌های زیر توضیح می‌دهند کامپایلر این مشکلات را چگونه حل می‌کند.

    پرسش پایداری: پل‌زدن شکاف بین جلسه‌های کامپایل

    همان‌طور که پیش‌تر گفته شد، شناسه‌های مختلف (مثل DefId) توسط کامپایلر به شکلی تولید می‌شوند که به محتوای کد منبع در حال کامپایل بستگی دارد. تخصیص شناسه معمولاً قطعی است. یعنی اگر دقیقاً همان کد دو بار کامپایل شود، همان چیزها شناسهٔ یکسان می‌گیرند. اما اگر چیزی تغییر کند، مثلاً تابعی در میانهٔ فایل اضافه شود، هیچ تضمینی نیست که چیزی همان شناسهٔ قبلی را داشته باشد.

    در نتیجه نمی‌توانیم داده‌ها را در cache روی دیسک همان‌طور که در حافظه نمایش داده می‌شوند نمایش دهیم. برای مثال، اگر فقط تکه‌ای از اطلاعات نوع مثل TyKind::FnDef(DefId, GenericArgsRef<'tcx>) را ذخیره کنیم (همان‌طور که در حافظه می‌کنیم) و سپس DefId داخل آن در جلسهٔ کامپایل جدید به تابع دیگری اشاره کند، به مشکل می‌خوریم.

    راه‌حل این مشکل یافتن شکل‌های «پایدار» برای شناسه‌هاست که بین جلسه‌های کامپایل معتبر می‌مانند. برای مهم‌ترین مورد، یعنی DefIdها، این‌ها DefPath نامیده می‌شوند. هر DefId یک DefPath متناظر دارد، اما به‌جای شناسهٔ عددی، DefPath بر اساس مسیر آیتم شناسایی‌شده است، مثلاً std::collections::HashMap. مزیت چنین شناسه‌ای این است که تغییرات نامرتبط روی آن اثر نمی‌گذارد. برای مثال، می‌توان تابع جدیدی به std::collections افزود اما std::collections::HashMap همچنان همان std::collections::HashMap است. DefPath نسبت به تغییرات منبع «پایدار» است در حالی که DefId نیست.

    DefPathHash هم هست که فقط مقدار هش ۱۲۸ بیتی DefPath است. این دو اطلاعات یکسانی دارند و ما بیشتر از DefPathHash استفاده می‌کنیم چون کار با آن ساده‌تر است، هم Copy است و هم مستقل.

    این اصل شناسه‌های پایدار برای مقاوم‌کردن داده‌های cache روی دیسک در برابر تغییرات کد منبع به‌کار می‌رود. به‌جای ذخیرهٔ DefId، DefPathHash را ذخیره می‌کنیم و وقتی چیزی را از cache deserialize می‌کنیم، DefPathHash را به DefId متناظر در جلسهٔ کامپایل فعلی نگاشت می‌کنیم (که فقط یک جست‌وجوی ساده در hash table است).

    HirId، که برای شناسایی اجزای HIR‌ای که DefId خودشان را ندارند به‌کار می‌رود، شناسهٔ پایدار دیگری است. از نظر مفهومی جفتی از یک DefPath و یک LocalId است، که LocalId چیزی (مثلاً hir::Expr) را به‌صورت محلی درون «مالک» آن (مثلاً hir::Item) شناسایی می‌کند. اگر مالک جابه‌جا شود، LocalIdهای درون آن همچنان یکسان می‌مانند.

    بررسی تغییر نتایج کوئری: StableHash و Fingerprintها

    برای انجام علامت‌گذاری red-green اغلب باید بررسی کنیم آیا نتیجهٔ یک کوئری نسبت به نتیجه‌ای که در جلسهٔ کامپایل قبلی داشت تغییر کرده است. با این حال دو مشکل عملکردی هست:

    • می‌خواهیم از بارگذاری نتیجهٔ قبلی از دیسک فقط برای مقایسه پرهیز کنیم. نتیجهٔ جدید را از قبل محاسبه کرده‌ایم و از آن استفاده می‌کنیم. همچنین بارگذاری نتیجه از دیسک interner‌ها را با داده‌ای «آلوده» می‌کند که بعید است هرگز استفاده شود.
    • نمی‌خواهیم تک‌تک نتایج را در cache روی دیسک ذخیره کنیم. برای مثال، اتلاف تلاش است چیزهایی را روی دیسک ماندگار کنیم که از قبل در crateهای بالادستی موجودند.

    کامپایلر با استفاده از آنچه Fingerprint نامیده می‌شود از این مشکلات پرهیز می‌کند. هر بار که نتیجهٔ جدید کوئری محاسبه می‌شود، موتور کوئری مقدار هش ۱۲۸ بیتی نتیجه را محاسبه می‌کند. این مقدار هش را «Fingerprint نتیجهٔ کوئری» می‌نامیم. هش‌کردن «به شکل پایدار» انجام می‌شود (و باید بشود). یعنی هر وقت چیزی هش می‌شود که ممکن است بین جلسه‌های کامپایل تغییر کند (مثلاً DefId)، به‌جای آن معادل پایدارش (مثلاً DefPath متناظر) را هش می‌کنیم. زیرساخت StableHash برای همین است. به این ترتیب Fingerprintهای محاسبه‌شده در دو جلسهٔ کامپایل متفاوت همچنان قابل‌مقایسه‌اند.

    گام بعد ذخیرهٔ این fingerprintها در کنار گراف وابستگی است. این ارزان است چون fingerprintها فقط بایت‌هایی هستند که باید کپی شوند. بارگذاری کل مجموعهٔ fingerprintها همراه با گراف وابستگی هم ارزان است.

    حالا وقتی علامت‌گذاری red-green به نقطه‌ای می‌رسد که باید بررسی کند آیا نتیجه تغییر کرده، می‌تواند fingerprint قبلی (که از قبل بارگذاری شده) را با fingerprint نتیجهٔ جدید مقایسه کند.

    این رویکرد نسبتاً خوب کار می‌کند اما بی‌نقص نیست:

    • احتمال کمی برای برخورد هش (hash collision) هست. یعنی دو نتیجهٔ متفاوت می‌توانند fingerprint یکسان داشته باشند و سامانه به‌اشتباه فرض کند نتیجه تغییر نکرده، که به یک به‌روزرسانی ازدست‌رفته می‌انجامد.

      این خطر را با استفاده از تابع هش باکیفیت و مقدار هش ۱۲۸ بیتی کاهش می‌دهیم. به لطف این اقدامات خطر عملی برخورد هش ناچیز است.

    • محاسبهٔ fingerprint بسیار پرهزینه است. دلیل اصلی این است که کامپایل افزایشی می‌تواند کندتر از کامپایل غیرافزایشی باشد. مجبوریم از تابع هش خوب و در نتیجه پرهزینه استفاده کنیم، و هنگام هش‌کردن باید چیزها را به معادل پایدارشان نگاشت کنیم.

    داستان دو DepGraph: قدیمی و جدید

    توضیح اولیهٔ ردیابی وابستگی چند جزئیات را سرسری می‌گذراند که هنگام تلاش واقعی برای پیاده‌سازی به‌سرعت سردرگم‌کننده می‌شوند. به‌ویژه به‌آسانی می‌توان نادیده گرفت که در واقع با دو گراف وابستگی سروکار داریم: گرافی که در جلسهٔ کامپایل قبلی ساختیم و گرافی که برای جلسهٔ کامپایل فعلی می‌سازیم.

    وقتی جلسهٔ کامپایل شروع می‌شود، کامپایلر گراف وابستگی قبلی را به‌عنوان داده‌ای تغییرناپذیر در حافظه بارگذاری می‌کند. سپس وقتی کوئری فراخوانی می‌شود، ابتدا سعی می‌کند گرهٔ متناظر را در گراف سبز علامت بزند. این واقعاً یعنی سعی می‌کنیم گره‌ای را در dep-graph قبلی سبز علامت بزنیم که با کلید کوئری در جلسهٔ فعلی متناظر است. چگونه این نگاشت بین کلید کوئری فعلی و DepNode قبلی را انجام می‌دهیم؟ پاسخ دوباره Fingerprintهاست: گره‌های گراف وابستگی با fingerprint کلید کوئری شناسایی می‌شوند. چون fingerprintها بین جلسه‌های کامپایل پایدارند، محاسبهٔ یکی در جلسهٔ فعلی به ما اجازه می‌دهد گره‌ای را در گراف وابستگی از جلسهٔ قبلی بیابیم. اگر گره‌ای با fingerprint داده‌شده نیابیم، یعنی کلید کوئری به چیزی اشاره دارد که در جلسهٔ قبلی هنوز وجود نداشت.

    پس با یافتن dep-node در گراف وابستگی قبلی، می‌توانیم وابستگی‌هایش (یعنی dep-nodeهای دیگر در گراف قبلی) را جست‌وجو کنیم و با بقیهٔ الگوریتم try-mark-green ادامه دهیم. اتفاق جالب بعدی وقتی رخ می‌دهد که گره را با موفقیت سبز علامت زدیم. در آن نقطه گره و یال‌های آن به وابستگی‌هایش را از گراف قدیمی به گراف جدید کپی می‌کنیم. باید این کار را بکنیم چون dep-graph جدید نمی‌تواند گره و یال‌ها را از ردیابی معمول وابستگی به دست آورد. سامانهٔ ردیابی فقط هنگام اجرای واقعی کوئری می‌تواند یال‌ها را ثبت کند — اما اجرای کوئری، هرچند نتیجه از قبل cache شده، دقیقاً همان چیزی است که می‌خواهیم از آن پرهیز کنیم.

    وقتی جلسهٔ کامپایل تمام شد، همهٔ بخش‌های تغییرنکرده از گراف قدیمی به گراف جدید کپی شده‌اند، در حالی که بخش‌های تغییریافته توسط سامانهٔ ردیابی به گراف جدید افزوده شده‌اند. در این نقطه گراف جدید همراه با cache نتایج کوئری روی دیسک serialize می‌شود و می‌تواند در جلسهٔ کامپایل بعدی نقش dep-graph قبلی را بازی کند.

    چیزی را فراموش نکردید؟: ارتقای cache (cache promotion)

    سامانهٔ توصیف‌شده تا اینجا ویژگی کمی ظریف دارد: اگر همهٔ ورودی‌های یک dep-node سبز باشند، خود dep-node را می‌توان بدون محاسبه یا بارگذاری نتیجهٔ کوئری متناظر سبز علامت زد. اعمال تعدّی این ویژگی اغلب به وضعیتی می‌رسد که برخی نتایج میانی هرگز واقعاً از دیسک بارگذاری نمی‌شوند، مثل مثال زیر:

       input(A) <-- intermediate_query(B) <-- leaf_query(C)

    کامپایلر ممکن است برای تولید برخی آرتیفکت‌های خروجی به مقدار leaf_query(C) نیاز داشته باشد. اگر بتواند leaf_query(C) را سبز علامت بزند، نتیجه را از cache روی دیسک بارگذاری می‌کند. اما نتیجهٔ intermediate_query(B) هرگز بارگذاری نمی‌شود. در نتیجه، وقتی کامپایلر cache نتایج جدید را با نوشتن همهٔ نتایج کوئری در حافظه روی دیسک ماندگار می‌کند، intermediate_query(B) در حافظه نخواهد بود و در نتیجه در cache نتایج جدید گم می‌شود.

    اگر بعداً جلسهٔ کامپایل دیگری واقعاً به نتیجهٔ intermediate_query(B) نیاز داشته باشد، باید دوباره محاسبه شود، با اینکه درست پیش از آن نتیجهٔ کاملاً معتبری برایش در cache داشتیم.

    برای جلوگیری از این، کامپایلر کاری به نام «cache promotion» انجام می‌دهد: پیش از صدور cache نتایج جدید، همهٔ dep-nodeهای سبز را پیمایش می‌کند و مطمئن می‌شود نتیجهٔ کوئری آن‌ها در حافظه بارگذاری شده است. به این ترتیب cache نتایج بی‌دلیل دوباره کوچک نمی‌شود.

    کامپایل افزایشی و backend کامپایلر

    backend کامپایلر، بخشی که LLVM را درگیر می‌کند، از سامانهٔ کوئری استفاده می‌کند اما خودش بر حسب کوئری پیاده‌سازی نشده است. در نتیجه به‌طور خودکار در ردیابی وابستگی شرکت نمی‌کند. اما یکپارچگی دستی با سامانهٔ ردیابی نسبتاً سرراست است. کامپایلر فقط ردیابی می‌کند هنگام تولید نسخهٔ LLVM اولیهٔ هر واحد تولید کد (CGU) چه کوئری‌هایی فراخوانی می‌شوند، که به یک dep-node برای هر CGU می‌انجامد. در جلسه‌های کامپایل بعدی سعی می‌کند dep-node مربوط به یک CGU را سبز علامت بزند. اگر موفق شود، می‌داند فایل‌های شیء و bitcode متناظر روی دیسک هنوز معتبرند. اگر موفق نشود، کل CGU باید دوباره کامپایل شود.

    این همان رویکردی است که برای کوئری‌های معمولی به‌کار می‌رود. تفاوت‌های اصلی:

    • اینکه نمی‌توانیم به‌آسانی fingerprint برای ماژول‌های LLVM محاسبه کنیم (چون آن‌ها اشیای مات C++ هستند)،

    • اینکه منطق برخورد با مقادیر cache‌شده با کوئری‌های معمولی کاملاً متفاوت است چون اینجا فایل‌های bitcode و شیء به‌جای مقادیر serialize‌شدهٔ Rust در فایل مشترک cache نتایج داریم، و

    • اینکه عملیات پیرامون LLVM از نظر زمان محاسبه و مصرف حافظه آن‌قدر پرهزینه‌اند که باید کنترل دقیقی بر اینکه چه چیزی چه وقت اجرا می‌شود و چه چیزی تا کی در حافظه می‌ماند داشته باشیم.

    سامانهٔ کوئری احتمالاً می‌تواند با سازوکارهای همه‌منظوره برای برخورد با همهٔ موارد بالا گسترش یابد اما تاکنون این به نظر دردسری بیش از صرفه‌جویی می‌آمد.

    Query modifiers

    FIXME: rustc_middle::query::modifiers را به خانهٔ مستندات modifierهای کوئری تبدیل کنید، و همهٔ مستندات modifier مفید دیگر را پس از بررسی اینکه هنوز دقیق‌اند به آنجا مهاجرت دهید.

    سامانهٔ کوئری اجازه می‌دهد modifierها روی کوئری‌ها اعمال شوند. این modifierها بر جنبه‌های مشخصی از نحوهٔ برخورد سامانه با کوئری در رابطه با کامپایل افزایشی اثر می‌گذارند:

    • eval_always - کوئری‌ای با attribute با نام eval_always در کامپایل افزایشی بی‌قیدوشرط دوباره اجرا می‌شود. یعنی سامانه حتی سعی نمی‌کند dep-node کوئری را سبز علامت بزند. این attribute دو کاربرد دارد:

      • کوئری‌های eval_always می‌توانند ورودی‌ها را بخوانند (از فایل‌ها، حالت سراسری و غیره). همچنین می‌توانند اثرات جانبی مثل نوشتن در فایل‌ها و تغییر حالت سراسری ایجاد کنند.

      • برخی کوئری‌ها به احتمال زیاد دوباره ارزیابی می‌شوند چون نتیجه‌شان به کل کد منبع بستگی دارد. در این حالت eval_always می‌تواند به‌عنوان بهینه‌سازی به‌کار رود چون سامانه می‌تواند از ابتدا ثبت وابستگی‌ها را رد کند.

    • no_force - هرگز dep-nodeهای این کوئری را «force» نکن، حتی اگر نوع کلید کوئری قابل‌بازیابی باشد.

    • no_hash - اعمال no_hash روی یک کوئری به سامانه می‌گوید fingerprint نتیجهٔ کوئری را محاسبه نکند. این دو پیامد دارد:

      • محاسبه‌نکردن fingerprint می‌تواند زمان قابل‌توجهی صرفه‌جویی کند چون fingerprint‌گرفتن پرهزینه است، به‌ویژه برای مقادیر بزرگ و پیچیده.

      • بدون fingerprint، سامانه باید بی‌قیدوشرط فرض کند نتیجهٔ کوئری تغییر کرده است. در نتیجه هر چیزی که به کوئری no_hash وابسته باشد همیشه دوباره اجرا می‌شود.

      استفاده از no_hash برای کوئری در دو شرایط می‌تواند منطقی باشد:

      • اگر نتیجهٔ کوئری به احتمال زیاد با تغییر هر یک از ورودی‌هایش تغییر می‌کند، مثلاً تابعی مثل |a, b, c| -> (a * b * c). در چنین مواردی محاسبهٔ مجدد کوئری، اگر یکی از ورودی‌ها قرمز باشد، همیشه گره قرمز می‌دهد، پس می‌توانیم از زحمت پرهیز کنیم و فوراً به قرمز پیش‌فرض برویم. مثال نقض تابعی مثل |a| -> (a == 42) است که نتیجه‌اش برای بیشتر تغییرات a تغییر نمی‌کند.

      • اگر نتیجهٔ کوئری مجموعهٔ بزرگ یکپارچه‌ای باشد (مثلاً index_hir) و «کوئری‌های تصویرگر (projection)» از آن مجموعه بخوانند (مثلاً hir_owner). در چنین موردی مجموعهٔ بزرگ احتمالاً شرط بالا را برآورده می‌کند (هر ورودی تغییریافته یعنی محاسبهٔ مجدد کل مجموعه) و نتایج کوئری‌های تصویرگر به هر حال هش می‌شوند. اگر کوئری مجموعه را هم هش کنیم، یعنی عملاً همان داده را دو بار هش می‌کنیم: یک بار هنگام هش‌کردن مجموعه و بار دیگر هنگام هش‌کردن همهٔ نتایج کوئری‌های تصویرگر. no_hash اجازه می‌دهد از آن افزونگی پرهیز کنیم و کوئری‌های تصویرگر مثل یک «دیوار آتش» عمل می‌کنند و وابسته‌هایشان را از گرهٔ همیشه‌قرمز no_hash محافظت می‌کنند.

    • cache_on_disk - مقادیر بازگشتی کوئری روی دیسک cache می‌شوند و اگر dep node متناظر سبز باشد جلسه‌های بعدی می‌توانند آن‌ها را بارگذاری کنند. اگر modifier با نام separate_provide_extern هم وجود داشته باشد، مقادیر فقط برای کلیدهای «محلی» روی دیسک cache می‌شوند، چون مقادیر crateهای خارجی باید از فرادادهٔ crate قابل‌بارگذاری باشند.

    • feedable - کوئری در واقع تابع نیست، بلکه نوع arena خودش است. این کار برای اعلان یک arena، «تغذیه» (feed) اطلاعاتی که باید در نقطه‌ای دیرتر از کامپایل ذخیره شود (مثلاً وقتی واقعاً شیء Crate در دسترس داریم)، و سپس بازیابی آن مثل هر crate دیگر انجام می‌شود. بنابراین تعریف تابع برای این کوئری‌ها وجود ندارد.

    الگوی کوئری تصویرگر (projection)

    جالب است بدانیم eval_always و no_hash را می‌توان با هم در الگوی به‌اصطلاح «کوئری تصویرگر» به‌کار برد. اغلب پیش می‌آید که کوئری‌ای به کل ورودی کامپایلر وابسته باشد (مثلاً HIR نمایه‌شده) و کوئری دیگری مقادیر جداگانه را از این مقدار یکپارچه تصویر (project) کند (مثلاً آیتم HIR با DefId مشخص). این کوئری‌های تصویرگر اجازه می‌دهند «دیوار آتش» ردیابی تغییر بسازیم چون حتی اگر نتیجهٔ کوئری یکپارچه تغییر کند (که بسیار محتمل است)، تصویرهای کوچک همچنان بیشتر می‌توانند سبز علامت بخورند.

      +------------+
  |            |           +---------------+           +--------+
  |            | <---------| projection(x) | <---------| foo(a) |
  |            |           +---------------+           +--------+
  |            |
  | monolithic |           +---------------+           +--------+
  |   query    | <---------| projection(y) | <---------| bar(b) |
  |            |           +---------------+           +--------+
  |            |
  |            |           +---------------+           +--------+
  |            | <---------| projection(z) | <---------| baz(c) |
  |            |           +---------------+           +--------+
  +------------+

    فرض کنید نتیجهٔ monolithic_query طوری تغییر کند که نتیجهٔ projection(x) هم تغییر کرده باشد، یعنی dep-nodeهای هر دو قرمز علامت می‌خورند. در نتیجه foo(a) باید دوباره اجرا شود؛ اما bar(b) و baz(c) را می‌توان سبز علامت زد. اما اگر foo، bar و baz مستقیماً به monolithic_query وابسته بودند، همهٔ آن‌ها باید دوباره ارزیابی می‌شدند.

    این الگو حتی بدون eval_always و no_hash هم کار می‌کند اما آن دو modifier می‌توانند برای پرهیز از سربار غیرضروری به‌کار روند. اگر کوئری یکپارچه با هر تغییر جزئی در ورودی کامپایلر احتمالاً تغییر می‌کند، منطقی است آن را eval_always علامت بزنیم و هزینهٔ ردیابی وابستگی‌اش را حذف کنیم. و همیشه منطقی است کوئری یکپارچه را no_hash علامت بزنیم چون تصویرها را داریم که تا حد ممکن سبز نگه داشتن چیزها را تضمین می‌کنند.

    کاستی‌های سامانهٔ فعلی

    چیزهای زیادی هست که هنوز می‌توان بهبودشان داد.

    افزایشی‌بودن ساختارهای داده روی دیسک

    سامانهٔ فعلی نمی‌تواند cacheهای روی دیسک و گراف وابستگی را در جا به‌روز کند. به‌جای آن مجبور است هر فایل را در هر جلسهٔ کامپایل کاملاً بازنویسی کند. سربار این کار چند درصد از کل زمان کامپایل است.

    Unnecessary data dependencies

    ساختارهای داده‌ای که به‌عنوان نتایج کوئری به‌کار می‌روند می‌توانند طوری بازتجزیه شوند که یال‌هایی را از گراف وابستگی حذف کنند. به‌ویژه اطلاعات «span» بسیار ناپایدار است، پس گنجاندن آن در نتیجهٔ کوئری احتمال اینکه نتیجه دوباره‌قابل‌استفاده نباشد را بالا می‌برد. برای اطلاعات بیشتر https://github.com/rust-lang/rust/issues/47389 را ببینید.
