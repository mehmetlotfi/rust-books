    محیط‌های نوع‌گذاری/پارامتر (Typing/Parameter environments)

    محیط‌های نوع‌گذاری (Typing environments)

    هنگام تعامل با سامانهٔ نوع، چند متغیر وجود دارد که باید در نظر گرفت و می‌توانند بر نتایج حل صفت اثر بگذارند. مجموعهٔ where clauseهای در دسترس، و اینکه عملیات سامانهٔ نوع در کدام فاز کامپایلر انجام می‌شود (به‌ترتیب ساختارهای ParamEnv و TypingMode).

    وقتی هنوز محیطی برای انجام عملیات سامانهٔ نوع ساخته نشده است، می‌توان از TypingEnv برای بسته‌بندی همهٔ بافت بیرونی لازم در یک نوع واحد استفاده کرد.

    پس از ساخته شدن بافتی برای انجام عملیات سامانهٔ نوع (مثلاً یک ObligationCtxt یا FnCtxt) معمولاً TypingEnv در جایی ذخیره نمی‌شود، چون فقط TypingMode ویژگی کل محیط است، در حالی که ParamEnvهای مختلف را می‌توان برای هر goal به‌طور جداگانه به کار برد.

    محیط‌های پارامتر (Parameter environments)

    ParamEnv چیست

    ParamEnv فهرستی از where-clauseهای در دسترس است و معمولاً با where clauseهای یک آیتم مشخص متناظر است. برخی clauseها صریحاً نوشته نمی‌شوند بلکه به‌طور ضمنی در query ‏clauses_of اضافه می‌شوند، مانند ConstArgHasType یا (برخی) کران‌های ضمنی.

    در بیشتر موارد ParamEnvها ابتدا از طریق param_env query ساخته می‌شوند که ParamEnvای برمی‌گرداند که از where clauseهای آیتم داده‌شده استخراج شده است. همچنین می‌توان ParamEnv را با مجموعه‌های دلخواهی از clauseها ساخت که از آیتم مشخصی استخراج نشده‌اند، مانند compare_method_clause_entailment که در آن یک ParamEnv ترکیبی می‌سازیم که از where clauseهای impl و where clauseهای تابعِ تعریف صفت تشکیل شده است.

    اگر تابعی مانند این داشته باشیم:

    // `foo` would have a `ParamEnv` of:
// `[T: Sized, T: Trait, <T as Trait>::Assoc: Clone]`
fn foo<T: Trait>()
where
    <T as Trait>::Assoc: Clone,
{}

    اگر از نظر مفهومی درون foo باشیم (مثلاً هنگام بررسی نوع یا lint کردن آن)، از این ParamEnv در همه‌جا که با سامانهٔ نوع تعامل داریم استفاده می‌کنیم. این به کارهایی مانند نرمال‌سازی، ارزیابی ثابت‌های جنریک و اثبات where clauseها/goalها اجازه می‌دهد به اندازه‌دار (sized) بودن T، پیاده‌سازی Trait و غیره تکیه کنند.

    یک مثال مشخص‌تر:

    // `foo` would have a `ParamEnv` of:
// `[T: Sized, T: Clone]`
fn foo<T: Clone>(a: T) {
    // when typechecking `foo` we require all the where clauses on `requires_clone`
    // to hold in order for it to be legal to call. This means we have to
    // prove `T: Clone`. As we are type checking `foo` we use `foo`'s
    // environment when trying to check that `T: Clone` holds.
    //
    // Trying to prove `T: Clone` with a `ParamEnv` of `[T: Sized, T: Clone]`
    // will trivially succeed as bound we want to prove is in our environment.
    requires_clone(a);
}

    یا به‌عنوان جایگزین، مثالی که کامپایل نمی‌شود:

    // `foo2` would have a `ParamEnv` of:
// `[T: Sized]`
fn foo2<T>(a: T) {
    // When typechecking `foo2` we attempt to prove `T: Clone`.
    // As we are type checking `foo2` we use `foo2`'s environment
    // when trying to prove `T: Clone`.
    //
    // Trying to prove `T: Clone` with a `ParamEnv` of `[T: Sized]` will
    // fail as there is nothing in the environment telling the trait solver
    // that `T` implements `Clone` and there exists no user written impl
    // that could apply.
    requires_clone(a);
}

    به دست آوردن یک ParamEnv

    استفاده از ParamEnv نادرست هنگام تعامل با سامانهٔ نوع می‌تواند به ICE، کامپایل شدن برنامه‌های نادرست‌ساخت (ill-formed)، یا خطا دادن در جایی که نباید، بینجامد. #82159 و #82067 را به‌عنوان نمونه‌هایی از PRهایی ببینید که کامپایلر را برای استفاده از param env درست تغییر دادند و در این فرایند ICEها را رفع کردند.

    در اکثریت قاطع موارد، وقتی ParamEnv لازم است یا از قبل جایی در دامنه وجود دارد، یا بالاتر در call stack و باید پایین فرستاده شود. فهرستی غیرجامع از جاهایی که ممکن است ParamEnv موجود پیدا کنید:

    • در حین typeck، FnCtxt یک فیلد param_env دارد
    • هنگام نوشتن late lintها، LateContext یک فیلد param_env دارد
    • در حین بررسی well-formed بودن، WfCheckingCtxt یک فیلد param_env دارد
    • TypeChecker که برای MIR Typeck به کار می‌رود یک فیلد param_env دارد
    • در حل‌کنندهٔ صفت نسل بعد، همهٔ Goalها یک فیلد param_env دارند که مشخص می‌کند goal در کدام محیط اثبات شود
    • هنگام ویرایش یک TypeRelation موجود، اگر PredicateEmittingRelation را پیاده‌سازی کند، یک متد param_env در دسترس خواهد بود.

    اگر مطمئن نیستید ParamEnvای جایی در دامنه هست که بتوان از آن استفاده کرد، شاید ارزش داشته باشد در کانال Zulip به نام #t-compiler/help رشته‌ای باز کنید تا کسی بتواند نشان دهد از کجا می‌توان ParamEnv به دست آورد.

    ساخت دستی یک ParamEnv معمولاً فقط در آغاز نوعی تحلیل سطح بالا لازم است (مثلاً hir typeck یا borrow checking). در چنین مواردی سه راه برای انجام آن وجود دارد:

    • فراخوانی query ‏tcx.param_env(def_id) که محیط مرتبط با یک تعریف مفروض را برمی‌گرداند.
    • ساخت یک محیط خالی با ParamEnv::empty.
    • استفاده از ParamEnv::new برای ساخت یک محیط با مجموعه‌ای دلخواه از where clauseها. سپس فراخوانی traits::normalize_param_env_or_error برای مدیریت نرمال‌سازی و بسط (elaborate) همهٔ where clauseهای محیط.

    استفاده از query ‏param_env با فاصله رایج‌ترین راه ساخت ParamEnv است، چون بیشتر اوقات کامپایلر تحلیلی را به‌عنوان بخشی از یک تعریف مشخص انجام می‌دهد.

    ساخت محیط خالی با ParamEnv::empty معمولاً فقط یا در codegen انجام می‌شود (به‌طور غیرمستقیم از طریق TypingEnv::fully_monomorphized)، یا به‌عنوان بخشی از تحلیل‌هایی که انتظار ندارند هرگز با پارامترهای جنریک روبه‌رو شوند (مثلاً بخش‌های گوناگون coherence/orphan check).

    ساخت یک محیط از مجموعه‌ای دلخواه از where clauseها معمولاً غیرضروری است و فقط باید انجام شود که محیط موردنیاز شما با آیتم واقعی در کد منبع متناظر نباشد (مثلاً compare_method_clause_entailment).

    چگونه ParamEnvها ساخته می‌شوند

    ساخت یک ParamEnv پیچیده‌تر از استفادهٔ ساده از فهرست where clauseهای تعریف‌شده روی یک آیتم است، همان‌طور که کاربر نوشته است. هم باید صفت‌های بالادستی (supertrait) را در محیط بسط دهیم و هم همهٔ aliasها را کاملاً نرمال کنیم. این منطق را traits::normalize_param_env_or_error مدیریت می‌کند (هرچند در نامش به بسط اشاره‌ای نشده است).

    بسط صفت‌های بالادستی (Elaborating supertraits)

    وقتی تابعی مانند fn foo<T: Copy>() داریم، می‌خواهیم بتوانیم T: Clone را درون تابع اثبات کنیم، چون صفت Copy یک صفت بالادستی Clone دارد. ساخت ParamEnv به همهٔ کران‌های صفت در محیط نگاه می‌کند و برای هر صفت بالادستی‌ای که روی صفت‌ها بیابد صراحتاً where clauseهای جدیدی به ParamEnv اضافه می‌کند.

    یک مثال مشخص تابع زیر خواهد بود:

    trait Trait: SuperTrait {}
trait SuperTrait: SuperSuperTrait {}

// `bar`'s unelaborated `ParamEnv` would be:
// `[T: Sized, T: Copy, T: Trait]`
fn bar<T: Copy + Trait>(a: T) {
    requires_impl(a);
}

fn requires_impl<T: Clone + SuperSuperTrait>(a: T) {}

    اگر محیط را بسط نمی‌دادیم، فراخوانی requires_impl در بررسی نوع شکست می‌خورد، چون نمی‌توانستیم T: Clone یا T: SuperSuperTrait را اثبات کنیم. در عمل محیط را بسط می‌دهیم، یعنی در bar، ParamEnv در واقع چنین است: [T: Sized, T: Copy, T: Clone, T: Trait, T: SuperTrait, T: SuperSuperTrait] این به ما اجازه می‌دهد هم T: Clone و هم T: SuperSuperTrait را هنگام بررسی نوع bar اثبات کنیم.

    صفت Clone یک صفت بالادستی Sized دارد، اما در محیط دو کران T: Sized نخواهیم داشت (یکی برای صفت بالادستی و یکی برای کران T: Sized که به‌طور ضمنی اضافه شده)، چون فرایند بسط (که با util::elaborate پیاده‌سازی شده) where clauseها را از تکرار پاک می‌کند.

    یک اثر جانبی این است که حتی اگر هیچ بسط واقعی صفت‌های بالادستی رخ ندهد، where clauseهای موجود در محیط نیز از تکرار پاک می‌شوند. مثال زیر را ببینید:

    trait Trait {}
// The unelaborated `ParamEnv` would be:
// `[T: Sized, T: Trait, T: Trait]`
// but after elaboration it would be:
// `[T: Sized, T: Trait]`
fn foo<T: Trait + Trait>() {}

    حل‌کنندهٔ صفت نسل بعد هم لازم دارد این بسط انجام شود.

    نرمال‌سازی همهٔ کران‌ها

    در حل‌کنندهٔ صفت قدیمی، where clauseهای ذخیره‌شده در ParamEnv باید کاملاً نرمال باشند، وگرنه حل‌کنندهٔ صفت درست کار نمی‌کند. یک مثال مشخص از نیاز به نرمال‌سازی ParamEnv این است:

    trait Trait<T> {
    type Assoc;
}

trait Other {
    type Bar;
}

impl<T> Other for T {
    type Bar = u32;
}

// `foo`'s unnormalized `ParamEnv` would be:
// `[T: Sized, U: Sized, U: Trait<T::Bar>]`
fn foo<T, U>(a: U)
where
    U: Trait<<T as Other>::Bar>,
{
    requires_impl(a);
}

fn requires_impl<U: Trait<u32>>(_: U) {}

    ما انسان‌ها می‌توانیم تشخیص دهیم <T as Other>::Bar با u32 برابر است، پس کران صفت روی U معادل U: Trait<u32> است. در عمل، تلاش برای اثبات U: Trait<u32> در حل‌کنندهٔ قدیمی در این محیط شکست می‌خورد، چون نمی‌تواند تشخیص دهد <T as Other>::Bar با u32 برابر است.

    برای دور زدن این مشکل، ParamEnvها را پس از ساخته شدن نرمال می‌کنیم تا در foo، ParamEnv در واقع چنین باشد: [T: Sized, U: Sized, U: Trait<u32>] که یعنی حل‌کنندهٔ صفت اکنون می‌تواند از U: Trait<u32> موجود در ParamEnv استفاده کند تا تشخیص دهد کران صفت U: Trait<u32> برقرار است.

    این راه‌حل موقت در همهٔ موارد کار نمی‌کند، چون نرمال‌سازی نوع‌های وابسته به یک ParamEnv نیاز دارد که یک مشکل خودراه‌انداز (bootstrapping) ایجاد می‌کند. برای اینکه نرمال‌سازی نتایج درست بدهد به یک ParamEnv نرمال‌شده نیاز داریم، اما برای به دست آوردن آن ParamEnv باید نرمال کنیم. در حال حاضر ParamEnv را یک بار با استفاده از param env نرمال‌نشده نرمال می‌کنیم و در عمل معمولاً نتایج قابل‌قبولی می‌دهد، هرچند مثال‌هایی وجود دارد که در آن‌ها از کار می‌افتد (مثال).

    در حل‌کنندهٔ صفت نسل بعد، الزام کاملاً نرمال بودن همهٔ where clauseهای ParamEnv وجود ندارد و بنابراین هنگام ساخت ParamEnvها نرمال‌سازی نمی‌کنیم.

    حالت‌های نوع‌گذاری (Typing modes)

    بسته به اینکه عملیات سامانهٔ نوع را در چه بافتی انجام می‌دهیم، ممکن است رفتار متفاوتی لازم باشد. برای مثال در حین coherence الزامات سخت‌گیرانه‌تری دربارهٔ اینکه چه زمانی می‌توانیم goalها را برقرارنشده بدانیم یا نوع‌ها را نابرابر بدانیم وجود دارد.

    پیگیری اینکه عملیات سامانهٔ نوع در کدام «فاز» کامپایلر انجام می‌شود توسط enum ‏TypingMode انجام می‌شود. مستندات enum ‏TypingMode کاملاً خوب است، پس به‌جای تکرار کلمه‌به‌کلمهٔ آن در اینجا توصیه می‌کنیم مستندات API را مستقیماً بخوانید.
