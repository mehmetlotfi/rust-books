    نام‌های مستعار و نرمال‌سازی (Aliases and normalization)

    نام‌های مستعار (Aliases)

    در Rust تعدادی نوع وجود دارد که برابر با یک نوع «زیرین» در نظر گرفته می‌شوند. نمونه‌ها عبارت‌اند از نوع‌های وابستهٔ ذاتی (inherent)، نوع‌های وابستهٔ صفت، نام‌های مستعار نوع آزاد (type Foo = u32) و نوع‌های opaque (-> impl RPIT). چنین نوع‌هایی را «alias» (نام مستعار) می‌نامیم. نوع‌های alias با گونهٔ TyKind::Alias نمایش داده می‌شوند و نوع alias را enum ‏AliasTyKind ردیابی می‌کند.

    نرمال‌سازی (normalization) فرایند گرفتن این نوع‌های alias و جایگزین کردن آن‌ها با نوع زیرینی است که با آن برابرند. برای مثال، با داشتن نام مستعار type Foo = u32، نرمال کردن Foo نتیجهٔ u32 را می‌دهد.

    افزون بر نوع‌ها، مفهوم alias دربارهٔ ثابت‌ها/const generics نیز صدق می‌کند. اما در حال حاضر در کامپایلر، aliasهای const را واقعاً «مفهومی درجه‌یک» تلقی نمی‌کنیم، بنابراین این فصل بیشتر مطالب را در بستر نوع‌ها بحث می‌کند (هرچند مفاهیم به‌خوبی منتقل می‌شوند).

    aliasهای صلب، مبهم و نرمال‌نشده

    aliasها یا «صلب» (rigid)، یا «مبهم» (ambiguous) و یا صرفاً نرمال‌نشده‌اند.

    نوع‌ها را صلب می‌دانیم اگر «شکل» آن‌ها تغییر نکند. برای مثال، Box صلب است چون هیچ مقدار نرمال‌سازی نمی‌تواند Box را به u32 تبدیل کند، در حالی که <vec::IntoIter<u32> as Iterator>::Item صلب نیست چون می‌توان آن را به u32 نرمال کرد.

    aliasها زمانی صلب‌اند که هرگز نتوانیم آن‌ها را بیشتر نرمال کنیم. یک نمونهٔ مشخص از alias صلب، <T as Iterator>::Item در محیطی است که کران T: Iterator<Item = ...> در آن وجود ندارد و فقط کران T: Iterator هست:

    fn foo<T: Iterator>() {
    // This alias is *rigid*
    let _: <T as Iterator>::Item;
}

fn bar<T: Iterator<Item = u32>>() {
    // This alias is *not* rigid as it can be normalized to `u32`
    let _: <T as Iterator>::Item;
}

    وقتی یک alias هنوز نمی‌تواند نرمال شود اما ممکن است در محیط جاری نرمال‌پذیر از آب درآید، آن را alias «مبهم» می‌دانیم. این می‌تواند وقتی رخ دهد که alias شامل متغیرهای استنتاج باشد که مانع از تعیین چگونگی پیاده‌سازی صفت می‌شوند:

    fn foo<T: Iterator, U: Iterator>() {
    // This alias is considered to be "ambiguous"
    let _: <_ as Iterator>::Item;
}

    دلیل اینکه آن‌ها را aliasهای «مبهم» می‌نامیم این است که مبهم است که این alias صلب هست یا نه.

    منبع پیاده‌سازی صفت _: Iterator مبهم (یعنی ناشناخته) است. ممکن است یک impl Iterator for u32 باشد یا یک کران صفت T: Iterator؛ هنوز نمی‌دانیم. بسته به اینکه چرا _: Iterator برقرار است، alias می‌تواند نرمال‌نشده یا صلب باشد؛ مبهم است که این چه نوع aliasی است.

    سرانجام، یک alias می‌تواند صرفاً نرمال‌نشده باشد. <Vec<u32> as IntoIterator>::Iter یک alias نرمال‌نشده است چون از پیش می‌توان آن را به std::vec::IntoIter<u32> نرمال کرد، فقط هنوز این کار انجام نشده است.

    شایان ذکر است که aliasهای آزاد (Free) و ذاتی (Inherent) نمی‌توانند صلب یا مبهم باشند، چون نام بردن از آن‌ها به معنای حل‌شدن تعریف alias نیز هست که نوع زیرین alias را مشخص می‌کند.

    aliasهای واگرا (Diverging)

    یک alias «واگرا» (diverge) تلقی می‌شود اگر تعریفش نوع زیرین غیر-aliasی را برای نرمال شدن مشخص نکند. یک نمونهٔ مشخص از aliasهای واگرا:

    type Diverges = Diverges;

trait Trait {
    type DivergingAssoc;
}
impl Trait for () {
    type DivergingAssoc = <() as Trait>::DivergingAssoc;
}

    در این مثال، هم Diverges و هم DivergingAssoc موارد «بدیهی» نام‌های مستعار نوع واگرا هستند که در آن‌ها برابر با خودشان تعریف شده‌اند. هیچ نوع زیرینی وجود ندارد که Diverges هرگز بتواند به آن نرمال شود.

    عموماً سعی می‌کنیم هنگام تعریف aliasهای واگرا خطا بدهیم، اما این کاملاً بررسی «با بهترین تلاش» است. در مثال قبل، تعریف‌ها «به‌اندازهٔ کافی ساده‌اند» که شناسایی شوند و در نتیجه خطا صادر می‌شود. اما در موارد پیچیده‌تر، یا مواردی که فقط برخی نمونه‌سازی‌های پارامترهای جنریک به alias واگرا می‌انجامند، خطا صادر نمی‌کنیم:

    trait Trait {
    type DivergingAssoc<U: Trait>;
}
impl<T: ?Sized> Trait for T {
    // This alias always diverges but we don't emit an error because
    // the compiler can't "see" that.
    type DivergingAssoc<U: Trait> = <U as Trait>::DivergingAssoc<U>;
}

    در نهایت این یعنی هیچ تضمینی نداریم که aliasها در سامانهٔ نوع واگرا نباشند. از آنجا که aliasها ممکن است فقط برای برخی آرگومان‌های جنریک مشخص واگرا شوند، همچنین یعنی فقط وقتی می‌دانیم alias واگراست که کاملاً مشخص (concrete) شده باشد. این یعنی codegen/ارزیابی const نیز باید aliasهای واگرا را مدیریت کند:

    trait Trait {
    type Diverges<U: Trait>;
}
impl<T: ?Sized> Trait for T {
    type Diverges<U: Trait> = <U as Trait>::Diverges<U>;
}

fn foo<T: Trait>() {
    let a: T::Diverges<T>;
}

fn main() {
    foo::<()>();
}

    در این مثال، فقط در حین codegen مربوط به foo::<()> با خطای alias واگرا روبه‌رو می‌شویم. اگر فراخوانی foo حذف شود، هیچ خطای کامپایلی صادر نخواهد شد.

    نوع‌های opaque

    نوع‌های opaque نوع نسبتاً ویژه‌ای از alias هستند و در فصل مخصوص خودشان پوشش داده شده‌اند.

    aliasهای const

    برخلاف نام‌های مستعار نوع، aliasهای const مستقیماً در سامانهٔ نوع نمایش داده نمی‌شوند. در عوض، aliasهای const همیشه یک بدنهٔ ناشناس‌اند که حاوی یک عبارت مسیر به یک آیتم const است. این یعنی تنها «alias const» در سامانهٔ نوع، یک بدنهٔ const ناشناسِ ارزیابی‌نشده است.

    به همین دلیل ConstKind::Alias(AliasCtKind::Projection/Inherent/Free, _) وجود ندارد. در عوض فقط ConstKind::Unevaluated داریم که برای نمایش ثابت‌های ناشناس به کار می‌رود.

    fn foo<const N: usize>() {}

const FREE_CONST: usize = 1 + 1;

fn bar() {
    foo::<{ FREE_CONST }>();
    // The const arg is represented with some anonymous constant:
    // ```pseudo-rust
    // const ANON: usize = FREE_CONST;
    // foo::<ConstKind::Unevaluated(DefId(ANON), [])>();
    // ```
}

    این احتمالاً با بهبود قابلیت const generics تغییر خواهد کرد. برای مثال، feature(associated_const_equality) و feature(gca_min_const_items) هر دو نیاز دارند aliasهای const مشابه نوع‌ها مدیریت شوند (بدون ثابت ناشناسی که همهٔ آرگومان‌های const را بپوشاند).

    نرمال‌سازی چیست

    نرمال‌سازی ساختاری در برابر عمیق

    دو شکل نرمال‌سازی وجود دارد: ساختاری (structural، که گاهی سطحی نامیده می‌شود) و عمیق (deep). نرمال‌سازی ساختاری را باید فقط نرمال کردن بخش «بیرونی‌ترین» یک نوع دانست. در مقابل، نرمال‌سازی عمیق همهٔ aliasها را در یک نوع نرمال می‌کند.

    در عمل، نرمال‌سازی ساختاری می‌تواند به نرمال شدن چیزی بیش از لایهٔ بیرونی نوع بینجامد، اما نباید به این رفتار تکیه کرد. aliasهای غیرصلبِ نرمال‌ناپذیر که از متغیرهای مقید (for<'a>) استفاده می‌کنند را هیچ‌یک از دو نوع نرمال‌سازی نمی‌تواند نرمال کند.

    برای نمونه: از نظر مفهومی، نرمال‌سازی ساختاری نوع Vec<<u8 as Identity>::Assoc> هیچ کاری نمی‌کند، در حالی که نرمال‌سازی عمیق Vec<u8> می‌دهد. در عمل، حتی نرمال‌سازی ساختاری هم Vec<u8> می‌دهد، اما باز هم نباید به آن تکیه کرد.

    تغییر alias به‌گونه‌ای که از متغیرهای مقید استفاده کند رفتار متفاوتی به بار می‌آورد؛ Vec<for<'a> fn(<&'a u8 as Identity>::Assoc)> با نرمال‌سازی ساختاری تغییری نمی‌کند، اما با نرمال‌سازی عمیق به Vec<for<'a> fn(&'a u8)> می‌رسد.

    منطق هستهٔ نرمال‌سازی

    نرمال‌سازی ساختاری aliasها کمی ظریف‌تر از جایگزین کردن alias با هر چیزی است که تعریفش آن را برابر با آن می‌داند؛ نتیجهٔ نرمال کردن یک alias باید یا یک نوع صلب باشد یا یک متغیر استنتاج (که بعداً به یک نوع صلب استنتاج خواهد شد). برای دستیابی به این، دو کار می‌کنیم:

    اول، هنگام نرمال کردن یک alias مبهم، آن را به‌جای رها کردن به همان صورت، به یک متغیر استنتاج نرمال می‌کنیم. این دو اثر اصلی دارد:

    • هرچند متغیر استنتاج نوع صلب نیست، همیشه در نهایت به یک نوع صلب استنتاج می‌شود، پس مطمئن می‌شویم نتیجهٔ نرمال‌سازی نیازی به نرمال شدن دوباره نخواهد داشت
    • متغیرهای استنتاج در همهٔ مواردی که نوع غیرصلب است به کار می‌روند و به بقیهٔ کامپایلر اجازه می‌دهند مجبور نباشد هم با aliasهای مبهم و هم با متغیرهای استنتاج سروکار داشته باشد

    دوم، به‌جای اینکه نرمال‌سازی مستقیماً نوع مشخص‌شده در تعریف alias را برگرداند، ابتدا آن نوع را نرمال می‌کنیم و بعد برمی‌گردانیم1. این را انجام می‌دهیم تا نرمال‌سازی خودتوان (idempotent) باشد/فراخواننده‌ها نیازی نداشته باشند آن را در یک حلقه اجرا کنند.

    #![feature(checked_type_alias)]

type Foo<T: Iterator> = Bar<T>;
type Bar<T: Iterator> = <T as Iterator>::Item;

fn foo() {
    let a_: Foo<_>;
}

    در این مثال:

    • نرمال کردن Foo<?x> به Bar<?x> می‌انجامد، جز اینکه می‌خواهیم aliasها را در نوعی که Foo برابر با آن تعریف شده نرمال کنیم
    • نرمال کردن Bar<?x> به <?x as Iterator>::Item می‌انجامد، جز اینکه باز هم می‌خواهیم aliasها را در نوعی که Bar برابر با آن تعریف شده نرمال کنیم
    • نرمال کردن <?x as Iterator>::Item به یک متغیر استنتاج جدید ?y می‌انجامد، چون <?x as Iterator>::Item یک alias مبهم است
    • نتیجهٔ نهایی این است که نرمال کردن Foo<?x> به ?y می‌انجامد

    چگونه نرمال کنیم

    هنگام تعامل با سامانهٔ نوع، اغلب لازم می‌شود درخواست نرمال شدن یک نوع داده شود. چند نقطهٔ ورودی مختلف به منطق نرمال‌سازی زیرین وجود دارد و هر نقطهٔ ورود فقط باید در بخش‌های مشخصی از کامپایلر استفاده شود.

    پیچیدگی دیگر این است که کامپایلر در حال حاضر در حال گذار از solver قدیمی صفت به solver جدید صفت است. به‌عنوان بخشی از این گذار، رویکرد ما به نرمال‌سازی در کامپایلر به‌طور نسبتاً قابل‌توجهی تغییر کرده است، و در نتیجه برخی نقاط ورود نرمال‌سازی «فقط برای solver قدیمی» هستند و قرار است پس از پایدار شدن solver جدید در بلندمدت حذف شوند. می‌توانید این گذار را از طریق برچسب WG-trait-system-refactor در GitHub دنبال کنید.

    در ادامه مروری کلی بر نقاط ورود مختلف نرمال‌سازی در کامپایلر آمده است:

    • infcx.at.structurally_normalize
    • infcx.at.(deeply_)?normalize
    • infcx.query_normalize
    • tcx.normalize_erasing_regions
    • traits::normalize_with_depth(_to)
    • EvalCtxt::structurally_normalize

    بیرون از solver صفت

    نوع InferCtxt راه‌های «اصلی» نرمال‌سازی در حین تحلیل را در دسترس می‌گذارد: normalize, deeply_normalize, and structurally_normalize. این توابع اغلب بسته‌بندی شده و روی انواع wrapper گوناگون InferCtxt دوباره در دسترس قرار می‌گیرند، مانند FnCtxt یا ObligationCtxt، با تغییرات جزئی API برای مدیریت خودکار برخی آرگومان‌ها یا بخش‌هایی از نوع بازگشتی.

    نرمال‌سازی ساختاری InferCtxt

    infcx.at.structurally_normalize نرمال‌سازی ساختاری‌ای را فراهم می‌کند که می‌تواند متغیرهای استنتاج و regionها را مدیریت کند. عموماً باید هر زمان که نوعِ (kind) یک type بررسی می‌شود به کار رود.

    در درون HIR Typeck، روش نرمال‌سازی مرتبط دیگری هست، fcx.structurally_resolve، که اگر نوعِ در حال حل، یک متغیر استنتاج حل‌نشده باشد خطا می‌دهد. وقتی solver جدید فعال باشد، سعی می‌کند نوع را به‌صورت ساختاری نیز نرمال کند.

    به همین دلیل، الگویی در HIR typeck هست که در آن یک نوع ابتدا با normalize نرمال می‌شود (که فقط در solver قدیمی نرمال می‌کند)، و سپس structurally_resolve می‌شود (که فقط در solver جدید نرمال می‌کند). این الگو باید بر فراخوانی structurally_normalize در حین HIR typeck ترجیح داده شود، زیرا structurally_resolve سعی می‌کند با ارزیابی goalها پیشرفت استنتاج ایجاد کند، در حالی که structurally_normalize این کار را نمی‌کند.

    نرمال‌سازی عمیق InferCtxt

    infcx.at.(deeply_)?normalize

    دو راه برای نرمال‌سازی عمیق با InferCtxt وجود دارد: normalize و deeply_normalize. دلیلش این است که normalize یک نقطهٔ ورود نرمال‌سازی «قدیمی» است که فقط solver قدیمی از آن استفاده می‌کند، در حالی که deeply_normalize قرار است راه بلندمدت نرمال‌سازی عمیق باشد. هر دوی این متدها می‌توانند regionها را مدیریت کنند.

    وقتی solver جدید پایدار شود، تابع infcx.at.normalize حذف خواهد شد و همه‌چیز به متدهای جدید نرمال‌سازی عمیق یا ساختاری مهاجرت داده شده خواهد بود. به همین دلیل، تابع normalize در solver جدید هیچ کاری نمی‌کند، و فقط وقتی مناسب است که solver قدیمی به نرمال‌سازی نیاز دارد اما solver جدید ندارد.

    استفاده از deeply_normalize هنگام برخورد با aliasهای مبهم2 به صدور خطا می‌انجامد، چون امکان ندارد نرمال کردن همهٔ aliasهای مبهم به متغیرهای استنتاج پشتیبانی شود3. deeply_normalize عموماً فقط باید در مواردی به کار رود که انتظار نداریم با aliasهای مبهم روبه‌رو شویم، مثلاً هنگام کار با نوع‌های امضای آیتم‌ها.

    infcx.query_normalize

    infcx.query_normalize بسیار به‌ندرت استفاده می‌شود؛ تقریباً همهٔ محدودیت‌های normalize_erasing_regions را دارد (نمی‌تواند متغیرهای استنتاج را مدیریت کند، پشتیبانی diagnostics ندارد)، و تفاوت اصلی‌اش این است که اطلاعات طول عمر را حفظ می‌کند. به همین دلیل، normalize_erasing_regions تقریباً در همهٔ شرایط انتخاب بهتری است، چون به‌دلیل کش کردن queryهای بدون طول عمر کاراتر است.

    در عمل، query_normalize برای نرمال‌سازی در borrow checker و جاهای دیگر به‌عنوان بهینه‌سازی عملکرد نسبت به infcx.normalize استفاده می‌شود. پس از پایدار شدن solver جدید، انتظار می‌رود query_normalize بتواند از کامپایلر حذف شود، چون پیاده‌سازی نرمال‌سازی solver جدید باید به‌اندازهٔ کافی کارا باشد که افت عملکرد ایجاد نکند.

    tcx.normalize_erasing_regions

    normalize_erasing_regions عموماً توسط بخش‌هایی از کامپایلر استفاده می‌شود که تحلیل سامانهٔ نوع انجام نمی‌دهند. این نقطهٔ ورود نرمال‌سازی متغیرهای استنتاج، طول عمرها یا هیچ diagnosticsی را مدیریت نمی‌کند. lintها و codegen استفادهٔ زیادی از این نقطهٔ ورود می‌کنند، چون معمولاً با aliasهای کاملاً استنتاج‌شده کار می‌کنند که می‌توان آن‌ها را well formed فرض کرد (یا دست‌کم مسئول خطا دادن دربارهٔ آن‌ها نیستند).

    درون solver صفت

    traits::normalize_with_depth(_to) and EvalCtxt::structurally_normalize فقط توسط درونیات solverهای صفت (به‌ترتیب قدیمی و جدید) استفاده می‌شوند. در عمل یک نقطهٔ ورود خام به درونیات چگونگی پیاده‌سازی نرمال‌سازی توسط هر solver صفت است. نقاط ورود نرمال‌سازی دیگر را نمی‌توان از درون درونیات حل صفت به کار برد، چون چرخه‌های goal و عمق بازگشت را درست مدیریت نمی‌کنند.

    چه زمانی/کجا نرمال کنیم (solver قدیمی در برابر جدید)

    یکی از تغییرات بزرگ میان solver قدیمی و جدید، رویکرد ما به این است که چه زمانی انتظار داریم aliasها نرمال شده باشند.

    solver قدیمی

    انتظار می‌رود همهٔ نوع‌ها در اولین فرصت نرمال شوند، به‌طوری که همهٔ نوع‌هایی که در سامانهٔ نوع با آن‌ها روبه‌رو می‌شویم یا صلب باشند یا متغیر استنتاج (که بعداً به یک term صلب استنتاج خواهد شد).

    به‌عنوان یک مثال مشخص، برابری aliasها با فرض صلب بودن آن‌ها و برابر کردن بازگشتی آرگومان‌های جنریک alias پیاده‌سازی می‌شود.

    solver جدید

    انتظار می‌رود همهٔ نوع‌ها بالقوه شامل aliasهای مبهم یا نرمال‌نشده باشند. هر زمان عملیاتی انجام می‌شود که نیاز دارد aliasها نرمال شوند، مسئولیت نرمال کردن alias با همان منطق است. این یعنی تطبیق روی ty.kind() تقریباً همیشه باید ابتدا به‌صورت ساختاری نرمال کند.

    به‌عنوان یک مثال مشخص، برابری aliasها با یک نوع goal سفارشی (PredicateKind::AliasRelate) پیاده‌سازی می‌شود تا بتواند خودش نرمال‌سازی aliasها را مدیریت کند، به‌جای اینکه فرض کند همهٔ نوع‌های alias در حال برابر شدن صلب‌اند.

    با وجود این رویکرد، همچنان در حین writeback برای عملکرد/سادگی به‌صورت عمیق نرمال می‌کنیم، تا بتوان همچنان فرض کرد نوع‌ها در MIR به‌صورت عمیق نرمال شده‌اند.

    چند مشکل اصلی در رویکرد solver قدیمی به نرمال‌سازی وجود داشت که انگیزهٔ تغییر در solver جدید بود:

    فراخوانی‌های نرمال‌سازی جاافتاده

    اغلب پیش می‌آمد که فراخوانی‌های نرمال‌سازی جا بیفتند و در نتیجه نوع‌های نرمال‌نشده به APIهایی داده شوند که انتظار دارند همه‌چیز از پیش نرمال شده باشد. رفتار با aliasهای مبهم یا نرمال‌نشده به‌عنوان صلب به انواع خطاهای عجیب می‌انجامید، از جمله برابر دانسته نشدن aliasها با یکدیگر، یا هدایت‌های استنتاج شگفت‌انگیز ناشی از برابر کردن آرگومان‌های جنریک aliasهای نرمال‌نشده.

    نرمال‌سازی محیط‌های پارامتر

    مشکل دیگر این بود که در solver قدیمی نمی‌شد ParamEnvها را درست نرمال کرد، چون خود نرمال‌سازی برای نتیجهٔ درست انتظار یک ParamEnv نرمال‌شده را دارد. برای اطلاعات بیشتر فصل ParamEnvها را ببینید: Typing/ParamEnvs: نرمال کردن همهٔ کران‌ها

    aliasهای غیرصلبِ نرمال‌ناپذیر در نوع‌های رتبه‌بالاتر

    با داشتن نوعی مانند for<'a> fn(<?x as Trait<'a>::Assoc>)، با رویکرد solver قدیمی به نرمال‌سازی نمی‌توان این را درست مدیریت کرد.

    اگر آن را به for<'a> fn(?y) نرمال کنیم و یک goal برای نرمال کردن for<'a> <?x as Trait<'a>>::Assoc -> ?y ثبت کنیم، این در مواردی که <?x as Trait<'a>>::Assoc به &'a u32 نرمال می‌شد به خطا می‌انجامید. متغیر استنتاج ?y در universe پایین‌تری از جانگهدارهای ساخته‌شده هنگام نمونه‌سازی binder ‏for<'a> قرار می‌گرفت.

    رها کردن alias به‌صورت نرمال‌نشده هم نادرست است چون solver قدیمی انتظار دارد همهٔ aliasها صلب باشند. این پیش از پایدار شدن solver جدید در coherence یک باگ سلامت (soundness) بود: relating projection substs is unsound during coherence.

    در نهایت، این یعنی همیشه نمی‌توان اطمینان یافت که همهٔ aliasهای درون یک مقدار صلب‌اند.

    مدیریت استفاده از aliasهای واگرا

    aliasهای واگرا، مانند aliasهای مبهم، به متغیرهای استنتاج نرمال می‌شوند. از آنجا که نرمال کردن aliasهای واگرا به چرخه‌های solver صفت می‌انجامد، در solver قدیمی همیشه به خطا می‌انجامد. در solver جدید فقط وقتی به خطا می‌انجامد که در نهایت لازم باشد همهٔ goalها در بستر جاری برقرار باشند. برای مثال، نرمال کردن aliasهای واگرا در حین HIR typeck در هر دو solver به خطا می‌انجامد.

    well formedness مربوط به alias لازم نمی‌کند که alias واگرا نباشد4. این یعنی بررسی well formed بودن یک alias برای صدور خطا دربارهٔ aliasهای واگرا کافی نیست؛ در واقع تلاش برای نرمال کردن alias لازم است.

    اینکه خطا دادن دربارهٔ aliasهای واگرا اثر جانبی نرمال‌سازی باشد یعنی اینکه واقعاً خطا صادر شود یا نه بسیار دلبخواهی است، و همچنین میان solver قدیمی و جدید فرق می‌کند چون اکنون در جاهای کمتری نرمال می‌کنیم.

    نمونه‌ای از ماهیت ad-hoc خطا دادن دربارهٔ aliasهای واگرا که «مشکل» ایجاد می‌کند:

    trait Trait {
    type Diverges<D: Trait>;
}

impl<T> Trait for T {
    type Diverges<D: Trait> = D::Diverges<D>;
}

struct Bar<T: ?Sized = <u8 as Trait>::Diverges<u8>>(Box<T>);

    در این مثال، یک alias واگرا استفاده شده، اما اتفاقاً خطایی صادر نمی‌شود چون هرگز مقادیر پیش‌فرض پارامترهای جنریک را صراحتاً نرمال نمی‌کنیم. اگر انصراف ?Sized حذف شود، خطا صادر می‌شود چون در نهایت یک goal ‏<u8 as Trait>::Diverges<u8>: Sized را نرمال می‌کنیم، که به‌عنوان اثر جانبی به خطا دادن دربارهٔ alias واگرا می‌انجامد.

    aliasهای const در اینجا اندکی با نام‌های مستعار نوع تفاوت دارند؛ well formedness مربوط به aliasهای const لازم می‌کند که بتوان آن‌ها را با موفقیت ارزیابی کرد (از طریق goalهای ConstEvaluatable). این یعنی صرفاً بررسی well formedness آرگومان‌های const برای خطا دادن در صورت شکست ارزیابی کافی است. تا حدی نامشخص است که آیا اتخاذ این روش برای نام‌های مستعار نوع هم منطقی است، یا aliasهای const باید دیگر برای well formedness این را الزام نکنند5.

    1. در solver جدید این به‌صورت ضمنی انجام می‌شود ↩

    2. تفاوت ظریفی در نحوهٔ مدیریت aliasهای مبهم درون binderها میان solver قدیمی و جدید وجود دارد. در solver قدیمی دربارهٔ برخی aliasهای مبهم درون نوع‌های رتبه‌بالاتر خطا نمی‌دهیم، در حالی که solver جدید درست خطا می‌دهد. ↩

    3. aliasهای مبهم درون binderها را نمی‌توان به متغیرهای استنتاج نرمال کرد؛ این در ادامه بیشتر پوشش داده می‌شود. ↩

    4. از آنجا که بررسی واگرا نبودن aliasها تا وقتی کاملاً مشخص (concrete) نشده‌اند ممکن نیست، این یا یعنی نمی‌توانیم well formed بودن aliasها را پیش از codegen/ارزیابی const بررسی کنیم یا اینکه aliasها پس از monomorphization از well-formed به غیر well-formed تغییر حالت می‌دهند. ↩

    5. اگر این کار را متوقف کنیم، aliasهای const قطعاً کمتر از نام‌های مستعار نوع سالم (sound) نخواهند بود ↩
