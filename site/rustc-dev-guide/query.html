راهنمای توسعهٔ rustcrustc Development Guide

    Queries: demand-driven compilation

    همان‌طور که در نمای کلی کامپایلر توضیح داده شد، کامپایلر Rust هنوز (تا ژوئیهٔ 2021 ) در حال گذار از ساختار سنتی «مبتنی بر گذر (pass)» به سامانهٔ «تقاضامحور (demand-driven)» است.

    «سامانهٔ کوئری» کامپایلر کلید سازمان تقاضامحور rustc است. به‌جای گذرهای کاملاً مستقل (تجزیه، بررسی نوع و غیره)، مجموعه‌ای از کوئری‌های تابع‌مانند اطلاعات مربوط به منبع ورودی را محاسبه می‌کنند. برای مثال، کوئری‌ای به نام type_of هست که با گرفتن DefId یک آیتم، نوع آن آیتم را محاسبه می‌کند و به شما برمی‌گرداند.

    اجرای کوئری memoize می‌شود. اولین باری که کوئری را فراخوانی می‌کنید، محاسبه را انجام می‌دهد، اما دفعهٔ بعد نتیجه از یک hashtable برمی‌گردد. علاوه بر این، اجرای کوئری به‌خوبی با محاسبهٔ افزایشی سازگار است؛ ایده تقریباً این است که وقتی کوئری را فراخوانی می‌کنید، نتیجه ممکن است با بارگذاری داده‌های ذخیره‌شده از دیسک به شما برگردد.1

    وقتی کوئری‌ای اجرا می‌کنیم، همچنین (در زمان اجرا!) کشف می‌کنیم به چه کوئری‌های دیگری وابسته است. این به ما اجازه می‌دهد گراف وابستگی crate خود را بسازیم، که محاسبهٔ افزایشی را sound می‌کند.

    در نهایت می‌خواهیم کل جریان کنترل کامپایلر کوئری‌محور باشد. عملاً یک کوئری سطح بالا (compile) خواهد بود که کامپایل را روی یک crate اجرا می‌کند؛ این به نوبهٔ خود اطلاعات آن crate را از انتها شروع کرده تقاضا می‌کند.

    برای مثال:

    • کوئری compile ممکن است تقاضا کند فهرستی از واحدهای codegen (یعنی ماژول‌هایی که باید توسط LLVM کامپایل شوند) بگیرد.
    • اما محاسبهٔ فهرست واحدهای codegen زیرکوئری‌ای را فراخوانی می‌کند که فهرست همهٔ ماژول‌های تعریف‌شده در منبع Rust را برمی‌گرداند.
    • آن کوئری به نوبهٔ خود چیزی را فراخوانی می‌کند که HIR را می‌خواهد.
    • این همین‌طور عقب‌تر و عقب‌تر می‌رود تا نهایتاً به تجزیهٔ واقعی برسیم.

    هرچند این چشم‌انداز کاملاً محقق نشده، بخش‌های بزرگی از کامپایلر (برای مثال، تولید MIR) در حال حاضر دقیقاً همین‌طور کار می‌کنند.

    Invoking queries

    فراخوانی کوئری ساده است. struct با نام TyCtxt («زمینهٔ نوع‌دهی») برای هر کوئری تعریف‌شده متدی ارائه می‌دهد. برای مثال، برای فراخوانی کوئری type_of فقط این را می‌نویسید:

    let ty = tcx.type_of(some_def_id);

    کامپایلر چگونه یک کوئری را اجرا می‌کند

    ممکن است بپرسید هنگام فراخوانی متد کوئری چه رخ می‌دهد. پاسخ این است که برای هر کوئری، کامپایلر یک cache نگه می‌دارد – اگر کوئری شما قبلاً اجرا شده باشد، پاسخ ساده است: مقدار بازگشتی را از cache clone می‌کنیم و برمی‌گردانیم (بنابراین باید سعی کنید مطمئن شوید نوع‌های بازگشتی کوئری‌ها به‌ارزانی قابل‌clone‌اند؛ در صورت نیاز Rc بگذارید).

    Providers

    اما اگر کوئری در cache نباشد، کامپایلر تابع provider متناظر را فراخوانی می‌کند. provider تابعی است که در ماژول مشخصی پیاده‌سازی شده و هنگام مقداردهی اولیهٔ کامپایلر به‌صورت دستی ثبت می‌شود در struct با نام Providers (برای کوئری‌های crate محلی) یا struct با نام ExternProviders (برای کوئری‌های crate خارجی). سامانهٔ ماکرو هر دو struct را تولید می‌کند، که به‌عنوان جدول تابع برای همهٔ پیاده‌سازی‌های کوئری عمل می‌کنند، و هر فیلد اشاره‌گر تابع به provider واقعی است.

    نکته: هر دو struct با نام Providers و ExternProviders توسط ماکروها تولید می‌شوند و به‌عنوان جدول تابع برای همهٔ پیاده‌سازی‌های کوئری عمل می‌کنند. آن‌ها trait در Rust نیستند، بلکه structهای ساده با فیلدهای اشاره‌گر تابع‌اند.

    providerها به‌ازای هر crate تعریف می‌شوند. کامپایلر در داخل، دست‌کم از نظر مفهومی، جدولی از providerها برای هر crate نگه می‌دارد. دو مجموعه provider هست:

    • struct با نام Providers برای کوئری‌های مربوط به crate محلی (یعنی crateای که در حال کامپایل است)
    • struct با نام ExternProviders برای کوئری‌های مربوط به crateهای خارجی (یعنی وابستگی‌های crate محلی)

    توجه کنید آنچه تعیین می‌کند کوئری کدام crate را هدف می‌گیرد نوع کوئری نیست، بلکه کلید آن است. برای مثال، وقتی tcx.type_of(def_id) را فراخوانی می‌کنید، بسته به اینکه def_id به کدام crate اشاره دارد می‌تواند کوئری محلی یا خارجی باشد (برای اطلاعات بیشتر دربارهٔ نحوهٔ کار این، trait با نام self::keys::QueryKey را ببینید).

    providerها همیشه امضای یکسانی دارند:

    fn provider<'tcx>(
    tcx: TyCtxt<'tcx>,
    key: QUERY_KEY,
) -> QUERY_RESULT {
    ...
}

    providerها دو آرگومان می‌گیرند: tcx و کلید کوئری. نتیجهٔ کوئری را برمی‌گردانند.

    توجه: بیشتر crateهای rustc_* فقط providerهای محلی ارائه می‌دهند. تقریباً همهٔ providerهای extern از rustc_metadata crate می‌گذرند، که اطلاعات را از فراداده crate بارگذاری می‌کند. اما در برخی موارد crateهایی هستند که کوئری‌ها را برای هر دو crateهای محلی و خارجی فراهم می‌کنند، که در آن صورت هم تابع provide و هم provide_extern تعریف می‌کنند، از طریق wasm_import_module_map، که rustc_driver می‌تواند فراخوانی کند.

    providerها چگونه راه‌اندازی می‌شوند

    وقتی tcx ساخته می‌شود، سازندهٔ آن هم providerهای محلی و هم خارجی را با استفاده از struct با نام Providers از rustc_middle::util به آن می‌دهد. این struct هم providerهای محلی و هم خارجی را دارد:

    pub struct Providers {
    pub queries: crate::query::Providers,        // Local crate providers
    pub extern_queries: crate::query::ExternProviders,  // External crate providers
    pub hooks: crate::hooks::Providers,
}

    هر یک از این structهای provider توسط ماکروها تولید می‌شود و اشاره‌گرهای تابع برای کوئری‌های مربوطه را دارد.

    providerها چگونه ثبت می‌شوند؟

    struct با نام util::Providers هنگام مقداردهی اولیهٔ کامپایلر توسط crate با نام rustc_interface از static با نام DEFAULT_QUERY_PROVIDERS پر می‌شود. توابع provider واقعی در crateهای مختلف rustc_* (مثل rustc_middle، rustc_hir_analysis و غیره) تعریف شده‌اند.

    برای ثبت providerها، هر crate تابعی به نام provide ارائه می‌دهد که این‌طور به نظر می‌رسد:

    pub fn provide(providers: &mut query::Providers) {
    *providers = query::Providers {
        type_of,
        // ... add more providers here
        ..*providers
    };
}

    توجه کنید این تابع query::Providers می‌پذیرد نه util::Providers. نیاز به تابع provide که فقط query::Providers را نمی‌پذیرد بسیار نادر است. اگر بیش از فیلد queries در util::Providers به‌روز می‌شود، می‌توان به‌جای آن util::Providers را پذیرفت:

    pub fn provide(providers: &mut rustc_middle::util::Providers) {
    providers.queries.type_of = type_of;
    // ... add more local providers here

    providers.extern_queries.type_of = extern_type_of;
    // ... add more external providers here

    providers.hooks.some_hook = some_hook;
    // ... add more hooks here
}

    افزودن provider جدید

    فرض کنید می‌خواهید کوئری جدیدی به نام fubar اضافه کنید. این بخش بر سیم‌کشی providerها تمرکز دارد؛ برای نحوهٔ اعلان خود کوئری در ماکروی بزرگ rustc_queries! افزودن کوئری جدید را در ادامه ببینید.

    در عمل معمولاً:

    1. تصمیم می‌گیرید کدام crate «مالک» کوئری است (مثلاً rustc_hir_analysis، rustc_mir_build یا crate دیگری از rustc_*).
    2. در آن crate، به‌دنبال تابع provide موجود بگردید: 
      pub fn provide(providers: &mut query::Providers) {
    // existing assignments
}
      اگر وجود دارد، آن را گسترش می‌دهید تا فیلد کوئری جدید را تنظیم کند. اگر crate هنوز تابع provide ندارد، یکی اضافه کنید و مطمئن شوید در DEFAULT_QUERY_PROVIDERS در crate با نام rustc_interface گنجانده شده تا واقعاً هنگام مقداردهی اولیه فراخوانی شود (بحث بالا را ببینید).
    3. خود تابع provider را پیاده‌سازی کنید: 
      fn fubar<'tcx>(tcx: TyCtxt<'tcx>, key: LocalDefId) -> Fubar<'tcx> { ... }
    4. آن را در تابع provide آن crate ثبت کنید: 
      pub fn provide(providers: &mut query::Providers) {
    *providers = query::Providers {
        fubar,
        ..*providers
    };
}

    کوئری‌ها چگونه با فرادادهٔ crateهای خارجی تعامل می‌کنند

    وقتی کوئری برای crate خارجی (یعنی وابستگی) انجام می‌شود، سامانهٔ کوئری باید اطلاعات را از فرادادهٔ آن crate بارگذاری کند. این توسط rustc_metadata crate مدیریت می‌شود که مسئول رمزگشایی و ارائهٔ اطلاعات ذخیره‌شده در فایل‌های .rmeta است.

    فرایند به این شکل کار می‌کند:

    1. وقتی کوئری انجام می‌شود، سامانهٔ کوئری ابتدا با بررسی def_id.krate == LOCAL_CRATE بررسی می‌کند DefId به crate محلی اشاره دارد یا خارجی. این تعیین می‌کند از provider محلی از Providers استفاده شود یا provider خارجی از ExternProviders.

    2. برای crateهای خارجی، سامانهٔ کوئری provider را در struct با نام ExternProviders جست‌وجو می‌کند. crate با نام rustc_metadata این providerهای خارجی را از طریق تابع provide_extern در rustc_metadata/src/rmeta/decoder/cstore_impl.rs ثبت می‌کند. درست مثل:

      pub fn provide_extern(providers: &mut ExternProviders) {
    providers.foo = |tcx, def_id| {
        // Load and decode metadata for external crate
        let cdata = CStore::from_tcx(tcx).get_crate_data(def_id.krate);
        cdata.foo(def_id.index)
    };
    // Register other external providers...
}

    3. فراداده در قالب دودویی در فایل‌های .rmeta ذخیره می‌شود که اطلاعات پیش‌محاسبه‌شدهٔ crate خارجی، مثل نوع‌ها، امضای توابع، پیاده‌سازی‌های trait و اطلاعات دیگر مورد نیاز کامپایلر را دارد. وقتی کوئری خارجی انجام می‌شود، crate با نام rustc_metadata:

      • فایل .rmeta را برای crate خارجی بارگذاری می‌کند
      • فراداده را با trait با نام Decodable رمزگشایی می‌کند
      • اطلاعات رمزگشایی‌شده را به سامانهٔ کوئری برمی‌گرداند

    این رویکرد از کامپایل مجدد crateهای خارجی جلوگیری می‌کند، کامپایل سریع‌تر crateهای وابسته را ممکن می‌کند و کامپایل افزایشی را قادر می‌سازد از مرزهای crate عبور کند. در ادامه مثال ساده‌شده‌ای می‌آید: وقتی tcx.type_of(def_id) را برای نوعی که در crate خارجی تعریف شده فراخوانی می‌کنید، سامانهٔ کوئری:

    1. با بررسی def_id.krate != LOCAL_CRATE تشخیص می‌دهد def_id به crate خارجی اشاره دارد
    2. provider مناسب را از ExternProviders که توسط rustc_metadata ثبت شده فراخوانی می‌کند
    3. provider اطلاعات نوع را از فرادادهٔ crate خارجی بارگذاری و رمزگشایی می‌کند
    4. نوع رمزگشایی‌شده را به فراخواننده برمی‌گرداند

    به همین دلیل بیشتر crateهای rustc_* فقط نیاز به ارائهٔ providerهای محلی دارند — providerهای خارجی توسط سامانهٔ فراداده مدیریت می‌شوند. تنها استثنا وقتی است که crate باید برخورد ویژه‌ای برای کوئری‌های خارجی فراهم کند، که در آن صورت هم providerهای محلی و هم خارجی را پیاده‌سازی می‌کند.

    وقتی کوئری جدیدی تعریف می‌کنیم که باید بین crateها کار کند، صرفاً چون در rustc_queries! فهرست شده خودکار بین‌crate نمی‌شود. معمولاً باید:

    • کوئری را با modifierهای مناسب به rustc_queries! اضافه کنید (برای مثال اینکه آیا روی دیسک cache می‌شود).
    • provider محلی را در crate مالک پیاده‌سازی کنید و از طریق تابع provide آن crate ثبتش کنید.
    • provider خارجی را در rustc_metadata از طریق provide_extern اضافه کنید و مطمئن شوید نتیجهٔ کوئری در فرادادهٔ crate کدگذاری و رمزگشایی می‌شود.

    نمونه‌ای از معرفی چنین کوئری بین‌crate را در commit با نام 996a185 در مخزن rust-lang/rust می‌یابید.

    افزودن کوئری جدید

    چگونه کوئری جدید اضافه کنیم؟ تعریف کوئری در دو گام انجام می‌شود:

    1. نام کوئری، آرگومان‌ها و توضیح آن را اعلان کنید.
    2. در صورت نیاز providerهای کوئری را فراهم کنید.

    برای اعلان نام و آرگومان‌های کوئری، فقط ورودی‌ای به فراخوانی ماکروی بزرگ در compiler/rustc_middle/src/query/mod.rs اضافه می‌کنید. سپس باید یک doc comment با توضیح داخلی به آن اضافه کنید. سپس attribute با نام desc را بدهید که توضیح رو به کاربر کوئری را دارد. attribute با نام desc در چرخه‌های کوئری به کاربر نمایش داده می‌شود.

    این چیزی شبیه این به نظر می‌رسد:

    rustc_queries! {
    /// Records the type of every item.
    query type_of(key: DefId) -> Ty<'tcx> {
        desc { |tcx| "computing the type of `{}`", tcx.def_path_str(key) }
        cache_on_disk
        separate_provide_extern
    }
    ...
}

    تعریف کوئری شکل زیر را دارد:

    query type_of(key: DefId) -> Ty<'tcx> { ... }
^^^^^ ^^^^^^^      ^^^^^     ^^^^^^^^   ^^^
|     |            |         |          |
|     |            |         |          query modifiers
|     |            |         result type
|     |            query key type
|     name of query
query keyword

    بیایید این عناصر را یکی‌یکی مرور کنیم:

    • کلیدواژهٔ Query: آغاز تعریف کوئری را نشان می‌دهد.
    • نام کوئری: نام متد کوئری (tcx.type_of(..)). همچنین به‌عنوان نام structی (ty::queries::type_of) به‌کار می‌رود که برای نمایش این کوئری تولید می‌شود.
    • نوع کلید کوئری: نوع آرگومان این کوئری. این نوع باید trait با نام ty::query::keys::QueryKey را پیاده‌سازی کند، که (برای مثال) تعریف می‌کند چگونه به یک crate نگاشت شود و مانند آن.
    • نوع نتیجهٔ کوئری: نوع تولیدشده توسط این کوئری. این نوع باید (الف) از RefCell یا تغییرپذیری داخلی دیگر استفاده نکند و (ب) به‌ارزانی قابل‌clone باشد. برای نوع‌های داده غیربدیهی interning یا استفاده از Rc یا Arc توصیه می‌شود.2
    • modifierهای کوئری: پرچم‌ها و گزینه‌های مختلفی که نحوهٔ پردازش کوئری را سفارشی می‌کنند (عمدتاً در رابطه با کامپایل افزایشی).

    پس برای افزودن کوئری:

    • با قالب بالا ورودی‌ای به rustc_queries! اضافه کنید.
    • provider را با تغییر متد provide مناسب پیوند دهید؛ یا در صورت لزوم یکی جدید اضافه کنید و مطمئن شوید rustc_driver آن را فراخوانی می‌کند.
