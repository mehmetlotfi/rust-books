راهنمای توسعهٔ rustcrustc Development Guide

    Rustdoc overview

    rustdoc درون‌درختی همراه با کامپایلر و کتابخانهٔ استاندارد قرار دارد. این فصل دربارهٔ نحوهٔ کار آن است. برای اطلاعات دربارهٔ قابلیت‌های Rustdoc و نحوهٔ استفاده از آن‌ها، کتاب Rustdoc را ببینید. برای جزئیات بیشتر دربارهٔ نحوهٔ کار rustdoc، فصل «درون‌ساز rustdoc» را ببینید.

    rustdoc از اجزای داخلی rustc (و البته کتابخانهٔ استاندارد) استفاده می‌کند، پس پیش از ساخت rustdoc باید یک بار کامپایلر و std را بسازید.

    Rustdoc کاملاً درون crate با نام librustdoc پیاده‌سازی شده است. کامپایلر را تا نقطه‌ای اجرا می‌کند که نمایش داخلی یک crate (HIR) و توانایی اجرای برخی پرس‌وجوها دربارهٔ نوع آیتم‌ها در اختیار داشته باشیم. HIR و کوئری‌ها در فصل‌های پیوندخورده بحث شده‌اند.

    librustdoc پس از آن دو گام اصلی برای رندر مجموعه‌ای از مستندات انجام می‌دهد:

    • AST را به شکلی «پاک‌سازی» (clean) می‌کند که برای ساخت مستندات مناسب‌تر است (و کمی در برابر تغییرات مداوم کامپایلر مقاوم‌تر).
    • از این AST پاک‌سازی‌شده برای رندر مستندات یک crate، صفحه به صفحه، استفاده می‌کند.

    البته چیزهای بیشتری از این هم هست، و این توضیح‌ها جزئیات زیادی را ساده کرده‌اند، اما این نمای کلی سطح بالاست.

    (نکتهٔ جانبی: librustdoc یک crate کتابخانه است! فایل دودویی rustdoc با استفاده از پروژه‌ای در src/tools/rustdoc ساخته می‌شود. توجه کنید که تمام کاری که آن انجام می‌دهد فراخوانی main() در lib.rs همین crate است.)

    Cheat sheet

    • پیش از شروع ./x setup tools را اجرا کنید. این x را با تنظیمات مناسب برای توسعهٔ rustdoc و ابزارهای دیگر پیکربندی می‌کند، از جمله دانلود یک نسخهٔ rustc به‌جای ساخت آن.
    • برای بررسی سریع خطاهای کامپایل از ./x check rustdoc استفاده کنید.
    • Use ./x build library rustdoc to make a usable rustdoc you can run on other projects.
      • برای اینکه بتوانید از rustdoc --test استفاده کنید، library/test را اضافه کنید.
      • دستور rustup toolchain link stage2 build/host/stage2 را اجرا کنید تا یک toolchain سفارشی به نام stage2 به محیط rustup شما اضافه شود. پس از آن، cargo +stage2 doc در هر پوشه‌ای با rustdoc کامپایل‌شدهٔ محلی شما می‌سازد.
    • Use ./x doc library to use this rustdoc to generate the standard library docs.
      • مستندات کامل‌شده در build/host/doc در دسترس خواهند بود (زیر core، alloc و std).
      • اگر می‌خواهید آن مستندات را به یک وب‌سرور کپی کنید، همهٔ build/host/doc را کپی کنید، چون CSS، JS، فونت‌ها و صفحهٔ فرود آنجا هستند.
      • برای اشکال‌زدایی frontend، گزینهٔ rust.docs-minification را در bootstrap.toml غیرفعال کنید.
    • Use ./x test tests/rustdoc* to run the tests using a stage1 rustdoc.
      • برای اطلاعات بیشتر دربارهٔ تست‌ها درون‌ساز Rustdoc را ببینید.
    • برای اجرای بررسی‌های JavaScript در rustdoc (eslint، es-check و tsc) از ./x test tidy --extra-checks=js استفاده کنید.

    نکته: ./x test tidy وقتی منابع JS/TS تغییر کرده باشند این بررسی‌ها را به‌طور خودکار اجرا می‌کند؛ --extra-checks=js آن‌ها را صراحتاً اجبار می‌کند.

    JavaScript CI checks

    JavaScript و TypeScript در rustdoc هنگام CI توسط eslint، es-check و tsc بررسی می‌شوند (نه توسط compiletest). این‌ها به‌عنوان بخشی از job با نام tidy اجرا می‌شوند.

    ./x test tidy --extra-checks=js

    پرچم --extra-checks=js linting مربوط به frontend را که در CI اجرا می‌شود فعال می‌کند.

    Code structure

    همهٔ مسیرهای این بخش نسبت به src/librustdoc/ در مخزن rust-lang/rust هستند.

    • بیشتر کد چاپ HTML در html/format.rs و html/render/mod.rs است. در مجموعه‌ای از توابع است که impl std::fmt::Display برمی‌گردانند.
    • نوع‌های داده‌ای که توسط توابع بالا رندر می‌شوند در clean/types.rs تعریف شده‌اند. توابعی که مسئول ساخت آن‌ها از HIR و IR با نام rustc_middle::ty هستند در clean/mod.rs قرار دارند.
    • بخش‌های مخصوص استفاده از rustdoc به‌عنوان test harness در doctest.rs هستند.
    • رندرکنندهٔ Markdown در html/markdown.rs بارگذاری می‌شود، از جمله توابعی برای استخراج doctestها از یک بلوک Markdown.
    • Frontend CSS and JavaScript are stored in html/static/.
      • دربارهٔ JavaScript، annotationهای نوع با کامنت‌های JSDoc سبک TypeScript و یک فایل خارجی .d.ts نوشته می‌شوند. به این ترتیب خود کد JavaScript ساده و معتبر می‌ماند. ما از tsc فقط به‌عنوان linter استفاده می‌کنیم.

    Tests

    تست‌های یکپارچگی rustdoc بین چند مجموعه تست تقسیم شده‌اند. برای جزئیات بیشتر مجموعه تست‌های Rustdoc را ببینید.

    Constraints

    تلاش می‌کنیم rustdoc با غیرفعال‌بودن JavaScript و هنگام مرور فایل‌های محلی نیز به‌طور معقول کار کند. ما فهرستی از مرورگرهای پشتیبانی‌شده داریم.

    پشتیبانی از فایل‌های محلی (نشانی‌های file:///) محدودیت‌های شگفت‌آوری به همراه دارد. برخی قابلیت‌های مرورگر که به originهای امن نیاز دارند، مثل localStorage و Service Worker، به‌طور قابل‌اعتماد کار نمی‌کنند. همچنان می‌توانیم از چنین قابلیت‌هایی استفاده کنیم، اما باید مطمئن شویم صفحه‌ها بدون آن‌ها هم قابل‌استفاده‌اند.

    Rustdoc بدنهٔ توابع را type-check نمی‌کند. این با بازنویسی پرس‌وجوهای داخلی typeck، با خاموش‌کردن خطاهای name resolution، و با حل‌نکردن opaque typeها انجام می‌شود. این چند محدودیت دارد: به‌ویژه، rustdoc نمی‌تواند هیچ بخشی از کامپایلر را که به type-check بدنه‌ها نیاز دارد اجرا کند؛ برای مثال نمی‌تواند فایل‌های .rlib تولید کند یا بیشتر lintها را اجرا کند. ما می‌خواهیم در نهایت از این مدل فاصله بگیریم، اما برای کسانی که از آن استفاده می‌کنند به جایگزینی نیاز داریم؛ بحث‌های متعدد قبلی در Zulip را ببینید. برای نمونه‌هایی از کدی که با حذف این hack می‌شکند، به tests/rustdoc-ui/error-in-impl-trait نگاه کنید.

    اجراهای متعدد، پوشهٔ خروجی یکسان

    Rustdoc را می‌توان چند بار برای ورودی‌های متفاوت اجرا کرد، در حالی که خروجی‌اش روی یک پوشه تنظیم شده است. cargo این‌طور مستندات وابستگی‌های crate فعلی را تولید می‌کند. اگر کاربری بخواهد یک بستهٔ مستندات بزرگ با همهٔ مستنداتی که به آن‌ها اهمیت می‌دهد داشته باشد، می‌تواند دستی هم این کار را بکند.

    HTML برای هر crate مستقل تولید می‌شود، اما برخی اطلاعات بین‌crate هست که با افزودن crateها به پوشهٔ خروجی به‌روز می‌کنیم:

    • crates<SUFFIX>.js فهرست همهٔ crateهای پوشهٔ خروجی را نگه می‌دارد.
    • search-index<SUFFIX>.js فهرست همهٔ آیتم‌های قابل‌جست‌وجو را نگه می‌دارد.
    • برای هر trait، فایلی زیر implementors/.../trait.TraitName.js هست که فهرست پیاده‌سازهای آن trait را دارد. پیاده‌سازها ممکن است در crateهایی غیر از crate خود trait باشند، و فایل JS با کشف موارد جدید به‌روز می‌شود.

    موارد استفاده

    چند مورد استفادهٔ اصلی برای rustdoc هست که هنگام کار روی آن باید در نظر داشته باشید:

    Standard library docs

    این‌ها به‌عنوان بخشی از فرایند انتشار Rust در https://doc.rust-lang.org/std منتشر می‌شوند. انتشارهای stable هم در نشانی‌های نسخه‌دار خاصی مثل https://doc.rust-lang.org/1.57.0/std/ بارگذاری می‌شوند. مستندات beta و nightly در https://doc.rust-lang.org/beta/std/ و https://doc.rust-lang.org/nightly/std/ منتشر می‌شوند. مستندات با ابزار promote-release بارگذاری و از S3 با CloudFront ارائه می‌شوند.

    مستندات کتابخانهٔ استاندارد پنج crate دارد: alloc، core، proc_macro، std و test.

    docs.rs

    وقتی crateها در crates.io منتشر می‌شوند، docs.rs به‌طور خودکار مستندات آن‌ها را می‌سازد و منتشر می‌کند، مثلاً در https://docs.rs/serde/latest/serde/. همیشه با rustdoc nightly فعلی می‌سازد، پس هر تغییری که در rustdoc land کنید «insta-stable» است، یعنی اثر عمومی فوری در docs.rs دارد. مستندات قدیمی فقط گاهی دوباره ساخته می‌شوند، پس هنگام مرور نسخه‌های قدیمی در docs.rs کمی تفاوت در رابط کاربری می‌بینید. نویسندگان crate می‌توانند درخواست بازسازی کنند که با جدیدترین rustdoc اجرا می‌شود.

    Docs.rs برای صرفه‌جویی در فضای ذخیره‌سازی و نمایش نوار ناوبری در بالا، برخی تبدیل‌ها را روی خروجی rustdoc انجام می‌دهد. به‌ویژه، برخی فایل‌های ایستا، مثل main.js و rustdoc.css، ممکن است بین چند فراخوانی از همان نسخهٔ rustdoc مشترک باشند. برخی دیگر، مثل crates.js و sidebar-items.js، برای فراخوانی‌های مختلف متفاوت‌اند. و برخی دیگر، مثل فونت‌ها، هرگز تغییر نمی‌کنند. این دسته‌ها با enum با نام SharedResource در src/librustdoc/html/render/write_shared.rs متمایز می‌شوند

    مستندات در docs.rs همیشه برای یک crate در هر بار تولید می‌شوند، پس عملکرد جست‌وجو و نوار کناری وابستگی‌های crate فعلی را شامل نمی‌شود.

    Locally generated docs

    نویسندگان crate می‌توانند در crateهایی که به‌صورت محلی checkout کرده‌اند cargo doc --open را اجرا کنند تا مستندات را ببینند. این برای بررسی مفیدبودن و درست‌نمایش‌داده‌شدن مستنداتی که می‌نویسند مفید است. همچنین برای افرادی که می‌خواهند مستندات crateهایی را ببینند که نویسنده‌شان نیستند اما می‌خواهند استفاده کنند، مفید است. در هر دو حالت، افراد ممکن است از پرچم Cargo با نام --document-private-items استفاده کنند تا متدها، فیلدها و غیره‌ای را ببینند که خصوصی‌اند و معمولاً نمایش داده نمی‌شوند.

    به‌طور پیش‌فرض، cargo doc مستندات یک crate و همهٔ وابستگی‌هایش را تولید می‌کند. این می‌تواند به بستهٔ مستندات بسیار بزرگی با corpus جست‌وجوی بزرگ (و کند) بینجامد. پرچم Cargo با نام --no-deps این رفتار را مهار می‌کند و مستندات را فقط برای خود crate تولید می‌کند.

    Self-hosted project docs

    برخی پروژه‌ها مستندات خودشان را میزبانی می‌کنند. این با تولید محلی مستندات و کپی‌کردن ساده آن‌ها به یک وب‌سرور آسان است. خروجی HTML در Rustdoc را می‌توان به‌طور گسترده با پرچم‌ها سفارشی کرد. کاربران می‌توانند یک theme اضافه کنند، theme پیش‌فرض را تنظیم کنند و HTML دلخواه تزریق کنند. برای جزئیات rustdoc --help را ببینید.
