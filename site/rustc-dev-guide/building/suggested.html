راهنمای توسعهٔ rustcrustc Development Guide

    Suggested workflows

    فرایند کامل بوت‌استرپ (bootstrapping) زمان زیادی می‌برد. در ادامه چند پیشنهاد برای راحت‌تر‌کردن کار آمده است.

    نصب hook از نوع pre-push

    اگر ساخت شما از tidy (ابزار داخلی ما برای تضمین کیفیت کد) عبور نکند، CI به‌طور خودکار آن را شکست‌خورده اعلام می‌کند. در صورت تمایل می‌توانید یک Git hook نصب کنید که در هر push به‌طور خودکار ./x test tidy را اجرا کند تا از مناسب‌بودن کدتان مطمئن شوید. اگر hook شکست خورد، ./x test tidy --bless را اجرا کنید و تغییرات را commit کنید. اگر بعداً تصمیم گرفتید رفتار pre-push مطلوب نیست، می‌توانید فایل pre-push را در .git/hooks حذف کنید.

    یک git hook آماده در src/etc/pre-push.sh قرار دارد. آن را می‌توان با نام pre-push (بدون پسوند .sh!) در پوشهٔ .git/hooks کپی کرد.

    همچنین می‌توانید hook را به‌عنوان یکی از گام‌های اجرای ./x setup نصب کنید!

    Config extensions

    هنگام کار روی وظایف مختلف ممکن است لازم شود بین پیکربندی‌های مختلف bootstrap جابه‌جا شوید. گاهی می‌خواهید پیکربندی قدیمی را برای استفادهٔ آینده نگه دارید. اما ذخیرهٔ مقادیر خام پیکربندی در فایل‌های پراکنده و کپی و paste دستی آن‌ها می‌تواند سریعاً درهم‌ریخته شود، به‌ویژه اگر سابقهٔ طولانی از پیکربندی‌های مختلف داشته باشید.

    برای ساده‌کردن مدیریت چند پیکربندی، می‌توانید افزونه‌های پیکربندی (config extensions) بسازید.

    برای مثال می‌توانید یک فایل پیکربندی ساده به نام cross.toml بسازید:

    [build]
build = "x86_64-unknown-linux-gnu"
host = ["i686-unknown-linux-gnu"]
target = ["i686-unknown-linux-gnu"]


[llvm]
download-ci-llvm = false

[target.x86_64-unknown-linux-gnu]
llvm-config = "/path/to/llvm-19/bin/llvm-config"

    سپس آن را در bootstrap.toml خود include کنید:

    include = ["cross.toml"]

    همچنین می‌توانید افزونه‌ها را به‌صورت بازگشتی درون افزونه‌ها include کنید.

    نکته: در فیلد include، منطق بازنویسی از راست به چپ است. برای مثال، در include = ["a.toml", "b.toml"]، افزونهٔ b.toml بر a.toml غلبه می‌کند. همچنین افزونه‌های والد همیشه بر افزونه‌های درونی غلبه می‌کنند.

    پیکربندی rust-analyzer برای rustc

    بررسی درخت «library»

    بررسی درخت «library» به کامپایلر stage1 نیاز دارد که روی برخی رایانه‌ها می‌تواند سنگین باشد. به همین دلیل bootstrap پرچمی به نام --skip-std-check-if-no-download-rustc دارد که اگر rust.download-rustc در دسترس نباشد، بررسی درخت «library» را رد می‌کند. اگر می‌خواهید از بار سنگین rust-analyzer روی رایانه‌تان پرهیز کنید، می‌توانید پرچم --skip-std-check-if-no-download-rustc را به دستور ./x check در پیکربندی rust-analyzer اضافه کنید.

    Project-local rust-analyzer setup

    rust-analyzer می‌تواند هر بار که فایلی را ذخیره می‌کنید کد شما را بررسی و قالب‌بندی کند. به‌طور پیش‌فرض rust-analyzer دستورهای cargo check و rustfmt را اجرا می‌کند، اما هنگام کار روی rustc می‌توانید این دستورها را با نسخه‌های مناسب‌تر این ابزارها بازنویسی کنید. با پیکربندی سفارشی، rust-analyzer می‌تواند از ./x check برای بررسی منابع و از rustfmt مرحلهٔ stage 0 برای قالب‌بندی آن‌ها استفاده کند.

    دستور پیش‌فرض rust-analyzer.check.overrideCommand همهٔ crateها و ابزارهای مخزن را بررسی می‌کند. اگر روی بخش مشخصی کار می‌کنید، می‌توانید دستور را بازنویسی کنید تا فقط همان بخش را بررسی کند و زمان بررسی کم شود. برای مثال، اگر روی کامپایلر کار می‌کنید، می‌توانید دستور را به x check compiler --json-output تغییر دهید تا فقط بخش کامپایلر بررسی شود. با اجرای x check --help --verbose می‌توانید بخش‌های موجود را ببینید.

    اجرای ./x setup editor از شما می‌خواهد یک فایل پیکربندی LSP محلی پروژه برای یکی از ویرایشگرهای پشتیبانی‌شده بسازید. همچنین می‌توانید فایل پیکربندی را به‌عنوان یکی از گام‌های اجرای ./x setup بسازید.

    استفاده از پوشهٔ ساخت مشترک برای rust-analyzer

    به‌طور پیش‌فرض، وقتی rust-analyzer یک دستور bootstrap را اجرا می‌کند، از پوشهٔ ساختی جدا از ساخت‌های دستی خط فرمان استفاده می‌کند. اگر بخواهید در فضای دیسک صرفه‌جویی کنید می‌توانید این را در فایل پیکربندی LSP تولیدشده بازنویسی کنید.

    اما این توصیه نمی‌شود:

    • هر ساخت پوشهٔ ساخت را قفل می‌کند و دیگری را به انتظار وامی‌دارد، پس اجرای ساخت‌های خط فرمان در حالی که rust-analyzer دستورها را در پس‌زمینه اجرا می‌کند غیرممکن می‌شود.
    • خطر بیشتری وجود دارد که یکی از ساخت‌ها آرتیفکت‌های ساخته‌شدهٔ قبلی را به‌دلیل پرچم‌های متضاد کامپایلر یا تنظیمات دیگر حذف کند، که در برخی موارد بازسازی‌های اضافی را ناگزیر می‌کند.

    Visual Studio Code

    انتخاب vscode در ./x setup editor از شما می‌خواهد فایل .vscode/settings.json را بسازید که Visual Studio Code را پیکربندی می‌کند. تنظیمات توصیه‌شدهٔ rust-analyzer در src/etc/rust_analyzer_settings.json قرار دارند.

    اگر اجرای ./x check هنگام ذخیره ناخوشایند است، در VS Code می‌توانید به‌جای آن از Build Task استفاده کنید:

    // .vscode/tasks.json
{
    "version": "2.0.0",
    "tasks": [
        {
            "label": "./x check",
            "command": "./x check",
            "type": "shell",
            "problemMatcher": "$rustc",
            "presentation": { "clear": true },
            "group": { "kind": "build", "isDefault": true }
        }
    ]
}

    Neovim

    برای کاربران Neovim چند گزینه وجود دارد:

    1. ساده‌ترین راه استفاده از neoconf.nvim است، اما این از API منسوخ require('lspconfig') استفاده می‌کند که در neovim 0.11 به بعد هشدار نمایش می‌دهد.
    2. استفاده از coc.nvim گزینهٔ دیگری است، اما نیاز دارد node.js نصب باشد.
    3. استفاده از یک اسکریپت سفارشی برای بارگذاری تنظیمات rust-analyzer.

    neoconf.nvim

    neoconf.nvim فایل‌های پیکربندی محلی پروژه را با LSP بومی ممکن می‌کند. گام‌های استفاده از آن در ادامه آمده است. توجه کنید که نیاز دارند rust-analyzer از قبل با Neovim پیکربندی شده باشد. گام‌های این کار را می‌توان اینجا یافت.

    1. ابتدا افزونه را نصب کنید. این کار با دنبال‌کردن گام‌های README ممکن است.
    2. ./x setup editor را اجرا کنید و vscode را برای ساخت فایل .vscode/settings.json انتخاب کنید. neoconf وقتی این فایل تشخیص داده شود می‌تواند تنظیمات rust-analyzer را هنگام باز‌شدن پروژه به‌طور خودکار بخواند و به‌روز کند. Neovim متغیر ${workspaceFolder} در VS Code را گسترش نمی‌دهد، پس هر مورد آن را در فایل تولیدشده با مسیر مطلق مخزن rust خود جایگزین کنید.

    coc.nvim

    اگر از coc.nvim استفاده می‌کنید، می‌توانید ./x setup editor را اجرا کنید و vim را برای ساخت .vim/coc-settings.json انتخاب کنید. تنظیمات را می‌توان با :CocLocalConfig ویرایش کرد. تنظیمات توصیه‌شده در src/etc/rust_analyzer_settings.json قرار دارند.

    Custom LSP settings

    اگر neovim 0.11 به بعد را اجرا می‌کنید، می‌توانید rust-analyzer را فقط با nvim-lspconfig و یک اسکریپت سفارشی پیکربندی کنید.

    1. مطمئن شوید rust-analyzer LSP راه‌اندازی شده است
    2. فایل $HOME/.config/nvim/after/plugged/rust_analyzer.lua را با محتوای زیر بسازید:
    -- Capture the default functions from nvim-lspconfig/lsp/rust_analyzer.lua before overriding it.
-- This file is in after/plugin to guarantee nvim-lspconfig has been initialised already.
local default_root_dir = vim.lsp.config["rust_analyzer"].root_dir
local default_before_init = vim.lsp.config["rust_analyzer"].before_init

vim.lsp.config("rust_analyzer", {
    cmd = { "rust-analyzer" },
    filetypes = { "rust" },
    -- To support rust-lang/rust, we need to detect when we're in the rust repo and use the git root
    -- instead of cargo project root.
    root_dir = function(bufnr, on_dir)
        local git_root = vim.fs.root(bufnr, { ".git" })
        if git_root then
            if vim.uv.fs_stat(vim.fs.joinpath(git_root, "src/etc/rust_analyzer_zed.json")) then
                on_dir(git_root)
                return
            end
        end
        -- For anything that doesn't match rust-lang/rust, fallback to default root_dir
        default_root_dir(bufnr, on_dir)
    end,
    before_init = function(init_params, config)
        -- When inside rust-lang/rust, we need to use the special rust-analyzer settings.
        local settings = vim.fs.joinpath(config.root_dir, "src/etc/rust_analyzer_zed.json")
        if vim.uv.fs_stat(settings) then
            local file = io.open(settings)
            -- nvim 0.12+ supports comments otherwise you'll need content:gsub("//[^\n]*", "").
            local json = vim.json.decode(file:read("*a"), { skip_comments = true })
            file:close()
            config.settings["rust-analyzer"] = vim.tbl_deep_extend(
                "force", -- Overwrite with the special settings when there is a conflict.
                config.settings["rust-analyzer"] or {},
                json.lsp["rust-analyzer"].initialization_options
            )
        end
        default_before_init(init_params, config)
    end,
})

vim.lsp.enable("rust_analyzer")

    اگر می‌خواهید از build task که بالا توضیح داده شد استفاده کنید، می‌توانید در پیکربندی خود دستور خودتان را بسازید، یا افزونه‌ای مثل overseer.nvim نصب کنید که می‌تواند فایل‌های task.json در VSCode را بخواند، و همان دستورالعمل‌های بالا را دنبال کنید.

    Emacs

    Emacs از طریق Eglot از rust-analyzer با پیکربندی محلی پروژه پشتیبانی می‌کند. گام‌های راه‌اندازی Eglot با rust-analyzer را می‌توان اینجا یافت. پس از راه‌اندازی Emacs و Eglot برای توسعهٔ Rust به‌طور کلی، می‌توانید ./x setup editor را اجرا کنید و emacs را انتخاب کنید، که از شما می‌خواهد فایل .dir-locals.el را با پیکربندی توصیه‌شده برای Eglot بسازید. تنظیمات توصیه‌شده در src/etc/rust_analyzer_eglot.el قرار دارند. برای اطلاعات بیشتر دربارهٔ پیکربندی Eglot مخصوص پروژه راهنما را ببینید.

    Helix

    Helix با LSP و پشتیبانی rust-analyzer داخلی می‌آید. می‌توان آن را با languages.toml پیکربندی کرد، همان‌طور که اینجا توضیح داده شده است. می‌توانید ./x setup editor را اجرا کنید و helix را انتخاب کنید، که از شما می‌خواهد languages.toml را با پیکربندی توصیه‌شده برای Helix بسازید. تنظیمات توصیه‌شده در src/etc/rust_analyzer_helix.toml قرار دارند.

    Zed

    Zed با LSP و پشتیبانی rust-analyzer داخلی می‌آید. می‌توان آن را با .zed/settings.json پیکربندی کرد، همان‌طور که اینجا توضیح داده شده است. انتخاب zed در ./x setup editor از شما می‌خواهد فایل .zed/settings.json را بسازید که Zed را با پیکربندی توصیه‌شده تنظیم می‌کند. تنظیمات توصیه‌شدهٔ rust-analyzer در src/etc/rust_analyzer_zed.json قرار دارند.

    بررسی کنید، بررسی کنید، و دوباره بررسی کنید

    هنگام بازآرایی (refactoring) ساده، می‌تواند مفید باشد ./x check را پیوسته اجرا کنید. اگر rust-analyzer را مطابق بالا راه‌اندازی کرده باشید، این کار هر بار که فایلی را ذخیره می‌کنید برایتان انجام می‌شود. در اینجا فقط بررسی می‌کنید که کامپایلر ساخته می‌شود، اما اغلب فقط همین لازم است (مثلاً هنگام تغییر نام یک متد). سپس می‌توانید وقتی واقعاً لازم شد تست‌ها را اجرا کنید، با ./x build.

    در واقع گاهی مفید است حتی وقتی صددرصد مطمئن نیستید کد کار می‌کند، تست‌ها را به تعویق بیندازید. سپس می‌توانید commitهای بازآرایی را پشت سر هم بسازید و تست‌ها را بعداً اجرا کنید. آن‌گاه می‌توانید با git bisect دقیقاً پیدا کنید کدام commit مشکل را ایجاد کرده است. یک اثر جانبی خوب این سبک این است که در پایان مجموعه‌ای ریزدانه از commitها دارید که همگی ساخته می‌شوند و تست‌ها را می‌گذرانند. این اغلب به بازبینی کمک می‌کند.

    پیکربندی rustup برای استفاده از nightly

    برخی بخش‌های فرایند bootstrap از نسخه‌های nightly سنجاق‌شدهٔ ابزارهایی مثل rustfmt استفاده می‌کنند. برای اینکه کارهایی مثل cargo fmt در مخزن شما درست کار کنند، یک toolchain از نوع nightly را با rustup نصب کنید و سپس این دستور را اجرا کنید:

    cd <path to rustc repo>
rustup override set nightly

    فراموش نکنید این کار را برای همهٔ پوشه‌هایی که برایشان worktree ساخته‌اید انجام دهید. ممکن است لازم باشد از نسخهٔ nightly سنجاق‌شده در src/stage0 استفاده کنید، اما اغلب کانال معمولی nightly هم کار می‌کند.

    نکته: برای اینکه ببینید چگونه با rustfmt واقعی‌ای که x استفاده می‌کند پیکربندی شود بخش مربوط به vscode را ببینید، و برای راه‌اندازی toolchain در rustup برای کامپایلر bootstrap‌شدهٔ خود بخش مربوط به rustup را ببینید.

    نکته: این کار به شما اجازه نمی‌دهد rustc را مستقیماً با cargo بسازید. همچنان باید برای کار روی کامپایلر یا کتابخانهٔ استاندارد از x استفاده کنید، این فقط به شما اجازه می‌دهد از cargo fmt استفاده کنید.

    ساخت سریع‌تر با CI-rustc

    اگر روی کامپایلر کار نمی‌کنید، اغلب نیازی نیست درخت کامپایلر را بسازید. برای مثال، می‌توانید ساخت کامپایلر را رد کنید و فقط درخت library یا ابزارهای زیر src/tools را بسازید. برای این کار، باید گزینهٔ download-rustc را در پیکربندی خود تنظیم کنید. این به bootstrap می‌گوید برای گام‌های stage > 0 از جدیدترین کامپایلر nightly استفاده کند، یعنی دو کامپایلر از پیش ساخته‌شده خواهد داشت: کامپایلر stage0 و کامپایلر download-rustc برای گام‌های stage > 0. به این ترتیب هرگز نیازی به ساخت کامپایلر درون‌درختی نخواهد بود. در نتیجه زمان ساخت شما با نساختن کامپایلر درون‌درختی به‌طور چشمگیری کاهش می‌یابد.

    بازسازی سریع‌تر با --keep-stage-std

    گاهی فقط بررسی اینکه کامپایلر ساخته می‌شود کافی نیست. مثال رایج این است که باید یک دستور debug! اضافه کنید تا مقدار برخی حالت‌ها را بررسی کنید یا مسئله را بهتر بفهمید. در آن صورت واقعاً به ساخت کامل نیاز ندارید. با دور‌زدن ابطال cache در bootstrap، اغلب می‌توانید این ساخت‌ها را سریع‌تر تمام کنید. تنها نکته این است که این کار کمی دستکاری لازم دارد و ممکن است کامپایلرهایی تولید کند که کار نمی‌کنند (اما این به‌آسانی تشخیص و رفع می‌شود).

    ترتیب دستورهای مورد نیاز به این شکل است:

    • Initial build: ./x build library
    • Subsequent builds: ./x build library --keep-stage-std=1

    همان‌طور که گفته شد، اثر --keep-stage-std=1 این است که فقط فرض می‌کنیم کتابخانهٔ استاندارد قدیمی قابل‌استفادهٔ مجدد است. اگر کامپایلر را ویرایش می‌کنید، این اغلب درست است: شما که کتابخانهٔ استاندارد را تغییر نداده‌اید. اما گاهی درست نیست: برای مثال، اگر بخش «فراداده» (metadata) کامپایلر را ویرایش می‌کنید، که نحوهٔ رمزگذاری نوع‌ها و حالت‌های دیگر در فایل‌های rlib را کنترل می‌کند، یا اگر چیزهایی را ویرایش می‌کنید که در فراداده قرار می‌گیرند (مثل تعریف MIR).

    یعنی ممکن است هنگام استفاده از --keep-stage-std=1 رفتار عجیبی از کامپایل ببینید، مثلاً ICEهای عجیب یا panicهای دیگر. در آن صورت باید به‌سادگی --keep-stage-std=1 را از دستور حذف کنید و دوباره بسازید.

    همچنین می‌توانید هنگام اجرای تست‌ها از --keep-stage-std=1 استفاده کنید. چیزی شبیه این:

    • Initial test run: ./x test tests/ui
    • Subsequent test run: ./x test tests/ui --keep-stage-std=1

    استفاده از کامپایل افزایشی

    می‌توانید برای صرفه‌جویی بیشتر در زمان بازسازی‌های بعدی، پرچم --incremental را هم فعال کنید:

    ./x test tests/ui --incremental --test-args issue-1234

    اگر نمی‌خواهید پرچم را در هر دستور بیاورید، می‌توانید آن را در bootstrap.toml فعال کنید:

    [rust]
incremental = true

    توجه کنید که کامپایل افزایشی بیش از حد معمول فضای دیسک مصرف می‌کند. اگر فضای دیسک برایتان مهم است، شاید بخواهید هر از چند گاهی اندازهٔ پوشهٔ build را بررسی کنید.

    Fine-tuning optimizations

    تنظیم optimize = false کامپایلر را برای تست‌ها بیش از حد کند می‌کند. اما برای بهبود چرخهٔ تست، می‌توانید بهینه‌سازی‌ها را به‌صورت انتخابی فقط برای crateهایی که باید دوباره بسازید غیرفعال کنید (منبع). برای مثال هنگام کار روی rustc_mir_build، crateهای rustc_mir_build و rustc_driver بیشترین زمان را برای بازسازی افزایشی می‌گیرند. بنابراین می‌توانید موارد زیر را در Cargo.toml ریشه قرار دهید:

    [profile.release.package.rustc_mir_build]
opt-level = 0
[profile.release.package.rustc_driver]
opt-level = 0

    کار روی چند شاخه (branch) به‌طور همزمان

    کار موازی روی چند شاخه می‌تواند کمی آزاردهنده باشد، چون ساخت کامپایلر روی یک شاخه باعث بازنویسی ساخت قبلی و cache کامپایل افزایشی می‌شود. یک راه‌حل داشتن چند clone از مخزن است، اما این یعنی ذخیرهٔ فراداده Git چندین بار، و لزوم به‌روزرسانی جداگانهٔ هر clone.

    خوشبختانه Git راه‌حل بهتری به نام worktree دارد. این به شما اجازه می‌دهد چند «درخت کاری» بسازید که همگی پایگاه‌دادهٔ Git یکسانی دارند. علاوه بر این، چون همهٔ worktreeها پایگاه‌دادهٔ شیء مشترکی دارند، اگر یک شاخه (مثلاً main) را در هر کدام به‌روز کنید، می‌توانید از commitهای جدید در هر یک از worktreeها استفاده کنید. یک نکته این است که زیرماژول‌ها به اشتراک گذاشته نمی‌شوند. آن‌ها همچنان چندین بار clone می‌شوند.

    با فرض اینکه در پوشهٔ ریشهٔ مخزن Rust خود هستید، می‌توانید با اجرای دستور زیر یک «درخت کاری پیوندی» در پوشهٔ جدید «rust2» بسازید:

    git worktree add ../rust2

    ساخت worktree جدید برای شاخهٔ جدیدی بر پایهٔ main به این شکل است:

    git worktree add -b my-feature ../rust2 main

    سپس می‌توانید از پوشهٔ rust2 به‌عنوان workspace جداگانه برای تغییر و ساخت rustc استفاده کنید!

    کار با nix

    چند پیکربندی nix در src/tools/nix-dev-shell تعریف شده است.

    اگر از direnv استفاده می‌کنید، می‌توانید یک پیوند نمادین (symbolic link) به src/tools/nix-dev-shell/envrc-flake یا src/tools/nix-dev-shell/envrc-shell بسازید

    ln -s ./src/tools/nix-dev-shell/envrc-flake ./.envrc # Use flake

    or

    ln -s ./src/tools/nix-dev-shell/envrc-shell ./.envrc # Use nix-shell

    اگر از flake استفاده می‌کنید، حتماً آن را با دستور زیر هم به‌روز کنید:

    nix flake update --flake ./src/tools/nix-dev-shell

    shell دستوری به نام x می‌سازد که اسکریپت ./x.py را با همهٔ وابستگی‌های درست تنظیم‌شده اجرا می‌کند.

    Note

    توجه کنید که هنگام استفاده از nix در توزیعی غیر از NixOS، ممکن است لازم باشد build.patch-binaries-for-nix = true را در bootstrap.toml تنظیم کنید. Bootstrap سعی می‌کند تشخیص دهد که در nix اجرا می‌شود یا نه و patch‌کردن را خودکار فعال کند، اما این تشخیص ممکن است false negative داشته باشد.

    همچنین می‌توانید از shell در nix برای مدیریت bootstrap.toml استفاده کنید:

    let
  config = pkgs.writeText "rustc-config" ''
    # Your bootstrap.toml content goes here
  ''
pkgs.mkShell {
  /* ... */
  # This environment variable tells bootstrap where our bootstrap.toml is.
  RUST_BOOTSTRAP_CONFIG = config;
}

    Shell Completions

    اگر از Bash، Zsh، Fish یا PowerShell استفاده می‌کنید، می‌توانید اسکریپت‌های تکمیل خودکار تولیدشدهٔ ./x را در src/etc/completions بیابید.

    می‌توانید از source ./src/etc/completions/x.<extension> برای بارگذاری تکمیل‌ها برای shell انتخابی خود، یا & .\src\etc\completions\x.ps1 برای PowerShell استفاده کنید. افزودن این به اسکریپت راه‌اندازی shell (مثلاً .bashrc) این تکمیل را به‌طور خودکار بارگذاری می‌کند.
