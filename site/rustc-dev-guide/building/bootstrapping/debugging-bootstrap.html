    اشکال‌زدایی bootstrap

    دو راه اصلی برای اشکال‌زدایی (و پروفایل‌گیری از) bootstrap وجود دارد. راه اول لاگ‌گیری با println و راه دوم feature با نام tracing است.

    لاگ‌گیری با println

    Bootstrap لاگ‌گیری گسترده و بدون ساختار دارد. بیشتر آن پشت پرچم --verbose قرار گرفته است (برای جزئیات بیشتر از -vv استفاده کنید).

    اگر می‌خواهید خروجی مفصل دستورهای Cargo اجراشده و انواع دیگر لاگ‌های جزئی را ببینید، هنگام فراخوانی bootstrap پرچم -v یا -vv را بدهید. توجه کنید که لاگ‌ها بدون ساختارند و ممکن است حجیم و طاقت‌فرسا باشند.

    tracing در bootstrap

    Bootstrap یک feature شرطی با نام tracing دارد که قابلیت‌های زیر را فراهم می‌کند:

    • لاگ‌گیری ساخت‌یافته را با استفاده از رویدادها و spanهای tracing فعال می‌کند.
    • یک فایل trace مرورگر Chrome تولید می‌کند که می‌توان از آن برای مصورسازی سلسله‌مراتب و مدت‌زمان stepها و دستورهای اجراشده استفاده کرد.
      • می‌توانید فایل تولیدشده chrome-trace.json را با Chrome در زبانه chrome://tracing یا مثلاً با Perfetto باز کنید.
    • نمودارهای GraphViz تولید می‌کند که وابستگی‌های میان stepهای اجراشده را نشان می‌دهند.
      • می‌توانید فایل تولیدشده step-graph-*.dot را مثلاً با xdot باز کنید تا نمودار stepها را ببینید، یا مثلاً با dot -Tsvg فایل GraphViz را به SVG تبدیل کنید.
    • یک خلاصه اجرای دستورها تولید می‌کند که نشان می‌دهد کدام دستورها اجرا شده‌اند، چند اجرای آن‌ها از کش استفاده کرده و کدام دستورها کندترین اجرا را داشته‌اند.
      • فایل تولیدشده command-stats.txt قالبی ساده و خوانا برای انسان دارد.

    لاگ‌های ساخت‌یافته در خروجی خطای استاندارد (stderr) نوشته می‌شوند، در حالی که خروجی‌های دیگر در فایل‌هایی در پوشه <build-dir>/bootstrap-trace/<pid> ذخیره می‌شوند. برای راحتی، bootstrap همچنین یک symlink به آخرین پوشه خروجی trace تولیدشده در <build-dir>/bootstrap-trace/latest می‌سازد.

    توجه کنید که اگر bootstrap را با --dry-run اجرا کنید، پوشه خروجی tracing ممکن است تغییر کند. Bootstrap همیشه در پایان اجرا مسیری را که فایل‌های خروجی tracing در آن ذخیره شده‌اند چاپ می‌کند.

    $ BOOTSTRAP_TRACING=trace ./x build library --stage 1

    کنترل خروجی tracing

    متغیر محیطی BOOTSTRAP_TRACING یک فیلتر tracing_subscriber می‌پذیرد. اگر BOOTSTRAP_TRACING=trace را تنظیم کنید، همه لاگ‌ها فعال می‌شوند، اما این می‌تواند طاقت‌فرسا باشد. بنابراین می‌توانید با فیلتر، حجم داده‌های لاگ‌شده را کم کنید.

    دو روش مستقل از هم برای کنترل نوع لاگ‌های tracing مورد نظر شما وجود دارد:

    1. می‌توانید سطح لاگ را مشخص کنید، مثلاً debug یا trace.
      • اگر سطحی را انتخاب کنید، همه رویدادها/spanهایی که سطح اولویت برابر یا بالاتر دارند نمایش داده می‌شوند.
    2. همچنین می‌توانید هدف لاگ را کنترل کنید، مثلاً bootstrap یا bootstrap::core::config یا یک هدف سفارشی مانند CONFIG_HANDLING یا STEP.
      • هدف‌های سفارشی برای محدود کردن نوع spanهای مورد علاقه شما به کار می‌روند، زیرا خروجی BOOTSTRAP_TRACING=trace می‌تواند بسیار پرحجم باشد. در حال حاضر می‌توانید از این هدف‌های سفارشی استفاده کنید:
        • CONFIG_HANDLING: spanهای مربوط به مدیریت پیکربندی را نشان می‌دهد.
        • STEP: همه stepهای اجراشده را نشان می‌دهد. دستورهای اجراشده سطح رویداد info دارند.
        • COMMAND: همه دستورهای اجراشده را نشان می‌دهد. دستورهای اجراشده سطح رویداد trace دارند.
        • IO: عملیات I/O انجام‌شده را نشان می‌دهد. دستورهای اجراشده سطح رویداد trace دارند.
          • توجه کنید که در حال حاضر بسیاری از عملیات I/O ردیابی نمی‌شوند.

    البته می‌توانید آن‌ها را با هم ترکیب کنید (لاگ‌های هدف‌های سفارشی معمولاً علاوه بر آن پشت سطح لاگ TRACE قرار دارند):

    $ BOOTSTRAP_TRACING=CONFIG_HANDLING=trace,STEP=info,COMMAND=trace ./x build library --stage 1

    توجه کنید که سطحی که با BOOTSTRAP_TRACING تعیین می‌کنید روی spanهایی که در فایل trace مرورگر Chrome ثبت می‌شوند نیز اثر دارد.

    همچنین می‌توانید متغیر محیطی BOOTSTRAP_TRACING_SKIP_TIME=1 را بدهید تا زمان‌نگاشت (timestamp) در خروجی tracing نیاید. این برای مقایسه/diff گرفتن stepهای اجراشده میان دو نسخه از bootstrap مفید است.

    FIXME(#96176): tracing اختصاصی برای compiler() در برابر compiler_for()

    هدف‌های اضافی COMPILER و COMPILER_FOR برای کمک به ردیابی کاری که builder.compiler() و builder.compiler_for() انجام می‌دهند به کار می‌روند. اگر #96176 حل شود، باید حذف شوند.

    استفاده از tracing در bootstrap

    هم ماکروهای tracing::* و هم ماکروی proc-macro به نام attribute tracing::instrument باید پشت feature با نام tracing قرار بگیرند. نمونه‌ها:

    #[cfg(feature = "tracing")]
use tracing::instrument;

struct Foo;

impl Step for Foo {
    type Output = ();

    #[cfg_attr(feature = "tracing", instrument(level = "trace", name = "Foo::should_run", skip_all))]
    fn should_run(run: ShouldRun<'_>) -> ShouldRun<'_> {
        trace!(?run, "entered Foo::should_run");

        todo!()
    }

    fn run(self, builder: &Builder<'_>) -> Self::Output {
        trace!(?run, "entered Foo::run");

        todo!()
    }    
}

    برای #[instrument] توصیه می‌شود:

    • برای جزئی‌نگری بیشتر آن را پشت سطح trace قرار دهید، و برای تابع‌های هسته‌ای احتمالاً سطح debug.
    • با name = ".." صریحاً یک نام instrumentation انتخاب کنید تا مثلاً run مربوط به stepهای مختلف از هم تمایز یابند.
    • مراقب باشید tracing باعث رفتار متفاوت نشود، مثلاً ساختن چیزهای اضافی فقط وقتی زیرساخت tracing فعال است.

    یکپارچگی با rust-analyzer؟

    متأسفانه، چون bootstrap یک rust-analyzer.linkedProjects است، نمی‌توانید از r-a بخواهید خود bootstrap را با feature با نام tracing فعال بررسی/ساخت کند تا تکمیل‌های مربوط را بگیرید، زیرا پشتیبانی لازم وجود ندارد، همان‌گونه که در https://github.com/rust-lang/rust-analyzer/issues/8521 توضیح داده شده است.
