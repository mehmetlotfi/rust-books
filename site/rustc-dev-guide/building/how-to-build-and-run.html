راهنمای توسعهٔ rustcrustc Development Guide

    نحوهٔ ساخت و اجرای کامپایلر

    برای کاربران profile = "library" یا کاربرانی که از download-rustc = true | "if-unchanged" استفاده می‌کنند، توجه داشته باشید که جریان ./x test library/std وقتی download-rustc فعال است (یعنی هیچ تغییری در کامپایلر نیست) فعلاً خراب است. این موضوع در https://github.com/rust-lang/rust/issues/142505 پیگیری می‌شود. در این حالت فقط جریان ./x test تحت‌تأثیر است؛ ./x {check,build} library/std همچنان باید کار کند.

    در کوتاه‌مدت ممکن است لازم باشد برای ./x test library/std گزینهٔ download-rustc را غیرفعال کنید. این کار را می‌توان به یکی از این دو روش انجام داد:

    1. ./x test library/std --set rust.download-rustc=false
    2. یا rust.download-rustc = false را در bootstrap.toml تنظیم کنید.

    متأسفانه این کار نیازمند ساخت کامپایلر stage 1 است. تیم bootstrap روی این موضوع کار می‌کند، اما پیاده‌سازی یک راه‌حل قابل‌نگهداری زمان می‌برد.

    کامپایلر با ابزاری به نام bootstrap ساخته می‌شود. برای اجرای آن باید Python نصب شده باشد.

    شروع سریع

    برای راهنمایی کوتاه‌تر در مورد راه‌اندازی کامپایلر، شروع سریع را ببینید.

    دریافت کد منبع

    مخزن اصلی rust-lang/rust است. این مخزن شامل کامپایلر، کتابخانهٔ استاندارد (از جمله core، alloc، test، proc_macro و غیره)، و مجموعه‌ای از ابزارهاست (مانند rustdoc، زیرساخت bootstrap و غیره).

    اولین قدم برای کار روی rustc کلون کردن مخزن است:

    git clone https://github.com/rust-lang/rust.git
cd rust

    توجه: در ویندوز، اسکن آنتی‌ویروس می‌تواند اجرای Git و دستورهای ساخت را در یک checkout بزرگ به‌طور محسوسی کند کند. اگر چنین شد، پیشنهاد می‌شود فقط پوشهٔ checkout مربوط به Rust را به فهرست استثناهای Windows Security اضافه کنید. از افزودن استثناهای گسترده‌تر از حد لازم خودداری کنید.

    کلون جزئی مخزن

    به دلیل حجم مخزن، کلون کردن با اینترنت کند می‌تواند زمان زیادی ببرد، و برای ذخیرهٔ تاریخچهٔ کامل هر فایل و پوشه به فضای دیسک نیاز دارد. در عوض می‌توان به git گفت که یک کلون جزئی (partial clone) انجام دهد؛ در این حالت فقط محتوای فعلی فایل‌ها به‌طور کامل دریافت می‌شود، و محتوای بقیهٔ فایل‌ها وقتی لازم شود، مثلاً وقتی به عقب در تاریخچه می‌روید، به‌طور خودکار دریافت می‌شود. همهٔ دستورهای git مثل همیشه کار می‌کنند، با این هزینه که برای مشاهدهٔ نقاطی از تاریخچه که هنوز بارگذاری نشده‌اند به اتصال اینترنت نیاز دارید.

    git clone --filter='blob:none' https://github.com/rust-lang/rust.git
cd rust

    توجه: این پیوند این نوع checkout را با جزئیات بیشتر توضیح می‌دهد و آن را با حالت‌های دیگر، مانند کلون سطحی (shallow clone)، مقایسه می‌کند.

    کلون سطحی مخزن

    یک جایگزین قدیمی‌تر برای کلون جزئی، کلون سطحی مخزن است. برای این کار می‌توانید از گزینهٔ --depth N همراه با دستور git clone استفاده کنید. این گزینه به git می‌گوید یک «کلون سطحی» انجام دهد، یعنی مخزن را کلون کند اما آن را به N کامیت آخر محدود کند.

    گذاشتن --depth 1 به git می‌گوید مخزن را کلون کند اما تاریخچه را به آخرین کامیتی که روی شاخهٔ main است محدود کند؛ این برای مرور کد منبع یا ساخت کامپایلر معمولاً کافی است.

    git clone --depth 1 https://github.com/rust-lang/rust.git
cd rust

    توجه: کلون سطحی محدود می‌کند که کدام دستورهای git قابل اجرا هستند. اگر قصد دارید روی کامپایلر کار کنید و در آن مشارکت کنید، معمولاً توصیه می‌شود مخزن را به‌طور کامل کلون کنید همان‌طور که در بالا نشان داده شد، یا به جای آن یک کلون جزئی انجام دهید.

    برای مثال، git bisect و git blame به تاریخچهٔ کامیت‌ها نیاز دارند، بنابراین اگر مخزن با --depth 1 کلون شده باشد کار نمی‌کنند.

    bootstrap چیست؟

    Bootstrap ابزار ساخت مخزن rust است. این ابزار می‌تواند مستندات را بسازد، آزمون‌ها را اجرا کند، و کامپایلر و کتابخانهٔ استاندارد را بسازد.

    این فصل بر مبانی لازم برای کار مؤثر تمرکز دارد، اما اگر می‌خواهید دربارهٔ bootstrap بیشتر بدانید، این فصل را بخوانید.

    اجرای bootstrap

    Bootstrap را می‌توان در بیشتر سیستم‌ها (یونیکس، و ویندوز در صورت پیکربندی) به این صورت اجرا کرد:

    ./x <subcommand> [flags]

    مستندات و مثال‌ها فرض می‌کنند که bootstrap را به این شکل اجرا می‌کنید. برخی روش‌های جایگزین عبارت‌اند از:

    # In Windows PowerShell (if PowerShell is configured to run scripts)
./x <subcommand> [flags]
# In NuShell (if PowerShell is configured to run scripts). `./x` does not work in NuShell if `.py` files are not configured to run Python.
./x.ps1 <subcommand> [flags]

# On the Windows Command Prompt (if .py files are configured to run Python)
x.py <subcommand> [flags]

# You can also run Python yourself, e.g.:
python x.py <subcommand> [flags]

# On a Unix shell if you have `python3` but an `sh` that doesn't support `local`, e.g. on Solaris
./x.py <subcommand> [flags]

    در ویندوز، دستورهای PowerShell ممکن است خطایی شبیه این بدهند:

    PS C:\Users\vboxuser\rust> ./x
./x : File C:\Users\vboxuser\rust\x.ps1 cannot be loaded because running scripts is disabled on this system. For more
information, see about_Execution_Policies at https://go.microsoft.com/fwlink/?LinkID=135170.
At line:1 char:1
+ ./x
+ ~~~
    + CategoryInfo          : SecurityError: (:) [], PSSecurityException
    + FullyQualifiedErrorId : UnauthorizedAccess

    می‌توانید با اجازه دادن به PowerShell برای اجرای اسکریپت‌های محلی از این خطا جلوگیری کنید:

    Set-ExecutionPolicy -ExecutionPolicy RemoteSigned -Scope CurrentUser

    اجرای راحت‌تر bootstrap

    یک فایل باینری وجود دارد که bootstrap را پوشش می‌دهد و x نام دارد. این باینری ./x را اجرا می‌کند، و می‌تواند در سطح سیستم نصب شود و از هر زیرپوشه‌ای از یک checkout اجرا شود. همچنین نسخهٔ مناسب Python را برای استفاده پیدا می‌کند و به این بستگی ندارد که اکنون از کدام shell استفاده می‌کنید.

    می‌توانید آن را با cargo install --locked --path src/tools/x نصب کنید.

    ساخت یک bootstrap.toml

    برای شروع، ./x setup را اجرا کنید و پیش‌فرض‌های compiler را انتخاب کنید. این کار مقداری مقداردهی اولیه انجام می‌دهد و یک bootstrap.toml با مقادیر پیش‌فرض معقول برای شما می‌سازد. اگر پیش‌فرض دیگری را انتخاب کنید (که احتمالاً اگر بخواهید در بخشی از rust غیر از کامپایلر، مثلاً rustdoc، مشارکت کنید چنین خواهید کرد)، حتماً اطلاعات مربوط به آن پیش‌فرض (در src/bootstrap/defaults) را بخوانید چون فرایند ساخت ممکن است برای پیش‌فرض‌های دیگر متفاوت باشد.

    به‌طور جایگزین، می‌توانید bootstrap.toml را دستی بنویسید. برای همهٔ تنظیمات موجود و کاربرد هر یک به bootstrap.example.toml نگاه کنید. برای تنظیمات متداولی که ممکن است بخواهید تغییر دهید به src/bootstrap/defaults نگاه کنید.

    اگر پیش‌تر rustc را ساخته‌اید و تنظیمات مربوط به LLVM را تغییر می‌دهید، ممکن است لازم باشد ./x clean --all را اجرا کنید تا تغییرات بعدی پیکربندی اعمال شوند. توجه کنید که ./x clean باعث ساخت مجدد LLVM نمی‌شود.

    دستورهای متداول x

    در اینجا فراخوانی‌های پایهٔ دستورهای x که بیشتر هنگام کار روی rustc، std، rustdoc و ابزارهای دیگر استفاده می‌شوند آمده است.

    دستورزمان استفاده
    ./x checkبررسی سریع برای اینکه ببینید بیشتر بخش‌ها کامپایل می‌شوند یا نه؛ rust-analyzer می‌تواند این را به‌طور خودکار برای شما اجرا کند
    ./x buildrustc، std و rustdoc را می‌سازد
    ./x testهمهٔ آزمون‌ها را اجرا می‌کند
    ./x fmtهمهٔ کد را قالب‌بندی می‌کند

    به همین شکل، این دستورها نقاط شروع مناسبی هستند. با این حال، برای هر یک گزینه‌ها و آرگومان‌های بیشتری وجود دارد که برای توسعهٔ جدی ارزش یادگیری دارند. به‌ویژه ./x build و ./x test راه‌های زیادی برای کامپایل یا آزمودن زیرمجموعه‌ای از کد فراهم می‌کنند که می‌تواند زمان زیادی صرفه‌جویی کند.

    همچنین توجه کنید که x از انواع پسوندهای مسیر برای پوشه‌های compiler، library و src/tools پشتیبانی می‌کند. بنابراین می‌توانید به‌جای x test src/tools/tidy به‌سادگی x test tidy را اجرا کنید. یا x build std را به‌جای x build library/std.

    برای جزئیات بیشتر، فصل‌های آزمون‌ها و rustdoc را ببینید.

    ساخت کامپایلر

    توجه کنید که ساخت به مقدار نسبتاً زیادی فضای ذخیره‌سازی نیاز دارد. ممکن است لازم باشد بیش از ۱۰ یا ۱۵ گیگابایت فضای آزاد برای ساخت کامپایلر داشته باشید.

    پس از ساخت bootstrap.toml، اکنون آمادهٔ اجرای x هستید. گزینه‌های زیادی وجود دارد، اما بیایید با دستوری شروع کنیم که احتمالاً بهترین دستور «اصلی» برای ساخت یک کامپایلر محلی است:

    ./x build library

    کاری که این دستور انجام می‌دهد:

    • rustc را با کامپایلر stage0 و std مربوط به stage0 می‌سازد.
    • library (کتابخانه‌های استاندارد) را با کامپایلر stage1 که همین الان ساخته شد می‌سازد.
    • یک sysroot کارکن stage1 را که شامل کامپایلر stage1 و کتابخانه‌های استاندارد stage1 است، مونتاژ می‌کند.

    این محصول نهایی (کامپایلر stage1 به‌علاوهٔ کتابخانه‌هایی که با آن کامپایلر ساخته شده‌اند) چیزی است که برای ساخت دیگر برنامه‌های Rust لازم دارید (مگر اینکه از #![no_std] یا #![no_core] استفاده کنید).

    احتمالاً متوجه می‌شوید که ساخت std مربوط به stage1 گلوگاه کار شماست، اما نگران نباشید، یک راه‌حل (نه‌چندان تمیز) وجود دارد… بخش اجتناب از ساخت مجدد std را ببینید.

    گاهی به ساخت کامل نیازی ندارید. وقتی نوعی «بازآرایی مبتنی بر نوع» انجام می‌دهید، مثل تغییر نام یک متد یا تغییر امضای یک تابع، می‌توانید به‌جای آن از ./x check برای ساختی بسیار سریع‌تر استفاده کنید.

    توجه کنید که کل این دستور فقط زیرمجموعه‌ای از ساخت کامل rustc را به شما می‌دهد. ساخت کامل rustc (آنچه با ./x build --stage 2 rustc به دست می‌آید) مراحل بیشتری دارد:

    • rustc را با کامپایلر stage1 بسازید.
      • کامپایلر حاصل در اینجا کامپایلر «stage2» نامیده می‌شود که از std مربوط به stage1 از دستور قبلی استفاده می‌کند.
    • librustdoc و چند چیز دیگر را با کامپایلر stage2 بسازید.

    تقریباً هرگز نیازی به این کار ندارید.

    ساخت مؤلفه‌های مشخص

    اگر روی کتابخانهٔ استاندارد کار می‌کنید، احتمالاً نیازی ندارید هر مؤلفهٔ پیش‌فرض دیگری را بسازید. در عوض می‌توانید با ارائهٔ نام یک مؤلفهٔ مشخص آن را بسازید، به این شکل:

    ./x build --stage 1 library

    اگر هنگام اجرای x setup پروفایل library را انتخاب کنید، می‌توانید --stage 1 را حذف کنید (این مقدار پیش‌فرض است).

    اگر می‌خواهید یک ابزار را بسازید، می‌توانید از این دستور استفاده کنید:

    ./x build src/tools/cargo

    همچنین می‌توانید بخش آزمون ابزارها را ببینید.

    ساخت یک toolchain برای rustup

    پس از اینکه rustc را با موفقیت ساختید، تعدادی فایل در پوشهٔ build شما ایجاد شده است. برای اینکه rustc حاصل را واقعاً اجرا کنید، توصیه می‌کنیم toolchainهای rustup بسازید. اولین دستور زیر toolchain مربوط به stage1 را که در مراحل بالا ساخته شد، با نام stage1 می‌سازد. دستور دوم toolchain مربوط به stage2 را با استفاده از کامپایلر stage1 می‌سازد. این در آینده در صورت اجرای کل مجموعهٔ آزمون لازم خواهد بود، اما در این صفحه ساخته نمی‌شود. ساخت stage2 با همان دستور ./x build که برای stage1 استفاده شد انجام می‌شود، با این تفاوت که مرحله 2 مشخص می‌شود.

    rustup toolchain link stage1 build/host/stage1
rustup toolchain link stage2 build/host/stage2

    اکنون می‌توانید rustc ساخته‌شده را از طریق toolchain اجرا کنید. اگر با -vV اجرا کنید، باید شمارهٔ نسخه‌ای ببینید که به -dev ختم می‌شود و نشان می‌دهد این نسخه از محیط محلی شما ساخته شده است:

    $ rustc +stage1 -vV
rustc 1.48.0-dev
binary: rustc
commit-hash: unknown
commit-date: unknown
host: x86_64-unknown-linux-gnu
release: 1.48.0-dev
LLVM version: 11.0

    toolchain مربوط به rustup به toolchain مشخص‌شده‌ای که در پوشهٔ build شما کامپایل شده اشاره می‌کند، بنابراین هر زمان x build یا x test برای آن toolchain/stage اجرا شود، toolchain مربوط به rustup به‌روز می‌شود.

    توجه: toolchain ساخته‌شده شامل cargo نیست. در این حالت، rustup به استفاده از cargo موجود در toolchain نصب‌شدهٔ nightly، beta یا stable (به همین ترتیب) بازمی‌گردد. اگر باید از flagهای ناپایدار cargo استفاده کنید، حتماً rustup install nightly را اجرا کنید، در صورتی که هنوز این کار را نکرده‌اید. مستندات rustup دربارهٔ toolchainهای سفارشی را ببینید.

    توجه: rust-analyzer و افزونهٔ IntelliJ Rust برای کار با proc macroها از مؤلفه‌ای به نام rust-analyzer-proc-macro-srv استفاده می‌کنند. اگر قصد دارید برای یک پروژه از یک toolchain سفارشی استفاده کنید (مثلاً با rustup override set stage1)، ممکن است بخواهید این مؤلفه را بسازید:

    ./x build proc-macro-srv-cli

    ساخت هدف‌ها برای کامپایل متقابل

    برای تولید کامپایلری که بتواند برای هدف‌های دیگر کامپایل متقابل (cross-compile) انجام دهد، هر تعداد flag از نوع target را به x build بدهید. برای مثال، اگر پلتفرم میزبان شما x86_64-unknown-linux-gnu است و هدف کامپایل متقابل شما wasm32-wasip1 است، می‌توانید این‌طور بسازید:

    ./x build --target x86_64-unknown-linux-gnu,wasm32-wasip1

    توجه کنید که اگر می‌خواهید کامپایلر حاصل بتواند crateهایی را بسازد که شامل proc macro یا build script هستند، باید حتماً پشتیبانی هدف را برای پلتفرم میزبان (در این مثال x86_64-unknown-linux-gnu) نیز به‌طور صریح بسازید.

    اگر می‌خواهید همیشه برای هدف‌های دیگر ساخت انجام شود بدون اینکه لازم باشد به x build flag بدهید، می‌توانید این را در بخش [build] فایل bootstrap.toml خود به این شکل پیکربندی کنید:

    build.target = ["x86_64-unknown-linux-gnu", "wasm32-wasip1"]

    توجه کنید که ساخت برای برخی هدف‌ها مستلزم نصب بودن وابستگی‌های خارجی است (مثلاً ساخت هدف‌های musl به یک نسخهٔ محلی از musl نیاز دارد). هر پیکربندی خاص هدف (مثلاً مسیر نسخهٔ محلی musl) باید در bootstrap.toml شما ارائه شود. برای اطلاعات دربارهٔ کلیدهای پیکربندی خاص هدف، bootstrap.example.toml را ببینید.

    برای نمونه‌هایی از پیکربندی کامل لازم برای ساخت یک هدف، لطفاً از کتاب rustc دیدن کنید، هر هدفی را در زیر عنوان «Platform Support» در سمت چپ انتخاب کنید، و به بخش مربوط به ساخت کامپایلر برای آن هدف نگاه کنید. برای هدف‌هایی که صفحهٔ متناظری در کتاب rustc ندارند، ممکن است بررسی Dockerfileها مفید باشد؛ این فایل‌ها را خود زیرساخت Rust برای راه‌اندازی و پیکربندی کامپایل متقابل به کار می‌برد.

    اگر دستورالعمل‌های بخش قبلی دربارهٔ ساخت toolchain برای rustup را دنبال کرده باشید، پس از ساخت کامپایلر می‌توانید از آن برای کامپایل متقابل به این شکل استفاده کنید:

    cargo +stage1 build --target wasm32-wasip1

    دیگر دستورهای x

    در اینجا چند دستور مفید دیگر x آمده است. برخی از آنها را در بخش‌های دیگر به تفصیل بررسی خواهیم کرد:

    • ساخت چیزها:
      • ./x build – همه‌چیز را با کامپایلر stage 1 می‌سازد، نه فقط تا std
      • ./x build --stage 2 – همه‌چیز را از جمله rustdoc با کامپایلر stage 2 می‌سازد
    • اجرای آزمون‌ها (برای جزئیات بیشتر بخش اجرای آزمون‌ها را ببینید):
      • ./x test library/std – آزمون‌های واحد و آزمون‌های یکپارچگی std را اجرا می‌کند
      • ./x test tests/ui – مجموعه آزمون ui را اجرا می‌کند
      • ./x test tests/ui/const-generics - همهٔ آزمون‌های زیرپوشهٔ const-generics/ از مجموعه آزمون ui را اجرا می‌کند
      • ./x test tests/ui/const-generics/const-types.rs - فقط آزمون const-types.rs را از مجموعه آزمون ui اجرا می‌کند

    پاک کردن پوشه‌های ساخت

    گاهی لازم است از صفر شروع کنید، اما معمولاً این‌طور نیست. اگر باید این کار را بکنید، به احتمال زیاد bootstrap درست کار نمی‌کند و باید دربارهٔ مشکل پیش‌آمده یک باگ گزارش کنید. اگر واقعاً لازم است همه‌چیز را پاک کنید، فقط یک دستور کافی است!

    ./x clean

    rm -rf build هم کار می‌کند، اما در این صورت باید LLVM را دوباره بسازید که حتی روی کامپیوترهای سریع هم می‌تواند زمان زیادی ببرد.

    نکاتی دربارهٔ فضای دیسک

    ساخت کامپایلر (به‌ویژه فراتر از stage 1) می‌تواند به مقدار قابل‌توجهی فضای خالی دیسک نیاز داشته باشد، احتمالاً حدود ۱۰۰ گیگابایت. اگر یک پوشهٔ ساخت جداگانه برای rust-analyzer داشته باشید (مثلاً build-rust-analyzer) این مقدار بیشتر هم می‌شود. رسیدن به این حد در dev-desktopها که برای هر کاربر یک سهمیهٔ دیسک مشخص دارند آسان است، اما این موضوع در توسعهٔ محلی هم صدق می‌کند. گاهی ممکن است لازم باشد:

    • پوشهٔ build/ را حذف کنید.
    • پوشهٔ build-rust-analyzer/ را حذف کنید (اگر یک پوشهٔ ساخت جداگانه برای rust-analyzer دارید).
    • toolchainهای غیرضروری را حذف کنید اگر از cargo-bisect-rustc استفاده می‌کنید. با rustup toolchain list می‌توانید ببینید کدام toolchainها نصب شده‌اند.
