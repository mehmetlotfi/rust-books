    Drop Check

    ما معمولاً الزام می‌کنیم که نوع متغیرهای محلی هر زمان که متغیر استفاده می‌شود well-formed باشد. این شامل اثبات where-boundهای متغیر محلی است و همچنین الزام می‌کند که تمام regionهای مورداستفاده‌ی آن زنده (live) باشند.

    تنها استثنا زمانی است که مقادیر هنگام خروج از حوزه (scope) به‌صورت ضمنی drop می‌شوند. در این حالت لزوماً لازم نیست مقدار زنده باشد:

    fn main() {
    let x = vec![];
    {
        let y = String::from("I am temporary");
        x.push(&y);
    }
    // `x` goes out of scope here, after the reference to `y`
    // is invalidated. This means that while dropping `x` its type
    // is not well-formed as it contain regions which are not live.
}

    این کار فقط زمانی سالم (sound) است که drop کردن مقدار تلاش نکند به regionی مرده دسترسی پیدا کند. ما این را با الزام به اینکه نوع مقدار drop-live باشد بررسی می‌کنیم. الزامات مربوط به آن در fn dropck_outlives محاسبه می‌شوند.

    ادامه‌ی این بخش از تعریف نوع زیر استفاده می‌کند که پارامتر region خود را ملزم می‌کند زنده باشد:

    struct PrintOnDrop<'a>(&'a str);
impl<'a> Drop for PrintOnDrop<'_> {
    fn drop(&mut self) {
        println!("{}", self.0);
    }
}

    مقادیر چگونه drop می‌شوند

    در اصل، مقداری از نوع T با اجرای «drop glue» آن drop می‌شود. Drop glue توسط کامپایلر تولید می‌شود و ابتدا <T as Drop>::drop را فراخوانی می‌کند و سپس به‌صورت بازگشتی drop glue هر مقدار تحت مالکیت را فراخوانی می‌کند.

    • اگر T یک Drop impl صریح داشته باشد، <T as Drop>::drop را فراخوانی کن.
    • صرف‌نظر از اینکه T پیاده‌سازی Drop دارد یا نه، به تمام مقادیری که T مالک آن‌هاست بازگشت کن:
      • ارجاع‌ها، اشاره‌گرهای خام، اشاره‌گرهای تابع، function itemها، شیء صفت‌ها1 و مقادیر اسکالر مالک چیزی نیستند.
      • تاپل‌ها، sliceها و آرایه‌ها عناصر خود را تحت مالکیت می‌دانند. برای آرایه‌هایی با طول صفر، هیچ مقداری از نوع عنصر در مالکیت نیست.
      • تمام فیلدهای (از همه‌ی variantها) ADTها تحت مالکیت در نظر گرفته می‌شوند. برای شمارش‌ها (enum) همه‌ی variantها را در نظر می‌گیریم. استثنا در اینجا ManuallyDrop<U> است که مالک U محسوب نمی‌شود. PhantomData<U> نیز مالک چیزی نیست. closureها و generatorها مالک upvarهای capture‌شده‌ی خود هستند.

    اینکه یک نوع drop glue دارد یا نه توسط fn Ty::needs_drop برگردانده می‌شود.

    drop جزئی یک متغیر محلی

    برای نوع‌هایی که خودشان Drop را پیاده‌سازی نمی‌کنند، می‌توانیم پیش از drop کردن بقیه، بخش‌هایی از مقدار را نیز به‌صورت جزئی move کنیم. در این حالت فقط drop glue مقادیری که هنوز move نشده‌اند فراخوانی می‌شود، برای مثال:

    fn main() {
    let mut x = (PrintOnDrop("third"), PrintOnDrop("first"));
    drop(x.1);
    println!("second")
}

    در طول ساخت MIR فرض می‌کنیم که یک متغیر محلی هر زمان که از حوزه خارج می‌شود ممکن است drop شود، به شرط آنکه نوع آن به drop نیاز داشته باشد. محاسبه‌ی drop glue دقیق برای یک متغیر پس از borrowck و در pass به نام ElaborateDrops انجام می‌شود. این یعنی حتی اگر بخشی از متغیر محلی قبلاً drop شده باشد، dropck همچنان لازم می‌داند که این مقدار زنده باشد. این حتی زمانی که متغیر محلی را کاملاً move کرده باشیم نیز صادق است.

    fn main() {
    let mut x;
    {
        let temp = String::from("I am temporary");
        x = PrintOnDrop(&temp);
        drop(x);
    }
} //~ ERROR `temp` does not live long enough.

    باید بتوان مقداری drop elaboration را پیش از borrowck انجام داد تا این مثال کامپایل شود. یک feature ناپایدار برای جابه‌جا کردن drop elaboration پیش از const checking وجود دارد: #73255. چنین feature gate‌ای برای انجام مقداری drop elaboration پیش از borrowck وجود ندارد، هرچند یک MCP مرتبط هست.

    dropck_outlives

    دو محاسبه‌ی «liveness» متمایز انجام می‌دهیم:

    • مقدار v در مکان L use-live است اگر ممکن باشد بعداً «استفاده» شود؛ «استفاده» در اینجا اساساً هر چیزی است که drop نباشد
    • مقدار v در مکان L drop-live است اگر ممکن باشد بعداً drop شود

    وقتی چیزی use-live است، کل نوع آن باید در L معتبر باشد. وقتی drop-live است، تمام regionهایی که dropck لازم می‌داند باید در L معتبر باشند. مقادیری که در MIR drop می‌شوند place هستند.

    قیدهایی که dropck_outlives برای یک نوع محاسبه می‌کند، از نزدیک با drop glue تولیدشده برای آن نوع مطابقت دارد. برخلاف drop glue، dropck_outlives به نوع مقادیر تحت مالکیت اهمیت می‌دهد، نه خود مقادیر. برای مقداری از نوع T

    • اگر T یک Drop صریح داشته باشد، لازم است همه‌ی آرگومان‌های جنریک زنده باشند، مگر آنکه با #[may_dangle] علامت‌گذاری شده باشند که در آن صورت کاملاً نادیده گرفته می‌شوند
    • صرف‌نظر از اینکه T یک Drop صریح دارد یا نه، به تمام نوع‌هایی که T مالک آن‌هاست بازگشت کن
      • ارجاع‌ها، اشاره‌گرهای خام، اشاره‌گرهای تابع، function itemها، شیء صفت‌ها1 و مقادیر اسکالر مالک چیزی نیستند.
      • تاپل‌ها، sliceها و آرایه‌ها نوع عنصر خود را تحت مالکیت می‌دانند. برای آرایه‌ها فعلاً بررسی نمی‌کنیم که طولشان صفر باشد یا نه.
      • تمام فیلدهای (از همه‌ی variantها) ADTها تحت مالکیت در نظر گرفته می‌شوند. استثنا در اینجا ManuallyDrop<U> است که مالک U محسوب نمی‌شود. ما PhantomData<U> را مالک U در نظر می‌گیریم.
      • closureها و generatorها مالک upvarهای capture‌شده‌ی خود هستند.

    بخش‌هایی که پررنگ شده‌اند، حالت‌هایی هستند که dropck_outlives نوع‌هایی را تحت مالکیت می‌داند که Ty::needs_drop نادیده‌شان می‌گیرد. ما فقط زمانی به dropck_outlives تکیه می‌کنیم که Ty::needs_drop برای متغیر محلی حاوی آن true برگردانده باشد. این یعنی الزامات liveness می‌توانند بسته به اینکه یک نوع درون متغیر محلی بزرگ‌تری قرار دارد یا نه تغییر کنند. این ناسازگار است و باید اصلاح شود: یک مثال برای آرایه‌ها و برای PhantomData.2

    یک راه ممکن برای رفع این ناسازگاری‌ها این است که ساخت MIR بدبینانه‌تر عمل کند، احتمالاً با ضعیف‌تر کردن Ty::needs_drop، یا به‌طور جایگزین با دقیق‌تر کردن dropck_outlives به‌گونه‌ای که لازم باشد regionهای کمتری زنده باشند.

    1. می‌توانید تصور کنید شیء صفت‌ها یک پیاده‌سازی Drop درونی دارند که مستقیماً از drop_in_place ارائه‌شده توسط vtable استفاده می‌کند. این پیاده‌سازی Drop ایجاب می‌کند همه‌ی پارامترهای جنریک آن زنده باشند. ↩ ↩2
