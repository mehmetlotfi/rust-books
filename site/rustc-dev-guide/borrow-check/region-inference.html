    استنتاج region (NLL)

    کد بررسی region مبتنی بر MIR در ماژول rustc_mir::borrow_check قرار دارد.

    تحلیل region مبتنی بر MIR از دو تابع اصلی تشکیل شده است:

    • replace_regions_in_mir که ابتدا فراخوانی می‌شود، دو وظیفه دارد:
      • اول، مجموعه‌ی regionهایی را که در signature تابع ظاهر می‌شوند پیدا می‌کند (مثلاً 'a در fn foo<'a>(&'a u32) { ... }). این‌ها regionهای «جهانی» (universal) یا «آزاد» (free) نامیده می‌شوند – به‌ویژه، آن‌ها regionهایی هستند که در بدنه‌ی تابع به‌صورت آزاد ظاهر می‌شوند.
      • دوم، تمام regionهای بدنه‌ی تابع را با متغیرهای استنتاج تازه جایگزین می‌کند. دلیلش این است که (در حال حاضر) آن regionها نتیجه‌ی استنتاج region واژگانی (lexical) هستند و بنابراین چندان جالب نیستند. هدف این است که در نهایت آن‌ها «regionهای پاک‌شده» (erased) باشند (یعنی هیچ اطلاعاتی نداشته باشند)، چون دیگر اصلاً استنتاج region واژگانی انجام نخواهیم داد.
    • compute_regions که دوم فراخوانی می‌شود: نتایج تحلیل move به‌عنوان آرگومان به آن داده می‌شود. وظیفه‌ی آن محاسبه‌ی مقادیر تمام متغیرهای استنتاجی است که replace_regions_in_mir معرفی کرده بود.
      • برای این کار، ابتدا MIR type checker را اجرا می‌کند. این اساساً یک type-checker معمولی است که برای MIR تخصصی شده و البته بسیار ساده‌تر از Rust کامل است. اجرای MIR type checker با این حال قیدهای (constraints) مختلفی بین متغیرهای region ایجاد می‌کند که مقادیر بالقوه‌ی آن‌ها و روابطشان با یکدیگر را نشان می‌دهند.
      • پس از آن، با ساختن یک RegionInferenceContext و فراخوانی متد solve آن، انتشار قیود (constraint propagation) را انجام می‌دهیم.
      • NLL RFC نیز پوشش نسبتاً کاملی (و امیدواریم خوانا) دارد.

    Regionهای جهانی

    نوع UniversalRegions مجموعه‌ای از regionهای جهانی را نمایش می‌دهد که به یک DefId در MIR مربوط‌اند. این نوع در replace_regions_in_mir ساخته می‌شود، یعنی زمانی که تمام regionها را با متغیرهای استنتاج تازه جایگزین می‌کنیم. UniversalRegions شامل اندیس‌های تمام regionهای آزاد در MIR مفروض است، همراه با هر رابطه‌ای که معلوم است بین آن‌ها برقرار است (مثلاً کران‌های ضمنی، where clauseها و غیره).

    برای مثال، MIR تابع زیر را در نظر بگیرید:

    fn foo<'a>(x: &'a u32) {
    // ...
}

    برای 'a یک region جهانی و برای 'static یکی دیگر ایجاد می‌کنیم. ممکن است در مدیریت closureها پیچیدگی‌هایی هم وجود داشته باشد، اما فعلاً آن‌ها را نادیده می‌گیریم.

    متغیرهای region

    مقدار یک region را می‌توان یک مجموعه در نظر گرفت. این مجموعه شامل تمام نقاطی از MIR است که region در آن‌ها معتبر است، همراه با هر regionی که این region از آن بیشتر عمر می‌کند (outlive) (مثلاً اگر 'a: 'b، آنگاه end('b) در مجموعه‌ی 'a قرار دارد)؛ دامنه‌ی این مجموعه را RegionElement می‌نامیم. در کد، مقدار تمام regionها در ماژول rustc_borrowck::region_infer نگهداری می‌شود. برای هر region مجموعه‌ای نگه می‌داریم که ذخیره می‌کند چه عناصری در مقدار آن حضور دارند (برای کارآمد کردن این کار، به هر نوع عنصر یک اندیس به نام RegionElementIndex می‌دهیم و از bitsetهای تُنُک (sparse) استفاده می‌کنیم).

    انواع عناصر region به این شرح‌اند:

    • هر location در گراف جریان کنترل MIR: یک location صرفاً جفتی از یک basic block و یک اندیس است. این مورد نقطه‌ی ورود به دستور با آن اندیس را مشخص می‌کند (یا terminator، اگر اندیس برابر statements.len() باشد).
    • برای هر region جهانی 'a یک عنصر end('a) وجود دارد که با بخشی از گراف جریان کنترل فراخواننده (یا فراخواننده‌ی فراخواننده و غیره) متناظر است.
    • به‌طور مشابه، عنصری با نماد end('static) وجود دارد که با باقی‌مانده‌ی اجرای برنامه پس از بازگشت این تابع متناظر است.
    • برای هر region از نوع placeholder مانند !1 یک عنصر !1 وجود دارد. این (به‌طور شهودی) با مجموعه‌ای ناشناخته از عناصر دیگر متناظر است – برای جزئیات درباره‌ی placeholderها، بخش placeholderها و universeها را ببینید.

    قیدها

    پیش از آنکه بتوانیم مقدار regionها را استنتاج کنیم، باید قیدهایی را روی regionها جمع‌آوری کنیم. مجموعه‌ی کامل قیدها در بخش انتشار قیود شرح داده شده است، اما دو نوع رایج‌تر قیود این‌ها هستند:

    1. قیدهای outlives. این‌ها قیدهایی هستند که می‌گویند یک region از region دیگر بیشتر عمر می‌کند (مثلاً 'a: 'b). قیدهای outlives توسط MIR type checker تولید می‌شوند.
    2. قیدهای liveness. هر region باید در نقاطی که ممکن است استفاده شود زنده (live) باشد.

    نمای کلی استنتاج

    پس چگونه محتوای یک region را محاسبه می‌کنیم؟ این فرایند استنتاج region نامیده می‌شود. ایده‌ی سطح بالا کاملاً ساده است، اما جزئیاتی هست که باید به آن‌ها رسیدگی کنیم.

    ایده‌ی سطح بالا این است: هر region را با مکان‌های MIR که از قیدهای liveness می‌دانیم باید در آن باشند شروع می‌کنیم. از آنجا، تمام قیدهای outlives محاسبه‌شده توسط type checker را برای انتشار قیدها به کار می‌بریم: برای هر region مانند 'a، اگر 'a: 'b باشد، تمام عناصر 'b را، از جمله end('b)، به 'a اضافه می‌کنیم. همه‌ی این‌ها در propagate_constraints رخ می‌دهد.

    سپس به دنبال خطاها می‌گردیم. ابتدا با فراخوانی check_type_tests بررسی می‌کنیم که type testها برآورده شده‌اند. این تابع قیدهایی مانند T: 'a را بررسی می‌کند. دوم، بررسی می‌کنیم که regionهای جهانی «بیش از حد بزرگ» نباشند. این کار با فراخوانی check_universal_regions انجام می‌شود. این تابع بررسی می‌کند که برای هر region مانند 'a، اگر 'a شامل عنصر end('b) باشد، آنگاه باید از قبل بدانیم که 'a: 'b برقرار است (مثلاً از یک where clause). اگر از قبل این را نمی‌دانیم، این یک خطاست… خب، تقریباً. برای closureها مدیریت ویژه‌ای وجود دارد که بعداً درباره‌اش بحث می‌کنیم.

    مثال

    مثال زیر را در نظر بگیرید:

    fn foo<'a, 'b>(x: &'a usize) -> &'b usize {
    x
}

    واضح است که این نباید کامپایل شود، چون نمی‌دانیم 'a از 'b بیشتر عمر می‌کند یا نه (اگر نکند، مقدار بازگشتی می‌تواند یک ارجاع معلق (dangling) باشد).

    کمی به عقب برگردیم. باید چند متغیر استنتاج آزاد معرفی کنیم (همان‌طور که در replace_regions_in_mir انجام می‌شود). این مثال دقیقاً از regionهای تولیدشده استفاده نمی‌کند، اما (امیدواریم) برای رساندن ایده کافی باشد.

    fn foo<'a, 'b>(x: &'a /* '#1 */ usize) -> &'b /* '#3 */ usize {
    x // '#2, location L1
}

    چند نماد: '#1 و '#3 و '#2 به ترتیب نمایانگر regionهای جهانی برای آرگومان، مقدار بازگشتی و عبارت x هستند. علاوه بر این، مکان عبارت x را L1 می‌نامم.

    حالا می‌توانیم از قیدهای liveness برای به‌دست آوردن نقاط شروع زیر استفاده کنیم:

    Regionمحتوا
    ’#1
    ’#2L1
    ’#3L1

    اکنون از قیدهای outlives برای گسترش هر region استفاده می‌کنیم. به‌طور مشخص، می‌دانیم که '#2: '#3 …

    Regionمحتوا
    ’#1L1
    ’#2L1, end('#3) // add contents of '#3 and end('#3)
    ’#3L1

    … و '#1: '#2، پس …

    Regionمحتوا
    ’#1L1, end('#2), end('#3) // add contents of '#2 and end('#2)
    ’#2L1, end('#3)
    ’#3L1

    حالا باید بررسی کنیم که هیچ regionی بیش از حد بزرگ نشده باشد (در این مورد هیچ type testای برای بررسی نداریم). توجه کنید که '#1 اکنون شامل end('#3) است، اما هیچ where clause یا کران ضمنی‌ای نداریم که بگوید 'a: 'b… این یک خطاست!

    چند جزئیات

    نوع RegionInferenceContext تمام اطلاعات لازم برای انجام استنتاج را در بر دارد، از جمله regionهای جهانی از replace_regions_in_mir و قیدهای محاسبه‌شده برای هر region. این نوع درست پس از محاسبه‌ی قیدهای liveness ساخته می‌شود.

    در اینجا برخی از فیلدهای این ساختار آمده است:

    • constraints: شامل تمام قیدهای outlives است.
    • liveness_constraints: شامل تمام قیدهای liveness است.
    • universal_regions: شامل UniversalRegions برگردانده‌شده توسط replace_regions_in_mir است.
    • universal_region_relations: شامل روابطی است که معلوم است درباره‌ی regionهای جهانی درست‌اند. برای مثال، اگر یک where clause داشته باشیم که 'a: 'b، این رابطه هنگام borrow checking پیاده‌سازی درست فرض می‌شود (در فراخواننده بررسی می‌شود)، بنابراین universal_region_relations شامل 'a: 'b خواهد بود.
    • type_tests: شامل برخی قیود روی نوع‌هاست که باید پس از استنتاج بررسی کنیم (مثلاً T: 'a).
    • closure_bounds_mapping: برای انتشار قیدهای region از closureها به سازنده‌ی closure استفاده می‌شود.
