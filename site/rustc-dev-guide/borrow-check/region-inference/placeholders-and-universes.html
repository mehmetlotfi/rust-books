    جانگهدارها و جهان‌ها

    گاهی لازم می‌شود درباره‌ی ناحیه‌هایی استدلال کنیم که نمی‌توانیم به‌طور مشخص بدانیم چه هستند. برای مثال، این برنامه را در نظر بگیرید:

    // A function that needs a static reference
fn foo(x: &'static u32) { }

fn bar(f: for<'a> fn(&'a u32)) {
       // ^^^^^^^^^^^^^^^^^^^ a function that can accept **any** reference
    let x = 22;
    f(&x);
}

fn main() {
    bar(foo);
}

    این برنامه نباید از بررسی نوع بگذرد: foo برای آرگومانش به یک ارجاع static نیاز دارد و bar می‌خواهد تابعی به او داده شود که هر ارجاعی را بپذیرد (تا مثلاً بتواند آن را با چیزی از پشته‌ی خودش فراخوانی کند). اما چگونه و چرا آن را رد می‌کنیم؟

    زیرنوع‌سازی و جانگهدارها

    وقتی main و به‌ویژه فراخوانی bar(foo) را بررسی نوع می‌کنیم، به یک رابطه‌ی زیرنوع‌سازی مانند این می‌رسیم:

    fn(&'static u32) <: for<'a> fn(&'a u32)
----------------    -------------------
the type of `foo`   the type `bar` expects

    این نوع زیرنوع‌سازی را چنین مدیریت می‌کنیم که متغیرهایی را که در ابرنوع مقید (bound) هستند برمی‌داریم و با نمایندگان سورشده‌ی عمومی جایگزین می‌کنیم که اینجا به شکل !1 نشان داده می‌شوند. این ناحیه‌ها را «ناحیه‌های جانگهدار» (placeholder) می‌نامیم – آن‌ها در اصل نماینده‌ی «یک ناحیه‌ی نامعلوم» هستند.

    پس از این جایگزینی، رابطه‌ی زیر را داریم:

    fn(&'static u32) <: fn(&'!1 u32)

    ایده‌ی کلیدی اینجا این است که این ناحیه‌ی نامعلوم '!1 با هیچ ناحیه‌ی دیگری ارتباط ندارد. بنابراین اگر بتوانیم ثابت کنیم رابطه‌ی زیرنوع‌سازی برای '!1 برقرار است، باید برای هر ناحیه‌ای برقرار باشد، و این دقیقاً همان چیزی است که می‌خواستیم.

    پس بیایید ببینیم در ادامه چه اتفاقی می‌افتد. برای بررسی اینکه دو تابع زیرنوع یکدیگرند، بررسی می‌کنیم که آرگومان‌هایشان رابطه‌ی مطلوب را داشته باشند (آرگومان‌های fn پادوردا هستند، پس اینجا چپ و راست را جابه‌جا می‌کنیم):

    &'!1 u32 <: &'static u32

    طبق قواعد پایه‌ی زیرنوع‌سازی برای ارجاع، این رابطه در صورتی برقرار است که '!1: 'static. یعنی اگر «ناحیه‌ی نامعلوم !1» از 'static بیشتر عمر کند. حالا، این ممکن است درست باشد – بالاخره '!1 می‌تواند همان 'static باشد – اما ما نمی‌دانیم که درست است. بنابراین این باید (در نهایت) به یک خطا بینجامد.

    جهان (universe) چیست؟

    در بخش قبل، ایده‌ی ناحیه‌ی جانگهدار را معرفی کردیم و آن را !1 نامیدیم. این عدد 1 را شاخص جهان (universe index) می‌نامیم. ایده‌ی «جهان» این است که مجموعه‌ای از نام‌هاست که درون یک نوع یا در یک نقطه در دامنه‌اند. جهان‌ها به شکل یک درخت سازمان می‌یابند که در آن هر فرزند نام‌های والدش را با چند نام جدید گسترش می‌دهد. بنابراین جهان ریشه از نظر مفهومی شامل نام‌های سراسری است، مانند طول عمر 'static یا نوع i32. در کامپایلر، پارامترهای نوع جنریک را هم در این جهان ریشه قرار می‌دهیم (از این نظر، فقط یک جهان ریشه وجود ندارد، بلکه به‌ازای هر آیتم یکی وجود دارد). پس این تابع bar را در نظر بگیرید:

    struct Foo { }

fn bar<'a, T>(t: &'a T) {
    ...
}

    در اینجا جهان ریشه شامل طول عمرهای 'static و 'a خواهد بود. در واقع، هرچند اینجا روی طول عمرها تمرکز کرده‌ایم، می‌توانیم همین مفهوم را به نوع‌ها هم اعمال کنیم؛ در آن صورت نوع‌های Foo و T (به‌همراه سایر نوع‌های سراسری مانند i32) در جهان ریشه خواهند بود. در اصل، جهان ریشه شامل همه‌ی نام‌هایی است که آزادانه ظاهر می‌شوند در بدنه‌ی bar.

    حالا بیایید bar را با افزودن یک متغیر x کمی گسترش دهیم:

    fn bar<'a, T>(t: &'a T) {
    let x: for<'b> fn(&'b u32) = ...;
}

    در اینجا نام 'b بخشی از جهان ریشه نیست. در عوض، وقتی وارد این for<'b> می‌شویم (مثلاً با جایگزین کردن آن با یک جانگهدار)، یک جهان فرزند از ریشه می‌سازیم که آن را U1 می‌نامیم:

    U0 (root universe)
│
└─ U1 (child universe)

    ایده این است که این جهان فرزند U1، جهان ریشه U0 را با یک نام جدید گسترش می‌دهد که آن را با شماره‌ی جهانش مشخص می‌کنیم: !1.

    حالا بیایید bar را با افزودن یک متغیر دیگر، y، کمی بیشتر گسترش دهیم:

    fn bar<'a, T>(t: &'a T) {
    let x: for<'b> fn(&'b u32) = ...;
    let y: for<'c> fn(&'c u32) = ...;
}

    وقتی وارد این نوع می‌شویم، دوباره یک جهان جدید می‌سازیم که آن را U2 می‌نامیم. والد آن جهان ریشه است و U1 همزاد (sibling) آن خواهد بود:

    U0 (root universe)
│
├─ U1 (child universe)
│
└─ U2 (child universe)

    این یعنی در U2 می‌توانیم چیزهایی را از U0 یا U2 نام ببریم، اما از U1 نه.

    دادن جهان به متغیرهای وجودی. حالا که این مفهوم جهان‌ها را داریم، می‌توانیم از آن برای گسترش بررسی‌گر نوع و سایر بخش‌ها استفاده کنیم تا از نشت نام‌های غیرمجاز جلوگیری شود. ایده این است که به هر متغیر استنتاج (وجودی) – چه نوع باشد و چه طول عمر – یک جهان بدهیم. آن‌گاه مقدار آن متغیر فقط می‌تواند به نام‌هایی ارجاع دهد که از آن جهان قابل مشاهده‌اند. برای مثال، اگر یک متغیر طول عمر در U0 ساخته شود، نمی‌توان مقدار !1 یا !2 را به آن داد، چون این نام‌ها از جهان U0 قابل مشاهده نیستند.

    نمایش جهان‌ها فقط با یک شمارنده. ممکن است تعجب کنید که کامپایلر یک درخت کامل از جهان‌ها را نگه نمی‌دارد. در عوض، فقط یک شمارنده نگه می‌دارد – و برای تشخیص اینکه آیا یک جهان می‌تواند جهان دیگری را ببیند، فقط بررسی می‌کند که آیا شاخص بزرگ‌تر است یا نه. برای مثال، U2 می‌تواند U0 را ببیند چون 2 >= 0. اما U0 نمی‌تواند U2 را ببیند، چون 0 >= 2 نادرست است.

    چطور می‌توانیم از این ساده‌سازی بگذریم؟ آیا این یعنی به U2 اجازه می‌دهیم U1 را هم ببیند؟ پاسخ این است که بله، اجازه می‌دهیم، اگر چنین پرسشی هرگز مطرح شود. اما به‌دلیل ساختار بررسی‌گر نوع و بقیه‌ی بخش‌ها، راهی برای رخ دادن آن وجود ندارد. برای اینکه چیزی که در جهان U1 رخ می‌دهد با چیزی که در U2 رخ می‌دهد «ارتباط» برقرار کند، باید یک متغیر استنتاج مشترک X داشته باشند. و چون همه‌چیز در U1 فقط به U1 و فرزندانش محدود است، آن متغیر استنتاج X باید در U0 باشد. و چون X در U0 است، نمی‌تواند چیزی از U1 (یا U2) را نام ببرد. شاید بهتر باشد این را با نوعی مثال «منطقی» عمومی ببینیم:

    exists<X> {
   forall<Y> { ... /* Y is in U1 ... */ }
   forall<Z> { ... /* Z is in U2 ... */ }
}

    در اینجا تنها راه تعامل دو forall از طریق X است، اما وقتی X اعلام می‌شود نه Y در دامنه است و نه Z، پس مقدارش نمی‌تواند به هیچ‌کدام از آن‌ها ارجاع دهد.

    جهان‌ها و عناصر ناحیه‌ی جانگهدار

    اما آن خطا از کجا می‌آید؟ ماجرا به این شکل است. وقتی زمینه‌ی استنتاج ناحیه را می‌سازیم، از روی زمینه‌ی استنتاج نوع می‌توانیم بفهمیم چند متغیر جانگهدار وجود دارد (InferCtxt یک شمارنده‌ی داخلی دارد). برای هر یک از آن‌ها، یک متغیر ناحیه‌ی عمومی (universal) متناظر !n و یک «عنصر ناحیه» به نام placeholder(n) می‌سازیم. این متناظر است با «یک مجموعه‌ی نامعلوم از عناصر دیگر». مقدار !n برابر {placeholder(n)} است.

    هم‌زمان، به هر متغیر وجودی هم یک جهان می‌دهیم (که آن هم از InferCtxt گرفته می‌شود). این جهان تعیین می‌کند کدام عناصر جانگهدار می‌توانند در مقدار آن ظاهر شوند: برای مثال، متغیری در جهان U3 می‌تواند placeholder(1)، placeholder(2) و placeholder(3) را نام ببرد، اما placeholder(4) را نه. توجه کنید که جهان یک متغیر استنتاج مشخص می‌کند چه عناصر ناحیه‌ای می‌توانند در مقدارش ظاهر شوند؛ نمی‌گوید چه عناصری حتماً ظاهر خواهند شد.

    جانگهدارها و محدودیت‌های outlives

    در موتور استنتاج ناحیه، محدودیت‌های outlives شکل زیر را دارند:

    V1: V2 @ P

    که در آن V1 و V2 شاخص‌های ناحیه‌اند و بنابراین به یک متغیر ناحیه نگاشت می‌شوند (که ممکن است سور عمومی یا وجودی داشته باشد). P در اینجا یک «نقطه» در گراف جریان کنترل است؛ برای این بخش مهم نیست. این متغیر یک جهان خواهد داشت، پس بیایید این جهان‌ها را به‌ترتیب U(V1) و U(V2) بنامیم. (در واقع، تنها چیزی که به آن اهمیت می‌دهیم U(V1) است.)

    وقتی به این محدودیت برمی‌خوریم، روال معمول این است که یک DFS از P آغاز کنیم. تا زمانی که گره‌هایی که از آن‌ها می‌گذریم در value(V2) حاضر باشند به حرکت ادامه می‌دهیم و آن گره‌ها را به value(V1) اضافه می‌کنیم. اگر به یک نقطه‌ی بازگشت برسیم، هر عنصر end(X) را اضافه می‌کنیم. این بخش بدون تغییر می‌ماند.

    اما پس از آن می‌خواهیم روی عناصر جانگهدار placeholder(x) در V2 پیمایش کنیم (هر یک از آن‌ها باید برای U(V2) قابل مشاهده باشد، اما می‌توانیم صرفاً فرض کنیم که چنین است و لازم نیست بررسی‌اش کنیم). باید اطمینان یابیم که value(V1) از هر یک از آن عناصر جانگهدار بیشتر عمر می‌کند.

    دو راه برای این کار وجود دارد. اول، اگر U(V1) بتواند جهان x را ببیند (یعنی x <= U(V1))، می‌توانیم placeholder(x) را به value(V1) اضافه کنیم و کار تمام است. اما اگر نتواند، باید تقریب بزنیم: شاید ندانیم placeholder(x) نماینده‌ی چه مجموعه‌ای از عناصر است، اما باید بتوانیم نوعی کران بالا B برایش محاسبه کنیم – ناحیه‌ای B که از placeholder(x) بیشتر عمر می‌کند. فعلاً برای این کار فقط از 'static استفاده می‌کنیم (چون از همه چیز بیشتر عمر می‌کند) – در آینده گاهی می‌توانیم اینجا هوشمندتر عمل کنیم (و در واقع کدی برای انجام این کار در زمینه‌های دیگر داریم). علاوه بر این، چون 'static در جهان ریشه U0 است، می‌دانیم همه‌ی متغیرها آن را می‌بینند – پس در اصل اگر دریابیم value(V2) شامل placeholder(x) برای جهانی مانند x است که V1 نمی‌تواند ببیند، آن‌گاه V1 را مجبور به 'static شدن می‌کنیم.

    گسترش بررسی «ناحیه‌های عمومی»

    پس از انتشار همه‌ی محدودیت‌ها، استنتاج ناحیه‌ی NLL یک بررسی نهایی دارد که در آن مقادیری را که برای هر ناحیه‌ی عمومی محاسبه شده‌اند مرور می‌کند و بررسی می‌کند که بیش از حد «بزرگ» نشده باشند. در مورد ما، از میان هر ناحیه‌ی جانگهدار می‌گذریم و بررسی می‌کنیم که فقط شامل عنصر placeholder(u) باشد که می‌دانیم از آن بیشتر عمر می‌کند. (بعداً شاید بتوانیم بدانیم که میان دو ناحیه‌ی جانگهدار روابطی وجود دارد و آن‌ها را هم در نظر بگیریم، همان‌طور که برای ناحیه‌های عمومی حاصل از امضای fn انجام می‌دهیم.)

    به بیان دیگر، می‌توان گفت بررسی «ناحیه‌های عمومی» محدودیت‌هایی از این دست را وارسی می‌کند:

    {placeholder(1)}: V1

    که در آن {placeholder(1)} مانند یک مجموعه‌ی ثابت است و V1 متغیری است که برای نمایش ناحیه‌ی !1 ساخته‌ایم.

    بازگشت به مثال خودمان

    خب، تا اینجا خوب بود. حالا بیایید ببینیم در مثال اول ما چه اتفاقی می‌افتد:

    fn(&'static u32) <: fn(&'!1 u32) @ P  // this point P is not imp't here

    موتور استنتاج ناحیه یک دامنه‌ی عناصر ناحیه مانند این می‌سازد:

    { CFG; end('static); placeholder(1) }
  ---  ------------  ------- from the universe `!1`
  |    'static is always in scope
  all points in the CFG; not especially relevant here

    این موتور همیشه دو متغیر عمومی می‌سازد، یکی نماینده‌ی 'static و دیگری نماینده‌ی '!1. بیایید آن‌ها را Vs و V1 بنامیم. آن‌ها مقادیر اولیه‌ای مانند این خواهند داشت:

    Vs = { CFG; end('static) } // it is in U0, so can't name anything else
V1 = { placeholder(1) }

    از محدودیت زیرنوع‌سازی بالا، یک محدودیت outlives مانند زیر خواهیم داشت

    '!1: 'static @ P

    برای پردازش این، مقدار V1 را بزرگ می‌کنیم تا همه‌ی Vs را در بر بگیرد:

    Vs = { CFG; end('static) }
V1 = { CFG; end('static), placeholder(1) }

    در این نقطه، انتشار محدودیت‌ها کامل است، چون همه‌ی روابط outlives برقرارند. سپس به بخش «بررسی ناحیه‌های عمومی» از کد می‌رسیم که آزمون می‌کند هیچ ناحیه‌ی عمومی بیش از حد بزرگ نشده باشد.

    در این مورد، V1 بیش از حد بزرگ شده است – معلوم نیست از end('static) یا هیچ‌یک از CFG بیشتر عمر کند – پس خطا گزارش می‌دهیم.

    مثالی دیگر

    درباره‌ی این رابطه‌ی زیرنوع‌سازی چه می‌گویید؟

    for<'a> fn(&'a u32, &'a u32)
    <:
for<'b, 'c> fn(&'b u32, &'c u32)

    اینجا ناحیه‌ی مقید در ابرنوع را مانند قبل با یک جانگهدار جایگزین می‌کنیم و نتیجه می‌شود:

    for<'a> fn(&'a u32, &'a u32)
    <:
fn(&'!1 u32, &'!2 u32)

    سپس متغیر سمت چپ را با یک متغیر وجودی در جهان U2 نمونه‌سازی می‌کنیم و نتیجه‌ی زیر به دست می‌آید (?n نمادی برای یک متغیر وجودی است):

    fn(&'?3 u32, &'?3 u32)
    <:
fn(&'!1 u32, &'!2 u32)

    سپس این را بیشتر تجزیه می‌کنیم:

    &'!1 u32 <: &'?3 u32
&'!2 u32 <: &'?3 u32

    و حتی بیشتر، که محدودیت‌های ناحیه‌ی ما را به دست می‌دهد:

    '!1: '?3
'!2: '?3

    توجه کنید که در این مورد، هر دوی '!1 و '!2 باید از متغیر '?3 بیشتر عمر کنند، اما '?3 مجبور نیست از چیز دیگری بیشتر عمر کند. بنابراین، به‌سادگی با مجموعه‌ی تهی از عناصر شروع می‌شود و با همان پایان می‌یابد و در نتیجه بررسی نوع اینجا موفق می‌شود.

    (این باید کمی شما را غافلگیر کند. وقتی برای اولین بار متوجه‌اش شدم من را غافلگیر کرد. ما می‌گوییم اگر تابعی باشیم که هر دو آرگومانش باید ناحیه‌ی یکسانی داشته باشند، می‌توانیم بپذیریم که با آرگومان‌هایی با دو ناحیه‌ی متمایز فراخوانی شویم. این به‌طور شهودی ناایمن به نظر می‌رسد. اما در واقع مشکلی ندارد، همان‌طور که مدتی پیش سعی کردم در این issue در ردیاب issueهای Rust توضیح دهم. دلیلش این است که حتی اگر با آرگومان‌هایی از دو طول عمر متمایز فراخوانی شویم، آن دو طول عمر اشتراکی دارند (خود فراخوانی)، و آن اشتراک می‌تواند مقدار 'a ما باشد که به‌عنوان طول عمر مشترک آرگومان‌هایمان از آن استفاده می‌کنیم. -nmatsakis)

    مثال پایانی

    بیایید به یک مثال آخر نگاه کنیم. مثال قبلی را گسترش می‌دهیم تا یک نوع بازگشتی داشته باشد:

    for<'a> fn(&'a u32, &'a u32) -> &'a u32
    <:
for<'b, 'c> fn(&'b u32, &'c u32) -> &'b u32

    با اینکه این مثال بسیار شبیه مثال قبلی به نظر می‌رسد، به یک خطا می‌انجامد. این خوب است: مشکل این است که از تابعی که وعده می‌دهد یکی از دو آرگومانش را برگرداند، به تابعی رسیده‌ایم که وعده می‌دهد اولی را برگرداند. این ناایمن است. ببینیم چگونه پیش می‌رود.

    اول، ناحیه‌ی مقید در ابرنوع را با یک جانگهدار جایگزین می‌کنیم:

    for<'a> fn(&'a u32, &'a u32) -> &'a u32
    <:
fn(&'!1 u32, &'!2 u32) -> &'!1 u32

    سپس زیرنوع را با متغیرهای وجودی (در U2) نمونه‌سازی می‌کنیم:

    fn(&'?3 u32, &'?3 u32) -> &'?3 u32
    <:
fn(&'!1 u32, &'!2 u32) -> &'!1 u32

    و حالا روابط زیرنوع‌سازی را می‌سازیم:

    &'!1 u32 <: &'?3 u32 // arg 1
&'!2 u32 <: &'?3 u32 // arg 2
&'?3 u32 <: &'!1 u32 // return type

    و سرانجام روابط outlives. در اینجا فرض کنید V1، V2 و V3 متغیرهایی هستند که به‌ترتیب به !1، !2 و ?3 اختصاص می‌دهیم:

    V1: V3
V2: V3
V3: V1

    این متغیرها مقادیر اولیه‌ی زیر را خواهند داشت:

    V1 in U1 = {placeholder(1)}
V2 in U2 = {placeholder(2)}
V3 in U2 = {}

    حالا به‌دلیل محدودیت V3: V1، باید placeholder(1) را به V3 اضافه کنیم (و در واقع از V3 قابل مشاهده است)، پس به این می‌رسیم:

    V3 in U2 = {placeholder(1)}

    سپس این محدودیت V2: V3 را داریم، پس مجبور می‌شویم V2 را بزرگ کنیم تا placeholder(1) را هم شامل شود (که آن را هم می‌تواند ببیند):

    V2 in U2 = {placeholder(1), placeholder(2)}

    اکنون انتشار محدودیت‌ها تمام شده است، اما وقتی روابط outlives را بررسی می‌کنیم، می‌بینیم V2 این عنصر جدید placeholder(1) را شامل می‌شود، پس خطا گزارش می‌کنیم.
