    محدودیت‌های استنتاج region برای opaque typeها

    در این فصل محدودیت‌های مختلفی را بررسی می‌کنیم که هنگام تعریف hidden typeهای opaque typeها، بر آرگومان‌های جنریک آن‌ها اعمال می‌کنیم: Opaque<'a, 'b, .., A, B, ..> := SomeHiddenType.

    این محدودیت‌ها در borrow checking پیاده‌سازی شده‌اند (منبع)، زیرا borrow checking آخرین گام استنتاج opaque typeهاست.

    پیش‌زمینه: آرگومان‌های جنریک نوع و ثابت

    برای آرگومان‌های نوع، دو محدودیت لازم است: هر آرگومان نوع باید (۱) یک پارامتر نوع باشد و (۲) در میان آرگومان‌های جنریک یکتا باشد. همین موارد برای آرگومان‌های const نیز اعمال می‌شود.

    مثالی از حالت (۱):

    type Opaque<X> = impl Sized;

// `T` is a type parameter.
// Opaque<T> := ();
fn good<T>() -> Opaque<T> {}

// `()` is not a type parameter.
// Opaque<()> := ();
fn bad() -> Opaque<()> {} //~ ERROR

    مثالی از حالت (۲):

    type Opaque<X, Y> = impl Sized;

// `T` and `U` are unique in the generic args.
// Opaque<T, U> := T;
fn good<T, U>(t: T, _u: U) -> Opaque<T, U> { t }

// `T` appears twice in the generic args.
// Opaque<T, T> := T;
fn bad<T>(t: T) -> Opaque<T, T> { t } //~ ERROR

    انگیزه: در حالت اول یعنی Opaque<()> := ()، hidden type مبهم است، زیرا با دو تفسیر مختلف سازگار است: Opaque<X> := X و Opaque<X> := (). به همین ترتیب در حالت دوم یعنی Opaque<T, T> := T، مبهم است که باید به‌صورت Opaque<X, Y> := X تفسیر شود یا Opaque<X, Y> := Y. به دلیل این ابهام، هر دو حالت به‌عنوان استفاده‌ی تعریف‌کننده‌ی (defining use) نامعتبر رد می‌شوند.

    محدودیت یکتایی

    هر آرگومان طول عمر باید در فهرست آرگومان‌ها یکتا باشد و نباید 'static باشد. این برای جلوگیری از ابهام در استنتاج hidden type است، مشابه حالت پارامترهای نوع. برای مثال، defining use نامعتبر زیر یعنی Opaque<'static> := Inv<'static> با هر دو Opaque<'x> := Inv<'static> و Opaque<'x> := Inv<'x> سازگار است.

    type Opaque<'x> = impl Sized + 'x;
type Inv<'a> = Option<*mut &'a ()>;

fn good<'a>() -> Opaque<'a> { Inv::<'static>::None }

fn bad() -> Opaque<'static> { Inv::<'static>::None }
//~^ ERROR
    type Opaque<'x, 'y> = impl Trait<'x, 'y>;

fn good<'a, 'b>() -> Opaque<'a, 'b> {}

fn bad<'a>() -> Opaque<'a, 'a> {}
//~^ ERROR

    برابری معنایی طول عمرها: یکی از پیچیدگی‌های طول عمرها در مقایسه با پارامترهای نوع این است که دو طول عمر که از نظر نحوی متفاوت‌اند ممکن است از نظر معنایی برابر باشند. بنابراین هنگام بررسی یکتا بودن طول عمرها باید محتاط باشیم.

    // This is also invalid because `'a` is *semantically* equal to `'static`.
fn still_bad_1<'a: 'static>() -> Opaque<'a> {}
//~^ Should error!

// This is also invalid because `'a` and `'b` are *semantically* equal.
fn still_bad_2<'a: 'b, 'b: 'a>() -> Opaque<'a, 'b> {}
//~^ Should error!

    یک استثنا برای قاعده‌ی یکتایی

    استثنایی برای قاعده‌ی یکتایی بالا زمانی است که کران‌های (bounds) موجود در تعریف opaque type ایجاب کنند یک پارامتر طول عمر برابر با پارامتر دیگری یا برابر با طول عمر 'static باشد.

    // The definition requires `'x` to be equal to `'static`.
type Opaque<'x: 'static> = impl Sized + 'x;

fn good() -> Opaque<'static> {}

    انگیزه: تلاش برای پیاده‌سازی محدودیت یکتایی برای RPITها منجر به شکستی شد که crater پیدا کرد. این مشکل را می‌توان با همین استثنا برای قاعده کاهش داد. مثالی از کدی که در غیر این صورت می‌شکست:

    struct Type<'a>(&'a ());
impl<'a> Type<'a> {
    // `'b == 'a`
    fn do_stuff<'b: 'a>(&'b self) -> impl Trait<'a, 'b> {}
}

    چرا این درست است: برای چنین defining useای مانند Opaque<'a, 'a> := &'a str، می‌توان آن را به هر دو شیوه تفسیر کرد – یا به‌صورت Opaque<'x, 'y> := &'x str یا به‌صورت Opaque<'x, 'y> := &'y str – و فرقی نمی‌کند، زیرا هر استفاده از Opaque طبق قواعد well-formedness تضمین می‌کند که هر دو پارامتر برابرند.

    محدودیت طول عمرهای جهانی

    فقط طول عمرهای کمیت‌پذیرشده‌ی جهانی (universally quantified) در آرگومان‌های opaque type مجازند. این شامل پارامترهای طول عمر و placeholderها می‌شود.

    type Opaque<'x> = impl Sized + 'x;

fn test<'a>() -> Opaque<'a> {
    // `Opaque<'empty> := ()`
    let _: Opaque<'_> = ();
    //~^ ERROR
}

    انگیزه: این باعث می‌شود آرگومان‌های طول عمر و نوع رفتاری سازگار داشته باشند، اما این فقط یک امتیاز جانبی است. دلیل واقعی این محدودیت صرفاً فنی است، چون الگوریتم member constraints با یک محدودیت بنیادین روبه‌رو است: هنگام مواجهه با تعریف opaque type به شکل Opaque<'?1> := &'?2 u8، یک member constraint به شکل '?2 member-of ['static, '?1] ثبت می‌شود. برای اینکه الگوریتم بتواند انتخاب درست را برگزیند، مجموعه‌ی کامل روابط «outlives» بین regionهای انتخاب ['static, '?1] باید پیش از انجام استنتاج region از قبل معلوم باشد. این فقط زمانی برآورده می‌شود که هر region انتخاب یکی از این دو باشد:

    1. یک region جهانی (universal)، یعنی RegionKind::Re{EarlyParam,LateParam,Placeholder,Static}، چون روابط بین regionهای جهانی پیش از استنتاج region، از کران‌های صریح و ضمنی کاملاً معلوم است.
    2. یا یک region وجودی (existential) که «به‌طور اکید برابر» با یک region جهانی است. برابری اکید طول عمر در ادامه تعریف شده است و در اینجا لازم است، چون تنها نوع برابری‌ای است که پیش از استنتاج کامل region قابل ارزیابی است.

    برابری اکید طول عمر: می‌گوییم دو طول عمر به‌طور اکید برابرند اگر بین آن‌ها قیدهای outlives دوطرفه وجود داشته باشد. در اصطلاح NLL، این یعنی طول عمرها بخشی از یک SCC یکسان‌اند. نکته‌ی مهم اینکه این نوع برابری را می‌توان پیش از استنتاج کامل region ارزیابی کرد (البته پس از جمع‌آوری قیدها). نوع دیگر برابری زمانی است که استنتاج region در نهایت به دو متغیر طول عمر یک مقدار یکسان بدهد، حتی اگر به‌طور اکید برابر نباشند. برای اینکه ببینید قبلاً چگونه این تفاوت را با هم خلط می‌کردیم، #113971 را ببینید.

    تعامل با محدودیت «یک‌بار به‌جز region‌ها» (once modulo regions) در مثال بالا توجه کنید که opaque type در signature برابر Opaque<'a> است و opaque type در defining use نامعتبر برابر Opaque<'empty> است. در طرح پیشنهادی MiniTAIT، یعنی قاعده‌ی “once modulo regions”، این حالت از قبل ممنوع است. اگرچه ممکن است به نظر برسد محدودیت «طول عمرهای جهانی» زائد می‌شود، چون به‌طور منطقی از محدودیت‌های «MiniTAIT» نتیجه می‌شود، بحث بعدیِ مرتبط درباره‌ی برابری طول عمر و closureها همچنان مرتبط باقی می‌ماند.

    محدودیت‌های closure

    وقتی opaque type در بدنه‌ی یک closure، coroutine یا inline-const تعریف می‌شود، طول عمرهای جهانی که نسبت به closure «خارجی» هستند در آرگومان‌های opaque type مجاز نیستند. regionهای خارجی در RegionClassification::External تعریف شده‌اند.

    مثال: (این یکی اتفاقاً در nightly فعلی کامپایل می‌شود، اما مثال‌های عملی‌تر از قبل با خطاهای گیج‌کننده رد می‌شوند.)

    type Opaque<'x> = impl Sized + 'x;

fn test<'a>() -> Opaque<'a> {
    let _ = || {
        // `'a` is external to the closure
        let _: Opaque<'a> = ();
        //~^ Should be an error!
    };
    ()
}

    انگیزه: در بدنه‌ی closureها، طول عمرهای خارجی، هرچند در دسته‌ی طول عمرهای «جهانی» قرار می‌گیرند، بیشتر مانند طول عمرهای وجودی رفتار می‌کنند، به این معنا که روابط بین آن‌ها از پیش معلوم نیست؛ در عوض مقادیرشان درست مثل طول عمرهای وجودی استنتاج می‌شود و الزامات به تابع والد بازگردانده می‌شود. این الگوریتم member constraints را، همان‌طور که در بالا توضیح داده شد، می‌شکند:

    برای اینکه الگوریتم بتواند انتخاب درست را برگزیند، مجموعه‌ی کامل روابط «outlives» بین regionهای انتخاب ['static, '?1] باید پیش از انجام استنتاج region از قبل معلوم باشد

    در اینجا مثالی هست که جزئیات چگونگی این را نشان می‌دهد:

    type Opaque<'x, 'y> = impl Sized;

//
fn test<'a, 'b>(s: &'a str) -> impl FnOnce() -> Opaque<'a, 'b> {
    move || { s }
    //~^ ERROR hidden type for `Opaque<'_, '_>` captures lifetime that does not appear in bounds
}

// The above closure body is desugared into something like:
fn test::{closure#0}(_upvar: &'?8 str) -> Opaque<'?6, '?7> {
    return _upvar
}

// where `['?8, '?6, ?7]` are universal lifetimes *external* to the closure.
// There are no known relations between them *inside* the closure.
// But in the parent fn it is known that `'?6: '?8`.
//
// When encountering an opaque definition `Opaque<'?6, '?7> := &'8 str`,
// The member constraints algorithm does not know enough to safely make `?8 = '?6`.
// For this reason, it errors with a sensible message:
// "hidden type captures lifetime that does not appear in bounds".

    بدون این محدودیت‌ها، پیام‌های خطا گیج‌کننده‌اند و مهم‌تر اینکه این خطر وجود دارد که کدی را بپذیریم که احتمالاً در آینده خواهد شکست، چون member constraints در closureها به‌شدت معیوب‌اند.

    نوع‌های خروجی: به باور من رایج‌ترین سناریویی که در کدهای دنیای واقعی باعث این مشکلات می‌شود، نوع‌های خروجی closureها و بلوک‌های async است. شایان ذکر است که بین closureها و بلوک‌های async تفاوتی وجود دارد که این مشکل را بیشتر نشان می‌دهد و ناشی از hack مربوط به replace_opaque_types_with_inference_vars است که فقط برای futureها اعمال می‌شود.

    type Opaque<'x> = impl Sized + 'x;
fn test<'a>() -> impl FnOnce() -> Opaque<'a> {
    // Output type of the closure is Opaque<'a>
    // -> hidden type definition happens *inside* the closure
    // -> rejected.
    move || {}
    //~^ ERROR expected generic lifetime parameter, found `'_`
}
    use std::future::Future;
type Opaque<'x> = impl Sized + 'x;
fn test<'a>() -> impl Future<Output = Opaque<'a>> {
    // Output type of the async block is unit `()`
    // -> hidden type definition happens in the parent fn
    // -> accepted.
    async move {}
}
