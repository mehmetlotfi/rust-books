راهنمای توسعهٔ rustcrustc Development Guide

    تولید کد مستقل از بک‌اند

    rustc_codegen_ssa یک رابط انتزاعی برای پیاده‌سازی توسط همهٔ بک‌اندها فراهم می‌کند، یعنی LLVM، Cranelift و GCC.

    در ادامه اطلاعات پیش‌زمینه‌ای دربارهٔ بازسازی‌ای آمده است که این رابط انتزاعی را پدید آورد.

    بازسازی rustc_codegen_llvm

    نوشتهٔ Denis Merigoux، ۲۳ اکتبر ۲۰۱۸

    وضعیت کد پیش از بازسازی

    تمام کدِ مربوط به کامپایل MIR به LLVM IR درون crate مربوط به rustc_codegen_llvm قرار داشت. تفکیک مهم‌ترین عناصر آن به این صورت است:

    • پوشهٔ back (۷٬۸۰۰ خط کد یا LOC) سازوکارهای ساخت فایل‌های شیء و آرشیوهای گوناگون را از طریق LLVM پیاده‌سازی می‌کند، و همچنین سازوکارهای ارتباطی برای تولید کد موازی را؛
    • پوشهٔ debuginfo (۳٬۲۰۰ LOC) شامل تمام کدی است که اطلاعات اشکال‌زدایی را به LLVM منتقل می‌کند؛
    • پوشهٔ llvm (۲٬۲۰۰ LOC) رابط FFI لازم برای ارتباط با LLVM از طریق API زبان C++ را تعریف می‌کند؛
    • پوشهٔ mir (۴٬۳۰۰ LOC) پایین‌آوردن واقعی MIR به LLVM IR را پیاده‌سازی می‌کند؛
    • فایل base.rs (۱٬۳۰۰ LOC) شامل برخی توابع کمکی و همچنین کد سطح بالایی است که تولید کد را آغاز می‌کند و کار را توزیع می‌کند.
    • فایل builder.rs (۱٬۲۰۰ LOC) شامل همهٔ توابعی است که دستورهای منفرد LLVM IR را درون یک بلوک پایه تولید می‌کنند؛
    • فایل common.rs (۴۵۰ LOC) شامل توابع کمکی گوناگون و همهٔ توابعی است که مقادیر ایستای LLVM را تولید می‌کنند؛
    • فایل type_.rs (۳۰۰ LOC) بیشتر ترجمه‌های نوع به LLVM IR را تعریف می‌کند.

    هدف از این بازسازی آن است که در درون این crate، کدی که مختص LLVM است از کدی که می‌تواند برای دیگر بک‌اندهای rustc دوباره استفاده شود جدا شود. برای مثال، پوشهٔ mir تقریباً به‌طور کامل مختص بک‌اند است، اما به‌شدت به بخش‌های دیگر crate وابسته است. این جداسازی نباید منطق کد را تغییر دهد و نباید بر کارایی آن اثر بگذارد.

    به همین دلایل، فرایند جداسازی شامل دو دگرگونی است که باید همزمان انجام شوند تا کد حاصل کامپایل شود:

    1. همهٔ نوع‌های مختص LLVM در امضای توابع و تعریف ساختارها با جنریک‌ها جایگزین شوند
    2. همهٔ توابعی که FFI مربوط به LLVM را فراخوانی می‌کنند در مجموعه‌ای از صفت‌ها (trait) محصور شوند که رابط میان کد مستقل از بک‌اند و بک‌اند را تعریف می‌کنند

    در حالی که کد مختص LLVM در rustc_codegen_llvm باقی می‌ماند، همهٔ صفت‌های جدید و کد مستقل از بک‌اند به rustc_codegen_ssa منتقل خواهند شد (پیشنهاد این نام از @eddyb بود).

    نوع‌ها و ساختارهای جنریک

    @irinagpopa شروع به پارامتری‌کردن نوع‌های rustc_codegen_llvm با یک نوع جنریک Value کرد که در LLVM با یک ارجاع &'ll Value پیاده‌سازی می‌شود. این کار به همهٔ ساختارهای درون پوشهٔ mir و جاهای دیگر گسترش یافته است، و همچنین به نوع‌های BasicBlock و Type در LLVM.

    دو ساختار مهم‌تر برای تولید کد LLVM، CodegenCx و Builder هستند. این‌ها با چندین پارامتر طول عمر و نوع Value پارامتری شده‌اند.

    struct CodegenCx<'ll, 'tcx> {
  /* ... */
}

struct Builder<'a, 'll, 'tcx> {
  cx: &'a CodegenCx<'ll, 'tcx>,
  /* ... */
}

    CodegenCx برای کامپایل یک codegen-unit به کار می‌رود که می‌تواند شامل چندین تابع باشد، در حالی که Builder برای کامپایل یک بلوک پایه ساخته می‌شود.

    کد موجود در rustc_codegen_llvm باید با چندین پارامتر طول عمر صریح سروکار داشته باشد که با موارد زیر متناظرند:

    • 'tcx بلندترین طول عمر است و با TyCtxt اصلی متناظر است که اطلاعات برنامه را در بر دارد؛
    • 'a یک ارجاع کوتاه‌عمر به یک CodegenCx یا شیء دیگری درون یک ساختار است؛
    • 'll طول عمر ارجاع‌ها به اشیای LLVM مانند Value یا Type است.

    هرچند هم‌اکنون پارامترهای طول عمر زیادی در کد وجود دارد، جنریک‌کردن آن موقعیت‌هایی را آشکار کرد که در آن‌ها بررسی‌کنندهٔ قرض تنها به‌دلیل ماهیت ویژهٔ اشیای LLVM که دستکاری می‌شوند (اشاره‌گرهای extern هستند) کد را می‌پذیرفت. برای مثال، باید یک پارامتر طول عمر اضافی به LocalAnalyser در analyse.rs افزوده می‌شد که به این تعریف انجامید:

    struct LocalAnalyzer<'mir, 'a, 'tcx> {
  /* ... */
}

    با این حال، دو ساختار مهم‌تر، یعنی CodegenCx و Builder، در کد مستقل از بک‌اند تعریف نشده‌اند. در واقع محتوای آن‌ها به‌شدت مختص بک‌اند است، و منطقی‌تر است که تعریف آن‌ها به پیاده‌ساز بک‌اند واگذار شود تا اینکه تنها یک نقطهٔ باریک از طریق یک فیلد جنریک برای زمینهٔ (context) بک‌اند اجازه داده شود.

    صفت‌ها و رابط

    چون CodegenCx و Builder باید توسط بک‌اند تعریف شوند، آن‌ها ساختارهایی خواهند بود که همهٔ صفت‌هایی را که رابط بک‌اند را تعریف می‌کنند پیاده‌سازی می‌کنند. این صفت‌ها در پوشهٔ rustc_codegen_ssa/traits تعریف شده‌اند و همهٔ کد مستقل از بک‌اند با آن‌ها پارامتری می‌شود. برای مثال، توضیح می‌دهیم که یک تابع در base.rs چگونه پارامتری شده است:

    pub fn codegen_instance<'a, 'tcx, Bx: BuilderMethods<'a, 'tcx>>(
    cx: &'a Bx::CodegenCx,
    instance: Instance<'tcx>
) {
    /* ... */
}

    در این امضا، دو پارامتر طول عمری را که پیشتر توضیح داده شد داریم، و نوع اصلی Bx که صفت BuilderMethods را برآورده می‌کند و متناظر است با رابطی که ساختار Builder برآورده می‌کند. BuilderMethods یک نوع وابسته، یعنی Bx::CodegenCx، تعریف می‌کند که خودش صفت‌های CodegenMethods را که ساختار CodegenCx پیاده‌سازی می‌کند برآورده می‌سازد.

    در سمت صفت، در اینجا مثالی با بخشی از تعریف BuilderMethods در traits/builder.rs آمده است:

    pub trait BuilderMethods<'a, 'tcx>:
    HasCodegen<'tcx>
    + DebugInfoBuilderMethods<'tcx>
    + ArgTypeMethods<'tcx>
    + AbiBuilderMethods<'tcx>
    + IntrinsicCallMethods<'tcx>
    + AsmBuilderMethods<'tcx>
{
    fn new_block<'b>(
        cx: &'a Self::CodegenCx,
        llfn: Self::Function,
        name: &'b str
    ) -> Self;
    /* ... */
    fn cond_br(
        &mut self,
        cond: Self::Value,
        then_llbb: Self::BasicBlock,
        else_llbb: Self::BasicBlock,
    );
    /* ... */
}

    سرانجام، یک ساختار اصلی که صفت ExtraBackendMethods را پیاده‌سازی می‌کند برای توابع سطح بالای هدایت‌کنندهٔ تولید کد، مانند codegen_crate در base.rs، به کار می‌رود. برای LLVM، این ساختار LlvmCodegenBackend تهی است. ExtraBackendMethods باید توسط همان ساختاری پیاده‌سازی شود که CodegenBackend تعریف‌شده در rustc_codegen_ssa/src/traits/backend.rs را پیاده‌سازی می‌کند.

    در جریان فرایند صفت‌سازی (traitification)، برخی توابع از متدهای یک ساختار محلی به متدهای CodegenCx یا Builder تبدیل شده‌اند و یک پارامتر self متناظر به آن‌ها افزوده شده است. در واقع LLVM اطلاعاتی را به‌صورت داخلی ذخیره می‌کند که هنگام فراخوانی از طریق API آن قابل دسترسی است. این اطلاعات در یک ساختار داده‌ای Rust که هنگام فراخوانی این متدها همراه آن‌ها منتقل شود ظاهر نمی‌شود. اما هنگام پیاده‌سازی یک بک‌اند Rust برای rustc، این متدها به اطلاعاتی از CodegenCx نیاز خواهند داشت، از این رو پارامتر اضافی (که در پیاده‌سازی LLVM از این صفت استفاده نمی‌شود) لازم است.

    وضعیت کد پس از بازسازی

    این صفت‌ها API‌ای ارائه می‌دهند که بسیار شبیه API مربوط به LLVM است. این بهترین راه‌حل نیست، زیرا LLVM شیوهٔ بسیار ویژه‌ای برای انجام کارها دارد: هنگام افزودن بک‌اندی دیگر، ممکن است تعریف صفت‌ها برای ارائهٔ انعطاف بیشتر تغییر کند.

    با این حال، جداسازی کنونی میان کد مستقل از بک‌اند و کد مختص LLVM امکان استفادهٔ دوباره از بخش قابل‌توجهی از rustc_codegen_llvm قدیمی را فراهم کرده است. در اینجا تفکیک جدید LOC میان کد مستقل از بک‌اند (BA) و LLVM برای مهم‌ترین عناصر آمده است:

    • پوشهٔ back: ۳٬۸۰۰ (BA) در برابر ۴٬۱۰۰ (LLVM)؛
    • پوشهٔ mir: ۴٬۴۰۰ (BA) در برابر ۰ (LLVM)؛
    • base.rs: ۱٬۱۰۰ (BA) در برابر ۲۵۰ (LLVM)؛
    • builder.rs: ۱٬۴۰۰ (BA) در برابر ۰ (LLVM)؛
    • common.rs: ۳۵۰ (BA) در برابر ۳۵۰ (LLVM)؛

    پوشهٔ debuginfo تقریباً دست‌نخورده از این تقسیم بیرون آمده و مختص LLVM است. تنها قابلیت‌های سطح بالای آن صفت‌سازی شده‌اند.

    پوشهٔ جدید traits فقط برای تعریف صفت‌ها ۱۵۰۰ LOC دارد. در مجموع، کد قدیمی rustc_codegen_llvm با حجم ۲۷٬۰۰۰ LOC به rustc_codegen_llvm جدید با حجم ۱۸٬۵۰۰ LOC و rustc_codegen_ssa با حجم ۱۲٬۰۰۰ LOC تقسیم شده است. می‌توان گفت این بازسازی امکان استفادهٔ دوبارهٔ حدود ۱۰٬۰۰۰ LOC را فراهم کرد که در غیر این صورت باید میان بک‌اندهای گوناگون rustc تکرار می‌شد.

    نسخهٔ بازسازی‌شدهٔ بک‌اند rustc نه در مجموعه آزمون و نه در بنچمارک کارایی هیچ پسرفتی ایجاد نکرد، که با ماهیت بازسازی سازگار است؛ بازسازی‌ای که فقط از پارامتری‌سازی در زمان کامپایل استفاده کرد (بدون شیء صفت).
