راهنمای توسعهٔ rustcrustc Development Guide

    به‌روزرسانی LLVM

    Rust از ساخت در برابر چند نسخهٔ LLVM پشتیبانی می‌کند:

    • Tip-of-tree شاخهٔ توسعهٔ فعلی LLVM معمولاً ظرف چند روز پشتیبانی می‌شود. PRهای مربوط به چنین رفع‌هایی با llvm-main برچسب‌گذاری می‌شوند.
    • آخرین نسخهٔ اصلی (major) منتشرشده همیشه پشتیبانی می‌شود.
    • یک یا دو نسخهٔ اصلی پیشین معمولاً به این معنا پشتیبانی می‌شوند که انتظار می‌رود با موفقیت ساخته شوند و بیشتر آزمون‌ها را بگذرانند. با این حال، رفع‌های مربوط به کامپایل نادرست (miscompilation) اغلب به نسخه‌های قدیمی‌تر LLVM backport نمی‌شوند، بنابراین استفاده از rustc با نسخه‌های قدیمی‌تر LLVM خطر باگ‌های سلامت (soundness) را افزایش می‌دهد. به‌شدت توصیه می‌کنیم از آخرین نسخهٔ LLVM استفاده کنید.

    به‌طور پیش‌فرض Rust از فورک خودش در مخزن rust-lang/llvm-project استفاده می‌کند. این فورک بر پایهٔ شاخهٔ release/$N.x پروژهٔ بالادستی (upstream) است، که $N یا آخرین نسخهٔ اصلی منتشرشده است، یا نسخهٔ اصلی فعلی در مرحلهٔ release candidate. فورک هرگز بر پایهٔ شاخهٔ توسعهٔ main نیست.

    فورک LLVM ما فقط این‌ها را می‌پذیرد:

    • backportهای تغییراتی که پیش‌تر در upstream وارد شده‌اند.
    • راه‌حل‌های موقت برای مشکلات ساخت که محیط CI ما را تحت تأثیر قرار می‌دهند.

    به‌استثنای یک وصلهٔ مشمول استثنا برای فعال‌سازی SGX، وصله‌های کارکردی را که ابتدا به upstream ارسال نشده باشند نمی‌پذیریم.

    سه نوع به‌روزرسانی LLVM وجود دارد که روال‌های متفاوتی دارند:

    • backport در حالی که نسخهٔ اصلی فعلی LLVM پشتیبانی می‌شود.
    • backport در حالی که نسخهٔ اصلی فعلی LLVM دیگر پشتیبانی نمی‌شود (یا تغییر واجد شرایط backport در upstream نیست).
    • به‌روزرسانی به یک نسخهٔ اصلی جدید LLVM.

    Backportها (upstream پشتیبانی‌شده)

    تا زمانی که نسخهٔ اصلی فعلی LLVM در upstream پشتیبانی می‌شود، رفع‌ها باید ابتدا در upstream backport شوند و سپس شاخهٔ release دوباره در فورک Rust ادغام شود.

    1. مطمئن شوید رفع باگ در LLVM بالادستی (upstream) وجود دارد.
    2. اگر این کار هنوز انجام نشده، درخواست backport به شاخهٔ release بالادستی بدهید. اگر دسترسی commit به LLVM دارید، فرایند backport را دنبال کنید. در غیر این صورت، یک issue برای درخواست backport باز کنید. پس از تأیید و ادغام backport ادامه دهید.
    3. شاخه‌ای را که rustc در حال حاضر از آن استفاده می‌کند شناسایی کنید. زیرماژول src/llvm-project همیشه به یک شاخه از مخزن rust-lang/llvm-project سنجاق شده است.
    4. مخزن rust-lang/llvm-project را فورک کنید.
    5. شاخهٔ مناسب را checkout کنید (معمولاً با نامی مانند rustc/a.b-yyyy-mm-dd).
    6. با git remote add upstream https://github.com/llvm/llvm-project.git یک remote برای مخزن بالادستی اضافه کنید و با git fetch upstream آن را دریافت کنید.
    7. شاخهٔ upstream/release/$N.x را ادغام (merge) کنید.
    8. این شاخه را به فورک خود push کنید.
    9. یک Pull Request به rust-lang/llvm-project روی همان شاخهٔ قبلی بفرستید. حتماً در توضیح PR به مسئلهٔ Rust و/یا LLVM که در حال رفع آن هستید ارجاع دهید.
    10. منتظر بمانید PR ادغام شود.
    11. یک PR به rust-lang/rust بفرستید که زیرماژول src/llvm-project را با رفع باگ شما به‌روز کند. این کار معمولاً به‌صورت محلی با git submodule update --remote src/llvm-project انجام می‌شود.
    12. منتظر بمانید PR ادغام شود.

    یک PR نمونه: #59089

    Backportها (upstream پشتیبانی‌نشده)

    نسخه‌های LLVM بالادستی فقط دو تا سه ماه پس از انتشار GA پشتیبانی می‌شوند. وقتی backportهای upstream دیگر پذیرفته نمی‌شوند، تغییرات باید مستقیماً به فورک ما cherry-pick شوند.

    1. مطمئن شوید رفع باگ در LLVM بالادستی (upstream) وجود دارد.
    2. شاخه‌ای را که rustc در حال حاضر از آن استفاده می‌کند شناسایی کنید. زیرماژول src/llvm-project همیشه به یک شاخه از مخزن rust-lang/llvm-project سنجاق شده است.
    3. مخزن rust-lang/llvm-project را فورک کنید.
    4. شاخهٔ مناسب را checkout کنید (معمولاً با نامی مانند rustc/a.b-yyyy-mm-dd).
    5. با git remote add upstream https://github.com/llvm/llvm-project.git یک remote برای مخزن بالادستی اضافه کنید و با git fetch upstream آن را دریافت کنید.
    6. commit(های) مربوطه را با git cherry-pick -x cherry-pick کنید.
    7. این شاخه را به فورک خود push کنید.
    8. یک Pull Request به rust-lang/llvm-project روی همان شاخهٔ قبلی بفرستید. حتماً در توضیح PR به مسئلهٔ Rust و/یا LLVM که در حال رفع آن هستید ارجاع دهید.
    9. منتظر بمانید PR ادغام شود.
    10. یک PR به rust-lang/rust بفرستید که زیرماژول src/llvm-project را با رفع باگ شما به‌روز کند. این کار معمولاً به‌صورت محلی با git submodule update --remote src/llvm-project انجام می‌شود.
    11. منتظر بمانید PR ادغام شود.

    به‌روزرسانی به نسخهٔ جدید LLVM

    برخلاف رفع باگ‌ها، به‌روزرسانی به یک نسخهٔ جدید LLVM معمولاً کار بسیار بیشتری لازم دارد. اینجا جایی است که نمی‌توانیم به‌طور معقول commitها را به عقب cherry-pick کنیم، پس باید به‌روزرسانی کامل انجام دهیم. کارهای زیادی برای انجام وجود دارد، پس هر کدام را با جزئیات مرور می‌کنیم.

    1. LLVM اعلام می‌کند آخرین نسخهٔ انتشارش شاخه‌بندی (branch) شده است. این در مخزن llvm/llvm-project به‌صورت یک شاخه ظاهر می‌شود که معمولاً release/$N.x نام دارد، و $N نسخهٔ LLVM در حال انتشار است.

    2. در مخزن rust-lang/llvm-project یک شاخهٔ جدید از این شاخهٔ release/$N.x بسازید و نامش را rustc/a.b-yyyy-mm-dd بگذارید، که a.b شمارهٔ نسخهٔ فعلی LLVM درون درخت (in-tree) در زمان ساخت شاخه است و بخش باقی‌مانده تاریخ جاری است.

    3. وصله‌های ویژهٔ Rust را روی مخزن llvm-project اعمال کنید. همهٔ قابلیت‌ها و رفع باگ‌ها در upstream هستند، اما اغلب چند وصلهٔ عجیب مرتبط با ساخت وجود دارد که ارسال‌شان به upstream معنا ندارد. این وصله‌ها معمولاً آخرین وصله‌های شاخهٔ rust-lang/llvm-project هستند که rustc در حال حاضر از آن استفاده می‌کند.

    4. LLVM جدید را در مخزن rust بسازید. برای این کار، باید مخزن src/llvm-project را به شاخهٔ خود و ریویژنی که ساخته‌اید به‌روز کنید. معمولاً به‌روزرسانی .gitmodules با نام شاخهٔ جدید زیرماژول LLVM هم ایدهٔ خوبی است. مطمئن شوید تغییرات src/llvm-project را commit کرده‌اید تا به‌روزرسانی‌های زیرماژول برگردانده نشوند. چند دستوری که باید اجرا کنید:

      • ./x build src/llvm-project - آزمودن اینکه LLVM همچنان ساخته می‌شود
      • ./x build - ساخت بقیهٔ rustc

      احتمالاً باید llvm-wrapper/*.cpp را برای کامپایل با bindingهای به‌روز LLVM به‌روز کنید. توجه کنید که باید از #ifdef و مانند آن استفاده کنید تا مطمئن شوید bindingها همچنان روی نسخه‌های قدیمی‌تر LLVM کامپایل می‌شوند.

      توجه کنید که profile = "compiler" و پیش‌فرض‌های دیگری که ./x setup تنظیم می‌کند LLVM را به‌جای ساخت از روی سورس، از CI دانلود می‌کنند. باید این را موقتاً غیرفعال کنید تا مطمئن شوید تغییرات شما استفاده می‌شوند. این کار با داشتن تنظیم زیر در bootstrap.toml انجام می‌شود:

      llvm.download-ci-llvm = false

    5. رگرسیون‌ها را روی پلتفرم‌های دیگر بیازمایید. LLVM اغلب دست‌کم یک باگ برای معماری‌های غیر tier-1 دارد، پس خوب است پیش از فرستادن این به bors کمی بیشتر آزمایش کنید! اگر منابع کمی دارید، می‌توانید PR را همان‌طور که هست اکنون به bors بفرستید و به‌هرحال آزمایش می‌شود.

      در حالت ایده‌آل، LLVM را بسازید و روی چند پلتفرم آزمایش کنید:

      • Linux
      • macOS
      • Windows

      پس از آن، چند کانتینر docker را که CI هم اجرا می‌کند اجرا کنید:

      • ./src/ci/docker/run.sh wasm32
      • ./src/ci/docker/run.sh arm-android
      • ./src/ci/docker/run.sh dist-various-1
      • ./src/ci/docker/run.sh dist-various-2
      • ./src/ci/docker/run.sh armhf-gnu

    6. یک PR برای rust-lang/rust آماده کنید. با نگهدارندگان rust-lang/llvm-project کار کنید تا commit شما در شاخه‌ای از آن مخزن قرار گیرد، و سپس می‌توانید یک PR به rust-lang/rust بفرستید. دست‌کم src/llvm-project را تغییر می‌دهید و احتمالاً llvm-wrapper را هم تغییر خواهید داد.

      برای نمونه‌های پیشین، این‌ها چند به‌روزرسانی قبلی LLVM هستند:

      • LLVM 17
      • LLVM 18
      • LLVM 19
      • LLVM 20
      • LLVM 21
      • LLVM 22

      توجه کنید که گاهی ساده‌ترین کار این است که سازگاری llvm-wrapper را به‌صورت یک PR پیش از به‌روزرسانی واقعی src/llvm-project وارد کنید. به این ترتیب، در حالی که مشغول رفع مشکلات LLVM هستید، دیگرانی که می‌خواهند LLVM جدید را امتحان کنند می‌توانند از کاری که برای به‌روزرسانی bindingهای C++ انجام داده‌اید بهره ببرند.

    7. طی چند ماه آینده، LLVM پیوسته commitهایی را به شاخهٔ release/a.b خود push می‌کند. اغلب می‌خواهیم آن رفع باگ‌ها را هم داشته باشیم. فرایند ادغام برای این کار استفاده از خود git merge برای ادغام شاخهٔ release/a.b مربوط به LLVM با شاخهٔ ساخته‌شده در گام ۲ است. این کار معمولاً در صورت لزوم چندین بار انجام می‌شود، در حالی که شاخهٔ release در LLVM در حال پخته شدن است.

    8. سپس LLVM انتشار نسخهٔ a.b را اعلام می‌کند.

    9. پس از انتشار رسمی LLVM، دوباره فرایند ساخت یک شاخهٔ جدید روی مخزن rust-lang/llvm-project را دنبال می‌کنیم، این بار با تاریخی جدید. فقط آن‌گاه PR مربوط به به‌روزرسانی Rust برای استفاده از آن نسخه ادغام می‌شود.

      تاریخچهٔ commitهای rust-lang/llvm-project با انجام یک git rebase بسیار تمیزتر به نظر می‌رسد، چون فقط چند commit ویژهٔ Rust روی شاخهٔ release استاندارد LLVM انباشته شده‌اند.

    هشدارها و نکات پرتله

    در حالت ایده‌آل دستورالعمل‌های بالا نسبتاً روان‌اند، اما این چند هشدار را هنگام پیمودنشان به یاد داشته باشید:

    • یافتن باگ‌های LLVM سخت است، در درخواست کمک تردید نکنید! دوپاره‌سازی (bisection) قطعاً در اینجا دوست شماست (بله، ساخت LLVM بی‌نهایت طول می‌کشد، با این حال bisection همچنان دوست شماست). توجه کنید که می‌توانید از Dev Desktops استفاده کنید، که ابتکاری برای فراهم کردن دسترسی از راه دور مشارکت‌کنندگان به سخت‌افزار قدرتمند است.
    • اگر پرسش‌های عمومی دارید، wg-llvm می‌تواند کمکتان کند.
    • ساخت شاخه‌ها در GitHub یک عمل دارای امتیاز ویژه است، پس به احتمال زیاد به کسی با دسترسی نوشتن نیاز دارید تا شاخه‌ها را برایتان بسازد.
