    مکان ضمنی فراخواننده (Implicit caller location)

    این ویژگی که در RFC 2091 تأیید شد، گزارش دقیق مکان فراخواننده را در panicهایی ممکن می‌کند که از توابعی مانند Option::unwrap، Result::expect و Index::index آغاز می‌شوند. این ویژگی attribute ‏#[track_caller] را برای توابع، intrinsic ‏caller_location و wrapper مناسب پایدارسازی یعنی core::panic::Location::caller را اضافه می‌کند.

    مثال انگیزه‌بخش

    این برنامهٔ نمونه را در نظر بگیرید:

    fn main() {
    let foo: Option<()> = None;
    foo.unwrap(); // this should produce a useful panic message!
}

    پیش از Rust 1.42، panicهایی مانند این unwrap() مکانی را در core چاپ می‌کردند:

    $ rustc +1.41.0 example.rs; example.exe
thread 'main' panicked at 'called `Option::unwrap()` on a `None` value',...core\macros\mod.rs:15:40
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace.

    از 1.42 به بعد، پیامی بسیار مفیدتر می‌گیریم:

    $ rustc +1.42.0 example.rs; example.exe
thread 'main' panicked at 'called `Option::unwrap()` on a `None` value', example.rs:3:5
note: run with `RUST_BACKTRACE=1` environment variable to display a backtrace

    این پیام‌های خطا از ترکیبی از تغییرات در درونیات panic! برای بهره‌گیری از core::panic::Location::caller و تعدادی حاشیه‌نویسی #[track_caller] در کتابخانهٔ استاندارد به دست می‌آیند که اطلاعات فراخواننده را منتشر می‌کنند.

    خواندن مکان فراخواننده

    پیش‌تر، panic! از ماکروهای file!()، line!() و column!() برای ساختن یک Location استفاده می‌کرد که به محل رخ دادن panic اشاره می‌کرد. نمی‌شد به این ماکروها مکانی جایگزین داد، پس توابعی که عمداً panic! را فراخوانی می‌کردند نمی‌توانستند مکان خودشان را فراهم کنند و منبع واقعی خطا پنهان می‌ماند.

    در درون، panic!() اکنون core::panic::Location::caller() را فراخوانی می‌کند تا بفهمد در کجا بسط داده شده است. این تابع خودش با #[track_caller] حاشیه‌نویسی شده و intrinsic کامپایلر ‏caller_location را که rustc پیاده‌سازی کرده است می‌پوشاند. این intrinsic را آسان‌تر می‌توان بر حسب نحوهٔ کارش در بافت const توضیح داد.

    مکان فراخواننده در const

    بازگرداندن مکان فراخواننده در بافت const دو فاز اصلی دارد: پیمایش به بالای پشته برای یافتن مکان درست و تخصیص یک مقدار const برای بازگرداندن.

    یافتن Location درست

    در بافت const از جایی که intrinsic فراخوانی شده «به بالای پشته پیمایش می‌کنیم» و وقتی به نخستین فراخوانی تابع در پشته می‌رسیم که attribute را ندارد متوقف می‌شویم. این پیمایش در InterpCx::find_closest_untracked_caller_location() قرار دارد.

    با شروع از پایین، روی Frameهای پشته در InterpCx::stack به سمت بالا پیمایش می‌کنیم و InstanceKind::requires_caller_location را روی Instanceهای هر Frame فراخوانی می‌کنیم. به محض اینکه یکی را بیابیم که false برمی‌گرداند متوقف می‌شویم و span مربوط به قاب قبلی را برمی‌گردانیم که «بالاترین» تابع ردیابی‌شده بود.

    تخصیص یک Location ایستا

    وقتی یک Span داریم، باید برای Location حافظهٔ ایستا تخصیص دهیم، که توسط query ‏TyCtxt::const_caller_location() انجام می‌شود. در درون این InterpCx::alloc_caller_location() را فراخوانی می‌کند و به یک نوع حافظهٔ یکتا (MemoryKind::CallerLocation) می‌انجامد. بک‌اند codegen از نوع SSA می‌تواند برای همین مقادیر کد تولید کند و ما آن کد را آنجا هم به کار می‌بریم.

    وقتی Location ما در حافظهٔ ایستا تخصیص یافت، intrinsic ما ارجاعی به آن برمی‌گرداند.

    تولید کد برای callee‌های #[track_caller]

    برای تولید کد کارآمد برای یک تابع ردیابی‌شده و فراخواننده‌های آن، باید از دید intrinsic همان رفتار را بدون داشتن پشته‌ای برای پیمایش به بالا در زمان اجرا فراهم کنیم. رویکرد را معکوس می‌کنیم: هنگامی که پشته را به پایین رشد می‌دهیم یک آرگومان اضافی به فراخوانی‌های توابع ردیابی‌شده می‌دهیم، به‌جای اینکه هنگام فراخوانی intrinsic به بالای پشته پیمایش کنیم. آن آرگومان اضافی را می‌توان هر جا مکان فراخواننده پرس‌وجو می‌شود برگرداند.

    آرگومانی که اضافه می‌کنیم از نوع &'static core::panic::Location<'static> است. ارجاع انتخاب شد تا از کپی غیرضروری پرهیز شود، چون در زمان نگارش، اندازهٔ یک اشاره‌گر یک‌سوم std::mem::size_of::<core::panic::Location>() == 24 است.

    هنگام تولید فراخوانی به تابعی که ردیابی می‌شود، به آرگومان مکان مقدار FunctionCx::get_caller_location را می‌دهیم.

    اگر تابع فراخواننده ردیابی شود، get_caller_location متغیر محلی را در FunctionCx::caller_location برمی‌گرداند که توسط فراخوانندهٔ فراخوانندهٔ فعلی پر شده است. در این موارد intrinsic ارجاعی را «برمی‌گرداند» که در واقع در یک آرگومان به فراخواننده‌اش داده شده بود.

    اگر تابع فراخواننده ردیابی نشود، get_caller_location یک Location ایستا را از Span فعلی تخصیص می‌دهد و ارجاعی به آن برمی‌گرداند.

    همان رفتار حلقه‌ای را که از پایین شروع شود کارآمدتر به دست می‌آوریم، با عبور یک مقدار &Location واحد از فیلدهای caller_location چند FunctionCx در حین رشد پشته به سمت پایین.

    مثال‌های codegen

    این تبدیل در عمل چه شکلی دارد؟ این مثال را که از ویژگی جدید استفاده می‌کند در نظر بگیرید:

    #![feature(track_caller)]
use std::panic::Location;

#[track_caller]
fn print_caller() {
    println!("called from {}", Location::caller());
}

fn main() {
    print_caller();
}

    در اینجا print_caller() ظاهراً هیچ آرگومانی نمی‌گیرد، اما آن را به چیزی شبیه این کامپایل می‌کنیم:

    #![feature(panic_internals)]
use std::panic::Location;

fn print_caller(caller: &Location) {
    println!("called from {}", caller);
}

fn main() {
    print_caller(&Location::internal_constructor(file!(), line!(), column!()));
}

    dispatch پویا

    در بافت‌های codegen باید ABI مربوط به callee را تغییر دهیم تا این اطلاعات را به پایین پشته منتقل کنیم، اما attribute صراحتاً نوع تابع را تغییر نمی‌دهد. تغییر ABI باید برای بررسی نوع شفاف باشد و در همهٔ کاربردها سالم (sound) بماند.

    فراخوانی‌های مستقیم به توابع ردیابی‌شده همیشه پرچم‌های کامل codegen مربوط به callee را می‌دانند و می‌توانند کد مناسب تولید کنند. فراخواننده‌های غیرمستقیم این اطلاعات را ندارند و در نوع اشاره‌گر تابعی که فراخوانی می‌کنند کدگذاری نشده است، پس هر وقت اشاره‌گری به تابع می‌گیریم یک ReifyShim دور آن تابع تولید می‌کنیم. این shim نمی‌تواند مکان واقعی فراخوانی غیرمستقیم را گزارش کند (به‌جای آن محل تعریف تابع گزارش می‌شود)، اما از کامپایل نادرست جلوگیری می‌کند و احتمالاً بهترین کاری است که بدون تغییر امضاهای نوع کاملاً پایدارشده می‌توانیم بکنیم.

    نکته: هر وقت اشاره‌گری به یک تابع ردیابی‌شده می‌گیریم همیشه یک ReifyShim تولید می‌کنیم. اگرچه این قید را بافت‌های codegen تحمیل می‌کنند، هنگام ساخت MIR مربوط به shim نمی‌دانیم آیا در بافت const فراخوانی می‌شویم (نادیده گرفتن shim ایمن است) یا در بافت codegen (نادیده گرفتن shim ناایمن است). حتی اگر می‌دانستیم، نتایج بافت‌های const و codegen باید با هم سازگار باشند.

    attribute

    attribute ‏#[track_caller] در کنار attributeهای codegen دیگر بررسی می‌شود تا مطمئن شویم تابع:

    • ABI ‏"Rust" دارد (نه مثلاً "C")
    • closure نیست
    • #[naked] نیست

    اگر کاربرد معتبر باشد، CodegenFnAttrsFlags::TRACK_CALLER را تنظیم می‌کنیم. این پرچم بر مقدار بازگشتی InstanceKind::requires_caller_location اثر می‌گذارد که به‌نوبهٔ خود هم در بافت‌های const و هم در بافت‌های codegen برای تضمین انتشار درست به کار می‌رود.

    صفت‌ها (Traits)

    وقتی بر پیاده‌سازی‌های متد صفت اعمال شود، attribute همان‌طور که برای توابع معمولی کار می‌کند عمل می‌کند.

    وقتی بر نمونهٔ اولیهٔ یک متد صفت اعمال شود، attribute بر همهٔ پیاده‌سازی‌های آن متد اعمال می‌شود. وقتی بر پیاده‌سازی پیش‌فرض متد صفت اعمال شود، attribute بر آن پیاده‌سازی و هر بازنویسی (override) آن اثر می‌گذارد.

    مثال‌ها:

    #![feature(track_caller)]

macro_rules! assert_tracked {
    () => {{
        let location = std::panic::Location::caller();
        assert_eq!(location.file(), file!());
        assert_ne!(location.line(), line!(), "line should be outside this fn");
        println!("called at {}", location);
    }};
}

trait TrackedFourWays {
    /// All implementations inherit `#[track_caller]`.
    #[track_caller]
    fn blanket_tracked();

    /// Implementors can annotate themselves.
    fn local_tracked();

    /// This implementation is tracked (overrides are too).
    #[track_caller]
    fn default_tracked() {
        assert_tracked!();
    }

    /// Overrides of this implementation are tracked (it is too).
    #[track_caller]
    fn default_tracked_to_override() {
        assert_tracked!();
    }
}

/// This impl uses the default impl for `default_tracked` and provides its own for
/// `default_tracked_to_override`.
impl TrackedFourWays for () {
    fn blanket_tracked() {
        assert_tracked!();
    }

    #[track_caller]
    fn local_tracked() {
        assert_tracked!();
    }

    fn default_tracked_to_override() {
        assert_tracked!();
    }
}

fn main() {
    <() as TrackedFourWays>::blanket_tracked();
    <() as TrackedFourWays>::default_tracked();
    <() as TrackedFourWays>::default_tracked_to_override();
    <() as TrackedFourWays>::local_tracked();
}

    پیش‌زمینه/تاریخچه

    به‌طور کلی، هدف این ویژگی بهبود پیام‌های خطای رایج Rust است، بدون شکستن تضمین‌های پایداری، نیاز به تغییر در کد منبع کاربر نهایی، تکیه بر اطلاعات دیباگ وابسته به پلتفرم، یا محروم کردن نوع‌های تعریف‌شده توسط کاربر از همین مزایای گزارش خطا.

    بهبود خروجی این panicها دست‌کم از اواسط ۲۰۱۶ هدف پیشنهادها بوده است (برای جزئیات جایگزین‌های ناممکن را در RFC تأییدشده ببینید). دو سال دیگر طول کشید تا RFC 2091 تأیید شود، و بخش بزرگی از استدلال طراحی این ویژگی در بحث پیرامون چند پیشنهاد پیشین کشف شده بود.

    طراحی در RFC اصلی خود را به پیاده‌سازی‌هایی محدود کرد که در آن زمان می‌شد بدون بازآرایی چشمگیر درون کامپایلر انجام داد. اما در یک سال و نیم میان تأیید RFC و کار پیاده‌سازی واقعی، یک طراحی بازنگری‌شده پیشنهاد و در tracking issue نوشته شد. در جریان پیاده‌سازی آن، همچنین کشف شد که پیاده‌سازی بدون تغییر تعداد آرگومان‌ها در MIR یک تابع ممکن است، که مراحل بعدی را ساده می‌کند و استفاده در صفت‌ها را ممکن می‌سازد.

    چون راهبرد پیاده‌سازی RFC نمی‌توانست به‌آسانی از صفت‌ها پشتیبانی کند، معناشناسی در ابتدا مشخص نشد. از آن زمان بر اساس مسیری پیاده‌سازی شده‌اند که از نظر نویسنده و بازبین‌ها درست‌تر به نظر می‌رسید.
