    ساختارهای Diagnostic و subdiagnostic

    rustc دو صفت تشخیصی (diagnostic trait) دارد که می‌توان از آن‌ها برای ساخت diagnosticها استفاده کرد: Diagnostic و Subdiagnostic.

    برای diagnosticهای ساده می‌توان از پیاده‌سازی‌های مشتق‌شده (derived impl) استفاده کرد، مثلاً #[derive(Diagnostic)]. این روش فقط برای diagnosticهای ساده مناسب است که برای تصمیم‌گیری درباره‌ی افزودن subdiagnosticهای اضافی به منطق زیادی نیاز ندارند.

    در مواردی که diagnosticها به رفتار پیچیده‌تر یا پویاتری نیاز دارند، مانند افزودن شرطی subdiagnosticها، سفارشی‌سازی منطق رندر کردن یا انتخاب پیام‌ها در زمان اجرا، باید صفت متناظر (Diagnostic یا Subdiagnostic) را به صورت دستی پیاده‌سازی کنید. این رویکرد انعطاف بیشتری فراهم می‌کند و برای diagnosticهایی که از ساختارهای ساده و ایستا فراتر می‌روند توصیه می‌شود.

    Diagnostic را می‌توان به زبان‌های مختلف ترجمه کرد.

    #[derive(Diagnostic)]

    تعریف diagnostic مربوط به «field already declared» را که در زیر آمده در نظر بگیرید:

    #[derive(Diagnostic)]
#[diag("field `{$field_name}` is already declared", code = E0124)]
pub struct FieldAlreadyDeclared {
    pub field_name: Ident,
    #[primary_span]
    #[label("field already declared")]
    pub span: Span,
    #[label("`{$field_name}` first declared here")]
    pub prev_span: Span,
}

    Diagnostic را فقط می‌توان روی ساختارها و شمارش‌ها مشتق کرد. attributeهایی که برای ساختارها روی نوع قرار می‌گیرند، برای شمارش‌ها روی هر واریانت قرار می‌گیرند (یا برعکس). هر Diagnostic باید یک attribute به نام #[diag(...)] داشته باشد که روی ساختار یا هر واریانت شمارش اعمال می‌شود.

    اگر یک خطا کد خطا دارد (مثلاً «E0624»)، آن را می‌توان با زیرattribute به نام code مشخص کرد. تعیین code اجباری نیست، اما اگر در حال انتقال یک diagnostic هستید که از Diag استفاده می‌کند تا از Diagnostic استفاده کند، باید در صورت وجود کد، آن را نگه دارید.

    #[diag(..)] باید یک پیام را به عنوان اولین آرگومان موقعیتی (positional) ارائه دهد. پیام به انگلیسی نوشته می‌شود، اما ممکن است به زبان محلی (locale) درخواستی کاربر ترجمه شود. برای اطلاع بیشتر درباره‌ی نحوه‌ی نوشتن و تولید پیام‌های خطای قابل ترجمه، مستندات ترجمه را ببینید.

    هر فیلد از Diagnostic که annotation ندارد، در پیام‌های Fluent به عنوان یک متغیر در دسترس است، مانند field_name در مثال بالا.

    استفاده از attribute به نام #[primary_span] روی یک فیلد (که نوع Span دارد) span اصلی diagnostic را مشخص می‌کند که پیام اصلی diagnostic را خواهد داشت.

    diagnosticها فقط پیام اصلی خود نیستند؛ اغلب شامل برچسب‌ها (label)، یادداشت‌ها (note)، پیام‌های راهنما (help) و پیشنهادها (suggestion) هستند که همه‌ی آن‌ها را نیز می‌توان روی یک Diagnostic مشخص کرد.

    #[label]، #[help]، #[warning] و #[note] همگی را می‌توان روی فیلدهایی که نوع Span دارند اعمال کرد. اعمال هر یک از این attributeها subdiagnostic متناظر را با آن Span ایجاد می‌کند. این attributeها یک پیام diagnostic را به عنوان آرگومان می‌گیرند.

    نوع‌های دیگر هنگام استفاده در یک derive از Diagnostic رفتار ویژه‌ای دارند:

    • هر attribute که روی Option<T> اعمال شود، فقط در صورتی یک subdiagnostic صادر می‌کند که option برابر Some(..) باشد.
    • هر attribute که روی Vec<T> اعمال شود، برای هر عنصر بردار تکرار می‌شود.

    #[help]، #[warning] و #[note] را می‌توان روی خود ساختار نیز اعمال کرد، که در این صورت دقیقاً مانند اعمال روی فیلدها کار می‌کنند، با این تفاوت که subdiagnostic هیچ Span نخواهد داشت. این attributeها را می‌توان برای همین اثر روی فیلدهایی از نوع () نیز اعمال کرد، که در ترکیب با نوع Option می‌تواند برای نمایش subdiagnosticهای اختیاری #[note]/#[help]/#[warning] به کار رود.

    پیشنهادها را می‌توان با یکی از چهار attribute فیلد صادر کرد:

    • #[suggestion("message", code = "...", applicability = "...")]
    • #[suggestion_hidden("message", code = "...", applicability = "...")]
    • #[suggestion_short("message", code = "...", applicability = "...")]
    • #[suggestion_verbose("message", code = "...", applicability = "...")]

    پیشنهادها باید روی فیلدی از نوع Span یا فیلدی از نوع (Span, MachineApplicability) اعمال شوند. مشابه سایر attributeهای فیلد، باید پیامی ارائه شود که به کاربر نمایش داده می‌شود. code کدی را مشخص می‌کند که باید به عنوان جایگزین پیشنهاد شود و یک رشته‌ی قالب (format string) است (مثلاً {field_name} با مقدار فیلد field_name ساختار جایگزین می‌شود). از applicability می‌توان برای مشخص کردن قابلیت اعمال در attribute استفاده کرد؛ هنگامی که نوع فیلد شامل یک Applicability باشد نمی‌توان از آن استفاده کرد.

    در نهایت، derive مربوط به Diagnostic یک پیاده‌سازی از Diagnostic تولید می‌کند که شبیه زیر است:

    impl<'a> Diagnostic<'a> for FieldAlreadyDeclared {
    fn into_diag(self, dcx: DiagCtxtHandle<'a>, level: Level) -> Diag<'a> {
        let mut diag = Diag::new(dcx, level, "field `{$field_name}` is already declared");
        diag.set_span(self.span);
        diag.span_label(
            self.span,
            "field already declared"
        );
        diag.span_label(
            self.prev_span,
            "`{$field_name}` first declared here"
        );
        diag
    }
}

    حال که diagnostic خود را تعریف کرده‌ایم، چگونه از آن استفاده کنیم؟ کاملاً سر راست است؛ فقط یک نمونه از ساختار بسازید و آن را به emit_err (یا emit_warning) بدهید:

    tcx.dcx().emit_err(FieldAlreadyDeclared {
    field_name: f.ident,
    span: f.span,
    prev_span,
});

    مرجع #[derive(Diagnostic)]

    #[derive(Diagnostic)] از attributeهای زیر پشتیبانی می‌کند:

    • #[diag("message", code = "...")]
      • روی ساختار یا واریانت شمارش اعمال می‌شود.
      • اجباری
      • متن و کد خطایی را که با diagnostic مرتبط می‌شود تعریف می‌کند.
      • پیام (اجباری)
        • پیام diagnostic که به کاربر نمایش داده می‌شود.
        • مستندات ترجمه را ببینید.
      • code = "..." (اختیاری)
        • کد خطا را مشخص می‌کند.
    • #[note("message")] (اختیاری)
      • روی ساختار یا فیلدهای ساختار از نوع Span، Option<()>، bool یا () اعمال می‌شود.
      • یک subdiagnostic از نوع note اضافه می‌کند.
      • مقدار، پیام note است.
      • اگر روی فیلد Span اعمال شود، یک note مبتنی بر span ایجاد می‌کند.
    • #[help("message")] (اختیاری)
      • روی ساختار یا فیلدهای ساختار از نوع Span، Option<()>، bool یا () اعمال می‌شود.
      • یک subdiagnostic از نوع help اضافه می‌کند.
      • مقدار، پیام help است.
      • اگر روی فیلد Span اعمال شود، یک help مبتنی بر span ایجاد می‌کند.
    • #[label("message")] (اختیاری)
      • روی فیلدهای Span اعمال می‌شود.
      • یک subdiagnostic از نوع label اضافه می‌کند.
      • مقدار، پیام label است.
    • #[warning("message")] (اختیاری)
      • روی ساختار یا فیلدهای ساختار از نوع Span، Option<()>، bool یا () اعمال می‌شود.
      • یک subdiagnostic از نوع warning اضافه می‌کند.
      • مقدار، پیام warning است.
    • #[suggestion("message", code = "...", applicability = "...", style = "...")] (اختیاری)
      • روی فیلدهای (Span, MachineApplicability) یا Span اعمال می‌شود.
      • یک subdiagnostic از نوع suggestion اضافه می‌کند.
      • پیام (اجباری)
        • مقدار، پیام پیشنهادی است که به کاربر نمایش داده می‌شود.
        • مستندات ترجمه را ببینید.
      • code = "..."/code("...", ...) (اجباری)
        • یک یا چند رشته‌ی قالب که کدی را که باید به عنوان جایگزین پیشنهاد شود نشان می‌دهند. چند مقدار به معنای چند جایگزین ممکن است.
      • applicability = "..." (اختیاری)
        • رشته‌ای که باید یکی از machine-applicable، maybe-incorrect، has-placeholders یا unspecified باشد.
      • style = "..." (اختیاری)
        • مقدار، سبک پیشنهاد است.
        • رشته‌ای که باید یکی از normal، short، hidden، verbose یا tool-only باشد.
    • #[subdiagnostic]
      • روی نوعی که Subdiagnostic را پیاده‌سازی می‌کند (از #[derive(Subdiagnostic)]) اعمال می‌شود.
      • subdiagnosticی را که ساختار subdiagnostic نمایندگی می‌کند اضافه می‌کند.
    • #[primary_span] (اختیاری)
      • روی فیلدهای Span در Subdiagnosticها اعمال می‌شود.
      • span اصلی diagnostic را مشخص می‌کند.

    #[derive(Subdiagnostic)]

    در کامپایلر رایج است که تابعی نوشته شود که در صورت قابل اعمال بودن، به صورت شرطی یک subdiagnostic مشخص را به یک خطا اضافه می‌کند. اغلب این subdiagnosticها را می‌توان با یک ساختار diagnostic نمایش داد، حتی اگر کل diagnostic را نتوان این‌گونه نمایش داد. در این شرایط، derive مربوط به Subdiagnostic را می‌توان برای نمایش یک diagnostic جزئی (مثلاً یک note، label، help یا suggestion) به صورت ساختار به کار برد.

    تعریف برچسب «expected return type» را که در زیر آمده در نظر بگیرید:

    #[derive(Subdiagnostic)]
pub enum ExpectedReturnTypeLabel<'tcx> {
    #[label("expected `()` because of default return type")]
    Unit {
        #[primary_span]
        span: Span,
    },
    #[label("expected `{$expected}` because of return type")]
    Other {
        #[primary_span]
        span: Span,
        expected: Ty<'tcx>,
    },
}

    مانند Diagnostic، می‌توان Subdiagnostic را برای ساختارها یا شمارش‌ها مشتق کرد. attributeهایی که برای ساختارها روی نوع قرار می‌گیرند، برای شمارش‌ها روی هر واریانت قرار می‌گیرند (یا برعکس). هر Subdiagnostic باید یک attribute روی ساختار یا هر واریانت داشته باشد، یکی از موارد زیر:

    • #[label(..)] برای تعریف یک label
    • #[note(..)] برای تعریف یک note
    • #[help(..)] برای تعریف یک help
    • #[warning(..)] برای تعریف یک warning
    • #[suggestion(..)] برای تعریف یک suggestion

    همه‌ی موارد بالا باید یک پیام diagnostic را به عنوان اولین آرگومان موقعیتی ارائه دهند. برای اطلاع بیشتر درباره‌ی نحوه‌ی تولید پیام‌های خطای قابل ترجمه، مستندات ترجمه را ببینید.

    استفاده از attribute به نام #[primary_span] روی یک فیلد (با نوع Span) span اصلی subdiagnostic را مشخص می‌کند. span اصلی فقط برای label یا suggestion لازم است، زیرا آن‌ها نمی‌توانند بدون span باشند.

    هر فیلد از نوع/واریانت که annotation ندارد، در پیام‌های Fluent به عنوان یک متغیر در دسترس است.

    مانند Diagnostic، Subdiagnostic از فیلدهای Option<T> و Vec<T> پشتیبانی می‌کند.

    پیشنهادها را می‌توان با یکی از چهار attribute روی نوع/واریانت صادر کرد:

    • #[suggestion("...", code = "...", applicability = "...")]
    • #[suggestion_hidden("...", code = "...", applicability = "...")]
    • #[suggestion_short("...", code = "...", applicability = "...")]
    • #[suggestion_verbose("...", code = "...", applicability = "...")]

    پیشنهادها نیاز دارند که #[primary_span] روی یک فیلد تنظیم شود و می‌توانند زیرattributeهای زیر را داشته باشند:

    • اولین آرگومان موقعیتی پیامی را مشخص می‌کند که به کاربر نمایش داده می‌شود.
    • code کدی را مشخص می‌کند که باید به عنوان جایگزین پیشنهاد شود و یک رشته‌ی قالب است (مثلاً {field_name} با مقدار فیلد field_name ساختار جایگزین می‌شود)، نه یک شناسه‌ی Fluent.
    • از applicability می‌توان برای مشخص کردن قابلیت اعمال در attribute استفاده کرد؛ هنگامی که نوع فیلد شامل یک Applicability باشد نمی‌توان از آن استفاده کرد.

    قابلیت اعمال را می‌توان به صورت یک فیلد (از نوع Applicability) با attribute به نام #[applicability] نیز مشخص کرد.

    در نهایت، derive مربوط به Subdiagnostic یک پیاده‌سازی از Subdiagnostic تولید می‌کند که شبیه زیر است:

    impl<'tcx> Subdiagnostic for ExpectedReturnTypeLabel<'tcx> {
    fn add_to_diag(self, diag: &mut rustc_errors::Diagnostic) {
        use rustc_errors::{Applicability, IntoDiagArg};
        match self {
            ExpectedReturnTypeLabel::Unit { span } => {
                diag.span_label(span, "expected `()` because of default return type")
            }
            ExpectedReturnTypeLabel::Other { span, expected } => {
                diag.set_arg("expected", expected);
                diag.span_label(span, "expected `{$expected}` because of return type")
            }
        }
    }
}

    پس از تعریف، یک subdiagnostic را می‌توان با دادن آن به تابع subdiagnostic (مثال و مثال) روی یک diagnostic یا با اختصاص دادن آن به فیلدی از ساختار diagnostic که با #[subdiagnostic] annotate شده است به کار برد.

    اشتراک و انزوای آرگومان‌ها

    subdiagnosticها پیش از رندر کردن اطلاعات، آرگومان‌های خودشان (یعنی برخی فیلدهای ساختارشان) را به ساختار Diag اضافه می‌کنند. ساختار Diag آرگومان‌های diagnostic اصلی را نیز ذخیره می‌کند، بنابراین subdiagnostic می‌تواند از آرگومان‌های diagnostic اصلی هم استفاده کند.

    با این حال، هنگامی که یک subdiagnostic با پیاده‌سازی #[derive(Subdiagnostic)] به یک diagnostic اصلی افزوده می‌شود، قواعد زیر، که در rust-lang/rust#142724 معرفی شدند، در مدیریت آرگومان‌ها (یعنی متغیرهای استفاده‌شده در پیام‌های Fluent) اعمال می‌شوند:

    انزوای آرگومان بین subdiagnosticها: آرگومان‌هایی که یک subdiagnostic تنظیم می‌کند فقط در طول رندر شدن همان subdiagnostic در دسترس هستند. پس از رندر شدن subdiagnostic، همه‌ی آرگومان‌هایی که معرفی کرده بود از diagnostic اصلی بازیابی می‌شوند. این کار تضمین می‌کند که چند subdiagnostic دامنه‌ی آرگومان‌های یکدیگر را آلوده نمی‌کنند. برای مثال، هنگام استفاده از Vec<Subdiag>، هر subdiagnostic ممکن است همان آرگومان را به طور مکرر اضافه کند.

    بازنویسی آرگومان هم‌نام بین sub و diagnostic اصلی: اگر یک subdiagnostic آرگومانی را با همان نام آرگومانی که قبلاً در diagnostic اصلی هست تنظیم کند، در زمان اجرا خطا گزارش می‌دهد، مگر اینکه هر دو دقیقاً یک مقدار داشته باشند. این دو مزیت دارد:

    • انعطاف‌پذیری آرگومان‌های diagnostic اصلی را برای ظاهر شدن در attributeهای subdiagnostic حفظ می‌کند. برای مثال، attributeای مانند #[suggestion("...", code = "{new_vis}")] در subdiagnostic می‌تواند به new_vis ارجاع دهد، که فیلدی در ساختار diagnostic اصلی است.
    • از بازنویسی یا حذف تصادفی آرگومان‌های موردنیاز diagnostic اصلی یا subdiagnosticهای دیگر جلوگیری می‌کند.

    این قواعد تضمین می‌کنند که آرگومان‌های تزریق‌شده توسط subdiagnosticها کاملاً به رندر شدن خودشان محدود می‌مانند. آرگومان‌های diagnostic اصلی حتی در صورت برخورد نام‌ها از منطق subdiagnostic تأثیری نمی‌پذیرند. علاوه بر این، subdiagnosticها در صورت نیاز می‌توانند به آرگومان‌های هم‌نام diagnostic اصلی دسترسی داشته باشند.

    مرجع #[derive(Subdiagnostic)]

    #[derive(Subdiagnostic)] از attributeهای زیر پشتیبانی می‌کند:

    • #[label("message")]، #[help("message")]، #[warning("message")] یا #[note("message")]
      • روی ساختار یا واریانت شمارش اعمال می‌شود. با attributeهای ساختار/واریانت شمارش دیگر ناسازگار (mutually exclusive) است.
      • اجباری
      • نوع را به عنوان نمایندگی یک label، help یا note تعریف می‌کند.
      • پیام (اجباری)
        • پیام diagnostic که به کاربر نمایش داده می‌شود.
        • مستندات ترجمه را ببینید.
    • #[suggestion("message", code = "...", applicability = "...", style = "...")]
      • روی ساختار یا واریانت شمارش اعمال می‌شود. با attributeهای ساختار/واریانت شمارش دیگر ناسازگار است.
      • اجباری
      • نوع را به عنوان نمایندگی یک suggestion تعریف می‌کند.
      • پیام (اجباری)
        • پیام diagnostic که به کاربر نمایش داده می‌شود.
        • مستندات ترجمه را ببینید.
      • code = "..."/code("...", ...) (اجباری)
        • یک یا چند رشته‌ی قالب که کدی را که باید به عنوان جایگزین پیشنهاد شود نشان می‌دهند. چند مقدار به معنای چند جایگزین ممکن است.
      • applicability = "..." (اختیاری)
        • با #[applicability] روی یک فیلد ناسازگار است.
        • مقدار، قابلیت اعمال پیشنهاد است.
        • رشته‌ای که باید یکی از موارد زیر باشد:
          • machine-applicable
          • maybe-incorrect
          • has-placeholders
          • unspecified
      • style = "..." (اختیاری)
        • مقدار، سبک پیشنهاد است.
        • رشته‌ای که باید یکی از موارد زیر باشد:
          • normal (پیش‌فرض)
          • short
          • hidden
          • verbose
          • tool-only
    • #[multipart_suggestion("message", applicability = "...", style = "...")]
      • روی ساختار یا واریانت شمارش اعمال می‌شود. با attributeهای ساختار/واریانت شمارش دیگر ناسازگار است.
      • اجباری
      • نوع را به عنوان نمایندگی یک پیشنهاد چندبخشی (multipart) تعریف می‌کند.
      • پیام (اجباری): به #[suggestion] مراجعه کنید
      • applicability = "..." (اختیاری): به #[suggestion] مراجعه کنید
      • style = "..." (اختیاری): به #[suggestion] مراجعه کنید
    • #[primary_span] (برای label و suggestion اجباری؛ در غیر این صورت اختیاری؛ برای پیشنهادهای چندبخشی قابل اعمال نیست)
      • روی فیلدهای Span اعمال می‌شود.
      • span اصلی subdiagnostic را مشخص می‌کند.
    • #[suggestion_part(code = "...")] (اجباری؛ فقط برای پیشنهادهای چندبخشی قابل اعمال است)
      • روی فیلدهای Span اعمال می‌شود.
      • مشخص می‌کند که span یک بخش از پیشنهاد چندبخشی است.
      • code = "..." (اجباری)
        • مقدار، یک رشته‌ی قالب است که کدی را که باید به عنوان جایگزین پیشنهاد شود نشان می‌دهد.
    • #[applicability] (اختیاری؛ فقط برای پیشنهادها (ساده و چندبخشی) قابل اعمال است)
      • روی فیلدهای Applicability اعمال می‌شود.
      • قابلیت اعمال پیشنهاد را مشخص می‌کند.
