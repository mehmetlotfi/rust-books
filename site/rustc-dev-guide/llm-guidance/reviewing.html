    بازبینی با LLMها

    استفاده از LLM برای بازبینی کد

    • اگر ابزار قابل‌اعتمادتری مثل linter یا formatter از قبل برای زبانی که می‌نویسید وجود دارد، قویاً پیشنهاد می‌کنیم از آن ابزار به‌جای LLM یا همراه آن استفاده کنید.
    • ابزارهای بازبینی LLM را پیکربندی کنید تا مثبت‌های کاذب و تمرکز بیش‌ازحد بر جزئیات بی‌اهمیت کم شود، چون این‌ها حالت‌های شکست رایج و خسته‌کننده‌اند.
    • هر جا ممکن است از LLM بخواهید یک linter تولید یا پیکربندی کند و سپس به آن بگویید آن را اجرا کند. این هم هزینهٔ توکن را کم می‌کند و هم به افرادی که از LLM استفاده نمی‌کنند اجازه می‌دهد تحلیل را اجرا کنند. برای مثال، اگر wrapper مخصوص codebase دارید که اجرای دستورها را در بر می‌گیرد، به‌جای اینکه از LLM بخواهید جاهایی را بیابد که باید از wrapper استفاده کنید، clippy را طوری پیکربندی کنید که Command::new را ممنوع کند.
    • LLMها گاهی خروجی تولیدشده با LLM را ترجیح می‌دهند، به‌ویژه خروجی همان مدل. بازبینی LLM را مشورتی بدانید، و به مدلی که تغییر را تولید کرده به‌عنوان تنها بازبین آن تکیه نکنید.

    Reviewing LLM-created code

    ابتدا برچسب جدید llm-assisted را به PR اضافه کنید.

    Rules

    انتظار داریم همه، نه فقط نویسندگان، از سیاست جدید پیروی کنند. یعنی مسئولیت شماست بررسی کنید آیا PR با برچسب llm-assisted به حوزه‌ای می‌خورد که سیاست آن را ممنوع کرده است. می‌توانید از نویسنده بخواهید بدون کد تولیدشده با LLM دوباره انجام دهد، که در آن صورت این بخش اعمال نمی‌شود.

    حوزه‌های زیر فعلاً ممنوع‌اند:

    • کدی که بر soundness اثر می‌گذارد. اگر نویسنده عضو سازمان با تجربه در آن حوزه نباشد، موظفید PR را ببندید.
    • پیام‌های تشخیصی. همهٔ پیام‌های تشخیصی رو به کاربر باید با دست انسان نوشته شوند.
    • مستندات. همهٔ doc-commentهای عمومی و همهٔ کامنت‌های // SAFETY باید با دست انسان نوشته شوند.

    «کدی که بر soundness اثر می‌گذارد» هم گسترده‌تر و هم محدودتر از آن چیزی است که به نظر می‌رسد. گسترده‌تر است چون تقریباً همهٔ کامپایلر به soundness مربوط است؛ محدودتر است چون بخش قابل‌توجهی از rust-lang/rust کامپایلر نیست (کتابخانه، bootstrap، compiletest، rustdoc، CI، …).

    در صورت تردید این معیار را پیشنهاد می‌کنیم: برای بخش‌هایی از کامپایلر که کد اشتباه اشتباه به نظر نمی‌رسد اجازهٔ کد تولیدشده با LLM ندهید. در نهایت این به قضاوت شما به‌عنوان بازبین بستگی دارد.

    همچنان انتظار می‌رود به حقوق r+ خود احترام بگذارید. لطفاً PRها را merge نکنید مگر به آن بخش از آن کد اطمینان داشته باشید، حتی اگر نگه‌دارنده نخواهد PRهای LLM را بازبینی کند.

    Guidelines

    افراد را آزادانه به #llm-mentoring ارجاع دهید. با PRهای کم‌کیفیت با بستن PR و درخواست از نویسنده برای پیروی از سیاست برخورد کنید. با PRهای مرزی با درخواست از نویسنده برخورد کنید که خودش کار را انجام دهد، نه اینکه آن را به شما واگذار کند. برای مثال از آن‌ها بخواهید باگ را بازتولید کنند، تغییر را با کلمات خودشان توضیح دهند، حالت‌های لبهٔ مرتبط را شناسایی کنند، یا تست اضافه یا توجیه کنند.

    اگر دیدید در چند PR یک رفع را پیشنهاد می‌کنید، افزودن آن‌ها به dev-guide را در نظر بگیرید.

    Missing disclosure

    اگر PRای را می‌بینید که «آشکارا» با LLM ساخته شده اما استفاده را اعلام نکرده، اختیار دارید — اما مسئولیتی ندارید — آن را به‌طور یک‌جانبه ببندید.

    پیشنهاد می‌کنیم از این عبارت‌بندی استفاده کنید:

    This PR appears to be LLM-generated without disclosing use of an LLM, so I am going to close this PR.
You are welcome to open additional PRs as long as they follow our [policy][forge-page].
For more information, see [#llm-mentoring] on Zulip.

[#llm-mentoring]: https://rust-lang.zulipchat.com/join/rlfvpemsaacs3pfi6kwqnqjb/
[forge-page]: https://forge.rust-lang.org/policies/llm-usage.html

    نمونه‌هایی از نشانه‌های «آشکار» LLM:

    • توضیحات PR که کاملاً اشتباه‌اند/با کد جور نیستند.
    • توضیحات PR که دقیقاً تست‌های اجراشده را می‌گویند (مثلاً ./x test --stage 1 tests/ui/<the-new-test-name>.rs) یا تست‌های بی‌فایده مثل git diff --check.
    • پاسخ به پرسش‌های بازبین که در یکی از دسته‌های بالا قرار می‌گیرند.

    تعهدی ندارید PRهای ساخته‌شده با LLM را تشخیص دهید؛ لازم نیست کارآگاه بازی کنید.

    قالب‌های PR پرسش «آیا از LLM استفاده کردید؟» را خواهند داشت تا این به‌ندرت پیش بیاید. اگر نویسنده پرسش را بدون پاسخ حذف کرده باشد، می‌توانید PR را ببندید، بدون پرسش.

    Missing solicited reviewer

    اگر PR استفاده را اعلام می‌کند اما طبق رهنمودهای آزمایش بازبین تعیین نمی‌کند، می‌توانید آن را به همین شکل ببندید:

    You've opened an LLM-generated PR, but it's in the normal review queue, which breaks our [policy][experiment guidelines].
I am going to close this PR.
Please do not re-open it until you find a project member who has volunteered to review it.
For more information, see [#llm-mentoring] on Zulip.

[#llm-mentoring]: https://rust-lang.zulipchat.com/join/rlfvpemsaacs3pfi6kwqnqjb/
[forge-page]: https://forge.rust-lang.org/policies/llm-usage.html

    تست ناموجود، کم‌کیفیت، یا بازبینی‌نشده توسط خود نویسنده

    اگر PRای آشکارا برای بازبینی آماده نیست، لازم نیست بازبینی‌اش کنید. اشکالی ندارد PR را فقط سرسری بخوانید و به نویسنده بگویید «پیش از اینکه بتوانم این را بازبینی کنم باید تست اضافه کنید». اگر در مرور سرسری متوجه شدید PR آشکارا رویکرد اشتباهی دارد، اشکالی ندارد PR را ببندید و به نویسنده بگویید پیش از باز‌کردن PR جدید در کانال #llm-mentoring با شما صحبت کند.
