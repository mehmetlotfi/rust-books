راهنمای توسعهٔ rustcrustc Development Guide

    Writing LLM-created code

    LLMها ابزار ارزشمندی هستند، اما ابزاری که سوءاستفاده از آن آسان است. خطرهای اصلی حجم طاقت‌فرسا و نبود درک هستند. هنگام نوشتن PR خود به یاد داشته باشید که در آن سو شخصی هست که باید تغییر شما را بازبینی و درک کند، و اینکه افراد دیگر در پروژه سال‌ها باید کد شما را بخوانند. با کوچک، هدفمند و باکیفیت نگه‌داشتن تغییرتان به ما کمک کنید.

    این نقل‌قول را به یاد داشته باشید:

    برنامه‌ها باید برای خوانده‌شدن توسط انسان‌ها نوشته شوند، و فقط به‌طور اتفاقی برای اجرا توسط ماشین‌ها. — هارولد آبلسون و جرالد جی ساسمن، ساختار و تفسیر برنامه‌های کامپیوتری

    Rules

    پیش از نوشتن کد

    پیش از هر چیز، بازبینی پیدا کنید که داوطلب بازبینی PR شما شود. اگر نمی‌دانید بازبین را کجا بیابید، در #llm-mentoring در Zulip بپرسید. پیام اول شما باید این‌ها را بگوید:

    • تجربهٔ مرتبط شما، تا بتوانیم issue مناسبی برایتان بیابیم
    • روی کدام مسئله (یا نوع مسئله) می‌خواهید کار کنید
    • (اختیاری) ایده‌هایی که تا اینجا برای راه‌حل دارید
    • (اختیاری) انتظار دارید راه‌حل خود را چگونه تست کنید

    mentorها اینجا هستند که کمک کنند. صحبت زودهنگام با آن‌ها از هدررفتن کارتان جلوگیری می‌کند.

    While working

    doc-commentها، کامنت‌های // SAFETY، متن پیام‌های تشخیصی و کد حیاتی برای soundness را خودتان بنویسید. مثل قبل، می‌توانید از LLM برای بازبینی کارتان استفاده کنید، اما نه برای نوشتن آن از ابتدا. اگر نمی‌دانید چه چیزی حیاتی برای soundness به حساب می‌آید، با بازبین خود در میان بگذارید.

    هنگام باز‌کردن PR

    استفاده از LLM را طبق رهنمودهای افشا در ادامه اعلام کنید. اعلام را خودتان بنویسید. می‌توانید از LLM برای بازبینی خصوصی اعلامی که خودتان نوشته‌اید استفاده کنید، اما نه برای پیش‌نویس یا بازنویسی آن.

    توضیحات و کامنت‌های PR خود را خودتان بنویسید. می‌خواهیم از شما بشنویم، نه از agent شما. توضیحات PR تولیدشده با LLM ممنوع است. کامنت‌های GitHub تولیدشده با LLM ممنوع است.

    Guidelines

    پیش از نوشتن کد

    با یک PR در هر زمان شروع کنید. تغییرات را آن‌قدر کوچک نگه دارید که شما و بازبینتان همهٔ بخش‌های آن را بفهمید. آرام پیش بروید.

    برای issueهای E-easy از LLM استفاده نکنید؛ این‌ها برای این‌اند که خودتان کد را بنویسید. پیش از کار روی issue با E-mentor ابتدا بپرسید؛ ممکن است mentorها نخواهند با کد تولیدشده با LLM کار کنند.

    تعیین کنید این تغییر مفید و با دامنهٔ مناسب است یا نه. برای مثال:

    • issueها و PRهای مرتبط را جست‌وجو کنید.
    • کد، تست‌ها، تاریخچهٔ git و گفت‌وگوهای Zulip مرتبط را بیابید.
    • اگر تغییر چندجانبه است، راهنمای pull request را مطالعه کنید.
    • کوچک‌ترین تغییری را بدهید که مشکل را رفع می‌کند. آن را با بازآرایی‌ها یا پاک‌سازی‌های نامرتبط ترکیب نکنید.

    While working

    هنگام رفع باگ، تأیید کنید تست شما پیش از تغییر شکست و پس از آن موفق می‌شود. برای روال تست افزودن تست‌های جدید و بهترین روش‌ها را ببینید. تست‌ها کاملاً الزامی‌اند؛ چه تست‌های موجود و چه تست‌های جدیدی که می‌نویسید. PRهای LLM بدون تست merge نمی‌شوند.

    بازنام‌گذاری‌ها یا بازنویسی‌های انبوه باید قویاً ترجیح دهند از ابزار درست بازنویسی نحو استفاده کنند، مثل ast-grep. می‌توانید از LLM برای تولید دستورالعمل آن ابزار استفاده کنید، اما باید بسیار محتاط باشید که بازنویسی را مستقیماً با LLM انجام دهید.

    هنگام نوشتن عملکرد را در نظر بگیرید.

    پیش از افزودن وابستگی‌ها فکر کنید؛ راهنمای وابستگی‌های جدید ما را مطالعه کنید.

    درک خود را با کد، مستندات و تست‌های موجود بسنجید. می‌توانید با گفتن به LLM که مواد مرتبط را بخواند توصیه بهتری از آن بگیرید. به LLM به‌عنوان منبع حقیقت تکیه نکنید.

    Write maintainable code

    کد تولیدشده را پیش‌نویس بدانید، نه محصول نهایی. قراردادهای درستی و نگه‌داشت‌پذیری ما را دنبال کنید.

    از انتزاع‌ها و لایه‌های سازگاری غیرضروری پرهیز کنید. Rustc API پایدار ندارد؛ لازم نیست برای APIهای داخلی کامپایلر سازگاری رو‌به‌عقب را حفظ کنید.

    Commit structure

    «چگونه PR خود را ساختار دهیم» را ببینید. پیام‌های commit باید توسط شما نوشته شوند، نه LLM شما.

    پیش از باز‌کردن PR

    PR خود را پیش از باز‌کردن بازبینی کنید: آیا معنا دارد؟ آیا می‌توانید بگویید هدف PR چیست؟ آیا به آن هدف می‌رسد؟

    کد منسوخ یا نمونه‌سازی و اشکال‌زدایی را حذف کنید.

    کل diff را دوباره بخوانید، نه فقط گفت‌وگوی خود با agent را. بازبین شما کد شما را می‌بیند، نه گفت‌وگوی شما را.

    تست‌ها را اجرا کنید تا تأیید کنید تغییر شما کار می‌کند. در توضیحات PR گزارش نکنید کدام تست‌های UI را اجرا کرده‌اید؛ این نویز است، چون CI به هر حال آن‌ها را اجرا می‌کند. اگر تست دستی یا benchmark انجام داده‌اید، آن را گزارش کنید، اما توجه کنید همهٔ PRهای LLM باید تست خودکار داشته باشند.

    snapshotهای پیام‌های تشخیصی را بازبینی کنید؛ آن‌ها را صرفاً با --bless کنار نگذارید.

    توصیه می‌کنیم پیش از انتشار تغییرات خود برای بازبینی محلی خصمانه از مدل دیگری استفاده کنید. شما همچنان مسئول بازبینی خودتان از تغییرات خودتان هستید.

    تغییر خودتان را بفهمید

    می‌خواهیم تغییر خود و حالت‌های لبه‌اش را بفهمید و بتوانید توضیح دهید. پرسیدن از LLM می‌تواند نقطهٔ شروع باشد اما با توضیح‌دادن خودتان یکی نیست.

    پیش از باز‌کردن PR سعی کنید تغییر خود را به خودتان توضیح دهید. برای مثال از خود بپرسید:

    • باگ اصلی چیست؟ چه وقت رخ می‌دهد؟ چقدر شدید است؟ چه چیزی باعث آن می‌شود؟
    • چرا این رفع درست است؟ آیا رفع‌های دیگری ممکن است؟ مزایا یا معایب آن‌ها چیست؟
    • آیا حالت لبه‌ای هست؟ آیا کد شما آن‌ها را مدیریت می‌کند؟
    • آیا کد پایاهای (invariant) موجود دارد؟ آیا آن پایاها را حفظ کرده‌اید؟
    • چه رفتاری بدون تغییر است؟ کدام تست آن را تثبیت می‌کند؟
    • چرا تست شما باگ را فعال می‌کند؟
    • هنوز دربارهٔ چه چیزی مطمئن نیستید؟

    اشکالی ندارد مطمئن نباشید و کمک بخواهید. خیلی ترجیح می‌دهیم چون مطمئن نیستید کمکتان کنیم تا اینکه حدس اشتباه بزنید و بعد مجبور شویم مهندسی معکوس کنیم کجا اشتباه کرده‌اید.

    Disclosure guidelines

    میزان و هدف استفاده از LLM را اعلام کنید. برایمان مهم نیست از کدام مدل استفاده کرده‌اید، اما مهم است که از LLM برای پیاده‌سازی ایده استفاده کرده‌اید یا برای ابداع آن.

    Good examples:

    اعلام LLM: سه commit را پس از مشاهدهٔ داده‌های profiling دستی نوشتم. پیش از ارسال از LLM برای بازبینی commitها استفاده کردم. LLM تشخیص داد ImplString::is_negative دیگر استفاده نمی‌شود، پس آن فیلد را دستی حذف کردم.

    با کمک LLM ساخته شد، که:

    • با بررسی سرایندهای Fastly در برابر CloudFront، cache missها را تا return(pass) بی‌قیدوشرط ردیابی کرد،
    • تاریخچهٔ git را بازبینی کرد تا بفهمد چرا آن تکه اضافه شده بود، و
    • تغییر VCL را اعمال کرد.
