    Name resolution

    در فصل‌های قبل دیدیم درخت نحو انتزاعی (AST) چگونه با گسترش همهٔ ماکروها ساخته می‌شود. دیدیم انجام این کار مستلزم مقداری name resolution برای حل importها و نام ماکروهاست. در این فصل نشان می‌دهیم این در واقع چگونه انجام می‌شود و بیشتر.

    در واقع، در گسترش ماکرو name resolution کامل انجام نمی‌دهیم – فقط importها و ماکروها را در آن زمان حل می‌کنیم. این لازم است تا بدانیم اصلاً چه چیزی را گسترش دهیم. بعداً، پس از داشتن کل AST، name resolution کامل را برای حل همهٔ نام‌های crate انجام می‌دهیم. این در rustc_resolve::late رخ می‌دهد. برخلاف گسترش ماکرو، در این گسترش دیرهنگام، فقط لازم است یک بار سعی کنیم نامی را حل کنیم، چون نام جدیدی افزوده نمی‌شود. اگر حل نام شکست بخورد، خطای کامپایلر است.

    Name resolution پیچیده است. فضاهای نام مختلفی هست (مثلاً ماکروها، مقادیر، نوع‌ها، طول‌عمرها)، و نام‌ها ممکن است در scopeهای (تو در توی) مختلف معتبر باشند. همچنین انواع مختلف نام می‌توانند به شکل‌های متفاوتی در حل شکست بخورند و شکست‌ها در scopeهای مختلف به شکل‌های متفاوتی رخ می‌دهند. برای مثال، در scope ماژول، شکست یعنی هیچ ماکروی گسترش‌نیافته و هیچ import سراسری (glob) حل‌نشده‌ای در آن ماژول نیست. از طرف دیگر، در scope بدنهٔ تابع، شکست مستلزم این است که نام در بلوکی که در آن هستیم، همهٔ scopeهای بیرونی و scope سراسری وجود نداشته باشد.

    Basics

    در برنامه‌های خود با دادن نام به متغیرها، نوع‌ها، توابع و غیره به آن‌ها ارجاع می‌دهیم. این نام‌ها همیشه یکتا نیستند. برای مثال، این برنامهٔ معتبر Rust را در نظر بگیرید:

    type x = u32;
let x: x = 1;
let y: x = 2;

    از کجا بدانیم در خط ۳ x یک نوع (u32) است یا یک مقدار (1)؟ این تعارض‌ها در name resolution حل می‌شوند. در این مورد مشخص، name resolution تعریف می‌کند که نام‌های نوع و نام‌های متغیر در فضاهای نام جداگانه زندگی می‌کنند و بنابراین می‌توانند هم‌زیستی داشته باشند.

    Name resolution در Rust فرایندی دوفازی است. در فاز اول، که در گسترش macro اجرا می‌شود، درختی از ماژول‌ها می‌سازیم و importها را حل می‌کنیم. گسترش ماکرو و name resolution از طریق trait با نام ResolverAstLoweringExt با هم ارتباط دارند.

    ورودی فاز دوم درخت نحو است که با تجزیهٔ فایل‌های ورودی و گسترش macros تولید می‌شود. این فاز پیوندهایی از همهٔ نام‌ها در منبع به مکان‌های مرتبطی که نام در آن‌ها معرفی شده تولید می‌کند. همچنین پیام‌های خطای مفیدی تولید می‌کند، مثل پیشنهاد غلط تایپی، traitهایی که باید import شوند یا lint دربارهٔ آیتم‌های استفاده‌نشده.

    اجرای موفق فاز دوم (Resolver::resolve_crate) نوعی فهرست ایجاد می‌کند که بقیهٔ کامپایل می‌تواند برای پرسش دربارهٔ نام‌های موجود به‌کار ببرد (از طریق رابط hir::lowering::Resolver).

    Name resolution در crate با نام rustc_resolve قرار دارد، با بخش عمدهٔ آن در lib.rs و برخی کمک‌کننده‌ها یا منطق مخصوص نوع نماد در ماژول‌های دیگر.

    Namespaces

    انواع مختلف نماد در فضاهای نام مختلف زندگی می‌کنند ‒ مثلاً نوع‌ها با متغیرها تعارض ندارند. این معمولاً رخ نمی‌دهد، چون متغیرها با حرف کوچک شروع می‌شوند و نوع‌ها با حرف بزرگ، اما این فقط یک قرارداد است. این کد معتبر Rust است که کامپایل می‌شود (با هشدار):

    type x = u32;
let x: x = 1;
let y: x = 2; // See? x is still a type here.

    برای مقابله با این، و با قواعد scope کمی متفاوت این فضاهای نام، resolver آن‌ها را جدا نگه می‌دارد و ساختارهای جداگانه‌ای برایشان می‌سازد.

    به عبارت دیگر، وقتی کد دربارهٔ فضاهای نام صحبت می‌کند، منظورش سلسله‌مراتب ماژول نیست، نوع‌ها در برابر مقادیر در برابر ماکروهاست.

    Scopeها و ribها

    یک نام فقط در ناحیهٔ مشخصی از کد منبع دیده می‌شود. این ساختاری سلسله‌مراتبی می‌سازد، اما لزوماً ساده نیست ‒ اگر یک scope بخشی از scope دیگر باشد، لزوماً یعنی نامی که در scope بیرونی دیده می‌شود در scope درونی هم دیده می‌شود، یا به همان چیز ارجاع می‌دهد.

    برای مقابله با این، کامپایلر مفهومی به نام Rib را معرفی می‌کند. این انتزاعی از یک scope است. هر بار که مجموعهٔ نام‌های دیدنی احتمالاً تغییر کند، یک Rib جدید روی پشته گذاشته می‌شود. جاهایی که این می‌تواند رخ دهد برای مثال شامل این‌هاست:

    • جاهای بدیهی ‒ آکولادهای دربرگیرندهٔ بلوک، مرزهای تابع، ماژول‌ها.
    • معرفی binding با let ‒ این می‌تواند binding دیگری با همان نام را سایه (shadow) کند.
    • مرز گسترش ماکرو ‒ برای مقابله با hygiene ماکرو.

    هنگام جست‌وجوی یک نام، پشتهٔ ribs از درونی‌ترین به سمت بیرون پیمایش می‌شود. این به یافتن نزدیک‌ترین معنای نام کمک می‌کند (آنکه چیز دیگری سایه‌اش نکرده). انتقال به Rib بیرونی ممکن است بر اینکه چه نام‌هایی قابل‌استفاده‌اند هم اثر بگذارد ‒ اگر توابع تو در تو باشند (نه closureها)، تابع درونی نمی‌تواند به پارامترها و bindingهای محلی تابع بیرونی دسترسی داشته باشد، هرچند طبق قواعد معمول scope باید دیده شوند. یک مثال:

    fn do_something<T: Default>(val: T) { // <- New rib in both types and values (1)
    // `val` is accessible, as is the helper function
    // `T` is accessible
   let helper = || { // New rib on the block (2)
        // `val` is accessible here
    }; // End of (2), new rib on `helper` (3)
    // `val` is accessible, `helper` variable shadows `helper` function
    fn helper() { // <- New rib in both types and values (4)
        // `val` is not accessible here, (4) is not transparent for locals
        // `T` is not accessible here
    } // End of (4)
    let val = T::default(); // New rib (5)
    // `val` is the variable, not the parameter here
} // End of (5), (3) and (1)

    چون قواعد فضاهای نام مختلف کمی متفاوت است، هر فضای نام پشتهٔ Rib مستقل خودش را دارد که به‌موازات بقیه ساخته می‌شود. علاوه بر این، پشتهٔ Rib برای برچسب‌های محلی (مثلاً نام حلقه‌ها یا بلوک‌ها) هم هست، که فضای نام کامل مستقل نیست.

    Overall strategy

    برای انجام name resolution کل crate، درخت نحو از بالا به پایین پیمایش می‌شود و هر نام برخوردشده حل می‌شود. این برای بیشتر انواع نام کار می‌کند، چون در نقطهٔ استفاده از نام، قبلاً در سلسله‌مراتب Rib معرفی شده است.

    چند استثنا برای این هست. آیتم‌ها کمی دشوارند، چون می‌توانند پیش از برخورد هم استفاده شوند ‒ بنابراین هر بلوک باید ابتدا برای آیتم‌ها اسکن شود تا Rib آن پر شود.

    موارد دیگر که حتی مشکل‌سازترند importها هستند که به حل بازگشتی نقطهٔ ثابت (fixed-point) نیاز دارند و ماکروها، که باید پیش از پردازش بقیهٔ کد حل و گسترش شوند.

    بنابراین حل در چند مرحله انجام می‌شود.

    Speculative crate loading

    برای دادن خطاهای مفید، rustc پیشنهاد می‌دهد مسیرها را به scope import کنید اگر یافت نشوند. چگونه این کار را می‌کند؟ هر ماژول از هر crate را مرور می‌کند و دنبال تطابق‌های ممکن می‌گردد. این حتی crateهایی را که هنوز بارگذاری نشده‌اند هم شامل می‌شود!

    بارگذاری eager crateها برای گنجاندن پیشنهادهای import که هنوز بارگذاری نشده‌اند بارگذاری تخمینی crate (speculative crate loading) نامیده می‌شود، چون هر خطایی که با آن روبه‌رو شود نباید گزارش شود: rustc_resolve تصمیم گرفت آن‌ها را بارگذاری کند، نه کاربر. تابعی که این کار را می‌کند lookup_import_candidates است و در rustc_resolve::diagnostics قرار دارد.

    برای تشخیص بارگذاری‌های تخمینی از بارگذاری‌های آغازشده توسط کاربر، rustc_resolve پارامتری به نام record_used دست‌به‌دست می‌کند که وقتی بارگذاری تخمینی است false است.
