    پروفایل‌کردن کامپایلر

    این بخش دربارهٔ نحوهٔ پروفایل‌کردن کامپایلر و یافتن اینکه زمانش را کجا صرف می‌کند است.

    بسته به آنچه می‌خواهید اندازه بگیرید، چند رویکرد مختلف هست:

    • اگر می‌خواهید ببینید یک PR عملکرد کامپایلر را بهبود می‌دهد یا بدتر می‌کند، برای درخواست اجرای benchmark فصل rustc-perf را ببینید.

    • اگر می‌خواهید نمای کلی سطح متوسط تا بالا از اینکه rustc زمانش را کجا صرف می‌کند داشته باشید:

      • پرچم -Z self-profile و ابزارهای measureme رویکردی مبتنی بر کوئری برای پروفایل‌کردن ارائه می‌دهند. برای اطلاعات بیشتر مستندات آن‌ها را ببینید.

    • اگر داده‌های عملکرد در سطح تابع یا حتی جزئیات بیشتر از رویکردهای بالا می‌خواهید:

      • استفاده از پروفایلر کد بومی مثل perf را در نظر بگیرید
      • یا tracy برای رابط گرافیکی کامل با دقت نانوثانیه.

    • اگر می‌خواهید نمایش بصری زیبایی از زمان‌های کامپایل گراف crateهای خود داشته باشید، می‌توانید از پرچم --timings در cargo استفاده کنید، مثلاً cargo build --timings. می‌توانید این پرچم را روی خود کامپایلر هم با ./x build compiler --timings به‌کار ببرید

    • اگر می‌خواهید مصرف حافظه را پروفایل کنید، بسته به سیستم‌عاملی که استفاده می‌کنید می‌توانید از ابزارهای مختلف بهره ببرید.

      • برای ویندوز، راهنمای WPA ما را بخوانید.

    بهینه‌سازی زمان bootstrap در rustc با cargo-llvm-lines

    با cargo-llvm-lines می‌توانید تعداد خطوط LLVM IR را در همهٔ نمونه‌سازی‌های یک تابع جنریک بشمارید. چون بیشتر زمان کامپایل rustc در LLVM صرف می‌شود، ایده این است که با کاهش مقدار کدی که به LLVM داده می‌شود، کامپایل rustc سریع‌تر شود.

    برای استفاده از cargo-llvm-lines همراه با فرایند ساخت تا حدی سفارشی rustc، می‌توانید از -C save-temps برای گرفتن LLVM IR لازم استفاده کنید. این گزینه محصولات کاری موقتی را که هنگام کامپایل ساخته می‌شوند حفظ می‌کند. در میان آن‌ها LLVM IR است که ورودی پایپ‌لاین بهینه‌سازی را نشان می‌دهد؛ برای هدف ما ایده‌آل است. در فایل‌هایی با پسوند *.no-opt.bc با قالب bitcode در LLVM ذخیره می‌شود.

    Example usage:

    cargo install --locked cargo-llvm-lines
# On a normal crate you could now run `cargo llvm-lines`, but `x` isn't normal :P

# Do a clean before every run, to not mix in the results from previous runs.
./x clean
env RUSTFLAGS=-Csave-temps ./x build --stage 0 compiler/rustc

# Single crate, e.g., rustc_middle. (Relies on the glob support of your shell.)
# Convert unoptimized LLVM bitcode into a human readable LLVM assembly accepted by cargo-llvm-lines.
for f in build/x86_64-unknown-linux-gnu/stage0-rustc/x86_64-unknown-linux-gnu/release/deps/rustc_middle-*.no-opt.bc; do
  ./build/x86_64-unknown-linux-gnu/llvm/bin/llvm-dis "$f"
done
cargo llvm-lines --files ./build/x86_64-unknown-linux-gnu/stage0-rustc/x86_64-unknown-linux-gnu/release/deps/rustc_middle-*.ll > llvm-lines-middle.txt

# Specify all crates of the compiler.
for f in build/x86_64-unknown-linux-gnu/stage0-rustc/x86_64-unknown-linux-gnu/release/deps/*.no-opt.bc; do
  ./build/x86_64-unknown-linux-gnu/llvm/bin/llvm-dis "$f"
done
cargo llvm-lines --files ./build/x86_64-unknown-linux-gnu/stage0-rustc/x86_64-unknown-linux-gnu/release/deps/*.ll > llvm-lines.txt

    چون به نظر می‌رسد این با کامپایل افزایشی یا ./x check کار نمی‌کند، باید بارها rustc را کامپایل کنید. توصیه می‌کنم چند تنظیم را در bootstrap.toml تغییر دهید تا قابل‌تحمل شود:

    # A debug build takes _a third_ as long on my machine,
# but compiling more than stage0 rustc becomes unbearably slow.
rust.optimize = false

# We can't use incremental anyway, so we disable it for a little speed boost.
rust.incremental = false
# We won't be running it, so no point in compiling debug checks.
rust.debug = false

# Using a single codegen unit gives less output, but is slower to compile.
rust.codegen-units = 0  # num_cpus

    خروجی llvm-lines تحت‌تأثیر چند گزینه است. rust.optimize = false آن را از 2.1GB به 3.5GB و codegen-units = 0 آن را به 4.1GB افزایش می‌دهد.

    بهینه‌سازی‌های MIR اثر کمی دارند. در مقایسه با پیش‌فرض RUSTFLAGS="-Z mir-opt-level=1"، سطح 0 مقدار 0.3GB می‌افزاید و سطح 2 مقدار 0.2GB کم می‌کند. تا ژوئیهٔ 2022، inlining در backendهای تولید کد LLVM و GCC انجام می‌شود، و فقط در Cranelift وجود ندارد.
