راهنمای توسعهٔ rustcrustc Development Guide

    روال‌های تغییرات شکننده

    این صفحه روال بهترین روش را برای انجام رفع باگ یا اصلاحات soundness در کامپایلر تعریف می‌کند که ممکن است باعث شود کد موجود دیگر کامپایل نشود. این متن بر اساس RFC 1589 است.

    Motivation

    گاه‌به‌گاه نیاز به رفع باگ، اصلاح soundness یا تغییر دیگری در کامپایلر پیدا می‌کنیم که باعث می‌شود کد موجود دیگر کامپایل نشود. وقتی این رخ می‌دهد، مهم است تغییر را طوری مدیریت کنیم که انتقال هموار برای کاربران Rust فراهم شود. آنچه می‌خواهیم از آن پرهیز کنیم این است که برنامه‌های موجود ناگهان با پیام‌های خطای مبهم کامپایل نشوند: ترجیح می‌دهیم دورهٔ تدریجی هشدار داشته باشیم، با راهنمایی روشن دربارهٔ مشکل چیست، چگونه رفع می‌شود و چرا تغییر انجام شد. این RFC روالی را شرح می‌دهد که برای مدیریت تغییرات شکننده توسعه داده‌ایم و هدفش دستیابی به چنین انتقال همواری است.

    یکی از نکات کلیدی این سیاست این است که (الف) در صورت امکان باید ابتدا هشدار صادر شود نه خطای سخت و (ب) هر تغییری که باعث شود کد موجود دیگر کامپایل نشود یک issue پیگیری متناظر خواهد داشت. این issue نقطه‌ای برای جمع‌آوری بازخورد دربارهٔ نتایج آن تغییر فراهم می‌کند. گاهی تغییرات پیامدهای غیرمنتظرهٔ بزرگ دارند یا ممکن است راهی برای پرهیز از تغییر باشد که در نظر گرفته نشده بود. در آن موارد، ممکن است تصمیم بگیریم مسیر را عوض کنیم و تغییر را برگردانیم، یا راه‌حل دیگری بیابیم (و اگر از هشدار استفاده می‌شود، انجام این کار به‌ویژه آسان است).

    چه چیزی رفع باگ به حساب می‌آید؟

    توجه کنید این RFC سعی نمی‌کند تعریف کند چه وقت تغییر شکننده مجاز است. آن از قبل تحت RFC 1122 پوشش داده شده است. این سند فرض می‌کند تغییری که انجام می‌شود مطابق آن سیاست‌هاست. در ادامه خلاصه‌ای از شرایط RFC 1122 آمده است:

    • تغییرات soundness: رفع حفره‌هایی که در سامانهٔ نوع کشف شده‌اند.
    • باگ‌های کامپایلر: جاهایی که کامپایلر معناشناسی مشخص‌شده در یک RFC یا تصمیم تیم lang را پیاده‌سازی نمی‌کند.
    • معناشناسی کم‌مشخص زبان: روشن‌سازی نواحی خاکستری که کامپایلر در آن‌ها ناسازگار رفتار می‌کند و پیش‌تر رفتار رسمی‌ای تصمیم‌گیری نشده بود.

    لطفاً برای جزئیات کامل RFC را ببینید!

    Detailed design

    روال انجام تغییر شکننده به این شرح است (هر یک از این گام‌ها در ادامه با جزئیات بیشتر شرح داده شده):

    1. یک اجرای crater برای ارزیابی اثر تغییر انجام دهید.
    2. یک issue پیگیری ویژه برای تغییر بسازید.
    3. Do not report an error right away. Instead, issue forwards-compatibility lint warnings.
      • گاهی این ساده نیست. متن زیر را برای پیشنهادهایی دربارهٔ تکنیک‌های مختلفی که در گذشته به‌کار برده‌ایم ببینید.
      • For cases where warnings are infeasible:
        • خطاها را گزارش دهید، اما تمام تلاش را بکنید پیام خطای هدفمندی بدهید که کاربران را به issue پیگیری هدایت کند
        • Submit PRs to all known affected crates that fix the issue
          • یا دست‌کم صاحبان آن crateها را از مشکل مطلع کنید و آن‌ها را به issue پیگیری هدایت کنید
    4. وقتی تغییر دست‌کم یک چرخه در دنیای واقعی بوده، می‌توانیم تغییر را پایدار کنیم و آن هشدارها را به خطا تبدیل کنیم.

    در نهایت، برای تغییرات rustc_ast که بر پلاگین‌ها اثر می‌گذارد، سیاست عمومی دسته‌بندی‌کردن این تغییرات است. این در ادامه با جزئیات بیشتر بحث می‌شود.

    Tracking issue

    هر تغییر شکننده باید همراه یک issue پیگیری اختصاصی برای آن تغییر باشد. متن اصلی این issue باید تغییری را که انجام می‌شود توصیف کند و بر آنچه کاربران باید برای رفع کدشان انجام دهند تمرکز داشته باشد. issue باید قابل‌فهم و عملی باشد؛ ممکن است منطقی باشد کاربران را برای جزئیات کامل به RFC یا issue دیگری هدایت کنید. issue همچنین جایی است که کاربران می‌توانند پرسش‌ها یا نگرانی‌های دیگر را کامنت کنند.

    قالبی برای این issueهای پیگیری تغییر شکننده را اینجا می‌یابید. مثالی از اینکه چنین issueای چگونه باید به نظر برسد را اینجا می‌یابید.

    صدور هشدارهای سازگاری آینده

    بهترین راه مدیریت تغییر شکننده شروع با صدور هشدارهای سازگاری آینده است. این‌ها دستهٔ ویژه‌ای از هشدارهای lint هستند. افزودن هشدار سازگاری آینده جدید را می‌توان این‌طور انجام داد.

    // 1. Define the lint in `compiler/rustc_lint/src/builtin.rs` and
//    add the metadata for the future incompatibility:
declare_lint! {
    pub YOUR_LINT_HERE,
    Warn,
    "illegal use of foo bar baz"
    @future_incompatible = FutureIncompatibleInfo {
        reason: fcw!(FutureReleaseError #1234) // your tracking issue here!
    },
}

// 2. Add a dedicated lint pass for it.
//    This step can be skipped if you emit the lint as part of an existing pass.

#[derive(Default)]
pub struct MyLintPass {
    ...
}

impl {Early,Late}LintPass for MyLintPass {
    ...
}

impl_lint_pass!(MyLintPass => [YOUR_LINT_HERE]);

// 3. emit the lint somewhere in your lint pass:
cx.emit_span_lint(
    YOUR_LINT_HERE,
    pat.span,
    // some diagnostic struct
    MyDiagnostic {
        ...
    },
);

    در نهایت، lint را در compiler/rustc_lint/src/lib.rs ثبت کنید. مثال‌های زیادی در آن فایل هست که قبلاً نشان می‌دهند چگونه.

    Helpful techniques

    اغلب فیلترکردن هشدارهای جدید از خطاهای قدیمی‌تر موجود چالش‌برانگیز است. یک تکنیکی که در گذشته به‌کار رفته اجرای کد قدیمی‌تر بدون تغییر و جمع‌آوری خطاهایی است که گزارش می‌داد. سپس می‌توانید برای هر خطایی که می‌دهید و در آن مجموعهٔ اصلی نیست هشدار صادر کنید. گزینهٔ دیگر لغو کامپایل پس از تکمیل کد اصلی است اگر خطاها گزارش شوند: آن‌گاه می‌دانید کد جدید شما فقط وقتی اجرا می‌شود که پیش‌تر خطایی نبوده باشد.

    Crater و crates.io

    Crater رباتی است که همهٔ crateهای crates.io و بسیاری از مخازن عمومی github را با کامپایلر دارای تغییرات شما کامپایل می‌کند. سپس گزارشی تولید می‌شود از crateهایی که با تغییرات شما کامپایل‌شدن را متوقف یا شروع کردند. اجراهای Crater می‌توانند چند روز طول بکشند.

    همیشه باید برای ارزیابی اثر اجرای crater انجام دهیم. مؤدبانه و با ملاحظه است که نویسندگان crateهای متأثر از تغییر شکننده را مطلع کنیم. حتی بهتر است PRهایی برای رفع شکستگی ارسال کنیم.

    آیا هرگز پذیرفتنی است مستقیماً به صدور خطا برویم؟

    تغییراتی که گمان می‌رود اثر ناچیز دارند می‌توانند مستقیماً به صدور خطا بروند. یک قاعدهٔ سرانگشتی بررسی با crates.io است: اگر کمتر از ۱۰ پروژهٔ متأثر در مجموع (نه خطاهای ریشه) یافت شود، می‌توانیم مستقیماً به خطا برویم. در چنین مواردی همچنان باید صفحهٔ «تغییر شکننده» را مثل قبل بسازیم، و باید مطمئن شویم خطا کاربران را به این صفحه هدایت می‌کند. به عبارت دیگر، همه‌چیز باید یکسان باشد جز اینکه کاربران خطا می‌گیرند، نه هشدار. علاوه بر این، باید PRهایی به پروژه‌های متأثر ارسال کنیم (ایده‌آل این است که پیش از land شدن PR پیاده‌سازی تغییر در rustc).

    اگر اثر ناچیز گمان نمی‌شود (مثلاً بیش از ۱۰ crate متأثر شوند)، هشدار الزامی است (مگر اینکه تیم کامپایلر موافقت کند در مورد خاصی معافیت ویژه بدهد). اگر پیاده‌سازی هشدار شدنی نیست، باید راهبرد تهاجمی مهاجرت crateها را پیش از land شدن تغییر در پیش بگیریم تا تعداد crateهای متأثر کم شود. در ادامه چند تکنیک برای رویکرد به این سناریو آمده است:

    1. برای زیربخش‌های مسئله هشدار صادر کنید و خطاهای جدید را برای کوچک‌ترین مجموعهٔ ممکن موارد نگه دارید.
    2. سعی کنید پیام خطای بسیار دقیقی بدهید که نحوهٔ رفع مشکل را پیشنهاد می‌کند و کاربران را به issue پیگیری هدایت می‌کند.
    3. It may also make sense to layer the fix:
      • ابتدا هر جا ممکن است هشدار اضافه کنید و بگذارید land شوند و سپس به صدور خطا بروید.
      • با نویسندگان crateهای متأثر کار کنید تا مطمئن شوید نسخه‌های اصلاح‌شده پیش از land شدن رفع در دسترس‌اند، تا کاربران پایین‌دست بتوانند از آن‌ها استفاده کنند.

    Stabilization

    پس از انجام تغییر، با همان فرایندی که برای قابلیت‌های ناپایدار به‌کار می‌بریم تغییر را پایدار می‌کنیم:

    • پس از انتشار نسخهٔ جدید، issueهای پیگیری معوق مربوط به تغییرات شکننده را مرور می‌کنیم و برخی را برای دورهٔ نظر نهایی (FCP) نامزد می‌کنیم.

    • FCP برای چنین issueهایی یک چرخه طول می‌کشد. در هفتهٔ یا دو هفتهٔ پایانی چرخه، کامنت‌ها را مرور می‌کنیم و تصمیم نهایی می‌گیریم:

      • تبدیل به خطا: تغییر باید به خطای سخت تبدیل شود.
      • بازگرداندن: باید هشدار را حذف کنیم و همچنان اجازه دهیم کد قدیمی‌تر کامپایل شود.
      • به تعویق: هنوز نمی‌توان تصمیم گرفت، بیشتر صبر کنید یا راهبردهای دیگر را امتحان کنید.

    ایده‌آل این است که تغییرات شکننده پیش از نهایی‌شدن روی شاخهٔ stable کامپایلر land شده باشند.

    حذف یک lint

    وقتی تصمیم گرفتیم «هشدار آینده» را به خطای سخت تبدیل کنیم، به PRای نیاز داریم که lint سفارشی را حذف کند. به‌عنوان مثال، گام‌های لازم برای حذف lint سازگاری با نام overlapping_inherent_impls این‌هاست. ابتدا نام lint را به حروف بزرگ تبدیل کنید (OVERLAPPING_INHERENT_IMPLS)؛ آن رشته را در منبع جست‌وجو کنید. اساساً هر جایی را که این نام lint ذکر شده تبدیل می‌کنیم (در کامپایلر از نام حروف بزرگ استفاده می‌کنیم و ماکرو رشتهٔ حروف کوچک را خودکار تولید می‌کند؛ پس جست‌وجوی overlapping_inherent_impls چیز زیادی نمی‌یابد).

    نکته: این فایل‌های دقیق دیگر وجود ندارند، اما روال همچنان یکسان است.

    lint را حذف کنید.

    اولین ارجاعی که احتمالاً می‌یابید تعریف lint در rustc_session/src/lint/builtin.rs است که شبیه این است:

    declare_lint! {
    pub OVERLAPPING_INHERENT_IMPLS,
    Deny, // this may also say Warning
    "two overlapping inherent impls define an item with the same name were erroneously allowed",
    @future_incompatible = FutureIncompatibleInfo {
        reason: fcw!(FutureReleaseError #1234), // your tracking issue here!
    },
}

    این ماکروی declare_lint! ساختارهای داده مرتبط را می‌سازد. آن را حذف کنید. همچنین متوجه می‌شوید در ادامهٔ فایل اشاره‌ای به OVERLAPPING_INHERENT_IMPLS هست که بخشی از lint_array! است؛ آن را هم حذف کنید.

    lint را به فهرست lintهای حذف‌شده اضافه کنید.

    در compiler/rustc_lint/src/lib.rs فهرستی از «lintهای تغییرنام‌یافته و حذف‌شده» هست. می‌توانید این lint را به فهرست اضافه کنید:

    store.register_removed("overlapping_inherent_impls", "converted into hard error, see #36889");

    که در آن #36889 issue پیگیری برای lint شماست.

    جاهایی را که lint را صادر می‌کنند به‌روز کنید

    در نهایت، آخرین دستهٔ ارجاع‌هایی که می‌بینید جاهایی است که واقعاً خود lint را فعال می‌کنند (یعنی چیزی که باعث ظاهرشدن هشدارها می‌شود). این‌ها را نمی‌خواهید حذف کنید. به‌جای آن، می‌خواهید آن‌ها را به خطا تبدیل کنید. در این مورد، فراخوانی add_lint این‌طور به نظر می‌رسد:

    self.tcx.sess.add_lint(lint::builtin::OVERLAPPING_INHERENT_IMPLS,
                       node_id,
                       self.tcx.span_of_impl(item1).unwrap(),
                       msg);

    همچنین اغلب node_span_lint را برای این به‌کار رفته می‌یابید.

    می‌خواهیم این را به خطا تبدیل کنیم. در برخی موارد ممکن است برای این سناریو خطای موجود باشد. در موارد دیگر باید کد تشخیصی تازه‌ای تخصیص دهیم. دستورالعمل تخصیص کد تشخیصی تازه را اینجا بیابید. ممکن است بخواهید در توضیح مفصل بیاورید که رفتار کامپایلر در این مورد تغییر کرده، و پیوندی به issue پیگیری آن تغییر بگذارید.

    فرض کنید E0592 را به‌عنوان کد خود پذیرفته‌ایم. آن‌گاه می‌توانیم فراخوانی add_lint() بالا را به چیزی شبیه این تغییر دهیم:

    struct_span_code_err!(self.dcx(), self.tcx.span_of_impl(item1).unwrap(), E0592, msg)
    .emit();

    یا بهتر: یک پیام تشخیصی ساختاریافته مثل این:

    #[derive(Diagnostic)]
struct MyDiagnostic {
    #[label]
    span: Span,
    ...
}

    Update tests

    در نهایت، مجموعهٔ تست را اجرا کنید. باید برخی تست‌ها باشند که قبلاً به lint با نام overlapping_inherent_impls ارجاع می‌دادند؛ آن‌ها باید به‌روز شوند. عموماً اگر تست قبلاً #[deny(overlapping_inherent_impls)] داشت، می‌توان آن را حذف کرد.

    ./x test

    All done!
