    Const generics

    انواع آرگومان‌های const

    بیشتر انواع ty::Const که وجود دارند معادل مستقیمی در انواع نوع‌ها دارند؛ برای مثال ConstKind::Param معادل TyKind::Param است.

    نکات جالب اصلی در اینجا عبارت‌اند از:

    • ConstKind::Alias, which is equivalent to TyKind::Alias.
    • ConstKind::Value، که مقدار نهایی یک ty::Const پس از monomorphization است. این تا حدی شبیه چیزهای کاملاً مشخصی مانند TyKind::Str یا TyKind::ADT است.

    برای فهرست کامل همهٔ انواع آرگومان‌های const و اینکه در سیستم نوع واقعاً چگونه نمایش داده می‌شوند، به نوع ConstKind مراجعه کنید.

    متغیرهای استنتاج (Inference Variables) کاملاً بی‌حاشیه‌اند و تقریباً در همه‌جا مانند متغیرهای استنتاج نوع با آن‌ها رفتار می‌شود. پارامترهای const (Const Parameters) نیز به همین ترتیب بی‌حاشیه‌اند و تقریباً در همه‌جا معادل استفاده از پارامترهای نوع هستند. با این حال، ظرافت‌های جالبی در نحوهٔ مدیریت آن‌ها در طول تجزیه (parsing)، تحلیل نام (name resolution) و lowering به AST وجود دارد: ambig-unambig-ty-and-consts.

    Anon constها

    Anon constها (مخفف anonymous const items) روشی هستند که عبارت‌های دلخواه در const generics با آن نمایش داده می‌شوند؛ برای مثال طول آرایهٔ 1 + 1 یا foo() یا حتی فقط 0. این‌ها مختص const generics هستند و معادل واقعی در نوع‌ها ندارند.

    Desugaring

    struct Foo<const N: usize>;
type Alias = [u8; 1 + 1];

    در این مثال یک آرگومان const به‌صورت 1 + 1 (طول آرایه) داریم که به‌شکل یک anon const نمایش داده می‌شود. desugaring چیزی شبیه این خواهد بود:

    struct Foo<const N: usize>;

const ANON: usize = 1 + 1;
type Alias = [u8; ANON];

    که در آن طول آرایه در [u8; ANON] خودش یک anon const شامل استفاده از ANON نیست، بلکه نوعی استفادهٔ «مستقیم» از آیتم const به نام ANON است (ConstKind::Unevaluated).

    Anon constها هیچ پارامتر جنریکی از آیتمی که درون آن هستند به ارث نمی‌برند:

    struct Foo<const N: usize>;
type Alias<T: Sized> = [T; 1 + 1];

// Desugars To;

struct Foo<const N: usize>;

const ANON: usize = 1 + 1;
type Alias<T: Sized> = [T; ANON];

    توجه کنید که ثابت ANON هیچ پارامتر جنریک یا where clause ندارد، هرچند Alias هم یک پارامتر نوع T و هم یک where clause به شکل T: Sized دارد. این desugaring بخشی از روشی است که با آن اعمال می‌کنیم anon constها نتوانند از پارامترهای جنریک استفاده کنند.

    اگرچه مفید است که anon constها را به‌صورت desugar شده به آیتم‌های const واقعی در نظر بگیریم، کامپایلر در واقع این‌گونه پیاده‌سازی نشده است.

    در زمان lowering به AST هنوز نوع anon const را نمی‌دانیم، بنابراین نمی‌توانیم آن را به یک آیتم HIR واقعی با نوعی که صریحاً نوشته شده desugar کنیم. برای دور زدن این مشکل، DefKind::AnonConst و hir::Node::AnonConst را داریم که برای نمایش این آیتم‌های const ناشناسی به کار می‌روند که در واقع نمی‌توان آن‌ها را desugar کرد.

    نوع این anon constها از کوئری type_of به دست می‌آید. با این حال، کوئری type_of در واقع منطقی برای محاسبهٔ نوع ندارد (و در حقیقت هنگام فراخوانی فقط ICE می‌دهد). در عوض، HIR Ty lowering مسئول تغذیهٔ (feeding) مقدار کوئری type_of برای هر anon constی است که lower می‌شود. HIR Ty lowering می‌تواند نوع anon const را با نگاه به نوع پارامتر Const که anon const آرگومانی برای آن است تعیین کند.

    به یک معنا، desugaringهای مثال‌های قبلی به این صورت‌اند:

    struct Foo<const N: usize>;
type Alias = [u8; 1 + 1];

// sort-of desugars to pseudo-rust:
struct Foo<const N: usize>;

const ANON = 1 + 1;
type Alias = [u8; ANON];

    وقتی برای نوع آرایه در Alias از HIR ty lowering می‌گذریم، طول آرایه را هم lower می‌کنیم و type_of(ANON) -> usize را feed می‌کنیم. این کار عملاً نوع آیتم const به نام ANON را در بخشی بعدی از کامپایلر تنظیم می‌کند، نه هنگام ساخت HIR.

    پس از انجام همهٔ این desugaringها، نمایش نهایی در سیستم نوع (یعنی به‌صورت یک ty::Const) یک ConstKind::Unevaluated با DefId مربوط به AnonConst است. این معادل روشی است که اگر می‌خواستیم استفاده از یک آیتم const واقعی را بدون عبور از anon const نمایش دهیم، به کار می‌بردیم (مثلاً وقتی min_generic_const_args فعال است).

    این کار اجازه می‌دهد نمایش «alias»های const با نمایش TyKind::Alias یکسان باشد. داشتن یک بدنهٔ HIR واقعی نیز امکان استفادهٔ مجدد بسیار زیادی از کد را فراهم می‌کند؛ برای مثال می‌توانیم از type checking در HIR و همهٔ مراحل lowering به MIR دوباره استفاده کنیم و سپس از ارزیابی ثابت (const eval) بهره ببریم.

    اعمال نبودن پارامترهای جنریک

    سه راه برای اعمال این قاعده وجود دارد که anon constها نتوانند از پارامترهای جنریک استفاده کنند:

    1. تحلیل نام (Name Resolution) مسیرهایی را که به پارامترهای جنریک اشاره می‌کنند درون یک anon const resolve نمی‌کند
    2. HIR Ty lowering وقتی درون یک anon const با یک alias نوع Self مواجه شود که به نوعی با ارجاع به پارامترهای جنریک اشاره دارد، خطا می‌دهد
    3. Anon constها where clauseها یا جنریک‌ها را از تعریف والد خود به ارث نمی‌برند (یعنی generics_of برای anon constها والد ندارد)
    // *1* Errors in name resolution
type Alias<const N: usize> = [u8; N + 1];
//~^ ERROR: generic parameters may not be used in const operations

// *2* Errors in HIR Ty lowering:
struct Foo<T>(T);
impl<T> Foo<T> {
    fn assoc() -> [u8; { let a: Self; 0 }] {}
    //~^ ERROR: generic `Self` types are currently not permitted in anonymous constants
}

// *3* Errors due to lack of where clauses on the desugared anon const
trait Trait<T> {
    const ASSOC: usize;
}
fn foo<T>() -> [u8; <()>::ASSOC]
//~^ ERROR: no associated item named `ASSOC` found for unit type `()`
where
    (): Trait<T> {}

    نکتهٔ دوم به‌ویژه ظریف است، زیرا بسیار آسان است که HIR Ty lowering را اشتباه پیاده کنیم و به‌درستی اعمال نکنیم که anon constها نمی‌توانند از پارامترهای جنریک استفاده کنند. بررسی موجود بیش از حد محافظه‌کارانه است و به‌طور تصادفی اجازه می‌دهد برخی پارامترهای جنریک در بدنهٔ anon const راه یابند #144547.

    مجاز دانستن اشتباهیِ پارامترهای جنریک در anon constها گاهی می‌تواند به ICE بینجامد، اما می‌تواند به پذیرفته‌شدن برنامه‌های نادرست نیز منجر شود.

    نکتهٔ سوم نیز تا حدی ظریف است: با به ارث نبردن هیچ‌یک از where clauseهای آیتم والد، از این پیش‌آمد جلوگیری می‌کنیم که trait solving بر پایهٔ where clauseهای موجود در دامنه که به پارامترهای جنریک اشاره دارند، متغیرهای استنتاج را به پارامترهای جنریک استنتاج کند. برای مثال، استنتاج ?x=T از عبارت <() as Trait<?x>>::ASSOC و یک where clause موجود در دامنه به شکل (): Trait<T>.

    این همچنین احتمال اینکه کامپایلر ICE بدهد یا دست‌کم به‌طور اتفاقی نوعی خطا صادر کند را بسیار بیشتر می‌کند، اگر به‌طور تصادفی اجازهٔ پارامترهای جنریک را در یک anon const بدهیم، زیرا anon const هیچ‌یک از اطلاعات لازم برای مدیریت درست پارامترهای جنریک را در محیط خود نخواهد داشت.

    عبارت‌های تکرار آرایه

    تنها استثنا در همهٔ موارد بالا، تعداد تکرار (repeat count) در عبارت‌های آرایه است. به‌عنوان یک ترفند سازگاری با گذشته، به آرگومان const تعداد تکرار اجازه می‌دهیم از پارامترهای جنریک استفاده کند.

    fn foo<T: Sized>() {
    let a = [1_u8; size_of::<T>()];
}

    با این حال، برای پرهیز از بیشتر مشکلاتی که مجاز کردن پارامترهای جنریک در آرگومان‌های const از نوع anon const به همراه دارد، لازم می‌دانیم ثابت پیش از monomorphization (مثلاً در طول type checking) ارزیابی شود. به یک معنا فقط وقتی اجازهٔ پارامترهای جنریک را در اینجا می‌دهیم که از نظر معنایی استفاده‌نشده باشند.

    در مثال قبل، anon const را می‌توان برای هر پارامتر نوع T ارزیابی کرد، زیرا اشاره‌گرهای خام به نوع‌های sized همیشه اندازهٔ یکسانی دارند (مثلاً 8 روی پلتفرم‌های ۶۴ بیتی).

    وقتی تشخیص دهیم anon constی ارزیابی شده که از نظر نحوی شامل پارامترهای جنریک بوده، اما موفقیت ارزیابی در واقع به آن‌ها وابسته نبوده، const_evaluatable_unchecked FCW را صادر می‌کنیم. قرار است این هشدار پس از پایدارسازی راه‌های بیشتری برای استفاده از پارامترهای جنریک در آرگومان‌های const، مثلاً min_generic_const_args یا (اکنون منسوخ‌شدهٔ) generic_const_exprs، به خطای سخت تبدیل شود.

    پیاده‌سازی این FCW را اینجا می‌توان یافت: const_eval_resolve_for_typeck

    ناسازگاری‌ها با generic_const_parameter_types

    پشتیبانی از پارامترهای const مانند const N: [u8; M] یا const N: Foo<T> با ساختار فعلی anon constها به‌خوبی کار نمی‌کند. دو دلیل برای این وجود دارد:

    1. چون anon constها نمی‌توانند از پارامترهای جنریک استفاده کنند، نوع آن‌ها نیز نمی‌تواند به پارامترهای جنریک ارجاع دهد. این یعنی اساساً ممکن نیست از یک anon const به‌عنوان آرگومان برای پارامتر constی استفاده کرد که نوعش هنوز به پارامترهای جنریک ارجاع می‌دهد.

      #![feature(adt_const_params, generic_const_parameter_types)]

fn foo<const N: usize, const M: [u8; N]>() {}

fn bar<const N: usize>() {
    // There is no way to specify the const argument to `M`
    foo::<N, { [1_u8; N] }>();
}

    2. در حال حاضر لازم است هنگام lower کردن anon constها در HIR ty lowering نوع آن‌ها را بدانیم. با نوع‌های پارامتر const جنریک ممکن است نوعی که در حال حاضر شناخته می‌شود شامل متغیرهای استنتاج باشد (یعنی هنوز ممکن است کاملاً معلوم نباشد).

      #![feature(adt_const_params, generic_const_parameter_types)]

fn foo<const N: usize, const M: [u8; N]>() {}

fn bar() {
    // The const argument to `N` must be explicitly specified
    // even though it is able to be inferred
    foo::<_, { [1_u8; 3] }>();
}

    هنوز روشن نیست که راه درست برای سازگار کردن generic_const_parameter_types با بقیهٔ const generics چیست.

    generic_const_exprs اجازهٔ anon constهایی را می‌داد که نوع‌هایشان به پارامترهای جنریک ارجاع دارند، اما آن طراحی عملاً غیرقابل‌استفاده از آب درآمد.

    min_generic_const_args اجازه خواهد داد برخی عبارت‌ها (مثلاً ساخت آرایه) بدون anon const و در نتیجه بدون برخورد با این مشکلات قابل نمایش باشند، هرچند هنوز مشخص نیست که این کافی است یا نه.

    بررسی نوع آرگومان‌های const

    برای آنکه یک آرگومان const خوش‌فرم (well formed) باشد باید همان نوع پارامتر constی را داشته باشد که آرگومانی برای آن است. برای مثال، آرگومان const از نوع bool برای طول آرایه خوش‌فرم نیست، زیرا پارامتر طول آرایه نوع usize دارد.

    type Alias<const B: bool> = [u8; B];
//~^ ERROR:

    برای بررسی این مورد، ClauseKind::ConstArgHasType(ty::Const, Ty) را داریم، که در آن، به‌ازای هر پارامتر Const تعریف‌شده روی یک آیتم، یک clause معادل ConstArgHasType را نیز در فهرست where clauseهای آن desugar می‌کنیم. این تضمین می‌کند که هر بار خوش‌فرمی چیزی را با اثبات همهٔ clauseهایش بررسی می‌کنیم، اتفاقاً بررسی می‌کنیم که همهٔ آرگومان‌های Const نوع درست دارند.

    fn foo<const N: usize>() {}

// desugars to in pseudo-rust

fn foo<const N>()
where
//  ConstArgHasType(N, usize)
    N: usize, {}

    اثبات goalهای ConstArgHasType به این صورت پیاده‌سازی شده که ابتدا نوع آرگومان const محاسبه می‌شود و سپس با نوع داده‌شده برابر قرار داده می‌شود. طرح کلی چگونگی محاسبهٔ نوع یک آرگومان Const:

    • برای ConstKind::Param(N) می‌توان در ParamEnv به دنبال یک clause به شکل ConstArgHasType(N, ty) گشت
    • ConstKind::Value نوع مقدار را درون خودش ذخیره می‌کند، پس می‌توان به‌سادگی به آن دسترسی داشت
    • نوع ConstKind::Unevaluated را می‌توان با فراخوانی کوئری type_of محاسبه کرد
    • برای اطلاعات دقیق‌تر، پیاده‌سازی اثبات goalهای ConstArgHasType را ببینید

    ConstArgHasType تنها روش حیاتی از نظر درستی (soundness) برای بررسی نوع درست آرگومان‌های Const است. با این حال، در برخی موارد نوع آرگومان‌های Const را به روش دیگری نیز به‌طور غیرمستقیم بررسی می‌کنیم.

    type Alias = [u8; true];

// desugars to

const ANON: usize = true;
type Alias = [u8; ANON];

    با feed کردن نوع یک anon const با نوع پارامتر Const، تضمین می‌کنیم که goal مربوط به ConstArgHasType که anon const را در بر دارد موفق شود. در مواردی که نوع anon const با نوع پارامتر Const مطابقت ندارد، آنچه در واقع رخ می‌دهد یک خطای type checking هنگام بررسی نوع بدنهٔ anon const است.

    با نگاه به مثال بالا، این متناظر است با اینکه [u8; ANON] نوعی خوش‌فرم است زیرا ANON نوع usize دارد، اما بدنهٔ ANON بدفرم است و به خطای type checking می‌انجامد، زیرا true را نمی‌توان از یک آیتم const با نوع usize برگرداند.
