    حل صفت (سبک قدیمی)

    این فصل فرایند کلی حل صفت (trait resolution) را توضیح می‌دهد و به چند نکتهٔ غیربدیهی اشاره می‌کند.

    نکته: این فصل (و زیرفصل‌هایش) توضیح می‌دهند حل‌کنندهٔ صفت در حال حاضر چگونه کار می‌کند. با این حال، در حال طراحی یک حل‌کنندهٔ صفت جدید هستیم. اگر ترجیح می‌دهید دربارهٔ آن بخوانید، این زیرفصل را ببینید.

    مفاهیم اصلی

    حل صفت فرایند جفت کردن یک impl با هر ارجاع به یک صفت است. پس برای مثال، اگر تابع جنریکی مانند این وجود داشته باشد:

    fn clone_slice<T:Clone>(x: &[T]) -> Vec<T> { ... }

    و سپس فراخوانی آن تابع:

    let v: Vec<isize> = clone_slice(&[1, 2, 3])

    کار حل صفت این است که بفهمد آیا impl‌ای از (در این مورد) isize : Clone وجود دارد یا نه.

    توجه کنید که در برخی موارد، مانند توابع جنریک، ممکن است نتوانیم impl مشخصی پیدا کنیم، اما می‌توانیم نتیجه بگیریم که فراخواننده باید یک impl فراهم کند. برای مثال، بدنهٔ clone_slice را در نظر بگیرید:

    fn clone_slice<T:Clone>(x: &[T]) -> Vec<T> {
    let mut v = Vec::new();
    for e in &x {
        v.push((*e).clone()); // (*)
    }
}

    خطی که با (*) علامت‌گذاری شده فقط در صورتی مجاز است که T (نوع *e) صفت Clone را پیاده‌سازی کند. طبیعتاً چون نمی‌دانیم T چیست، نمی‌توانیم impl مشخص را پیدا کنیم؛ اما بر پایهٔ کران T:Clone می‌توانیم بگوییم impl‌ای وجود دارد که فراخواننده باید فراهم کند.

    اصطلاح تعهد (obligation) را برای اشاره به ارجاع صفتی به کار می‌بریم که به یک impl نیاز دارد. در اصل، سامانهٔ حل صفت یک تعهد را با اثبات اینکه impl مناسب واقعاً وجود دارد حل می‌کند.

    در طول بررسی نوع، نتایج انتخاب صفت (trait selection) را ذخیره نمی‌کنیم. فقط می‌خواهیم وارسی کنیم انتخاب صفت موفق خواهد بود. سپس بعداً، در زمان codegen، وقتی همهٔ نوع‌های مشخص در دسترس‌اند، می‌توانیم انتخاب صفت را تکرار کنیم تا پیاده‌سازی واقعی انتخاب شود، که سپس در باینری خروجی تولید می‌شود.

    نمای کلی

    حل صفت از سه بخش اصلی تشکیل شده است:

    • انتخاب (Selection): تصمیم‌گیری دربارهٔ اینکه یک تعهد مشخص چگونه حل شود. برای مثال، انتخاب ممکن است تصمیم بگیرد یک تعهد مشخص را می‌توان با به‌کارگیری impl‌ای که با نوع Self مطابقت دارد، یا با استفاده از یک کران پارامتر (مثلاً T: Trait) حل کرد. در مورد یک impl، انتخاب یک تعهد می‌تواند به‌دلیل where clauseهای خود impl تعهدهای تودرتو بسازد. ممکن است ارزیابی آن تعهدهای تودرتو را هم برای رفع ابهام‌ها لازم داشته باشد.

    • برآورده‌سازی (Fulfillment): کد fulfillment همان چیزی است که پیگیری می‌کند تعهدها به‌طور کامل برآورده شده‌اند. در اصل یک فهرست کار (worklist) از تعهدهاست که باید انتخاب شوند: هنگامی که انتخاب موفق شد، تعهد از فهرست کار حذف می‌شود و هر تعهد تودرتو در صف قرار می‌گیرد. Fulfillment متغیرهای استنتاج را مقید می‌کند.

    • ارزیابی (Evaluation): بررسی می‌کند آیا تعهدها برقرارند، بدون اینکه هیچ متغیر استنتاجی را مقید کند. توسط selection استفاده می‌شود.

    انتخاب (Selection)

    انتخاب فرایند تصمیم‌گیری دربارهٔ این است که آیا یک تعهد می‌تواند حل شود و اگر می‌تواند، چگونه حل شود (از طریق impl، where clause و غیره). رابط اصلی تابع select() است که یک تعهد می‌گیرد و SelectionResult برمی‌گرداند. سه نتیجهٔ ممکن وجود دارد:

    • Ok(Some(selection)) – بله، تعهد را می‌توان حل کرد و selection نشان می‌دهد چگونه. اگر تعهد از طریق یک impl حل شده باشد، selection ممکن است تعهدهای تودرتویی را هم که impl لازم دارد نشان دهد.

    • Ok(None) – هنوز مطمئن نیستیم تعهد قابل حل است یا نه. این بیشتر وقتی رخ می‌دهد که تعهد متغیرهای نوع بدون مقدار داشته باشد.

    • Err(err) – تعهد قطعاً نمی‌تواند حل شود، به‌دلیل یک خطای نوع یا چون هیچ impl‌ای وجود ندارد که بتواند اعمال شود.

    الگوریتم پایهٔ انتخاب به دو فاز بزرگ تقسیم می‌شود: جمع‌آوری کاندیداها (candidate assembly) و تأیید (confirmation).

    توجه کنید که به‌دلیل نحوهٔ کار استنتاج طول عمر، نمی‌توان بازخورد فوری دربارهٔ برقرار بودن یا نبودن یک یکسان‌سازی یا رابطهٔ زیرنوع میان طول عمرها داد. بنابراین تطبیق طول عمر در حین انتخاب در نظر گرفته نمی‌شود. این در این واقعیت منعکس می‌شود که انتساب زیرناحیه (subregion) شکست‌ناپذیر است. این ممکن است قیدهای طول عمری ایجاد کند که بعداً معلوم می‌شود خطا هستند (در مقابل، قیدهای غیر طول عمر پیش‌تر در حین انتخاب بررسی شده‌اند و هرگز نمی‌توانند خطا ایجاد کنند، هرچند طبیعتاً ممکن است به خطاهای دیگری در پایین‌دست بینجامند).

    به جستجوی impl‌ها/where-clauseها/و غیره می‌پردازد که ممکن است برای برآورده کردن تعهد به کار روند. هر یک از آن‌ها یک کاندیدا نامیده می‌شود. برای پرهیز از ابهام، می‌خواهیم دقیقاً یک کاندیدا پیدا کنیم که به‌طور قطعی قابل اعمال باشد. در برخی موارد ممکن است ندانیم یک impl/where-clause اعمال می‌شود یا نه – این وقتی رخ می‌دهد که تعهد متغیرهای استنتاج بدون مقدار داشته باشد.

    زیربرنامه‌هایی که تصمیم می‌گیرند یک impl/where-clause/و غیره مشخص بر یک تعهد مشخص اعمال می‌شود در مجموع فرایند تطبیق (matching) نامیده می‌شوند. برای کاندیداهای impl ، این به یکسان‌سازی سرایند impl (نوع Self و آرگومان‌های صفت) با چشم‌پوشی از تعهدهای تودرتو می‌انجامد. اگر تطبیق موفق شود آن را به مجموعه‌ای از کاندیداها اضافه می‌کنیم. هنگام جمع‌آوری کاندیداها برای صفت‌های توکار مانند Copy، Sized و CoerceUnsized قواعد دیگری هم وجود دارد.

    پس از پایان این گذر نخست، می‌توانیم مجموعهٔ کاندیداها را بررسی کنیم. اگر مجموعه‌ای تک‌عضوی باشد، کار تمام است: این تنها impl در دامنه است که ممکن است اعمال شود. در غیر این صورت، می‌توانیم مجموعهٔ کاندیداها را با استفاده از where clauseها و شرط‌های دیگر غربال (winnow) کنیم. غربال کردن از evaluate_candidate استفاده می‌کند تا بررسی کند آیا تعهدهای تودرتو ممکن است اعمال شوند. اگر این باز هم بیش از ۱ کاندیدا باقی بگذارد، از fn candidate_should_be_dropped_in_favor_of استفاده می‌کنیم تا برخی کاندیداها را بر برخی دیگر ترجیح دهیم.

    اگر این مجموعهٔ کاهش‌یافته یک مدخل واحد و بدون ابهام بدهد، کار درست است، در غیر این صورت نتیجه مبهم در نظر گرفته می‌شود.

    غربال کردن (Winnowing): رفع ابهام‌ها

    اما اگر چند impl وجود داشته باشد که در همهٔ آن‌ها نوع‌ها یکسان‌سازی شوند چه می‌شود؟ این مثال را در نظر بگیرید:

    trait Get {
    fn get(&self) -> Self;
}

impl<T: Copy> Get for T {
    fn get(&self) -> T {
        *self
    }
}

impl<T: Get> Get for Box<T> {
    fn get(&self) -> Box<T> {
        Box::new(<T>::get(self))
    }
}

    مثلاً وقتی get(&Box::new(1_u16)) را فراخوانی می‌کنیم چه می‌شود؟ در این مورد، نوع Self برابر Box<u16> است – که با هر دو impl یکسان‌سازی می‌شود، چون اولی بر همهٔ نوع‌های T اعمال می‌شود و دومی بر همهٔ Box<T>. برای اینکه این بدون ابهام باشد، کامپایلر یک گذر غربال‌کردن انجام می‌دهد که where clauseها را در نظر می‌گیرد و می‌کوشد کاندیداها را حذف کند. در این مورد، impl نخست فقط در صورتی اعمال می‌شود که Box<u16> : Copy برقرار باشد که برقرار نیست. پس از غربال کردن، فقط یک کاندیدا باقی می‌ماند، بنابراین می‌توانیم ادامه دهیم.

    where clauseها

    جز impl، راه اصلی دیگر برای حل یک تعهد از طریق یک where clause است. به فرایند انتخاب همیشه یک محیط پارامتر (parameter environment) داده می‌شود که فهرستی از where clauseها دارد، که اساساً تعهدهایی‌اند که می‌توانیم فرض کنیم برآورده‌شدنی‌اند. روی آن فهرست پیمایش می‌کنیم و بررسی می‌کنیم آیا تعهد فعلی ما در آن فهرست یافت می‌شود. اگر بود، برآورده‌شده در نظر گرفته می‌شود. دقیق‌تر، می‌خواهیم بررسی کنیم آیا تعهد where-clauseای وجود دارد که برای همان صفت (یا یک زیرصفت) باشد و بتواند با تعهد تطبیق یابد.

    این مثال ساده را در نظر بگیرید:

    trait A1 {
    fn do_a1(&self);
}
trait A2 : A1 { ... }

trait B {
    fn do_b(&self);
}

fn foo<X:A2+B>(x: X) {
    x.do_a1(); // (*)
    x.do_b();  // (#)
}

    در بدنهٔ foo، آشکارا می‌توانیم از متدهای A1، A2 یا B روی متغیر x استفاده کنیم. خط علامت‌گذاری‌شده با (*) تعهد X: A1 ایجاد می‌کند، در حالی که خط علامت‌گذاری‌شده با (#) تعهد X: B ایجاد می‌کند. در همین حال، محیط پارامتر دو where-clause خواهد داشت: X : A2 و X : B. پس برای هر تعهد، این فهرست where-clauseها را جستجو می‌کنیم. تعهد X: B به‌سادگی با where-clause به شکل X: B تطبیق می‌یابد. برای حل تعهد X:A1، توجه می‌کنیم که X:A2 مستلزم X:A1 است.

    تأیید (Confirmation)

    تأیید (Confirmation) پارامترهای نوع خروجی صفت را با مقادیر یافت‌شده در تعهد یکسان‌سازی می‌کند و احتمالاً خطای نوع می‌دهد.

    فرض کنید گونه‌ای از مثال Convert را در بخش پیشین داریم، به این شکل:

    trait Convert<Target> {
    fn convert(&self) -> Target;
}

impl Convert<usize> for isize { ... } // isize -> usize
impl Convert<isize> for usize { ... } // usize -> isize

let x: isize = ...;
let y: char = x.convert(); // NOTE: `y: char` now!

    تأیید جایی است که خطا گزارش می‌شود، چون impl مشخص کرده بود Target برابر usize خواهد بود، اما تعهد char را گزارش کرد. بنابراین نتیجهٔ انتخاب یک خطا خواهد بود.

    توجه کنید که impl کاندیدا بر پایهٔ نوع Self انتخاب می‌شود، اما تأیید بر پایهٔ (در این مورد) پارامتر نوع Target انجام می‌شود.

    انتخاب در حین codegen

    همان‌طور که در بالا گفته شد، در طول بررسی نوع، نتایج انتخاب صفت را ذخیره نمی‌کنیم. در زمان codegen، انتخاب صفت را تکرار می‌کنیم تا برای هر فراخوانی متد impl مشخصی انتخاب شود. این کار با fn codegen_select_candidate انجام می‌شود. در این انتخاب دوم، هیچ where-clauseای را در دامنه در نظر نمی‌گیریم چون می‌دانیم هر حل به یک impl مشخص حل می‌شود.

    یک پیچ جالب به تعهدهای تودرتو مربوط است. در حالت کلی، در codegen فقط باید بفهمیم کدام کاندیدا اعمال می‌شود و به تعهدهای تودرتو اهمیت نمی‌دهیم، چون از قبل فرض می‌شود درست‌اند. با این حال، در حال حاضر همهٔ آن‌ها را برآورده می‌کنیم. دلیلش این است که گاهی می‌تواند نتایج استنتاج نوع را تحت تأثیر قرار دهد. یعنی جایگزین‌های کامل بر حسب متغیرهای نوع impl در دسترس ما نیست، پس باید انتخاب صفت را اجرا کنیم تا همه‌چیز را بفهمیم.
