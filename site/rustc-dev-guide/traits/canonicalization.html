    کانونی‌سازی (Canonicalization)

    نکته: FIXME: محتوای این فصل با فصل Canonicalization در حل صفت نسل بعد تا حدی هم‌پوشانی دارد. پیشنهاد می‌شود این محتواها در آینده بازسازماندهی شوند.

    کانونی‌سازی (Canonicalization) فرایند جداسازی یک مقدار استنتاجی از بافت آن است. بخش کلیدی پیاده‌سازی query‌های کانونی است، و شاید بخواهید فصل مادر را بخوانید تا بافت بیشتری به دست آورید.

    کانونی‌سازی در واقع بر مفهومی بسیار ساده استوار است: هر متغیر استنتاج همیشه در یکی از دو حالت است: یا بدون مقدار (unbound) است که در این حالت هنوز نمی‌دانیم چه نوعی است، یا مقید (bound) است که در این حالت می‌دانیم. پس برای جدا کردن یک ساختار داده T که شامل نوع‌ها/نواحی است از محیطش، فقط پایین می‌رویم و متغیرهای بدون مقداری را که در T ظاهر می‌شوند پیدا می‌کنیم؛ این متغیرها با «متغیرهای کانونی (canonical variables)» جایگزین می‌شوند که از صفر شروع می‌شوند و با ترتیبی ثابت شماره‌گذاری می‌شوند (بیشتر از چپ به راست، اما در واقع تا وقتی یکنواخت باشد مهم نیست).

    برای مثال، اگر نوع X = (?T, ?U) را داشته باشیم که ?T و ?U متغیرهای استنتاج متمایز و بدون مقدارند، آن‌گاه شکل کانونی X برابر (?0, ?1) خواهد بود، که ?0 و ?1 این جانگهدارهای کانونی را نشان می‌دهند. توجه کنید که نوع Y = (?U, ?T) هم به (?0, ?1) کانونی می‌شود. اما نوع Z = (?T, ?T) به (?0, ?0) کانونی می‌شود (همان‌طور که (?U, ?U) هم می‌شود). به عبارت دیگر، هویت دقیق متغیرهای استنتاج مهم نیست – مگر اینکه تکرار شده باشند.

    از این برای بهبود کش کردن و نیز تشخیص چرخه‌ها و چیزهای دیگر در حین حل صفت استفاده می‌کنیم. به‌طور تقریبی، ایده این است که اگر دو query صفت شکل کانونی یکسان داشته باشند، پاسخ یکسان می‌گیرند. آن پاسخ بر حسب متغیرهای کانونی (?0، ?1) بیان می‌شود که می‌توانیم آن‌ها را دوباره به متغیرهای اصلی (?T، ?U) نگاشت کنیم.

    کانونی‌سازی query

    برای دیدن اینکه چگونه کار می‌کند، تصور کنید می‌خواهیم query صفت زیر را حل کنیم: ?A: Foo<'static, ?B>، که ?A و ?B بدون مقدارند. این query دو متغیر بدون مقدار دارد، اما طول عمر 'static را هم دارد. سامانهٔ صفت عموماً همهٔ طول عمرها را نادیده می‌گیرد و با همه یکسان رفتار می‌کند، پس هنگام کانونی‌سازی هر طول عمر آزاد را هم با یک متغیر کانونی جایگزین می‌کنیم (توجه کنید که 'static در اینجا در واقع یک متغیر طول عمر آزاد است. آن را در بافت نوع‌گذاری کل برنامه در نظر نمی‌گیریم، بلکه فقط در بافت این ارجاع صفت. از نظر ریاضی، روی کل برنامه سورگذاری (quantify) نمی‌کنیم، بلکه فقط روی همین الزام). بنابراین نتیجهٔ زیر را می‌گیریم:

    ?0: Foo<'?1, ?2>

    گاهی این را به شکل دیگری می‌نویسیم، مانند:

    for<T,L,T> { ?0: Foo<'?1, ?2> }

    این for<> اطلاعاتی دربارهٔ هر یک از متغیرهای کانونی درون آن می‌دهد. در این مورد، هر T یک متغیر نوع را نشان می‌دهد، پس ?0 و ?2 نوع‌اند؛ L یک متغیر طول عمر را نشان می‌دهد، پس ?1 یک طول عمر است. متد canonicalize همچنین آرایهٔ CanonicalVarValues به نام OV را با «مقادیر اصلی» هر متغیر کانونی‌شده برمی‌گرداند:

    [?A, 'static, ?B]

    بعداً، هنگام پردازش پاسخ query، به این بردار OV نیاز خواهیم داشت.

    اجرای query

    پس از ساختن query کانونی، می‌توانیم تلاش کنیم آن را حل کنیم. برای این کار، در نهایت یک بافت استنتاج تازه می‌سازیم و query کانونی را در آن بافت نمونه‌سازی (instantiate) می‌کنیم. ایده این است که از شکل کانونی یک جایگزین S می‌سازیم که برای هر متغیر کانونی یک متغیر استنتاج تازه (از نوع مناسب) دارد. پس برای query نمونهٔ ما:

    for<T,L,T> { ?0: Foo<'?1, ?2> }

    جایگزین S ممکن است چنین باشد:

    S = [?A, '?B, ?C]

    سپس می‌توانیم متغیرهای کانونی مقید (?0 و غیره) را با این متغیرهای استنتاج جایگزین کنیم و query کاملاً نمونه‌سازی‌شدهٔ زیر را به دست آوریم:

    ?A: Foo<'?B, ?C>

    اما آن جایگزین S را به یاد داشته باشید! بعداً به آن نیاز خواهیم داشت.

    خب، اکنون که یک بافت استنتاج تازه و یک query نمونه‌سازی‌شده داریم، می‌توانیم تلاش کنیم آن را حل کنیم. خود حل‌کنندهٔ صفت در بخشی دیگر با جزئیات بیشتر توضیح داده شده است، اما همین‌قدر بگوییم که یک مقدار قطعیت (Proven یا Ambiguous) محاسبه می‌کند و بر متغیرهای استنتاجی که ساخته‌ایم اثر جانبی می‌گذارد. برای مثال، اگر فقط یک impl از Foo وجود داشت، مانند این:

    impl<'a, X> Foo<'a, X> for Vec<X>
where X: 'a
{ ... }

    آن‌گاه ممکن است به مقدار قطعیت Proven برسیم، و نیز متغیرهای استنتاج تازهٔ '?D و ?E را بسازیم (تا پارامترهای impl را نشان دهند) و به‌صورت زیر یکسان‌سازی کنیم:

    • '?B = '?D
    • ?A = Vec<?E>
    • ?C = ?E

    همچنین به‌دلیل where clause، قید ناحیهٔ ?E: '?D را انباشته می‌کنیم.

    برای ساختن نتیجهٔ نهایی query، باید این مقادیر را از بافت استنتاج query «بالا ببریم» و به چیزی تبدیل کنیم که بتوان آن را دوباره در بافت استنتاج اصلی‌مان اعمال کرد. این کار را با اعمال دوبارهٔ کانونی‌سازی انجام می‌دهیم، اما روی نتیجهٔ query.

    کانونی‌سازی نتیجهٔ query

    همان‌طور که در بخش مادر بحث شد، بیشتر query‌های صفت به نتیجه‌ای ختم می‌شوند که یک «مقدار قطعیت» به نام certainty، یک جایگزین نتیجه به نام var_values و چند قید ناحیه را کنار هم می‌آورد. برای ساختن این، در نهایت از جایگزین S که هنگام نمونه‌سازی اولیهٔ query ساختیم دوباره استفاده می‌کنیم. برای تازه کردن حافظه‌تان، query‌ای داشتیم

    for<T,L,T> { ?0: Foo<'?1, ?2> }

    که برایش جایگزین S را ساختیم:

    S = [?A, '?B, ?C]

    سپس کارهایی انجام دادیم که برخی از آن متغیرها را با چیزهای دیگر یکسان‌سازی کرد. اگر S را با آخرین نتایج «تازه‌سازی» کنیم، می‌رسیم به:

    S = [Vec<?E>, '?D, ?E]

    این‌ها دقیقاً مقادیر جدید سه متغیر ورودی query اصلی ما هستند. اما توجه کنید که شامل چند متغیر جدید هم هستند (مانند ?E). می‌توانیم با کانونی‌سازی دوباره آن‌ها را از بین ببریم! اما فقط S را کانونی نمی‌کنیم، بلکه کل پاسخ query یعنی QR را کانونی می‌کنیم:

    QR = {
    certainty: Proven,             // or whatever
    var_values: [Vec<?E>, '?D, ?E] // this is S
    region_constraints: [?E: '?D], // from the impl
    value: (),                     // for our purposes, just (), but
                                   // in some cases this might have
                                   // a type or other info
}

    نتیجه چنین خواهد بود:

    Canonical(QR) = for<T, L> {
    certainty: Proven,
    var_values: [Vec<?0>, '?1, ?0]
    region_constraints: [?0: '?1],
    value: (),
}

    (یک نکتهٔ ظریف: هنگامی که نتیجهٔ query را کانونی می‌کنیم، با طول عمرهای آزاد رفتار ویژه‌ای نداریم. توجه کنید که برای مثال هر دو ارجاع به '?D به همان متغیر کانونی (?1) تبدیل شدند. این برخلاف query اصلی است، که در آن هر طول عمر آزاد را به یک متغیر کانونی تازه کانونی کردیم.)

    اکنون این نتیجه باید در هر بافتی که لازم است دوباره اعمال شود.

    پردازش نتیجهٔ query کانونی‌شده

    در بخش پیشین یک نتیجهٔ query کانونی تولید کردیم. اکنون باید آن نتیجه را در بافت اصلی‌مان اعمال کنیم. اگر به یاد داشته باشید، خیلی پیش‌تر، در ابتدا، می‌خواستیم این query را اثبات کنیم:

    ?A: Foo<'static, ?B>

    آن را به این کانونی کردیم:

    for<T,L,T> { ?0: Foo<'?1, ?2> }

    و اکنون یک پاسخ کانونی پس گرفتیم:

    for<T, L> {
    certainty: Proven,
    var_values: [Vec<?0>, '?1, ?0]
    region_constraints: [?0: '?1],
    value: (),
}

    اکنون می‌خواهیم آن پاسخ را در بافت خود اعمال کنیم. از نظر مفهومی، روش انجام آن چنین است: (الف) هر یک از متغیرهای کانونی نتیجه را با یک متغیر استنتاج تازه نمونه‌سازی کنیم، (ب) مقادیر نتیجه را با مقادیر اصلی یکسان‌سازی کنیم، و سپس (ج) قیدهای ناحیه را برای بعد ثبت کنیم. انجام گام (الف) نتیجه‌ای به این شکل می‌دهد

    {
      certainty: Proven,
      var_values: [Vec<?C>, '?D, ?C]
                       ^^   ^^^ fresh inference variables
      region_constraints: [?C: '?D],
      value: (),
}

    گام (ب) سپس یکسان‌سازی می‌کند:

    ?A with Vec<?C>
'static with '?D
?B with ?C

    و سرانجام قید ناحیهٔ ?C: 'static برای وارسی بعدی ثبت می‌شود.

    (آنچه در عمل انجام می‌دهیم گونه‌ای کمی بهینه‌شده از آن است: به‌جای نمونه‌سازی مشتاقانهٔ همهٔ مقادیر کانونی نتیجه با متغیرها، بردار مقادیر را پیمایش می‌کنیم و به دنبال مواردی می‌گردیم که مقدار صرفاً یک متغیر کانونی است. در مثال ما، values[2] برابر ?C است، پس می‌توانیم نتیجه بگیریم ?C := ?B و '?D := 'static. این یک مجموعهٔ جزئی از مقادیر به ما می‌دهد. برای هر چیزی که مقداری برایش پیدا نکنیم، یک متغیر استنتاج می‌سازیم.)
