    goalها و clauseها

    در اصطلاحات برنامه‌نویسی منطقی، goal چیزی است که باید اثبات کنید و clause چیزی است که می‌دانید درست است. همان‌طور که در فصل تبدیل به منطق (lowering to logic) توضیح داده شد، حل‌کنندهٔ صفت Rust بر پایهٔ گسترشی از clauseهای harrop ارثی (HH) است که clauseهای Horn سنتی Prolog را با چند ابرقدرت تازه گسترش می‌دهند.

    فراساختار goalها و clauseها

    در حل‌کنندهٔ Rust، goalها و clauseها شکل‌های زیر را دارند (توجه کنید که این دو تعریف به یکدیگر ارجاع می‌دهند):

    Goal = DomainGoal           // defined in the section below
        | Goal && Goal
        | Goal || Goal
        | exists<K> { Goal }   // existential quantification
        | forall<K> { Goal }   // universal quantification
        | if (Clause) { Goal } // implication
        | true                 // something that's trivially true
        | ambiguous            // something that's never provable

Clause = DomainGoal
        | Clause :- Goal     // if can prove Goal, then Clause is true
        | Clause && Clause
        | forall<K> { Clause }

K = <type>     // a "kind"
    | <lifetime>

    روش اثبات برای این نوع goalها در واقع کاملاً سرراست است. اساساً نوعی جستجوی عمق‌اول است. مقالهٔ “A Proof Procedure for the Logic of Hereditary Harrop Formulas” جزئیات را ارائه می‌دهد.

    از نظر کد، این نوع‌ها در rustc_middle/src/traits/mod.rs در rustc، و در chalk-ir/src/lib.rs در chalk تعریف شده‌اند.

    goalهای دامنه (Domain goals)

    goalهای دامنه اتم‌های منطق صفت‌اند. همان‌طور که از تعریف‌های بالا پیداست، goalهای عمومی اساساً از ترکیبی از goalهای دامنه تشکیل می‌شوند.

    افزون بر این، با کمی هموار کردن تعریف clauseها که پیش‌تر داده شد، می‌توان دید که clauseها همیشه به این شکل‌اند:

    forall<K1, ..., Kn> { DomainGoal :- Goal }

    بنابراین goalهای دامنه در واقع سمت چپ (LHS) clauseها هستند. یعنی در ریزترین سطح، goalهای دامنه چیزهایی‌اند که حل‌کنندهٔ صفت در نهایت می‌کوشد اثبات کند.

    برای تعریف مجموعهٔ goalهای دامنه در سامانهٔ خود، ابتدا باید چند صورت‌بندی ساده معرفی کنیم. یک ارجاع صفت (trait reference) شامل نام یک صفت به‌همراه مجموعهٔ مناسبی از ورودی‌های P0..Pn است:

    TraitRef = P0: TraitName<P1..Pn>

    پس برای مثال، u32: Display یک ارجاع صفت است، همان‌طور که Vec<T>: IntoIterator هم هست. توجه کنید که نحو ظاهری Rust چیزهای اضافه‌ای هم مجاز می‌داند، مانند مقیدسازی نوع وابسته (Vec<T>: IntoIterator<Item = T>) که بخشی از ارجاع صفت نیستند.

    یک projection شامل ارجاع به یک آیتم وابسته به‌همراه ورودی‌های آن P0..Pm است:

    Projection = <P0 as TraitName<P1..Pn>>::AssocItem<Pn+1..Pm>

    با داشتن این‌ها، می‌توانیم DomainGoal را چنین تعریف کنیم:

    DomainGoal = Holds(WhereClause)
            | FromEnv(TraitRef)
            | FromEnv(Type)
            | WellFormed(TraitRef)
            | WellFormed(Type)
            | Normalize(Projection -> Type)

WhereClause = Implemented(TraitRef)
            | ProjectionEq(Projection = Type)
            | Outlives(Type: Region)
            | Outlives(Region: Region)

    WhereClause به یک where clause اشاره دارد که کاربر Rust واقعاً می‌تواند در برنامهٔ Rust بنویسد. این انتزاع فقط برای راحتی وجود دارد، چون گاهی می‌خواهیم فقط با goalهای دامنه‌ای سروکار داشته باشیم که عملاً در Rust قابل نوشتن‌اند.

    بیایید هر یک از این‌ها را یکی‌یکی بشکافیم.

    Implemented(TraitRef)

    مثلاً Implemented(i32: Copy)

    درست است اگر صفت داده‌شده برای نوع‌ها و طول عمرهای ورودی داده‌شده پیاده‌سازی شده باشد.

    ProjectionEq(Projection = Type)

    مثلاً ProjectionEq<T as Iterator>::Item = u8

    نوع وابستهٔ داده‌شدهٔ Projection با Type برابر است؛ این را می‌توان با نرمال‌سازی یا با استفاده از نوع‌های وابستهٔ جانگهدار (placeholder) ثابت کرد. ببینید بخش مربوط به نوع‌های وابسته در Chalk Book.

    Normalize(Projection -> Type)

    مثلاً ProjectionEq<T as Iterator>::Item -> u8

    نوع وابستهٔ داده‌شدهٔ Projection را می‌توان به Type نرمال‌سازی کرد.

    همان‌طور که در بخش مربوط به نوع‌های وابسته در Chalk Book بحث شد، Normalize مستلزم ProjectionEq است، اما برعکس نه. در حالت کلی، اثبات Normalize(<T as Trait>::Item -> U) مستلزم اثبات Implemented(T: Trait) هم هست.

    FromEnv(TraitRef)

    مثلاً FromEnv(Self: Add<i32>)

    درست است اگر TraitRef درونی فرض شده درست باشد، یعنی اگر بتوان آن را از where clauseهای در دسترس استنتاج کرد.

    برای مثال، تابع زیر را در نظر بگیرید:

    fn loud_clone<T: Clone>(stuff: &T) -> T {
    println!("cloning!");
    stuff.clone()
}

    درون بدنهٔ تابع ما، FromEnv(T: Clone) را خواهیم داشت. where clauseهای در دسترس تودرتو می‌شوند، پس بدنهٔ یک تابع درون بدنهٔ یک impl، where clauseهای بدنهٔ impl را هم به ارث می‌برد.

    این قاعده و قاعدهٔ بعدی برای پیاده‌سازی کران‌های ضمنی (implied bounds) به کار می‌روند. همان‌طور که در بخش lowering خواهیم دید، FromEnv(TraitRef) مستلزم Implemented(TraitRef) است، اما برعکس نه. این تمایز برای کران‌های ضمنی حیاتی است.

    FromEnv(Type)

    مثلاً FromEnv(HashSet<K>)

    درست است اگر Type درونی فرض شده well-formed باشد، یعنی اگر نوع ورودی یک تابع یا یک impl باشد.

    برای مثال، کد زیر را در نظر بگیرید:

    struct HashSet<K> where K: Hash { ... }

fn loud_insert<K>(set: &mut HashSet<K>, item: K) {
    println!("inserting!");
    set.insert(item);
}

    HashSet<K> نوع ورودی تابع loud_insert است. بنابراین فرض می‌کنیم well-formed است، پس درون بدنهٔ تابع خود FromEnv(HashSet<K>) را خواهیم داشت. همان‌طور که در بخش lowering خواهیم دید، FromEnv(HashSet<K>) مستلزم Implemented(K: Hash) است، زیرا اعلان HashSet با یک where clause به شکل K: Hash نوشته شده بود. بنابراین لازم نیست آن کران را روی تابع loud_insert تکرار کنیم: بلکه به‌طور خودکار فرض می‌کنیم درست است.

    WellFormed(Item)

    این goalها دلالت دارند که آیتم داده‌شده well-formed است.

    می‌توانیم دربارهٔ well-formed بودن انواع مختلف آیتم‌ها صحبت کنیم:

    • نوع‌ها، مانند WellFormed(Vec<i32>) که در Rust درست است، یا WellFormed(Vec<str>) که درست نیست (زیرا str برابر Sized نیست.)

    • TraitRefها، مانند WellFormed(Vec<i32>: Clone).

    well-formed بودن برای کران‌های ضمنی مهم است. به‌ویژه، دلیل اینکه فرض FromEnv(T: Clone) در مثال loud_clone اشکالی ندارد این است که همچنین WellFormed(T: Clone) را برای هر محل فراخوانی loud_clone وارسی می‌کنیم. به‌همین‌ترتیب، فرض FromEnv(HashSet<K>) در مثال loud_insert اشکالی ندارد، زیرا WellFormed(HashSet<K>) را برای هر محل فراخوانی loud_insert وارسی خواهیم کرد.

    Outlives(Type: Region), Outlives(Region: Region)

    مثلاً Outlives(&'a str: 'b)، Outlives('a: 'static)

    درست است اگر نوع یا ناحیهٔ داده‌شدهٔ سمت چپ از ناحیهٔ سمت راست بیشتر عمر کند (outlive).

    goalهای هم‌استقرایی (Coinductive)

    بیشتر goalها در سامانهٔ ما «استقرایی (inductive)» هستند. در یک goal استقرایی، استدلال دوری مجاز نیست. این clause نمونه را در نظر بگیرید:

        Implemented(Foo: Bar) :-
        Implemented(Foo: Bar).

    اگر استقرایی در نظر بگیریم، این clause بی‌فایده است: اگر بخواهیم Implemented(Foo: Bar) را اثبات کنیم، آن‌گاه باید به‌صورت بازگشتی Implemented(Foo: Bar) را اثبات کنیم و این چرخه تا بی‌نهایت ادامه می‌یابد (حل‌کنندهٔ صفت اینجا متوقف می‌شود، و صرفاً Implemented(Foo: Bar) را «شناخته‌شده به‌عنوان درست» نمی‌پندارد).

    با این حال، برخی goalها هم‌استقرایی (co-inductive) هستند. به زبان ساده، یعنی چرخه‌ها مشکلی ندارند. پس اگر Bar یک صفت هم‌استقرایی بود، قاعدهٔ بالا کاملاً معتبر می‌بود و نشان می‌داد Implemented(Foo: Bar) درست است.

    صفت‌های خودکار (Auto traits) یک نمونه در Rust هستند که در آن‌ها goalهای هم‌استقرایی به کار می‌روند. صفت Send را در نظر بگیرید و تصور کنید این struct را داریم:

    struct Foo {
    next: Option<Box<Foo>>
}

    قواعد پیش‌فرض صفت‌های خودکار می‌گویند Foo برابر Send است اگر نوع فیلدهایش Send باشند. بنابراین قاعده‌ای مانند این خواهیم داشت

    Implemented(Foo: Send) :-
    Implemented(Option<Box<Foo>>: Send).

    همان‌طور که احتمالاً می‌توانید تصور کنید، اثبات اینکه Option<Box<Foo>>: Send به‌صورت دوری دوباره ما را ملزم می‌کند ثابت کنیم Foo: Send. پس این نمونه‌ای است که در آن به یک چرخه می‌رسیم – اما اشکالی ندارد، ما واقعاً Foo: Send را برقرار می‌دانیم، هرچند به خودش ارجاع می‌دهد.

    به‌طور کلی، صفت‌های هم‌استقرایی در حل صفت Rust وقتی به کار می‌روند که بخواهیم مجموعهٔ ثابتی از امکان‌ها را برشماریم. در مورد صفت‌های خودکار، مجموعهٔ نوع‌های قابل دسترس از یک نقطهٔ شروع مفروض را برمی‌شماریم (یعنی Foo می‌تواند به مقادیری از نوع Option<Box<Foo>> برسد، که یعنی می‌تواند به مقادیری از نوع Box<Foo> و سپس از نوع Foo برسد، و بعد چرخه کامل می‌شود).

    افزون بر صفت‌های خودکار، گزاره‌های WellFormed هم‌استقرایی‌اند. این‌ها برای رسیدن به الگوی مشابهی از «برشمردن همهٔ حالت‌ها» به کار می‌روند، همان‌طور که در بخش کران‌های ضمنی توضیح داده شد.
