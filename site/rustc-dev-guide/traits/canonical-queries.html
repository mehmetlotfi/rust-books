    پرس‌وجوهای کانونی (Canonical queries)

    «آغاز» سامانهٔ صفت (trait) همان query کانونی است (این‌ها هم query به معنای عام کلمه‌اند – چیزی که دوست دارید پاسخش را بدانید – و هم به معنای خاص rustc). ایده این است که type checker یا بخش‌های دیگر سامانه، در حین انجام کار خود ممکن است بخواهند بدانند آیا صفتی برای نوعی پیاده‌سازی شده است (مثلاً آیا u32: Debug درست است؟). یا ممکن است بخواهند یک نوع وابسته را نرمال‌سازی کنند.

    این بخش query‌ها را در سطح انتزاع نسبتاً بالا پوشش می‌دهد. زیربخش‌ها دقیق‌تر بررسی می‌کنند این ایده‌ها در rustc چگونه پیاده‌سازی شده‌اند.

    query سنتی و تعاملی Prolog

    در یک سامانهٔ Prolog سنتی، وقتی یک query را شروع می‌کنید، حل‌کننده (solver) شروع می‌کند و هر پاسخ ممکنی را که پیدا کند به شما می‌دهد. پس با چیزی مانند این:

    ?- Vec<i32>: AsRef<?U>

    حل‌کننده ممکن است چنین پاسخ دهد:

    Vec<i32>: AsRef<[i32]>
    continue? (y/n)

    این بخش continue جالب است. ایده در Prolog این است که حل‌کننده همهٔ نمونه‌سازی‌های ممکن query شما را که درست‌اند پیدا می‌کند. در اینجا، اگر ?U = [i32] را نمونه‌سازی کنیم، query درست است (توجه کنید که یک رابط Prolog سنتی مستقیماً مقدار ?U را به ما نمی‌گوید، اما می‌توانیم با یکسان‌سازی (unify) پاسخ با query اصلی‌مان آن را استنتاج کنیم – حل‌کنندهٔ Rust در عوض یک جایگزین (substitution) برمی‌گرداند). اگر y را بزنیم، حل‌کننده ممکن است پاسخ ممکن دیگری به ما بدهد:

    Vec<i32>: AsRef<Vec<i32>>
    continue? (y/n)

    این پاسخ از این واقعیت ناشی می‌شود که یک impl بازتابی (impl<T> AsRef<T> for T) برای AsRef وجود دارد. اگر دوباره y را بزنیم، ممکن است پاسخ منفی بگیریم:

    no

    طبیعتاً در برخی موارد ممکن است هیچ پاسخ ممکنی وجود نداشته باشد، و بنابراین حل‌کننده بلافاصله no برمی‌گرداند:

    ?- Box<i32>: Copy
    no

    در برخی موارد ممکن است تعداد بی‌نهایت پاسخ وجود داشته باشد. مثلاً اگر این query را بدهم و مدام y را بزنم، حل‌کننده هرگز از برگرداندن پاسخ باز نمی‌ایستد:

    ?- Vec<?U>: Clone
    Vec<i32>: Clone
        continue? (y/n)
    Vec<Box<i32>>: Clone
        continue? (y/n)
    Vec<Box<Box<i32>>>: Clone
        continue? (y/n)
    Vec<Box<Box<Box<i32>>>>: Clone
        continue? (y/n)

    همان‌طور که می‌توانید تصور کنید، حل‌کننده با خوشحالی لایهٔ دیگری از Box اضافه می‌کند تا وقتی که از او بخواهیم متوقف شود، یا حافظه‌اش تمام شود.

    نکتهٔ جالب دیگر این است که query‌ها ممکن است همچنان متغیر داشته باشند. برای مثال:

    ?- Rc<?T>: Clone

    ممکن است این پاسخ را تولید کند:

    Rc<?T>: Clone
    continue? (y/n)

    در نهایت، Rc<?T> صرف‌نظر از اینکه ?T چه نوعی باشد درست است.

    یک query صفت در rustc

    query‌های صفت در rustc تا حدی متفاوت کار می‌کنند. به‌جای تلاش برای برشمردن همهٔ پاسخ‌های ممکن برای شما، به دنبال یک پاسخ بدون ابهام هستند. به‌ویژه، وقتی مقدار یک متغیر نوع را به شما می‌گویند، یعنی این تنها نمونه‌سازی ممکنی است که با توجه به مجموعهٔ فعلی impl‌ها و where-clauseها قابل اثبات است و می‌توانید از آن استفاده کنید.

    پاسخ یک query صفت در rustc معمولاً Result<QueryResult<T>, NoSolution> است (که T کمی بسته به خود query تغییر می‌کند). حالت Err(NoSolution) نشان می‌دهد query نادرست بوده و هیچ پاسخی نداشته است (مثلاً Box<i32>: Copy). در غیر این صورت، QueryResult اطلاعاتی دربارهٔ پاسخ(های) ممکنی که پیدا کرده‌ایم برمی‌گرداند. از چهار بخش تشکیل شده است:

    • Certainty (قطعیت): نشان می‌دهد چقدر از این پاسخ مطمئنیم. دو مقدار می‌تواند داشته باشد:
      • Proven یعنی نتیجه به‌طور قطعی درست است.
        • این ممکن است نتیجهٔ تلاش برای اثبات مثلاً Vec<i32>: Clone یا Rc<?T>: Clone باشد.
      • Ambiguous یعنی چیزهایی بود که هنوز نتوانستیم درست یا نادرست بودنشان را ثابت کنیم، معمولاً چون اطلاعات نوع بیشتری لازم بود. (به‌زودی مثالی خواهیم دید.)
        • این ممکن است نتیجهٔ تلاش برای اثبات Vec<?T>: Clone باشد.
    • Var values (مقادیر متغیرها): مقادیر هر یک از متغیرهای استنتاج بدون مقدار (مانند ?T) که در query اصلی شما ظاهر شده بودند. (به یاد داشته باشید که در Prolog باید این‌ها را خودمان استنتاج می‌کردیم.)
      • همان‌طور که در مثال زیر خواهیم دید، حتی برای حالت‌های Ambiguous هم می‌توانیم مقادیر متغیرها را پس بگیریم.
    • Region constraints (قیدهای ناحیه): این‌ها روابطی هستند که باید میان طول عمرهایی که به‌عنوان ورودی داده‌اید برقرار باشند. در اینجا آن‌ها را نادیده می‌گیریم.
    • Value (مقدار): نتیجهٔ query همچنین با مقداری از نوع T همراه است. برای برخی query‌های تخصصی – مانند نرمال‌سازی نوع‌های وابسته – از آن برای برگرداندن یک نتیجهٔ اضافی استفاده می‌شود، اما اغلب فقط () است.

    مثال‌ها

    بیایید یک query نمونه را مرور کنیم تا ببینیم همهٔ بخش‌ها چه معنایی دارند. صفت Borrow را در نظر بگیرید. این صفت تعدادی impl دارد؛ از جمله این دو (برای وضوح، کران‌های Sized را صریح نوشته‌ام):

    impl<T> Borrow<T> for T where T: ?Sized
impl<T> Borrow<[T]> for Vec<T> where T: Sized

    مثال ۱. تصور کنید در حال بررسی نوع این قطعه کد (نسبتاً مصنوعی) هستیم:

    fn foo<A, B>(a: A, vec_b: Option<B>) where A: Borrow<B> { }

fn main() {
    let mut t: Vec<_> = vec![]; // Type: Vec<?T>
    let mut u: Option<_> = None; // Type: Option<?U>
    foo(t, u); // Example 1: requires `Vec<?T>: Borrow<?U>`
    ...
}

    همان‌طور که توضیحات نشان می‌دهند، ابتدا دو متغیر t و u می‌سازیم؛ t یک بردار خالی و u یک option از نوع None است. هر دوی این متغیرها در نوع خود متغیرهای استنتاج بدون مقدار دارند: ?T عناصر بردار t را نشان می‌دهد و ?U مقدار ذخیره‌شده در option یعنی u را. سپس foo را فراخوانی می‌کنیم؛ با مقایسهٔ امضای foo با آرگومان‌هایش به A = Vec<?T> و B = ?U می‌رسیم. بنابراین، where clause روی foo ایجاب می‌کند که Vec<?T>: Borrow<?U> برقرار باشد. این اولین query صفت نمونهٔ ماست.

    برای query ‏Vec<?T>: Borrow<?U> راه‌حل‌های ممکن فراوانی وجود دارد؛ برای مثال:

    • ?U = Vec<?T>,
    • ?U = [?T],
    • ?T = u32, ?U = [u32]
    • و به همین ترتیب.

    بنابراین نتیجه‌ای که پس می‌گیریم چنین خواهد بود (قیدهای ناحیه و «مقدار» را نادیده می‌گیرم):

    • Certainty: ‏Ambiguous – هنوز مطمئن نیستیم این برقرار است یا نه
    • Var values: ‏[?T = ?T, ?U = ?U] – چیزی دربارهٔ مقادیر متغیرها یاد نگرفتیم

    خلاصه اینکه نتیجهٔ query می‌گوید هنوز زود است دربارهٔ اثبات‌شدن این صفت چیز زیادی بگوییم. هنگام بررسی نوع، این یک خطای فوری نیست: در عوض، type checker این الزام (Vec<?T>: Borrow<?U>) را نگه می‌دارد و منتظر می‌ماند. همان‌طور که در مثال بعدی خواهیم دید، ممکن است ?T و ?U از منابع دیگر مقید شوند، که در آن صورت می‌توانیم query صفت را دوباره امتحان کنیم.

    مثال ۲. اکنون می‌توانیم مثال قبلی را کمی گسترش دهیم و به u مقداری بدهیم:

    fn foo<A, B>(a: A, vec_b: Option<B>) where A: Borrow<B> { }

fn main() {
    // What we saw before:
    let mut t: Vec<_> = vec![]; // Type: Vec<?T>
    let mut u: Option<_> = None; // Type: Option<?U>
    foo(t, u); // `Vec<?T>: Borrow<?U>` => ambiguous

    // New stuff:
    u = Some(vec![]); // ?U = Vec<?V>
}

    در نتیجهٔ این انتساب، نوع u ناگزیر Option<Vec<?V>> می‌شود، که ?V نوع عنصر بردار را نشان می‌دهد. این به‌نوبهٔ خود یعنی ?U با Vec<?V> یکسان‌سازی می‌شود.

    فرض کنیم type checker تصمیم می‌گیرد به الزام صفتِ «هنوز اثبات‌نشدهٔ» قبلی یعنی Vec<?T>: Borrow<?U> دوباره نگاهی بیندازد. ?U دیگر یک متغیر استنتاج بدون مقدار نیست؛ اکنون مقدار Vec<?V> را دارد. پس اگر query را با این مقدار «تازه‌سازی» کنیم، می‌رسیم به:

    Vec<?T>: Borrow<Vec<?V>>

    این بار فقط یک impl قابل اعمال است، همان impl بازتابی:

    impl<T> Borrow<T> for T where T: ?Sized

    بنابراین trait checker پاسخ می‌دهد:

    • Certainty: Proven
    • Var values: [?T = ?T, ?V = ?T]

    در اینجا می‌گوید که واقعاً ثابت کرده‌ایم این الزام برقرار است، و همچنین می‌دانیم ?T و ?V یک نوع‌اند (اما هنوز نمی‌دانیم آن نوع چیست!).

    (در واقع، چون تابع اینجا تمام می‌شود، type checker در این نقطه خطا می‌دهد، زیرا نوع عناصر t و u هنوز معلوم نیست، هرچند معلوم است که یکسان‌اند.)
