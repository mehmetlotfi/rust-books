    تبدیل به منطق (Lowering to logic)

    مشاهدهٔ کلیدی در اینجا این است که سامانهٔ صفت Rust اساساً نوعی منطق است و می‌توان آن را به قواعد استنتاج منطقی استاندارد نگاشت کرد. سپس می‌توانیم راه‌حل‌های این قواعد استنتاج را به شیوه‌ای بسیار شبیه به کار یک حل‌گر Prolog بجوییم. معلوم می‌شود که نمی‌توانیم دقیقاً از قواعد Prolog (که بندهای Horn نیز نامیده می‌شوند) استفاده کنیم و به گونه‌ای کمی رساتر نیاز داریم.

    صفت‌های Rust و منطق

    یکی از نخستین مشاهدات این است که سامانهٔ صفت Rust اساساً نوعی منطق است. به همین دلیل می‌توانیم اعلان‌های struct، trait و impl خود را به قواعد استنتاج منطقی نگاشت کنیم. در بیشتر موارد این‌ها اساساً بندهای Horn هستند، هرچند خواهیم دید که برای دربرگرفتن غنای کامل Rust – و به‌ویژه برای پشتیبانی از برنامه‌نویسی جنریک – باید کمی فراتر از بندهای Horn استاندارد برویم.

    برای دیدن اینکه این نگاشت چگونه کار می‌کند، با یک مثال شروع می‌کنیم. تصور کنید یک صفت و چند impl را این‌گونه اعلان می‌کنیم:

    trait Clone { }
impl Clone for usize { }
impl<T> Clone for Vec<T> where T: Clone { }

    می‌توانیم این اعلان‌ها را به برخی بندهای Horn، با نمادگذاری شبیه Prolog، به این شکل نگاشت کنیم:

    Clone(usize).
Clone(Vec<?T>) :- Clone(?T).

// The notation `A :- B` means "A is true if B is true".
// Or, put another way, B implies A.

    در اصطلاحات Prolog، می‌توانیم بگوییم Clone(Foo) – که در آن Foo یک نوع Rust است – یک گزاره (predicate) است که این ایده را نمایش می‌دهد که نوع Foo صفت Clone را پیاده‌سازی می‌کند. این قواعد بندهای برنامه هستند؛ آن‌ها شرایطی را بیان می‌کنند که تحت آن می‌توان آن گزاره را اثبات کرد (یعنی درست دانست). پس قاعدهٔ اول فقط می‌گوید «Clone برای usize پیاده‌سازی شده است». قاعدهٔ بعدی می‌گوید «برای هر نوع ?T، Clone برای Vec<?T> پیاده‌سازی شده است اگر clone برای ?T پیاده‌سازی شده باشد». بنابراین مثلاً اگر بخواهیم Clone(Vec<Vec<usize>>) را اثبات کنیم، این کار را با اعمال بازگشتی قواعد انجام می‌دهیم:

    • Clone(Vec<Vec<usize>>) قابل اثبات است اگر:
      • Clone(Vec<usize>) قابل اثبات باشد، که قابل اثبات است اگر:
        • Clone(usize) قابل اثبات باشد. (که هست، پس همه‌چیز خوب است.)

    اما حالا فرض کنید می‌خواستیم Clone(Vec<Bar>) را اثبات کنیم. این شکست می‌خورد (در نهایت، من impl از Clone برای Bar نداده‌ام):

    • Clone(Vec<Bar>) قابل اثبات است اگر:
      • Clone(Bar) قابل اثبات باشد. (اما نیست، چون هیچ قاعدهٔ قابل‌اعمالی وجود ندارد.)

    به‌آسانی می‌توانیم مثال بالا را برای صفت‌های جنریکی که بیش از یک نوع ورودی دارند گسترش دهیم. پس صفت Eq<T> را تصور کنید که اعلام می‌کند Self با مقداری از نوع T قابل مقایسهٔ برابری است:

    trait Eq<T> { ... }
impl Eq<usize> for usize { }
impl<T: Eq<U>> Eq<Vec<U>> for Vec<T> { }

    این را می‌توان این‌گونه نگاشت کرد:

    Eq(usize, usize).
Eq(Vec<?T>, Vec<?U>) :- Eq(?T, ?U).

    تا اینجا خوب است.

    بررسی نوع توابع عادی

    خب، حالا که چند قاعدهٔ منطقی تعریف کرده‌ایم که می‌توانند بیان کنند صفت‌ها چه زمانی پیاده‌سازی شده‌اند و نوع‌های وابسته را مدیریت کنند، بیایید کمی تمرکزمان را روی بررسی نوع (type-checking) بگذاریم. بررسی نوع جالب است چون همان چیزی است که goalهایی را که باید اثبات کنیم به ما می‌دهد. یعنی هرچه تا اینجا دیدیم دربارهٔ این بود که چگونه قواعدی را که با آن‌ها می‌توانیم goalها را اثبات کنیم از صفت‌ها و implهای برنامه به دست آوریم؛ اما ما به این هم علاقه‌مندیم که goalهایی را که باید اثبات کنیم چگونه به دست می‌آیند، و آن‌ها از بررسی نوع می‌آیند.

    بررسی نوع تابع foo() را در اینجا در نظر بگیرید:

    fn foo() { bar::<usize>() }
fn bar<U: Eq<U>>() { }

    البته این تابع بسیار ساده است: تنها کاری که می‌کند فراخوانی bar::<usize>() است. حالا با نگاه به تعریف bar() می‌بینیم که یک بند where دارد: U: Eq<U>. پس این یعنی foo() باید ثابت کند usize: Eq<usize> تا نشان دهد می‌تواند bar() را با usize به‌عنوان آرگومان نوع فراخوانی کند.

    اگر بخواهیم، می‌توانیم یک گزارهٔ Prolog بنویسیم که شرایطی را تعریف می‌کند که تحت آن bar() قابل فراخوانی است. می‌گوییم این شرایط «خوش‌ساخت» (well-formed) بودن نامیده می‌شوند:

    barWellFormed(?U) :- Eq(?U, ?U).

    سپس می‌توانیم بگوییم foo() بررسی نوع را می‌گذراند اگر ارجاع به bar::<usize> (یعنی bar() اعمال‌شده بر نوع usize) خوش‌ساخت باشد:

    fooTypeChecks :- barWellFormed(usize).

    اگر بخواهیم goal به نام fooTypeChecks را اثبات کنیم، موفق می‌شود:

    • fooTypeChecks قابل اثبات است اگر:
      • barWellFormed(usize)، که قابل اثبات است اگر:
        • Eq(usize, usize)، که به‌خاطر یک impl قابل اثبات است.

    خب، تا اینجا خوب است. بیایید به سراغ بررسی نوع یک تابع پیچیده‌تر برویم.

    بررسی نوع توابع جنریک: فراتر از بندهای Horn

    در بخش قبل، از بندهای Horn استاندارد Prolog (به‌علاوهٔ مفهوم برابری نوع در Rust) برای بررسی نوع چند تابع ساده Rust استفاده کردیم. اما این فقط وقتی کار می‌کند که توابع غیرجنریک را بررسی نوع کنیم. اگر بخواهیم یک تابع جنریک را بررسی نوع کنیم، معلوم می‌شود به مفهومی قوی‌تر از goal نیاز داریم نسبت به آنچه Prolog می‌تواند ارائه دهد. برای دیدن منظورم، بیایید مثال قبلی را بازسازی کنیم تا foo جنریک شود:

    fn foo<T: Eq<T>>() { bar::<T>() }
fn bar<U: Eq<U>>() { }

    برای بررسی نوع بدنهٔ foo، باید بتوانیم نوع T را «انتزاعی» نگه داریم. یعنی باید بررسی کنیم که بدنهٔ foo برای همهٔ نوع‌های T از نظر نوع ایمن است، نه فقط برای یک نوع مشخص. ممکن است این را این‌گونه بیان کنیم:

    fooTypeChecks :-
  // for all types T...
  forall<T> {
    // ...if we assume that Eq(T, T) is provable...
    if (Eq(T, T)) {
      // ...then we can prove that `barWellFormed(T)` holds.
      barWellFormed(T)
    }
  }.

    این نمادگذاری‌ای که اینجا به کار می‌برم همان نمادگذاری‌ای است که در پیاده‌سازی نمونهٔ اولیهٔ خودم به کار برده‌ام؛ شبیه نمادگذاری ریاضی استاندارد است اما کمی Rust‌پسند. به هر حال، مشکل این است که بندهای Horn استاندارد اجازهٔ سورگذاری عمومی (forall) یا استلزام (if) را در goalها نمی‌دهند (هرچند بسیاری از موتورهای Prolog به‌عنوان افزونه از آن‌ها پشتیبانی می‌کنند). به همین دلیل باید بندهایی را بپذیریم که «first-order hereditary harrop» (FOHH) نامیده می‌شوند – این نام بلند اساساً یعنی «بندهای Horn استاندارد با forall و if در بدنه». اما خوب است نام درست را بدانیم، چون کارهای زیادی وجود دارد که توضیح می‌دهند بندهای FOHH را چگونه کارا مدیریت کنیم؛ برای نمونه مقالهٔ عالی گوپالان ناداتور «A Proof Procedure for the Logic of Hereditary Harrop Formulas» را در کتاب‌نامهٔ کتاب Chalk ببینید.

    معلوم می‌شود پشتیبانی از FOHH واقعاً آن‌قدرها هم سخت نیست. و وقتی بتوانیم این کار را بکنیم، به‌آسانی می‌توانیم قاعدهٔ بررسی نوع برای توابع جنریکی مانند foo را در منطق خود توصیف کنیم.
