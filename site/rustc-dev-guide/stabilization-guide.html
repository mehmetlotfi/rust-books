راهنمای توسعهٔ rustcrustc Development Guide

    درخواست پایدارسازی

    نکته: این صفحه دربارهٔ پایدارسازی قابلیت‌های زبان است. برای پایدارسازی قابلیت‌های کتابخانه، پایدارسازی یک قابلیت کتابخانه را ببینید.

    وقتی یک قابلیت ناپایدار به‌خوبی تست شد و نگرانی باقی‌مانده‌ای نیست، هر کسی می‌تواند برای پایدارسازی آن پیگیری کند، هرچند درگیرکردن افرادی که روی آن کار کرده‌اند عاقلانه است. این گام‌ها را دنبال کنید:

    در صورت نیاز RFC بنویسید

    اگر قابلیت بخشی از یک آزمایش lang بوده، تیم lang عموماً می‌خواهد پیش از پایدارسازی ابتدا یک RFC پذیرفته شود.

    Documentation PRs

    ممکن است قابلیت در Unstable Book مستند شده باشد، که در src/doc/unstable-book قرار دارد. صفحهٔ مربوط به feature gate را در صورت وجود حذف کنید. بخش‌های مفید آن مستندات را در جاهای دیگر ادغام کنید.

    جاهایی که ممکن است نیاز به به‌روزرسانی مستندات داشته باشند شامل این‌هاست:

    • مرجع (The Reference): این باید با تمام جزئیات به‌روز شود، و یکی از اعضای تیم lang-docs باید PR را بازبینی و تأیید کند پیش از اینکه پایدارسازی بتواند merge شود.
    • کتاب (The Book): این در صورت نیاز به‌روز می‌شود. اگر مطمئن نیستید، لطفاً در این مخزن issueای باز کنید تا بحث شود.
    • مستندات کتابخانهٔ استاندارد: این در صورت نیاز به‌روز می‌شود. قابلیت‌های زبان اغلب به این نیاز ندارند، اما اگر قابلیتی نحوهٔ نوشتن مثال‌های اصطلاحی را تغییر می‌دهد، مثل وقتی که ? به زبان افزوده شد، به‌روزرسانی آن‌ها در مستندات کتابخانه مهم است. مستندات کلیدواژه‌ها و ABI در کتابخانهٔ استاندارد را هم بازبینی کنید، چون گاهی برای تغییرات زبان به‌روزرسانی لازم دارند.
    • Rust by Example: این در صورت نیاز به‌روز می‌شود.

    PRهایی را برای به‌روزرسانی مستندات مربوط به این قابلیت جدید در مخازن بالا آماده کنید. نگه‌دارندگان این مخازن آن PRها را تا تکمیل کل فرایند پایدارسازی باز نگه می‌دارند. در این بین می‌توانیم به گام بعد برویم.

    گزارش پایدارسازی بنویسید

    با استفاده از قالب موجود در این مخزن گزارش پایدارسازی تهیه کنید.

    گزارش پایدارسازی این‌ها را خلاصه می‌کند:

    • The main design decisions and deviations since the RFC was accepted, including both decisions that were FCP’d or otherwise accepted by the language team as well as those being presented to the lang team for the first time.
      • اغلب، قابلیت زبان پایدارشدهٔ نهایی انحرافات طراحی قابل‌توجهی از RFC اصلی دارد. اشکالی ندارد، اما این انحرافات باید برجسته و با دقت توضیح داده شوند.
    • کاری که از زمان پذیرش RFC انجام شده، با قدردانی از مشارکت‌کنندگان اصلی که به پیشبرد قابلیت زبان کمک کردند.

    قالب پایدارسازی مجموعه‌ای از پرسش‌ها دارد که هدفشان آشکار‌کردن ارتباط‌های این قابلیت با زیرتیم‌های lang (مثل types، opsem، lang-docs و غیره) و شناسایی مواردی است که معمولاً نادیده گرفته می‌شوند.

    گزارش پایدارسازی معمولاً به‌عنوان کامنت اصلی PR پایدارسازی منتشر می‌شود (بخش بعد را ببینید).

    Stabilization PR

    هر قابلیتی متفاوت است، و ممکن است برخی گام‌هایی فراتر از آنچه این راهنما بحث می‌کند لازم داشته باشند.

    پیش از اینکه تیم lang پایدارسازی را بررسی کند، باید یک PR کامل به مرجع (Reference) وجود داشته باشد که قابلیت را شرح می‌دهد، و پیش از merge شدن PR پایدارسازی، این PR باید توسط تیم lang-docs بازبینی و تأیید شده باشد.

    به‌روزرسانی فهرست feature-gateها

    فهرست مرکزی feature-gateهای ناپایدار در compiler/rustc_feature/src/unstable.rs قرار دارد. ماکرو declare_features! را جست‌وجو کنید. باید ورودی‌ای برای قابلیتی که قصد پایدارسازی آن را دارید باشد، چیزی شبیه این (برگرفته از rust-lang/rust#32409):

    // pub(restricted) visibilities (RFC 1422)
(unstable, pub_restricted, "CURRENT_RUSTC_VERSION", Some(32409)),

    خط بالا باید به compiler/rustc_feature/src/accepted.rs منتقل شود. ورودی‌های فراخوانی declare_features! مرتب‌شده‌اند، پس جای درست را بیابید. وقتی انجام شد، باید این‌طور به نظر برسد:

    // pub(restricted) visibilities (RFC 1422)
(accepted, pub_restricted, "CURRENT_RUSTC_VERSION", Some(32409)),
// note that we changed this

    (هرچند در فایل شمارهٔ نسخه‌های تغییرات گذشته را می‌بینید، نباید نسخهٔ rustc‌ای را که انتظار دارید پایدارسازی در آن رخ دهد بنویسید، بلکه به‌جای آن از CURRENT_RUSTC_VERSION استفاده کنید.)

    حذف استفاده‌های موجود از feature-gate

    سپس رشتهٔ قابلیت (در این مورد pub_restricted) را در codebase جست‌وجو کنید تا ببینید کجا ظاهر می‌شود. استفاده‌های #![feature(XXX)] را در std و هر crate مربوط به rustc (که شامل پوشه‌های تست زیر library/ و compiler/ است، اما نه tests/ سطح بالا) به #![cfg_attr(bootstrap, feature(XXX))] تغییر دهید. این شامل feature-gate فقط برای stage1 است که با beta فعلی ساخته می‌شود (این لازم است چون قابلیت در beta فعلی هنوز ناپایدار است).

    همچنین آن رشته‌ها را از هر تست (مثلاً زیر tests/) حذف کنید. اگر تست‌هایی هستند که به‌طور مشخص feature-gate را هدف می‌گیرند (یعنی تست می‌کنند feature-gate برای استفاده از قابلیت لازم است، اما نه چیز دیگر)، ساده‌اند تست را حذف کنید.

    لازم نکنید feature-gate برای استفاده از قابلیت باشد

    مهم‌تر از همه، کدی را حذف کنید که اگر feature-gate وجود نداشته باشد خطا علامت می‌زند (چون قابلیت اکنون پایدار محسوب می‌شود). اگر قابلیت را بتوان از نحو جدیدی که به‌کار می‌برد تشخیص داد، یک جای رایج برای آن کد compiler/rustc_ast_passes/src/feature_gate.rs است. برای مثال ممکن است کدی مثل این ببینید:

    gate_all!(pub_restricted, "`pub(restricted)` syntax is experimental");

    ماکرو gate_all! اگر قابلیت pub_restricted فعال نباشد خطا گزارش می‌دهد. اکنون که pub(restricted) پایدار است لازم نیست.

    برای قابلیت‌های ظریف‌تر ممکن است کدی مثل این بیابید:

    if self.tcx.features().async_fn_in_dyn_trait() { /* XXX */ }

    این فیلد pub_restricted (که بر اساس قابلیت نام‌گذاری شده) معمولاً اگر پرچم قابلیت وجود نداشته باشد false و اگر داشته باشد true است. پس کد را طوری تغییر دهید که فرض کند فیلد true است. در این مورد یعنی حذف if و باقی‌گذاشتن فقط /* XXX */.

    if self.tcx.sess.features.borrow().pub_restricted { /* XXX */ }
becomes
/* XXX */

if self.tcx.sess.features.borrow().pub_restricted && something { /* XXX */ }
 becomes
if something { /* XXX */ }

    Team nominations

    هنگام باز‌کردن PR پایدارسازی، تیم lang و مشاوران آن (@rust-lang/lang @rust-lang/lang-advisors) و هر تیم دیگری را که قابلیت به آن مربوط است CC کنید، مثلاً:

    • @rust-lang/types، برای تعامل با سامانهٔ نوع.
    • @rust-lang/opsem، برای تعامل با کد unsafe.
    • @rust-lang/compiler، برای استواری پیاده‌سازی.
    • @rust-lang/libs، برای تغییرات API کتابخانهٔ استاندارد یا تضمین‌های آن.
    • @rust-lang/lang-docs، برای پرسش‌هایی دربارهٔ اینکه این باید در مرجع چگونه مستند شود.

    پس از باز‌شدن PR پایدارسازی با گزارش پایدارسازی، کمی برای کامنت‌های فوری صبر کنید. وقتی آن کامنت‌ها «آرام» شدند و احساس کردید PR برای بررسی تیم lang آماده است، PR را نامزد کنید تا در دستور کار یکی از جلسات lang قرار گیرد.

    اگر عضو سازمان rust-lang نیستید، می‌توانید از بازبین تعیین‌شدهٔ خود بخواهید از طرف شما تیم‌های مربوط را CC کند.

    در PR پیشنهاد FCP بدهید

    پس از اینکه تیم lang و تیم‌های مرتبط دیگر پایدارسازی را بازبینی کردند، و پس از اینکه به هر پرسشی که داشتند پاسخ دادید، یکی از اعضای تیم‌ها ممکن است با کامنت‌گذاشتن پیشنهاد پذیرش پایدارسازی بدهد:

    @rfcbot fcp merge

    وقتی تعداد کافی از اعضای تیم بازبینی کردند، PR وارد «دورهٔ نظر نهایی» (FCP) می‌شود. اگر نگرانی جدیدی مطرح نشود، این دوره تمام می‌شود و PR پس از بازبینی پیاده‌سازی به شکل معمول می‌تواند merge شود.

    بازبینی و merge پایدارسازی‌ها

    در یک پایدارسازی، پیش از دادن r+، مطمئن شوید PR:

    • با آنچه تیم برای پایدارسازی پیشنهاد داد و آنچه در PR مرجع مستند شده مطابقت دارد.
    • شامل هر تغییری است که تیم در طول راه برای رفع یا پرهیز از نگرانی‌ها درخواست کرده است.
    • در غیر این صورت دقیقاً همان چیزی است که در گزارش پایدارسازی و در هر RFC مرتبط یا FCPهای قبلی lang توصیف شده است.
    • رفتارهایی غیر از آنچه مشخص، برای پایدارسازی پذیرفته و در مرجع مستند شده در stable نمایان نمی‌کند.
    • تست کافی دارد تا این موارد را به‌طور متقاعدکننده نشان دهد.
    • همراه PR به مرجع است که توسط یکی از اعضای lang-docs بازبینی و تأیید شده است.

    به‌ویژه هنگام بازبینی PR، مراقب هر جزئیات قابل‌مشاهده برای کاربر باشید که تیم lang آن را نادیده گرفته و مشخص نکرده است. اگر موردی یافتید، آن را توصیف کنید و PR را برای تیم lang نامزد کنید.
