    سریالایز‌کردن در rustc

    rustc باید در طول کامپایل داده‌های مختلف را سریالایز و دی‌سریالایز کند. به‌طور مشخص:

    • «فراداده crate»، که عمدتاً از خروجی کوئری‌ها تشکیل شده، از قالب دودویی به فایل‌های rlib و rmeta سریالایز می‌شود که هنگام کامپایل یک crate کتابخانه خروجی داده می‌شوند. این فایل‌های rlib و rmeta سپس توسط crateهایی که به آن کتابخانه وابسته‌اند دی‌سریالایز می‌شوند.
    • برخی خروجی‌های کوئری با قالب دودویی سریالایز می‌شوند تا نتایج کامپایل افزایشی را ماندگار کنند.
    • CrateInfo هنگام استفاده از پرچم JSON به -Z no-link سریالایز می‌شود و با پرچم JSON از -Z link-only دی‌سریالایز می‌شود.

    traitهای Encodable و Decodable

    crate با نام rustc_serialize دو trait برای نوع‌هایی که می‌توان سریالایز کرد تعریف می‌کند:

    pub trait Encodable<S: Encoder> {
    fn encode(&self, s: &mut S) -> Result<(), S::Error>;
}

pub trait Decodable<D: Decoder>: Sized {
    fn decode(d: &mut D) -> Result<Self, D::Error>;
}

    همچنین پیاده‌سازی این‌ها را برای نوع‌های رایج کتابخانهٔ استاندارد مثل نوع‌های اولیه مثل نوع‌های عدد صحیح، نوع‌های ممیز شناور، bool, char, strو غیره تعریف می‌کند.

    برای نوع‌هایی که از آن نوع‌ها ساخته می‌شوند، Encodable و Decodable معمولاً توسط deriveپیاده‌سازی می‌شوند. این‌ها پیاده‌سازی‌هایی تولید می‌کنند که دی‌سریالایز را به فیلدهای struct یا enum می‌سپارند. برای struct، آن implها چیزی شبیه این هستند:

    #![feature(rustc_private)]
extern crate rustc_serialize;
use rustc_serialize::{Decodable, Decoder, Encodable, Encoder};

struct MyStruct {
    int: u32,
    float: f32,
}

impl<E: Encoder> Encodable<E> for MyStruct {
    fn encode(&self, s: &mut E) -> Result<(), E::Error> {
        s.emit_struct("MyStruct", 2, |s| {
            s.emit_struct_field("int", 0, |s| self.int.encode(s))?;
            s.emit_struct_field("float", 1, |s| self.float.encode(s))
        })
    }
}

impl<D: Decoder> Decodable<D> for MyStruct {
    fn decode(s: &mut D) -> Result<MyStruct, D::Error> {
        s.read_struct("MyStruct", 2, |d| {
            let int = d.read_struct_field("int", 0, Decodable::decode)?;
            let float = d.read_struct_field("float", 1, Decodable::decode)?;

            Ok(MyStruct { int, float })
        })
    }
}

    انکد و دیکد نوع‌های تخصیص‌یافته از arena

    rustc نوع‌های تخصیص‌یافته از arenaزیادی داردرا ممکن می‌کنند. دی‌سریالایز این نوع‌ها بدون دسترسی به arenaای که باید در آن تخصیص یابند ممکن نیست. traitهای TyDecoder و TyEncoder زیرtraitهای Decoder و Encoder هستند که دسترسی به TyCtxt.

    نوع‌هایی که arena نوع‌های تخصیص‌یافته از arena دارند می‌توانند پارامتر نوع پیاده‌سازی‌های Encodable و Decodable خود را با این traitها محدود کنند. برای مثال

    impl<'tcx, D: TyDecoder<'tcx>> Decodable<D> for MyStruct<'tcx> {
    /* ... */
}

    ماکروهای TyEncodable و TyDecodable derive به چنین پیاده‌سازی‌ای گسترش می‌یابند.

    دیکد کردن نوع واقعی arena تخصیص‌یافته از arena دشوارتر است، چون برخی پیاده‌سازی‌ها به‌دلیل قواعد orphanقابل‌نوشتن نیستند. برای دورزدن این، trait با نام RefDecodable در rustc_middleتعریف شده است. آن را می‌توان برای هر نوعی پیاده‌سازی کرد. ماکرو TyDecodable برای دیکد کردن ارجاع‌ها RefDecodable را فراخوانی می‌کند، اما کد جنریک گوناگون لازم دارد نوع‌ها واقعاً Decodable با دیکودر مشخصی باشند.

    برای نوع‌های intern‌شده، به‌جای پیاده‌سازی دستی RefDecodable، استفاده از wrapper نوع جدید، مثل ty::Predicate و پیاده‌سازی دستی Encodable و Decodable ممکن است ساده‌تر باشد.

    Derive macros

    crate با نام rustc_macros derive‌های مختلفی برای کمک به پیاده‌سازی Decodable و Encodableتعریف می‌کند.

    • ماکروهای Encodable و Decodable پیاده‌سازی‌هایی تولید می‌کنند که برای همهٔ Encoders و Decodersاعمال می‌شوندرا پیاده‌سازی نمی‌کند. این‌ها باید در crateهایی استفاده شوند که به rustc_middleوابسته نیستند، یا باید توسط نوعی سریالایز شوند که TyEncoder.
    • MetadataEncodable پیاده‌سازی‌هایی تولید می‌کند که فقط دیکد توسط rustc_metadata::rmeta::encoder::EncodeContextرا مجاز می‌کنند.
    • BlobDecodable و LazyDecodable همتای دیکد برای MetadataEncodableهستند. پیاده‌سازی‌هایی تولید می‌کنند که با دیکودرهای blob فراداده در rustc_metadata::rmetaدیکد می‌کنند؛ وقتی نوع هیچ handle فراداده‌ٔ lazy ندارد از BlobDecodable استفاده کنید و وقتی دارد از LazyDecodable .
    • TyEncodable و TyDecodable پیاده‌سازی‌ای تولید می‌کنند که برای هر TyEncoder یا TyDecoderاعمال می‌شودهستند. این‌ها باید برای نوع‌هایی به‌کار روند که فقط در فرادادهٔ crate و/یا cache افزایشی سریالایز می‌شوند، که بیشتر نوع‌های سریالایزپذیر در rustc_middle.

    Shorthands

    Ty می‌تواند عمیقاً بازگشتی باشد؛ اگر هر Ty را ساده‌لوحانه انکد کنیم، فرادادهٔ crate بسیار بزرگ می‌شودبه‌کار می‌رود. برای مدیریت این، هر TyEncoder یک cache از مکان‌هایی در خروجی‌اش دارد که نوع‌ها را در آن‌ها سریالایز کرده است. اگر نوعی که انکد می‌شود در cache باشد، به‌جای سریالایز عادی نوع، آفست بایت درون فایل در حال نوشتن انکد می‌شود. طرح مشابهی برای ty::Predicate.

    LazyValue<T>

    فرادادهٔ crate پیش از ساخته‌شدن TyCtxt<'tcx> بارگذاری می‌شود، پس برخی دی‌سریالایزها باید از بارگذاری اولیهٔ فراداده به تعویق بیفتند. نوع LazyValue<T> آفست (نسبی) را در فرادادهٔ crate می‌پیچد که T در آن سریالایز شده است. چند گونه هم هست، LazyArray<T> و LazyTable<I, T>.

    نوع‌های LazyArray<[T]> و LazyTable<I, T> قابلیت‌هایی فراتر از Lazy<Vec<T>> و Lazy<HashMap<I, T>>فراهم می‌کنند:

    • می‌توان LazyArray<T> را مستقیماً از یک Iteratorانکد کرد، بدون اینکه ابتدا در Vec<T>جمع شود.
    • اندیس‌گذاری در LazyTable<I, T> نیازمند دیکد کردن ورودی‌ها نیست، جز آنکه در حال خواندن است.

    نکته: LazyValue<T> پس از اولین دی‌سریالایز مقدارش را cache نمی‌کند. در عوض، خود سامانهٔ کوئری راه اصلی cache کردن این نتایج است.

    Specialization

    چند نوع، به‌ویژه DefId، باید پیاده‌سازی‌های متفاوتی برای Encoderهای مختلف داشته باشنددارد. این فعلاً با تخصصی‌سازی‌های موردی مدیریت می‌شود، برای مثال: DefId یک پیاده‌سازی default از Encodable<E> و یکی تخصصی برای Encodable<CacheEncoder>.
