    بررسی الگو و جامعیت (exhaustiveness)

    در Rust، تطبیق الگو و bindingها چند ویژگی بسیار مفید دارند. کامپایلر بررسی می‌کند که bindingها هنگام ساخته شدن رد‌ناپذیر (irrefutable) باشند و شاخه‌های match جامع (exhaustive) باشند.

    کارآمدی الگو (usefulness)

    پرسش اصلی که بررسی usefulness به آن پاسخ می‌دهد این است: «در این عبارت match، آیا آن شاخه زائد است؟». دقیق‌تر بگوییم، این مسئله به محاسبه‌ی این برمی‌گردد که با داشتنِ فهرستی از الگوهایی که قبلاً دیده‌ایم، آیا یک الگوی جدید ممکن است با مقدار جدیدی تطبیق پیدا کند یا نه.

    برای مثال، در عبارت match زیر، به‌ترتیب می‌پرسیم آیا هر الگو ممکن است با چیزی تطبیق پیدا کند که الگوهای بالاترش آن را تطبیق نداده‌اند. در اینجا می‌بینیم الگوی چهارم نسبت به الگوی اول زائد است؛ آن شاخه یک هشدار «unreachable» دریافت می‌کند. الگوی سوم ممکن است مفید باشد یا نباشد، بسته به این‌که Foo علاوه بر Bar شمارنده‌های (variant) دیگری دارد یا نه. در نهایت، می‌توانیم بپرسیم آیا کل match جامع است، به این صورت که بپرسیم آیا الگوی wildcard (یعنی _) نسبت به فهرست همه‌ی الگوهای آن match مفید است. در اینجا می‌بینیم _ مفید است (حالت (false, None) را می‌گیرد)؛ بنابراین این عبارت خطای «non-exhaustive match» دریافت می‌کند.

    // x: (bool, Option<Foo>)
match x {
    (true, _) => {} // 1
    (false, Some(Foo::Bar)) => {} // 2
    (false, Some(_)) => {} // 3
    (true, None) => {} // 4
}

    بنابراین usefulness برای دو هدف استفاده می‌شود: تشخیص کد غیرقابل دسترس (که برای کاربر مفید است)، و اطمینان از جامع بودن matchها (که برای صحت (soundness) مهم است، چون یک عبارت match می‌تواند مقدار برگرداند).

    کجا رخ می‌دهد

    این بررسی در هر جایی که بتوانید الگو بنویسید انجام می‌شود: عبارت‌های match، if let، let else، let ساده و آرگومان‌های تابع.

    // `match`
// Usefulness can detect unreachable branches and forbid non-exhaustive matches.
match foo() {
    Ok(x) => x,
    Err(_) => panic!(),
}

// `if let`
// Usefulness can detect unreachable branches.
if let Some(x) = foo() {
    // ...
}

// `while let`
// Usefulness can detect infinite loops and dead loops.
while let Some(x) = it.next() {
    // ...
}

// Destructuring `let`
// Usefulness can forbid non-exhaustive patterns.
let Foo::Bar(x, y) = foo();

// Destructuring function arguments
// Usefulness can forbid non-exhaustive patterns.
fn foo(Foo { x, y }: Foo) {
    // ...
}

    الگوریتم

    بررسی جامعیت پیش از ساخت MIR در check_match اجرا می‌شود. این بررسی در crate با نام rustc_pattern_analysis پیاده‌سازی شده است، و هسته‌ی الگوریتم در ماژول usefulness قرار دارد. آن فایل شرح مفصلی از الگوریتم دارد.

    مفاهیم مهم

    سازنده‌ها و فیلدها

    در مقدار Pair(Some(0), true)، Pair سازنده‌ی (constructor) مقدار نامیده می‌شود و Some(0) و true فیلدهای آن هستند. هر مقدار قابل تطبیقی را می‌توان به این شکل تجزیه کرد. نمونه‌هایی از سازنده‌ها عبارت‌اند از: Some، None، (,) (سازنده‌ی تاپل دوتایی)، Foo {..} (سازنده‌ی ساختار Foo)، و 2 (سازنده‌ی عدد 2).

    هر سازنده تعداد ثابتی فیلد می‌گیرد؛ این تعداد arity نامیده می‌شود. Pair و (,) دارای arity برابر ۲ هستند، Some دارای arity برابر ۱ است، None و 42 دارای arity برابر ۰ هستند. هر نوع مجموعه‌ی مشخصی از سازنده‌ها دارد. برخی نوع‌ها سازنده‌های بسیار زیادی دارند (مانند u64) یا حتی بی‌نهایت سازنده (مانند &str و &[T]).

    الگوها هم مشابه‌اند: Pair(Some(_), _) سازنده‌ی Pair و دو فیلد دارد. تفاوت در این است که چند سازنده‌ی اضافی مخصوص الگو داریم، یعنی: wildcard یعنی _، bindingهای متغیر، بازه‌های صحیح مانند 0..=10، و slice‌های با طول متغیر مانند [_, .., _]. الگوهای or را جداگانه بررسی می‌کنیم.

    حال برای بررسی این‌که آیا مقدار v با الگوی p تطبیق دارد، بررسی می‌کنیم که آیا سازنده‌ی v با سازنده‌ی p تطبیق دارد، سپس در صورت لزوم فیلدهای آن‌ها را به‌صورت بازگشتی مقایسه می‌کنیم. چند مثال نمونه:

    • matches!(v, _) := true
    • matches!((v0, v1), (p0, p1)) := matches!(v0, p0) && matches!(v1, p1)
    • matches!(Foo { a: v0, b: v1 }, Foo { a: p0, b: p1 }) := matches!(v0, p0) && matches!(v1, p1)
    • matches!(Ok(v0), Ok(p0)) := matches!(v0, p0)
    • matches!(Ok(v0), Err(p0)) := false (شمارنده‌های ناسازگار)
    • matches!(v, 1..=100) := matches!(v, 1) || ... || matches!(v, 100)
    • matches!([v0], [p0, .., p1]) := false (طول‌های ناسازگار)
    • matches!([v0, v1, v2], [p0, .., p1]) := matches!(v0, p0) && matches!(v2, p1)

    این مفهوم در تحلیل الگو کاملاً محوری است. ماژول constructor توابعی برای استخراج، فهرست‌کردن و دستکاری سازنده‌ها فراهم می‌کند. این مفهوم آن‌قدر مفید است که گونه‌هایی از آن را در بخش‌های دیگر کامپایلر هم می‌توان یافت، مانند پایین‌آوری (lowering) عبارت match به MIR و برخی lintهای clippy.

    گروه‌بندی و تقسیم سازنده‌ها

    سازنده‌های مخصوص الگو (_، بازه‌ها و sliceهای با طول متغیر) هر کدام نماینده‌ی مجموعه‌ای از سازنده‌های معمولی هستند؛ مثلاً _: Option<T> نماینده‌ی مجموعه‌ی {None, Some} است و [_, .., _] نماینده‌ی مجموعه‌ی بی‌نهایت {[,], [,,], [,,,], …} از سازنده‌های slice با arity >= 2 است.

    برای مدیریت این سازنده‌ها، آن‌ها را تا حد امکان گروه‌بندی‌شده نگه می‌داریم. برای مثال:

    match (0, false) {
    (0 ..=100, true) => {}
    (50..=150, false) => {}
    (0 ..=200, _) => {}
}

    در این مثال، همه‌ی مقادیر 0، 1، .., 49 با شاخه‌های یکسانی تطبیق پیدا می‌کنند و بنابراین می‌توان آن‌ها را به‌صورت یک گروه در نظر گرفت. در واقع، در این match، تنها بازه‌هایی که باید در نظر بگیریم این‌ها هستند: 0..50، 50..=100، 101..=150، 151..=200 و 201... به‌طور مشابه:

    enum Direction { North, South, East, West }
let wind = (Direction::North, 0u8);
match wind {
    (Direction::North, 50..) => {}
    (_, _) => {}
}

    در اینجا می‌توانیم همه‌ی سازنده‌های غیر از North را یک گروه در نظر بگیریم و فقط دو حالت برای مدیریت باقی بماند: North و بقیه‌ی موارد.

    این کار «تقسیم سازنده‌ها» (constructor splitting) نامیده می‌شود و برای اجرای بررسی جامعیت در زمانی معقول حیاتی است.

    usefulness در برابر دسترسی‌پذیری (reachability) در حضور نوع‌های تهی

    این احتمالاً ظریف‌ترین جنبه‌ی بررسی جامعیت است. برای دقت کامل، یک match روی یک مقدار عمل نمی‌کند؛ روی یک مکان (place) عمل می‌کند. در برخی شرایط unsafe ممکن است یک مکان داده‌ی معتبری برای نوع خود نداشته باشد. این موضوع پیامدهای ظریفی برای نوع‌های تهی دارد. مثال زیر را در نظر بگیرید:

    enum Void {}
let x: u8 = 0;
let ptr: *const Void = &x as *const u8 as *const Void;
unsafe {
    match *ptr {
        _ => println!("Reachable!"),
    }
}

    در این مثال، ptr یک اشاره‌گر معتبر است که به مکانی با داده‌ی نامعتبر اشاره می‌کند. الگوی _ به محتوای مکان *ptr نگاه نمی‌کند، بنابراین این کد درست است و شاخه اجرا می‌شود. به عبارت دیگر، با وجود این‌که مکانی که بررسی می‌کنیم از نوع Void است، یک شاخه‌ی قابل دسترسی وجود دارد. اما اگر شاخه یک binding داشت:

    #[derive(Copy, Clone)]
enum Void {}
let x: u8 = 0;
let ptr: *const Void = &x as *const u8 as *const Void;
unsafe {
match *ptr {
    _a => println!("Unreachable!"),
}
}

    در اینجا binding مقداری از نوع Void را از مکان *ptr بارگذاری می‌کند. در این مثال، این کار باعث UB می‌شود، چون داده معتبر نیست. در حالت کلی، این کار معتبر بودن داده در *ptr را تأیید (assert) می‌کند. در هر صورت، این شاخه هرگز اجرا نخواهد شد.

    در نهایت، match تهی match *ptr {} را در نظر بگیریم. اگر آن را جامع بدانیم، آنگاه داشتن داده‌ی نامعتبر در *ptr نامعتبر است. به عبارت دیگر، match تهی از نظر معنایی با match به‌صورت _a => ... معادل است. به‌خاطر صریح بودن، حالت دارای شاخه را ترجیح می‌دهیم، از این رو به کاربر نمی‌گوییم شاخه‌ی _a را حذف کند. به عبارت دیگر، شاخه‌ی _a غیرقابل دسترسی است اما زائد نیست. به همین دلیل است که برای شاخه‌های زائد lint می‌دهیم نه برای شاخه‌های غیرقابل دسترسی، با این‌که پیام lint می‌گوید «unreachable».

    این ملاحظات فقط بر مکان‌های خاصی اثر می‌گذارند، یعنی مکان‌هایی که می‌توانند داده‌ی نامعتبر را بدون UB داشته باشند. این مکان‌ها عبارت‌اند از: dereference اشاره‌گر، dereference ارجاع و دسترسی به فیلد union. در طول بررسی جامعیت پیگیری می‌کنیم که آیا معلوم است یک مکان مشخص داده‌ی معتبر دارد یا نه.

    با همه‌ی این‌ها، پیاده‌سازی فعلی بررسی جامعیت از ملاحظات بالا پیروی نمی‌کند. در نسخه‌ی stable، نوع‌های تهی بیشتر اوقات غیرتهی در نظر گرفته می‌شوند. ویژگی exhaustive_patterns در سوی دیگر خطا می‌کند: اجازه می‌دهد شاخه‌هایی حذف شوند که در شرایط unsafe ممکن است قابل دسترسی باشند. ویژگی آزمایشی never_patterns هدفش رفع این مشکل و امکان‌دادن رفتار صحیح نوع‌های تهی در الگوهاست.
