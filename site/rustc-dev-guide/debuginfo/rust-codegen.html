راهنمای توسعهٔ rustcrustc Development Guide

    تولید کد در Rust

    نخستین فاز تولید اطلاعات اشکال‌زدایی (debug info) ایجاب می‌کند که Rust، MIR برنامه را بررسی کند و آن را به LLVM منتقل کند. این کار عمدتاً در rustc_codegen_llvm/debuginfo انجام می‌شود، هرچند مقداری پردازش نام نوع‌ها در rustc_codegen_ssa/debuginfo وجود دارد. Rust از طریق API ‏DIBuilder با LLVM ارتباط برقرار می‌کند، که پوششی باریک دور اجزای داخلی LLVM است و در rustc_llvm قرار دارد.

    اطلاعات نوع

    اطلاعات نوع معمولاً شامل نام نوع، اندازه و تراز (alignment) است، و در صورت ارتباط، مواردی مانند فیلدها، پارامترهای جنریک و مُغیِّرهای ذخیره‌سازی. بخش عمدهٔ این کار در rustc_codegen_llvm/src/debuginfo/metadata انجام می‌شود.

    مهم است به خاطر داشته باشید که هدف لزوماً «نمایش نوع‌ها دقیقاً به همان شکلی که در Rust ظاهر می‌شوند» نیست، بلکه نمایش آن‌ها به شکلی است که به اشکال‌زداها امکان دهد دقیق‌ترین بازسازی داده را هنگام اشکال‌زدایی انجام دهند. این تمایز برای درک کار اصلی‌ای که در این لایه رخ می‌دهد حیاتی است؛ بسیاری از تغییراتی که اینجا انجام می‌شوند برای دور زدن محدودیت‌های اشکال‌زداها هستند، آن هم وقتی هیچ گزینهٔ دیگری کار نکند.

    ویژگی‌های عجیب

    گره‌های DI تولیدشدهٔ Rust برای رضایت هم CDB و هم LLDB «وانمود می‌کنند» که C/C++ هستند. این می‌تواند به اطلاعات اشکال‌زدایی‌ای منجر شود که شهودی نیستند و با سبک رایج همخوانی ندارند.

    اشاره‌گرها و ارجاع‌ها

    اشاره‌گرها/ارجاع‌ها/Boxهای پهن (wide) مانند یک struct با ۲ فیلد در نظر گرفته می‌شوند: data_ptr و length.

    همهٔ اشاره‌گرها، ارجاع‌ها و اشاره‌گرهای Box غیرپهن به‌صورت گره‌های اشاره‌گر خروجی داده می‌شوند و میان mut و غیر mut تمایزی قائل نمی‌شود. چند تلاش برای اصلاح این موضوع انجام شده است، اما متأسفانه راه‌حل سرراستی وجود ندارد. استفاده از گره‌های DI با نام reference در قالب‌های مربوطه تله‌هایی دارد. میان ارجاع‌های C++ و ارجاع‌های Rust تفاوت معنایی‌ای وجود دارد که قابل جمع کردن نیست.

    از cppreference:

    ارجاع‌ها شیء نیستند؛ لزوماً فضای ذخیره‌سازی اشغال نمی‌کنند، هرچند کامپایلر ممکن است در صورت لزوم برای پیاده‌سازی معناشناسی مطلوب فضا تخصیص دهد (مثلاً عضو داده‌ای غیرایستا از نوع ارجاع معمولاً اندازهٔ کلاس را به‌اندازهٔ لازم برای ذخیرهٔ یک نشانی حافظه افزایش می‌دهد).

    چون ارجاع‌ها شیء نیستند، آرایه‌ای از ارجاع‌ها، اشاره‌گری به ارجاع‌ها و ارجاعی به ارجاع‌ها وجود ندارد

    راه‌حل پیشنهادی فعلی این است که به‌سادگی برای گره‌های اشاره‌گر typedef بسازیم.

    استفاده از مُحدِّد const برای نشان دادن غیر mut بودن، به‌دلیل بهینه‌سازی‌های داخلی LLDB مشکلات بالقوه‌ای دارد. به‌طور خلاصه، LLDB هنگام گام‌به‌گام اجرا کردن کد سعی می‌کند مقادیر فرزند متغیرها (مثلاً فیلدهای struct، عناصر آرایه) را کش کند. از یک روش ابتکاری (heuristic) برای تعیین اینکه کدام مقادیر به‌طور ایمن قابل کش‌اند استفاده می‌شود و const بخشی از آن روش است. دربارهٔ اینکه این با چیزهایی مانند سازه‌های تغییرپذیری درونی (interior mutability) در Rust چگونه تعامل می‌کند پژوهشی انجام نشده است.

    DWARF در برابر PDB

    هرچند بیشتر اطلاعات نوع نسبتاً سرراست است، یک مسئلهٔ قابل‌توجه قالب اطلاعات اشکال‌زدایی target است. هر قالب معناشناسی و محدودیت‌های متفاوتی دارد و به همین دلیل در برخی موارد به اطلاعات اشکال‌زدایی کمی متفاوتی نیاز دارند. این موضوع با فراخوانی‌های cpp_like_debuginfo کنترل می‌شود.

    نام‌گذاری

    Rust می‌کوشد نام نوع‌ها را تا حد ممکن دقیق منتقل کند، اما اشکال‌زداها و قالب‌های اطلاعات اشکال‌زدایی همیشه به آن احترام نمی‌گذارند.

    به‌دلیل محدودیت‌های تجزیه‌گر عبارت MSVC، تبدیل‌های نامی زیر برای اطلاعات اشکال‌زدایی PDB انجام می‌شوند:

    جنریک‌ها

    Rust اطلاعات نوع جنریک را (T در ArrayVec<T, N: usize>) خروجی می‌دهد، اما اطلاعات مقدار جنریک را (N در ArrayVec<T, N: usize>) خروجی نمی‌دهد.

    CodeView گره برگی برای جنریک‌ها/قالب‌های C++ ندارد، بنابراین همهٔ اطلاعات جنریک هنگام تولید اطلاعات اشکال‌زدایی PDB از دست می‌رود. راه‌های دور زدنی وجود دارد که به اشکال‌زدا اجازه می‌دهد آرگومان‌های جنریک را از طریق نام نوع بازیابی کند، اما در بهترین حالت راه‌حلی شکننده است. تلاش‌هایی در جریان است تا با مایکروسافت تماس گرفته شود و این کمبود اصلاح شود، و/یا یکی از نوع‌های گره استفاده‌نشدهٔ CodeView به‌عنوان معادلی مناسب به کار گرفته شود.

    نام‌های مستعار نوع

    Rust در چند مورد برای کمک به جبران محدودیت‌های اشکال‌زداها گره‌های typedef خروجی می‌دهد، اما در حال حاضر برای نام‌های مستعار نوع در کد منبع گره‌ای خروجی نمی‌دهد.

    enumها

    گره‌های DI مربوط به enum در rustc_codegen_llvm/src/debuginfo/metadata/enums تولید می‌شوند

    DWARF

    DWARF گره‌ای اختصاصی برای unionهای متمایزشده (discriminated unions) دارد: DW_TAG_variant. این یک ظرف است که به گره‌های DW_TAG_variant_part ارجاع می‌دهد که ممکن است مقدار discriminant داشته باشند یا نداشته باشند. سلسله‌مراتب به این شکل است:

    DW_TAG_structure_type      (top-level type for the coroutine)
  DW_TAG_variant_part      (variant part)
    DW_AT_discr            (reference to discriminant DW_TAG_member)
    DW_TAG_member          (discriminant member)
    DW_TAG_variant         (variant 1)
    DW_TAG_variant         (variant 2)
    DW_TAG_variant         (variant 3)
  DW_TAG_structure_type    (type of variant 1)
  DW_TAG_structure_type    (type of variant 2)
  DW_TAG_structure_type    (type of variant 3)

    PDB

    PDB گره اختصاصی ندارد، بنابراین معادل C یک union متمایزشده را تولید می‌کند:

    union enum2$<RUST_ENUM_NAME> {
    enum VariantNames {
        First,
        Second
    };
    struct Variant0 {
        struct First {
            // fields
        };
        static const enum2$<RUST_ENUM_NAME>::VariantNames NAME;
        static const unsigned long DISCR_EXACT;
        enum2$<RUST_ENUM_NAME>::Variant0::First value;
    };
    struct Variant1 {
        struct Second {
            // fields
        };
        static enum2$<RUST_ENUM_NAME>::VariantNames NAME;
        static unsigned long DISCR_EXACT;
        enum2$<RUST_ENUM_NAME>::Variant1::Second value;
    };
    enum2$<RUST_ENUM_NAME>::Variant0 variant0;
    enum2$<RUST_ENUM_NAME>::Variant1 variant1;
    unsigned long tag;
}

    نکتهٔ مهم این است که به‌دلیل محدودیت‌های LLDB، مقدار DISCR_* تولیدشده همیشه از نوع u64 است، حتی اگر مقدار #[repr(u64)] نباشد. این برای LLDB عمدتاً مشکلی نیست، چون مقدار DISCR_* و tag صرف‌نظر از نوعشان در مقادیر uint64_t خوانده می‌شوند.
