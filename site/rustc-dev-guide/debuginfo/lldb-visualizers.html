راهنمای توسعهٔ rustcrustc Development Guide

    LLDB - ارائه‌دهنده‌های Python (Python Providers)

    نکته: FFI مربوط به C++<->Python در LLDB نسخه‌ای از Python را انتظار دارد که هنگام کامپایل LLDB تعیین شده است. LLDB دقت می‌کند این نسخه را با کمینهٔ نسخه در توزیع‌های رایج Linux و macOS هماهنگ کند، اما در Windows راه‌حل آسانی نیست. اگر خطای import دربارهٔ وجود نداشتن _lldb دریافت کردید، احتمالاً علت ناسازگاری نسخهٔ Python است.

    LLDB در حال بررسی راه‌حل‌هایی برای این مشکل است. برای به‌روزرسانی‌ها، این بحث و این issue در github را ببینید

    نکته: تا نوامبر ۲۰۲۵، کمینهٔ نسخهٔ Python پشتیبانی‌شده توسط LLDB برابر 3.8 است، با برنامه برای ارتقا به 3.9 یا 3.10 بسته به چند عامل بیرونی. در حالت ایده‌آل اسکریپت‌ها باید فقط با قابلیت‌های موجود در کمینهٔ نسخهٔ Python پشتیبانی‌شده نوشته شوند. برای اطلاعات بیشتر این بحث را ببینید.

    نکته: مسیر بستهٔ Python مربوط به LLDB را می‌توان با دستور CLI ‏lldb -P یافت

    LLDB سه سازوکار برای سفارشی‌سازی خروجی فراهم می‌کند:

    • قالب‌ها (Formats)
    • ارائه‌دهنده‌های مصنوعی (Synthetic providers)
    • ارائه‌دهنده‌های خلاصه (Summary providers)

    قالب‌ها (Formats)

    مستندات رسمی اینجاست. به‌اختصار، قالب‌ها اجازه می‌دهند قالب چاپ پیش‌فرض نوع‌های اولیه تنظیم شود (مثلاً چاپ 25u8 به‌صورت دهدهی 25، شانزدهی 0x19 یا دودویی 00011001).

    Rust تقریباً همیشه باید unsigned char، signed char، char، u8 و i8 را به قالب دهدهی (بدون علامت) بازنویسی کند.

    ارائه‌دهنده‌های مصنوعی (Synthetic Providers)

    مستندات رسمی اینجاست، اما برخی اطلاعات مبهم، قدیمی یا کاملاً غایب است.

    تقریباً همهٔ تعامل کاربر با متغیرها از طریق اشیای SBValue در LLDB انجام می‌شود که هم در API پایتون و هم در درون از طریق افزونه‌ها و CLI مربوط به LLDB به کار می‌روند.

    Synthetic Provider یک کلاس Python است که با یک رابط مشخص نوشته می‌شود و با یک یا چند نوع Rust مرتبط می‌شود. Synthetic Provider اشیای SBValue را می‌پوشاند و LLDB هنگام بررسی متغیر توابع کلاس ما را فراخوانی می‌کند.

    مقدار پوشانده‌شده همچنان یک SBValue است، اما وقتی مثلاً SBValue.GetChildAtIndex فراخوانی می‌شود، در درون SyntheticProvider.get_child_at_index را فراخوانی می‌کند. می‌توانید با SBValue.IsSynthetic() بررسی کنید که آیا مقداری synthetic provider دارد، و با SBValue.GetTypeSynthetic() بفهمید کدام synthetic است. اگر می‌خواهید با مقدار غیر-synthetic زیرین تعامل کنید، می‌توانید SBValue.GetNonSyntheticValue() را فراخوانی کنید.

    رابط مورد انتظار به این شکل است:

    class SyntheticProvider:
    def __init__(self, valobj: SBValue, _lldb_internal): ...

    # optional
    def update(self) -> bool: ...

    # optional
    def has_children(self) -> bool: ...

    # optional
    def num_children(self, max_children: int) -> int: ...

    def get_child_index(self, name: str) -> int: ...

    def get_child_at_index(self, index: int) -> SBValue: ...

    # optional
    def get_type_name(self) -> str: ...

    # optional
    def get_value(self) -> SBValue: ...

    در ادامه توضیح متدها، نکات عجیب آن‌ها و چگونگی استفادهٔ عمومی‌شان آمده است. اگر متدی یک متد SBValue را بازنویسی کند، آن متد فهرست می‌شود.

    __init__

    این تابع یک بار برای هر شیء فراخوانی می‌شود و باید valobj را در کلاس Python ذخیره کند تا در جاهای دیگر در دسترس باشد. در اینجا باید بسیار کم کار دیگری انجام شود.

    (اختیاری) update

    این تابع پیش از تعامل LLDB با یک متغیر، اما پس از __init__ فراخوانی می‌شود. LLDB پیگیری می‌کند که آیا update از پیش فراخوانی شده است. اگر شده باشد و ممکن نباشد متغیر تغییر کرده باشد (مثلاً بررسی دوبارهٔ همان متغیر بدون گام برداشتن)، فراخوانی update را حذف می‌کند.

    این تابع دو هدف دارد:

    • ذخیره/به‌روزرسانی هر اطلاعاتی که ممکن است از آخرین باری که update اجرا شد تغییر کرده باشد
    • اطلاع دادن به LLDB اگر فرزندان تغییر کرده‌اند تا کش فرزندان را پاک کند.

    عملیات معمول شامل ذخیرهٔ اشاره‌گر heap، طول، ظرفیت و نوع عنصر یک Vec، تعیین گونهٔ یک متغیر enum، یا بررسی اینکه کدام جایگاه‌های یک HashMap اشغال شده‌اند است.

    مقدار bool برگردانده‌شده از این تابع تا حدی پیچیده است؛ برای اطلاعات بیشتر کش کردن update را در ادامه ببینید. در صورت تردید، False/None برگردانید. تا نوامبر ۲۰۲۵، هیچ‌یک از visualizerها True برنمی‌گردانند، اما این ممکن است با بهبود مجموعهٔ آزمون اطلاعات اشکال‌زدایی تغییر کند.

    کش کردن update

    LLDB در صورت امکان سعی می‌کند مقادیر، از جمله مقادیر فرزندان را کش کند. این کش در عمل تعداد اشیای فرزند و نشانی‌های حافظهٔ debuggee زیرینی است که شیء فرزند نمایش می‌دهد. با برگرداندن True، به LLDB می‌گویید تعداد فرزندان و نشانی‌های آن فرزندان از آخرین باری که update اجرا شد تغییر نکرده‌اند، یعنی می‌تواند از فرزندان کش‌شده دوباره استفاده کند.

    برگرداندن True در شرایط نادرست باعث می‌شود debugger اطلاعات نادرست خروجی دهد.

    برگرداندن False نشان می‌دهد تغییراتی رخ داده است، کش پاک می‌شود و فرزندان از ابتدا واکشی می‌شوند. اگر مطمئن نیستید این گزینهٔ امن‌تر است.

    تنها رابطه‌ای که اهمیت دارد والد-به-فرزند است. نوه‌ها به تابع update والد مستقیم خود وابسته‌اند، نه والد والد.

    مهم است که کش فرزندان را به‌صورت اشاره‌گر-به-حافظه ببینید. برای مثال، اگر مقدار data_ptr یک slice و length آن تغییر نکرده باشند، برگرداندن True مناسب است. حتی اگر slice تغییرپذیر باشد و عناصرش بازنویسی شوند (مثلاً slice[0] = 15)، چون کش فرزندان از اشاره‌گر تشکیل شده، داده‌های جدید در آن مکان حافظه را منعکس می‌کنند.

    برعکس، اگر data_ptr تغییر کرده باشد، یعنی به مکان جدیدی در حافظه اشاره می‌کند، اشاره‌گرهای فرزند نامعتبرند و کش باید پاک شود. اگر length تغییر کرده باشد، باید کش را پاک کنیم تا تعداد جدید فرزندان منعکس شود. اگر length تغییر کرده اما data_ptr نکرده باشد، می‌توان فرزندان قدیمی را در خود SyntheticProvider ذخیره کرد (مثلاً list[SBValue]) و آن‌ها را به‌جای تولید از ابتدا تحویل داد، و فقط در صورتی فرزندان جدید ساخت که از پیش در فهرست SyntheticProvider وجود نداشته باشند.

    برای توضیح بیشتر، این بحث را ببینید

    نکته: هنگام آزمودن رفتار کش، به اکتشاف (heuristic) LLDB برای ماندگار کردن متغیرها هنگام گام برداشتن تکیه نکنید. در عوض، متغیر را در یک شیء Python ذخیره کنید (مثلاً v = lldb.frame.var("var_name"))، جلو بروید و سپس متغیر ذخیره‌شده را بررسی کنید.

    (اختیاری) has_children

    SBValue.MightHaveChildren را بازنویسی می‌کند

    این میان‌بری است که LLDB برای بررسی اینکه آیا مقدار اصلاً فرزند دارد به کار می‌برد، بدون انجام محاسبات بالقوه گران برای تعیین تعداد فرزندان (مثلاً لیست پیوندی). اغلب، این یک تک‌خطی return True/return False یا return self.valobj.MightHaveChildren() خواهد بود.

    (اختیاری) num_children

    SBValue.GetNumChildren را بازنویسی می‌کند

    تعداد کل فرزندانی را برمی‌گرداند که LLDB هنگام چاپ نوع باید سعی کند به آن‌ها دسترسی یابد. این عدد لازم نیست با تعداد کل فرزندان synthetic برابر باشد.

    اگر محاسبهٔ تعداد فرزندان می‌تواند گران باشد، می‌توان آرگومان max_children را برگرداند (مثلاً لیست پیوندی). اگر این ملاحظه‌ای نیست، max_children را می‌توان از امضای تابع حذف کرد.

    افزون بر این، می‌توان فیلدها را عمداً از LLDB «پنهان» کرد در حالی که همچنان برای کاربر در دسترس‌اند. برای مثال، ممکن است بخواهید vec![1, 2, 3] فقط عناصرش را نمایش دهد، اما همچنان مقادیر len و capacity در صورت درخواست در دسترس باشند. با برگرداندن 3 از num_children، می‌توان LLDB را محدود کرد که فقط [1, 2, 3] را نمایش دهد، در حالی که کاربران همچنان مستقیماً به v.len و v.capacity دسترسی دارند. برای دیدن پیاده‌سازی این، ارائه‌دهندهٔ نمونه: Vec<T> را ببینید.

    get_child_index

    SBValue.GetIndexOfChildWithName را بازنویسی می‌کند

    SBValue.GetChildMemberWithName را تحت تأثیر قرار می‌دهد

    با گرفتن یک نام، اندیسی را برمی‌گرداند که فرزند باید در آن اندیس دسترسی شود. انتظار می‌رود مقدار بازگشتی این تابع مستقیماً به get_child_at_index داده شود. مانند num_children، مقادیر بازگشتی در اینجا می‌توانند دلبخواه باشند، به شرط اینکه به‌درستی با get_child_at_index هماهنگ شوند.

    یک مقدار ویژه $$dereference$$ است. در نظر گرفتن این شبه‌فیلد به LLDB اجازه می‌دهد SBValue برگردانده‌شده از get_child_at_index را به‌عنوان نتیجهٔ یک dereference از طریق تجزیه‌گر عبارت LLDB به کار ببرد (مثلاً *val و val->field)

    get_child_at_index

    SBValue.GetChildAtIndex را بازنویسی می‌کند

    با گرفتن یک اندیس، یک SBValue فرزند برمی‌گرداند. اغلب این‌ها با SBValue.CreateValueFromAddress تولید می‌شوند، اما کمتر با SBValue.CreateChildAtOffset، SBValue.CreateValueFromExpression و SBValue.CreateValueFromData. این توابع می‌توانند کمی وسواسی باشند، پس ممکن است لازم باشد برای گرفتن خروجی دلخواه با آن‌ها ور بروید.

    در برخی موارد SBValue.Clone مناسب است. فرزند جدیدی می‌سازد که نسخهٔ دقیق یک فرزند موجود اما با نام جدید است. این برای مواردی مانند tupleها مفید است که نام فیلدهایی از سبک __0، __1، … دارند در حالی که ترجیح می‌دهیم 0، 1، … نام بگیرند

    پیش از برگرداندن فرزند حاصل، می‌توان تغییرات کوچکی در آن داد. این برای &str/String مفید است، که ترجیح می‌دهیم فرزندان به‌صورت lldb.eFormatBytesWithASCII نمایش داده شوند نه فقط به‌صورت مقدار دهدهی.

    (اختیاری) get_type_name

    SBValue.GetDisplayTypeName را بازنویسی می‌کند

    نام نمایش‌داده‌شدهٔ یک نوع را بازنویسی می‌کند. برای یک SBValue مصنوعی که نام نوعش بازنویسی شده، نام نوع اصلی همچنان از SBValue.GetTypeName() و SBValue.GetType().GetName() قابل بازیابی است

    این می‌تواند در کوتاه کردن نام نوع‌های رایج کتابخانهٔ استاندارد مفید باشد (مثلاً std::collections::hash::map::HashMap<K, V, std::hash::random::RandomState> -> HashMap<K, V>)، یا در نرمال‌سازی نام نوع‌های MSVC (مثلاً ref$<str$> -> &str).

    دستکاری رشته می‌تواند کمی پیچیده باشد، به‌ویژه در MSVC که نمی‌توانیم به‌راحتی به پارامترهای جنریک نوع دسترسی داشته باشیم.

    (اختیاری) get_value

    SBValue.GetValue()، SBValue.GetValueAsUnsigned()، SBValue.GetValueAsSigned()، SBValue.GetValueAsAddress() را بازنویسی می‌کند،

    انتظار می‌رود SBValue برگردانده‌شده یک نوع اولیه یا اشاره‌گر باشد و در عبارت‌ها به‌عنوان مقدار متغیر در نظر گرفته می‌شود.

    مهم: SBValue برگردانده‌شده باید در SyntheticProvider ذخیره شود. تا نوامبر ۲۰۲۵، باگی وجود دارد که اگر SBValue درون get_value به دست آید و جایی ذخیره نشود، Python هنگامی که LLDB سعی می‌کند به مقدار دسترسی یابد segfault می‌کند.

    ارائه‌دهنده‌های خلاصه (Summary Providers)

    Summary providerها توابع Python با شکل زیر هستند:

    def SummaryProvider(valobj: SBValue, _lldb_internal) -> str: ...

    رشتهٔ برگردانده‌شده کلمه‌به‌کلمه به کاربر داده می‌شود. اگر مقدار برگردانده‌شده رشته نباشد، به‌ساده‌ترین شکل به رشته تبدیل می‌شود (مثلاً return None رشتهٔ "None" را چاپ می‌کند، نه رشتهٔ خالی).

    اگر SBValue ورودی از نوعی باشد که Synthetic Provider دارد، valobj.IsSynthetic() True برمی‌گرداند و توابع متناظر synthetic به کار می‌روند. اگر این نامطلوب است، می‌توان مقدار اصلی را با valobj.GetNonSyntheticValue() بازیابی کرد. این می‌تواند در مواردی مانند String مفید باشد، که فراخوانی جداگانهٔ GetChildAtIndex در یک حلقه بسیار کندتر از دسترسی به اشاره‌گر heap، خواندن کل آرایهٔ بایت مستقیماً از حافظهٔ debuggee و استفاده از bytes.decode() در Python است.

    خلاصه‌های نمونه (Instance Summaries)

    توابع معمولی SummaryProvider یک SBValue مات (opaque) می‌گیرند. آن SBValue در صورت وجود SyntheticProvider نوع را منعکس می‌کند، اما نمی‌توانیم به خود نمونهٔ SyntheticProvider یا هیچ‌یک از جزئیات پیاده‌سازی درونی‌اش دسترسی داشته باشیم. این در مواردی که برای تکمیل خلاصه به برخی از آن جزئیات درونی نیاز داریم زیان‌بار است. تا نوامبر ۲۰۲۵، در synthetic فقط مقدار غیر-synthetic را از synthetic provider عبور می‌دهیم (synth = SyntheticProvider(valobj.GetNonSyntheticValue(), _dict))، اما این آشکارا بهینه نیست و برنامه‌هایی برای استفاده از روش شرح‌داده‌شده در ادامه وجود دارد.

    در عوض می‌توانیم از وضعیت ماژول Python برای امکان خلاصه‌های نمونه بهره ببریم. سابقهٔ این تکنیک در اسکریپت‌های قدیمی visualizer مربوط به Rust در CodeLLDB وجود دارد.

    به‌اختصار: تابع __init__ هر Synthetic Provider یک شناسهٔ یکتا و یک ارجاع ضعیف به self را در یک دیکشنری سراسری ذخیره می‌کند. کلاس Synthetic Provider همچنین یک تابع get_summary پیاده‌سازی می‌کند. SummaryProvider نوع تابعی است که شناسهٔ یکتا را در این دیکشنری می‌یابد و سپس get_summary را روی نمونه‌ای که بازیابی می‌کند فراخوانی می‌کند.

    import weakref

SYNTH_BY_ID = weakref.WeakValueDictionary()

class SyntheticProvider:
    valobj: SBValue

    # slots requires opting-in to __weakref__
    __slots__ = ("valobj", "__weakref__")

    def __init__(valobj: SBValue, _dict):
        SYNTH_BY_ID[valobj.GetID()] = self
        self.valobj = valobj

    def get_summary(self) -> str:
        ...

def InstanceSummaryProvider(valobj: SBValue, _dict) -> str:
    # GetNonSyntheticValue should never fail as InstanceSummaryProvider implies an instance of a
    # `SyntheticProvider`. No non-synthetic types should ever have this summary assigned to them
    # We use GetNonSyntheticValue because the synthetic vaobj has its own unique ID
    return SYNTH_BY_ID[valobj.GetNonSyntheticValue().GetID()].get_summary()

    برای مثال، ممکن است این را برای synthetic provider مربوط به Enum به کار ببرید. خلاصه می‌خواهد به نام گونه دسترسی یابد، اما راه مناسبی برای بازتاب این از طریق نام نوع یا مقادیر فرزند synthetic نیست. با پیاده‌سازی یک instance summary، می‌توانیم نام گونه را از طریق self.variant.GetTypeName() و مقداری دستکاری رشته بازیابی کنیم.

    نوشتن اسکریپت‌های visualizer

    مهم: برخلاف GDB و CDB، LLDB می‌تواند فایل‌های اجرایی با اطلاعات اشکال‌زدایی DWARF یا PDB را اشکال‌زدایی کند. visualizerها باید تا حد امکان با در نظر گرفتن هر دو قالب نوشته شوند. برای مرور تفاوت‌ها rust-codegen را ببینید

    اسکریپت‌ها از طریق دستور CLI ‏command script import <path-to-script>.py به LLDB تزریق می‌شوند. پس از تزریق، می‌توان کلاس‌ها و توابع را به‌ترتیب با type synthetic add و type summary add به مخزن synthetic/summary اضافه کرد. خلاصه‌ها و syntheticها را می‌توان با یک «دسته (category)» مرتبط کرد که معمولاً به نام زبانی نام‌گذاری می‌شود که providerها برای آن در نظر گرفته شده‌اند. دسته‌ای که ما به کار می‌بریم Rust نام دارد.

    نکته: همهٔ دستورهای LLDB را می‌توان با help پیشوند داد (مثلاً help type synthetic add) تا توضیح کوتاه، فهرست آرگومان‌ها و مثال‌ها نشان داده شود.

    در گذشته از command source ... استفاده می‌کردیم که مجموعه‌ای از دستورهای CLI را از فایل lldb_commands برای افزودن providerها اجرا می‌کرد. این فایل تا حدی دست‌وپاگیر بود و با معادل API پایتون که در ادامه شرح داده شده جایگزین شده است.

    __lldb_init_module

    این یک تابع اختیاری با شکل زیر است:

    def __lldb_init_module(debugger: SBDebugger, _lldb_internal) -> None: ...

    این تابع در پایان command script import ... اما پیش از بازگشت کنترل به CLI فراخوانی می‌شود. به اسکریپت اجازه می‌دهد وضعیت خودش را مقداردهی اولیه کند.

    نکتهٔ حیاتی این است که یک ارجاع به خود debugger به آن داده می‌شود. این به ما اجازه می‌دهد دستهٔ Rust را بسازیم و providerها را به آن اضافه کنیم. همچنین می‌تواند به ما اجازه دهد به‌صورت شرطی تغییر دهیم کدام providerها را بسته به نسخه‌ای از LLDB که اسکریپت تشخیص می‌دهد به کار ببریم. این برای سازگاری با گذشته حیاتی است وقتی استفاده از recognizer functionها را آغاز کنیم، چون recognizerها در lldb 19.0 اضافه شدند.

    حل visualizer

    ترتیب حل visualizerها اینجا فهرست شده است. به‌اختصار:

    • اگر تطابق دقیقی وجود دارد (نام بدون regex، recognizer function، یا نوعی که از پیش با provider تطبیق یافته)، از آن استفاده کن
    • اگر شیء اشاره‌گر/ارجاع است، سعی کن از formatter نوع dereference‌شده استفاده کنی
    • اگر شیء typedef است، formatter نوع زیرین را بررسی کن
    • اگر هیچ‌یک از موارد بالا کار نکرد، matcherهای نوع regex را پیمایش کن

    در هر یک از این گام‌ها، پیمایش به‌صورت معکوس انجام می‌شود تا دستورهای جدید بتوانند دستورهای قدیمی را «بازنویسی» کنند. این برای مواردی مانند Box<str> در برابر Box<T> مهم است، که می‌خواهیم برای اولی یک synthetic تخصصی و برای دومی یک synthetic عمومی‌تر داشته باشیم.

    ریزه‌کاری‌ها

    API مربوط به LLDB بسیار قدرتمند است، اما چند «دام» و رفتار غیرشهودی دارد که برخی از آن‌ها در ادامه شرح داده می‌شود. پیاده‌سازی Python را می‌توان در مسیری که دستور CLI ‏lldb -P برمی‌گرداند در lldb\__init__.py دید. افزون بر مثال‌های مخزن lldb، visualizerهای C++ نیز هستند که می‌توان به‌عنوان مرجع به کار برد (مثلاً LibCxxVector، معادل Vec<T>). هرچند visualizerهای C++ با C++ نوشته شده‌اند و به درونیات LLDB دسترسی دارند، API و رویه‌های عمومی بسیار شبیه‌اند.

    SBValue

    • SBValueهای اشاره‌گر/ارجاع در برخی موارد در عمل «auto-deref» می‌کنند و طوری رفتار می‌کنند که گویی فرزندان شیء اشاره‌شده فرزندان خودشان‌اند.
    • فیلدهای غیرتابع معمولاً فیلدهای property() هستند که به‌هرحال مستقیماً به تابع اشاره می‌کنند (مثلاً SBValue.type = property(GetType, None)). دسترسی از طریق این میان‌برها اندکی کندتر از فراخوانی مستقیم تابع است، پس باید از آن‌ها پرهیز کرد. برخی از propertyها اشیای ویژه‌ای با ویژگی‌های ویژه برمی‌گردانند (مثلاً SBValue.member شیئی برمی‌گرداند که مانند dict[str, SBValue] برای دسترسی به فرزندان عمل می‌کند). در درون، بسیاری از این اشیای ویژه فقط یک نمونهٔ کلاس جدید تخصیص می‌دهند و به‌هرحال تابع را روی SBValue فراخوانی می‌کنند که به افت عملکرد بیشتر می‌انجامد (مثلاً SBValue.member در درون فقط __getitem__ را پیاده‌سازی می‌کند که تک‌خطی return self.valobj.GetChildMemberWithName(name) است)
    • SBValue.GetID برای هر مقدار تا پایان جلسهٔ اشکال‌زدایی یک int یکتا برمی‌گرداند. SBValueهای synthetic شناسه‌ای متفاوت از SBValue زیرین خود دارند. شناسهٔ زیرین را می‌توان با SBValue.GetNonSyntheticValue().GetID() بازیابی کرد.
    • هنگام محاسبهٔ دستی یک نشانی، SBValue.GetValueAsAddress باید بر SBValue.GetValueAsUnsigned ترجیح داده شود، به‌دلیل رفتار مختص هدف
    • گرفتن نمایش رشته‌ای یک SBValue می‌تواند دشوار باشد چون GetSummary به summary provider نیاز دارد و GetValue نیاز دارد نوع با یک نوع اولیه قابل نمایش باشد. تقریباً در همهٔ مواردی که هیچ‌یک از آن شرایط برقرار نیست، نوع یک struct تعریف‌شده توسط کاربر است که می‌توان آن را از StructSummaryProvider عبور داد.

    SBType

    • «نوع تجمیعی (Aggregate type)» یعنی struct/class/union غیراولیه
    • «Template» معادل «Generic» است
    • نوع‌ها را می‌توان با نامشان از طریق SBTarget.FindFirstType(type_name) جستجو کرد. SBTarget را می‌توان از SBValue.GetTarget به دست آورد
    • SBType.template_args اگر نوع جنریک نداشته باشد به‌جای فهرست خالی None برمی‌گرداند
    • گاهی لازم است نوعی را از طریق توابعی مانند SBType.GetArrayType و SBType.GetPointerType به نوع دلخواه تبدیل کنید. این توابع نمی‌توانند شکست بخورند. آن‌ها نوع را از افزونهٔ زیرین TypeSystem مربوط به LLDB می‌پرسند و اطلاعات اشکال‌زدایی را کاملاً دور می‌زنند. حتی اگر نوع اصلاً در اطلاعات اشکال‌زدایی وجود نداشته باشد، این توابع می‌توانند نوع مناسب را بسازند.
    • SBType.GetCanonicalType در عمل SBType.GetTypedefedType + SBType.GetUnqualifiedType است. برخلاف SBType.GetTypedefedType، همیشه یک SBType معتبر برمی‌گرداند، صرف‌نظر از اینکه SBType اصلی typedef باشد یا نه.
    • SBType.GetStaticFieldWithName در LLDB 18 اضافه شد. متأسفانه سازگاری با گذشته همیشه ممکن نیست چون در غیر این صورت فیلدهای static کاملاً غیرقابل‌دسترس‌اند.

    ارائه‌دهندهٔ نمونه: Vec<T>

    SyntheticProvider

    با مقدمهٔ معمول شروع می‌کنیم و چون فیلدهای شناخته‌شده داریم از __slots__ استفاده می‌کنیم. افزون بر خود شیء، باید نوع عناصر را هم ذخیره کنیم چون اشاره‌گر heap مربوط به Vec یک *mut u8 است نه *mut T. Rust زبانی با نوع‌دهی ایستاست، پس نوع T هرگز تغییر نمی‌کند. یعنی می‌توانیم آن را هنگام مقداردهی اولیه ذخیره کنیم. اما اشاره‌گر heap، طول و ظرفیت می‌توانند تغییر کنند و بنابراین در اینجا با مقدار پیش‌فرض مقداردهی اولیه می‌شوند.

    import lldb

class VecSyntheticProvider:
    valobj: SBValue
    data_ptr: SBValue
    len: int
    cap: int
    element_type: SBType

    __slots__ = (
        "valobj",
        "data_ptr",
        "len",
        "cap",
        "element_type",
        "__weakref__",
    )

    def __init__(valobj: SBValue, _dict) -> None:
        self.valobj = valobj
        # invalid type is a better default than `None`
        self.element_type = SBType()

        # special handling to account for DWARF/PDB differences
        if (arg := valobj.GetType().GetTemplateArgumentType(0)):
            self.element_type = arg
        else:
            arg_name = next(get_template_args(valobj.GetTypeName()))
            self.element_type = resolve_msvc_template_arg(arg_name, valobj.GetTarget())

    برای پیاده‌سازی get_template_args و resolve_msvc_template_arg، لطفاً lldb_providers.py را ببینید.

    سپس، تابع update. بررسی می‌کنیم آیا اشاره‌گر یا طول تغییر کرده‌اند. می‌توانیم بررسی ظرفیت را حذف کنیم، چون تعداد فرزندان تا وقتی len تغییر نکند یکسان می‌ماند. اگر تغییر ظرفیت به تخصیص مجدد بینجامد، نشانی data_ptr متفاوت خواهد بود.

    اگر data_ptr و length تغییر نکرده باشند، می‌توانیم از کش LLDB بهره ببریم و زودتر برگردیم. اگر تغییر کرده باشند، مقادیر جدید را ذخیره می‌کنیم و به LLDB می‌گوییم کش را پاک کند.

    def update(self):
    ptr = self.valobj.GetChildMemberWithName("data_ptr")
    len = self.valobj.GetChildMemberWithName("length").GetValueAsUnsigned()

    if (
        self.data_ptr.GetValueAsAddress() == ptr.GetValueAsAddress()
        and self.len == len
    ):
        # Our child address offsets and child count are still valid
        # so we can reuse cached children
        return True

    self.data_ptr = ptr
    self.len = len

    return False

    has_children و num_children هر دو سرراست‌اند:

    def has_children(self) -> bool:
    return True

def num_children(self) -> int:
    return self.len

    هنگام دسترسی به عناصر، انتظار مقادیری با قالب [0]، [1] و غیره داریم تا اندیس‌گذاری را تقلید کنند. افزون بر این، همچنان می‌خواهیم کاربر بتواند به‌سرعت به طول و ظرفیت دسترسی یابد، چون می‌توانند هنگام اشکال‌زدایی بسیار مفید باشند. به این مقادیر به‌ترتیب u32::MAX - 1 و u32::MAX - 2 را اختصاص می‌دهیم، چون تقریباً مطمئناً می‌توانیم تضمین کنیم با مقادیر عناصر همپوشانی نخواهند داشت. توجه کنید که می‌توانیم هم نام کامل و هم نام کوتاه capacity را در نظر بگیریم.

        def get_child_index(self, name: str) -> int:
        index = name.lstrip("[").rstrip("]")
        if index.isdigit():
            return int(index)
        if name == "len":
            return lldb.UINT32_MAX - 1
        if name == "cap" or name == "capacity":
            return lldb.UINT32_MAX - 2

        return -1

    اکنون باید get_child_at_index را به‌درستی هماهنگ کنیم تا عناصر، طول و ظرفیت همگی در دسترس باشند.

    def get_child_at_index(self, index: int) -> SBValue:
    if index == UINT32_MAX - 1:
        return self.valobj.GetChildMemberWithName("len")
    if index == UINT32_MAX - 2:
        return (
            self.valobj.GetChildMemberWithName("buf")
            .GetChildMemberWithName("inner")
            .GetChildMemberWithName("cap")
            .GetChildAtIndex(0)
            .Clone("capacity")
        )
    addr = self.data_ptr.GetValueAsAddress()
    addr += index * self.element_type.GetByteSize()
    return self.valobj.CreateValueFromAddress(f"[{index}]", addr, self.element_type)

    برای نام نمایشی نوع، می‌توانیم qualifier مسیر را حذف کنیم. نوع‌های تعریف‌شده توسط کاربر به نام Vec در نهایت کاملاً qualified می‌شوند، پس نباید ابهامی باشد. همچنین می‌توانیم جنریک allocator را حذف کنیم، چون به‌ندرت مفید است. به سه دلیل از get_template_args به‌جای self.element_type.GetName() استفاده می‌کنیم:

    1. اگر به هر دلیلی نتوانیم نوع عنصر را حل کنیم، نام نوع self.valobj همچنان می‌تواند به کاربر بگوید نوع واقعی عنصر چیست
    2. نام نوع‌ها تابع محدودیت‌های گره‌های DWARF و PDB نیستند، پس نوع template در نام چیزهایی مانند *const/*mut و &/&mut را منعکس می‌کند.
    3. تا نوامبر ۲۰۲۵، نام نوع‌های MSVC را نرمال نمی‌کنیم، اما وقتی بکنیم، به‌هرحال لازم خواهد بود با نام‌های رشته‌ای نوع‌ها کار کنیم. همچنین کش کردن تبدیل رشته-به-رشته بسیار آسان‌تر است در مقایسه با تبدیل SBType-به-رشته.
    def get_type_name(self) -> str:
    return f"Vec<{next(get_template_args(self.valobj))}>"

    مقدار اولیهٔ مناسبی برای نمایش یک Vec وجود ندارد، پس تابع get_value را صرفاً حذف می‌کنیم.

    SummaryProvider

    summary provider به‌لطف synthetic provider ما بسیار ساده است. تنها مشکل واقعی این است که GetSummary فقط وقتی مقداری برمی‌گرداند که نوع شیء یک SummaryProvider داشته باشد. اگر نداشته باشد، یک رشتهٔ خالی برمی‌گرداند که ایده‌آل نیست. در یک مجموعهٔ کامل اسکریپت‌های visualizer، می‌توانیم اطمینان یابیم که هر نوعی که GetSummary() یا GetValue() ندارد یک struct است و سپس به یک StructSummaryProvider عمومی واگذار کنیم. برای این نمایش، از آن جزئیات چشم‌پوشی می‌کنم.

    def VecSummaryProvider(valobj: SBValue, _lldb_internal) -> str:
    children = []
    for i in range(valobj.GetNumChildren()):
        child = valobj.GetChildAtIndex(i)
        summary = child.GetSummary()
        if summary is None:
            summary = child.GetValue()
            if summary is None:
                summary = "{...}"

        children.append(summary)

    return f"vec![{", ".join(children)}]"

    فرض کنید این synthetic در lldb_lookup.py import شده است

    با دستورهای CLI:

    type synthetic add -l lldb_lookup.synthetic_lookup -x "^(alloc::([a-z_]+::)+)Vec<.+>$" --category Rust
type summary add -F lldb_lookup.summary_lookup -x "^(alloc::([a-z_]+::)+)Vec<.+>$" --category Rust

    با __lldb_init_module:

    def __lldb_init_module(debugger: SBDebugger, _dict: LLDBOpaque):
    # Ensure the category exists and is enabled
    rust_cat = debugger.GetCategory("Rust")

    if not rust_cat.IsValid():
        rust_cat = debugger.CreateCategory("Rust")

    rust_cat.SetEnabled(True)

    # Register Vec providers
    vec_regex = r"^(alloc::([a-z_]+::)+)Vec<.+>$"
    sb_name = lldb.SBTypeNameSpecifier(vec_regex, is_regex=True)

    sb_synth = lldb.SBTypeSynthetic.CreateWithClassName("lldb_lookup.VecSyntheticProvider")
    sb_synth.SetOptions(lldb.eTypeOptionCascade)

    sb_summary = lldb.SBTypeSummary.CreateWithFunctionName("lldb_lookup.VecSummaryProvider")
    sb_summary.SetOptions(lldb.eTypeOptionCascade)

    rust_cat.AddTypeSynthetic(sb_name, sb_synth)
    rust_cat.AddSummary(sb_name, sb_summary)
