    مدیریت سیگنال

    فرایندها، مانند برنامه‌های خط فرمان، باید به سیگنال‌هایی که سیستم‌عامل ارسال می‌کند واکنش نشان دهند. شاید رایج‌ترین مثال Ctrl+C باشد، سیگنالی که معمولاً به فرایند می‌گوید پایان یابد. برای مدیریت سیگنال‌ها در برنامه‌های Rust باید در نظر بگیرید که چگونه می‌توانید این سیگنال‌ها را دریافت کنید و نیز چگونه می‌توانید به آن‌ها واکنش نشان دهید.

    توجه: اگر برنامهٔ شما نیازی به خاموش شدن تدریجی (graceful) ندارد، همان مدیریت پیش‌فرض کافی است (یعنی فوراً خارج شود و اجازه دهد سیستم‌عامل منابعی مانند دستگیره‌های فایل بازشده را پاک‌سازی کند). در آن صورت: نیازی نیست آنچه این فصل می‌گوید انجام دهید!

    **توجه:** اگر برنامهٔ شما نیازی ندارد به‌صورت مرتب و منظم خاموش شود، مدیریت پیش‌فرض کافی است (یعنی فوراً خارج شود و بگذارد سیستم‌عامل منابعی مانند فایل‌های باز را پاک‌سازی کند). در آن صورت: نیازی نیست آنچه این فصل می‌گوید انجام دهید! با این حال، برای برنامه‌هایی که باید پس از خود پاک‌سازی کنند، این فصل بسیار مرتبط است! برای مثال، اگر برنامهٔ شما باید اتصال‌های شبکه را به‌درستی ببندد (و به فرایندهای سمت دیگر «خداحافظ» بگوید)، فایل‌های موقت را حذف کند، یا تنظیمات سیستم را بازنشانی کند، به خواندن ادامه دهید.

    تفاوت‌ها میان سیستم‌عامل‌ها

    در سیستم‌های یونیکس (مانند Linux، macOS و FreeBSD) یک فرایند می‌تواند سیگنال‌هایی دریافت کند. فرایند می‌تواند یا به شیوهٔ پیش‌فرض (ارائه‌شده توسط سیستم‌عامل) به آن‌ها واکنش نشان دهد، یا سیگنال را بگیرد و به شیوه‌ای که برنامه تعریف می‌کند مدیریتش کند، یا سیگنال را کاملاً نادیده بگیرد.

    ویندوز سیگنال ندارد. می‌توانید از Console Handlers برای تعریف callbackهایی استفاده کنید که هنگام رخ دادن یک رویداد اجرا می‌شوند. همچنین مدیریت استثنای ساخت‌یافته وجود دارد که همهٔ انواع گوناگون استثناهای سیستمی مانند تقسیم بر صفر، استثناهای دسترسی نامعتبر، سرریز پشته و غیره را مدیریت می‌کند

    نخست: مدیریت Ctrl+C

    crate با نام ctrlc دقیقاً همان کاری را می‌کند که نامش می‌گوید: به شما اجازه می‌دهد به فشردن Ctrl+C توسط کاربر به‌صورت چندسکویی واکنش نشان دهید. روش اصلی استفاده از این crate چنین است:

    use std::{thread, time::Duration};

fn main() {
    ctrlc::set_handler(move || {
        println!("received Ctrl+C!");
    })
    .expect("Error setting Ctrl-C handler");

    // Following code does the actual work, and can be interrupted by pressing
    // Ctrl-C. As an example: Let's wait a few seconds.
    thread::sleep(Duration::from_secs(2));
}

    البته این چندان مفید نیست: فقط یک پیام چاپ می‌کند و در غیر این صورت برنامه را متوقف نمی‌کند.

    در یک برنامهٔ واقعی، ایدهٔ خوبی است که در عوض در مدیریت‌کنندهٔ سیگنال یک متغیر تنظیم کنید و سپس آن را در جاهای مختلف برنامه بررسی کنید. برای مثال، می‌توانید در مدیریت‌کنندهٔ سیگنال یک Arc<AtomicBool> (یک مقدار بولی که میان نخ‌ها قابل اشتراک است) را تنظیم کنید، و در حلقه‌های پرتکرار، یا هنگام منتظر ماندن برای یک نخ، مقدار آن را به‌طور دوره‌ای بررسی کنید و هنگامی که true شد، حلقه را بشکنید.

    مدیریت انواع دیگر سیگنال‌ها

    crate با نام ctrlc فقط Ctrl+C را مدیریت می‌کند، یا آنچه در سیستم‌های یونیکس SIGINT («سیگنال وقفه») نامیده می‌شود. برای واکنش به سیگنال‌های بیشتر یونیکس، باید نگاهی به signal-hook بیندازید. طراحی آن در این نوشتهٔ وبلاگ توضیح داده شده است و در حال حاضر کتابخانه‌ای است که بیشترین پشتیبانی جامعه را دارد.

    این یک مثال ساده است:

    use signal_hook::{consts::SIGINT, iterator::Signals};
use std::{error::Error, thread, time::Duration};

fn main() -> Result<(), Box<dyn Error>> {
    let mut signals = Signals::new([SIGINT])?;

    thread::spawn(move || {
        for sig in signals.forever() {
            println!("Received signal {:?}", sig);
        }
    });

    // Following code does the actual work, and can be interrupted by pressing
    // Ctrl-C. As an example: Let's wait a few seconds.
    thread::sleep(Duration::from_secs(2));

    Ok(())
}

    استفاده از کانال‌ها

    به‌جای تنظیم یک متغیر و بررسی آن توسط بخش‌های دیگر برنامه، می‌توانید از کانال‌ها استفاده کنید: کانالی می‌سازید که مدیریت‌کنندهٔ سیگنال هر بار که سیگنال دریافت شود مقداری را در آن منتشر می‌کند. در کد برنامه‌تان از این کانال و کانال‌های دیگر به‌عنوان نقاط همگام‌سازی میان نخ‌ها (thread) استفاده می‌کنید. با استفاده از crossbeam-channel چیزی شبیه این خواهد بود:

    use anyhow::Result;
use crossbeam_channel::{Receiver, bounded, select, tick};
use std::time::Duration;

fn ctrl_channel() -> Result<Receiver<()>, ctrlc::Error> {
    let (sender, receiver) = bounded(100);
    ctrlc::set_handler(move || {
        let _ = sender.send(());
    })?;

    Ok(receiver)
}

fn main() -> Result<()> {
    let ctrl_c_events = ctrl_channel()?;
    let ticks = tick(Duration::from_secs(1));

    loop {
        select! {
            recv(ticks) -> _ => {
                println!("working!");
            }
            recv(ctrl_c_events) -> _ => {
                println!();
                println!("Goodbye!");
                break;
            }
        }
    }

    Ok(())
}

    استفاده از futureها و streamها

    اگر از tokio استفاده می‌کنید، به احتمال زیاد برنامهٔ خود را از قبل با الگوهای ناهمگام و طراحی رویدادمحور می‌نویسید. به‌جای استفاده مستقیم از کانال‌های crossbeam، می‌توانید ویژگی tokio-support در signal-hook را فعال کنید. این کار به شما اجازه می‌دهد .into_async() را روی نوع‌های Signals در signal-hook فراخوانی کنید تا نوعی جدید بگیرید که futures::Stream را پیاده‌سازی می‌کند.

    وقتی هنگام مدیریت نخستین Ctrl+C، Ctrl+C دیگری دریافت می‌کنید چه باید کرد

    بیشتر کاربران Ctrl+C را می‌زنند و سپس چند ثانیه به برنامهٔ شما فرصت می‌دهند تا خارج شود یا به آن‌ها بگوید چه خبر است. اگر این اتفاق نیفتد، دوباره Ctrl+C را می‌زنند. رفتار معمول این است که برنامه فوراً خارج شود.
