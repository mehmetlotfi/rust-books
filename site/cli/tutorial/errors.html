کتاب برنامه‌های خط فرمانCommand Line Applications in Rust

    گزارش‌دهی بهتر خطا

    چاره‌ای جز پذیرفتن این واقعیت نداریم که خطاها رخ خواهند داد. برخلاف بسیاری از زبان‌های دیگر، هنگام استفاده از Rust نادیده گرفتن این واقعیت و نپرداختن به آن بسیار دشوار است، چون Rust استثنا (exception) ندارد. همهٔ حالت‌های خطای ممکن اغلب در نوع بازگشتی تابع‌ها کدگذاری می‌شوند.

    Resultها

    تابعی مانند read_to_string یک رشته برنمی‌گرداند. در عوض، یک Result برمی‌گرداند که یا شامل یک String یا یک خطا از نوعی خاص است. در این مورد، std::io::Error.

    از کجا بفهمیم کدام است؟ چون Result یک enum است، می‌توانید با match بررسی کنید کدام یک از حالت‌ها (variant) است:

    let result = std::fs::read_to_string("test.txt");
match result {
    Ok(content) => { println!("File content: {}", content); }
    Err(error) => { println!("Oh noes: {}", error); }
}

    **توجه:** مطمئن نیستید enumها چه هستند یا در Rust چگونه کار می‌کنند؟ [این فصل از کتاب Rust را ببینید](https://doc.rust-lang.org/1.39.0/book/ch06-00-enums.html) تا به سرعت با آن‌ها آشنا شوید.

    باز کردن مقدار (Unwrapping)

    اکنون توانستیم به محتوای فایل دسترسی پیدا کنیم، اما بعد از بلوک match واقعاً نمی‌توانیم کاری با آن بکنیم. برای این کار، باید حالت خطا را مدیریت کنیم. اگرچه این یک چالش است که همهٔ بازوهای (arm) یک بلوک match باید چیزی از یک نوع برگردانند، ترفند ظریفی برای دور زدن آن وجود دارد:

    let result = std::fs::read_to_string("test.txt");
let content = match result {
    Ok(content) => { content },
    Err(error) => { panic!("Can't deal with {}, just exit here", error); }
};
println!("file content: {}", content);

    می‌توانیم بعد از بلوک match از String موجود در content استفاده کنیم، اما اگر result یک خطا بود، آن String وجود نمی‌داشت. این مشکلی ندارد، چون برنامه پیش از رسیدن به نقطه‌ای که از content استفاده می‌کنیم خارج می‌شود.

    این ممکن است تند به نظر برسد، اما بسیار راحت است. اگر برنامهٔ شما باید آن فایل را بخواند و در صورت نبودن فایل نمی‌تواند کاری انجام دهد، خارج شدن راهبردی معتبر است. حتی یک متد میان‌بر روی Result به نام unwrap وجود دارد:

    let content = std::fs::read_to_string("test.txt").unwrap();

    نیازی به panic نیست

    البته، متوقف کردن برنامه تنها راه مدیریت خطاها نیست. به‌جای استفاده از panic!، می‌توانیم فقط از return استفاده کنیم:

    fn main() -> Result<(), Box<dyn std::error::Error>> {
let result = std::fs::read_to_string("test.txt");
let content = match result {
    Ok(content) => { content },
    Err(error) => { return Err(error.into()); }
};
Ok(())
}

    با این حال، این کار نوع بازگشتی تابع ما را تغییر می‌دهد. در تمام این مدت چیزی در مثال‌هایمان پنهان بود: امضای تابعی که این کد در آن قرار دارد. و در این آخرین مثال با return، اهمیت پیدا می‌کند. این هم مثال کامل:

    fn main() -> Result<(), Box<dyn std::error::Error>> {
    let result = std::fs::read_to_string("test.txt");
    let content = match result {
        Ok(content) => { content },
        Err(error) => { return Err(error.into()); }
    };
    println!("file content: {}", content);
    Ok(())
}

    نوع بازگشتی ما یک Result است! به همین دلیل می‌توانیم در بازوی دوم match بنویسیم return Err(error);. می‌بینید که در پایین یک Ok(()) وجود دارد؟ این مقدار بازگشتی پیش‌فرض تابع است و معنایش این است: «Result سالم است و محتوایی ندارد».

    توجه: چرا این به‌صورت return Ok(()); نوشته نشده است؟ به‌راحتی می‌شد آن را این‌طور نوشت – این هم کاملاً معتبر است. آخرین عبارت هر بلوک در Rust مقدار بازگشتی آن است، و رسم بر این است که return غیرضروری حذف شود.

    علامت سؤال

    همان‌طور که فراخوانی .unwrap() میان‌بری است برای match همراه با panic! در بازوی خطا، میان‌بر دیگری برای matchای داریم که در بازوی خطا return می‌کند: ?.

    درست است، یک علامت سؤال. می‌توانید این عملگر را به مقداری از نوع Result اضافه کنید، و Rust آن را در درون به چیزی بسیار شبیه به همان match که همین حالا نوشتیم باز می‌کند.

    امتحانش کنید:

    fn main() -> Result<(), Box<dyn std::error::Error>> {
    let content = std::fs::read_to_string("test.txt")?;
    println!("file content: {}", content);
    Ok(())
}

    بسیار مختصر!

    توجه: چند اتفاق دیگر هم این‌جا در حال رخ دادن است که برای کار کردن با این کد لازم نیست آن‌ها را بفهمید. برای مثال، نوع خطا در تابع main ما Box<dyn std::error::Error> است، اما در بالا دیدیم که read_to_string یک std::io::Error برمی‌گرداند. این کار می‌کند زیرا ? به کدی گسترش می‌یابد که انواع خطا را تبدیل می‌کند.

    Box<dyn std::error::Error> نیز نوعی جالب است. این یک Box است که می‌تواند هر نوعی را در خود جای دهد که trait استاندارد Error را پیاده‌سازی می‌کند. این یعنی همهٔ خطاها را می‌توان در این جعبه گذاشت، و می‌توانیم ? را روی همهٔ توابع معمولی که یک Result برمی‌گردانند به کار ببریم.

    فراهم کردن زمینه (Context)

    خطاهایی که هنگام استفاده از ? در تابع main می‌گیرید قابل‌قبول هستند، اما عالی نیستند. برای مثال، وقتی std::fs::read_to_string("test.txt")? را اجرا می‌کنید و فایل test.txt وجود ندارد، این خروجی را می‌گیرید:

    Error: Os { code: 2, kind: NotFound, message: "No such file or directory" }

    در مواردی که کد شما در واقع نام فایل را در خود ندارد، تشخیص اینکه کدام فایل NotFound بوده دشوار خواهد بود. راه‌های متعددی برای مدیریت این وضعیت وجود دارد.

    برای مثال، می‌توانیم نوع خطای خودمان را بسازیم و از آن برای ساختن یک پیام خطای سفارشی استفاده کنیم:

    #[derive(Debug)]
struct CustomError(String);

fn main() -> Result<(), CustomError> {
    let path = "test.txt";
    let content = std::fs::read_to_string(path)
        .map_err(|err| CustomError(format!("Error reading `{}`: {}", path, err)))?;
    println!("file content: {}", content);
    Ok(())
}

    با اجرای این، پیام خطای سفارشی خود را می‌گیریم:

    Error: CustomError("Error reading `test.txt`: No such file or directory (os error 2)")

    چندان زیبا نیست، اما می‌توانیم بعداً خروجی debug را برای نوع خودمان تطبیق دهیم.

    این الگو بسیار رایج است. با این حال یک مشکل دارد: خطای اصلی را ذخیره نمی‌کنیم، فقط نمایش رشته‌ای آن را. کتابخانهٔ محبوب anyhow راه‌حل ظریفی برای این دارد: trait با نام Context آن را می‌توان برای افزودن توضیحی مشابه نوع CustomError ما به کار برد. علاوه بر این، خطای اصلی را نگه می‌دارد، بنابراین «زنجیره‌ای» از پیام‌های خطا می‌گیریم که به علت ریشه‌ای اشاره می‌کند.

    بیایید ابتدا crate با نام anyhow را با افزودن anyhow = "1.0" به بخش [dependencies] فایل Cargo.toml خود وارد کنیم.

    مثال کامل چنین خواهد بود:

    use anyhow::{Context, Result};

fn main() -> Result<()> {
    let path = "test.txt";
    let content =
        std::fs::read_to_string(path).with_context(|| format!("could not read file `{}`", path))?;
    println!("file content: {}", content);
    Ok(())
}

    این یک خطا چاپ می‌کند:

    Error: could not read file `test.txt`

Caused by:
    No such file or directory (os error 2)

    جمع‌بندی

    کد شما اکنون باید این‌گونه باشد:

    use anyhow::{Context, Result};
use clap::Parser;

/// Search for a pattern in a file and display the lines that contain it.
#[derive(Parser)]
struct Cli {
    /// The pattern to look for
    pattern: String,
    /// The path to the file to read
    path: std::path::PathBuf,
}

fn main() -> Result<()> {
    let args = Cli::parse();

    let content = std::fs::read_to_string(&args.path)
        .with_context(|| format!("could not read file `{}`", args.path.display()))?;

    for line in content.lines() {
        if line.contains(&args.pattern) {
            println!("{}", line);
        }
    }

    Ok(())
}
