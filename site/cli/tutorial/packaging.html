کتاب برنامه‌های خط فرمانCommand Line Applications in Rust

    بسته‌بندی و توزیع یک ابزار Rust

    اگر مطمئن هستید که برنامه‌تان آمادهٔ استفادهٔ دیگران است، وقت آن رسیده که آن را بسته‌بندی و منتشر کنید!

    چند رویکرد وجود دارد و ما سه‌تای آن‌ها را بررسی می‌کنیم، از سریع‌ترین روش برای راه‌اندازی تا راحت‌ترین روش برای کاربران.

    سریع‌ترین: cargo publish

    ساده‌ترین راه برای انتشار برنامه‌تان استفاده از cargo است. به یاد دارید چگونه وابستگی‌های خارجی را به پروژه‌مان اضافه کردیم؟ Cargo آن‌ها را از رجیستری پیش‌فرض crateهای خود دانلود کرد: crates.io. با cargo publish می‌توانید crateها را در crates.io منتشر کنید، و این برای همهٔ crateها کار می‌کند، از جمله آن‌هایی که هدف‌های باینری دارند.

    انتشار یک crate در crates.io در چند گام انجام می‌شود. نخست، اگر هنوز این کار را نکرده‌اید، در crates.io یک حساب کاربری بسازید. این کار با مجاز کردن ورود از طریق GitHub انجام می‌شود، پس باید یک حساب GitHub داشته باشید و در آن‌جا وارد شده باشید. دوم، با استفاده از cargo روی رایانهٔ محلی خود وارد شوید. برای این کار به صفحهٔ حساب crates.io خود بروید، یک توکن جدید بسازید، و cargo login <your-new-token> را اجرا کنید. این کار را فقط یک بار برای هر رایانه باید انجام دهید. دربارهٔ این موضوع بیشتر می‌توانید در راهنمای انتشار cargo بخوانید.

    اکنون که cargo و crates.io شما را می‌شناسند، آمادهٔ انتشار crateها هستید. پیش از آن‌که با عجله نسخهٔ جدید یک crate را منتشر کنید، بهتر است یک بار دیگر فایل Cargo.toml خود را باز کنید و مطمئن شوید فراداده‌های لازم را اضافه کرده‌اید. همهٔ فیلدهایی را که می‌توانید تنظیم کنید در مستندات قالب مانیفست cargo پیدا می‌کنید. در ادامه مروری سریع بر برخی از مدخل‌های رایج آمده است:

    [package]
name = "grrs"
version = "0.1.0"
authors = ["Your Name <your@email.com>"]
license = "MIT OR Apache-2.0"
description = "A tool to search files"
readme = "README.md"
homepage = "https://github.com/you/grrs"
repository = "https://github.com/you/grrs"
keywords = ["cli", "search", "demo"]
categories = ["command-line-utilities"]

    توجه: این مثال شامل فیلد اجباری مجوز (license) است با انتخابی رایج برای پروژه‌های Rust: همان مجوزی که برای خود کامپایلر استفاده می‌شود. همچنین به یک فایل README.md اشاره می‌کند. این فایل باید توضیح کوتاهی دربارهٔ موضوع پروژهٔ شما داشته باشد و نه‌تنها در صفحهٔ crate شما در crates.io قرار می‌گیرد، بلکه GitHub نیز به‌طور پیش‌فرض آن را در صفحه‌های مخزن نشان می‌دهد.

    چگونه یک باینری را از crates.io نصب کنیم

    دیدیم چگونه یک crate را در crates.io منتشر کنیم، و شاید بپرسید چگونه آن را نصب کنیم. برخلاف کتابخانه‌ها، که cargo هنگام اجرای cargo build یا فرمان مشابه آن‌ها را برای شما دانلود و کامپایل می‌کند، باید صریحاً به cargo بگویید که باینری‌ها را نصب کند.

    این کار با cargo install <crate-name> انجام می‌شود. این فرمان به‌طور پیش‌فرض crate را دانلود می‌کند، همهٔ هدف‌های باینری آن را کامپایل می‌کند (در حالت «release»، پس ممکن است کمی طول بکشد) و آن‌ها را در دایرکتوری ~/.cargo/bin/ کپی می‌کند. مطمئن شوید شل شما می‌داند باید باینری‌ها را آن‌جا جست‌وجو کند!

    همچنین می‌توان crateها را از مخزن‌های git نصب کرد، فقط باینری‌های مشخصی از یک crate را نصب کرد، و دایرکتوری دیگری را برای نصب آن‌ها تعیین کرد. برای جزئیات به cargo install --help نگاه کنید.

    چه زمانی از آن استفاده کنیم

    cargo install راهی ساده برای نصب یک crate باینری است. برای توسعه‌دهندگان Rust بسیار راحت است اما معایب قابل‌توجهی دارد: از آن‌جا که همیشه سورس شما را از صفر کامپایل می‌کند، کاربران ابزار شما باید Rust، cargo و همهٔ وابستگی‌های سیستمی دیگر پروژهٔ شما را روی رایانهٔ خود نصب کرده باشند. کامپایل کدبیس‌های بزرگ Rust می‌تواند مدتی طول بکشد.

    بهتر است از این روش برای توزیع ابزارهایی استفاده شود که مخاطبانشان دیگر توسعه‌دهندگان Rust هستند. برای نمونه، بسیاری از زیرفرمان‌های cargo مانند cargo-tree یا cargo-outdated را می‌توان با آن نصب کرد.

    توزیع باینری‌ها

    Rust زبانی است که به کد بومی کامپایل می‌شود و به‌طور پیش‌فرض همهٔ وابستگی‌ها را به‌صورت ایستا پیوند می‌دهد. وقتی cargo build را روی پروژه‌ای اجرا می‌کنید که باینری‌ای به نام grrs دارد، در نهایت یک فایل باینری به نام grrs خواهید داشت. امتحانش کنید! با cargo build این فایل target/debug/grrs خواهد بود، و وقتی cargo build --release را اجرا کنید، target/release/grrs خواهد بود. مگر آن‌که از crateهایی استفاده کنید که صراحتاً به کتابخانه‌های خارجی نصب‌شده روی سیستم هدف نیاز دارند (مانند استفاده از نسخهٔ OpenSSL خود سیستم)، این باینری فقط به کتابخانه‌های رایج سیستم وابسته خواهد بود. یعنی همان یک فایل را برمی‌دارید، برای افرادی که همان سیستم‌عامل شما را دارند می‌فرستید، و آن‌ها می‌توانند آن را اجرا کنند.

    این همین حالا هم بسیار قدرتمند است! دو مورد از معایبی را که برای cargo install دیدیم دور می‌زند: نیازی نیست Rust روی رایانهٔ کاربر نصب باشد، و به‌جای آن‌که کامپایل یک دقیقه طول بکشد، کاربر می‌تواند باینری را بلافاصله اجرا کند.

    همان‌طور که دیدیم، cargo build همین حالا هم برای ما باینری می‌سازد. مشکل این است که تضمینی نیست آن باینری‌ها روی همهٔ سکوها کار کنند. اگر cargo build را روی رایانهٔ ویندوزی خود اجرا کنید، به‌طور پیش‌فرض باینری‌ای نمی‌گیرید که روی مک کار کند. آیا راهی هست که این باینری‌ها برای همهٔ سکوهای هدف به‌طور خودکار تولید شوند؟

    ساخت انتشارهای باینری روی CI

    اگر ابزار شما متن‌باز است و روی GitHub میزبانی می‌شود، راه‌اندازی یک سرویس رایگان CI (یکپارچه‌سازی پیوسته) مانند Travis CI کاملاً آسان است. سرویس‌های دیگری هم این قابلیت را ارائه می‌دهند، اما Travis بسیار محبوب است. این سرویس هر بار که تغییرات را به مخزن خود push می‌کنید، دستورهای راه‌اندازی را در یک ماشین مجازی اجرا می‌کند. این‌که آن دستورها چه باشند، و روی چه نوع ماشین‌هایی اجرا شوند، قابل تنظیم است. برای مثال، ایدهٔ خوبی است که cargo test را روی ماشینی اجرا کنید که Rust و چند ابزار ساخت رایج روی آن نصب است. اگر این اجرا شکست بخورد، می‌دانید در آخرین تغییرات مشکلاتی وجود دارد.

    همچنین می‌توانیم از این سرویس استفاده کنیم تا باینری‌ها را بسازیم و در GitHub بارگذاری کنیم! اگر cargo build --release را اجرا کنیم و باینری را جایی بارگذاری کنیم، باید همه‌چیز آماده باشد، درست است؟ نه کاملاً. هنوز باید مطمئن شویم باینری‌هایی که می‌سازیم با بیشترین تعداد ممکن از سیستم‌ها سازگارند. برای مثال، در لینوکس می‌توانیم برای سیستم فعلی کامپایل کنیم یا هدف x86_64-unknown-linux-musl را انتخاب کنیم تا به کتابخانه‌های پیش‌فرض سیستم وابسته نباشیم. در macOS می‌توانیم MACOSX_DEPLOYMENT_TARGET را روی 10.7 بگذاریم تا فقط به قابلیت‌های سیستمی موجود در نسخهٔ 10.7 و قدیمی‌تر وابسته باشیم.

    نمونه‌ای از ساخت باینری‌ها با این رویکرد را این‌جا برای لینوکس و macOS و این‌جا برای ویندوز با استفاده از AppVeyor می‌بینید.

    راه دیگر استفاده از ایمیج‌های از پیش ساخته‌شده (مثلاً Docker) است که همهٔ ابزارهای لازم برای ساخت باینری‌ها را در خود دارند. این کار به ما امکان می‌دهد سکوهای غیرمعمول‌تر را هم به‌سادگی هدف بگیریم. پروژهٔ trust شامل اسکریپت‌هایی است که می‌توانید در پروژهٔ خود بگنجانید و دستورالعمل‌های راه‌اندازی آن‌ها. این پروژه از ویندوز با AppVeyor هم پشتیبانی می‌کند.

    اگر ترجیح می‌دهید این را به‌صورت محلی راه‌اندازی کنید و فایل‌های انتشار را روی رایانهٔ خودتان تولید کنید، به trust نگاه کنید. این پروژه در درون خود از cross استفاده می‌کند، که شبیه cargo کار می‌کند اما فرمان‌ها را به یک فرایند cargo درون یک کانتینر Docker ارسال می‌کند. تعریف ایمیج‌ها نیز در مخزن cross در دسترس است.

    چگونه این باینری‌ها را نصب کنیم

    کاربران خود را به صفحهٔ انتشارهای خود راهنمایی می‌کنید که ممکن است چیزی شبیه این یکی باشد، و آن‌ها می‌توانند فایل‌هایی را که همین حالا ساخته‌ایم دانلود کنند. فایل‌های انتشاری که تولید کرده‌ایم چیز خاصی نیستند. آن‌ها فقط فایل‌های آرشیوی هستند که باینری‌های ما را در خود دارند! یعنی کاربران ابزار شما می‌توانند آن‌ها را با مرورگر خود دانلود کنند، (اغلب به‌طور خودکار) استخراج کنند، و باینری‌ها را به جایی که دوست دارند کپی کنند.

    این کار مقداری تجربه در نصب دستی برنامه‌ها می‌طلبد، پس بهتر است بخشی به فایل README خود اضافه کنید که توضیح دهد این برنامه چگونه نصب می‌شود.

    توجه: اگر از trust برای ساخت باینری‌های خود و افزودن آن‌ها به انتشارهای GitHub استفاده می‌کنید، در صورتی که فکر می‌کنید کار را آسان‌تر می‌کند، می‌توانید به افراد بگویید این فرمان را هم اجرا کنند: curl -LSfs https://japaric.github.io/trust/install.sh | sh -s -- --git your-name/repo-name

    چه زمانی از آن استفاده کنیم

    داشتن انتشارهای باینری به‌طور کلی ایدهٔ خوبی است. تقریباً هیچ عیبی ندارد. این روش مشکل نصب و به‌روزرسانی دستی ابزارهای شما توسط کاربران را حل نمی‌کند، اما کاربران می‌توانند بدون نیاز به نصب Rust به‌سرعت نسخهٔ آخرین انتشار را بگیرند.

    چه چیزهایی را علاوه بر باینری‌ها بسته‌بندی کنیم

    در حال حاضر، وقتی کاربری ساخت‌های انتشار ما را دانلود می‌کند، یک فایل .tar.gz می‌گیرد که فقط شامل فایل‌های باینری است. در پروژهٔ نمونهٔ ما، فقط یک فایل grrs می‌گیرند که می‌توانند اجرایش کنند، اما فایل‌های دیگری هم در مخزن خود داریم که ممکن است بخواهند داشته باشند. برای مثال فایل README که به آن‌ها می‌گوید چگونه از این ابزار استفاده کنند و فایل(های) مجوز. از آن‌جا که این‌ها را از قبل داریم، اضافه کردنشان آسان است.

    فایل‌های جالب‌تری هم هستند که به‌ویژه برای ابزارهای خط فرمان معنا دارند. چه‌طور است علاوه بر آن فایل README یک صفحهٔ man و فایل‌های پیکربندی‌ای هم ارائه کنیم که تکمیل خودکار پرچم‌های ممکن را به شل شما اضافه می‌کنند؟ می‌توانید این‌ها را دستی بنویسید، اما clap، کتابخانهٔ تحلیل آرگومان که استفاده می‌کنیم (که clap بر پایهٔ آن ساخته شده است) راهی دارد که همهٔ این فایل‌ها را برای ما تولید کند. برای جزئیات بیشتر این فصل عمیق‌تر را ببینید.

    قرار دادن برنامه‌تان در مخزن‌های بسته

    هر دو رویکردی که تا این‌جا دیدیم روشی نیستند که معمولاً نرم‌افزار را روی رایانه‌تان نصب می‌کنید، به‌ویژه برای ابزارهای خط فرمان که در بیشتر سیستم‌عامل‌ها با مدیرهای بستهٔ سراسری نصب می‌کنید. مزیت‌ها برای کاربران کاملاً آشکار است: اگر برنامهٔ شما را بتوان همان‌طور نصب کرد که ابزارهای دیگر را نصب می‌کنند، دیگر لازم نیست دربارهٔ نحوهٔ نصب آن فکر کنند. این مدیرهای بسته همچنین به کاربران اجازه می‌دهند وقتی نسخهٔ جدیدی در دسترس است، برنامه‌هایشان را به‌روزرسانی کنند.

    متأسفانه، پشتیبانی از سیستم‌های مختلف یعنی باید ببینید این سیستم‌های مختلف چگونه کار می‌کنند. برای برخی، ممکن است به آسانی افزودن یک فایل به مخزن شما باشد (مثلاً افزودن یک فایل Formula مانند این برای brew در macOS)، اما برای بقیه، اغلب باید خودتان وصله‌هایی (patch) ارسال کنید و ابزارتان را به مخزن‌های آن‌ها اضافه کنید. ابزارهای مفیدی مانند cargo-bundle، cargo-deb و cargo-aur وجود دارند، اما توضیح نحوهٔ کار آن‌ها و این‌که چگونه ابزارتان را برای آن سیستم‌های مختلف درست بسته‌بندی کنید، خارج از حوصلهٔ این فصل است.

    در عوض، بیایید به ابزاری نگاه کنیم که با Rust نوشته شده و در مدیرهای بستهٔ بسیار متفاوتی در دسترس است.

    یک مثال: ripgrep

    ripgrep جایگزینی برای grep/ack/ag است و با Rust نوشته شده است. بسیار موفق بوده و برای سیستم‌عامل‌های زیادی بسته‌بندی شده است: فقط به بخش «Installation» در README آن نگاه کنید!

    توجه کنید که چند گزینهٔ مختلف برای نصب آن فهرست شده است: با پیوندی به انتشارهای GitHub شروع می‌شود، که باینری‌ها را در خود دارند تا مستقیماً دانلودشان کنید، سپس نحوهٔ نصب آن را با تعدادی مدیر بستهٔ مختلف فهرست می‌کند، و همچنین می‌توانید آن را با cargo install نصب کنید.

    این ایدهٔ بسیار خوبی به نظر می‌رسد. فقط یکی از رویکردهای ارائه‌شده در این‌جا را برنگزینید. با cargo install شروع کنید و انتشارهای باینری را اضافه کنید و در نهایت ابزارتان را با مدیرهای بستهٔ سیستمی توزیع کنید.
