کتاب برنامه‌های خط فرمانCommand Line Applications in Rust

    آزمون

    در طول دهه‌ها توسعهٔ نرم‌افزار، مردم به یک حقیقت رسیده‌اند: نرم‌افزار آزمون‌نشده به‌ندرت کار می‌کند. بسیاری از آدم‌ها حتی تا آنجا پیش می‌روند که بگویند بیشتر نرم‌افزارهای آزمون‌شده هم کار نمی‌کنند. اما ما همه این‌جا خوش‌بین هستیم، درست است؟ برای اطمینان از این‌که برنامه‌تان همان کاری را می‌کند که انتظار دارید، عاقلانه است که آن را آزمون کنید.

    نقطهٔ شروع خوب این است که یک فایل README بنویسید که توضیح دهد برنامه‌تان باید چه کاری انجام دهد، و وقتی آمادهٔ انتشار نسخهٔ جدید شدید، README را مرور کنید و مطمئن شوید که رفتار برنامه هنوز مطابق انتظار است. می‌توانید این کار را با نوشتن این‌که برنامه‌تان چگونه باید به ورودی‌های نادرست واکنش نشان دهد، دقیق‌تر کنید.

    یک ایدهٔ جذاب‌تر هم این است: آن README را پیش از نوشتن کد بنویسید.

    توجه: اگر دربارهٔ توسعهٔ آزمون‌محور (TDD) چیزی نشنیده‌اید، به آن نگاهی بیندازید.

    آزمون خودکار

    خب، همهٔ این‌ها خوب و قشنگ است، اما انجام دستی همهٔ این کارها؟ این می‌تواند زمان زیادی ببرد. در عین حال، بسیاری از مردم از این‌که به رایانه‌ها بگویند کارها را برایشان انجام دهند لذت می‌برند. بیایید دربارهٔ خودکارسازی این آزمون‌ها صحبت کنیم.

    Rust یک چارچوب آزمون داخلی دارد، پس بیایید با نوشتن نخستین آزمون خود شروع کنیم:

    fn answer() -> i32 {
  42
}

#[test]
fn check_answer_validity() {
    assert_eq!(answer(), 42);
}

    می‌توانید این قطعه کد را تقریباً در هر فایل سورسی بسته‌تان قرار دهید و cargo test آن را پیدا و اجرا می‌کند. نکتهٔ کلیدی این‌جا attribute به نام #[test] است. این attribute به سامانهٔ ساخت اجازه می‌دهد چنین تابع‌هایی را کشف کند و آن‌ها را به‌عنوان آزمون اجرا کند، و بررسی کند که panic نمی‌کنند.

    تمرین برای خواننده: این آزمون را به کار بیندازید.

    در پایان باید خروجی‌ای مانند زیر داشته باشید:

    running 1 test
test check_answer_validity ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

    اکنون که دیدیم چگونه می‌توانیم آزمون بنویسیم، هنوز باید بفهمیم چه چیزی را آزمون کنیم. همان‌طور که دیدید، نوشتن assertion برای تابع‌ها کد کمی لازم دارد، اما یک برنامهٔ CLI اغلب بیش از یک تابع است! بدتر این‌که اغلب با ورودی کاربر سروکار دارد، فایل‌ها را می‌خواند، و خروجی می‌نویسد.

    آزمون‌پذیر کردن کد

    دو رویکرد مکمل برای آزمون عملکرد وجود دارد. یکی آزمودن واحدهای کوچکی است که برای ساخت برنامهٔ کامل خود به کار می‌برید. این‌ها «آزمون‌های واحد» (unit tests) نامیده می‌شوند. دیگری آزمودن برنامهٔ نهایی از بیرون است که آزمون جعبه‌سیاه یا آزمون یکپارچگی نامیده می‌شود. بیایید با اولی شروع کنیم.

    برای این‌که بفهمیم چه چیزی را باید آزمون کنیم، بیایید ببینیم برنامهٔ ما چه ویژگی‌هایی دارد. grrs قرار است خط‌هایی را که با یک الگوی داده‌شده مطابقت دارند چاپ کند، پس بیایید برای دقیقاً همین آزمون‌های واحد بنویسیم. می‌خواهیم مطمئن شویم مهم‌ترین بخش منطق ما کار می‌کند، و می‌خواهیم این کار را به شیوه‌ای انجام دهیم که به هیچ‌یک از کدهای راه‌اندازی پیرامون آن، مانند آرگومان‌های CLI، وابسته نباشد.

    با بازگشت به نخستین پیاده‌سازی grrs، این بلوک کد را به تابع main اضافه کردیم:

    // ...
for line in content.lines() {
    if line.contains(&args.pattern) {
        println!("{}", line);
    }
}

    متأسفانه آزمودن این کد چندان آسان نیست. نخست این‌که در تابع main است، پس نمی‌توانیم به‌راحتی آن را فراخوانی کنیم. این مشکل با انتقال این قطعه کد به یک تابع حل می‌شود:

    fn find_matches(content: &str, pattern: &str) {
    for line in content.lines() {
        if line.contains(pattern) {
            println!("{}", line);
        }
    }
}

    اکنون می‌توانیم این تابع را در آزمون خود فراخوانی کنیم و ببینیم خروجی‌اش چیست:

    #[test]
fn find_a_match() {
    find_matches("lorem ipsum\ndolor sit amet", "lorem");
    assert_eq!( // uhhhh

    یا… می‌توانیم؟ در حال حاضر find_matches مستقیماً در stdout یعنی ترمینال چاپ می‌کند. نمی‌توانیم به‌راحتی این را در یک آزمون بگیریم! این مشکلی است که اغلب هنگام نوشتن آزمون پس از پیاده‌سازی پیش می‌آید: تابعی نوشته‌ایم که به‌شدت با بافتی که در آن استفاده می‌شود درهم‌تنیده است.

    **توجه:** هنگام نوشتن برنامه‌های CLI کوچک این کاملاً مشکلی ندارد. لازم نیست همه‌چیز آزمون‌پذیر باشد! مهم است که فکر کنید برای کدام بخش‌های کدتان شاید بخواهید آزمون واحد بنویسید. هرچند خواهیم دید که تغییر این تابع برای آزمون‌پذیر شدن ساده است، همیشه چنین نیست.

    خب، چگونه می‌توانیم این را آزمون‌پذیر کنیم؟ باید به‌نحوی خروجی را بگیریم. کتابخانهٔ استاندارد Rust انتزاع‌های خوبی برای کار با I/O (ورودی/خروجی) دارد، و ما از یکی از آن‌ها به نام std::io::Write استفاده می‌کنیم. این یک صفت است که روی چیزهایی که می‌توانیم در آن‌ها بنویسیم انتزاع می‌کند، از جمله رشته‌ها و stdout.

    اگر این نخستین بار است که در زمینهٔ Rust واژهٔ «صفت» (trait) را می‌شنوید، در انتظار یک سورپرایز خوب باشید. صفت‌ها از قدرتمندترین ویژگی‌های Rust هستند. می‌توانید آن‌ها را مانند interfaceها در Java یا type classها در Haskell در نظر بگیرید، هر کدام که برایتان آشناتر است. آن‌ها به شما اجازه می‌دهند روی رفتارهایی انتزاع کنید که می‌تواند بین نوع‌های مختلف مشترک باشد. کدی که از صفت‌ها استفاده می‌کند می‌تواند ایده‌ها را به شیوه‌هایی بسیار جنریک و انعطاف‌پذیر بیان کند. این یعنی خواندن آن هم می‌تواند دشوار شود. بگذارید این شما را نترساند. حتی کسانی که سال‌هاست از Rust استفاده می‌کنند همیشه فوراً متوجه نمی‌شوند کد جنریک چه می‌کند. در آن حالت کمک می‌کند به کاربردهای مشخص فکر کنید. در مورد ما، رفتاری که روی آن انتزاع می‌کنیم «نوشتن در آن» است. نمونه‌هایی از نوع‌هایی که آن را پیاده‌سازی (impl) می‌کنند شامل خروجی استاندارد ترمینال، فایل‌ها، یک بافر در حافظه، یا اتصال‌های شبکهٔ TCP هستند. در مستندات std::io::Write به پایین بروید تا فهرست «Implementors» را ببینید.

    با این دانش، بیایید تابع خود را طوری تغییر دهیم که پارامتر سومی بپذیرد. این پارامتر می‌تواند هر نوعی باشد که Write را پیاده‌سازی می‌کند. به این ترتیب می‌توانیم در آزمون‌هایمان یک رشتهٔ ساده بدهیم و روی آن assertion بنویسیم. این نسخه از find_matches را می‌توانیم این‌گونه بنویسیم:

    fn find_matches(content: &str, pattern: &str, mut writer: impl std::io::Write) {
    for line in content.lines() {
        if line.contains(pattern) {
            writeln!(writer, "{}", line);
        }
    }
}

    پارامتر جدید mut writer است، یعنی چیزی تغییرپذیر که آن را «writer» می‌نامیم. نوع آن impl std::io::Write است، که می‌توانید آن را جایگاهی برای هر نوعی که صفت Write را پیاده‌سازی می‌کند بخوانید. توجه کنید که println!(…) ای را که پیش‌تر به کار می‌بردیم با writeln!(writer, …) جایگزین کردیم. println! مانند writeln! کار می‌کند، اما همیشه از خروجی استاندارد استفاده می‌کند.

    اکنون می‌توانیم خروجی را آزمون کنیم:

    #[test]
fn find_a_match() {
    let mut result = Vec::new();
    find_matches("lorem ipsum\ndolor sit amet", "lorem", &mut result);
    assert_eq!(result, b"lorem ipsum\n");
}

    برای استفاده از این در کد برنامه‌مان، باید فراخوانی find_matches را در main تغییر دهیم و &mut std::io::stdout() را به‌عنوان پارامتر سوم اضافه کنیم. در ادامه نمونه‌ای از تابع main آمده که بر آنچه در فصل‌های قبل دیدیم بنا شده و از تابع استخراج‌شدهٔ find_matches ما استفاده می‌کند:

    fn main() -> Result<()> {
    let args = Cli::parse();
    let content = std::fs::read_to_string(&args.path)
        .with_context(|| format!("could not read file `{}`", args.path.display()))?;

    find_matches(&content, &args.pattern, &mut std::io::stdout());

    Ok(())
}

    توجه: از آن‌جا که stdout بایت می‌خواهد (نه رشته)، به‌جای std::fmt::Write از std::io::Write استفاده می‌کنیم. در نتیجه در آزمون‌هایمان یک بردار خالی را به‌عنوان writer می‌دهیم (نوع آن به Vec<u8> استنباط می‌شود)، و در assert_eq! از b"foo" استفاده می‌کنیم. پیشوند b آن را به یک لیترال رشتهٔ بایتی تبدیل می‌کند، پس نوع آن به‌جای &str، &[u8] خواهد بود.

    توجه: می‌توانستیم این تابع را وادار کنیم یک String برگرداند، اما این رفتار آن را تغییر می‌داد. به‌جای نوشتن مستقیم در ترمینال، آنگاه همه‌چیز را در یک رشته جمع می‌کرد و همهٔ نتایج را یک‌جا در پایان خالی می‌کرد.

    تمرین برای خواننده: writeln! یک io::Result برمی‌گرداند زیرا نوشتن می‌تواند شکست بخورد (برای مثال، وقتی بافر پر است و نمی‌توان آن را بزرگ‌تر کرد). مدیریت خطا را به find_matches اضافه کنید.

    اکنون دیدیم چگونه این قطعه کد را آزمون‌پذیر کنیم. کارهایی که کردیم:

    1. یکی از بخش‌های اصلی برنامه‌مان را شناسایی کردیم.
    2. آن را در تابع مخصوص خودش گذاشتیم.
    3. آن را انعطاف‌پذیرتر کردیم.

    هرچند هدف آزمون‌پذیر کردن بود، نتیجه‌ای که به آن رسیدیم در واقع قطعه کد Rust بسیار اصطلاحی و قابل‌استفادهٔ مجدد است. عالی است!

    تقسیم کد به هدف‌های کتابخانه و باینری

    می‌توانیم یک کار دیگر هم این‌جا انجام دهیم. تا اینجا همهٔ چیزهایی را که نوشتیم در فایل src/main.rs گذاشته‌ایم. این یعنی پروژهٔ فعلی ما یک باینری تولید می‌کند، اما می‌توانیم کدمان را به‌صورت یک کتابخانه هم در دسترس قرار دهیم، این‌گونه:

    1. تابع find_matches را در یک src/lib.rs جدید بگذارید.
    2. یک pub پیش از fn اضافه کنید تا آن را به چیزی تبدیل کنید که کاربران کتابخانهٔ ما به آن دسترسی دارند (یعنی pub fn find_matches).
    3. find_matches را از src/main.rs حذف کنید.
    4. در fn main، پیش از فراخوانی find_matches عبارت grrs:: را بیفزایید تا اکنون grrs::find_matches(…) شود. این یعنی از تابعی استفاده می‌کند که در کتابخانهٔ تازه‌نوشته‌مان است!

    روشی که Rust با پروژه‌ها کار می‌کند کاملاً انعطاف‌پذیر است، و فکر کردن از همان ابتدا به این‌که چه چیزی را در بخش کتابخانهٔ crate خود بگذارید ایدهٔ خوبی است. برای مثال می‌توانید ابتدا به نوشتن کتابخانه‌ای برای منطق مخصوص برنامه‌تان فکر کنید و سپس آن را در CLI خود مانند هر کتابخانهٔ دیگری به کار ببرید. یا اگر پروژه‌تان چند باینری دارد، می‌توانید عملکرد مشترک را در بخش کتابخانهٔ آن crate بگذارید.

    توجه: حالا که صحبت از قرار دادن همه‌چیز در src/main.rs شد، اگر به این کار ادامه دهیم خواندن کد دشوار می‌شود. سامانهٔ ماژول می‌تواند به ساختاردهی و سازمان‌دهی کدتان کمک کند.

    آزمون برنامه‌های CLI با اجرای آن‌ها

    تا اینجا برای آزمودن منطق کسب‌وکار برنامه‌مان که معلوم شد همان تابع find_matches است، زحمت زیادی کشیده‌ایم. این بسیار ارزشمند است و گام نخست عالی‌ای است به‌سوی یک کدبیس به‌خوبی آزمون‌شده. معمولاً این نوع آزمون‌ها «آزمون واحد» نامیده می‌شوند.

    کد زیادی هست که آزمون نمی‌کنیم: هر چیزی که برای سروکار داشتن با دنیای بیرون نوشتیم! تصور کنید تابع main را نوشته‌اید اما به‌طور تصادفی یک رشتهٔ ثابت را رها کرده‌اید به‌جای آن‌که از آرگومان مسیر ارائه‌شده توسط کاربر استفاده کنید. باید برای آن هم آزمون بنویسیم! این سطح از آزمون اغلب آزمون یکپارچگی یا آزمون سیستم نامیده می‌شود.

    در هسته، هنوز داریم تابع می‌نویسیم و آن‌ها را با #[test] حاشیه‌نویسی می‌کنیم. فقط مسئله این است که درون این تابع‌ها چه می‌کنیم. برای مثال، می‌خواهیم از باینری اصلی پروژه‌مان استفاده کنیم و آن را مانند یک برنامهٔ معمولی اجرا کنیم. این آزمون‌ها را در یک فایل جدید در یک دایرکتوری جدید می‌گذاریم: tests/cli.rs.

    توجه: طبق قرارداد، cargo آزمون‌های یکپارچگی را در دایرکتوری tests/ جست‌وجو می‌کند. به‌همین ترتیب بنچمارک‌ها را در benches/ و مثال‌ها را در examples/ می‌جوید. این قراردادها به کد سورس اصلی شما هم تعمیم می‌یابند: کتابخانه‌ها فایل src/lib.rs دارند، باینری اصلی src/main.rs است، و اگر چند باینری وجود داشته باشد، cargo انتظار دارد آن‌ها در src/bin/<name>.rs باشند. پیروی از این قراردادها کدبیس شما را برای کسانی که به خواندن کد Rust عادت دارند قابل‌کشف‌تر می‌کند.

    grrs ابزار کوچکی است که یک رشته را در یک فایل جست‌وجو می‌کند. پیش‌تر آزمون کرده‌ایم که می‌توانیم یک تطابق پیدا کنیم. بیایید فکر کنیم چه عملکردهای دیگری را می‌توانیم آزمون کنیم.

    این‌ها مواردی است که به ذهن من رسید:

    • وقتی فایل وجود ندارد چه اتفاقی می‌افتد؟
    • وقتی هیچ تطابقی نیست خروجی چیست؟
    • آیا وقتی یکی (یا هر دو) آرگومان را فراموش می‌کنیم، برنامهٔ ما با خطا خارج می‌شود؟

    همهٔ این‌ها موارد آزمون معتبری هستند. علاوه بر این، باید یک مورد آزمون هم برای مسیر موفق داشته باشیم: دست‌کم یک تطابق پیدا می‌کنیم و آن را چاپ می‌کنیم.

    برای آسان‌تر کردن این نوع آزمون‌ها از crate به نام assert_cmd استفاده می‌کنیم. این crate مجموعه‌ای از کمک‌کننده‌های خوب دارد که به ما اجازه می‌دهند باینری اصلی خود را اجرا کنیم و ببینیم چگونه رفتار می‌کند. همچنین crate به نام predicates را اضافه می‌کنیم که به ما کمک می‌کند assertionهایی بنویسیم که assert_cmd بتواند با آن‌ها آزمون کند و پیام‌های خطای عالی دارند. این وابستگی‌ها را به فهرست اصلی اضافه نمی‌کنیم، بلکه به بخش dev dependencies در Cargo.toml اضافه می‌کنیم. آن‌ها فقط هنگام توسعهٔ crate لازم هستند، نه هنگام استفاده از آن.

    [dev-dependencies]
assert_cmd = "2.0.14"
predicates = "3.1.0"

    این به نظر راه‌اندازی زیادی می‌رسد. با این حال، بیایید یک‌راست وارد شویم و فایل tests/cli.rs خود را بسازیم:

    use assert_cmd::cargo::*; // Import cargo_bin_cmd! macro and methods
use predicates::prelude::*; // Used for writing assertions

#[test]
fn file_doesnt_exist() -> Result<(), Box<dyn std::error::Error>> {
    let mut cmd = cargo_bin_cmd!("grrs");

    cmd.arg("foobar").arg("test/file/doesnt/exist");
    cmd.assert()
        .failure()
        .stderr(predicate::str::contains("could not read file"));

    Ok(())
}

    می‌توانید این آزمون را با cargo test اجرا کنید، درست مانند آزمون‌هایی که بالاتر نوشتیم. بار نخست ممکن است کمی بیشتر طول بکشد چون Command::cargo_bin("grrs") باید باینری اصلی شما را کامپایل کند.

    تولید فایل‌های آزمون

    آزمونی که همین حالا دیدیم فقط بررسی می‌کند که برنامه‌مان وقتی فایل ورودی وجود ندارد پیام خطا می‌نویسد. این آزمون مهمی است، اما شاید مهم‌ترین آزمون نباشد. بیایید آزمون کنیم که واقعاً تطابق‌هایی را که در یک فایل پیدا کردیم چاپ می‌کنیم!

    به فایلی نیاز داریم که محتوایش را بدانیم تا بدانیم برنامه‌مان باید چه چیزی برگرداند و این انتظار را در کدمان بررسی کنیم. یک ایده می‌تواند افزودن فایلی با محتوای دلخواه به پروژه و استفاده از آن در آزمون‌هایمان باشد. ایدهٔ دیگر ساختن فایل‌های موقت در آزمون‌هایمان است. برای این آموزش به رویکرد دوم نگاه می‌کنیم. این رویکرد انعطاف‌پذیرتر است و در موارد دیگر هم کار می‌کند؛ برای مثال وقتی برنامه‌هایی را آزمون می‌کنید که فایل‌ها را تغییر می‌دهند.

    برای ساختن این فایل‌های موقت از crate به نام assert_fs استفاده می‌کنیم. بیایید آن را به dev-dependencies در Cargo.toml خود اضافه کنیم:

    assert_fs = "1.1.1"

    این یک مورد آزمون جدید است که یک فایل موقت می‌سازد (یک فایل «نام‌دار» تا بتوانیم مسیرش را بگیریم)، آن را با مقداری متن پر می‌کند، و سپس برنامه‌مان را اجرا می‌کند تا ببیند خروجی درست می‌گیریم یا نه. می‌توانید آن را زیر مورد آزمون دیگر بنویسید. وقتی متغیر file در پایان تابع از محدوده خارج می‌شود، فایل موقت واقعی به‌طور خودکار حذف می‌شود.

    #[test]
fn find_content_in_file() -> Result<(), Box<dyn std::error::Error>> {
    let file = assert_fs::NamedTempFile::new("sample.txt")?;
    file.write_str("A test\nActual content\nMore content\nAnother test")?;

    let mut cmd = cargo_bin_cmd!("grrs");
    cmd.arg("test").arg(file.path());
    cmd.assert()
        .success()
        .stdout(predicate::str::contains("A test\nAnother test"));

    Ok(())
}

    **تمرین برای خواننده:** آزمون‌های یکپارچگی‌ای برای وقتی که یک رشتهٔ خالی را به‌عنوان الگو می‌دهیم اضافه کنید. برنامه را در صورت نیاز تنظیم کنید.

    چه چیزی را آزمون کنیم؟

    هرچند نوشتن آزمون‌های یکپارچگی قطعاً می‌تواند سرگرم‌کننده باشد، نوشتن آن‌ها مدتی طول می‌کشد و همچنین به‌روز کردن آن‌ها وقتی رفتار برنامه‌تان تغییر می‌کند. برای اطمینان از این‌که زمانتان را عاقلانه صرف می‌کنید، باید از خودتان بپرسید چه چیزی را باید آزمون کنید.

    به‌طور کلی ایدهٔ خوبی است که آزمون یکپارچگی برای همهٔ انواع رفتاری که کاربر می‌تواند مشاهده کند بنویسید. این یعنی لازم نیست همهٔ حالت‌های مرزی را پوشش دهید. معمولاً کافی است برای انواع مختلف مثال داشته باشید و برای پوشش حالت‌های مرزی به آزمون‌های واحد تکیه کنید.

    همچنین ایدهٔ خوبی است که آزمون‌هایتان را روی چیزهایی که نمی‌توانید فعالانه کنترل کنید متمرکز نکنید. آزمودن چیدمان دقیق --help ایدهٔ بدی خواهد بود چون برای شما تولید می‌شود. در عوض ممکن است فقط بخواهید بررسی کنید که عناصر خاصی حاضرند.

    بسته به ماهیت برنامه‌تان، می‌توانید تکنیک‌های آزمون بیشتری هم امتحان کنید. برای مثال، اگر بخش‌هایی از برنامه‌تان را استخراج کرده‌اید و می‌بینید هنگام تلاش برای یافتن همهٔ حالت‌های مرزی مثال‌های زیادی را به‌صورت آزمون واحد می‌نویسید، باید به proptest نگاه کنید. اگر برنامه‌ای دارید که فایل‌های دلخواه را مصرف و تحلیل می‌کند، سعی کنید یک fuzzer بنویسید تا باگ‌ها را در حالت‌های مرزی پیدا کند.

    توجه: کد سورس کامل و قابل‌اجرایی را که در این فصل به کار رفته در مخزن این کتاب پیدا می‌کنید.
