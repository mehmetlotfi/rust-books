    مالکیت و طول عمر

    مالکیت ویژگی برجستهٔ Rust است. این ویژگی به Rust اجازه می‌دهد کاملاً امن از نظر حافظه و کارا باشد، و در عین حال از زباله‌روبی (garbage collection) پرهیز کند. پیش از ورود به جزئیات سیستم مالکیت، انگیزهٔ پشت این طراحی را بررسی می‌کنیم.

    فرض می‌کنیم می‌پذیرید که زباله‌روبی (GC) همیشه راه‌حل بهینه‌ای نیست و در برخی زمینه‌ها مدیریت دستی حافظه مطلوب است. اگر این را نمی‌پذیرید، آیا می‌توانم زبانی دیگر را به شما پیشنهاد کنم؟

    فارغ از نظرتان دربارهٔ GC، کاملاً روشن است که یک مزیت عظیم برای امن‌کردن کد است. هرگز لازم نیست نگران از بین رفتن چیزها خیلی زود باشید (هرچند اینکه آیا هنوز می‌خواستید به آن چیز اشاره کنید یا نه، مسئلهٔ دیگری است…). این یک مشکل فراگیر است که برنامه‌های C و C++ باید با آن سروکار داشته باشند. این اشتباه ساده را در نظر بگیرید که همهٔ ما که از یک زبان بدون GC استفاده کرده‌ایم، زمانی مرتکب آن شده‌ایم:

    fn as_str(data: &u32) -> &str {
    // compute the string
    let s = format!("{}", data);

    // OH NO! We returned a reference to something that
    // exists only in this function!
    // Dangling pointer! Use after free! Alas!
    // (this does not compile in Rust)
    &s
}

    این دقیقاً همان چیزی است که سیستم مالکیت Rust برای حل آن ساخته شد. Rust حوزه‌ای را که &s در آن زنده است می‌شناسد و به همین دلیل می‌تواند از فرار آن جلوگیری کند. با این حال این یک حالت ساده است که حتی یک کامپایلر C هم احتمالاً می‌تواند آن را بگیرد. هرچه کد بزرگ‌تر می‌شود و اشاره‌گرها از میان تابع‌های مختلف عبور داده می‌شوند، کار پیچیده‌تر می‌شود. در نهایت، کامپایلر C از پا درمی‌آید و نمی‌تواند تحلیل فرار کافی برای اثبات ناامن بودن کد شما انجام دهد. در نتیجه مجبور می‌شود برنامهٔ شما را با این فرض که درست است بپذیرد.

    این هرگز برای Rust اتفاق نمی‌افتد. این برنامه‌نویس است که باید به کامپایلر ثابت کند همه چیز سالم و امن است.

    البته، داستان مالکیت در Rust بسیار پیچیده‌تر از صرفِ تأیید این است که ارجاع‌ها از حوزهٔ مرجع‌شان فرار نمی‌کنند. دلیلش این است که تضمین معتبر بودن همیشگی اشاره‌گرها بسیار پیچیده‌تر از این است. برای مثال در این کد،

    let mut data = vec![1, 2, 3];
// get an internal reference
let x = &data[0];

// OH NO! `push` causes the backing storage of `data` to be reallocated.
// Dangling pointer! Use after free! Alas!
// (this does not compile in Rust)
data.push(4);

println!("{}", x);

    تحلیل ساده‌لوحانهٔ حوزه برای جلوگیری از این باگ کافی نخواهد بود، زیرا data در واقع به‌اندازهٔ لازم زنده است. با این حال در حالی که ارجاعی به درون آن داشتیم، آن تغییر کرد. به همین دلیل Rust از هر ارجاعی می‌خواهد مرجع و مالکانش را منجمد کند.
