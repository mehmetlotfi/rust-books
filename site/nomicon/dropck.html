    بررسی drop

    دیدیم که طول عمرها چگونه قوانین نسبتاً ساده‌ای برای تضمین اینکه هرگز ارجاع معلق (dangling) نخوانیم در اختیارمان می‌گذارند. با این حال تا اینجا رابطه‌ی outlives را همیشه به شکل فراگیر (inclusive) به کار برده‌ایم. یعنی وقتی از 'a: 'b صحبت می‌کردیم، اشکالی نداشت که 'a دقیقاً به اندازه‌ی 'b زنده بماند. در نگاه اول، این تمایز بی‌معنی به نظر می‌رسد. هیچ چیزی همزمان با چیز دیگری drop نمی‌شود، درست است؟ به همین دلیل از این desugaring برای دستورهای let استفاده کردیم:

    let x;
let y;

    که desugar می‌شود به:

    {
    let x;
    {
        let y;
    }
}

    شرایط پیچیده‌تری هم هست که نمی‌توان با استفاده از scopeها آن‌ها را desugar کرد، اما ترتیب همچنان تعریف‌شده است ‒ متغیرها به ترتیب معکوس تعریفشان drop می‌شوند و فیلدهای ساختارها و tupleها به ترتیب تعریفشان. جزئیات بیشتری درباره‌ی ترتیب drop در RFC 1857 آمده است.

    بیایید این کار را بکنیم:

    let tuple = (vec![], vec![]);

    بردار سمت چپ ابتدا drop می‌شود. اما آیا این بدان معناست که از دید borrow checker، بردار سمت راست به‌طور اکید از آن بیشتر عمر می‌کند؟ پاسخ این پرسش خیر است. borrow checker می‌تواند فیلدهای tuple را جداگانه ردیابی کند، اما باز هم نمی‌تواند در مورد عناصر بردار تصمیم بگیرد که چه چیزی از چه چیزی بیشتر عمر می‌کند، چون این عناصر به‌صورت دستی و از طریق کد کتابخانه‌ای محض drop می‌شوند که borrow checker آن را نمی‌فهمد.

    پس چرا اهمیت می‌دهیم؟ چون اگر سیستم نوع دقت نکند، ممکن است به‌طور تصادفی اشاره‌گرهای معلق بسازد. برنامه‌ی ساده‌ی زیر را در نظر بگیرید:

    struct Inspector<'a>(&'a u8);

struct World<'a> {
    inspector: Option<Inspector<'a>>,
    days: Box<u8>,
}

fn main() {
    let mut world = World {
        inspector: None,
        days: Box::new(1),
    };
    world.inspector = Some(Inspector(&world.days));
}

    این برنامه کاملاً صحیح (sound) است و امروز کامپایل می‌شود. اینکه days به‌طور اکید بیشتر از inspector عمر نمی‌کند اهمیتی ندارد. تا زمانی که inspector زنده است، days هم زنده است.

    اما اگر یک destructor اضافه کنیم، برنامه دیگر کامپایل نمی‌شود!

    struct Inspector<'a>(&'a u8);

impl<'a> Drop for Inspector<'a> {
    fn drop(&mut self) {
        println!("I was only {} days from retirement!", self.0);
    }
}

struct World<'a> {
    inspector: Option<Inspector<'a>>,
    days: Box<u8>,
}

fn main() {
    let mut world = World {
        inspector: None,
        days: Box::new(1),
    };
    world.inspector = Some(Inspector(&world.days));
    // Let's say `days` happens to get dropped first.
    // Then when Inspector is dropped, it will try to read free'd memory!
}

    می‌توانید ترتیب فیلدها را تغییر دهید یا به‌جای ساختار از tuple استفاده کنید، باز هم کامپایل نخواهد شد.

    پیاده‌سازی Drop به Inspector اجازه می‌دهد هنگام مرگش کدی دلخواه اجرا کند. این یعنی ممکن است بتواند ببیند که نوع‌هایی که قرار بود به اندازه‌ی خودش زنده بمانند، در واقع زودتر نابود شده‌اند.

    جالب اینکه فقط نوع‌های جنریک باید نگران این موضوع باشند. اگر جنریک نباشند، تنها طول عمری که می‌توانند در خود جای دهند 'static است که واقعاً برای همیشه زنده می‌ماند. به همین دلیل این مشکل را sound generic drop (drop صحیح جنریک) می‌نامند. sound generic drop توسط drop checker اِعمال می‌شود. در زمان نگارش این متن، برخی از جزئیات دقیق‌تر اینکه drop checker (که dropck هم نامیده می‌شود) چگونه نوع‌ها را اعتبارسنجی می‌کند کاملاً نامشخص است. با این حال «قانون بزرگ» همان ظرافتی است که در سراسر این بخش بر آن تمرکز کرده‌ایم:

    برای اینکه یک نوع جنریک بتواند drop را به‌صورت صحیح پیاده‌سازی کند، آرگومان‌های جنریک آن باید به‌طور اکید بیشتر از خودش عمر کنند.

    رعایت این قانون (معمولاً) برای راضی‌کردن borrow checker لازم است؛ رعایت آن برای صحیح‌بودن کافی است اما ضروری نیست. یعنی اگر نوع شما از این قانون پیروی کند، قطعاً drop آن صحیح است.

    دلیل اینکه همیشه لازم نیست قانون بالا رعایت شود این است که برخی پیاده‌سازی‌های Drop به داده‌ی قرض‌گرفته‌شده دسترسی نمی‌یابند، هرچند نوعشان چنین قابلیت دسترسی‌ای به آن‌ها می‌دهد، یا اینکه ترتیب دقیق drop را می‌دانیم و داده‌ی قرض‌گرفته‌شده حتی اگر borrow checker این را نداند، همچنان سالم است.

    برای مثال، این گونه‌ی مثال Inspector بالا هرگز به داده‌ی قرض‌گرفته‌شده دسترسی نخواهد یافت:

    struct Inspector<'a>(&'a u8, &'static str);

impl<'a> Drop for Inspector<'a> {
    fn drop(&mut self) {
        println!("Inspector(_, {}) knows when *not* to inspect.", self.1);
    }
}

struct World<'a> {
    inspector: Option<Inspector<'a>>,
    days: Box<u8>,
}

fn main() {
    let mut world = World {
        inspector: None,
        days: Box::new(1),
    };
    world.inspector = Some(Inspector(&world.days, "gadget"));
    // Let's say `days` happens to get dropped first.
    // Even when Inspector is dropped, its destructor will not access the
    // borrowed `days`.
}

    به همین ترتیب، این گونه نیز هرگز به داده‌ی قرض‌گرفته‌شده دسترسی نخواهد یافت:

    struct Inspector<T>(T, &'static str);

impl<T> Drop for Inspector<T> {
    fn drop(&mut self) {
        println!("Inspector(_, {}) knows when *not* to inspect.", self.1);
    }
}

struct World<T> {
    inspector: Option<Inspector<T>>,
    days: Box<u8>,
}

fn main() {
    let mut world = World {
        inspector: None,
        days: Box::new(1),
    };
    world.inspector = Some(Inspector(&world.days, "gadget"));
    // Let's say `days` happens to get dropped first.
    // Even when Inspector is dropped, its destructor will not access the
    // borrowed `days`.
}

    با این حال، borrow checker هر دو گونه‌ی بالا را هنگام تحلیل fn main رد می‌کند و می‌گوید days به اندازه‌ی کافی زنده نمی‌ماند.

    دلیل این است که تحلیل borrow checking برای main از جزئیات داخلی پیاده‌سازی Drop هر Inspector خبر ندارد. تا آنجا که borrow checker هنگام تحلیل main می‌داند، بدنه‌ی destructor یک inspector ممکن است به آن داده‌ی قرض‌گرفته‌شده دسترسی پیدا کند.

    بنابراین drop checker همه‌ی داده‌های قرض‌گرفته‌شده در یک مقدار را مجبور می‌کند که به‌طور اکید بیشتر از آن مقدار عمر کنند.

    یک راه گریز

    قوانین دقیقی که بررسی drop را کنترل می‌کنند ممکن است در آینده محدودکننده‌ی کمتری باشند.

    تحلیل فعلی عمداً محافظه‌کارانه است؛ همه‌ی داده‌های قرض‌گرفته‌شده در یک مقدار را مجبور می‌کند بیشتر از آن مقدار عمر کنند، که قطعاً صحیح است.

    نسخه‌های آینده‌ی زبان ممکن است تحلیل را دقیق‌تر کنند تا شمار حالت‌هایی که در آن‌ها کد صحیح به‌عنوان ناایمن رد می‌شود کاهش یابد. این کار به رفع حالت‌هایی مانند دو Inspector بالا که می‌دانند هنگام نابودی نباید چیزی را بازرسی کنند کمک می‌کند.

    در این میان، یک attribute ناپایدار وجود دارد که می‌توان از آن برای ادعای (به‌صورت ناایمن) این استفاده کرد که destructor یک نوع جنریک تضمین‌شده به هیچ داده‌ی منقضی‌شده‌ای دسترسی نمی‌یابد، حتی اگر نوعش این قابلیت را به آن بدهد.

    این attribute may_dangle نام دارد و در RFC 1327 معرفی شد. برای به‌کارگیری آن روی Inspector بالا، چنین می‌نویسیم:

    #![feature(dropck_eyepatch)]

struct Inspector<'a>(&'a u8, &'static str);

unsafe impl<#[may_dangle] 'a> Drop for Inspector<'a> {
    fn drop(&mut self) {
        println!("Inspector(_, {}) knows when *not* to inspect.", self.1);
    }
}

struct World<'a> {
    days: Box<u8>,
    inspector: Option<Inspector<'a>>,
}

fn main() {
    let mut world = World {
        inspector: None,
        days: Box::new(1),
    };
    world.inspector = Some(Inspector(&world.days, "gadget"));
}

    استفاده از این attribute مستلزم آن است که پیاده‌سازی Drop با unsafe علامت‌گذاری شود، زیرا کامپایلر این ادعای ضمنی را که به هیچ داده‌ی بالقوه منقضی‌شده‌ای (مثلاً self.0 در بالا) دسترسی نمی‌شود بررسی نمی‌کند.

    این attribute را می‌توان بر هر تعداد پارامتر طول عمر و نوع اعمال کرد. در مثال زیر، ادعا می‌کنیم که به هیچ داده‌ای پشت ارجاعی با طول عمر 'b دسترسی نداریم و تنها کاربردهای T انتقال یا drop خواهند بود، اما attribute را از 'a و U حذف می‌کنیم، چون به داده‌هایی با آن طول عمر و آن نوع دسترسی داریم:

    #![feature(dropck_eyepatch)]
use std::fmt::Display;

struct Inspector<'a, 'b, T, U: Display>(&'a u8, &'b u8, T, U);

unsafe impl<'a, #[may_dangle] 'b, #[may_dangle] T, U: Display> Drop for Inspector<'a, 'b, T, U> {
    fn drop(&mut self) {
        println!("Inspector({}, _, _, {})", self.0, self.3);
    }
}

    گاهی واضح است که چنین دسترسی‌ای رخ نمی‌دهد، مانند حالت بالا. اما هنگام کار با یک پارامتر نوع جنریک، چنین دسترسی‌ای می‌تواند به‌طور غیرمستقیم رخ دهد. نمونه‌هایی از این دسترسی غیرمستقیم عبارت‌اند از:

    • فراخوانی یک callback،
    • از طریق فراخوانی متد یک صفت.

    (تغییرات آینده‌ی زبان، مانند impl specialization، ممکن است راه‌های دیگری برای چنین دسترسی غیرمستقیمی اضافه کنند.)

    این هم مثالی از فراخوانی یک callback:

    struct Inspector<T>(T, &'static str, Box<for <'r> fn(&'r T) -> String>);

impl<T> Drop for Inspector<T> {
    fn drop(&mut self) {
        // The `self.2` call could access a borrow e.g. if `T` is `&'a _`.
        println!("Inspector({}, {}) unwittingly inspects expired data.",
                 (self.2)(&self.0), self.1);
    }
}

    و این هم مثالی از فراخوانی متد یک صفت:

    use std::fmt;

struct Inspector<T: fmt::Display>(T, &'static str);

impl<T: fmt::Display> Drop for Inspector<T> {
    fn drop(&mut self) {
        // There is a hidden call to `<T as Display>::fmt` below, which
        // could access a borrow e.g. if `T` is `&'a _`
        println!("Inspector({}, {}) unwittingly inspects expired data.",
                 self.0, self.1);
    }
}

    و البته همه‌ی این دسترسی‌ها می‌توانند در متد دیگری که destructor آن را فراخوانی می‌کند پنهان شوند، به‌جای آنکه مستقیماً در خود destructor نوشته شوند.

    در همه‌ی حالت‌های بالا که در destructor به &'a u8 دسترسی می‌شود، افزودن attribute با نام #[may_dangle] نوع را در برابر سوءاستفاده‌ای آسیب‌پذیر می‌کند که borrow checker آن را نمی‌گیرد و به آشوب دعوت می‌کند. بهتر است از افزودن این attribute پرهیز شود.

    یادداشتی جانبی و مرتبط درباره‌ی ترتیب drop

    اگرچه ترتیب drop فیلدهای درون یک struct تعریف‌شده است، تکیه‌کردن بر آن شکننده و ظریف است. وقتی ترتیب اهمیت دارد، بهتر است از پوشانهٔ ManuallyDrop استفاده شود.

    آیا درباره‌ی drop checker همین بود؟

    معلوم می‌شود هنگام نوشتن کد unsafe، عموماً اصلاً لازم نیست نگران انجام کار درست برای drop checker باشیم. با این حال یک حالت خاص وجود دارد که باید نگرانش باشید و در بخش بعد به آن می‌پردازیم.
