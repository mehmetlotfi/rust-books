    کار با Unsafe

    Rust عموماً فقط ابزارهایی به ما می‌دهد که بتوانیم دربارهٔ Unsafe Rust به شیوه‌ای محدود به دامنه (scoped) و دودویی صحبت کنیم. متأسفانه واقعیت به‌طور قابل‌توجهی پیچیده‌تر از این است. برای مثال، تابع اسباب‌بازی زیر را در نظر بگیرید:

    fn index(idx: usize, arr: &[u8]) -> Option<u8> {
    if idx < arr.len() {
        unsafe {
            Some(*arr.get_unchecked(idx))
        }
    } else {
        None
    }
}

    این تابع ایمن و درست است. بررسی می‌کنیم که اندیس در محدوده باشد، و اگر بود، به شیوه‌ای بررسی‌نشده به آرایه اندیس می‌زنیم. چنین تابع درستی را که به‌صورت ناایمن پیاده‌سازی شده است سالم (sound) می‌نامیم، یعنی کد ایمن نمی‌تواند از طریق آن رفتار تعریف‌نشده ایجاد کند (که، یادتان باشد، تنها ویژگی بنیادین Safe Rust است).

    اما حتی در چنین تابع پیش‌پاافتاده‌ای هم دامنهٔ بلوک unsafe محل پرسش است. تغییر < به <= را در نظر بگیرید:

    fn index(idx: usize, arr: &[u8]) -> Option<u8> {
    if idx <= arr.len() {
        unsafe {
            Some(*arr.get_unchecked(idx))
        }
    } else {
        None
    }
}

    این برنامه حالا ناسالم (unsound) است، Safe Rust می‌تواند رفتار تعریف‌نشده ایجاد کند، و با این حال ما فقط کد ایمن را تغییر دادیم. این مسئلهٔ بنیادین ایمنی است: غیرمحلی است. سلامت عملیات ناایمن ما ناگزیر به حالتی بستگی دارد که عملیات «ایمنِ» دیگر برقرار کرده‌اند.

    ایمنی از این نظر ماژولار است که انتخاب ناایمنی از شما نمی‌خواهد انواع دیگر و دلخواهِ بدی را در نظر بگیرید. برای مثال، اندیس‌زدن بررسی‌نشده به یک slice به این معنا نیست که ناگهان باید نگران null بودن slice یا داشتن حافظهٔ مقداردهی‌نشده باشید. هیچ چیزی به‌طور بنیادین تغییر نمی‌کند. با این حال ایمنی از این نظر ماژولار نیست که برنامه‌ها ذاتاً دارای حالت‌اند و عملیات ناایمن شما ممکن است به حالت‌های دلخواه دیگری وابسته باشد.

    وقتی حالت پایدار واقعی را وارد کنیم، این غیرمحلی بودن بسیار بدتر می‌شود. پیاده‌سازی ساده‌ای از Vec را در نظر بگیرید:

    use std::ptr;

// Note: This definition is naive. See the chapter on implementing Vec.
pub struct Vec<T> {
    ptr: *mut T,
    len: usize,
    cap: usize,
}

// Note this implementation does not correctly handle zero-sized types.
// See the chapter on implementing Vec.
impl<T> Vec<T> {
    pub fn push(&mut self, elem: T) {
        if self.len == self.cap {
            // not important for this example
            self.reallocate();
        }
        unsafe {
            ptr::write(self.ptr.add(self.len), elem);
            self.len += 1;
        }
    }
    fn reallocate(&mut self) { }
}

fn main() {}

    این کد آن‌قدر ساده است که بتوان به‌طور معقول آن را بازرسی و به‌صورت غیررسمی راستی‌آزمایی کرد. حالا اضافه کردن متد زیر را در نظر بگیرید:

    fn make_room(&mut self) {
    // grow the capacity
    self.cap += 1;
}

    این کد ۱۰۰٪ Safe Rust است اما کاملاً ناسالم هم هست. تغییر ظرفیت، پایاهای (invariant) Vec را نقض می‌کند (اینکه cap فضای تخصیص‌یافته در Vec را منعکس می‌کند). این چیزی نیست که بقیهٔ Vec بتواند در برابرش محافظت کند. Vec ناچار است به فیلد ظرفیت اعتماد کند چون راهی برای راستی‌آزمایی آن وجود ندارد.

    چون به پایاهای یک فیلد ساختار متکی است، این کد unsafe بیش از آلوده کردن یک تابع کامل کار می‌کند: یک ماژول کامل را آلوده می‌کند. عموماً تنها راه ضدگلوله برای محدود کردن دامنهٔ کد ناایمن، مرز ماژول به‌همراه حریم خصوصی (privacy) است.

    با این حال این روش کاملاً جواب می‌دهد. وجود make_room برای سلامت Vec مشکلی نیست چون آن را عمومی علامت نزده‌ایم. فقط ماژولی که این تابع را تعریف می‌کند می‌تواند آن را صدا بزند. همچنین make_room مستقیماً به فیلدهای خصوصی Vec دسترسی دارد، پس فقط می‌توان آن را در همان ماژولِ Vec نوشت.

    بنابراین برای ما ممکن است انتزاعی کاملاً ایمن بنویسیم که به پایاهای پیچیده متکی است. این برای رابطهٔ میان Safe Rust و Unsafe Rust حیاتی است.

    پیش‌تر دیده‌ایم که کد ناایمن باید به بعضی از کدهای ایمن اعتماد کند، اما نباید به کد ایمنِ جنریک اعتماد کند. حریم خصوصی به دلایل مشابهی برای کد ناایمن مهم است: این مانع می‌شود که مجبور باشیم به همهٔ کدهای ایمن دنیا اعتماد کنیم که با حالت مورد اعتماد ما دست‌کاری نمی‌کنند.

    ایمنی زنده است!
