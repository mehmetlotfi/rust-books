    تخصیص حافظه

    استفاده از NonNull مشکلی برای یکی از ویژگی‌های مهم Vec (و در واقع همهٔ مجموعه‌های std) ایجاد می‌کند: ساختن یک Vec خالی اصلاً چیزی تخصیص نمی‌دهد. این با تخصیص یک بلوک حافظهٔ با اندازهٔ صفر یکی نیست، که تخصیص‌دهندهٔ سراسری (global allocator) آن را مجاز نمی‌داند (به رفتار تعریف‌نشده می‌انجامد!). پس اگر نمی‌توانیم تخصیص بدهیم، و همچنین نمی‌توانیم اشاره‌گر null را در ptr بگذاریم، در Vec::new چه کنیم؟ خب، فقط یک مقدار بی‌اهمیت دیگر را آنجا می‌گذاریم!

    این کاملاً اشکالی ندارد، چون از قبل cap == 0 را به‌عنوان نشانگر «بدون تخصیص» داریم. تقریباً در هیچ کدی لازم نیست آن را به‌طور ویژه مدیریت کنیم، چون معمولاً به‌هرحال باید بررسی کنیم که cap > len یا len > 0 است. مقداری که Rust توصیه می‌کند اینجا قرار دهیم mem::align_of::<T>() است. NonNull برای این کار یک تابع کمکی فراهم می‌کند: NonNull::dangling(). جاهای زیادی هست که می‌خواهیم از dangling استفاده کنیم، چون تخصیص واقعی‌ای وجود ندارد که از آن حرف بزنیم، اما null باعث می‌شود کامپایلر کارهای بدی انجام دهد.

    پس:

    use std::mem;

impl<T> Vec<T> {
    pub fn new() -> Self {
        assert!(mem::size_of::<T>() != 0, "We're not ready to handle ZSTs");
        Vec {
            ptr: NonNull::dangling(),
            len: 0,
            cap: 0,
        }
    }
}
fn main() {}

    آن assert را آنجا گنجاندم چون نوع‌های با اندازهٔ صفر در سراسر کدمان به مدیریت ویژه نیاز خواهند داشت، و فعلاً می‌خواهم این موضوع را به تعویق بیندازم. بدون این assert، بعضی از پیش‌نویس‌های اولیهٔ ما کارهای خیلی بدی خواهند کرد.

    در مرحلهٔ بعد باید بفهمیم وقتی واقعاً فضا می‌خواهیم چه کار کنیم. برای این منظور از توابع تخصیص سراسری alloc، realloc و dealloc استفاده می‌کنیم که در Rust پایدار در std::alloc در دسترس‌اند. انتظار می‌رود پس از پایدار شدن نوع std::alloc::Global، این توابع به نفع متدهای آن منسوخ شوند.

    همچنین به راهی برای رسیدگی به شرایط کمبود حافظه (OOM) نیاز داریم. کتابخانهٔ استاندارد تابعی به نام alloc::handle_alloc_error فراهم می‌کند که برنامه را به شیوه‌ای وابسته به پلتفرم متوقف (abort) می‌کند. دلیل اینکه abort می‌کنیم و panic نمی‌کنیم این است که unwinding می‌تواند باعث انجام تخصیص‌هایی شود، و وقتی تخصیص‌دهندهٔ شما همین الان گفته «هی، دیگر حافظه ندارم»، این کار بد به نظر می‌رسد.

    البته این کمی احمقانه است، چون بیشتر پلتفرم‌ها در واقع به شیوهٔ مرسوم حافظه کم نمی‌آورند. اگر واقعاً شروع کنید به مصرف تمام حافظه، سیستم‌عامل شما احتمالاً برنامه را با روشی دیگر می‌کشد. محتمل‌ترین راه برای فعال کردن OOM این است که یک‌باره مقدار مضحکی حافظه درخواست کنیم (مثلاً نصف فضای آدرس نظری). به همین دلیل احتمالاً panic کردن اشکالی ندارد و اتفاق بدی نمی‌افتد. با این حال، ما سعی داریم تا حد امکان شبیه کتابخانهٔ استاندارد باشیم، پس کل برنامه را متوقف می‌کنیم.

    خب، حالا می‌توانیم رشد را بنویسیم. به‌طور کلی، می‌خواهیم این منطق را داشته باشیم:

    if cap == 0:
    allocate()
    cap = 1
else:
    reallocate()
    cap *= 2

    اما تنها API تخصیص‌دهندهٔ پشتیبانی‌شدهٔ Rust آن‌قدر سطح پایین است که باید مقدار قابل‌توجهی کار اضافه انجام دهیم. همچنین باید در برابر برخی شرایط خاص که با تخصیص‌های واقعاً بزرگ یا تخصیص‌های خالی رخ می‌دهند محافظت کنیم.

    به‌طور خاص، ptr::offset دردسر زیادی برایمان ایجاد می‌کند، چون معنایی مانند دستور GEP inbounds در LLVM دارد. اگر به اندازهٔ کافی خوش‌شانس بوده‌اید که با این دستور سروکار نداشته‌اید، داستان اصلی GEP این است: تحلیل نام‌های مستعار (alias analysis)، تحلیل نام‌های مستعار، تحلیل نام‌های مستعار. برای یک کامپایلر بهینه‌ساز بسیار مهم است که بتواند دربارهٔ وابستگی‌های داده و نام‌های مستعار استدلال کند.

    به‌عنوان یک مثال ساده، قطعه کد زیر را در نظر بگیرید:

    *x *= 7;
*y *= 3;

    اگر کامپایلر بتواند ثابت کند x و y به مکان‌های متفاوتی در حافظه اشاره می‌کنند، در تئوری این دو عملیات را می‌توان به‌صورت موازی اجرا کرد (مثلاً با بارگذاری آن‌ها در ثبات‌های مختلف و کار روی آن‌ها به‌طور مستقل). اما کامپایلر در حالت کلی نمی‌تواند این کار را بکند، چون اگر x و y به یک مکان در حافظه اشاره کنند، عملیات باید روی یک مقدار انجام شوند و بعداً نمی‌توان آن‌ها را صرفاً با هم ادغام کرد.

    وقتی از GEP inbounds استفاده می‌کنید، صراحتاً به LLVM می‌گویید که offset‌هایی که می‌خواهید انجام دهید درون محدودهٔ یک موجودیت «تخصیص‌یافتهٔ» واحد هستند. نتیجهٔ نهایی این است که LLVM می‌تواند فرض کند اگر معلوم باشد دو اشاره‌گر به دو شیء مجزا اشاره می‌کنند، همهٔ offset‌های آن اشاره‌گرها نیز نام مستعار یکدیگر نیستند (چون شما به‌سادگی به یک مکان تصادفی در حافظه نمی‌رسید). LLVM به‌شدت برای کار با offset‌های GEP بهینه شده است و offset‌های inbounds از همه بهترند، پس مهم است که تا حد ممکن از آن‌ها استفاده کنیم.

    پس GEP این است؛ چطور می‌تواند برایمان دردسر ایجاد کند؟

    مشکل اول این است که ما آرایه‌ها را با اعداد صحیح بدون علامت اندیس‌گذاری می‌کنیم، اما GEP (و در نتیجه ptr::offset) یک عدد صحیح علامت‌دار می‌گیرد. این یعنی نیمی از اندیس‌های به‌ظاهر معتبر یک آرایه باعث سرریز GEP می‌شوند و در واقع به جهت اشتباه می‌روند! بنابراین باید همهٔ تخصیص‌ها را به isize::MAX عنصر محدود کنیم. این در واقع یعنی فقط باید نگران اشیای یک‌بایتی باشیم، چون مثلاً > isize::MAX عدد u16 واقعاً تمام حافظهٔ سیستم را تمام می‌کند. با این حال، برای جلوگیری از موارد مرزی ظریفی که در آن‌ها کسی آرایه‌ای از اشیای < isize::MAX را به‌صورت بایت بازتفسیر می‌کند، std همهٔ تخصیص‌ها را به isize::MAX بایت محدود می‌کند.

    در همهٔ هدف‌های ۶۴ بیتی‌ای که Rust فعلاً پشتیبانی می‌کند، ما به‌طور مصنوعی به مقداری بسیار کمتر از کل ۶۴ بیت فضای آدرس محدود هستیم (پلتفرم‌های x64 مدرن فقط آدرس‌دهی ۴۸ بیتی را در دسترس قرار می‌دهند)، پس می‌توانیم روی این حساب کنیم که ابتدا حافظه تمام می‌شود. اما در هدف‌های ۳۲ بیتی، به‌ویژه آن‌هایی که افزونه‌هایی برای استفادهٔ بیشتر از فضای آدرس دارند (PAE x86 یا x32)، از نظر تئوری ممکن است بتوان با موفقیت بیش از isize::MAX بایت حافظه تخصیص داد.

    با این حال، چون این یک آموزش است، قرار نیست اینجا خیلی بهینه عمل کنیم، و به‌جای استفاده از cfg‌های هوشمندانهٔ وابسته به پلتفرم، به‌طور بی‌قیدوشرط بررسی می‌کنیم.

    مورد مرزی دیگری که باید نگرانش باشیم تخصیص‌های خالی است. دو نوع تخصیص خالی وجود دارد که باید نگرانشان باشیم: cap = 0 برای همهٔ T، و cap > 0 برای نوع‌های با اندازهٔ صفر.

    این موارد پیچیده‌اند چون به این برمی‌گردند که LLVM از «تخصیص‌یافته» چه منظوری دارد. مفهوم LLVM از تخصیص به‌طور قابل‌توجهی انتزاعی‌تر از شیوهٔ معمول استفادهٔ ماست. چون LLVM باید با معناشناسی زبان‌های مختلف و تخصیص‌دهنده‌های سفارشی کار کند، نمی‌تواند واقعاً تخصیص را عمیقاً درک کند. در عوض، ایدهٔ اصلی پشت تخصیص این است که «با چیزهای دیگر همپوشانی ندارد». یعنی تخصیص‌های هیپ، تخصیص‌های پشته و global‌ها به‌طور تصادفی همپوشانی ندارند. بله، موضوع تحلیل نام‌های مستعار است. به همین دلیل، Rust از نظر فنی می‌تواند با مفهوم تخصیص کمی آزادانه رفتار کند، به شرط اینکه سازگار باشد.

    برگردیم به حالت تخصیص خالی؛ چند جا هست که در نتیجهٔ کد جنریک می‌خواهیم به اندازهٔ ۰ offset بدهیم. پرسش این است: آیا انجام این کار سازگار است؟ برای نوع‌های با اندازهٔ صفر، به این نتیجه رسیده‌ایم که انجام یک offset از نوع GEP inbounds به تعداد دلخواه عنصر واقعاً سازگار است. این در زمان اجرا هیچ کاری نمی‌کند چون هر عنصر هیچ فضایی اشغال نمی‌کند، و اشکالی ندارد وانمود کنیم بی‌نهایت نوع با اندازهٔ صفر در 0x01 تخصیص یافته‌اند. هیچ تخصیص‌دهنده‌ای هرگز آن آدرس را تخصیص نخواهد داد، چون 0x00 را تخصیص نمی‌دهند و معمولاً با ترازی حداقلی بالاتر از یک بایت تخصیص می‌دهند. همچنین معمولاً کل صفحهٔ اول حافظه به‌هرحال از تخصیص یافتن محافظت می‌شود (در بسیاری از پلتفرم‌ها یک ۴ کیلوبایت کامل).

    اما در مورد نوع‌هایی با اندازهٔ مثبت چه؟ آن یکی کمی پیچیده‌تر است. در اصل، می‌توان استدلال کرد که offset دادن به اندازهٔ ۰ هیچ اطلاعاتی به LLVM نمی‌دهد: یا عنصری پیش از آن آدرس هست یا بعد از آن، اما LLVM نمی‌تواند بداند کدام. با این حال ما محافظه‌کارانه فرض کرده‌ایم که ممکن است کارهای بدی بکند. به همین دلیل صراحتاً در برابر این حالت محافظت می‌کنیم.

    اوف

    خب، حالا که از شر این مزخرفات خلاص شدیم، بیایید واقعاً مقداری حافظه تخصیص دهیم:

    use std::alloc::{self, Layout};

impl<T> Vec<T> {
    fn grow(&mut self) {
        let (new_cap, new_layout) = if self.cap == 0 {
            (1, Layout::array::<T>(1))
        } else {
            // This can't overflow since self.cap <= isize::MAX.
            let new_cap = 2 * self.cap;
            (new_cap, Layout::array::<T>(new_cap))
        };

        // `Layout::array` checks that the number of bytes allocated is
        // in 1..=isize::MAX and will error otherwise.  An allocation of
        // 0 bytes isn't possible thanks to the above condition.
        let new_layout = new_layout.expect("Allocation too large");

        let new_ptr = if self.cap == 0 {
            unsafe { alloc::alloc(new_layout) }
        } else {
            let old_layout = Layout::array::<T>(self.cap).unwrap();
            let old_ptr = self.ptr.as_ptr() as *mut u8;
            unsafe { alloc::realloc(old_ptr, old_layout, new_layout.size()) }
        };

        // If allocation fails, `new_ptr` will be null, in which case we abort.
        self.ptr = match NonNull::new(new_ptr as *mut T) {
            Some(p) => p,
            None => alloc::handle_alloc_error(new_layout),
        };
        self.cap = new_cap;
    }
}
fn main() {}
