    مدیریت نوع‌های با اندازهٔ صفر

    وقتش رسیده است. می‌خواهیم با شبح نوع‌های با اندازهٔ صفر (zero-sized type) بجنگیم. Safe Rust هرگز لازم نیست به این موضوع اهمیت بدهد، اما Vec به‌شدت به اشاره‌گرهای خام و تخصیص‌های خام وابسته است، که دقیقاً همان دو چیزی هستند که به نوع‌های با اندازهٔ صفر اهمیت می‌دهند. باید مراقب دو چیز باشیم:

    • API تخصیص‌دهندهٔ خام اگر ۰ را به‌عنوان اندازهٔ تخصیص به آن بدهید رفتار تعریف‌نشده دارد.
    • offset دادن به اشاره‌گر خام برای نوع‌های با اندازهٔ صفر هیچ کاری نمی‌کند، که iterator اشاره‌گریِ C‌مانند ما را خراب می‌کند.

    خوشبختانه ما iterator‌های اشاره‌گری و مدیریت تخصیص را به‌ترتیب در RawValIter و RawVec جدا کرده‌ایم. چه راحتیِ مرموزی.

    تخصیص نوع‌های با اندازهٔ صفر

    پس اگر API تخصیص‌دهنده از تخصیص‌های با اندازهٔ صفر پشتیبانی نمی‌کند، آخر چه چیزی را به‌عنوان تخصیص خود ذخیره کنیم؟ البته NonNull::dangling()! تقریباً هر عملیاتی روی یک ZST هیچ کاری نمی‌کند، چون ZST‌ها دقیقاً یک مقدار دارند و بنابراین برای ذخیره یا بارگذاری آن‌ها لازم نیست هیچ حالتی در نظر گرفته شود. این در واقع به ptr::read و ptr::write هم تعمیم می‌یابد: آن‌ها اصلاً به اشاره‌گر نگاه نمی‌کنند. به همین دلیل هرگز لازم نیست اشاره‌گر را تغییر دهیم.

    با این حال توجه کنید که تکیهٔ قبلی ما بر این که پیش از سرریز، حافظه تمام می‌شود، با نوع‌های با اندازهٔ صفر دیگر معتبر نیست. باید صراحتاً در برابر سرریز ظرفیت برای نوع‌های با اندازهٔ صفر محافظت کنیم.

    به دلیل معماری فعلی ما، همهٔ این‌ها فقط به معنای نوشتن ۳ محافظ است، یکی در هر متد از RawVec.

    impl<T> RawVec<T> {
    fn new() -> Self {
        // This branch should be stripped at compile time.
        let cap = if mem::size_of::<T>() == 0 { usize::MAX } else { 0 };

        // `NonNull::dangling()` doubles as "unallocated" and "zero-sized allocation"
        RawVec {
            ptr: NonNull::dangling(),
            cap,
        }
    }

    fn grow(&mut self) {
        // since we set the capacity to usize::MAX when T has size 0,
        // getting to here necessarily means the Vec is overfull.
        assert!(mem::size_of::<T>() != 0, "capacity overflow");

        let (new_cap, new_layout) = if self.cap == 0 {
            (1, Layout::array::<T>(1).unwrap())
        } else {
            // This can't overflow because we ensure self.cap <= isize::MAX.
            let new_cap = 2 * self.cap;

            // `Layout::array` checks that the number of bytes is <= usize::MAX,
            // but this is redundant since old_layout.size() <= isize::MAX,
            // so the `unwrap` should never fail.
            let new_layout = Layout::array::<T>(new_cap).unwrap();
            (new_cap, new_layout)
        };

        // Ensure that the new allocation doesn't exceed `isize::MAX` bytes.
        assert!(new_layout.size() <= isize::MAX as usize, "Allocation too large");

        let new_ptr = if self.cap == 0 {
            unsafe { alloc::alloc(new_layout) }
        } else {
            let old_layout = Layout::array::<T>(self.cap).unwrap();
            let old_ptr = self.ptr.as_ptr() as *mut u8;
            unsafe { alloc::realloc(old_ptr, old_layout, new_layout.size()) }
        };

        // If allocation fails, `new_ptr` will be null, in which case we abort.
        self.ptr = match NonNull::new(new_ptr as *mut T) {
            Some(p) => p,
            None => alloc::handle_alloc_error(new_layout),
        };
        self.cap = new_cap;
    }
}

impl<T> Drop for RawVec<T> {
    fn drop(&mut self) {
        let elem_size = mem::size_of::<T>();

        if self.cap != 0 && elem_size != 0 {
            unsafe {
                alloc::dealloc(
                    self.ptr.as_ptr() as *mut u8,
                    Layout::array::<T>(self.cap).unwrap(),
                );
            }
        }
    }
}

    همین. حالا از push و pop کردن نوع‌های با اندازهٔ صفر پشتیبانی می‌کنیم. با این حال iterator‌های ما (آن‌هایی که از Deref به slice تأمین نمی‌شوند) هنوز خراب‌اند.

    پیمایش نوع‌های با اندازهٔ صفر

    offset‌های با اندازهٔ صفر هیچ کاری نمی‌کنند. این یعنی طراحی فعلی ما همیشه start و end را با یک مقدار یکسان مقداردهی اولیه می‌کند و iterator‌های ما هیچ چیزی تولید نمی‌کنند. راه‌حل فعلی برای این مشکل این است که اشاره‌گرها را به عدد صحیح تبدیل کنیم، افزایش دهیم و سپس دوباره به اشاره‌گر برگردانیم:

    impl<T> RawValIter<T> {
    unsafe fn new(slice: &[T]) -> Self {
        RawValIter {
            start: slice.as_ptr(),
            end: if mem::size_of::<T>() == 0 {
                ((slice.as_ptr() as usize) + slice.len()) as *const _
            } else if slice.len() == 0 {
                slice.as_ptr()
            } else {
                slice.as_ptr().add(slice.len())
            },
        }
    }
}

    حالا باگ متفاوتی داریم. به‌جای اینکه iterator‌های ما اصلاً اجرا نشوند، حالا برای همیشه اجرا می‌شوند. باید همین ترفند را در پیاده‌سازی‌های iteratorمان هم به کار ببریم. همچنین، کد محاسبهٔ size_hint ما برای ZST‌ها بر ۰ تقسیم می‌کند. چون اساساً با دو اشاره‌گر طوری رفتار می‌کنیم که انگار به بایت اشاره می‌کنند، اندازهٔ ۰ را فقط به تقسیم بر ۱ نگاشت می‌کنیم. next این‌گونه خواهد بود:

    fn next(&mut self) -> Option<T> {
    if self.start == self.end {
        None
    } else {
        unsafe {
            let result = ptr::read(self.start);
            self.start = if mem::size_of::<T>() == 0 {
                (self.start as usize + 1) as *const _
            } else {
                self.start.offset(1)
            };
            Some(result)
        }
    }
}

    «باگ» را می‌بینید؟ هیچ‌کس دیگر هم ندید! نویسندهٔ اصلی سال‌ها بعد، هنگام لینک دادن به این صفحه، تازه متوجه مشکل شد. این کد کمی مشکوک است، چون سوءاستفاده از اشاره‌گرهای iterator به‌عنوان شمارنده باعث می‌شود تراز نباشند! تنها وظیفهٔ ما هنگام کار با ZST‌ها این است که اشاره‌گرها را تراز نگه داریم! کف دست روی پیشانی

    اشاره‌گرهای خام لازم نیست همیشه تراز باشند، پس ترفند پایه‌ای استفاده از اشاره‌گرها به‌عنوان شمارنده اشکالی ندارد، اما وقتی به ptr::read داده می‌شوند قطعاً باید تراز باشند! این شاید وسواس بی‌مورد باشد چون ptr::read برای یک ZST هیچ کاری نمی‌کند، اما بیایید کمی مسئولانه‌تر باشیم و در مسیر ZST از NonNull::dangling بخوانیم.

    (به‌عنوان جایگزین، می‌توانید در مسیر ZST تابع read_unaligned را صدا بزنید. هر دو اشکالی ندارد، چون در هر دو حالت داریم مقداری را از هیچ می‌سازیم و همه‌چیز به انجام ندادن هیچ کاری کامپایل می‌شود.)

    impl<T> Iterator for RawValIter<T> {
    type Item = T;
    fn next(&mut self) -> Option<T> {
        if self.start == self.end {
            None
        } else {
            unsafe {
                if mem::size_of::<T>() == 0 {
                    self.start = (self.start as usize + 1) as *const _;
                    Some(ptr::read(NonNull::<T>::dangling().as_ptr()))
                } else {
                    let old_ptr = self.start;
                    self.start = self.start.offset(1);
                    Some(ptr::read(old_ptr))
                }
            }
        }
    }

    fn size_hint(&self) -> (usize, Option<usize>) {
        let elem_size = mem::size_of::<T>();
        let len = (self.end as usize - self.start as usize)
                  / if elem_size == 0 { 1 } else { elem_size };
        (len, Some(len))
    }
}

impl<T> DoubleEndedIterator for RawValIter<T> {
    fn next_back(&mut self) -> Option<T> {
        if self.start == self.end {
            None
        } else {
            unsafe {
                if mem::size_of::<T>() == 0 {
                    self.end = (self.end as usize - 1) as *const _;
                    Some(ptr::read(NonNull::<T>::dangling().as_ptr()))
                } else {
                    self.end = self.end.offset(-1);
                    Some(ptr::read(self.end))
                }
            }
        }
    }
}

    و تمام! پیمایش کار می‌کند!

    آخرین چیزی که باید در نظر بگیریم این است که وقتی بردار ما drop می‌شود، حافظه‌ای را که در زمان حیاتش تخصیص داده شده بود آزاد می‌کند. با ZSTها، ما هیچ حافظه‌ای تخصیص نداده‌ایم؛ در واقع هرگز نمی‌دهیم. بنابراین، در حال حاضر کد ما ناسالمی (unsoundness) دارد: هنوز سعی می‌کنیم اشاره‌گر NonNull::dangling() را که برای شبیه‌سازی ZST در بردارمان استفاده می‌کنیم آزاد کنیم. این یعنی اگر سعی کنیم چیزی را که هرگز تخصیص نداده‌ایم آزاد کنیم، رفتار تعریف‌نشده ایجاد می‌کنیم (بدیهی است، و به دلایل موجه). برای رفع این مشکل، در صفت Drop مربوط به RawVec آن را تغییر می‌دهیم تا مطمئن شویم فقط نوع‌هایی را آزاد می‌کنیم که اندازه دارند.

    impl<T> Drop for RawVec<T> {
    fn drop(&mut self) {
        println!("RawVec<T> Drop called, deallocating memory");
        if self.cap != 0 && std::mem::size_of::<T>() > 0 {
            let layout = std::alloc::Layout::array::<T>(self.cap).unwrap();
            unsafe {
                std::alloc::dealloc(self.ptr.as_ptr() as *mut _, layout);
            }
        }
    }
}
