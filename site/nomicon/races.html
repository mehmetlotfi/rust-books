    رقابت‌های داده و شرایط رقابتی

    Safe Rust نبود رقابت داده (data race) را تضمین می‌کند، که به این صورت تعریف می‌شود:

    • دو یا چند نخ هم‌زمان به یک مکان از حافظه دسترسی دارند
    • یک یا چند تا از آن‌ها در حال نوشتن‌اند
    • یک یا چند تا از آن‌ها همگام‌سازی نشده‌اند

    رقابت داده رفتار تعریف‌نشده دارد و بنابراین انجام آن در Safe Rust غیرممکن است. رقابت‌های داده عمدتاً فقط از طریق سیستم مالکیت Rust جلوگیری می‌شوند: نمی‌توان یک ارجاع تغییرپذیر را alias کرد، پس نمی‌توان رقابت داده ایجاد کرد. تغییرپذیری درونی (interior mutability) این را پیچیده‌تر می‌کند، و این تا حد زیادی دلیل وجود صفت‌های Send و Sync است (برای توضیح بیشتر بخش بعد را ببینید).

    با این حال Rust از شرایط رقابتی (race condition) عمومی جلوگیری نمی‌کند.

    این در شرایطی که زمان‌بند (scheduler) را کنترل نمی‌کنید از نظر ریاضی غیرممکن است، و این در محیط عادی سیستم‌عامل صادق است. اگر پیشگیری (preemption) را کنترل کنید، جلوگیری از رقابت‌های عمومی ممکن است شدنی باشد - این تکنیک در فریم‌ورک‌هایی مانند RTIC به کار می‌رود. با این حال، در عمل کنترل بر زمان‌بندی حالتی بسیار نادر است.

    به همین دلیل، «امن» به حساب می‌آید که Rust دچار بن‌بست (deadlock) شود یا به‌خاطر همگام‌سازی نادرست کاری بی‌معنی انجام دهد: این را شرط رقابتی عمومی یا رقابت منابع می‌نامند. بدیهی است که چنین برنامه‌ای چندان خوب نیست، اما Rust البته نمی‌تواند از همهٔ خطاهای منطقی جلوگیری کند.

    در هر صورت، یک شرط رقابتی به‌تنهایی نمی‌تواند امنیت حافظه را در یک برنامهٔ Rust نقض کند. فقط در ترکیب با کد unsafe دیگری است که یک شرط رقابتی می‌تواند واقعاً امنیت حافظه را نقض کند. برای مثال، یک برنامهٔ درست این شکلی است:

    use std::thread;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

let data = vec![1, 2, 3, 4];
// Arc so that the memory the AtomicUsize is stored in still exists for
// the other thread to increment, even if we completely finish executing
// before it. Rust won't compile the program without it, because of the
// lifetime requirements of thread::spawn!
let idx = Arc::new(AtomicUsize::new(0));
let other_idx = idx.clone();

// `move` captures other_idx by-value, moving it into this thread
thread::spawn(move || {
    // It's ok to mutate idx because this value
    // is an atomic, so it can't cause a Data Race.
    other_idx.fetch_add(10, Ordering::SeqCst);
});

// Index with the value loaded from the atomic. This is safe because we
// read the atomic memory only once, and then pass a copy of that value
// to the Vec's indexing implementation. This indexing will be correctly
// bounds checked, and there's no chance of the value getting changed
// in the middle. However our program may panic if the thread we spawned
// managed to increment before this ran. A race condition because correct
// program execution (panicking is rarely correct) depends on order of
// thread execution.
println!("{}", data[idx.load(Ordering::SeqCst)]);

    اگر در عوض بررسی کران را از پیش انجام دهیم و سپس به‌صورت unsafe با یک مقدار بررسی‌نشده به داده دسترسی پیدا کنیم، می‌توانیم باعث شویم یک شرط رقابتی امنیت حافظه را نقض کند:

    use std::thread;
use std::sync::atomic::{AtomicUsize, Ordering};
use std::sync::Arc;

let data = vec![1, 2, 3, 4];

let idx = Arc::new(AtomicUsize::new(0));
let other_idx = idx.clone();

// `move` captures other_idx by-value, moving it into this thread
thread::spawn(move || {
    // It's ok to mutate idx because this value
    // is an atomic, so it can't cause a Data Race.
    other_idx.fetch_add(10, Ordering::SeqCst);
});

if idx.load(Ordering::SeqCst) < data.len() {
    unsafe {
        // Incorrectly loading the idx after we did the bounds check.
        // It could have changed. This is a race condition, *and dangerous*
        // because we decided to do `get_unchecked`, which is `unsafe`.
        println!("{}", data.get_unchecked(idx.load(Ordering::SeqCst)));
    }
}
