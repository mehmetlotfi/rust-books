    ایمنی در برابر استثنا

    اگرچه برنامه‌ها باید از unwinding به‌ندرت استفاده کنند، کد زیادی وجود دارد که می‌تواند panic کند. اگر روی None از unwrap استفاده کنید، از محدوده‌ی اندیس خارج شوید یا بر ۰ تقسیم کنید، برنامه‌ی شما panic می‌کند. در ساخت‌های debug، هر عمل حسابی در صورت سرریز می‌تواند panic کند. مگر اینکه بسیار دقیق باشید و اجرای کد را به‌شدت کنترل کنید، تقریباً هر چیزی می‌تواند unwind شود و باید برای آن آماده باشید.

    آمادگی برای unwinding در دنیای وسیع‌تر برنامه‌نویسی اغلب ایمنی در برابر استثنا (exception safety) نامیده می‌شود. در Rust دو سطح از ایمنی در برابر استثنا وجود دارد که ممکن است به آن‌ها اهمیت دهیم:

    • در کد unsafe، باید تا حدی در برابر استثنا ایمن باشیم که ایمنی حافظه نقض نشود. این را ایمنی حداقلی در برابر استثنا می‌نامیم.

    • در کد safe، خوب است که تا حدی در برابر استثنا ایمن باشیم که برنامه‌ی شما کار درست را انجام دهد. این را ایمنی حداکثری در برابر استثنا می‌نامیم.

    همان‌طور که در بسیاری از جاهای Rust صدق می‌کند، کد Unsafe باید آماده‌ی مقابله با کد Safe بد در مورد unwinding باشد. کدی که به‌طور گذرا حالت‌های ناصحیح ایجاد می‌کند باید دقت کند که یک panic باعث استفاده از آن حالت نشود. عموماً این یعنی اطمینان از اینکه تا زمانی که این حالت‌ها وجود دارند فقط کدی اجرا شود که panic نمی‌کند، یا ساختن یک guard که در صورت panic حالت را پاک‌سازی کند. این لزوماً به این معنا نیست که حالتی که panic شاهد آن است یک حالت کاملاً منسجم باشد. فقط باید تضمین کنیم که یک حالت امن است.

    بیشتر کدهای Unsafe برگ‌مانند هستند و بنابراین ایمن‌کردن آن‌ها در برابر استثنا نسبتاً آسان است. آن‌ها همه‌ی کدی را که اجرا می‌شود کنترل می‌کنند و بیشتر آن کد نمی‌تواند panic کند. با این حال غیرمعمول نیست که کد Unsafe با آرایه‌هایی از داده‌ی موقتاً مقداردهی‌نشده کار کند و در همان حال بارها کدی را که فراخواننده فراهم کرده فراخوانی کند. چنین کدی باید دقت کند و ایمنی در برابر استثنا را در نظر بگیرد.

    Vec::push_all

    Vec::push_all یک ترفند موقتی است تا بدون specialization، گسترش یک Vec با یک slice به‌طور قابل‌اعتمادی کارآمد شود. این هم یک پیاده‌سازی ساده:

    impl<T: Clone> Vec<T> {
    fn push_all(&mut self, to_push: &[T]) {
        self.reserve(to_push.len());
        unsafe {
            let end_ptr = self.as_mut_ptr().add(self.len());

            // can't overflow because we just reserved this
            self.set_len(self.len() + to_push.len());

            for (i, x) in to_push.iter().enumerate() {
                end_ptr.add(i).write(x.clone());
            }
        }
    }
}

    ما push را دور می‌زنیم تا از بررسی‌های اضافی ظرفیت و len روی Vec که قطعاً می‌دانیم ظرفیت دارد جلوگیری کنیم. منطق کاملاً درست است، جز اینکه مشکل ظریفی در کد ما هست: در برابر استثنا ایمن نیست! set_len، add و write همه مشکلی ندارند؛ clone بمب panic‌ای است که از آن غافل شدیم.

    Clone کاملاً خارج از کنترل ماست و کاملاً آزاد است که panic کند. اگر چنین کند، تابع ما زودتر و در حالی که طول Vec بیش از حد بزرگ تنظیم شده خارج می‌شود. اگر به Vec نگاه شود یا drop شود، حافظه‌ی مقداردهی‌نشده خوانده خواهد شد!

    راه‌حل در این مورد نسبتاً ساده است. اگر بخواهیم تضمین کنیم مقادیری که کلون کرده‌ایم drop می‌شوند، می‌توانیم len را در هر تکرار حلقه تنظیم کنیم. اگر فقط بخواهیم تضمین کنیم حافظه‌ی مقداردهی‌نشده قابل مشاهده نیست، می‌توانیم len را پس از حلقه تنظیم کنیم.

    BinaryHeap::sift_up

    بالا آوردن یک عنصر در heap کمی پیچیده‌تر از گسترش یک Vec است. شبه‌کد آن به این صورت است:

    bubble_up(heap, index):
    while index != 0 && heap[index] < heap[parent(index)]:
        heap.swap(index, parent(index))
        index = parent(index)

    رونویسی تحت‌اللفظی این کد به Rust کاملاً مشکلی ندارد، اما یک ویژگی عملکردی آزاردهنده دارد: عنصر self بارها و بارها بی‌فایده جابه‌جا می‌شود. ترجیح می‌دهیم چنین چیزی داشته باشیم:

    bubble_up(heap, index):
    let elem = heap[index]
    while index != 0 && elem < heap[parent(index)]:
        heap[index] = heap[parent(index)]
        index = parent(index)
    heap[index] = elem

    این کد تضمین می‌کند هر عنصر کمترین تعداد ممکن کپی شود (در واقع به‌طور کلی لازم است که elem دو بار کپی شود). با این حال اکنون مشکلی در ایمنی در برابر استثنا آشکار می‌کند! در تمام لحظات، دو نسخه از یک مقدار وجود دارد. اگر در این تابع panic کنیم، چیزی دو بار drop می‌شود. متأسفانه کنترل کامل کد هم در دست ما نیست: آن مقایسه توسط کاربر تعریف شده است!

    برخلاف Vec، راه‌حل در اینجا آن‌قدر آسان نیست. یک گزینه این است که کد تعریف‌شده توسط کاربر و کد unsafe را به دو فاز جدا بشکنیم:

    bubble_up(heap, index):
    let end_index = index;
    while end_index != 0 && heap[index] < heap[parent(end_index)]:
        end_index = parent(end_index)

    let elem = heap[index]
    while index != end_index:
        heap[index] = heap[parent(index)]
        index = parent(index)
    heap[index] = elem

    اگر کد تعریف‌شده توسط کاربر منفجر شود، دیگر مشکلی نیست، چون هنوز به حالت heap دست نزده‌ایم. وقتی شروع به دستکاری heap می‌کنیم، فقط با داده‌ها و توابعی کار می‌کنیم که به آن‌ها اعتماد داریم، پس نگرانی‌ای از panic نیست.

    شاید از این طراحی راضی نباشید. مطمئناً این تقلب است! و باید پیمایش پیچیده‌ی heap را دو بار انجام دهیم! بسیار خب، بیایید دل به دریا بزنیم. بیایید کد نامطمئن و unsafe را واقعاً درهم بیامیزیم.

    اگر Rust مانند Java دارای try و finally بود، می‌توانستیم این کار را بکنیم:

    bubble_up(heap, index):
    let elem = heap[index]
    try:
        while index != 0 && elem < heap[parent(index)]:
            heap[index] = heap[parent(index)]
            index = parent(index)
    finally:
        heap[index] = elem

    ایده‌ی اصلی ساده است: اگر مقایسه panic کند، فقط عنصر رهاشده را در اندیسی که از نظر منطقی مقداردهی‌نشده است می‌گذاریم و بیرون می‌پریم. هر کس heap را مشاهده کند ممکن است یک heap ناسازگار ببیند، اما دست‌کم باعث هیچ drop دوباره‌ای نمی‌شود! اگر الگوریتم به‌طور عادی پایان یابد، این عملیات دقیقاً با شیوه‌ی پایان‌دادن ما در هر حال منطبق است.

    متأسفانه Rust چنین ساختاری ندارد، پس باید خودمان آن را بسازیم! راهش این است که حالت الگوریتم را در یک ساختار جداگانه با یک destructor برای منطق «finally» نگه داریم. چه panic کنیم چه نه، آن destructor اجرا می‌شود و پس از ما پاک‌سازی می‌کند.

    struct Hole<'a, T: 'a> {
    data: &'a mut [T],
    /// `elt` is always `Some` from new until drop.
    elt: Option<T>,
    pos: usize,
}

impl<'a, T> Hole<'a, T> {
    fn new(data: &'a mut [T], pos: usize) -> Self {
        unsafe {
            let elt = ptr::read(&data[pos]);
            Hole {
                data,
                elt: Some(elt),
                pos,
            }
        }
    }

    fn pos(&self) -> usize { self.pos }

    fn removed(&self) -> &T { self.elt.as_ref().unwrap() }

    fn get(&self, index: usize) -> &T { &self.data[index] }

    unsafe fn move_to(&mut self, index: usize) {
        let index_ptr: *const _ = &self.data[index];
        let hole_ptr = &mut self.data[self.pos];
        ptr::copy_nonoverlapping(index_ptr, hole_ptr, 1);
        self.pos = index;
    }
}

impl<'a, T> Drop for Hole<'a, T> {
    fn drop(&mut self) {
        // fill the hole again
        unsafe {
            let pos = self.pos;
            ptr::write(&mut self.data[pos], self.elt.take().unwrap());
        }
    }
}

impl<T: Ord> BinaryHeap<T> {
    fn sift_up(&mut self, pos: usize) {
        unsafe {
            // Take out the value at `pos` and create a hole.
            let mut hole = Hole::new(&mut self.data, pos);

            while hole.pos() != 0 {
                let parent = parent(hole.pos());
                if hole.removed() <= hole.get(parent) { break }
                hole.move_to(parent);
            }
            // Hole will be unconditionally filled here; panic or not!
        }
    }
}
