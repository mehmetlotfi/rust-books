    رابط توابع خارجی (Foreign Function Interface)

    رابط تابع خارجی (FFI)

    این راهنما از کتابخانهٔ فشرده‌سازی/باز‌کردن فشرده‌سازی snappy به‌عنوان مقدمه‌ای برای نوشتن بایندینگ برای کد خارجی استفاده می‌کند. Rust در حال حاضر نمی‌تواند مستقیماً یک کتابخانهٔ C++ را فراخوانی کند، اما snappy یک رابط C دارد (که در snappy-c.h مستند شده است).

    نکته‌ای دربارهٔ libc

    بسیاری از این مثال‌ها از crate با نام libc استفاده می‌کنند که از جمله تعریف انواع گوناگون C را فراهم می‌کند. اگر خودتان این مثال‌ها را امتحان می‌کنید، باید libc را به Cargo.toml خود اضافه کنید:

    [dependencies]
libc = "0.2.0"

    آماده‌سازی اسکریپت ساخت

    از آنجا که snappy به‌طور پیش‌فرض یک کتابخانهٔ ایستا است، stdc++ در فایل خروجی پیوند داده نمی‌شود. برای استفاده از این کتابخانهٔ خارجی در Rust باید به‌صورت دستی مشخص کنیم که می‌خواهیم stdc++ را به پروژهٔ خود پیوند دهیم. ساده‌ترین راه برای این کار تنظیم یک اسکریپت ساخت است.

    ابتدا Cargo.toml را ویرایش کنید و درون package عبارت build = "build.rs" را اضافه کنید:

    [package]
...
build = "build.rs"

    سپس در ریشهٔ workspace خود فایل جدیدی به نام build.rs بسازید:

    // build.rs
fn main() {
    println!("cargo:rustc-link-lib=dylib=stdc++"); // This line may be unnecessary for some environments.
    println!("cargo:rustc-link-search=<YOUR SNAPPY LIBRARY PATH>");
}

    برای اطلاعات بیشتر، کتاب Cargo - اسکریپت ساخت را بخوانید.

    فراخوانی توابع خارجی

    مثال زیر یک نمونهٔ حداقلی از فراخوانی یک تابع خارجی است که در صورت نصب بودن snappy کامپایل خواهد شد:

    use libc::size_t;

#[link(name = "snappy")]
unsafe extern "C" {
    fn snappy_max_compressed_length(source_length: size_t) -> size_t;
}

fn main() {
    let x = unsafe { snappy_max_compressed_length(100) };
    println!("max compressed length of a 100 byte buffer: {}", x);
}

    بلوک extern فهرستی از امضاهای توابع در یک کتابخانهٔ خارجی است که در اینجا با ABI زبان C در پلتفرم مورد نظر تعریف شده‌اند. attribute به نام #[link(...)] برای آن است که به پیوندهنده (linker) بگوییم با کتابخانهٔ snappy پیوند بزند تا نمادها (symbols) حل شوند.

    توابع خارجی به‌طور پیش‌فرض ناامن (unsafe) فرض می‌شوند، بنابراین فراخوانی آن‌ها باید درون unsafe {} قرار گیرد تا قولی به کامپایلر باشد که هر آنچه درون آن است واقعاً امن است. کتابخانه‌های C اغلب رابط‌هایی ارائه می‌دهند که نخ‌ایمن (thread-safe) نیستند و تقریباً هر تابعی که یک آرگومان اشاره‌گر بگیرد برای همهٔ ورودی‌های ممکن معتبر نیست، زیرا ممکن است اشاره‌گر معلق (dangling) باشد و اشاره‌گرهای خام (raw pointer) بیرون از مدل حافظهٔ امن Rust قرار می‌گیرند.

    هنگام اعلان نوع آرگومان‌های یک تابع خارجی، کامپایلر Rust نمی‌تواند بررسی کند که اعلان درست است یا نه، بنابراین درست مشخص کردن آن بخشی از صحیح نگه‌داشتن بایندینگ در زمان اجرا است.

    بلوک extern را می‌توان گسترش داد تا کل API کتابخانهٔ snappy را پوشش دهد:

    use libc::{c_int, size_t};

#[link(name = "snappy")]
unsafe extern "C" {
    fn snappy_compress(input: *const u8,
                       input_length: size_t,
                       compressed: *mut u8,
                       compressed_length: *mut size_t) -> c_int;
    fn snappy_uncompress(compressed: *const u8,
                         compressed_length: size_t,
                         uncompressed: *mut u8,
                         uncompressed_length: *mut size_t) -> c_int;
    fn snappy_max_compressed_length(source_length: size_t) -> size_t;
    fn snappy_uncompressed_length(compressed: *const u8,
                                  compressed_length: size_t,
                                  result: *mut size_t) -> c_int;
    fn snappy_validate_compressed_buffer(compressed: *const u8,
                                         compressed_length: size_t) -> c_int;
}
fn main() {}

    ساخت یک رابط امن

    API خام C باید پوشانده (wrap) شود تا امنیت حافظه فراهم شود و بتوان از مفاهیم سطح بالاتر مانند بردارها استفاده کرد. یک کتابخانه می‌تواند تنها رابط امن و سطح‌بالا را در دسترس بگذارد و جزئیات ناامن درونی را پنهان کند.

    پوشاندن توابعی که بافر می‌خواهند مستلزم استفاده از ماژول slice::raw است تا بردارهای Rust را به‌صورت اشاره‌گر به حافظه دستکاری کنیم. تضمین شده است که بردارهای Rust یک بلوک پیوستهٔ حافظه باشند. طول (length) تعداد عناصری است که در حال حاضر در بردار هست و ظرفیت (capacity) کل اندازهٔ حافظهٔ تخصیص‌یافته بر حسب تعداد عناصر است. طول همیشه کوچکتر یا مساوی ظرفیت است.

    use libc::{c_int, size_t};
unsafe fn snappy_validate_compressed_buffer(_: *const u8, _: size_t) -> c_int { 0 }
fn main() {}
pub fn validate_compressed_buffer(src: &[u8]) -> bool {
    unsafe {
        snappy_validate_compressed_buffer(src.as_ptr(), src.len() as size_t) == 0
    }
}

    پوشانندهٔ validate_compressed_buffer در بالا از یک بلوک unsafe استفاده می‌کند، اما با نگذاشتن unsafe در امضای تابع تضمین می‌کند که فراخوانی آن برای همهٔ ورودی‌ها امن است.

    توابع snappy_compress و snappy_uncompress پیچیده‌ترند، زیرا باید برای نگه‌داشتن خروجی هم یک بافر تخصیص داده شود.

    تابع snappy_max_compressed_length را می‌توان برای تخصیص برداری با حداکثر ظرفیتِ لازم برای نگه‌داشتن خروجی فشرده به کار برد. سپس می‌توان بردار را به‌عنوان پارامتر خروجی به تابع snappy_compress داد. یک پارامتر خروجی دیگر نیز برای دریافت طول واقعی پس از فشرده‌سازی و تنظیم طول بردار ارسال می‌شود.

    use libc::{size_t, c_int};
unsafe fn snappy_compress(a: *const u8, b: size_t, c: *mut u8,
                          d: *mut size_t) -> c_int { 0 }
unsafe fn snappy_max_compressed_length(a: size_t) -> size_t { a }
fn main() {}
pub fn compress(src: &[u8]) -> Vec<u8> {
    unsafe {
        let srclen = src.len() as size_t;
        let psrc = src.as_ptr();

        let mut dstlen = snappy_max_compressed_length(srclen);
        let mut dst = Vec::with_capacity(dstlen as usize);
        let pdst = dst.as_mut_ptr();

        snappy_compress(psrc, srclen, pdst, &mut dstlen);
        dst.set_len(dstlen as usize);
        dst
    }
}

    باز‌کردن فشرده‌سازی مشابه است، زیرا snappy اندازهٔ داده‌های فشرده‌نشده را بخشی از قالب فشرده‌سازی ذخیره می‌کند و snappy_uncompressed_length اندازهٔ دقیق بافر موردنیاز را برمی‌گرداند.

    use libc::{size_t, c_int};
unsafe fn snappy_uncompress(compressed: *const u8,
                            compressed_length: size_t,
                            uncompressed: *mut u8,
                            uncompressed_length: *mut size_t) -> c_int { 0 }
unsafe fn snappy_uncompressed_length(compressed: *const u8,
                                     compressed_length: size_t,
                                     result: *mut size_t) -> c_int { 0 }
fn main() {}
pub fn uncompress(src: &[u8]) -> Option<Vec<u8>> {
    unsafe {
        let srclen = src.len() as size_t;
        let psrc = src.as_ptr();

        let mut dstlen: size_t = 0;
        snappy_uncompressed_length(psrc, srclen, &mut dstlen);

        let mut dst = Vec::with_capacity(dstlen as usize);
        let pdst = dst.as_mut_ptr();

        if snappy_uncompress(psrc, srclen, pdst, &mut dstlen) == 0 {
            dst.set_len(dstlen as usize);
            Some(dst)
        } else {
            None // SNAPPY_INVALID_INPUT
        }
    }
}

    سپس می‌توانیم چند آزمون اضافه کنیم تا نحوهٔ استفاده از آن‌ها را نشان دهیم.

    use libc::{c_int, size_t};
unsafe fn snappy_compress(input: *const u8,
                          input_length: size_t,
                          compressed: *mut u8,
                          compressed_length: *mut size_t)
                          -> c_int { 0 }
unsafe fn snappy_uncompress(compressed: *const u8,
                            compressed_length: size_t,
                            uncompressed: *mut u8,
                            uncompressed_length: *mut size_t)
                            -> c_int { 0 }
unsafe fn snappy_max_compressed_length(source_length: size_t) -> size_t { 0 }
unsafe fn snappy_uncompressed_length(compressed: *const u8,
                                     compressed_length: size_t,
                                     result: *mut size_t)
                                     -> c_int { 0 }
unsafe fn snappy_validate_compressed_buffer(compressed: *const u8,
                                            compressed_length: size_t)
                                            -> c_int { 0 }
fn main() { }

#[cfg(test)]

    #[test]
    fn valid() {
        let d = vec![0xde, 0xad, 0xd0, 0x0d];
        let c: &[u8] = &compress(&d);
        assert!(validate_compressed_buffer(c));

    }

        assert!(!validate_compressed_buffer(&d));

        assert!(validate_compressed_buffer(&c));
        assert!(uncompress(&c) == Some(d));
    }
}

    نابودگرها

    کتابخانه‌های خارجی اغلب مالکیت منابع را به کدِ فراخواننده واگذار می‌کنند. هنگامی که این اتفاق می‌افتد، باید از نابودگرهای (destructor) Rust استفاده کنیم تا امنیت را فراهم و آزادسازی این منابع را تضمین کنیم (به‌ویژه در صورت بروز panic).

    برای اطلاعات بیشتر دربارهٔ نابودگرها، صفت Drop را ببینید.

    فراخوانی کد Rust از C

    شاید بخواهید کد Rust را طوری کامپایل کنید که از C قابل فراخوانی باشد. این کار نسبتاً آسان است، اما چند چیز لازم دارد.

    سمت Rust

    ابتدا فرض می‌کنیم یک crate کتابخانه‌ای با نام rust_from_c دارید. فایل lib.rs باید کد Rust زیر را داشته باشد:

    #[unsafe(no_mangle)]
pub extern "C" fn hello_from_rust() {
    println!("Hello from Rust!");
}
fn main() {}

    extern "C" باعث می‌شود این تابع از قرارداد فراخوانی C پیروی کند، همان‌طور که در ادامه در «قراردادهای فراخوانی خارجی» بحث شده است. attribute به نام no_mangle تغییر نام (name mangling) در Rust را خاموش می‌کند تا نماد (symbol) به‌خوبی تعریف‌شده‌ای برای پیوند دادن وجود داشته باشد.

    سپس برای کامپایل کد Rust به‌صورت یک کتابخانهٔ اشتراکی که از C قابل فراخوانی باشد، موارد زیر را به Cargo.toml خود اضافه کنید:

    [lib]
crate-type = ["cdylib"]

    (توجه: می‌توانیم از نوع crate به نام staticlib نیز استفاده کنیم، اما آن هم به تنظیم برخی پرچم‌های پیوند نیاز دارد.)

    دستور cargo build را اجرا کنید و سمت Rust آماده است.

    سمت C

    یک فایل C می‌سازیم تا تابع hello_from_rust را فراخوانی کند و آن را با gcc کامپایل می‌کنیم.

    فایل C باید این شکل را داشته باشد:

    extern void hello_from_rust();

int main(void) {
    hello_from_rust();
    return 0;
}

    نام فایل را call_rust.c می‌گذاریم و آن را در ریشهٔ crate قرار می‌دهیم. برای کامپایل، دستور زیر را اجرا کنید:

    gcc call_rust.c -o call_rust -lrust_from_c -L./target/debug

    -l و -L به gcc می‌گویند کتابخانهٔ Rust ما را پیدا کند.

    سرانجام می‌توانیم با مشخص کردن LD_LIBRARY_PATH کد Rust را از C فراخوانی کنیم:

    $ LD_LIBRARY_PATH=./target/debug ./call_rust
Hello from Rust!

    همین! برای یک مثال واقعی‌تر، به cbindgen نگاه کنید.

    بازخوانی‌ها (callback) از کد C به توابع Rust

    برخی کتابخانه‌های خارجی برای گزارش وضعیت فعلی یا داده‌های میانی به فراخواننده به استفاده از callback نیاز دارند. می‌توان توابعی را که در Rust تعریف شده‌اند به یک کتابخانهٔ خارجی داد. شرط لازم برای این کار آن است که تابع callback با قرارداد فراخوانی درست به‌صورت extern علامت‌گذاری شود تا از کد C قابل فراخوانی باشد.

    سپس تابع callback را می‌توان از طریق یک فراخوانی ثبت (registration) به کتابخانهٔ C فرستاد و بعداً از همان‌جا آن را صدا زد.

    یک مثال ساده:

    کد Rust:

    extern fn callback(a: i32) {
    println!("I'm called from C with value {0}", a);
}

#[link(name = "extlib")]
unsafe extern "C" {
   fn register_callback(cb: extern fn(i32)) -> i32;
   fn trigger_callback();
}

fn main() {
    unsafe {
        register_callback(callback);
        trigger_callback(); // Triggers the callback.
    }
}

    کد C:

    typedef void (*rust_callback)(int32_t);
rust_callback cb;

int32_t register_callback(rust_callback callback) {
    cb = callback;
    return 1;
}

void trigger_callback() {
  cb(7); // Will call callback(7) in Rust.
}

    در این مثال، main() در Rust تابع trigger_callback() را در C فراخوانی می‌کند که به نوبهٔ خود callback() را در Rust صدا می‌زند.

    هدف‌گیری callbackها به اشیای Rust

    مثال قبلی نشان داد که چگونه می‌توان یک تابع سراسری را از کد C فراخوانی کرد. با این حال، اغلب لازم است که callback به یک شیء خاص در Rust هدایت شود. این می‌تواند شیئی باشد که پوشانندهٔ شیء متناظر در C را نمایش می‌دهد.

    این کار با فرستادن یک اشاره‌گر خام به شیء برای کتابخانهٔ C امکان‌پذیر است. کتابخانهٔ C سپس می‌تواند اشاره‌گر به شیء Rust را در اعلان (notification) بگنجاند. این کار به callback اجازه می‌دهد به‌صورت ناامن به شیء Rust مورد اشاره دسترسی پیدا کند.

    کد Rust:

    struct RustObject {
    a: i32,
    // Other members...
}

unsafe extern "C" fn callback(target: *mut RustObject, a: i32) {
    println!("I'm called from C with value {0}", a);
    unsafe {
        // Update the value in RustObject with the value received from the callback:
        (*target).a = a;
    }
}

#[link(name = "extlib")]
unsafe extern "C" {
   fn register_callback(target: *mut RustObject,
                        cb: unsafe extern "C" fn(*mut RustObject, i32)) -> i32;
   fn trigger_callback();
}

fn main() {
    // Create the object that will be referenced in the callback:
    let mut rust_object = Box::new(RustObject { a: 5 });

    unsafe {
        register_callback(&mut *rust_object, callback);
        trigger_callback();
    }
}

    کد C:

    typedef void (*rust_callback)(void*, int32_t);
void* cb_target;
rust_callback cb;

int32_t register_callback(void* callback_target, rust_callback callback) {
    cb_target = callback_target;
    cb = callback;
    return 1;
}

void trigger_callback() {
  cb(cb_target, 7); // Will call callback(&rustObject, 7) in Rust.
}

    callbackهای ناهمگام

    در مثال‌های پیشین، callbackها به‌عنوان واکنشی مستقیم به فراخوانی یک تابع در کتابخانهٔ C خارجی صدا زده می‌شدند. کنترل نخ جاری برای اجرای callback از Rust به C و دوباره به Rust منتقل می‌شود، اما در نهایت callback روی همان نخی اجرا می‌شود که تابع آغازگر callback را فراخوانی کرده بود.

    وقتی کتابخانهٔ خارجی نخ‌های خودش را ایجاد می‌کند و callbackها را از آن‌ها صدا می‌زند، اوضاع پیچیده‌تر می‌شود. در این موارد، دسترسی به ساختارهای داده Rust درون callbackها به‌ویژه ناامن است و باید از سازوکارهای هم‌گام‌سازی مناسب استفاده شود. افزون بر سازوکارهای کلاسیک هم‌گام‌سازی مانند mutexها، یک امکان در Rust استفاده از کانال‌ها (در std::sync::mpsc) برای ارسال داده از نخ C که callback را صدا زده به یک نخ Rust است.

    اگر یک callback ناهمگام یک شیء خاص در فضای آدرس Rust را هدف بگیرد، لازم است که پس از نابود شدن آن شیء Rust، کتابخانهٔ C دیگر هیچ callbackای اجرا نکند. این کار با لغو ثبت callback در نابودگر شیء و طراحی کتابخانه به‌گونه‌ای که تضمین کند پس از لغو ثبت هیچ callbackای اجرا نخواهد شد، ممکن است.

    پیوند دادن (Linking)

    attribute به نام link روی بلوک‌های extern بنیان اصلی را فراهم می‌کند که با آن به rustc می‌گوییم چگونه با کتابخانه‌های بومی پیوند بزند. امروزه دو شکل پذیرفته‌شده برای attribute به نام link وجود دارد:

    • #[link(name = "foo")]
    • #[link(name = "foo", kind = "bar")]

    در هر دو حالت، foo نام کتابخانهٔ بومی‌ای است که به آن پیوند می‌زنیم و در حالت دوم bar نوع کتابخانهٔ بومی‌ای است که کامپایلر به آن پیوند می‌زند. در حال حاضر سه نوع شناخته‌شده از کتابخانه‌های بومی وجود دارد:

    • پویا (Dynamic) - #[link(name = "readline")]
    • ایستا (Static) - #[link(name = "my_build_dependency", kind = "static")]
    • چارچوب‌ها (Frameworks) - #[link(name = "CoreFoundation", kind = "framework")]

    توجه کنید که frameworkها فقط روی هدف‌های macOS در دسترس‌اند.

    مقدارهای مختلف kind برای تمایز دادن شیوهٔ مشارکت کتابخانهٔ بومی در پیوند دادن به کار می‌روند. از دیدگاه پیوند دادن، کامپایلر Rust دو نوع فایل خروجی (artifact) می‌سازد: جزئی (rlib/staticlib) و نهایی (dylib/binary). وابستگی‌های کتابخانهٔ بومی پویا و framework تا مرز artifact نهایی منتقل می‌شوند، در حالی که وابستگی‌های کتابخانهٔ ایستا اصلاً منتقل نمی‌شوند، زیرا کتابخانه‌های ایستا مستقیماً در artifact بعدی ادغام می‌شوند.

    چند مثال از کاربردهای این مدل عبارت‌اند از:

    • یک وابستگی ساخت بومی. گاهی هنگام نوشتن کد Rust به مقداری کد واسط C/C++ نیاز است، اما توزیع کد C/C++ در قالب کتابخانه دردسر دارد. در این حالت، کد در libfoo.a بایگانی می‌شود و سپس crate مربوط به Rust وابستگی را از طریق #[link(name = "foo", kind = "static")] اعلام می‌کند.

      صرف‌نظر از نوع خروجی crate، کتابخانهٔ ایستای بومی در خروجی گنجانده می‌شود، یعنی توزیع کتابخانهٔ ایستای بومی ضروری نیست.

    • یک وابستگی پویای معمولی. کتابخانه‌های رایج سیستمی (مانند readline) در تعداد زیادی از سیستم‌ها موجودند و اغلب نمی‌توان نسخهٔ ایستای این کتابخانه‌ها را پیدا کرد. وقتی این وابستگی در یک crate از Rust گنجانده شود، هدف‌های جزئی (مانند rlibها) با کتابخانه پیوند نمی‌زنند، اما وقتی rlib در یک هدف نهایی (مانند یک binary) گنجانده شود، کتابخانهٔ بومی پیوند داده می‌شود.

    در macOS، frameworkها همان معنای کتابخانهٔ پویا را دارند.

    بلوک‌های unsafe

    برخی عملیات، مانند ارجاع‌زدایی (dereference) اشاره‌گرهای خام یا فراخوانی توابعی که unsafe علامت‌گذاری شده‌اند، فقط درون بلوک‌های unsafe مجازند. بلوک‌های unsafe ناامنی را ایزوله می‌کنند و قولی به کامپایلر هستند که ناامنی از بلوک بیرون نشت نمی‌کند.

    از سوی دیگر، توابع unsafe این موضوع را به همگان اعلام می‌کنند. یک تابع unsafe این‌گونه نوشته می‌شود:

    unsafe fn kaboom(ptr: *const i32) -> i32 { *ptr }

    این تابع را فقط از یک بلوک unsafe یا یک تابع unsafe دیگر می‌توان فراخوانی کرد.

    دسترسی به متغیرهای سراسری خارجی

    APIهای خارجی اغلب یک متغیر سراسری صادر می‌کنند که می‌تواند کارهایی مانند ردیابی وضعیت سراسری را انجام دهد. برای دسترسی به این متغیرها، آن‌ها را در بلوک‌های extern با کلیدواژهٔ static اعلان می‌کنید:

    #[link(name = "readline")]
unsafe extern "C" {
    static rl_readline_version: libc::c_int;
}

fn main() {
    println!("You have readline version {} installed.",
             unsafe { rl_readline_version as i32 });
}

    از طرف دیگر، ممکن است لازم باشد وضعیت سراسری‌ای را که یک رابط خارجی فراهم می‌کند تغییر دهید. برای این کار، می‌توان staticها را با mut اعلان کرد تا بتوانیم آن‌ها را تغییر دهیم.

    use std::ffi::CString;
use std::ptr;

#[link(name = "readline")]
unsafe extern "C" {
    static mut rl_prompt: *const libc::c_char;
}

fn main() {
    let prompt = CString::new("[my-awesome-shell] $").unwrap();
    unsafe {
        rl_prompt = prompt.as_ptr();

        println!("{:?}", rl_prompt);

        rl_prompt = ptr::null();
    }
}

    توجه کنید که هر تعاملی با یک static mut ناامن است، چه خواندن و چه نوشتن. کار با وضعیت سراسریِ تغییرپذیر نیازمند دقت فراوان است.

    قراردادهای فراخوانی خارجی

    بیشتر کدهای خارجی یک ABI زبان C را در دسترس می‌گذارند و Rust هنگام فراخوانی توابع خارجی به‌طور پیش‌فرض از قرارداد فراخوانی C پلتفرم استفاده می‌کند. برخی توابع خارجی، به‌ویژه API ویندوز، از قراردادهای فراخوانی دیگری استفاده می‌کنند. Rust راهی فراهم می‌کند تا به کامپایلر بگوییم از کدام قرارداد استفاده کند:

    #[cfg(all(target_os = "win32", target_arch = "x86"))]
#[link(name = "kernel32")]
#[allow(non_snake_case)]
unsafe extern "stdcall" {
    fn SetEnvironmentVariableA(n: *const u8, v: *const u8) -> libc::c_int;
}
fn main() { }

    این مورد برای کل بلوک extern اعمال می‌شود. فهرست محدودیت‌های ABI پشتیبانی‌شده از این قرار است:

    • stdcall
    • aapcs
    • cdecl
    • fastcall
    • thiscall
    • vectorcall در حال حاضر این مورد پشت گیت abi_vectorcall پنهان است و ممکن است تغییر کند.
    • Rust
    • system
    • C
    • win64
    • sysv64

    بیشتر ABIهای این فهرست روشن و بدیهی‌اند، اما ABI به نام system ممکن است کمی عجیب به نظر برسد. این محدودیت هر ABI‌ای را که برای همکاری با کتابخانه‌های هدف مناسب باشد انتخاب می‌کند. برای مثال، روی win32 با معماری x86 یعنی ABI به‌کاررفته stdcall خواهد بود. اما روی x86_64، ویندوز از قرارداد فراخوانی C استفاده می‌کند، بنابراین C به کار می‌رود. این یعنی در مثال قبلی می‌توانستیم از extern "system" { ... } برای تعریف بلوکی برای همهٔ سیستم‌های ویندوزی استفاده کنیم، نه فقط سیستم‌های x86.

    همکاری با کد خارجی (Interoperability)

    Rust فقط در صورتی تضمین می‌کند که چینش (layout) یک struct با نمایش C در پلتفرم سازگار باشد که attribute به نام #[repr(C)] روی آن اعمال شده باشد. از #[repr(C, packed)] می‌توان برای چیدن اعضای ساختار بدون padding استفاده کرد. #[repr(C)] را می‌توان روی یک enum نیز اعمال کرد.

    جعبه‌های مالک (Box<T>) در Rust از اشاره‌گرهای غیرتهی به‌عنوان دستگیره استفاده می‌کنند که به شیء درون آن اشاره دارند. با این حال نباید آن‌ها را به‌صورت دستی ساخت، زیرا تخصیص‌دهنده‌های درونی آن‌ها را مدیریت می‌کنند. می‌توان با اطمینان فرض کرد که ارجاع‌ها اشاره‌گرهای غیرتهیِ مستقیم به آن نوع هستند. با این حال، شکستن قواعد بررسی قرض یا تغییرپذیری تضمینی برای امن بودن ندارد، بنابراین در صورت نیاز، استفاده از اشاره‌گرهای خام (*) را ترجیح دهید، چون کامپایلر دربارهٔ آن‌ها فرض‌های کمتری می‌تواند بکند.

    بردارها و رشته‌ها چینش حافظهٔ پایهٔ یکسانی دارند و ابزارهایی در ماژول‌های vec و str برای کار با APIهای C در دسترس است. با این حال، رشته‌ها با \0 خاتمه نمی‌یابند. اگر برای همکاری با C به رشتهٔ خاتمه‌یافته با NUL نیاز دارید، باید از نوع CString در ماژول std::ffi استفاده کنید.

    crate با نام libc در crates.io شامل نام‌های مستعار نوع و تعریف‌های تابع برای کتابخانهٔ استاندارد C در ماژول libc است و Rust به‌طور پیش‌فرض با libc و libm پیوند می‌زند.

    توابع متغیر‌آرگومان (Variadic)

    در C، توابع می‌توانند «variadic» باشند، یعنی تعداد متغیری آرگومان بپذیرند. این در Rust با مشخص کردن ... در فهرست آرگومان‌های اعلان یک تابع خارجی امکان‌پذیر است:

    unsafe extern "C" {
    fn foo(x: i32, ...);
}

fn main() {
    unsafe {
        foo(10, 20, 30, 40, 50);
    }
}

    توابع معمولی Rust نمی‌توانند variadic باشند:

    // This will not compile

fn foo(x: i32, ...) {}

    «بهینه‌سازی اشاره‌گر تهی‌پذیر»

    برخی انواع Rust تعریف شده‌اند که هرگز null نباشند. این شامل ارجاع‌ها (&T، &mut T)، جعبه‌ها (Box<T>) و اشاره‌گرهای تابع (extern "abi" fn()) می‌شود. هنگام تعامل با C اغلب از اشاره‌گرهایی استفاده می‌شود که ممکن است null باشند، که به‌نظر می‌رسد برای مدیریت تبدیل‌ها از/به انواع Rust به چند transmute درهم‌ریخته و/یا کد ناامن نیاز داشته باشد. با این حال، تلاش برای ساختن/کار با این مقادیر نامعتبر رفتار تعریف‌نشده (undefined behavior) است، پس باید به‌جای آن از راه‌حل زیر استفاده کنید.

    به‌عنوان یک حالت خاص، یک enum واجد شرایط «بهینه‌سازی اشاره‌گر تهی‌پذیر» است اگر دقیقاً دو گونه (variant) داشته باشد که یکی هیچ داده‌ای ندارد و دیگری فیلدی از یکی از انواع غیرتهی فهرست‌شده در بالا دارد. این یعنی برای تمایزدهنده (discriminant) فضای اضافه‌ای لازم نیست؛ بلکه گونهٔ خالی با گذاشتن مقدار null در فیلد غیرتهی نمایش داده می‌شود. این مورد «بهینه‌سازی» نامیده می‌شود، اما برخلاف بهینه‌سازی‌های دیگر، تضمین شده است که برای انواع واجد شرایط اعمال شود.

    رایج‌ترین نوعی که از بهینه‌سازی اشاره‌گر تهی‌پذیر بهره می‌برد Option<T> است، که در آن None متناظر با null است. پس Option<extern "C" fn(c_int) -> c_int> راه درستی است برای نمایش یک اشاره‌گر تابع تهی‌پذیر با ABI زبان C (که متناظر با نوع C یعنی int (*)(int) است).

    یک مثال ساختگی در اینجا آمده است. فرض کنید یک کتابخانهٔ C امکانی برای ثبت یک callback دارد که در موقعیت‌های معینی صدا زده می‌شود. به callback یک اشاره‌گر تابع و یک عدد صحیح داده می‌شود و قرار است تابع را با آن عدد صحیح به‌عنوان پارامتر اجرا کند. بنابراین اشاره‌گرهای تابع در هر دو جهت از مرز FFI عبور می‌کنند.

    use libc::c_int;

#[cfg(hidden)]
unsafe extern "C" {
    /// Registers the callback.
    fn register(cb: Option<extern "C" fn(Option<extern "C" fn(c_int) -> c_int>, c_int) -> c_int>);
}
unsafe fn register(_: Option<extern "C" fn(Option<extern "C" fn(c_int) -> c_int>,
                                           c_int) -> c_int>)
{}

/// This fairly useless function receives a function pointer and an integer
/// from C, and returns the result of calling the function with the integer.
/// In case no function is provided, it squares the integer by default.
extern "C" fn apply(process: Option<extern "C" fn(c_int) -> c_int>, int: c_int) -> c_int {
    match process {
        Some(f) => f(int),
        None    => int * int
    }
}

fn main() {
    unsafe {
        register(Some(apply));
    }
}

    و کد سمت C به این شکل است:

    void register(int (*f)(int (*)(int), int)) {
    ...
}

    هیچ transmuteای لازم نیست!

    FFI و بازگشایی پشته (unwinding)

    هنگام کار با FFI مهم است که به unwinding توجه داشته باشید. بیشتر رشته‌های ABI در دو گونه می‌آیند، یکی با پسوند -unwind و دیگری بدون آن. ABI به نام Rust همیشه unwinding را مجاز می‌داند، بنابراین ABI ای به نام Rust-unwind وجود ندارد.

    اگر انتظار دارید panicهای Rust یا استثناهای خارجی (مثلاً C++) از مرز FFI عبور کنند، آن مرز باید از رشتهٔ ABI مناسبِ -unwind استفاده کند. برعکس، اگر انتظار ندارید unwinding از یک مرز ABI عبور کند، از یکی از رشته‌های ABI بدون unwind استفاده کنید.

    توجه: کامپایل با panic=abort همچنان باعث می‌شود panic! بی‌درنگ فرایند را متوقف (abort) کند، صرف‌نظر از اینکه تابعی که panic می‌کند چه ABI ای مشخص کرده است.

    اگر یک عملیات unwinding با مرز ABI ای روبه‌رو شود که اجازهٔ unwind ندارد، رفتار به منبع unwinding بستگی دارد (panic در Rust یا یک استثنای خارجی):

    • panic باعث می‌شود فرایند به‌صورت امن متوقف شود.
    • ورود یک استثنای خارجی به Rust باعث رفتار تعریف‌نشده می‌شود.

    توجه کنید که تعامل catch_unwind با استثناهای خارجی تعریف‌نشده است، همان‌طور که تعامل panic با سازوکارهای گرفتن استثنای خارجی (به‌ویژه try/catch در C++) تعریف‌نشده است.

    panic در Rust با "C-unwind"

    #[unsafe(no_mangle)]
unsafe extern "C-unwind" fn example() {
    panic!("Uh oh");
}

    این تابع (وقتی با panic=unwind کامپایل شود) مجاز است فریم‌های پشتهٔ C++ را unwind کند.

    [Rust function with `catch_unwind`, which stops the unwinding]
      |
     ...
      |
[C++ frames]
      |                           ^
      | (calls)                   | (unwinding
      v                           |  goes this
[Rust function `example`]         |  way)
      |                           |
      +--- rust function panics --+

    اگر فریم‌های C++ شیء داشته باشند، نابودگرهای آن‌ها صدا زده می‌شوند.

    throw در C++ با "C-unwind"

    #[link(...)]
unsafe extern "C-unwind" {
    // A C++ function that may throw an exception
    fn may_throw();
}

#[unsafe(no_mangle)]
unsafe extern "C-unwind" fn rust_passthrough() {
    let b = Box::new(5);
    unsafe { may_throw(); }
    println!("{:?}", &b);
}

    یک تابع C++ با بلوک try می‌تواند rust_passthrough را فراخوانی کند و استثنایی را که may_throw پرتاب کرده catch کند.

    [C++ function with `try` block that invokes `rust_passthrough`]
      |
     ...
      |
[Rust function `rust_passthrough`]
      |                            ^
      | (calls)                    | (unwinding
      v                            |  goes this
[C++ function `may_throw`]         |  way)
      |                            |
      +--- C++ function throws ----+

    اگر may_throw واقعاً استثنایی پرتاب کند، b drop می‌شود. در غیر این صورت 5 چاپ خواهد شد.

    panic را می‌توان در مرز ABI متوقف کرد

    #[unsafe(no_mangle)]
extern "C" fn assert_nonzero(input: u32) {
    assert!(input != 0)
}

    اگر assert_nonzero با آرگومان 0 فراخوانی شود، تضمین شده است که زمان اجرا (runtime) فرایند را (به‌صورت امن) متوقف کند، چه با panic=abort کامپایل شده باشد و چه نه.

    گرفتن پیشگیرانهٔ panic

    اگر کد Rust ای می‌نویسید که ممکن است panic کند و نمی‌خواهید در صورت panic فرایند متوقف شود، باید از catch_unwind استفاده کنید:

    use std::panic::catch_unwind;

#[unsafe(no_mangle)]
pub extern "C" fn oh_no() -> i32 {
    let result = catch_unwind(|| {
        panic!("Oops!");
    });
    match result {
        Ok(_) => 0,
        Err(_) => 1,
    }
}

fn main() {}

    لطفاً توجه کنید که catch_unwind فقط panicهایی را می‌گیرد که unwind می‌کنند، نه آن‌هایی که فرایند را متوقف می‌کنند. برای اطلاعات بیشتر مستندات catch_unwind را ببینید.

    نمایش ساختارهای مبهم (opaque)

    گاهی یک کتابخانهٔ C می‌خواهد اشاره‌گری به چیزی بدهد، اما جزئیات درونی آن چیز را به شما نشان ندهد. یک راه پایدار و ساده استفاده از آرگومان void * است:

    void foo(void *arg);
void bar(void *arg);

    این را در Rust می‌توانیم با نوع c_void نمایش دهیم:

    unsafe extern "C" {
    pub fn foo(arg: *mut libc::c_void);
    pub fn bar(arg: *mut libc::c_void);
}
fn main() {}

    این روش کاملاً معتبری برای مدیریت این وضعیت است. با این حال، می‌توانیم کمی بهتر عمل کنیم. برای حل این مسئله، برخی کتابخانه‌های C به‌جای آن یک struct می‌سازند که جزئیات و چینش حافظهٔ آن خصوصی است. این کار مقداری امنیت نوع فراهم می‌کند. این ساختارها «مبهم» (opaque) نامیده می‌شوند. این هم یک مثال در C:

    struct Foo; /* Foo is a structure, but its contents are not part of the public interface */
struct Bar;
void foo(struct Foo *arg);
void bar(struct Bar *arg);

    برای انجام این کار در Rust، نوع‌های مبهم خودمان را می‌سازیم:

    #[repr(C)]
pub struct Foo {
    _data: (),
    _marker:
        core::marker::PhantomData<(*mut u8, core::marker::PhantomPinned)>,
}
#[repr(C)]
pub struct Bar {
    _data: (),
    _marker:
        core::marker::PhantomData<(*mut u8, core::marker::PhantomPinned)>,
}

unsafe extern "C" {
    pub fn foo(arg: *mut Foo);
    pub fn bar(arg: *mut Bar);
}
fn main() {}

    با گنجاندن دست‌کم یک فیلد خصوصی و نداشتن سازنده (constructor)، نوعی مبهم می‌سازیم که بیرون از این ماژول نمی‌توان از آن نمونه ساخت. (از یک struct بدون فیلد، هر کسی می‌تواند نمونه بسازد.) همچنین می‌خواهیم از این نوع در FFI استفاده کنیم، پس باید #[repr(C)] را اضافه کنیم. نشانگر (marker) تضمین می‌کند که کامپایلر ساختار را Send، Sync و Unpin علامت‌گذاری نمی‌کند. (*mut u8 نه Send است و نه Sync، و PhantomPinned نیز Unpin نیست.)

    اما چون نوع‌های Foo و Bar ما متفاوت‌اند، بین این دو امنیت نوع خواهیم داشت، بنابراین نمی‌توانیم به‌طور تصادفی اشاره‌گری به Foo را به bar() بدهیم.

    توجه کنید که استفاده از یک enum خالی به‌عنوان نوع FFI ایدهٔ واقعاً بدی است. کامپایلر بر این تکیه می‌کند که enumهای خالی غیرقابل سکونت (uninhabited) هستند، پس کار با مقادیری از نوع &Empty یک تلهٔ بزرگ است و می‌تواند به رفتار اشتباه برنامه بینجامد (با فعال کردن رفتار تعریف‌نشده).

    توجه: ساده‌ترین راه استفاده از «نوع‌های extern» (extern types) است. اما در حال حاضر (تا ژوئن ۲۰۲۱) ناپایدار است و پرسش‌های حل‌نشده‌ای دارد؛ برای جزئیات بیشتر صفحهٔ RFC و issue پیگیری را ببینید.
