    نابودگرها (Destructors)

    آنچه زبان فراهم می‌کند نابودگرهای خودکار کامل از طریق صفت Drop است که متد زیر را ارائه می‌دهد:

    fn drop(&mut self);

    این متد به نوع فرصت می‌دهد تا به شکلی کاری را که در حال انجام آن بود به پایان برساند.

    پس از اجرای drop، Rust به‌صورت بازگشتی تلاش می‌کند همه‌ی فیلدهای self را drop کند.

    این یک ویژگی راحتی است تا لازم نباشد برای drop کردن فرزندان «کد تکراری نابودگر» بنویسید. اگر یک ساختار هیچ منطق ویژه‌ای برای drop شدن جز drop کردن فرزندانش نداشته باشد، یعنی Drop اصلاً نیازی به پیاده‌سازی ندارد!

    در Rust 1.0 هیچ راه پایداری برای جلوگیری از این رفتار وجود ندارد.

    توجه کنید که گرفتن &mut self به این معناست که حتی اگر می‌توانستید Drop بازگشتی را سرکوب کنید، Rust مانع می‌شود که مثلاً فیلدها را از self بیرون منتقل کنید. برای بیشتر نوع‌ها این کاملاً مشکلی ندارد.

    برای مثال، یک پیاده‌سازی سفارشی از Box ممکن است Drop را این‌گونه بنویسد:

    use std::alloc::{Allocator, Global, GlobalAlloc, Layout};
use std::marker::PhantomData;
use std::mem;
use std::ptr::{drop_in_place, NonNull};

struct Box<T>{ ptr: NonNull<T>, _marker: PhantomData<T> }

impl<T> Drop for Box<T> {
    fn drop(&mut self) {
        unsafe {
            drop_in_place(self.ptr.as_ptr());
            Global.deallocate(self.ptr.cast(), Layout::new::<T>())
        }
    }
}
fn main() {}

    و این به‌خوبی کار می‌کند، چون وقتی Rust می‌خواهد فیلدها را drop کند، فقط یک NonNull و یک PhantomData می‌بیند که هیچ‌کدام پیاده‌سازی Drop واقعی ندارند. به‌طور مشابه هیچ چیزی نمی‌تواند ptr را use-after-free کند، چون وقتی drop به پایان می‌رسد، ptr دیگر قابل دسترسی نیست.

    اما این کار نمی‌کند:

    use std::alloc::{Allocator, Global, GlobalAlloc, Layout};
use std::marker::PhantomData;
use std::ptr::{drop_in_place, NonNull};
use std::mem;

struct Box<T>{ ptr: NonNull<T>, _marker: PhantomData<T> }

impl<T> Drop for Box<T> {
    fn drop(&mut self) {
        unsafe {
            drop_in_place(self.ptr.as_ptr());
            Global.deallocate(self.ptr.cast(), Layout::new::<T>());
        }
    }
}

struct SuperBox<T> { my_box: Box<T> }

impl<T> Drop for SuperBox<T> {
    fn drop(&mut self) {
        unsafe {
            // Hyper-optimized: deallocate the box's contents for it
            // without `drop`ing the contents
            Global.deallocate(self.my_box.ptr.cast::<u8>(), Layout::new::<T>());
        }
    }
}
fn main() {}

    پس از اینکه ptr مربوط به box را در نابودگر SuperBox آزاد کردیم، Rust با کمال میل ادامه می‌دهد و به box می‌گوید خودش را Drop کند و همه‌چیز با use-after-free و double-free منفجر می‌شود.

    توجه کنید که رفتار drop بازگشتی برای همه‌ی ساختارها و شمارش‌ها (enum) اعمال می‌شود، صرف‌نظر از اینکه Drop را پیاده‌سازی کرده باشند یا نه. بنابراین چیزی مانند

    struct Boxy<T> {
    data1: Box<T>,
    data2: Box<T>,
    info: u32,
}

    هر زمان که «قرار بود» drop شود، نابودگرهای فیلدهای data1 و data2 آن فراخوانی می‌شوند، حتی اگر خودش Drop را پیاده‌سازی نکرده باشد. می‌گوییم چنین نوعی به Drop نیاز دارد (needs Drop)، هرچند خودش Drop نیست.

    به همین ترتیب،

    enum Link {
    Next(Box<Link>),
    None,
}

    فیلد Box درونی‌اش را اگر و فقط اگر نمونه‌ای واریانت Next را ذخیره کرده باشد drop می‌کند.

    به‌طور کلی این کار بسیار خوب عمل می‌کند چون هنگام بازآرایی چیدمان داده لازم نیست نگران افزودن/حذف drop ها باشید. با این حال قطعاً موارد استفاده‌ی معتبر زیادی وجود دارد که در آن‌ها لازم است کارهای پیچیده‌تری با نابودگرها انجام دهید.

    راه‌حل امن کلاسیک برای نادیده گرفتن drop بازگشتی و اجازه‌ی منتقل کردن از Self در حین drop، استفاده از Option است:

    use std::alloc::{Allocator, GlobalAlloc, Global, Layout};
use std::marker::PhantomData;
use std::ptr::{drop_in_place, NonNull};
use std::mem;

struct Box<T>{ ptr: NonNull<T>, _marker: PhantomData<T> }

impl<T> Drop for Box<T> {
    fn drop(&mut self) {
        unsafe {
            drop_in_place(self.ptr.as_ptr());
            Global.deallocate(self.ptr.cast(), Layout::new::<T>());
        }
    }
}

struct SuperBox<T> { my_box: Option<Box<T>> }

impl<T> Drop for SuperBox<T> {
    fn drop(&mut self) {
        unsafe {
            // Hyper-optimized: deallocate the box's contents for it
            // without `drop`ing the contents. Need to set the `box`
            // field as `None` to prevent Rust from trying to Drop it.
            let my_box = self.my_box.take().unwrap();
            Global.deallocate(my_box.ptr.cast(), Layout::new::<T>());
            mem::forget(my_box);
        }
    }
}
fn main() {}

    با این حال این معناشناسی نسبتاً عجیبی دارد: شما می‌گویید فیلدی که باید همیشه Some باشد، ممکن است None باشد، فقط به خاطر آنچه در نابودگر رخ می‌دهد. البته در مقابل این کاملاً منطقی است: می‌توانید در طول نابودگر متدهای دلخواه را روی self فراخوانی کنید، و این باید مانع شود که پس از مقداردهی‌زدایی فیلد چنین کاری بکنید. هرچند این مانع تولید هر وضعیت نامعتبر دلخواه دیگری در آنجا نمی‌شود.

    در مجموع این انتخاب قابل‌قبولی است. قطعاً چیزی است که باید به‌صورت پیش‌فرض سراغش بروید. با این حال، انتظار داریم در آینده راهی درجه‌یک برای اعلام اینکه یک فیلد نباید به‌طور خودکار drop شود وجود داشته باشد.
