    حافظهٔ مقداردهی‌نشدهٔ بررسی‌نشده

    یک استثنای جالب برای این قاعده، کار با آرایه‌هاست. Safe Rust اجازه نمی‌دهد یک آرایه را به‌طور جزئی مقداردهی اولیه کنید. وقتی یک آرایه را مقداردهی اولیه می‌کنید، یا می‌توانید همهٔ مقدارها را با let x = [val; N] روی یک چیز یکسان تنظیم کنید، یا می‌توانید هر عضو را جداگانه با let x = [val1, val2, val3] مشخص کنید. متأسفانه این کار کاملاً سفت و سخت است، به‌ویژه اگر لازم باشد آرایه‌تان را به شیوه‌ای تدریجی‌تر یا پویاتر مقداردهی کنید.

    Unsafe Rust ابزار قدرتمندی برای رسیدگی به این مسئله به ما می‌دهد: MaybeUninit. از این نوع می‌توان برای مدیریت حافظه‌ای که هنوز به‌طور کامل مقداردهی اولیه نشده است استفاده کرد.

    با MaybeUninit می‌توانیم یک آرایه را عنصر به عنصر به‌صورت زیر مقداردهی اولیه کنیم:

    use std::mem::{self, MaybeUninit};

// Size of the array is hard-coded but easy to change (meaning, changing just
// the constant is sufficient). This means we can't use [a, b, c] syntax to
// initialize the array, though, as we would have to keep that in sync
// with `SIZE`!
const SIZE: usize = 10;

let x = {
    // Create an uninitialized array of `MaybeUninit`.
    let mut x = [const { MaybeUninit::uninit() }; SIZE];

    // Dropping a `MaybeUninit` does nothing. Thus using raw pointer
    // assignment instead of `ptr::write` does not cause the old
    // uninitialized value to be dropped.
    // Exception safety is not a concern because Box can't panic
    for i in 0..SIZE {
        x[i] = MaybeUninit::new(Box::new(i as u32));
    }

    // Everything is initialized. Transmute the array to the
    // initialized type.
    unsafe { mem::transmute::<_, [Box<u32>; SIZE]>(x) }
};

println!("{x:?}");

    این کد در سه گام پیش می‌رود:

    1. یک آرایه از MaybeUninit<T> ایجاد کنید.

    2. آرایه را مقداردهی اولیه کنید. نکتهٔ ظریف این است که معمولاً وقتی از = برای انتساب به مقداری استفاده می‌کنیم که بررسی‌کنندهٔ نوع Rust آن را از قبل مقداردهی شده می‌داند (مثل x[i])، مقدار قدیمی ذخیره‌شده در سمت چپ drop می‌شود. این فاجعه می‌شد. اما در این مورد، نوع سمت چپ MaybeUninit<Box<u32>> است و drop شدن آن هیچ کاری نمی‌کند! برای بحث بیشتر دربارهٔ این مسئلهٔ drop به پایین نگاه کنید.

    3. سرانجام، باید نوع آرایه‌مان را تغییر دهیم تا MaybeUninit برداشته شود. با Rust پایدار فعلی، این به یک transmute نیاز دارد. این transmute قانونی است چون در حافظه، MaybeUninit<T> همان شکل T را دارد.

      با این حال، توجه کنید که در حالت کلی، Container<MaybeUninit<T>>> شبیه Container<T> نیست! تصور کنید Container برابر Option بود و T برابر bool؛ آنگاه Option<bool> از این بهره می‌برد که bool فقط دو مقدار معتبر دارد، اما Option<MaybeUninit<bool>> نمی‌تواند این کار را بکند چون bool لازم نیست مقداردهی اولیه شده باشد.

      پس اینکه آیا برداشتن MaybeUninit با transmute مجاز است یا نه به Container بستگی دارد. برای آرایه‌ها مجاز است (و در نهایت کتابخانهٔ استاندارد با ارائهٔ متدهای مناسب این را به رسمیت خواهد شناخت).

    ارزش دارد کمی بیشتر روی حلقهٔ میانی وقت بگذاریم، و به‌طور خاص روی عملگر انتساب و برهم‌کنش آن با drop. اگر چیزی شبیه این می‌نوشتیم:

    *x[i].as_mut_ptr() = Box::new(i as u32); // WRONG!

    در واقع یک Box<u32> را بازنویسی می‌کردیم که به drop شدن داده‌ای مقداردهی‌نشده می‌انجامید و غم و درد فراوانی ببار می‌آورد.

    جایگزین درست، اگر به هر دلیلی نتوانیم از MaybeUninit::new استفاده کنیم، این است که از ماژول ptr استفاده کنیم. به‌طور خاص، این ماژول سه تابع فراهم می‌کند که به ما اجازه می‌دهند بایت‌ها را بدون drop کردن مقدار قدیمی به یک مکان از حافظه اختصاص دهیم: write، copy و copy_nonoverlapping.

    • ptr::write(ptr, val) یک val می‌گیرد و آن را به آدرسی که ptr به آن اشاره می‌کند منتقل می‌کند.
    • ptr::copy(src, dest, count) بیت‌هایی را که count آیتم از نوع T اشغال می‌کنند از src به dest کپی می‌کند. (این معادل memmove در C است – توجه کنید که ترتیب آرگومان‌ها برعکس است!)
    • ptr::copy_nonoverlapping(src, dest, count) همان کاری را می‌کند که copy می‌کند، اما با فرض اینکه دو بازهٔ حافظه هم‌پوشانی ندارند کمی سریع‌تر. (این معادل memcpy در C است – توجه کنید که ترتیب آرگومان‌ها برعکس است!)

    نیازی به گفتن نیست که این تابع‌ها در صورت سوءاستفاده، آشوبی جدی یا مستقیماً رفتار تعریف‌نشده ایجاد می‌کنند. تنها الزام خود این تابع‌ها این است که مکان‌هایی که می‌خواهید بخوانید و بنویسید تخصیص یافته و به‌درستی تراز شده باشند. با این حال، راه‌هایی که نوشتن بیت‌های دلخواه در مکان‌های دلخواه حافظه می‌تواند چیزها را خراب کند اساساً بی‌شمارند!

    شایان ذکر است که لازم نیست نگران ترفندهای سبک ptr::write با نوع‌هایی باشید که Drop را پیاده‌سازی نمی‌کنند یا نوع‌های Drop در خود ندارند، چون Rust می‌داند که نباید سعی کند آن‌ها را drop کند. این همان چیزی بود که در مثال بالا به آن تکیه کردیم.

    با این حال هنگام کار با حافظهٔ مقداردهی‌نشده باید همیشه مراقب باشید که Rust سعی نکند مقادیری را که این‌گونه می‌سازید پیش از مقداردهی کامل drop کند. اگر یک متغیر نابودگر دارد، هر مسیر کنترلی که از حوزهٔ آن متغیر می‌گذرد باید پیش از پایان آن مقدار را مقداردهی اولیه کند. این شامل panic کردن کد هم می‌شود. MaybeUninit اینجا کمی کمک می‌کند، چون محتوایش را به‌طور ضمنی drop نمی‌کند - اما در صورت panic، همهٔ این‌ها در واقع فقط به این معناست که به‌جای double-free بخش‌های هنوز مقداردهی‌نشده، با نشت حافظهٔ بخش‌هایی که از قبل مقداردهی شده‌اند مواجه می‌شوید.

    توجه کنید که برای استفاده از متدهای ptr، ابتدا باید یک اشاره‌گر خام به داده‌ای که می‌خواهید مقداردهی اولیه کنید به‌دست آورید. ساختن یک ارجاع به داده‌ٔ مقداردهی‌نشده غیرقانونی است، که یعنی هنگام به‌دست آوردن آن اشاره‌گر خام باید مراقب باشید:

    • برای یک آرایه از T می‌توانید از base_ptr.add(idx) استفاده کنید، که در آن base_ptr: *mut T، تا آدرس اندیس idx آرایه را محاسبه کنید. این به نحوهٔ چیده شدن آرایه‌ها در حافظه تکیه دارد.
    • اما برای یک struct، در حالت کلی نمی‌دانیم چگونه چیده شده است، و همچنین نمی‌توانیم از &mut base_ptr.field استفاده کنیم چون این یک ارجاع می‌سازد. بنابراین باید با دقت از نحو ارجاع خام استفاده کنید. این نحو بدون ساختن ارجاع میانی، یک اشاره‌گر خام به فیلد می‌سازد:
    use std::{ptr, mem::MaybeUninit};

struct Demo {
    field: bool,
}

let mut uninit = MaybeUninit::<Demo>::uninit();
// `&uninit.as_mut().field` would create a reference to an uninitialized `bool`,
// and thus be Undefined Behavior!
let f1_ptr = unsafe { &raw mut (*uninit.as_mut_ptr()).field };
unsafe { f1_ptr.write(true); }

let init = unsafe { uninit.assume_init() };

    یک نکتهٔ پایانی: هنگام خواندن کد قدیمی Rust، ممکن است به تابع منسوخ‌شدهٔ mem::uninitialized برخورد کنید. آن تابع زمانی تنها راه کار با حافظهٔ مقداردهی‌نشده روی پشته بود، اما معلوم شد که ادغام درست آن با بقیهٔ زبان ناممکن است. همیشه در کد جدید به‌جای آن از MaybeUninit استفاده کنید و هرگاه فرصت کردید کد قدیمی را منتقل کنید.

    و کار با حافظهٔ مقداردهی‌نشده تقریباً همین است! اساساً هیچ چیزی در هیچ جا انتظار ندارد حافظهٔ مقداردهی‌نشده به آن داده شود، پس اگر قرار است آن را اصلاً جابه‌جا کنید، حتماً واقعاً مراقب باشید.
