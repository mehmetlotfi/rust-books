    طول عمرها (Lifetimes)

    Rust این قواعد را از طریق طول عمرها اعمال می‌کند. طول عمرها نواحی نام‌دار از کد هستند که یک ارجاع باید برای آن‌ها معتبر باشد. این نواحی می‌توانند نسبتاً پیچیده باشند، چون با مسیرهای اجرا در برنامه متناظرند. حتی ممکن است در این مسیرهای اجرا حفره‌هایی وجود داشته باشد، چون می‌توان یک ارجاع را نامعتبر کرد، به شرط آنکه پیش از استفادهٔ دوباره از آن دوباره مقداردهی شود. انواعی که شامل ارجاع هستند (یا وانمود می‌کنند که هستند) نیز ممکن است با طول عمر برچسب بخورند تا Rust بتواند از نامعتبر شدن آن‌ها هم جلوگیری کند.

    در بیشتر مثال‌های ما، طول عمرها با حوزه‌ها (scope) هم‌خوانی دارند. این به این دلیل است که مثال‌های ما ساده‌اند. موارد پیچیده‌تری که در آن‌ها هم‌خوانی ندارند در ادامه توضیح داده می‌شوند.

    درون بدنهٔ یک تابع، Rust معمولاً اجازه نمی‌دهد طول عمرهای درگیر را به‌صراحت نام ببرید. دلیلش این است که در یک زمینهٔ محلی معمولاً واقعاً لازم نیست دربارهٔ طول عمرها صحبت کنیم؛ Rust همهٔ اطلاعات را دارد و می‌تواند همه‌چیز را تا حد ممکن بهینه استنباط کند. بسیاری از حوزه‌های ناشناس و موقت‌ها که در غیر این صورت باید خودتان می‌نوشتید اغلب معرفی می‌شوند تا کد شما فقط کار کند.

    با این حال، به‌محض عبور از مرز تابع، باید شروع به صحبت دربارهٔ طول عمرها کنید. طول عمرها با آپوستروف نشان داده می‌شوند: 'a، 'static. برای آشنایی اولیه با طول عمرها، وانمود می‌کنیم که واقعاً اجازه داریم حوزه‌ها را با طول عمر برچسب بزنیم و مثال‌های ابتدای این فصل را desugar می‌کنیم.

    در ابتدا، مثال‌های ما از قند نحوی تهاجمی – حتی شربت ذرت با فروکتوز بالا – دربارهٔ حوزه‌ها و طول عمرها استفاده می‌کردند، چون نوشتن همه‌چیز به‌صراحت فوق‌العاده شلوغ است. همهٔ کد Rust بر استنباط تهاجمی و حذف چیزهای «بدیهی» تکیه دارد.

    یکی از قندهای نحوی بسیار جالب این است که هر دستور let به‌طور ضمنی یک حوزه معرفی می‌کند. در بیشتر موارد این واقعاً اهمیتی ندارد. اما برای متغیرهایی که به یکدیگر ارجاع می‌دهند اهمیت دارد. به‌عنوان یک مثال ساده، بیایید این قطعه کد ساده Rust را کاملاً desugar کنیم:

    let x = 0;
let y = &x;
let z = &y;

    borrow checker همیشه سعی می‌کند وسعت یک طول عمر را کمینه کند، بنابراین احتمالاً به شکل زیر desugar می‌شود:

    // NOTE: `'a: {` and `&'b x` is not valid syntax!
'a: {
    let x: i32 = 0;
    'b: {
        // lifetime used is 'b because that's good enough.
        let y: &'b i32 = &'b x;
        'c: {
            // ditto on 'c
            let z: &'c &'b i32 = &'c y; // "a reference to a reference to an i32" (with lifetimes annotated)
        }
    }
}

    وای. این… وحشتناک است. بیایید همگی لحظه‌ای از Rust تشکر کنیم که این کار را آسان‌تر کرده است.

    در واقع، فرستادن ارجاع‌ها به حوزه‌های بیرونی‌تر باعث می‌شود Rust طول عمر بزرگ‌تری استنباط کند:

    let x = 0;
let z;
let y = &x;
z = y;
    'a: {
    let x: i32 = 0;
    'b: {
        let z: &'b i32;
        'c: {
            // Must use 'b here because the reference to x is
            // being passed to the scope 'b.
            let y: &'b i32 = &'b x;
            z = y;
        }
    }
}

    مثال: ارجاع‌هایی که از مرجع‌شان بیشتر عمر می‌کنند

    بسیار خوب، بیایید به برخی از آن مثال‌های قبلی نگاهی بیندازیم:

    fn as_str(data: &u32) -> &str {
    let s = format!("{}", data);
    &s
}

    که desugar می‌شود به:

    fn as_str<'a>(data: &'a u32) -> &'a str {
    'b: {
        let s = format!("{}", data);
        return &'a s;
    }
}

    این امضای as_str یک ارجاع به u32 با یک طول عمر می‌گیرد و قول می‌دهد که بتواند ارجاعی به str تولید کند که به همان اندازه زنده بماند. همین حالا می‌توانیم ببینیم چرا این امضا ممکن است دردسرساز باشد. این اساساً به این معنا است که قرار است یک str را جایی در حوزه‌ای پیدا کنیم که ارجاع به u32 در آن پدید آمده، یا جایی حتی زودتر. این کمی انتظار زیادی است.

    سپس به محاسبهٔ رشتهٔ s می‌پردازیم و ارجاعی به آن برمی‌گردانیم. چون قرارداد تابع ما می‌گوید ارجاع باید بیشتر از 'a عمر کند، این همان طول عمری است که برای ارجاع استنباط می‌کنیم. متأسفانه s در حوزهٔ 'b تعریف شده است، پس تنها راهی که این صحیح باشد آن است که 'b شامل 'a باشد – که به‌وضوح نادرست است، چون 'a باید خود فراخوانی تابع را در بر بگیرد. بنابراین ارجاعی ساخته‌ایم که طول عمرش از مرجعش بیشتر است، که به معنای واقعی کلمه اولین کاری است که گفتیم ارجاع‌ها نمی‌توانند انجام دهند. کامپایلر به‌حق جلوی چشممان منفجر می‌شود.

    برای روشن‌تر شدن، می‌توانیم مثال را بسط دهیم:

    fn as_str<'a>(data: &'a u32) -> &'a str {
    'b: {
        let s = format!("{}", data);
        return &'a s
    }
}

fn main() {
    'c: {
        let x: u32 = 0;
        'd: {
            // An anonymous scope is introduced because the borrow does not
            // need to last for the whole scope x is valid for. The return
            // of as_str must find a str somewhere before this function
            // call. Obviously not happening.
            println!("{}", as_str::<'d>(&'d x));
        }
    }
}

    لعنت!

    البته راه درست نوشتن این تابع به این صورت است:

    fn to_string(data: &u32) -> String {
    format!("{}", data)
}

    باید درون تابع یک مقدار مالک تولید کنیم تا بتوانیم آن را برگردانیم! تنها راهی که می‌توانستیم &'a str را برگردانیم این بود که در یکی از فیلدهای &'a u32 باشد، که آشکارا چنین نیست.

    (در واقع می‌توانستیم فقط یک لیترال رشته‌ای هم برگردانیم که به‌عنوان یک سراسری می‌توان آن را ساکن در پایین پشته دانست؛ هرچند این کار پیاده‌سازی ما را کمی محدود می‌کند.)

    مثال: alias کردن یک ارجاع تغییرپذیر

    مثال دیگر چطور؟

    let mut data = vec![1, 2, 3];
let x = &data[0];
data.push(4);
println!("{}", x);
    'a: {
    let mut data: Vec<i32> = vec![1, 2, 3];
    'b: {
        // 'b is as big as we need this borrow to be
        // (just need to get to `println!`)
        let x: &'b i32 = Index::index::<'b>(&'b data, 0);
        'c: {
            // Temporary scope because we don't need the
            // &mut to last any longer.
            Vec::push(&'c mut data, 4);
        }
        println!("{}", x);
    }
}

    مشکل در اینجا کمی ظریف‌تر و جالب‌تر است. می‌خواهیم Rust این برنامه را به این دلیل رد کند: وقتی می‌خواهیم برای push یک ارجاع تغییرپذیر به data بگیریم، یک ارجاع مشترک زندهٔ x به یکی از فرزندان data داریم. این کار یک ارجاع تغییرپذیر alias شده ایجاد می‌کند که قاعدهٔ دوم ارجاع‌ها را نقض می‌کند.

    با این حال Rust به‌هیچ وجه این‌گونه استدلال نمی‌کند که این برنامه بد است. Rust نمی‌فهمد که x ارجاعی به یک زیرمسیر از data است. اصلاً Vec را نمی‌فهمد. چیزی که می‌بیند این است که x برای چاپ شدن باید تا 'b زنده بماند. امضای Index::index در ادامه می‌خواهد که ارجاعی که به data می‌گیریم باید تا 'b دوام بیاورد. وقتی می‌خواهیم push را فراخوانی کنیم، می‌بیند که می‌خواهیم یک &'c mut data بسازیم. Rust می‌داند که 'c درون 'b قرار دارد و برنامهٔ ما را رد می‌کند، چون &'b data هنوز باید زنده باشد!

    در اینجا می‌بینیم که سیستم طول عمر بسیار درشت‌دانه‌تر از معناشناسی ارجاعی است که واقعاً می‌خواهیم حفظ کنیم. در بیشتر موارد، این کاملاً اشکالی ندارد، چون مانع می‌شود تمام روز را صرف توضیح دادن برنامه‌مان به کامپایلر کنیم. با این حال، این یعنی چندین برنامه که نسبت به معناشناسی واقعی Rust کاملاً درست‌اند رد می‌شوند، چون طول عمرها بیش از حد ساده‌لوح‌اند.

    ناحیه‌ای که یک طول عمر پوشش می‌دهد

    یک ارجاع (که گاهی قرض (borrow) نامیده می‌شود) از جایی که ساخته می‌شود تا آخرین استفاده‌اش زنده است. مقدار قرض‌گرفته‌شده فقط باید بیشتر از قرض‌هایی عمر کند که زنده‌اند. این ساده به نظر می‌رسد، اما چند ظرافت دارد.

    قطعه کد زیر کامپایل می‌شود، چون پس از چاپ x دیگر به آن نیازی نیست، پس مهم نیست که معلق (dangling) یا alias شده باشد (هرچند متغیر x از نظر فنی تا انتهای حوزه وجود دارد).

    let mut data = vec![1, 2, 3];
let x = &data[0];
println!("{}", x);
// This is OK, x is no longer needed
data.push(4);

    با این حال، اگر مقدار نابودگر داشته باشد، نابودگر در پایان حوزه اجرا می‌شود. و اجرای نابودگر یک استفاده به حساب می‌آید ‒ آشکارا آخرین استفاده. بنابراین این یکی کامپایل نمی‌شود.

    #[derive(Debug)]
struct X<'a>(&'a i32);

impl Drop for X<'_> {
    fn drop(&mut self) {}
}

let mut data = vec![1, 2, 3];
let x = X(&data[0]);
println!("{:?}", x);
data.push(4);
// Here, the destructor is run and therefore this'll fail to compile.

    یک راه برای متقاعد کردن کامپایلر که x دیگر معتبر نیست، استفاده از drop(x) پیش از data.push(4) است.

    علاوه بر این، ممکن است چندین آخرین استفادهٔ ممکن از قرض وجود داشته باشد، برای مثال در هر شاخهٔ یک شرط.

    fn some_condition() -> bool { true }
let mut data = vec![1, 2, 3];
let x = &data[0];

if some_condition() {
    println!("{}", x); // This is the last use of `x` in this branch
    data.push(4);      // So we can push here
} else {
    // There's no use of `x` in here, so effectively the last use is the
    // creation of x at the top of the example.
    data.push(5);
}

    و یک طول عمر می‌تواند یک وقفه داشته باشد. یا می‌توانید آن را دو قرض متمایز ببینید که فقط به یک متغیر محلی یکسان گره خورده‌اند. این اغلب پیرامون حلقه‌ها رخ می‌دهد (نوشتن مقدار جدید یک متغیر در انتهای حلقه و استفاده از آن برای آخرین بار در ابتدای تکرار بعدی).

    let mut data = vec![1, 2, 3];
// This mut allows us to change where the reference points to
let mut x = &data[0];

println!("{}", x); // Last use of this borrow
data.push(4);
x = &data[3]; // We start a new borrow here
println!("{}", x);

    از نظر تاریخی، Rust قرض را تا پایان حوزه زنده نگه می‌داشت، پس این مثال‌ها ممکن است با کامپایلرهای قدیمی‌تر کامپایل نشوند. همچنین هنوز چند حالت مرزی وجود دارد که Rust نمی‌تواند بخش زندهٔ قرض را به‌درستی کوتاه کند و حتی وقتی به نظر می‌رسد باید کامپایل شود، کامپایل نمی‌شود. این‌ها با گذر زمان حل خواهند شد.
