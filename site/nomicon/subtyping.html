راست‌نومیکونThe Rustonomicon

    زیرنوع‌سازی و وردایی

    Rust از طول عمرها برای ردیابی روابط میان قرض‌گیری و مالکیت استفاده می‌کند. با این حال، پیاده‌سازی ساده‌لوحانهٔ طول عمرها یا بیش از حد محدودکننده خواهد بود یا اجازهٔ رفتار تعریف‌نشده را می‌دهد.

    برای اینکه استفادهٔ انعطاف‌پذیر از طول عمرها ممکن شود و در عین حال از سوءاستفاده از آن‌ها جلوگیری شود، Rust از زیرنوع‌سازی (subtyping) و وردایی (variance) استفاده می‌کند.

    بیایید با یک مثال شروع کنیم.

    // Note: debug expects two parameters with the *same* lifetime
fn debug<'a>(a: &'a str, b: &'a str) {
    println!("a = {a:?} b = {b:?}");
}

fn main() {
    let hello: &'static str = "hello";
    {
        let world = String::from("world");
        let world = &world; // 'world has a shorter lifetime than 'static
        debug(hello, world);
    }
}

    در یک پیاده‌سازی محافظه‌کارانهٔ طول عمرها، چون hello و world طول عمرهای متفاوتی دارند، ممکن است خطای زیر را ببینیم:

    error[E0308]: mismatched types
 --> src/main.rs:10:16
   |
10 |         debug(hello, world);
   |                      ^
   |                      |
   |                      expected `&'static str`, found struct `&'world str`

    این نسبتاً ناخوشایند خواهد بود. در این مورد، چیزی که می‌خواهیم این است که هر نوعی را بپذیریم که دست‌کم به اندازهٔ 'world عمر می‌کند. بیایید زیرنوع‌سازی را با طول عمرهایمان امتحان کنیم.

    زیرنوع‌سازی

    زیرنوع‌سازی ایده‌ای است که طبق آن یک نوع می‌تواند به‌جای نوع دیگر به کار رود.

    فرض کنیم Sub زیرنوعی از Super است (در سراسر این فصل از نماد Sub <: Super استفاده خواهیم کرد).

    این به ما می‌گوید که مجموعهٔ الزاماتی که Super تعریف می‌کند به‌طور کامل توسط Sub برآورده می‌شود. Sub ممکن است الزامات بیشتری هم داشته باشد.

    اکنون، برای اینکه بتوانیم زیرنوع‌سازی را با طول عمرها به کار ببریم، باید الزام یک طول عمر را تعریف کنیم:

    'a یک ناحیه از کد را تعریف می‌کند.

    حالا که مجموعهٔ مشخصی از الزامات برای طول عمرها داریم، می‌توانیم تعریف کنیم که آن‌ها چگونه به یکدیگر مربوط می‌شوند:

    'long <: 'short اگر و فقط اگر 'long ناحیه‌ای از کد را تعریف کند که 'short را به‌طور کامل در بر می‌گیرد.

    'long ممکن است ناحیه‌ای بزرگ‌تر از 'short تعریف کند، اما این هنوز با تعریف ما سازگار است.

    همان‌طور که در ادامهٔ این فصل خواهیم دید، زیرنوع‌سازی بسیار پیچیده‌تر و ظریف‌تر از این است، اما این قاعدهٔ ساده شهودی بسیار خوب برای ۹۹٪ موارد است. و مگر اینکه کد ناایمن بنویسید، کامپایلر همهٔ حالت‌های خاص را خودکار برای شما مدیریت می‌کند.

    اما اینجا Rustonomicon است. ما داریم کد ناایمن می‌نویسیم، پس باید بفهمیم این چیزها واقعاً چگونه کار می‌کنند و چگونه می‌توانیم آن‌ها را خراب کنیم.

    با بازگشت به مثال بالا، می‌توانیم بگوییم 'static <: 'world. فعلاً بیایید این ایده را هم بپذیریم که زیرنوع‌های طول عمرها می‌توانند از طریق ارجاع‌ها منتقل شوند (توضیح بیشتر در وردایی)، مثلاً &'static str زیرنوعی از &'world str است، پس می‌توانیم &'static str را به یک &'world str «تنزل» دهیم. با این کار، مثال بالا کامپایل می‌شود:

    fn debug<'a>(a: &'a str, b: &'a str) {
    println!("a = {a:?} b = {b:?}");
}

fn main() {
    let hello: &'static str = "hello";
    {
        let world = String::from("world");
        let world = &world; // 'world has a shorter lifetime than 'static
        debug(hello, world); // hello silently downgrades from `&'static str` into `&'world str`
    }
}

    وردایی

    در بالا از این واقعیت چشم‌پوشی کردیم که 'static <: 'b نتیجه می‌دهد &'static T <: &'b T. این از ویژگی‌ای استفاده می‌کند که با نام وردایی (variance) شناخته می‌شود. اما همیشه به‌سادگی این مثال نیست. برای فهمیدن آن، بیایید این مثال را کمی گسترش دهیم:

    fn assign<T>(input: &mut T, val: T) {
    *input = val;
}

fn main() {
    let mut hello: &'static str = "hello";
    {
        let world = String::from("world");
        assign(&mut hello, &world);
    }
    println!("{hello}"); // use after free 😿
}

    در assign، ارجاع hello را طوری تنظیم می‌کنیم که به world اشاره کند. اما سپس world از حوزه خارج می‌شود، پیش از آنکه hello بعداً در println! استفاده شود.

    این یک باگ کلاسیک use-after-free است!

    اولین غریزهٔ ما شاید مقصر دانستن پیاده‌سازی assign باشد، اما واقعاً هیچ ایرادی اینجا وجود ندارد. جای تعجب نیست که بخواهیم یک T را در یک T بریزیم.

    مشکل این است که نمی‌توانیم فرض کنیم &'static str هنوز هم می‌تواند به &'world str تنزل یابد تا T را برآورده کند، آن هم وقتی پشت یک ارجاع &mut قرار گرفته است. این یعنی &mut &'static str نمی‌تواند زیرنوعی از &mut &'world str باشد، حتی اگر 'static زیرنوعی از 'world باشد.

    وردایی مفهومی است که Rust قرض می‌گیرد تا روابط مربوط به زیرنوع‌ها را از طریق پارامترهای جنریک‌شان تعریف کند.

    نکته: برای سهولت، یک نوع جنریک F<T> تعریف می‌کنیم تا بتوانیم به‌راحتی دربارهٔ T صحبت کنیم. امیدواریم در متن روشن باشد.

    وردایی نوع F این است که زیرنوع‌سازیِ ورودی‌هایش چگونه روی زیرنوع‌سازیِ خروجی‌هایش اثر می‌گذارد. در Rust سه نوع وردایی وجود دارد. با فرض دو نوع Sub و Super که در آن Sub زیرنوعی از Super است:

    • F هم‌وردا (covariant) است اگر F<Sub> زیرنوعی از F<Super> باشد (ویژگی زیرنوع بودن منتقل می‌شود)
    • F پادوردا (contravariant) است اگر F<Super> زیرنوعی از F<Sub> باشد (ویژگی زیرنوع بودن «وارونه» می‌شود)
    • در غیر این صورت F ناوردا (invariant) است (هیچ رابطهٔ زیرنوعی وجود ندارد)

    اگر از مثال‌های بالا به یاد داشته باشیم، می‌توانستیم &'a T را در صورتی که 'a <: 'b باشد زیرنوعی از &'b T بدانیم، بنابراین می‌توانیم بگوییم &'a T نسبت به 'a هم‌وردا است.

    همچنین دیدیم که نمی‌توانستیم &mut &'a T را زیرنوعی از &mut &'b T بدانیم، بنابراین می‌توانیم بگوییم &mut T نسبت به T ناوردا است.

    در اینجا جدولی از چند نوع جنریک دیگر و وردایی‌های آن‌ها آمده است:

    ’aTU
    &'a T هم‌ورداهم‌وردا
    &'a mut Tهم‌ورداناوردا
    Box<T>هم‌وردا
    Vec<T>هم‌وردا
    UnsafeCell<T>ناوردا
    Cell<T>ناوردا
    fn(T) -> Uپادورداهم‌وردا
    *const Tهم‌وردا
    *mut Tناوردا

    برخی از این‌ها را می‌توان به‌سادگی در ارتباط با بقیه توضیح داد:

    • Vec<T> و همهٔ اشاره‌گرها و مجموعه‌های مالک دیگر از همان منطق Box<T> پیروی می‌کنند
    • Cell<T> و همهٔ نوع‌های تغییرپذیری درونی دیگر از همان منطق UnsafeCell<T> پیروی می‌کنند
    • تغییرپذیری درونیِ UnsafeCell<T> همان ویژگی‌های وردایی &mut T را به آن می‌دهد
    • *const T از منطق &T پیروی می‌کند
    • *mut T از منطق &mut T (یا UnsafeCell<T>) پیروی می‌کند

    برای نوع‌های بیشتر، به بخش «وردایی» در مرجع نگاه کنید.

    نکته: تنها منبع پادوردایی در زبان، آرگومان‌های یک تابع است، که دلیل اینکه در عمل چندان پیش نمی‌آید همین است. به کار انداختن پادوردایی شامل برنامه‌نویسی مرتبهٔ بالاتر با اشاره‌گرهای تابع است که ارجاع‌هایی با طول عمرهای مشخص می‌گیرند (در مقابل حالت معمول «هر طول عمری»، که به طول عمرهای مرتبهٔ بالاتر می‌رسد و مستقل از زیرنوع‌سازی کار می‌کند).

    اکنون که درک رسمی‌تری از وردایی داریم، بیایید چند مثال دیگر را با جزئیات بیشتری مرور کنیم.

    fn assign<T>(input: &mut T, val: T) {
    *input = val;
}

fn main() {
    let mut hello: &'static str = "hello";
    {
        let world = String::from("world");
        assign(&mut hello, &world);
    }
    println!("{hello}");
}

    و وقتی این را اجرا کنیم چه می‌گیریم؟

    error[E0597]: `world` does not live long enough
  --> src/main.rs:9:28
   |
6  |     let mut hello: &'static str = "hello";
   |                    ------------ type annotation requires that `world` is borrowed for `'static`
...
9  |         assign(&mut hello, &world);
   |                            ^^^^^^ borrowed value does not live long enough
10 |     }
   |     - `world` dropped here while still borrowed

    خوب است، کامپایل نمی‌شود! بیایید جزئیات آنچه اینجا اتفاق می‌افتد را بررسی کنیم.

    ابتدا به تابع assign نگاه می‌کنیم:

    fn assign<T>(input: &mut T, val: T) {
    *input = val;
}

    تنها کاری که می‌کند این است که یک ارجاع تغییرپذیر و یک مقدار می‌گیرد و مقدار مرجع را با آن بازنویسی می‌کند. نکتهٔ مهم دربارهٔ این تابع این است که یک محدودیت برابری نوع ایجاد می‌کند. در امضایش به‌روشنی می‌گوید که مرجع و مقدار باید دقیقاً همان نوع باشند.

    در همین حال، در فراخواننده &mut &'static str و &'world str را می‌دهیم.

    از آنجا که &mut T نسبت به T ناوردا است، کامپایلر نتیجه می‌گیرد که نمی‌تواند هیچ زیرنوع‌سازی‌ای را روی آرگومان اول اعمال کند، و بنابراین T باید دقیقاً &'static str باشد.

    این برخلاف حالت &T است:

    fn debug<T: std::fmt::Debug>(a: T, b: T) {
    println!("a = {a:?} b = {b:?}");
}

    که در آن نیز به همین ترتیب a و b باید نوع یکسان T را داشته باشند. اما چون &'a T نسبت به 'a هم‌وردا است، مجاز به انجام زیرنوع‌سازی هستیم. پس کامپایلر تصمیم می‌گیرد که &'static str فقط و فقط وقتی می‌تواند به &'b str تبدیل شود که &'static str زیرنوعی از &'b str باشد، که در صورتی برقرار است که 'static <: 'b. این درست است، پس کامپایلر با خوشحالی به کامپایل این کد ادامه می‌دهد.

    معلوم می‌شود استدلال اینکه چرا هم‌وردا بودن Box (و Vec، HashMap و غیره) اشکالی ندارد کاملاً شبیه استدلال اینکه چرا هم‌وردا بودن طول عمرها اشکالی ندارد است: به محض اینکه سعی کنید آن‌ها را درون چیزی مثل یک ارجاع تغییرپذیر بگذارید، ناوردایی را به ارث می‌برند و از انجام هر کار بدی بازداشته می‌شوید.

    با این حال Box تمرکز بر جنبهٔ «با مقدار» (by-value) ارجاع‌ها را که تا حدی از آن چشم‌پوشی کردیم آسان‌تر می‌کند.

    برخلاف بسیاری از زبان‌ها که اجازه می‌دهند مقادیر همیشه آزادانه alias شوند، Rust قاعدهٔ بسیار سخت‌گیرانه‌ای دارد: اگر مجاز باشید مقداری را تغییر دهید یا جابه‌جا کنید، تضمین می‌شود که تنها کسی هستید که به آن دسترسی دارد.

    کد زیر را در نظر بگیرید:

    let hello: Box<&'static str> = Box::new("hello");

let mut world: Box<&'b str>;
world = hello;

    اینکه فراموش کرده‌ایم hello برای 'static زنده بود اصلاً مشکلی ندارد، زیرا به محض اینکه hello را به متغیری منتقل کردیم که فقط می‌دانست برای 'b زنده است، تنها چیزی را در جهان که به یاد داشت بیشتر عمر می‌کند نابود کردیم!

    فقط یک چیز برای توضیح باقی مانده است: اشاره‌گرهای تابع.

    برای اینکه ببینیم چرا fn(T) -> U باید نسبت به U هم‌وردا باشد، امضای زیر را در نظر بگیرید:

    fn get_str() -> &'a str;

    این تابع ادعا می‌کند یک str تولید می‌کند که به یک طول عمر 'a محدود است. به همین دلیل، کاملاً معتبر است که به‌جای آن تابعی با امضای زیر ارائه شود:

    fn get_static() -> &'static str;

    پس وقتی تابع فراخوانی می‌شود، تنها چیزی که فراخواننده‌اش انتظار دارد یک &str است که دست‌کم به اندازهٔ طول عمر 'a عمر کند، و مهم نیست که مقدار واقعاً بیشتر عمر کند.

    با این حال، همین منطق دربارهٔ آرگومان‌ها صدق نمی‌کند. سعی کنید این را برآورده کنید:

    fn store_ref(&'a str);

    با این:

    fn store_static(&'static str);

    تابع اول می‌تواند هر ارجاع رشته‌ای را بپذیرد به شرط آنکه دست‌کم برای 'a عمر کند، اما تابع دوم نمی‌تواند ارجاع رشته‌ای را بپذیرد که برای مدتی کمتر از 'static عمر می‌کند، که باعث تعارض می‌شود. هم‌وردایی اینجا کار نمی‌کند. اما اگر آن را برعکس کنیم، در واقع کار می‌کند! اگر به تابعی نیاز داریم که بتواند &'static str را مدیریت کند، تابعی که بتواند ارجاع با هر طول عمری را مدیریت کند قطعاً درست کار خواهد کرد.

    بیایید این را در عمل ببینیم

    use std::cell::RefCell;
thread_local! {
    pub static StaticVecs: RefCell<Vec<&'static str>> = RefCell::new(Vec::new());
}

/// saves the input given into a thread local `Vec<&'static str>`
fn store(input: &'static str) {
    StaticVecs.with_borrow_mut(|v| v.push(input));
}

/// Calls the function with it's input (must have the same lifetime!)
fn demo<'a>(input: &'a str, f: fn(&'a str)) {
    f(input);
}

fn main() {
    demo("hello", store); // "hello" is 'static. Can call `store` fine

    {
        let smuggle = String::from("smuggle");

        // `&smuggle` is not static. If we were to call `store` with `&smuggle`,
        // we would have pushed an invalid lifetime into the `StaticVecs`.
        // Therefore, `fn(&'static str)` cannot be a subtype of `fn(&'a str)`
        demo(&smuggle, store);
    }

    // use after free 😿
    StaticVecs.with_borrow(|v| println!("{v:?}"));
}

    و به همین دلیل است که نوع‌های تابع، برخلاف هر چیز دیگری در زبان، نسبت به آرگومان‌هایشان پادوردا هستند.

    اکنون، همهٔ این‌ها برای نوع‌هایی که کتابخانهٔ استاندارد فراهم می‌کند خوب است، اما وردایی برای نوع‌هایی که شما تعریف می‌کنید چگونه تعیین می‌شود؟ به‌طور غیررسمی، یک ساختار وردایی فیلدهایش را به ارث می‌برد. اگر ساختار MyType یک آرگومان جنریک A داشته باشد که در فیلد a استفاده شده است، آنگاه وردایی MyType نسبت به A دقیقاً همان وردایی a نسبت به A است.

    با این حال اگر A در چند فیلد استفاده شده باشد:

    • اگر همهٔ استفاده‌ها از A هم‌وردا باشند، MyType نسبت به A هم‌وردا است
    • اگر همهٔ استفاده‌ها از A پادوردا باشند، MyType نسبت به A پادوردا است
    • در غیر این صورت، MyType نسبت به A ناوردا است
    use std::cell::Cell;

struct MyType<'a, 'b, A: 'a, B: 'b, C, D, E, F, G, H, In, Out, Mixed> {
    a: &'a A,     // covariant over 'a and A
    b: &'b mut B, // covariant over 'b and invariant over B

    c: *const C,  // covariant over C
    d: *mut D,    // invariant over D

    e: E,         // covariant over E
    f: Vec<F>,    // covariant over F
    g: Cell<G>,   // invariant over G

    h1: H,        // would also be covariant over H except...
    h2: Cell<H>,  // invariant over H, because invariance wins all conflicts

    i: fn(In) -> Out,       // contravariant over In, covariant over Out

    k1: fn(Mixed) -> usize, // would be contravariant over Mixed except..
    k2: Mixed,              // invariant over Mixed, because invariance wins all conflicts
}
