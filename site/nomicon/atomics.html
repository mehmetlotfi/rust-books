    Atomics

    Rust به‌صراحت و بی‌پرده مدل حافظه‌ی atomicها را از C++20 به ارث برده است. دلیلش این نیست که این مدل به‌طور خاص عالی یا ساده باشد. در واقع این مدل کاملاً پیچیده است و چند نقص شناخته‌شده دارد. بلکه این انتخاب یک مصالحه‌ی عمل‌گرایانه است، چون همه در مدل‌سازی atomicها نسبتاً ضعیف‌اند. دست‌کم می‌توانیم از ابزارها و پژوهش‌های موجود پیرامون مدل حافظه‌ی C/C++ بهره ببریم. (اغلب این مدل را با نام «C/C++11» یا فقط «C11» می‌شنوید. C صرفاً مدل حافظه‌ی C++ را کپی کرده است؛ و C++11 نخستین نسخه‌ی این مدل بوده، هرچند از آن زمان تاکنون چند اصلاح اشکال دریافت کرده است.)

    تلاش برای توضیح کامل این مدل در این کتاب تقریباً بی‌فایده است. این مدل بر پایهٔ گراف‌های علیتِ جنون‌آمیزی تعریف شده که فهم کاربردی آن‌ها به یک کتاب کامل نیاز دارد. اگر همهٔ ریزه‌کاری‌ها را می‌خواهید، باید به مشخصات C++ مراجعه کنید. با این حال، ما سعی می‌کنیم مبانی و برخی از مشکلاتی را که توسعه‌دهندگان Rust با آن‌ها روبه‌رو می‌شوند پوشش دهیم.

    مدل حافظه‌ی C++ در اصل تلاشی است برای پرکردن شکاف میان معناشناسی‌ای که ما می‌خواهیم، بهینه‌سازی‌هایی که کامپایلرها می‌خواهند، و هرج‌ومرج ناسازگاری که سخت‌افزار ما می‌خواهد. ما دوست داریم فقط برنامه بنویسیم و آن‌ها دقیقاً همان کاری را بکنند که گفته‌ایم، البته سریع. عالی نمی‌شد؟

    جابه‌جایی توسط کامپایلر (Compiler Reordering)

    کامپایلرها اساساً می‌خواهند بتوانند انواع تبدیل‌های پیچیده را برای کاهش وابستگی‌های داده و حذف کد مرده انجام دهند. به‌ویژه ممکن است ترتیب واقعی رویدادها را به‌کلی تغییر دهند، یا کاری کنند که برخی رویدادها هرگز رخ ندهند! اگر چیزی شبیه این بنویسیم:

    x = 1;
y = 3;
x = 2;

    کامپایلر ممکن است نتیجه بگیرد که بهتر است برنامه‌ی شما این کار را انجام دهد:

    x = 2;
y = 3;

    این کار ترتیب رویدادها را وارونه کرده و یک رویداد را به‌کلی حذف کرده است. از دید یک برنامه‌ی تک‌نخی این موضوع کاملاً غیرقابل مشاهده است: پس از اجرای همه‌ی دستورها دقیقاً در همان وضعیت قرار داریم. اما اگر برنامه‌ی ما چندنخی باشد، ممکن است به این تکیه کرده باشیم که x واقعاً پیش از انتساب y برابر 1 شده باشد. ما می‌خواهیم کامپایلر بتواند این نوع بهینه‌سازی‌ها را انجام دهد، زیرا می‌توانند عملکرد را به‌طور جدی بهبود دهند. از سوی دیگر، می‌خواهیم بتوانیم به این هم اعتماد کنیم که برنامه‌مان همان کاری را می‌کند که گفته‌ایم.

    جابه‌جایی توسط سخت‌افزار (Hardware Reordering)

    از طرف دیگر، حتی اگر کامپایلر دقیقاً بفهمد ما چه می‌خواهیم و به خواسته‌هایمان احترام بگذارد، ممکن است سخت‌افزار ما را به دردسر بیندازد. دردسر از سوی CPUها و به شکل سلسله‌مراتب حافظه می‌آید. بله، جایی در سخت‌افزار شما یک فضای حافظه‌ی مشترک سراسری وجود دارد، اما از دید هر هسته‌ی CPU این حافظه بسیار دور و بسیار کند است. هر CPU ترجیح می‌دهد با کش محلی خودش از داده کار کند و تنها وقتی آن حافظه را در کش ندارد، رنجِ صحبت با حافظه‌ی مشترک را به جان بخرد.

    به هر حال، هدف اصلی کش همین است، درست نیست؟ اگر هر خواندن از کش مجبور بود به حافظه‌ی مشترک برگردد تا دوباره بررسی کند که چیزی تغییر نکرده، دیگر کش چه فایده‌ای داشت؟ نتیجه این است که سخت‌افزار تضمین نمی‌کند رویدادهایی که در یک نخ به ترتیبی رخ می‌دهند، در نخ دیگر هم با همان ترتیب دیده شوند. برای تضمین این موضوع باید دستورهای ویژه‌ای به CPU بدهیم که به آن می‌گویند کمی کمتر هوشمند باشد.

    برای مثال، فرض کنید کامپایلر را قانع کنیم این منطق را تولید کند:

    initial state: x = 0, y = 1

THREAD 1        THREAD 2
y = 3;          if x == 1 {
x = 1;              y *= 2;
                }

    در حالت ایده‌آل این برنامه ۲ وضعیت نهایی ممکن دارد:

    • y = 3: (نخ ۲ بررسی را پیش از تکمیل نخ ۱ انجام داده است)
    • y = 6: (نخ ۲ بررسی را پس از تکمیل نخ ۱ انجام داده است)

    اما یک وضعیت سوم هم هست که سخت‌افزار امکانش را فراهم می‌کند:

    • y = 2: (نخ ۲ مقدار x = 1 را دیده، اما y = 3 را ندیده، و سپس y = 3 را بازنویسی کرده است)

    شایان ذکر است که انواع مختلف CPU تضمین‌های متفاوتی ارائه می‌دهند. معمول است که سخت‌افزار را به دو دسته تقسیم کنند: با ترتیب قوی (strongly-ordered) و با ترتیب ضعیف (weakly-ordered). مهم‌ترین مثال این است که x86/64 تضمین‌های ترتیب قوی می‌دهد، در حالی که ARM تضمین‌های ترتیب ضعیف فراهم می‌کند. این موضوع دو پیامد برای برنامه‌نویسی همروند دارد:

    • درخواست تضمین‌های قوی‌تر روی سخت‌افزارهای با ترتیب قوی ممکن است ارزان یا حتی رایگان باشد، چون این سخت‌افزارها خودشان به‌طور بی‌قیدوشرط تضمین‌های قوی می‌دهند. تضمین‌های ضعیف‌تر فقط روی سخت‌افزارهای با ترتیب ضعیف ممکن است به بهبود عملکرد بینجامند.

    • درخواست تضمین‌هایی که بیش از حد ضعیف‌اند روی سخت‌افزارهای با ترتیب قوی احتمال بیشتری دارد که «اتفاقاً» کار کند، هرچند برنامه‌ی شما به‌طور دقیق نادرست است. در صورت امکان، الگوریتم‌های همروند باید روی سخت‌افزارهای با ترتیب ضعیف آزمایش شوند.

    دسترسی‌های داده (Data Accesses)

    مدل حافظه‌ی C++ تلاش می‌کند با اجازه دادن به ما برای صحبت درباره‌ی علیت برنامه، این شکاف را پر کند. معمولاً این کار با برقراری رابطه‌ی happens before (رخ‌دادن پیش از) میان بخش‌های برنامه و نخ‌هایی که آن‌ها را اجرا می‌کنند انجام می‌شود. این موضوع به سخت‌افزار و کامپایلر اجازه می‌دهد جایی که رابطه‌ی happens-before سخت‌گیرانه‌ای برقرار نشده، برنامه را با شدت بیشتری بهینه کنند، اما آن‌ها را وادار می‌کند جایی که چنین رابطه‌ای برقرار شده با دقت بیشتری عمل کنند. راهی که این روابط را از طریق آن اعلام می‌کنیم، دسترسی‌های داده (data accesses) و دسترسی‌های atomic است.

    دسترسی‌های داده نان و آب دنیای برنامه‌نویسی‌اند. آن‌ها اساساً همگام‌سازی‌نشده‌اند و کامپایلرها آزادند به‌شدت بهینه‌شان کنند. به‌ویژه، کامپایلر مجاز است با این فرض که برنامه تک‌نخی است، دسترسی‌های داده را جابه‌جا کند. سخت‌افزار هم آزاد است تغییرات اعمال‌شده در دسترسی‌های داده را به‌صورت تنبل و ناسازگار هر قدر که بخواهد به نخ‌های دیگر منتشر کند. از همه مهم‌تر، data raceها از طریق دسترسی‌های داده رخ می‌دهند. دسترسی‌های داده برای سخت‌افزار و کامپایلر بسیار مناسب‌اند، اما همان‌طور که دیدیم، برای نوشتن کد همگام‌سازی‌شده معناشناسی افتضاحی دارند. در واقع این هم کم‌گفتن است.

    نوشتن کد همگام‌سازی‌شده‌ی صحیح فقط با دسترسی‌های داده به معنای واقعی کلمه غیرممکن است.

    دسترسی‌های atomic راهی است که به سخت‌افزار و کامپایلر می‌گوییم برنامه‌ی ما چندنخی است. هر دسترسی atomic را می‌توان با یک ترتیب (ordering) علامت‌گذاری کرد که مشخص می‌کند چه نوع رابطه‌ای با دسترسی‌های دیگر برقرار می‌کند. در عمل، این کار به این برمی‌گردد که به کامپایلر و سخت‌افزار بگوییم چه کارهایی را نمی‌توانند انجام دهند. برای کامپایلر، این عمدتاً حول جابه‌جایی دستورها می‌چرخد. برای سخت‌افزار، عمدتاً حول نحوه‌ی انتشار نوشتن‌ها به نخ‌های دیگر. مجموعه‌ی ترتیب‌هایی که Rust عرضه می‌کند این‌هاست:

    • سازگار ترتیبی (Sequentially Consistent یا SeqCst)
    • Release
    • Acquire
    • Relaxed

    (نکته: ما ترتیب consume در C++ را عمداً عرضه نمی‌کنیم)

    Sequentially Consistent (سازگار ترتیبی)

    Sequentially Consistent قوی‌ترین ترتیب است و محدودیت‌های همه‌ی ترتیب‌های دیگر را نیز در بر دارد. به‌طور شهودی، یک عملیات sequentially consistent قابل جابه‌جایی نیست: همه‌ی دسترسی‌های یک نخ که پیش از یک دسترسی SeqCst و پس از آن رخ می‌دهند، پیش و پس از آن باقی می‌مانند. برنامه‌ای عاری از data race که فقط از atomicهای sequentially consistent و دسترسی‌های داده استفاده کند، ویژگی بسیار خوبی دارد: یک اجرای سراسری واحد از دستورهای برنامه وجود دارد که همه‌ی نخ‌ها بر سر آن توافق دارند. استدلال درباره‌ی این اجرا هم به‌ویژه ساده است: صرفاً درهم‌آمیختگی اجراهای جداگانه‌ی هر نخ است. اگر از ترتیب‌های atomic ضعیف‌تر استفاده کنید، این ویژگی برقرار نیست.

    دوستدار توسعه‌دهنده بودن نسبیِ sequential consistency رایگان نیست. حتی روی پلتفرم‌های با ترتیب قوی، sequential consistency مستلزم تولید memory fenceهاست.

    در عمل، sequential consistency به‌ندرت برای درستی برنامه ضروری است. با این حال، اگر به ترتیب‌های حافظه‌ی دیگر اطمینان ندارید، sequential consistency قطعاً انتخاب درستی است. اینکه برنامه‌تان کمی کندتر از حد لازم اجرا شود قطعاً بهتر از اجرای نادرست آن است! همچنین بعداً تنزل دادن عملیات atomic به سازگاری ضعیف‌تر از نظر مکانیکی بدیهی است. فقط SeqCst را به Relaxed تغییر دهید و کار تمام است! البته اثبات درست بودن این تبدیل موضوع کاملاً دیگری است.

    Acquire-Release (کسب و رهاسازی)

    Acquire و Release عمدتاً برای این طراحی شده‌اند که جفت شوند. نام‌هایشان به کاربردشان اشاره دارد: برای گرفتن و رها کردن قفل‌ها و اطمینان از اینکه بخش‌های بحرانی هم‌پوشانی ندارند، کاملاً مناسب‌اند.

    به‌طور شهودی، یک دسترسی acquire تضمین می‌کند که هر دسترسی پس از آن، پس از آن باقی بماند. اما عملیاتی که پیش از acquire رخ می‌دهند آزادند طوری جابه‌جا شوند که پس از آن رخ دهند. به همین ترتیب، یک دسترسی release تضمین می‌کند که هر دسترسی پیش از آن، پیش از آن باقی بماند. اما عملیاتی که پس از release رخ می‌دهند آزادند طوری جابه‌جا شوند که پیش از آن رخ دهند.

    وقتی نخ A یک مکان از حافظه را release می‌کند و سپس نخ B همان مکان از حافظه را acquire می‌کند، علیت برقرار می‌شود. هر نوشتنی (از جمله نوشتن‌های غیر atomic و atomic از نوع relaxed) که پیش از release نخ A رخ داده باشد، پس از acquire نخ B توسط B مشاهده خواهد شد. اما هیچ علیتی با نخ‌های دیگر برقرار نمی‌شود. به همین ترتیب، اگر A و B به مکان‌های متفاوتی از حافظه دسترسی داشته باشند هم هیچ علیتی برقرار نمی‌شود.

    بنابراین استفاده‌ی پایه از release-acquire ساده است: برای شروع بخش بحرانی یک مکان از حافظه را acquire می‌کنید و سپس برای پایان دادن به آن، آن مکان را release می‌کنید. برای مثال، یک spinlock ساده ممکن است چنین به نظر برسد:

    use std::sync::Arc;
use std::sync::atomic::{AtomicBool, Ordering};
use std::thread;

fn main() {
    let lock = Arc::new(AtomicBool::new(false)); // value answers "am I locked?"

    // ... distribute lock to threads somehow ...

    // Try to acquire the lock by setting it to true
    while lock.compare_exchange(false, true, Ordering::Acquire, Ordering::Relaxed).is_err() { }
    // broke out of the loop, so we successfully acquired the lock!

    // ... scary data accesses ...

    // ok we're done, release the lock
    lock.store(false, Ordering::Release);
}

    روی پلتفرم‌های با ترتیب قوی، بیشتر دسترسی‌ها معناشناسی release یا acquire دارند، و در نتیجه release و acquire اغلب کاملاً رایگان‌اند. روی پلتفرم‌های با ترتیب ضعیف چنین نیست.

    Relaxed (آسوده)

    دسترسی‌های relaxed ضعیف‌ترین حالت ممکن‌اند. آن‌ها را می‌توان آزادانه جابه‌جا کرد و هیچ رابطه‌ی happens-before ایجاد نمی‌کنند. با این حال، عملیات relaxed همچنان atomic هستند. یعنی دسترسی داده حساب نمی‌شوند و هر عملیات خواندن-تغییر-نوشتن (read-modify-write) که روی آن‌ها انجام شود به‌صورت atomic رخ می‌دهد. عملیات relaxed برای کارهایی مناسب‌اند که قطعاً می‌خواهید انجام شوند، اما فراتر از آن اهمیت خاصی به آن‌ها نمی‌دهید. برای مثال، اگر از شمارنده برای همگام‌سازی دسترسی‌های دیگر استفاده نمی‌کنید، چند نخ می‌توانند با یک fetch_add از نوع relaxed آن را با خیال راحت افزایش دهند.

    روی پلتفرم‌های با ترتیب قوی، relaxed کردن یک عملیات به‌ندرت سودی دارد، چون این پلتفرم‌ها معمولاً به‌هرحال معناشناسی release-acquire را فراهم می‌کنند. اما عملیات relaxed روی پلتفرم‌های با ترتیب ضعیف می‌توانند ارزان‌تر باشند.
