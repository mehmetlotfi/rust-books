    هم‌نامی (Aliasing)

    پیش از هر چیز، چند هشدار مهم را روشن کنیم:

    • برای سادگی بحث، از گسترده‌ترین تعریف ممکن از هم‌نامی استفاده می‌کنیم. تعریف Rust احتمالاً محدودتر است و تغییرپذیری (mutation) و زنده‌بودن (liveness) را هم در نظر می‌گیرد.

    • فرض می‌کنیم اجرا تک‌نخی و بدون وقفه (interrupt) است. همچنین چیزهایی مانند سخت‌افزار نگاشت‌شده به حافظه را نادیده می‌گیریم. Rust فرض می‌کند این چیزها رخ نمی‌دهند، مگر اینکه خلافش را به آن بگویید. برای جزئیات بیشتر، فصل همروندی را ببینید.

    با این توضیح، تعریف کاری ما این است: متغیرها و اشاره‌گرها اگر به نواحی هم‌پوشان از حافظه ارجاع دهند، با هم هم‌نام (alias) هستند.

    چرا هم‌نامی اهمیت دارد

    پس چرا باید به هم‌نامی اهمیت بدهیم؟

    این تابع ساده را در نظر بگیرید:

    fn compute(input: &u32, output: &mut u32) {
    if *input > 10 {
        *output = 1;
    }
    if *input > 5 {
        *output *= 2;
    }
    // remember that `output` will be `2` if `input > 10`
}

    دوست داریم بتوانیم آن را به تابع زیر بهینه کنیم:

    fn compute(input: &u32, output: &mut u32) {
    let cached_input = *input; // keep `*input` in a register
    if cached_input > 10 {
        // If the input is greater than 10, the previous code would set the output to 1 and then double it,
        // resulting in an output of 2 (because `>10` implies `>5`).
        // Here, we avoid the double assignment and just set it directly to 2.
        *output = 2;
    } else if cached_input > 5 {
        *output *= 2;
    }
}

    در Rust این بهینه‌سازی باید درست (sound) باشد. در تقریباً هر زبان دیگری درست نخواهد بود (مگر با تحلیل سراسری). دلیلش این است که این بهینه‌سازی بر دانستنِ رخ‌ندادنِ هم‌نامی تکیه دارد، در حالی که بیشتر زبان‌ها در این باره نسبتاً آزادانه عمل می‌کنند. به‌طور مشخص باید نگران آرگومان‌های تابعی باشیم که باعث هم‌پوشانی input و output می‌شوند، مانند compute(&x, &mut x).

    با چنین ورودی‌ای ممکن است این اجرا را داشته باشیم:

                        //  input ==  output == 0xabad1dea
                    // *input == *output == 20
if *input > 10 {    // true  (*input == 20)
    *output = 1;    // also overwrites *input, because they are the same
}
if *input > 5 {     // false (*input == 1)
    *output *= 2;
}
                    // *input == *output == 1

    تابع بهینه‌شدهٔ ما برای این ورودی *output == 2 تولید می‌کند، پس درستیِ بهینه‌سازی ما به غیرممکن‌بودن این ورودی وابسته است.

    در Rust می‌دانیم این ورودی باید غیرممکن باشد، چون &mut اجازهٔ هم‌نام‌شدن ندارد. بنابراین می‌توانیم با اطمینان امکان آن را رد کنیم و این بهینه‌سازی را انجام دهیم. در بیشتر زبان‌های دیگر این ورودی کاملاً ممکن است و باید در نظر گرفته شود.

    به همین دلیل تحلیل هم‌نامی (alias analysis) مهم است: به کامپایلر اجازه می‌دهد بهینه‌سازی‌های مفیدی انجام دهد! چند نمونه:

    • نگه‌داشتن مقدارها در ثبات‌ها (register) با اثبات اینکه هیچ اشاره‌گری به حافظهٔ آن مقدار دسترسی ندارد
    • حذف خواندن‌ها با اثبات اینکه از آخرین باری که حافظه‌ای را خوانده‌ایم، در آن نوشته نشده است
    • حذف نوشتن‌ها با اثبات اینکه حافظه‌ای پیش از نوشتنِ بعدی در آن هرگز خوانده نمی‌شود
    • جابه‌جایی یا مرتب‌سازی مجدد خواندن‌ها و نوشتن‌ها با اثبات اینکه به یکدیگر وابسته نیستند

    این بهینه‌سازی‌ها معمولاً درستیِ بهینه‌سازی‌های بزرگ‌تری مانند برداری‌سازی حلقه (loop vectorization)، انتشار ثابت‌ها (constant propagation) و حذف کد مرده (dead code elimination) را هم ثابت می‌کنند.

    در مثال قبل از این واقعیت استفاده کردیم که &mut u32 نمی‌تواند هم‌نام باشد، تا ثابت کنیم نوشتن در *output نمی‌تواند روی *input اثر بگذارد. این کار به ما اجازه می‌دهد *input را در یک ثبات نگه داریم و یک خواندن را حذف کنیم.

    با نگه‌داشتن این مقدار خوانده‌شده، می‌دانستیم نوشتن در شاخهٔ > 10 نمی‌تواند بر اینکه وارد شاخهٔ > 5 شویم اثر بگذارد؛ بنابراین وقتی *input > 10 است، می‌توانیم یک خواندن-تغییر-نوشتن (دو برابر کردن *output) را نیز حذف کنیم.

    نکتهٔ کلیدی دربارهٔ تحلیل هم‌نامی این است که نوشتن‌ها خطر اصلی بهینه‌سازی‌ها هستند. یعنی تنها چیزی که مانع انتقال یک خواندن به هر نقطهٔ دیگر برنامه می‌شود، احتمال جابه‌جایی آن با نوشتنی در همان مکان است.

    برای مثال، در نسخهٔ اصلاح‌شدهٔ زیر از تابعمان نگران هم‌نامی نیستیم، چون تنها نوشتن در *output را به انتهای تابع برده‌ایم. این کار به ما اجازه می‌دهد خواندن‌های *input را که پیش از آن رخ می‌دهند آزادانه جابه‌جا کنیم:

    fn compute(input: &u32, output: &mut u32) {
    let mut temp = *output;
    if *input > 10 {
        temp = 1;
    }
    if *input > 5 {
        temp *= 2;
    }
    *output = temp;
}

    هنوز به تحلیل هم‌نامی تکیه داریم تا فرض کنیم input با temp هم‌نام نیست، اما اثبات آن بسیار ساده‌تر است: مقدار یک متغیر محلی نمی‌تواند توسط چیزهایی که پیش از تعریف آن وجود داشته‌اند هم‌نام شود. این فرضی است که هر زبانی آزادانه می‌پذیرد، و بنابراین این نسخهٔ تابع را در هر زبانی می‌توان به شیوهٔ دلخواه بهینه کرد.

    به همین دلیل تعریفی که Rust از «هم‌نامی» به کار خواهد برد احتمالاً مفهومی از زنده‌بودن و تغییرپذیری را در بر می‌گیرد: اگر هیچ نوشتن واقعی در حافظه رخ نمی‌دهد، در واقع به رخ‌دادن هم‌نامی اهمیتی نمی‌دهیم.

    البته یک مدل کامل هم‌نامی برای Rust باید مواردی مانند فراخوانی تابع‌ها (که ممکن است چیزهایی را که نمی‌بینیم تغییر دهند)، اشاره‌گرهای خام (که به‌خودی‌خود الزامی دربارهٔ هم‌نامی ندارند) و UnsafeCell (که اجازه می‌دهد مرجعِ یک & تغییر کند) را نیز در نظر بگیرد.
