    PhantomData

    هنگام کار با کد unsafe، اغلب ممکن است به وضعیتی برسیم که نوع‌ها یا طول عمرها از نظر منطقی به یک ساختار مرتبط‌اند، اما در واقع بخشی از هیچ فیلدی نیستند. این بیشتر با طول عمرها رخ می‌دهد. برای مثال، Iter برای &'a [T] (تقریباً) به این صورت تعریف می‌شود:

    struct Iter<'a, T: 'a> {
    ptr: *const T,
    end: *const T,
}

    اما از آنجا که 'a در بدنهٔ ساختار استفاده نشده است، بدون کران است. به دلیل مشکلاتی که این وضعیت در گذشته ایجاد کرده است، طول عمرها و نوع‌های بدون کران در تعریف ساختارها ممنوع هستند. بنابراین باید به نحوی در بدنه به این نوع‌ها ارجاع بدهیم. انجام درست این کار برای داشتن وردایی (variance) درست و drop checking درست ضروری است.

    این کار را با PhantomData انجام می‌دهیم که یک نوع نشانگر ویژه است. PhantomData هیچ فضایی اشغال نمی‌کند، اما برای مقاصد تحلیل ایستا فیلدی از نوع داده‌شده را شبیه‌سازی می‌کند. این روش کم‌خطاتر از آن دانسته شد که صراحتاً به سیستم نوع بگوییم چه نوع وردایی‌ای می‌خواهیم، و در عین حال چیزهای مفید دیگری مانند صفت‌های خودکار (auto trait) و اطلاعات موردنیاز drop check را نیز فراهم می‌کند.

    Iter از نظر منطقی شامل تعدادی &'a T است، پس دقیقاً همین را به PhantomData می‌گوییم که شبیه‌سازی کند:

    use std::marker;

struct Iter<'a, T: 'a> {
    ptr: *const T,
    end: *const T,
    _marker: marker::PhantomData<&'a T>,
}

    و تمام. طول عمر کران‌دار خواهد شد و iterator شما نسبت به 'a و T هم‌وردا (covariant) خواهد بود. همه‌چیز به‌درستی کار می‌کند.

    پارامترهای جنریک و drop-checking

    در گذشته یک نکتهٔ دیگر نیز باید در نظر گرفته می‌شد.

    همین مستندات پیش‌تر می‌گفت:

    مثال مهم دیگر Vec است که (تقریباً) به این صورت تعریف می‌شود:

    struct Vec<T> {
    data: *const T, // *const for variance!
    len: usize,
    cap: usize,
}

    برخلاف مثال قبلی، به نظر می‌رسد همه‌چیز دقیقاً همان‌طور است که می‌خواهیم. هر آرگومان جنریک Vec دست‌کم در یک فیلد ظاهر می‌شود. آماده‌ایم!

    نه.

    drop checker با سخاوت تشخیص می‌دهد که Vec<T> مالک هیچ مقداری از نوع T نیست. این به نوبهٔ خود باعث می‌شود نتیجه بگیرد که برای تعیین درستی drop check لازم نیست نگران باشد Vec در نابودگرش (destructor) هیچ T ای را drop کند. این به نوبهٔ خود به افراد اجازه می‌دهد با استفاده از نابودگر Vec ناامنی ایجاد کنند.

    برای اینکه به drop checker بگوییم ما مالک مقادیری از نوع T هستیم و بنابراین ممکن است هنگام drop شدن خودمان برخی T ها را drop کنیم، باید یک PhantomData اضافی اضافه کنیم که دقیقاً همین را بگوید:

    use std::marker;

struct Vec<T> {
    data: *const T, // *const for variance!
    len: usize,
    cap: usize,
    _owns_T: marker::PhantomData<T>,
}

    اما از زمان RFC 1238، این دیگر درست نیست و ضرورتی هم ندارد.

    اگر بنویسید:

    struct Vec<T> {
    data: *const T, // `*const` for variance!
    len: usize,
    cap: usize,
}

#[cfg(any())]
impl<T> Drop for Vec<T> { /* … */ }

    آنگاه وجود آن impl<T> Drop for Vec<T> باعث می‌شود Rust در نظر بگیرد که آن Vec<T> مالک مقادیری از نوع T است (به‌طور دقیق‌تر: ممکن است مقادیری از نوع T را در پیاده‌سازی Drop خود به کار ببرد) و بنابراین Rust اجازه نخواهد داد هنگام drop شدن یک Vec<T> این مقادیر معلق (dangle) باشند.

    وقتی یک نوع از قبل Drop impl دارد، افزودن یک فیلد اضافی _owns_T: PhantomData<T> در نتیجه زائد است و از نظر dropck هیچ کاری انجام نمی‌دهد (همچنان روی وردایی و صفت‌های خودکار اثر می‌گذارد).

    • (یک حالت مرزی پیشرفته: اگر نوعی که PhantomData را در بر دارد اصلاً Drop impl نداشته باشد، اما همچنان drop glue داشته باشد (از طریق داشتن فیلدی دیگر که drop glue دارد)، آنگاه ملاحظات dropck/#[may_dangle] که در اینجا ذکر شد نیز صدق می‌کنند: در این صورت یک فیلد PhantomData<T> الزام می‌کند که هر زمان نوع در بر گیرنده از حوزه خارج می‌شود، T قابل drop شدن باشد).

    اما این وضعیت گاهی می‌تواند به کدی بیش‌ازحد محدودکننده منجر شود. به همین دلیل کتابخانهٔ استاندارد از یک اتریبیوت ناپایدار و unsafe استفاده می‌کند تا دوباره به رفتار drop-checking «بررسی‌نشدهٔ» قدیمی، که همین مستندات دربارهٔ آن هشدار می‌داد، برگردد: اتریبیوت #[may_dangle].

    یک استثنا: حالت ویژهٔ کتابخانهٔ استاندارد و #[may_dangle] ناپایدار آن

    اگر فقط کد کتابخانهٔ خودتان را می‌نویسید می‌توانید از این بخش بگذرید؛ اما اگر کنجکاو هستید که کتابخانهٔ استاندارد با تعریف واقعی Vec چه می‌کند، متوجه می‌شوید که برای سلامت و امنیت همچنان باید از یک فیلد _owns_T: PhantomData<T> استفاده کند.

    برای دیدن دلیل اینجا کلیک کنید

    برای دیدن دلیل اینجا کلیک کنید

    fn main() {
    let mut v: Vec<&str> = Vec::new();
    let s: String = "Short-lived".into();
    v.push(&s);
    drop(s);
} // <- `v` is dropped here

    با تعریف کلاسیک impl<T> Drop for Vec<T> {، کد بالا رد می‌شود.

    در واقع، در این حالت ما یک بردار Vec</* T = */ &'s str> از ارجاع‌هایی با طول عمر 's به strها داریم، اما در حالت let s: String، این رشته پیش از Vec drop می‌شود و در نتیجه تا زمانی که Vec drop می‌شود، 's منقضی شده است و impl<'s> Drop for Vec<&'s str> { به کار می‌رود.

    این یعنی اگر چنین Dropی به کار می‌رفت، با یک طول عمر 's منقضی‌شده یا معلق (dangling) سروکار داشت. اما این با اصول Rust در تضاد است، که طبق آن‌ها به‌طور پیش‌فرض همهٔ ارجاع‌های Rust که در امضای یک تابع دخیل‌اند معلق نیستند و dereference کردنشان معتبر است.

    به همین دلیل Rust باید این قطعه کد را محافظه‌کارانه رد کند.

    و با این حال، در مورد Vec واقعی، پیاده‌سازی Drop به &'s str اهمیتی نمی‌دهد، چون drop glue مختص خودش را ندارد: فقط می‌خواهد بافر پشتیبان را آزاد کند.

    به بیان دیگر، خوب می‌شد اگر قطعه کد بالا به‌نحوی پذیرفته می‌شد، یا با در نظر گرفتن حالت ویژه برای Vec، یا با تکیه بر یک ویژگی خاص Vec: Vec می‌توانست سعی کند قول بدهد هنگام drop شدن از &'s strهایی که نگه داشته استفاده نمی‌کند.

    این همان نوع قول unsafe است که با #[may_dangle] قابل بیان است:

    unsafe impl<#[may_dangle] 's> Drop for Vec<&'s str> { /* … */ }

    مثال زیر را در نظر بگیرید:

    unsafe impl<#[may_dangle] T> Drop for Vec<T> { /* … */ }

    راه unsafe برای کنار گذاشتن این فرض محافظه‌کارانه‌ای است که drop checker در Rust دربارهٔ پارامترهای نوعِ یک نمونهٔ drop‌شده می‌کند، یعنی اینکه اجازه ندارند معلق باشند.

    و وقتی این کار انجام می‌شود، مانند آنچه در کتابخانهٔ استاندارد هست، باید در حالتی که T خودش drop glue دارد دقت کنیم. در این مورد، تصور کنید &'s strها را با struct PrintOnDrop<'s> /* = */ (&'s str); جایگزین کنیم که یک پیاده‌سازی Drop دارد و در آن &'s str درونی dereference شده و روی صفحه چاپ می‌شود.

    در واقع، Drop for Vec<T> { پیش از آزاد کردن بافر پشتیبان، باید هر آیتم T را در صورت داشتن drop glue به‌صورت تراگذری (transitive) drop کند؛ در مورد PrintOnDrop<'s> این یعنی Drop for Vec<PrintOnDrop<'s>> پیش از آزاد کردن بافر پشتیبان باید عناصر PrintOnDrop<'s> را به‌صورت تراگذری drop کند.

    پس وقتی گفتیم 's می‌تواند #[may_dangle] باشد، این گزاره بیش‌ازحد آزادانه بود. بهتر است بگوییم: «'s می‌تواند معلق باشد، به شرط آنکه در drop glue تراگذری‌ای دخیل نباشد». یا به‌طور کلی‌تر، «T می‌تواند معلق باشد، به شرط آنکه در drop glue تراگذری‌ای دخیل نباشد». این «استثنا بر استثنا» هرگاه مالک یک T باشیم وضعیتی فراگیر است. به همین دلیل #[may_dangle] در Rust به‌اندازهٔ کافی هوشمند است که از این کنار گذاشتن آگاه باشد، و بنابراین وقتی پارامتر جنریک به‌صورت مالکانه در فیلدهای struct نگه داشته شود، غیرفعال می‌شود.

    به همین دلیل کتابخانهٔ استاندارد در نهایت به این می‌رسد:

    #[cfg(any())]
// we pinky-swear not to use `T` when dropping a `Vec`…
unsafe impl<#[may_dangle] T> Drop for Vec<T> {
    fn drop(&mut self) {
        unsafe {
            if mem::needs_drop::<T>() {
                /* … except here, that is, … */
                ptr::drop_in_place::<[T]>(/* … */);
            }
            // …
            dealloc(/* … */)
            // …
        }
    }
}

struct Vec<T> {
    // … except for the fact that a `Vec` owns `T` items and
    // may thus be dropping `T` items on drop!
    _owns_T: core::marker::PhantomData<T>,

    ptr: *const T, // `*const` for variance (but this does not express ownership of a `T` *per se*)
    len: usize,
    cap: usize,
}

    اشاره‌گرهای خامی که مالک یک تخصیص هستند الگویی چنان فراگیر است که نوع‌های خودِ کتابخانهٔ استاندارد هر بار همین اجزا را کنار هم می‌گذارند:

    • یک NonNull<T>، برای واریانس و بهینه‌سازی اشاره‌گر تهی (null-pointer optimization)
    • a PhantomData<T>
    • پیاده‌سازی‌های Send/Sync طوری که انگار یک T در آن نگه داشته شده است

    (سال‌ها کتابخانهٔ استاندارد این اجزا را در یک نوع داخلی با نام Unique<T> بسته‌بندی می‌کرد. این نوع هرگز پایدار نشد و از آن زمان حذف شده است.)

    جدول الگوهای PhantomData

    در اینجا جدولی از همهٔ شیوه‌های شگفت‌انگیزی آمده که می‌توان از PhantomData استفاده کرد:

    نوع Phantomوردایی 'aوردایی TSend/Sync
    (یا نبود آن‌ها)    		'a یا T معلق در drop glue
    (مثلاً #[may_dangle] Drop)
    PhantomData<T>-هم‌وردابه ارث می‌رسدغیرمجاز («مالک T»)
    PhantomData<&'a T>هم‌ورداهم‌ورداSend + Sync
    نیازمند
    T : Sync    		مجاز
    PhantomData<&'a mut T>هم‌ورداناوردابه ارث می‌رسدمجاز
    PhantomData<*const T>-هم‌وردا!Send + !Syncمجاز
    PhantomData<*mut T>-ناوردا!Send + !Syncمجاز
    PhantomData<fn(T)>-پادورداSend + Syncمجاز
    PhantomData<fn() -> T>-هم‌ورداSend + Syncمجاز
    PhantomData<fn(T) -> T>-ناورداSend + Syncمجاز
    PhantomData<Cell<&'a ()>>ناوردا-Send + !Syncمجاز
