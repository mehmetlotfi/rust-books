    Send و Sync

    با این حال، همه‌چیز از تغییرپذیری ارثی (inherited mutability) پیروی نمی‌کند. بعضی نوع‌ها اجازه می‌دهند هنگام تغییر دادن یک مکان در حافظه، چندین نام مستعار (alias) برای آن داشته باشید. اگر این نوع‌ها برای مدیریت این دسترسی از همگام‌سازی استفاده نکنند، قطعاً برای کار با نخ‌ها ایمن نیستند. Rust این موضوع را از طریق صفت‌های Send و Sync بیان می‌کند.

    • نوعی Send است که ارسال آن به نخ دیگر ایمن باشد.
    • نوعی Sync است که اشتراک‌گذاری آن میان نخ‌ها ایمن باشد (T تنها و تنها وقتی Sync است که &T از نوع Send باشد).

    Send و Sync برای داستان هم‌روندی (concurrency) در Rust بنیادین‌اند. به همین دلیل، ابزارهای ویژهٔ قابل‌توجهی وجود دارد تا آن‌ها درست کار کنند. پیش از هر چیز، آن‌ها صفت‌های ناایمن هستند. یعنی پیاده‌سازی‌شان ناایمن است و کد ناایمن دیگر می‌تواند فرض کند که درست پیاده‌سازی شده‌اند. از آنجا که آن‌ها صفت‌های نشانگر هستند (آیتم وابسته‌ای مانند متد ندارند)، «درست پیاده‌سازی شدن» صرفاً به این معناست که ویژگی‌های ذاتی‌ای را داشته باشند که یک پیاده‌ساز باید داشته باشد. پیاده‌سازی نادرست Send یا Sync می‌تواند باعث رفتار تعریف‌نشده شود.

    Send و Sync همچنین صفت‌هایی هستند که به‌طور خودکار استنتاج می‌شوند. یعنی برخلاف هر صفت دیگری، اگر نوعی کاملاً از نوع‌های Send یا Sync تشکیل شده باشد، خودش هم Send یا Sync است. تقریباً همهٔ نوع‌های اولیه Send و Sync هستند و در نتیجه تقریباً همهٔ نوع‌هایی که با آن‌ها سروکار خواهید داشت Send و Sync‌اند.

    استثناهای عمده عبارت‌اند از:

    • اشاره‌گرهای خام نه Send هستند و نه Sync (چون هیچ محافظ ایمنی‌ای ندارند).
    • UnsafeCell از نوع Sync نیست (و بنابراین Cell و RefCell هم نیستند).
    • Rc نه Send است و نه Sync (چون شمارندهٔ ارجاع مشترک و ناهمگام‌شده است).

    Rc و UnsafeCell ذاتاً و بنیادین برای نخ‌ها ایمن نیستند: آن‌ها حالت تغییرپذیر مشترکِ همگام‌نشده را ممکن می‌کنند. اما اشاره‌گرهای خام، به‌طور دقیق‌تر، بیشتر به‌عنوان یک lint ناایمن برای نخ علامت‌گذاری شده‌اند. انجام هر کار مفیدی با یک اشاره‌گر خام مستلزم ارجاع‌زدایی (dereference) آن است که خودش ناایمن است. از این منظر می‌توان استدلال کرد که علامت‌گذاری آن‌ها به‌عنوان ایمن برای نخ «اشکالی نداشت».

    با این حال مهم است که آن‌ها برای نخ ایمن نباشند تا نوع‌هایی که آن‌ها را در بر می‌گیرند به‌طور خودکار ایمن برای نخ علامت‌گذاری نشوند. این نوع‌ها مالکیتِ غیرپیش‌پاافتادهٔ ردیابی‌نشده‌ای دارند و بعید است نویسندهٔ آن‌ها لزوماً به‌دقت به ایمنی نخ فکر کرده باشد. در مورد Rc، نمونهٔ خوبی داریم از نوعی که یک *mut دارد و قطعاً برای نخ ایمن نیست.

    نوع‌هایی که به‌طور خودکار استنتاج نمی‌شوند، در صورت تمایل می‌توانند آن‌ها را صرفاً پیاده‌سازی کنند:

    struct MyBox(*mut u8);

unsafe impl Send for MyBox {}
unsafe impl Sync for MyBox {}

    در حالت فوق‌العاده نادر که نوعی به‌اشتباه به‌طور خودکار Send یا Sync استنتاج شود، می‌توان پیاده‌سازی Send و Sync را لغو هم کرد:

    #![feature(negative_impls)]

// I have some magic semantics for some synchronization primitive!
struct SpecialThreadToken(u8);

impl !Send for SpecialThreadToken {}
impl !Sync for SpecialThreadToken {}

    توجه کنید که به‌خودیِ خود ممکن نیست Send و Sync به‌اشتباه استنتاج شوند. فقط نوع‌هایی که کد ناایمن دیگر به آن‌ها معنای ویژه‌ای می‌دهد می‌توانند با به‌اشتباه Send یا Sync بودن دردسر ایجاد کنند.

    بیشتر استفاده‌ها از اشاره‌گرهای خام باید پشت یک انتزاعِ کافی کپسوله شوند تا بتوان Send و Sync را استنتاج کرد. برای مثال، همهٔ مجموعه‌های استاندارد Rust (وقتی نوع‌های Send و Sync را در خود دارند) با وجود استفادهٔ فراگیرشان از اشاره‌گرهای خام برای مدیریت تخصیص‌ها و مالکیت پیچیده، Send و Sync هستند. به‌طور مشابه، بیشتر iterator‌های این مجموعه‌ها Send و Sync هستند، چون عمدتاً مثل یک & یا &mut به مجموعه رفتار می‌کنند.

    مثال

    Box به دلایل گوناگون توسط کامپایلر به‌صورت یک نوع ذاتیِ ویژهٔ خودش پیاده‌سازی شده است، اما می‌توانیم خودمان چیزی با رفتاری تقریباً مشابه پیاده‌سازی کنیم تا مثالی ببینیم از اینکه چه زمانی پیاده‌سازی Send و Sync درست (sound) است. اسمش را Carton می‌گذاریم.

    با نوشتن کدی شروع می‌کنیم که مقداری را که روی پشته تخصیص یافته بگیرد و آن را به هیپ منتقل کند.

    pub mod libc {
   pub use ::std::os::raw::{c_int, c_void};
   #[allow(non_camel_case_types)]
   pub type size_t = usize;
   unsafe extern "C" { pub fn posix_memalign(memptr: *mut *mut c_void, align: size_t, size: size_t) -> c_int; }
}
use std::{
    mem::{align_of, size_of},
    ptr,
    cmp::max,
};

struct Carton<T>(ptr::NonNull<T>);

impl<T> Carton<T> {
    pub fn new(value: T) -> Self {
        // Allocate enough memory on the heap to store one T.
        assert_ne!(size_of::<T>(), 0, "Zero-sized types are out of the scope of this example");
        let mut memptr: *mut T = ptr::null_mut();
        unsafe {
            let ret = libc::posix_memalign(
                (&mut memptr as *mut *mut T).cast(),
                max(align_of::<T>(), size_of::<usize>()),
                size_of::<T>()
            );
            assert_eq!(ret, 0, "Failed to allocate or invalid alignment");
        };

        // NonNull is just a wrapper that enforces that the pointer isn't null.
        let ptr = {
            // Safety: memptr is dereferenceable because we created it from a
            // reference and have exclusive access.
            ptr::NonNull::new(memptr)
                .expect("Guaranteed non-null if posix_memalign returns 0")
        };

        // Move value from the stack to the location we allocated on the heap.
        unsafe {
            // Safety: If non-null, posix_memalign gives us a ptr that is valid
            // for writes and properly aligned.
            ptr.as_ptr().write(value);
        }

        Self(ptr)
    }
}

    این چندان مفید نیست، چون وقتی کاربران ما مقداری به ما بدهند راهی برای دسترسی به آن ندارند. Box صفت‌های Deref و DerefMut را پیاده‌سازی می‌کند تا بتوانید به مقدار درونی دسترسی پیدا کنید. بیایید همین کار را بکنیم.

    use std::ops::{Deref, DerefMut};

struct Carton<T>(std::ptr::NonNull<T>);

impl<T> Deref for Carton<T> {
    type Target = T;

    fn deref(&self) -> &Self::Target {
        unsafe {
            // Safety: The pointer is aligned, initialized, and dereferenceable
            //   by the logic in [`Self::new`]. We require readers to borrow the
            //   Carton, and the lifetime of the return value is elided to the
            //   lifetime of the input. This means the borrow checker will
            //   enforce that no one can mutate the contents of the Carton until
            //   the reference returned is dropped.
            self.0.as_ref()
        }
    }
}

impl<T> DerefMut for Carton<T> {
    fn deref_mut(&mut self) -> &mut Self::Target {
        unsafe {
            // Safety: The pointer is aligned, initialized, and dereferenceable
            //   by the logic in [`Self::new`]. We require writers to mutably
            //   borrow the Carton, and the lifetime of the return value is
            //   elided to the lifetime of the input. This means the borrow
            //   checker will enforce that no one else can access the contents
            //   of the Carton until the mutable reference returned is dropped.
            self.0.as_mut()
        }
    }
}

    در نهایت، بیایید فکر کنیم که آیا Carton ما Send و Sync است یا نه. چیزی می‌تواند با ایمنی Send باشد مگر اینکه حالت تغییرپذیر را با چیز دیگری به اشتراک بگذارد بدون آنکه دسترسی انحصاری به آن را اِعمال کند. هر Carton یک اشاره‌گر یکتا دارد، پس مشکلی نداریم.

    struct Carton<T>(std::ptr::NonNull<T>);
// Safety: No one besides us has the raw pointer, so we can safely transfer the
// Carton to another thread if T can be safely transferred.
unsafe impl<T> Send for Carton<T> where T: Send {}

    Sync چطور؟ برای اینکه Carton از نوع Sync باشد باید اِعمال کنیم که نتوان در چیزی که در یک &Carton ذخیره شده نوشت، در حالی که همان چیز می‌تواند از &Carton دیگری خوانده یا نوشته شود. از آنجا که برای نوشتن روی اشاره‌گر به یک &mut Carton نیاز دارید و بررسی‌کنندهٔ قرض‌گیری (borrow checker) اِعمال می‌کند که ارجاع‌های تغییرپذیر باید انحصاری باشند، هیچ مشکل صحتی در Sync کردن Carton هم وجود ندارد.

    struct Carton<T>(std::ptr::NonNull<T>);
// Safety: Since there exists a public way to go from a `&Carton<T>` to a `&T`
// in an unsynchronized fashion (such as `Deref`), then `Carton<T>` can't be
// `Sync` if `T` isn't.
// Conversely, `Carton` itself does not use any interior mutability whatsoever:
// all the mutations are performed through an exclusive reference (`&mut`). This
// means it suffices that `T` be `Sync` for `Carton<T>` to be `Sync`:
unsafe impl<T> Sync for Carton<T> where T: Sync  {}

    وقتی ادعا می‌کنیم نوع ما Send و Sync است، معمولاً باید اِعمال کنیم که هر نوعِ درونی‌اش Send و Sync باشد. وقتی نوع‌های سفارشی‌ای می‌نویسیم که مثل نوع‌های کتابخانهٔ استاندارد رفتار می‌کنند، می‌توانیم ادعا کنیم همان الزامات را دارند. برای مثال، کد زیر ادعا می‌کند که Carton وقتی Send است که همان نوع Box هم Send باشد، که در این مورد معادل این است که بگوییم T، Send است.

    struct Carton<T>(std::ptr::NonNull<T>);
unsafe impl<T> Send for Carton<T> where Box<T>: Send {}

    اکنون Carton<T> نشت حافظه دارد، چون هرگز حافظه‌ای را که تخصیص می‌دهد آزاد نمی‌کند. وقتی این را رفع کنیم، الزام تازه‌ای پیدا می‌کنیم که برای Send بودن باید برآورده شود: باید بدانیم free را می‌توان روی اشاره‌گری صدا زد که از تخصیصی در نخ دیگر به‌دست آمده است. می‌توانیم درستی این موضوع را در مستندات libc::free بررسی کنیم.

    struct Carton<T>(std::ptr::NonNull<T>);
mod libc {
    pub use ::std::os::raw::c_void;
    unsafe extern "C" { pub fn free(p: *mut c_void); }
}
impl<T> Drop for Carton<T> {
    fn drop(&mut self) {
        unsafe {
            libc::free(self.0.as_ptr().cast());
        }
    }
}

    نمونهٔ خوبی که در آن این اتفاق نمی‌افتد MutexGuard است: توجه کنید که Send نیست. پیاده‌سازی MutexGuard از کتابخانه‌هایی استفاده می‌کند که از شما می‌خواهند مطمئن شوید قفلی را که در نخی دیگر گرفته‌اید آزاد نمی‌کنید. اگر می‌توانستید یک MutexGuard را به نخ دیگری Send کنید، نابودگر (destructor) در نخی اجرا می‌شد که آن را به آنجا فرستاده‌اید و این الزام را نقض می‌کرد. MutexGuard همچنان می‌تواند Sync باشد، چون تنها چیزی که می‌توانید به نخ دیگری بفرستید یک &MutexGuard است و رها کردن (drop) یک ارجاع هیچ کاری نمی‌کند.
