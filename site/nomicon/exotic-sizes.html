    نوع‌هایی با اندازه‌های عجیب

    در بیشتر مواقع انتظار داریم نوع‌ها اندازه‌ای مثبت و مشخص در زمان کامپایل داشته باشند. در Rust همیشه این‌طور نیست.

    نوع‌های با اندازه پویا (DSTها)

    Rust از نوع‌های با اندازه پویا (Dynamically Sized Types یا DSTها) پشتیبانی می‌کند: نوع‌هایی که اندازه و ترازبندی (alignment) آن‌ها در زمان کامپایل معلوم نیست. در نگاه اول این کمی بی‌معنی به نظر می‌رسد: Rust باید اندازه و ترازبندی هر چیزی را بداند تا بتواند درست با آن کار کند! از این نظر، DSTها نوع‌های معمولی نیستند. چون اندازه‌ای ایستا و معلوم ندارند، این نوع‌ها فقط پشت یک اشاره‌گر می‌توانند وجود داشته باشند. در نتیجه، هر اشاره‌گر به یک DST به یک اشاره‌گر عریض (wide pointer) تبدیل می‌شود که از خود اشاره‌گر و اطلاعاتی تشکیل شده که آن را «کامل» می‌کند (در ادامه بیشتر توضیح می‌دهیم).

    دو DST اصلی در زبان وجود دارد:

    • شیء‌های صفت (trait objects): dyn MyTrait
    • برش‌ها (slices): [T]، str و موارد دیگر

    یک شیء صفت نماینده‌ی نوعی است که صفت‌های مشخص‌شده را پیاده‌سازی می‌کند. نوع اصلی دقیق پاک می‌شود و به‌جای آن بازتاب زمان اجرا (runtime reflection) از طریق یک vtable به کار می‌رود که همه‌ی اطلاعات لازم برای استفاده از آن نوع را در خود دارد. اطلاعاتی که اشاره‌گر شیء صفت را کامل می‌کند، اشاره‌گر به vtable است. اندازه‌ی زمان اجرای شیء مورد اشاره را می‌توان به‌صورت پویا از vtable درخواست کرد.

    یک برش صرفاً نمایی از یک فضای ذخیره‌سازی پیوسته است – معمولاً یک آرایه یا Vec. اطلاعاتی که اشاره‌گر برش را کامل می‌کند فقط تعداد عناصری است که به آن‌ها اشاره می‌کند. اندازه‌ی زمان اجرای شیء مورد اشاره برابر است با اندازه‌ی ایستای شناخته‌شده‌ی یک عنصر ضرب در تعداد عناصر.

    ساختارها (structs) در واقع می‌توانند یک DST را مستقیماً به‌عنوان آخرین فیلد خود نگه دارند، اما این کار آن‌ها را هم به یک DST تبدیل می‌کند:

    // Can't be stored on the stack directly
struct MySuperSlice {
    info: u32,
    data: [u8],
}

    متأسفانه چنین نوعی بدون راهی برای ساختنش تقریباً بی‌فایده است. در حال حاضر تنها راهی که به‌درستی پشتیبانی می‌شود برای ایجاد یک DST سفارشی این است که نوع خود را جنریک کنید و یک تبدیل اندازه‌زدایی (unsizing coercion) انجام دهید:

    struct MySuperSliceable<T: ?Sized> {
    info: u32,
    data: T,
}

fn main() {
    let sized: MySuperSliceable<[u8; 8]> = MySuperSliceable {
        info: 17,
        data: [0; 8],
    };

    let dynamic: &MySuperSliceable<[u8]> = &sized;

    // prints: "17 [0, 0, 0, 0, 0, 0, 0, 0]"
    println!("{} {:?}", dynamic.info, &dynamic.data);
}

    (بله، DSTهای سفارشی فعلاً قابلیتی نیمه‌کاره هستند.)

    نوع‌های با اندازه صفر (ZSTها)

    Rust همچنین اجازه می‌دهد نوع‌هایی تعریف شوند که هیچ فضایی اشغال نمی‌کنند:

    struct Nothing; // No fields = no size

// All fields have no size = no size
struct LotsOfNothing {
    foo: Nothing,
    qux: (),      // empty tuple has no size
    baz: [u8; 0], // empty array has no size
}

    نوع‌های با اندازه صفر (Zero Sized Types یا ZSTها) به‌تنهایی، به دلایل واضح، کاملاً بی‌فایده‌اند. با این حال، مانند بسیاری از انتخاب‌های کنجکاوانه‌ی چیدمان در Rust، توان بالقوه‌ی آن‌ها در بستر جنریک آشکار می‌شود: Rust تا حد زیادی می‌داند که هر عملیاتی که یک ZST تولید یا ذخیره می‌کند را می‌توان به یک عملیات تهی (no-op) کاهش داد. اول اینکه ذخیره‌کردن آن حتی معنا ندارد – چون هیچ فضایی اشغال نمی‌کند. همچنین فقط یک مقدار از آن نوع وجود دارد، بنابراین هر چیزی که آن را بارگیری می‌کند می‌تواند آن را از هیچ تولید کند – که آن هم یک عملیات تهی است چون هیچ فضایی اشغال نمی‌کند.

    یکی از شدیدترین نمونه‌های این موضوع مجموعه‌ها (Sets) و نگاشت‌ها (Maps) است. با داشتن یک Map<Key, Value>، پیاده‌سازی Set<Key> به‌صورت یک لایه‌ی نازک دور Map<Key, UselessJunk> رایج است. در بسیاری از زبان‌ها، این کار مستلزم تخصیص فضا برای UselessJunk و انجام کار برای ذخیره و بارگیری UselessJunk فقط برای دور انداختن آن است. اثبات بی‌مصرف‌بودن این کارها برای کامپایلر تحلیلی دشوار خواهد بود.

    اما در Rust می‌توانیم به‌سادگی بگوییم Set<Key> = Map<Key, ()>. اکنون Rust به‌صورت ایستا می‌داند که هر بارگیری و ذخیره بی‌فایده است و هیچ تخصیصی اندازه‌ای ندارد. نتیجه این است که کد تک‌ریختی‌شده (monomorphized) اساساً یک پیاده‌سازی سفارشی از HashSet است، بدون هیچ‌کدام از سربارهایی که HashMap برای پشتیبانی از مقادیر باید تحمل کند.

    کد امن لازم نیست نگران ZSTها باشد، اما کد unsafe باید مراقب پیامدهای نوع‌های بدون اندازه باشد. به‌ویژه، جابه‌جایی اشاره‌گر (pointer offset) عملیات تهی است، و تخصیص‌دهنده‌ها (allocators) معمولاً اندازه‌ی غیرصفر را الزامی می‌دانند.

    توجه کنید که ارجاع‌ها به ZSTها (از جمله برش‌های خالی)، درست مانند همه‌ی ارجاع‌های دیگر، باید غیر null و به‌درستی تراز شده باشند. با این حال، بارگیری یا ذخیره از طریق یک اشاره‌گر null به یک ZST برخلاف اشاره‌گر به نوع‌های دیگر، رفتار تعریف‌نشده نیست.

    نوع‌های تهی

    Rust همچنین اجازه می‌دهد نوع‌هایی تعریف شوند که حتی نمی‌توان از آن‌ها نمونه ساخت. این نوع‌ها فقط در سطح نوع قابل بحث هستند و هرگز در سطح مقدار وجود ندارند. نوع‌های تهی را می‌توان با تعریف یک شمارش بدون هیچ گونه (variant) اعلام کرد:

    enum Void {} // No variants = EMPTY

    نوع‌های تهی حتی از ZSTها حاشیه‌ای‌ترند. اصلی‌ترین مثال انگیزه‌بخش برای یک نوع تهی، دست‌نیافتنی‌بودن در سطح نوع است. برای نمونه، فرض کنید یک API در حالت کلی باید یک Result برگرداند، اما یک حالت خاص در واقع هرگز شکست نمی‌خورد. در واقع می‌توان این را در سطح نوع با برگرداندن Result<T, Void> اعلام کرد. مصرف‌کنندگان API می‌توانند با اطمینان چنین Resultی را unwrap کنند، چون می‌دانند از نظر ایستا غیرممکن است که این مقدار یک Err باشد، زیرا این کار مستلزم ارائه‌ی مقداری از نوع Void است.

    در اصل، Rust می‌تواند بر پایه‌ی این واقعیت تحلیل‌ها و بهینه‌سازی‌های جالبی انجام دهد. برای نمونه، Result<T, Void> فقط به‌صورت T نمایش داده می‌شود، چون حالت Err در واقع وجود ندارد (به بیان دقیق، این فقط یک بهینه‌سازی است که تضمین نشده است، بنابراین مثلاً تبدیل یکی به دیگری با transmute همچنان رفتار تعریف‌نشده است).

    کد زیر هم کامپایل می‌شود:

    enum Void {}

let res: Result<u32, Void> = Ok(0);

// Err doesn't exist anymore, so Ok is actually irrefutable.
let Ok(num) = res;

    یک نکته‌ی ظریف پایانی درباره‌ی نوع‌های تهی این است که ساختن اشاره‌گر خام به آن‌ها در واقع مجاز است، اما صرف‌نظر کردن (dereference) از آن‌ها رفتار تعریف‌نشده است چون معنایی ندارد.

    توصیه می‌کنیم نوع void* زبان C را با *const Void مدل نکنید. افراد زیادی این کار را شروع کردند، اما به‌سرعت به مشکل خوردند، چون Rust در واقع هیچ حفاظ ایمنی در برابر تلاش برای ساخت نمونه از نوع‌های تهی با کد unsafe ندارد و اگر این کار را بکنید، رفتار تعریف‌نشده است. این موضوع به‌ویژه مشکل‌ساز بود چون توسعه‌دهندگان عادت داشتند اشاره‌گرهای خام را به ارجاع تبدیل کنند و ساختن &Void هم خودش رفتار تعریف‌نشده است.

    *const () (یا معادل آن) برای void* به‌طور معقولی خوب کار می‌کند و می‌توان آن را بدون هیچ مشکل ایمنی به یک ارجاع تبدیل کرد. این هنوز مانع از تلاش برای خواندن یا نوشتن مقادیر نمی‌شود، اما دست‌کم به‌جای رفتار تعریف‌نشده به یک عملیات تهی کامپایل می‌شود.

    نوع‌های extern

    یک RFC پذیرفته‌شده برای افزودن نوع‌های واقعی با اندازه‌ی نامعلوم وجود دارد، به نام نوع‌های extern، که به توسعه‌دهندگان Rust اجازه می‌دهد چیزهایی مانند void* در C و دیگر نوع‌های «اعلام‌شده اما هرگز تعریف‌نشده» را دقیق‌تر مدل کنند. با این حال، از زمان Rust 2018، این قابلیت در بلاتکلیفی گیر کرده است که size_of_val::<MyExternType>() چگونه باید رفتار کند.
