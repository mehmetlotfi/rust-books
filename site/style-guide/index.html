    راهنمای سبک Rust

    انگیزه — چرا از ابزار قالب‌بندی استفاده کنیم؟

    قالب‌بندی کد کاری عمدتاً مکانیکی است و هم وقت می‌برد و هم تمرکز ذهنی. با استفاده از یک ابزار قالب‌بندی خودکار، برنامه‌نویس از این کار آزاد می‌شود و می‌تواند روی مسائل مهم‌تر تمرکز کند.

    افزون بر این، با پیروی از یک راهنمای سبک معتبر (مانند همین راهنما)، برنامه‌نویس‌ها دیگر لازم نیست قواعد سبک موردی بسازند و با دیگران بر سر این‌که کدام قواعد به کار بروند بحث کنند. این کار زمان، هزینهٔ ارتباط و انرژی ذهنی را ذخیره می‌کند.

    انسان‌ها اطلاعات را از راه تشخیص الگو می‌فهمند. وقتی همهٔ کدهای Rust قالب مشابهی داشته باشند، برای درک یک پروژهٔ تازه به تلاش ذهنی کمتری نیاز است و ورود توسعه‌دهندگان جدید آسان‌تر می‌شود.

    بنابراین استفاده از یک ابزار قالب‌بندی (مانند rustfmt) بهره‌وری را بالا می‌برد و استفاده از قالب‌بندی مورد پذیرش جامعه، معمولاً با تنظیمات پیش‌فرض همان ابزار، سود بیشتری دارد.

    قالب پیش‌فرض Rust

    راهنمای سبک Rust قالب پیش‌فرض Rust را تعریف می‌کند و توسعه‌دهندگان و ابزارها را به پیروی از آن توصیه می‌کند. ابزارهایی مانند rustfmt این راهنما را به‌عنوان مرجع قالب پیش‌فرض به کار می‌برند. هر چیزی در این راهنما، چه با واژه‌هایی مانند «باید» بیان شده باشد و چه با فعل امری مانند «یک فاصله درج کنید» یا «پس از … خط را بشکنید»، به قالب پیش‌فرض اشاره دارد.

    این موضوع به معنای منع توسعه‌دهندگان از پیروی از قالب غیرپیش‌فرض یا منع ابزارها از افزودن برخی گزینه‌های پیکربندی نیست.

    باگ‌ها

    اگر راهنمای سبک با rustfmt تفاوت داشته باشد، ممکن است این تفاوت نشانهٔ باگی در rustfmt یا باگی در خود راهنمای سبک باشد. در هر دو حالت، لطفاً آن را به تیم سبک یا تیم rustfmt یا هر دو گزارش دهید تا بررسی و رفع شود.

    اگر ابزار قالب‌بندی جدیدی بر اساس راهنمای سبک و سبک پیش‌فرض Rust پیاده‌سازی می‌کنید، لطفاً آن را روی مجموعهٔ کدهای موجود Rust آزمایش کنید و از ایجاد خرابی گسترده پرهیز کنید. پیاده‌سازی و آزمایش چنین ابزاری ممکن است باگ‌هایی را هم در راهنمای سبک یا rustfmt و هم در خود ابزار آشکار کند.

    ما معمولاً باگ‌ها را به شیوه‌ای برطرف می‌کنیم که از خرابی گسترده جلوگیری کند.

    قواعد قالب‌بندی

    تورفتگی و عرض خط

    • از فاصله استفاده کنید، نه تب.
    • هر سطح تورفتگی باید ۴ فاصله باشد؛ یعنی تمام تورفتگی‌ها بیرون از رشته‌های لفظی و کامنت‌ها باید مضربی از ۴ باشند.
    • حداکثر عرض یک خط ۱۰۰ نویسه است.

    تورفتگی بلوکی

    تورفتگی بلوکی را به تورفتگی بصری ترجیح دهید:

    // Block indent
a_function_call(
    foo,
    bar,
);

// Visual indent
a_function_call(foo,
                bar);

    این کار تفاوت‌های (diff) کوچک‌تری ایجاد می‌کند (مثلاً اگر a_function_call در مثال بالا تغییر نام دهد) و باعث می‌شود کد کمتر به سمت راست کشیده شود.

    کاما انتهایی

    در فهرست‌های جداشده با کاما از هر نوعی، وقتی کاما قبل از خط جدید می‌آید، از کاما انتهایی استفاده کنید:

    function_call(
    argument,
    another_argument,
);

let array = [
    element,
    another_element,
    yet_another_element,
];

    این کار جابه‌جایی کد (مثلاً با کپی و پیست) را آسان‌تر می‌کند و باعث می‌شود تفاوت‌ها کوچک‌تر باشند، چون افزودن یا حذف یک آیتم نیازی به تغییر کاما در خط دیگری ندارد.

    خطوط خالی

    آیتم‌ها و دستورها را با صفر یا یک خط خالی از هم جدا کنید (یعنی یک یا دو خط جدید). برای نمونه:

    fn foo() {
    let x = ...;

    let y = ...;
    let z = ...;
}

fn bar() {}
fn baz() {}

    فاصلهٔ خالی انتهای خط

    هیچ فاصلهٔ خالی‌ای در انتهای هیچ خطی قرار ندهید. این شامل خطوط خالی، خطوط کامنت، خطوط کد و رشته‌های لفظی هم می‌شود.

    توجه کنید که پرهیز از فاصلهٔ خالی انتهای رشته‌های لفظی نیاز به دقت دارد تا مقدار آن رشته حفظ شود.

    مرتب‌سازی

    در مواردی، قالب پیش‌فرض Rust مرتب‌سازی را مشخص می‌کند. اگر چیزی دیگری تعیین نشده باشد، این مرتب‌سازی باید «مرتب‌سازی نسخه‌ای» باشد؛ یعنی مثلاً x8 قبل از x16 قرار بگیرد، با این‌که نویسهٔ 1 پیش از 8 می‌آید.

    برای مقایسهٔ دو رشته به‌منظور مرتب‌سازی نسخه‌ای در سبک Rust، این مراحل را دنبال کنید:

    • هر دو رشته را از ابتدا تا انتها به‌عنوان دنباله‌ای از بخش‌های حداکثر طولانی پردازش کنید؛ هر بخش یا دنبالهٔ نویسه‌هایی است که رقم ASCII نیستند، یا دنبالهٔ ارقام ASCII (بخش عددی). سپس بخش‌های متناظر دو رشته را مقایسه کنید.
    • برای مقایسهٔ دو بخش عددی، آن‌ها را بر اساس مقدار عددی و بدون درنظرگرفتن صفرهای ابتدایی مقایسه کنید. اگر مقدار عددی دو بخش برابر باشد ولی تعداد ارقام ابتدایی آن‌ها متفاوت باشد، و این اولین باری باشد که چنین می‌شود، آن دو بخش را برابر در نظر بگیرید (و به بخش بعدی بروید) ولی به خاطر بسپارید کدام رشته صفرهای ابتدایی بیشتری داشته است.
    • برای مقایسهٔ دو بخشی که عددی نیستند، آن‌ها را بر اساس ترتیب واژه‌نامه‌ای نویسه‌های یونیکد مقایسه کنید، با دو استثنا:
      • _ (زیرخط) بلافاصله بعد از (فاصله) و پیش از هر نویسهٔ دیگری مرتب می‌شود. (این کار زیرخط را جداکنندهٔ کلمه در نظر می‌گیرد، همان‌طور که معمولاً در شناسه‌ها به کار می‌رود.)
      • مگر این‌که چیز دیگری تعیین شده باشد، در مرتب‌سازی نسخه‌ای نویسه‌های غیرحروف‌کوچک (یعنی نویسه‌هایی که می‌توانند شناسهٔ UpperCamelCase را شروع کنند) پیش از حروف کوچک قرار می‌گیرند.
    • اگر مقایسه به انتهای رشته برسد و همهٔ جفت بخش‌ها برابر تشخیص داده شوند:
      • اگر یکی از مقایسه‌های عددی اولین نقطه‌ای را نشان داده باشد که در آن یک رشته صفرهای ابتدایی بیشتری نسبت به دیگری داشته است، رشته‌ای که صفرهای ابتدایی بیشتری دارد اول قرار می‌گیرد.
      • در غیر این صورت، رشته‌ها برابرند.

    توجه کنید که الگوریتم‌های متعددی با نام «مرتب‌سازی نسخه‌ای» وجود دارند که معمولاً همان مسئله را حل می‌کنند ولی در جزئیات، مثلاً در برخورد با اعداد دارای صفر ابتدایی، با هم فرق دارند. این الگوریتم ادعا نمی‌کند دقیقاً با رفتار هیچ الگوریتم دیگری یکی است؛ فقط هدفش تولید نتیجه‌ای ساده و رضایت‌بخش برای قالب‌بندی Rust است. به‌طور مشخص، این الگوریتم می‌خواهد برای مجموعه‌ای از نمادها با تعداد یکسان صفر ابتدایی نتیجهٔ مطلوبی بدهد و برای مجموعه‌ای از نمادها با تعداد متفاوت صفر ابتدایی، نتیجه‌ای قابل قبول و قابل فهم.

    کامنت‌ها

    رهنمودهای زیر برای کامنت‌ها فقط توصیه‌اند؛ یک ابزار قالب‌بندی مکانیکی ممکن است قالب‌بندی کامنت‌ها را نادیده بگیرد.

    کامنت خطی (//) را به کامنت بلوکی (/* ... */) ترجیح دهید.

    هنگام استفاده از کامنت خطی، بعد از نشانهٔ شروع یک فاصلهٔ واحد بگذارید.

    هنگام استفاده از کامنت بلوکی تک‌خطی، بعد از نشانهٔ شروع و قبل از نشانهٔ پایان یک فاصلهٔ واحد بگذارید. برای کامنت‌های بلوکی چندخطی، بعد از نشانهٔ شروع یک خط جدید و قبل از نشانهٔ پایان یک خط جدید قرار دهید.

    ترجیح دهید کامنت در خط جداگانهٔ خودش باشد. وقتی کامنت بعد از کد می‌آید، قبل از آن یک فاصلهٔ واحد بگذارید. وقتی کامنت بلوکی درون یک خط می‌آید، از فاصلهٔ اطراف آن همان‌طور استفاده کنید که برای یک شناسه یا کلیدواژه استفاده می‌کنید.

    مثال‌ها:

    // A comment on an item.
struct Foo { ... }

fn foo() {} // A comment after an item.

pub fn foo(/* a comment before an argument */ x: T) {...}

    کامنت‌ها معمولاً باید جمله‌های کامل باشند. با حرف بزرگ شروع کنید و با نقطه (.) پایان دهید. کامنت بلوکی درون‌خطی ممکن است به‌عنوان یادداشتی بدون علامت نگارشی در نظر گرفته شود.

    خطوط منبعی که کاملاً کامنت هستند باید حداکثر ۸۰ نویسه طول داشته باشند (شامل نشانه‌های کامنت، ولی بدون تورفتگی)، یا حداکثر عرض خط (شامل نشانه‌های کامنت و تورفتگی)، هر کدام که کوچک‌تر باشد:

    // This comment goes up to the ................................. 80 char margin.

{
    // This comment is .............................................. 80 chars wide.
}

{
    {
        {
            {
                {
                    {
                        // This comment is limited by the ......................... 100 char margin.
                    }
                }
            }
        }
    }
}

    کامنت‌های مستندسازی

    کامنت خطی مستندسازی (///) را به کامنت بلوکی مستندسازی (/** ... */) ترجیح دهید.

    کامنت‌های مستندسازی بیرونی (/// یا /** ... */) را ترجیح دهید و از کامنت‌های مستندسازی درونی (//! و /*! ... */) فقط برای نوشتن مستندات سطح ماژول یا سطح کراته استفاده کنید.

    کامنت‌های مستندسازی را پیش از ویژگی‌ها (attribute) قرار دهید.

    ویژگی‌ها (attribute)

    هر ویژگی را در خط جداگانه‌ای قرار دهید و آن را هم‌سطح با آیتم تورفتگی دهید. در مورد ویژگی‌های درونی (#!)، آن را هم‌سطح با درون آیتم تورفتگی دهید. ویژگی‌های بیرونی را در صورت امکان ترجیح دهید.

    برای ویژگی‌هایی که فهرست آرگومان دارند، مانند توابع قالب‌بندی کنید.

    #[repr(C)]
#[foo(foo, bar)]
#[long_multi_line_attribute(
    split,
    across,
    lines,
)]
struct CRepr {
    #![repr(C)]
    x: f32,
    y: f32,
}

    برای ویژگی‌هایی که علامت مساوی دارند، قبل و بعد از = یک فاصلهٔ واحد بگذارید، مثلاً #[foo = 42].

    فقط یک ویژگی derive باید وجود داشته باشد. نکته برای نویسندگان ابزار: اگر چند ویژگی derive را در یک ویژگی واحد ادغام می‌کنید، ترتیب نام‌های مشتق‌شده باید برای درستی به‌طور کلی حفظ شود: #[derive(Foo)] #[derive(Bar)] struct Baz; باید به #[derive(Foo, Bar)] struct Baz; تبدیل شود.

    آیتم‌های کوچک

    در بسیاری از جاهای این راهنما، قالب‌بندی مشخصی به کوچک بودن یک ساختار کد بستگی دارد. برای مثال، ساختار لفظی یک‌خطی یا چندخطی:

    // Normal formatting
Foo {
    f1: an_expression,
    f2: another_expression(),
}

// "small" formatting
Foo { f1, f2 }

    تعیین دقیق این‌که کوچک یعنی چه را به ابزارهای مختلف واگذار کرده‌ایم. به‌ویژه، ابزارها آزادند در شرایط مختلف تعریف‌های متفاوتی به کار ببرند.

    برخی راهنماهای مناسب، اندازهٔ آیتم (بر حسب نویسه) یا پیچیدگی آن است (برای مثال این‌که همهٔ اجزا باید نام ساده باشند، نه عبارت‌های پیچیده‌تر). برای بحث بیشتر دربارهٔ راهنماهای مناسب، به این مسئله مراجعه کنید.
