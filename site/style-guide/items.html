راهنمای سبک RustRust Style Guide

    آیتم‌ها

    آیتم‌ها مجموعه‌ای از مواردی هستند که در سطح بالای یک ماژول مجاز است. با این حال، Rust اجازه می‌دهد برخی آیتم‌ها در داخل برخی انواع دیگر آیتم‌ها ظاهر شوند، مثلاً داخل یک تابع. همان قواعد قالب‌بندی چه آیتم در سطح ماژول باشد و چه داخل آیتم دیگری، اعمال می‌شود.

    extern crate باید اولین عبارت در فایل باشد. این عبارت‌ها باید به ترتیب الفبایی مرتب شوند.

    دستورهای use و اعلان‌های ماژول (mod foo;، نه mod { ... }) باید پیش از سایر آیتم‌ها بیایند. importها را پیش از اعلان‌های ماژول بگذارید. هر کدام را به ترتیب مرتب‌سازی نسخه‌ای بچینید، با این استثنا که self و super باید پیش از هر نام دیگری بیایند.

    ماژول‌های اعلان‌شده با #[macro_use] را خودکار جابه‌جا نکنید، چون ممکن است معنای برنامه تغییر کند.

    تعریف توابع

    در Rust، افراد معمولاً توابع را با جست‌وجوی fn [function-name] پیدا می‌کنند، پس قالب‌بندی تعریف توابع باید این جست‌وجو را ممکن کند.

    ترتیب و فاصله‌گذاری درست به این شکل است:

    [pub] [unsafe] [extern ["ABI"]] fn foo(arg1: i32, arg2: i32) -> i32 {
    ...
}

    از نوشتن کامنت داخل خود امضا پرهیز کنید.

    اگر امضای تابع در یک خط جا نشود، بعد از پرانتز بازکننده و قبل از پرانتز بسته خط بشکنید و هر آرگومان را در خط جداگانه‌ای با تورفتگی بلوکی بنویسید. برای نمونه:

    fn foo(
    arg1: i32,
    arg2: i32,
) -> i32 {
    ...
}

    به کاما انتهایی بعد از آخرین آرگومان توجه کنید.

    تاپل‌ها و structهای تاپلی

    فهرست نوع‌ها را همان‌طور بنویسید که فهرست پارامترهای یک تابع را می‌نویسید.

    تاپل یا struct تاپلی را همان‌طور بسازید که یک تابع را فراخوانی می‌کنید.

    تک‌خطی

    struct Bar(Type1, Type2);

let x = Bar(11, 22);
let y = (11, 22, 33);

    شمارش‌ها (enum)

    در اعلان، هر variant را در خط جداگانه‌ای با تورفتگی بلوکی بنویسید.

    هر variant را بسته به نوعش به‌صورت یک struct (بدون کلیدواژهٔ struct)، یک struct تاپلی، یا یک شناسه (که نیاز به قالب‌بندی خاصی ندارد) قالب‌بندی کنید:

    enum FooBar {
    First(u32),
    Second,
    Error {
        err: Box<Error>,
        line: u32,
    },
}

    اگر یک struct variant کوچک باشد، آن را در یک خط قرار دهید. در این حالت کاما انتهایی برای فهرست فیلدها نگذارید، ولی اطراف هر آکولاد فاصله بگذارید:

    enum FooBar {
    Error { err: Box<Error>, line: u32 },
}

    در یک enum که چند struct variant دارد، اگر هر struct variant در چند خط نوشته شود، برای همهٔ struct variantها از قالب‌بندی چندخطی استفاده کنید. با این حال، چنین وضعی ممکن است نشانهٔ آن باشد که باید فیلدهای variant را در یک struct جداگانه قرار دهید.

    Structها و Unionها

    نام struct باید در همان خطی بیاید که کلیدواژهٔ struct قرار دارد، و آکولاد بازکننده هم در همان خط باشد، به شرطی که در حاشیهٔ راست جا شود. همهٔ فیلدهای struct یک‌بار تورفتگی دارند و با کاما انتهایی تمام می‌شوند. آکولاد بسته تورفتگی ندارد و در خط جداگانه‌ای قرار می‌گیرد.

    struct Foo {
    a: A,
    b: B,
}

    اگر و فقط اگر نوع یک فیلد در حاشیهٔ راست جا نشود، آن نوع به خط خودش منتقل و دوباره تورفتگی داده می‌شود.

    struct Foo {
    a: A,
    long_name:
        LongType,
}

    به‌جای struct خالی، یک unit struct (مانند struct Foo;) را ترجیح دهید. struct خالی (مانند struct Foo(); یا struct Foo {}) فقط برای ساده‌کردن تولید کد وجود دارد. با این حال، اگر ناچار به struct خالی هستید، آن را در یک خط نگه دارید و بین آکولادها فاصله نگذارید: struct Foo(); یا struct Foo {}.

    همین رهنمودها برای اعلان‌های union بدون برچسب (untagged) هم به کار می‌روند.

    union Foo {
    a: A,
    b: B,
    long_name:
        LongType,
}

    Structهای تاپلی

    اگر ممکن است کل struct را در یک خط بنویسید. نوع‌های داخل پرانتز را با کاما و یک فاصله جدا کنید. برای struct تاپلی تک‌خطی کاما انتهایی نگذارید. اطراف پرانتزها و سمی‌کالن فاصله نگذارید:

    pub struct Foo(String, u8);

    به‌جای struct تاپلی خالی، unit struct ترجیح دارد (struct تاپلی خالی فقط برای ساده‌کردن تولید کد وجود دارد)، مثلاً struct Foo; به‌جای struct Foo();.

    برای struct تاپلی با فیلدهای زیاد (به‌ویژه اگر در یک خط جا نشود)، یک struct واقعی با فیلدهای نام‌دار ترجیح دارد.

    برای struct تاپلی چندخطی، فیلدها را با هر فیلد در یک خط و کاما انتهایی قالب‌بندی کنید:

    pub struct Foo(
    String,
    u8,
);

    Traitها

    برای آیتم‌های trait از تورفتگی بلوکی استفاده کنید. اگر آیتمی وجود ندارد، trait (همراه با {}) را در یک خط قرار دهید. در غیر این صورت، بعد از آکولاد بازکننده و قبل از آکولاد بسته خط بشکنید:

    trait Foo {}

pub trait Bar {
    ...
}

    اگر trait کران دارد، بعد از دونقطه فاصله بگذارید ولی قبل از آن فاصله نگذارید، و اطراف هر + فاصله بگذارید، مثلاً:

    trait Foo: Debug + Bar {}

    تا جای ممکن در کران‌ها خط نشکنید (استفاده از بند where را در نظر بگیرید). شکستن بین کران‌ها را به شکستن خود یک کران ترجیح دهید. اگر ناچار به شکستن کران‌ها هستید، هر کران (از جمله اولی) را در خط جداگانه‌ای با تورفتگی بلوکی قرار دهید، قبل از + بشکنید و آکولاد بازکننده را در خط جداگانه‌ای بگذارید:

    pub trait IndexRanges:
    Index<Range<usize>, Output=Self>
    + Index<RangeTo<usize>, Output=Self>
    + Index<RangeFrom<usize>, Output=Self>
    + Index<RangeFull, Output=Self>
{
    ...
}

    Implها

    برای آیتم‌های impl از تورفتگی بلوکی استفاده کنید. اگر آیتمی وجود ندارد، impl (همراه با {}) را در یک خط بنویسید. در غیر این صورت بعد از آکولاد بازکننده و قبل از آکولاد بسته خط بشکنید:

    impl Foo {}

impl Bar for Foo {
    ...
}

    تا جای ممکن در امضا خط نشکنید. اگر در یک impl غیر-inherent شکستن خط لازم است، درست قبل از for بشکنید، نوع مشخص را با تورفتگی بلوکی بنویسید و آکولاد بازکننده را در خط جداگانه‌ای قرار دهید:

    impl Bar
    for Foo
{
    ...
}

    crate خارجی (Extern crate)

    extern crate foo;

    اطراف کلیدواژه‌ها فاصله بگذارید و اطراف سمی‌کالن فاصله نگذارید.

    ماژول‌ها

    mod foo {
}
    mod foo;

    اطراف کلیدواژه‌ها و قبل از آکولاد بازکننده فاصله بگذارید، و اطراف سمی‌کالن فاصله نگذارید.

    macro_rules!

    برای تعریف کامل ماکرو از {} استفاده کنید.

    macro_rules! foo {
}

    Generics

    ترجیح دهید بخش generics در یک خط باشد. بخش‌های دیگر اعلان آیتم را بشکنید، به‌جای این‌که بخش generics را بشکنید. اگر بخش generics آن‌قدر بزرگ است که باید شکسته شود، یک بند where ترجیح دارد.

    قبل و بعد از < و قبل از > فاصله نگذارید. بعد از > فقط وقتی فاصله بگذارید که بعدش یک کلمه یا آکولاد باز بیاید، نه پرانتز باز. بعد از هر کاما فاصله بگذارید. برای بخش generics تک‌خطی، کاما انتهایی نگذارید.

    fn foo<T: Display, U: Debug>(x: Vec<T>, y: Vec<U>) ...

impl<T: Display, U: Debug> SomeType<T, U> { ...

    اگر بخش generics باید در چند خط قالب‌بندی شود، هر پارامتر را در خط جداگانه‌ای با تورفتگی بلوکی قرار دهید، بعد از < بازکننده و قبل از > بسته خط بشکنید، و کاما انتهایی بگذارید:

    fn foo<
    T: Display,
    U: Debug,
>(x: Vec<T>, y: Vec<U>) ...

    اگر یک نوع مرتبط (associated type) در یک نوع عمومی مقید شده است، اطراف = فاصله بگذارید:

    <T: Example<Item = u32>>

    تا جای ممکن برای پارامترهای عمومی از نام‌های تک‌حرفی استفاده کنید.

    بندهای where

    این قواعد برای بندهای where روی هر آیتمی اعمال می‌شود.

    اگر بلافاصله بعد از یک بستنده (از هر نوعی) قرار دارد، کلیدواژهٔ where را در همان خط با یک فاصله قبل از آن بنویسید.

    در غیر این صورت، where را در خط جدید و در همان سطح تورفتگی قرار دهید. هر جزء بند where را در خط جداگانه‌ای با تورفتگی بلوکی قرار دهید. اگر بند با سمی‌کالن تمام نشده باشد، کاما انتهایی بگذارید. اگر بند where با یک بلوک (یا انتساب) دنبال می‌شود، آن بلوک را در خط جدید شروع کنید. مثال‌ها:

    fn function<T, U>(args)
where
    T: Bound,
    U: AnotherBound,
{
    body
}

fn foo<T>(
    args
) -> ReturnType
where
    T: Bound,
{
    body
}

fn foo<T, U>(
    args,
) where
    T: Bound,
    U: AnotherBound,
{
    body
}

fn foo<T, U>(
    args
) -> ReturnType
where
    T: Bound,
    U: AnotherBound;  // Note, no trailing comma.

// Note that where clauses on `type` aliases are not enforced and should not
// be used.
type Foo<T>
where
    T: Bound
= Bar<T>;

    اگر بند where بسیار کوتاه است، ترجیح دهید از کران درون‌خطی روی پارامتر نوع استفاده کنید.

    اگر جزئی از بند where جا نمی‌شود و شامل + است، قبل از هر + بشکنید و خط‌های ادامه را با تورفتگی بلوکی بنویسید. هر کران را در خط جداگانه‌ای قرار دهید. برای نمونه:

    impl<T: ?Sized, Idx> IndexRanges<Idx> for T
where
    T: Index<Range<Idx>, Output = Self::Output>
        + Index<RangeTo<Idx>, Output = Self::Output>
        + Index<RangeFrom<Idx>, Output = Self::Output>
        + Index<RangeInclusive<Idx>, Output = Self::Output>
        + Index<RangeToInclusive<Idx>, Output = Self::Output>
        + Index<RangeFull>,

    نام‌های مستعار نوع (Type aliases)

    اگر جا شود، نام‌های مستعار نوع را در یک خط نگه دارید. اگر لازم است خط شکسته شود، قبل از = بشکنید و سمت راست را با تورفتگی بلوکی بنویسید:

    pub type Foo = Bar<T>;

// If multi-line is required
type VeryLongType<T, U: SomeBound>
    = AnEvenLongerType<T, U, Foo<T>>;

    وقتی بعد از نوع یک بند where پایانی وجود دارد و قبل از نوع بند where نیست، قبل از = بشکنید و تورفتگی بدهید. سپس قبل از کلیدواژهٔ where بشکنید و بندها را عادی قالب‌بندی کنید:

    // With only a trailing where clause
type VeryLongType<T, U>
    = AnEvenLongerType<T, U, Foo<T>>
where
    T: U::AnAssociatedType,
    U: SomeBound;

    وقتی قبل از نوع یک بند where وجود دارد، آن را عادی قالب‌بندی کنید و بعد از آخرین بند بشکنید. قبل از = تورفتگی ندهید تا از بندهای where که پیش از آن هستند بصری متمایز بماند. اگر بند where پایانی هم وجود دارد، قبل از کلیدواژهٔ where بشکنید و بندها را عادی قالب‌بندی کنید:

    // With only a preceding where clause.
type WithPrecedingWC<T, U>
where
    T: U::AnAssociatedType,
    U: SomeBound,
= AnEvenLongerType<T, U, Foo<T>>;

// Or with both a preceding and trailing where clause.
type WithPrecedingWC<T, U>
where
    T: U::AnAssociatedType,
    U: SomeBound,
= AnEvenLongerType<T, U, Foo<T>>
where
    T: U::AnAssociatedType2,
    U: SomeBound2;

    نوع‌های مرتبط (associated types)

    نوع‌های مرتبط را مانند نام‌های مستعار نوع قالب‌بندی کنید. اگر نوع مرتبط کران دارد، بعد از دونقطه فاصله بگذارید ولی قبل از آن فاصله نگذارید:

    pub type Foo: Bar;

    آیتم‌های extern

    وقتی آیتم‌های extern (مانند extern "C" fn) می‌نویسید، همیشه ABI را مشخص کنید. برای نمونه extern "C" fn foo ... یا unsafe extern "C" { ...} بنویسید و از extern fn foo ... و unsafe extern { ... } پرهیز کنید.

    Importها (دستورهای use)

    تا جای ممکن importها را در یک خط قرار دهید. اطراف آکولادها فاصله نگذارید.

    use a::b::c;
use a::b::d::*;
use a::b::{foo, bar, baz};

    importهای فهرست بزرگ

    ترجیح دهید به‌جای یک import چندخطی از چند import استفاده کنید. با این حال، ابزارها نباید به‌طور پیش‌فرض importها را تقسیم کنند.

    اگر یک import باید در چند خط نوشته شود (چه به این دلیل که فهرست نام‌های تک‌تک از عرض بیشینه بیشتر است و چه به‌خاطر قواعد importهای تودرتو که در ادامه می‌آید)، بعد از آکولاد بازکننده و قبل از آکولاد بسته خط بشکنید، کاما انتهایی بگذارید و نام‌ها را با تورفتگی بلوکی بنویسید:

    // Prefer
foo::{long, list, of, imports};
foo::{more, imports};

// If necessary
foo::{
    long, list, of, imports, more,
    imports,  // Note trailing comma
};

    ترتیب importها

    یک گروه از importها، مجموعه‌ای از importها در همان خط یا خط‌های پشت‌سرهم است. یک یا چند خط خالی، یا آیتم‌های دیگر (مانند یک تابع)، گروه‌های importها را از هم جدا می‌کنند.

    در داخل یک گروه از importها باید به ترتیب مرتب‌سازی نسخه‌ای بچینید. گروه‌های importها نباید ادغام یا دوباره مرتب شوند.

    برای نمونه، ورودی:

    use d;
use c;

use b;
use a;

    خروجی:

    use c;
use d;

use a;
use b;

    به‌دلیل macro_use، ویژگی‌ها (attribute) هم باید یک گروه جدید شروع کنند و مانع جابه‌جایی شوند.

    ترتیب فهرست importها

    نام‌ها در یک فهرست import باید به ترتیب مرتب‌سازی نسخه‌ای باشند، با این استثناها:

    • self و super در صورت وجود همیشه اول می‌آیند، و
    • گروه‌ها و importهای glob همیشه در انتها می‌آیند.

    این قاعده به‌صورت بازگشتی اعمال می‌شود. برای مثال a::* قبل از b::a می‌آید، ولی a::b قبل از a::* می‌آید. برای نمونه: use foo::bar::{a, b::c, b::d, b::d::{x, y, z}, b::{self, r, s}};.

    نرمال‌سازی

    ابزارها باید این نرمال‌سازی‌ها را به‌صورت بازگشتی انجام دهند:

    • use a::self; -> use a;
    • use a::{}; ← (هیچ)
    • use a::{b}; -> use a::b;

    ابزارها نباید بدون گزینهٔ صریح، فهرست‌های import را به شکل دیگری ادغام یا تجزیه کنند، یا importهای glob را تغییر دهند.

    importهای تودرتو

    اگر در یک فهرست import، importهای تودرتو وجود دارد، از قالب چندخطی استفاده کنید، حتی اگر import در یک خط جا شود. هر import تودرتو باید در خط جداگانه‌ای باشد، ولی importهای غیرتودرتو باید تا جای ممکن در خط‌های کمتری گروه‌بندی شوند.

    برای نمونه:

    use a::b::{
    x, y, z,
    u::{...},
    w::{...},
};

    ادغام و تجزیهٔ importها

    یک مثال:

    // Un-merged
use a::b;
use a::c::d;

// Merged
use a::{b, c::d};

    ابزارها به‌طور پیش‌فرض نباید importها را ادغام یا تجزیه کنند. آن‌ها می‌توانند ادغام یا تجزیه را به‌عنوان یک گزینه ارائه دهند.
