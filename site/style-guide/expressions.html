راهنمای سبک RustRust Style Guide

    عبارت‌ها

    بلوک‌ها

    یک عبارت بلوکی باید بعد از { اولیه و قبل از } پایانی یک خط جدید داشته باشد، مگر این‌که طبق یکی از قواعد دیگر بتواند در یک خط نوشته شود.

    کلیدواژه‌ای که قبل از بلوک می‌آید (مانند unsafe یا async) باید در همان خط آکولاد بازکننده باشد، با یک فاصلهٔ واحد بین کلیدواژه و آکولاد بازکننده. محتوای بلوک را تورفتگی دهید.

    fn block_as_stmt() {
    a_call();

    {
        a_call_inside_a_block();

        // a comment in a block
        the_value
    }
}

fn block_as_expr() {
    let foo = {
        a_call_inside_a_block();

        // a comment in a block
        the_value
    };
}

fn unsafe_block_as_stmt() {
    a_call();

    unsafe {
        a_call_inside_a_block();

        // a comment in a block
        the_value
    }
}

    اگر بلوکی ویژگی (attribute) دارد، آن را در خط جداگانه‌ای قبل از بلوک بنویسید:

    fn block_as_stmt() {
    #[an_attribute]
    {
        #![an_inner_attribute]

        // a comment in a block
        the_value
    }
}

    از نوشتن کامنت در همان خط هیچ‌کدام از آکولادها پرهیز کنید.

    بلوک خالی را به‌صورت {} بنویسید.

    یک بلوک را در یک خط بنویسید اگر:

    • در موقعیت عبارت (نه موقعیت دستور) استفاده شده باشد، یا بلوک unsafe در موقعیت دستور باشد،
    • شامل یک عبارت تک‌خطی و بدون دستور باشد، و
    • هیچ کامنتی نداشته باشد.

    برای بلوک تک‌خطی، بعد از آکولاد بازکننده و قبل از آکولاد بسته فاصله بگذارید.

    مثال‌ها:

    fn main() {
    // Single line
    let _ = { a_call() };
    let _ = unsafe { a_call() };

    // Not allowed on one line
    // Statement position.
    {
        a_call()
    }

    // Contains a statement
    let _ = {
        a_call();
    };
    unsafe {
        a_call();
    }

    // Contains a comment
    let _ = {
        // A comment
    };
    let _ = {
        // A comment
        a_call()
    };

    // Multiple lines
    let _ = {
        a_call();
        another_call()
    };
    let _ = {
        a_call(
            an_argument,
            another_arg,
        )
    };
}

    Closureها

    قبل از اولین | فاصلهٔ اضافی نگذارید (مگر این‌که closure با کلیدواژه‌ای مانند move شروع شود)؛ بین دومین | و عبارت closure یک فاصله بگذارید. بین |ها از نحو تعریف تابع استفاده کنید، ولی هر جا ممکن است نوع‌ها را حذف کنید.

    در صورت امکان، closureها را بدون {} اطرافشان بنویسید. در صورتی {} اضافه کنید که نوع بازگشتی دارید، دستور (statement) وجود دارد، داخل closure کامنت هست، یا عبارت بدنه یک عبارت کنترل جریان است که چند خط را در بر می‌گیرد. اگر از آکولاد استفاده می‌کنید، قواعد بالا برای بلوک‌ها را رعایت کنید. مثال‌ها:

    |arg1, arg2| expr

move |arg1: i32, arg2: i32| -> i32 {
    expr1;
    expr2
}

|| Foo {
    field1,
    field2: 0,
}

|| {
    if true {
        blah
    } else {
        boo
    }
}

|x| unsafe {
    expr
}

    لیترال‌های struct

    اگر یک لیترال struct کوچک است، آن را در یک خط قالب‌بندی کنید و کاما انتهایی نگذارید. اگر کوچک نیست، آن را در چند خط تقسیم کنید، هر فیلد را در خط جداگانه‌ای با تورفتگی بلوکی بنویسید و کاما انتهایی بگذارید.

    برای هر ورودی field: value فقط بعد از دونقطه فاصله بگذارید.

    قبل از آکولاد بازکننده فاصله بگذارید. در شکل تک‌خطی، بعد از آکولاد بازکننده و قبل از آکولاد بسته فاصله بگذارید.

    Foo { field1, field2: 0 }
let f = Foo {
    field1,
    field2: an_expr,
};

    به‌روزرسانی رکورد تابعی (functional record update) مانند یک فیلد رفتار می‌شود، ولی هرگز نباید کاما انتهایی داشته باشد. بعد از .. فاصله نگذارید.

    let f = Foo {
    field1,
    ..an_expr
};

    لیترال‌های یکه (unit)

    هرگز بین پرانتز بازکننده و بسته‌کنندهٔ لیترال یکه () خط نشکنید. این حتی وقتی صدق می‌کند که پرانتز بسته از عرض بیشینهٔ خط بگذرد.

    لیترال‌های تاپل

    در صورت امکان از شکل تک‌خطی استفاده کنید. بین پرانتز بازکننده و عنصر اول، و بین آخرین عنصر و پرانتز بسته فاصله نگذارید. عناصر را با کاما و یک فاصله جدا کنید.

    اگر شکل تک‌خطی ممکن نیست، تاپل را در چند خط بنویسید؛ هر عنصر را در خط جداگانه‌ای با تورفتگی بلوکی قرار دهید و کاما انتهایی بگذارید.

    (a, b, c)

let x = (
    a_long_expr,
    another_very_long_expr,
);

    لیترال‌های struct تاپلی

    بین شناسه و پرانتز بازکننده فاصله نگذارید. در غیر این صورت از قواعد لیترال‌های تاپل پیروی کنید:

    Foo(a, b, c)

let x = Foo(
    a_long_expr,
    another_very_long_expr,
);

    لیترال‌های enum

    قواعد قالب‌بندی لیترال‌های مختلف struct را دنبال کنید. ترجیح دهید نام enum را به‌عنوان نام واجد شرایط (qualifying name) به کار ببرید، مگر این‌که enum در prelude باشد:

    Foo::Bar(a, b)
Foo::Baz {
    field1,
    field2: 1001,
}
Ok(an_expr)

    لیترال‌های آرایه

    لیترال‌های کوچک آرایه را در یک خط بنویسید. بین کروشهٔ بازکننده و عنصر اول، و بین آخرین عنصر و کروشهٔ بسته فاصله نگذارید. عناصر را با کاما و یک فاصله جدا کنید.

    اگر از مقداردهی تکراری (repeating initializer) استفاده می‌کنید، فقط بعد از سمی‌کالن فاصله بگذارید.

    همین قواعد را برای vec! یا ماکروهای مشابه آرایه هم اعمال کنید؛ برای این ماکروها همیشه از کروشه استفاده کنید. مثال‌ها:

    fn main() {
    let x = [1, 2, 3];
    let y = vec![a, b, c, d];
    let a = [42; 10];
}

    برای آرایه‌هایی که باید در چند خط شکسته شوند، اگر از مقداردهی تکراری استفاده می‌کنید، بعد از ; بشکنید، نه قبل از آن. در غیر این صورت قواعد فراخوانی توابع را دنبال کنید. در هر حال محتوای مقداردهنده را با تورفتگی بلوکی بنویسید و بعد از کروشهٔ بازکننده و قبل از کروشهٔ بسته خط بشکنید:

    fn main() {
    [
        a_long_expression();
        1234567890
    ]
    let x = [
        an_expression,
        another_expression,
        a_third_expression,
    ];
}

    دسترسی به اندیس‌ها، indexing و slicing

    اطراف کروشه‌ها فاصله نگذارید. تا جای ممکن خط نشکنید. هرگز بین عبارت هدف و کروشهٔ بازکننده خط نشکنید. اگر عبارت اندیس باید در خط بعدی بیاید، یا خودش چند خط است، عبارت اندیس را با تورفتگی بلوکی بنویسید و بعد از کروشهٔ بازکننده و قبل از کروشهٔ بسته خط بشکنید.

    مثال‌ها:

    fn main() {
    foo[42];
    &foo[..10];
    bar[0..100];
    foo[4 + 5 / bar];
    a_long_target[
        a_long_indexing_expression
    ];
}

    عملگرهای یکانی (unary)

    بین یک عملگر یکانی و عملوندش فاصله نگذارید (یعنی !x درست است، نه ! x). اما بعد از &mut باید فاصله باشد. از شکستن خط بین عملگر یکانی و عملوندش پرهیز کنید.

    عملگرهای دودویی (binary)

    اطراف عملگرهای دودویی فاصله بگذارید (یعنی x + 1، نه x+1)؛ این شامل = و عملگرهای انتساب دیگر مانند += یا *= هم می‌شود.

    برای عملگرهای مقایسه، چون برای T op U پیاده‌سازی &T op &U هم وجود دارد: اگر t: &T و u: U داریم، *t op u را به t op &u ترجیح دهید. به‌طور کلی در عبارت‌ها، جز در صورت ضرورت (مثلاً برای پرهیز از یک عملیات بسیار پرهزینه)، dereference کردن را به گرفتن ارجاع ترجیح دهید.

    از پرانتز به‌طور آزادانه استفاده کنید و صرفاً به‌خاطر اولویت آن‌ها را حذف نکنید. ابزارها نباید پرانتز را خودکار اضافه یا حذف کنند. برای نشان دادن اولویت از فاصله استفاده نکنید.

    اگر خط شکسته می‌شود، هر خط بعدی را با تورفتگی بلوکی بنویسید. برای عملگرهای انتساب، بعد از عملگر بشکنید؛ برای سایر عملگرها، عملگر را در خط بعدی قرار دهید. هر زیرعبارت را در خط جداگانه‌ای بگذارید:

    foo_bar
    + bar
    + baz
    + qux
    + whatever

    ترجیح دهید خط را در یک عملگر انتساب (= یا += و غیره) بشکنید تا در سایر عملگرهای دودویی.

    کست‌ها (as)

    کست‌های as را مانند یک عملگر دودویی قالب‌بندی کنید. یعنی همیشه اطراف as فاصله بگذارید، و اگر خط را می‌شکنید، قبل از as بشکنید (هرگز بعد از آن) و خط بعدی را با تورفتگی بلوکی بنویسید. نوع سمت راست را طبق قواعد نوع‌ها قالب‌بندی کنید.

    با این حال، برخلاف سایر عملگرهای دودویی، اگر زنجیره‌ای از کست‌های as نیاز به شکستن خط دارد و شکستن قبل از اولین as کافی است تا بقیه در خط بعد جا شوند، قبل از asهای بعدی نشکنید؛ بلکه همهٔ نوع‌ها را در همان خط نگه دارید:

    let cstr = very_long_expression()
    as *const str as *const [u8] as *const std::os::raw::c_char;

    اگر خط بعدی هنوز به شکستن نیاز دارد، قبل از هر as بشکنید و تورفتگی بلوکی بدهید، همان‌طور که برای سایر عملگرهای دودویی انجام می‌دهید.

    کنترل جریان

    برای عبارت‌های if و while پرانتز اضافی نگذارید.

    if true {
}

    بهتر از کد زیر است:

    if (true) {
}

    است. اما اگر پرانتز به فهم یک عبارت حسابی یا منطقی کمک می‌کند، می‌توانید آن را بگذارید ((x * 15) + (y * 20) اشکالی ندارد).

    فراخوانی توابع

    بین نام تابع و پرانتز بازکننده فاصله نگذارید.

    بین یک آرگومان و کاما‌ی که بعد از آن می‌آید فاصله نگذارید.

    بین یک آرگومان و کاما‌ی که قبل از آن می‌آید فاصله بگذارید.

    ترجیح دهید در عبارت فراخوانشونده (callee) خط نشکنید.

    برای فراخوانی تابع بدون آرگومان (مانند func()) هرگز داخل پرانتزها خط نشکنید و بین پرانتزها فاصله نگذارید. همیشه فراخوانی بدون آرگومان را تک‌خطی بنویسید، نه چندخطی. این حتی وقتی صدق می‌کند که پرانتز بسته از عرض بیشینه بگذرد.

    فراخوانی‌های تک‌خطی

    بین نام تابع و پرانتز بازکننده، بین پرانتز بازکننده و اولین آرگومان، و بین آخرین آرگومان و پرانتز بسته فاصله نگذارید.

    بعد از آخرین آرگومان کاما نگذارید.

    foo(x, y, z)

    فراخوانی‌های چندخطی

    اگر فراخوانی تابع کوچک نیست، یا از عرض بیشینه بیشتر می‌شود، یا هر آرگومان یا فراخوانشونده چندخطی است، فراخوانی را در چند خط بنویسید. در این حالت، هر آرگومان را در خط جداگانه‌ای با تورفتگی بلوکی قرار دهید، بعد از پرانتز بازکننده و قبل از پرانتز بسته خط بشکنید، و کاما انتهایی بگذارید:

    a_function_call(
    arg1,
    a_nested_call(a, b),
)

    فراخوانی متدها

    قواعد فراخوانی توابع را دنبال کنید.

    اطراف . فاصله نگذارید.

    x.foo().bar().baz(x, y, z);

    استفاده از ماکروها

    اگر یک ماکرو را می‌توان مانند سازه‌های دیگر تجزیه کرد، آن را مانند همان سازه‌ها قالب‌بندی کنید. برای مثال، فراخوانی ماکروی foo!(a, b, c) را می‌توان (با نادیده گرفتن !) مانند یک فراخوانی تابع تجزیه کرد، پس با قواعد فراخوانی توابع قالب‌بندی می‌شود.

    راهنمای سبک قالب‌بندی مشخصی برای ماکروهای خاصِ موجود در زبان یا کتابخانهٔ استاندارد تعریف می‌کند. این راهنما قالب‌بندی هیچ ماکرو شخص ثالثی را تعریف نمی‌کند، حتی اگر شبیه ماکروهای زبان یا کتابخانهٔ استاندارد باشد.

    ماکروهای رشتهٔ قالب (format string)

    برای ماکروهایی که یک رشتهٔ قالب می‌گیرند: اگر همهٔ آرگومان‌های دیگر کوچک هستند، آرگومان‌های قبل از رشتهٔ قالب را اگر جا شوند در یک خط بنویسید، و آرگومان‌های بعد از رشتهٔ قالب را اگر جا شوند در یک خط بنویسید، و خود رشتهٔ قالب در خط جداگانه‌ای باشد. اگر آرگومان‌ها کوچک نیستند یا جا نمی‌شوند، هر کدام را مانند یک تابع در خط جداگانه‌ای بگذارید. برای نمونه:

    println!(
    "Hello {} and {}",
    name1, name2,
);

assert_eq!(
    x, y,
    "x and y were not equal, see {}",
    reason,
);

    زنجیره‌های فیلد و فراخوانی متد

    زنجیره دنباله‌ای از دسترسی به فیلد، فراخوانی متد و/یا استفاده از عملگر پرس‌وجو ? است. مثلاً a.b.c().d یا foo?.bar().baz?.

    اگر زنجیره «کوچک» است و امکانش هست، آن را در یک خط بنویسید. اگر در چند خط می‌نویسید، هر دسترسی به فیلد یا فراخوانی متد را در خط جداگانه‌ای قرار دهید، و خط‌شکنی را قبل از . و بعد از هر ? بگذارید. خط‌های بعدی را با تورفتگی بلوکی بنویسید:

    let foo = bar
    .baz?
    .qux();

    اگر طول آخرین خط عنصر اول به‌علاوهٔ تورفتگی آن کمتر یا برابر تورفتگی خط دوم است، و اگر در یک خط جا می‌شوند، خط اول و دوم را ترکیب کنید. این قاعده را به‌صورت بازگشتی اعمال کنید:

    x.baz?
    .qux()

x.y.z
    .qux()

let foo = x
    .baz?
    .qux();

foo(
    expr1,
    expr2,
).baz?
    .qux();

    عناصر چندخطی

    اگر هر عنصری از زنجیره در چند خط نوشته شده، آن عنصر و همهٔ عناصر بعدی‌اش را در خط‌های جداگانه بنویسید.

    a.b.c()?
    .foo(
        an_expr,
        another_expr,
    )
    .bar
    .baz

    توجه کنید که در مثال بالا، به‌خاطر زنجیره و فراخوانی تابع، تورفتگی بلوکی وجود دارد.

    ترجیح دهید کل زنجیره با سبک چندخطی نوشته شود و هر عنصر در یک خط باشد، نه این‌که برخی عناصر چندخطی و برخی تک‌خطی باشند. برای نمونه:

    // Better
self.pre_comment
    .as_ref()
    .map_or(false, |comment| comment.starts_with("//"))

// Worse
self.pre_comment.as_ref().map_or(
    false,
    |comment| comment.starts_with("//"),
)

    عبارت‌های کنترل جریان

    این بخش for و loop و همچنین if و while با زیرعبارت‌هایشان را پوشش می‌دهد. این شامل عبارت‌هایی با یک زیرعبارت let (یعنی if let و while let) و همچنین let-chainها می‌شود: عبارت‌هایی با یک یا چند زیرعبارت let و یک یا چند شرط بولی (مانند if a && let Some(b) = c).

    کلیدواژه، هر بند اولیه و آکولاد بازکنندهٔ بلوک را، اگر جا شوند، در یک خط قرار دهید. قواعد معمول قالب‌بندی بلوک را روی بلوک اعمال کنید.

    اگر بخش else وجود دارد، آکولاد بسته، else، هر بند بعدی و آکولاد بازکننده را در یک خط قرار دهید، با یک فاصلهٔ واحد قبل و بعد از کلیدواژهٔ else:

    if ... {
    ...
} else {
    ...
}

if let ... {
    ...
} else if ... {
    ...
} else {
    ...
}

    اگر خط کنترل باید شکسته شود، برای هر زیرعبارت let در یک if یا while که جا نمی‌شود ترجیح دهید بعد از = بشکنید، و در یک for قبل از in بشکنید؛ خط بعدی باید با تورفتگی بلوکی باشد. اگر خط کنترل به هر دلیلی شکسته شود، آکولاد بازکننده باید در خط جداگانه‌ای و بدون تورفتگی باشد. مثال‌ها:

    while let Some(foo)
    = a_long_expression
{
    ...
}

for foo
    in a_long_expression
{
    ...
}

if a_long_expression
    && another_long_expression
    || a_third_long_expression
{
    ...
}

if let Some(a) = b
    && another_long_expression
    && a_third_long_expression
{
    // ...
}

if let Some(relatively_long_thing)
    = a_long_expression
    && another_long_expression
    && a_third_long_expression
{
    // ...
}

if some_expr
    && another_long_expression
    && let Some(relatively_long_thing) =
        a_long_long_long_long_long_long_really_reallllllllllyyyyyyy_long_expression
    && a_third_long_expression
{
    // ...
}

    خط کنترل یک let-chain مجاز است در یک خط نوشته شود، به شرطی که فقط از دو بند تشکیل شده باشد؛ بند اول (عملوند سمت چپ) یک لیترال یا ident باشد (که می‌تواند قبل از آن هر تعداد عملگر یکانی پیشوندی بیاید)، و بند دوم (عملوند سمت راست) یک بند let تک‌خطی باشد. در غیر این صورت، خط کنترل باید طبق قواعد بالا شکسته و قالب‌بندی شود. برای نمونه:

    if a && let Some(b) = foo() {
    // ...
}

if true && let Some(b) = foo() {
    // ...
}

let operator = if !from_hir_call && let Some(p) = parent {
    // ...
};

if let Some(b) = foo()
    && a
{
    // ..
}

if foo()
    && let Some(b) = bar
{
    // ...
}

if gen_pos != GenericArgPosition::Type
    && let Some(b) = gen_args.bindings.first()
{
    // ..
}

    جایی که بند اولیه در چند خط است و با یک یا چند پرانتز بسته، کروشهٔ بسته یا آکولاد بسته تمام می‌شود، و در آن خط چیز دیگری نیست، و آن خط بیشتر از تورفتگی خط اول عبارت کنترل جریان تورفتگی ندارد، آکولاد بازکنندهٔ بلوک را با یک فاصله در همان خط قرار دهید. برای نمونه:

    if !self.config.file_lines().intersects(
    &self.codemap.lookup_line_range(
        stmt.span,
    ),
) {  // Opening brace on same line as initial clause.
    ...
}

    if else تک‌خطی

    یک if else یا if let else را اگر در بافت عبارت است (یعنی دستور مستقل نیست)، یک بند else دارد و کوچک است، در یک خط قرار دهید:

    let y = if x { 0 } else { 1 };

// Examples that must be multi-line.
let y = if something_very_long {
    not_small
} else {
    also_not_small
};

if x {
    0
} else {
    1
}

    Match

    ترجیح دهید در عبارت جداکننده (discriminant) خط نشکنید. همیشه بعد از آکولاد بازکننده و قبل از آکولاد بسته خط بشکنید. بازوهای match را یک‌بار تورفتگی بلوکی دهید:

    match foo {
    // arms
}

let x = match foo.bar.baz() {
    // arms
};

    برای یک بازوی match فقط در صورتی کاما انتهایی بگذارید که از بلوک استفاده نکرده باشد.

    هرگز الگوی یک بازوی match را با | شروع نکنید:

    match foo {
    // Don't do this.
    | foo => bar,
    // Or this.
    | a_very_long_pattern
    | another_pattern
    | yet_another_pattern
    | a_fourth_pattern => {
        ...
    }
}

    ترجیح دهید:

    match foo {
    foo => bar,
    a_very_long_pattern
    | another_pattern
    | yet_another_pattern
    | a_fourth_pattern => {
        ...
    }
}

    از شکستن سمت چپ (قبل از =>) یک بازوی match تا جای ممکن پرهیز کنید. اگر سمت راست بازو در همان خط سمت چپ می‌ماند، هرگز از بلوک استفاده نکنید (مگر بلوک خالی باشد).

    اگر سمت راست از چند دستور تشکیل شده، یا کامنت خطی دارد، یا شروع آن در همان خط سمت چپ جا نمی‌شود، از بلوک استفاده کنید. بلوکی که شامل یک فراخوانی ماکروی تکی است را تخت نکنید، چون ممکن است گسترش آن یک سمی‌کالن انتهایی داشته باشد.

    بدنهٔ بازوی بلوکی را با تورفتگی بلوکی بنویسید.

    مثال‌ها:

    match foo {
    foo => bar,
    a_very_long_pattern | another_pattern if an_expression() => {
        no_room_for_this_expression()
    }
    foo => {
        // A comment.
        an_expression()
    }
    foo => {
        let a = statement();
        an_expression()
    }
    bar => {}
    // Trailing comma on last item.
    foo => bar,
    baz => qux!(),
    lorem => {
        ipsum!()
    }
}

    اگر بدنه یک عبارت تکی بدون کامنت خطی و غیرکنترل‌جریانی است، آن را در همان خط سمت چپ شروع کنید. اگر نه، باید در بلوک باشد. مثال:

    match foo {
    // A combinable expression.
    foo => a_function_call(another_call(
        argument1,
        argument2,
    )),
    // A non-combinable expression
    bar => {
        a_function_call(
            another_call(
                argument1,
                argument2,
            ),
            another_argument,
        )
    }
}

    شکستن خط

    اگر استفاده از شکل بلوکی در سمت راست بازوی match امکان می‌دهد از شکستن سمت چپ اجتناب شود، این کار را بکنید:

        // Assuming the following line does not fit in the max width
    a_very_long_pattern | another_pattern => ALongStructName {
        ...
    },
    // Prefer this
    a_very_long_pattern | another_pattern => {
        ALongStructName {
            ...
        }
    }
    // To splitting the pattern.

    هرگز بعد از => بدون استفاده از شکل بلوکی بدنه نشکنید.

    اگر سمت چپ باید شکسته شود و یک بند if وجود دارد، قبل از if بشکنید و تورفتگی بلوکی بدهید. در این حالت همیشه از بدنهٔ بلوکی استفاده کنید و بدنه را در خط جدید شروع کنید:

        a_very_long_pattern | another_pattern
        if expr =>
    {
        ...
    }

    اگر الگو باید شکسته شود، هر بند الگو را در خط جداگانه‌ای و بدون تورفتگی اضافی قرار دهید، و قبل از | بشکنید. اگر بند if وجود دارد، از شکل بالا استفاده کنید:

        a_very_long_pattern
    | another_pattern
    | yet_another_pattern
    | a_forth_pattern => {
        ...
    }
    a_very_long_pattern
    | another_pattern
    | yet_another_pattern
    | a_forth_pattern
        if expr =>
    {
        ...
    }

    اگر الگو چندخطی است و خط آخرش از تورفتگی کمتر است، بند if را در خط جدید قرار ندهید. مثلاً:

        Token::Dimension {
         value,
         ref unit,
         ..
    } if num_context.is_ok(context.parsing_mode, value) => {
        ...
    }

    اگر هر بند در یک الگو کوچک است، ولی کل الگو در یک خط جا نمی‌شود، الگو را در چند خط قرار دهید و تا جای ممکن بندها را در هر خط جای دهید. باز هم قبل از | بشکنید:

        foo | bar | baz
    | qux => {
        ...
    }

    ما یک بند الگو را کوچک تعریف می‌کنیم اگر در یک خط جا شود و با گرامر «کوچک» زیر مطابقت داشته باشد:

    small:
    - small_no_tuple
    - unary tuple constructor: `(` small_no_tuple `,` `)`
    - `&` small

small_no_tuple:
    - single token
    - `&` small_no_tuple

    مثلاً &&Some(foo) مطابقت دارد، ولی Foo(4, Bar) ندارد.

    عبارت‌های ترکیب‌پذیر

    اگر یک فراخوانی تابع یک آرگومان دارد و آن آرگومان در چند خط با تورفتگی بلوکی نوشته شده، فراخوانی بیرونی را مانند یک فراخوانی تک‌خطی قالب‌بندی کنید، به شرطی که نتیجه جا شود. همین رفتار ترکیبی را برای هر عبارت مشابه که فهرستی از زیرعبارت‌ها در پرانتز و با تورفتگی بلوکی دارد اعمال کنید (مثلاً ماکروها یا لیترال‌های struct تاپلی). برای نمونه:

    foo(bar(
    an_expr,
    another_expr,
))

let x = foo(Bar {
    field: whatever,
});

foo(|param| {
    action();
    foo(param)
})

let x = combinable([
    an_expr,
    another_expr,
]);

let arr = [combinable(
    an_expr,
    another_expr,
)];

    این رفتار را به‌صورت بازگشتی اعمال کنید.

    برای تابعی با چند آرگومان، اگر آخرین آرگومان یک closure چندخطی با بلوک صریح است، هیچ آرگومان closure دیگری نیست، و همهٔ آرگومان‌ها و خط اول closure در یک خط جا می‌شوند، از همان رفتار ترکیبی استفاده کنید:

    foo(first_arg, x, |param| {
    action();
    foo(param)
})

    بازه‌ها (ranges)

    در بازه‌ها فاصله نگذارید، مثلاً 0..10، x..=y، ..x.len()، foo...

    وقتی بازه‌ای هم کران پایین و هم کران بالا دارد و خط باید داخل بازه شکسته شود، قبل از عملگر بازه بشکنید و خط دوم را با تورفتگی بلوکی بنویسید:

    a_long_expression
    ..another_long_expression

    برای نشان دادن اولویت، اگر یکی از کران‌ها عبارت مرکب است، دور آن پرانتز بگذارید، مثلاً ..(x + 1)، (x.f)..(x.f.len()) یا 0..(x - 10).

    لیترال‌های هگزادسیمال

    لیترال‌های هگزادسیمال ممکن است حروف بزرگ یا کوچک داشته باشند، ولی نباید در یک لیترال با هم ترکیب شوند. پروژه‌ها باید برای همهٔ لیترال‌ها از یک حالت استفاده کنند، ولی ما برای حروف کوچک یا بزرگ توصیه‌ای نداریم.

    الگوها (patterns)

    الگوها را مانند عبارت‌های متناظرشان قالب‌بندی کنید. برای قالب‌بندی بیشتر الگوها در بازوهای match، بخش مربوط به match را ببینید.
