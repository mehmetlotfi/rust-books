    رفتارهای تعریف‌نشده

    [undefined.intro]

    اگر کد Rust هر یک از رفتارهای فهرست زیر را از خود نشان دهد، نادرست است. این شامل کد درون بلوک‌های unsafe و تابع‌های unsafe نیز می‌شود. unsafe فقط به این معناست که پرهیز از رفتار تعریف‌نشده بر عهدهٔ برنامه‌نویس است؛ این موضوع هیچ تغییری در این واقعیت نمی‌دهد که برنامه‌های Rust هرگز نباید رفتار تعریف‌نشده ایجاد کنند.

    [undefined.soundness]

    هنگام نوشتن کد unsafe، برنامه‌نویس مسئول است اطمینان یابد هر کد ایمنی که با کد unsafe تعامل دارد نمی‌تواند این رفتارها را برانگیزد. کد unsafe که این ویژگی را برای هر کلاینت ایمن برآورده کند، صحیح (sound) نامیده می‌شود؛ اگر کد unsafe بتواند توسط کد ایمن چنان مورد سوءاستفاده قرار گیرد که رفتار تعریف‌نشده نشان دهد، ناصحیح (unsound) است.

    Warning

    هشدار فهرست زیر جامع نیست و ممکن است بزرگ‌تر یا کوچک‌تر شود. مدل رسمی‌ای از معنای Rust برای تعیین همهٔ اعمال مجاز و غیرمجاز در کد ناامن وجود ندارد؛ بنابراین شاید رفتارهای ناامن دیگری نیز باشند. همچنین ممکن است برخی رفتارهای این فهرست در آینده تعریف‌شده شوند. پس این فهرست نمی‌گوید چیزی در تمام نسخه‌های آیندهٔ Rust قطعاً همیشه تعریف‌نشده خواهد بود، هرچند ممکن است در آینده دربارهٔ بعضی موارد چنین تعهدی بدهیم.

    پیش از نوشتن کد ناامن، Rustonomicon را بخوانید.

    [undefined.race]
    • رقابت داده‌ای.
    [undefined.pointer-access]
    • دسترسی—بارگذاری یا ذخیره‌سازی—به مکانی که آویزان است یا بر اشاره‌گر ناهم‌تراز مبتنی است.
    [undefined.place-projection]
    • اجرای تصویرسازی مکان با offset که الزامات حساب اشاره‌گر درون محدوده را نقض کند. این تصویرسازی شامل عبارت فیلد، عبارت نمایهٔ تاپل یا عبارت نمایهٔ آرایه/برش است.
    [undefined.alias]

    • شکستن قواعد نام مستعار اشاره‌گر. قواعد دقیق هنوز تعیین نشده‌اند، اما اصول کلی چنین‌اند:

      • &T باید به حافظه‌ای اشاره کند که تا زمان زنده‌بودن ارجاع تغییر نمی‌کند، به‌جز دادهٔ درون UnsafeCell<U>.
      • &mut T باید به حافظه‌ای اشاره کند که تا زمان زنده‌بودن ارجاع، هیچ اشاره‌گر مشتق‌نشده از آن نخواند یا ننویسد و هیچ ارجاع دیگری به آن اشاره نکند، بدون استثنا.
      • برای این قواعد، با Box<T> مشابه &'static mut T رفتار می‌شود.

      این قواعد بر همهٔ ارجاع‌ها و Box<T>ها اعمال می‌شوند، حتی موارد ذخیره‌شده در فیلدهای خصوصی. برای نمونه، اگر نوع شما فیلد خصوصی &mut T دارد، آن ارجاع باید تا زمانی که مقادیر نوع زنده‌اند به معنای بالا یکتا باشد.

      مدت دقیق زنده‌بودن مشخص نشده، اما کران‌هایی دارد:

      • برای ارجاع‌ها، طول این مدت حداکثر طول‌عمر نحوی تخصیص‌یافته توسط بررسی‌کنندهٔ قرض است و نمی‌تواند از آن طولانی‌تر باشد.
      • هر بار ارجاع یا box ارجاع‌زدایی یا دوباره قرض گرفته شود، زنده در نظر گرفته می‌شود.
      • هر بار ارجاع یا box به تابع داده یا از آن بازگردانده شود، زنده در نظر گرفته می‌شود.
      • وقتی ارجاع—اما نه Box—به تابع داده می‌شود، دست‌کم به‌اندازهٔ فراخوانی تابع زنده است؛ باز هم به‌جز وقتی &T دارای UnsafeCell<U> باشد.

      همهٔ این موارد هنگام عبور مقادیر این نوع‌ها در فیلد تودرتوی یک نوع مرکب نیز اعمال می‌شوند، اما پشت غیرمستقیم‌سازی اشاره‌گر اعمال نمی‌شوند.

    [undefined.immutable]

    • تغییردادن بایت‌های تغییرناپذیر. همهٔ بایت‌های دسترس‌پذیر از عبارت ارتقایافتهٔ const و بایت‌های دسترس‌پذیر از قرض‌ها در مقداردهنده‌های اولیهٔ static و const که طول‌عمرشان تا 'static گسترش یافته، تغییرناپذیرند. بایت‌های متعلق به اتصال تغییرناپذیر یا static تغییرناپذیر نیز تغییرناپذیرند، مگر بخش درون UnsafeCell<U>.

      افزون بر این، بایت‌هایی که ارجاع اشتراکی به آن‌ها اشاره می‌کند، حتی به‌طور تعدی از راه ارجاع‌های دیگر—اشتراکی یا تغییرپذیر—و Boxها، تغییرناپذیرند. تعدی شامل ارجاع‌های ذخیره‌شده در فیلدهای نوع مرکب نیز می‌شود.

      تغییر (mutation) هر نوشتنِ بیش از ۰ بایت است که با هر یک از بایت‌های مرتبط هم‌پوشانی داشته باشد (حتی اگر آن نوشتن محتوای حافظه را تغییر ندهد).

    [undefined.intrinsic]
    • فراخواندن رفتار تعریف‌نشده از طریق intrinsicهای کامپایلر.
    [undefined.target-feature]
    • اجرای کد کامپایل‌شده با قابلیت‌های سکویی که سکوی جاری پشتیبانی نمی‌کند؛ target_feature را ببینید. استثنا زمانی است که سکو صریحاً ایمن‌بودن آن را مستند کرده باشد.
    [undefined.call]
    • فراخوانی تابع با ABI فراخوانی نادرست، یا بازکردن پشته از قاب پشته‌ای که اجازهٔ unwind ندارد؛ برای نمونه فراخوانی تابع "C-unwind" واردشده یا تبدیل‌شده به‌عنوان تابع یا اشاره‌گر تابع "C".
    [undefined.invalid]
    • تولید مقدار نامعتبر. «تولید» هر زمان رخ می‌دهد که مقدار به مکانی نسبت داده یا از آن خوانده شود، به تابع/عملیات ابتدایی داده شود یا از آن بازگردد.
    [undefined.asm]
    • استفادهٔ نادرست از اسمبلی درون‌خطی. برای جزئیات، قواعد نوشتن کد اسمبلی درون‌خطی را ببینید.
    [undefined.runtime]
    • نقض فرض‌های محیط زمان اجرای Rust. بیشتر این فرض‌ها اکنون صریحاً مستند نشده‌اند.
      • فرض‌های مربوط به بازکردن پشته در مستندات panic آمده‌اند.
      • محیط زمان اجرا فرض می‌کند قاب پشتهٔ Rust بدون اجرای ویرانگر متغیرهای محلی متعلق به آن آزاد نمی‌شود. تابع‌های C مانند longjmp می‌توانند این فرض را نقض کنند.

    Note

    نکته رفتار تعریف‌نشده بر کل برنامه اثر می‌گذارد. برای مثال، فراخوانی تابع C دارای رفتار تعریف‌نشدهٔ C یعنی کل برنامهٔ شما رفتار تعریف‌نشده دارد و کد Rust نیز ممکن است متأثر شود. برعکس، رفتار تعریف‌نشده در Rust نیز می‌تواند بر کدی که فراخوانی‌های FFI در زبان‌های دیگر اجرا می‌کنند اثر منفی بگذارد.

    [undefined.pointed-to]

    بایت‌های مورد اشاره

    بازهٔ بایت‌هایی که اشاره‌گر یا ارجاع «به آن اشاره می‌کند»، با مقدار اشاره‌گر و اندازهٔ نوع مورد اشاره—با size_of_val—تعیین می‌شود.

    [undefined.misaligned]

    مکان‌های مبتنی بر اشاره‌گر ناهم‌تراز

    [undefined.misaligned.ptr]

    مکان زمانی «مبتنی بر اشاره‌گر ناهم‌تراز» است که آخرین تصویرسازی * هنگام محاسبهٔ مکان روی اشاره‌گری انجام شده باشد که برای نوعش هم‌تراز نیست. اگر عبارت مکان تصویرسازی * نداشته باشد، دسترسی به فیلد یک متغیر محلی یا static است و rustc هم‌ترازی درست را تضمین می‌کند. اگر چند تصویرسازی * باشد، هرکدام بارگذاری خود اشاره‌گر مورد ارجاع‌زدایی از حافظه را در پی دارد و هر بارگذاری مشمول قید هم‌ترازی است. بعضی تصویرسازی‌های * به‌دلیل ارجاع‌زدایی خودکار در نحو ظاهری Rust حذف می‌شوند؛ اینجا عبارت مکان کاملاً گسترش‌یافته را در نظر می‌گیریم.

    برای نمونه، اگر ptr نوع *const S و S هم‌ترازی ۸ داشته باشد، ptr باید هم‌تراز با ۸ باشد؛ وگرنه (*ptr).f مبتنی بر اشاره‌گر ناهم‌تراز است. این حکم حتی اگر نوع فیلد f برابر u8 با هم‌ترازی ۱ باشد برقرار است. یعنی الزام هم‌ترازی از نوع اشاره‌گر ارجاع‌زدایی‌شده می‌آید، نه نوع فیلد مورد دسترسی.

    [undefined.misaligned.load-store]

    مکان مبتنی بر اشاره‌گر ناهم‌تراز فقط هنگام بارگذاری از آن یا ذخیره در آن به رفتار تعریف‌نشده منجر می‌شود.

    [undefined.misaligned.raw]

    استفاده از &raw const یا &raw mut روی چنین مکانی مجاز است.

    [undefined.misaligned.reference]

    استفاده از & یا &mut روی مکان، هم‌ترازی نوع فیلد را لازم دارد؛ وگرنه برنامه «مقدار نامعتبر تولید می‌کند». این الزام عموماً از مبتنی‌بودن بر اشاره‌گر هم‌تراز محدودیت کمتری دارد.

    [undefined.misaligned.packed]

    اگر نوع فیلد ممکن است از نوع دربرگیرنده هم‌ترازتر باشد، یعنی در repr(packed)، گرفتن ارجاع به خطای کامپایلر منجر می‌شود. پس مبتنی‌بودن بر اشاره‌گر هم‌تراز همیشه برای تضمین هم‌ترازی ارجاع جدید کافی است، اما همیشه ضروری نیست.

    [undefined.dangling]

    اشاره‌گرهای آویزان

    [undefined.dangling.def]

    ارجاع/اشاره‌گر زمانی «آویزان» است که همهٔ بایت‌هایی که به آن‌ها اشاره می‌کند بخشی از یک تخصیص زندهٔ واحد نباشند؛ بنابراین همه باید بخشی از یک تخصیص باشند.

    Note

    این به آن معناست که اندازهٔ پویای یک مقدار Rust (که با size_of_val تعیین می‌شود) هرگز نباید از isize::MAX بیشتر باشد، زیرا غیرممکن است که یک تخصیص واحد از isize::MAX بزرگ‌تر باشد.

    Note

    این همچنین به آن معناست که اگر اندازه ۰ باشد، آنگاه اشاره‌گر به‌طور بدیهی هرگز «آویزان» (dangling) نیست (حتی اگر اشاره‌گر null باشد).

    [undefined.validity]

    مقادیر نامعتبر

    [undefined.validity.def]

    کامپایلر Rust فرض می‌کند همهٔ مقادیر تولیدشده هنگام اجرای برنامه «معتبرند»؛ پس تولید مقدار نامعتبر فوراً رفتار تعریف‌نشده است.

    اعتبار مقدار به نوع آن بستگی دارد:

    [undefined.validity.bool]
    • مقدار bool باید false (0) یا true (1) باشد.
    [undefined.validity.fn-pointer]
    • مقدار اشاره‌گر fn نباید null باشد.
    [undefined.validity.char]
    • مقدار char نباید surrogate باشد، یعنی در بازهٔ 0xD800..=0xDFFF قرار گیرد، و باید کوچک‌تر یا مساوی char::MAX باشد.
    [undefined.validity.never]
    • مقدار ! هرگز نباید وجود داشته باشد.
    [undefined.validity.scalar]
    • عدد صحیح (i*/u*)، مقدار ممیز شناور (f*) یا اشاره‌گر خام باید مقداردهی اولیه شده باشد و از حافظهٔ مقداردهی‌نشده به‌دست نیاید.
    [undefined.validity.str]
    • با مقدار str مانند [u8] رفتار می‌شود و باید مقداردهی اولیه شده باشد.
    [undefined.validity.enum]
    • یک enum باید ممیز معتبر داشته باشد و همهٔ فیلدهای گونه‌ای که ممیز نشان می‌دهد باید برای نوع خود معتبر باشند.
    [undefined.validity.struct]
    • در struct، تاپل و آرایه، همهٔ فیلدها/عناصر باید برای نوع خود معتبر باشند.
    [undefined.validity.union]
    • الزامات دقیق اعتبار union هنوز تعیین نشده است. بدیهی است همهٔ مقادیری که کاملاً با کد ایمن ساخته می‌شوند معتبرند. اگر union فیلدی با اندازهٔ صفر داشته باشد، هر مقدار ممکن معتبر است. جزئیات بیشتر هنوز در حال بحث است.
    [undefined.validity.reference-box]
    • ارجاع یا Box<T> باید هم‌تراز و غیر-null باشد، نمی‌تواند آویزان باشد و باید به مقداری معتبر اشاره کند. برای نوع‌های با اندازهٔ پویا، نوع پویای واقعی مورد اشاره که فراداده تعیین می‌کند استفاده می‌شود. نکتهٔ آخر دربارهٔ اشاره به مقدار معتبر همچنان محل بحث است.
    [undefined.validity.wide]

    • فرادادهٔ ارجاع پهن، Box<T> یا اشاره‌گر خام باید با نوع دنبالهٔ بدون اندازه مطابقت داشته باشد:

      • فرادادهٔ dyn Trait باید اشاره‌گری به vtable تولیدشده توسط کامپایلر برای Trait باشد. دربارهٔ اشاره‌گرهای خام، این الزام همچنان محل بحث است.
      • فرادادهٔ برش ([T]) و str باید یک usize معتبر باشد.

      افزون بر این، برای ارجاع پهن یا Box<T>، اگر فراداده اندازهٔ کل مقدار مورد اشاره را طبق size_of_val از isize::MAX بزرگ‌تر کند نامعتبر است.

      Note

      نکته این کران روی اندازهٔ کل مقدار مورد اشاره است، نه فقط دنبالهٔ بدون اندازهٔ آن؛ و فرادادهٔ dyn Trait را همانند طول برش یا str محدود می‌کند. vtable معتبر نوع حذف‌شده‌ای را توصیف می‌کند که از isize::MAX بزرگ‌تر نیست، اما پیشوند اندازه‌دار همچنان می‌تواند مجموع را از حد عبور دهد.

    [undefined.validity.valid-range]

    • اگر نوع بازهٔ معتبر سفارشی داشته باشد، مقدار معتبر باید در همان بازه باشد. در کتابخانهٔ استاندارد این موضوع بر NonNull<T> و NonZero<T> اثر دارد.

      Note

      نکته rustc این کار را با ویژگی‌های ناپایدار rustc_layout_scalar_valid_range_* انجام می‌دهد.

    [undefined.validity.const-provenance]

    • در بافت‌های const: افزون بر موارد بالا، هنگام ارزیابی const الزام‌های بیشتری دربارهٔ منشأ اعمال می‌شود. هر مقدار دارای دادهٔ صحیح خالص—نوع‌های i*/u*/f* و نیز bool و char، ممیزهای enum و فرادادهٔ برش—نباید هیچ منشأیی داشته باشد. مقدار دارای دادهٔ اشاره‌گر—ارجاع، اشاره‌گر خام، اشاره‌گر تابع و فرادادهٔ dyn Trait—یا نباید منشأ داشته باشد، یا همهٔ بایت‌هایش باید به‌ترتیب درست قطعات همان مقدار اشاره‌گر اصلی باشند.

      در نتیجه، تبدیل یا بازتفسیر اشاره‌گر دارای منشأ—ارجاع، اشاره‌گر خام یا اشاره‌گر تابع—به نوع غیر اشاره‌گر مانند عدد صحیح، رفتار تعریف‌نشده است.

      مثال همهٔ موارد زیر رفتار تعریف‌نشده‌اند:

      use core::mem::MaybeUninit;
use core::ptr;
// We cannot reinterpret a pointer with provenance as an integer,
// as then the bytes of the integer will have provenance.
const _: usize = {
    let ptr = &0;
    unsafe { (&raw const ptr as *const usize).read() }
};

// We cannot rearrange the bytes of a pointer with provenance and
// then interpret them as a reference, as then a value holding
// pointer data will have pointer fragments in the wrong order.
const _: &i32 = {
    let mut ptr = &0;
    let ptr_bytes = &raw mut ptr as *mut MaybeUninit::<u8>;
    unsafe { ptr::swap(ptr_bytes.add(1), ptr_bytes.add(2)) };
    ptr
};
    [undefined.validity.undef]

    نکته: حافظهٔ مقداردهی‌نشده برای هر نوعی که مجموعهٔ مقادیر معتبر محدود دارد نیز به‌طور ضمنی نامعتبر است. یعنی تنها موارد مجاز خواندن حافظهٔ مقداردهی‌نشده، درون unionها و «padding»—شکاف میان فیلدهای یک نوع—هستند.
