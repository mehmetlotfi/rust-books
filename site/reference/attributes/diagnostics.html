    [attributes.diagnostics]

    ویژگی‌های تشخیصی

    [attributes.diagnostics.intro]

    ویژگی‌های زیر برای کنترل یا تولید پیام‌های تشخیصی هنگام کامپایل به کار می‌روند.

    [attributes.diagnostics.lint]

    ویژگی‌های بررسی Lint

    [attributes.diagnostics.lint.intro]

    هر بررسی lint یک الگوی کدنویسی بالقوه نامطلوب، مانند کد دسترس‌ناپذیر یا مستندسازی حذف‌شده، را نام‌گذاری می‌کند.

    [attributes.diagnostics.lint.level]

    ویژگی‌های lint یعنی allow، expect، warn، deny و forbid از نحو MetaListPaths استفاده می‌کنند تا فهرستی از نام‌های lint را مشخص کنند که سطحشان برای موجودیتی که ویژگی روی آن اعمال شده تغییر می‌کند.

    برای هر بررسی lint با نام C:

    [attributes.diagnostics.lint.allow]
    • #[allow(C)] بررسی C را بازنویسی می‌کند تا تخلف‌ها گزارش نشوند.
    [attributes.diagnostics.lint.expect]
    • #[expect(C)] نشان می‌دهد انتظار می‌رود lint نوع C صادر شود. این ویژگی صدور C را سرکوب می‌کند، یا اگر انتظار برآورده نشود هشدار می‌دهد.
    [attributes.diagnostics.lint.warn]
    • #[warn(C)] دربارهٔ تخلف‌های C هشدار می‌دهد، اما کامپایل را ادامه می‌دهد.
    [attributes.diagnostics.lint.deny]
    • #[deny(C)] پس از برخورد با تخلف C خطا می‌دهد.
    [attributes.diagnostics.lint.forbid]
    • #[forbid(C)] همان deny(C) است، اما تغییر سطح lint در ادامه را نیز ممنوع می‌کند.

    Note

    نکته بررسی‌های lint پشتیبانی‌شده در rustc همراه با تنظیمات پیش‌فرضشان از طریق rustc -W help قابل مشاهده‌اند و در کتاب rustc مستند شده‌اند.

    pub mod m1 {
    // Missing documentation is ignored here
    #[allow(missing_docs)]
    pub fn undocumented_one() -> i32 { 1 }

    // Missing documentation signals a warning here
    #[warn(missing_docs)]
    pub fn undocumented_too() -> i32 { 2 }

    // Missing documentation signals an error here
    #[deny(missing_docs)]
    pub fn undocumented_end() -> i32 { 3 }
}
    [attributes.diagnostics.lint.override]

    ویژگی‌های lint می‌توانند سطح مشخص‌شده به‌وسیلهٔ ویژگی قبلی را بازنویسی کنند، به شرط آنکه سطح جدید در پی تغییر lint ممنوع‌شده‌ای نباشد؛ deny استثناست که در بافت forbid مجاز ولی نادیده گرفته می‌شود. ویژگی‌های قبلی، ویژگی‌هایی در سطح بالاتر در درخت نحو یا ویژگی‌های پیشین همان موجودیت به‌ترتیب چپ به راست در منبع‌اند.

    نمونهٔ زیر نشان می‌دهد چگونه می‌توان با allow و warn یک بررسی معین را خاموش و روشن کرد:

    #[warn(missing_docs)]
pub mod m2 {
    #[allow(missing_docs)]
    pub mod nested {
        // Missing documentation is ignored here
        pub fn undocumented_one() -> i32 { 1 }

        // Missing documentation signals a warning here,
        // despite the allow above.
        #[warn(missing_docs)]
        pub fn undocumented_two() -> i32 { 2 }
    }

    // Missing documentation signals a warning here
    pub fn undocumented_too() -> i32 { 3 }
}

    نمونهٔ بعد نشان می‌دهد چگونه می‌توان با forbid استفاده از allow یا expect را برای آن بررسی lint ممنوع کرد:

    #[forbid(missing_docs)]
pub mod m3 {
    // Attempting to toggle warning signals an error here
    #[allow(missing_docs)]
    /// Returns 2.
    pub fn undocumented_too() -> i32 { 2 }
}

    Note

    نکته rustc تنظیم سطح lint از خط فرمان و نیز گذاشتن سقف روی lintهای گزارش‌شده را پشتیبانی می‌کند.

    [attributes.diagnostics.lint.reason]

    دلیل Lint

    همهٔ ویژگی‌های lint پارامتر افزودهٔ reason را می‌پذیرند تا علت افزودن ویژگی را توضیح دهند. اگر lint در سطح تعریف‌شده صادر شود، این دلیل به‌عنوان بخشی از پیام lint نمایش داده می‌شود.

    // `keyword_idents` is allowed by default. Here we deny it to
// avoid migration of identifiers when we update the edition.
#![deny(
    keyword_idents,
    reason = "we want to avoid these idents to be future compatible"
)]

// This name was allowed in Rust's 2015 edition. We still aim to avoid
// this to be future compatible and not confuse end users.
fn dyn() {}

    در نمونهٔ دیگری، lint با ذکر دلیل مجاز شده است:

    use std::path::PathBuf;

pub fn get_path() -> PathBuf {
    // The `reason` parameter on `allow` attributes acts as documentation for the reader.
    #[allow(unused_mut, reason = "this is only modified on some platforms")]
    let mut file_name = PathBuf::from("git");

    #[cfg(target_os = "windows")]
    file_name.set_extension("exe");

    file_name
}
    [attributes.diagnostics.expect]

    ویژگی #[expect]

    [attributes.diagnostics.expect.intro]

    ویژگی #[expect(C)] برای lint نوع C یک انتظار lint می‌سازد. اگر ویژگی #[warn(C)] در همان محل به صدور lint می‌انجامید، انتظار برآورده می‌شود. اگر چون C صادر نمی‌شد انتظار برآورده نشود، lint نوع unfulfilled_lint_expectations در محل ویژگی صادر خواهد شد.

    fn main() {
    // This `#[expect]` attribute creates a lint expectation, that the `unused_variables`
    // lint would be emitted by the following statement. This expectation is
    // unfulfilled, since the `question` variable is used by the `println!` macro.
    // Therefore, the `unfulfilled_lint_expectations` lint will be emitted at the
    // attribute.
    #[expect(unused_variables)]
    let question = "who lives in a pineapple under the sea?";
    println!("{question}");

    // This `#[expect]` attribute creates a lint expectation that will be fulfilled, since
    // the `answer` variable is never used. The `unused_variables` lint, that would usually
    // be emitted, is suppressed. No warning will be issued for the statement or attribute.
    #[expect(unused_variables)]
    let answer = "SpongeBob SquarePants!";
}
    [attributes.diagnostics.expect.fulfillment]

    انتظار lint تنها با صدور lintهایی برآورده می‌شود که ویژگی expect آن‌ها را سرکوب کرده باشد. اگر سطح lint در دامنه با ویژگی‌های سطح دیگری مانند allow یا warn تغییر کند، صدور lint مطابق آن ویژگی پردازش می‌شود و انتظار برآورده‌نشده باقی می‌ماند.

    #[expect(unused_variables)]
fn select_song() {
    // This will emit the `unused_variables` lint at the warn level
    // as defined by the `warn` attribute. This will not fulfill the
    // expectation above the function.
    #[warn(unused_variables)]
    let song_name = "Crab Rave";

    // The `allow` attribute suppresses the lint emission. This will not
    // fulfill the expectation as it has been suppressed by the `allow`
    // attribute and not the `expect` attribute above the function.
    #[allow(unused_variables)]
    let song_creator = "Noisestorm";

    // This `expect` attribute will suppress the `unused_variables` lint emission
    // at the variable. The `expect` attribute above the function will still not
    // be fulfilled, since this lint emission has been suppressed by the local
    // expect attribute.
    #[expect(unused_variables)]
    let song_version = "Monstercat Release";
}
    [attributes.diagnostics.expect.independent]

    اگر ویژگی expect چند lint داشته باشد، انتظار هر کدام جداگانه سنجیده می‌شود. برای گروه lint کافی است یکی از lintهای درون گروه صادر شده باشد:

    // This expectation will be fulfilled by the unused value inside the function
// since the emitted `unused_variables` lint is inside the `unused` lint group.
#[expect(unused)]
pub fn thoughts() {
    let unused = "I'm running out of examples";
}

pub fn another_example() {
    // This attribute creates two lint expectations. The `unused_mut` lint will be
    // suppressed and with that fulfill the first expectation. The `unused_variables`
    // wouldn't be emitted, since the variable is used. That expectation will therefore
    // be unsatisfied, and a warning will be emitted.
    #[expect(unused_mut, unused_variables)]
    let mut link = "https://www.rust-lang.org/";

    println!("Welcome to our community: {link}");
}

    Note

    نکته رفتار #[expect(unfulfilled_lint_expectations)] در حال حاضر چنین تعریف شده که همیشه lint نوع unfulfilled_lint_expectations را تولید کند.

    [attributes.diagnostics.lint.group]

    گروه‌های Lint

    [attributes.diagnostics.lint.group.intro]

    Lintها می‌توانند در گروه‌های نام‌دار سازمان‌دهی شوند تا سطح lintهای مرتبط با هم تنظیم شود.

    [attributes.diagnostics.lint.group.equivalence]

    استفاده از گروه نام‌دار معادل فهرست‌کردن lintهای درون آن گروه است.

    // This allows all lints in the "unused" group.
#[allow(unused)]
// This overrides the "unused_must_use" lint from the "unused"
// group to deny.
#[deny(unused_must_use)]
fn example() {
    // This does not generate a warning because the "unused_variables"
    // lint is in the "unused" group.
    let x = 1;
    // This generates an error because the result is unused and
    // "unused_must_use" is marked as "deny".
    std::fs::remove_file("some_file"); // ERROR: unused `Result` that must be used
}
    [attributes.diagnostics.lint.group.warnings]

    گروه ویژه‌ای به نام «warnings» وجود دارد که همهٔ lintهای سطح «warn» را شامل می‌شود. گروه «warnings» ترتیب ویژگی‌ها را نادیده می‌گیرد و بر همهٔ lintهایی اعمال می‌شود که در غیر این صورت درون آن موجودیت هشدار می‌دادند.

    unsafe fn an_unsafe_fn() {}
// The order of these two attributes does not matter.
#[deny(warnings)]
// The unsafe_code lint is normally "allow" by default.
#[warn(unsafe_code)]
fn example_err() {
    // This is an error because the `unsafe_code` warning has
    // been lifted to "deny".
    unsafe { an_unsafe_fn() } // ERROR: use of `unsafe` block
}
    [attributes.diagnostics.lint.tool]

    ویژگی‌های Lint ابزارها

    [attributes.diagnostics.lint.tool.intro]

    Lint ابزارها امکان استفاده از lintهای دامنه‌دار را می‌دهد تا lintهای ابزارهای معین allow، warn، deny یا forbid شوند.

    [attributes.diagnostics.lint.tool.activation]

    Lintهای ابزار تنها هنگامی بررسی می‌شوند که ابزار مرتبط فعال باشد. اگر ویژگی lint مانند allow به lint ابزاری ناموجود اشاره کند، کامپایلر تا زمانی که آن ابزار را به کار نبرید دربارهٔ lint ناموجود هشدار نمی‌دهد.

    در دیگر جنبه‌ها، آن‌ها درست مانند ویژگی‌های lint عادی کار می‌کنند:

    // set the entire `pedantic` clippy lint group to warn
#![warn(clippy::pedantic)]
// silence warnings from the `filter_map` clippy lint
#![allow(clippy::filter_map)]

fn main() {
    // ...
}

// silence the `cmp_nan` clippy lint just for this function
#[allow(clippy::cmp_nan)]
fn foo() {
    // ...
}

    Note

    نکته rustc در حال حاضر lint ابزارهای clippy و rustdoc را می‌شناسد.

    [attributes.diagnostics.deprecated]

    ویژگی deprecated

    [attributes.diagnostics.deprecated.intro]

    ویژگی deprecated آیتمی را منسوخ علامت می‌زند. rustc هنگام استفاده از آیتم‌های #[deprecated] هشدار می‌دهد. rustdoc منسوخ‌شدن آیتم را همراه با نسخهٔ since و note در صورت وجود نشان می‌دهد.

    [attributes.diagnostics.deprecated.syntax]

    ویژگی deprecated چند شکل دارد:

    • deprecated — پیامی عمومی صادر می‌کند.
    • deprecated = "message" — رشتهٔ داده‌شده را در پیام منسوخ‌شدن می‌آورد.
    • نحو MetaListNameValueStr با دو فیلد اختیاری:
      • since — شمارهٔ نسخه‌ای را مشخص می‌کند که آیتم در آن منسوخ شده است. rustc در حال حاضر رشته را تفسیر نمی‌کند، اما ابزارهای خارجی مانند Clippy ممکن است اعتبار مقدار را بررسی کنند.
      • note — رشته‌ای را مشخص می‌کند که باید در پیام منسوخ‌شدن بیاید. معمولاً برای توضیح علت منسوخ‌شدن و جایگزین‌های ترجیحی استفاده می‌شود.
    [attributes.diagnostics.deprecated.allowed-positions]

    ویژگی deprecated را می‌توان روی هر آیتم، آیتم صفت، گونهٔ برشمردنی، فیلد ساختار، آیتم بلوک خارجی یا تعریف ماکرو اعمال کرد. این ویژگی روی آیتم‌های پیاده‌سازی صفت قابل اعمال نیست. هنگامی که روی آیتمی حاوی آیتم‌های دیگر، مانند ماژول یا پیاده‌سازی اعمال شود، همهٔ آیتم‌های فرزند ویژگی منسوخ‌شدن را به ارث می‌برند.

    در اینجا یک مثال آمده است:

    #[deprecated(since = "5.2.0", note = "foo was rarely used. Users should instead use bar")]
pub fn foo() {}

pub fn bar() {}

    RFC شامل انگیزه‌ها و جزئیات بیشتر است.

    [attributes.diagnostics.must_use]

    ویژگی must_use

    [attributes.diagnostics.must_use.intro]

    ویژگی must_use مقداری را علامت می‌زند که باید استفاده شود.

    [attributes.diagnostics.must_use.syntax]

    ویژگی must_use از نحوهای MetaWord و MetaNameValueStr استفاده می‌کند.

    مثال

    #[must_use]
fn use_me1() -> u8 { 0 }

#[must_use = "explanation of why it should be used"]
fn use_me2() -> u8 { 0 }
    [attributes.diagnostics.must_use.allowed-positions]

    ویژگی must_use را می‌توان روی موارد زیر اعمال کرد:

    • struct
    • Enumeration
    • union
    • تابع
    • trait

    Note

    نکته rustc استفاده در موقعیت‌های دیگر را نادیده می‌گیرد، اما دربارهٔ آن هشدار lint می‌دهد. این وضعیت ممکن است در آینده به خطا تبدیل شود.

    [attributes.diagnostics.must_use.duplicates]

    ویژگی must_use تنها یک بار روی هر آیتم قابل استفاده است.

    Note

    نکته rustc دربارهٔ هر استفاده پس از نخستین مورد هشدار lint می‌دهد. این وضعیت ممکن است در آینده به خطا تبدیل شود.

    [attributes.diagnostics.must_use.message]

    ویژگی must_use می‌تواند با نحو MetaNameValueStr پیامی داشته باشد، مانند #[must_use = "example message"]. این پیام ممکن است به‌عنوان بخشی از lint صادر شود.

    [attributes.diagnostics.must_use.type]

    هنگامی که ویژگی روی ساختار، برشمردنی یا اجتماع اعمال شده باشد، اگر عبارت یک گزارهٔ عبارتی از آن نوع باشد، lint نوع unused_must_use فعال می‌شود.

    #![deny(unused_must_use)]
#[must_use]
struct MustUse();
MustUse(); // ERROR: Unused value that must be used.
    [attributes.diagnostics.must_use.type-uninhabited]

    به‌عنوان استثنا بر attributes.diagnostics.must_use.type، lint برای Result<(), E> زمانی که E غیرقابل‌سکونت است و برای ControlFlow<B, ()> زمانی که B غیرقابل‌سکونت است فعال نمی‌شود. نوع #[non_exhaustive] از جعبه‌ای خارجی برای این منظور غیرقابل‌سکونت شمرده نمی‌شود، زیرا ممکن است در آینده سازنده‌هایی بگیرد.

    #![deny(unused_must_use)]
use core::ops::ControlFlow;
fn f1() -> Result<(), !> { Ok(()) }
f1(); // OK: `!` is uninhabited.
fn f2() -> ControlFlow<!, ()> { ControlFlow::Continue(()) }
f2(); // OK: `!` is uninhabited.
    [attributes.diagnostics.must_use.fn]

    اگر عبارت یک گزارهٔ عبارتی، عبارت فراخوانی یا عبارت فراخوانی متد باشد و عملوند تابع آن تابعی باشد که ویژگی روی آن اعمال شده است، lint نوع unused_must_use فعال می‌شود.

    #![deny(unused_must_use)]
#[must_use]
fn f() {}
f(); // ERROR: Unused return value that must be used.
    [attributes.diagnostics.must_use.trait]

    اگر عبارت یک گزارهٔ عبارتی، عبارت فراخوانی یا عبارت فراخوانی متد باشد و عملوند تابع آن تابعی باشد که نوع impl trait یا dyn trait برمی‌گرداند و یک یا چند صفت در کران با این ویژگی علامت خورده باشند، lint نوع unused_must_use فعال می‌شود.

    #![deny(unused_must_use)]
#[must_use]
trait Tr {}
impl Tr for () {}
fn f() -> impl Tr {}
f(); // ERROR: Unused implementor that must be used.
    [attributes.diagnostics.must_use.trait-function]

    هنگامی که ویژگی روی تابعی در اعلان صفت اعمال شود، قواعد attributes.diagnostics.must_use.fn زمانی نیز برقرارند که عملوند تابع در عبارت فراخوانی یا عبارت فراخوانی متد پیاده‌سازی همان تابع باشد.

    #![deny(unused_must_use)]
trait Tr {
    #[must_use]
    fn use_me(&self);
}

impl Tr for () {
    fn use_me(&self) {}
}

().use_me(); // ERROR: Unused return value that must be used.
    #![deny(unused_must_use)]
trait Tr {
    #[must_use]
    fn use_me(&self);
}

impl Tr for () {
    fn use_me(&self) {}
}

<() as Tr>::use_me(&());
//          ^^^^^^^^^^^ ERROR: Unused return value that must be used.
    [attributes.diagnostics.must_use.block-expr]

    هنگام بررسی عبارت یک گزارهٔ عبارتی برای attributes.diagnostics.must_use.type، attributes.diagnostics.must_use.fn، attributes.diagnostics.must_use.trait و attributes.diagnostics.must_use.trait-function، lint از میان عبارت‌های بلوکی—از جمله بلوک‌های unsafe و عبارت‌های بلوکی برچسب‌دار—به عبارت پایانی هر یک نگاه می‌کند. این کار برای بلوک‌های تودرتو بازگشتی است.

    #![deny(unused_must_use)]
#[must_use]
fn f() {}

{ f() };        // ERROR: The lint looks through block expressions.
unsafe { f() }; // ERROR: The lint looks through `unsafe` blocks.
{ { f() } };    // ERROR: The lint looks through nested blocks.
    [attributes.diagnostics.must_use.trait-impl-function]

    هنگامی که این ویژگی روی تابعی در پیاده‌سازی صفت به کار رود، اثری ندارد.

    #![deny(unused_must_use)]
trait Tr {
    fn f(&self);
}

impl Tr for () {
    #[must_use] // This has no effect.
    fn f(&self) {}
}

().f(); // OK.

    Note

    نکته rustc دربارهٔ استفاده روی تابع‌های پیاده‌سازی صفت هشدار lint می‌دهد. این وضعیت ممکن است در آینده به خطا تبدیل شود.

    [attributes.diagnostics.must_use.wrapping-suppression]

    Note

    نکته پیچیدن نتیجهٔ تابع #[must_use] در برخی عبارت‌ها می‌تواند بررسی مبتنی بر تابع را سرکوب کند، زیرا عبارت گزارهٔ عبارتی دیگر یک عبارت فراخوانی یا عبارت فراخوانی متد به تابع #[must_use] نیست. اگر نوع کل عبارت #[must_use] باشد، بررسی مبتنی بر نوع همچنان برقرار است.

    #![deny(unused_must_use)]
#[must_use]
fn f() {}

// The fn-based check does not fire for any of these, because the
// expression of the expression statement is not a call to a
// `#[must_use]` function.
(f(),);                    // Expression is a tuple, not a call.
Some(f());                 // Callee `Some` is not `#[must_use]`.
if true { f() } else {};   // Expression is an `if`, not a call.
match true {               // Expression is a `match`, not a call.
    _ => f()
};
    #![deny(unused_must_use)]
#[must_use]
struct MustUse;
fn g() -> MustUse { MustUse }

// Despite the `if` expression not being a call, the type-based check
// fires because the type of the expression is `MustUse`, which has
// the `#[must_use]` attribute.
if true { g() } else { MustUse }; // ERROR: Must be used.
    [attributes.diagnostics.must_use.underscore-idiom]

    Note

    نکته وقتی مقداری که باید استفاده شود عمداً کنار گذاشته می‌شود، استفاده از گزارهٔ let یا انتساب ساختارشکن با الگوی _ شیوهٔ رایج است.

    #![deny(unused_must_use)]
#[must_use]
fn f() {}
let _ = f(); // OK.
_ = f(); // OK.
    [attributes.diagnostic.namespace]

    فضای نام ویژگی ابزار diagnostic

    [attributes.diagnostic.namespace.intro]

    فضای نام ویژگی #[diagnostic] جایگاهی برای ویژگی‌هایی است که بر پیام‌های خطای زمان کامپایل اثر می‌گذارند. تضمینی نیست راهنمایی‌های ارائه‌شده با این ویژگی‌ها استفاده شوند.

    [attributes.diagnostic.namespace.unknown-invalid-syntax]

    ویژگی‌های ناشناخته در این فضای نام پذیرفته می‌شوند، هرچند ممکن است برای ویژگی استفاده‌نشده هشدار صادر کنند. افزون بر این، ورودی نامعتبر به ویژگی‌های شناخته‌شده معمولاً هشدار است؛ برای جزئیات تعریف هر ویژگی را ببینید. هدف این است که افزودن یا کنارگذاشتن ویژگی‌ها و تغییر ورودی‌ها در آینده بدون نیاز به حفظ کارکرد ویژگی‌ها یا گزینه‌های بی‌معنا امکان‌پذیر باشد.

    [attributes.diagnostic.on_unimplemented]

    ویژگی diagnostic::on_unimplemented

    [attributes.diagnostic.on_unimplemented.intro]

    ویژگی #[diagnostic::on_unimplemented] راهنمایی‌ای به کامپایلر است تا در وضعیتی که یک صفت لازم است اما روی نوعی پیاده‌سازی نشده، پیام خطای معمول را تکمیل کند.

    [attributes.diagnostic.on_unimplemented.allowed-positions]

    ویژگی باید روی اعلان صفت قرار گیرد، هرچند حضور آن در موقعیت‌های دیگر خطا نیست.

    [attributes.diagnostic.on_unimplemented.syntax]

    ویژگی برای مشخص‌کردن ورودی‌هایش از نحو MetaListNameValueStr استفاده می‌کند، با این حال هیچ ورودی بدشکل به ویژگی خطا محسوب نمی‌شود تا سازگاری رو به جلو و عقب فراهم باشد.

    [attributes.diagnostic.on_unimplemented.keys]

    کلیدهای زیر معنای مشخص‌شده را دارند:

    • message — متن پیام خطای سطح بالا.
    • label — متن برچسبی که در پیام خطا درون کد خراب نمایش داده می‌شود.
    • note — یادداشت‌های تکمیلی فراهم می‌کند.
    [attributes.diagnostic.on_unimplemented.note-repetition]

    گزینهٔ note می‌تواند چند بار ظاهر شود و در نتیجه چند پیام یادداشت صادر می‌شود.

    [attributes.diagnostic.on_unimplemented.repetition]

    اگر هر یک از گزینه‌های دیگر چند بار ظاهر شود، نخستین رخداد گزینهٔ مربوط مقدار واقعاً استفاده‌شده را تعیین می‌کند. رخدادهای بعدی هشدار تولید می‌کنند.

    [attributes.diagnostic.on_unimplemented.unknown-keys]

    برای هر کلید ناشناخته هشدار تولید می‌شود.

    [attributes.diagnostic.on_unimplemented.format-string]

    هر سه گزینه یک رشته را به‌عنوان آرگومان می‌پذیرند که با همان قالب‌بندی رشتهٔ std::fmt تفسیر می‌شود.

    [attributes.diagnostic.on_unimplemented.format-parameters]

    پارامترهای قالب با نام داده‌شده با متن زیر جایگزین می‌شوند:

    • {Self} — نام نوعی که صفت را پیاده‌سازی می‌کند.
    • { GenericParameterName } — نام نوع آرگومان عام برای پارامتر عام داده‌شده.
    [attributes.diagnostic.on_unimplemented.invalid-formats]

    هر پارامتر قالب دیگر هشدار تولید می‌کند، اما در باقی موارد بدون تغییر در رشته می‌ماند.

    [attributes.diagnostic.on_unimplemented.invalid-string]

    رشته‌های قالب نامعتبر ممکن است هشدار تولید کنند، اما در غیر این صورت مجازند؛ هرچند شاید آن‌طور که انتظار می‌رود نمایش داده نشوند. مشخص‌کننده‌های قالب نیز ممکن است هشدار تولید کنند، اما در غیر این صورت نادیده گرفته می‌شوند.

    در این نمونه:

    #[diagnostic::on_unimplemented(
    message = "My Message for `ImportantTrait<{A}>` implemented for `{Self}`",
    label = "My Label",
    note = "Note 1",
    note = "Note 2"
)]
trait ImportantTrait<A> {}

fn use_my_trait(_: impl ImportantTrait<i32>) {}

fn main() {
    use_my_trait(String::new());
}

    کامپایلر ممکن است پیامی شبیه این تولید کند:

    error[E0277]: My Message for `ImportantTrait<i32>` implemented for `String`
  --> src/main.rs:14:18
   |
14 |     use_my_trait(String::new());
   |     ------------ ^^^^^^^^^^^^^ My Label
   |     |
   |     required by a bound introduced by this call
   |
   = help: the trait `ImportantTrait<i32>` is not implemented for `String`
   = note: Note 1
   = note: Note 2

    ویژگی diagnostic::do_not_recommend

    [attributes.diagnostic.do_not_recommend.intro]

    ویژگی #[diagnostic::do_not_recommend] راهنمایی‌ای به کامپایلر است تا پیاده‌سازی صفت علامت‌خورده را به‌عنوان بخشی از پیام تشخیصی نشان ندهد.

    Note

    نکته سرکوب پیشنهاد زمانی سودمند است که بدانید پیشنهاد معمولاً برای برنامه‌نویس مفید نخواهد بود. این وضعیت اغلب در پیاده‌سازی‌های blanket گسترده رخ می‌دهد. پیشنهاد ممکن است برنامه‌نویس را به مسیر اشتباه بفرستد، پیاده‌سازی صفت شاید جزئیاتی داخلی باشد که نمی‌خواهید آشکار شود، یا ممکن است برنامه‌نویس نتواند کران‌ها را برآورده کند.

    برای نمونه، در پیام خطایی دربارهٔ پیاده‌سازی‌نشدن صفتی لازم برای یک نوع، کامپایلر ممکن است پیاده‌سازی صفتی بیابد که اگر کران‌های معینی در آن نبودند نیازها را برآورده می‌کرد. کامپایلر شاید به کاربر بگوید پیاده‌سازی وجود دارد اما مشکل از کران‌های آن است. ویژگی #[diagnostic::do_not_recommend] می‌تواند به کامپایلر بگوید این پیاده‌سازی را به کاربر معرفی نکند و در عوض تنها بگوید نوع، صفت لازم را پیاده‌سازی نمی‌کند.

    [attributes.diagnostic.do_not_recommend.allowed-positions]

    ویژگی باید روی یک آیتم پیاده‌سازی صفت قرار گیرد، هرچند حضور آن در موقعیت‌های دیگر خطا نیست.

    [attributes.diagnostic.do_not_recommend.syntax]

    ویژگی هیچ آرگومانی نمی‌پذیرد، هرچند آرگومان‌های غیرمنتظره خطا محسوب نمی‌شوند.

    در نمونهٔ زیر، صفتی با نام AsExpression وجود دارد که برای تبدیل نوع‌های دلخواه به نوع Expression مورد استفاده در یک کتابخانهٔ SQL به کار می‌رود. متدی به نام check نیز وجود دارد که یک AsExpression می‌گیرد.

    pub trait Expression {
    type SqlType;
}

pub trait AsExpression<ST> {
    type Expression: Expression<SqlType = ST>;
}

pub struct Text;
pub struct Integer;

pub struct Bound<T>(T);
pub struct SelectInt;

impl Expression for SelectInt {
    type SqlType = Integer;
}

impl<T> Expression for Bound<T> {
    type SqlType = T;
}

impl AsExpression<Integer> for i32 {
    type Expression = Bound<Integer>;
}

impl AsExpression<Text> for &'_ str {
    type Expression = Bound<Text>;
}

impl<T> Foo for T where T: Expression {}

// Uncomment this line to change the recommendation.
// #[diagnostic::do_not_recommend]
impl<T, ST> AsExpression<ST> for T
where
    T: Expression<SqlType = ST>,
{
    type Expression = T;
}

trait Foo: Expression + Sized {
    fn check<T>(&self, _: T) -> <T as AsExpression<<Self as Expression>::SqlType>>::Expression
    where
        T: AsExpression<Self::SqlType>,
    {
        todo!()
    }
}

fn main() {
    SelectInt.check("bar");
}

    متد check در نوع SelectInt انتظار نوع Integer دارد. فراخوانی آن با نوع i32 کار می‌کند، زیرا صفت AsExpression آن را به Integer تبدیل می‌کند. اما فراخوانی با رشته کار نمی‌کند و ممکن است خطایی شبیه زیر تولید کند:

    error[E0277]: the trait bound `&str: Expression` is not satisfied
  --> src/main.rs:53:15
   |
53 |     SelectInt.check("bar");
   |               ^^^^^ the trait `Expression` is not implemented for `&str`
   |
   = help: the following other types implement trait `Expression`:
             Bound<T>
             SelectInt
note: required for `&str` to implement `AsExpression<Integer>`
  --> src/main.rs:45:13
   |
45 | impl<T, ST> AsExpression<ST> for T
   |             ^^^^^^^^^^^^^^^^     ^
46 | where
47 |     T: Expression<SqlType = ST>,

    با افزودن ویژگی #[diagnostic::do_not_recommend] به impl همگانی (blanket) برای AsExpression، پیام به این صورت تغییر می‌کند:

    error[E0277]: the trait bound `&str: AsExpression<Integer>` is not satisfied
  --> src/main.rs:53:15
   |
53 |     SelectInt.check("bar");
   |               ^^^^^ the trait `AsExpression<Integer>` is not implemented for `&str`

    پیام خطای نخست توضیحی نسبتاً گیج‌کننده دربارهٔ ارتباط &str و Expression و نیز کران صفت برآورده‌نشده در پیاده‌سازی blanket دارد. پس از افزودن #[diagnostic::do_not_recommend]، پیاده‌سازی blanket دیگر برای پیشنهاد در نظر گرفته نمی‌شود. پیام باید کمی روشن‌تر باشد و نشان دهد رشته را نمی‌توان به Integer تبدیل کرد.
