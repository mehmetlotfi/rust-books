    workspaceهای Cargo

    در فصل ۱۲ بسته‌ای ساختیم که شامل یک crate باینری و یک crate کتابخانه‌ای بود. با پیشرفت پروژه ممکن است متوجه شوید که crate کتابخانه‌ای مدام بزرگ‌تر می‌شود و بخواهید بسته‌تان را به چند crate کتابخانه‌ای تقسیم کنید. Cargo قابلیتی به نام workspace دارد که به مدیریت چند بستهٔ مرتبط که هم‌زمان توسعه داده می‌شوند کمک می‌کند.

    ساخت یک workspace

    workspace مجموعه‌ای از بسته‌هاست که فایل Cargo.lock و دایرکتوری خروجی یکسانی دارند. بیایید پروژه‌ای با workspace بسازیم؛ از کد ساده‌ای استفاده می‌کنیم تا بتوانیم روی ساختار workspace تمرکز کنیم. روش‌های مختلفی برای ساختاردهی یک workspace وجود دارد، بنابراین فقط یکی از رایج‌ترین آن‌ها را نشان می‌دهیم. workspace ما شامل یک باینری و دو کتابخانه خواهد بود. باینری که قابلیت اصلی را فراهم می‌کند، به هر دو کتابخانه وابسته است. یک کتابخانه تابع add_one و کتابخانهٔ دیگر تابع add_two را ارائه می‌دهد. این سه crate بخشی از یک workspace خواهند بود. کار را با ساخت یک دایرکتوری جدید برای workspace شروع می‌کنیم:

    $ mkdir add
$ cd add

    سپس در دایرکتوری add فایل Cargo.toml را می‌سازیم که کل workspace را پیکربندی می‌کند. این فایل بخش [package] نخواهد داشت. در عوض با بخش [workspace] شروع می‌شود که به ما اجازه می‌دهد اعضایی به workspace اضافه کنیم. همچنین با تنظیم مقدار resolver روی "3" مطمئن می‌شویم که در workspace از جدیدترین و بهترین نسخهٔ الگوریتم resolver در Cargo استفاده شود:

    نام فایل: Cargo.toml

    [workspace]
resolver = "3"

    در ادامه با اجرای cargo new داخل دایرکتوری add، crate باینری adder را می‌سازیم:

    $ cargo new adder
     Created binary (application) `adder` package
      Adding `adder` as member of workspace at `file:///projects/add`

    اجرای cargo new داخل یک workspace، بستهٔ تازه‌ساخته‌شده را به‌طور خودکار به کلید members در تعریف [workspace] در فایل Cargo.toml آن workspace نیز اضافه می‌کند، به این صورت:

    [workspace]
resolver = "3"
members = ["adder"]

    در این مرحله می‌توانیم با اجرای cargo build workspace را بسازیم. فایل‌های دایرکتوری add شما باید به این شکل باشند:

    ├── Cargo.lock
├── Cargo.toml
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

    workspace یک دایرکتوری target در سطح بالا دارد که artifactهای کامپایل‌شده در آن قرار می‌گیرند؛ بستهٔ adder دایرکتوری target مخصوص به خود را ندارد. حتی اگر cargo build را از داخل دایرکتوری adder اجرا کنیم، artifactهای کامپایل‌شده باز هم در add/target قرار می‌گیرند، نه در add/adder/target. Cargo دایرکتوری target را در یک workspace به این شکل ساختاردهی می‌کند، چون crateهای یک workspace قرار است به یکدیگر وابسته باشند. اگر هر crate دایرکتوری target خودش را می‌داشت، هر crate مجبور بود برای قرار دادن artifactها در دایرکتوری target خودش، همهٔ crateهای دیگر workspace را دوباره کامپایل کند. با اشتراک‌گذاری یک دایرکتوری target، crateها می‌توانند از ساخت مجدد غیرضروری پرهیز کنند.

    ساخت بستهٔ دوم در workspace

    حال بیایید بستهٔ عضو دیگری در workspace بسازیم و آن را add_one بنامیم. یک crate کتابخانه‌ای جدید با نام add_one تولید کنید:

    $ cargo new add_one --lib
     Created library `add_one` package
      Adding `add_one` as member of workspace at `file:///projects/add`

    فایل Cargo.toml سطح بالا اکنون مسیر add_one را در فهرست members خواهد داشت:

    نام فایل: Cargo.toml

    [workspace]
resolver = "3"
members = ["adder", "add_one"]

    دایرکتوری add شما اکنون باید این دایرکتوری‌ها و فایل‌ها را داشته باشد:

    ├── Cargo.lock
├── Cargo.toml
├── add_one
│   ├── Cargo.toml
│   └── src
│       └── lib.rs
├── adder
│   ├── Cargo.toml
│   └── src
│       └── main.rs
└── target

    در فایل add_one/src/lib.rs تابعی به نام add_one اضافه می‌کنیم:

    نام فایل: add_one/src/lib.rs

    pub fn add_one(x: i32) -> i32 {
    x + 1
}

    اکنون می‌توانیم بستهٔ adder را که باینری ما را دارد، وابسته به بستهٔ add_one که کتابخانهٔ ما را دارد کنیم. ابتدا باید یک وابستگی مسیری (path dependency) به add_one در فایل adder/Cargo.toml اضافه کنیم.

    نام فایل: adder/Cargo.toml

    [dependencies]
add_one = { path = "../add_one" }

    Cargo فرض نمی‌کند که crateهای یک workspace به یکدیگر وابسته‌اند، بنابراین باید روابط وابستگی را صریحاً مشخص کنیم.

    در ادامه بیایید از تابع add_one (از crate با نام add_one) در crate با نام adder استفاده کنیم. فایل adder/src/main.rs را باز کنید و تابع main را طوری تغییر دهید که تابع add_one را فراخوانی کند، مانند لیستینگ ۱۴-۷.

    بیایید workspace را با اجرای cargo build در دایرکتوری سطح بالای add بسازیم!

    $ cargo build
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.22s

    برای اجرای crate باینری از دایرکتوری add، می‌توانیم با استفاده از آرگومان -p و نام بسته همراه با cargo run مشخص کنیم کدام بسته از workspace اجرا شود:

    $ cargo run -p adder
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running `target/debug/adder`
Hello, world! 10 plus one is 11!

    این دستور کد موجود در adder/src/main.rs را اجرا می‌کند که به crate با نام add_one وابسته است.

    وابستگی به یک بستهٔ خارجی

    توجه کنید که workspace فقط یک فایل Cargo.lock در سطح بالا دارد، نه یک Cargo.lock در دایرکتوری هر crate. این کار تضمین می‌کند که همهٔ crateها از یک نسخهٔ یکسان از همهٔ وابستگی‌ها استفاده می‌کنند. اگر بستهٔ rand را به فایل‌های adder/Cargo.toml و add_one/Cargo.toml اضافه کنیم، Cargo هر دو را به یک نسخه از rand تبدیل می‌کند و آن را در همان یک Cargo.lock ثبت می‌کند. وقتی همهٔ crateهای workspace از وابستگی‌های یکسان استفاده کنند، crateها همیشه با یکدیگر سازگار خواهند بود. بیایید crate rand را به بخش [dependencies] در فایل add_one/Cargo.toml اضافه کنیم تا بتوانیم از crate rand در crate add_one استفاده کنیم:

    نام فایل: add_one/Cargo.toml

    [dependencies]
rand = "0.10.1"

    اکنون می‌توانیم use rand; را به فایل add_one/src/lib.rs اضافه کنیم، و ساخت کل workspace با اجرای cargo build در دایرکتوری add، crate با نام rand را دریافت و کامپایل می‌کند. یک هشدار (warning) دریافت می‌کنیم، چون به rand واردشده به scope ارجاعی نداده‌ایم:

    $ cargo build
    Updating crates.io index
  Downloaded rand v0.10.1
   --snip--
   Compiling rand v0.10.1
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
warning: unused import: `rand`
 --> add_one/src/lib.rs:1:5
  |
1 | use rand;
  |     ^^^^
  |
  = note: `#[warn(unused_imports)]` (part of `#[warn(unused)]`) on by default

warning: `add_one` (lib) generated 1 warning (run `cargo fix --lib -p add_one` to apply 1 suggestion)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `dev` profile [unoptimized + debuginfo] target(s) in 0.95s

    فایل Cargo.lock سطح بالا اکنون اطلاعات وابستگی add_one به rand را دربردارد. با این حال، حتی با اینکه rand جایی در workspace استفاده شده است، نمی‌توانیم از آن در crateهای دیگر workspace استفاده کنیم، مگر اینکه rand را به فایل‌های Cargo.toml آن‌ها هم اضافه کنیم. برای مثال، اگر use rand; را به فایل adder/src/main.rs در بستهٔ adder اضافه کنیم، با خطا مواجه می‌شویم:

    $ cargo build
  --snip--
   Compiling adder v0.1.0 (file:///projects/add/adder)
error[E0432]: unresolved import `rand`
 --> adder/src/main.rs:2:5
  |
2 | use rand;
  |     ^^^^ no external crate `rand`

    برای رفع این مشکل، فایل Cargo.toml بستهٔ adder را ویرایش کنید و مشخص کنید که rand وابستگی آن هم هست. ساخت بستهٔ adder باعث می‌شود rand به فهرست وابستگی‌های adder در Cargo.lock اضافه شود، اما نسخه‌های اضافی از rand دانلود نخواهد شد. Cargo تضمین می‌کند که هر crate در هر بسته‌ای از workspace که از بستهٔ rand استفاده می‌کند، از یک نسخهٔ یکسان استفاده کند، به شرط آنکه نسخه‌های سازگار از rand را مشخص کرده باشند. این کار در فضا صرفه‌جویی می‌کند و تضمین می‌کند که crateهای workspace با یکدیگر سازگار باشند.

    اگر crateهای workspace نسخه‌های ناسازگاری از یک وابستگی مشخص کنند، Cargo هر کدام را جداگانه تعیین‌نسخه می‌کند، اما همچنان سعی می‌کند تا حد امکان نسخه‌های کمتری را برگزیند.

    افزودن آزمون به یک workspace

    برای یک بهبود دیگر، بیایید آزمونی برای تابع add_one::add_one در crate با نام add_one اضافه کنیم:

    نام فایل: add_one/src/lib.rs

    pub fn add_one(x: i32) -> i32 {
    x + 1
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn it_works() {
        assert_eq!(3, add_one(2));
    }
}

    حال cargo test را در دایرکتوری سطح بالای add اجرا کنید. اجرای cargo test در workspaceای با چنین ساختاری، آزمون‌های همهٔ crateهای workspace را اجرا می‌کند:

    $ cargo test
   Compiling add_one v0.1.0 (file:///projects/add/add_one)
   Compiling adder v0.1.0 (file:///projects/add/adder)
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.20s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

     Running unittests src/main.rs (target/debug/deps/adder-3a47283c568d2b6a)

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

    بخش اول خروجی نشان می‌دهد که آزمون it_works در crate با نام add_one موفق بوده است. بخش بعدی نشان می‌دهد که هیچ آزمونی در crate با نام adder پیدا نشده، و بخش آخر نشان می‌دهد که هیچ آزمون مستنداتی (documentation test) در crate با نام add_one یافت نشده است.

    همچنین می‌توانیم از دایرکتوری سطح بالا، آزمون‌های یک crate مشخص از workspace را با استفاده از پرچم -p و تعیین نام crate موردنظر اجرا کنیم:

    $ cargo test -p add_one
    Finished `test` profile [unoptimized + debuginfo] target(s) in 0.00s
     Running unittests src/lib.rs (target/debug/deps/add_one-93c49ee75dc46543)

running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

   Doc-tests add_one

running 0 tests

test result: ok. 0 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out; finished in 0.00s

    این خروجی نشان می‌دهد که cargo test فقط آزمون‌های crate با نام add_one را اجرا کرد و آزمون‌های crate با نام adder را اجرا نکرد.

    اگر crateهای workspace را در crates.io منتشر کنید، هر crate در workspace باید جداگانه منتشر شود. مانند cargo test، می‌توانیم با استفاده از پرچم -p و تعیین نام crate موردنظر، crate مشخصی از workspace را منتشر کنیم.

    برای تمرین بیشتر، یک crate با نام add_two را به همین روشی که add_one را ساختید، به این workspace اضافه کنید!

    با رشد پروژه‌تان، استفاده از workspace را در نظر بگیرید: این کار به شما امکان می‌دهد با اجزای کوچک‌تر و قابل‌فهم‌تری کار کنید، به‌جای یک توده بزرگ از کد. علاوه بر این، نگه‌داشتن crateها در یک workspace می‌تواند هماهنگی بین crateها را آسان‌تر کند، به‌ویژه اگر اغلب هم‌زمان تغییر کنند.
