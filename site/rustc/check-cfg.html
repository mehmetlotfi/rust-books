    بررسی پیکربندی‌های شرطی

    rustc از بررسی این موضوع پشتیبانی می‌کند که هر #[cfg] دسترس‌پذیر1 با فهرستی از نام‌ها و مقادیر پیکربندی مورد انتظار مطابقت داشته باشد.

    این قابلیت می‌تواند به اطمینان از این کمک کند که crate کامپایل شرطی را برای پلتفرم‌های هدف یا featureهای مختلف به‌درستی مدیریت می‌کند. این بررسی تضمین می‌کند که تنظیمات cfg میان آنچه در نظر گرفته شده و آنچه به‌کار رفته است سازگار باشند و به شناسایی زودهنگام اشکال‌ها و خطاهای احتمالی در فرایند توسعه کمک می‌کند.

    برای رسیدن به این هدف، rustc پرچم --check-cfg را می‌پذیرد که مشخص می‌کند آیا شرط‌ها بررسی شوند و چگونه بررسی شوند.

    توجه: برای کار با این قابلیت از طریق Cargo، صفحهٔ ویژگی‌های مخصوص Cargo را ببینید.

    مشخص‌کردن نام‌ها و مقادیر مورد انتظار

    برای مشخص‌کردن نام‌ها و مقادیر مورد انتظار، مشخصات بررسی cfg گزینهٔ cfg(...) را فراهم می‌کند که امکان تعیین یک نام پیکربندی مورد انتظار و مقادیر مورد انتظار آن را می‌دهد.

    توجه: هنگام استفاده از --cfg هیچ انتظار ضمنی‌ای اضافه نمی‌شود. از کاربران انتظار می‌رود همهٔ نام‌ها و مقادیر مورد انتظار را با استفاده از مشخصات بررسی cfg ارائه کنند.

    شکل پایهٔ آن چنین است:

    rustc --check-cfg 'cfg(name, values("value1", "value2", ... "valueN"))'

    که در آن name یک شناسهٔ ساده (بدون نقل‌قول) است و هر عبارت "value" یک رشتهٔ لفظی داخل نقل‌قول است. name نام شرط را مشخص می‌کند، مانند feature یا my_cfg. "value" یکی از مقادیر آن نام شرط را مشخص می‌کند.

    وقتی گزینهٔ cfg(...) مشخص شده باشد، rustc همهٔ موارد زیر را بررسی می‌کند1:

    • attribute به شکل #[cfg(name = "value")]
    • attribute به شکل #[cfg_attr(name = "value")]
    • attribute به شکل #[link(name = "a", cfg(name = "value"))]
    • فراخوانی ماکرو به شکل cfg!(name = "value")

    آرگومان‌های --cfg در خط فرمان در حال حاضر بررسی نمی‌شوند، اما ممکن است در آینده بررسی شوند.

    rustc بررسی می‌کند که "value" مشخص‌شده در فهرست مقادیر مورد انتظار وجود داشته باشد. اگر "value" در آن نباشد، rustc یک تشخیص lint به نام unexpected_cfgs گزارش می‌کند. سطح پیش‌فرض تشخیص برای این lint برابر Warn است.

    برای بررسی مقدار هیچ (یعنی #[cfg(foo)]) می‌توان از گزارهٔ none() درون values() استفاده کرد: values(none()). این گزاره می‌تواند پس از هر تعداد "value" یا پیش از آن‌ها بیاید.

    برای فعال‌کردن بررسی مقادیر، اما با ارائهٔ مجموعهٔ هیچ/خالی از مقادیر مورد انتظار (یعنی انتظار #[cfg(name)])، از این شکل‌ها استفاده کنید:

    rustc --check-cfg 'cfg(name)'
rustc --check-cfg 'cfg(name, values(none()))'

    برای فعال‌کردن بررسی نام اما نه مقادیر، از یکی از این شکل‌ها استفاده کنید:

    • بدون مقدار مورد انتظار (برای هر مقدار name هشدار lint می‌دهد): bash rustc --check-cfg 'cfg(name, values())'

      rustc --check-cfg 'cfg(name, values())'

    • مقادیر مورد انتظار ناشناخته (هرگز برای مقدار name هشدار lint نمی‌دهد): bash rustc --check-cfg 'cfg(name, values(any()))'

      rustc --check-cfg 'cfg(name, values(any()))'

    برای جلوگیری از تکرار یک مجموعهٔ مقادیر، از این شکل استفاده کنید:

    rustc --check-cfg 'cfg(name1, ..., nameN, values("value1", "value2", ... "valueN"))'

    برای فعال‌کردن بررسی بدون مشخص‌کردن هیچ نام یا مقداری، از این شکل استفاده کنید:

    rustc --check-cfg 'cfg()'

    گزینهٔ --check-cfg cfg(...) را می‌توان تکرار کرد، هم برای یک نام شرط یکسان و هم برای نام‌های متفاوت. اگر برای یک نام شرط یکسان تکرار شود، مجموعه‌های مقادیر آن شرط با هم ادغام می‌شوند (اولویت با values(any()) است).

    برای کمک، یک جدول هم‌ارزی میان آرگومان‌های --cfg و --check-cfg در پایین در دسترس است.

    نام‌ها و مقادیر شناخته‌شده

    rustc فهرستی از نام‌های شناخته‌شده و مقادیر متناظر آن‌ها را نگه می‌دارد تا نیازی به مشخص‌کردن دستی آن‌ها نباشد.

    نام‌ها و مقادیر شناخته‌شده تا زمانی که دست‌کم یک آرگومان --check-cfg وجود داشته باشد به‌صورت ضمنی اضافه می‌شوند.

    از نسخهٔ 1.85.0 به بعد، cfg با نام test یک پیکربندی «فضای کاربر» در نظر گرفته می‌شود، با وجود اینکه rustc نیز آن را تنظیم می‌کند، و باید توسط خود سامانهٔ ساخت مدیریت شود.

    مانند values(any())، بررسی نام‌های شناخته‌شده را می‌توان با ارسال cfg(any()) به‌عنوان آرگومان --check-cfg غیرفعال کرد.

    جدول هم‌ارزی با --cfg

    این جدول هم‌ارزی میان یک آرگومان --cfg و یک آرگومان --check-cfg را توصیف می‌کند.

    --cfg--check-cfg
    هیچ‌چیزهیچ‌چیز یا --check-cfg=cfg() (برای فعال‌کردن بررسی)
    --cfg foo--check-cfg=cfg(foo) یا --check-cfg=cfg(foo, values(none()))
    --cfg foo=""--check-cfg=cfg(foo, values(""))
    --cfg foo="bar"--check-cfg=cfg(foo, values("bar"))
    --cfg foo="1" --cfg foo="2"--check-cfg=cfg(foo, values("1", "2"))
    --cfg foo="1" --cfg bar="2"--check-cfg=cfg(foo, values("1")) --check-cfg=cfg(bar, values("2"))
    --cfg foo --cfg foo="bar"--check-cfg=cfg(foo, values(none(), "bar"))

    مثال‌ها

    مثال: نمونهٔ feature به سبک Cargo

    این خط فرمان را در نظر بگیرید:

    rustc --check-cfg 'cfg(feature, values("lion", "zebra"))' \
      --cfg 'feature="lion"' example.rs

    این خط فرمان نشان می‌دهد که این crate دو feature دارد: lion و zebra. feature با نام lion فعال است، در حالی که feature با نام zebra غیرفعال است.

    #[cfg(feature = "lion")]     // This condition is expected, as "lion" is an
                             // expected value of `feature`
fn tame_lion(lion: Lion) {}

#[cfg(feature = "zebra")]    // This condition is expected, as "zebra" is an expected
                             // value of `feature` but the condition will evaluate
                             // to false since only --cfg feature="lion" was passed
fn ride_zebra(z: Zebra) {}

#[cfg(feature = "platypus")] // This condition is UNEXPECTED, as "platypus" is NOT
                             // an expected value of `feature` and will cause a
                             // the compiler to emit the `unexpected_cfgs` lint
fn poke_platypus() {}

#[cfg(feechure = "lion")]    // This condition is UNEXPECTED, as 'feechure' is NOT
                             // a expected condition name, no `cfg(feechure, ...)`
                             // was passed in `--check-cfg`
fn tame_lion() {}

#[cfg(windows = "unix")]     // This condition is UNEXPECTED, as the well known
                             // 'windows' cfg doesn't expect any values
fn tame_windows() {}

    مثال: چند نام و مقدار

    rustc --check-cfg 'cfg(is_embedded, has_feathers)' \
      --check-cfg 'cfg(feature, values("zapping", "lasers"))' \
      --cfg has_feathers --cfg 'feature="zapping"'

    #[cfg(is_embedded)]         // This condition is expected, as 'is_embedded' was
                            // provided in --check-cfg and doesn't take any value
fn do_embedded() {}

#[cfg(has_feathers)]        // This condition is expected, as 'has_feathers' was
                            // provided in --check-cfg and doesn't take any value
fn do_features() {}

#[cfg(has_mumble_frotz)]    // This condition is UNEXPECTED, as 'has_mumble_frotz'
                            // was NEVER provided in any --check-cfg arguments
fn do_mumble_frotz() {}

#[cfg(feature = "lasers")]  // This condition is expected, as "lasers" is an
                            // expected value of `feature`
fn shoot_lasers() {}

#[cfg(feature = "monkeys")] // This condition is UNEXPECTED, as "monkeys" is NOT
                            // an expected value of `feature`
fn write_shakespeare() {}

    مثال: نام‌های شرط بدون مقدار

    rustc --check-cfg 'cfg(is_embedded, has_feathers, values(any()))' \
      --cfg has_feathers

    #[cfg(is_embedded)]      // This condition is expected, as 'is_embedded' was
                         // provided in --check-cfg as condition name
fn do_embedded() {}

#[cfg(has_feathers)]     // This condition is expected, as "has_feathers" was
                         // provided in --check-cfg as condition name
fn do_features() {}

#[cfg(has_feathers = "zapping")] // This condition is expected, as "has_feathers"
                                 // was provided and because *any* values is
                                 // expected for 'has_feathers' no
                                 // warning is emitted for the value "zapping"
fn do_zapping() {}

#[cfg(has_mumble_frotz)] // This condition is UNEXPECTED, as 'has_mumble_frotz'
                         // was not provided in any --check-cfg arguments
fn do_mumble_frotz() {}
