    سطوح lint

    در rustc، lint‌ها به شش سطح تقسیم می‌شوند:

    1. allow
    2. expect
    3. warn
    4. force-warn
    5. deny
    6. forbid

    هر lint یک سطح پیش‌فرض دارد (که در فهرست lint‌ها، بعداً در همین فصل، توضیح داده شده است) و کامپایلر نیز یک سطح هشدار پیش‌فرض دارد. ابتدا توضیح می‌دهیم این سطوح چه معنایی دارند و سپس دربارهٔ پیکربندی صحبت می‌کنیم.

    allow

    این lint‌ها وجود دارند، اما به‌طور پیش‌فرض هیچ کاری نمی‌کنند. برای مثال، این کد منبع را در نظر بگیرید:

    pub fn foo() {}

    کامپایل این فایل هیچ هشداری تولید نمی‌کند:

    $ rustc lib.rs --crate-type=lib
$

    اما این کد lint با نام missing_docs را نقض می‌کند.

    این lint‌ها بیشتر برای آن وجود دارند که به‌صورت دستی و از طریق پیکربندی روشن شوند، همان‌طور که بعداً در همین بخش دربارهٔ آن صحبت خواهیم کرد.

    expect

    گاهی مفید است که lint‌ها را سرکوب کنیم، اما در عین حال مطمئن شویم که کد مورد نظر همچنان آن‌ها را صادر می‌کند. سطح ‘expect’ دقیقاً همین کار را انجام می‌دهد. اگر lint مورد نظر صادر نشود، lint با نام unfulfilled_lint_expectations روی attribute با نام expect فعال می‌شود و به شما اطلاع می‌دهد که این انتظار دیگر برآورده نمی‌شود.

    fn main() {
    #[expect(unused_variables)]
    let unused = "Everyone ignores me";

    #[expect(unused_variables)] // `unused_variables` lint is not emitted
    let used = "I'm useful";    // the expectation is therefore unfulfilled
    println!("The `used` value is equal to: {:?}", used);
}

    این کد هشدار زیر را تولید می‌کند:

    warning: this lint expectation is unfulfilled
 --> src/main.rs:7:14
  |
7 |     #[expect(unused_variables)]
  |              ^^^^^^^^^^^^^^^^
  |
  = note: `#[warn(unfulfilled_lint_expectations)]` on by default

    این سطح را فقط می‌توان از طریق attribute با نام #[expect] تعریف کرد؛ پرچم معادلی وجود ندارد. lint‌هایی که سطح ویژهٔ ‘force-warn’ دارند همچنان مثل همیشه صادر می‌شوند.

    warn

    سطح lint با نام ‘warn’ در صورتی که lint را نقض کنید یک هشدار تولید می‌کند. برای مثال، این کد با lint با نام unused_variables در تعارض است:

    pub fn foo() {
    let x = 5;
}

    این کد این هشدار را تولید می‌کند:

    $ rustc lib.rs --crate-type=lib
warning: unused variable: `x`
 --> lib.rs:2:9
  |
2 |     let x = 5;
  |         ^
  |
  = note: `#[warn(unused_variables)]` on by default
  = note: to avoid this warning, consider using `_x` instead

    force-warn

    ‘force-warn’ یک سطح lint ویژه است. از این جهت مثل ‘warn’ است که lint در این سطح یک هشدار تولید می‌کند، اما برخلاف سطح ‘warn’، سطح ‘force-warn’ را نمی‌توان بازنویسی (override) کرد. اگر یک lint روی ‘force-warn’ تنظیم شود، تضمین می‌شود که هشدار بدهد: نه بیشتر و نه کمتر. این موضوع حتی در صورتی که سطح کلی lint از طریق cap-lints محدود شده باشد نیز صادق است.

    deny

    یک lint با سطح ‘deny’ در صورت نقض یک خطا تولید می‌کند. برای مثال، این کد با lint با نام arithmetic_overflow برخورد می‌کند.

    fn main() {
    100u8 << 10;
}
    $ rustc main.rs
error: this arithmetic operation will overflow
 --> main.rs:2:5
  |
2 |     100u8 << 10;
  |     ^^^^^^^^^^^ attempt to shift left by `10_i32`, which would overflow
  |
  = note: `#[deny(arithmetic_overflow)]` on by default

    تفاوت یک خطای ناشی از lint با یک خطای معمولی قدیمی چیست؟ lint‌ها از طریق سطوح قابل پیکربندی هستند، بنابراین مشابه lint‌های ‘allow’، هشدارهایی که به‌طور پیش‌فرض ‘deny’ هستند به شما اجازه می‌دهند آن‌ها را مجاز کنید. به همین ترتیب، ممکن است بخواهید lint‌ی را که به‌طور پیش‌فرض warn است طوری تنظیم کنید که به‌جای آن خطا تولید کند. این سطح lint همین امکان را به شما می‌دهد.

    forbid

    ‘forbid’ یک سطح lint ویژه است که برای ‘deny’ همان نقشی را دارد که ‘force-warn’ برای ‘warn’ دارد. از این جهت مثل ‘deny’ است که lint در این سطح یک خطا تولید می‌کند، اما برخلاف سطح ‘deny’، سطح ‘forbid’ را نمی‌توان به سطحی پایین‌تر از خطا بازنویسی کرد. با این حال، سطوح lint همچنان می‌توانند با --cap-lints محدود شوند (بخش پایین را ببینید)، بنابراین rustc --cap-lints warn باعث می‌شود lint‌هایی که روی ‘forbid’ تنظیم شده‌اند فقط هشدار بدهند.

    پیکربندی سطوح هشدار

    مثال missing_docs را از سطح lint با نام ‘allow’ به یاد دارید؟

    $ cat lib.rs
pub fn foo() {}
$ rustc lib.rs --crate-type=lib
$

    می‌توانیم این lint را طوری پیکربندی کنیم که در سطح بالاتری عمل کند، هم با پرچم‌های کامپایلر و هم با attribute در کد منبع.

    همچنین می‌توانید برای lint‌ها «سقف» (cap) تعیین کنید تا کامپایلر بتواند برخی سطوح lint را نادیده بگیرد. این مورد را در آخر توضیح می‌دهیم.

    از طریق پرچم کامپایلر

    پرچم‌های -A، -W، --force-warn، -D و -F به شما اجازه می‌دهند یک یا چند lint را به سطوح allow، warn، force-warn، deny یا forbid ببرید، به این صورت:

    $ rustc lib.rs --crate-type=lib -W missing-docs
warning: missing documentation for crate
 --> lib.rs:1:1
  |
1 | pub fn foo() {}
  | ^^^^^^^^^^^^
  |
  = note: requested on the command line with `-W missing-docs`

warning: missing documentation for a function
 --> lib.rs:1:1
  |
1 | pub fn foo() {}
  | ^^^^^^^^^^^^

    $ rustc lib.rs --crate-type=lib -D missing-docs
error: missing documentation for crate
 --> lib.rs:1:1
  |
1 | pub fn foo() {}
  | ^^^^^^^^^^^^
  |
  = note: requested on the command line with `-D missing-docs`

error: missing documentation for a function
 --> lib.rs:1:1
  |
1 | pub fn foo() {}
  | ^^^^^^^^^^^^

error: aborting due to 2 previous errors

    همچنین می‌توانید برای تغییر چند lint، هر پرچم را بیش از یک بار بدهید:

    $ rustc lib.rs --crate-type=lib -D missing-docs -D unused-variables

    و البته می‌توانید این پنج پرچم را با هم ترکیب کنید:

    $ rustc lib.rs --crate-type=lib -D missing-docs -A unused-variables

    ترتیب این آرگومان‌های خط فرمان در نظر گرفته می‌شود. دستور زیر lint با نام unused-variables را مجاز می‌کند، چون آخرین آرگومان برای آن lint است:

    $ rustc lib.rs --crate-type=lib -D unused-variables -A unused-variables

    می‌توانید از این رفتار استفاده کنید و سطح یک lint مشخص را از میان گروهی از lint‌ها بازنویسی کنید. مثال زیر همهٔ lint‌های گروه unused را deny می‌کند، اما lint با نام unused-variables را در آن گروه صراحتاً مجاز می‌کند (forbid صرف‌نظر از ترتیب همچنان بر همه چیز غلبه دارد):

    $ rustc lib.rs --crate-type=lib -D unused -A unused-variables

    از آنجا که force-warn و forbid را نمی‌توان بازنویسی کرد، تنظیم یکی از آن‌ها مانع از اثرگذاری هر سطح بعدی برای همان lint می‌شود.

    از طریق attribute

    همچنین می‌توانید سطح lint را با یک attribute در سطح کل crate تغییر دهید:

    $ cat lib.rs
#![warn(missing_docs)]

pub fn foo() {}
$ rustc lib.rs --crate-type=lib
warning: missing documentation for crate
 --> lib.rs:1:1
  |
1 | / #![warn(missing_docs)]
2 | |
3 | | pub fn foo() {}
  | |_______________^
  |
note: lint level defined here
 --> lib.rs:1:9
  |
1 | #![warn(missing_docs)]
  |         ^^^^^^^^^^^^

warning: missing documentation for a function
 --> lib.rs:3:1
  |
3 | pub fn foo() {}
  | ^^^^^^^^^^^^

    warn، allow، deny و forbid همگی به همین شکل کار می‌کنند. راهی برای تنظیم یک lint روی force-warn با استفاده از attribute وجود ندارد.

    همچنین می‌توانید چند lint را در هر attribute بدهید:

    #![warn(missing_docs, unused_variables)]

pub fn foo() {}

    و چند attribute را با هم به کار ببرید:

    #![warn(missing_docs)]
#![deny(unused_variables)]

pub fn foo() {}

    همهٔ attribute‌های lint از یک پارامتر اضافی با نام reason پشتیبانی می‌کنند تا زمینه‌ای دربارهٔ اینکه چرا یک attribute خاص افزوده شده است ارائه دهند. اگر lint در سطح تعریف‌شده صادر شود، این دلیل به‌عنوان بخشی از پیام lint نمایش داده می‌شود.

    use std::path::PathBuf;
pub fn get_path() -> PathBuf {
    #[allow(unused_mut, reason = "this is only modified on some platforms")]
    let mut file_name = PathBuf::from("git");
    #[cfg(target_os = "windows")]
    file_name.set_extension("exe");
    file_name
}

    سقف‌گذاری برای lint‌ها

    rustc از پرچمی با نام --cap-lints LEVEL پشتیبانی می‌کند که «سطح سقف lint» را تعیین می‌کند. این بیشینهٔ سطح برای همهٔ lint‌هاست. بنابراین برای مثال، اگر نمونه‌کد خود را از سطح lint با نام «deny» در بالا در نظر بگیریم:

    fn main() {
    100u8 << 10;
}

    و آن را با سقف warn برای lint‌ها کامپایل کنیم:

    $ rustc lib.rs --cap-lints warn
warning: this arithmetic operation will overflow
 --> lib.rs:2:5
  |
2 |     100u8 << 10;
  |     ^^^^^^^^^^^ attempt to shift left by `10_i32`, which would overflow
  |
  = note: `#[warn(arithmetic_overflow)]` on by default

    اکنون فقط هشدار می‌دهد و خطا تولید نمی‌کند. می‌توانیم جلوتر برویم و همهٔ lint‌ها را مجاز کنیم:

    $ rustc lib.rs --cap-lints allow
$

    Cargo از این قابلیت به‌شدت استفاده می‌کند؛ هنگام کامپایل وابستگی‌های شما --cap-lints allow را می‌دهد تا اگر آن‌ها هشداری داشتند، خروجی ساخت شما را آلوده نکنند. با این حال، توجه کنید که --cap-lints allow lint‌هایی را که با force-warn علامت‌گذاری شده‌اند بازنویسی نمی‌کند.

    اولویت منابع سطح lint

    Rust اجازه می‌دهد سطوح lint (allow، warn، deny، forbid، force-warn) از طریق منابع گوناگون تنظیم شوند:

    • attribute‌ها: #[allow(...)]، #![deny(...)] و مانند آن.
    • گزینه‌های خط فرمان: --cap-lints، --force-warn، -A، -W، -D، -F

    در ادامه توضیح می‌دهیم که این کنترل‌های مختلف lint چگونه با هم تعامل می‌کنند:

    1. --force-warn یک lint را به سطح هشدار می‌برد و بر attribute‌ها و همهٔ پرچم‌های دیگر CLI اولویت دارد.

      #[forbid(unused_variables)]
fn main() {
    let x = 42;
}

      کامپایل با:

       $ rustc --force-warn unused_variables lib.rs
 warning: unused variable: `x`
   --> lib.rs:3:9
   |
 3 |     let x = 42;
   |         ^ help: if this is intentional, prefix it with an underscore: `_x`
   |
   = note: requested on the command line with `--force-warn unused-variables`

 warning: 1 warning emitted

    2. --cap-lints بیشینهٔ سطح یک lint را تعیین می‌کند و بر attribute‌ها و همچنین پرچم‌های -D، -W و -F در CLI اولویت دارد.

      #[deny(unused_variables)]
fn main() {
    let x = 42;
}

      کامپایل با:

       $ rustc --cap-lints=warn lib.rs
 warning: unused variable: `x`
 --> test1.rs:3:9
   |
 3 |     let x = 42;
   |         ^ help: if this is intentional, prefix it with an underscore: `_x`
   |
 note: the lint level is defined here
 --> test1.rs:1:8
   |
 1 | #[deny(unused_variables)]
   |        ^^^^^^^^^^^^^^^^

 warning: 1 warning emitted

    3. پرچم‌های سطح CLI سطح پیش‌فرض یک lint را بازنویسی می‌کنند. این پرچم‌ها اساساً مانند attribute‌های سطح crate رفتار می‌کنند. attribute‌های داخل کد منبع بر پرچم‌های CLI اولویت دارند، به‌جز -F/--forbid که نمی‌توان آن را بازنویسی کرد.

      ترتیب پرچم‌ها اهمیت دارد؛ پرچم‌های سمت راست بر پرچم‌های قبلی اولویت دارند.

      fn main() {
    let x = 42;
}

      کامپایل با:

       $ rustc -A unused_variables -D unused_variables lib.rs
 error: unused variable: `x`
 --> test1.rs:2:9
   |
 2 |     let x = 42;
   |         ^ help: if this is intentional, prefix it with an underscore: `_x`
   |
   = note: requested on the command line with `-D unused-variables`

 error: aborting due to 1 previous error

    4. در داخل کد منبع، attribute‌های در سطح پایین‌تر درخت نحو بر attribute‌های سطح بالاتر اولویت دارند، و همچنین بر attribute قبلی روی همان موجودیت، با ترتیب چپ‌به‌راست در کد منبع.

      #![deny(unused_variables)]

#[allow(unused_variables)]
fn main() {
    let x = 42; // Allow wins
}
      • استثنا این است که وقتی یک lint روی “forbid” تنظیم شد، تلاش برای تغییر سطح آن خطا است، به‌جز deny که درون بافتار forbid مجاز است، اما نادیده گرفته می‌شود.

    از نظر اولویت، گروه‌های lint طوری رفتار می‌شوند که گویی به فهرستی از همهٔ lint‌هایی که در بر دارند گسترش یافته‌اند. استثنا گروه warnings است که ترتیب attribute‌ها و CLI را نادیده می‌گیرد و بر همهٔ lint‌هایی که در غیر این صورت داخل آن موجودیت هشدار می‌دادند اعمال می‌شود.
