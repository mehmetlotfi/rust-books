    *-unknown-uefi

    سطح: 2

    اهداف Unified Extensible Firmware Interface (UEFI) برای فایل‌های دودویی برنامه‌ای، درایور و هستهٔ UEFI.

    اهداف موجود:

    • aarch64-unknown-uefi
    • i686-unknown-uefi
    • x86_64-unknown-uefi

    نگهدارندگان هدف

    • @dvdhrm
    • @nicholasbishop
    • (for aarch64-unknown-uefi only) arm-maintainers (rust@arm.com)
      • برای اطلاع‌رسانی به ما از @rustbot ping arm-maintainers استفاده کنید

    الزامات

    همهٔ اهداف UEFI را می‌توان از طریق کامپایل متقاطع به‌عنوان محیط‌های no-std به کار برد. پشتیبانی از std وجود دارد، اما ناقص و بسیار جدید است. alloc در صورتی پشتیبانی می‌شود که کاربر یک تخصیص‌دهنده فراهم کند یا از std استفاده شود. هیچ ابزار میزبانی پشتیبانی نمی‌شود.

    محیط UEFI شبیه محیط Microsoft Windows است، با چند تفاوت جزئی. بنابراین کامپایل متقاطع برای UEFI با همان ابزارهایی انجام می‌شود که کامپایل متقاطع برای Windows. فایل‌های دودویی هدف با قالب PE32+ کدگذاری می‌شوند؛ قرارداد فراخوانی در هر معماری متفاوت است، اما با آنچه Windows استفاده می‌کند مطابقت دارد (اگر معماری را Windows پشتیبانی کند). قرارداد فراخوانی ویژهٔ efiapi در Rust ABI درست را برای پلتفرم هدف انتخاب می‌کند (extern "C" دست‌کم روی اهداف Intel نادرست است). اگر جزئیات بیشتری لازم باشد، مشخصات (specification) بخش مفصلی دربارهٔ قراردادهای فراخوانی پشتیبانی‌شدهٔ مختلف دارد.

    MMX، SSE و دیگر واحدهای FP به‌طور پیش‌فرض غیرفعال هستند تا امکان کامپایل کد هستهٔ UEFI که پیش از راه‌اندازی آن‌ها اجرا می‌شود فراهم باشد. این رفتار را می‌توان برای کامپایل‌های جداگانه از طریق پرچم‌های خط فرمان rustc تغییر داد. با این حال همهٔ firmwareها این واحدها را به‌درستی پیکربندی نمی‌کنند، بنابراین بازرسی دقیق لازم است.

    همان‌طور که در PE32+ بومی است، فایل‌های دودویی وابسته به موقعیت هستند، اما اگر مکان مطلوبشان در دسترس نباشد، می‌توان آن‌ها را در زمان اجرا جابه‌جا (relocate) کرد. کد باید به‌صورت ایستا پیوند شود. پیوند پویا پشتیبانی نمی‌شود. کد از طریق رابط‌های UEFI به اشتراک گذاشته می‌شود، نه با پیوند پویا. علاوه بر این، UEFI اجرای کد روی هر چیزی جز CPU/نخ بوت را ممنوع می‌کند و استفاده از وقفه (interrupt) نیز مجاز نیست (به‌جز وقفهٔ تایمر). درایورهای دستگاه موظف‌اند از روش‌های polling استفاده کنند.

    UEFI از یک فضای آدرس واحد برای اجرای همهٔ کدها استفاده می‌کند. چندین برنامه را می‌توان هم‌زمان بارگذاری کرد و آن‌ها با چندوظیفگی همکارانه (cooperative multitasking) روی یک پشتهٔ واحد اجرا می‌شوند.

    به‌طور پیش‌فرض، اهداف UEFI از نوع link پیوندگر LLVM یعنی lld استفاده می‌کنند تا فایل‌های دودویی را به فایل PE32+ نهایی با پسوند *.efi پیوند دهند. زیرسیستم PE روی EFI_APPLICATION تنظیم شده است، اما می‌توان با ارسال /subsystem:<...> به پیوندگر آن را تغییر داد. به‌طور مشابه، نقطهٔ ورود روی efi_main تنظیم شده است اما می‌توان آن را از طریق /entry:<...> تغییر داد. راهبرد panic روی abort تنظیم شده است.

    مشخصات UEFI به‌صورت رایگان به‌صورت آنلاین در دسترس است: UEFI Specification Directory

    ساخت Rust برای اهداف UEFI

    می‌توان Rust را برای اهداف UEFI با فعال کردن آن‌ها در پیکربندی ساخت rustc ساخت. توجه کنید که فقط می‌توانید کتابخانه‌های استاندارد را بسازید. کامپایلر و ابزارهای میزبان فعلاً برای اهداف UEFI قابل کامپایل نیستند. یک پیکربندی نمونه چنین است:

    [build]
build-stage = 1
target = ["x86_64-unknown-uefi"]

    ساخت برنامه‌های Rust

    از Rust 1.67 به بعد، artifactهای از پیش کامپایل‌شده از طریق rustup ارائه می‌شوند. برای مثال، برای استفاده از x86_64-unknown-uefi:

    # install cross-compile toolchain
rustup target add x86_64-unknown-uefi
# target flag may be used with any cargo or rustc command
cargo build --target x86_64-unknown-uefi

    ساخت یک درایور

    سه نوع فایل اجرایی UEFI وجود دارد: برنامه (application)، درایور سرویس بوت (boot service driver) و درایور زمان اجرا (runtime driver). همهٔ اهداف UEFI در Rust به‌طور پیش‌فرض برنامه تولید می‌کنند. برای ساخت درایور به‌جای آن، پرچم پیوندگر subsystem را با مقدار efi_boot_service_driver یا efi_runtime_driver بدهید.

    مثال:

    # In .cargo/config.toml:
[build]
rustflags = ["-C", "link-args=/subsystem:efi_runtime_driver"]

    آزمون

    برنامه‌های UEFI را می‌توان روی هر سیستم UEFI در ESP کپی کرد و از طریق منوی بوت firmware اجرا کرد. مجموعهٔ qemu نیز امکان شبیه‌سازی سیستم‌های UEFI و اجرای برنامه‌های UEFI را فراهم می‌کند. برای جزئیات، مستندات آن را ببینید.

    ابزار Rust با نام uefi-run یک پوشش ساده پیرامون qemu است که می‌تواند برنامه‌های UEFI را در qemu اجرا کند. می‌توانید آن را با cargo install --locked uefi-run نصب کنید و برنامه‌های qemu را به‌صورت uefi-run ./application.efi اجرا کنید.

    toolchainهای کامپایل متقاطع و کد C

    سه روش رایج برای کامپایل کد C بومی برای اهداف UEFI وجود دارد:

    • استفاده از SDK رسمی Intel: Tianocore/EDK2. این SDK از پلتفرم‌های بسیاری پشتیبانی می‌کند، مشخصات کامل را به C منتقل‌شده همراه دارد، و مثال‌ها و یکپارچه‌سازی‌های فراوانی با سیستم ساخت دارد. این تنها پلتفرمی است که Intel به‌طور رسمی پشتیبانی می‌کند و بسیاری از پیاده‌سازی‌های بزرگ firmware از آن استفاده می‌کنند. هر کدی که با SDK کامپایل شود با فایل‌های دودویی Rust که برای اهداف UEFI کامپایل شده‌اند سازگار است. می‌توانید آن‌ها را مستقیماً به فایل‌های دودویی Rust خود پیوند دهید، یا از طریق پروتکل‌های UEFI یکدیگر را فراخوانی کنند.
    • استفاده از مجموعهٔ GNU-EFI. این رویکرد را بسیاری از برنامه‌های UEFI در اکوسیستم Linux/OSS به کار می‌برند. کامپایلر GCC برای کامپایل فایل‌های دودویی ELF استفاده می‌شود، و با یک pre-loader پیوند می‌شود که فایل دودویی ELF را در زمان اجرا به PE32+ تبدیل می‌کند. تنها از طریق پروتکل‌های UEFI می‌توانید چنین فایل‌های دودویی‌ای را با اهداف UEFI در Rust ترکیب کنید. پیوند دادن هر دو به یک فایل اجرایی واحد شکست می‌خورد، زیرا یکی فایل اجرایی ELF است و دیگری PE32+. اگر پیوند به فایل‌های اجرایی GNU-EFI مطلوب باشد، باید کد Rust خود را به‌صورت بومی برای همان هدف GNU که GNU-EFI استفاده می‌کند کامپایل کنید و از pre-loader آن‌ها استفاده کنید. این کار نیازمند بررسی دقیق دربارهٔ این است که هنگام فراخوانی پروتکل‌های بومی UEFI یا فراخوانی کد پیوندشدهٔ GNU-EFI از کدام قرارداد فراخوانی استفاده شود (مشابه اینکه این تفاوت‌ها هنگام نوشتن کد C برای GNU-EFI باید لحاظ شوند).
    • استفاده از اهداف بومی Windows. یعنی کد C خود را برای پلتفرم Windows کامپایل کنید، گویی پلتفرم UEFI است. این روش برای کتابخانه‌های ایستا کار می‌کند، اما هنگام پیوند به یک فایل اجرایی UEFI به تنظیماتی نیاز دارد. با این حال می‌توانید چنین کتابخانه‌های ایستایی را به‌سادگی به کد Rust که برای اهداف UEFI کامپایل شده پیوند دهید. مراقب هر includeی باشید که به‌طور خاص برای اهداف UEFI مناسب نیست (به‌ویژه includeهای کتابخانهٔ استاندارد C همیشه سازگار نیستند). برای جلوگیری از ناسازگاری‌ها، کامپایل freestanding توصیه می‌شود.

    اکوسیستم

    زبان Rust سابقهٔ طولانی در پشتیبانی از اهداف UEFI دارد. crateهای بسیاری برای دسترسی به پروتکل‌های UEFI و راحت‌تر کردن برنامه‌نویسی UEFI در Rust توسعه یافته‌اند. فهرست زیر مروری کوتاه است (به ترتیب الفبایی):

    • efi: اتصال‌های (binding) ارگونومیک Rust برای نوشتن برنامه‌های UEFI. دسترسی rustified به پروتکل‌های UEFI را فراهم می‌کند، تخصیص‌دهنده‌ها را پیاده‌سازی می‌کند و یک محیط امن برای نوشتن برنامه‌های UEFI ارائه می‌دهد.
    • r-efi: ثابت‌ها و تعریف‌های پروتکل در مشخصات مرجع UEFI. یک انتقال خالص مشخصات UEFI به Rust. این crate تعریف‌های خام مشخصات را بدون هیچ کمک‌کنندهٔ توسعه‌یافته یا rustification ارائه می‌دهد. به‌عنوان پایه‌ای برای پیاده‌سازی هر لایهٔ پیچیده‌تر UEFI در Rust به کار می‌رود.
    • uefi-rs: پوششی امن و آسان برای ساخت برنامه‌های UEFI. یک کتابخانهٔ مفصل که انتزاع‌های امن برای پروتکل‌ها و قابلیت‌های UEFI فراهم می‌کند. تخصیص‌دهنده‌ها را پیاده‌سازی می‌کند و یک محیط اجرا برای برنامه‌های UEFI نوشته‌شده با Rust فراهم می‌کند.
    • uefi-run: اجرای برنامه‌های UEFI. یک پوشش کوچک پیرامون qemu برای اجرای برنامه‌های UEFI در یک ماشین شبیه‌سازی‌شدهٔ x86_64.

    مثال: Freestanding

    کد زیر یک برنامهٔ UEFI معتبر است که هنگام اجرا بلافاصله با کد خروج 0 برمی‌گردد. یک panic handler نیز ارائه شده است که هنگام panic توسط Rust اجرا می‌شود. برای سادگی، فقط در یک حلقهٔ بی‌نهایت می‌افتیم.

    این مثال را می‌توان به‌عنوان یک crate دودویی با cargo کامپایل کرد:

    cargo build --target x86_64-unknown-uefi

    #![no_main]
#![no_std]

#[panic_handler]
fn panic_handler(_info: &core::panic::PanicInfo) -> ! {
    loop {}
}

#[export_name = "efi_main"]
pub extern "C" fn main(_h: *mut core::ffi::c_void, _st: *mut core::ffi::c_void) -> usize {
    0
}

    مثال: Hello World

    این مثال یک برنامهٔ UEFI است که “Hello World!” را چاپ می‌کند، سپس پیش از خروج منتظر ورودی کلید می‌ماند. این مثال پایه‌ای است برای نوشتن برنامه‌های UEFI بدون هیچ ماژول کمکی، جز تعریف‌های مستقل پروتکل UEFI که crate با نام r-efi ارائه می‌دهد.

    این مثال مثال “Freestanding” را گسترش می‌دهد و بر تنظیمات آن بنا می‌شود. برای دستور کامپایل آن به‌عنوان crate دودویی به آنجا مراجعه کنید.

    توجه کنید که UEFI از رشته‌های UTF-16 استفاده می‌کند. چون literalهای Rust با UTF-8 هستند، باید از یک آرایهٔ UTF-16 دستی (open-coded) و پایان‌یافته با صفر به‌عنوان آرگومان output_string() استفاده کنیم. مشابه panic handler، برنامه‌های واقعی باید به‌جای این از ماژول‌های UTF-16 استفاده کنند.

    #![no_main]
#![no_std]

use r_efi::efi;

#[panic_handler]
fn panic_handler(_info: &core::panic::PanicInfo) -> ! {
    loop {}
}

#[export_name = "efi_main"]
pub extern "C" fn main(_h: efi::Handle, st: *mut efi::SystemTable) -> efi::Status {
    let s = [
        0x0048u16, 0x0065u16, 0x006cu16, 0x006cu16, 0x006fu16, // "Hello"
        0x0020u16, //                                             " "
        0x0057u16, 0x006fu16, 0x0072u16, 0x006cu16, 0x0064u16, // "World"
        0x0021u16, //                                             "!"
        0x000au16, //                                             "\n"
        0x0000u16, //                                             NUL
    ];

    // Print "Hello World!".
    let r =
        unsafe { ((*(*st).con_out).output_string)((*st).con_out, s.as_ptr() as *mut efi::Char16) };
    if r.is_error() {
        return r;
    }

    // Wait for key input, by waiting on the `wait_for_key` event hook.
    let r = unsafe {
        let mut x: usize = 0;
        ((*(*st).boot_services).wait_for_event)(1, &mut (*(*st).con_in).wait_for_key, &mut x)
    };
    if r.is_error() {
        return r;
    }

    efi::Status::SUCCESS
}

    std در Rust برای UEFI

    این بخش اطلاعاتی دربارهٔ نحوهٔ استفاده از std در UEFI دارد.

    ساخت std

    بخش ساخت std تقریباً همان مستندات رسمی است. پیوندگری که باید استفاده شود rust-lld است. این یک bootstrap.toml نمونه است:

    [rust]
lld = true

    سپس فقط با x.py بسازید:

    ./x.py build --target x86_64-unknown-uefi --stage 1

    از طرف دیگر، می‌توان از قابلیت build-std استفاده کرد. با این حال باید از toolchain‌ای استفاده کنید که وصله‌های std برای UEFI را دارد. سپس پروژه را فقط با دستور زیر بسازید:

    cargo build --target x86_64-unknown-uefi -Zbuild-std=std,panic_abort

    قابلیت‌های پیاده‌سازی‌شده

    alloc

    • با EFI_BOOT_SERVICES.AllocatePool() و EFI_BOOT_SERVICES.FreePool() پیاده‌سازی شده است.
    • همهٔ آزمون‌ها را با موفقیت می‌گذراند.
    • در حال حاضر از EfiLoaderData به‌عنوان EFI_ALLOCATE_POOL->PoolType استفاده می‌کند.

    cmath

    • توسط compiler-builtins ارائه می‌شود.

    env

    • فقط چند ثابت سراسری.

    locks

    • قفل‌های ارائه‌شده باید روی همهٔ پیاده‌سازی‌های استاندارد تک‌نخی UEFI کار کنند.

    os_str

    • اگرچه رشته‌ها در UEFI باید UCS-2 معتبر باشند، در عمل بسیاری از پیاده‌سازی‌ها اهمیتی نمی‌دهند و از رشته‌های UTF-16 استفاده می‌کنند.
    • بنابراین پیاده‌سازی فعلی از رشته‌های کامل UTF-16 پشتیبانی می‌کند.

    stdio

    • از Simple Text Input Protocol و Simple Text Output Protocol استفاده می‌کند.
    • توجه: UEFI برای خط جدید از CRLF استفاده می‌کند. این یعنی کلید Enter به‌جای LF به‌صورت CR ثبت می‌شود.

    args

    • از EFI_LOADED_IMAGE_PROTOCOL->LoadOptions استفاده می‌کند

    مثال: Hello World با std

    کد زیر یک برنامهٔ UEFI معتبر را نشان می‌دهد که شامل stdio و alloc (OsString و Vec) است:

    این مثال را می‌توان به‌عنوان یک crate دودویی با cargo و با استفاده از toolchain ساخته‌شده از سورس بالا (با نام custom) کامپایل کرد:

    cargo +custom build --target x86_64-unknown-uefi

    #![feature(uefi_std)]

use r_efi::{efi, protocols::simple_text_output};
use std::{
  ffi::OsString,
  os::uefi::{env, ffi::OsStrExt}
};

pub fn main() {
  println!("Starting Rust Application...");

  // Use System Table Directly
  let st = env::system_table().as_ptr() as *mut efi::SystemTable;
  let mut s: Vec<u16> = OsString::from("Hello World!\n").encode_wide().collect();
  s.push(0);
  let r =
      unsafe {
        let con_out: *mut simple_text_output::Protocol = (*st).con_out;
        let output_string: extern "efiapi" fn(_: *mut simple_text_output::Protocol, *mut u16) -> efi::Status = (*con_out).output_string;
        output_string(con_out, s.as_ptr() as *mut efi::Char16)
      };
  assert!(!r.is_error())
}

    BootServices

    پیاده‌سازی فعلی std پس از فراخوانی ExitBootServices، BootServices را در دسترس قرار نمی‌دهد. برای اطلاعات بیشتر دربارهٔ نحوهٔ مدیریت جابه‌جایی از آدرس‌های فیزیکی به آدرس‌های مجازی، به Runtime Drivers مراجعه کنید.
