    QNX

    سطح (Tier): ۳

    پشتیبانی از QNX® و QNX Software Development Platform (SDP)، نسخه‌های 7.0، 7.1 و 8.0.

    QNX Software Development Platform (SDP) یک محیط توسعه است که آن را روی یک رایانهٔ میزبان دانلود و نصب می‌کنید. این محیط شامل یک toolchain زبان C برای میزبان شما، یک IDE و بسته‌های پشتیبانی برد (board support package) گوناگون برای پلتفرم‌های هدف مختلف است. سپس می‌توانید از QNX SDP برای ساخت یک محیط زمان اجرای سفارشی استفاده کنید که آن را روی یک دستگاه نهفته (embedded) مستقر می‌کنید. این محیط زمان اجرا شامل یک میکروکرنل (microkernel)، هر سرویسی که انتخاب کرده باشید و شاید یک یا چند برنامهٔ نوشته‌شده با Rust خواهد بود.

    در QNX SDP 7.x محیط زمان اجرا بر پایه QNX Neutrino RTOS 7.x است، در حالی که در QNX SDP 8.0 محیط زمان اجرا بر پایه QNX OS 8.0 است. تغییر نام بازتاب‌دهنده تغییرات معماری در RTOS است، اما هر دو از طراحی میکروکرنل استفاده می‌کنند.

    در جدول بالا، «پشتیبانی کامل» به پشتیبانی از ساخت برنامه‌های Rust با کتابخانه استاندارد کامل اشاره دارد. علامت «?» یعنی پشتیبانی در دست انجام است. پشتیبانی no_std برای ساخت برنامه‌های #![no_std] است که در آن‌ها فقط core و alloc در دسترس هستند.

    برای ساخت یا استفاده از toolchain زبان Rust برای QNX، نسخهٔ مربوط از QNX Software Development Platform (SDP) باید نصب و مقداردهی اولیه شده باشد. مقداردهی اولیه معمولاً با source کردن qnxsdp-env.sh انجام می‌شود (این فایل به‌عنوان بخشی از SDP نصب می‌شود، پس دستورالعمل نصب همراه SDP را ببینید). پس از آن qcc (کامپایلر C/C++ در QNX) باید در PATH سیستم شما در دسترس باشد، چون در حین کامپایل Rust فراخوانی می‌شود (مثلاً برای لینک کردن فایل‌های اجرایی).

    هنگام لینک کردن برنامه‌های no_std، آن‌ها باید با libc.so لینک شوند (مثال را ببینید). این کار لازم است چون برنامه‌ها همیشه با کتابخانه crt لینک می‌شوند و crt به libc.so وابسته است. هنگام استفاده از کتابخانه استاندارد این کار به‌طور خودکار انجام می‌شود.

    کامپایل شرطی

    برای کامپایل شرطی، attributeهای ویژه QNX زیر تعریف شده‌اند:

    • target_os = "nto"
      • target_env = "nto70" (برای QNX SDP 7.0)
      • target_env = "nto71" (برای QNX SDP 7.1 با پشته شبکه «کلاسیک» یعنی “io_pkt”)
      • target_env = "nto71_iosock" (برای QNX SDP 7.1 با پشته شبکه «جدید» یعنی “io_sock”)
    • target_os = "qnx" (برای QNX SDP 8.0 یا بالاتر)

    ساخت هدف

    1. ایجاد یک فایل bootstrap.toml

      محتوای نمونه:

      profile = "compiler"
change-id = 999999

[build]
host = ["x86_64-unknown-linux-gnu"]
target = ["x86_64-unknown-linux-gnu", "aarch64-unknown-nto-qnx710"]

    2. کامپایل toolchain زبان Rust با بارگذاری‌شدن محیط QNX SDP

      همان‌طور که در بالا اشاره شد، برای کار کردن QNX SDP به متغیرهای محیطی درست نیاز داریم و باید qcc در PATH سیستم شما باشد. معمولاً این کار با source کردن فایل qnxsdp-env.sh (یا معادل آن برای پلتفرم میزبان شما) انجام می‌شود.

      برای ساخت روی لینوکس، این دستورها را اجرا می‌کنید:

      source ~/qnx710/qnxsdp-env.sh
./x.py build rustc library/core library/alloc library/std

    ساخت برنامه‌های Rust

    Rust مصنوعات (artifact) از پیش کامپایل‌شده‌ای برای این هدف ارائه نمی‌کند. برای کامپایل برای این هدف، باید یا Rust را با فعال بودن این هدف بسازید (به «ساخت هدف» در بالا مراجعه کنید)، یا نسخه خودتان از core را با استفاده از build-std یا روشی مشابه بسازید.

    فایل‌های اجرایی کامپایل‌شده می‌توانند مستقیماً روی QNX اجرا شوند، چه با گنجاندن آن‌ها در تصویر دیسک (disk image)، و چه با کپی کردن آن‌ها از طریق شبکه به یک سیستم در حال اجرا.

    کامپایل کد C نیازمند تنظیم همان متغیرهای محیطی‌ای است که برای کامپایل toolchain زبان Rust لازم است (بالا را ببینید)، تا اطمینان حاصل شود qcc با آرگومان‌های مناسب استفاده می‌شود. برای حفظ سازگاری، هیچ آرگومان دیگری را که مثلاً قرارداد فراخوانی یا چینش حافظه را تغییر می‌دهد مشخص نکنید.

    اجرای مجموعه آزمون‌های Rust

    مجموعه آزمون‌های کامپایلر Rust و کتابخانه استاندارد را می‌توان تقریباً مانند هدف‌های دیگر Rust اجرا کرد. محیط آزمون باید با محیطی که هنگام کامپایل کامپایلر استفاده شده یکسان باشد (به نکته‌های مربوط به qnxsdp-env.sh در بالا مراجعه کنید) و علاوه بر آن متغیر محیطی TEST_DEVICE_ADDR هم تنظیم شود. متغیر TEST_DEVICE_ADDR اجراکننده راه دور را کنترل می‌کند و باید به یک هدف در حال اجرای فایل اجرایی remote-test-server اشاره کند.

    توجه کنید که برخی آزمون‌ها شکست می‌خورند و به همین دلیل نگهدارندگان هدف در حال حاضر آن‌ها را کنار گذاشته‌اند، که در مثال زیر دیده می‌شود.

    برای اجرای همه آزمون‌ها روی یک هدف x86_64 QNX Neutrino 7.1:

    source ~/qnx710/qnxsdp-env.sh
export TEST_DEVICE_ADDR="1.2.3.4:12345" # must address the test target, can be a SSH tunnel

# Disable tests that only work on the host or don't make sense for this target.
# See also:
# - src/ci/docker/host-x86_64/i686-gnu/Dockerfile
# - https://rust-lang.zulipchat.com/#narrow/stream/182449-t-compiler.2Fhelp/topic/Running.20tests.20on.20remote.20target
# - .github/workflows/ci.yml
export exclude_tests='
    --exclude src/bootstrap
    --exclude src/tools/error_index_generator
    --exclude src/tools/linkchecker
    --exclude tests/ui-fulldeps
    --exclude rustc
    --exclude rustdoc'

./x.py test \
    $exclude_tests \
    --stage 1 \
    --target x86_64-pc-nto-qnx710

    مجموعه آزمون‌های کتابخانه استاندارد Rust

    هدف برای اجرای همه آزمون‌ها به منابع کافی نیاز دارد. دستورهای زیر فرض می‌کنند که از یک تصویر QEMU استفاده می‌شود.

    • مطمئن شوید که پوشه موقتی که remote-test-server استفاده می‌کند فضای آزاد و inode کافی دارد. ۵ گیگابایت فضای آزاد و ۴۰۰۰۰ inode به‌طور شناخته‌شده کافی هستند (آزمون بیش از 32k فایل ایجاد می‌کند). برای ساخت یک تصویر QEMU در یک پوشه خالی، این دستور را داخل همان پوشه اجرا کنید:

      mkqnximage --type=qemu --ssh-ident=$HOME/.ssh/id_ed25519.pub --data-size=5000 --data-inodes=40000

      پوشه /data باید منابع آزاد کافی داشته باشد. هنگام اجرای remote-test-server متغیر محیطی TMPDIR را متناسب با آن تنظیم کنید، مثلاً: bash TMPDIR=/data/tmp/rust remote-test-server --bind 0.0.0.0:12345

      TMPDIR=/data/tmp/rust remote-test-server --bind 0.0.0.0:12345

    • مطمئن شوید که پشته TCP می‌تواند تعداد کافی اتصال موازی را مدیریت کند (پیش‌فرض ۲۰۰ است و باید ۳۰۰ یا بیشتر باشد). پس از ساخت یک تصویر (بالا را ببینید)، فایل output/build/startup.sh را ویرایش کنید:

      1. به دنبال io-pkt-v6-hc بگردید
      2. پارامتر -ptcpip threads_max=300 را اضافه کنید، مثلاً: text io-pkt-v6-hc -U 33:33 -d e1000 -ptcpip threads_max=300 
        io-pkt-v6-hc -U 33:33 -d e1000 -ptcpip threads_max=300
      3. تصویر را با اجرای دوباره mkqnximage با همان پارامترهای بالا که برای ساخت آن استفاده شد به‌روز کنید.

    • اجرا و توقف ماشین مجازی

      برای راه‌اندازی ماشین مجازی، این دستور را داخل پوشه VM اجرا کنید:

      mkqnximage --run=-h

      برای توقف ماشین مجازی، این دستور را داخل پوشه VM اجرا کنید:

      mkqnximage --stop

    • اطمینان از شبکه محلی

      مطمئن شوید که ‘localhost’ به 127.0.0.1 resolve می‌شود. اگر نمی‌توانید localhost را ping کنید، ممکن است برخی آزمون‌ها شکست بخورند. مطمئن شوید که این مورد به /etc/hosts اضافه شده است (اگر دستور ping اول شکست خورد). دستورها باید داخل ماشین مجازی اجرا شوند!

      $ ping localhost
ping: Cannot resolve "localhost" (Host name lookup failure)

$ echo "127.0.0.1 localhost" >> /etc/hosts

$ ping localhost
PING localhost (127.0.0.1): 56 data bytes
64 bytes from 127.0.0.1: icmp_seq=0 ttl=255 time=1 ms

    غیرفعال کردن RELocation Read-Only (RELRO)

    اگرچه به‌طور پیش‌فرض توصیه نمی‌شود، برخی پیکربندی‌های هسته QNX ممکن است نیاز داشته باشند RELRO با -C relro_level=off غیرفعال شود، مثلاً با افزودن آن به فایل .cargo/config.toml:

    [target.aarch64-unknown-nto-qnx700]
rustflags = ["-C", "relro_level=off"]

    اگر هسته QNX شما این را مجاز نکند و relro غیرفعال نشده باشد، اجرای فایل دودویی کامپایل‌شده با syntax error: ... unexpected یا خطایی مشابه شکست می‌خورد. دلیل این است که هسته سعی می‌کند فایل دودویی کامپایل‌شده را با /bin/sh تفسیر کند و طبیعتاً ناموفق است. برای اطمینان از اینکه واقعاً چنین است، فایل دودویی خود را با متغیر محیطی DL_DEBUG=all اجرا کنید و به دنبال این خروجی بگردید. اگر آن را دیدید، باید relro را همان‌طور که در بالا شرح داده شد غیرفعال کنید.
