    thumbv7a-vex-v5

    Tier: 3

    امکان کامپایل برنامه‌های کاربر را برای VEX V5 Brain فراهم می‌کند، میکروکنترلری برای رباتیک آموزشی و رقابتی.

    پشتیبانی Rust از این هدف وابسته به VEX Robotics یا IFI نیست و با هیچ SDK رسمی VEX پیوند نمی‌خورد.

    این هدف پیش‌تر armv7a-vex-v5 نام داشت.

    نگهدارندگان هدف

    این هدف توسط اعضای سازمان vexide نگهداری می‌شود:

    • @lewisfm
    • @tropicaaal
    • @Gavin-Niederman

    الزامات

    این هدف کامپایل متقابل می‌شود. پیوند پویا (dynamic linking) پشتیبانی نمی‌شود.

    crateهای #![no_std] را می‌توان با استفاده از build-std برای ساخت core و panic_abort و در صورت تمایل alloc ساخت. panicهای همراه با unwinding هنوز روی این هدف پشتیبانی نمی‌شوند.

    ساخت هدف

    می‌توانید با افزودن این هدف به فهرست target در bootstrap.toml و سپس اجرای ./x build --target thumbv7a-vex-v5 compiler، Rust را با پشتیبانی از این هدف بسازید.

    ساخت برنامه‌های Rust

    Rust هنوز فایل‌های از پیش کامپایل‌شده برای این هدف ارائه نمی‌کند. برای کامپایل برای این هدف، یا باید Rust را با فعال بودن این هدف بسازید (بخش «ساخت هدف» در بالا را ببینید)، یا نسخهٔ خودتان از std را با build-std یا روشی مشابه بسازید.

    وقتی کامپایلر یک فایل دودویی می‌سازد، یک artifact ساخت با قالب ELF تولید می‌شود. برای اینکه VEXos این artifact را به‌عنوان یک برنامهٔ کاربر بشناسد، به ابزارهای اضافی نیاز است.

    ابزار cargo-v5 می‌تواند فایل‌های دودویی‌ای بسازد که بتوان آن‌ها را روی brain سری V5 بارگذاری کرد. این ابزار دستور cargo build را با ارائهٔ آرگومان‌های لازم برای ساخت هدف و تولید artifactی قابل‌شناسایی برای VEXos در بر می‌گیرد و همچنین امکان بارگذاری از طریق USB روی V5 Controller یا Brain را فراهم می‌کند.

    برای نصب این ابزار، دستور زیر را اجرا کنید:

    cargo install --locked cargo-v5

    فیلدهای زیر در Cargo.toml پروژهٔ شما توسط cargo-v5 خوانده می‌شوند تا رفتار بارگذاری را پیکربندی کنند:

    [package.metadata.v5]
# Slot number to upload the user program to. This should be from 1-8.
slot = 1
# Program icon/thumbnail that will be displayed on the dashboard.
icon = "cool-x"
# Use gzip compression when uploading binaries.
compress = true

    برای ساخت یک فایل BIN قابل بارگذاری با استفاده از پروفایل release، دستور زیر را اجرا کنید:

    cargo v5 build --release

    برنامه‌ها را می‌توان بلافاصله پس از ساخت، مستقیماً از طریق اتصال USB روی brain بارگذاری کرد:

    cargo v5 upload --release

    برنامهٔ Hello World

    use ::vex_sdk_jumptable as _; // Bring VEX SDK symbols into scope

fn main() {
    println!("Hello, world");
}

    محیط

    تابع main روی CPU1 تراشهٔ Zynq 7000 در حالت پردازندهٔ System و وضعیت Secure وارد می‌شود. برنامه‌ها یا runtimeها باید به‌طور دوره‌ای std::thread::yield_now را فراخوانی کنند تا بافرها را تخلیه کنند و آخرین وضعیت سخت‌افزارهای جانبی را دریافت کنند.

    توسعه‌دهندگانی که برای این هدف برنامه می‌نویسند باید از یک runtime سطح بالا مانند vexide یا یک crate دسترسی سیستمی سطح پایین‌تر مانند vex-sdk برای دسترسی به سخت‌افزارهای جانبی مانند موتورها و حسگرها استفاده کنند.

    هنگام کامپایل برای این هدف، قرارداد فراخوانی «C» به AAPCS با ثبات‌های VFP (ABI اعشاری سخت‌افزاری یا hard float) و قرارداد فراخوانی «system» به AAPCS بدون ثبات‌های VFP (ABI از نوع softfp) نگاشت می‌شود.

    این هدف فایل‌های دودویی با قالب ELF تولید می‌کند که می‌توان آن‌ها را با ابزارهای خارجی روی brain بارگذاری کرد.

    همچنین ببینید: VEX V5 Environment.

    SDKهای پلتفرم

    برای استفاده از بیشتر APIهای مخصوص پلتفرم، کاربران باید یک SDK زمان اجرای پشتیبان را پیکربندی کنند تا libstd با آن پیوند شود. SDKهای رسمی VEXcode از VEX را می‌توان دانلود کرد و از طریق crate با نام vex-sdk-vexcode پیوند داد، اما سیاست بازتوزیع محدودکننده‌ای دارند که ممکن است برای همهٔ پروژه‌ها مناسب نباشد. SDK پیشنهادی برای پروژه‌های متن‌باز، crate با نام vex-sdk-jumptable است که توسط جامعه پشتیبانی می‌شود. پیاده‌سازی‌های SDK عموماً لایه‌های نازکی روی فراخوانی‌های سیستمی هستند، بنابراین پروژه‌ها نباید انتظار تفاوت چشمگیری در رفتار، بسته به SDK مورد استفاده، داشته باشند.

    کتابخانه‌ها می‌توانند با استفاده از crate با نام vex-sdk و بدون وابستگی به یک پیاده‌سازی مشخص، به نمادهای (symbol) SDK فعال VEX دسترسی داشته باشند.

    پشتیبانی از کتابخانهٔ استاندارد

    std به‌دلیل محدودیت‌های پلتفرم فقط پشتیبانی جزئی دارد. به‌ویژه:

    • std::process و std::net پیاده‌سازی نشده‌اند. std::thread فقط از خوابیدن (sleep) و واگذاری اجرا (yield) پشتیبانی می‌کند، چون این محیط تک‌نخی است.
    • std::time پشتیبانی کامل از Instant دارد، اما از SystemTime پشتیبانی نمی‌کند.
    • std::io پشتیبانی کامل از stdin/stdout/stderr دارد. stdout و stderr هر دو روی این پلتفرم در کانال USB شمارهٔ 1 می‌نویسند و از هم متمایز نمی‌شوند.
    • std::fs برای خواندن یا نوشتن فایل‌ها پشتیبانی محدودی دارد. ویژگی‌های زیر پشتیبانی نمی‌شوند:
      • همهٔ عملیات مربوط به دایرکتوری (از جمله mkdir و readdir)، اگرچه خواندن دایرکتوری‌ها از طریق crateهای شخص ثالث ممکن است
      • حذف فایل‌ها و دایرکتوری‌ها
      • فراداده‌های فایل به‌جز اندازه و نوع فایل (یعنی فایل در برابر دایرکتوری)
      • باز کردن فایل‌ها با ترکیب‌های نامعمول گزینه‌های باز کردن، مانند خواندن + نوشتن هم‌زمان. حالت‌های پشتیبانی‌شده برای باز کردن فایل‌ها عبارت‌اند از حالت فقط‌خواندنی، حالت افزودن (append) یا حالت نوشتن (با یا بدون truncate کردن).
    • یک تخصیص‌دهندهٔ سراسری که بر پایهٔ dlmalloc پیاده‌سازی شده فراهم است.
    • ابتدایی‌های (primitive) همگام‌سازی در std::sync فرض می‌کنند اجرا تک‌نخی است.
    • ماژول‌هایی که فراتر از تخصیص حافظه نیازی به تعامل با سیستم‌عامل ندارند، مانند std::collections، std::hash، std::future و غیره، به‌طور کامل پشتیبانی می‌شوند.
    • این هدف باینری‌هایی با قالب ELF تولید می‌کند که می‌توان آن‌ها را با ابزارهای خارجی روی brain بارگذاری کرد.

    ایمنی نخ و همگام‌سازی

    این بخش فقط برای برنامه‌هایی است که از crate با نام std استفاده می‌کنند.

    هنگام اجرا روی این هدف، crate با نام std فقط از یک زمینهٔ اجرای Rust به‌علاوهٔ هر کنترل‌کنندهٔ استثنای Armv7-A نصب‌شده توسط کاربر (که با ثبات VBAR پیکربندی می‌شود) پشتیبانی می‌کند، به شرطی که دسترسی به منابع مشترک را به‌درستی همگام‌سازی کنند. std روی این هدف از هیچ اجرایی درون یک زمان‌بند وظایف (task scheduler) آگاه نیست، بنابراین globalهای thread_local همیشه هویت یکسانی خواهند داشت.

    SDKهای پلتفرم

    این هدف اجرا را بیرون از زمینهٔ زمان‌بند وظایف VEXos داخلی آغاز می‌کند. ایجاد VEXos Full Taskها از طریق API زمان‌بند مستندنشدهٔ VEX (برای مثال با تابع vexTaskAdd) یا استفاده از هر زمان‌بند دیگری که پشته را عوض می‌کند (از جمله FreeRTOS) در این هدف کاملاً ممنوع است و به رفتار تعریف‌نشده (undefined behavior) می‌انجامد. برنامه‌های Rust می‌توانند فرض کنند که vexTasksRun و std::thread::yield_now هرگز پشته را تعویض نمی‌کنند.

    کدی که درون زمینهٔ VEXos Simple Task اجرا می‌شود (برای مثال درون یک callback صفحهٔ لمسی کاربر) مجاز نیست زمان‌بند وظایف را به‌صورت بازگشتی (reentrant) تیک بزند. بنابراین برای کدِ وظیفه نامعتبر است که:

    • vexTasksRun، thread::yield_now، thread::sleep، thread::park یا مشتقات آن‌ها را فراخوانی کند،
    • یا از طریق std::io به جریان‌های ورودی/خروجی استاندارد دسترسی پیدا کند.

    ساخت برنامه‌های Rust

    وقتی کامپایلر یک باینری می‌سازد، یک آرتیفکت ساخت با قالب ELF تولید می‌شود. برای اینکه VEXos این آرتیفکت را به‌عنوان یک برنامهٔ کاربر بشناسد، ابزارهای اضافی لازم است.

    کنترل‌کننده‌های استثنا در برنامه‌هایی که از std استفاده می‌کنند نباید:

    • برای همگام‌سازی دسترسی به وضعیت مشترک از ساختارهای داده در std::sync استفاده کنند،
    • به هیچ وجه از مقادیر thread_local! استفاده کنند،
    • panic کنند، که به‌طور غیرمستقیم به thread localها دسترسی دارد،
    • از طریق std::io به جریان‌های ورودی/خروجی استاندارد دسترسی پیدا کنند،
    • برای نصب این ابزار، اجرا کنید:
    • با تخصیص‌دهندهٔ System تخصیص/آزادسازی حافظه انجام دهند،
    • یا std::thread::current را فراخوانی کنند که با تخصیص‌دهندهٔ System تخصیص حافظه انجام می‌دهد،

    آزمون

    باینری‌های ساخته‌شده برای این هدف را می‌توان در یک شبیه‌ساز (مانند vex-v5-qemu) اجرا کرد، یا از طریق اتصال سریال USB روی یک دستگاه فیزیکی بارگذاری کرد.

    اجراکنندهٔ آزمون پیش‌فرض Rust پشتیبانی نمی‌شود.

    مجموعه آزمون Rust برای library/std هنوز پشتیبانی نمی‌شود.

    زنجیرهٔ ابزار کامپایل متقابل و کد C

    این هدف را می‌توان از هر میزبانی کامپایل متقابل کرد.

    پیکربندی توصیه‌شده برای کامپایل کد C سازگار، استفاده از Arm Toolchain for Embedded با پرچم‌های کامپایل زیر است:

    clang --target=thumbv7a-none-eabihf -mcpu=cortex-a9 -mfpu=neon -fno-pic -fno-exceptions -fno-rtti -funwind-tables

    پیکربندی Cargo زیر را می‌توان برای پیوند با picolibc (کتابخانهٔ C که Arm Toolchain for Embedded از آن استفاده می‌کند) به کار برد:

    [target.thumbv7a-vex-v5]
# We use ARM Clang as a linker because ld.lld by itself doesn't include the
# multilib logic for resolving static libraries.
linker = "clang"

rustflags = [
    # These link flags resolve to this sysroot:
    # `…/arm-none-eabi/armv7a_hard_vfpv3_d16_unaligned`
    # (hard float / VFP version 3 with 16 regs / unaligned access)
    "-Clink-arg=--target=thumbv7a-none-eabihf",
    "-Clink-arg=-fno-rtti",
    "-Clink-arg=-fno-exceptions",

    # To disable crt0 and use Rust's _boot implementation
    # (or something custom):
    #"-Clink-arg=-nostartfiles",

    # Explicit `-lc` required because Rust calls the linker with
    # `-nodefaultlibs` which disables libc, libm, etc.
    "-Clink-arg=-lc",
]

    ممکن است بخواهید این متغیرهای محیطی را هم تنظیم کنید تا crateهای شخص ثالث از کامپایلر C درست استفاده کنند:

    PATH=/path/to/arm-toolchain/bin:$PATH
CC_armv7a_vex_v5=clang
AR_armv7a_vex_v5=clang
CFLAGS_armv7a_vex_v5=[See above]

    CMake

    اگر به crate با نام cmake وابسته هستید، ممکن است ساخت یک زنجیرهٔ ابزار CMake مانند زیر مفید باشد:

    # toolchain.cmake
set(CMAKE_SYSTEM_NAME Generic)
set(CMAKE_SYSTEM_PROCESSOR arm)

set(triple armv7a-none-eabihf)

set(CMAKE_C_COMPILER clang)
set(CMAKE_C_COMPILER_TARGET ${triple})
set(CMAKE_CXX_COMPILER clang++)
set(CMAKE_CXX_COMPILER_TARGET ${triple})
set(CMAKE_TRY_COMPILE_TARGET_TYPE "STATIC_LIBRARY")

    می‌توانید آن را با تنظیم متغیر محیطی زیر، در کنار متغیرهای محیطی ذکرشده پیشین، فعال کنید:

    CMAKE_TOOLCHAIN_FILE_armv7a_vex_v5=/path/to/toolchain.cmake
