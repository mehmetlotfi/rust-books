    {arm,thumb}*-none-eabi(hf)?

    جزئیات مشترک اهداف

    این مستندات جزئیاتی را شرح می‌دهد که برای طیفی از اهداف bare-metal مربوط به پردازنده‌های Arm ۳۲ بیتی صدق می‌کنند. زنجیرابزار arm-none-eabi از کامپایلر GNU اغلب برای کمک به کامپایل به این اهداف به کار می‌رود.

    جزئیاتی که فقط برای یک هدف مشخص در این گروه صادق است، در سند اختصاصی همان هدف آمده است.

    مجموعه دستورالعمل‌ها

    Arm دو معماری مجموعه دستورالعمل ۳۲ بیتی (ISA) تعریف کرده است:

    • A32 ISA با دستورالعمل‌های ۳۲ بیتیِ طول ثابت. این ISA که پیش‌تر با نام Arm ISA شناخته می‌شد، از ARM1 اصلی در سال ۱۹۸۵ آغاز شد و از آن زمان با بازنگری‌های گوناگون مشخصات معماری به‌روزرسانی شده است.
    • T32 ISA با ترکیبی از دستورالعمل‌های ۱۶ بیتی و ۳۲ بیتی. توجه کنید که این اصطلاح هم Thumb ISA اصلی ۱۶ بیتی را که همراه با معماری Armv4T در سال ۱۹۹۴ معرفی شد دربر می‌گیرد، و هم Thumb-2 ISA بعدی با اندازهٔ ۱۶/۳۲ بیتی را که همراه با معماری Armv6T2 در سال ۲۰۰۳ آمد. این ISA‌ها نیز در بازنگری‌های بعدیِ مشخصات معماری Arm بازنگری شده‌اند.

    یک ISA ۶۴ بیتی با دستورالعمل‌های ۳۲ بیتیِ طول ثابت نیز وجود دارد که A64 ISA نام دارد، اما اهدافی که این مجموعه دستورالعمل را پیاده‌سازی می‌کنند معمولاً با aarch64* شروع می‌شوند و در جای دیگری بحث شده‌اند.

    اهداف Rust که با arm* شروع می‌شوند به‌طور پیش‌فرض کد Arm (A32) تولید می‌کنند، در حالی که اهدافی که نامشان thumb* است به‌طور پیش‌فرض کد Thumb (T32) تولید می‌کنند. بیشتر تراشه‌های Arm هم از حالت Thumb و هم از حالت Arm پشتیبانی می‌کنند؛ استثنای مهم آن پردازنده‌های پروفایل M (اهداف thumbv*m*-none-eabi*) هستند که فقط از حالت Thumb پشتیبانی می‌کنند.

    اهداف Rust که به eabi ختم می‌شوند از چیزی به نام soft-float ABI استفاده می‌کنند: توابعی که f32 یا f64 را به‌عنوان آرگومان می‌گیرند، این مقادیر را در ثبات‌های صحیح (integer) بسته‌بندی می‌کنند. این یعنی از دید ABI نیازی به FPU نیست، اما اگر کد با گزینهٔ target-cpu یا target-feature که پشتیبانی از FPU را فعال می‌کند کامپایل شود، ممکن است درون یک تابع همچنان از دستورالعمل‌های ممیز شناور استفاده شود.

    اهداف Rust که به eabihf ختم می‌شوند از چیزی به نام hard-float ABI استفاده می‌کنند: توابعی که f32 یا f64 را به‌عنوان آرگومان می‌گیرند، آن‌ها را از طریق ثبات‌های FPU دریافت می‌کنند. بنابراین این اهداف به وجود یک FPU نیاز دارند و فرض می‌کنند سطح پایه‌ای از پشتیبانی ممیز شناور در دسترس است (که بسته به هدف می‌تواند متفاوت باشد). اگر کد با گزینهٔ target-cpu یا target-feature که چنین پشتیبانی تکمیلی FPU را فعال می‌کند کامپایل شود، ممکن است دستورالعمل‌های ممیز شناور پیشرفته‌تری تولید شود. برای مثال، اگر یک هدف hard-float مشخص در سخت‌افزار پشتیبانی پایهٔ دقت یگانه (f32) داشته باشد، ممکن است گزینه‌های target-cpu یا target-feature وجود داشته باشند که به LLVM بگویند فرض کند پردازندهٔ شما در واقع از دقت مضاعف (f64) هم پشتیبانی می‌کند.

    البته می‌توانید در کد خود از انواع f32 و f64 استفاده کنید، صرف‌نظر از ABI به‌کاررفته یا سطح پشتیبانی پردازندهٔ شما از انجام این عملیات در سخت‌افزار. هر عملیات ممیز شناوری که LLVM فرض کند پردازندهٔ شما نمی‌تواند پشتیبانی کند، به فراخوانی‌های کتابخانه‌ای (مانند __aeabi_dadd) تبدیل می‌شود که عملیات ممیز شناور را با استفاده از دستورالعمل‌های صحیح به‌صورت نرم‌افزاری انجام می‌دهند.

    گزینه‌های Target CPU و Target Feature

    می‌توانید با گزینهٔ -C target-cpu به Rust (یا LLVM) بگویید که مدل مشخصی از پردازندهٔ Arm دارید. همچنین می‌توانید با -C target-feature کنترل کنید که Rust (یا LLVM) دستورالعمل‌هایی را که ویژگی‌های سخت‌افزاری اختیاری را هدف می‌گیرند، مانند ممیز شناور سخت‌افزاری یا عملیات Advanced SIMD، شامل شود یا نه.

    مهم است بدانید که انتخاب یک target-cpu معمولاً همهٔ ویژگی‌های اختیاری را که Arm برای آن مدل CPU ارائه می‌دهد فعال می‌کند، و ممکن است پیاده‌سازی خاص شما از آن CPU این ویژگی‌ها را نداشته باشد. در آن صورت می‌توانید از -C target-feature=-option استفاده کنید تا ویژگی‌های CPU را که در دسترس ندارید خاموش کنید، و زمان‌بندی بهینهٔ دستورالعمل‌ها و پشتیبانی از ویژگی‌هایی که دارید برایتان باقی بماند. جزئیات بیشتر در مستندات تفصیلیِ مخصوص هر هدف آمده است.

    بسیاری از target-feature‌ها در حال حاضر ناپایدار هستند و ممکن است تغییر کنند؛ اگر از آن‌ها استفاده می‌کنید، باید خروجی کامپایلر را disassemble کنید و آن را دستی بررسی کنید تا مطمئن شوید فقط دستورالعمل‌های مناسب CPU شما تولید شده‌اند.

    اگر می‌خواهید از گزینه‌های target-cpu و target-feature استفاده کنید، می‌توانید آن‌ها را در کنار سایر پرچم‌هایی که پروژه‌تان به کار می‌برد (احتمالاً پرچم‌های مربوط به لینکر) به فایل .cargo/config.toml اضافه کنید:

    rustflags = [
  # Usual Arm bare-metal linker setup
  "-Clink-arg=-Tlink.x",
  "-Clink-arg=--nmagic",
  # tell Rust we have a Cortex-M55
  "-Ctarget-cpu=cortex-m55",
  # tell Rust our Cortex-M55 doesn't have Floating-Point M-Profile Vector
  # Extensions (but it does have everything else a Cortex-M55 could have).
  "-Ctarget-feature=-mve.fp"
]

[build]
target = "thumbv8m.main-none-eabihf"

    الزامات

    این اهداف cross-compile می‌شوند و از پیوند ایستا (static linking) استفاده می‌کنند.

    به‌طور پیش‌فرض از لینکر lld که همراه Rust ارائه می‌شود استفاده می‌شود؛ با این حال ممکن است بخواهید به‌جای آن از لینکر GNU استفاده کنید. این لینکر را می‌توان برای Windows/Mac/Linux از وب‌سایت توسعه‌دهندگان Arm یا احتمالاً از مدیر بستهٔ سیستم‌عامل خود به دست آورد. برای استفاده از آن، موارد زیر را به .cargo/config.toml خود اضافه کنید:

    [target.<your-target>]
linker = "arm-none-eabi-ld"

    لینکر GNU را می‌توان با مشخص کردن arm-none-eabi-gcc به‌عنوان لینکر نیز به کار برد. هنگام استفاده از بهینه‌سازی زمان پیوند (link time optimization) در GCC به این کار نیاز است.

    این اهداف اسکریپت لینکر ارائه نمی‌دهند، پس باید بسته به دستگاه مشخصی که استفاده می‌کنید اسکریپت خودتان را فراهم کنید. با ارسال -Clink-arg=-Tyour_script.ld به‌عنوان آرگومان rustc، لینکر را وادار کنید در هنگام پیوند از your_script.ld استفاده کند.

    برای اهداف arm*، تولید کد حالت Thumb را می‌توان با -C target-feature=+thumb-mode فعال کرد. با استفاده از #![feature(arm_target_feature)] ناپایدار، می‌توان attribute به شکل #[target_feature(enable = "thumb-mode")] را روی تابع‌های unsafe منفرد اعمال کرد تا آن توابع به کد حالت Thumb کامپایل شوند.

    ساخت برنامه‌های Rust

    برای اهداف Tier 3 در این خانواده، Rust مصنوعات (artifact) از پیش کامپایل‌شده ارائه نمی‌کند.

    فقط از قابلیت build-std در cargo نسخهٔ nightly برای ساخت کتابخانهٔ core استفاده کنید. می‌توانید آن را به‌صورت آرگومان خط فرمان به cargo بدهید، یا فایل .cargo/config.toml شما می‌تواند شامل خطوط زیر باشد:

    [unstable]
build-std = ["core"]

    بیشتر core باید طبق انتظار کار کند، با توجه به نکات زیر:

    • عملیات ممیز شناور به‌صورت نرم‌افزاری شبیه‌سازی می‌شود، مگر اینکه به LLVM گفته شود پشتیبانی از FPU را فعال کند (یا با استفاده از یک هدف eabihf، یا با مشخص کردن یک target-cpu دارای پشتیبانی FPU، یا با استفاده از یک target-feature برای پشتیبانی از نوع مشخصی از FPU)
    • تقسیم صحیح نیز در برخی اهداف، بسته به هدف، target-cpu و target-feature‌ها، به‌صورت نرم‌افزاری شبیه‌سازی می‌شود.
    • معماری‌های قدیمی‌تر Arm (مثلاً Armv4، Armv5TE و Armv6-M) به عملیات پایهٔ load و store محدود هستند و عملیات پیشرفته‌تری مانند fetch_add یا compare_exchange را ندارند.

    alloc نیز پشتیبانی می‌شود، به شرطی که تخصیص‌دهندهٔ سراسری (global allocator) خودتان را فراهم کنید.

    برنامه‌های Rust به‌صورت فایل ELF خروجی داده می‌شوند.

    زنجیرابزارهای cross-compilation و کد C

    این هدف از کد C کامپایل‌شده با سه‌تایی هدف arm-none-eabi و یک پرچم -march یا -mcpu مناسب پشتیبانی می‌کند.

    می‌توان از gcc یا clang استفاده کرد، اما توجه کنید که gcc برای اهداف arm-none* به‌طور پیش‌فرض از -fshort-enums استفاده می‌کند، در حالی که clang چنین نمی‌کند. rustc رفتار gcc را دنبال می‌کند؛ یعنی اندازهٔ یک #[repr(C)] enum در Rust می‌تواند تا ۱ بایت کوچک باشد، نه ۴ بایت مانند اهداف arm-linux.
