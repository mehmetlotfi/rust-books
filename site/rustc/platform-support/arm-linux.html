    پشتیبانی از Arm Linux در Rust

    معماری Arm از اواسط دههٔ ۱۹۸۰ وجود داشته است؛ نُه بازنگری عمده و بازنگری‌های جزئی بسیاری را پشت سر گذاشته و هم معماری‌های ۳۲ بیتی و هم ۶۴ بیتی را دربر می‌گیرد. این صفحه پلتفرم‌های Arm ۳۲ بیتی را پوشش می‌دهد که نوعی از Linux را اجرا می‌کنند (اما نه Android). این اهداف عبارت‌اند از:

    • arm-unknown-linux-gnueabi
    • arm-unknown-linux-gnueabihf
    • arm-unknown-linux-musleabi
    • arm-unknown-linux-musleabihf
    • armeb-unknown-linux-gnueabi
    • armv4t-unknown-linux-gnueabi
    • armv5te-unknown-linux-gnueabi
    • armv5te-unknown-linux-musleabi
    • armv5te-unknown-linux-uclibceabi
    • armv7-unknown-linux-gnueabi
    • armv7-unknown-linux-gnueabihf
    • armv7-unknown-linux-musleabi
    • armv7-unknown-linux-musleabihf
    • armv7-unknown-linux-ohos
    • armv7-unknown-linux-uclibceabi
    • armv7-unknown-linux-uclibceabihf
    • thumbv7neon-unknown-linux-gnueabihf
    • thumbv7neon-unknown-linux-musleabihf

    برخی از این اهداف صفحهٔ اختصاصی دارند و برخی ندارند. این امر بیشتر به اتفاقات تاریخی یا شور و شوق نگه‌دارندگان برمی‌گردد. این سند می‌کوشد همهٔ اهداف را پوشش دهد، اما فقط در خطوط کلی.

    برای درک این فهرست، مؤلفه‌های معماری و ABI در سه‌تایی <architecture>-unknown-linux-<abi> جداگانه بررسی می‌شوند.

    بخش دوم این سه‌تایی unknown است، چون این سیستم‌ها از هیچ فروشندهٔ مشخصی نمی‌آیند (مانند powerpc-ibm-aix یا aarch64-apple-darwin). بخش سوم linux است، چون این صفحه فقط اهداف Linux را بررسی می‌کند.

    مؤلفهٔ معماری

    • arm
    • armeb
    • armv4t
    • armv5te
    • armv7
    • thumbv7neon

    مؤلفهٔ معماری‌ای که صرفاً arm نامیده می‌شود با معماری Armv6 متناظر است؛ یعنی نسخهٔ ۶ معماری Arm همان‌طور که در نسخهٔ ۶ راهنمای مرجع معماری Arm (Arm ARM) تعریف شده است. این آخرین نسخهٔ «قدیمی» (legacy) معماری Arm بود، پیش از آنکه به پروفایل‌های Application، Real-Time و Microcontroller تقسیم شود (که به Armv7-A، Armv7-R و Armv7-M انجامید). پردازنده‌هایی که معماری Armv6 را پیاده‌سازی می‌کنند شامل ARM1176JZF-S هستند که در SoC مدل BCM2835 به کار رفته و Raspberry Pi Zero را قدرت می‌بخشد. پردازنده‌های Arm عموماً با نسخه‌های قبلی خود سازگار هستند، به‌ویژه برای کد حالت کاربر (user-mode)، بنابراین کدی که برای معماری arm کامپایل شده باشد باید روی سیستم‌های جدیدتر ARMv7-A و حتی سیستم‌های ۶۴/۳۲ بیتی Armv8-A نیز کار کند.

    مؤلفهٔ معماری armeb یک پردازندهٔ Armv6 را مشخص می‌کند که در حالت Big Endian اجرا می‌شود (eb مخفف big-endian است؛ حروف برعکس نوشته شده‌اند، چون مهندسانی که به سیستم‌های little-endian عادت دارند، اعداد big-endian را برعکس در حافظه نوشته‌شده می‌بینند و این را بامزه می‌دانستند). بیشتر پردازنده‌های Arm می‌توانند در هر یک از حالت‌های little-endian یا big-endian کار کنند و حالت little-endian با اختلاف رایج‌ترین است. با این حال، اگر به هر دلیلی بخواهید بایت‌های پرارزش‌تر (Most Significant Bytes) را اول ذخیره کنید، این اهداف در دسترس هستند. فقط خیلی خوب آزمایش نشده‌اند و با بیشتر کتابخانه‌های Arm از پیش کامپایل‌شدهٔ موجود هم سازگار نیستند.

    اهدافی که با armv4t شروع می‌شوند برای پردازنده‌هایی هستند که معماری Armv4T از سال ۱۹۹۴ را پیاده‌سازی می‌کنند. از جمله ARM7TDMI که در تلفن آجری Nokia 6110 و Game Boy Advance استفاده شده است. حرف «T» مخفف Thumb است و نشان می‌دهد که این پردازنده‌ها می‌توانند نسخه‌های کوچک‌تر ۱۶ بیتی برخی از دستورهای ۳۲ بیتی Arm را اجرا کنند. دلیلش این است که Thumb (انگشت شست) مانند نسخهٔ کوچکی از Arm (بازو) است.

    اهدافی که با armv5te شروع می‌شوند برای پردازنده‌هایی هستند که معماری Armv5TE را پیاده‌سازی می‌کنند. این‌ها بیشتر از خانوادهٔ ARM9 هستند، مانند ARM946E-S که در Nintendo DS به کار رفته است. اگر برای یک ماشین Arm مربوط به اوایل دههٔ ۲۰۰۰ برنامه می‌نویسید، شاید این همان چیزی باشد که نیاز دارید.

    نام armv7 را می‌توان نامی نادرست دانست و درست آن armv7a است. دلیلش این است که با پروفایل Application از Armv7 (یعنی Armv7-A) متناظر است، نه با پروفایل Real-Time یا Microcontroller. پردازنده‌هایی که این معماری را پیاده‌سازی می‌کنند شامل Cortex-A7 و Cortex-A8 هستند.

    مؤلفهٔ thumbv7neon پشتیبانی از پردازنده‌ای را نشان می‌دهد که ARMv7-A را پیاده‌سازی می‌کند (مانند armv7)، اما دستورهای Thumb (به‌طور دقیق Thumb-2 که با نام T32 ISA نیز شناخته می‌شود) تولید می‌کند، نه دستورهای Arm (که با نام A32 ISA نیز شناخته می‌شوند). این دستورها کوچک‌ترند و به ازای هر KB از RAM کد بیشتری جا می‌دهند، اما اگر انجام کاری که دستورهای Arm در یک دستور انجام می‌دهند به دو دستور نیاز داشته باشد، ممکن است افت کارایی داشته باشند. این یک موازنهٔ پیچیده است و اگر به اندازهٔ کد یا کارایی اهمیت زیادی می‌دهید، باید با اجرای بنچمارک‌ها تشخیص دهید کدام برای شما بهتر است. این مؤلفه همچنین پشتیبانی از افزونه‌های SIMD در Arm، یعنی Neon، را فعال می‌کند. این افزونه‌ها کارایی برخی انواع عملیات تکراری را بهبود می‌دهند.

    مؤلفهٔ ABI

    • gnueabi
    • gnueabihf
    • musleabi
    • musleabihf
    • ohos
    • uclibceabi
    • uclibceabihf

    باید ABI مناسبی را انتخاب کنید که با سیستمی که قرار است این کد را روی آن اجرا کنید مطابقت داشته باشد. برای مثال، اجرای کد eabihf روی یک سیستم eabi درست کار نخواهد کرد.

    مؤلفهٔ ABI با نام gnueabi پشتیبانی از استفادهٔ کتابخانهٔ C گنو (GNU C Library یا glibc) و ABI نهفتهٔ Arm (EABI) را نشان می‌دهد. EABI جایگزین ABI اصلی (که اکنون Old ABI یا OABI نامیده می‌شود) است و ABI استاندارد سیستم‌های Arm ۳۲ بیتی به شمار می‌رود. با این ABI، پارامترهای تابعی که از نوع f32 یا f64 هستند مانند عددهای صحیح ارسال می‌شوند، نه از طریق ثبات‌های FPU. معمولاً این اهداف استفاده از FPU را به‌کلی غیرفعال می‌کنند، هرچند این همیشه صادق نیست.

    مؤلفهٔ ABI با نام gnueabihf مانند gnueabi است، با این تفاوت که از «hard-float» در EABI پشتیبانی می‌کند. یعنی پارامترهای تابعی که از نوع f32 یا f64 هستند در ثبات‌های FPU ارسال می‌شوند. طبیعتاً این کار FPU را اجباری می‌کند.

    بیشتر توزیع‌های Linux «دسکتاپ» (Debian، Ubuntu، Fedora و غیره) از کتابخانهٔ C گنو استفاده می‌کنند و بنابراین احتمالاً باید gnueabi یا gnueabihf را انتخاب کنید، بسته به اینکه توزیع شما از «soft-float» (یعنی EABI) استفاده می‌کند یا «hard-float» (یعنی EABIHF). Debian هر دو نوع را ارائه می‌دهد.

    مؤلفه‌های ABI با نام‌های musleabi و musleabihf از کتابخانهٔ C با نام musl پشتیبانی می‌کنند. این کتابخانهٔ C را می‌توان برای ساخت «باینری‌های ایستا» به کار برد که هیچ نیازمندی کتابخانهٔ زمان اجرا ندارند (قابلیتی که glibc پشتیبانی نمی‌کند). مانند اهداف gnu* بالا، انواع soft-float (eabi) و hard-float (eabihf) وجود دارند.

    مؤلفه‌های ABI با نام‌های uclibceabi و uclibceabihf برای کتابخانهٔ C با نام uClibc-ng هستند. این کتابخانه گاهی در توزیع‌های Linux نهفتهٔ سبک‌وزن به کار می‌رود، مانند آن‌هایی که با buildroot ساخته می‌شوند.

    کامپایل متقابل

    متأسفانه ماشین‌های Arm ۳۲ بیتی عموماً سریع‌ترین ماشین‌ها نیستند و RAM زیادی هم ندارند. این یعنی احتمالاً باید کامپایل متقابل (cross-compile) انجام دهید.

    برای این کار باید یک لینکر مناسب به Rust بدهید؛ لینکری که معماری Arm را بشناسد و مهم‌تر از آن بداند کتابخانهٔ C مناسب را برای لینک کردن از کجا پیدا کند.

    برای این منظور می‌توانید ویژگی linker را به .cargo/config.toml خود اضافه کنید. معمولاً به نسخه‌ای مناسب از GCC اشاره می‌کنید که به‌عنوان کامپایلر متقابل ساخته شده است، در کنار یک کتابخانهٔ C.

    [target.arm-unknown-linux-gnueabi]
linker = "arm-linux-gnueabi-gcc"

    در Debian می‌توانید چنین زنجیرهٔ ابزار کامپایل متقابلی را با apt install gcc-arm-linux-gnueabi نصب کنید. برای ترکیب‌های غیرمعمول‌تر، شاید لازم باشد نسخه‌ای اختصاصی از GCC را با crosstool-ng بسازید.

    توجه کنید که برای GCC، همهٔ معماری‌های ۳۲ بیتی Arm در یک ساخت یکسان مدیریت می‌شوند

    • توجه کنید که برای GCC، همهٔ معماری‌های Arm ۳۲ بیتی در یک ساخت واحد مدیریت می‌شوند و ساخت‌های جداگانه‌ای از GCC برای Armv4T یا Armv6 وجود ندارد. معماری با پرچم‌هایی مانند -march=armv6 انتخاب می‌شود، اما این پرچم‌ها برای لینکر لازم نیستند.

    فرض کنیم روی یک ماشین Debian هستیم و می‌خواهیم یک باینری ساده برای Arm Linux بسازیم، برای توزیعی که از کتابخانهٔ C گنو استفاده می‌کند، با هدف Armv6 و ABI از نوع hard-float. چنین باینری‌ای مثلاً باید روی Raspberry Pi کار کند. دستورها این‌ها هستند:

    sudo apt install -y gcc-arm-linux-gnueabihf
rustup target add arm-unknown-linux-gnueabihf
cargo new --bin armdemo
cd armdemo
mkdir .cargo
cat > .cargo/config.toml << EOF
[target.arm-unknown-linux-gnueabihf]
linker = "arm-linux-gnueabihf-gcc"
EOF
cargo build --target=arm-unknown-linux-gnueabihf

    این کار باینری Arm Linux ما را برای کتابخانهٔ C گنو با ABI از نوع soft-float تولید می‌کند:

    $ file ./target/arm-unknown-linux-gnueabi/debug/armdemo
./target/arm-unknown-linux-gnueabi/debug/armdemo: ELF 32-bit LSB pie
  executable, ARM, EABI5 version 1 (SYSV), dynamically linked, interpreter
  /lib/ld-linux.so.3, BuildID[sha1]=dd0b9aa5ae876330fd4e2fcf393850f083ec7fcd,
  for GNU/Linux 3.2.0, with debug_info, not stripped

    اگر بخشی از پروژهٔ Rust شما کد C را می‌سازد، شاید بخواهید cc-rs را با متغیر محیطی CROSS_COMPILE به استفاده از یک کامپایلر متقابل مناسب هدایت کنید. همچنین ممکن است بخواهید متغیر محیطی CFLAGS را برای هدف تنظیم کنید. برای مثال:

    export CROSS_COMPILE=arm-linux-gnueabi
export CFLAGS_arm_unknown_linux_gnueabi="-march=armv6"

    (توجه کنید که خط تیره‌ها (-) برای تشکیل نام متغیر محیطی CFLAGS به زیرخط (_) تبدیل می‌شوند)

    اگر با استفاده از -Zbuild-std (در Rust نسخهٔ Nightly) برای یک هدف رده ۳ می‌سازید، باید این متغیرها را هم تنظیم کنید:

    export CXX_arm_unknown_linux_gnueabi=arm-linux-gnueabi-g++
export CC_arm_unknown_linux_gnueabi=arm-linux-gnueabi-gcc
cargo +nightly build -Zbuild-std --target=arm-unknown-linux-gnueabi
