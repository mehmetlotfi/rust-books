راهنمای خطاهای کامپایلرCompiler Error Index

    برای هر trait به نام Trait ممکن است یک نوع مرتبط وجود داشته باشد که نوع شیء trait نام دارد و معمولاً به شکل dyn Trait نوشته می‌شود. در ویرایش‌های قدیمی‌تر Rust، نوع شیء trait به‌صورت ساده Trait (فقط نام trait در جایگاه نوع) نوشته می‌شد، اما این کمی گیج‌کننده بود، بنابراین اکنون dyn Trait می‌نویسیم.

    برخی traitها اجازه ندارند به‌عنوان نوع شیء trait به کار روند. traitهایی که اجازه دارند به‌عنوان نوع شیء trait استفاده شوند، traitهای «dyn-compatible»1 نامیده می‌شوند. تلاش برای استفاده از نوع شیء trait برای traitی که dyn-compatible نیست، خطای E0038 را ایجاد می‌کند.

    دو جنبه کلی از انواع شیء trait منشأ این محدودیت‌ها هستند:

    1. انواع شیء trait، انواعی با اندازه پویا (DST) هستند و اشیای trait از این انواع فقط از طریق اشاره‌گر قابل دسترسی‌اند، مانند &dyn Trait یا Box<dyn Trait>. اندازه چنین اشاره‌گری مشخص است، اما اندازه شیء dyn Trait که اشاره‌گر به آن اشاره می‌کند برای کدی که با آن کار می‌کند مبهم (opaque) است، و اشیای trait متفاوت با نوع شیء trait یکسان ممکن است اندازه‌های متفاوتی داشته باشند.

    2. اشاره‌گری که برای دسترسی به یک شیء trait به کار می‌رود با یک اشاره‌گر اضافی جفت می‌شود که به «جدول متد مجازی» یا «vtable» اشاره می‌کند و برای پیاده‌سازی توزیع پویا (dynamic dispatch) به پیاده‌سازی‌های شیء از متدهای trait به کار می‌رود. برای هر پیاده‌سازی trait یک vtable منحصربه‌فرد وجود دارد، اما اشیای trait متفاوت با نوع شیء trait یکسان ممکن است به vtableهای پیاده‌سازی‌های مختلف اشاره کنند.

    شرایط خاصی که dyn-compatibility را نقض می‌کنند در ادامه آمده است؛ بیشتر آن‌ها به نبود اطلاعات اندازه و چندریختی vtable ناشی از این جنبه‌ها مربوط می‌شوند.

    trait شرط Self: Sized را لازم دارد

    traitهایی که به شکل Trait: Sized تعریف شده‌اند یا به‌گونه‌ای دیگر قید Self:Sized را به ارث برده‌اند، dyn-compatible نیستند.

    استدلال پشت این موضوع تا حدی ظریف است. این استدلال از این واقعیت ناشی می‌شود که Rust الزام می‌کند (و تعریف می‌کند) که هر نوع شیء trait به شکل dyn Trait به‌طور خودکار Trait را پیاده‌سازی کند. Rust این کار را برای ساده‌کردن گزارش خطا و تسهیل تعامل بین چندریختی ایستا و پویا انجام می‌دهد. برای مثال، این کد کار می‌کند:

    trait Trait {
}

fn static_foo<T:Trait + ?Sized>(b: &T) {
}

fn dynamic_bar(a: &dyn Trait) {
    static_foo(a)
}

    این کد کار می‌کند چون dyn Trait، در صورت وجود، همیشه Trait را پیاده‌سازی می‌کند.

    اما همان‌طور که می‌دانیم، هر dyn Trait بدون اندازه (unsized) نیز هست و بنابراین هرگز نمی‌تواند traitی با اندازه مشخص مانند Trait:Sized را پیاده‌سازی کند. پس به‌جای آنکه استثنایی برای این قاعده که dyn Trait همیشه Trait را پیاده‌سازی می‌کند در نظر بگیرد، Rust ترجیح می‌دهد وجود چنین dyn Traitای را به‌کلی ممنوع کند.

    فقط traitهای بدون اندازه (unsized) dyn-compatible محسوب می‌شوند.

    به‌طور کلی، Self: Sized برای نشان‌دادن این به کار می‌رود که trait نباید به‌عنوان شیء trait استفاده شود. اگر trait از crate خودتان است، حذف این محدودیت را در نظر بگیرید.

    متد در پارامترها یا نوع بازگشتی خود به نوع Self ارجاع می‌دهد

    این زمانی رخ می‌دهد که trait متدی مانند مثال زیر داشته باشد:

    trait Trait {
    fn foo(&self) -> Self;
}

impl Trait for String {
    fn foo(&self) -> Self {
        "hi".to_owned()
    }
}

impl Trait for u8 {
    fn foo(&self) -> Self {
        1
    }
}

    (توجه کنید که &self و &mut self مشکلی ندارند؛ آنچه این مشکل را ایجاد می‌کند، نوع‌های Self اضافی است.)

    در چنین حالتی، کامپایلر نمی‌تواند نوع بازگشتی foo() را در موقعیتی مانند زیر پیش‌بینی کند:

    trait Trait {
    fn foo(&self) -> Self;
}

fn call_foo(x: Box<dyn Trait>) {
    let y = x.foo(); // What type is y?
    // ...
}

    اگر فقط برخی متدها dyn-compatible نیستند، می‌توانید قید where Self: Sized را به آن‌ها اضافه کنید تا به‌صراحت برای اشیای trait غیرقابل‌دسترس علامت‌گذاری شوند. این قابلیت همچنان برای همه پیاده‌سازهای دیگر در دسترس خواهد بود، از جمله Box<dyn Trait> که خودش اندازه مشخص دارد (با فرض اینکه impl Trait for Box<dyn Trait> را بنویسید).

    trait Trait {
    fn foo(&self) -> Self where Self: Sized;
    // more functions
}

    اکنون دیگر نمی‌توان foo() را روی یک شیء trait فراخوانی کرد، اما اجازه خواهید داشت یک شیء trait بسازید و آن شیء می‌تواند هر متد dyn-compatible را فراخوانی کند. با چنین قیدی، همچنان می‌توان foo() را روی انواعی که آن trait را پیاده‌سازی می‌کنند و پشت شیء trait نیستند فراخوانی کرد.

    متد پارامترهای نوع جنریک دارد

    همان‌طور که پیش‌تر گفته شد، اشیای trait حاوی اشاره‌گر به جدول متدها هستند. بنابراین اگر داشته باشیم:

    trait Trait {
    fn foo(&self);
}

impl Trait for String {
    fn foo(&self) {
        // implementation 1
    }
}

impl Trait for u8 {
    fn foo(&self) {
        // implementation 2
    }
}
// ...

    در زمان کامپایل، هر پیاده‌سازی Trait جدولی شامل متدهای مختلف (و آیتم‌های دیگر) مربوط به آن پیاده‌سازی تولید می‌کند، که به‌عنوان جدول متد مجازی برای شیء dyn Trait حاصل از آن پیاده‌سازی به کار می‌رود.

    این به‌خوبی کار می‌کند، اما وقتی متد پارامترهای جنریک پیدا می‌کند، ممکن است مشکل پیش بیاید.

    معمولاً پارامترهای جنریک monomorphize می‌شوند. برای مثال، اگر داشته باشم

    fn foo<T>(x: T) {
    // ...
}

    کد ماشین foo::<u8>()، foo::<bool>()، foo::<String>() یا هر نمونه‌سازی دیگر متفاوت است. از این رو کامپایلر پیاده‌سازی را در صورت نیاز تولید می‌کند. اگر foo() را با پارامتری از نوع bool فراخوانی کنید، کامپایلر فقط برای foo::<bool>() کد تولید می‌کند. وقتی پارامترهای نوع بیشتری داریم، تعداد پیاده‌سازی‌های monomorphize‌شده‌ای که کامپایلر تولید می‌کند به‌شدت افزایش نمی‌یابد، زیرا کامپایلر فقط وقتی پیاده‌سازی تولید می‌کند که تابع با آرگومان‌های کاملاً مشخص (یعنی آرگومان‌هایی که شامل هیچ پارامتر جنریکی نیستند) فراخوانی شود.

    اما در مورد اشیای trait باید جدولی بسازیم که شامل همه اشیایی باشد که trait را پیاده‌سازی می‌کنند. حالا اگر پارامتر نوع وجود داشته باشد، باید برای هر نوعی که trait را پیاده‌سازی می‌کند پیاده‌سازی‌هایی اضافه کنیم، و از نظر تئوری می‌تواند تعداد بی‌نهایتی نوع وجود داشته باشد.

    برای مثال، با:

    trait Trait {
    fn foo<T>(&self, on: T);
    // more methods
}

impl Trait for String {
    fn foo<T>(&self, on: T) {
        // implementation 1
    }
}

impl Trait for u8 {
    fn foo<T>(&self, on: T) {
        // implementation 2
    }
}

// 8 more implementations

    حالا اگر کد زیر را داشته باشیم:

    # trait Trait { fn foo<T>(&self, on: T); }
# impl Trait for String { fn foo<T>(&self, on: T) {} }
# impl Trait for u8 { fn foo<T>(&self, on: T) {} }
# impl Trait for bool { fn foo<T>(&self, on: T) {} }
# // etc.
fn call_foo(thing: Box<dyn Trait>) {
    thing.foo(true); // this could be any one of the 8 types above
    thing.foo(1);
    thing.foo("hello");
}

    ما فقط نیاز نداریم جدولی از همه پیاده‌سازی‌های همه متدهای Trait بسازیم، بلکه باید چنین جدولی را برای هر نوع متفاوتی که به foo() داده می‌شود بسازیم. در این مورد، این برابر می‌شود با (۱۰ نوع پیاده‌سازکننده Trait)*(۳ نوعی که به foo() داده می‌شوند) = ۳۰ پیاده‌سازی!

    با traitهای دنیای واقعی، این اعداد می‌توانند به‌شدت رشد کنند.

    برای رفع این مشکل، اگر قصد ندارید متد را با پارامترهای نوع فراخوانی کنید، پیشنهاد می‌شود از قید where Self: Sized مشابه راه‌حل زیرخطای بالا استفاده کنید:

    trait Trait {
    fn foo<T>(&self, on: T) where Self: Sized;
    // more methods
}

    اگر این گزینه ممکن نیست، جایگزین‌کردن پارامتر نوع با شیء trait دیگری را در نظر بگیرید (مثلاً اگر T: OtherTrait، از on: Box<dyn OtherTrait> استفاده کنید). اگر تعداد انواعی که قصد دارید به این متد بدهید محدود است، می‌توانید متدهای انواع مختلف را به‌صورت دستی فهرست کنید.

    متد گیرنده (receiver) ندارد

    متدهایی که پارامتر self نمی‌گیرند قابل فراخوانی نیستند، زیرا راهی برای به‌دست‌آوردن اشاره‌گر به جدول متد آن‌ها وجود نخواهد داشت.

    trait Foo {
    fn foo() -> u8;
}

    این متد را می‌توان به شکل <Foo as Foo>::foo() فراخوانی کرد، که نمی‌تواند یک پیاده‌سازی را انتخاب کند.

    افزودن قید Self: Sized به این متدها معمولاً باعث می‌شود کد کامپایل شود.

    trait Foo {
    fn foo() -> u8 where Self: Sized;
}

    trait شامل ثابت‌های وابسته است

    درست مثل توابع ایستا، ثابت‌های وابسته (associated constants) در جدول متد ذخیره نمی‌شوند. اگر trait یا هر زیر‌trait آن شامل ثابت وابسته باشد، dyn-compatible نیست.

    trait Foo {
    const X: i32;
}

impl dyn Foo {}

    یک راه‌حل ساده استفاده از یک متد کمکی به‌جای آن است:

    trait Foo {
    fn x(&self) -> i32;
}

    trait در فهرست supertraitها از Self به‌عنوان پارامتر نوع استفاده می‌کند

    این مورد مشابه زیرخطای دوم است، اما ظریف‌تر. در موقعیت‌هایی مانند زیر رخ می‌دهد:

    trait Super<A: ?Sized> {}

trait Trait: Super<Self> {
}

struct Foo;

impl Super<Foo> for Foo{}

impl Trait for Foo {}

fn main() {
    let x: Box<dyn Trait>;
}

    در اینجا، supertrait ممکن است متدهایی به شکل زیر داشته باشد:

    trait Super<A: ?Sized> {
    fn get_a(&self) -> &A; // note that this is dyn-compatible!
}

    اگر trait به نام Trait از چیزی مانند Super<String> یا Super<T> ارث می‌برد (که در آن خود Foo به شکل Foo<T> است)، مشکلی نیست، زیرا با داشتن یک نوع، get_a() قطعاً شیئی از همان نوع را برمی‌گرداند.

    اما اگر از Super<Self> ارث ببرد، با اینکه Super dyn-compatible است، متد get_a() هنگام فراخوانی روی تابع، شیئی با نوع نامعلوم برمی‌گرداند. پارامترهای نوع Self می‌توانند traitهای dyn-compatible را غیرسازگار کنند، بنابراین هنگام تعیین supertraitها ممنوع هستند.

    راه‌حل آسانی برای این مشکل وجود ندارد. به‌طور کلی، کد باید بازآرایی شود تا دیگر نیازی به ارث‌بری از Super<Self> نداشته باشید.
