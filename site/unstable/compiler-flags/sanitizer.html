    sanitizer

    sanitizerها ابزارهایی هستند که به شناسایی و پیشگیری از انواع مختلف باگ‌ها و آسیب‌پذیری‌ها در نرم‌افزار کمک می‌کنند. آن‌ها در کامپایلرها در دسترس‌اند و با ابزارمند کردن (instrumenting) کد و افزودن بررسی‌های اضافی در زمان اجرا کار می‌کنند. اگرچه ابزارهای قدرتمندی برای شناسایی باگ‌ها یا مشکلات امنیتی‌اند، باید توجه داشت که استفاده از sanitizerها می‌تواند سربار زمان اجرا ایجاد کند و ممکن است همهٔ مشکلات ممکن را پیدا نکند. بنابراین معمولاً در کنار دیگر روش‌های برتر توسعهٔ نرم‌افزار، مانند آزمون و fuzzing، به کار می‌روند تا بالاترین کیفیت و امنیت نرم‌افزار تضمین شود.

    issueهای پیگیری این قابلیت:

    • #39699.
    • #89653.

    این قابلیت امکان استفاده از یکی از sanitizerهای زیر را فراهم می‌کند:

    • آن‌هایی که برای آزمون یا fuzzing در نظر گرفته شده‌اند (اما برای استفاده در محیط تولید نه):

      • AddressSanitizer یک تشخیص‌دهندهٔ سریع خطاهای حافظه.
      • HWAddressSanitizer یک تشخیص‌دهندهٔ خطاهای حافظه شبیه AddressSanitizer، اما مبتنی بر کمک سخت‌افزاری جزئی.
      • KernelHWAddressSanitizer گونه‌ای از HWAddressSanitizer که برای محیط‌های bare metal طراحی شده است.
      • LeakSanitizer یک تشخیص‌دهندهٔ نشت حافظه در زمان اجرا.
      • MemorySanitizer یک تشخیص‌دهندهٔ خواندن‌های مقداردهی‌نشده.
      • RealtimeSanitizer یک تشخیص‌دهندهٔ فراخوانی توابعی با زمان اجرای غیرقطعی در بسترهای بی‌درنگ (realtime).
      • ThreadSanitizer یک تشخیص‌دهندهٔ سریع data race.

    • آن‌هایی که جدا از آزمون، می‌توانند در محیط تولید نیز استفاده شوند:

      • ControlFlowIntegrity یکپارچگی جریان کنترل (CFI) در LLVM حفاظت جریان کنترل لبهٔ رو‌به‌جلو (forward-edge) را فراهم می‌کند.
      • DataFlowSanitizer یک چارچوب عمومی تحلیل پویای جریان داده.
      • KernelControlFlowIntegrity یکپارچگی جریان کنترل هستهٔ LLVM (KCFI) حفاظت جریان کنترل لبهٔ رو‌به‌جلو را برای هستهٔ سیستم‌عامل‌ها فراهم می‌کند.
      • MemTagSanitizer یک تشخیص‌دهندهٔ سریع خطاهای حافظه مبتنی بر افزونهٔ Memory Tagging در Armv8.5-A.
      • SafeStack با جدا کردن پشته به نواحی امن و ناامن، حفاظت جریان کنترل لبهٔ رو‌به‌عقب (backward-edge) را فراهم می‌کند.
      • ShadowCallStack حفاظت جریان کنترل لبهٔ رو‌به‌عقب را فراهم می‌کند (فقط aarch64).

    برای فعال کردن یک sanitizer با -Zsanitizer=address، -Zsanitizer=cfi، -Zsanitizer=dataflow،-Zsanitizer=hwaddress، -Zsanitizer=leak، -Zsanitizer=memory، -Zsanitizer=memtag، -Zsanitizer=realtime، -Zsanitizer=shadow-call-stack یا -Zsanitizer=thread کامپایل کنید. ممکن است به پرچم‌های --target و build-std نیز نیاز داشته باشید. اگر با زبان‌های دیگری کار می‌کنید که آن‌ها نیز با sanitizerها ابزارمند شده‌اند، ممکن است به پرچم external-clangrt نیاز داشته باشید. بخش کار با زبان‌های دیگر را ببینید.

    مثال:

    $ RUSTFLAGS=-Zsanitizer=address cargo build -Zbuild-std --target x86_64-unknown-linux-gnu

    گزینه‌های اضافی sanitizerها را می‌توان از طریق آرگومان‌های LLVM و با گزینهٔ codegen به نام llvm-args به پردازشگر آرگومان‌های خط فرمان LLVM ارسال کرد (برای مثال، -Cllvm-args=-dfsan-combine-pointer-labels-on-load=false). برای اطلاعات بیشتر دربارهٔ گزینه‌های اضافی، مستندات sanitizer را ببینید.

    AddressSanitizer

    AddressSanitizer یک تشخیص‌دهندهٔ خطاهای حافظه است. این ابزار می‌تواند انواع زیر از باگ‌ها را شناسایی کند:

    • دسترسی خارج از محدوده به heap، پشته و globalها
    • استفاده پس از آزادسازی (use after free)
    • استفاده پس از بازگشت (use after return) (پرچم زمان اجرا ASAN_OPTIONS=detect_stack_use_after_return=1)
    • استفاده پس از پایان scope
    • آزادسازی مضاعف (double-free) و آزادسازی نامعتبر
    • نشت حافظه

    تشخیص نشت حافظه در لینوکس به‌طور پیش‌فرض فعال است و در macOS می‌توان آن را با پرچم زمان اجرا ASAN_OPTIONS=detect_leaks=1 فعال کرد.

    AddressSanitizer روی هدف‌های زیر پشتیبانی می‌شود:

    • aarch64-apple-darwin
    • aarch64-unknown-fuchsia
    • aarch64-unknown-linux-gnu
    • x86_64-apple-darwin
    • x86_64-unknown-fuchsia
    • x86_64-unknown-freebsd
    • x86_64-unknown-linux-gnu

    AddressSanitizer با کد ابزارمندنشده نیز کار می‌کند، هرچند توانایی آن در شناسایی برخی باگ‌ها را کاهش می‌دهد. انتظار نمی‌رود گزارش‌های مثبت کاذب تولید کند.

    ControlFlowIntegrity

    پشتیبانی LLVM CFI در کامپایلر Rust حفاظت جریان کنترل لبهٔ رو‌به‌جلو را هم برای کدی که فقط با Rust کامپایل شده و هم برای باینری‌های چندزبانه‌ای که با C یا C++ و Rust کامپایل شده‌اند، که «باینری‌های مختلط» (mixed binaries) نیز نامیده می‌شوند (یعنی وقتی کد کامپایل‌شده با C یا C++ و Rust فضای آدرس مجازی یکسانی را به اشتراک می‌گذارند)، فراهم می‌کند؛ این کار با گروه‌بندی اشاره‌گرهای تابع بر اساس نوع بازگشتی و نوع پارامترهایشان انجام می‌شود.

    LLVM CFI را می‌توان با -Zsanitizer=cfi فعال کرد و به LTO نیاز دارد (یعنی -Clinker-plugin-lto یا -Clto). LLVM CFI میان‌زبانی را می‌توان با -Zsanitizer=cfi فعال کرد، و برای پشتیبانی از آن لازم است گزینهٔ -Zsanitizer-cfi-normalize-integers همراه با گزینهٔ -fsanitize-cfi-icall-experimental-normalize-integers در Clang استفاده شود، و LTO مناسب (یعنی غیر از rustc، با -Clinker-plugin-lto) به کار رود.

    هنگام فعال کردن CFI توصیه می‌شود کتابخانهٔ استاندارد با CFI فعال و با استفاده از قابلیت build-std در Cargo (یعنی -Zbuild-std) دوباره ساخته شود.

    برای جزئیات بیشتر مستندات Clang ControlFlowIntegrity را ببینید.

    انحراف از ABI زبان Rust

    به دلیل نحوهٔ پیاده‌سازی sanitizer مربوط به CFI، چند نکتهٔ مهم دربارهٔ قواعد سازگاری ABI برای فراخوانی‌های Rust به Rust وجود دارد. CFI ابزاری است که می‌توان از آن برای اعتبارسنجی اینکه فراخوانی‌های پویای تابع به ABI احترام می‌گذارند استفاده کرد، اما به دلیل خاستگاه C/C++ آن، در چند مورد با تضمین‌های مستندشدهٔ بالا مغایرت دارد که در ادامه آمده است. از آنجا که CFI ناپایدار است، جزئیات ممکن است در آینده تغییر کنند.

    هنگام اجرای sanitizer مربوط به CFI، نوع‌های اشاره‌گر فقط در صورتی از نظر ABI سازگارند که نوع هدف و تغییرپذیری یکسان باشد. یعنی *mut String و *mut i32 هنگام استفاده از CFI ناسازگارند. همچنین یعنی *mut i32 با *const i32 ناسازگار است. نوع‌های اشاره‌گر NonNull<_> و Box<_> در حال حاضر تحت CFI تغییرناپذیر در نظر گرفته می‌شوند. برای نوع‌های هدف غیر اولیه، CFI برای بررسی سازگاری از نام نوع استفاده می‌کند.

    وقتی پرچم -Zsanitizer-cfi-normalize-integers به کار نرود، sanitizer مربوط به CFI قواعد را بیشتر محدود می‌کند و usize/isize را با نوع صحیح uN/iN هم‌اندازه ناسازگار می‌داند.

    برخلاف سایر مواردی که ABI تابع نقض می‌شود، فراخوانی‌هایی که قواعد سازگاری ABI ویژهٔ CFI را نقض می‌کنند رفتار تعریف‌نشده (undefined behavior) نیستند. تضمین می‌شود که یا درست کار کنند یا برنامه را از کار بیندازند.

    این بخش فقط مواردی را پوشش می‌دهد که در آن‌ها CFI با قواعد سازگاری ABI برای فراخوانی‌های Rust به Rust مغایرت دارد. قرار نیست توضیح کاملی از نحوهٔ کار CFI باشد، و جزئیات مهم برای فراخوانی‌های C به Rust یا Rust به C حذف شده‌اند.

    مثال 1: تغییر مسیر جریان کنترل با استفاده از پرش/فراخوانی غیرمستقیم به مقصدی نامعتبر

    fn add_one(x: i32) -> i32 {
    x + 1
}

#[unsafe(naked)]
#[cfg(all(target_os = "linux", target_arch = "x86_64"))]
pub extern "sysv64" fn add_two(x: i32) {
    // x + 2 preceded by a landing pad/nop block
    std::arch::naked_asm!(
        "
         nop
         nop
         nop
         nop
         nop
         nop
         nop
         nop
         nop
         lea eax, [rdi+2]
         ret
        "
    );
}

fn do_twice(f: fn(i32) -> i32, arg: i32) -> i32 {
    f(arg) + f(arg)
}

fn main() {
    let answer = do_twice(add_one, 5);

    println!("The answer is: {}", answer);

  #[cfg(all(target_os = "linux", target_arch = "x86_64"))] {
        println!("With CFI enabled, you should not see the next answer");
        let f: fn(i32) -> i32 = unsafe {
            // Offset 0 is a valid branch/call destination (i.e., the function entry
            // point), but offsets 1-8 within the landing pad/nop block are invalid
            // branch/call destinations (i.e., within the body of the function).
            std::mem::transmute::<*const u8, fn(i32) -> i32>((add_two as *const u8).offset(5))
        };
        let next_answer = do_twice(f, 5);

        println!("The next answer is: {}", next_answer);
  }
}

    مثال 2: تغییر مسیر جریان کنترل با استفاده از پرش/فراخوانی غیرمستقیم به تابعی با تعداد پارامتر متفاوت

    use std::mem;

fn add_one(x: i32) -> i32 {
    x + 1
}

fn add_two(x: i32, _y: i32) -> i32 {
    x + 2
}

fn do_twice(f: fn(i32) -> i32, arg: i32) -> i32 {
    f(arg) + f(arg)
}

fn main() {
    let answer = do_twice(add_one, 5);

    println!("The answer is: {}", answer);

    println!("With CFI enabled, you should not see the next answer");
    let f: fn(i32) -> i32 =
        unsafe { mem::transmute::<*const u8, fn(i32) -> i32>(add_two as *const u8) };
    let next_answer = do_twice(f, 5);

    println!("The next answer is: {}", next_answer);
}

    KernelHWAddressSanitizer

    KernelHWAddressSanitizer نسخهٔ هسته (kernel) از HWAddressSanitizer است که همان هدف را دنبال می‌کند اما برای محیط‌های bare-metal طراحی شده است.

    HWAddressSanitizer روی هدف‌های aarch64*-unknown-none و aarch64*-unknown-none-softfloat پشتیبانی می‌شود.

    KernelControlFlowIntegrity

    پشتیبانی LLVM Kernel Control Flow Integrity (CFI) در کامپایلر Rust در ابتدا حفاظت جریان کنترل لبهٔ رو‌به‌جلو را برای هستهٔ سیستم‌عامل‌ها فقط برای کدی که با Rust کامپایل شده فراهم می‌کند، و این کار را با گروه‌بندی اشاره‌گرهای تابع بر اساس نوع بازگشتی و نوع پارامترهایشان انجام می‌دهد. (به کامیت LLVM با شناسهٔ cff5bef با عنوان «KCFI sanitizer» مراجعه کنید.)

    حفاظت جریان کنترل لبهٔ رو‌به‌جلو برای «باینری‌های مختلط» کامپایل‌شده با C یا C++ و Rust (یعنی وقتی کد کامپایل‌شده با C یا C++ و Rust فضای آدرس مجازی یکسانی را به اشتراک می‌گذارند) در کارهای بعدی و با تعریف و استفاده از شناسه‌های نوع سازگار فراهم خواهد شد (به Type metadata در سند طراحی در issue پیگیری #89653 مراجعه کنید).

    LLVM KCFI را می‌توان با -Zsanitizer=kcfi فعال کرد.

    LLVM KCFI روی هدف‌های زیر پشتیبانی می‌شود:

    • aarch64-linux-android
    • aarch64-unknown-linux-gnu
    • x86_64-linux-android
    • x86_64-unknown-linux-gnu

    برای جزئیات بیشتر مستندات Clang KernelControlFlowIntegrity را ببینید.

    DataFlowSanitizer

    DataFlowSanitizer یک تحلیل پویای عمومی جریان داده است.

    برخلاف سایر ابزارهای Sanitizer، این ابزار برای شناسایی یک دستهٔ مشخص از باگ‌ها به‌تنهایی طراحی نشده است. در عوض، یک چارچوب عمومی تحلیل پویای جریان داده فراهم می‌کند تا کلاینت‌ها از آن برای کمک به شناسایی مشکلات ویژهٔ برنامه در کد خودشان استفاده کنند.

    DataFlowSanitizer روی هدف‌های زیر پشتیبانی می‌شود:

    • x86_64-unknown-linux-gnu

    برای جزئیات بیشتر مستندات Clang DataFlowSanitizer را ببینید.

    KernelAddressSanitizer

KernelAddressSanitizer نیازمند پیاده‌سازی دستی توابع زیربنایی است که برای ردیابی وضعیت KernelAddressSanitizer به کار می‌روند.

    • aarch64-unknown-none
    • riscv64gc-unknown-none-elf
    • riscv64imac-unknown-none-elf
    • x86_64-unknown-none

    برای جزئیات بیشتر مستندات KernelAddressSanitizer در هستهٔ لینوکس را ببینید.

    برای جزئیات بیشتر مستندات Clang SafeStack را ببینید.

    ShadowCallStack

    ShadowCallStack حفاظت جریان کنترل لبهٔ رو‌به‌عقب را با ذخیرهٔ آدرس بازگشت تابع در یک «پشتهٔ فراخوانی سایه» (shadow call stack) که جداگانه تخصیص داده شده و بارگذاری آدرس بازگشت از آن فراهم می‌کند. هر دو معماری AArch64 و RISC-V در ABI خود یک رجیستر پلتفرم تعریف کرده‌اند، به‌ترتیب x18 و x3/gp، که می‌توان آن را به‌طور اختیاری برای این منظور رزرو کرد. بسته به پلتفرم هدف، ممکن است پشتیبانی نرم‌افزاری از سوی سیستم‌عامل و runtime لازم باشد که در بخش‌های باقی‌مانده شرح داده شده است. برای جزئیات بیشتر مستندات Clang ShadowCallStack را ببینید.

    ShadowCallStack را می‌توان با گزینهٔ -Zsanitizer=shadow-call-stack فعال کرد و روی هدف‌های زیر پشتیبانی می‌شود:

    خانوادهٔ AArch64

    ShadowCallStack نیازمند استفاده از رجیستر پلتفرم تعریف‌شده در ABI، یعنی x18، است که برای مقاصد تولید کد لازم است. وقتی x18 رزرو نشده باشد و در عوض بعداً به‌عنوان رجیستر موقت (scratch) استفاده شود، فعال کردن ShadowCallStack به رفتار تعریف‌نشده می‌انجامد، زیرا آدرس بازگشت خراب می‌شود یا هنگامی که ابزارمندی مقدار رجیستر بازگشت را از رجیستر x18 که قبلاً بازنویسی شده به رجیستر پیوند lr بازمی‌گرداند، دسترسی نامعتبر به حافظه رخ می‌دهد. به بیان دیگر، کدی که توابع ابزارمندشده با ShadowCallStack را فراخوانی می‌کند یا توسط آن‌ها فراخوانی می‌شود باید رجیستر x18 را رزرو کند یا مقدار آن را حفظ کند.

    aarch64-linux-android و aarch64-unknown-fuchsia/aarch64-fuchsia

    این هدف از قبل رجیستر x18 را رزرو می‌کند. یک runtime باید توسط برنامه یا سیستم‌عامل فراهم شود. اگر روی این هدف از bionic استفاده شود، پشتیبانی نرم‌افزاری فراهم است. در غیر این صورت، یک runtime باید ناحیه‌ای از حافظه را آماده کند و x18 را به آن ناحیه که به‌عنوان پشتهٔ فراخوانی سایه عمل می‌کند اشاره دهد.

    aarch64-unknown-none

    علاوه بر پشتیبانی runtime از سوی برنامه یا سیستم‌عامل، پرچم -Zfixed-x18 نیز اجباری است.

    خانوادهٔ RISC-V 64

    ShadowCallStack برای پشتهٔ سایهٔ نرم‌افزاری از رجیستر gp، که x3 نیز نامیده می‌شود، یا اگر افزونهٔ Zicfiss در دسترس باشد از رجیستر ssp استفاده می‌کند. gp/x3 در حال حاضر همیشه برای ابزارمندی ShadowCallStack رزرو و در دسترس است، و ssp در حالت Zicfiss فقط از طریق دستورهای اختصاصی پشتهٔ سایهٔ خود قابل دسترسی است.

    وقتی gp/x3 برای پشتهٔ سایهٔ نرم‌افزاری استفاده شود، پشتیبانی runtime و سیستم‌عامل لازم است. یک runtime باید پیش از اجرای کد ناحیه‌ای از حافظه را آماده کند و gp/x3 را به آن اشاره دهد.

    هدف‌های زیر از ShadowCallStack پشتیبانی می‌کنند.

    • riscv64imac-unknown-none-elf
    • riscv64gc-unknown-none-elf
    • riscv64gc-unknown-fuchsia

    ThreadSanitizer

    ThreadSanitizer ابزاری برای شناسایی data race است. روی هدف‌های زیر پشتیبانی می‌شود:

    • aarch64-apple-darwin
    • aarch64-unknown-linux-gnu
    • x86_64-apple-darwin
    • x86_64-unknown-freebsd
    • x86_64-unknown-linux-gnu

    برای کار درست، ThreadSanitizer باید از همهٔ عملیات همگام‌سازی در برنامه «آگاه» باشد. این ابزار معمولاً این کار را با ترکیبی از رهگیری کتابخانه (برای مثال همگام‌سازی انجام‌شده از طریق pthread_mutex_lock / pthread_mutex_unlock) و ابزارمندی در زمان کامپایل (مثلاً عملیات اتمی) انجام می‌دهد. استفاده از آن بدون ابزارمند کردن همهٔ کد برنامه می‌تواند به گزارش‌های مثبت کاذب بینجامد.

    ThreadSanitizer از fenceهای اتمی std::sync::atomic::fence و همچنین همگام‌سازی انجام‌شده با کد اسمبلی درون‌خطی پشتیبانی نمی‌کند.

    RealtimeSanitizer

    RealtimeSanitizer فراخوانی‌هایی با زمان اجرای غیرقطعی را در بسترهای بی‌درنگ (real-time) شناسایی می‌کند. توابعی که با attribute به نام #[sanitize(realtime = "nonblocking")] علامت‌گذاری شده‌اند، توابع بی‌درنگ محسوب می‌شوند. وقتی RTSan در حین اجرا در یک بستر بی‌درنگ فراخوانی تابعی با زمان اجرای غیرقطعی، مانند malloc یا free، را شناسایی کند، یک خطا گزارش می‌دهد.

    علاوه بر “nonblocking”، این attribute را می‌توان با “blocking” و “caller” نیز به کار برد.

    • “blocking” به برنامه‌نویس اجازه می‌دهد توابع خودش را به‌عنوان توابعی با زمان اجرای غیرقطعی علامت‌گذاری کند. هنگام رسیدن به چنین تابعی در حالی که در بستر بی‌درنگ هستیم، یک تخلف گزارش می‌شود. یک مورد استفادهٔ معمول spinlock در فضای کاربر است.
    • توابع علامت‌گذاری‌شده با “caller” در صورتی sanitize می‌شوند که از یک بستر بی‌درنگ فراخوانی شده باشند. اگر هیچ attribute ای تنظیم نشده باشد، این حالت پیش‌فرض است. از لحظهٔ ورود به یک تابع “nonblocking” تا لحظهٔ خروج دوبارهٔ از آن تابع، برنامه sanitize خواهد شد.

    بررسی‌های sanitizer را می‌توان با استفاده از توابع خارجی __rtsan_disable() و __rtsan_enable() غیرفعال کرد. هر فراخوانی __rtsan_disable() باید با یک فراخوانی بعدی __rtsan_enable() جفت شود، در غیر این صورت رفتار تعریف‌نشده است.

    unsafe extern "C" {
  fn __rtsan_disable();
  fn __rtsan_enable();
}
    // in a real-time context
#[cfg(debug_assertions)]
{
    unsafe { __rtsan_disable() };
    log!("logging xyz");
    unsafe { __rtsan_enable() };
}

    ابزارمند کردن وابستگی‌های خارجی و std

    sanitizerها تا درجات مختلف با کد ابزارمندشدهٔ جزئی به‌درستی کار می‌کنند. در یک سو LeakSanitizer قرار دارد که از هیچ ابزارمندی در زمان کامپایل استفاده نمی‌کند، و در سوی دیگر MemorySanitizer است که نیاز دارد همهٔ کد برنامه ابزارمند شود (در غیر این صورت ناگزیر مثبت‌های کاذب پدید می‌آیند).

    به‌شدت توصیه می‌شود sanitizerها با کتابخانهٔ استاندارد دوباره‌کامپایل‌شده و ابزارمندشده ترکیب شوند، برای مثال با استفاده از قابلیت -Zbuild-std در cargo.

    کار با زبان‌های دیگر

    sanitizerها برای عملکرد صحیح به کتابخانه‌های runtime کامپایلر متکی هستند. Rust runtime کامپایلر خودش را پیوند می‌دهد که ممکن است با runtimeهای مورد نیاز زبان‌هایی مانند C++ تداخل داشته باشد. از آنجا که runtime مربوط به Rust همیشه نمادهای مورد نیاز کد ابزارمندشدهٔ C++ را ندارد، ممکن است لازم باشد پیوند دادن آن را نادیده بگیرید تا runtime دیگری به جای آن پیوند شود.

    از گزینهٔ ناپایدار جداگانهٔ -Zexternal-clangrt می‌توان استفاده کرد تا rustc پیوند دادن runtime کامپایلر برای sanitizer را رد کند. این کار شما را ملزم می‌کند یک runtime خارجی، مثلاً از clang، را به جای آن پیوند دهید.

    اسکریپت‌های ساخت و ماکروهای رویه‌ای

    استفاده از sanitizerها همراه با اسکریپت‌های ساخت (build script) و ماکروهای رویه‌ای (procedural macro) از نظر فنی ممکن است، اما در تقریباً همهٔ موارد بهتر است از آن اجتناب شود. این موضوع به‌ویژه دربارهٔ ماکروهای رویه‌ای صادق است که نیاز به نسخهٔ ابزارمندشده‌ای از rustc دارند.

    در عمل، هنگام استفاده از cargo همیشه به یاد داشته باشید که پرچم --target را ارسال کنید تا rustflags روی اسکریپت‌های ساخت و ماکروهای رویه‌ای اعمال نشود.

    نمادگذاری گزارش‌ها (Symbolizing)

    sanitizerها وقتی فایل اجرایی llvm-symbolizer در PATH باشد، stack traceهای نمادگذاری‌شده تولید می‌کنند.
