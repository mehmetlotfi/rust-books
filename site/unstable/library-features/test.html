    test

    مسئلهٔ پیگیری (tracking issue) این ویژگی: ندارد.

    بخش‌های داخلی crate با نام test ناپایدارند و پشت feature با نام test قرار دارند. پرکاربردترین بخش crate با نام test، آزمون‌های بنچمارک (benchmark) است که می‌توانند کارایی کد شما را بسنجند. بیایید src/lib.rs خود را این‌گونه بنویسیم (کامنت‌ها حذف شده‌اند):

    #![feature(test)]

extern crate test;

pub fn add_two(a: i32) -> i32 {
    a + 2
}

#[cfg(test)]
mod tests {
    use super::*;
    use test::Bencher;

    #[test]
    fn it_works() {
        assert_eq!(4, add_two(2));
    }

    #[bench]
    fn bench_add_two(b: &mut Bencher) {
        b.iter(|| add_two(2));
    }
}

    به feature gate با نام test توجه کنید که این ویژگی ناپایدار را فعال می‌کند.

    ما crate با نام test را که پشتیبانی از بنچمارک در آن است، import کرده‌ایم. همچنین تابع جدیدی داریم که attribute با نام bench دارد. برخلاف آزمون‌های معمولی که آرگومانی نمی‌گیرند، آزمون‌های بنچمارک یک &mut Bencher می‌گیرند. این Bencher متدی به نام iter فراهم می‌کند که یک closure می‌گیرد. این closure شامل کدی است که می‌خواهیم بنچمارک کنیم.

    می‌توانیم آزمون‌های بنچمارک را با cargo bench اجرا کنیم:

    $ cargo bench
   Compiling adder v0.0.1 (file:///home/steve/tmp/adder)
     Running target/release/adder-91b3e234d4ed382a

running 2 tests
test tests::it_works ... ignored
test tests::bench_add_two ... bench:         1 ns/iter (+/- 0)

test result: ok. 0 passed; 0 failed; 1 ignored; 1 measured

    آزمون غیربنچمارک ما نادیده گرفته شد. ممکن است متوجه شده باشید که cargo bench کمی بیشتر از cargo test طول می‌کشد. دلیلش این است که Rust بنچمارک ما را چندین بار اجرا می‌کند و سپس میانگین می‌گیرد. چون در این مثال کار بسیار کمی انجام می‌دهیم، نتیجه 1 ns/iter (+/- 0) است، اما اگر واریانسی وجود داشت، همین‌جا نشان داده می‌شد.

    توصیه‌هایی برای نوشتن بنچمارک:

    • کد آماده‌سازی را بیرون از حلقهٔ iter ببرید؛ فقط بخشی را که می‌خواهید اندازه بگیرید داخل آن بگذارید
    • کاری کنید که کد در هر تکرار «همان کار» را انجام دهد؛ حالت را انباشته یا تغییر ندهید
    • تابع بیرونی را هم idempotent کنید؛ احتمالاً اجراکنندهٔ بنچمارک آن را بارها اجرا می‌کند
    • حلقهٔ iter درونی را کوتاه و سریع نگه دارید تا اجرای بنچمارک‌ها سریع باشد و کالیبره‌کننده بتواند طول اجرا را با دقت ریز تنظیم کند
    • کدی که در حلقهٔ iter است باید کار ساده‌ای انجام دهد تا یافتن بهبودهای کارایی (یا پسرفت‌ها) آسان‌تر شود

    نکتهٔ مهم: بهینه‌سازی‌ها

    نوشتن بنچمارک یک بخش پیچیدهٔ دیگر هم دارد: بنچمارک‌هایی که با بهینه‌سازی فعال کامپایل می‌شوند، ممکن است توسط بهینه‌ساز چنان تغییر کنند که دیگر آنچه انتظار دارید را اندازه نگیرند. برای مثال، کامپایلر ممکن است تشخیص دهد که یک محاسبه هیچ اثر خارجی ندارد و آن را به‌کلی حذف کند.

    #![feature(test)]

extern crate test;
use test::Bencher;

#[bench]
fn bench_xor_1000_ints(b: &mut Bencher) {
    b.iter(|| {
        (0..1000).fold(0, |old, new| old ^ new);
    });
}

    نتایج زیر را می‌دهد

    running 1 test
test bench_xor_1000_ints ... bench:         0 ns/iter (+/- 0)

test result: ok. 0 passed; 0 failed; 0 ignored; 1 measured

    اجراکنندهٔ بنچمارک دو راه برای جلوگیری از این مشکل ارائه می‌دهد. راه اول این است که closure‌ای که iter دریافت می‌کند می‌تواند مقداری دلخواه برگرداند؛ این کار بهینه‌ساز را مجبور می‌کند نتیجه را «استفاده‌شده» بداند و تضمین می‌کند که نمی‌تواند محاسبه را به‌کلی حذف کند. در مثال بالا می‌توان این کار را با تغییر فراخوانی b.iter انجام داد:

    struct X;
impl X { fn iter<T, F>(&self, _: F) where F: FnMut() -> T {} } let b = X;
b.iter(|| {
    // Note lack of `;` (could also use an explicit `return`).
    (0..1000).fold(0, |old, new| old ^ new)
});

    راه دوم فراخوانی تابع جنریک test::black_box است که برای بهینه‌ساز یک «جعبهٔ سیاه» مبهم است و بنابراین آن را مجبور می‌کند هر آرگومانی را استفاده‌شده بداند.

    #![feature(test)]

extern crate test;

fn main() {
struct X;
impl X { fn iter<T, F>(&self, _: F) where F: FnMut() -> T {} } let b = X;
b.iter(|| {
    let n = test::black_box(1000);

    (0..n).fold(0, |a, b| a ^ b)
})
}

    هیچ‌کدام از این دو، مقدار را نمی‌خوانند یا تغییر نمی‌دهند و برای مقادیر کوچک بسیار ارزان‌اند. مقادیر بزرگ‌تر را می‌توان به‌صورت غیرمستقیم پاس داد تا سربار کاهش یابد (مثلاً black_box(&huge_struct)).

    با اعمال هر یک از تغییرهای بالا، نتایج بنچمارک به این صورت می‌شود

    running 1 test
test bench_xor_1000_ints ... bench:       131 ns/iter (+/- 3)

test result: ok. 0 passed; 0 failed; 0 ignored; 1 measured

    با این حال، حتی با استفاده از هر یک از روش‌های بالا، بهینه‌ساز همچنان می‌تواند یک testcase را به شکلی نامطلوب تغییر دهد.
