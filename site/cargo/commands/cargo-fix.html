کتاب CargoThe Cargo Book

    cargo-fix(1)

    نام

    cargo-fix — رفع خودکار هشدارهای lint گزارش‌شده توسط rustc

    خلاصه

    cargo fix [options]

    توضیحات

    این زیرفرمان Cargo به‌طور خودکار پیشنهادهای rustc را از تشخیص‌هایی مانند هشدارها برمی‌دارد و آن‌ها را روی کد منبع شما اعمال می‌کند. هدف این است که کمک کند کارهایی که خود rustc از قبل می‌داند چگونه به شما بگوید رفعشان کنید، خودکار شوند!

    اجرای cargo fix در پشت صحنه cargo-check(1) را اجرا می‌کند. هر هشداری که به crate شما مربوط باشد (در صورت امکان) خودکار رفع می‌شود و همهٔ هشدارهای باقی‌مانده پس از پایان فرایند بررسی نمایش داده می‌شوند. برای مثال، اگر بخواهید همهٔ رفع‌ها را روی بستهٔ فعلی اعمال کنید، می‌توانید این را اجرا کنید:

    cargo fix

    که رفتارش با cargo check --all-targets یکسان است.

    cargo fix فقط می‌تواند کدی را رفع کند که به‌طور معمول با cargo check کامپایل می‌شود. اگر کدی به‌صورت مشروط با featureهای اختیاری فعال می‌شود، باید آن featureها را فعال کنید تا آن کد تحلیل شود:

    cargo fix --features foo

    به‌طور مشابه، سایر عبارت‌های cfg مانند کد مختص یک پلتفرم باید --target را بگیرند تا کد برای هدف داده‌شده رفع شود.

    cargo fix --target x86_64-pc-windows-gnu

    اگر با cargo fix به مشکلی برخوردید یا پرسش یا درخواست قابلیتی دارید، لطفاً بی‌درنگ در https://github.com/rust-lang/cargo یک issue ثبت کنید.

    مهاجرت edition

    زیرفرمان cargo fix را می‌توان برای مهاجرت یک بسته از یک edition به edition بعدی هم به کار برد. روند کلی به این صورت است:

    1. cargo fix --edition را اجرا کنید. اگر پروژهٔ شما چند feature دارد، استفاده از پرچم --all-features را هم در نظر بگیرید. اگر پروژهٔ شما کد مختص پلتفرم دارد که با attributeهای cfg محدود شده است، شاید بخواهید cargo fix --edition را چندین بار با پرچم‌های --target متفاوت اجرا کنید.
    2. فایل Cargo.toml را تغییر دهید تا فیلد edition روی edition جدید تنظیم شود.
    3. آزمون‌های پروژهٔ خود را اجرا کنید تا مطمئن شوید همه‌چیز هنوز کار می‌کند. اگر هشدارهای جدیدی صادر شد، شاید بخواهید دوباره cargo fix را (بدون پرچم --edition) اجرا کنید تا پیشنهادهای کامپایلر اعمال شوند.

    و امیدواریم کار همین باشد! فقط محدودیت‌هایی را که در بالا گفته شد به خاطر داشته باشید: cargo fix نمی‌تواند کد مربوط به featureهای غیرفعال یا عبارت‌های cfg را به‌روزرسانی کند. همچنین در برخی موارد نادر کامپایلر نمی‌تواند همهٔ کد را به‌طور خودکار به edition جدید مهاجرت دهد و ممکن است پس از ساخت با edition جدید به تغییرات دستی نیاز باشد.

    گزینه‌ها

    گزینه‌های رفع

    --broken-code

    کد را حتی اگر از قبل خطای کامپایلر داشته باشد رفع می‌کند. این گزینه زمانی مفید است که cargo fix نتواند تغییرات را اعمال کند. تغییرات را اعمال می‌کند و کد خراب را در دایرکتوری کاری باقی می‌گذارد تا شما آن را بررسی کنید و دستی رفع کنید.

    --edition

    تغییراتی را اعمال می‌کند که کد را به edition بعدی به‌روزرسانی می‌کنند. این گزینه edition را در manifest فایل Cargo.toml به‌روزرسانی نمی‌کند؛ آن را باید پس از پایان cargo fix --edition به‌صورت دستی به‌روزرسانی کرد.

    --edition-idioms

    پیشنهادهایی را اعمال می‌کند که کد را به سبک ترجیحی edition فعلی به‌روزرسانی می‌کنند.

    --allow-no-vcs

    کد را حتی اگر VCS تشخیص داده نشد رفع می‌کند.

    --allow-dirty

    کد را حتی اگر دایرکتوری کاری تغییراتی داشته باشد (از جمله تغییرات staged) رفع می‌کند.

    --allow-staged

    کد را حتی اگر دایرکتوری کاری تغییرات staged داشته باشد رفع می‌کند.

    انتخاب بسته

    به‌طور پیش‌فرض، وقتی هیچ گزینهٔ انتخاب بسته‌ای داده نشده باشد، بسته‌های انتخاب‌شده به فایل manifest انتخاب‌شده بستگی دارند (اگر --manifest-path داده نشده باشد، بر اساس دایرکتوری کاری فعلی). اگر manifest ریشهٔ یک workspace باشد، اعضای پیش‌فرض workspace انتخاب می‌شوند؛ در غیر این صورت فقط بسته‌ای که manifest تعریف می‌کند انتخاب خواهد شد.

    اعضای پیش‌فرض یک workspace را می‌توان با کلید workspace.default-members در manifest ریشه به‌صراحت تعیین کرد. اگر این کلید تنظیم نشده باشد، یک workspace مجازی همهٔ اعضای workspace را شامل می‌شود (معادل دادن --workspace) و یک workspace غیرمجازی فقط خود crate ریشه را شامل می‌شود.

    -p spec…
    --package spec…

    فقط بسته‌های مشخص‌شده را رفع می‌کند. برای قالب SPEC به cargo-pkgid(1) مراجعه کنید. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    --workspace

    همهٔ اعضای workspace را رفع می‌کند.

    --all

    نام مستعار منسوخ‌شدهٔ --workspace.

    --exclude SPEC…

    بسته‌های مشخص‌شده را کنار می‌گذارد. باید همراه با گزینهٔ --workspace استفاده شود. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    انتخاب هدف

    وقتی هیچ گزینهٔ انتخاب هدفی داده نشده باشد، cargo fix همهٔ هدف‌ها را رفع می‌کند (--all-targets مفروض است). اگر باینری‌ها required-features داشته باشند که فعال نشده‌اند، از آن‌ها صرف‌نظر می‌شود.

    با دادن گزینه‌های انتخاب هدف، فقط هدف‌های مشخص‌شده رفع می‌شوند.

    توجه کنید که گزینه‌های --bin، --example، --test و --bench نیز از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کنند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگوی glob از نقل‌قول تکی یا دوتایی استفاده کنید.

    --lib

    کتابخانهٔ بسته را رفع می‌کند.

    --bin name…

    باینری مشخص‌شده را رفع می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --bins

    همهٔ هدف‌های باینری را رفع می‌کند.

    --example name…

    نمونهٔ (example) مشخص‌شده را رفع می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --examples

    همهٔ هدف‌های نمونه (example) را رفع می‌کند.

    --test name…

    آزمون یکپارچگی مشخص‌شده را رفع می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --tests

    همهٔ هدف‌هایی را رفع می‌کند که پرچم manifest به نام test = true برایشان تنظیم شده است. به‌طور پیش‌فرض این شامل کتابخانه و باینری‌هایی است که به‌عنوان آزمون واحد ساخته می‌شوند، و نیز آزمون‌های یکپارچگی. توجه داشته باشید که این کار هر وابستگی موردنیاز را هم می‌سازد، بنابراین ممکن است هدف lib دو بار ساخته شود (یک بار به‌عنوان آزمون واحد و یک بار به‌عنوان وابستگی برای باینری‌ها، آزمون‌های یکپارچگی و غیره). هدف‌ها را می‌توان با تنظیم پرچم test در تنظیمات manifest همان هدف فعال یا غیرفعال کرد.

    --bench name…

    benchmark مشخص‌شده را رفع می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --benches

    همهٔ هدف‌هایی را رفع می‌کند که پرچم manifest به نام bench = true برایشان تنظیم شده است. به‌طور پیش‌فرض این شامل کتابخانه و باینری‌هایی است که به‌عنوان benchmark ساخته می‌شوند، و نیز هدف‌های bench. توجه داشته باشید که این کار هر وابستگی موردنیاز را هم می‌سازد، بنابراین ممکن است هدف lib دو بار ساخته شود (یک بار به‌عنوان benchmark و یک بار به‌عنوان وابستگی برای باینری‌ها، benchmarkها و غیره). هدف‌ها را می‌توان با تنظیم پرچم bench در تنظیمات manifest همان هدف فعال یا غیرفعال کرد.

    --all-targets

    همهٔ هدف‌ها را رفع می‌کند. این معادل مشخص کردن --lib --bins --tests --benches --examples است.

    انتخاب feature

    پرچم‌های feature به شما امکان می‌دهند کنترل کنید کدام featureها فعال باشند. وقتی هیچ گزینهٔ featureای داده نشده باشد، feature به نام default برای هر بستهٔ انتخاب‌شده فعال می‌شود.

    برای جزئیات بیشتر، مستندات featureها را ببینید.

    -F features
    --features features

    فهرستی از featureهای قابل فعال‌سازی که با فاصله یا کاما جدا شده است. featureهای اعضای workspace را می‌توان با نحو package-name/feature-name فعال کرد. این گزینه را می‌توان چندین بار مشخص کرد که همهٔ featureهای مشخص‌شده را فعال می‌کند.

    --all-features

    همهٔ featureهای موجود همهٔ بسته‌های انتخاب‌شده را فعال می‌کند.

    --no-default-features

    feature به نام default بسته‌های انتخاب‌شده را فعال نمی‌کند.

    گزینه‌های کامپایل

    --target tuple

    برای معماری هدف مشخص‌شده رفع می‌کند. این گزینه را می‌توان چندین بار مشخص کرد. پیش‌فرض معماری میزبان (host) است. قالب کلی tuple به این صورت است: <arch><sub>-<vendor>-<sys>-<abi>.

    مقادیر ممکن:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple" که به‌طور داخلی با هدف میزبان جایگزین می‌شود. این مورد به‌ویژه وقتی مفید است که برخی crateها را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان خود را به‌عنوان هدف مشخص کنید (برای مثال، یک xtask در پروژه‌ای مشترک که ممکن است میزبان‌های بسیاری روی آن کار کنند).
    • مسیر یک مشخصهٔ هدف سفارشی. برای اطلاعات بیشتر مسیر جست‌وجوی هدف سفارشی را ببینید.

    این گزینه را می‌توان با مقدار پیکربندی build.target نیز مشخص کرد.

    توجه کنید که مشخص کردن این پرچم باعث می‌شود Cargo در حالتی متفاوت اجرا شود که در آن artifactهای هدف در یک دایرکتوری جداگانه قرار می‌گیرند. برای جزئیات بیشتر، مستندات حافظهٔ نهان ساخت را ببینید.

    -r
    --release

    artifactهای بهینه‌شده را با profile به نام release رفع می‌کند. برای انتخاب یک profile مشخص بر اساس نام، گزینهٔ --profile را هم ببینید.

    --profile name

    با profile داده‌شده رفع می‌کند.

    به‌عنوان یک حالت خاص، مشخص کردن profile به نام test بررسی در حالت آزمون را هم فعال می‌کند که بررسی آزمون‌ها و گزینهٔ cfg به نام test را فعال می‌کند. برای جزئیات بیشتر آزمون‌های rustc را ببینید.

    برای جزئیات بیشتر دربارهٔ profileها مرجع را ببینید.

    --timings

    اطلاعاتی دربارهٔ مدت زمان هر کامپایل خروجی می‌دهد و اطلاعات هم‌زمانی را در طول زمان ردیابی می‌کند.

    در پایان ساخت، فایلی به نام cargo-timing.html در دایرکتوری target/cargo-timings نوشته می‌شود. اگر بخواهید اجرای قبلی را ببینید، یک گزارش اضافی هم با مهر زمانی در نام فایلش نوشته می‌شود. این گزارش‌ها فقط برای مصرف انسانی مناسب‌اند و داده‌های زمان‌بندی قابل‌خواندن برای ماشین ارائه نمی‌دهند.

    گزینه‌های خروجی

    --target-dir directory

    دایرکتوری همهٔ artifactهای تولیدشده و فایل‌های میانی. همچنین می‌توان آن را با متغیر محیطی CARGO_TARGET_DIR یا با مقدار پیکربندی build.target-dir مشخص کرد. پیش‌فرض آن target در ریشهٔ workspace است.

    گزینه‌های نمایش

    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با مقدار پیکربندی term.quiet مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با مقدار پیکربندی term.color مشخص کرد.

    --message-format fmt

    قالب خروجی پیام‌های تشخیصی. می‌توان آن را چندین بار مشخص کرد و از مقادیر جداشده با کاما تشکیل می‌شود. مقادیر معتبر:

    • human (پیش‌فرض): با قالب متنی قابل‌خواندن برای انسان نمایش می‌دهد. با short و json تعارض دارد.
    • short: پیام‌های متنی کوتاه‌تر و قابل‌خواندن برای انسان صادر می‌کند. با human و json تعارض دارد.
    • json: پیام‌های JSON را در stdout صادر می‌کند. برای جزئیات بیشتر مرجع را ببینید. با human و short تعارض دارد.
    • json-diagnostic-short: تضمین می‌کند فیلد rendered پیام‌های JSON شامل نمایش «کوتاه» rustc باشد. با human یا short قابل استفاده نیست.
    • json-diagnostic-rendered-ansi: تضمین می‌کند فیلد rendered پیام‌های JSON شامل کدهای رنگ ANSI تعبیه‌شده باشد تا طرح رنگ پیش‌فرض rustc رعایت شود. با human یا short قابل استفاده نیست.
    • json-render-diagnostics: به Cargo دستور می‌دهد تشخیص‌های rustc را در پیام‌های JSON چاپ‌شده نگنجاند، بلکه خود Cargo تشخیص‌های JSON دریافتی از rustc را نمایش دهد. تشخیص‌های JSON خود Cargo و سایر تشخیص‌هایی که از rustc می‌آیند همچنان صادر می‌شوند. با human یا short قابل استفاده نیست.

    گزینه‌های manifest

    --manifest-path path

    مسیر فایل Cargo.toml. به‌طور پیش‌فرض، Cargo فایل Cargo.toml را در دایرکتوری فعلی یا هر دایرکتوری والد جست‌وجو می‌کند.

    --ignore-rust-version

    مشخصهٔ rust-version را در بسته‌ها نادیده می‌گیرد.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از آفلاین شدن، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.

    گزینه‌های متفرقه

    -j N
    --jobs N

    تعداد jobهای موازی برای اجرا. همچنین می‌توان آن را با مقدار پیکربندی build.jobs مشخص کرد. پیش‌فرض تعداد CPUهای منطقی است. اگر منفی باشد، حداکثر تعداد jobهای موازی را برابر تعداد CPUهای منطقی به‌علاوهٔ مقدار داده‌شده قرار می‌دهد. اگر رشتهٔ default داده شود، مقدار را به پیش‌فرض بازمی‌گرداند. نباید 0 باشد.

    --keep-going

    تا جای ممکن crateهای بیشتری از گراف وابستگی را می‌سازد، به‌جای آنکه با اولین crateی که ساخته نمی‌شود، ساخت را متوقف کند.

    برای مثال، اگر بستهٔ فعلی به وابستگی‌های fails و works وابسته باشد و یکی از آن‌ها ساخته نشود، cargo fix -j1 ممکن است crateی را که موفق می‌شود بسازد یا نسازد (بسته به اینکه Cargo کدام یک از دو ساخت را زودتر اجرا کند)، در حالی که cargo fix -j1 --keep-going قطعاً هر دو ساخت را اجرا می‌کند، حتی اگر ساختی که اول اجرا شده شکست بخورد.

    متغیرهای محیطی

    برای جزئیات متغیرهای محیطی که Cargo می‌خواند، مرجع را ببینید.

    وضعیت خروج

    • 0: Cargo موفق بود.
    • 101: Cargo نتوانست کار را به پایان برساند.

    مثال‌ها

    1. پیشنهادهای کامپایلر را روی بستهٔ محلی اعمال کنید:

      cargo fix

    2. یک بسته را برای آماده شدن برای edition بعدی به‌روزرسانی کنید:

      cargo fix --edition

    3. idiomهای پیشنهادی را برای edition فعلی اعمال کنید:

      cargo fix --edition-idioms
