    cargo-yank(1)

    نام

    cargo-yank — حذف یک crate منتشرشده از index

    خلاصه

    cargo yank [options] crate@version
    cargo yank [options] --version version [crate]

    توضیحات

    فرمان yank نسخهٔ یک crate را که پیش‌تر منتشر شده است از index سرور حذف می‌کند. این فرمان هیچ داده‌ای را حذف نمی‌کند و crate همچنان از طریق پیوند دانلود registry برای دانلود در دسترس خواهد بود.

    Cargo نسخهٔ yank‌شده را برای هیچ پروژهٔ جدید یا checkout‌ای که فایل lock از پیش موجود ندارد استفاده نمی‌کند، و اگر دیگر هیچ نسخهٔ سازگاری برای crate شما باقی نمانده باشد، خطا تولید می‌کند.

    این فرمان نیاز دارد که یا با گزینهٔ --token یا با cargo-login(1) احراز هویت شده باشید.

    اگر نام crate مشخص نشود، از نام بستهٔ دایرکتوری فعلی استفاده می‌شود.

    yank چگونه کار می‌کند

    برای مثال، crate با نام foo نسخهٔ 1.5.0 را منتشر کرده و crate دیگری به نام bar یک وابستگی به نسخهٔ foo = "1.5" تعریف کرده است. اکنون foo نسخهٔ جدید 2.0.0 را که با semver سازگار نیست منتشر می‌کند و مشکلی بحرانی در 1.5.0 می‌یابد. اگر 1.5.0 yank شود، هیچ پروژه یا checkout جدیدی که فایل lock موجود ندارد نمی‌تواند از crate bar استفاده کند، زیرا bar به 1.5 وابسته است.

    در این حالت، نگه‌دارندگان foo باید پیش از yank کردن 1.5.0، ابتدا یک نسخهٔ سازگار با semver مانند 1.5.1 منتشر کنند تا bar و همهٔ پروژه‌هایی که به bar وابسته‌اند همچنان کار کنند.

    به‌عنوان مثالی دیگر، crate‌ای به نام bar را در نظر بگیرید که نسخه‌های منتشرشدهٔ آن 1.5.0، 1.5.1، 1.5.2، 2.0.0 و 3.0.0 است. جدول زیر مشخص می‌کند که پس از yank شدن یک نسخهٔ معین، cargo در نبود فایل lock برای نیازمندی‌های مختلف SemVer می‌تواند از کدام نسخه‌ها استفاده کند:

    نسخهٔ yank‌شده / نیازمندی SemVerbar = "1.5.0"bar = "=1.5.0"bar = "2.0.0"
    1.5.0از 1.5.1 یا 1.5.2 استفاده می‌کندخطا برمی‌گردانداز 2.0.0 استفاده می‌کند
    1.5.1از 1.5.0 یا 1.5.2 استفاده می‌کنداز 1.5.0 استفاده می‌کنداز 2.0.0 استفاده می‌کند
    2.0.0از 1.5.0، 1.5.1 یا 1.5.2 استفاده می‌کنداز 1.5.0 استفاده می‌کندخطا برمی‌گرداند

    چه زمانی yank کنیم

    crateها باید فقط در شرایط استثنایی yank شوند؛ برای مثال انتشار تصادفی، شکستن ناخواستهٔ SemVer، یا crate‌ای که به‌شدت خراب و غیرقابل استفاده است. در مورد آسیب‌پذیری‌های امنیتی، RustSec معمولاً سازوکاری کم‌اختلال‌تر برای آگاه کردن کاربران و تشویق آن‌ها به ارتقا است و از احتمال اختلال گستردهٔ پایین‌دستی، صرف‌نظر از حساس بودن به آسیب‌پذیری مورد نظر، جلوگیری می‌کند.

    یک روند کاری رایج این است که crate را پس از انتشار یک نسخهٔ سازگار با semver yank کنند، تا احتمال جلوگیری از کامپایل شدن crateهای وابسته کاهش یابد.

    هنگام رسیدگی به مسائل مربوط به حق نشر، مجوز یا داده‌های شخصی در یک crate منتشرشده، صرفاً yank کردن آن ممکن است کافی نباشد. در چنین مواردی با نگه‌دارندگان registry‌ای که استفاده کرده‌اید تماس بگیرید. برای crates.io، سیاست‌های آن‌ها را ببینید و از طریق help@crates.io با آن‌ها تماس بگیرید.

    اگر اعتبارنامه‌ها (credentials) افشا شده باشند، اقدام توصیه‌شده این است که فوراً آن‌ها را باطل کنید. پس از انتشار یک crate، نمی‌توان تشخیص داد که آیا اعتبارنامه‌های افشاشده کپی شده‌اند یا نه. yank کردن فقط Cargo را از انتخاب این نسخه هنگام حل‌وفصل وابستگی‌ها به‌صورت پیش‌فرض بازمی‌دارد. فایل‌های lock موجود یا دانلودهای مستقیم تحت‌تأثیر قرار نمی‌گیرند، بنابراین yank کردن نمی‌تواند از انتشار بیشتر اعتبارنامه‌های افشاشده جلوگیری کند.

    گزینه‌ها

    گزینه‌های yank

    --vers version
    --version version

    نسخه‌ای که باید yank یا un-yank شود.

    --undo

    yank را لغو می‌کند و نسخه را به index برمی‌گرداند.

    --token token

    توکن API که هنگام احراز هویت استفاده می‌شود. این گزینه توکن ذخیره‌شده در فایل credentials (که توسط cargo-login(1) ساخته می‌شود) را بازنویسی می‌کند.

    متغیرهای محیطی پیکربندی Cargo را می‌توان برای بازنویسی توکن‌های ذخیره‌شده در فایل credentials به کار برد. توکن crates.io را می‌توان با متغیر محیطی CARGO_REGISTRY_TOKEN مشخص کرد. توکن‌های registryهای دیگر را می‌توان با متغیرهای محیطی به شکل CARGO_REGISTRIES_NAME_TOKEN مشخص کرد که در آن NAME نام registry با حروف بزرگ است.

    --index index

    نشانی URL مربوط به index رجیستری که باید استفاده شود.

    --registry registry

    نام registry‌ای که باید استفاده شود. نام registryها در فایل‌های پیکربندی Cargo تعریف می‌شوند. اگر مشخص نشود، از registry پیش‌فرض استفاده می‌شود که با کلید پیکربندی registry.default تعریف می‌شود و مقدار پیش‌فرض آن crates-io است.

    گزینه‌های نمایش

    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با مقدار پیکربندی term.quiet مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با مقدار پیکربندی term.color مشخص کرد.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.
