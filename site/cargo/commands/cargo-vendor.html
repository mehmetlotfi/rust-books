    cargo-vendor(1)

    نام

    cargo-vendor — قرار دادن همهٔ وابستگی‌ها به‌صورت محلی (vendor)

    خلاصه

    cargo vendor [options] [path]

    توضیحات

    این زیرفرمان cargo همهٔ وابستگی‌های crates.io و git یک پروژه را در دایرکتوری مشخص‌شده در <path> vendor می‌کند. پس از پایان این فرمان، دایرکتوری vendor مشخص‌شده با <path> شامل همهٔ منابع راه‌دور وابستگی‌های مشخص‌شده خواهد بود. با گزینهٔ -s می‌توان manifestهای اضافی دیگری را فراتر از manifest پیش‌فرض مشخص کرد.

    پس از پایان فرایند vendor کردن توسط cargo vendor، پیکربندی لازم برای استفاده از منابع vendor‌شده در stdout چاپ می‌شود. باید آن را به فایل پیکربندی Cargo خود اضافه یا به آن هدایت کنید؛ این فایل معمولاً برای بستهٔ فعلی به‌صورت محلی .cargo/config.toml است.

    Cargo منابع vendor‌شده را مانند منابع registry و git فقط‌خواندنی در نظر می‌گیرد. اگر قصد دارید crate‌ای را از یک منبع راه‌دور تغییر دهید، از [patch] یا یک وابستگی path که به یک نسخهٔ محلی از آن crate اشاره می‌کند استفاده کنید. در این صورت Cargo آن crate را در ساخت‌های افزایشی (incremental) به‌درستی مدیریت می‌کند، زیرا می‌داند که دیگر یک وابستگی فقط‌خواندنی نیست.

    گزینه‌ها

    گزینه‌های vendor

    -s manifest
    --sync manifest

    یک manifest اضافی Cargo.toml برای workspaceهایی مشخص می‌کند که باید vendor شوند و با خروجی همگام‌سازی شوند. می‌توان آن را چندین بار مشخص کرد.

    --no-delete

    هنگام vendor کردن، دایرکتوری «vendor» را حذف نمی‌کند و در عوض همهٔ محتویات موجود دایرکتوری vendor را نگه می‌دارد.

    --respect-source-config

    به‌جای نادیده گرفتن پیش‌فرض پیکربندی [source] در .cargo/config.toml، آن را می‌خواند و هنگام دانلود crateها به کار می‌برد.

    --versioned-dirs

    به‌طور معمول نسخه‌ها فقط برای تمایز میان چند نسخهٔ یک بستهٔ یکسان اضافه می‌شوند. این گزینه باعث می‌شود همهٔ دایرکتوری‌های درون دایرکتوری «vendor» شامل نسخه باشند؛ این کار ردیابی تاریخچهٔ بسته‌های vendor‌شده در طول زمان را آسان‌تر می‌کند و می‌تواند وقتی فقط زیرمجموعه‌ای از بسته‌ها تغییر کرده‌اند به کارایی vendor کردن مجدد کمک کند.

    گزینه‌های manifest

    --manifest-path path

    مسیر فایل Cargo.toml. به‌طور پیش‌فرض، Cargo فایل Cargo.toml را در دایرکتوری فعلی یا هر دایرکتوری والد جست‌وجو می‌کند.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از رفتن به حالت آفلاین، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های نمایش

    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با مقدار پیکربندی term.quiet مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با مقدار پیکربندی term.color مشخص کرد.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.

    متغیرهای محیطی

    برای جزئیات متغیرهای محیطی که Cargo می‌خواند، مرجع را ببینید.

    وضعیت خروج

    • 0: Cargo موفق بود.
    • 101: Cargo نتوانست کار را به پایان برساند.

    مثال‌ها

    1. همهٔ وابستگی‌ها را در پوشهٔ محلی «vendor» قرار دهید

      cargo vendor

    2. همهٔ وابستگی‌ها را در پوشهٔ محلی «third-party/vendor» قرار دهید

      cargo vendor third-party/vendor

    3. workspace فعلی و نیز یک workspace دیگر را در «vendor» قرار دهید

      cargo vendor -s ../path/to/Cargo.toml

    4. vendor کنید و پیکربندی‌های لازم vendor را به یک فایل پیکربندی هدایت کنید.

      cargo vendor > path/to/my/cargo/config.toml
