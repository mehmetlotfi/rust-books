کتاب CargoThe Cargo Book

    cargo-bench(1)

    نام

    cargo-bench — اجرای benchmarkهای یک بسته

    خلاصه

    cargo bench [options] [benchname] [-- bench-options]

    توضیحات

    benchmarkها را کامپایل و اجرا می‌کند.

    آرگومان فیلتر benchmark یعنی benchname و همهٔ آرگومان‌هایی که پس از دو خط تیره (--) می‌آیند به باینری‌های benchmark و در نتیجه به libtest (چارچوب داخلی rustc برای آزمون واحد و ریزبنچمارک) ارسال می‌شوند. اگر هم به Cargo و هم به باینری آرگومان می‌دهید، آرگومان‌های پس از -- به باینری و آرگومان‌های پیش از آن به Cargo می‌روند. برای جزئیات آرگومان‌های libtest، خروجی cargo bench -- --help را ببینید و فصل کتاب rustc دربارهٔ نحوهٔ کار آزمون‌ها را در https://doc.rust-lang.org/rustc/tests/index.html مطالعه کنید.

    برای مثال، این فرمان فقط benchmark به نام foo را اجرا می‌کند (و benchmarkهایی با نام مشابه مانند foobar را نادیده می‌گیرد):

    cargo bench -- foo --exact

    benchmarkها با گزینهٔ --test برای rustc ساخته می‌شوند که با پیوند دادن کد شما به libtest یک فایل اجرایی ویژه تولید می‌کند. این فایل اجرایی به‌طور خودکار همهٔ تابع‌هایی را اجرا می‌کند که با attribute به نام #[bench] علامت‌گذاری شده‌اند. Cargo پرچم --bench را به test harness می‌دهد تا به آن بگوید فقط benchmarkها را اجرا کند، چه harness همان libtest باشد و چه یک harness سفارشی.

    harness مربوط به libtest را می‌توان با تنظیم harness = false در تنظیمات manifest هدف غیرفعال کرد؛ در این صورت کد شما باید تابع main خودش را برای اجرای benchmarkها فراهم کند.

    توجه: attribute به نام #[bench] فعلاً ناپایدار است و فقط در کانال nightly در دسترس است. چند بسته در crates.io وجود دارند که می‌توانند در اجرای benchmarkها در کانال stable کمک کنند، مانند Criterion.

    به‌طور پیش‌فرض، cargo bench از profile به نام bench استفاده می‌کند که بهینه‌سازی‌ها را فعال و اطلاعات اشکال‌زدایی را غیرفعال می‌کند. اگر نیاز دارید یک benchmark را اشکال‌زدایی کنید، می‌توانید با گزینهٔ خط فرمان --profile=debug به profile اشکال‌زدایی (debug) تغییر دهید. سپس می‌توانید benchmark دارای اطلاعات اشکال‌زدایی را درون یک دیباگر اجرا کنید.

    دایرکتوری کاری benchmarkها

    دایرکتوری کاری هر benchmark روی دایرکتوری ریشهٔ بسته‌ای تنظیم می‌شود که benchmark به آن تعلق دارد. تنظیم دایرکتوری کاری benchmarkها روی دایرکتوری ریشهٔ بسته این امکان را فراهم می‌کند که benchmarkها بتوانند با مسیرهای نسبی و به‌طور قابل‌اعتماد به فایل‌های بسته دسترسی داشته باشند، صرف‌نظر از اینکه cargo bench از کجا اجرا شده است.

    گزینه‌ها

    گزینه‌های benchmark

    --no-run

    benchmarkها را کامپایل می‌کند اما اجرا نمی‌کند.

    --no-fail-fast

    همهٔ benchmarkها را بدون توجه به شکست اجرا می‌کند. بدون این پرچم، Cargo پس از شکست خوردن اولین فایل اجرایی خارج می‌شود. test harness در Rust همهٔ benchmarkهای درون یک فایل اجرایی را تا پایان اجرا می‌کند؛ این پرچم فقط بر فایل اجرایی به‌صورت کلی اعمال می‌شود.

    انتخاب بسته

    به‌طور پیش‌فرض، وقتی هیچ گزینهٔ انتخاب بسته‌ای داده نشده باشد، بسته‌های انتخاب‌شده به فایل manifest انتخاب‌شده بستگی دارند (اگر --manifest-path داده نشده باشد، بر اساس دایرکتوری کاری فعلی). اگر manifest ریشهٔ یک workspace باشد، اعضای پیش‌فرض workspace انتخاب می‌شوند؛ در غیر این صورت فقط بسته‌ای که manifest تعریف می‌کند انتخاب خواهد شد.

    اعضای پیش‌فرض یک workspace را می‌توان با کلید workspace.default-members در manifest ریشه به‌صراحت تعیین کرد. اگر این کلید تنظیم نشده باشد، یک workspace مجازی همهٔ اعضای workspace را شامل می‌شود (معادل دادن --workspace) و یک workspace غیرمجازی فقط خود crate ریشه را شامل می‌شود.

    -p spec…
    --package spec…

    فقط benchmark بسته‌های مشخص‌شده را اجرا می‌کند. برای قالب SPEC به cargo-pkgid(1) مراجعه کنید. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    --workspace

    benchmark همهٔ اعضای workspace را اجرا می‌کند.

    --all

    نام مستعار منسوخ‌شدهٔ --workspace.

    --exclude SPEC…

    بسته‌های مشخص‌شده را کنار می‌گذارد. باید همراه با گزینهٔ --workspace استفاده شود. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    انتخاب هدف

    وقتی هیچ گزینهٔ انتخاب هدفی داده نشده باشد، cargo bench هدف‌های زیر از بسته‌های انتخاب‌شده را می‌سازد:

    • lib — برای پیوند دادن با باینری‌ها و benchmarkها استفاده می‌شود
    • bins (فقط اگر هدف‌های benchmark ساخته شوند و featureهای موردنیاز در دسترس باشند)
    • lib به‌عنوان benchmark
    • bins به‌عنوان benchmark
    • هدف‌های benchmark

    رفتار پیش‌فرض را می‌توان با تنظیم پرچم bench برای هدف در تنظیمات manifest تغییر داد. تنظیم نمونه‌ها (example) روی bench = true باعث می‌شود نمونه به‌عنوان benchmark ساخته و اجرا شود و تابع main نمونه با harness مربوط به libtest جایگزین گردد.

    تنظیم هدف‌ها روی bench = false مانع از benchmark شدن پیش‌فرض آن‌ها می‌شود. گزینه‌های انتخاب هدف که هدف را با نام می‌گیرند (مانند --example foo) پرچم bench را نادیده می‌گیرند و همیشه هدف داده‌شده را benchmark می‌کنند.

    برای اطلاعات بیشتر دربارهٔ تنظیمات هر هدف، پیکربندی یک هدف را ببینید.

    اگر یک آزمون یکپارچگی یا benchmark برای اجرای benchmark انتخاب شده باشد، هدف‌های باینری به‌طور خودکار ساخته می‌شوند. این کار به آزمون یکپارچگی اجازه می‌دهد فایل اجرایی را اجرا کند تا رفتار آن را بیازماید. هنگام ساخت و اجرای آزمون یکپارچگی، متغیر محیطی CARGO_BIN_EXE_<name> تنظیم می‌شود تا آزمون بتواند با ماکروی env یا تابع var فایل اجرایی را پیدا کند.

    با دادن پرچم‌های انتخاب هدف، فقط هدف‌های مشخص‌شده benchmark می‌شوند.

    توجه کنید که پرچم‌های --bin، --example، --test و --bench نیز از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کنند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگوی glob از نقل‌قول تکی یا دوتایی استفاده کنید.

    --lib

    benchmark کتابخانهٔ بسته را اجرا می‌کند.

    --bin name…

    benchmark باینری مشخص‌شده را اجرا می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --bins

    benchmark همهٔ هدف‌های باینری را اجرا می‌کند.

    --example name…

    benchmark نمونهٔ (example) مشخص‌شده را اجرا می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --examples

    benchmark همهٔ هدف‌های نمونه (example) را اجرا می‌کند.

    --test name…

    benchmark آزمون یکپارچگی مشخص‌شده را اجرا می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --tests

    benchmark همهٔ هدف‌هایی را اجرا می‌کند که پرچم manifest به نام test = true برایشان تنظیم شده است. به‌طور پیش‌فرض این شامل کتابخانه و باینری‌هایی است که به‌عنوان آزمون واحد ساخته می‌شوند، و نیز آزمون‌های یکپارچگی. توجه داشته باشید که این کار هر وابستگی موردنیاز را هم می‌سازد، بنابراین ممکن است هدف lib دو بار ساخته شود (یک بار به‌عنوان آزمون واحد و یک بار به‌عنوان وابستگی برای باینری‌ها، آزمون‌های یکپارچگی و غیره). هدف‌ها را می‌توان با تنظیم پرچم test در تنظیمات manifest همان هدف فعال یا غیرفعال کرد.

    --bench name…

    benchmark مشخص‌شده را اجرا می‌کند. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --benches

    benchmark همهٔ هدف‌هایی را اجرا می‌کند که پرچم manifest به نام bench = true برایشان تنظیم شده است. به‌طور پیش‌فرض این شامل کتابخانه و باینری‌هایی است که به‌عنوان benchmark ساخته می‌شوند، و نیز هدف‌های bench. توجه داشته باشید که این کار هر وابستگی موردنیاز را هم می‌سازد، بنابراین ممکن است هدف lib دو بار ساخته شود (یک بار به‌عنوان benchmark و یک بار به‌عنوان وابستگی برای باینری‌ها، benchmarkها و غیره). هدف‌ها را می‌توان با تنظیم پرچم bench در تنظیمات manifest همان هدف فعال یا غیرفعال کرد.

    --all-targets

    benchmark همهٔ هدف‌ها را اجرا می‌کند. این معادل مشخص کردن --lib --bins --tests --benches --examples است.

    انتخاب feature

    پرچم‌های feature به شما امکان می‌دهند کنترل کنید کدام featureها فعال باشند. وقتی هیچ گزینهٔ featureای داده نشده باشد، feature به نام default برای هر بستهٔ انتخاب‌شده فعال می‌شود.

    برای جزئیات بیشتر، مستندات featureها را ببینید.

    -F features
    --features features

    فهرستی از featureهای قابل فعال‌سازی که با فاصله یا کاما جدا شده است. featureهای اعضای workspace را می‌توان با نحو package-name/feature-name فعال کرد. این گزینه را می‌توان چندین بار مشخص کرد که همهٔ featureهای مشخص‌شده را فعال می‌کند.

    --all-features

    همهٔ featureهای موجود همهٔ بسته‌های انتخاب‌شده را فعال می‌کند.

    --no-default-features

    feature به نام default بسته‌های انتخاب‌شده را فعال نمی‌کند.

    گزینه‌های کامپایل

    --target tuple

    benchmark را برای معماری هدف مشخص‌شده اجرا می‌کند. این گزینه را می‌توان چندین بار مشخص کرد. پیش‌فرض معماری میزبان (host) است. قالب کلی tuple به این صورت است: <arch><sub>-<vendor>-<sys>-<abi>.

    مقادیر ممکن:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple" که به‌طور داخلی با هدف میزبان جایگزین می‌شود. این مورد به‌ویژه وقتی مفید است که برخی crateها را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان خود را به‌عنوان هدف مشخص کنید (برای مثال، یک xtask در پروژه‌ای مشترک که ممکن است میزبان‌های بسیاری روی آن کار کنند).
    • مسیر یک مشخصهٔ هدف سفارشی. برای اطلاعات بیشتر مسیر جست‌وجوی هدف سفارشی را ببینید.

    این گزینه را می‌توان با مقدار پیکربندی build.target نیز مشخص کرد.

    توجه کنید که مشخص کردن این پرچم باعث می‌شود Cargo در حالتی متفاوت اجرا شود که در آن artifactهای هدف در یک دایرکتوری جداگانه قرار می‌گیرند. برای جزئیات بیشتر، مستندات حافظهٔ نهان ساخت را ببینید.

    --profile name

    benchmark را با profile داده‌شده اجرا می‌کند. برای جزئیات بیشتر دربارهٔ profileها مرجع را ببینید.

    --timings

    اطلاعاتی دربارهٔ مدت زمان هر کامپایل خروجی می‌دهد و اطلاعات هم‌زمانی را در طول زمان ردیابی می‌کند.

    در پایان ساخت، فایلی به نام cargo-timing.html در دایرکتوری target/cargo-timings نوشته می‌شود. اگر بخواهید اجرای قبلی را ببینید، یک گزارش اضافی هم با مهر زمانی در نام فایلش نوشته می‌شود. این گزارش‌ها فقط برای مصرف انسانی مناسب‌اند و داده‌های زمان‌بندی قابل‌خواندن برای ماشین ارائه نمی‌دهند.

    گزینه‌های خروجی

    --target-dir directory

    دایرکتوری همهٔ artifactهای تولیدشده و فایل‌های میانی. همچنین می‌توان آن را با متغیر محیطی CARGO_TARGET_DIR یا با مقدار پیکربندی build.target-dir مشخص کرد. پیش‌فرض آن target در ریشهٔ workspace است.

    گزینه‌های نمایش

    به‌طور پیش‌فرض، test harness در Rust خروجی اجرای benchmark را پنهان می‌کند تا نتایج خوانا بمانند. با ارسال --no-capture به باینری‌های benchmark می‌توان خروجی benchmark را بازیابی کرد (مثلاً برای اشکال‌زدایی):

    cargo bench -- --no-capture
    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با مقدار پیکربندی term.quiet مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با مقدار پیکربندی term.color مشخص کرد.

    --message-format fmt

    قالب خروجی پیام‌های تشخیصی. می‌توان آن را چندین بار مشخص کرد و از مقادیر جداشده با کاما تشکیل می‌شود. مقادیر معتبر:

    • human (پیش‌فرض): با قالب متنی قابل‌خواندن برای انسان نمایش می‌دهد. با short و json تعارض دارد.
    • short: پیام‌های متنی کوتاه‌تر و قابل‌خواندن برای انسان صادر می‌کند. با human و json تعارض دارد.
    • json: پیام‌های JSON را در stdout صادر می‌کند. برای جزئیات بیشتر مرجع را ببینید. با human و short تعارض دارد.
    • json-diagnostic-short: تضمین می‌کند فیلد rendered پیام‌های JSON شامل نمایش «کوتاه» rustc باشد. با human یا short قابل استفاده نیست.
    • json-diagnostic-rendered-ansi: تضمین می‌کند فیلد rendered پیام‌های JSON شامل کدهای رنگ ANSI تعبیه‌شده باشد تا طرح رنگ پیش‌فرض rustc رعایت شود. با human یا short قابل استفاده نیست.
    • json-render-diagnostics: به Cargo دستور می‌دهد تشخیص‌های rustc را در پیام‌های JSON چاپ‌شده نگنجاند، بلکه خود Cargo تشخیص‌های JSON دریافتی از rustc را نمایش دهد. تشخیص‌های JSON خود Cargo و سایر تشخیص‌هایی که از rustc می‌آیند همچنان صادر می‌شوند. با human یا short قابل استفاده نیست.

    گزینه‌های manifest

    --manifest-path path

    مسیر فایل Cargo.toml. به‌طور پیش‌فرض، Cargo فایل Cargo.toml را در دایرکتوری فعلی یا هر دایرکتوری والد جست‌وجو می‌کند.

    --ignore-rust-version

    مشخصهٔ rust-version را در بسته‌ها نادیده می‌گیرد.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از آفلاین شدن، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.

    گزینه‌های متفرقه

    آرگومان --jobs بر ساخت فایل اجرایی benchmark اثر می‌گذارد اما بر تعداد نخ‌هایی که هنگام اجرای benchmarkها استفاده می‌شوند اثری ندارد. test harness در Rust benchmarkها را به‌صورت ترتیبی و در یک نخ واحد اجرا می‌کند.

    -j N
    --jobs N

    تعداد jobهای موازی برای اجرا. همچنین می‌توان آن را با مقدار پیکربندی build.jobs مشخص کرد. پیش‌فرض تعداد CPUهای منطقی است. اگر منفی باشد، حداکثر تعداد jobهای موازی را برابر تعداد CPUهای منطقی به‌علاوهٔ مقدار داده‌شده قرار می‌دهد. اگر رشتهٔ default داده شود، مقدار را به پیش‌فرض بازمی‌گرداند. نباید 0 باشد.

    اگرچه cargo bench شامل کامپایل است، پرچم --keep-going را ارائه نمی‌دهد. از --no-fail-fast استفاده کنید تا بدون توقف در اولین شکست، تا جای ممکن benchmarkهای بیشتری اجرا شوند. برای «کامپایل» تا جای ممکن benchmarkهای بیشتر، از --benches استفاده کنید تا باینری‌های benchmark جداگانه ساخته شوند. برای مثال:

    cargo build --benches --release --keep-going
cargo bench --no-fail-fast

    متغیرهای محیطی

    برای جزئیات متغیرهای محیطی که Cargo می‌خواند، مرجع را ببینید.

    وضعیت خروج

    • 0: Cargo موفق بود.
    • 101: Cargo نتوانست کار را به پایان برساند.

    مثال‌ها

    1. همهٔ benchmarkهای بستهٔ فعلی را بسازید و اجرا کنید:

      cargo bench

    2. فقط یک benchmark مشخص را درون یک هدف benchmark مشخص اجرا کنید:

      cargo bench --bench bench_name -- modname::some_benchmark
