کتاب CargoThe Cargo Book

    cargo-package(1)

    نام

    cargo-package — بسته‌بندی بستهٔ محلی در یک tarball قابل‌توزیع

    خلاصه

    cargo package [options]

    توضیحات

    این فرمان یک فایل .crate فشرده و قابل‌توزیع می‌سازد که حاوی کد منبع بسته در دایرکتوری فعلی است. فایل حاصل در دایرکتوری target/package ذخیره می‌شود. مراحل زیر انجام می‌شوند:

    1. workspace فعلی را بارگذاری و بررسی می‌کند و چند بررسی ساده انجام می‌دهد.

      • وابستگی‌های مسیری (path) مجاز نیستند، مگر اینکه کلید version داشته باشند. Cargo کلید path را برای وابستگی‌ها در بسته‌های منتشرشده نادیده می‌گیرد. dev-dependencies این محدودیت را ندارند.

    2. فایل .crate فشرده را می‌سازد.

      • فایل Cargo.toml اصلی بازنویسی و نرمال‌سازی می‌شود.
      • بخش‌های [patch]، [replace] و [workspace] از manifest حذف می‌شوند.
      • Cargo.lock همیشه گنجانده می‌شود. اگر وجود نداشته باشد، یک فایل lock جدید تولید می‌شود، مگر اینکه پرچم --exclude-lockfile به کار رفته باشد. cargo-install(1) در صورت استفاده از پرچم --locked از فایل lock بسته‌بندی‌شده استفاده می‌کند.
      • یک فایل .cargo_vcs_info.json گنجانده می‌شود که در صورت وجود، اطلاعاتی دربارهٔ هش checkout فعلی VCS دارد و نیز پرچمی که نشان می‌دهد worktree تغییرات ثبت‌نشده (dirty) دارد یا نه.
      • symlinkها به فایل‌های هدفشان تبدیل (flatten) می‌شوند.
      • فایل‌ها و دایرکتوری‌ها بر اساس قوانین ذکرشده در فیلدهای [include] و [exclude] گنجانده یا کنار گذاشته می‌شوند.

    3. فایل .crate را استخراج می‌کند و آن را می‌سازد تا مطمئن شود قابل ساخت است.

      • این کار بستهٔ شما را از صفر دوباره می‌سازد تا اطمینان حاصل شود که از یک حالت دست‌نخورده ساخته می‌شود. برای رد شدن از این مرحله می‌توان از پرچم --no-verify استفاده کرد.

    4. بررسی می‌کند که build scriptها هیچ فایل منبعی را تغییر نداده باشند.

    فهرست فایل‌های گنجانده‌شده را می‌توان با فیلدهای include و exclude در manifest کنترل کرد.

    برای جزئیات بیشتر دربارهٔ بسته‌بندی و انتشار، مرجع را ببینید.

    قالب .cargo_vcs_info.json

    فایل .cargo_vcs_info.json را با قالب زیر تولید می‌کند

    {
 "git": {
   "sha1": "aac20b6e7e543e6dd4118b246c77225e3a3a1302",
   "dirty": true
 },
 "path_in_vcs": ""
}

    dirty نشان می‌دهد که worktree گیت هنگام ساخت بسته تغییرات ثبت‌نشده داشته است.

    path_in_vcs برای بسته‌هایی که در زیردایرکتوری‌های مخزن کنترل نسخه قرار دارند، روی یک مسیر نسبت‌به مخزن تنظیم می‌شود.

    سازگاری این فایل تحت همان سیاستی حفظ می‌شود که برای خروجی JSON فرمان cargo-metadata(1) اعمال می‌شود.

    توجه کنید که این فایل یک تصویر لحظه‌ای با بهترین تلاش از اطلاعات VCS ارائه می‌دهد. با این حال، منشأ بسته راستی‌آزمایی نمی‌شود. هیچ تضمینی وجود ندارد که کد منبع درون tarball با اطلاعات VCS مطابقت داشته باشد.

    گزینه‌ها

    گزینه‌های بسته‌بندی

    -l
    --list

    فایل‌های گنجانده‌شده در یک بسته را بدون ساختن آن چاپ می‌کند.

    --no-verify

    محتویات را با ساختن آن‌ها راستی‌آزمایی نمی‌کند.

    --no-metadata

    هشدارهای مربوط به نبود فراداده‌های قابل‌استفاده برای انسان (مانند توضیحات یا مجوز) را نادیده می‌گیرد.

    --allow-dirty

    اجازه می‌دهد دایرکتوری‌های کاری دارای تغییرات VCS ثبت‌نشده بسته‌بندی شوند.

    --exclude-lockfile

    هنگام بسته‌بندی فایل lock را نمی‌گنجاند.

    این پرچم برای استفادهٔ عمومی نیست. برخی ابزارها ممکن است انتظار داشته باشند فایل lock وجود داشته باشد (مثلاً cargo install --locked). پیش از استفاده از آن گزینه‌های دیگر را در نظر بگیرید.

    --index index

    نشانی URL ایندکس رجیستری که باید استفاده شود.

    --registry registry

    نام رجیستری‌ای که برای آن بسته‌بندی انجام می‌شود؛ برای جزئیات بیشتر دربارهٔ پیکربندی نام رجیستری‌ها cargo publish --help را ببینید. بسته‌ها روی این رجیستری منتشر نخواهند شد، اما اگر چند crate وابسته به هم را بسته‌بندی کنیم، فایل‌های lock با این فرض تولید می‌شوند که وابستگی‌ها روی این رجیستری منتشر خواهند شد.

    --message-format fmt

    قالب پیام خروجی را مشخص می‌کند. در حال حاضر فقط با --list کار می‌کند و بر قالب فهرست فایل‌ها اثر می‌گذارد. این گزینه ناپایدار است و به -Zunstable-options نیاز دارد. قالب‌های خروجی معتبر:

    • human (پیش‌فرض): فایل‌ها را به‌صورت یک فایل در هر خط نمایش می‌دهد.
    • json: اطلاعات قابل‌خواندن برای ماشین دربارهٔ هر بسته را در قالب JSON تولید می‌کند. برای هر بسته یک خط JSON چاپ می‌شود (Newline delimited JSON). 
      {
  /* The Package ID Spec of the package. */
  "id": "path+file:///home/foo#0.0.0",
  /* Files of this package */
  "files" {
    /* Relative path in the archive file. */
    "Cargo.toml.orig": {
      /* Where the file is from.
         - "generate" for file being generated during packaging
         - "copy" for file being copied from another location.
      */
      "kind": "copy",
      /* For the "copy" kind,
         it is an absolute path to the actual file content.
         For the "generate" kind,
         it is the original file the generated one is based on.
      */
      "path": "/home/foo/Cargo.toml"
    },
    "Cargo.toml": {
      "kind": "generate",
      "path": "/home/foo/Cargo.toml"
    },
    "src/main.rs": {
      "kind": "copy",
      "path": "/home/foo/src/main.rs"
    }
  }
}

    انتخاب بسته

    به‌طور پیش‌فرض، وقتی هیچ گزینهٔ انتخاب بسته‌ای داده نشده باشد، بسته‌های انتخاب‌شده به فایل manifest انتخاب‌شده بستگی دارند (اگر --manifest-path داده نشده باشد، بر اساس دایرکتوری کاری فعلی). اگر manifest ریشهٔ یک workspace باشد، اعضای پیش‌فرض workspace انتخاب می‌شوند؛ در غیر این صورت فقط بسته‌ای که manifest تعریف می‌کند انتخاب خواهد شد.

    اعضای پیش‌فرض یک workspace را می‌توان با کلید workspace.default-members در manifest ریشه به‌صراحت تعیین کرد. اگر این کلید تنظیم نشده باشد، یک workspace مجازی همهٔ اعضای workspace را شامل می‌شود (معادل دادن --workspace) و یک workspace غیرمجازی فقط خود crate ریشه را شامل می‌شود.

    -p spec…
    --package spec…

    فقط بسته‌های مشخص‌شده را بسته‌بندی می‌کند. برای قالب SPEC به cargo-pkgid(1) مراجعه کنید. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    --workspace

    همهٔ اعضای workspace را بسته‌بندی می‌کند.

    --exclude SPEC…

    بسته‌های مشخص‌شده را کنار می‌گذارد. باید همراه با گزینهٔ --workspace استفاده شود. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    گزینه‌های کامپایل

    --target tuple

    برای معماری هدف مشخص‌شده بسته‌بندی می‌کند. این پرچم را می‌توان چندین بار مشخص کرد. پیش‌فرض معماری میزبان (host) است. قالب کلی tuple به این صورت است: <arch><sub>-<vendor>-<sys>-<abi>.

    مقادیر ممکن:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple" که به‌طور داخلی با هدف میزبان جایگزین می‌شود. این مورد به‌ویژه وقتی مفید است که برخی crateها را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان خود را به‌عنوان هدف مشخص کنید (برای مثال، یک xtask در پروژه‌ای مشترک که ممکن است میزبان‌های بسیاری روی آن کار کنند).
    • مسیر یک مشخصهٔ هدف سفارشی. برای اطلاعات بیشتر مسیر جست‌وجوی هدف سفارشی را ببینید.

    این گزینه را می‌توان با مقدار پیکربندی build.target نیز مشخص کرد.

    توجه کنید که مشخص کردن این پرچم باعث می‌شود Cargo در حالتی متفاوت اجرا شود که در آن artifactهای هدف در یک دایرکتوری جداگانه قرار می‌گیرند. برای جزئیات بیشتر، مستندات حافظهٔ نهان ساخت را ببینید.

    --target-dir directory

    دایرکتوری همهٔ artifactهای تولیدشده و فایل‌های میانی. همچنین می‌توان آن را با متغیر محیطی CARGO_TARGET_DIR یا با مقدار پیکربندی build.target-dir مشخص کرد. پیش‌فرض آن target در ریشهٔ workspace است.

    انتخاب feature

    پرچم‌های feature به شما امکان می‌دهند کنترل کنید کدام featureها فعال باشند. وقتی هیچ گزینهٔ featureای داده نشده باشد، feature به نام default برای هر بستهٔ انتخاب‌شده فعال می‌شود.

    برای جزئیات بیشتر، مستندات featureها را ببینید.

    -F features
    --features features

    فهرستی از featureهای قابل فعال‌سازی که با فاصله یا کاما جدا شده است. featureهای اعضای workspace را می‌توان با نحو package-name/feature-name فعال کرد. این گزینه را می‌توان چندین بار مشخص کرد که همهٔ featureهای مشخص‌شده را فعال می‌کند.

    --all-features

    همهٔ featureهای موجود همهٔ بسته‌های انتخاب‌شده را فعال می‌کند.

    --no-default-features

    feature به نام default بسته‌های انتخاب‌شده را فعال نمی‌کند.

    گزینه‌های manifest

    --manifest-path path

    مسیر فایل Cargo.toml. به‌طور پیش‌فرض، Cargo فایل Cargo.toml را در دایرکتوری فعلی یا هر دایرکتوری والد جست‌وجو می‌کند.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از آفلاین شدن، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های متفرقه

    -j N
    --jobs N

    تعداد jobهای موازی برای اجرا. همچنین می‌توان آن را با مقدار پیکربندی build.jobs مشخص کرد. پیش‌فرض تعداد CPUهای منطقی است. اگر منفی باشد، حداکثر تعداد jobهای موازی را برابر تعداد CPUهای منطقی به‌علاوهٔ مقدار داده‌شده قرار می‌دهد. اگر رشتهٔ default داده شود، مقدار را به پیش‌فرض بازمی‌گرداند. نباید 0 باشد.

    --keep-going

    تا جای ممکن crateهای بیشتری از گراف وابستگی را می‌سازد، به‌جای آنکه با اولین crateی که ساخته نمی‌شود، ساخت را متوقف کند.

    برای مثال، اگر بستهٔ فعلی به وابستگی‌های fails و works وابسته باشد و یکی از آن‌ها ساخته نشود، cargo package -j1 ممکن است crateی را که موفق می‌شود بسازد یا نسازد (بسته به اینکه Cargo کدام یک از دو ساخت را زودتر اجرا کند)، در حالی که cargo package -j1 --keep-going قطعاً هر دو ساخت را اجرا می‌کند، حتی اگر ساختی که اول اجرا شده شکست بخورد.

    گزینه‌های نمایش

    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با term.verbose مقدار پیکربندی مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با term.quiet مقدار پیکربندی مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با term.color مقدار پیکربندی مشخص کرد.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.
