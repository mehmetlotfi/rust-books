کتاب CargoThe Cargo Book

    cargo-test(1)

    نام

    cargo-test — اجرای آزمون‌های واحد و یکپارچگی یک بسته

    خلاصه

    cargo test [options] [testname] [-- test-options]

    توضیحات

    آزمون‌های واحد، یکپارچگی و مستندات را کامپایل و اجرا می‌کند.

    آرگومان فیلتر آزمون یعنی TESTNAME و همهٔ آرگومان‌هایی که پس از دو خط تیرهٔ (--) می‌آیند به فایل‌های اجرایی آزمون و در نتیجه به libtest (چارچوب داخلی rustc برای آزمون واحد و ریزسنجش عملکرد) داده می‌شوند. اگر آرگومان‌هایی را هم به Cargo و هم به فایل اجرایی می‌دهید، آن‌هایی که بعد از -- می‌آیند به فایل اجرایی و آن‌هایی که قبل از آن هستند به Cargo می‌رسند. برای جزئیات آرگومان‌های libtest، خروجی cargo test -- --help را ببینید و فصل کتاب rustc دربارهٔ نحوهٔ کار آزمون‌ها را در https://doc.rust-lang.org/rustc/tests/index.html مطالعه کنید.

    برای مثال، دستور زیر آزمون‌هایی را که foo در نامشان دارند فیلتر می‌کند و آن‌ها را روی ۳ نخ به‌صورت موازی اجرا می‌کند:

    cargo test foo -- --test-threads 3

    آزمون‌ها با گزینهٔ --test در rustc ساخته می‌شوند که با پیوند دادن کد شما به libtest یک فایل اجرایی ویژه تولید می‌کند. این فایل اجرایی به‌طور خودکار همهٔ تابع‌هایی را که با attribute به نام #[test] علامت‌گذاری شده‌اند در چند نخ اجرا می‌کند. تابع‌هایی که با #[bench] علامت‌گذاری شده‌اند نیز یک‌بار اجرا می‌شوند تا از کارکرد درست آن‌ها اطمینان حاصل شود.

    اگر بسته چند هدف آزمون داشته باشد، هر هدف همان‌طور که گفته شد به یک فایل اجرایی ویژه کامپایل می‌شود و سپس این فایل‌ها به‌صورت ترتیبی اجرا می‌شوند.

    با تنظیم harness = false در تنظیمات manifest هدف می‌توان harness مربوط به libtest را غیرفعال کرد؛ در این حالت کد شما باید تابع main مخصوص خود را برای اجرای آزمون‌ها فراهم کند.

    به‌طور پیش‌فرض، cargo test از پروفایل test استفاده می‌کند که برای بازخورد سریع، برخی بهینه‌سازی‌ها را فعال و اطلاعات اشکال‌زدایی را غیرفعال می‌کند. اگر لازم است یک آزمون را اشکال‌زدایی کنید، می‌توانید با گزینهٔ خط فرمان --profile=debug به پروفایل debug تغییر دهید. سپس می‌توانید آزمونی را که اشکال‌زدایی در آن فعال است درون یک debugger اجرا کنید.

    آزمون‌های مستندات

    آزمون‌های مستندات نیز به‌طور پیش‌فرض اجرا می‌شوند و این کار را rustdoc انجام می‌دهد. rustdoc نمونه‌کدها را از کامنت‌های مستندات هدف کتابخانه استخراج و سپس اجرا می‌کند.

    برخلاف هدف‌های آزمون معمولی، هر بلوک کد در لحظه با rustc به یک فایل اجرایی doctest کامپایل می‌شود. این فایل‌های اجرایی در فرایندهای جداگانه و به‌صورت موازی اجرا می‌شوند. کامپایل یک بلوک کد در واقع بخشی از تابع آزمونی است که libtest آن را کنترل می‌کند، به همین دلیل برخی گزینه‌ها مانند --jobs ممکن است اثری نداشته باشند. توجه کنید که این مدل اجرای doctestها تضمین‌شده نیست و ممکن است در آینده تغییر کند؛ از وابسته شدن به آن بپرهیزید.

    برای اطلاعات بیشتر دربارهٔ نوشتن آزمون‌های مستندات، کتاب rustdoc را ببینید.

    دایرکتوری کاری آزمون‌ها

    دایرکتوری کاری هنگام اجرای هر آزمون واحد و یکپارچگی روی دایرکتوری ریشهٔ بسته‌ای تنظیم می‌شود که آزمون به آن تعلق دارد. تنظیم دایرکتوری کاری آزمون‌ها روی دایرکتوری ریشهٔ بسته این امکان را می‌دهد که آزمون‌ها بتوانند با مسیرهای نسبی، فارغ از اینکه cargo test از کجا اجرا شده است، به‌طور مطمئن به فایل‌های بسته دسترسی داشته باشند.

    برای آزمون‌های مستندات، دایرکتوری کاری هنگام فراخوانی rustdoc روی دایرکتوری ریشهٔ workspace تنظیم می‌شود و همین دایرکتوری است که rustdoc آن را به‌عنوان دایرکتوری کامپایل هر آزمون مستندات به کار می‌برد. دایرکتوری کاری هنگام اجرای هر آزمون مستندات روی دایرکتوری ریشهٔ بسته‌ای تنظیم می‌شود که آزمون به آن تعلق دارد و از طریق گزینهٔ --test-run-directory در rustdoc کنترل می‌شود.

    گزینه‌ها

    گزینه‌های آزمون

    --no-run

    کامپایل می‌کند، اما آزمون‌ها را اجرا نمی‌کند.

    --no-fail-fast

    همهٔ آزمون‌ها را صرف‌نظر از شکست اجرا می‌کند. بدون این پرچم، Cargo پس از شکست نخستین فایل اجرایی خارج می‌شود. harness آزمون Rust همهٔ آزمون‌های درون فایل اجرایی را تا پایان اجرا می‌کند؛ این پرچم فقط بر کل فایل اجرایی اعمال می‌شود.

    انتخاب بسته

    به‌طور پیش‌فرض، وقتی هیچ گزینهٔ انتخاب بسته‌ای داده نشده باشد، بسته‌های انتخاب‌شده به فایل manifest انتخاب‌شده بستگی دارند (اگر --manifest-path داده نشده باشد، بر اساس دایرکتوری کاری فعلی). اگر manifest ریشهٔ یک workspace باشد، اعضای پیش‌فرض workspace انتخاب می‌شوند؛ در غیر این صورت فقط بسته‌ای که manifest تعریف می‌کند انتخاب خواهد شد.

    اعضای پیش‌فرض یک workspace را می‌توان با کلید workspace.default-members در manifest ریشه به‌صراحت تعیین کرد. اگر این کلید تنظیم نشده باشد، یک workspace مجازی همهٔ اعضای workspace را شامل می‌شود (معادل دادن --workspace) و یک workspace غیرمجازی فقط خود crate ریشه را شامل می‌شود.

    -p spec…
    --package spec…

    فقط بسته‌های مشخص‌شده را آزمون می‌کند. برای قالب SPEC، cargo-pkgid(1) را ببینید. این پرچم را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    --workspace

    همهٔ اعضای workspace را آزمون می‌کند.

    --all

    نام مستعار منسوخ‌شدهٔ --workspace.

    --exclude SPEC…

    بسته‌های مشخص‌شده را کنار می‌گذارد. باید همراه با گزینهٔ --workspace استفاده شود. این گزینه را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگو از نقل‌قول تکی یا دوتایی استفاده کنید.

    انتخاب هدف

    وقتی هیچ گزینهٔ انتخاب هدفی داده نشده باشد، cargo test هدف‌های زیر از بسته‌های انتخاب‌شده را می‌سازد:

    • lib — برای پیوند با فایل‌های باینری، مثال‌ها، آزمون‌های یکپارچگی و آزمون‌های مستندات به کار می‌رود
    • bins (فقط اگر آزمون‌های یکپارچگی ساخته شوند و featureهای لازم در دسترس باشند)
    • examples — برای اطمینان از کامپایل شدن آن‌ها
    • lib به‌عنوان آزمون واحد
    • bins به‌عنوان آزمون واحد
    • آزمون‌های یکپارچگی
    • آزمون‌های مستندات برای هدف lib

    رفتار پیش‌فرض را می‌توان با تنظیم پرچم test برای هدف در تنظیمات manifest تغییر داد. تنظیم test = true برای مثال‌ها باعث می‌شود مثال به‌عنوان آزمون ساخته و اجرا شود و تابع main مثال با harness مربوط به libtest جایگزین گردد. اگر نمی‌خواهید تابع main جایگزین شود، harness = false را هم اضافه کنید؛ در این صورت مثال همان‌گونه که هست ساخته و اجرا می‌شود.

    تنظیم test = false برای هدف‌ها باعث می‌شود آن‌ها به‌طور پیش‌فرض آزمون نشوند. گزینه‌های انتخاب هدف که هدف را با نام می‌گیرند (مانند --example foo) پرچم test را نادیده می‌گیرند و همیشه هدف داده‌شده را آزمون می‌کنند.

    آزمون‌های مستندات کتابخانه‌ها را می‌توان با تنظیم doctest = false برای کتابخانه در manifest غیرفعال کرد.

    برای اطلاعات بیشتر دربارهٔ تنظیمات هر هدف، پیکربندی یک هدف را ببینید.

    اگر یک آزمون یکپارچگی یا benchmark برای آزمون انتخاب شده باشد، هدف‌های باینری به‌طور خودکار ساخته می‌شوند. این کار به آزمون یکپارچگی اجازه می‌دهد فایل اجرایی را اجرا کند تا رفتار آن را بسنجد و آزمون کند. هنگام ساخت و اجرای آزمون یکپارچگی، متغیر محیطی CARGO_BIN_EXE_<name> تنظیم می‌شود تا آزمون بتواند با ماکروی env یا تابع var مسیر فایل اجرایی را پیدا کند.

    با دادن پرچم‌های انتخاب هدف، فقط هدف‌های مشخص‌شده آزمون می‌شوند.

    توجه کنید که گزینه‌های --bin، --example، --test و --bench نیز از الگوهای glob رایج یونیکس مانند *، ? و [] پشتیبانی می‌کنند. با این حال، برای اینکه shell شما پیش از رسیدن الگوها به Cargo به‌طور ناخواسته آن‌ها را باز نکند، باید دور هر الگوی glob از نقل‌قول تکی یا دوتایی استفاده کنید.

    --lib

    کتابخانهٔ بسته را آزمون می‌کند.

    --bin name…

    فایل باینری مشخص‌شده را آزمون می‌کند. این پرچم را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --bins

    همهٔ هدف‌های باینری را آزمون می‌کند.

    --example name…

    مثال مشخص‌شده را آزمون می‌کند. این پرچم را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --examples

    همهٔ هدف‌های مثال را آزمون می‌کند.

    --test name…

    آزمون یکپارچگی مشخص‌شده را اجرا می‌کند. این پرچم را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --tests

    همهٔ هدف‌هایی را که پرچم manifest به نام test = true برایشان تنظیم شده است آزمون می‌کند. به‌طور پیش‌فرض این شامل کتابخانه و فایل‌های باینری ساخته‌شده به‌عنوان آزمون واحد، و آزمون‌های یکپارچگی است. توجه کنید که این کار وابستگی‌های لازم را نیز می‌سازد، بنابراین هدف lib ممکن است دو بار ساخته شود (یک بار به‌عنوان آزمون واحد و یک بار به‌عنوان وابستگی فایل‌های باینری، آزمون‌های یکپارچگی و غیره). با تنظیم پرچم test در تنظیمات manifest مربوط به هدف، می‌توان هدف‌ها را فعال یا غیرفعال کرد.

    --bench name…

    benchmark مشخص‌شده را آزمون می‌کند. این پرچم را می‌توان چندین بار مشخص کرد و از الگوهای glob رایج یونیکس پشتیبانی می‌کند.

    --benches

    همهٔ هدف‌هایی را که پرچم manifest به نام bench = true برایشان تنظیم شده است آزمون می‌کند. به‌طور پیش‌فرض این شامل کتابخانه و فایل‌های باینری ساخته‌شده به‌عنوان benchmark، و هدف‌های bench است. توجه کنید که این کار وابستگی‌های لازم را نیز می‌سازد، بنابراین هدف lib ممکن است دو بار ساخته شود (یک بار به‌عنوان benchmark و یک بار به‌عنوان وابستگی فایل‌های باینری، benchmarkها و غیره). با تنظیم پرچم bench در تنظیمات manifest مربوط به هدف، می‌توان هدف‌ها را فعال یا غیرفعال کرد.

    --all-targets

    همهٔ هدف‌ها را آزمون می‌کند. این معادل مشخص کردن --lib --bins --tests --benches --examples است.

    --doc

    فقط مستندات کتابخانه را آزمون می‌کند. این گزینه را نمی‌توان با سایر گزینه‌های هدف ترکیب کرد.

    انتخاب feature

    پرچم‌های feature به شما امکان می‌دهند کنترل کنید کدام featureها فعال باشند. وقتی هیچ گزینهٔ featureای داده نشده باشد، feature به نام default برای هر بستهٔ انتخاب‌شده فعال می‌شود.

    برای جزئیات بیشتر، مستندات featureها را ببینید.

    -F features
    --features features

    فهرستی از featureهای قابل فعال‌سازی که با فاصله یا کاما جدا شده است. featureهای اعضای workspace را می‌توان با نحو package-name/feature-name فعال کرد. این گزینه را می‌توان چندین بار مشخص کرد که همهٔ featureهای مشخص‌شده را فعال می‌کند.

    --all-features

    همهٔ featureهای موجود همهٔ بسته‌های انتخاب‌شده را فعال می‌کند.

    --no-default-features

    feature به نام default بسته‌های انتخاب‌شده را فعال نمی‌کند.

    گزینه‌های کامپایل

    --target tuple

    برای معماری هدف مشخص‌شده آزمون می‌کند. این پرچم را می‌توان چندین بار مشخص کرد. پیش‌فرض، معماری میزبان است. قالب کلی tuple به این صورت است: <arch><sub>-<vendor>-<sys>-<abi>.

    مقادیر ممکن:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple" که در داخل با هدف میزبان جایگزین می‌شود. این مقدار به‌ویژه وقتی مفید است که چند crate را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان خود را به‌عنوان هدف مشخص کنید (برای مثال، یک xtask در پروژه‌ای مشترک که چند میزبان ممکن است روی آن کار کنند).
    • مسیر یک مشخصهٔ هدف سفارشی. برای اطلاعات بیشتر، مسیر جست‌وجوی هدف سفارشی را ببینید.

    این مورد را می‌توان با مقدار پیکربندی build.target نیز مشخص کرد.

    توجه کنید که مشخص کردن این پرچم باعث می‌شود Cargo در حالتی متفاوت اجرا شود که در آن مصنوعات هدف در دایرکتوری جداگانه‌ای قرار می‌گیرند. برای جزئیات بیشتر، مستندات حافظهٔ نهان ساخت را ببینید.

    -r
    --release

    مصنوعات بهینه‌شده را با پروفایل release آزمون می‌کند. برای انتخاب یک پروفایل مشخص با نام، گزینهٔ --profile را نیز ببینید.

    --profile name

    با پروفایل داده‌شده آزمون می‌کند. برای جزئیات بیشتر دربارهٔ پروفایل‌ها، مرجع را ببینید.

    --timings

    اطلاعاتی دربارهٔ مدت زمان هر کامپایل خروجی می‌دهد و اطلاعات هم‌زمانی را در طول زمان ردیابی می‌کند.

    در پایان ساخت، فایلی به نام cargo-timing.html در دایرکتوری target/cargo-timings نوشته می‌شود. اگر بخواهید اجرای قبلی را ببینید، یک گزارش اضافی هم با مهر زمانی در نام فایلش نوشته می‌شود. این گزارش‌ها فقط برای مصرف انسانی مناسب‌اند و داده‌های زمان‌بندی قابل‌خواندن برای ماشین ارائه نمی‌دهند.

    گزینه‌های خروجی

    --target-dir directory

    دایرکتوری همهٔ artifactهای تولیدشده و فایل‌های میانی. همچنین می‌توان آن را با متغیر محیطی CARGO_TARGET_DIR یا با مقدار پیکربندی build.target-dir مشخص کرد. پیش‌فرض آن target در ریشهٔ workspace است.

    گزینه‌های نمایش

    به‌طور پیش‌فرض harness آزمون Rust خروجی اجرای آزمون‌ها را پنهان می‌کند تا نتایج خوانا بمانند. با دادن --no-capture به فایل‌های اجرایی آزمون می‌توان خروجی آزمون‌ها را بازیابی کرد (مثلاً برای اشکال‌زدایی):

    cargo test -- --no-capture
    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با term.quiet مقدار پیکربندی مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با term.color مقدار پیکربندی مشخص کرد.

    --message-format fmt

    قالب خروجی پیام‌های تشخیصی. می‌توان آن را چندین بار مشخص کرد و از مقادیر جداشده با کاما تشکیل می‌شود. مقادیر معتبر:

    • human (پیش‌فرض): با قالب متنی قابل‌خواندن برای انسان نمایش می‌دهد. با short و json تعارض دارد.
    • short: پیام‌های متنی کوتاه‌تر و قابل‌خواندن برای انسان صادر می‌کند. با human و json تعارض دارد.
    • json: پیام‌های JSON را در stdout صادر می‌کند. برای جزئیات بیشتر مرجع را ببینید. با human و short تعارض دارد.
    • json-diagnostic-short: تضمین می‌کند فیلد rendered پیام‌های JSON شامل نمایش «کوتاه» rustc باشد. با human یا short قابل استفاده نیست.
    • json-diagnostic-rendered-ansi: تضمین می‌کند فیلد rendered پیام‌های JSON شامل کدهای رنگ ANSI تعبیه‌شده باشد تا طرح رنگ پیش‌فرض rustc رعایت شود. با human یا short قابل استفاده نیست.
    • json-render-diagnostics: به Cargo دستور می‌دهد تشخیص‌های rustc را در پیام‌های JSON چاپ‌شده نگنجاند، بلکه خود Cargo تشخیص‌های JSON دریافتی از rustc را نمایش دهد. تشخیص‌های JSON خود Cargo و سایر تشخیص‌هایی که از rustc می‌آیند همچنان صادر می‌شوند. با human یا short قابل استفاده نیست.

    گزینه‌های manifest

    --manifest-path path

    مسیر فایل Cargo.toml. به‌طور پیش‌فرض، Cargo فایل Cargo.toml را در دایرکتوری فعلی یا هر دایرکتوری والد جست‌وجو می‌کند.

    --ignore-rust-version

    مشخصهٔ rust-version را در بسته‌ها نادیده می‌گیرد.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از آفلاین شدن، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.

    گزینه‌های متفرقه

    آرگومان --jobs بر ساخت فایل اجرایی آزمون اثر می‌گذارد، اما بر تعداد نخ‌هایی که هنگام اجرای آزمون‌ها به کار می‌روند اثری ندارد. harness آزمون Rust گزینه‌ای برای کنترل تعداد نخ‌های مورد استفاده دارد:

    cargo test -j 2 -- --test-threads=2
    -j N
    --jobs N

    تعداد jobهای موازی برای اجرا. با مقدار پیکربندی build.jobs نیز می‌توان آن را مشخص کرد. پیش‌فرض برابر تعداد CPUهای منطقی است. اگر منفی باشد، حداکثر تعداد jobهای موازی را برابر تعداد CPUهای منطقی به‌اضافهٔ مقدار داده‌شده قرار می‌دهد. اگر رشتهٔ default داده شود، مقدار را به پیش‌فرض برمی‌گرداند. نباید ۰ باشد.

    --future-incompat-report

    برای هر هشدار ناسازگاری آینده که هنگام اجرای این فرمان تولید شده باشد، یک گزارش future-incompat نمایش می‌دهد.

    به cargo-report(1) مراجعه کنید.

    اگرچه cargo test شامل کامپایل است، پرچم --keep-going را ارائه نمی‌کند. از --no-fail-fast استفاده کنید تا تا حد امکان آزمون‌های بیشتری بدون توقف در نخستین شکست اجرا شوند. برای «کامپایل» تا حد امکان آزمون‌های بیشتر، از --tests استفاده کنید تا فایل‌های اجرایی آزمون جداگانه ساخته شوند. برای مثال:

    cargo build --tests --keep-going
cargo test --tests --no-fail-fast

    متغیرهای محیطی

    برای جزئیات متغیرهای محیطی که Cargo می‌خواند، مرجع را ببینید.

    وضعیت خروج

    • 0: Cargo موفق بود.
    • 101: Cargo نتوانست کار را به پایان برساند.

    مثال‌ها

    1. فقط آزمون‌هایی را اجرا کنید که نامشان با یک رشتهٔ فیلتر مطابقت دارد:

      cargo test

    2. فقط یک آزمون مشخص را درون یک آزمون یکپارچگی مشخص اجرا کنید:

      cargo test name_filter

    3. اجرای فقط یک آزمون مشخص درون یک آزمون یکپارچگی مشخص:

      cargo test --test int_test_name -- modname::test_name
