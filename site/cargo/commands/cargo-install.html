    cargo-install(1)

    نام

    cargo-install — ساخت و نصب یک باینری Rust

    خلاصه

    cargo install [options] crate[@version]…
    cargo install [options] --path path
    cargo install [options] --git url [crate…]
    cargo install [options] --list

    توضیحات

    این فرمان مجموعهٔ محلی crateهای باینریِ نصب‌شدهٔ Cargo را مدیریت می‌کند. فقط بسته‌هایی که هدف‌های اجرایی [[bin]] یا [[example]] دارند قابل نصب‌اند و همهٔ فایل‌های اجرایی در پوشهٔ bin ریشهٔ نصب نصب می‌شوند. به‌طور پیش‌فرض فقط باینری‌ها نصب می‌شوند، نه مثال‌ها.

    ریشهٔ نصب به ترتیب اولویت زیر تعیین می‌شود:

    • گزینهٔ --root
    • متغیر محیطی CARGO_INSTALL_ROOT
    • مقدار پیکربندی install.root در Cargo
    • متغیر محیطی CARGO_HOME
    • $HOME/.cargo

    منابع متعددی وجود دارند که یک crate را می‌توان از آن‌ها نصب کرد. محل منبع پیش‌فرض crates.io است، اما پرچم‌های --git، --path و --registry می‌توانند این منبع را تغییر دهند. اگر منبع بیش از یک بسته داشته باشد (مانند crates.io یا یک مخزن git با چند crate)، آرگومان crate لازم است تا مشخص کند کدام crate باید نصب شود.

    crateهای crates.io می‌توانند به‌صورت اختیاری با پرچم‌های --version نسخه‌ای را که می‌خواهند نصب شود مشخص کنند، و به همین ترتیب بسته‌های مخزن‌های git می‌توانند به‌صورت اختیاری شاخه، برچسب (tag) یا revisionی را که باید نصب شود مشخص کنند. اگر یک crate چند باینری داشته باشد، آرگومان --bin می‌تواند فقط یکی از آن‌ها را به‌طور انتخابی نصب کند، و اگر ترجیح می‌دهید مثال‌ها را نصب کنید، از آرگومان --example هم می‌توان استفاده کرد.

    اگر بسته از قبل نصب شده باشد، Cargo در صورتی آن را دوباره نصب می‌کند که نسخهٔ نصب‌شده به‌روز به نظر نرسد. اگر هر یک از مقادیر زیر تغییر کند، Cargo بسته را دوباره نصب می‌کند:

    • نسخه و منبع بسته.
    • مجموعهٔ نام‌های باینری نصب‌شده.
    • featureهای انتخاب‌شده.
    • profile (--profile).
    • هدف (--target).

    نصب با --path همیشه ساخت و نصب را انجام می‌دهد، مگر اینکه باینری‌های متعارضی از بستهٔ دیگری وجود داشته باشند. می‌توان از پرچم --force استفاده کرد تا Cargo را وادار کرد همیشه بسته را دوباره نصب کند.

    اگر منبع crates.io یا --git باشد، crate به‌طور پیش‌فرض در یک دایرکتوری هدف موقت ساخته می‌شود. برای اجتناب از این کار، می‌توان دایرکتوری هدف را با تنظیم متغیر محیطی CARGO_TARGET_DIR روی یک مسیر مشخص کرد. این کار به‌ویژه می‌تواند برای نگهداری artifactهای ساخت در حافظهٔ نهان در سیستم‌های یکپارچه‌سازی پیوسته مفید باشد.

    کار با Lockfile

    به‌طور پیش‌فرض، Cargo در صورت وجود از فایل Cargo.lock همراه بسته استفاده می‌کند. این کار تضمین می‌کند فایل اجرایی نصب‌شده از نسخه‌های وابستگی‌هایی استفاده کند که هنگام انتشار بسته انتخاب شده بودند. اگر هیچ lockfileای در دسترس نباشد، از جمله برای بسته‌هایی که با نسخه‌های Cargo پیش از 1.37 منتشر شده‌اند، Cargo وابستگی‌ها را به‌طور عادی حل‌وفصل می‌کند.

    پرچم --locked در حال حاضر حل‌وفصل وابستگی‌ها را برای cargo install تغییر نمی‌دهد. اگر هیچ Cargo.lockای در دسترس نباشد، استفاده از --locked یک هشدار صادر می‌کند.

    کشف پیکربندی

    این فرمان در سطح سیستم یا کاربر عمل می‌کند، نه در سطح پروژه. یعنی کشف پیکربندی محلی نادیده گرفته می‌شود. در عوض، کشف پیکربندی از $CARGO_HOME/config.toml آغاز می‌شود. اگر بسته با --path $PATH نصب شود، پیکربندی محلی استفاده خواهد شد و کشف از $PATH/.cargo/config.toml آغاز می‌شود.

    گزینه‌ها

    گزینه‌های نصب

    --vers version
    --version version

    نسخه‌ای را که باید نصب شود مشخص می‌کند. این می‌تواند یک نیازمندی نسخه مانند ~1.2 باشد، تا Cargo جدیدترین نسخه را از نیازمندی داده‌شده انتخاب کند. اگر نسخه عملگر نیازمندی (مانند ^ یا ~) نداشته باشد، باید به شکل MAJOR.MINOR.PATCH باشد و دقیقاً همان نسخه را نصب می‌کند؛ با آن مانند نیازمندی caret که برای وابستگی‌های Cargo به کار می‌رود، رفتار نمی‌شود.

    --git url

    نشانی Git که crate مشخص‌شده از آن نصب می‌شود.

    --branch branch

    شاخه‌ای که هنگام نصب از git استفاده می‌شود.

    --tag tag

    برچسبی (tag) که هنگام نصب از git استفاده می‌شود.

    --rev sha

    کامیت مشخصی که هنگام نصب از git استفاده می‌شود.

    --path path

    مسیر سیستم فایل به crate محلی که از آن نصب می‌شود.

    --list

    همهٔ بسته‌های نصب‌شده و نسخه‌های آن‌ها را فهرست می‌کند.

    -n
    --dry-run

    (ناپایدار) همهٔ بررسی‌ها را بدون نصب انجام می‌دهد.

    -f
    --force

    بازنویسی crateها یا باینری‌های موجود را اجباری می‌کند. می‌توان از آن استفاده کرد اگر بسته‌ای باینری‌ای با همان نام بستهٔ دیگری نصب کرده باشد. همچنین وقتی چیزی در سیستم تغییر کرده که می‌خواهید با آن دوباره بسازید، مانند نسخهٔ جدیدتر rustc، مفید است.

    --no-track

    به‌طور پیش‌فرض، Cargo بسته‌های نصب‌شده را با یک فایل metadata که در دایرکتوری ریشهٔ نصب ذخیره می‌شود ردیابی می‌کند. این پرچم به Cargo می‌گوید آن فایل را استفاده یا ایجاد نکند. با این پرچم، Cargo از بازنویسی هر فایل موجود خودداری می‌کند، مگر اینکه پرچم --force استفاده شود. این پرچم همچنین توانایی Cargo را برای محافظت در برابر اجراهای هم‌زمان متعدد Cargo که همزمان نصب می‌کنند غیرفعال می‌کند.

    --bin name…

    فقط باینری مشخص‌شده را نصب می‌کند.

    --bins

    همهٔ باینری‌ها را نصب می‌کند. این رفتار پیش‌فرض است.

    --example name…

    فقط مثال مشخص‌شده را نصب می‌کند.

    --examples

    همهٔ مثال‌ها را نصب می‌کند.

    --root dir

    دایرکتوری‌ای که بسته‌ها در آن نصب می‌شوند.

    --registry registry

    نام رجیستری مورد استفاده. نام رجیستری‌ها در فایل‌های پیکربندی Cargo تعریف می‌شوند. اگر مشخص نشود، از رجیستری پیش‌فرض استفاده می‌شود که با کلید پیکربندی registry.default تعریف می‌شود و پیش‌فرض آن crates-io است.

    --index index

    نشانی URL ایندکس رجیستری مورد استفاده.

    انتخاب feature

    پرچم‌های feature به شما امکان می‌دهند کنترل کنید کدام featureها فعال باشند. وقتی هیچ گزینهٔ featureای داده نشده باشد، feature به نام default برای هر بستهٔ انتخاب‌شده فعال می‌شود.

    برای جزئیات بیشتر، مستندات featureها را ببینید.

    -F features
    --features features

    فهرستی از featureهای قابل فعال‌سازی که با فاصله یا کاما جدا شده است. featureهای اعضای workspace را می‌توان با نحو package-name/feature-name فعال کرد. این گزینه را می‌توان چندین بار مشخص کرد که همهٔ featureهای مشخص‌شده را فعال می‌کند.

    --all-features

    همهٔ featureهای موجود همهٔ بسته‌های انتخاب‌شده را فعال می‌کند.

    --no-default-features

    feature به نام default بسته‌های انتخاب‌شده را فعال نمی‌کند.

    گزینه‌های کامپایل

    --target tuple

    برای معماری هدف مشخص‌شده نصب می‌کند. پیش‌فرض معماری میزبان (host) است. قالب کلی tuple به این صورت است: <arch><sub>-<vendor>-<sys>-<abi>.

    مقادیر ممکن:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple" که به‌طور داخلی با هدف میزبان جایگزین می‌شود. این مورد به‌ویژه وقتی مفید است که برخی crateها را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان خود را به‌عنوان هدف مشخص کنید (برای مثال، یک xtask در پروژه‌ای مشترک که ممکن است میزبان‌های بسیاری روی آن کار کنند).
    • مسیر یک مشخصهٔ هدف سفارشی. برای اطلاعات بیشتر مسیر جست‌وجوی هدف سفارشی را ببینید.

    این گزینه را می‌توان با مقدار پیکربندی build.target نیز مشخص کرد.

    توجه کنید که مشخص کردن این پرچم باعث می‌شود Cargo در حالتی متفاوت اجرا شود که در آن artifactهای هدف در یک دایرکتوری جداگانه قرار می‌گیرند. برای جزئیات بیشتر، مستندات حافظهٔ نهان ساخت را ببینید.

    --target-dir directory

    دایرکتوری همهٔ artifactهای تولیدشده و فایل‌های میانی. همچنین می‌توان آن را با متغیر محیطی CARGO_TARGET_DIR یا با مقدار پیکربندی build.target-dir مشخص کرد. پیش‌فرض آن یک پوشهٔ موقت جدید است که در دایرکتوری موقت پلتفرم قرار دارد.

    هنگام استفاده از --path، به‌طور پیش‌فرض از دایرکتوری target در workspace مربوط به crate محلی استفاده می‌شود، مگر اینکه --target-dir مشخص شده باشد.

    --debug

    به‌جای profile به نام release، با profile به نام debug می‌سازد. همچنین برای انتخاب یک profile مشخص با نام، گزینهٔ --profile را ببینید.

    --profile name

    با profile داده‌شده نصب می‌کند. برای جزئیات بیشتر دربارهٔ profileها مرجع را ببینید.

    --timings

    اطلاعاتی دربارهٔ مدت زمان هر کامپایل خروجی می‌دهد و اطلاعات هم‌زمانی را در طول زمان ردیابی می‌کند.

    در پایان ساخت، فایلی به نام cargo-timing.html در دایرکتوری target/cargo-timings نوشته می‌شود. اگر بخواهید اجرای قبلی را ببینید، یک گزارش اضافی هم با مهر زمانی در نام فایلش نوشته می‌شود. این گزارش‌ها فقط برای مصرف انسانی مناسب‌اند و داده‌های زمان‌بندی قابل‌خواندن برای ماشین ارائه نمی‌دهند.

    گزینه‌های manifest

    --ignore-rust-version

    مشخصهٔ rust-version را در بسته‌ها نادیده می‌گیرد.

    --locked

    تأیید می‌کند که دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده شوند که هنگام تولید اولیهٔ فایل Cargo.lock موجود به کار رفته بودند. Cargo در هر یک از دو حالت زیر با خطا خارج می‌شود:

    • فایل lock وجود نداشته باشد.
    • Cargo به‌دلیل حل‌وفصل متفاوت وابستگی‌ها بخواهد فایل lock را تغییر دهد.

    می‌توان از آن در محیط‌هایی استفاده کرد که ساخت‌های قطعی (deterministic) موردنیاز است، مانند pipelineهای CI.

    --offline

    Cargo را از دسترسی به شبکه به هر دلیلی بازمی‌دارد. بدون این پرچم، اگر Cargo نیاز به دسترسی به شبکه داشته باشد و شبکه در دسترس نباشد، با خطا متوقف می‌شود. با این پرچم، Cargo در صورت امکان بدون شبکه ادامه می‌دهد.

    توجه داشته باشید که این ممکن است به حل‌وفصل وابستگی‌هایی متفاوت از حالت آنلاین منجر شود. Cargo خود را به crateهایی محدود می‌کند که به‌صورت محلی دانلود شده‌اند، حتی اگر طبق نسخهٔ محلی index نسخهٔ جدیدتری وجود داشته باشد. برای دانلود وابستگی‌ها پیش از آفلاین شدن، فرمان cargo-fetch(1) را ببینید.

    همچنین می‌توان آن را با مقدار پیکربندی net.offline مشخص کرد.

    --frozen

    معادل مشخص کردن همزمان --locked و --offline است.

    گزینه‌های متفرقه

    -j N
    --jobs N

    تعداد jobهای موازی برای اجرا. همچنین می‌توان آن را با مقدار پیکربندی build.jobs مشخص کرد. پیش‌فرض تعداد CPUهای منطقی است. اگر منفی باشد، حداکثر تعداد jobهای موازی را برابر تعداد CPUهای منطقی به‌علاوهٔ مقدار داده‌شده قرار می‌دهد. اگر رشتهٔ default داده شود، مقدار را به پیش‌فرض بازمی‌گرداند. نباید 0 باشد.

    --keep-going

    تا جای ممکن crateهای بیشتری از گراف وابستگی را می‌سازد، به‌جای آنکه با اولین crateی که ساخته نمی‌شود، ساخت را متوقف کند.

    برای مثال، اگر بستهٔ فعلی به وابستگی‌های fails و works وابسته باشد و یکی از آن‌ها ساخته نشود، cargo install -j1 ممکن است crateی را که موفق می‌شود بسازد یا نسازد (بسته به اینکه Cargo کدام یک از دو ساخت را زودتر اجرا کند)، در حالی که cargo install -j1 --keep-going قطعاً هر دو ساخت را اجرا می‌کند، حتی اگر ساختی که اول اجرا شده شکست بخورد.

    گزینه‌های نمایش

    -v
    --verbose

    از خروجی مفصل استفاده می‌کند. برای خروجی «بسیار مفصل» که شامل خروجی اضافی مانند هشدارهای وابستگی‌ها و خروجی build script است، می‌توان آن را دو بار مشخص کرد. همچنین می‌توان آن را با مقدار پیکربندی term.verbose مشخص کرد.

    -q
    --quiet

    پیام‌های log مربوط به cargo را چاپ نمی‌کند. همچنین می‌توان آن را با مقدار پیکربندی term.quiet مشخص کرد.

    --color when

    تعیین می‌کند خروجی رنگی چه زمانی استفاده شود. مقادیر معتبر:

    • auto (پیش‌فرض): به‌طور خودکار تشخیص می‌دهد که آیا ترمینال از رنگ پشتیبانی می‌کند.
    • always: همیشه رنگ‌ها را نمایش می‌دهد.
    • never: هرگز رنگ‌ها را نمایش نمی‌دهد.

    همچنین می‌توان آن را با مقدار پیکربندی term.color مشخص کرد.

    --message-format fmt

    قالب خروجی پیام‌های تشخیصی. می‌توان آن را چندین بار مشخص کرد و از مقادیر جداشده با کاما تشکیل می‌شود. مقادیر معتبر:

    • human (پیش‌فرض): با قالب متنی قابل‌خواندن برای انسان نمایش می‌دهد. با short و json تعارض دارد.
    • short: پیام‌های متنی کوتاه‌تر و قابل‌خواندن برای انسان صادر می‌کند. با human و json تعارض دارد.
    • json: پیام‌های JSON را در stdout صادر می‌کند. برای جزئیات بیشتر مرجع را ببینید. با human و short تعارض دارد.
    • json-diagnostic-short: تضمین می‌کند فیلد rendered پیام‌های JSON شامل نمایش «کوتاه» rustc باشد. با human یا short قابل استفاده نیست.
    • json-diagnostic-rendered-ansi: تضمین می‌کند فیلد rendered پیام‌های JSON شامل کدهای رنگ ANSI تعبیه‌شده باشد تا طرح رنگ پیش‌فرض rustc رعایت شود. با human یا short قابل استفاده نیست.
    • json-render-diagnostics: به Cargo دستور می‌دهد تشخیص‌های rustc را در پیام‌های JSON چاپ‌شده نگنجاند، بلکه خود Cargo تشخیص‌های JSON دریافتی از rustc را نمایش دهد. تشخیص‌های JSON خود Cargo و سایر تشخیص‌هایی که از rustc می‌آیند همچنان صادر می‌شوند. با human یا short قابل استفاده نیست.

    گزینه‌های رایج

    +toolchain

    اگر Cargo با rustup نصب شده باشد و اولین آرگومان cargo با + شروع شود، به‌عنوان نام یک toolchain در rustup تفسیر می‌شود (مانند +stable یا +nightly). برای اطلاعات بیشتر دربارهٔ نحوهٔ کار override کردن toolchain، به مستندات rustup مراجعه کنید.

    --config KEY=VALUE یا PATH

    یک مقدار پیکربندی Cargo را بازنویسی می‌کند. آرگومان باید به نحو TOML و به شکل KEY=VALUE باشد، یا مسیر یک فایل پیکربندی اضافی داده شود. این پرچم را می‌توان چندین بار مشخص کرد. برای اطلاعات بیشتر بخش بازنویسی از خط فرمان را ببینید.

    -C PATH

    پیش از اجرای هر عملیات مشخص‌شده، دایرکتوری کاری فعلی را تغییر می‌دهد. این بر مواردی مانند محل پیش‌فرض جست‌وجوی manifest پروژه (Cargo.toml) توسط cargo و نیز دایرکتوری‌هایی که برای یافتن .cargo/config.toml جست‌وجو می‌شوند اثر می‌گذارد. این گزینه باید پیش از نام فرمان بیاید، برای مثال cargo -C path/to/my-project build.

    این گزینه فقط در کانال nightly در دسترس است و برای فعال شدن به پرچم -Z unstable-options نیاز دارد (به #10098 مراجعه کنید).

    -h
    --help

    اطلاعات راهنما را چاپ می‌کند.

    -Z flag

    پرچم‌های ناپایدار (فقط nightly) برای Cargo. برای جزئیات cargo -Z help را اجرا کنید.

    متغیرهای محیطی

    برای جزئیات متغیرهای محیطی که Cargo می‌خواند، مرجع را ببینید.

    وضعیت خروج

    • 0: Cargo موفق بود.
    • 101: Cargo نتوانست کار را به پایان برساند.

    مثال‌ها

    1. یک بسته را از crates.io نصب یا به‌روزرسانی کنید:

      cargo install ripgrep

    2. بستهٔ دایرکتوری فعلی را نصب یا دوباره نصب کنید:

      cargo install --path .

    3. فهرست بسته‌های نصب‌شده را ببینید:

      cargo install --list
