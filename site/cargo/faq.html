    پرسش‌های متداول

    آیا برنامه این است که از GitHub به‌عنوان مخزن بسته استفاده شود؟

    خیر. برنامهٔ Cargo این است که از crates.io استفاده کند، همان‌طور که npm و Rubygems از npmjs.com و rubygems.org استفاده می‌کنند.

    ما قصد داریم برای همیشه از مخزن‌های git به‌عنوان منبع بسته‌ها پشتیبانی کنیم، زیرا می‌توان از آن‌ها برای توسعهٔ اولیه و وصله‌های موقت استفاده کرد، حتی وقتی افراد از registry به‌عنوان منبع اصلی بسته‌ها بهره می‌گیرند.

    چرا crates.io را ساختید و از GitHub به‌عنوان registry استفاده نکردید؟

    ما فکر می‌کنیم پشتیبانی از چند روش برای دانلود بسته‌ها بسیار مهم است، از جمله دانلود از GitHub و کپی کردن بسته‌ها درون خود بستهٔ شما.

    با این حال، فکر می‌کنیم crates.io مزایای مهم متعددی دارد و احتمالاً به روش اصلی دانلود بسته‌ها در Cargo تبدیل خواهد شد.

    برای نمونه، هم npm در Node.js و هم bundler در Ruby هم از یک مدل registry مرکزی و هم از یک مدل مبتنی بر Git پشتیبانی می‌کنند، و در آن اکوسیستم‌ها بیشتر بسته‌ها از طریق registry دانلود می‌شوند، در حالی که اقلیت مهمی از بسته‌ها از بسته‌های مبتنی بر git استفاده می‌کنند.

    برخی از مزایایی که یک registry مرکزی را در زبان‌های دیگر محبوب کرده‌اند عبارت‌اند از:

    • قابلیت کشف. یک registry مرکزی جای آسانی برای جست‌وجوی بسته‌های موجود فراهم می‌کند. همراه با برچسب‌گذاری، این امکان را هم برای registry فراهم می‌کند که اطلاعاتی در سطح کل اکوسیستم ارائه دهد، مانند فهرست محبوب‌ترین بسته‌ها یا بسته‌هایی که بیشترین وابستگی به آن‌ها وجود دارد.
    • سرعت. یک registry مرکزی این امکان را فراهم می‌کند که فقط فرادادهٔ بسته‌ها به‌سرعت و به‌طور کارآمد دریافت شود و سپس فقط بستهٔ منتشرشده به‌طور کارآمد دانلود شود، نه سایر حجم‌های اضافی‌ای که اتفاقاً در مخزن وجود دارند. این‌ها روی هم بهبود چشمگیری در سرعت تحلیل وابستگی‌ها و دریافت آن‌ها ایجاد می‌کند. وقتی گراف وابستگی‌ها بزرگ می‌شود، دانلود همهٔ مخزن‌های git به‌سرعت کار را کند می‌کند. همچنین به یاد داشته باشید که همه اینترنت پرسرعت و با تأخیر کم ندارند.

    آیا Cargo با کد C (یا زبان‌های دیگر) کار می‌کند؟

    بله!

    Cargo کامپایل کد Rust را بر عهده دارد، اما می‌دانیم که بسیاری از بسته‌های Rust با کد C لینک می‌شوند. همچنین می‌دانیم که دهه‌ها ابزار پیرامون کامپایل زبان‌هایی غیر از Rust ساخته شده است.

    راه‌حل ما: Cargo به یک بسته اجازه می‌دهد یک اسکریپت مشخص کند (نوشته‌شده با Rust) که پیش از فراخوانی rustc اجرا شود. از Rust برای پیاده‌سازی پیکربندی‌های وابسته به پلتفرم و جدا کردن عملکردهای ساخت مشترک میان بسته‌ها بهره گرفته می‌شود.

    آیا می‌توان Cargo را درون make (یا ninja یا …) استفاده کرد؟

    بله. اگرچه قصد ما این است که Cargo به‌عنوان یک روش مستقل برای کامپایل بسته‌های Rust در سطح بالا مفید باشد، می‌دانیم که برخی افراد می‌خواهند Cargo را از ابزارهای ساخت دیگر فراخوانی کنند.

    ما Cargo را طوری طراحی کرده‌ایم که در این زمینه‌ها خوب کار کند و به مواردی مانند کدهای خروج و حالت‌های خروجی قابل‌خواندن برای ماشین توجه کرده‌ایم. هنوز در این زمینه‌ها کارهایی داریم که باید انجام دهیم، اما استفاده از Cargo در بستر اسکریپت‌های رایج چیزی است که از ابتدا برایش طراحی کرده‌ایم و همچنان در اولویت خواهیم داشت.

    آیا Cargo بسته‌های چندپلتفرمی یا کراس‌کامپایل را پشتیبانی می‌کند؟

    خود Rust امکاناتی برای پیکربندی بخش‌هایی از کد بر اساس پلتفرم فراهم می‌کند. Cargo نیز از وابستگی‌های مخصوص پلتفرم پشتیبانی می‌کند و قصد داریم در آینده پیکربندی‌های بیشتری برای هر پلتفرم را در Cargo.toml پشتیبانی کنیم.

    در بلندمدت، در حال بررسی راه‌هایی هستیم تا بتوان بسته‌ها را با Cargo به‌راحتی کراس‌کامپایل کرد.

    آیا Cargo از محیط‌هایی مانند production یا test پشتیبانی می‌کند؟

    ما با استفاده از profileها از محیط‌ها پشتیبانی می‌کنیم تا این موارد را ممکن کنیم:

    • پرچم‌های مخصوص هر محیط (مانند -g --opt-level=0 برای توسعه و --opt-level=3 برای محیط production).
    • وابستگی‌های مخصوص هر محیط (مانند hamcrest برای assertionهای آزمون).
    • #[cfg] مخصوص هر محیط
    • یک دستور cargo test

    آیا Cargo روی Windows کار می‌کند؟

    بله!

    همهٔ commitهای Cargo باید مجموعه آزمون‌های محلی را روی Windows با موفقیت بگذرانند. اگر هنگام اجرا روی Windows با مشکلی روبه‌رو شدید، آن را یک باگ می‌دانیم، پس لطفاً یک issue ثبت کنید.

    چرا Cargo.lock در کنترل نسخه باشد؟

    اگرچه cargo new به‌طور پیش‌فرض Cargo.lock را در کنترل نسخه پیگیری می‌کند، اینکه شما چنین کنید یا نه به نیازهای بستهٔ شما بستگی دارد.

    هدف lockfile به نام Cargo.lock این است که وضعیت جهان را در زمان یک ساخت موفق توصیف کند. Cargo از lockfile برای فراهم کردن ساخت‌های قطعی (deterministic) در زمان‌های مختلف و روی سیستم‌های مختلف استفاده می‌کند، به این ترتیب که اطمینان می‌دهد دقیقاً همان وابستگی‌ها و نسخه‌هایی استفاده می‌شوند که هنگام تولید اولیهٔ فایل Cargo.lock استفاده شده بودند.

    ساخت‌های قطعی به موارد زیر کمک می‌کنند

    • اجرای git bisect برای یافتن علت اصلی یک باگ
    • اطمینان از اینکه CI فقط به‌دلیل commitهای جدید شکست می‌خورد و نه عوامل بیرونی
    • کاهش سردرگمی وقتی مشارکت‌کنندگان رفتاری متفاوت از دیگر مشارکت‌کنندگان یا CI می‌بینند

    داشتن این تصویر لحظه‌ای از وابستگی‌ها همچنین وقتی پروژه‌ها باید در برابر نسخه‌های ثابتی از وابستگی‌ها اعتبارسنجی شوند کمک می‌کند، مانند وقتی که

    • اعتبارسنجی حداقل نسخهٔ پشتیبانی‌شدهٔ Rust (MSRV) که از آخرین نسخهٔ پشتیبانی‌شده توسط یک وابستگی کمتر است
    • اعتبارسنجی خروجی قابل‌خواندن برای انسان که تضمین سازگاری نخواهد داشت (مثلاً آزمون snapshot پیام‌های خطا تا مطمئن شویم «قابل‌فهم» هستند، معیاری که برای خودکارسازی بیش از حد مبهم است)

    با این حال، این قطعی بودن می‌تواند حس امنیت کاذب ایجاد کند، چون Cargo.lock بر مصرف‌کنندگان بستهٔ شما تأثیری ندارد و فقط Cargo.toml چنین می‌کند. برای مثال:

    • cargo install آخرین وابستگی‌ها را انتخاب می‌کند، مگر اینکه --locked داده شود.
    • وابستگی‌های جدید، مانند آن‌هایی که با cargo add اضافه می‌شوند، روی آخرین نسخه قفل می‌شوند

    lockfile همچنین می‌تواند منبع تعارض‌های merge باشد.

    برای راهبردهای اعتبارسنجی نسخه‌های جدیدتر وابستگی‌ها از طریق CI، تأیید آخرین وابستگی‌ها را ببینید.

    آیا کتابخانه‌ها می‌توانند از * به‌عنوان نسخهٔ وابستگی‌هایشان استفاده کنند؟

    از ۲۲ ژانویهٔ ۲۰۱۶، crates.io همهٔ بسته‌ها (نه فقط کتابخانه‌ها) را که قیدهای وابستگی با wildcard داشته باشند رد می‌کند.

    اگرچه کتابخانه‌ها می‌توانند چنین کنند، به‌طور دقیق‌تر نباید این کار را بکنند. یک الزام نسخه به شکل * می‌گوید «این با هر نسخه‌ای که تاکنون بوده کار خواهد کرد»، که هرگز درست نخواهد بود. کتابخانه‌ها باید همیشه بازه‌ای را که واقعاً با آن کار می‌کنند مشخص کنند، حتی اگر چیزی به کلی‌گویی «هر نسخهٔ 1.x.y» باشد.

    چرا Cargo.toml؟

    به‌عنوان یکی از پرتکرارترین تعامل‌ها با Cargo، پرسش اینکه چرا فایل پیکربندی Cargo.toml نامیده شده است گاهی مطرح می‌شود. حرف بزرگ C در ابتدا انتخاب شد تا manifest در فهرست پوشه‌ها همراه با دیگر فایل‌های پیکربندی مشابه دسته‌بندی شود. مرتب‌سازی فایل‌ها اغلب حروف بزرگ را پیش از حروف کوچک قرار می‌دهد، که تضمین می‌کند فایل‌هایی مانند Makefile و Cargo.toml کنار هم قرار بگیرند. پسوند .toml در انتها انتخاب شد تا بر این واقعیت تأکید کند که فایل در قالب پیکربندی TOML است.

    Cargo نام‌های دیگری مانند cargo.toml یا Cargofile را مجاز نمی‌داند تا بر سهولت شناسایی یک مخزن Cargo تأکید شود. وجود گزینه‌ای از میان نام‌های ممکن متعدد، از دیرباز به سردرگمی انجامیده است، به این صورت که یک حالت مدیریت می‌شد اما حالت‌های دیگر به‌طور اتفاقی فراموش می‌شدند.

    Cargo چگونه می‌تواند آفلاین کار کند؟

    پرچم‌های --offline یا --frozen به Cargo می‌گویند به شبکه دست نزند. در صورتی که بخواهد به شبکه دسترسی پیدا کند، خطا برمی‌گرداند. می‌توانید از cargo fetch در یک پروژه استفاده کنید تا وابستگی‌ها را پیش از آفلاین شدن دانلود کنید، و سپس همان وابستگی‌ها را در پروژهٔ دیگری به کار ببرید. برای تنظیم از طریق پیکربندی Cargo به مقدار پیکربندی مراجعه کنید.

    Vendor کردن نیز مرتبط است؛ برای اطلاعات بیشتر مستندات جایگزینی منبع را ببینید.

    چرا Cargo کد من را دوباره می‌سازد؟

    Cargo مسئول کامپایل افزایشی crateهای پروژهٔ شماست. این یعنی اگر cargo build را دو بار اجرا کنید، اجرای دوم نباید مثلاً وابستگی‌های crates.io شما را دوباره بسازد. با این حال باگ‌هایی پیش می‌آیند و Cargo گاهی ممکن است کدی را بازسازی کند در حالی که انتظارش را ندارید!

    ما از مدت‌ها پیش می‌خواستیم تشخیص‌های بهتری دربارهٔ این موضوع ارائه دهیم اما متأسفانه مدتی طولانی است که نتوانسته‌ایم در آن مسئله پیشرفتی داشته باشیم. در این میان، می‌توانید دست‌کم تا حدی یک بازسازی را با تنظیم متغیر محیطی CARGO_LOG اشکال‌زدایی کنید:

    $ CARGO_LOG=cargo::compiler::fingerprint=info cargo build

    این کار باعث می‌شود Cargo اطلاعات زیادی دربارهٔ تشخیص‌ها و بازسازی چاپ کند. این اغلب می‌تواند سرنخ‌هایی دربارهٔ اینکه چرا پروژهٔ شما دوباره ساخته می‌شود در خود داشته باشد، هرچند اغلب باید برخی نکته‌ها را خودتان به هم وصل کنید چون خواندن این خروجی هنوز چندان آسان نیست. توجه داشته باشید که CARGO_LOG باید برای دستوری تنظیم شود که فکر می‌کنید نباید بازسازی کند، اما می‌کند. متأسفانه Cargo فعلاً راهی برای اشکال‌زدایی پس از وقوع، یعنی «چرا آن بازسازی شد؟»، ندارد.

    برخی مشکلاتی که از قبل دیده‌ایم و می‌توانند باعث بازسازی crateها شوند عبارت‌اند از:

    • یک build script عبارت cargo::rerun-if-changed=foo را چاپ می‌کند که در آن foo فایلی است که وجود ندارد و هیچ چیز آن را تولید نمی‌کند. در این حالت Cargo به اجرای build script ادامه می‌دهد چون فکر می‌کند آن فایل را تولید خواهد کرد، اما هیچ‌وقت چنین نمی‌شود. راه‌حل این است که در این سناریو از چاپ rerun-if-changed پرهیز کنید.

    • دو ساخت پیاپی Cargo ممکن است در مجموعهٔ featureهای فعال برای برخی وابستگی‌ها تفاوت داشته باشند. برای مثال اگر نخستین دستور ساخت کل workspace را بسازد و دستور دوم فقط یک crate را بسازد، ممکن است باعث شود وابستگی‌ای از crates.io مجموعهٔ متفاوتی از featureهای فعال داشته باشد و خودش و هر چیزی که به آن وابسته است دوباره ساخته شود. متأسفانه راه‌حل چندان خوبی برای این مورد وجود ندارد، اگرچه در صورت امکان بهتر است مجموعهٔ featureهای فعال روی یک crate، بدون توجه به آنچه در workspace خود می‌سازید، ثابت باشد.

    • برخی فایل‌سیستم‌ها رفتار غیرعادی‌ای پیرامون مهرهای زمانی (timestamp) نشان می‌دهند. Cargo عمدتاً از مهرهای زمانی فایل‌ها برای تعیین اینکه آیا بازسازی لازم است استفاده می‌کند، اما اگر از فایل‌سیستمی غیراستاندارد استفاده می‌کنید، ممکن است به‌نوعی روی مهرهای زمانی اثر بگذارد (مثلاً آن‌ها را کوتاه کند، باعث رانش آن‌ها شود و غیره). در این حالت، با خیال راحت یک issue باز کنید تا ببینیم می‌توانیم به‌نوعی با آن فایل‌سیستم سازگار شویم.

    • یک فرایند ساخت همزمان یا آرتیفکت‌ها را حذف می‌کند یا فایل‌ها را تغییر می‌دهد. گاهی ممکن است فرایندی در پس‌زمینه داشته باشید که سعی می‌کند پروژهٔ شما را بسازد یا بررسی کند. این فرایندهای پس‌زمینه ممکن است به‌طور شگفت‌آوری برخی آرتیفکت‌های ساخت را حذف کنند یا به فایل‌ها touch بزنند (یا شاید فقط از روی اشتباه)، که می‌تواند باعث شود بازسازی‌ها بی‌دلیل به نظر برسند! بهترین راه‌حل در اینجا این است که فرایند پس‌زمینه را طوری مهار کنید که با کار شما تداخل نداشته باشد.

    با این حال، اگر پس از تلاش برای اشکال‌زدایی، همچنان با مشکل روبه‌رو هستید، با خیال راحت یک issue باز کنید!

    «تعارض نسخه» به چه معناست و چگونه آن را حل کنیم؟

    انتخاب نسخه‌ای برای x که بتواند این تعارض را حل کند ناموفق بود

    آیا پیام خطای بالا را دیده‌اید؟

    این یکی از آزاردهنده‌ترین پیام‌های خطا برای کاربران Cargo است. چند وضعیت ممکن است به تعارض نسخه منجر شوند. در ادامه علل ممکن را مرور می‌کنیم و تکنیک‌های تشخیصی ارائه می‌دهیم تا در این زمینه به شما کمک کنند:

    • پروژه و وابستگی‌هایش از links برای لینک مکرر کتابخانهٔ محلی استفاده می‌کنند. Cargo لینک کردن دو بسته با یک کتابخانهٔ بومی مشابه را ممنوع می‌کند، پس حتی با لایه‌های متعدد وابستگی نیز مجاز نیست. در این حالت، پیام خطا این را نشان می‌دهد: Only one package in the dependency graph may specify the same links value؛ ممکن است لازم باشد مقادیر links تکراری را دستی بررسی و حذف کنید. جامعه نیز برای کاهش این مشکل قراردادهایی دارد.

    • هنگام وابسته شدن به crateهای مختلف در پروژه، اگر این crateها از یک کتابخانهٔ وابستهٔ مشترک استفاده کنند اما نسخهٔ مورد استفاده محدود شده باشد و تعیین نسخهٔ درست ممکن نباشد، این نیز باعث تعارض می‌شود. پیام خطا این را نشان می‌دهد: all possible versions conflict with previously selected packages. ممکن است لازم باشد الزام‌های نسخه را تغییر دهید تا با هم سازگار شوند.

    • اگر چند نسخه از وابستگی‌ها در پروژه وجود داشته باشد، هنگام استفاده از direct-minimal-versions ممکن است الزام‌های حداقل نسخه برآورده نشوند و این باعث تعارض شود. ممکن است لازم باشد الزام‌های نسخهٔ وابستگی‌های مستقیم خود را برای برآورده کردن حداقل نسخهٔ SemVer مربوطه تغییر دهید.

    • اگر crate وابسته featureهایی را که شما انتخاب کرده‌اید نداشته باشد، این نیز باعث تعارض می‌شود. در این حالت باید نسخهٔ وابسته و featureهای آن را بررسی کنید.

    • هنگام merge کردن شاخه‌ها یا PRها ممکن است تعارض رخ دهد. اگر تعارض‌های غیرساده‌ای وجود دارد، می‌توانید همهٔ تغییرات «خودتان» را بازنشانی کنید، همهٔ تعارض‌های دیگر را در شاخه رفع کنید و سپس یک دستور cargo (مانند cargo tree یا cargo check) اجرا کنید که باید lockfile را با تغییرات محلی خودتان دوباره به‌روز کند. اگر پیش‌تر دستورهای cargo updateای را در شاخهٔ خود اجرا کرده‌اید، می‌توانید این بار دوباره آن‌ها را اجرا کنید. جامعه در پی آن بوده است که تعارض‌های merge مربوط به Cargo.lock و Cargo.toml را با یک ابزار merge سفارشی حل کند.

    چرا ساخت من فضای این‌قدر زیادی اشغال می‌کند؟

    Cargo برای ساخت‌های سریع‌تر، فضای دیسک را فدا می‌کند، از جمله با:

    • نگهداری یک cache از آرتیفکت‌های ساخت میانی تا هنگام تغییر در یک بسته نیازی به ساخت مجدد همه‌چیز نباشد
    • نگهداری ورودی‌های cache جداگانه برای ترکیب‌های مختلف نسخه‌های toolchain، نسخه‌های بسته، featureها و غیره تا هنگام جابه‌جایی میان پیکربندی‌ها نیازی به ساخت مجدد بسته‌ها نباشد
    • فعال کردن کامپایل افزایشی برای بسته‌های محلی تا بسته‌ای که تغییر کرده سریع‌تر دوباره ساخته شود
    • فعال کردن debuginfo در پروفایل dev برای حالتی که از debugger استفاده می‌کنید
