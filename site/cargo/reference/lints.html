    Lintها

    Note

    این فصل دربارهٔ lintهایی است که خود cargo تولید می‌کند.

    پیکربندی lintهای Cargo

    lintهای Cargo را می‌توان در جدول [lints.cargo] در manifest فایل Cargo.toml پیکربندی کرد. کلید، نام lint بدون پیشوند cargo:: است. برای مثال:

    [lints.cargo]
unused_dependencies = "deny"

    برای جزئیات دربارهٔ سطح‌ها و اولویت‌های lint، بخش [lints] را ببینید.

    گروه‌های lint

    Cargo مفهومی به نام «گروه lint» دارد که به کمک آن می‌توانید چند هشدار را با یک نام واحد روشن یا خاموش کنید.

    گروهتوضیحسطح پیش‌فرض
    cargo::defaultهمهٔ lintهایی که به‌صورت پیش‌فرض روشن هستند (correctness، suspicious، style، complexity، perf)warn/deny
    cargo::correctnessکدی که آشکارا نادرست یا بی‌فایده استdeny
    cargo::styleکدی که باید به شیوه‌ای اصطلاحی‌تر (idiomatic) نوشته شودwarn
    cargo::suspiciousکدی که به احتمال زیاد نادرست یا بی‌فایده استwarn
    cargo::pedanticlintهایی که نسبتاً سخت‌گیرانه‌اند یا گاهی هشدار نادرست (false positive) می‌دهندallow
    cargo::restrictionlintهایی که از استفاده از قابلیت‌های Cargo جلوگیری می‌کنندallow

    blanket_hint_mostly_unused

    • گروه: suspicious
    • سطح: warn
    • حداقل package.rust-version: 1.79.0

    چه کاری انجام می‌دهد

    بررسی می‌کند که آیا hint-mostly-unused روی همهٔ وابستگی‌ها اعمال شده است یا نه.

    چرا بد است؟

    hint-mostly-unused نشان می‌دهد که بخش عمدهٔ سطح API یک crate توسط هر چیزی که به آن وابسته است استفاده نخواهد شد؛ این راهنما می‌تواند با تلاش برای کمینه‌کردن زمان کامپایل آیتم‌هایی که اصلاً استفاده نمی‌شوند، ساخت را سریع‌تر کند. اعمال نادرست آن روی crateهایی که با این معیار سازگار نیستند، به‌جای سریع‌تر کردن، ساخت را کندتر می‌کند. این راهنما باید به‌صورت گزینشی روی وابستگی‌هایی اعمال شود که این معیارها را دارند. اعمال سراسری آن همیشه نادرست است و به احتمال زیاد ساخت را کند می‌کند.

    مثال

    [profile.dev.package."*"]
hint-mostly-unused = true

    در عوض باید این‌طور نوشته شود:

    [profile.dev.package.huge-mostly-unused-dependency]
hint-mostly-unused = true

    non_kebab_case_bins

    • گروه: pedantic
    • سطح: allow
    • حداقل package.rust-version: 1.79.0

    چه کاری انجام می‌دهد

    نام‌های فایل‌های اجرایی (binary)، چه صریح و چه ضمنی، را که kebab-case نیستند تشخیص می‌دهد.

    چرا بد است؟

    نام‌گذاری فایل‌های اجرایی به صورت kebab-case قراردادی رایج در میان ابزارهای خط فرمان است.

    معایب

    تغییر نام فایل اجرایی برای کاربران موجود مخرب خواهد بود.

    ممکن است یک فایل اجرایی لازم باشد با قراردادهایی که از بیرون کنترل می‌شوند و می‌توانند شامل قرارداد نام‌گذاری متفاوتی باشند هماهنگ شود.

    برنامه‌های گرافیکی (GUI) ممکن است بخواهند قرارداد نام‌گذاری کاربرمحورتری مانند «Title Case» یا «Sentence case» را انتخاب کنند.

    مثال

    [[bin]]
name = "foo_bar"

    باید این‌طور نوشته شود:

    [[bin]]
name = "foo-bar"

    text_direction_codepoint_in_comment

    • گروه: correctness
    • سطح: deny
    • حداقل package.rust-version: 1.79.0

    چه کاری انجام می‌دهد

    کدپوینت‌های یونیکد را در کامنت‌های manifest تشخیص می‌دهد که نمایش بصری متن را روی صفحه به شیوه‌ای تغییر می‌دهند که با نمایش آن در حافظه مطابقت ندارد.

    چرا بد است؟

    یونیکد اجازه می‌دهد جریان بصری متن روی صفحه تغییر کند تا از خط‌هایی که از راست به چپ نوشته می‌شوند پشتیبانی شود، اما یک کامنت که به‌طور خاص ساخته شده باشد می‌تواند کدی را که کامپایل خواهد شد بسته به نرم‌افزاری که برای خواندن کد به کار می‌رود، بخشی از کامنت نشان دهد. برای پرهیز از مشکلات یا سردرگمی احتمالی، مانند آنچه در CVE-2021-42574 رخ داد، به‌طور پیش‌فرض استفاده از آن‌ها را ممنوع (deny) می‌کنیم.

    unknown_lints

    • گروه: suspicious
    • سطح: warn
    • حداقل package.rust-version: 1.79.0

    چه کاری انجام می‌دهد

    lintهای ناشناخته را در جدول [lints.cargo] بررسی می‌کند.

    چرا بد است؟

    • نام lint ممکن است غلط املایی داشته باشد و این موضوع باعث سردرگمی شود که چرا آن‌طور که انتظار می‌رود کار نمی‌کند
    • اگر cargo در آینده تصمیم بگیرد lintی با همان نام ایجاد کند، lint ناشناخته می‌تواند در نهایت باعث خطا شود

    مثال

    [lints.cargo]
this-lint-does-not-exist = "warn"

    unused_dependencies

    • گروه: style
    • سطح: warn
    • حداقل package.rust-version: 1.79.0

    چه کاری انجام می‌دهد

    وابستگی‌هایی را که توسط هیچ‌یک از هدف‌های cargo استفاده نمی‌شوند بررسی می‌کند.

    چرا بد است؟

    زمان کامپایل را کند می‌کند.

    معایب

    این lint فقط در شرایط خاصی تولید می‌شود، زیرا برای جدول‌های مختلف وابستگی‌ها چندین هدف cargo وجود دارد و برای اینکه بدانیم یک وابستگی استفاده نشده است باید همهٔ آن‌ها ساخته شوند. در حال حاضر فقط بسته‌های انتخاب‌شده بررسی می‌شوند و برخلاف بیشتر lintها، همهٔ وابستگی‌های path بررسی نمی‌شوند. پرچم‌های انتخاب هدف cargo، مستقل از اینکه کدام بسته‌ها انتخاب شده‌اند، تعیین می‌کنند کدام جدول‌های وابستگی‌ها بررسی شوند. از آنجا که راهی برای انتخاب همهٔ هدف‌های cargo که از [dev-dependencies] استفاده می‌کنند وجود ندارد، این وابستگی‌ها بررسی نمی‌شوند.

    مثال‌ها:

    • cargo check جدول‌های [build-dependencies] و [dependencies] را بررسی می‌کند
    • cargo check --all-targets همچنان فقط [build-dependencies] و [dependencies] را بررسی می‌کند و [dev-dependencoes] را نه
    • cargo check --bin foo جدول [dependencies] را بررسی نخواهد کرد، حتی اگر foo تنها bin باشد، اما [build-dependencies] بررسی خواهد شد
    • cargo check -p foo هیچ جدول وابستگی‌ای را برای وابستگی path به نام bar بررسی نخواهد کرد، حتی اگر bar فقط یک [lib] داشته باشد

    هنگام وابستگی به یک وابستگی انتقالی برای فعال‌کردن یک feature، ممکن است هشدارهای نادرست (false positive) رخ دهد.

    برای هشدارهای نادرستی که از پین‌کردن نسخهٔ یک وابستگی انتقالی در Cargo.toml ناشی می‌شوند، وابستگی را به جدول target."cfg(false)".dependencies منتقل کنید.

    مثال

    [package]
name = "foo"

[dependencies]
unused = "1"

    باید این‌طور نوشته شود:

    [package]
name = "foo"
