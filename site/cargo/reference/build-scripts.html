    اسکریپت‌های ساخت

    برخی بسته‌ها باید کدی غیر از Rust و متعلق به اشخاص ثالث را کامپایل کنند، برای مثال کتابخانه‌های C. بسته‌های دیگر باید به کتابخانه‌های C پیوند بخورند که یا روی سیستم موجودند یا شاید لازم باشد از سورس ساخته شوند. بعضی دیگر هم پیش از ساخت به امکاناتی مانند تولید کد نیاز دارند (مثلاً مولدهای تجزیه‌گر).

    Cargo قصد جایگزینی ابزارهایی را ندارد که برای این کارها به‌خوبی بهینه شده‌اند، اما از طریق اسکریپت‌های ساخت سفارشی با آن‌ها یکپارچه می‌شود. قرار دادن فایلی با نام build.rs در ریشهٔ یک بسته باعث می‌شود Cargo آن اسکریپت را کامپایل کند و درست پیش از ساخت بسته اجرایش کند.

    // Example custom build script.
fn main() {
    // Tell Cargo that if the given file changes, to rerun this build script.
    println!("cargo::rerun-if-changed=src/hello.c");
    // Use the `cc` crate to build a C file and statically link it.
    cc::Build::new()
        .file("src/hello.c")
        .compile("hello");
}

    چند نمونه از کاربردهای اسکریپت‌های ساخت:

    • ساخت یک کتابخانهٔ C همراه بسته.
    • پیدا کردن یک کتابخانهٔ C روی سیستم میزبان.
    • تولید یک ماژول Rust از روی یک مشخصات (specification).
    • انجام هر پیکربندی خاص پلتفرم که crate به آن نیاز دارد.

    بخش‌های زیر نحوهٔ کار اسکریپت‌های ساخت را شرح می‌دهند و فصل مثال‌ها نمونه‌های متنوعی از نوشتن اسکریپت را نشان می‌دهد.

    Note

    کلید package.build در manifest را می‌توان برای تغییر نام اسکریپت ساخت یا غیرفعال کردن کامل آن به کار برد.

    چرخهٔ حیات یک اسکریپت ساخت

    درست پیش از ساخت یک بسته، Cargo اسکریپت ساخت را به یک فایل اجرایی کامپایل می‌کند (اگر از قبل ساخته نشده باشد). سپس اسکریپت را اجرا می‌کند، که می‌تواند هر تعداد کاری انجام دهد. اسکریپت می‌تواند با چاپ دستورهای قالب‌بندی‌شدهٔ خاصی که با cargo:: شروع می‌شوند در stdout با Cargo ارتباط برقرار کند.

    اگر هر یک از فایل‌های سورس اسکریپت یا وابستگی‌هایش تغییر کند، اسکریپت ساخت دوباره ساخته می‌شود.

    به‌طور پیش‌فرض، Cargo در صورت تغییر هر یک از فایل‌های بسته، اسکریپت ساخت را دوباره اجرا می‌کند. معمولاً بهتر است از دستورهای rerun-if که در بخش تشخیص تغییر در ادامه توضیح داده شده‌اند استفاده کنید تا دامنهٔ آنچه باعث اجرای مجدد اسکریپت ساخت می‌شود محدود گردد.

    پس از آنکه اسکریپت ساخت با موفقیت اجرا شد، بقیهٔ بسته کامپایل می‌شود. اگر خطایی رخ دهد، اسکریپت‌ها باید با کد خروج غیرصفر خارج شوند تا ساخت متوقف شود؛ در این حالت خروجی اسکریپت ساخت در ترمینال نمایش داده می‌شود.

    ورودی‌های اسکریپت ساخت

    هنگامی که اسکریپت ساخت اجرا می‌شود، تعدادی ورودی دارد که همگی به شکل متغیرهای محیطی به آن داده می‌شوند.

    علاوه بر متغیرهای محیطی، دایرکتوری جاری اسکریپت ساخت همان دایرکتوری ریشهٔ بستهٔ اسکریپت ساخت است.

    Warning

    هنگام بررسی گزینه‌های پیکربندی مانند target_os یا target_arch در یک اسکریپت ساخت، از ماکروی cfg! یا attribute #[cfg] استفاده نکنید؛ این‌ها ماشین میزبان (جایی که اسکریپت ساخت اجرا می‌شود) را بررسی می‌کنند، نه پلتفرم هدفی که برایش کامپایل می‌کنید. این تفاوت در کامپایل متقابل (cross-compiling) اهمیت دارد.

    در عوض، متغیرهای محیطی متناظر CARGO_CFG_* را بخوانید که پیکربندی هدف را درست منعکس می‌کنند. برای یک API نوع‌دار، استفاده از crate با نام build-rs را در نظر بگیرید. برای جزئیات بیشتر مثال‌های اسکریپت ساخت را ببینید.

    خروجی‌های اسکریپت ساخت

    اسکریپت‌های ساخت می‌توانند هر فایل خروجی یا مصنوع (artifact) میانی را در دایرکتوری مشخص‌شده در متغیر محیطی OUT_DIR ذخیره کنند. اسکریپت‌ها نباید هیچ فایلی را خارج از آن دایرکتوری تغییر دهند.

    Important

    Cargo بین ساخت‌ها OUT_DIR را پاک یا بازنشانی نمی‌کند. محتوای این دایرکتوری ممکن است حتی با اجرای مجدد اسکریپت ساخت، بین ساخت‌های مجدد باقی بماند. این رفتار عمدی است تا از ساخت‌های افزایشی (incremental)، مانند کامپایل کد بومی، پشتیبانی شود.

    اسکریپت‌های ساخت نباید فرض کنند OUT_DIR خالی است، زیرا محتوای آن ممکن است بین ساخت‌های مجدد باقی بماند. اگر اسکریپتی به دایرکتوری تمیز نیاز دارد، در حال حاضر خودش مسئول مدیریت یا پاک‌سازی فایل‌ها و زیردایرکتوری‌هایی است که ایجاد می‌کند. دربارهٔ بهبودهای آینده در این زمینه بحث می‌شود (به #16427 و #9661 مراجعه کنید).

    اسکریپت‌های ساخت با چاپ در stdout با Cargo ارتباط برقرار می‌کنند. Cargo هر خطی را که با cargo:: شروع شود به‌عنوان دستوری تفسیر می‌کند که بر کامپایل بسته اثر می‌گذارد. همهٔ خطوط دیگر نادیده گرفته می‌شوند.

    ترتیب دستورهای cargo:: که اسکریپت ساخت چاپ می‌کند ممکن است بر ترتیب آرگومان‌هایی که cargo به rustc می‌دهد اثر بگذارد. این ترتیبِ آرگومان‌های rustc نیز به نوبهٔ خود ممکن است بر ترتیب آرگومان‌های داده‌شده به لینکر اثر بگذارد. بنابراین باید به ترتیب دستورهای اسکریپت ساخت توجه کنید. برای مثال، اگر شیء foo باید با کتابخانهٔ bar پیوند بخورد، باید مطمئن شوید دستور cargo::rustc-link-lib برای کتابخانهٔ bar پس از دستورهای پیوند دادن شیء foo ظاهر می‌شود.

    خروجی اسکریپت در طول کامپایل عادی از ترمینال پنهان است. اگر می‌خواهید خروجی را مستقیماً در ترمینال ببینید، Cargo را با پرچم -vv به‌صورت «بسیار پرجزئیات» (very verbose) اجرا کنید. این فقط زمانی رخ می‌دهد که اسکریپت ساخت اجرا شود. اگر Cargo تشخیص دهد چیزی تغییر نکرده، اسکریپت را دوباره اجرا نمی‌کند؛ برای اطلاعات بیشتر تشخیص تغییر را در ادامه ببینید.

    همهٔ خطوطی که اسکریپت ساخت در stdout چاپ می‌کند در فایلی مانند target/debug/build/<pkg>/output نوشته می‌شود (مکان دقیق ممکن است به پیکربندی شما بستگی داشته باشد). خروجی stderr نیز در همان دایرکتوری ذخیره می‌شود.

    در ادامه خلاصه‌ای از دستورهایی آمده که Cargo می‌شناسد؛ هر یک در پایین به‌تفصیل شرح داده شده است.

    • cargo::rerun-if-changed=PATH — به Cargo می‌گوید چه زمانی اسکریپت را دوباره اجرا کند.
    • cargo::rerun-if-env-changed=VAR — به Cargo می‌گوید چه زمانی اسکریپت را دوباره اجرا کند.
    • cargo::rustc-link-arg=FLAG — پرچم‌های سفارشی را برای لینکر به بنچمارک‌ها، فایل‌های اجرایی، crateهای cdylib، مثال‌ها و آزمون‌ها می‌دهد.
    • cargo::rustc-link-arg-cdylib=FLAG — پرچم‌های سفارشی را برای لینکر به crateهای cdylib می‌دهد.
    • cargo::rustc-link-arg-bin=BIN=FLAG — پرچم‌های سفارشی را برای لینکر به فایل اجرایی BIN می‌دهد.
    • cargo::rustc-link-arg-bins=FLAG — پرچم‌های سفارشی را برای لینکر به فایل‌های اجرایی می‌دهد.
    • cargo::rustc-link-arg-tests=FLAG — پرچم‌های سفارشی را برای لینکر به آزمون‌ها می‌دهد.
    • cargo::rustc-link-arg-examples=FLAG — پرچم‌های سفارشی را برای لینکر به مثال‌ها می‌دهد.
    • cargo::rustc-link-arg-benches=FLAG — پرچم‌های سفارشی را برای لینکر به بنچمارک‌ها می‌دهد.
    • cargo::rustc-link-lib=LIB — یک کتابخانه برای پیوند دادن اضافه می‌کند.
    • cargo::rustc-link-search=[KIND=]PATH — به مسیر جست‌وجوی کتابخانه اضافه می‌کند.
    • cargo::rustc-flags=FLAGS — برخی پرچم‌ها را به کامپایلر می‌دهد.
    • cargo::rustc-cfg=KEY[="VALUE"] — تنظیمات cfg زمان کامپایل را فعال می‌کند.
    • cargo::rustc-check-cfg=CHECK_CFG – cfgهای سفارشی را برای بررسی زمان کامپایلِ پیکربندی‌ها به‌عنوان مورد انتظار ثبت می‌کند.
    • cargo::rustc-env=VAR=VALUE — یک متغیر محیطی تنظیم می‌کند.
    • cargo::error=MESSAGE — یک خطا را در ترمینال نمایش می‌دهد.
    • cargo::warning=MESSAGE — یک هشدار را در ترمینال نمایش می‌دهد.
    • cargo::metadata=KEY=VALUE — فراداده، که اسکریپت‌های links از آن استفاده می‌کنند.

    MSRV: برای نحو cargo::KEY=VALUE نسخهٔ 1.77 لازم است. برای پشتیبانی از نسخه‌های قدیمی‌تر، از نحو cargo:KEY=VALUE استفاده کنید.

    cargo::rustc-link-arg=FLAG

    دستور rustc-link-arg به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت هدف‌های پشتیبانی‌شده (بنچمارک‌ها، فایل‌های اجرایی، crateهای cdylib، مثال‌ها و آزمون‌ها). استفاده از آن به‌شدت به پلتفرم وابسته است. برای تنظیم نسخهٔ کتابخانهٔ اشتراکی یا اسکریپت لینکر مفید است.

    cargo::rustc-link-arg-cdylib=FLAG

    دستور rustc-link-arg-cdylib به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت هدف کتابخانهٔ cdylib. استفاده از آن به‌شدت به پلتفرم وابسته است. برای تنظیم نسخهٔ کتابخانهٔ اشتراکی یا مسیر زمان اجرا (runtime-path) مفید است.

    به دلایل تاریخی، شکل cargo::rustc-cdylib-link-arg نام مستعار cargo::rustc-link-arg-cdylib است و معنای یکسانی دارد.

    cargo::rustc-link-arg-bin=BIN=FLAG

    دستور rustc-link-arg-bin به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت هدف فایل اجرایی با نام BIN. استفاده از آن به‌شدت به پلتفرم وابسته است. برای تنظیم اسکریپت لینکر یا سایر گزینه‌های لینکر مفید است.

    cargo::rustc-link-arg-bins=FLAG

    دستور rustc-link-arg-bins به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت یک هدف فایل اجرایی. استفاده از آن به‌شدت به پلتفرم وابسته است. برای تنظیم اسکریپت لینکر یا سایر گزینه‌های لینکر مفید است.

    cargo::rustc-link-arg-tests=FLAG

    دستور rustc-link-arg-tests به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت یک هدف آزمون.

    cargo::rustc-link-arg-examples=FLAG

    دستور rustc-link-arg-examples به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت یک هدف مثال.

    cargo::rustc-link-arg-benches=FLAG

    دستور rustc-link-arg-benches به Cargo می‌گوید گزینهٔ -C link-arg=FLAG را به کامپایلر بدهد، اما فقط هنگام ساخت یک هدف بنچمارک.

    cargo::rustc-link-lib=LIB

    دستور rustc-link-lib به Cargo می‌گوید کتابخانهٔ داده‌شده را با پرچم -l کامپایلر پیوند دهد. این معمولاً برای پیوند دادن یک کتابخانهٔ بومی با استفاده از FFI به کار می‌رود.

    رشتهٔ LIB مستقیماً به rustc داده می‌شود، بنابراین هر نحوی را که -l پشتیبانی می‌کند پشتیبانی می‌کند. \ در حال حاضر نحو کاملاً پشتیبانی‌شده برای LIB به شکل [KIND[:MODIFIERS]=]NAME[:RENAME] است.

    پرچم -l فقط به هدف کتابخانهٔ بسته داده می‌شود، مگر اینکه هدف کتابخانه‌ای وجود نداشته باشد؛ در آن صورت به همهٔ هدف‌ها داده می‌شود. دلیلش این است که همهٔ هدف‌های دیگر وابستگی ضمنی به هدف کتابخانه دارند و کتابخانهٔ مورد نظر برای پیوند فقط باید یک بار گنجانده شود. این یعنی اگر بسته‌ای هم هدف کتابخانه و هم هدف فایل اجرایی داشته باشد، کتابخانه به نمادهای کتابخانهٔ داده‌شده دسترسی دارد و فایل اجرایی باید از طریق API عمومی هدف کتابخانه به آن‌ها دسترسی پیدا کند.

    KIND اختیاری می‌تواند یکی از dylib، static یا framework باشد. برای جزئیات بیشتر کتاب rustc را ببینید.

    cargo::rustc-link-search=[KIND=]PATH

    دستور rustc-link-search به Cargo می‌گوید پرچم -L را به کامپایلر بدهد تا یک دایرکتوری به مسیر جست‌وجوی کتابخانه اضافه شود.

    KIND اختیاری می‌تواند یکی از dependency، crate، native، framework یا all باشد. برای جزئیات بیشتر کتاب rustc را ببینید.

    اگر این مسیرها درون OUT_DIR باشند، به متغیر محیطی مسیر جست‌وجوی کتابخانه‌های پویا نیز اضافه می‌شوند. اتکا به این رفتار توصیه نمی‌شود، زیرا استفاده از فایل اجرایی حاصل را دشوار می‌کند. به‌طور کلی بهتر است از ساخت کتابخانه‌های پویا در اسکریپت ساخت پرهیز شود (استفاده از کتابخانه‌های موجود سیستم اشکالی ندارد).

    cargo::rustc-flags=FLAGS

    دستور rustc-flags به Cargo می‌گوید پرچم‌های داده‌شده را که با فاصله جدا شده‌اند به کامپایلر بدهد. این فقط پرچم‌های -l و -L را مجاز می‌داند و معادل استفاده از rustc-link-lib و rustc-link-search است.

    cargo::rustc-cfg=KEY[="VALUE"]

    دستور rustc-cfg به Cargo می‌گوید مقدار داده‌شده را به پرچم --cfg کامپایلر بدهد. این می‌تواند برای تشخیص زمان کامپایلِ featureها به‌منظور فعال کردن کامپایل شرطی به کار رود. cfgهای سفارشی باید یا با دستور cargo::rustc-check-cfg به‌عنوان مورد انتظار ثبت شوند، یا استفاده از آن‌ها باید lint با نام unexpected_cfgs را مجاز کند تا هشدارهای مربوط به cfgهای غیرمنتظره پیش نیاید.

    توجه کنید که این بر حل وابستگی‌های Cargo اثری ندارد. نمی‌توان از آن برای فعال کردن یک وابستگی اختیاری یا فعال کردن featureهای دیگر Cargo استفاده کرد.

    آگاه باشید که featureهای Cargo از قالب feature="foo" استفاده می‌کنند. مقدارهای cfg که با این پرچم داده می‌شوند به آن قالب محدود نیستند و می‌توانند فقط یک شناسهٔ تکی یا هر جفت کلید/مقدار دلخواه باشند. برای مثال، صادر کردن cargo::rustc-cfg=abc به کد اجازه می‌دهد از #[cfg(abc)] استفاده کند (توجه کنید feature= وجود ندارد). یا می‌توان یک جفت کلید/مقدار دلخواه را با نماد = به کار برد، مانند cargo::rustc-cfg=my_component="foo". کلید باید یک شناسهٔ Rust باشد و مقدار باید یک رشته.

    cargo::rustc-check-cfg=CHECK_CFG

    به فهرست نام‌ها و مقدارهای پیکربندیِ مورد انتظار که هنگام بررسی عبارت‌های cfgِ دست‌یافتنی با lint با نام unexpected_cfgs به کار می‌رود، می‌افزاید.

    نحو CHECK_CFG مشابه پرچم --check-cfg در rustc است؛ برای جزئیات بیشتر بررسی پیکربندی‌های شرطی را ببینید.

    این دستور را می‌توان این‌گونه به کار برد:

    // build.rs
println!("cargo::rustc-check-cfg=cfg(foo, values(\"bar\"))");
if foo_bar_condition {
    println!("cargo::rustc-cfg=foo=\"bar\"");
}

    توجه کنید که همهٔ cfgهای ممکن باید تعریف شوند، صرف‌نظر از اینکه در حال حاضر کدام cfgها فعال‌اند. این شامل همهٔ مقدارهای ممکنِ یک نام cfg می‌شود.

    توصیه می‌شود دستورهای cargo::rustc-check-cfg و cargo::rustc-cfg تا حد ممکن کنار هم گروه‌بندی شوند تا از اشتباه تایپی، check-cfg جاافتاده، cfgهای کهنه و… جلوگیری شود.

    همچنین مثال کامپایل شرطی را ببینید.

    MSRV: از نسخهٔ 1.80 رعایت می‌شود

    cargo::rustc-env=VAR=VALUE

    دستور rustc-env به Cargo می‌گوید هنگام کامپایل بسته، متغیر محیطی داده‌شده را تنظیم کند. سپس مقدار را می‌توان با ماکروی env! در crate کامپایل‌شده بازیابی کرد. این برای جاسازی فراداده‌های اضافی در کد crate مفید است، مانند هش HEAD در git یا شناسهٔ یکتای یک سرور یکپارچه‌سازی مداوم (continuous integration).

    همچنین متغیرهای محیطی‌ای که Cargo به‌طور خودکار می‌گنجاند را ببینید.

    Note

    این متغیرهای محیطی هنگام اجرای یک فایل اجرایی با cargo run یا cargo test نیز تنظیم می‌شوند. با این حال این استفاده توصیه نمی‌شود، زیرا فایل اجرایی را به محیط اجرای Cargo وابسته می‌کند. معمولاً این متغیرهای محیطی باید فقط در زمان کامپایل با ماکروی env! بررسی شوند.

    cargo::error=MESSAGE

    دستور error به Cargo می‌گوید پس از پایان اجرای اسکریپت ساخت یک خطا نمایش دهد و سپس ساخت را ناموفق کند.

    Note

    کتابخانه‌های اسکریپت ساخت باید با دقت بررسی کنند که می‌خواهند از cargo::error استفاده کنند یا یک Result برگردانند. ممکن است بهتر باشد یک Result برگردانده شود و به فراخواننده اجازه داده شود تصمیم بگیرد خطا کشنده است یا نه. سپس فراخواننده می‌تواند تصمیم بگیرد که آیا واریانت Err را با cargo::error نمایش دهد یا نه.

    MSRV: از نسخهٔ 1.84 رعایت می‌شود

    cargo::warning=MESSAGE

    دستور warning به Cargo می‌گوید پس از پایان اجرای اسکریپت ساخت یک هشدار نمایش دهد. هشدارها فقط برای وابستگی‌های path (یعنی آن‌هایی که به‌صورت محلی روی آن‌ها کار می‌کنید) نمایش داده می‌شوند، بنابراین برای مثال هشدارهای چاپ‌شده در crateهای crates.io به‌طور پیش‌فرض منتشر نمی‌شوند، مگر اینکه ساخت ناموفق شود. می‌توان از پرچم «بسیار پرجزئیات» -vv استفاده کرد تا Cargo هشدارها را برای همهٔ crateها نمایش دهد.

    وابستگی‌های ساخت

    اسکریپت‌های ساخت می‌توانند به crateهای دیگر مبتنی بر Cargo هم وابسته باشند. وابستگی‌ها از طریق بخش build-dependencies در manifest تعریف می‌شوند.

    [build-dependencies]
cc = "1.0.46"

    اسکریپت ساخت به وابستگی‌های فهرست‌شده در بخش dependencies یا dev-dependencies دسترسی ندارد (آن‌ها هنوز ساخته نشده‌اند!). همچنین وابستگی‌های ساخت در دسترس خود بسته نیستند، مگر اینکه صراحتاً در جدول [dependencies] هم اضافه شوند.

    توصیه می‌شود هر وابستگی‌ای را که اضافه می‌کنید با دقت بررسی کنید و تأثیر آن بر زمان کامپایل، مجوزدهی، نگهداری و غیره را بسنجید. Cargo تلاش می‌کند اگر یک وابستگی بین وابستگی‌های ساخت و وابستگی‌های عادی مشترک باشد از آن دوباره استفاده کند. با این حال این همیشه ممکن نیست، مثلاً هنگام کامپایل متقابل، پس تأثیر آن بر زمان کامپایل را در نظر داشته باشید.

    تشخیص تغییر

    هنگام ساخت مجدد یک بسته، Cargo لزوماً نمی‌داند که آیا اسکریپت ساخت باید دوباره اجرا شود یا نه. به‌طور پیش‌فرض رویکردی محافظه‌کارانه دارد: اگر هر فایلی در بسته تغییر کند (یا فهرست فایل‌هایی که فیلدهای exclude و include کنترل می‌کنند)، اسکریپت ساخت را همیشه دوباره اجرا می‌کند. در بیشتر موارد این انتخاب خوبی نیست، پس توصیه می‌شود هر اسکریپت ساخت دست‌کم یکی از دستورهای rerun-if را (که در ادامه شرح داده شده‌اند) صادر کند. اگر این‌ها صادر شوند، Cargo فقط در صورتی اسکریپت را دوباره اجرا می‌کند که مقدار داده‌شده تغییر کرده باشد. اگر Cargo اسکریپت‌های ساخت crate خودتان یا یک وابستگی را دوباره اجرا می‌کند و دلیلش را نمی‌دانید، «چرا Cargo کد من را دوباره می‌سازد؟» در پرسش‌های متداول را ببینید.

    cargo::rerun-if-changed=PATH

    دستور rerun-if-changed به Cargo می‌گوید اگر فایل موجود در مسیر داده‌شده تغییر کرده باشد، اسکریپت ساخت را دوباره اجرا کند. در حال حاضر Cargo فقط از مهر زمانیِ آخرین ویرایش در سیستم فایل (mtime) استفاده می‌کند تا تشخیص دهد فایل تغییر کرده است یا نه. این مهر زمانی را با یک مهر زمانی کش‌شدهٔ داخلی از آخرین اجرای اسکریپت ساخت مقایسه می‌کند.

    اگر مسیر به یک دایرکتوری اشاره کند، کل دایرکتوری را برای هر تغییری پویش می‌کند.

    اگر اسکریپت ساخت ذاتاً در هیچ شرایطی نیازی به اجرای مجدد ندارد، صادر کردن cargo::rerun-if-changed=build.rs راه ساده‌ای برای جلوگیری از اجرای مجدد آن است (در غیر این صورت، اگر هیچ دستور rerun-if صادر نشود، پیش‌فرض این است که کل دایرکتوری بسته برای یافتن تغییرات پویش شود). Cargo به‌طور خودکار مدیریت می‌کند که آیا خود اسکریپت باید دوباره کامپایل شود یا نه، و البته اسکریپت پس از کامپایل مجدد دوباره اجرا می‌شود. در غیر این صورت، مشخص کردن build.rs زائد و غیرضروری است.

    cargo::rerun-if-env-changed=NAME

    دستور rerun-if-env-changed به Cargo می‌گوید اگر مقدار متغیر محیطی با نام داده‌شده تغییر کرده باشد، اسکریپت ساخت را دوباره اجرا کند.

    توجه کنید که متغیرهای محیطی در اینجا برای متغیرهای محیطی سراسری مانند CC و مشابه آن در نظر گرفته شده‌اند؛ نمی‌توان از این برای متغیرهای محیطی‌ای مانند TARGET که Cargo برای اسکریپت‌های ساخت تنظیم می‌کند استفاده کرد. متغیرهای محیطی مورد استفاده، همان‌هایی هستند که فراخوانی‌های cargo دریافت می‌کنند، نه آن‌هایی که فایل اجرایی اسکریپت ساخت دریافت می‌کند.

    از نسخهٔ 1.46، استفاده از env! و option_env! در کد سورس به‌طور خودکار تغییرات را تشخیص می‌دهد و ساخت مجدد را راه می‌اندازد. rerun-if-env-changed دیگر برای متغیرهایی که از قبل توسط این ماکروها ارجاع داده شده‌اند لازم نیست.

    کلید links در Manifest

    کلید package.links را می‌توان در manifest با نام Cargo.toml تنظیم کرد تا اعلام شود که بسته با کتابخانهٔ بومی داده‌شده پیوند می‌خورد. هدف این کلید manifest آن است که به Cargo درکی از مجموعهٔ وابستگی‌های بومی یک بسته بدهد و نیز سامانه‌ای اصولی برای انتقال فراداده بین اسکریپت‌های ساخت بسته‌ها فراهم کند.

    [package]
# ...
links = "foo"

    این manifest بیان می‌کند که بسته به کتابخانهٔ بومی libfoo پیوند می‌خورد. هنگام استفاده از کلید links، بسته باید یک اسکریپت ساخت داشته باشد و اسکریپت ساخت باید از دستور rustc-link-lib برای پیوند دادن کتابخانه استفاده کند.

    در درجهٔ اول، Cargo الزام می‌کند که برای هر مقدار links حداکثر یک بسته وجود داشته باشد. به عبارت دیگر، پیوند خوردن دو بسته به یک کتابخانهٔ بومی ممنوع است. این کار از نمادهای تکراری بین crateها جلوگیری می‌کند. با این حال توجه کنید که قراردادهایی وجود دارند که این محدودیت را کاهش می‌دهند.

    اسکریپت‌های ساخت می‌توانند مجموعه‌ای دلخواه از فراداده را به شکل جفت‌های کلید-مقدار تولید کنند. این فراداده با دستور cargo::metadata=KEY=VALUE تنظیم می‌شود.

    فراداده به اسکریپت‌های ساخت بسته‌های وابسته داده می‌شود. برای مثال، اگر بستهٔ foo به bar وابسته باشد و bar به baz پیوند بخورد، آنگاه اگر bar در فراداده‌های اسکریپت ساخت خود key=value را تولید کند، اسکریپت ساخت foo متغیرهای محیطی DEP_BAZ_KEY=value را خواهد داشت (توجه کنید که مقدار کلید links به کار می‌رود و حروف key تغییر می‌کند). برای مثالی از کاربرد این، «استفاده از crate sys دیگر» را ببینید.

    توجه کنید که فراداده فقط به وابسته‌های مستقیم داده می‌شود، نه به وابسته‌های انتقالی (transitive).

    MSRV: برای cargo::metadata=KEY=VALUE نسخهٔ 1.77 لازم است. برای پشتیبانی از نسخه‌های قدیمی‌تر، از cargo:KEY=VALUE استفاده کنید (دستورهای پشتیبانی‌نشده به‌عنوان کلید فراداده فرض می‌شوند).

    بسته‌های *-sys

    برخی بسته‌های Cargo که به کتابخانه‌های سیستمی پیوند می‌خورند، قراردادی نام‌گذاری دارند و پسوند -sys می‌گیرند. هر بسته‌ای با نام foo-sys باید دو قابلیت اصلی ارائه دهد:

    • crate کتابخانه باید به کتابخانهٔ بومی libfoo پیوند بخورد. این اغلب پیش از روی آوردن به ساخت از سورس، سیستم جاری را برای یافتن libfoo بررسی می‌کند.
    • crate کتابخانه باید اعلان‌هایی برای نوع‌ها و توابع در libfoo فراهم کند، اما نه انتزاع‌های سطح بالاتر.

    مجموعهٔ بسته‌های *-sys مجموعه‌ای مشترک از وابستگی‌ها برای پیوند به کتابخانه‌های بومی فراهم می‌کند. داشتن این قرارداد برای بسته‌های مرتبط با کتابخانهٔ بومی مزایای متعددی دارد:

    • وابستگی‌های مشترک به foo-sys قاعدهٔ «یک بسته به ازای هر مقدار links» را کاهش می‌دهد.
    • بسته‌های -sys دیگر می‌توانند از متغیرهای محیطی DEP_LINKS_KEY=value بهره ببرند تا بهتر با بسته‌های دیگر یکپارچه شوند. مثال «استفاده از crate sys دیگر» را ببینید.
    • یک وابستگی مشترک اجازه می‌دهد منطق کشف خود libfoo (یا ساخت آن از سورس) متمرکز شود.
    • این وابستگی‌ها به‌سادگی قابل بازنویسی هستند.

    معمول است که یک بستهٔ همراه بدون پسوند -sys وجود داشته باشد که انتزاع‌های امن و سطح بالا را روی بستهٔ sys فراهم می‌کند. برای مثال، crate git2 یک واسط سطح بالا برای crate libgit2-sys فراهم می‌کند.

    بازنویسی اسکریپت‌های ساخت

    اگر یک manifest کلید links داشته باشد، Cargo از بازنویسی اسکریپت ساخت مشخص‌شده با یک کتابخانهٔ سفارشی پشتیبانی می‌کند. هدف این قابلیت آن است که از اجرای کلِ اسکریپت ساخت مورد نظر جلوگیری شود و در عوض فراداده از پیش فراهم گردد.

    برای بازنویسی یک اسکریپت ساخت، پیکربندی زیر را در هر فایل config.toml قابل‌قبول قرار دهید.

    [target.x86_64-unknown-linux-gnu.foo]
rustc-link-lib = ["foo"]
rustc-link-search = ["/path/to/foo"]
rustc-flags = "-L /some/path"
rustc-cfg = ['key="value"']
rustc-env = {key = "value"}
rustc-cdylib-link-arg = ["…"]
metadata_key1 = "value"
metadata_key2 = "value"

    با این پیکربندی، اگر بسته‌ای اعلام کند که به foo پیوند می‌خورد، اسکریپت ساخت کامپایل یا اجرا نخواهد شد و به‌جای آن فرادادهٔ مشخص‌شده به کار می‌رود.

    کلیدهای warning، rerun-if-changed و rerun-if-env-changed نباید استفاده شوند و نادیده گرفته می‌شوند.

    Jobserver

    Cargo و rustc از پروتکل jobserver که برای GNU make توسعه یافته استفاده می‌کنند تا هم‌روندی (concurrency) را بین فرایندها هماهنگ کنند. این در اصل یک سمافور است که تعداد کارهایی را که هم‌زمان اجرا می‌شوند کنترل می‌کند. هم‌روندی را می‌توان با پرچم --jobs تنظیم کرد، که پیش‌فرضش تعداد CPUهای منطقی است.

    هر اسکریپت ساخت یک اسلات کار از Cargo به ارث می‌برد و باید بکوشد هنگام اجرا فقط از یک CPU استفاده کند. اگر اسکریپت بخواهد به‌طور موازی از CPUهای بیشتری استفاده کند، باید از crate jobserver برای هماهنگی با Cargo بهره ببرد.

    برای مثال، crate cc می‌تواند feature اختیاری parallel را فعال کند که از پروتکل jobserver استفاده می‌کند تا چند فایل C را هم‌زمان بسازد.
