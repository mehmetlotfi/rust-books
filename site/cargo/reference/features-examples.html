    نمونه‌هایی از Featureها

    در ادامه چند نمونهٔ واقعی از کاربرد featureها آورده شده است.

    کاهش زمان ساخت و حجم فایل‌ها

    برخی بسته‌ها از featureها استفاده می‌کنند تا در صورت فعال نبودن آن‌ها، اندازهٔ crate و زمان کامپایل کاهش یابد. چند نمونه:

    • syn یک crate محبوب برای تجزیهٔ کد Rust است. چون بسیار محبوب است، کاهش زمان کامپایل آن مفید است، زیرا بر پروژه‌های زیادی اثر می‌گذارد. این crate فهرستی با مستندات روشن از featureها دارد که می‌توان با آن‌ها مقدار کدی را که شامل می‌شود به حداقل رساند.
    • regex [چند feature]regex-features دارد که به‌خوبی مستند شده‌اند. حذف پشتیبانی از یونیکد می‌تواند حجم فایل حاصل را کم کند، چون می‌تواند برخی جدول‌های بزرگ را حذف کند.
    • winapi [تعداد زیادی]winapi-features feature دارد که مشخص می‌کنند کدام اتصال‌های (binding) API ویندوز را پشتیبانی کند.
    • web-sys نمونهٔ دیگری شبیه winapi است که سطح بسیار وسیعی از اتصال‌های API را فراهم می‌کند و با استفاده از featureها محدود می‌شود.

    گسترش رفتار

    بستهٔ serde_json یک feature به نام preserve_order دارد که رفتار نقشه‌های JSON را طوری تغییر می‌دهد که ترتیب درج کلیدها حفظ شود. توجه کنید که این feature یک وابستگی اختیاری یعنی indexmap را برای پیاده‌سازی رفتار جدید فعال می‌کند.

    هنگام تغییر رفتار به این شکل، مراقب باشید که تغییرات با SemVer سازگار باشند. یعنی فعال کردن feature نباید کدی را که معمولاً با خاموش بودن feature ساخته می‌شود، دچار شکست کند.

    پشتیبانی از no_std

    برخی بسته‌ها می‌خواهند هم از محیط‌های no_std و هم از محیط‌های std پشتیبانی کنند. این کار برای پشتیبانی از پلتفرم‌های نهفته و دارای منابع محدود مفید است، و در عین حال قابلیت‌های گسترده‌تر را برای پلتفرم‌هایی که کتابخانهٔ استاندارد کامل را پشتیبانی می‌کنند حفظ می‌کند.

    بستهٔ wasm-bindgen یک feature به نام std تعریف می‌کند که به‌طور پیش‌فرض فعال است. در ابتدای کتابخانه، attribute با نام no_std را بدون هیچ شرطی فعال می‌کند. این کار تضمین می‌کند که std و prelude مربوط به std به‌طور خودکار در دامنه نباشند. سپس در جاهای مختلف کد (نمونهٔ ۱، نمونهٔ ۲) از attributeهای #[cfg(feature = "std")] استفاده می‌کند تا قابلیت‌های اضافی را که به std نیاز دارند، به‌صورت شرطی فعال کند.

    صادر کردن مجدد featureهای وابستگی

    صادر کردن مجدد (re-export) featureهای یک وابستگی می‌تواند راحت باشد. این کار به کاربری که به crate وابسته است اجازه می‌دهد آن featureها را کنترل کند، بدون اینکه لازم باشد آن وابستگی‌ها را مستقیماً مشخص کند. برای مثال، regex featureهای بستهٔ regex_syntax را دوباره صادر می‌کند. کاربران regex لازم نیست از وجود بستهٔ regex_syntax خبر داشته باشند، اما همچنان می‌توانند به featureهای آن دسترسی داشته باشند.

    وندورینگ (vendoring) کتابخانه‌های C

    برخی بسته‌ها اتصال‌هایی (binding) به کتابخانه‌های رایج C فراهم می‌کنند (که گاهی crateهای «sys» نامیده می‌شوند). گاهی این بسته‌ها این انتخاب را به شما می‌دهند که از کتابخانهٔ C نصب‌شده روی سیستم استفاده کنید یا آن را از روی سورس بسازید. برای مثال، بستهٔ openssl یک feature به نام vendored دارد که feature هم‌نام vendored در openssl-sys را فعال می‌کند. build script بستهٔ openssl-sys مقداری منطق شرطی دارد که باعث می‌شود به‌جای استفاده از نسخهٔ سیستم، از یک نسخهٔ محلی سورس OpenSSL ساخته شود.

    بستهٔ curl-sys نمونهٔ دیگری است که در آن feature به نام static-curl باعث می‌شود libcurl از روی سورس ساخته شود. توجه کنید که این بسته همچنین یک feature به نام force-system-lib-on-osx دارد که آن را مجبور می‌کند از libcurl سیستم استفاده کند و تنظیم static-curl را نادیده بگیرد.

    اولویت featureها

    برخی بسته‌ها ممکن است featureهای متقابلاً ناسازگار داشته باشند. یک راه برای مدیریت این وضعیت، ترجیح دادن یک feature بر feature دیگر است. بستهٔ log نمونه‌ای از این است. این بسته چند feature برای انتخاب بیشینهٔ سطح لاگ‌گیری در زمان کامپایل دارد که اینجا توضیح داده شده‌اند. این بسته از cfg-if برای انتخاب اولویت استفاده می‌کند. اگر چند feature هم‌زمان فعال باشند، سطوح «max» بالاتر بر سطوح پایین‌تر ترجیح داده می‌شوند.

    بستهٔ همراه proc-macro

    برخی بسته‌ها یک proc-macro دارند که پیوندی تنگاتنگ با آن‌ها دارد. با این حال، همهٔ کاربران نیازی به استفاده از proc-macro نخواهند داشت. اگر proc-macro را به یک وابستگی اختیاری تبدیل کنید، می‌توانید به‌راحتی انتخاب کنید که شامل شود یا نه. این کار مفید است، زیرا گاهی نسخهٔ proc-macro باید با بستهٔ اصلی هماهنگ بماند و نمی‌خواهید کاربران را مجبور کنید هر دو وابستگی را مشخص کنند و آن‌ها را هماهنگ نگه دارند.

    نمونه‌ای از این serde است که یک feature به نام derive دارد و proc-macro با نام serde_derive را فعال می‌کند. crate با نام serde_derive بسیار تنگاتنگ به serde وابسته است، بنابراین از الزام نسخهٔ برابری (equals version requirement) استفاده می‌کند تا مطمئن شود هماهنگ می‌مانند.

    featureهای مختص nightly

    برخی بسته‌ها می‌خواهند با APIها یا قابلیت‌های زبانی که فقط در کانال nightly Rust در دسترس‌اند آزمایش کنند. با این حال ممکن است نخواهند کاربرانشان را ملزم کنند که آن‌ها هم از کانال nightly استفاده کنند. نمونه‌اش wasm-bindgen است که یک feature به نام nightly دارد و یک API گسترده‌تر را فعال می‌کند که از صفت نشانگر (marker trait) به نام Unsize استفاده می‌کند؛ این صفت در زمان نگارش فقط در کانال nightly در دسترس است.

    توجه کنید که این بسته در ریشهٔ crate از cfg_attr برای فعال کردن feature مربوط به nightly استفاده می‌کند. به یاد داشته باشید که attribute با نام feature ربطی به featureهای Cargo ندارد و برای فعال‌سازی صریح قابلیت‌های آزمایشی زبان به کار می‌رود.

    feature به نام simd_support در بستهٔ rand نمونهٔ دیگری است که به وابستگی‌ای تکیه دارد که فقط روی کانال nightly ساخته می‌شود.

    featureهای آزمایشی

    برخی بسته‌ها قابلیت‌های جدیدی دارند که می‌خواهند بدون تعهد به پایداری آن APIها با آن‌ها آزمایش کنند. این featureها معمولاً به‌عنوان آزمایشی مستند می‌شوند و بنابراین ممکن است در آینده، حتی در یک انتشار جزئی (minor)، تغییر کنند یا از کار بیفتند. نمونه‌اش بستهٔ async-std است که یک feature به نام unstable دارد و APIهای جدید را پشت یک دروازه قرار می‌دهد؛ مردم می‌توانند انتخاب کنند از آن‌ها استفاده کنند، اما ممکن است هنوز کاملاً آمادهٔ تکیه کردن نباشند.
