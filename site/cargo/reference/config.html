    Configuration

    این سند توضیح می‌دهد نظام پیکربندی Cargo چگونه کار می‌کند و چه کلیدها یا گزینه‌هایی در دسترس‌اند. برای پیکربندی یک بسته از طریق manifest آن، قالب manifest را ببینید.

    Hierarchical structure

    Cargo هم پیکربندی محلی برای یک بستهٔ خاص را می‌پذیرد و هم پیکربندی سراسری را. فایل‌های پیکربندی را در پوشهٔ فعلی و همهٔ پوشه‌های والد جست‌وجو می‌کند. برای مثال، اگر Cargo در /projects/foo/bar/baz فراخوانی شود، فایل‌های پیکربندی زیر به همین ترتیب بررسی و ادغام می‌شوند:

    • /projects/foo/bar/baz/.cargo/config.toml
    • /projects/foo/bar/.cargo/config.toml
    • /projects/foo/.cargo/config.toml
    • /projects/.cargo/config.toml
    • /.cargo/config.toml
    • $CARGO_HOME/config.toml which defaults to:
      • Windows: %USERPROFILE%\.cargo\config.toml
      • Unix: $HOME/.cargo/config.toml

    با این ساختار می‌توانید پیکربندی را برای هر بسته مشخص کنید و حتی آن را در کنترل نسخه قرار دهید. همچنین می‌توانید پیش‌فرض‌های شخصی خود را در یک فایل پیکربندی در پوشهٔ خانگی تعیین کنید.

    اگر یک کلید در چند فایل پیکربندی مشخص شده باشد، مقدارها با هم ادغام می‌شوند. برای عددها، رشته‌ها و مقادیر بولی، مقدار در پوشهٔ عمیق‌تر بر پوشه‌های پیشین ارجحیت دارد و پوشهٔ خانگی کمترین اولویت را دارد. آرایه‌ها به هم الحاق می‌شوند و موارد با اولویت بالاتر در آرایهٔ ادغام‌شده دیرتر قرار می‌گیرند.

    در حال حاضر، وقتی Cargo از یک workspace فراخوانی می‌شود، فایل‌های پیکربندی را از crateهای درون workspace نمی‌خواند. یعنی اگر workspace دو crate به نام‌های /projects/foo/bar/baz/mylib و /projects/foo/bar/baz/mybin داشته باشد و فایل‌های پیکربندی Cargo در /projects/foo/bar/baz/mylib/.cargo/config.toml و /projects/foo/bar/baz/mybin/.cargo/config.toml وجود داشته باشند، Cargo وقتی از ریشهٔ workspace (/projects/foo/bar/baz/) فراخوانی شود، آن فایل‌ها را نمی‌خواند.

    Note

    Cargo فایل‌های پیکربندی بدون پسوند .toml را هم می‌خواند، مثل .cargo/config. پشتیبانی از پسوند .toml در نسخهٔ 1.39 افزوده شد و شکل ترجیحی است. اگر هر دو فایل وجود داشته باشند، Cargo از فایل بدون پسوند استفاده می‌کند.

    Configuration format

    فایل‌های پیکربندی با قالب TOML نوشته می‌شوند (مثل manifest)، با جفت‌های کلید-مقدار ساده درون بخش‌ها (جدول‌ها). مطلب زیر نمای کلی سریعی از همهٔ تنظیمات است و توضیح‌های کامل در ادامه آمده است.

    paths = ["/path/to/override"] # path dependency overrides

[alias]     # command aliases
b = "build"
c = "check"
t = "test"
r = "run"
rr = "run --release"
recursive_example = "rr --example recursions"
space_example = ["run", "--release", "--", "\"command list\""]

rustc-wrapper = "…"           # run this wrapper instead of `rustc`
rustc-workspace-wrapper = "…" # run this wrapper instead of `rustc` for workspace members
rustdoc = "rustdoc"           # the doc generator tool
target = "tuple"              # build for the target tuple (ignored by `cargo install`)
profile = "dev"               # build using the specified profile (ignored by `cargo install`)
target-dir = "target"         # path of where to place generated artifacts
build-dir = "target"          # path of where to place intermediate build artifacts

    Environment variables

    علاوه بر فایل‌های پیکربندی TOML، Cargo را می‌توان از طریق متغیرهای محیطی هم پیکربندی کرد. برای هر کلید پیکربندی به شکل foo.bar می‌توان از متغیر محیطی CARGO_FOO_BAR هم برای تعیین مقدار استفاده کرد. کلیدها به حروف بزرگ تبدیل می‌شوند و نقطه‌ها و خط‌تیره‌ها به زیرخط. برای مثال کلید target.x86_64-unknown-linux-gnu.runner را می‌توان با متغیر محیطی CARGO_TARGET_X86_64_UNKNOWN_LINUX_GNU_RUNNER هم تعریف کرد.

    متغیرهای محیطی بر فایل‌های پیکربندی TOML اولویت دارند. فعلاً فقط مقادیر صحیح، بولی، رشته و برخی آرایه‌ها را می‌توان با متغیرهای محیطی تعریف کرد. توضیحات زیر نشان می‌دهند کدام کلیدها از متغیر محیطی پشتیبانی می‌کنند؛ بقیه به دلیل مشکلات فنی پشتیبانی نمی‌شوند.

    علاوه بر سازوکار بالا، Cargo چند متغیر محیطی مشخص دیگر را هم می‌شناسد.

    Command-line overrides

    Cargo همچنین بازنویسی‌های دلخواه پیکربندی را از طریق گزینهٔ خط فرمان --config می‌پذیرد. آرگومان باید به نحو TOML به شکل KEY=VALUE باشد یا به‌صورت مسیر یک فایل پیکربندی اضافی داده شود:

    # With `KEY=VALUE` in TOML syntax
cargo --config net.git-fetch-with-cli=true fetch

# With a path to a configuration file
cargo --config ./path/to/my/extra-config.toml fetch

    گزینهٔ --config را می‌توان چند بار مشخص کرد؛ در این صورت مقدارها به ترتیب از چپ به راست ادغام می‌شوند، با همان منطق ادغامی که وقتی چند فایل پیکربندی اعمال می‌شود به‌کار می‌رود. مقادیری که به این روش مشخص شوند بر متغیرهای محیطی اولویت دارند، و آن‌ها بر فایل‌های پیکربندی.

    وقتی گزینهٔ --config به‌صورت یک فایل پیکربندی اضافی داده شود، فایل پیکربندی بارگذاری‌شده از این راه از همان قواعد اولویتی پیروی می‌کند که گزینه‌های دیگری که مستقیماً با --config مشخص می‌شوند.

    چند مثال از شکل آن با نحو Bourne shell:

    # Most shells will require escaping.
cargo --config http.proxy=\"http://example.com\" …

# Spaces may be used.
cargo --config "net.git-fetch-with-cli = true" …

# TOML array example. Single quotes make it easier to read and write.
cargo --config 'build.rustdocflags = ["--html-in-header", "header.html"]' …

# Example of a complex TOML key.
cargo --config "target.'cfg(all(target_arch = \"arm\", target_os = \"none\"))'.runner = 'my-runner'" …

# Example of overriding a profile setting.
cargo --config profile.dev.package.image.opt-level=3 …

    افزودن فایل‌های پیکربندی اضافی

    پیکربندی می‌تواند با کلید سطح بالای include فایل‌های پیکربندی دیگر را هم شامل شود. این کار اشتراک پیکربندی بین چند پروژه یا تقسیم پیکربندی‌های پیچیده به چند فایل را ممکن می‌کند.

    include

    • نوع: آرایه‌ای از رشته‌ها یا جدول‌ها
    • Default: none
    • متغیر محیطی: پشتیبانی نمی‌شود

    فایل‌های پیکربندی اضافی را بارگذاری می‌کند. مسیرها نسبت به فایل پیکربندی‌ای هستند که آن‌ها را include می‌کند. فقط مسیرهایی که به .toml ختم می‌شوند پذیرفته می‌شوند.

    قالب‌های زیر پشتیبانی می‌شوند:

    # array of paths
include = [
    "frodo.toml",
    "samwise.toml",
]

# inline tables for more control
include = [
    { path = "required.toml" },
    { path = "optional.toml", optional = true },
]

    Note

    برای خوانایی بهتر و پرهیز از سردرگمی، توصیه می‌شود:

    • include را بالای فایل پیکربندی بگذارید
    • هر include را در یک خط جدا بنویسید تا تفاوت‌ها در کنترل نسخه واضح‌تر باشد
    • وقتی includeهای اختیاری لازم‌اند از نحو جدول درون‌خطی (inline table) استفاده کنید

    هنگام استفاده از نحو جدول، فیلدهای زیر پشتیبانی می‌شوند:

    • path (رشته، الزامی): مسیر فایل پیکربندی‌ای که باید include شود.
    • optional (بولی، پیش‌فرض: false): اگر true باشد، فایل‌های ناموجود به‌جای ایجاد خطا بی‌صدا نادیده گرفته می‌شوند.

    رفتار ادغام include با دیگر مقادیر پیکربندی فرق دارد:

    1. Config values are first loaded from the include paths.
      • فایل‌های include‌شده از چپ به راست بارگذاری می‌شوند، و مقادیر فایل‌های بعدی بر فایل‌های قبلی اولویت دارند.
      • اگر فایل‌های پیکربندی include‌شده خودشان هم کلید include داشته باشند، این مرحله به‌صورت بازگشتی تکرار می‌شود.
    2. سپس مقادیر خود فایل پیکربندی روی پیکربندی include‌شده ادغام می‌شوند و بالاترین اولویت را دارند.

    Config-relative paths

    مسیرها در فایل‌های پیکربندی می‌توانند مطلق، نسبی، یا یک نام ساده بدون هیچ جداکنندهٔ مسیر باشند. مسیر فایل‌های اجرایی بدون جداکنندهٔ مسیر برای جست‌وجوی فایل اجرایی از متغیر محیطی PATH استفاده می‌کند. مسیر غیر اجرایی‌ها نسبت به جایی است که مقدار پیکربندی تعریف شده است.

    به‌طور خاص، قواعد این‌هاست:

    • برای متغیرهای محیطی، مسیرها نسبت به پوشهٔ کاری فعلی‌اند.
    • برای مقادیر پیکربندی که مستقیماً از گزینهٔ --config KEY=VALUE بارگذاری می‌شوند، مسیرها نسبت به پوشهٔ کاری فعلی‌اند.
    • برای فایل‌های پیکربندی، مسیرها نسبت به پوشهٔ والدِ پوشه‌ای هستند که فایل‌های پیکربندی در آن تعریف شده‌اند، چه آن فایل‌ها از جست‌وجوی سلسله‌مراتبی آمده باشند و چه از گزینهٔ --config <path>.

    Important

    برای حفظ سازگاری با رفتار موجود جست‌وجوی .cargo/config.toml، عمداً چنین طراحی شده که مسیر در فایل پیکربندی‌ای که با --config <path> داده می‌شود هم نسبت به دو سطح بالاتر از خود فایل پیکربندی باشد.

    برای پرهیز از نتایج غیرمنتظره، قاعدهٔ سرانگشتی این است که فایل‌های پیکربندی اضافی را در همان سطحی بگذارید که .cargo/config.toml در پروژهٔ شما پیدا می‌شود. مثلاً برای پروژهٔ /my/project توصیه می‌شود فایل‌های پیکربندی را زیر /my/project/.cargo یا در پوشهٔ جدیدی در همان سطح بگذارید، مثل /my/project/.config.

    # Relative path examples.

[target.x86_64-unknown-linux-gnu]
runner = "foo"  # Searches `PATH` for `foo`.

[source.vendored-sources]
# Directory is relative to the parent where `.cargo/config.toml` is located.
# For example, `/my/project/.cargo/config.toml` would result in `/my/project/vendor`.
directory = "vendor"

    مسیر فایل‌های اجرایی همراه با آرگومان‌ها

    برخی دستورهای Cargo برنامه‌های خارجی را فراخوانی می‌کنند که می‌توان آن‌ها را به‌صورت یک مسیر و تعدادی آرگومان پیکربندی کرد.

    مقدار می‌تواند آرایه‌ای از رشته‌ها باشد مثل ['/path/to/program', 'somearg'] یا یک رشتهٔ جداشده با فاصله مثل '/path/to/program somearg'. اگر مسیر فایل اجرایی فاصله داشته باشد، باید از شکل آرایه‌ای استفاده کرد.

    اگر Cargo آرگومان‌های دیگری مثل مسیری برای باز‌کردن یا اجرا به برنامه بدهد، آن‌ها بعد از آخرین آرگومان مشخص‌شده در مقدار گزینه‌ای با این قالب داده می‌شوند. اگر برنامهٔ مشخص‌شده جداکنندهٔ مسیر نداشته باشد، Cargo فایل اجرایی آن را در PATH جست‌وجو می‌کند.

    Credentials

    مقادیر پیکربندی که اطلاعات حساس دارند در فایل $CARGO_HOME/credentials.toml ذخیره می‌شوند. وقتی از ارائه‌دهندهٔ اعتبارنامهٔ cargo:token استفاده شود، این فایل به‌طور خودکار توسط cargo login و cargo logout ساخته و به‌روز می‌شود.

    توکن‌ها در برخی دستورهای Cargo مثل cargo publish برای احراز هویت با registryهای راه‌دور استفاده می‌شوند. باید مراقب بود از توکن‌ها محافظت شود و محرمانه بمانند.

    قالب آن همان قالب فایل‌های پیکربندی Cargo است.

    [registry]
token = "…"   # Access token for crates.io

[registries.<name>]
token = "…"   # Access token for the named registry

    مثل بیشتر مقادیر پیکربندی دیگر، توکن‌ها را می‌توان با متغیرهای محیطی مشخص کرد. توکن crates.io را می‌توان با متغیر محیطی CARGO_REGISTRY_TOKEN مشخص کرد. توکن registryهای دیگر را می‌توان با متغیرهای محیطی به شکل CARGO_REGISTRIES_<name>_TOKEN مشخص کرد که در آن <name> نام registry با حروف بزرگ است.

    Note

    Cargo فایل‌های اعتبارنامه را هم بدون پسوند .toml می‌خواند و می‌نویسد، مثل .cargo/credentials. پشتیبانی از پسوند .toml در نسخهٔ 1.39 افزوده شد. در نسخهٔ 1.68، Cargo به‌طور پیش‌فرض در فایل دارای پسوند می‌نویسد. اما به دلیل سازگاری با نسخه‌های قبلی، وقتی هر دو فایل وجود داشته باشند، Cargo فایل بدون پسوند را می‌خواند و در آن می‌نویسد.

    Configuration keys

    این بخش همهٔ کلیدهای پیکربندی را مستند می‌کند. توضیح کلیدهایی که بخش متغیر دارند با قلاب‌های زاویه‌ای مشخص شده، مثل target.<tuple> که در آن بخش <tuple> می‌تواند هر target tuple مثل target.x86_64-pc-windows-msvc باشد.

    paths

    • نوع: آرایه‌ای از رشته‌ها (مسیرها)
    • Default: none
    • متغیر محیطی: پشتیبانی نمی‌شود

    آرایه‌ای از مسیرها به بسته‌های محلی که باید به‌عنوان بازنویسی (override) برای وابستگی‌ها استفاده شوند. برای اطلاعات بیشتر راهنمای بازنویسی وابستگی‌ها را ببینید.

    [alias]

    • نوع: رشته یا آرایه‌ای از رشته‌ها
    • Default: see below
    • Environment: CARGO_ALIAS_<name>

    جدول [alias] نام‌های مستعار (alias) دستورهای خط فرمان را تعریف می‌کند. برای مثال، اجرای cargo b نام مستعاری برای اجرای cargo build است. هر کلید در جدول زیردستور است و مقدار، دستور واقعی‌ای است که باید اجرا شود. مقدار می‌تواند آرایه‌ای از رشته‌ها باشد که عنصر اول دستور و بقیه آرگومان‌ها هستند. همچنین می‌تواند رشته‌ای باشد که با فاصله به زیردستور و آرگومان‌ها تقسیم می‌شود. نام‌های مستعار زیر در Cargo ازپیش‌تعبیه‌شده‌اند:

    [alias]
b = "build"
c = "check"
d = "doc"
t = "test"
r = "run"
rm = "remove"

    نام‌های مستعار اجازهٔ بازتعریف دستورهای داخلی موجود را ندارند.

    نام‌های مستعار بازگشتی‌اند:

    [alias]
rr = "run --release"
recursive_example = "rr --example recursions"

    [build]

    جدول [build] عملیات زمان ساخت و تنظیمات کامپایلر را کنترل می‌کند.

    build.warnings

    • Type: string
    • Default: "warn"
    • Environment: CARGO_BUILD_WARNINGS

    سطح مؤثر هشدارهای lint را برای بسته‌های محلی تنظیم می‌کند. سطح‌های مجاز عبارت‌اند از:

    • "warn": ادامهٔ تولید lintها به‌صورت هشدار (پیش‌فرض).
    • "allow": پنهان‌کردن lintها.
    • "deny": برای crate‌ای که هشدار lint دارد خطا تولید می‌کند. برای دیدن هشدارهای lint همهٔ crateهای وابسته از --keep-going استفاده کنید.

    فقط هشدارهایی که lint هستند (یعنی سطحشان قابل‌تنظیم است) تحت‌تأثیر قرار می‌گیرند، مثلاً هشدارهایی که lint نیستند یا هشدارهای وابستگی‌ها دست‌نخورده می‌مانند و از طریق --verbose --verbose قابل‌مشاهده‌اند.

    MSRV: از نسخهٔ 1.97 رعایت می‌شود.

    build.jobs

    • نوع: عدد صحیح یا رشته
    • پیش‌فرض: تعداد CPUهای منطقی
    • Environment: CARGO_BUILD_JOBS

    حداکثر تعداد فرایندهای کامپایلر را که به‌صورت موازی اجرا می‌شوند تعیین می‌کند. اگر منفی باشد، حداکثر تعداد فرایندهای کامپایلر برابر تعداد CPUهای منطقی به‌علاوهٔ مقدار داده‌شده می‌شود. نباید 0 باشد. اگر رشتهٔ default داده شود، مقدار به پیش‌فرض‌ها برمی‌گردد.

    می‌توان آن را با گزینهٔ خط فرمان --jobs بازنویسی کرد.

    build.rustc

    • نوع: رشته (مسیر برنامه)
    • Default: "rustc"
    • متغیر محیطی: CARGO_BUILD_RUSTC یا RUSTC

    فایل اجرایی مورد استفاده برای rustc را تعیین می‌کند.

    build.rustc-wrapper

    • نوع: رشته (مسیر برنامه)
    • Default: none
    • متغیر محیطی: CARGO_BUILD_RUSTC_WRAPPER یا RUSTC_WRAPPER

    wrapper‌ای را تعیین می‌کند که به‌جای rustc اجرا شود. اولین آرگومانی که به wrapper داده می‌شود مسیر فایل اجرایی واقعی است (یعنی build.rustc اگر تنظیم شده باشد، در غیر این صورت "rustc").

    build.rustc-workspace-wrapper

    • نوع: رشته (مسیر برنامه)
    • Default: none
    • متغیر محیطی: CARGO_BUILD_RUSTC_WORKSPACE_WRAPPER یا RUSTC_WORKSPACE_WRAPPER

    wrapper‌ای را تعیین می‌کند که به‌جای rustc فقط برای اعضای workspace اجرا شود. در پروژهٔ تک‌بسته‌ای بدون workspace، همان بسته workspace به حساب می‌آید. اولین آرگومانی که به wrapper داده می‌شود مسیر فایل اجرایی واقعی است (یعنی build.rustc اگر تنظیم شده باشد، در غیر این صورت "rustc"). این بر هش نام فایل اثر می‌گذارد تا آرتیفکت‌های تولیدشده توسط wrapper جداگانه cache شوند.

    اگر هم rustc-wrapper و هم rustc-workspace-wrapper تنظیم شده باشند، تو در تو اجرا می‌شوند: فراخوانی نهایی $RUSTC_WRAPPER $RUSTC_WORKSPACE_WRAPPER $RUSTC است.

    build.rustdoc

    • نوع: رشته (مسیر برنامه)
    • Default: "rustdoc"
    • متغیر محیطی: CARGO_BUILD_RUSTDOC یا RUSTDOC

    فایل اجرایی مورد استفاده برای rustdoc را تعیین می‌کند.

    build.target

    • نوع: رشته یا آرایه‌ای از رشته‌ها
    • Default: host platform
    • Environment: CARGO_BUILD_TARGET

    سه‌تایی‌های پلتفرم هدف پیش‌فرض برای کامپایل.

    Possible values:

    • هر هدف پشتیبانی‌شده در rustc --print target-list.
    • "host-tuple"، که به‌طور داخلی با هدف میزبان جایگزین می‌شود. این برای وقتی مفید است که برخی crateها را cross-compile می‌کنید و نمی‌خواهید ماشین میزبان را به‌عنوان هدف مشخص کنید (مثلاً یک xtask در پروژهٔ مشترکی که میزبان‌های زیادی روی آن کار می‌کنند).
    • مسیر یک مشخصات هدف سفارشی. برای اطلاعات بیشتر مسیر جست‌وجوی هدف سفارشی را ببینید.

    می‌توان آن را با گزینهٔ خط فرمان --target بازنویسی کرد.

    [build]
target = ["x86_64-unknown-linux-gnu", "i686-unknown-linux-gnu"]

    build.profile

    • Type: string
    • پیش‌فرض: "test" اگر cargo test باشد، در غیر این صورت "dev"
    • Environment: CARGO_BUILD_PROFILE

    profile پیش‌فرضی که با آن کامپایل می‌شود.

    می‌توان آن را با گزینه‌های خط فرمان --release یا --profile بازنویسی کرد.

    [build]
profile = "debug"

    build.target-dir

    • Type: string (path)
    • Default: "target"
    • متغیر محیطی: CARGO_BUILD_TARGET_DIR یا CARGO_TARGET_DIR

    مسیری که همهٔ خروجی‌های کامپایلر در آن قرار می‌گیرد. اگر مشخص نشود، پیش‌فرض پوشه‌ای به نام target در ریشهٔ workspace است.

    build.build-dir

    • Type: string (path)
    • پیش‌فرض: مقدار build.target-dir
    • Environment: CARGO_BUILD_BUILD_DIR

    پوشه‌ای که آرتیفکت‌های میانی ساخت در آن ذخیره می‌شوند. آرتیفکت‌های میانی توسط Rustc/Cargo در فرایند ساخت تولید می‌شوند.

    این گزینه از قالب‌بندی مسیر (path templating) پشتیبانی می‌کند.

    Available template variables:

    • {workspace-root} به ریشهٔ workspace فعلی تبدیل می‌شود.
    • {cargo-cache-home} به CARGO_HOME تبدیل می‌شود
    • {workspace-path-hash} به هشی از مسیر manifest تبدیل می‌شود

    برای اطلاعات بیشتر مستندات cache ساخت را ببینید.

    build.rustflags

    • نوع: رشته یا آرایه‌ای از رشته‌ها
    • Default: none
    • متغیر محیطی: CARGO_BUILD_RUSTFLAGS یا CARGO_ENCODED_RUSTFLAGS یا RUSTFLAGS

    پرچم‌های اضافی خط فرمان که به rustc داده می‌شوند. مقدار می‌تواند آرایه‌ای از رشته‌ها یا یک رشتهٔ جداشده با فاصله باشد.

    چهار منبع متقابلاً ناسازگار برای پرچم‌های اضافی وجود دارد. به ترتیب بررسی می‌شوند و اولینی که یافت شود استفاده می‌شود:

    1. CARGO_ENCODED_RUSTFLAGS environment variable.
    2. RUSTFLAGS environment variable.
    3. همهٔ ورودی‌های پیکربندی منطبق target.<tuple>.rustflags و target.<cfg>.rustflags که به هم متصل می‌شوند.
    4. build.rustflags config value.

    پرچم‌های اضافی را می‌توان با دستور cargo rustc هم داد.

    اگر پرچم --target (یا build.target) استفاده شود، پرچم‌ها فقط به کامپایلر برای آن هدف داده می‌شوند. چیزهایی که برای میزبان ساخته می‌شوند، مثل اسکریپت‌های ساخت یا proc macroها، این آرگومان‌ها را دریافت نمی‌کنند. بدون --target، پرچم‌ها به همهٔ فراخوانی‌های کامپایلر داده می‌شوند (از جمله اسکریپت‌های ساخت و proc macroها) چون وابستگی‌ها مشترک‌اند. اگر آرگومان‌هایی دارید که نمی‌خواهید به اسکریپت‌های ساخت یا proc macroها داده شوند و برای میزبان می‌سازید، --target را با host tuple بدهید.

    توصیه نمی‌شود پرچم‌هایی را بدهید که معمولاً خود Cargo مدیریت می‌کند. برای مثال، پرچم‌هایی که از profileها می‌آیند بهتر است با تنظیم گزینهٔ مناسب profile اعمال شوند.

    Caution

    به‌دلیل ماهیت سطح پایین دادن مستقیم پرچم‌ها به کامپایلر، این کار ممکن است با نسخه‌های آیندهٔ Cargo تداخل پیدا کند، چون ممکن است خود همان پرچم‌ها یا مشابه آن‌ها را بدهند و با پرچم‌هایی که شما مشخص می‌کنید تداخل کنند. این حوزه‌ای است که Cargo ممکن است همیشه سازگار با نسخه‌های قبلی نباشد.

    build.incremental

    • Type: bool
    • پیش‌فرض: از profile
    • متغیر محیطی: CARGO_BUILD_INCREMENTAL یا CARGO_INCREMENTAL

    اینکه آیا کامپایل افزایشی انجام شود یا نه.

    به‌طور پیش‌فرض، متغیرهای مشخص‌شده مقادیری را که از قبل در محیط وجود دارند بازنویسی نمی‌کنند. این رفتار را می‌توان با تنظیم پرچم force تغییر داد.

    [env]
TMPDIR = { value = "/home/tmp", force = true }
OPENSSL_DIR = { value = "vendor/openssl", relative = true }

    کنترل می‌کند هر چند وقت یک‌بار، وقتی گزارش future incompat در دسترس است، اعلانی در ترمینال نمایش داده شود. مقادیر ممکن:

    • always (پیش‌فرض): هر بار که دستوری (مثلاً cargo build) گزارش future incompat تولید کند، اعلان نمایش داده می‌شود
    • never: هرگز اعلان نمایش داده نمی‌شود

    [cache]

    جدول [cache] تنظیمات cacheهای cargo را تعریف می‌کند.

    Global caches

    هنگام اجرای دستورهای cargo، Cargo به‌طور خودکار پیگیری می‌کند کدام فایل‌ها را درون cache سراسری استفاده می‌کنید. Cargo به‌طور دوره‌ای فایل‌هایی را که مدتی استفاده نشده‌اند پاک می‌کند. فایل‌هایی را که باید از شبکه دانلود شوند اگر ۳ ماه استفاده نشده باشند پاک می‌کند. فایل‌هایی که بدون دسترسی به شبکه قابل‌تولیدند اگر ۱ ماه استفاده نشده باشند پاک می‌شوند.

    پاک‌سازی خودکار فایل‌ها فقط هنگام اجرای دستورهایی رخ می‌دهد که از قبل کار قابل‌توجهی انجام می‌دهند، مثل همهٔ دستورهای ساخت (cargo build، cargo test، cargo check و غیره) و cargo fetch.

    اگر cargo آفلاین باشد، مثلاً با --offline یا --frozen، پاک‌سازی خودکار غیرفعال می‌شود تا آرتیفکت‌هایی که ممکن است در آفلاین‌بودن طولانی‌مدت لازم شوند پاک نشوند.

    Note

    این پیگیری فعلاً فقط برای cache سراسری در پوشهٔ خانگی Cargo پیاده‌سازی شده است. این شامل فهرست‌های registry و فایل‌های منبعی است که از registryها و وابستگی‌های git دانلود می‌شوند. پشتیبانی از پیگیری آرتیفکت‌های ساخت هنوز پیاده‌سازی نشده و در cargo#13136 پیگیری می‌شود.

    علاوه بر این، یک قابلیت ناپایدار برای پشتیبانی از راه‌اندازی دستی پاک‌سازی cache و سفارشی‌سازی بیشتر گزینه‌های پیکربندی وجود دارد. برای اطلاعات بیشتر فصل قابلیت‌های ناپایدار را ببینید.

    cache.auto-clean-frequency

    • Type: string
    • Default: "1 day"
    • Environment: CARGO_CACHE_AUTO_CLEAN_FREQUENCY

    این گزینه تعیین می‌کند Cargo هر چند وقت یک‌بار فایل‌های استفاده‌نشده را از cache سراسری به‌طور خودکار پاک کند. این گزینه تعیین نمی‌کند فایل‌ها چقدر باید قدیمی باشند؛ آن آستانه‌ها در بالا توضیح داده شده‌اند.

    تنظیمات زیر را پشتیبانی می‌کند:

    • "never" — هرگز فایل‌های قدیمی را پاک نمی‌کند.
    • "always" — هر بار که Cargo اجرا می‌شود بررسی می‌کند فایل‌های قدیمی را پاک کند.
    • یک عدد صحیح به‌دنبال «seconds»، «minutes»، «hours»، «days»، «weeks» یا «months» — حداکثر یک‌بار در بازهٔ زمانی داده‌شده بررسی می‌کند فایل‌های قدیمی را پاک کند.

    [http]

    جدول [http] تنظیمات رفتار HTTP را تعریف می‌کند. این شامل دریافت وابستگی‌های crate و دسترسی به مخازن git راه‌دور است.

    http.debug

    • Type: boolean
    • Default: false
    • Environment: CARGO_HTTP_DEBUG

    اگر true باشد، اشکال‌زدایی درخواست‌های HTTP را فعال می‌کند. اطلاعات اشکال‌زدایی را می‌توان با تنظیم متغیر محیطی CARGO_LOG=network=debug دید (یا برای اطلاعات بیشتر از network=trace استفاده کنید).

    هنگام انتشار لاگ‌های این خروجی در جای عمومی محتاط باشید. خروجی ممکن است سرایندهایی با توکن‌های احراز هویت داشته باشد که نمی‌خواهید فاش شوند! حتماً لاگ‌ها را پیش از انتشار بررسی کنید.

    http.proxy

    • Type: string
    • Default: none
    • متغیر محیطی: CARGO_HTTP_PROXY یا HTTPS_PROXY یا https_proxy یا http_proxy

    یک پروکسی HTTP و HTTPS را برای استفاده تنظیم می‌کند. قالب آن قالب libcurl است، مثل [protocol://]host[:port]. اگر تنظیم نشود، Cargo تنظیم http.proxy را در پیکربندی سراسری git شما هم بررسی می‌کند. اگر هیچ‌کدام تنظیم نشده باشند، متغیرهای محیطی HTTPS_PROXY یا https_proxy پروکسی را برای درخواست‌های HTTPS تعیین می‌کنند و http_proxy آن را برای درخواست‌های HTTP تعیین می‌کند.

    http.timeout

    • Type: integer
    • Default: 30
    • متغیر محیطی: CARGO_HTTP_TIMEOUT یا HTTP_TIMEOUT

    مهلت هر درخواست HTTP را بر حسب ثانیه تنظیم می‌کند.

    http.cainfo

    • Type: string (path)
    • Default: none
    • Environment: CARGO_HTTP_CAINFO

    مسیر فایل بستهٔ مرجع صدور گواهی (CA) که برای تأیید گواهی‌های TLS استفاده می‌شود. اگر مشخص نشود، Cargo سعی می‌کند از گواهی‌های سیستم استفاده کند.

    http.proxy-cainfo

    • Type: string (path)
    • پیش‌فرض: اگر تنظیم نشود به http.cainfo برمی‌گردد
    • Environment: CARGO_HTTP_PROXY_CAINFO

    مسیر فایل بستهٔ مرجع صدور گواهی (CA) که برای تأیید گواهی‌های TLS پروکسی استفاده می‌شود.

    http.check-revoke

    • Type: boolean
    • پیش‌فرض: true (ویندوز)، false (بقیه)
    • Environment: CARGO_HTTP_CHECK_REVOKE

    این تعیین می‌کند آیا بررسی ابطال گواهی TLS انجام شود یا نه. این فقط در ویندوز کار می‌کند.

    http.ssl-version

    • نوع: رشته یا جدول min/max
    • Default: none
    • Environment: CARGO_HTTP_SSL_VERSION

    این حداقل نسخهٔ TLS مورد استفاده را تنظیم می‌کند. یک رشته می‌گیرد، با یکی از مقادیر ممکن "default"، "tlsv1"، "tlsv1.0"، "tlsv1.1"، "tlsv1.2" یا "tlsv1.3".

    همچنین می‌تواند جدولی با دو کلید min و max بگیرد که هر کدام مقدار رشته‌ای از همین نوع می‌گیرند و بازهٔ حداقل و حداکثر نسخه‌های TLS مورد استفاده را مشخص می‌کنند.

    پیش‌فرض، حداقل نسخهٔ "tlsv1.0" و حداکثر جدیدترین نسخهٔ پشتیبانی‌شده در پلتفرم شماست، که معمولاً "tlsv1.3" است.

    http.low-speed-limit

    • Type: integer
    • Default: 10
    • Environment: CARGO_HTTP_LOW_SPEED_LIMIT

    این تنظیم رفتار مهلت‌زمانی (timeout) برای اتصال‌های کند را کنترل می‌کند. اگر میانگین سرعت انتقال بر حسب بایت در ثانیه برای http.timeout ثانیه (پیش‌فرض ۳۰ ثانیه) کمتر از مقدار داده‌شده باشد، اتصال بیش از حد کند در نظر گرفته می‌شود و Cargo آن را رها کرده و دوباره تلاش می‌کند.

    http.multiplexing

    • Type: boolean
    • Default: true
    • Environment: CARGO_HTTP_MULTIPLEXING

    وقتی true باشد، Cargo سعی می‌کند از پروتکل HTTP2 با multiplexing استفاده کند. این به چند درخواست اجازه می‌دهد از یک اتصال استفاده کنند و معمولاً عملکرد دریافت چند فایل را بهبود می‌دهد. اگر false باشد، Cargo از HTTP 1.1 بدون pipelining استفاده می‌کند.

    http.user-agent

    • Type: string
    • Default: Cargo’s version
    • Environment: CARGO_HTTP_USER_AGENT

    یک سرایند user-agent سفارشی برای استفاده مشخص می‌کند. پیش‌فرض در صورت مشخص‌نشدن رشته‌ای است که نسخهٔ Cargo را در بر دارد.

    [install]

    جدول [install] پیش‌فرض‌های دستور cargo install را تعریف می‌کند.

    install.root

    • Type: string (path)
    • پیش‌فرض: پوشهٔ خانگی Cargo
    • Environment: CARGO_INSTALL_ROOT

    مسیر پوشهٔ ریشه را برای نصب فایل‌های اجرایی توسط cargo install تنظیم می‌کند. فایل‌های اجرایی در پوشهٔ bin زیر ریشه قرار می‌گیرند.

    برای پیگیری اطلاعات فایل‌های اجرایی نصب‌شده، چند فایل اضافی مثل .crates.toml و .crates2.json هم زیر همین ریشه ساخته می‌شوند.

    پیش‌فرض در صورت مشخص‌نشدن، پوشهٔ خانگی Cargo است (پیش‌فرض .cargo در پوشهٔ خانگی شما).

    می‌توان آن را با گزینهٔ خط فرمان --root بازنویسی کرد.

    install.profile

    • Type: string
    • Default: "release"
    • Environment: CARGO_INSTALL_PROFILE

    profile پیش‌فرضی که cargo install با آن کامپایل می‌کند.

    می‌توان آن را با گزینه‌های خط فرمان --debug یا --profile بازنویسی کرد.

    [install]
profile = "tool"

[profile.tool]
inherits = "release"
lto = true

    MSRV: از نسخهٔ 1.100 رعایت می‌شود.

    [net]

    جدول [net] پیکربندی شبکه را کنترل می‌کند.

    net.retry

    • Type: integer
    • Default: 3
    • Environment: CARGO_NET_RETRY

    تعداد دفعات تلاش مجدد برای خطاهای شبکه‌ای که احتمالاً گذرا (spurious) هستند.

    net.git-fetch-with-cli

    • Type: boolean
    • Default: auto-detect
    • Environment: CARGO_NET_GIT_FETCH_WITH_CLI

    اگر این true باشد، Cargo برای دریافت فهرست‌های registry و وابستگی‌های git از فایل اجرایی git استفاده می‌کند. اگر false باشد، از کتابخانهٔ git داخلی استفاده می‌کند.

    تنظیم این روی true وقتی می‌تواند مفید باشد که نیازهای احراز هویت ویژه‌ای دارید که Cargo پشتیبانی نمی‌کند. برای اطلاعات بیشتر دربارهٔ راه‌اندازی احراز هویت git، احراز هویت Git را ببینید.

    net.offline

    • Type: boolean
    • Default: false
    • Environment: CARGO_NET_OFFLINE

    اگر این true باشد، Cargo از دسترسی به شبکه خودداری می‌کند و سعی می‌کند با داده‌های cache‌شدهٔ محلی ادامه دهد. اگر false باشد، Cargo در صورت نیاز به شبکه دسترسی پیدا می‌کند و اگر با خطای شبکه روبه‌رو شود، خطا تولید می‌کند.

    می‌توان آن را با گزینهٔ خط فرمان --offline بازنویسی کرد.

    net.ssh

    جدول [net.ssh] تنظیمات اتصال‌های SSH را در بر دارد.

    net.ssh.known-hosts

    • نوع: آرایه‌ای از رشته‌ها
    • Default: see description
    • متغیر محیطی: پشتیبانی نمی‌شود

    آرایهٔ known-hosts فهرستی از کلیدهای میزبان SSH را دربر دارد که باید هنگام اتصال به سرور SSH (مثلاً برای وابستگی‌های git از طریق SSH) معتبر پذیرفته شوند. هر ورودی باید رشته‌ای با قالبی مشابه فایل‌های known_hosts در OpenSSH باشد. هر رشته باید با یک یا چند نام میزبان که با ویرگول جدا شده‌اند، یک فاصله، نام نوع کلید، یک فاصله و کلید رمزگذاری‌شده با base64 شروع شود. برای مثال:

    [net.ssh]
known-hosts = [
    "example.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIFO4Q5T0UV0SQevair9PFwoxY9dl4pQl3u5phoqJH3cF"
]

    Cargo سعی می‌کند کلیدهای میزبان شناخته‌شده را از مکان‌های رایج پشتیبانی‌شده در OpenSSH بارگذاری کند و آن‌ها را با هر کلید فهرست‌شده در فایل پیکربندی Cargo ترکیب می‌کند. اگر هر ورودی منطبق کلید درست داشته باشد، اتصال مجاز خواهد بود.

    Cargo کلیدهای میزبان github.com را از پیش دارد. اگر آن‌ها تغییر کنند، می‌توانید کلیدهای جدید را به config یا فایل known_hosts اضافه کنید.

    برای جزئیات بیشتر احراز هویت Git را ببینید.

    [patch]

    همان‌طور که می‌توانید وابستگی‌ها را با [patch] در Cargo.toml بازنویسی کنید، می‌توانید آن‌ها را در فایل پیکربندی cargo هم بازنویسی کنید تا آن patchها روی هر ساخت متأثر اعمال شوند. قالب آن با قالب Cargo.toml یکسان است.

    از آنجا که فایل‌های .cargo/config.toml معمولاً در کنترل نسخه ثبت نمی‌شوند، بهتر است تا حد امکان patch را با Cargo.toml انجام دهید تا دیگر توسعه‌دهندگان بتوانند crate شما را در محیط‌های خودشان کامپایل کنند. patch‌کردن از طریق فایل‌های پیکربندی cargo معمولاً فقط وقتی مناسب است که بخش patch به‌طور خودکار توسط یک ابزار ساخت خارجی تولید شود.

    اگر یک وابستگی هم در فایل پیکربندی cargo و هم در فایل Cargo.toml patch شده باشد، patch فایل پیکربندی استفاده می‌شود. اگر چند فایل پیکربندی یک وابستگی را patch کنند، ادغام استاندارد پیکربندی cargo به‌کار می‌رود که مقداری را ترجیح می‌دهد که نزدیک‌ترین به پوشهٔ فعلی تعریف شده است و $HOME/.cargo/config.toml کمترین اولویت را دارد.

    وابستگی‌های path نسبی در چنین بخش [patch]ای نسبت به فایل پیکربندی‌ای که در آن آمده‌اند حل می‌شوند.

    [resolver]

    جدول [resolver] رفتار حل وابستگی را برای توسعهٔ محلی بازنویسی می‌کند (مثلاً cargo install را شامل نمی‌شود).

    • Type: string (path)
    • Default: <workspace_root>/Cargo.lock
    • Environment: CARGO_RESOLVER_LOCKFILE_PATH

    مسیر lockfile مورد استفاده هنگام حل وابستگی‌ها را مشخص می‌کند. این گزینه هنگام کار با پوشه‌های منبع فقط‌خواندنی مفید است.

    resolver.incompatible-rust-versions

    • Type: string
    • Default: See resolver docs
    • Environment: CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS

    هنگام حل اینکه از کدام نسخهٔ یک وابستگی استفاده شود، مشخص می‌کند با نسخه‌هایی که package.rust-version ناسازگار دارند چگونه رفتار شود. مقادیر عبارت‌اند از:

    • allow: نسخه‌های ناسازگار با rust-version مثل هر نسخهٔ دیگر در نظر گرفته می‌شوند
    • fallback: نسخه‌های ناسازگار با rust-version فقط وقتی در نظر گرفته می‌شوند که هیچ نسخهٔ دیگری منطبق نباشد

    می‌توان آن را بازنویسی کرد با

    • --ignore-rust-version CLI option
    • تنظیم نیازمندی نسخهٔ وابستگی بالاتر از هر نسخه‌ای که rust-version سازگار دارد
    • مشخص‌کردن نسخه برای cargo update با --precise

    برای جزئیات بیشتر فصل حل‌کننده (resolver) را ببینید.

    MSRV:

    • allow در هر نسخه‌ای پشتیبانی می‌شود
    • fallback از نسخهٔ 1.84 رعایت می‌شود

    resolver.incompatible-publish-age

    • Type: string
    • Default: "deny"
    • Environment: CARGO_RESOLVER_INCOMPATIBLE_PUBLISH_AGE

    • allow: نسخه‌های ناسازگار از نظر pubtime مثل هر نسخهٔ دیگر در نظر گرفته می‌شوند
    • deny: نسخه‌های ناسازگار از نظر pubtime نادیده گرفته می‌شوند، مگر اینکه از قبل در فایل lock وجود داشته باشند

    [target]

    جدول [target] برای مشخص‌کردن تنظیمات اهداف پلتفرم‌های خاص به‌کار می‌رود. شامل یک زیرجدول است که یا tuple پلتفرم یا یک عبارت cfg() است. مقادیر داده‌شده وقتی استفاده می‌شوند که پلتفرم هدف با مقدار <tuple> یا عبارت <cfg> مطابقت داشته باشد.

    [target.thumbv7m-none-eabi]
linker = "arm-none-eabi-gcc"
runner = "my-emulator"
rustflags = ["…", "…"]

[target.'cfg(all(target_arch = "arm", target_os = "none"))']
runner = "my-arm-wrapper"
rustflags = ["…", "…"]

    مقادیر cfg از مقادیر داخلی کامپایلر می‌آیند (برای دیدن آن‌ها rustc --print=cfg را اجرا کنید) و از پرچم‌های اضافی --cfg که به rustc داده می‌شوند (مثل آن‌هایی که در RUSTFLAGS تعریف می‌شوند). سعی نکنید با debug_assertions، test، featureهای Cargo مثل feature="foo" یا مقادیری که اسکریپت‌های ساخت تنظیم می‌کنند مطابقت دهید.

    اگر از فایل JSON مشخصات هدف استفاده می‌کنید، مقدار <tuple> نام فایل بدون پسوند است. مثلاً --target foo/bar.json با [target.bar] مطابقت می‌کند.

    target.<tuple>.ar

    این گزینه منسوخ و بی‌استفاده است.

    target.<tuple>.linker

    • نوع: رشته (مسیر برنامه)
    • Default: none
    • Environment: CARGO_TARGET_<tuple>_LINKER

    لینکری را مشخص می‌کند که هنگام کامپایل برای <tuple> به rustc داده می‌شود (از طریق -C linker). به‌طور پیش‌فرض لینکر بازنویسی نمی‌شود.

    target.<cfg>.linker

    این مشابه لینکر هدف است، اما با استفاده از یک عبارت cfg(). اگر هم لینکر <tuple> و هم <cfg> منطبق باشند، <tuple> اولویت دارد. اگر بیش از یک لینکر <cfg> با هدف فعلی مطابقت کند، خطاست.

    target.<tuple>.runner

    • نوع: رشته یا آرایه‌ای از رشته‌ها (مسیر برنامه همراه با آرگومان‌ها)
    • Default: none
    • Environment: CARGO_TARGET_<tuple>_RUNNER

    اگر runner ارائه شود، فایل‌های اجرایی هدف <tuple> با فراخوانی runner مشخص‌شده اجرا می‌شوند و فایل اجرایی واقعی به‌عنوان آرگومان به آن داده می‌شود. این برای دستورهای cargo run، cargo test و cargo bench صدق می‌کند. به‌طور پیش‌فرض فایل‌های اجرایی کامپایل‌شده مستقیماً اجرا می‌شوند.

    target.<cfg>.runner

    این مشابه runner هدف است، اما با استفاده از یک عبارت cfg(). اگر هم runner <tuple> و هم <cfg> منطبق باشند، <tuple> اولویت دارد. اگر بیش از یک runner <cfg> با هدف فعلی مطابقت کند، خطاست.

    target.<tuple>.rustflags

    • نوع: رشته یا آرایه‌ای از رشته‌ها
    • Default: none
    • Environment: CARGO_TARGET_<tuple>_RUSTFLAGS

    مجموعه‌ای از پرچم‌های سفارشی را برای این <tuple> به کامپایلر می‌دهد. مقدار می‌تواند آرایه‌ای از رشته‌ها یا رشته‌ای جداشده با فاصله باشد.

    برای جزئیات بیشتر دربارهٔ راه‌های مختلف مشخص‌کردن پرچم‌های اضافی، build.rustflags را ببینید.

    target.<cfg>.rustflags

    این مشابه rustflags هدف است، اما با استفاده از یک عبارت cfg(). اگر چند ورودی <cfg> و <tuple> با هدف فعلی مطابقت کنند، پرچم‌ها به هم متصل می‌شوند.

    target.<tuple>.rustdocflags

    • نوع: رشته یا آرایه‌ای از رشته‌ها
    • Default: none
    • Environment: CARGO_TARGET_<tuple>_RUSTDOCFLAGS

    مجموعه‌ای از پرچم‌های سفارشی را برای این <tuple> به کامپایلر می‌دهد. مقدار می‌تواند آرایه‌ای از رشته‌ها یا رشته‌ای جداشده با فاصله باشد.

    برای جزئیات بیشتر دربارهٔ راه‌های مختلف مشخص‌کردن پرچم‌های اضافی، build.rustdocflags را ببینید.

    target.<cfg>.rustdocflags

    این مشابه rustdocflags هدف است، اما با استفاده از یک عبارت cfg(). اگر چند ورودی <cfg> و <tuple> با هدف فعلی مطابقت کنند، پرچم‌ها به هم متصل می‌شوند.

    کنترل می‌کند نوار پیشرفت در ترمینال نمایش داده شود یا نه. مقادیر ممکن:

    • auto (پیش‌فرض): هوشمندانه حدس می‌زند که نوار پیشرفت نمایش داده شود یا نه.
    • always: همیشه نوار پیشرفت را نمایش می‌دهد.
    • never: هرگز نوار پیشرفت را نمایش نمی‌دهد.

    term.progress.width

    • Type: integer
    • Default: none
    • Environment: CARGO_TERM_PROGRESS_WIDTH

    پهنای نوار پیشرفت را تنظیم می‌کند.

    term.progress.term-integration

    • Type: bool
    • Default: auto-detect
    • Environment: CARGO_TERM_PROGRESS_TERM_INTEGRATION
