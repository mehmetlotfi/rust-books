    حل وابستگی‌ها (Dependency Resolution)

    یکی از وظایف اصلی Cargo این است که بر اساس نیازمندی‌های نسخه‌ای که در هر بسته مشخص شده‌اند، تعیین کند از چه نسخه‌هایی از وابستگی‌ها استفاده شود. این فرایند «حل وابستگی‌ها» (dependency resolution) نام دارد و توسط «حل‌کننده» (resolver) انجام می‌شود. نتیجهٔ حل در فایل Cargo.lock ذخیره می‌شود که وابستگی‌ها را روی نسخه‌های مشخصی «قفل» می‌کند و آن‌ها را در طول زمان ثابت نگه می‌دارد. از دستور cargo tree می‌توان برای نمایش بصری نتیجهٔ resolver استفاده کرد.

    قیدها و قواعد اکتشافی (Constraints and Heuristics)

    در بسیاری از موارد، تنها یک حل وابستگی «بهینه» وجود ندارد. resolver تحت قیدها و قواعد اکتشافی (heuristic) گوناگونی کار می‌کند تا حلی بیابد که به‌طور کلی قابل‌اعمال باشد. برای درک نحوهٔ تعامل این‌ها با یکدیگر، داشتن شناختی کلی از نحوهٔ کار حل وابستگی‌ها مفید است.

    این شبه‌کد تقریبی از کار resolver در Cargo را نشان می‌دهد:

    pub fn resolve(workspace: &[Package], policy: Policy) -> Option<ResolveGraph> {
    let dep_queue = Queue::new(workspace);
    let resolved = ResolveGraph::new();
    resolve_next(dep_queue, resolved, policy)
}

fn resolve_next(dep_queue: Queue, resolved: ResolveGraph, policy: Policy) -> Option<ResolveGraph> {
    let Some(dep_spec) = policy.pick_next_dep(&mut dep_queue) else {
        // Done
        return Some(resolved);
    };

    if let Some(resolved) = policy.try_unify_version(dep_spec, resolved.clone()) {
        return Some(resolved);
    }

    let dep_versions = dep_spec.lookup_versions()?;
    let mut dep_versions = policy.filter_versions(dep_spec, dep_versions);
    while let Some(dep_version) = policy.pick_next_version(&mut dep_versions) {
        if policy.needs_version_unification(&dep_version, &resolved) {
            continue;
        }

        let mut dep_queue = dep_queue.clone();
        dep_queue.enqueue(&dep_version.dependencies);
        let mut resolved = resolved.clone();
        resolved.register(dep_version);
        if let Some(resolved) = resolve_next(dep_queue, resolved, policy) {
            return Some(resolved);
        }
    }

    // No valid solution found, backtrack and `pick_next_version`
    None
}

    مراحل کلیدی:

    • پیمایش وابستگی‌ها (pick_next_dep): ترتیب پیمایش وابستگی‌ها می‌تواند بر نحوهٔ حل نیازمندی‌های نسخهٔ مرتبط با یک وابستگی واحد تأثیر بگذارد (به یکپارچه‌سازی نسخه‌ها نگاه کنید) و همچنین بر میزان بازگشت به عقب (backtrack) در resolver، و در نتیجه بر کارایی آن اثر بگذارد،
    • یکپارچه‌سازی نسخه‌ها (try_unify_version، needs_version_unification): Cargo در صورت امکان از نسخه‌ها دوباره استفاده می‌کند تا زمان ساخت کاهش یابد و بتوان نوع‌های وابستگی‌های مشترک را بین APIها جابه‌جا کرد. اگر چند نسخه به‌جز به‌خاطر تعارض در مشخصات وابستگی آن‌ها یکپارچه می‌شدند، Cargo به عقب برمی‌گردد و اگر راه‌حلی پیدا نشود به‌جای انتخاب چند نسخه خطا می‌دهد. یک مشخصهٔ وابستگی یا خود Cargo ممکن است تشخیص دهد که یک نسخه نامطلوب است و ترجیح دهد به‌جای استفاده از آن به عقب برگردد یا خطا بدهد.
    • ترجیح دادن نسخه‌ها (pick_next_version): Cargo ممکن است تصمیم بگیرد که یک نسخهٔ مشخص را ترجیح دهد و هنگام بازگشت به عقب به نسخهٔ بعدی برود.

    شماره‌های نسخه (Version numbers)

    به‌طور کلی، Cargo بالاترین نسخهٔ موجود در حال حاضر را ترجیح می‌دهد.

    برای مثال، اگر بسته‌ای در گراف حل داشته باشید که این‌گونه باشد:

    [dependencies]
bitflags = "*"

    و در زمان تولید فایل Cargo.lock بزرگ‌ترین نسخهٔ bitflags برابر 1.2.1 باشد، آن بسته از 1.2.1 استفاده خواهد کرد.

    برای نمونه‌ای از یک استثنای ممکن، نسخهٔ Rust را ببینید.

    نیازمندی‌های نسخه (Version requirements)

    بسته‌ها از طریق نیازمندی‌های نسخه مشخص می‌کنند که از چه نسخه‌هایی پشتیبانی می‌کنند و همهٔ نسخه‌های دیگر را رد می‌کنند.

    برای مثال، اگر بسته‌ای در گراف حل داشته باشید که این‌گونه باشد:

    [dependencies]
bitflags = "1.0"  # meaning `>=1.0.0,<2.0.0`

    و در زمان تولید فایل Cargo.lock بزرگ‌ترین نسخهٔ bitflags برابر 1.2.1 باشد، آن بسته از 1.2.1 استفاده می‌کند، چون بزرگ‌ترین نسخه در بازهٔ سازگاری است. اگر 2.0.0 منتشر شود، باز هم از 1.2.1 استفاده خواهد کرد، زیرا 2.0.0 ناسازگار شمرده می‌شود.

    سازگاری SemVer (SemVer compatibility)

    Cargo فرض می‌کند بسته‌ها از SemVer پیروی می‌کنند و اگر نسخه‌های وابستگی‌ها طبق نیازمندی‌های نسخهٔ caret با SemVer سازگار باشند، آن‌ها را یکپارچه می‌کند. اگر دو نسخهٔ سازگار به‌دلیل تعارض نیازمندی‌های نسخه نتوانند یکپارچه شوند، Cargo خطا می‌دهد.

    برای راهنمایی دربارهٔ اینکه چه تغییری «سازگار» شمرده می‌شود، فصل سازگاری SemVer را ببینید.

    مثال‌ها:

    در دو بسته زیر، وابستگی‌هایشان به bitflags یکپارچه خواهد شد، زیرا هر نسخه‌ای که انتخاب شود با دیگری سازگار خواهد بود.

    # Package A
[dependencies]
bitflags = "1.0"  # meaning `>=1.0.0,<2.0.0`

# Package B
[dependencies]
bitflags = "1.1"  # meaning `>=1.1.0,<2.0.0`

    بسته‌های زیر خطا خواهند داد، زیرا نیازمندی‌های نسخه با هم تعارض دارند و دو نسخهٔ سازگار متمایز انتخاب می‌شوند.

    # Package A
[dependencies]
log = "=0.4.11"

# Package B
[dependencies]
log = "=0.4.8"

    در دو بسته زیر، وابستگی‌هایشان به rand یکپارچه نخواهد شد، زیرا برای هر کدام فقط نسخه‌های ناسازگار در دسترس است. در عوض، دو نسخهٔ متفاوت (مثلاً 0.6.5 و 0.7.3) حل و ساخته خواهند شد. این می‌تواند به مشکلات احتمالی منجر شود؛ برای جزئیات بیشتر بخش خطرات ناسازگاری نسخه را ببینید.

    # Package A
[dependencies]
rand = "0.7"  # meaning `>=0.7.0,<0.8.0`

# Package B
[dependencies]
rand = "0.6"  # meaning `>=0.6.0,<0.7.0`

    به‌طور کلی، در دو بسته زیر وابستگی‌ها یکپارچه نخواهند شد، زیرا نسخه‌های ناسازگاری در دسترس‌اند که نیازمندی‌های نسخه را برآورده می‌کنند: در عوض، دو نسخهٔ متفاوت (مثلاً 0.6.5 و 0.7.3) حل و ساخته خواهند شد. اعمال قیدها یا قواعد اکتشافی دیگر ممکن است باعث شود این‌ها یکپارچه شوند و یک نسخه (مثلاً 0.6.5) انتخاب شود.

    # Package A
[dependencies]
rand = ">=0.6,<0.8.0"

# Package B
[dependencies]
rand = "0.6"  # meaning `>=0.6.0,<0.7.0`

    خطرات ناسازگاری نسخه (Version-incompatibility hazards)

    وقتی چند نسخه از یک crate در گراف حل ظاهر می‌شوند، اگر نوع‌های آن crateها توسط crateهای استفاده‌کنندهٔ آن‌ها در معرض دید قرار گرفته باشند، ممکن است مشکل ایجاد شود. دلیلش این است که کامپایلر Rust نوع‌ها و آیتم‌ها را متفاوت می‌داند، حتی اگر نام یکسانی داشته باشند. کتابخانه‌ها باید هنگام انتشار نسخهٔ ناسازگار با SemVer (برای مثال، انتشار 2.0.0 پس از اینکه 1.0.0 مدتی مورد استفاده بوده است) دقت کنند، به‌ویژه کتابخانه‌هایی که به‌طور گسترده استفاده می‌شوند.

    «ترفند semver» (semver trick) راه‌حلی برای این مشکل است که امکان انتشار یک تغییر ناسازگار را با حفظ سازگاری با نسخه‌های قدیمی‌تر فراهم می‌کند. صفحهٔ پیوندشده جزئیات مشکل و نحوهٔ رفع آن را توضیح می‌دهد. به‌طور خلاصه، وقتی یک کتابخانه می‌خواهد نسخه‌ای منتشر کند که SemVer را می‌شکند، نسخهٔ جدید را منتشر کنید و همچنین یک نسخهٔ نقطه‌ای (point release) از نسخهٔ قبلی منتشر کنید که نوع‌های نسخهٔ جدیدتر را دوباره صادر (reexport) می‌کند.

    این ناسازگاری‌ها معمولاً به‌صورت خطای زمان کامپایل ظاهر می‌شوند، اما گاهی فقط به‌صورت رفتار نادرست در زمان اجرا بروز می‌کنند. برای مثال، فرض کنید یک کتابخانهٔ مشترک به نام foo وجود دارد که در نهایت هم با نسخهٔ 1.0.0 و هم با 2.0.0 در گراف حل ظاهر می‌شود. اگر downcast_ref روی شیئی استفاده شود که توسط کتابخانه‌ای با نسخهٔ 1.0.0 ساخته شده است، و کدی که downcast_ref را فراخوانی می‌کند به نوعی از نسخهٔ 2.0.0 تبدیل کند، این downcast در زمان اجرا شکست می‌خورد.

    مهم است که اگر چند نسخه از یک کتابخانه دارید مطمئن شوید که از آن‌ها درست استفاده می‌کنید، به‌ویژه اگر امکان استفادهٔ هم‌زمان نوع‌های نسخه‌های مختلف وجود داشته باشد. از دستور cargo tree -d می‌توان برای شناسایی نسخه‌های تکراری و منشأ آن‌ها استفاده کرد. به همین ترتیب، مهم است که اگر نسخه‌ای ناسازگار با SemVer از یک کتابخانهٔ محبوب منتشر می‌کنید، تأثیر آن بر اکوسیستم را در نظر بگیرید.

    فایل قفل (Lock file)

    Cargo در صورت استفاده، بالاترین اولویت را به نسخه‌های موجود در فایل Cargo.lock می‌دهد. هدف این است که میان ساخت‌های تکرارپذیر و سازگاری با تغییرات در manifest تعادل برقرار شود.

    برای مثال، اگر بسته‌ای در گراف حل داشته باشید که این‌گونه باشد:

    [dependencies]
bitflags = "*"

    و در زمان تولید فایل Cargo.lock شما بزرگ‌ترین نسخهٔ bitflags برابر 1.2.1 باشد، آن بسته از 1.2.1 استفاده می‌کند و این نسخه در فایل Cargo.lock ثبت می‌شود.

    تا زمانی که Cargo دوباره اجرا شود، bitflags نسخهٔ 1.3.5 منتشر شده است. هنگام حل وابستگی‌ها، باز هم 1.2.1 استفاده می‌شود، چون در فایل Cargo.lock شما وجود دارد.

    سپس بسته به این صورت ویرایش می‌شود:

    [dependencies]
bitflags = "1.3.0"

    bitflags نسخهٔ 1.2.1 با این نیازمندی نسخه مطابقت ندارد و بنابراین آن ورودی در فایل Cargo.lock شما نادیده گرفته می‌شود و اکنون نسخهٔ 1.3.5 استفاده و در فایل Cargo.lock شما ثبت می‌شود.

    نسخهٔ Rust (Rust version)

    برای پشتیبانی از توسعهٔ نرم‌افزار با یک نسخهٔ Rust حداقلِ پشتیبانی‌شده، resolver می‌تواند سازگاری نسخهٔ یک وابستگی با نسخهٔ Rust شما را در نظر بگیرد. این رفتار با فیلد پیکربندی resolver.incompatible-rust-versions کنترل می‌شود.

    با تنظیم fallback، resolver بسته‌هایی را ترجیح می‌دهد که نسخهٔ Rust آن‌ها کمتر از نسخهٔ Rust شما یا برابر با آن باشد. برای مثال، فرض کنید برای توسعهٔ بستهٔ زیر از Rust 1.85 استفاده می‌کنید:

    [package]
name = "my-cli"
rust-version = "1.62"

[dependencies]
clap = "4.0"  # resolves to 4.0.32

    resolver نسخهٔ 4.0.32 را انتخاب می‌کند، چون نسخهٔ Rust آن 1.60.0 است.

    • 4.0.0 انتخاب نمی‌شود، چون با اینکه آن هم نسخهٔ Rust برابر 1.60.0 دارد، شمارهٔ نسخهٔ پایین‌تری دارد.
    • 4.5.20 انتخاب نمی‌شود، چون با نسخهٔ Rust برابر 1.62 در my-cli ناسازگار است، هرچند نسخهٔ بسیار بالاتری دارد و نسخهٔ Rust آن 1.74.0 است که با toolchain نسخهٔ 1.85 شما سازگار است.

    اگر یک نیازمندی نسخه شامل هیچ نسخهٔ وابستگی سازگار با نسخهٔ Rust نباشد، resolver خطا نمی‌دهد و در عوض یک نسخه را انتخاب می‌کند، حتی اگر احتمالاً بهینه نباشد. برای مثال، وابستگی به clap را تغییر می‌دهید:

    [package]
name = "my-cli"
rust-version = "1.62"

[dependencies]
clap = "4.2"  # resolves to 4.5.20

    هیچ نسخه‌ای از clap که با آن نیازمندی نسخه مطابقت داشته باشد با نسخهٔ Rust برابر 1.62 سازگار نیست. در این حالت resolver یک نسخهٔ ناسازگار را انتخاب می‌کند، مثلاً 4.5.20، هرچند نسخهٔ Rust آن 1.74 است.

    وقتی resolver یک نسخهٔ وابستگی را برای یک بسته انتخاب می‌کند، نمی‌داند در نهایت کدام اعضای workspace وابستگی تراگذری (transitive) به آن نسخه خواهند داشت و بنابراین نمی‌تواند فقط نسخه‌های Rust مرتبط با آن وابستگی را در نظر بگیرد. resolver قواعد اکتشافی‌ای دارد تا هنگامی که اعضای workspace نسخه‌های Rust متفاوتی دارند، راه‌حلی «به‌اندازهٔ کافی خوب» پیدا کند. این موضوع حتی برای بسته‌های یک workspace که نسخهٔ Rust ندارند نیز صدق می‌کند.

    وقتی یک workspace اعضایی با نسخه‌های Rust متفاوت دارد، resolver ممکن است نسخهٔ وابستگی‌ای پایین‌تر از حد لازم انتخاب کند. برای مثال، اعضای workspace زیر را در نظر بگیرید:

    [package]
name = "a"
rust-version = "1.62"

[package]
name = "b"

[dependencies]
clap = "4.2"  # resolves to 4.5.20

    با اینکه بستهٔ b نسخهٔ Rust ندارد و می‌تواند از نسخهٔ بالاتری مانند 4.5.20 استفاده کند، به‌دلیل نسخهٔ Rust برابر 1.62 در بستهٔ a، نسخهٔ 4.0.32 انتخاب می‌شود.

    یا resolver ممکن است نسخه‌ای بیش از حد بالا انتخاب کند. برای مثال، اعضای workspace زیر را در نظر بگیرید:

    [package]
name = "a"
rust-version = "1.62"

[dependencies]
clap = "4.2"  # resolves to 4.5.20

[package]
name = "b"

[dependencies]
clap = "4.5"  # resolves to 4.5.20

    با اینکه هر بسته نیازمندی نسخه‌ای برای clap دارد که نسخهٔ Rust خودش را برآورده می‌کند، به‌دلیل یکپارچه‌سازی نسخه‌ها، resolver باید نسخه‌ای را انتخاب کند که در هر دو حالت کار کند، و آن نسخه‌ای مانند 4.5.20 خواهد بود.

    زمان انتشار (Publish age)

    نسخه‌هایی که زمان انتشارشان جدیدتر از min-publish-age پیکربندی‌شده باشد، از نظر زمان انتشار ناسازگار (pubtime-incompatible) در نظر گرفته می‌شوند. وقتی resolver.incompatible-publish-age روی deny تنظیم شده باشد، resolver این نسخه‌ها را نادیده می‌گیرد، مگر اینکه از قبل در فایل Cargo.lock وجود داشته باشند. تنظیم این پیکربندی روی allow این بررسی را غیرفعال می‌کند، و اگر با cargo update --precise ترکیب شود، cargo یک نسخهٔ مشخص و وابستگی‌های تراگذری آن را وارد می‌کند.

    featureها (Features)

    به‌منظور تولید Cargo.lock، resolver گراف وابستگی را طوری می‌سازد که گویی همهٔ featureهای همهٔ اعضای workspace فعال هستند. این کار تضمین می‌کند که هر وابستگی اختیاری در دسترس است و هنگام افزودن یا حذف featureها با پرچم خط فرمان --features به‌درستی همراه با بقیهٔ گراف حل می‌شود. resolver بار دوم اجرا می‌شود تا featureهای واقعاً استفاده‌شده هنگام کامپایل یک crate را بر اساس featureهای انتخاب‌شده در خط فرمان تعیین کند.

    وابستگی‌ها با اجتماع همهٔ featureهایی که روی آن‌ها فعال شده است حل می‌شوند. برای مثال، اگر یک بسته به بستهٔ im با وابستگی serde فعال‌شده وابسته باشد و بستهٔ دیگری به آن با وابستگی rayon فعال‌شده وابسته باشد، آنگاه im با هر دو feature فعال ساخته می‌شود، و crateهای serde و rayon در گراف حل قرار می‌گیرند. اگر هیچ بسته‌ای با آن featureها به im وابسته نباشد، آن وابستگی‌های اختیاری نادیده گرفته می‌شوند و بر حل تأثیری نخواهند داشت.

    هنگام ساخت چند بسته در یک workspace (مثلاً با --workspace یا چند پرچم -p)، featureهای وابستگی‌های همهٔ آن بسته‌ها یکپارچه می‌شوند. اگر موقعیتی دارید که می‌خواهید از این یکپارچه‌سازی برای اعضای مختلف workspace جلوگیری کنید، باید آن‌ها را با فراخوانی‌های جداگانهٔ cargo بسازید.

    resolver از نسخه‌هایی از بسته‌ها که featureهای لازم را ندارند عبور می‌کند. برای مثال، اگر بسته‌ای به نسخهٔ ^1 از regex با feature با نام perf وابسته باشد، قدیمی‌ترین نسخه‌ای که می‌تواند انتخاب کند 1.3.0 است، چون نسخه‌های پیش از آن feature با نام perf را نداشتند. به همین ترتیب، اگر یک feature از نسخهٔ جدیدی حذف شود، بسته‌هایی که به آن feature نیاز دارند روی نسخه‌های قدیمی‌ای که آن را دارند گیر می‌کنند. حذف featureها در نسخهٔ سازگار با SemVer توصیه نمی‌شود. توجه داشته باشید که وابستگی‌های اختیاری نیز یک feature ضمنی تعریف می‌کنند، بنابراین حذف یک وابستگی اختیاری یا غیراختیاری کردن آن می‌تواند مشکل ایجاد کند؛ حذف یک وابستگی اختیاری را ببینید.

    نسخهٔ ۲ حل‌کنندهٔ feature (Feature resolver version 2)

    وقتی resolver = "2" در Cargo.toml مشخص شده باشد (در ادامه نسخه‌های resolver را ببینید)، از یک حل‌کنندهٔ feature متفاوت استفاده می‌شود که الگوریتم متفاوتی برای یکپارچه‌سازی featureها دارد. resolver نسخهٔ "1" featureهای یک بسته را صرف‌نظر از جایی که مشخص شده‌اند یکپارچه می‌کند. resolver نسخهٔ "2" در موقعیت‌های زیر از یکپارچه‌سازی featureها پرهیز می‌کند:

    • featureهای وابستگی‌های مخصوص یک هدف (target) فعال نمی‌شوند، اگر آن هدف در حال حاضر ساخته نمی‌شود. برای مثال:

      [dependencies.common]
version = "1.0"
features = ["f1"]

[target.'cfg(windows)'.dependencies.common]
version = "1.0"
features = ["f2"]

      هنگام ساخت این مثال برای یک پلتفرم غیر Windows، feature با نام f2 فعال نخواهد شد.

    • featureهای فعال‌شده روی build-dependencies یا proc-macroها وقتی همان وابستگی‌ها به‌عنوان وابستگی معمولی استفاده می‌شوند، یکپارچه نمی‌شوند. برای مثال:

      [dependencies]
log = "0.4"

[build-dependencies]
log = {version = "0.4", features=['std']}

      هنگام ساخت build script، crate با نام log با feature با نام std ساخته می‌شود. هنگام ساخت کتابخانهٔ بستهٔ شما، این feature فعال نخواهد شد.

    • featureهای فعال‌شده روی dev-dependencies وقتی همان وابستگی‌ها به‌عنوان وابستگی معمولی استفاده می‌شوند یکپارچه نمی‌شوند، مگر اینکه آن dev-dependencyها در حال حاضر ساخته شوند. برای مثال:

      [dependencies]
serde = {version = "1.0", default-features = false}

[dev-dependencies]
serde = {version = "1.0", features = ["std"]}

      در این مثال، کتابخانه به‌طور معمول بدون feature با نام std با serde پیوند می‌شود. اما وقتی به‌عنوان آزمون یا مثال ساخته شود، feature با نام std را شامل می‌شود. برای مثال، cargo test یا cargo build --all-targets این featureها را یکپارچه می‌کنند. توجه کنید که dev-dependencyها در وابستگی‌ها همیشه نادیده گرفته می‌شوند؛ این فقط برای بستهٔ سطح بالا یا اعضای workspace اهمیت دارد.

    links

    فیلد links برای اطمینان از این استفاده می‌شود که فقط یک نسخه از یک کتابخانهٔ بومی (native) در یک فایل باینری پیوند شود. resolver تلاش می‌کند گرافی بیابد که در آن از هر نام links فقط یک نمونه وجود داشته باشد. اگر نتواند گرافی پیدا کند که این قید را برآورده کند، خطا برمی‌گرداند.

    برای مثال، اگر یک بسته به libgit2-sys نسخهٔ 0.11 و بستهٔ دیگری به 0.12 وابسته باشد، خطا رخ می‌دهد، چون Cargo نمی‌تواند آن‌ها را یکپارچه کند، اما هر دو به کتابخانهٔ بومی git2 پیوند می‌شوند. به‌دلیل این الزام، اگر کتابخانهٔ شما رایج است، توصیه می‌شود هنگام انتشار نسخه‌های ناسازگار با SemVer که فیلد links را دارند بسیار مراقب باشید.

    نسخه‌های yank‌شده (Yanked versions)

    نسخه‌های yank‌شده نسخه‌هایی هستند که علامت‌گذاری شده‌اند تا استفاده نشوند. وقتی resolver گراف را می‌سازد، همهٔ نسخه‌های yank‌شده را نادیده می‌گیرد، مگر اینکه از قبل در فایل Cargo.lock وجود داشته باشند یا صریحاً با پرچم --precise در cargo update درخواست شده باشند.

    به‌روزرسانی وابستگی‌ها (Dependency updates)

    حل وابستگی‌ها به‌طور خودکار توسط همهٔ دستورهای Cargo که باید از گراف وابستگی خبر داشته باشند انجام می‌شود. برای مثال، cargo build resolver را اجرا می‌کند تا همهٔ وابستگی‌هایی را که باید ساخته شوند بیابد. پس از نخستین اجرا، نتیجه در Cargo.lock ذخیره می‌شود. دستورهای بعدی resolver را اجرا می‌کنند و در صورت امکان وابستگی‌ها را روی نسخه‌های موجود در Cargo.lock قفل نگه می‌دارند.

    اگر فهرست وابستگی‌ها در Cargo.toml تغییر کرده باشد، مثلاً نسخهٔ یک وابستگی از 1.0 به 2.0 تغییر کرده باشد، resolver نسخهٔ جدیدی برای آن وابستگی انتخاب می‌کند که با نیازمندی‌های جدید مطابقت داشته باشد. اگر آن وابستگی جدید نیازمندی‌های تازه‌ای وارد کند، آن نیازمندی‌ها نیز ممکن است به‌روزرسانی‌های بیشتری را برانگیزند. فایل Cargo.lock با نتیجهٔ جدید به‌روزرسانی می‌شود. می‌توان از پرچم‌های --locked یا --frozen استفاده کرد تا این رفتار تغییر کند و هنگام تغییر نیازمندی‌ها از به‌روزرسانی خودکار جلوگیری شود و در عوض خطا برگردانده شود.

    cargo update را می‌توان برای به‌روزرسانی ورودی‌های Cargo.lock هنگام انتشار نسخه‌های جدید به کار برد. بدون هیچ گزینه‌ای، تلاش می‌کند همهٔ بسته‌های موجود در فایل قفل را به‌روزرسانی کند. پرچم -p را می‌توان برای هدف قرار دادن به‌روزرسانی یک بستهٔ خاص به کار برد، و پرچم‌های دیگری مانند --recursive یا --precise را می‌توان برای کنترل نحوهٔ انتخاب نسخه‌ها استفاده کرد.

    بازنویسی‌ها (Overrides)

    Cargo چند سازوکار برای بازنویسی (override) وابستگی‌ها در گراف دارد. فصل بازنویسی وابستگی‌ها جزئیات نحوهٔ استفاده از overrideها را توضیح می‌دهد. overrideها مانند یک لایهٔ پوششی روی رجیستری ظاهر می‌شوند و نسخهٔ وصله‌شده را با ورودی جدید جایگزین می‌کنند. در غیر این صورت، حل مانند حالت عادی انجام می‌شود.

    انواع وابستگی (Dependency kinds)

    در یک بسته سه نوع وابستگی وجود دارد: معمولی، build و dev. از دید resolver، این‌ها تا حد زیادی همگی یکسان رفتار می‌شوند. یک تفاوت این است که dev-dependencyهای اعضایی که عضو workspace نیستند همیشه نادیده گرفته می‌شوند و بر حل تأثیری ندارند.

    وابستگی‌های مخصوص پلتفرم با جدول [target] طوری حل می‌شوند که گویی همهٔ پلتفرم‌ها فعال هستند. به عبارت دیگر، resolver پلتفرم یا عبارت cfg را نادیده می‌گیرد.

    چرخه‌های dev-dependency (dev-dependency cycles)

    معمولاً resolver چرخه‌ها را در گراف مجاز نمی‌داند، اما برای dev-dependencies اجازه می‌دهد. برای مثال، پروژهٔ «foo» یک dev-dependency به «bar» دارد، و «bar» یک وابستگی معمولی به «foo» دارد (معمولاً به‌صورت وابستگی «path»). این مجاز است، چون از دید مصنوعات ساخت (build artifacts) واقعاً چرخه‌ای وجود ندارد. در این مثال، کتابخانهٔ «foo» ساخته می‌شود (که به «bar» نیازی ندارد، چون «bar» فقط برای آزمون‌ها استفاده می‌شود)، و سپس «bar» می‌تواند با وابستگی به «foo» ساخته شود، و بعد آزمون‌های «foo» با پیوند به «bar» ساخته می‌شوند.

    توجه داشته باشید که این می‌تواند به خطاهای گیج‌کننده منجر شود. در مورد ساخت آزمون‌های واحد کتابخانه، در واقع دو نسخه از کتابخانه در باینری آزمون نهایی پیوند می‌شوند: نسخه‌ای که با «bar» پیوند شده است، و نسخه‌ای که ساخته شده و شامل آزمون‌های واحد است. مشابه مشکلاتی که در بخش خطرات ناسازگاری نسخه برجسته شد، نوع‌های این دو با هم سازگار نیستند. هنگام در معرض قرار دادن نوع‌های «foo» از «bar» در این وضعیت دقت کنید، چون آزمون‌های واحد «foo» آن‌ها را با نوع‌های محلی یکسان در نظر نمی‌گیرند.

    در صورت امکان، سعی کنید بستهٔ خود را به چند بسته تقسیم کنید و ساختار آن را طوری تغییر دهید که کاملاً غیرچرخه‌ای (acyclic) باقی بماند.

    نسخه‌های resolver (Resolver versions)

    می‌توان رفتار متفاوتی از resolver را از طریق نسخهٔ resolver در Cargo.toml به این صورت مشخص کرد:

    [package]
name = "my-package"
version = "1.0.0"
resolver = "2"
    • "1" (پیش‌فرض)
    • "2" (پیش‌فرض برای edition = "2021"): تغییراتی در یکپارچه‌سازی featureها ایجاد می‌کند. برای جزئیات بیشتر فصل featureها را ببینید.
    • "3" (پیش‌فرض برای edition = "2024"، به Rust 1.84+ نیاز دارد): پیش‌فرض resolver.incompatible-rust-versions را از allow به fallback تغییر می‌دهد

    resolver یک گزینهٔ سراسری است که کل workspace را تحت تأثیر قرار می‌دهد. نسخهٔ resolver در وابستگی‌ها نادیده گرفته می‌شود و فقط مقدار موجود در بستهٔ سطح بالا استفاده خواهد شد. اگر از workspace مجازی استفاده می‌کنید، نسخه باید در جدول [workspace] مشخص شود، برای مثال:

    [workspace]
members = ["member1", "member2"]
resolver = "2"

    MSRV: به نسخهٔ 1.51 یا بالاتر نیاز دارد

    توصیه‌ها (Recommendations)

    موارد زیر چند توصیه برای تعیین نسخه در بستهٔ شما و برای مشخص کردن نیازمندی‌های وابستگی‌ها هستند. این‌ها رهنمودهای کلی‌ای هستند که باید در موقعیت‌های رایج به کار بروند، اما البته برخی موقعیت‌ها ممکن است مستلزم تعیین نیازمندی‌های غیرمعمول باشند.

    • هنگام تصمیم‌گیری دربارهٔ اینکه شمارهٔ نسخه‌تان را چگونه به‌روز کنید و اینکه آیا باید تغییر نسخه‌ای ناسازگار با SemVer انجام دهید یا نه، از رهنمودهای SemVer پیروی کنید.

    • در بیشتر موارد از نیازمندی‌های caret برای وابستگی‌ها استفاده کنید، مانند "1.2.3". این کار تضمین می‌کند که resolver در انتخاب نسخه بیشترین انعطاف را دارد و در عین حال سازگاری ساخت حفظ می‌شود.

      • هر سه مؤلفه را با نسخه‌ای که اکنون استفاده می‌کنید مشخص کنید. این کار به تعیین حداقل نسخه‌ای که استفاده خواهد شد کمک می‌کند و تضمین می‌کند که کاربران دیگر به نسخه‌ای قدیمی‌تر از وابستگی نمی‌رسند که ممکن است چیزی را که بستهٔ شما لازم دارد نداشته باشد.
      • از نیازمندی‌های * پرهیز کنید، چون در crates.io مجاز نیستند و می‌توانند در یک cargo update معمولی تغییرات شکنندهٔ SemVer را وارد کنند.
      • از نیازمندی‌های نسخهٔ بیش از حد گسترده پرهیز کنید. برای مثال، >=2.0.0 می‌تواند هر نسخهٔ ناسازگار با SemVer، مانند نسخهٔ 5.0.0، را وارد کند و این در آینده می‌تواند به ساخت‌های خراب منجر شود.
      • در صورت امکان از نیازمندی‌های نسخهٔ بیش از حد محدود پرهیز کنید. برای مثال، اگر یک نیازمندی tilde مانند bar="~1.3" مشخص کنید و بستهٔ دیگری نیازمندی bar="1.4" را مشخص کند، حل شکست می‌خورد، با اینکه نسخه‌های minor باید سازگار باشند.

    • سعی کنید نسخه‌های وابستگی‌ها را با حداقل نسخه‌های واقعی‌ای که کتابخانهٔ شما لازم دارد به‌روز نگه دارید. برای مثال، اگر نیازمندی bar="1.0.12" دارید و سپس در نسخه‌ای آینده شروع به استفاده از قابلیت‌های جدیدی کنید که در نسخهٔ 1.1.0 از «bar» اضافه شده‌اند، نیازمندی وابستگی خود را به bar="1.1.0" به‌روز کنید.

      اگر این کار را نکنید، ممکن است بلافاصله آشکار نشود، چون Cargo هنگام اجرای یک cargo update کلی می‌تواند فرصت‌طلبانه جدیدترین نسخه را انتخاب کند. اما اگر کاربر دیگری به کتابخانهٔ شما وابسته باشد و cargo update your-library را اجرا کند، «bar» در صورتی که در Cargo.lock او قفل شده باشد به‌طور خودکار به‌روز نمی‌شود. در آن وضعیت فقط در صورتی «bar» را به‌روز می‌کند که اعلان وابستگی نیز به‌روز شده باشد. انجام ندادن این کار می‌تواند برای کاربری که cargo update your-library را اجرا می‌کند خطاهای ساخت گیج‌کننده‌ای ایجاد کند.

    • اگر دو بسته به‌شدت به هم وابسته‌اند، یک نیازمندی وابستگی از نوع = می‌تواند به همگام ماندن آن‌ها کمک کند. برای مثال، کتابخانه‌ای که یک کتابخانهٔ proc-macro همراه دارد گاهی بین آن دو کتابخانه فرض‌هایی می‌کند که اگر آن دو هماهنگ نباشند خوب کار نمی‌کنند (و هرگز انتظار نمی‌رود آن دو کتابخانه مستقل از هم استفاده شوند). کتابخانهٔ والد می‌تواند از یک نیازمندی = روی proc-macro استفاده کند و ماکروها را برای دسترسی آسان دوباره صادر (re-export) کند.

    • نسخه‌های 0.0.x را می‌توان برای بسته‌هایی به کار برد که دائماً ناپایدار هستند.

    به‌طور کلی، هرچه نیازمندی‌های وابستگی را سخت‌گیرانه‌تر کنید، احتمال شکست خوردن resolver بیشتر می‌شود. در مقابل، اگر از نیازمندی‌هایی استفاده کنید که بیش از حد آزاد هستند، ممکن است نسخه‌های جدیدی منتشر شوند که ساخت را خراب کنند.

    رفع مشکل (Troubleshooting)

    موارد زیر برخی مشکلاتی را که ممکن است با آن‌ها روبه‌رو شوید و برخی راه‌حل‌های ممکن را نشان می‌دهند.

    چرا یک وابستگی گنجانده شد؟ (Why was a dependency included?)

    فرض کنید وابستگی rand را در خروجی cargo check می‌بینید اما فکر نمی‌کنید لازم باشد و می‌خواهید بفهمید چرا وارد شده است.

    می‌توانید اجرا کنید

    $ cargo tree --workspace --target all --all-features --invert rand
rand v0.8.5
└── ...

└── ...

    چرا آن feature روی این وابستگی فعال شد؟ (Why was that feature on this dependency enabled?)

    ممکن است تشخیص دهید که یک feature فعال‌شده باعث ظاهر شدن rand شده است. برای پی بردن به اینکه کدام بسته آن feature را فعال کرده است، می‌توانید --edges features را اضافه کنید

    $ cargo tree --workspace --target all --all-features --edges features --invert rand
rand v0.8.5
└── ...

rand v0.8.5
└── ...

    تکرار غیرمنتظرهٔ وابستگی (Unexpected dependency duplication)

    هنگام اجرای این دستور چند نمونه از rand را می‌بینید

    $ cargo tree --workspace --target all --all-features --duplicates
rand v0.7.3
└── ...

rand v0.8.5
└── ...

    الگوریتم resolver به راه‌حلی همگرا شده است که شامل دو نسخه از یک وابستگی است، در حالی که یکی کافی بود. برای مثال:

    # Package A
[dependencies]
rand = "0.7"

# Package B
[dependencies]
rand = ">=0.6"  # note: open requirements such as this are discouraged

    در این مثال، Cargo ممکن است دو نسخه از crate با نام rand بسازد، با اینکه یک نسخهٔ واحد 0.7.3 همهٔ نیازمندی‌ها را برآورده می‌کرد. دلیلش این است که الگوریتم resolver ساخت جدیدترین نسخهٔ موجود rand را برای بستهٔ B ترجیح می‌دهد، که در زمان نگارش این متن 0.8.5 است، و آن با مشخصات بستهٔ A ناسازگار است. الگوریتم resolver در حال حاضر تلاشی برای «حذف تکرار» (deduplicate) در این وضعیت نمی‌کند.

    استفاده از نیازمندی‌های نسخهٔ باز مانند >=0.6 در Cargo توصیه نمی‌شود. اما اگر با این وضعیت روبه‌رو شدید، می‌توان از دستور cargo update با پرچم --precise برای حذف دستی چنین تکرارهایی استفاده کرد.

    چرا نسخهٔ جدیدتر انتخاب نشد؟ (Why wasn’t a newer version selected?)

    فرض کنید متوجه شدید هنگام اجرای دستور زیر، آخرین نسخهٔ یک وابستگی انتخاب نشده است:

    $ cargo update

    می‌توانید برای دیدن دلیل این اتفاق، گزارش‌گیری (logging) اضافی را فعال کنید:

    $ env CARGO_LOG=cargo::resolver=trace cargo update

    Note

    هدف‌ها و سطح‌های گزارش‌گیری Cargo ممکن است با گذر زمان تغییر کنند.

    نسخهٔ وصلهٔ شکنندهٔ SemVer ساخت را خراب می‌کند (SemVer-breaking patch release breaks the build)

    گاهی یک پروژه ممکن است سهواً یک نسخهٔ نقطه‌ای (point release) را با یک تغییر شکنندهٔ SemVer منتشر کند. وقتی کاربران با cargo update به‌روز می‌کنند، این نسخهٔ جدید را دریافت می‌کنند و سپس ساخت آن‌ها ممکن است خراب شود. در این وضعیت، توصیه می‌شود پروژه نسخه را yank کند و یا تغییر شکنندهٔ SemVer را حذف کند، یا آن را به‌صورت افزایش نسخهٔ major جدید SemVer منتشر کند.

    اگر تغییر در یک پروژهٔ شخص ثالث رخ داده است، در صورت امکان سعی کنید (مؤدبانه!) با آن پروژه برای رفع مشکل همکاری کنید.

    تا زمانی که منتظر yank شدن نسخه هستید، برخی راه‌حل‌های موقت بسته به شرایط وجود دارند:

    • اگر پروژهٔ شما محصول نهایی است (مثلاً یک فایل اجرایی باینری)، فقط از به‌روز کردن بستهٔ مشکل‌دار در Cargo.lock خودداری کنید. این کار را می‌توان با پرچم --precise در cargo update انجام داد.
    • اگر یک باینری را در crates.io منتشر می‌کنید، می‌توانید موقتاً یک نیازمندی = اضافه کنید تا وابستگی را روی یک نسخهٔ سالم مشخص مجبور کنید.
      • پروژه‌های باینری می‌توانند به‌جای آن به کاربران توصیه کنند که از پرچم --locked همراه با cargo install استفاده کنند تا از Cargo.lock اصلی که نسخهٔ سالم شناخته‌شده را دارد استفاده شود.
    • کتابخانه‌ها نیز می‌توانند انتشار یک نسخهٔ جدید موقت با نیازمندی‌های سخت‌گیرانه‌تر را در نظر بگیرند که از وابستگی مشکل‌ساز دوری می‌کند. شاید بخواهید از نیازمندی‌های بازه‌ای (به‌جای =) استفاده کنید تا از نیازمندی‌های بیش از حد سخت‌گیرانه‌ای که ممکن است با بسته‌های دیگری که از همان وابستگی استفاده می‌کنند تعارض داشته باشد، پرهیز شود. پس از رفع مشکل، می‌توانید یک نسخهٔ نقطه‌ای دیگر منتشر کنید که وابستگی را دوباره به نیازمندی caret سست می‌کند.
    • اگر به نظر می‌رسد پروژهٔ شخص ثالث نمی‌تواند یا نمی‌خواهد نسخه را yank کند، یک گزینه این است که کد خود را برای سازگاری با تغییرات به‌روز کنید و نیازمندی وابستگی را طوری به‌روز کنید که حداقل نسخه همان نسخهٔ جدید باشد. همچنین باید در نظر بگیرید که آیا این تغییر برای کتابخانهٔ خودتان نیز شکنندهٔ SemVer است، برای مثال اگر نوع‌های وابستگی را در معرض دید قرار می‌دهد.
