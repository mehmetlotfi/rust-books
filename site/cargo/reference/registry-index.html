    قالب ایندکس

    مطالب زیر قالب ایندکس را تعریف می‌کنند. گهگاه قابلیت‌های جدیدی اضافه می‌شود که فقط از نسخه‌ای از Cargo که آن‌ها را معرفی کرده به بعد فهمیده می‌شوند. نسخه‌های قدیمی‌تر Cargo ممکن است نتوانند از بسته‌هایی که از قابلیت‌های جدید استفاده می‌کنند بهره ببرند. با این حال، قالب بسته‌های قدیمی‌تر نباید تغییر کند، بنابراین نسخه‌های قدیمی‌تر Cargo باید بتوانند از آن‌ها استفاده کنند.

    پیکربندی ایندکس

    ریشهٔ ایندکس شامل فایلی با نام config.json است که اطلاعات JSON مورد استفادهٔ Cargo برای دسترسی به رجیستری را در خود دارد. این نمونه‌ای از ظاهر فایل پیکربندی crates.io است:

    {
    "dl": "https://crates.io/api/v1/crates",
    "api": "https://crates.io"
}

    کلیدها عبارت‌اند از:

    • dl: این URL مربوط به دانلود crateهای فهرست‌شده در ایندکس است. مقدار آن می‌تواند شامل نشانگرهای زیر باشد که با مقدار متناظرشان جایگزین می‌شوند:

      • {crate}: نام crate.
      • {version}: نسخهٔ crate.
      • {prefix}: یک پیشوند پوشه که از نام crate محاسبه می‌شود. برای مثال، crateای به نام cargo پیشوند ca/rg دارد. جزئیات را در ادامه ببینید.
      • {lowerprefix}: نوع حروف کوچک {prefix}.
      • {sha256-checksum}: چک‌سام sha256 مربوط به crate.

      اگر هیچ‌یک از نشانگرها وجود نداشته باشد، مقدار /{crate}/{version}/download به انتها اضافه می‌شود.

    • api: این URL پایهٔ API وب است. این کلید اختیاری است، اما اگر مشخص نشود، دستورهایی مانند cargo publish کار نخواهند کرد. API وب در ادامه شرح داده شده است. این URL نباید اسلش پایانی داشته باشد.

    • auth-required: نشان می‌دهد که آیا این یک رجیستری خصوصی است که نیاز دارد همهٔ عملیات، از جمله درخواست‌های API، دانلود crateها و به‌روزرسانی‌های ایندکس sparse، احراز هویت شوند.

    نقطهٔ پایانی دانلود

    نقطهٔ پایانی دانلود (download endpoint) باید فایل .crate بستهٔ درخواستی را ارسال کند. Cargo از URLهای https، http و file، تغییر مسیرهای HTTP، و HTTP1 و HTTP2 پشتیبانی می‌کند. جزئیات دقیق پشتیبانی از TLS به پلتفرمی که Cargo روی آن اجرا می‌شود، نسخهٔ Cargo و نحوهٔ کامپایل آن بستگی دارد.

    اگر auth-required: true در config.json تنظیم شده باشد، هدر Authorization همراه درخواست‌های دانلود http(s) ارسال خواهد شد.

    فایل‌های ایندکس

    بقیهٔ مخزن ایندکس برای هر بسته یک فایل دارد که نام فایل همان نام بسته با حروف کوچک است. هر نسخه از بسته در فایل یک خط جداگانه دارد. فایل‌ها در یک ساختار لایه‌ای از پوشه‌ها سازمان‌دهی می‌شوند:

    • بسته‌هایی که نامشان 1 نویسه است در پوشه‌ای به نام 1 قرار می‌گیرند.
    • بسته‌هایی که نامشان 2 نویسه است در پوشه‌ای به نام 2 قرار می‌گیرند.
    • بسته‌هایی که نامشان 3 نویسه است در پوشهٔ 3/{first-character} قرار می‌گیرند که در آن {first-character} نخستین نویسهٔ نام بسته است.
    • همهٔ بسته‌های دیگر در پوشه‌هایی به نام {first-two}/{second-two} ذخیره می‌شوند که پوشهٔ بالایی دو نویسهٔ نخست نام بسته است و زیرپوشهٔ بعدی نویسهٔ سوم و چهارم نام بسته. برای مثال، cargo در فایلی به نام ca/rg/cargo ذخیره می‌شود.

    Note

    اگرچه نام فایل‌های ایندکس با حروف کوچک است، فیلدهایی که در Cargo.toml و داده‌های JSON ایندکس شامل نام بسته‌اند به بزرگی و کوچکی حروف حساس‌اند و ممکن است حروف بزرگ و کوچک داشته باشند.

    نام پوشهٔ بالا بر اساس نام بسته‌ای که به حروف کوچک تبدیل شده محاسبه می‌شود؛ این نام با نشانگر {lowerprefix} نمایش داده می‌شود. وقتی نام اصلی بسته بدون تبدیل حروف به کار می‌رود، نام پوشهٔ حاصل با نشانگر {prefix} نمایش داده می‌شود. برای مثال، بستهٔ MyCrate مقدار {prefix} برابر My/Cr و مقدار {lowerprefix} برابر my/cr خواهد داشت. به‌طور کلی استفاده از {prefix} بر {lowerprefix} ترجیح داده می‌شود، اما هر انتخاب مزایا و معایبی دارد. استفاده از {prefix} در سیستم‌فایل‌های نسبت‌به‌حروف‌بزرگ‌وکوچک بی‌تفاوت به نتیجه‌ای می‌انجامد که در آن پوشه‌ها هم‌نام‌سازی (aliasing) می‌شوند (بی‌ضرر اما ناظریف). برای مثال، crate و CrateTwo مقادیر {prefix} برابر cr/at و Cr/at دارند؛ این‌ها در ماشین‌های Unix متمایزند اما در Windows به یک پوشه نگاشت می‌شوند. استفاده از پوشه‌هایی با حروف نرمال‌شده از aliasing جلوگیری می‌کند، اما در سیستم‌فایل‌های حساس به بزرگی و کوچکی حروف، پشتیبانی از نسخه‌های قدیمی‌تر Cargo که {prefix}/{lowerprefix} را ندارند دشوارتر است. برای مثال، قواعد بازنویسی nginx به‌راحتی می‌توانند {prefix} را بسازند اما نمی‌توانند برای ساخت {lowerprefix} تبدیل حروف انجام دهند.

    محدودیت‌های نام

    رجیستری‌ها باید اعمال محدودیت‌هایی بر نام بسته‌هایی که به ایندکس خود اضافه می‌شوند را در نظر بگیرند. خود Cargo نام‌هایی با هر نویسهٔ الفبایی-عددی، - یا _ را مجاز می‌داند. crates.io محدودیت‌های خود را اعمال می‌کند، از جمله موارد زیر:

    • فقط نویسه‌های ASCII را مجاز می‌داند.
    • فقط نویسه‌های الفبایی-عددی، - و _ را مجاز می‌داند.
    • نویسهٔ اول باید الفبایی باشد.
    • تشخیص برخورد نام بدون حساسیت به بزرگی و کوچکی حروف.
    • جلوگیری از تفاوت‌هایی که فقط در - در برابر _ باشند.
    • کمتر از یک طول مشخص (حداکثر 64).
    • نام‌های رزروشده، مانند نام‌های خاص فایل در Windows مانند “nul”، را رد می‌کند.

    رجیستری‌ها باید گنجاندن محدودیت‌های مشابه را در نظر بگیرند و پیامدهای امنیتی مانند حملات هم‌شکلی IDN و دغدغه‌های دیگر در UTR36 و UTS39 را نیز بسنجند.

    یکتایی نسخه

    ایندکس‌ها باید تضمین کنند که هر نسخه برای هر بسته فقط یک بار ظاهر می‌شود. این شامل نادیده گرفتن فرادادهٔ ساخت (build metadata) در SemVer نیز می‌شود. برای مثال، ایندکس نباید دو مدخل با نسخه‌های 1.0.7 و 1.0.7+extra داشته باشد.

    طرح‌واره JSON

    هر خط در فایل یک بسته شامل یک شیء JSON است که یک نسخهٔ منتشرشده از بسته را توصیف می‌کند. در ادامه یک نمونهٔ قالب‌بندی‌شده همراه با توضیحاتی آمده که قالب مدخل را شرح می‌دهند.

    {
    // The name of the package.
    // This must only contain alphanumeric, `-`, or `_` characters.
    "name": "foo",
    // The version of the package this row is describing.
    // This must be a valid version number according to the Semantic
    // Versioning 2.0.0 spec at https://semver.org/.
    "vers": "0.1.0",
    // Array of direct dependencies of the package.
    "deps": [
        {
            // Name of the dependency.
            // If the dependency is renamed from the original package name,
            // this is the new name. The original package name is stored in
            // the `package` field.
            "name": "rand",
            // The SemVer requirement for this dependency.
            // This must be a valid version requirement defined at
            // https://doc.rust-lang.org/cargo/reference/specifying-dependencies.html.
            "req": "^0.6",
            // Array of features (as strings) enabled for this dependency.
            // Since Cargo 1.84, defaults to `[]` if not specified.
            "features": ["i128_support"],
            // Boolean of whether or not this is an optional dependency.
            // Since Cargo 1.84, defaults to `false` if not specified.
            "optional": false,
            // Boolean of whether or not default features are enabled.
            // Since Cargo 1.84, defaults to `true` if not specified.
            "default_features": true,
            // The target platform for the dependency.
            // If not specified or `null`, it is not a target dependency.
            // Otherwise, a string such as "cfg(windows)".
            "target": null,
            // The dependency kind.
            // "dev", "build", or "normal".
            // If not specified or `null`, it defaults to "normal".
            "kind": "normal",
            // The URL of the index of the registry where this dependency is
            // from as a string. If not specified or `null`, it is assumed the
            // dependency is in the current registry.
            "registry": null,
            // If the dependency is renamed, this is a string of the actual
            // package name. If not specified or `null`, this dependency is not
            // renamed.
            "package": null,
        }
    ],
    // A SHA256 checksum of the `.crate` file.
    "cksum": "d867001db0e2b6e0496f9fac96930e2d42233ecd3ca0413e0753d4c7695d289c",
    // Set of features defined for the package.
    // Each feature maps to an array of features or dependencies it enables.
    // Since Cargo 1.84, defaults to `{}` if not specified.
    "features": {
        "extras": ["rand/simd_support"]
    },
    // Boolean of whether or not this version has been yanked.
    "yanked": false,
    // The `links` string value from the package's manifest, or null if not
    // specified. This field is optional and defaults to null.
    "links": null,
    // An unsigned 32-bit integer value indicating the schema version of this
    // entry.
    //
    // If this is not specified, it should be interpreted as the default of 1.
    //
    // Cargo (starting with version 1.51) will ignore versions it does not
    // recognize. This provides a method to safely introduce changes to index
    // entries and allow older versions of cargo to ignore newer entries it
    // doesn't understand. Versions older than 1.51 ignore this field, and
    // thus may misinterpret the meaning of the index entry.
    //
    // The current values are:
    //
    // * 1: The schema as documented here, not including newer additions.
    //      This is honored in Rust version 1.51 and newer.
    // * 2: The addition of the `features2` field.
    //      This is honored in Rust version 1.60 and newer.
    "v": 2,
    // This optional field contains features with new, extended syntax.
    // Specifically, namespaced features (`dep:`) and weak dependencies
    // (`pkg?/feat`).
    //
    // This is separated from `features` because versions older than 1.19
    // will fail to load due to not being able to parse the new syntax, even
    // with a `Cargo.lock` file.
    //
    // Cargo will merge any values listed here with the "features" field.
    //
    // If this field is included, the "v" field should be set to at least 2.
    //
    // Registries are not required to use this field for extended feature
    // syntax, they are allowed to include those in the "features" field.
    // Using this is only necessary if the registry wants to support cargo
    // versions older than 1.19, which in practice is only crates.io since
    // those older versions do not support other registries.
    "features2": {
        "serde": ["dep:serde", "chrono?/serde"]
    }
    // The minimal supported Rust version (optional)
    // This must be a valid version requirement without an operator (e.g. no `=`)
    "rust_version": "1.60",
    // The publish time of this package version (optional).
    //
    // The format is a subset of ISO8601:
    // - `yyyy-mm-ddThh:mm:ssZ`
    // - no fractional seconds
    // - always `Z` for UTC timezone, no timezone offsets supported
    // - fields are 0-padded
    //
    // Example: 2025-11-12T19:30:12Z
    //
    // This should be the original publish time and not changed on any status changes,
    // like `yanked`.
    "pubtime": "2025-11-12T19:30:12Z"
}

    شیءهای JSON پس از افزوده شدن نباید تغییر کنند، به‌جز فیلد yanked که مقدار آن ممکن است در هر زمان تغییر کند.

    Important

    قالب JSON ایندکس تفاوت‌های ظریفی با قالب JSON در Publish API و cargo metadata دارد. اگر از یکی از آن‌ها به‌عنوان منبعی برای تولید مدخل‌های ایندکس استفاده می‌کنید، توصیه می‌شود تفاوت‌های مستندات آن‌ها را با دقت بررسی کنید.

    برای Publish API، تفاوت‌ها عبارت‌اند از:

    • deps
      • name — وقتی وابستگی در Cargo.toml تغییر نام داده شده باشد، publish API نام اصلی بسته را در فیلد name و نام مستعار را در فیلد explicit_name_in_toml قرار می‌دهد. ایندکس نام مستعار را در فیلد name و نام اصلی بسته را در فیلد package قرار می‌دهد.
      • req — فیلد Publish API با نام version_req شناخته می‌شود.
    • cksum — publish API چک‌سام را مشخص نمی‌کند و رجیستری باید پیش از افزودن به ایندکس آن را محاسبه کند.
    • features — ممکن است برخی از featureها در فیلد features2 قرار بگیرند. توجه: این فقط یک الزام قدیمی برای crates.io است؛ رجیستری‌های دیگر نیازی به زحمت تغییر نقشهٔ featureها ندارند. فیلد v حضور فیلد features2 را نشان می‌دهد.
    • publish API چند فیلد دیگر مانند description و readme را نیز شامل می‌شود که در ایندکس ظاهر نمی‌شوند. این‌ها برای آسان‌تر کردن دریافت فراداده دربارهٔ crate توسط رجیستری در نظر گرفته شده‌اند تا بتواند آن را در یک وب‌سایت نمایش دهد، بدون نیاز به استخراج و تجزیهٔ فایل .crate. این اطلاعات اضافی معمولاً به یک پایگاه داده در سرور رجیستری افزوده می‌شود.
    • اگرچه rust_version در اینجا گنجانده شده است، crates.io این فیلد را نادیده می‌گیرد و در عوض آن را از Cargo.toml موجود در فایل .crate می‌خواند.

    برای cargo metadata، تفاوت‌ها عبارت‌اند از:

    • vers — فیلد cargo metadata با نام version شناخته می‌شود.
    • deps
      • name — وقتی وابستگی در Cargo.toml تغییر نام داده شده باشد، cargo metadata نام اصلی بسته را در فیلد name و نام مستعار را در فیلد rename قرار می‌دهد. ایندکس نام مستعار را در فیلد name و نام اصلی بسته را در فیلد package قرار می‌دهد.
      • default_features — فیلد cargo metadata با نام uses_default_features شناخته می‌شود.
      • registry — cargo metadata از مقدار null استفاده می‌کند تا نشان دهد وابستگی از crates.io می‌آید. ایندکس از مقدار null استفاده می‌کند تا نشان دهد وابستگی از همان رجیستری ایندکس می‌آید. هنگام ساخت یک مدخل ایندکس، رجیستری‌ای غیر از crates.io باید مقدار null را به https://github.com/rust-lang/crates.io-index ترجمه کند و URLی را که با ایندکس جاری مطابقت دارد به null ترجمه کند.
      • cargo metadata چند فیلد اضافی مانند source و path را شامل می‌شود.
    • ایندکس فیلدهای اضافی‌ای مانند yanked، cksum و v را شامل می‌شود.

    پروتکل‌های ایندکس

    Cargo از دو پروتکل رجیستری راه‌دور پشتیبانی می‌کند: git و sparse. پروتکل git فایل‌های ایندکس را در یک مخزن git ذخیره می‌کند و پروتکل sparse فایل‌ها را یک‌به‌یک از طریق HTTP دریافت می‌کند.

    پروتکل Git

    پروتکل git در URL ایندکس پیشوند پروتکل ندارد. برای مثال، URL ایندکس git برای crates.io برابر https://github.com/rust-lang/crates.io-index است.

    Cargo مخزن git را روی دیسک کش می‌کند تا بتواند به‌روزرسانی‌ها را به‌صورت افزایشی و کارآمد دریافت کند.

    پروتکل Sparse

    پروتکل sparse از پیشوند پروتکل sparse+ در URL رجیستری استفاده می‌کند. برای مثال، URL ایندکس sparse برای crates.io برابر sparse+https://index.crates.io/ است.

    پروتکل sparse هر فایل ایندکس را با یک درخواست HTTP جداگانه دانلود می‌کند. از آنجا که این کار به تعداد زیادی درخواست HTTP کوچک می‌انجامد، کارایی با سروری که از pipelining و HTTP/2 پشتیبانی کند به‌طور قابل‌توجهی بهبود می‌یابد.

    احراز هویت Sparse

    Cargo پیش از دریافت هر فایل دیگری تلاش می‌کند فایل config.json را دریافت کند. اگر سرور با HTTP 401 پاسخ دهد، Cargo فرض می‌کند که رجیستری به احراز هویت نیاز دارد و درخواست config.json را دوباره با توکن احراز هویت انجام می‌دهد.

    در صورت شکست احراز هویت (یا نبود توکن احراز هویت)، سرور می‌تواند یک هدر www-authenticate با چالش Cargo login_url="<URL>" بگنجاند تا نشان دهد کاربر کجا می‌تواند توکن بگیرد.

    رجیستری‌هایی که به احراز هویت نیاز دارند باید auth-required: true را در config.json تنظیم کنند.

    کش کردن

    Cargo فایل‌های فراداده crate را کش می‌کند و هدر HTTP با نام ETag یا Last-Modified را برای هر مدخل از سرور ثبت می‌کند. هنگام تازه‌سازی فراداده crate، Cargo هدر If-None-Match یا If-Modified-Since را ارسال می‌کند تا سرور بتواند در صورت معتبر بودن کش محلی با HTTP 304 «Not Modified» پاسخ دهد و در زمان و پهنای باند صرفه‌جویی شود. اگر هر دو هدر ETag و Last-Modified وجود داشته باشند، Cargo فقط از ETag استفاده می‌کند.

    باطل‌سازی کش

    اگر رجیستری از نوعی CDN یا پروکسی استفاده می‌کند که دسترسی به فایل‌های ایندکس را کش می‌کند، توصیه می‌شود رجیستری‌ها هنگام به‌روزرسانی فایل‌ها نوعی باطل‌سازی کش پیاده‌سازی کنند. اگر این کش‌ها به‌روز نشوند، ممکن است کاربران تا پاک شدن کش نتوانند به crateهای جدید دسترسی پیدا کنند.

    crateهای ناموجود

    برای crateهایی که وجود ندارند، رجیستری باید با کد 404 «Not Found»، 410 «Gone» یا 451 «Unavailable For Legal Reasons» پاسخ دهد.

    محدودیت‌های Sparse

    از آنجا که URL رجیستری در lockfile ذخیره می‌شود، توصیه نمی‌شود رجیستری‌ای با هر دو پروتکل ارائه شود. بحث دربارهٔ یک برنامهٔ گذار در issue #10964 ادامه دارد. رجیستری crates.io استثنا است، زیرا Cargo هنگام استفاده از پروتکل sparse در داخل، URL معادل git را جایگزین می‌کند.

    اگر رجیستری هر دو پروتکل را ارائه می‌دهد، در حال حاضر توصیه می‌شود یکی از پروتکل‌ها به‌عنوان پروتکل اصلی انتخاب شود و برای پروتکل دیگر از جایگزینی منبع استفاده شود.
