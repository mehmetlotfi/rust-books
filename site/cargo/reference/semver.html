    SemVer Compatibility

    این فصل جزئیات آنچه را به‌طور قراردادی تغییر سازگار یا شکننده (breaking) در SemVer برای انتشارهای جدید یک بسته به شمار می‌رود ارائه می‌دهد. برای جزئیات اینکه SemVer چیست و Cargo چگونه از آن برای تضمین سازگاری کتابخانه‌ها استفاده می‌کند، بخش سازگاری SemVer را ببینید.

    این‌ها فقط رهنمود هستند و لزوماً قواعد سفت‌وسختی نیستند که همهٔ پروژه‌ها رعایت کنند. بخش دسته‌بندی تغییرها توضیح می‌دهد این راهنما سطح و شدت یک تغییر را چگونه طبقه‌بندی می‌کند. بیشتر این راهنما بر تغییرهایی تمرکز دارد که باعث می‌شوند cargo و rustc چیزی را که قبلاً ساخته می‌شد نتوانند بسازند. تقریباً هر تغییری این خطر را دارد که بر رفتار زمان اجرا اثر منفی بگذارد، و در آن موارد معمولاً تصمیم با نگه‌دارندگان پروژه است که آیا این یک تغییر ناسازگار با SemVer است یا نه.

    Change categories

    همهٔ سیاست‌های زیر بر اساس سطح تغییر دسته‌بندی شده‌اند:

    • تغییر major: تغییری که افزایش major در SemVer را می‌طلبد.
    • تغییر minor: تغییری که فقط افزایش minor در SemVer را می‌طلبد.
    • تغییر احتمالاً شکننده: تغییری که برخی پروژه‌ها آن را major و برخی دیگر minor می‌دانند.

    دستهٔ «احتمالاً شکننده» تغییرهایی را شامل می‌شود که پتانسیل شکستن هنگام به‌روزرسانی را دارند، اما لزوماً باعث شکست نمی‌شوند. اثر این تغییرها باید با دقت سنجیده شود. ماهیت دقیق آن به تغییر و اصول نگه‌دارندگان پروژه بستگی دارد.

    برخی پروژه‌ها ممکن است در تغییر minor فقط شمارهٔ patch را افزایش دهند. توصیه می‌شود از مشخصات SemVer پیروی شود و رفع باگ‌ها فقط در انتشارهای patch اعمال شوند. با این حال ممکن است رفع یک باگ نیازمند تغییر API‌ای باشد که «تغییر minor» علامت‌گذاری شده و نباید سازگاری را تحت‌تأثیر قرار دهد. این راهنما موضعی دربارهٔ نحوهٔ برخورد با هر «تغییر minor» مشخص نمی‌گیرد، چون تفاوت بین تغییرهای minor و patch قراردادهایی هستند که به ماهیت تغییر بستگی دارند.

    برخی تغییرها «minor» علامت‌گذاری شده‌اند، با اینکه خطر بالقوهٔ شکستن ساخت را دارند. این برای موقعیت‌هایی است که این احتمال بسیار کم است و کدی که ممکن است بشکند بعید است به Rust اصطلاحی (idiomatic) نوشته شده باشد، یا استفاده از آن صراحتاً منع شده است.

    این راهنما اصطلاح‌های «major» و «minor» را با این فرض به‌کار می‌برد که به انتشار «1.0.0» یا بعد از آن مربوط می‌شود. انتشارهای توسعهٔ اولیه که با «0.y.z» شروع می‌شوند می‌توانند تغییرهای «y» را انتشار major و «z» را انتشار minor بدانند. انتشارهای «0.0.z» همیشه تغییر major‌اند. دلیلش این است که Cargo این قرارداد را به‌کار می‌برد که فقط تغییر در چپ‌ترین مؤلفهٔ غیرصفر ناسازگار محسوب می‌شود.

    API compatibility

    همهٔ مثال‌های زیر سه بخش دارند: کد اصلی، کد پس از تغییر، و یک نمونهٔ استفاده از کد که ممکن است در پروژهٔ دیگری بیاید. در تغییر minor، نمونهٔ استفاده باید هم با نسخهٔ قبل و هم با نسخهٔ بعد با موفقیت ساخته شود.

    Major: تغییر نام/جابه‌جایی/حذف هر آیتم عمومی

    نبودِ یک آیتم که به‌صورت عمومی در دسترس بود باعث می‌شود هر استفاده‌ای از آن آیتم کامپایل نشود.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn foo() {}

///////////////////////////////////////////////////////////
// After
// ... item has been removed

///////////////////////////////////////////////////////////
// Example usage that will break.
fn main() {
    updated_crate::foo(); // Error: cannot find function `foo`
}

    این شامل افزودن هر نوع attribute با نام cfg هم می‌شود که می‌تواند بر اساس کامپایل شرطی تغییر دهد کدام آیتم‌ها یا رفتارها در دسترس‌اند.

    Mitigating strategies:

    • آیتم‌هایی را که باید حذف شوند deprecated علامت بزنید و بعداً در یک انتشار شکننده از نظر SemVer حذف‌شان کنید.
    • آیتم‌های تغییرنام‌یافته را deprecated علامت بزنید و با یک آیتم pub use آن را با نام قدیمی دوباره صادر (re-export) کنید.

    Minor: افزودن آیتم‌های عمومی جدید

    افزودن آیتم‌های عمومی جدید یک تغییر minor است.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
// ... absence of item

///////////////////////////////////////////////////////////
// After
pub fn foo() {}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
// `foo` is not used since it didn't previously exist.

    توجه کنید که در برخی موارد نادر این می‌تواند به‌دلیل glob import یک تغییر شکننده باشد. برای مثال، اگر trait جدیدی اضافه کنید و پروژه‌ای از glob import استفاده کرده باشد که آن trait را وارد scope می‌کند، و trait جدید عضو وابسته‌ای معرفی کند که با نوع‌هایی که روی آن‌ها پیاده‌سازی شده تداخل دارد، این می‌تواند به‌دلیل ابهام باعث خطای زمان کامپایل شود. مثال:

    // Breaking change example

///////////////////////////////////////////////////////////
// Before
// ... absence of trait

///////////////////////////////////////////////////////////
// After
pub trait NewTrait {
    fn foo(&self) {}
}

impl NewTrait for i32 {}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::*;

pub trait LocalTrait {
    fn foo(&self) {}
}

impl LocalTrait for i32 {}

fn main() {
    123i32.foo(); // Error:  multiple applicable items in scope
}

    این یک تغییر major به حساب نمی‌آید چون طبق قرارداد glob importها خطری شناخته‌شده برای سازگاری رو‌به‌جلو هستند. glob import آیتم‌ها از crateهای خارجی باید پرهیز شود.

    Major: تغییر تراز (alignment)، چیدمان (layout) یا اندازهٔ نوعی که به‌خوبی تعریف شده است

    تغییر تراز، چیدمان یا اندازهٔ نوعی که قبلاً به‌خوبی تعریف شده بود یک تغییر شکننده است.

    به‌طور کلی، نوع‌هایی که از نمایش پیش‌فرض استفاده می‌کنند تراز، چیدمان یا اندازهٔ به‌خوبی تعریف‌شده‌ای ندارند. کامپایلر آزاد است تراز، چیدمان یا اندازه را تغییر دهد، پس کد نباید دربارهٔ آن فرضی بکند.

    Note

    ممکن است crateهای خارجی اگر دربارهٔ تراز، چیدمان یا اندازهٔ نوعی فرض کنند، حتی اگر به‌خوبی تعریف نشده باشد، بشکنند. این یک شکست SemVer به حساب نمی‌آید چون نباید چنین فرض‌هایی کرد.

    برخی نمونه‌های تغییرهایی که شکننده نیستند (با فرض اینکه هیچ قاعدهٔ دیگری در این راهنما نقض نشود):

    • افزودن، حذف، جابه‌جایی ترتیب یا تغییر فیلدهای struct، union یا enum با نمایش پیش‌فرض، به‌گونه‌ای که تغییر از قواعد دیگر این راهنما پیروی کند (مثلاً استفاده از non_exhaustive برای مجاز‌کردن آن تغییرها، یا تغییر فیلدهایی که از قبل خصوصی‌اند). نگاه کنید به struct-add-private-field-when-public، struct-add-public-field-when-no-private، struct-private-fields-with-private، enum-fields-new.
    • افزودن variant به enum با نمایش پیش‌فرض، اگر enum از non_exhaustive استفاده کند. این ممکن است تراز یا اندازهٔ enum را تغییر دهد، اما آن‌ها به‌خوبی تعریف نشده‌اند. نگاه کنید به enum-variant-new.
    • افزودن، حذف، جابه‌جایی ترتیب یا تغییر فیلدهای خصوصی struct، union یا enum از نوع repr(C)، با پیروی از قواعد دیگر این راهنما (مثلاً استفاده از non_exhaustive، یا افزودن فیلد خصوصی وقتی فیلدهای خصوصی دیگری از قبل وجود دارند). نگاه کنید به repr-c-private-change.
    • افزودن variant به enum از نوع repr(C)، اگر enum از non_exhaustive استفاده کند. نگاه کنید به repr-c-enum-variant-new.
    • افزودن repr(C) به struct، union یا enum با نمایش پیش‌فرض. نگاه کنید به repr-c-add.
    • افزودن نمایش اولیه (primitive representation) به شکل repr(<int>) به یک enum. نگاه کنید به repr-int-enum-add.
    • افزودن repr(transparent) به struct یا enum با نمایش پیش‌فرض. نگاه کنید به repr-transparent-add.

    نوع‌هایی که از attribute با نام repr استفاده می‌کنند، تراز و چیدمانی دارند که به‌نحوی تعریف شده و کد ممکن است دربارهٔ آن فرض‌هایی بکند که با تغییر آن نوع می‌شکنند.

    در برخی موارد، نوع‌هایی با attribute با نام repr ممکن است تراز، چیدمان یا اندازهٔ به‌خوبی تعریف‌شده‌ای نداشته باشند. در این موارد ممکن است تغییر دادن نوع‌ها ایمن باشد، اما باید احتیاط کرد. برای مثال، نوع‌هایی با فیلدهای خصوصی که تضمین‌های تراز، چیدمان یا اندازهٔ خود را مستند نکرده‌اند، نمی‌توانند مورد اتکای crateهای خارجی باشند، چون API عمومی تراز، چیدمان یا اندازهٔ نوع را کامل تعریف نمی‌کند.

    مثال رایج نوعی با فیلدهای خصوصی که به‌خوبی تعریف شده، نوعی با یک فیلد خصوصی از نوع جنریک است که از repr(transparent) استفاده می‌کند و متن مستندات دربارهٔ شفاف‌بودن آن نسبت به نوع جنریک بحث می‌کند. برای مثال UnsafeCell را ببینید.

    برخی نمونه‌های تغییرهای شکننده:

    • افزودن repr(packed) به struct یا union. نگاه کنید به repr-packed-add.
    • افزودن repr(align) به struct، union یا enum. نگاه کنید به repr-align-add.
    • حذف repr(packed) از struct یا union. نگاه کنید به repr-packed-remove.
    • تغییر مقدار N در repr(packed(N)) اگر تراز یا چیدمان را تغییر دهد. نگاه کنید به repr-packed-n-change.
    • تغییر مقدار N در repr(align(N)) اگر تراز را تغییر دهد. نگاه کنید به repr-align-n-change.
    • حذف repr(align) از struct، union یا enum. نگاه کنید به repr-align-remove.
    • تغییر ترتیب فیلدهای عمومی نوعی با repr(C). نگاه کنید به repr-c-shuffle.
    • حذف repr(C) از struct، union یا enum. نگاه کنید به repr-c-remove.
    • حذف repr(<int>) از enum. نگاه کنید به repr-int-enum-remove.
    • تغییر نمایش اولیهٔ enum با repr(<int>). نگاه کنید به repr-int-enum-change.
    • حذف repr(transparent) از struct یا enum. نگاه کنید به repr-transparent-remove.

    Minor: افزودن، حذف یا تغییر فیلد خصوصی در repr(C)

    افزودن، حذف یا تغییر فیلد خصوصی struct، union یا enum با repr(C) معمولاً ایمن است، به شرط پیروی از رهنمودهای دیگر این راهنما (نگاه کنید به struct-add-private-field-when-public، struct-add-public-field-when-no-private، struct-private-fields-with-private، enum-fields-new).

    برای مثال، افزودن فیلد خصوصی فقط وقتی ممکن است که فیلدهای خصوصی دیگری از قبل وجود داشته باشند، یا نوع non_exhaustive باشد. فیلدهای عمومی را می‌توان اضافه کرد اگر فیلد خصوصی وجود داشته باشد یا non_exhaustive باشد، و افزودن آن چیدمان فیلدهای دیگر را تغییر ندهد.

    با این حال، این ممکن است اندازه و تراز نوع را تغییر دهد. اگر اندازه یا تراز تغییر کند باید احتیاط کرد. کد نباید دربارهٔ اندازه یا تراز نوع‌هایی با فیلد خصوصی یا non_exhaustive فرضی بکند، مگر اینکه اندازه یا ترازی مستند شده باشد.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
#[derive(Default)]
#[repr(C)]
pub struct Example {
    pub f1: i32,
    f2: i32, // a private field
}

///////////////////////////////////////////////////////////
// After
#[derive(Default)]
#[repr(C)]
pub struct Example {
    pub f1: i32,
    f2: i32,
    f3: i32, // a new field
}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
fn main() {
    // NOTE: Users should not make assumptions about the size or alignment
    // since they are not documented.
    let f = updated_crate::Example::default();
}

    Minor: افزودن variant به enum با repr(C)

    افزودن variant به enum با repr(C) معمولاً ایمن است، اگر enum از non_exhaustive استفاده کند. برای بحث بیشتر enum-variant-new را ببینید.

    توجه کنید که این می‌تواند تغییری شکننده باشد چون اندازه و تراز نوع را عوض می‌کند. برای نگرانی‌های مشابه repr-c-private-change را ببینید.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
#[repr(C)]
#[non_exhaustive]
pub enum Example {
    Variant1 { f1: i16 },
    Variant2 { f1: i32 },
}

///////////////////////////////////////////////////////////
// After
#[repr(C)]
#[non_exhaustive]
pub enum Example {
    Variant1 { f1: i16 },
    Variant2 { f1: i32 },
    Variant3 { f1: i64 }, // added
}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
fn main() {
    // NOTE: Users should not make assumptions about the size or alignment
    // since they are not specified. For example, this raised the size from 8
    // to 16 bytes.
    let f = updated_crate::Example::Variant2 { f1: 123 };
}

    افزودن فیلدهای جدید به variant از enum تغییری شکننده است، چون همهٔ فیلدها عمومی‌اند و سازنده‌ها و matchکردن کامپایل نمی‌شوند.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub enum E {
    Variant1 { f1: i32 },
}

///////////////////////////////////////////////////////////
// After
pub enum E {
    Variant1 { f1: i32, f2: i32 },
}

///////////////////////////////////////////////////////////
// Example usage that will break.
fn main() {
    use updated_crate::E;
    let x = E::Variant1 { f1: 1 }; // Error: missing f2
    match x {
        E::Variant1 { f1 } => {} // Error: missing f2
    }
}

    Mitigation strategies:

    • هنگام معرفی enum، variant را non_exhaustive علامت بزنید تا بدون wildcard نتوان آن را ساخت یا match کرد. 
      pub enum E {
    #[non_exhaustive]
    Variant1{f1: i32}
}
    • هنگام معرفی enum، یک struct صریح را به‌عنوان مقدار به‌کار ببرید تا بتوانید دید (visibility) فیلدها را کنترل کنید. 
      pub struct Foo {
   f1: i32,
   f2: i32,
}
pub enum E {
    Variant1(Foo)
}

    Major: افزودن عضو trait بدون پیاده‌سازی پیش‌فرض

    افزودن عضو بدون پیاده‌سازی پیش‌فرض به trait تغییری شکننده است. این همهٔ پیاده‌ساز‌های trait را می‌شکند.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}

///////////////////////////////////////////////////////////
// After
pub trait Trait {
    fn foo(&self);
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Trait;
struct Foo;

impl Trait for Foo {}  // Error: not all trait items implemented

    Mitigation strategies:

    • همیشه برای اعضای وابستهٔ جدید trait پیاده‌سازی یا مقدار پیش‌فرض ارائه دهید.
    • هنگام معرفی trait، از تکنیک sealed trait استفاده کنید تا کاربران بیرون از crate نتوانند trait را پیاده‌سازی کنند.

    Major: هر تغییر در امضای اعضای trait

    هر تغییری در امضای عضو trait تغییری شکننده است. این می‌تواند پیاده‌ساز‌های خارجی trait را بشکند.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {
    fn f(&self, x: i32) {}
}

///////////////////////////////////////////////////////////
// After
pub trait Trait {
    // For sealed traits or normal functions, this would be a minor change
    // because generalizing with generics strictly expands the possible uses.
    // But in this case, trait implementations must use the same signature.
    fn f<V>(&self, x: V) {}
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Trait;
struct Foo;

impl Trait for Foo {
    fn f(&self, x: i32) {}  // Error: trait declaration has 1 type parameter
}

    Mitigation strategies:

    • به‌جای تغییر اعضای موجود، اعضای جدید با پیاده‌سازی پیش‌فرض بیفزایید تا قابلیت جدید را پوشش دهند.
    • هنگام معرفی trait، از تکنیک sealed trait استفاده کنید تا کاربران بیرون از crate نتوانند trait را پیاده‌سازی کنند.

    Possibly-breaking: افزودن عضو trait دارای پیاده‌سازی پیش‌فرض

    افزودن عضو trait دارای پیاده‌سازی پیش‌فرض معمولاً ایمن است. اما گاهی می‌تواند باعث خطای کامپایل شود. برای مثال اگر متدی با همین نام در trait دیگری وجود داشته باشد، ابهام ایجاد می‌شود.

    // Breaking change example

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}

///////////////////////////////////////////////////////////
// After
pub trait Trait {
    fn foo(&self) {}
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Trait;
struct Foo;

trait LocalTrait {
    fn foo(&self) {}
}

impl Trait for Foo {}
impl LocalTrait for Foo {}

fn main() {
    let x = Foo;
    x.foo(); // Error: multiple applicable items in scope
}

    توجه کنید که این ابهام برای تداخل نام در پیاده‌سازی‌های ذاتی (inherent) وجود ندارد، چون آن‌ها بر اعضای trait اولویت دارند.

    برای یک حالت خاص که هنگام افزودن اعضای trait باید در نظر گرفت، trait-object-safety را ببینید.

    Mitigation strategies:

    • برخی پروژه‌ها ممکن است این شکستگی را قابل‌قبول بدانند، به‌ویژه اگر نام آیتم جدید بعید باشد با کد موجود تداخل کند. نام‌ها را با دقت انتخاب کنید تا از این تداخل‌ها جلوگیری شود. همچنین ممکن است قابل‌قبول باشد که از کاربران پایین‌دست خواسته شود هنگام به‌روزرسانی وابستگی، نحو رفع ابهام را اضافه کنند تا تابع درست انتخاب شود.

    Major: افزودن عضوی به trait که آن را non-object-safe می‌کند

    افزودن عضوی به trait که باعث شود trait دیگر object safe نباشد، تغییری شکننده است.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}

///////////////////////////////////////////////////////////
// After
pub trait Trait {
    // An associated const makes the trait not object-safe.
    const CONST: i32 = 123;
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Trait;
struct Foo;

impl Trait for Foo {}

fn main() {
    let obj: Box<dyn Trait> = Box::new(Foo); // Error: the trait `updated_crate::Trait` is not dyn compatible
}

    عکس آن (تبدیل trait غیر object safe به object safe) ایمن است.

    Major: افزودن پارامتر نوع بدون مقدار پیش‌فرض

    افزودن پارامتر نوع بدون مقدار پیش‌فرض به trait تغییری شکننده است.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}

///////////////////////////////////////////////////////////
// After
pub trait Trait<T> {}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Trait;
struct Foo;

impl Trait for Foo {}  // Error: missing generics

    Mitigating strategies:

    • افزودن پارامتر نوع دارای مقدار پیش‌فرض به trait را ببینید.

    Minor: افزودن پارامتر نوع دارای مقدار پیش‌فرض به trait

    افزودن پارامتر نوع به trait تا زمانی که مقدار پیش‌فرض داشته باشد ایمن است. پیاده‌ساز‌های خارجی بدون نیاز به مشخص‌کردن پارامتر، از مقدار پیش‌فرض استفاده می‌کنند.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}

///////////////////////////////////////////////////////////
// After
pub trait Trait<T = i32> {}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::Trait;
struct Foo;

impl Trait for Foo {}

    Possibly-breaking: افزودن هر عضو ذاتی (inherent)

    معمولاً افزودن اعضای ذاتی به یک پیاده‌سازی باید ایمن باشد چون اعضای ذاتی بر اعضای trait اولویت دارند. با این حال، در برخی موارد اگر نام با عضو trait پیاده‌سازی‌شده‌ای که امضای متفاوت دارد یکی باشد، این تداخل می‌تواند مشکل ایجاد کند.

    // Breaking change example

///////////////////////////////////////////////////////////
// Before
pub struct Foo;

///////////////////////////////////////////////////////////
// After
pub struct Foo;

impl Foo {
    pub fn foo(&self) {}
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Foo;

trait Trait {
    fn foo(&self, x: i32) {}
}

impl Trait for Foo {}

fn main() {
    let x = Foo;
    x.foo(1); // Error: this method takes 0 arguments but 1 argument was supplied
}

    توجه کنید که اگر امضاها یکی باشند، خطای زمان کامپایل رخ نمی‌دهد، اما ممکن است رفتار زمان اجرا بی‌صدا تغییر کند (چون اکنون تابع دیگری اجرا می‌شود).

    Mitigation strategies:

    • برخی پروژه‌ها ممکن است این شکستگی را قابل‌قبول بدانند، به‌ویژه اگر نام آیتم جدید بعید باشد با کد موجود تداخل کند. نام‌ها را با دقت انتخاب کنید تا از این تداخل‌ها جلوگیری شود. همچنین ممکن است قابل‌قبول باشد که از کاربران پایین‌دست خواسته شود هنگام به‌روزرسانی وابستگی، نحو رفع ابهام را اضافه کنند تا تابع درست انتخاب شود.

    Major: سخت‌گیرانه‌ترکردن کران‌های جنریک

    سخت‌گیرانه‌ترکردن کران‌های جنریک یک نوع تغییری شکننده است چون می‌تواند کاربرانی را که انتظار کران‌های سهل‌گیرانه‌تر دارند بشکند.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo<A> {
    pub f1: A,
}

///////////////////////////////////////////////////////////
// After
pub struct Foo<A: Eq> {
    pub f1: A,
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Foo;

fn main() {
    let s = Foo { f1: 1.23 }; // Error: the trait bound `{float}: Eq` is not satisfied
}

    Minor: سهل‌گیرانه‌ترکردن کران‌های جنریک

    سهل‌گیرانه‌ترکردن کران‌های جنریک یک نوع ایمن است، چون فقط آنچه را مجاز است گسترش می‌دهد.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo<A: Clone> {
    pub f1: A,
}

///////////////////////////////////////////////////////////
// After
pub struct Foo<A> {
    pub f1: A,
}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::Foo;

fn main() {
    let s = Foo { f1: 123 };
}

    Minor: افزودن پارامترهای نوع دارای مقدار پیش‌فرض

    افزودن پارامتر نوع به یک نوع تا زمانی که مقدار پیش‌فرض داشته باشد ایمن است. همهٔ ارجاع‌های موجود بدون نیاز به مشخص‌کردن پارامتر از مقدار پیش‌فرض استفاده می‌کنند.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
#[derive(Default)]
pub struct Foo {}

///////////////////////////////////////////////////////////
// After
#[derive(Default)]
pub struct Foo<A = i32> {
    f1: A,
}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::Foo;

fn main() {
    let s: Foo = Default::default();
}

    Minor: تعمیم یک نوع به جنریک (با نوع‌های یکسان)

    فیلد struct یا enum می‌تواند از نوع مشخص به پارامتر نوع جنریک تغییر کند، به شرط اینکه تغییر برای همهٔ موارد استفادهٔ موجود نوعی یکسان بدهد. برای مثال تغییر زیر مجاز است:

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo(pub u8);

///////////////////////////////////////////////////////////
// After
pub struct Foo<T = u8>(pub T);

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::Foo;

fn main() {
    let s: Foo = Foo(123);
}

    چون استفاده‌های موجود از Foo مخفف Foo<u8> هستند که نوع فیلد یکسانی می‌دهد.

    Major: تعمیم یک نوع به جنریک (با نوع‌هایی که ممکن است متفاوت باشند)

    تغییر فیلد struct یا enum از نوع مشخص به پارامتر نوع جنریک می‌تواند شکننده باشد اگر نوع بتواند تغییر کند.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo<T = u8>(pub T, pub u8);

///////////////////////////////////////////////////////////
// After
pub struct Foo<T = u8>(pub T, pub T);

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::Foo;

fn main() {
    let s: Foo<f32> = Foo(3.14, 123); // Error: mismatched types
}

    Minor: تغییر یک نوع جنریک به نوع جنریک‌تر

    تغییر یک نوع جنریک به نوع جنریک‌تر ایمن است. برای مثال، مثال زیر یک پارامتر جنریک می‌افزاید که پیش‌فرضش نوع اصلی است؛ این ایمن است چون همهٔ کاربران موجود برای هر دو فیلد همان نوع را به‌کار می‌برند و پارامتر دارای مقدار پیش‌فرض نیازی به مشخص‌شدن ندارد.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo<T>(pub T, pub T);

///////////////////////////////////////////////////////////
// After
pub struct Foo<T, U = T>(pub T, pub U);

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::Foo;

fn main() {
    let s: Foo<f32> = Foo(1.0, 2.0);
}

    Major: capture پارامترهای جنریک بیشتر در RPIT

    capture پارامترهای جنریک اضافی در یک RPIT (impl trait در جایگاه بازگشتی) تغییری شکننده است.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn f<'a, 'b>(x: &'a str, y: &'b str) -> impl Iterator<Item = char> + use<'a> {
    x.chars()
}

///////////////////////////////////////////////////////////
// After
pub fn f<'a, 'b>(x: &'a str, y: &'b str) -> impl Iterator<Item = char> + use<'a, 'b> {
    x.chars().chain(y.chars())
}

///////////////////////////////////////////////////////////
// Example usage that will break.
fn main() {
    let a = String::new();
    let b = String::new();
    let iter = updated_crate::f(&a, &b);
    drop(b); // Error: cannot move out of `b` because it is borrowed
}

    افزودن پارامترهای جنریک به RPIT قیدهای اضافی دربارهٔ نحوهٔ استفاده از نوع حاصل ایجاد می‌کند.

    توجه کنید که وقتی نحو use<> مشخص نشده باشد، captureهای ضمنی وجود دارند. در Rust 2021 و ویرایش‌های قبلی، پارامترهای طول عمر فقط وقتی capture می‌شوند که از نظر نحوی درون یک کران در امضای نوع RPIT ظاهر شوند. از Rust 2024، همهٔ پارامترهای طول عمر بدون قید capture می‌شوند. یعنی از Rust 2024 پیش‌فرض حداکثر سازگاری را دارد و وقتی می‌خواهید کمتر capture کنید باید صریح باشید، که یک تعهد SemVer است.

    برای اطلاعات بیشتر دربارهٔ captureکردن در RPIT، راهنمای ویرایش‌ها و مرجع را ببینید.

    capture پارامترهای جنریک کمتر در RPIT تغییری minor است.

    Note

    همهٔ پارامترهای جنریک نوع و ثابت (const) در scope باید یا ضمنی capture شوند (بدون + use<…>) یا صریح (باید در + use<…> فهرست شوند)، و بنابراین فعلاً تغییر آنچه از این نوع جنریک‌ها capture می‌شود مجاز نیست.

    Major: افزودن/حذف پارامترهای تابع

    تغییر تعداد پارامترهای تابع (arity) تغییری شکننده است.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn foo() {}

///////////////////////////////////////////////////////////
// After
pub fn foo(x: i32) {}

///////////////////////////////////////////////////////////
// Example usage that will break.
fn main() {
    updated_crate::foo(); // Error: this function takes 1 argument
}

    Mitigating strategies:

    • تابع جدیدی با امضای جدید معرفی کنید و احتمالاً تابع قدیمی را deprecate کنید.
    • تابع‌هایی معرفی کنید که یک struct را به‌عنوان آرگومان می‌گیرند و struct با الگوی builder ساخته می‌شود. این به افزودن فیلدهای جدید به struct در آینده اجازه می‌دهد.

    Possibly-breaking: معرفی پارامتر نوع جدید برای تابع

    معمولاً افزودن پارامتر نوع بدون مقدار پیش‌فرض ایمن است، اما در برخی موارد می‌تواند تغییری شکننده باشد:

    // Breaking change example

///////////////////////////////////////////////////////////
// Before
pub fn foo<T>() {}

///////////////////////////////////////////////////////////
// After
pub fn foo<T, U>() {}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::foo;

fn main() {
    foo::<u8>(); // Error: function takes 2 generic arguments but 1 generic argument was supplied
}

    با این حال، چنین فراخوانی‌های صریحی آن‌قدر نادرند (و معمولاً می‌توان به شکل دیگری نوشتشان) که این شکستگی معمولاً قابل‌قبول است. باید در نظر گرفت که چقدر احتمال دارد تابع مورد نظر با آرگومان‌های نوع صریح فراخوانی شود.

    Minor: تعمیم تابع به جنریک (با پشتیبانی از نوع اصلی)

    نوع پارامتر تابع یا مقدار بازگشتی آن را می‌توان با جنریک تعمیم داد، از جمله با معرفی پارامتر نوع جدید، مادامی که بتوان آن را با نوع اصلی نمونه‌سازی کرد. برای مثال تغییرهای زیر مجازند:

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn foo(x: u8) -> u8 {
    x
}
pub fn bar<T: Iterator<Item = u8>>(t: T) {}

///////////////////////////////////////////////////////////
// After
use std::ops::Add;
pub fn foo<T: Add>(x: T) -> T {
    x
}
pub fn bar<T: IntoIterator<Item = u8>>(t: T) {}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::{bar, foo};

fn main() {
    foo(1);
    bar(vec![1, 2, 3].into_iter());
}

    چون همهٔ استفاده‌های موجود نمونه‌سازی‌هایی از امضای جدید هستند.

    شاید تا حدی شگفت‌آور، تعمیم برای trait objectها هم صدق می‌کند، چون هر trait خودش را پیاده‌سازی می‌کند:

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub trait Trait {}
pub fn foo(t: &dyn Trait) {}

///////////////////////////////////////////////////////////
// After
pub trait Trait {}
pub fn foo<T: Trait + ?Sized>(t: &T) {}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.
use updated_crate::{foo, Trait};

struct Foo;
impl Trait for Foo {}

fn main() {
    let obj = Foo;
    foo(&obj);
}

    (استفاده از ?Sized ضروری است؛ در غیر این صورت نمی‌توانید امضای اصلی را بازیابی کنید.)

    معرفی جنریک‌ها به این شکل می‌تواند بالقوه باعث شکست استنتاج نوع شود. این معمولاً نادر است و ممکن است برای برخی پروژه‌ها شکستگی قابل‌قبول باشد، چون با افزودن annotationهای نوع قابل‌رفع است.

    // Breaking change example

///////////////////////////////////////////////////////////
// Before
pub fn foo() -> i32 {
    0
}

///////////////////////////////////////////////////////////
// After
pub fn foo<T: Default>() -> T {
    Default::default()
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::foo;

fn main() {
    let x = foo(); // Error: type annotations needed
}

    Major: تعمیم تابع به جنریک با عدم تطابق نوع

    تغییر پارامتر یا نوع بازگشتی تابع شکننده است اگر نوع جنریک نوع‌های مجاز قبلی را محدود یا عوض کند. برای مثال، مثال زیر قید جنریکی می‌افزاید که ممکن است کد موجود آن را برآورده نکند:

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn foo(x: Vec<u8>) {}

///////////////////////////////////////////////////////////
// After
pub fn foo<T: Copy + IntoIterator<Item = u8>>(x: T) {}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::foo;

fn main() {
    foo(vec![1, 2, 3]); // Error: `Copy` is not implemented for `Vec<u8>`
}

    Minor: safe‌کردن یک تابع unsafe

    تابعی که قبلاً unsafe بود می‌تواند بدون شکستن کد safe شود.

    توجه کنید با این حال ممکن است lint با نام unused_unsafe را مانند مثال زیر فعال کند، که باعث می‌شود crateهای محلی‌ای که #![deny(warnings)] را مشخص کرده‌اند دیگر کامپایل نشوند. طبق معرفی lintهای جدید، به‌روزرسانی‌ها مجازند هشدارهای جدید معرفی کنند.

    در جهت عکس (unsafeکردن یک تابع safe) تغییری شکننده است.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub unsafe fn foo() {}

///////////////////////////////////////////////////////////
// After
pub fn foo() {}

///////////////////////////////////////////////////////////
// Example use of the library that will trigger a lint.
use updated_crate::foo;

unsafe fn bar(f: unsafe fn()) {
    f()
}

fn main() {
    unsafe { foo() }; // The `unused_unsafe` lint will trigger here
    unsafe { bar(foo) };
}

    safe‌کردن یک تابع وابسته یا متد unsafe روی structها / enumها هم تغییر minor است، اما همین موضوع برای تابع وابسته در traitها صدق نمی‌کند (هر تغییر در امضای اعضای trait را ببینید).

    Major: تغییر از پشتیبانی no_std به نیاز به std

    اگر کتابخانهٔ شما صراحتاً از محیط no_std پشتیبانی می‌کند، انتشار نسخهٔ جدیدی که std را لازم دارد تغییری شکننده است.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
#![no_std]
pub fn foo() {}

///////////////////////////////////////////////////////////
// After
pub fn foo() {
    std::time::SystemTime::now();
}

///////////////////////////////////////////////////////////
// Example usage that will break.
// This will fail to link for no_std targets because they don't have a `std` crate.
#![no_std]
use updated_crate::foo;

fn example() {
    foo();
}

    Mitigation strategies:

    • یک الگوی رایج برای پرهیز از این، افزودن feature در Cargo با نام std است که پشتیبانی از std را به‌صورت اختیاری فعال می‌کند، و وقتی feature خاموش باشد، کتابخانه در محیط no_std قابل‌استفاده است.

    Major: افزودن non_exhaustive به enum، variant یا struct موجودی که فیلد خصوصی ندارد

    #[non_exhaustive]کردن آیتم‌ها نحوهٔ استفاده از آن‌ها را بیرون از crate‌ای که در آن تعریف شده‌اند تغییر می‌دهد:

    • structها و variantهای enum از نوع non-exhaustive را نمی‌توان با نحو struct literal ساخت، از جمله نحو به‌روزرسانی تابعی (functional update).
    • pattern matching روی structهای non-exhaustive نیازمند .. است و matchکردن روی enumها در جامع‌بودن (exhaustiveness) حساب نمی‌شود.
    • تبدیل variantهای enum به discriminant با as مجاز نیست.

    structهای دارای فیلد خصوصی را نمی‌توان با نحو struct literal ساخت، چه #[non_exhaustive] استفاده شود چه نه. افزودن #[non_exhaustive] به چنین structی تغییر شکننده نیست.

    // MAJOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub struct Foo {
    pub bar: usize,
}

pub enum Bar {
    X,
    Y(usize),
    Z { a: usize },
}

pub enum Quux {
    Var,
}

///////////////////////////////////////////////////////////
// After
#[non_exhaustive]
pub struct Foo {
    pub bar: usize,
}

pub enum Bar {
    #[non_exhaustive]
    X,

    #[non_exhaustive]
    Y(usize),

    #[non_exhaustive]
    Z { a: usize },
}

#[non_exhaustive]
pub enum Quux {
    Var,
}

///////////////////////////////////////////////////////////
// Example usage that will break.
use updated_crate::{Bar, Foo, Quux};

fn main() {
    let foo = Foo { bar: 0 }; // Error: cannot create non-exhaustive struct using struct expression

    let bar_x = Bar::X; // Error: unit variant `X` is private
    let bar_y = Bar::Y(0); // Error: tuple variant `Y` is private
    let bar_z = Bar::Z { a: 0 }; // Error: cannot create non-exhaustive variant using struct expression

    let q = Quux::Var;
    match q {
        Quux::Var => 0,
        // Error: non-exhaustive patterns: `_` not covered
    };
}

    Mitigation strategies:

    • structها، enumها و variantهای enum را هنگام معرفی اولیه به‌صورت #[non_exhaustive] علامت بزنید، نه اینکه بعداً آن را اضافه کنید.

    سازگاری ابزار و محیط

    Possibly-breaking: تغییر حداقل نسخهٔ Rust مورد نیاز

    استفاده از قابلیت‌های جدید در انتشار جدید Rust می‌تواند پروژه‌هایی را که از نسخه‌های قدیمی‌تر Rust استفاده می‌کنند بشکند. این شامل استفاده از قابلیت‌های جدید در انتشار جدید Cargo هم می‌شود، و نیاز به قابلیتی که فقط در nightly هست در crate‌ای که قبلاً روی stable کار می‌کرد.

    به‌طور کلی توصیه می‌شود این را به‌جای تغییر major، تغییر minor به حساب آورید، به دلایل گوناگون. معمولاً به‌روزرسانی به نسخهٔ جدیدتر Rust نسبتاً آسان است. Rust همچنین چرخهٔ انتشار سریع ۶هفته‌ای دارد و برخی پروژه‌ها در یک پنجرهٔ انتشارها سازگاری ارائه می‌دهند (مثلاً انتشار stable فعلی به‌علاوهٔ N انتشار قبلی). فقط به یاد داشته باشید که برخی پروژه‌های بزرگ ممکن است نتوانند toolchain خود را سریع به‌روز کنند.

    Mitigation strategies:

    • حداقل نسخهٔ Rust پشتیبانی‌شدهٔ بستهٔ خود را با تنظیم package.rust-version مستند کنید، تا حل وابستگی Cargo در صورت نیاز بتواند نسخه‌های قدیمی‌تر بستهٔ شما را انتخاب کند. هنگام این کار حتماً انتظارات پشتیبانی را در نظر بگیرید.
    • از featureهای Cargo استفاده کنید تا قابلیت‌های جدید اختیاری (opt-in) باشند.
    • پنجرهٔ بزرگی از پشتیبانی برای انتشارهای قدیمی‌تر ارائه دهید.
    • اگر ممکن است منبع آیتم‌های جدید کتابخانهٔ استاندارد را کپی کنید تا بتوانید همچنان از نسخهٔ قدیمی‌تر استفاده کنید اما از قابلیت جدید بهره ببرید.
    • یک شاخهٔ جداگانه برای انتشارهای minor قدیمی‌تر نگه دارید که بتواند backport رفع باگ‌های مهم را دریافت کند.
    • [cfg(version(..))] و #[cfg(accessible(..))] را زیر نظر داشته باشید؛ این قابلیت‌ها سازوکاری اختیاری برای قابلیت‌های جدید فراهم می‌کنند. فعلاً ناپایدارند و فقط در کانال nightly در دسترس‌اند.

    Possibly-breaking: تغییر نیازمندی‌های پلتفرم و محیط

    کتابخانه فرض‌های بسیار گسترده‌ای دربارهٔ محیطی که در آن اجرا می‌شود می‌کند، مثل پلتفرم میزبان، نسخهٔ سیستم‌عامل، سرویس‌های در دسترس، پشتیبانی سیستم‌فایل و غیره. اگر انتشار جدیدی آنچه را قبلاً پشتیبانی می‌شد محدود کند، مثلاً نسخهٔ جدیدتری از سیستم‌عامل را لازم بداند، می‌تواند تغییری شکننده باشد. پیگیری این تغییرها دشوار است، چون همیشه نمی‌دانید یک تغییر در محیطی که به‌طور خودکار تست نمی‌شود می‌شکند یا نه.

    برخی پروژه‌ها ممکن است این شکستگی را قابل‌قبول بدانند، به‌ویژه اگر شکستگی برای بیشتر کاربران بعید باشد یا پروژه منابع پشتیبانی از همهٔ محیط‌ها را نداشته باشد. موقعیت قابل‌توجه دیگر وقتی است که فروشنده‌ای پشتیبانی از سخت‌افزار یا سیستم‌عاملی را متوقف می‌کند و پروژه ممکن است قطع پشتیبانی خود را هم منطقی بداند.

    Mitigation strategies:

    • پلتفرم‌ها و محیط‌هایی را که صراحتاً پشتیبانی می‌کنید مستند کنید.
    • کد خود را در CI روی طیف گسترده‌ای از محیط‌ها تست کنید.

    Minor: معرفی lintهای جدید

    برخی تغییرها در یک کتابخانه ممکن است باعث فعال‌شدن lintهای جدید در کاربران آن کتابخانه شوند. این معمولاً باید تغییری سازگار به حساب آید.

    // MINOR CHANGE

///////////////////////////////////////////////////////////
// Before
pub fn foo() {}

///////////////////////////////////////////////////////////
// After
#[deprecated]
pub fn foo() {}

///////////////////////////////////////////////////////////
// Example use of the library that will safely work.

fn main() {
    updated_crate::foo(); // Warning: use of deprecated function
}

    توجه کنید که از نظر فنی ممکن است این باعث شکست پروژه شود اگر هشدار را صراحتاً deny کرده باشد و crate به‌روزشده وابستگی مستقیم باشد. denyکردن هشدارها باید با دقت و با درک اینکه lintهای جدید ممکن است با گذشت زمان معرفی شوند انجام شود. با این حال، نویسندگان کتابخانه باید در معرفی هشدارهای جدید محتاط باشند و ممکن است بخواهند اثر بالقوهٔ آن را بر کاربران خود بسنجند.

    lintهای زیر نمونه‌هایی از lintهایی هستند که ممکن است هنگام به‌روزرسانی یک وابستگی معرفی شوند:

    • deprecated — وقتی وابستگی attribute با نام #[deprecated] را به آیتمی که شما استفاده می‌کنید اضافه کند معرفی می‌شود.
    • unused_must_use — وقتی وابستگی attribute با نام #[must_use] را به آیتمی اضافه کند که شما نتیجه‌اش را مصرف نمی‌کنید معرفی می‌شود.
    • unused_unsafe — وقتی وابستگی qualifier با نام unsafe را از تابعی حذف کند و آن تنها تابع unsafe فراخوانی‌شده در بلوک unsafe باشد معرفی می‌شود.

    علاوه بر این، به‌روزرسانی rustc به نسخهٔ جدید ممکن است lintهای جدید معرفی کند.

    وابستگی‌های تعدّی‌ای (transitive) که lintهای جدید معرفی می‌کنند معمولاً نباید باعث شکست شوند، چون Cargo از --cap-lints برای خاموش‌کردن همهٔ lintها در وابستگی‌ها استفاده می‌کند.

    Mitigating strategies:

    • اگر با deny‌کردن هشدارها می‌سازید، بدانید که ممکن است هر بار که وابستگی‌هایتان را به‌روز می‌کنید لازم شود هشدارهای جدید را رفع کنید. اگر برای دادن -Dwarnings از RUSTFLAGS استفاده می‌کنید، پرچم -A را هم برای مجاز‌کردن lintهایی که احتمالاً مشکل‌ساز می‌شوند اضافه کنید، مثل -Adeprecated.
    • deprecationها را پشت یک feature معرفی کنید. برای مثال #[cfg_attr(feature = "deprecated", deprecated="use bar instead")]. سپس وقتی قصد دارید آیتمی را در تغییر شکنندهٔ SemVer آینده حذف کنید، می‌توانید به کاربران اطلاع دهید که پیش از به‌روزرسانی، featureٔ deprecated را فعال کنند تا استفاده از آیتم‌های deprecated را از بین ببرند. این به کاربران اجازه می‌دهد خودشان تعیین کنند چه زمانی به deprecationها پاسخ دهند، بدون نیاز به پاسخ فوری. یک نقطه‌ضعف این است که رساندن این پیام به کاربران که باید این گام‌های دستی را برای آماده‌شدن برای به‌روزرسانی major انجام دهند دشوار است.

    Cargo

    Minor: افزودن feature جدید Cargo

    افزودن featureهای جدید Cargo معمولاً ایمن است. اگر feature تغییرهایی معرفی کند که باعث شکست شوند، این می‌تواند برای پروژه‌هایی که نیازهای سازگاری رو‌به‌عقب سخت‌گیرانه‌تری دارند مشکل ایجاد کند. در آن سناریو از افزودن feature به فهرست «default» پرهیز کنید و احتمالاً پیامدهای فعال‌کردن feature را مستند کنید.

    # MINOR CHANGE

###########################################################
# Before
[features]
# ..empty

###########################################################
# After
[features]
std = []

    Major: حذف یک feature در Cargo

    حذف featureهای Cargo معمولاً تغییری شکننده است. این برای هر پروژه‌ای که feature را فعال کرده بود خطا ایجاد می‌کند.

    # MAJOR CHANGE

###########################################################
# Before
[features]
logging = []

###########################################################
# After
[dependencies]
# ..logging removed

    Mitigation strategies:

    • featureهای خود را به‌روشنی مستند کنید. اگر feature داخلی یا آزمایشی وجود دارد، آن را چنین علامت بزنید تا کاربران وضعیت feature را بدانند.
    • feature قدیمی را در Cargo.toml نگه دارید، اما عملکردش را حذف کنید. مستند کنید که feature منسوخ (deprecated) است و آن را در یک انتشار major آیندهٔ SemVer حذف کنید.

    Major: حذف یک feature از فهرست featureها اگر عملکرد یا آیتم‌های عمومی را تغییر دهد

    اگر featureای را از feature دیگری حذف کنید، این می‌تواند کاربران موجود را بشکند، اگر انتظار داشته باشند آن عملکرد از طریق همان feature در دسترس باشد.

    # Breaking change example

###########################################################
# Before
[features]
default = ["std"]
std = []

###########################################################
# After
[features]
default = []  # This may cause packages to fail if they are expecting std to be enabled.
std = []

    Possibly-breaking: حذف یک وابستگی اختیاری

    حذف یک وابستگی اختیاری می‌تواند پروژه‌ای را که از کتابخانهٔ شما استفاده می‌کند بشکند، چون پروژه‌ای دیگر ممکن است آن وابستگی را از طریق featureهای Cargo فعال کرده باشد.

    وقتی وابستگی اختیاری وجود دارد، cargo به‌طور ضمنی featureای با همان نام تعریف می‌کند تا سازوکاری برای فعال‌کردن وابستگی و بررسی فعال‌بودن آن فراهم شود. می‌توان با استفاده از نحو dep: در جدول [features] از این مشکل پرهیز کرد، چون این feature ضمنی را غیرفعال می‌کند. استفاده از dep: امکان پنهان‌کردن وجود وابستگی‌های اختیاری را زیر نام‌هایی با معنای مرتبط‌تر می‌دهد که تغییرشان ایمن‌تر است.

    # Breaking change example

###########################################################
# Before
[dependencies]
curl = { version = "0.4.31", optional = true }

###########################################################
# After
[dependencies]
# ..curl removed

    # MINOR CHANGE
#
# This example shows how to avoid breaking changes with optional dependencies.

###########################################################
# Before
[dependencies]
curl = { version = "0.4.31", optional = true }

[features]
networking = ["dep:curl"]

###########################################################
# After
[dependencies]
# Here, one optional dependency was replaced with another.
hyper = { version = "0.14.27", optional = true }

[features]
networking = ["dep:hyper"]

    Mitigation strategies:

    • برای اینکه از ابتدا وابستگی‌های اختیاری را آشکار نکنید، از نحو dep: در جدول [features] استفاده کنید. برای اطلاعات بیشتر وابستگی‌های اختیاری را ببینید.
    • featureهای خود را به‌روشنی مستند کنید. اگر وابستگی اختیاری در فهرست مستند featureها نباشد، می‌توانید تغییر ورودی‌های مستندنشده را ایمن بدانید.
    • وابستگی اختیاری را نگه دارید و فقط در کتابخانه‌تان از آن استفاده نکنید.
    • وابستگی اختیاری را با یک feature در Cargo که کاری نمی‌کند جایگزین کنید و مستند کنید که منسوخ است.
    • از featureهای سطح بالا استفاده کنید که وابستگی‌های اختیاری را فعال می‌کنند و مستند کنید که این روش ترجیحی برای فعال‌کردن قابلیت گسترش‌یافته است. برای مثال، اگر کتابخانهٔ شما پشتیبانی اختیاری از چیزی مثل «networking» دارد، یک نام feature عمومی «networking» بسازید که وابستگی‌های اختیاری لازم برای پیاده‌سازی «networking» را فعال می‌کند. سپس feature «networking» را مستند کنید.

    Minor: تغییر featureهای وابستگی

    تغییر featureهای یک وابستگی معمولاً ایمن است، به شرط اینکه feature تغییری شکننده معرفی نکند.

    # MINOR CHANGE

###########################################################
# Before
[dependencies]
rand = { version = "0.7.3", features = ["small_rng"] }


###########################################################
# After
[dependencies]
rand = "0.7.3"

    Minor: adding dependencies

    افزودن وابستگی‌های جدید معمولاً ایمن است، به شرط اینکه وابستگی جدید نیازمندی‌های تازه‌ای معرفی نکند که به تغییر شکننده بینجامد. برای مثال، افزودن وابستگی جدیدی که nightly می‌خواهد در پروژه‌ای که قبلاً روی stable کار می‌کرد تغییر major است.

    # MINOR CHANGE

###########################################################
# Before
[dependencies]
# ..empty

###########################################################
# After
[dependencies]
log = "0.4.11"

    Application compatibility

    پروژه‌های Cargo ممکن است شامل فایل‌های دودویی اجرایی هم باشند که رابط‌های خودشان را دارند (مثل رابط CLI، تعامل در سطح سیستم‌عامل و غیره). از آنجا که این‌ها بخشی از بستهٔ Cargo هستند، اغلب از همان نسخهٔ بسته استفاده می‌کنند. باید تصمیم بگیرید که آیا و چگونه می‌خواهید یک قرارداد SemVer با کاربران خود دربارهٔ تغییرهایی که در برنامه می‌دهید به‌کار ببرید. تغییرهای شکننده و سازگار بالقوهٔ یک برنامه آن‌قدر زیادند که نمی‌توان فهرستشان کرد، پس توصیه می‌شود از روح مشخصات SemVer برای هدایت تصمیم‌هایتان دربارهٔ نحوهٔ اعمال نسخه‌گذاری بر برنامه استفاده کنید، یا دست‌کم تعهدهایتان را مستند کنید.
