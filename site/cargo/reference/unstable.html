    Unstable Features

    قابلیت‌های آزمایشی Cargo فقط در کانال nightly در دسترس‌اند. توصیه می‌شود این قابلیت‌ها را امتحان کنید تا ببینید نیازهایتان را برآورده می‌کنند یا نه و آیا مشکلی هست. برای اطلاعات بیشتر دربارهٔ هر قابلیت، issueهای پیگیری (tracking) پیوندخورده در زیر را ببینید، و اگر خواهان به‌روزرسانی‌های آینده هستید دکمهٔ subscribe در GitHub را بزنید.

    پس از مدتی، اگر قابلیت نگرانی عمده‌ای نداشته باشد، می‌تواند پایدار (stabilize) شود، که آن را پس از رسیدن انتشار nightly فعلی به کانال stable (بین ۶ تا ۱۲ هفته) در stable در دسترس می‌کند.

    بسته به نحوهٔ کار قابلیت، سه روش مختلف برای فعال‌کردن قابلیت‌های ناپایدار وجود دارد:

    • نحو جدید در Cargo.toml یک کلید cargo-features در بالای Cargo.toml، پیش از هر جدولی، لازم دارد. برای مثال:

      # This specifies which new Cargo.toml features are enabled.
cargo-features = ["test-dummy-unstable"]

[package]
name = "my-package"
version = "0.1.0"
im-a-teapot = true  # This is a new option enabled by test-dummy-unstable.

    • پرچم‌ها، گزینه‌ها و زیردستورهای جدید خط فرمان نیاز دارند گزینهٔ -Z unstable-options هم داده شود. برای مثال، گزینهٔ جدید --artifact-dir فقط در nightly در دسترس است:

      cargo +nightly build --artifact-dir=out -Z unstable-options

    • پرچم‌های خط فرمان -Z برای فعال‌کردن قابلیت‌های جدیدی به‌کار می‌روند که ممکن است رابطی نداشته باشند، یا رابطشان هنوز طراحی نشده، یا برای قابلیت‌های پیچیده‌تری که چند بخش Cargo را تحت‌تأثیر قرار می‌دهند. برای مثال، قابلیت mtime-on-use را می‌توان با این فعال کرد:

      cargo +nightly build -Z mtime-on-use

      برای دیدن فهرست پرچم‌های موجود cargo -Z help را اجرا کنید.

      هر چیزی را که با پرچم -Z می‌توان پیکربندی کرد، می‌توان در فایل پیکربندی cargo (.cargo/config.toml) و در جدول unstable هم تنظیم کرد. برای مثال:

      [unstable]
mtime-on-use = true
build-std = ["core", "alloc"]

    هر قابلیت جدیدی که در ادامه شرح داده شده باید توضیح دهد چگونه از آن استفاده می‌شود.

    برای جدیدترین nightly، نسخهٔ nightly این صفحه را ببینید.

    • Unstable-specific features

    • Build scripts and linking
      • Metabuild — اسکریپت‌های ساخت اعلانی (declarative) فراهم می‌کند.
      • Multiple Build Scripts — استفاده از چند اسکریپت ساخت را ممکن می‌کند.
      • Any Build Script Metadata — اجازه می‌دهد هر اسکریپت ساخت از طریق cargo::metadata=key=value متغیرهای محیطی مشخص کند

      • no-index-update — از به‌روزرسانی cache فهرست توسط cargo جلوگیری می‌کند.
      • avoid-dev-deps — از گنجاندن dev-dependencies در حل وابستگی توسط حل‌کننده جلوگیری می‌کند.
      • minimal-versions — حل‌کننده را مجبور می‌کند به‌جای بالاترین نسخه از پایین‌ترین نسخهٔ سازگار استفاده کند.
      • direct-minimal-versions — حل‌کننده را مجبور می‌کند به‌جای بالاترین نسخه از پایین‌ترین نسخهٔ سازگار استفاده کند.
      • public-dependency — اجازه می‌دهد وابستگی‌ها به‌صورت عمومی یا خصوصی طبقه‌بندی شوند.
      • msrv-policy — حل‌کننده و انتخاب نسخهٔ آگاه از MSRV
      • prerelease — اجازه می‌دهد نسخه‌های پیش‌انتشار با update --precise انتخاب شوند
      • sbom — فایل‌های پیش‌نیاز SBOM را برای آرتیفکت‌های کامپایل‌شده تولید می‌کند
      • feature-unification — حالت‌های جدید یکپارچه‌سازی featureها را در workspaceها فعال می‌کند
      • lockfile-publish-time — حل‌کننده را به بسته‌های قدیمی‌تر از زمان مشخص‌شده محدود می‌کند
    • Output behavior
      • artifact-dir — پوشه‌ای اضافه می‌کند که آرتیفکت‌ها در آن کپی می‌شوند.
      • Different binary name — به فایل دودویی ساخته‌شده نامی جدا از نام crate می‌دهد.
      • root-dir — پوشهٔ ریشه‌ای را که مسیرها نسبت به آن چاپ می‌شوند کنترل می‌کند
    • Compile behavior
      • mtime-on-use — هر بار که یک وابستگی استفاده شود زمان آخرین تغییر آن را به‌روز می‌کند تا سازوکاری برای حذف آرتیفکت‌های استفاده‌نشده فراهم شود.
      • build-std — به‌جای استفاده از فایل‌های دودویی از پیش ساخته‌شده، کتابخانهٔ استاندارد را می‌سازد.
      • build-std-features — featureهایی را که با کتابخانهٔ استاندارد استفاده می‌شوند تنظیم می‌کند.
      • binary-dep-depinfo — باعث می‌شود فایل dep-info وابستگی‌های دودویی را هم دنبال کند.
      • checksum-freshness — در صورت استفاده، تصمیم دربارهٔ لزوم بازسازی crate به‌جای mtime فایل بر اساس checksum فایل‌ها گرفته می‌شود.
      • panic-abort-tests — اجرای تست‌ها با راهبرد panic از نوع «abort» را ممکن می‌کند.
      • host-config — امکان تنظیم پیکربندی‌هایی شبیه [target] را برای اهداف ساخت میزبان فراهم می‌کند.
      • embed-metadata — اگر روی no تنظیم شود، cargo پرچم -Zembed-metadata=no را به کامپایلر می‌دهد که از جاسازی فراداده در آرتیفکت‌های rlib و dylib جلوگیری می‌کند تا فضای دیسک ذخیره شود.
      • target-applies-to-host — تعیین می‌کند آیا برخی پرچم‌ها به اهداف ساخت میزبان داده شوند یا نه.
      • gc — پاک‌سازی (garbage collection) cache سراسری.
      • open-namespaces — اجازه می‌دهد چند بسته در یک فضای نام API مشترک شرکت کنند
      • panic-immediate-abort — پرچم -Cpanic=immediate-abort را به کامپایلر می‌دهد.
      • compile-time-deps — قابلیت دائماً ناپایدار برای rust-analyzer
      • fine-grain-locking — به‌جای قفل‌کردن کل cache ساخت، از قفل‌گذاری ریزدانه استفاده می‌کند
      • json-target-spec — استفاده از مشخصات هدف سفارشی با فایل .json را مجاز می‌کند.
      • hint-msrv — به Cargo اجازه می‌دهد -Zhint-msrv را تنظیم کند
      • mem-stats — اوج مصرف حافظه را برای هر واحد ساخت در --timings گزارش می‌کند.
    • rustdoc
      • rustdoc-map — نگاشت‌هایی فراهم می‌کند تا مستندات به سایت‌های خارجی مثل docs.rs پیوند دهند.
      • scrape-examples — مثال‌ها را درون مستندات نشان می‌دهد.
      • output-format — اجازه می‌دهد مستندات در قالب JSON آزمایشی هم تولید شوند.
      • rustdoc-depinfo — از فایل‌های dep-info در تشخیص نیاز به بازسازی rustdoc استفاده می‌کند.
      • rustdoc-mergeable-info — از فایل‌های اطلاعات بین‌crate قابل‌ادغام rustdoc استفاده می‌کند.
    • Cargo.toml extensions
      • Profile rustflags option — مستقیماً به rustc داده می‌شود.
      • Profile hint-mostly-unused option — اشاره می‌کند که یک وابستگی عمدتاً استفاده نمی‌شود، تا زمان کامپایل بهینه شود.

      • per-package-target — --target مورد استفاده برای هر بستهٔ جداگانه را تنظیم می‌کند.
      • artifact dependencies — اجازه می‌دهد آرتیفکت‌های ساخت در آرتیفکت‌های ساخت دیگر گنجانده شوند و برای اهداف مختلف ساخته شوند.

      • unstable-editions — استفاده از ویرایش‌هایی را که هنوز پایدار نیستند مجاز می‌کند.

      • Build analysis — معیارهای دقیق ساخت را در اجراهای مختلف ثبت و ذخیره می‌کند و دستورهای جدیدی برای پرس‌وجو از ساخت‌های گذشته دارد.

    • Configuration

    allow-features

    این پرچم دائماً ناپایدار باعث می‌شود فقط مجموعهٔ فهرست‌شده‌ای از قابلیت‌های ناپایدار قابل‌استفاده باشد. به‌طور مشخص، اگر -Zallow-features=foo,bar را بدهید، همچنان می‌توانید -Zfoo و -Zbar را به cargo بدهید، اما نمی‌توانید -Zbaz بدهید. می‌توانید رشتهٔ خالی (-Zallow-features=) بدهید تا همهٔ قابلیت‌های ناپایدار غیرمجاز شوند.

    -Zallow-features همچنین محدود می‌کند که کدام قابلیت‌های ناپایدار می‌توانند به ورودی cargo-features در Cargo.toml داده شوند. برای مثال، اگر بخواهید این را مجاز کنید

    cargo-features = ["test-dummy-unstable"]

    که در آن test-dummy-unstable ناپایدار است، آن feature هم با -Zallow-features= غیرمجاز می‌شود و با -Zallow-features=test-dummy-unstable مجاز.

    فهرست featureهایی که به -Zallow-features در cargo داده می‌شود به هر ابزار Rust که cargo فراخوانی می‌کند (مثل rustc یا rustdoc) هم داده می‌شود. بنابراین اگر cargo -Zallow-features= را اجرا کنید، هیچ قابلیت ناپایدار Cargo یا Rust قابل‌استفاده نیست.

    no-index-update

    • Original Issue: #3479
    • Tracking Issue: #7404

    پرچم -Z no-index-update تضمین می‌کند Cargo سعی نمی‌کند فهرست registry را به‌روز کند. این برای ابزارهایی مثل Crater است که دستورهای Cargo زیادی صادر می‌کنند و می‌خواهید از تأخیر شبکه برای به‌روزرسانی فهرست در هر بار پرهیز کنید.

    mtime-on-use

    • Original Issue: #6477
    • issue پیگیری کلی استفاده از cache: #7150

    پرچم -Z mtime-on-use آزمایشی است برای اینکه Cargo زمان mtime فایل‌های استفاده‌شده را به‌روز کند تا ابزارهایی مثل cargo-sweep راحت‌تر بتوانند تشخیص دهند کدام فایل‌ها کهنه‌اند. در بسیاری از گردش‌کارها لازم است این روی همهٔ فراخوانی‌های cargo تنظیم شود. برای عملی‌تر‌شدن، تنظیم پرچم unstable.mtime_on_use در .cargo/config.toml یا متغیر محیطی متناظر، -Z mtime-on-use را روی همهٔ فراخوانی‌های cargo در nightly اعمال می‌کند. (در stable پرچم config نادیده گرفته می‌شود)

    avoid-dev-deps

    • Original Issue: #4988
    • Tracking Issue: #5133

    هنگام اجرای دستورهایی مثل cargo install یا cargo build، Cargo فعلاً لازم دارد dev-dependencies دانلود شوند، حتی اگر استفاده نشوند. پرچم -Z avoid-dev-deps به Cargo اجازه می‌دهد از دانلود dev-dependencies در صورت نیاز‌نداشتن به آن‌ها پرهیز کند. اگر dev-dependencies رد شوند، فایل Cargo.lock تولید نخواهد شد.

    minimal-versions

    • Original Issue: #4100
    • Tracking Issue: #5657

    Warning

    استفاده از این قابلیت توصیه نمی‌شود. چون نسخه‌های حداقلی را برای همهٔ وابستگی‌های تعدّی اعمال می‌کند، کاربردش محدود است چون همهٔ وابستگی‌های خارجی کران پایین نسخه را درست اعلام نمی‌کنند. قرار است در آینده تغییر کند تا فقط برای وابستگی‌های مستقیم نسخه‌های حداقلی را اعمال کند.

    وقتی فایل Cargo.lock تولید می‌شود، پرچم -Z minimal-versions وابستگی‌ها را به کمترین نسخهٔ SemVer حل می‌کند که نیازمندی‌ها را برآورده کند (به‌جای بیشترین نسخه).

    کاربرد مورد نظر این پرچم این است که در یکپارچه‌سازی پیوسته (CI) بررسی شود که نسخه‌های مشخص‌شده در Cargo.toml بازتاب درستی از حداقل نسخه‌هایی هستند که واقعاً استفاده می‌کنید. یعنی اگر Cargo.toml می‌گوید foo = "1.0.0"، به‌طور تصادفی به قابلیت‌هایی که فقط در foo 1.5.0 افزوده شده‌اند وابسته نشوید.

    کاربرد مورد نظر این پرچم این است که در یکپارچه‌سازی پیوسته (CI) بررسی شود که نسخه‌های مشخص‌شده در Cargo.toml بازتاب درستی از حداقل نسخه‌هایی هستند که واقعاً استفاده می‌کنید. یعنی اگر Cargo.toml می‌گوید foo = "1.0.0"، به‌طور تصادفی به قابلیت‌هایی که فقط در foo 1.5.0 افزوده شده‌اند وابسته نشوید.

    وابستگی‌های غیرمستقیم به‌طور عادی حل می‌شوند تا گیر اعتبارسنجی نسخهٔ حداقلی آن‌ها نکنند.

    artifact-dir

    • Original Issue: #4875
    • Tracking Issue: #6790

    این قابلیت به شما اجازه می‌دهد پوشه‌ای را مشخص کنید که آرتیفکت‌ها پس از ساخت در آن کپی شوند. معمولاً آرتیفکت‌ها فقط در پوشه‌های target/release یا target/debug نوشته می‌شوند. اما تعیین نام دقیق فایل می‌تواند دشوار باشد چون باید خروجی JSON را تجزیه کرد. پرچم --artifact-dir دسترسی قابل‌پیش‌بینی به آرتیفکت‌ها را آسان‌تر می‌کند. توجه کنید که آرتیفکت‌ها کپی می‌شوند، پس نسخه‌های اصلی هنوز در پوشهٔ target هستند. مثال:

    cargo +nightly build --artifact-dir=out -Z unstable-options

    این را می‌توان در فایل‌های .cargo/config.toml هم مشخص کرد.

    [build]
artifact-dir = "out"

    root-dir

    • Original Issue: #9887
    • issue پیگیری: ندارد (فعلاً برای پایدارسازی برنامه‌ریزی نشده)

    پرچم -Zroot-dir پوشهٔ ریشه‌ای را تعیین می‌کند که مسیرها نسبت به آن چاپ می‌شوند. این هم پیام‌های تشخیصی را تحت‌تأثیر قرار می‌دهد و هم مسیرهایی را که ماکروی file!() تولید می‌کند.

    Metabuild

    • issue پیگیری: rust-lang/rust#49803
    • RFC: #2196

    Metabuild قابلیتی برای داشتن اسکریپت‌های ساخت اعلانی است. به‌جای نوشتن اسکریپت build.rs، فهرستی از وابستگی‌های ساخت را در کلید metabuild در Cargo.toml مشخص می‌کنید. یک اسکریپت ساخت به‌طور خودکار تولید می‌شود که هر وابستگی ساخت را به‌ترتیب اجرا می‌کند. بسته‌های metabuild سپس می‌توانند فراداده را از Cargo.toml بخوانند تا رفتارشان را مشخص کنند.

    cargo-features را در بالای Cargo.toml بیاورید، کلید metabuild را در package بگذارید، وابستگی‌ها را در build-dependencies فهرست کنید و هر فراداده‌ای را که بسته‌های metabuild لازم دارند زیر package.metadata اضافه کنید. مثال:

    cargo-features = ["metabuild"]

[package]
name = "mypackage"
version = "0.0.1"
metabuild = ["foo", "bar"]

[build-dependencies]
foo = "1.0"
bar = "1.0"

[package.metadata.foo]
extra-info = "qwerty"

    build-std

    • مخزن پیگیری: https://github.com/rust-lang/wg-cargo-std-aware

    قابلیت build-std به Cargo اجازه می‌دهد خود کتابخانهٔ استاندارد را به‌عنوان بخشی از کامپایل گراف crateها کامپایل کند. این قابلیت پیش‌تر هم با نام «std-aware Cargo» شناخته می‌شد. این قابلیت هنوز در مراحل بسیار اولیهٔ توسعه است و می‌تواند افزودنی بسیار بزرگ به Cargo باشد. مستندسازی این قابلیت بسیار بزرگ است، حتی در شکل حداقلی‌ای که امروز دارد، پس اگر می‌خواهید به‌روز بمانید باید مخزن پیگیری و issueهای آن را دنبال کنید.

    قابلیت پیاده‌سازی‌شدهٔ امروز پشت پرچم -Z build-std است. این پرچم نشان می‌دهد Cargo باید کتابخانهٔ استاندارد را از کد منبع و با همان profile ساخت اصلی کامپایل کند. توجه کنید برای کارکردن این، باید کد منبع کتابخانهٔ استاندارد را در اختیار داشته باشید، و فعلاً تنها روش پشتیبانی‌شده برای این کار افزودن مؤلفهٔ rust-src در rustup است:

    $ rustup component add rust-src --toolchain nightly

    Usage looks like:

    $ cargo new foo
$ cd foo
$ cargo +nightly run -Z build-std --target x86_64-unknown-linux-gnu
   Compiling core v0.0.0 (...)
   ...
   Compiling foo v0.1.0 (...)
    Finished dev [unoptimized + debuginfo] target(s) in 21.00s
     Running `target/x86_64-unknown-linux-gnu/debug/foo`
Hello, world!

    در اینجا کتابخانهٔ استاندارد را در حالت debug و با debug assertions دوباره کامپایل کردیم (مثل کامپایل src/main.rs) و همه‌چیز در پایان به هم لینک شد.

    استفاده از -Z build-std به‌طور ضمنی crateهای پایدار core، std، alloc و proc_macro را کامپایل می‌کند. اگر از cargo test استفاده کنید، crate با نام test را هم کامپایل می‌کند. اگر با محیطی کار می‌کنید که از برخی این crateها پشتیبانی نمی‌کند، می‌توانید به -Zbuild-std هم آرگومان بدهید:

    $ cargo +nightly build -Z build-std=core,alloc

    مقدار اینجا فهرستی از crateهای کتابخانهٔ استاندارد است که باید ساخته شوند و با ویرگول جدا می‌شود.

    Requirements

    در خلاصه، فهرست نیازمندی‌های امروز برای استفاده از -Z build-std این‌هاست:

    • باید کد منبع libstd را با rustup component add rust-src نصب کنید
    • باید هم Cargo و هم rustc را از نوع nightly به‌کار ببرید
    • پرچم -Z build-std باید به همهٔ فراخوانی‌های cargo داده شود.

    گزارش باگ‌ها و کمک‌کردن

    قابلیت -Z build-std در مراحل بسیار اولیهٔ توسعه است! این قابلیت در Cargo تاریخچهٔ بسیار طولانی و دامنهٔ بسیار بزرگی دارد، و این فقط آغاز راه است. اگر می‌خواهید باگی گزارش کنید، لطفاً آن را به یکی از این‌ها گزارش دهید:

    • Cargo — https://github.com/rust-lang/cargo/issues/new — برای باگ‌های پیاده‌سازی
    • مخزن پیگیری — https://github.com/rust-lang/wg-cargo-std-aware/issues/new — برای پرسش‌های طراحی بزرگ‌تر.

    همچنین اگر قابلیتی را می‌خواهید که هنوز پیاده‌سازی نشده و/یا اگر چیزی آن‌طور که می‌خواهید کار نمی‌کند، issue tracker مخزن پیگیری را ببینید، و اگر آنجا نبود issue جدیدی ثبت کنید!

    # .cargo/config.toml
[unstable]

[build]
fingerprint = "content"

    build.fingerprint

    • Type: string
    • Default: "mtime"
    • Environment: CARGO_BUILD_FINGERPRINT

    • mtime: زمان آخرین تغییر ورودی
    • content: checksum ورودی

    این بر دستور cargo::rerun-if-changed در اسکریپت ساخت اثر نمی‌گذارد.

    target-applies-to-host

    • Original Pull Request: #9322
    • Tracking Issue: #9453

    از نظر تاریخی، رفتار Cargo دربارهٔ اینکه آیا گزینه‌های پیکربندی linker و rustflags از متغیرهای محیطی و [target] برای اسکریپت‌های ساخت، پلاگین‌ها، و آرتیفکت‌های دیگری که همیشه برای پلتفرم میزبان ساخته می‌شوند رعایت شوند تا حدی ناسازگار بوده است. وقتی --target داده نشود، Cargo همان linker و rustflags را برای اسکریپت‌های ساخت مثل همهٔ آرتیفکت‌های کامپایل دیگر رعایت می‌کند. اما وقتی --target داده شود، Cargo linker را از [target.<host tuple>] رعایت می‌کند و هیچ پیکربندی rustflags را برنمی‌دارد. این رفتار دوگانه گیج‌کننده است، و همچنین پیکربندی درست ساخت‌هایی را دشوار می‌کند که در آن‌ها host tuple و target tuple یکی‌اند، اما آرتیفکت‌هایی که قرار است روی میزبان ساخت اجرا شوند هنوز باید متفاوت پیکربندی شوند.

    -Ztarget-applies-to-host تنظیم سطح بالای target-applies-to-host را در فایل‌های پیکربندی Cargo فعال می‌کند که به کاربران اجازه می‌دهد رفتار متفاوت (و منسجم‌تری) را برای این ویژگی‌ها انتخاب کنند. وقتی target-applies-to-host در فایل پیکربندی تنظیم نشده یا روی true باشد، رفتار موجود Cargo حفظ می‌شود (هرچند -Zhost-config را ببینید که این پیش‌فرض را تغییر می‌دهد). وقتی روی false باشد، هیچ گزینه‌ای از [target.<host tuple>]، RUSTFLAGS یا [build] برای آرتیفکت‌های میزبان رعایت نمی‌شود، صرف‌نظر از اینکه --target به Cargo داده شده باشد یا نه. برای سفارشی‌سازی آرتیفکت‌هایی که قرار است روی میزبان اجرا شوند، از [host] استفاده کنید (host-config).

    در آینده ممکن است target-applies-to-host پیش‌فرضش false شود تا رفتار پیش‌فرض معقول‌تر و منسجم‌تری ارائه دهد.

    # config.toml
target-applies-to-host = false

    cargo +nightly -Ztarget-applies-to-host build --target x86_64-unknown-linux-gnu

    Profile hint-mostly-unused option

    • Tracking Issue: #15644

    این قابلیت گزینهٔ جدیدی در بخش [profile] فراهم می‌کند تا گزینهٔ hint-mostly-unused در rustc فعال شود. این بیش از همه برای وابستگی‌های مشخص مفید است:

    [profile.dev.package.huge-mostly-unused-dependency]
hint-mostly-unused = true

    برای فعال‌کردن این قابلیت، -Zprofile-hint-mostly-unused را بدهید. اما از آنجا که این گزینه یک راهنمایی (hint) است، استفاده از آن بدون دادن -Zprofile-hint-mostly-unused فقط هشدار می‌دهد و گزینهٔ profile را نادیده می‌گیرد. نسخه‌های Cargo پیش از معرفی این قابلیت هشدار «unused manifest key» می‌دهند، اما در غیر این صورت بدون خطا کار می‌کنند. این امکان می‌دهد hint در Cargo.toml یک crate استفاده شود، بدون اینکه ساخت آن به Cargo جدیدتر منوط شود.

    یک crate همچنین می‌تواند این hint را به‌طور خودکار برای crateهایی که به آن وابسته‌اند ارائه دهد، با استفاده از جدول [hints] (که به همین شکل توسط Cargo قدیمی‌تر نادیده گرفته می‌شود):

    [hints]
mostly-unused = true

    این باعث می‌شود crate به‌طور پیش‌فرض hint-mostly-unused داشته باشد، مگر اینکه با profile بازنویسی شود که اولویت دارد و فقط در crate سطح بالایی که ساخته می‌شود می‌تواند مشخص شود.

    Documentation updates

    min-opt-level

    به‌عنوان زیربخش جدیدی از «بخش [hints]»، که برای هر hint یک زیربخش خواهد داشت

    hint با نام min-opt-level پایین‌ترین opt-level را که Cargo برای ساخت این بسته به‌کار می‌برد تعیین می‌کند. برخی بسته‌ها بدون بهینه‌سازی بسیار کند هستند، یا ساختشان بدون آن بیشتر طول می‌کشد. چنین بسته‌ای می‌تواند حداقل سطح بهینه‌سازی را درخواست کند:

    # In example-dependency's Cargo.toml
[hints]
min-opt-level = 2

    مقادیر معتبر 0، 1، 2 و 3 هستند. Cargo دربارهٔ هر مقدار دیگر هشدار می‌دهد و آن را نادیده می‌گیرد. سطح‌های "s" و "z" معتبر نیستند، چون با سطح‌های عددی قابل‌مقایسه نیستند و انتخاب آن‌ها با بستهٔ سطح بالاست.

    وقتی profile انتخاب‌شده opt-level پایین‌تر از hint داشته باشد، Cargo بسته را به‌جای آن در سطح hint می‌سازد. وقتی profile opt-level بالاتری داشته باشد، Cargo سطح بالاتر را نگه می‌دارد. این چه opt-level profile پیش‌فرض باشد و چه کاربر تنظیم کرده باشد صدق می‌کند. همچنین برای پیش‌فرض opt-level = 0 در وابستگی‌های ساخت هم صدق می‌کند.

    بستهٔ سطح بالا می‌تواند hint را با بازنویسی (override) profile باطل کند. هر opt-level که در جدول package، در بستهٔ "*" یا در جدول build-override تنظیم شده باشد بر hint اولویت دارد. تنظیم opt-level = "s" یا "z" در profile هم اولویت دارد، چون بسته‌ای که برای اندازه بهینه می‌شود معمولاً می‌خواهد وابستگی‌هایش هم همین کار را بکنند.

    # Does not lower the `opt-level` below a dependency's hint.
[profile.dev]
opt-level = 0

# Overrides the hint for the `example-dependency` package.
[profile.dev.package.example-dependency]
opt-level = 0

# Overrides the hint for all dependencies.
[profile.dev.package."*"]
opt-level = 1

    hint فقط بر بسته‌ای که آن را تنظیم می‌کند اعمال می‌شود، نه وابستگی‌هایش. اگر کد کند در یک وابستگی باشد، آن وابستگی باید hint خودش را تنظیم کند.

    این hint را فقط وقتی به‌کار ببرید که بهینه‌کردن بسته ساخت کامل را سریع‌تر کند، یا وقتی بسته بدون بهینه‌سازی چندین برابر کندتر است.

    rustdoc-map

    • Tracking Issue: #8296

    این قابلیت تنظیمات پیکربندی‌ای اضافه می‌کند که به rustdoc داده می‌شوند تا بتواند برای وابستگی‌هایی که مستنداتشان جای دیگری میزبانی می‌شود و در آن مستند نشده‌اند پیوند تولید کند. ابتدا این را به .cargo/config بیفزایید:

    [doc.extern-map.registries]
crates-io = "https://docs.rs/"

    سپس هنگام ساخت مستندات، از پرچم‌های زیر استفاده کنید تا پیوندهای وابستگی‌ها به docs.rs اشاره کنند:

    cargo +nightly doc --no-deps -Zrustdoc-map

    جدول registries نگاشتی از نام registry به URL مقصد پیوند دارد. URL می‌تواند نشانگرهای {pkg_name} و {version} داشته باشد که با مقادیر متناظر جایگزین می‌شوند. اگر هیچ‌کدام مشخص نشود، Cargo پیش‌فرضاً {pkg_name}/{version}/ را به انتهای URL اضافه می‌کند.

    تنظیم پیکربندی دیگری برای تغییر مسیر پیوندهای کتابخانهٔ استاندارد هست. به‌طور پیش‌فرض، rustdoc پیوندهایی به https://doc.rust-lang.org/nightly/ می‌سازد. برای تغییر این رفتار، از تنظیم doc.extern-map.std استفاده کنید:

    [doc.extern-map]
std = "local"

    مقدار "local" یعنی پیوند به مستنداتی که در sysroot مربوط به rustc هست. اگر از rustup استفاده می‌کنید، این مستندات را می‌توان با rustup component add rust-docs نصب کرد.

    مقدار پیش‌فرض "remote" است.

    مقدار می‌تواند URL محل سفارشی هم باشد.

    artifact-dependencies

    • Tracking Issue: #9096
    • Original Pull Request: #9992

    وابستگی‌های آرتیفکتی (Artifact dependencies) به بسته‌های Cargo اجازه می‌دهند به crateهای bin، cdylib و staticlib وابسته شوند و از آرتیفکت‌هایی که آن crateها می‌سازند در زمان کامپایل استفاده کنند.

    برای فعال‌کردن این قابلیت cargo را با -Z bindeps اجرا کنید.

    artifact-dependencies: Dependency declarations

    Artifact-dependencies کلیدهای زیر را به تعریف وابستگی در Cargo.toml می‌افزاید:

    • artifact — این هدف Cargo را که باید ساخته شود مشخص می‌کند. معمولاً بدون این فیلد، Cargo فقط هدف [lib] را از یک وابستگی می‌سازد. این فیلد اجازه می‌دهد مشخص شود کدام هدف ساخته و در زمان ساخت به‌صورت فایل دودویی در دسترس قرار گیرد:

      • "bin" — فایل‌های دودویی اجرایی کامپایل‌شده، متناظر با همهٔ بخش‌های [[bin]] در manifest وابستگی.
      • "bin:<bin-name>" — فایل دودویی اجرایی کامپایل‌شده، متناظر با یک هدف دودویی مشخص که با <bin-name> داده شده.
      • "cdylib" — کتابخانهٔ پویای سازگار با C، متناظر با بخش [lib] با crate-type = ["cdylib"] در manifest وابستگی.
      • "staticlib" — کتابخانهٔ ایستای سازگار با C، متناظر با بخش [lib] با crate-type = ["staticlib"] در manifest وابستگی.

      مقدار artifact می‌تواند رشته باشد، یا آرایه‌ای از رشته‌ها برای مشخص‌کردن چند هدف.

      Example:

      [dependencies]
bar = { version = "1.0", artifact = "staticlib" }
zoo = { version = "1.0", artifact = ["bin:cat", "bin:dog"]}

    • lib — مقدار بولی که مشخص می‌کند کتابخانهٔ وابستگی هم به‌عنوان وابستگی عادی lib در Rust ساخته شود یا نه. این فیلد فقط وقتی می‌تواند مشخص شود که artifact مشخص شده باشد.

      پیش‌فرض این فیلد وقتی artifact مشخص شده false است. اگر true باشد، هدف [lib] وابستگی هم برای پلتفرم هدفی که بستهٔ اعلام‌کننده برای آن ساخته می‌شود ساخته می‌شود. این به بسته اجازه می‌دهد علاوه بر وابستگی آرتیفکتی، از وابستگی در کد Rust مثل یک وابستگی عادی هم استفاده کند.

      Example:

      [dependencies]
bar = { version = "1.0", artifact = "bin", lib = true }

    • target — پلتفرم هدفی که وابستگی برای آن ساخته می‌شود. این فیلد فقط وقتی می‌تواند مشخص شود که artifact مشخص شده باشد.

      پیش‌فرض در صورت مشخص‌نشدن به نوع وابستگی بستگی دارد. وابستگی‌های ساخت برای هدف میزبان ساخته می‌شوند. بقیهٔ وابستگی‌ها برای همان اهدافی ساخته می‌شوند که بستهٔ اعلام‌کننده برای آن‌ها ساخته می‌شود.

      برای وابستگی ساخت، می‌توان مقدار ویژهٔ "target" را هم داد که یعنی وابستگی برای همان اهدافی ساخته شود که بسته برای آن‌ها ساخته می‌شود.

      [build-dependencies]
bar = { version = "1.0", artifact = "cdylib", target = "wasm32-unknown-unknown"}
same-target = { version = "1.0", artifact = "bin", target = "target" }

    artifact-dependencies: Environment variables

    پس از ساخت یک وابستگی آرتیفکتی، Cargo متغیرهای محیطی زیر را در اختیار می‌گذارد که می‌توانید برای دسترسی به آرتیفکت استفاده کنید:

    • CARGO_<ARTIFACT-TYPE>_DIR_<DEP> — پوشه‌ای که همهٔ آرتیفکت‌های وابستگی را در بر دارد.

      <ARTIFACT-TYPE> همان artifact مشخص‌شده برای وابستگی است (با حروف بزرگ مثل CDYLIB، STATICLIB یا BIN) و <DEP> نام وابستگی است. مثل متغیرهای محیطی دیگر Cargo، نام وابستگی‌ها به حروف بزرگ تبدیل می‌شوند و خط‌تیره‌ها با زیرخط جایگزین.

      اگر manifest شما نام وابستگی را تغییر دهد، <DEP> با نامی که شما مشخص می‌کنید متناظر است، نه نام اصلی بسته.

    • CARGO_<ARTIFACT-TYPE>_FILE_<DEP>_<NAME> — مسیر کامل آرتیفکت.

      <ARTIFACT-TYPE> همان artifact مشخص‌شده برای وابستگی است (با حروف بزرگ مثل بالا)، <DEP> نام وابستگی است (با همان تبدیل بالا)، و <NAME> نام آرتیفکت در وابستگی است.

      توجه کنید که <NAME> به هیچ شکلی نسبت به name مشخص‌شده در crate عرضه‌کنندهٔ آرتیفکت، یا نام crate در صورت مشخص‌نشدن، تغییر نمی‌کند؛ برای مثال ممکن است با حروف کوچک باشد یا خط‌تیره داشته باشد.

      برای راحتی، اگر نام آرتیفکت با نام بستهٔ اصلی یکی باشد، cargo علاوه بر آن نسخه‌ای از این متغیر را بدون پسوند _<NAME> هم فراهم می‌کند. برای مثال اگر crate با نام cmake فایل دودویی‌ای به نام cmake عرضه کند، Cargo هر دو CARGO_BIN_FILE_CMAKE و CARGO_BIN_FILE_CMAKE_cmake را فراهم می‌کند.

    برای هر نوع وابستگی، این متغیرها به همان بخش فرایند ساخت داده می‌شوند که به آن نوع وابستگی دسترسی دارد:

    • برای build-dependencies، این متغیرها به اسکریپت build.rs داده می‌شوند و با std::env::var_os قابل‌دسترسی‌اند. (مثل هر مسیر فایل در سیستم‌عامل، ممکن است UTF-8 معتبر باشند یا نباشند.)
    • برای وابستگی‌های عادی، این متغیرها هنگام کامپایل crate داده می‌شوند و با ماکروی env! قابل‌دسترسی‌اند.
    • برای dev-dependencies، این متغیرها هنگام کامپایل مثال‌ها، تست‌ها و benchmarkها داده می‌شوند و با ماکروی env! قابل‌دسترسی‌اند.

    artifact-dependencies: Examples

    مثال: استفاده از فایل اجرایی دودویی در اسکریپت ساخت

    در فایل Cargo.toml می‌توانید وابستگی به یک فایل دودویی را مشخص کنید تا برای اسکریپت ساخت در دسترس باشد:

    سپس درون اسکریپت ساخت می‌توان فایل دودویی را در زمان ساخت اجرا کرد:

    fn main() {

    let status = std::process::Command::new(build_tool)
        .arg("do-stuff")
        .status()
        .unwrap();
    if !status.success() {
        eprintln!("failed!");
        std::process::exit(1);
    }
}

    فایل Cargo.toml در بستهٔ مصرف‌کننده، که فایل دودویی bar را برای گنجاندن به‌عنوان آرتیفکت می‌سازد و در عین حال آن را به‌عنوان کتابخانه هم در دسترس قرار می‌دهد…

    scrape-examples

    • RFC: #3123
    • Tracking Issue: #9910

    پرچم -Z rustdoc-scrape-examples به Rustdoc می‌گوید crateهای workspace فعلی را برای فراخوانی تابع‌ها جست‌وجو کند. آن نقاط فراخوانی سپس به‌عنوان مستندات گنجانده می‌شوند. می‌توانید پرچم را این‌طور به‌کار ببرید:

    cargo doc -Z unstable-options -Z rustdoc-scrape-examples

    به‌طور پیش‌فرض، Cargo مثال‌ها را از اهداف مثال بسته‌هایی که مستند می‌شوند استخراج می‌کند. می‌توانید با پرچم doc-scrape-examples استخراج از هر هدف را جداگانه فعال یا غیرفعال کنید، مثلاً:

    # Enable scraping examples from a library
[lib]
doc-scrape-examples = true

# Disable scraping examples from an example target
[[example]]
name = "my-example"
doc-scrape-examples = false

    نکته دربارهٔ تست‌ها: فعال‌کردن doc-scrape-examples روی اهداف تست فعلاً اثری ندارد. استخراج مثال از تست‌ها در دست انجام است.

    نکته دربارهٔ dev-dependencies: مستندسازی یک کتابخانه معمولاً به dev-dependencies آن crate نیاز ندارد. اما اهداف مثال به dev-deps نیاز دارند. برای سازگاری رو‌به‌عقب، -Z rustdoc-scrape-examples برای cargo doc نیاز جدیدی به dev-deps ایجاد نمی‌کند. بنابراین در شرایط زیر مثال‌ها از اهداف مثال استخراج نمی‌شوند:

    1. هیچ هدفی که مستند می‌شود به dev-deps نیاز ندارد، و
    2. دست‌کم یک crate که اهدافش مستند می‌شوند dev-deps دارد، و
    3. پارامتر doc-scrape-examples برای همهٔ اهداف [[example]] تنظیم نشده یا false است.

    اگر می‌خواهید مثال‌ها از اهداف مثال استخراج شوند، نباید یکی از شرایط بالا برقرار باشد. برای مثال، می‌توانید doc-scrape-examples را برای یک هدف مثال روی true بگذارید، و این به Cargo می‌فهماند که با ساخته‌شدن dev-deps برای cargo doc مشکلی ندارید.

    git

    • Tracking Issue: #13285

    با قابلیت ناپایدار «git»، هم gitoxide و هم git2 دریافت‌های سطحی (shallow) از فهرست crateها و وابستگی‌های git انجام می‌دهند.

    در حالی که -Zgit همهٔ قابلیت‌های فعلاً پیاده‌سازی‌شده را فعال می‌کند، می‌توان با نحو -Zgit=operation[,operationN] انتخاب کرد چه زمانی دریافت سطحی انجام شود.

    عملیات معتبر عبارت‌اند از:

    • shallow-index - انجام clone سطحی فهرست.
    • shallow-deps - انجام clone سطحی وابستگی‌های git.

    جزئیات دربارهٔ clone سطحی

    • برای فعال‌کردن clone سطحی، -Zgit=shallow-deps را برای دریافت وابستگی‌های git یا -Zgit=shallow-index را برای دریافت فهرست registry اضافه کنید.
    • Shallow-cloned and shallow-checked-out git repositories reside at their own -shallow suffixed directories, i.e,
      • ~/.cargo/registry/index/*-shallow
      • ~/.cargo/git/db/*-shallow
      • ~/.cargo/git/checkouts/*-shallow
    • وقتی قابلیت ناپایدار روشن باشد، دریافت/clone یک مخزن git همیشه سطحی است. این تقریباً معادل git fetch --depth 1 در همه‌جاست.
    • حتی با وجود Cargo.lock یا مشخص‌کردن commit به‌صورت { rev = "…" }، gitoxide و libgit2 همچنان به‌اندازهٔ کافی هوشمندند که بدون unshallow‌کردن مخزن موجود، دریافت سطحی کنند.

    Single-file packages

    علاوه بر بسته‌های چندفایلی امروزی (فایل Cargo.toml با فایل‌های .rs دیگر)، مفهوم بسته‌های تک‌فایلی را اضافه می‌کنیم که ممکن است manifest تعبیه‌شده داشته باشند. هیچ تمایز الزامی‌ای بین بستهٔ تک‌فایلی .rs و هر فایل .rs دیگر وجود ندارد.

    بسته‌های تک‌فایلی را می‌توان با --manifest-path انتخاب کرد، مثل cargo test --manifest-path foo.rs. برخلاف Cargo.toml، این فایل‌ها خودکار کشف نمی‌شوند.

    بستهٔ تک‌فایلی می‌تواند manifest تعبیه‌شده داشته باشد. manifest تعبیه‌شده با TOML در «frontmatter» زبان Rust ذخیره می‌شود، یعنی یک code fence مارک‌داون که cargo در ابتدای infostring آن در بالای فایل است.

    فیلدهای manifest که استنتاج می‌شوند / پیش‌فرض دارند:

    • package.name = <slugified file stem>
    • package.edition = <current> to avoid always having to add an embedded manifest at the cost of potentially breaking scripts on rust upgrades
      • وقتی edition مشخص نشده باشد هشدار بده تا از این موضوع آگاهی ایجاد شود

    Disallowed manifest fields:

    • [workspace], [lib], [[bin]], [[example]], [[test]], [[bench]]
    • package.workspace, package.build, package.links, package.autolib, package.autobins, package.autoexamples, package.autotests, package.autobenches

    CARGO_TARGET_DIR پیش‌فرض برای بسته‌های تک‌فایلی در $CARGO_HOME/target/<hash> است:

    • از تداخل چند بستهٔ تک‌فایلی در یک پوشه جلوگیری می‌کند
    • از مشکلات فقط‌خواندنی‌بودن پوشهٔ والد بستهٔ تک‌فایلی جلوگیری می‌کند
    • از شلوغ‌شدن پوشهٔ کاربر جلوگیری می‌کند

    lockfile بسته‌های تک‌فایلی در CARGO_TARGET_DIR قرار می‌گیرد. در آینده، وقتی workspaceها پشتیبانی شوند، این به کاربر اجازه می‌دهد lockfile پایدار داشته باشد.

    Manifest-commands

    می‌توانید یک manifest را مستقیماً به دستور cargo بدهید، بدون زیردستور، مثل foo/Cargo.toml یا یک بستهٔ تک‌فایلی مثل foo.rs. این بیشتر برای قرار‌گرفتن در خط‌های #! است.

    اولویت تفسیر cargo <subcommand> این است

    1. داخلی یا بستهٔ تک‌فایلی (xor)
    2. Aliases
    3. External subcommands

    یک پارامتر وقتی manifest-command شناخته می‌شود که یکی از این‌ها را داشته باشد:

    • Path separators
    • پسوند .rs
    • نام فایل Cargo.toml باشد

    تفاوت‌های cargo run --manifest-path <path> و cargo <path>

    • cargo <path> با پیکربندی <path> اجرا می‌شود نه پوشهٔ فعلی، بیشتر شبیه cargo install --path <path>
    • cargo <path> یک سطح پایین‌تر از سطح پرگویی پیش‌فرض عادی است. برای خروجی عادی -v بدهید.

    هنگام اجرای بسته‌ای با manifest تعبیه‌شده، arg0 مسیر اسکریپت خواهد بود. برای گرفتن مسیر فایل اجرایی، current_exe را ببینید.

    gc

    • Tracking Issue: #12633

    پرچم -Zgc برای فعال‌کردن برخی قابلیت‌های مربوط به garbage-collection در cache سراسری cargo درون پوشهٔ خانگی cargo به‌کار می‌رود.

    Automatic gc configuration

    پرچم -Zgc به Cargo اجازه می‌دهد گزینه‌های پیکربندی اضافی مربوط به garbage collection را بخواند. تنظیمات موجود عبارت‌اند از:

    # Example config.toml file.

# Sub-table for defining specific settings for cleaning the global cache.
[cache.global-clean]
# Anything older than this duration will be deleted in the source cache.
max-src-age = "1 month"
# Anything older than this duration will be deleted in the compressed crate cache.
max-crate-age = "3 months"
# Any index older than this duration will be deleted from the index cache.
max-index-age = "3 months"
# Any git checkout older than this duration will be deleted from the checkout cache.
max-git-co-age = "1 month"
# Any git clone older than this duration will be deleted from the git cache.
max-git-db-age = "3 months"

    توجه کنید که گزینهٔ cache.auto-clean-frequency در Rust 1.88 پایدار شد.

    garbage collection دستی با cargo clean

    حذف دستی را می‌توان با دستور cargo clean gc -Zgc انجام داد. حذف محتویات cache با دادن یکی از گزینه‌های cache انجام می‌شود:

    • --max-src-age=DURATION — فایل‌های cache منبع را که از سن داده‌شده به بعد استفاده نشده‌اند حذف می‌کند.
    • --max-crate-age=DURATION — فایل‌های cache مربوط به crate را که از سن داده‌شده به بعد استفاده نشده‌اند حذف می‌کند.
    • --max-index-age=DURATION — فهرست‌های registry را که از سن داده‌شده به بعد استفاده نشده‌اند حذف می‌کند (از جمله فایل‌های .crate و src آن‌ها).
    • --max-git-co-age=DURATION — checkoutهای وابستگی‌های git را که از سن داده‌شده به بعد استفاده نشده‌اند حذف می‌کند.
    • --max-git-db-age=DURATION — cloneهای وابستگی‌های git را که از سن داده‌شده به بعد استفاده نشده‌اند حذف می‌کند.
    • --max-download-age=DURATION — هر داده cache دانلودشده را که از سن داده‌شده به بعد استفاده نشده حذف می‌کند.
    • --max-src-size=SIZE — قدیمی‌ترین فایل‌های cache منبع را تا وقتی cache زیر اندازهٔ داده‌شده برسد حذف می‌کند.
    • --max-crate-size=SIZE — قدیمی‌ترین فایل‌های cache مربوط به crate را تا وقتی cache زیر اندازهٔ داده‌شده برسد حذف می‌کند.
    • --max-git-size=SIZE — قدیمی‌ترین cacheهای وابستگی git را تا وقتی cache زیر اندازهٔ داده‌شده برسد حذف می‌کند.
    • --max-download-size=SIZE — قدیمی‌ترین داده‌های cache دانلودشده را تا وقتی cache زیر اندازهٔ داده‌شده برسد حذف می‌کند.

    DURATION به شکل «N seconds/minutes/days/weeks/months» مشخص می‌شود که N عدد صحیح است.

    SIZE به شکل «N suffix» مشخص می‌شود که suffix یکی از B، kB، MB، GB، kiB، MiB یا GiB است و N عدد صحیح یا اعشاری است. اگر پسوندی مشخص نشود، عدد تعداد بایت است.

    cargo clean gc -Zgc
cargo clean gc -Zgc --max-download-age=1week
cargo clean gc -Zgc --max-git-size=0 --max-download-size=100MB

    Path Bases

    • Tracking Issue: #14355

    یک وابستگی path می‌تواند به‌صورت اختیاری با تنظیم کلید base روی نام یک path base از جدول [path-bases] در پیکربندی یا یکی از path baseهای داخلی، یک مبنا مشخص کند. مقدار آن path base (در صورت لزوم همراه با جداکنندهٔ مسیر) به ابتدای مقدار path افزوده می‌شود تا مکان واقعی‌ای که Cargo وابستگی را در آن جست‌وجو می‌کند به دست آید.

    برای مثال، اگر Cargo.toml این را در بر داشته باشد:

    cargo-features = ["path-bases"]

[dependencies]
foo = { base = "dev", path = "foo" }

    با فرض اینکه جدول [path-bases] در پیکربندی این را داشته باشد:

    [path-bases]
dev = "/home/user/dev/rust/libraries/"

    این یک وابستگی path به نام foo تولید می‌کند که در /home/user/dev/rust/libraries/foo قرار دارد.

    path baseها می‌توانند مطلق یا نسبی باشند. path baseهای نسبی نسبت به پوشهٔ والد فایل پیکربندی‌ای هستند که آن path base را اعلام کرده است.

    نام یک path base باید فقط از نویسه‌های alphanumeric یا - یا _ استفاده کند، باید با یک نویسهٔ alphabetic شروع شود، و نباید خالی باشد.

    اگر نام path baseای که در وابستگی استفاده شده نه در پیکربندی باشد و نه یکی از path baseهای داخلی، Cargo خطا می‌دهد.

    Built-in path bases

    Cargo path baseهای ضمنی‌ای فراهم می‌کند که بدون نیاز به مشخص‌کردن آن‌ها در جدول [path-bases] قابل‌استفاده‌اند.

    • workspace - اگر پروژه workspace یا عضو workspace باشد، این path base پوشهٔ والد Cargo.toml ریشهٔ workspace تعریف می‌شود.

    اگر نام یک path base داخلی در پیکربندی هم اعلام شود، Cargo مقدار پیکربندی را ترجیح می‌دهد. این به Cargo اجازه می‌دهد path baseهای داخلی جدیدی بدون مشکل سازگاری اضافه کند (چون استفاده‌های موجود نام داخلی را پوشش می‌دهند).

    cargo-features = ["unstable-editions"]

    ویرایش ویژهٔ «future» جایی برای قابلیت‌های جدیدی است که در حال توسعه‌اند و دائماً ناپایدار است. ویرایش «future» به‌خودی‌خود رفتار جدیدی هم ندارد. هر تغییر در ویرایش future به opt-in نیاز دارد، مثل attribute با نام #![feature(...)].

    fix-edition

    -Zfix-edition یک پرچم دائماً ناپایدار برای کمک به تست مهاجرت ویرایش‌هاست، به‌ویژه با استفاده از crater. فقط با زیردستور cargo fix کار می‌کند. دو شکل مختلف دارد:

    • -Zfix-edition=start=$INITIAL — این شکل بررسی می‌کند آیا ویرایش فعلی با عدد داده‌شده برابر است. اگر نه، با موفقیت خارج می‌شود (چون می‌خواهیم ویرایش‌های قدیمی‌تر را نادیده بگیریم). اگر بله، معادل cargo check را اجرا می‌کند. این برای استفاده با toolchain «start» در crater است تا خط مبنایی برای toolchain «قبل» تعیین شود.
    • -Zfix-edition=end=$INITIAL,$NEXT — این شکل بررسی می‌کند آیا ویرایش فعلی با مقدار داده‌شدهٔ $INITIAL برابر است. اگر نه، با موفقیت خارج می‌شود. اگر بله، مهاجرت ویرایش را به ویرایش مشخص‌شده در $NEXT انجام می‌دهد. سپس Cargo.toml را تغییر می‌دهد تا cargo-features = ["unstable-edition"] مناسب را اضافه کند، فیلد edition را به‌روز می‌کند و معادل cargo check را اجرا می‌کند تا تأیید کند مهاجرت روی ویرایش جدید کار می‌کند.

    برای مثال:

    cargo +nightly fix -Zfix-edition=end=2024,future

    Build analysis

    • issue اولیه: rust-lang/rust-project-goals#332
    • Tracking Issue: #15844

    قابلیت -Zbuild-analysis معیارهای دقیق ساخت را روی دیسک ثبت و ذخیره می‌کند، و دستورهای جدیدی برای پرس‌وجو از ساخت‌های گذشته دارد.

    وقتی فعال باشد، Cargo لاگ‌های ساخت را با قالب JSONL در پوشهٔ $CARGO_HOME/log/ می‌نویسد. هر فراخوانی cargo یک فایل لاگ با نامی شامل شناسهٔ جلسهٔ یکتا تولید می‌کند. این لاگ‌ها اطلاعات زمان‌بندی، دلایل بازسازی و فراداده‌های دیگر ساخت را دارند که با زیردستورهای cargo report قابل‌تحلیل‌اند.

    برای فعال‌کردن تحلیل ساخت، پیکربندی Cargo زیر را اضافه کنید:

    # Example config.toml file.

[unstable]
build-analysis = true

# Enable the build metric collection
[build.analysis]
enabled = true

    تنظیم آن روی toolchain پایدار فقط هشدار پیکربندی ناشناخته می‌دهد، پس نگه‌داشتن آن در پیکربندی Cargo ایمن است.

    cargo report commands

    دستورهای زیر تحت -Zbuild-analysis در دسترس‌اند:

    • cargo report sessions — جلسه‌های ساخت قبلی را فهرست می‌کند. از آن برای پیدا‌کردن شناسهٔ جلسه برای دستورهای گزارش دیگر استفاده کنید.
    • cargo report timings — گزارش زمان‌بندی HTML را از یک جلسهٔ قبلی تولید می‌کند، شبیه cargo build --timings اما بدون ساخت دوباره.
    • cargo report rebuilds — گزارش می‌دهد چرا crateها دوباره ساخته شدند، و به تشخیص بازکامپایل‌های غیرمنتظره کمک می‌کند.

    feature-metadata

    • Tracking Issue: #14157
    • RFC: #3416

    این امکان می‌دهد featureها با یک جدول فراداده تعریف شوند.

    cargo-features = ["feature-metadata"]

[package]
# ...

[features]
# same as `foo = []`
foo = { enables = [] }

    فیلد الزامی enables معادل نحو آرایه‌ای از رشته‌هاست.

    با فعال‌بودن feature-metadata، cargo metadata --format-version 1 فیلد features_v2 را کنار فیلد موجود features شامل می‌شود. این فیلد هر feature را به‌صورت شیئی با آرایهٔ enables و فیلدهای فراداده‌ای دیگر بازتاب می‌دهد:

    "features_v2": {
  "foo": { "enables": [] },
  "serde": {
    "enables": ["dep:serde"],
    "doc": "Enables support for serialization via serde."
  }
}

    برای فیلدهای فراداده‌ای دیگر، زیربخش‌های زیر را ببینید.

    feature-documentation

    • Tracking Issue: #17445
    • RFC: #3485

    این یک فیلد doc به جدول feature می‌افزاید، که مستندات feature را فراهم می‌کند.

    cargo-features = ["feature-metadata"]

[package]
# ...

[features.serde]
enables = []
doc = "Enables support for serialization and deserialization via serde."

    مستندات را ابزارها می‌توانند مصرف و نمایش دهند. می‌تواند رشتهٔ چندخطی TOML باشد، چند بند داشته باشد و از نشانه‌گذاری Markdown استفاده کند، مشابه توضیحات مستندات (doc comments) در Rust. ابزارها ممکن است در برخی زمینه‌ها فقط بند اول را نمایش دهند، پس باید نسبتاً کوتاه باشد و بدون بقیهٔ توضیح هم معنا داشته باشد.
