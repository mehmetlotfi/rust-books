    نمونه‌های build script

    بخش‌های زیر چند نمونه از نوشتن build scriptها را نشان می‌دهند.

    برخی قابلیت‌های رایج build script را می‌توان از طریق crateهای موجود در crates.io به دست آورد. کلیدواژهٔ build-dependencies را ببینید تا بدانید چه چیزهایی در دسترس است. فهرست زیر نمونه‌ای از چند crate محبوب است1:

    • bindgen — به‌طور خودکار bindingهای FFI زبان Rust را برای کتابخانه‌های C تولید می‌کند.
    • cc — کد C/C++/اسمبلی را کامپایل می‌کند.
    • pkg-config — کتابخانه‌های سیستم را با استفاده از ابزار pkg-config شناسایی می‌کند.
    • cmake — ابزار ساخت cmake را برای ساخت یک کتابخانهٔ بومی (native) اجرا می‌کند.
    • autocfg، rustc_version، version_check — این crateها راه‌هایی برای پیاده‌سازی کامپایل شرطی بر اساس rustc فعلی، مانند نسخهٔ کامپایلر، فراهم می‌کنند.

    تولید کد

    برخی بسته‌های Cargo به دلایل گوناگون لازم است درست پیش از کامپایل، کدشان تولید شود. در اینجا یک مثال ساده را بررسی می‌کنیم که به‌عنوان بخشی از build script یک فراخوانی کتابخانه تولید می‌کند.

    ابتدا ساختار دایرکتوری این بسته را ببینیم:

    .
├── Cargo.toml
├── build.rs
└── src
    └── main.rs

1 directory, 3 files

    همان‌طور که می‌بینیم، یک build script به نام build.rs و باینری ما در main.rs قرار دارد. این بسته یک manifest ساده دارد:

    # Cargo.toml

[package]
name = "hello-from-generated-code"
version = "0.1.0"
edition = "2024"

    ببینیم داخل build script چیست:

    // build.rs

use std::env;
use std::fs;
use std::path::Path;

fn main() {
    let out_dir = env::var_os("OUT_DIR").unwrap();
    let dest_path = Path::new(&out_dir).join("hello.rs");
    fs::write(
        &dest_path,
        "pub fn message() -> &'static str {
            \"Hello, World!\"
        }
        "
    ).unwrap();
    println!("cargo::rerun-if-changed=build.rs");
}

    چند نکتهٔ قابل‌توجه در اینجا وجود دارد:

    • این اسکریپت از متغیر محیطی OUT_DIR استفاده می‌کند تا محل فایل‌های خروجی را پیدا کند. می‌تواند از دایرکتوری کاری فعلی فرایند برای یافتن محل فایل‌های ورودی استفاده کند، اما در این مثال هیچ فایل ورودی نداریم.
    • به‌طور کلی، build scriptها نباید هیچ فایلی را بیرون از OUT_DIR تغییر دهند. در نگاه اول ممکن است اشکالی نداشته باشد، اما وقتی چنین crateی را به‌عنوان وابستگی به کار ببرید مشکل ایجاد می‌کند، چون یک پیش‌شرط ضمنی وجود دارد که سورس‌های داخل .cargo/registry باید تغییرناپذیر باشند. cargo هنگام بسته‌بندی چنین اسکریپت‌هایی را مجاز نمی‌داند.
      • گاهی پروژه‌ها می‌خواهند یک فایل تولیدشده را در مخزن ثبت (check in) کنند و آن را مانند کد منبع در نظر بگیرند. با این حال، در این صورت نباید فایل از build.rs تولید شود. در عوض، یک آزمون یا مشابه آن داشته باشید که بررسی کند فایل دقیقاً با نسخهٔ تولیدشده یکسان است و اگر نتیجه یکسان نبود شکست بخورد، و آن آزمون را به‌عنوان بخشی از CI اجرا کنید. (آزمون می‌تواند یک فایل موقت برای مقایسه تولید کند و اگر خواستید فایل تولیدشده را به‌روز کنید، می‌توانید فایل ثبت‌شده را با آن فایل موقت جایگزین کنید.)
    • این اسکریپت نسبتاً ساده است، چون فقط یک فایل تولیدشدهٔ کوچک می‌نویسد. می‌توان تصور کرد که عملیات پیچیده‌تر دیگری نیز انجام شود، مثلاً تولید یک ماژول Rust از یک فایل سرآیند C یا تعریف یک زبان دیگر.
    • دستور rerun-if-changed به Cargo می‌گوید که build script فقط وقتی باید دوباره اجرا شود که خود build script تغییر کند. بدون این خط، Cargo اگر هر فایلی در بسته تغییر کند، build script را خودکار اجرا می‌کند. اگر تولید کد شما از چند فایل ورودی استفاده می‌کند، اینجا همان جایی است که فهرست هر یک از آن فایل‌ها را چاپ می‌کنید.

    سپس نگاهی به خود کتابخانه بیندازیم:

    // src/main.rs

include!(concat!(env!("OUT_DIR"), "/hello.rs"));

fn main() {
    println!("{}", message());
}

    اینجا جادوی اصلی اتفاق می‌افتد. کتابخانه از ماکرو include! تعریف‌شده در rustc همراه با ماکروهای concat! و env! استفاده می‌کند تا فایل تولیدشده (hello.rs) را در کامپایل crate بگنجاند.

    با استفاده از ساختاری که اینجا نشان داده شد، crateها می‌توانند هر تعداد فایل تولیدشده را از خود build script بگنجانند.

    ساخت یک کتابخانهٔ بومی

    گاهی لازم است بخشی از کد بومی C یا C++ به‌عنوان بخشی از یک بسته ساخته شود. این هم یک مورد استفادهٔ عالی دیگر از build script است: ساخت یک کتابخانهٔ بومی پیش از خود crate مربوط به Rust. به‌عنوان مثال، یک کتابخانهٔ Rust می‌سازیم که به C فراخوانی می‌کند تا «Hello, World!» را چاپ کند.

    مانند مثال قبل، ابتدا چیدمان بسته را ببینیم:

    .
├── Cargo.toml
├── build.rs
└── src
    ├── hello.c
    └── main.rs

1 directory, 4 files

    بسیار شبیه قبل! سپس manifest:

    # Cargo.toml

[package]
name = "hello-world-from-c"
version = "0.1.0"
edition = "2024"

    فعلاً قصد نداریم از هیچ وابستگی ساخت (build dependency) استفاده کنیم، پس بیایید build script را ببینیم:

    // build.rs

use std::process::Command;
use std::env;
use std::path::Path;

fn main() {
    let out_dir = env::var("OUT_DIR").unwrap();

    // Note that there are a number of downsides to this approach, the comments
    // below detail how to improve the portability of these commands.
    Command::new("gcc").args(&["src/hello.c", "-c", "-fPIC", "-o"])
                       .arg(&format!("{}/hello.o", out_dir))
                       .status().unwrap();
    Command::new("ar").args(&["crus", "libhello.a", "hello.o"])
                      .current_dir(&Path::new(&out_dir))
                      .status().unwrap();

    println!("cargo::rustc-link-search=native={}", out_dir);
    println!("cargo::rustc-link-lib=static=hello");
    println!("cargo::rerun-if-changed=src/hello.c");
}

    این build script ابتدا فایل C ما را به یک فایل شیء کامپایل می‌کند (با فراخوانی gcc) و سپس این فایل شیء را به یک کتابخانهٔ ایستا تبدیل می‌کند (با فراخوانی ar). گام پایانی بازخورد به خود Cargo است تا بگوید خروجی ما در out_dir بود و کامپایلر باید crate را با پرچم -l static=hello به‌صورت ایستا به libhello.a پیوند (link) دهد.

    توجه کنید که این رویکرد با مقادیر ثابت (hard-coded) چند عیب دارد:

    • خود فرمان gcc بین پلتفرم‌ها قابل‌حمل نیست. برای مثال بعید است پلتفرم‌های ویندوز gcc داشته باشند و حتی همهٔ پلتفرم‌های یونیکس هم لزوماً gcc ندارند. فرمان ar نیز وضعیت مشابهی دارد.
    • این فرمان‌ها کامپایل متقابل (cross-compilation) را در نظر نمی‌گیرند. اگر برای پلتفرمی مانند اندروید کامپایل متقابل انجام دهیم، بعید است gcc یک فایل اجرایی ARM تولید کند.

    اما جای نگرانی نیست؛ اینجاست که یک مدخل build-dependencies کمک می‌کند! اکوسیستم Cargo بسته‌های متعددی دارد که این‌گونه کارها را بسیار ساده‌تر، قابل‌حمل‌تر و استاندارد می‌کنند. بیایید crate cc را از crates.io امتحان کنیم. ابتدا آن را به build-dependencies در Cargo.toml اضافه کنید:

    [build-dependencies]
cc = "1.0"

    و build script را برای استفاده از این crate بازنویسی کنید:

    // build.rs

fn main() {
    cc::Build::new()
        .file("src/hello.c")
        .compile("hello");
    println!("cargo::rerun-if-changed=src/hello.c");
}

    crate cc طیفی از نیازهای build script برای کد C را انتزاعی می‌کند:

    • کامپایلر مناسب را فراخوانی می‌کند (MSVC برای ویندوز، gcc برای MinGW، cc برای پلتفرم‌های یونیکس و غیره).
    • متغیر TARGET را با ارسال پرچم‌های مناسب به کامپایلر مورداستفاده در نظر می‌گیرد.
    • سایر متغیرهای محیطی، مانند OPT_LEVEL، DEBUG و غیره، همگی خودکار مدیریت می‌شوند.
    • خروجی stdout و محل‌های OUT_DIR نیز توسط کتابخانهٔ cc مدیریت می‌شوند.

    اینجا می‌توانیم برخی از مزایای اصلی واگذار کردن هرچه بیشتر قابلیت‌ها به وابستگی‌های ساخت مشترک را ببینیم، به‌جای اینکه منطق در همهٔ build scriptها تکرار شود!

    اما به مطالعهٔ موردی برگردیم؛ نگاه سریعی به محتوای دایرکتوری src بیندازیم:

    // src/hello.c

#include <stdio.h>

void hello() {
    printf("Hello, World!\n");
}

    // src/main.rs

// Note the lack of the `#[link]` attribute. We’re delegating the responsibility
// of selecting what to link over to the build script rather than hard-coding
// it in the source file.
unsafe extern { fn hello(); }

fn main() {
    unsafe { hello(); }
}

    و تمام! این مثال ساخت مقداری کد C از یک بستهٔ Cargo را با استفاده از خود build script کامل می‌کند. همچنین نشان می‌دهد چرا استفاده از یک وابستگی ساخت در بسیاری از موارد می‌تواند حیاتی و حتی بسیار مختصرتر باشد!

    همچنین مثال کوتاهی دیدیم از اینکه چگونه یک build script می‌تواند از یک crate صرفاً برای فرایند ساخت به‌عنوان وابستگی استفاده کند و نه برای خود crate در زمان اجرا.

    پیوند دادن به کتابخانه‌های سیستم

    این مثال نشان می‌دهد چگونه یک کتابخانهٔ سیستم را پیوند دهیم و build script چگونه برای پشتیبانی از این کاربرد استفاده می‌شود.

    بسیار پیش می‌آید که یک crate در Rust بخواهد به کتابخانه‌ای بومی که روی سیستم موجود است پیوند بخورد تا قابلیت‌های آن را bind کند یا صرفاً از آن به‌عنوان بخشی از جزئیات پیاده‌سازی استفاده کند. وقتی بخواهیم این کار را به شکلی مستقل از پلتفرم انجام دهیم، مسئله‌ای بسیار ظریف است. بهتر است، در صورت امکان، تا جای ممکن آن را به چیزی واگذار کنیم که کار را برای مصرف‌کنندگان تا حد امکان آسان کند.

    در این مثال، یک binding برای کتابخانهٔ zlib سیستم می‌سازیم. این کتابخانه‌ای است که معمولاً در بیشتر سیستم‌های شبه‌یونیکس یافت می‌شود و فشرده‌سازی داده را فراهم می‌کند. این کتابخانه پیش‌تر در crate libz-sys بسته‌بندی شده است، اما برای این مثال یک نسخهٔ بسیار ساده‌شده می‌سازیم. برای مثال کامل کد منبع را ببینید.

    برای اینکه یافتن محل کتابخانه آسان شود، از crate pkg-config استفاده می‌کنیم. این crate از ابزار pkg-config سیستم استفاده می‌کند تا اطلاعات یک کتابخانه را کشف کند. به‌طور خودکار به Cargo می‌گوید برای پیوند دادن کتابخانه چه چیزی لازم است. این روش احتمالاً فقط روی سیستم‌های شبه‌یونیکسی که pkg-config نصب دارند کار می‌کند. بیایید با تنظیم manifest شروع کنیم:

    # Cargo.toml

[package]
name = "libz-sys"
version = "0.1.0"
edition = "2024"
links = "z"

[build-dependencies]
pkg-config = "0.3.16"

    توجه کنید که کلید links را در جدول package گنجانده‌ایم. این به Cargo می‌گوید که به کتابخانهٔ libz پیوند می‌خوریم. برای مثالی که از این بهره می‌برد، «استفاده از یک crate از نوع sys دیگر» را ببینید.

    build script نسبتاً ساده است:

    // build.rs

fn main() {
    pkg_config::Config::new().probe("zlib").unwrap();
    println!("cargo::rerun-if-changed=build.rs");
}

    بیایید مثال را با یک binding ساده برای FFI کامل کنیم:

    // src/lib.rs

use std::os::raw::{c_uint, c_ulong};

unsafe extern "C" {
    pub fn crc32(crc: c_ulong, buf: *const u8, len: c_uint) -> c_ulong;
}

#[test]
fn test_crc32() {
    let s = "hello";
    unsafe {
        assert_eq!(crc32(0, s.as_ptr(), s.len() as c_uint), 0x3610a686);
    }
}

    برای دیدن خروجی build script دستور cargo build -vv را اجرا کنید. روی سیستمی که libz از قبل روی آن نصب است، ممکن است چیزی شبیه این ببینید:

    [libz-sys 0.1.0] cargo::rustc-link-search=native=/usr/lib
[libz-sys 0.1.0] cargo::rustc-link-lib=z
[libz-sys 0.1.0] cargo::rerun-if-changed=build.rs

    عالی! pkg-config همهٔ کار پیدا کردن کتابخانه و اطلاع دادن محل آن به Cargo را انجام داد.

    غیرعادی نیست که بسته‌ها سورس کتابخانه را هم شامل شوند و اگر کتابخانه روی سیستم پیدا نشد، یا یک feature یا متغیر محیطی تنظیم شده بود، آن را به‌صورت ایستا بسازند. برای مثال، crate libz-sys واقعی متغیر محیطی LIBZ_SYS_STATIC یا feature به نام static را بررسی می‌کند تا به‌جای استفاده از کتابخانهٔ سیستم آن را از روی سورس بسازد. برای مثالی کامل‌تر سورس را ببینید.

    استفاده از یک crate از نوع sys دیگر

    هنگام استفاده از کلید links، crateها می‌توانند فراداده‌ای تنظیم کنند که crateهای وابسته به آن‌ها بتوانند بخوانند. این سازوکاری برای انتقال اطلاعات بین crateها فراهم می‌کند. در این مثال، یک کتابخانهٔ C می‌سازیم که از zlib در crate libz-sys واقعی استفاده می‌کند.

    اگر کتابخانهٔ C دارید که به zlib وابسته است، می‌توانید از crate libz-sys برای یافتن یا ساخت خودکار آن بهره ببرید. این برای پشتیبانی چندپلتفرمی عالی است، مثلاً در ویندوز که zlib معمولاً نصب نیست. libz-sys فراداده include را تنظیم می‌کند تا به بسته‌های دیگر بگوید فایل‌های سرآیند zlib کجا هستند. build script ما می‌تواند آن فراداده را با متغیر محیطی DEP_Z_INCLUDE بخواند. این هم یک مثال:

    # Cargo.toml

[package]
name = "z_user"
version = "0.1.0"
edition = "2024"

[dependencies]
libz-sys = "1.0.25"

[build-dependencies]
cc = "1.0.46"

    اینجا libz-sys را گنجانده‌ایم که تضمین می‌کند در کتابخانهٔ نهایی فقط یک libz استفاده شود و دسترسی به آن را از build script به ما می‌دهد:

    // build.rs

fn main() {
    let mut cfg = cc::Build::new();
    cfg.file("src/z_user.c");
    if let Some(include) = std::env::var_os("DEP_Z_INCLUDE") {
        cfg.include(include);
    }
    cfg.compile("z_user");
    println!("cargo::rerun-if-changed=src/z_user.c");
}

    با اینکه libz-sys همهٔ کار سنگین را انجام می‌دهد، کد C اکنون می‌تواند سرآیند zlib را include کند و باید آن را پیدا کند، حتی روی سیستم‌هایی که از قبل نصب نشده است.

    // src/z_user.c

#include "zlib.h"

// … rest of code that makes use of zlib.

    خواندن پیکربندی هدف

    وقتی یک build script باید بر اساس پلتفرم هدف تصمیم بگیرد، باید متغیرهای محیطی CARGO_CFG_* را بخواند، نه اینکه از cfg! یا attributeهای #[cfg] استفاده کند. دلیلش این است که build script برای ماشین میزبان (host) کامپایل می‌شود و روی آن اجرا می‌شود، در حالی که متغیرهای CARGO_CFG_* پلتفرم هدف را نشان می‌دهند؛ تمایزی مهم هنگام کامپایل متقابل.

    // build.rs

fn main() {
    // reads the TARGET configuration
    let target_os = std::env::var("CARGO_CFG_TARGET_OS").unwrap();

    if target_os == "windows" {
        println!("cargo::rustc-link-lib=userenv");
    } else if target_os == "linux" {
        println!("cargo::rustc-link-lib=pthread");
    }
}

    توجه کنید که برخی مقادیر پیکربندی ممکن است چند مقدار داشته باشند که با کاما جدا شده‌اند (برای مثال، CARGO_CFG_TARGET_FAMILY ممکن است unix,wasm باشد). هنگام بررسی این مقادیر، حتماً آن را به‌درستی مدیریت کنید.

    برای یک API تایپ‌دار و راحت‌تر، استفاده از crate به نام build-rs را در نظر بگیرید که این جزئیات را برای شما مدیریت می‌کند.

    کامپایل شرطی

    یک build script می‌تواند دستورهای rustc-cfg صادر کند که می‌توانند شرط‌هایی را فعال کنند که در زمان کامپایل قابل بررسی‌اند. در این مثال، می‌بینیم که crate openssl چگونه از این برای پشتیبانی از نسخه‌های متعدد کتابخانهٔ OpenSSL استفاده می‌کند.

    crate openssl-sys ساخت و پیوند کتابخانهٔ OpenSSL را پیاده‌سازی می‌کند. از چندین پیاده‌سازی مختلف (مانند LibreSSL) و چندین نسخه پشتیبانی می‌کند. از کلید links استفاده می‌کند تا بتواند اطلاعات را به build scriptهای دیگر منتقل کند. یکی از چیزهایی که منتقل می‌کند کلید version_number است که نسخهٔ OpenSSL شناسایی‌شده را نشان می‌دهد. کد داخل build script چیزی شبیه به این است:

    println!("cargo::metadata=version_number={openssl_version:x}");

    این دستور باعث می‌شود متغیر محیطی DEP_OPENSSL_VERSION_NUMBER در همهٔ crateهایی که مستقیماً به openssl-sys وابسته‌اند تنظیم شود.

    crate به نام openssl که رابط سطح بالاتر را فراهم می‌کند، openssl-sys را به‌عنوان وابستگی مشخص می‌کند. build script مربوط به openssl می‌تواند اطلاعات نسخهٔ تولیدشده توسط build script مربوط به openssl-sys را با متغیر محیطی DEP_OPENSSL_VERSION_NUMBER بخواند. از این برای تولید چند مقدار cfg استفاده می‌کند:

    // (portion of build.rs)

println!("cargo::rustc-check-cfg=cfg(ossl101,ossl102)");
println!("cargo::rustc-check-cfg=cfg(ossl110,ossl110g,ossl111)");

if let Ok(version) = env::var("DEP_OPENSSL_VERSION_NUMBER") {
    let version = u64::from_str_radix(&version, 16).unwrap();

    if version >= 0x1_00_01_00_0 {
        println!("cargo::rustc-cfg=ossl101");
    }
    if version >= 0x1_00_02_00_0 {
        println!("cargo::rustc-cfg=ossl102");
    }
    if version >= 0x1_01_00_00_0 {
        println!("cargo::rustc-cfg=ossl110");
    }
    if version >= 0x1_01_00_07_0 {
        println!("cargo::rustc-cfg=ossl110g");
    }
    if version >= 0x1_01_01_00_0 {
        println!("cargo::rustc-cfg=ossl111");
    }
}

    سپس می‌توان این مقادیر cfg را با attribute cfg یا ماکرو cfg برای گنجاندن شرطی کد به کار برد. برای مثال، پشتیبانی از SHA3 در OpenSSL 1.1.1 اضافه شد، بنابراین برای نسخه‌های قدیمی‌تر به‌صورت شرطی کنار گذاشته می‌شود:

    // (portion of openssl crate)

#[cfg(ossl111)]
pub fn sha3_224() -> MessageDigest {
    unsafe { MessageDigest(ffi::EVP_sha3_224()) }
}

    البته باید هنگام استفاده از این روش دقت کرد، زیرا باینری حاصل را حتی بیشتر به محیط ساخت وابسته می‌کند. در این مثال، اگر باینری روی سیستم دیگری توزیع شود، ممکن است دقیقاً همان کتابخانه‌های مشترک را نداشته باشد که می‌تواند مشکل‌ساز شود.
