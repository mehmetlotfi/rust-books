    هدف‌های Cargo

    بسته‌های Cargo از هدف‌هایی (targets) تشکیل می‌شوند که با فایل‌های منبعی متناظرند که می‌توان آن‌ها را به یک crate کامپایل کرد. بسته‌ها می‌توانند هدف‌های کتابخانه، باینری، نمونه، آزمون و benchmark داشته باشند. فهرست هدف‌ها را می‌توان در manifest فایل Cargo.toml پیکربندی کرد و اغلب به‌طور خودکار استنباط می‌شود؛ استنباط بر اساس چیدمان دایرکتوری فایل‌های منبع انجام می‌شود.

    برای جزئیات پیکربندی تنظیمات یک هدف، پیکربندی یک هدف را در ادامه ببینید.

    کتابخانه

    هدف کتابخانه یک «کتابخانه» تعریف می‌کند که کتابخانه‌ها و فایل‌های اجرایی دیگر می‌توانند از آن استفاده کنند و به آن پیوند (link) بخورند. نام فایل به‌طور پیش‌فرض src/lib.rs است و نام کتابخانه به‌طور پیش‌فرض نام بسته است، با این تفاوت که هر خط تیره با زیرخط جایگزین می‌شود. هر بسته فقط می‌تواند یک کتابخانه داشته باشد. تنظیمات کتابخانه را می‌توان در جدول [lib] در Cargo.toml سفارشی کرد.

    # Example of customizing the library in Cargo.toml.
[lib]
crate-type = ["cdylib"]
bench = false

    باینری‌ها

    هدف‌های باینری برنامه‌های اجرایی هستند که پس از کامپایل می‌توان آن‌ها را اجرا کرد. منبع یک باینری می‌تواند src/main.rs باشد و/یا در دایرکتوری src/bin/ قرار گیرد. برای src/main.rs، نام پیش‌فرض باینری همان نام بسته است. تنظیمات هر باینری را می‌توان در جدول‌های [[bin]] در Cargo.toml سفارشی کرد.

    باینری‌ها می‌توانند از API عمومی کتابخانهٔ بسته استفاده کنند. آن‌ها همچنین با [dependencies] که در Cargo.toml تعریف شده است پیوند می‌خورند.

    می‌توانید باینری‌ها را جداگانه با فرمان cargo run و گزینهٔ --bin <bin-name> اجرا کنید. از cargo install می‌توان برای کپی کردن فایل اجرایی به یک مکان مشترک استفاده کرد.

    # Example of customizing binaries in Cargo.toml.
[[bin]]
name = "cool-tool"
test = false
bench = false

[[bin]]
name = "frobnicator"
required-features = ["frobnicate"]

    نمونه‌ها

    فایل‌هایی که زیر دایرکتوری examples قرار دارند، نمونه‌هایی از کاربرد قابلیت‌هایی هستند که کتابخانه ارائه می‌دهد. هنگام کامپایل، این فایل‌ها در دایرکتوری target/debug/examples قرار می‌گیرند.

    نمونه‌ها می‌توانند از API عمومی کتابخانهٔ بسته استفاده کنند. آن‌ها همچنین با [dependencies] و [dev-dependencies] که در Cargo.toml تعریف شده‌اند پیوند می‌خورند.

    به‌طور پیش‌فرض، نمونه‌ها باینری‌های اجرایی هستند (با تابع main()). می‌توانید فیلد crate-type را مشخص کنید تا یک نمونه به‌صورت کتابخانه کامپایل شود:

    [[example]]
name = "foo"
crate-type = ["staticlib"]

    می‌توانید نمونه‌های اجرایی را جداگانه با فرمان cargo run و گزینهٔ --example <example-name> اجرا کنید. نمونه‌های کتابخانه‌ای را می‌توان با cargo build و گزینهٔ --example <example-name> ساخت. از cargo install با گزینهٔ --example <example-name> می‌توان برای کپی کردن باینری‌های اجرایی به یک مکان مشترک استفاده کرد. نمونه‌ها به‌طور پیش‌فرض توسط cargo test کامپایل می‌شوند تا از پوسیدگی (bit-rot) آن‌ها جلوگیری شود. اگر در نمونه توابع #[test] دارید که می‌خواهید با cargo test اجرا شوند، فیلد test را روی true تنظیم کنید.

    آزمون‌ها

    در یک پروژهٔ Cargo دو سبک آزمون وجود دارد:

    • آزمون‌های واحد که توابعی هستند با attribute #[test] علامت‌گذاری شده‌اند و در کتابخانه یا باینری‌های شما (یا هر هدفی که با فیلد test فعال شده باشد) قرار دارند. این آزمون‌ها به APIهای خصوصی هدفی که در آن تعریف شده‌اند دسترسی دارند.
    • آزمون‌های یکپارچگی که یک باینری اجرایی جداگانه‌اند و آن‌ها نیز شامل توابع #[test] هستند، با کتابخانهٔ پروژه پیوند می‌خورند و به API عمومی آن دسترسی دارند.

    آزمون‌ها با فرمان cargo test اجرا می‌شوند. به‌طور پیش‌فرض، Cargo و rustc از harness مربوط به libtest استفاده می‌کنند که مسئول جمع‌آوری توابعی است که با attribute #[test] حاشیه‌نویسی شده‌اند و اجرای موازی آن‌ها و گزارش موفقیت و شکست هر آزمون. اگر می‌خواهید از harness یا راهبرد آزمون دیگری استفاده کنید، فیلد harness را ببینید.

    Note

    در Cargo یک سبک آزمون ویژهٔ دیگر هم وجود دارد: آزمون‌های مستندات. این آزمون‌ها توسط rustdoc مدیریت می‌شوند و مدل اجرای کمی متفاوتی دارند. برای اطلاعات بیشتر، لطفاً cargo test را ببینید.

    آزمون‌های یکپارچگی

    فایل‌هایی که زیر دایرکتوری tests قرار دارند آزمون‌های یکپارچگی هستند. وقتی cargo test را اجرا می‌کنید، Cargo هر یک از این فایل‌ها را به‌عنوان یک crate جداگانه کامپایل می‌کند و اجرا می‌کند.

    آزمون‌های یکپارچگی می‌توانند از API عمومی کتابخانهٔ بسته استفاده کنند. آن‌ها همچنین با [dependencies] و [dev-dependencies] که در Cargo.toml تعریف شده‌اند پیوند می‌خورند.

    اگر می‌خواهید کد را بین چند آزمون یکپارچگی به اشتراک بگذارید، می‌توانید آن را در یک ماژول جداگانه مانند tests/common/mod.rs قرار دهید و سپس mod common; را در هر آزمون بگذارید تا آن را وارد کنید.

    هر آزمون یکپارچگی به یک باینری اجرایی جداگانه منجر می‌شود و cargo test آن‌ها را به‌صورت پشت‌سرهم (serial) اجرا می‌کند. در برخی موارد این می‌تواند ناکارآمد باشد، چون ممکن است کامپایل بیشتر طول بکشد و هنگام اجرای آزمون‌ها از چند CPU استفادهٔ کامل نشود. اگر آزمون‌های یکپارچگی زیادی دارید، می‌توانید یک آزمون یکپارچگی واحد بسازید و آزمون‌ها را در چند ماژول تقسیم کنید. harness مربوط به libtest به‌طور خودکار همهٔ توابع دارای attribute #[test] را پیدا می‌کند و به‌صورت موازی اجرا می‌کند. می‌توانید نام ماژول‌ها را به cargo test بدهید تا فقط آزمون‌های درون آن ماژول اجرا شوند.

    اگر آزمون یکپارچگی وجود داشته باشد، هدف‌های باینری به‌طور خودکار ساخته می‌شوند. این به آزمون یکپارچگی اجازه می‌دهد باینری را اجرا کند تا رفتارش را بسنجد و آزمایش کند. متغیر محیطی CARGO_BIN_EXE_<name> هنگام ساخت و اجرای آزمون یکپارچگی تنظیم می‌شود تا آزمون بتواند با ماکرو env یا تابع var فایل اجرایی را پیدا کند.

    Benchmarkها

    Benchmarkها راهی برای آزمودن کارایی کد شما با استفاده از فرمان cargo bench فراهم می‌کنند. ساختار آن‌ها مانند آزمون‌ها است و هر تابع benchmark با attribute #[bench] حاشیه‌نویسی می‌شود. مانند آزمون‌ها:

    • Benchmarkها در دایرکتوری benches قرار می‌گیرند.
    • توابع benchmark که در کتابخانه‌ها و باینری‌ها تعریف می‌شوند به API خصوصی هدفی که در آن تعریف شده‌اند دسترسی دارند. Benchmarkهای موجود در دایرکتوری benches می‌توانند از API عمومی استفاده کنند.
    • از فیلد bench می‌توان برای تعیین اینکه کدام هدف‌ها به‌طور پیش‌فرض benchmark شوند استفاده کرد.
    • از فیلد harness می‌توان برای غیرفعال کردن harness داخلی استفاده کرد.

    Note

    attribute #[bench] در حال حاضر ناپایدار است و فقط در کانال nightly در دسترس است. چند بسته در crates.io وجود دارند که ممکن است در اجرای benchmarkها روی کانال stable کمک کنند، مانند Criterion.

    پیکربندی یک هدف

    همهٔ بخش‌های [lib]، [[bin]]، [[example]]، [[test]] و [[bench]] در Cargo.toml از پیکربندی مشابهی برای مشخص کردن نحوهٔ ساخت یک هدف پشتیبانی می‌کنند. بخش‌های با دو کروشه مانند [[bin]]، آرایه‌ای از جدول‌ها (array-of-table) در TOML هستند که یعنی می‌توانید بیش از یک بخش [[bin]] بنویسید تا چند فایل اجرایی در crate خود بسازید. فقط یک کتابخانه می‌توانید مشخص کنید، بنابراین [lib] یک جدول معمولی TOML است.

    آنچه در ادامه می‌آید مرور کلی تنظیمات TOML برای هر هدف است و هر فیلد در ادامه به‌تفصیل توضیح داده شده است.

    [lib]
name = "foo"           # The name of the target.
path = "src/lib.rs"    # The source file of the target.
test = true            # Is tested by default.
doctest = true         # Documentation examples are tested by default.
bench = true           # Is benchmarked by default.
doc = true             # Is documented by default.
proc-macro = false     # Set to `true` for a proc-macro library.
harness = true         # Use libtest harness.
crate-type = ["lib"]   # The crate types to generate.
required-features = [] # Features required to build this target (N/A for lib).

    فیلد name

    فیلد name نام هدف را مشخص می‌کند که با نام فایل artifactی که تولید خواهد شد متناظر است. برای یک کتابخانه، این همان نام crate است که وابستگی‌ها برای ارجاع به آن استفاده می‌کنند.

    برای هدف کتابخانه، به‌طور پیش‌فرض نام بسته است، با این تفاوت که هر خط تیره با زیرخط جایگزین می‌شود. برای باینری پیش‌فرض (src/main.rs)، آن نیز به‌طور پیش‌فرض نام بسته است، بدون جایگزینی خط تیره‌ها. برای هدف‌هایی که به‌طور خودکار کشف می‌شوند، پیش‌فرض نام دایرکتوری یا فایل است.

    این فیلد برای همهٔ هدف‌ها به‌جز [lib] الزامی است.

    فیلد path

    فیلد path مشخص می‌کند منبع crate در کجا قرار دارد، نسبت به فایل Cargo.toml.

    اگر مشخص نشود، مسیر استنباط‌شده بر اساس نام هدف به کار می‌رود.

    فیلد test

    فیلد test مشخص می‌کند که آیا هدف به‌طور پیش‌فرض توسط cargo test آزموده می‌شود یا نه. پیش‌فرض برای lib، باینری‌ها و آزمون‌ها true است.

    Note

    نمونه‌ها به‌طور پیش‌فرض توسط cargo test ساخته می‌شوند تا مطمئن شویم همچنان کامپایل می‌شوند، اما به‌طور پیش‌فرض آزموده نمی‌شوند. تنظیم test = true برای یک نمونه باعث می‌شود آن نمونه به‌عنوان آزمون نیز ساخته شود و هر تابع #[test] که در نمونه تعریف شده باشد اجرا شود.

    فیلد doctest

    فیلد doctest مشخص می‌کند که آیا نمونه‌های مستندات به‌طور پیش‌فرض توسط cargo test آزموده می‌شوند یا نه. این فقط برای کتابخانه‌ها مرتبط است و روی بخش‌های دیگر اثری ندارد. پیش‌فرض برای کتابخانه true است.

    فیلد bench

    فیلد bench مشخص می‌کند که آیا هدف به‌طور پیش‌فرض توسط cargo bench benchmark می‌شود یا نه. پیش‌فرض برای lib، باینری‌ها و benchmarkها true است.

    فیلد doc

    فیلد doc مشخص می‌کند که آیا هدف به‌طور پیش‌فرض در مستنداتی که cargo doc تولید می‌کند گنجانده می‌شود یا نه. پیش‌فرض برای کتابخانه‌ها و باینری‌ها true است.

    Note

    اگر نام باینری با هدف lib یکسان باشد، باینری نادیده گرفته می‌شود.

    فیلد plugin

    این گزینه منسوخ است و استفاده نمی‌شود.

    فیلد proc-macro

    فیلد proc-macro نشان می‌دهد که کتابخانه یک ماکروی رویه‌ای (مرجع) است. این فقط برای هدف [lib] معتبر است.

    فیلد harness

    فیلد harness نشان می‌دهد که پرچم --test به rustc ارسال می‌شود که به‌طور خودکار کتابخانهٔ libtest را شامل می‌کند؛ libtest محرکی برای جمع‌آوری و اجرای آزمون‌هایی است که با attribute #[test] علامت‌گذاری شده‌اند یا benchmarkهایی که با attribute #[bench] علامت‌گذاری شده‌اند. پیش‌فرض برای همهٔ هدف‌ها true است.

    اگر روی false تنظیم شود، شما مسئول تعریف یک تابع main() برای اجرای آزمون‌ها و benchmarkها هستید.

    آزمون‌ها عبارت شرطی cfg(test) را فعال دارند، چه harness فعال باشد چه نباشد.

    فیلد crate-type

    فیلد crate-type نوع‌های crate را که هدف تولید می‌کند تعریف می‌کند. این یک آرایه از رشته‌هاست و به شما امکان می‌دهد چند نوع crate را برای یک هدف مشخص کنید. این فقط برای کتابخانه‌ها و نمونه‌ها قابل مشخص کردن است. باینری‌ها، آزمون‌ها و benchmarkها همیشه نوع crate «bin» هستند. پیش‌فرض‌ها این‌ها هستند:

    هدفنوع crate
    کتابخانهٔ معمولی"lib"
    کتابخانهٔ proc-macro"proc-macro"
    نمونه"bin"

    گزینه‌های موجود bin، lib، rlib، dylib، cdylib، staticlib و proc-macro هستند. دربارهٔ نوع‌های مختلف crate می‌توانید بیشتر در مرجع زبان Rust بخوانید.

    فیلد required-features

    فیلد required-features مشخص می‌کند هدف برای ساخته شدن به کدام featureها نیاز دارد. اگر هر یک از featureهای موردنیاز فعال نباشد، هدف نادیده گرفته می‌شود. این فقط برای بخش‌های [[bin]]، [[bench]]، [[test]] و [[example]] مرتبط است و روی [lib] اثری ندارد.

    [features]
# ...
postgres = []
sqlite = []
tools = []

[[bin]]
name = "my-pg-tool"
required-features = ["postgres", "tools"]

    فیلد edition

    فیلد edition مشخص می‌کند هدف از کدام edition زبان Rust استفاده کند. اگر مشخص نشود، به‌طور پیش‌فرض برابر فیلد edition در بخش [package] است.

    Important

    این فیلد منسوخ است و در یک Edition آینده حذف خواهد شد

    کشف خودکار هدف‌ها

    به‌طور پیش‌فرض، Cargo هدف‌هایی را که باید ساخته شوند به‌طور خودکار بر اساس چیدمان فایل‌ها در سیستم فایل تعیین می‌کند. جدول‌های پیکربندی هدف، مانند [lib]، [[bin]]، [[test]]، [[bench]] یا [[example]]، را می‌توان برای افزودن هدف‌های اضافی که از چیدمان استاندارد دایرکتوری پیروی نمی‌کنند به کار برد.

    می‌توان کشف خودکار هدف‌ها را غیرفعال کرد تا فقط هدف‌هایی که به‌صورت دستی پیکربندی شده‌اند ساخته شوند. تنظیم کلیدهای autolib، autobins، autoexamples، autotests یا autobenches روی false در بخش [package]، کشف خودکار نوع هدف متناظر را غیرفعال می‌کند.

    [package]
# ...
autolib = false
autobins = false
autoexamples = false
autotests = false
autobenches = false

    غیرفعال کردن کشف خودکار فقط در موقعیت‌های خاص لازم است. برای مثال، اگر کتابخانه‌ای دارید که می‌خواهید یک ماژول با نام bin داشته باشد، این مشکل‌ساز است زیرا Cargo معمولاً هر چیزی را که در دایرکتوری bin باشد به‌عنوان فایل اجرایی کامپایل می‌کند. این هم نمونهٔ چیدمان این سناریو:

    ├── Cargo.toml
└── src
    ├── lib.rs
    └── bin
        └── mod.rs

    برای جلوگیری از اینکه Cargo فایل src/bin/mod.rs را به‌عنوان فایل اجرایی استنباط کند، در Cargo.toml مقدار autobins = false را تنظیم کنید تا کشف خودکار غیرفعال شود:

    [package]
# …
autobins = false

    Note

    برای بسته‌هایی با edition 2015، اگر دست‌کم یک هدف به‌صورت دستی در Cargo.toml تعریف شده باشد، پیش‌فرض کشف خودکار false است. از edition 2018 به بعد، پیش‌فرض همیشه true است.

    MSRV: از نسخهٔ 1.83 برای autolib رعایت می‌شود
