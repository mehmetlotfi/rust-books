    نسخهٔ Rust

    فیلد rust-version کلیدی اختیاری است که به cargo می‌گوید بسته شما از چه نسخه‌ای از toolchain زبان Rust پشتیبانی می‌کند.

    [package]
# ...
rust-version = "1.56"

    نسخهٔ Rust باید یک شمارهٔ نسخهٔ ساده با دست‌کم یک مؤلفه باشد؛ نمی‌تواند شامل عملگرهای semver یا شناسه‌های پیش‌انتشار باشد. شناسه‌های پیش‌انتشار کامپایلر مانند -nightly هنگام بررسی نسخهٔ Rust نادیده گرفته می‌شوند.

    MSRV: از نسخهٔ 1.56 رعایت می‌شود

    کاربردها

    تشخیص‌ها (Diagnostics):

    وقتی بستهٔ شما روی toolchainای پشتیبانی‌نشده کامپایل شود، Cargo این موضوع را به‌صورت خطا به کاربر گزارش می‌کند. این کار انتظارات پشتیبانی را روشن می‌کند و از گزارش تشخیص‌های غیرمستقیم‌تر مانند نحو نامعتبر یا نبود قابلیتی در کتابخانهٔ استاندارد جلوگیری می‌کند. این موضوع بر همهٔ هدف‌های Cargo در بسته اثر می‌گذارد، از جمله فایل‌های باینری، مثال‌ها، مجموعه‌آزمون‌ها، ریزسنجی‌ها و غیره. کاربر می‌تواند با پرچم --ignore-rust-version ساخت پشتیبانی‌نشدهٔ یک بسته را انتخاب کند.

    کمک به توسعه:

    cargo add الزام نسخهٔ وابستگی را به‌طور خودکار روی جدیدترین نسخهٔ سازگار با rust-version شما تنظیم می‌کند. اگر آن نسخه جدیدترین نسخه نباشد، cargo add کاربران را مطلع می‌کند تا بتوانند تصمیم بگیرند که آن را نگه دارند یا rust-version شما را به‌روز کنند.

    resolver ممکن است هنگام انتخاب وابستگی‌ها نسخهٔ Rust را در نظر بگیرد.

    ابزارهای دیگر نیز می‌توانند از آن بهره ببرند، مانند lint به نام incompatible_msrv در cargo clippy.

    Note

    می‌توان rust-version را با گزینهٔ --ignore-rust-version نادیده گرفت.

    انتظارات پشتیبانی

    این‌ها انتظارات کلی هستند؛ برخی بسته‌ها ممکن است مستند کنند که از آن‌ها پیروی نمی‌کنند.

    کامل:

    همهٔ قابلیت‌ها، از جمله فایل‌های باینری و API، روی نسخه‌های پشتیبانی‌شدهٔ Rust و زیر هر feature در دسترس‌اند.

    راستی‌آزمایی‌شده:

    قابلیت‌های یک بسته روی نسخه‌های پشتیبانی‌شدهٔ Rust آن، از جمله با آزمون خودکار، راستی‌آزمایی می‌شود. همچنین راهنمای CI برای نسخهٔ Rust ما را ببینید.

    قابل وصله‌کردن:

    وقتی مجوزها اجازه دهند، کاربران می‌توانند وابستگی محلی خود را جایگزین کنند و از یک fork از بستهٔ شما استفاده کنند. در این وضعیت، Cargo ممکن است کل workspace را برای وابستگی وصله‌شده بارگذاری کند که باید روی نسخه‌های پشتیبانی‌شدهٔ Rust کار کند، حتی اگر بسته‌های دیگر workspace نسخه‌های پشتیبانی‌شدهٔ Rust متفاوتی داشته باشند.

    پشتیبانی از وابستگی‌ها:

    برای پشتیبانی از موارد بالا، انتظار می‌رود الزام نسخهٔ هر وابستگی دست‌کم یک نسخهٔ سازگار با rust-version شما را پوشش دهد. با این حال، انتظار نمی‌رود که مشخصات وابستگی نسخه‌های ناسازگار با rust-version شما را حذف کند. در واقع، پشتیبانی از هر دو به شما امکان می‌دهد میان نیازهای کاربرانی که از نسخه‌های قدیمی‌تر Rust پشتیبانی می‌کنند و کاربرانی که نمی‌کنند تعادل برقرار کنید.

    تعیین و به‌روزرسانی نسخهٔ Rust

    اینکه از چه نسخه‌هایی از Rust پشتیبانی شود، مصالحه‌ای میان این موارد است

    • هزینه‌های نگه‌دارنده برای استفاده نکردن از featureهای جدیدتر toolchain زبان Rust یا وابستگی‌هایش
    • هزینه‌های کاربرانی که از استفادهٔ بسته از featureهای جدیدتر یک toolchain سود می‌برند، مثلاً کاهش زمان ساخت با مهاجرت از یک polyfill به featureای در کتابخانهٔ استاندارد
    • در دسترس بودن بسته برای کاربرانی که از نسخه‌های قدیمی‌تر Rust پشتیبانی می‌کنند

    Note

    تغییر rust-version یک ناسازگاری جزئی (minor) فرض می‌شود

    Tip

    سیاستی برای اینکه از چه نسخه‌هایی از Rust پشتیبانی می‌شود و چه زمانی تغییر می‌کند انتخاب کنید تا کاربران بتوانند آن را با سیاست خودشان مقایسه کنند و اگر سازگار نبود، تصمیم بگیرند که از دست دادن بهبودهای عمومی یا خطر یک باگ مسدودکننده که رفع نخواهد شد قابل‌پذیرش است یا نه.

    ساده‌ترین سیاست برای پشتیبانی این است که همیشه از جدیدترین نسخهٔ Rust استفاده شود.

    بسته به نمایهٔ ریسک شما، ساده‌ترین رویکرد بعدی این است که به پشتیبانی از نسخه‌های major یا minor قدیمی بستهٔ خود که از نسخه‌های قدیمی‌تر Rust پشتیبانی می‌کنند ادامه دهید.

    انتخاب نسخه‌های پشتیبانی‌شدهٔ Rust

    کاربران بستهٔ شما به احتمال زیاد نسخه‌های پشتیبانی‌شدهٔ Rust خود را با این‌ها هماهنگ می‌کنند:

    • سیاست پشتیبانی عرضه‌کنندهٔ toolchain زبان Rust، مثلاً پروژهٔ Rust یا یک توزیع لینوکس
      • توجه: پروژهٔ Rust فقط برای جدیدترین نسخه رفع باگ و به‌روزرسانی امنیتی ارائه می‌کند.
    • زمان‌بندی ثابتی برای اینکه کاربران بسته‌های خود را با toolchain جدید دوباره راستی‌آزمایی کنند، مثلاً نخستین انتشار سال، یا هر ۵ انتشار.

    علاوه بر این، بعید است کاربران بلافاصله از نسخهٔ جدید Rust استفاده کنند؛ آن‌ها به زمان نیاز دارند تا متوجه شوند و دوباره راستی‌آزمایی کنند، یا ممکن است دقیقاً با همان زمان‌بندی هماهنگ نباشند.

    نمونه‌هایی از سیاست‌های نسخه:

    • «N-2» به معنای «جدیدترین نسخه با دورهٔ مهلت ۲ انتشاری برای به‌روزرسانی»
    • هر انتشار زوج با دورهٔ مهلت ۲ انتشاری برای به‌روزرسانی
    • هر نسخهٔ این سال تقویمی با دورهٔ مهلت یک‌ساله برای به‌روزرسانی

    Note

    برای یافتن کمینهٔ rust-version سازگار با پروژهٔ خود به همین شکل فعلی، می‌توانید از ابزارهای شخص ثالث مانند cargo-msrv استفاده کنید.

    زمان‌بندی به‌روزرسانی

    وقتی سیاست شما مشخص می‌کند دیگر نیازی به پشتیبانی از یک نسخهٔ Rust نیست، می‌توانید rust-version را فوراً یا هر زمان لازم شد به‌روز کنید.

    با اجازه دادن به اینکه rust-version از سیاست شما فاصله بگیرد، به کاربران مهلت بیشتری برای ارتقا می‌دهید. با این حال، این موضوع آن‌قدر پیش‌بینی‌ناپذیر است که نمی‌توان برای هماهنگی با نسخهٔ Rustی که کاربران دنبال می‌کنند به آن تکیه کرد.

    هرچه rust-version بیشتر از سیاست مشخص‌شدهٔ شما فاصله بگیرد، احتمال بیشتری دارد که کاربران سیاستی را برداشت کنند که قصدش را نداشته‌اید و این به ناامیدی از انتظارات برآورده‌نشده بینجامد.

    وقتی انحراف مجاز باشد، این پرسش پیش می‌آید که چه چیزی «به‌اندازهٔ کافی موجه» است که نسخه‌های پشتیبانی‌شده حذف شوند. هر فرد ممکن است به توجیهی کاملاً متفاوت برسد؛ پیش بردن آن بحث می‌تواند برای طرف‌های درگیر ناخوشایند باشد. این موضوع کسانی را بی‌قدرت می‌کند که می‌خواهند از چنین تعارضی دوری کنند، که به‌ویژه دربارهٔ مشارکت‌کنندگان تازه‌وارد یا گاه‌به‌گاه صدق می‌کند، چراکه یا احساس می‌کنند در موقعیتی نیستند که این پرسش را مطرح کنند، یا فکر می‌کنند تعارض ممکن است به شانس ادغام شدن تغییرشان آسیب بزند.

    چند سیاست در یک workspace

    Cargo اجازه می‌دهد چند سیاست در یک workspace پشتیبانی شود.

    راستی‌آزمایی بسته‌های مشخص زیر نسخه‌های مشخص Rust می‌تواند پیچیده شود. ابزارهایی مانند cargo-hack می‌توانند کمک کنند.

    برای هر وابستگی که میان سیاست‌ها مشترک است، باید از کمترین نسخه‌های مشترک استفاده شود، زیرا Cargo نسخه‌های سازگار با SemVer را یکپارچه می‌کند و این ممکن است دسترسی عضو workspace با rust-version بالاتر را به featureهای وابستگی مشترک محدود کند.

    برای اینکه کاربران بتوانند یکی از اعضای workspace شما را به‌عنوان وابستگی وصله کنند، هر بستهٔ workspace باید در قدیمی‌ترین نسخهٔ Rust پشتیبانی‌شده توسط workspace قابل بارگذاری باشد.

    هنگام استفاده از incompatible-rust-versions = "fallback"، نسخهٔ Rust یک بسته می‌تواند بر نسخه‌های وابستگی انتخاب‌شده برای بستهٔ دیگری با نسخهٔ Rust متفاوت اثر بگذارد. برای جزئیات بیشتر، فصل resolver را ببینید.

    یک یا چند سیاست

    یکی از راه‌های کاهش معایب پشتیبانی از نسخه‌های قدیمی‌تر Rust این است که سیاست خود را روی نسخه‌های major یا minor قدیمی‌تر بستهٔ خود که همچنان پشتیبانی می‌کنید اعمال کنید. احتمالاً هنوز برای اینکه شاخهٔ توسعه چه نسخه‌هایی از Rust را پشتیبانی کند، در مقایسه با شاخه‌های انتشار آن نسخه‌های major یا minor، به یک سیاست نیاز دارید.

    به‌روزرسانی شاخهٔ توسعه فقط وقتی «لازم» است می‌تواند به کاهش تعداد شاخه‌های انتشار پشتیبانی‌شده کمک کند.

    این پرسش وجود دارد که چه چیزهایی را می‌توان به این شاخه‌های انتشار backport کرد. با backport کردن قابلیت‌های جدید میان نسخه‌های minor، نسخهٔ بعدیِ در دسترس آن را نخواهد داشت و این می‌تواند تغییری ناسازگار (breaking change) و نقض SemVer تلقی شود. backport کردن تغییرات همچنین خطر وارد شدن باگ را به همراه دارد.

    پشتیبانی از نسخه‌های قدیمی‌تر هزینه دارد. این هزینه به ریسک و تأثیر باگ‌ها در بسته و آنچه برای backport قابل‌قبول است بستگی دارد. ایجاد شاخه‌های انتشار در صورت نیاز و سپردن بار backport به جامعه راه‌هایی برای متعادل کردن این هزینه‌اند.

    هنوز راهی برای ابزارهای مدیریت وابستگی وجود ندارد که گزارش دهند نسخه‌ای غیر از جدیدترین هنوز پشتیبانی می‌شود، و این مسئولیت را به دوش کاربران می‌گذارد که این را در مستندات متوجه شوند.

    برای مثال، یک سیاست پشتیبانی از نسخهٔ Rust می‌تواند چنین باشد:

    • شاخهٔ توسعه جدیدترین انتشار پایدار پروژهٔ Rust را دنبال می‌کند و در صورت نیاز به‌روز می‌شود
      • هنگام تغییر rust-version، نسخهٔ minor افزایش می‌یابد
    • پروژه از هر نسخهٔ این سال تقویمی پشتیبانی می‌کند، با یک سال مهلت اضافی
      • آخرین نسخهٔ minor که از یک نسخهٔ پشتیبانی‌شدهٔ Rust پشتیبانی می‌کند، رفع باگ‌های ارائه‌شده توسط جامعه را دریافت می‌کند
      • رفع‌ها باید به همهٔ انتشارهای minor پشتیبانی‌شده میان شاخهٔ توسعه و نسخهٔ پشتیبانی‌شدهٔ Rust مورد نیاز backport شوند
