    Workspaceها

    یک workspace مجموعه‌ای از یک یا چند بسته است که اعضای workspace نامیده می‌شوند و با هم مدیریت می‌شوند.

    نکات کلیدی workspaceها عبارت‌اند از:

    • دستورهای رایج را می‌توان روی همهٔ اعضای workspace اجرا کرد، مانند cargo check --workspace.
    • همهٔ بسته‌ها یک فایل Cargo.lock مشترک دارند که در ریشهٔ workspace قرار دارد.
    • همهٔ بسته‌ها یک دایرکتوری خروجی مشترک دارند که به‌طور پیش‌فرض دایرکتوری‌ای به نام target در ریشهٔ workspace است.
    • اشتراک‌گذاری فرادادهٔ بسته، مانند workspace.package.
    • بخش‌های [patch]، [replace] و [profile.*] در Cargo.toml فقط در مانیفست ریشه شناخته می‌شوند و در مانیفست crateهای عضو نادیده گرفته می‌شوند.

    فایل Cargo.toml ریشهٔ یک workspace از بخش‌های زیر پشتیبانی می‌کند:

    • [workspace] — یک workspace را تعریف می‌کند.
      • resolver — حل‌کنندهٔ وابستگی (resolver) مورد استفاده را تعیین می‌کند.
      • members — بسته‌هایی که در workspace گنجانده می‌شوند.
      • exclude — بسته‌هایی که از workspace کنار گذاشته می‌شوند.
      • default-members — بسته‌هایی که وقتی بستهٔ مشخصی انتخاب نشده باشد روی آن‌ها عمل می‌شود.
      • package — کلیدهایی برای ارث‌بری در بسته‌ها.
      • dependencies — کلیدهایی برای ارث‌بری در وابستگی‌های بسته.
      • lints — کلیدهایی برای ارث‌بری در lintهای بسته.
      • metadata — تنظیمات اضافی برای ابزارهای خارجی.
    • [patch] — بازنویسی وابستگی‌ها.
    • [replace] — بازنویسی وابستگی‌ها (منسوخ‌شده).
    • [profile] — تنظیمات و بهینه‌سازی‌های کامپایلر.

    بخش [workspace]

    برای ایجاد یک workspace، جدول [workspace] را به یک Cargo.toml اضافه می‌کنید:

    [workspace]
# ...

    یک workspace دست‌کم باید یک عضو داشته باشد، یا با یک بستهٔ ریشه یا به‌صورت مانیفست مجازی.

    بستهٔ ریشه

    اگر بخش [workspace] به Cargo.tomlای اضافه شود که از قبل یک [package] تعریف کرده است، آن بسته بستهٔ ریشه workspace است. ریشهٔ workspace دایرکتوری‌ای است که Cargo.toml مربوط به workspace در آن قرار دارد.

    [workspace]

[package]
name = "hello_world" # the name of the package
version = "0.1.0"    # the current version, obeying semver

    Workspace مجازی

    به‌طور جایگزین، می‌توان یک فایل Cargo.toml با بخش [workspace] اما بدون بخش [package] ایجاد کرد. این را مانیفست مجازی می‌نامند. این روش معمولاً زمانی مفید است که «بستهٔ اصلی» وجود ندارد یا می‌خواهید همهٔ بسته‌ها را در دایرکتوری‌های جداگانه سازمان‌دهی کنید.

    # [PROJECT_DIR]/Cargo.toml
[workspace]
members = ["hello_world"]
resolver = "3"

    # [PROJECT_DIR]/hello_world/Cargo.toml
[package]
name = "hello_world" # the name of the package
version = "0.1.0"    # the current version, obeying semver
edition = "2024"     # the edition, will have no effect on a resolver used in the workspace

    با داشتن workspace بدون بستهٔ ریشه،

    • resolver باید در workspaceهای مجازی به‌صراحت تنظیم شود، زیرا آن‌ها package.edition ندارند تا نسخهٔ resolver از آن استنباط شود.
    • دستورهایی که در ریشهٔ workspace اجرا می‌شوند به‌طور پیش‌فرض روی همهٔ اعضای workspace اجرا می‌شوند؛ default-members را ببینید.

    فیلدهای members و exclude

    فیلدهای members و exclude مشخص می‌کنند کدام بسته‌ها عضو workspace هستند:

    [workspace]
members = ["member1", "path/to/member2", "crates/*"]
exclude = ["crates/foo", "path/to/other"]

    همهٔ وابستگی‌های path که در دایرکتوری workspace قرار دارند به‌طور خودکار عضو می‌شوند. اعضای اضافی را می‌توان با کلید members فهرست کرد، که باید آرایه‌ای از رشته‌ها شامل دایرکتوری‌هایی با فایل Cargo.toml باشد.

    فهرست members از globها نیز برای تطبیق چند مسیر پشتیبانی می‌کند و از الگوهای رایج glob نام فایل مانند * و ? استفاده می‌کند.

    Tip

    همهٔ بسته‌های عضو را در یک دایرکتوری تخت (معمولاً crates/) نگه دارید و برای فیلد members از الگوی glob استفاده کنید، مثلاً members = ["crates/*"]. این کار تغییرات لازم برای نگهداری فهرست members را به حداقل می‌رساند.

    کلید exclude را می‌توان برای جلوگیری از گنجانده‌شدن مسیرها در یک workspace به کار برد. این زمانی مفید است که برخی وابستگی‌های مسیری اصلاً نباید در workspace باشند، یا از الگوی glob استفاده می‌کنید و می‌خواهید یک دایرکتوری را حذف کنید.

    وقتی درون یک زیردایرکتوری از workspace هستید، Cargo به‌طور خودکار دایرکتوری‌های بالادست را برای یافتن یک فایل Cargo.toml دارای تعریف [workspace] جست‌وجو می‌کند تا مشخص کند از کدام workspace استفاده کند. کلید مانیفست package.workspace را می‌توان در crateهای عضو به کار برد تا به ریشهٔ یک workspace اشاره کند و این جست‌وجوی خودکار را بازنویسی کند. این تنظیم دستی زمانی مفید است که عضو درون یک زیردایرکتوری از ریشهٔ workspace نباشد.

    انتخاب بسته

    در یک workspace، دستورهای Cargo مرتبط با بسته مانند cargo build می‌توانند از پرچم‌های خط فرمان -p / --package یا --workspace استفاده کنند تا مشخص شود روی کدام بسته‌ها عمل شود. اگر هیچ‌یک از این پرچم‌ها مشخص نشده باشد، Cargo از بستهٔ موجود در دایرکتوری کاری فعلی استفاده می‌کند. اما اگر دایرکتوری فعلی ریشهٔ workspace باشد، از default-members استفاده می‌شود.

    فیلد default-members

    فیلد default-members مسیر اعضایی را مشخص می‌کند که هنگام قرار داشتن در ریشهٔ workspace و بدون استفاده از پرچم‌های انتخاب بسته روی آن‌ها عمل می‌شود:

    [workspace]
members = ["path/to/member1", "path/to/member2", "path/to/member3/*"]
default-members = ["path/to/member2", "path/to/member3/foo"]

    Note

    وقتی بستهٔ ریشه وجود دارد، فقط با پرچم‌های --package و --workspace می‌توانید روی آن عمل کنید.

    وقتی مشخص نشده باشد، از بستهٔ ریشه استفاده می‌شود. در مورد workspace مجازی، همهٔ اعضا استفاده می‌شوند (انگار --workspace در خط فرمان مشخص شده است).

    جدول package

    جدول workspace.package جایی است که کلیدهایی را تعریف می‌کنید که اعضای workspace می‌توانند آن‌ها را به ارث ببرند. این کلیدها را می‌توان با تعریف‌کردن آن‌ها در بستهٔ عضو به‌صورت {key}.workspace = true به ارث برد.

    کلیدهای پشتیبانی‌شده:
    authorscategories
    descriptiondocumentation
    editionexclude
    homepageinclude
    keywordslicense
    license-filepublish
    readmerepository
    rust-versionversion
    • license-file و readme نسبت به ریشهٔ workspace هستند
    • include و exclude نسبت به ریشهٔ بستهٔ شما هستند

    مثال:

    # [PROJECT_DIR]/Cargo.toml
[workspace]
members = ["bar"]

[workspace.package]
version = "1.2.3"
authors = ["Nice Folks"]
description = "A short description of my package"
documentation = "https://example.com/bar"

    # [PROJECT_DIR]/bar/Cargo.toml
[package]
name = "bar"
version.workspace = true
authors.workspace = true
description.workspace = true
documentation.workspace = true

    جدول dependencies

    جدول workspace.dependencies جایی است که وابستگی‌هایی را تعریف می‌کنید تا اعضای workspace آن‌ها را به ارث ببرند.

    مشخص‌کردن یک وابستگی workspace شبیه وابستگی‌های بسته است، با این تفاوت‌ها:

    • وابستگی‌های این جدول را نمی‌توان optional اعلام کرد
    • features اعلام‌شده در این جدول با features در [dependencies] جمع می‌شوند
    • default-features اعلام‌شده روی وابستگی یک بسته، مقدار تنظیم‌شده در اینجا را در بسته‌های Edition 2024 بازنویسی می‌کند (به Rust 1.99+ نیاز دارد). پیش از Rust 1.99 یا در editionهای قدیمی‌تر، ممکن است default-features = false در سطح بسته نادیده گرفته شود یا رد شود، مگر اینکه وابستگی workspace نیز ویژگی‌های پیش‌فرض را غیرفعال کرده باشد.

    سپس می‌توانید وابستگی workspace را به‌عنوان وابستگی بسته به ارث ببرید

    مثال:

    # [PROJECT_DIR]/Cargo.toml
[workspace]
members = ["bar"]

[workspace.dependencies]
cc = "1.0.73"
rand = "0.8.5"
regex = { version = "1.6.0", default-features = false, features = ["std"] }
serde = { version = "1.0.190", default-features = true }

    # [PROJECT_DIR]/bar/Cargo.toml
[package]
name = "bar"
version = "0.2.0"
edition = "2024"

[dependencies]
regex = { workspace = true, features = ["unicode"] }
serde = { workspace = true, default-features = false }

[build-dependencies]
cc.workspace = true

[dev-dependencies]
rand.workspace = true

    جدول lints

    جدول workspace.lints جایی است که پیکربندی lint را تعریف می‌کنید تا اعضای workspace آن را به ارث ببرند.

    مشخص‌کردن پیکربندی lint در workspace شبیه lintهای بسته است.

    مثال:

    # [PROJECT_DIR]/Cargo.toml
[workspace]
members = ["crates/*"]

[workspace.lints.rust]
unsafe_code = "forbid"

    # [PROJECT_DIR]/crates/bar/Cargo.toml
[package]
name = "bar"
version = "0.1.0"

[lints]
workspace = true

    MSRV: از 1.74 رعایت می‌شود

    جدول metadata

    جدول workspace.metadata توسط Cargo نادیده گرفته می‌شود و دربارهٔ آن هشداری داده نخواهد شد. این بخش را می‌توان برای ابزارهایی به کار برد که می‌خواهند پیکربندی workspace را در Cargo.toml ذخیره کنند. برای مثال:

    [workspace]
members = ["member1", "member2"]

[workspace.metadata.webcontents]
root = "path/to/webproject"
tool = ["npm", "run", "build"]
# ...

    مجموعه‌ای مشابه از جدول‌ها در سطح بسته در package.metadata وجود دارد. اگرچه cargo قالبی برای محتوای هیچ‌یک از این دو جدول تعیین نمی‌کند، پیشنهاد می‌شود ابزارهای خارجی از آن‌ها به شیوه‌ای یکدست استفاده کنند، مثلاً اگر داده‌ای در package.metadata وجود نداشت، به داده‌های workspace.metadata مراجعه کنند، البته اگر برای ابزار موردنظر منطقی باشد.
