    بازنویسی وابستگی‌ها

    نیاز به بازنویسی (override) یک وابستگی می‌تواند در سناریوهای متعددی پیش بیاید. اما بیشتر آن‌ها در نهایت به توانایی کار با یک crate پیش از انتشار آن در crates.io برمی‌گردند. برای مثال:

    • crateای که روی آن کار می‌کنید در یک برنامهٔ بسیار بزرگ‌تر هم که روی آن کار می‌کنید استفاده می‌شود و می‌خواهید یک رفع اشکال در کتابخانه را درون برنامهٔ بزرگ‌تر آزمایش کنید.
    • یک crate بالادستی که روی آن کار نمی‌کنید در شاخهٔ master مخزن git خود یک ویژگی جدید یا یک رفع اشکال دارد و می‌خواهید آن را امتحان کنید.
    • می‌خواهید یک نسخهٔ major جدید از crate خود را منتشر کنید، اما می‌خواهید آزمون یکپارچگی را روی کل یک بسته انجام دهید تا مطمئن شوید نسخهٔ major جدید کار می‌کند.
    • برای اشکالی که پیدا کرده‌اید، یک رفع اشکال به یک crate بالادستی ارسال کرده‌اید، اما می‌خواهید برنامه‌تان فوراً به نسخهٔ اصلاح‌شدهٔ crate وابسته شود تا منتظر ادغام شدن رفع اشکال نمانید.

    این سناریوها را می‌توان با بخش مانیفست [patch] حل کرد.

    این فصل چند مورد کاربرد مختلف را مرور می‌کند و جزئیات راه‌های مختلف بازنویسی یک وابستگی را شامل می‌شود.

    Note

    همچنین مشخص‌کردن یک وابستگی با چند مکان را ببینید، که می‌توان از آن برای بازنویسی منبع یک تعریف وابستگی واحد در یک بستهٔ محلی استفاده کرد.

    آزمایش یک رفع اشکال

    فرض کنید با crate uuid کار می‌کنید، اما هنگام کار با آن اشکالی کشف می‌کنید. شما بسیار پرتلاش هستید، پس تصمیم می‌گیرید سعی کنید اشکال را هم رفع کنید! در ابتدا مانیفست شما چنین به نظر می‌رسد:

    [package]
name = "my-library"
version = "0.1.0"

[dependencies]
uuid = "1.0"

    اولین کاری که می‌کنیم این است که مخزن uuid را به‌صورت محلی clone کنیم:

    $ git clone https://github.com/uuid-rs/uuid.git

    سپس مانیفست my-library را ویرایش می‌کنیم تا شامل این باشد:

    [patch.crates-io]
uuid = { path = "../path/to/uuid" }

    در اینجا اعلام می‌کنیم که منبع crates-io را با یک وابستگی جدید وصله (patch) می‌کنیم. این کار عملاً نسخهٔ checkout‌شدهٔ محلی uuid را به رجیستری crates.io برای بستهٔ محلی ما اضافه می‌کند.

    در مرحلهٔ بعد باید مطمئن شویم فایل قفل ما به‌روز شده تا از این نسخهٔ جدید uuid استفاده کند، تا بستهٔ ما به‌جای نسخهٔ crates.io از نسخهٔ checkout‌شدهٔ محلی استفاده کند. [patch] به این شکل کار می‌کند که وابستگی را در ../path/to/uuid بارگذاری می‌کند و سپس هرگاه از crates.io دربارهٔ نسخه‌های uuid پرس‌وجو شود، نسخهٔ محلی را نیز برمی‌گرداند.

    این یعنی شمارهٔ نسخهٔ checkout محلی اهمیت دارد و بر اینکه patch استفاده شود یا نه اثر می‌گذارد. مانیفست ما uuid = "1.0" را اعلام کرده است که یعنی فقط به >= 1.0.0, < 2.0.0 حل می‌شود و الگوریتم حل حریصانهٔ Cargo هم یعنی به بیشترین نسخه در آن بازه حل می‌شود. معمولاً این مهم نیست، چون نسخهٔ مخزن git از قبل بزرگ‌تر یا برابر با بیشترین نسخهٔ منتشرشده در crates.io است، اما مهم است که این را در نظر داشته باشید!

    به هر حال، معمولاً تنها کاری که اکنون باید بکنید این است:

    $ cargo build
   Compiling uuid v1.0.0 (.../uuid)
   Compiling my-library v0.1.0 (.../my-library)
    Finished dev [unoptimized + debuginfo] target(s) in 0.32 secs

    و تمام! اکنون با نسخهٔ محلی uuid ساخت می‌گیرید (به مسیر داخل پرانتز در خروجی ساخت توجه کنید). اگر نمی‌بینید که نسخهٔ مسیر محلی ساخته می‌شود، ممکن است لازم باشد cargo update uuid --precise $version را اجرا کنید که $version نسخهٔ کپی checkout‌شدهٔ محلی uuid است.

    پس از رفع اشکالی که در ابتدا پیدا کردید، کار بعدی که احتمالاً می‌خواهید بکنید این است که آن را به‌صورت یک pull request به خود crate uuid ارسال کنید. وقتی این کار را کردید، می‌توانید بخش [patch] را هم به‌روز کنید. فهرست درون [patch] درست مانند بخش [dependencies] است، پس وقتی pull request شما ادغام شد، می‌توانید وابستگی path خود را به این تغییر دهید:

    [patch.crates-io]
uuid = { git = 'https://github.com/uuid-rs/uuid.git' }

    کار با یک نسخهٔ minor منتشرنشده

    حالا از رفع اشکال به افزودن ویژگی برویم. هنگام کار روی my-library کشف می‌کنید که یک ویژگی کاملاً جدید در crate uuid لازم است. این ویژگی را پیاده‌سازی کرده‌اید، در بالا با [patch] به‌صورت محلی آزمایش کرده‌اید و یک pull request ارسال کرده‌اید. ببینیم چگونه می‌توانید پیش از انتشار واقعی آن را به کار ببرید و آزمایش کنید.

    فرض کنیم نسخهٔ فعلی uuid در crates.io برابر 1.0.0 است، اما از آن زمان شاخهٔ master مخزن git به 1.0.1 به‌روز شده است. این شاخه شامل ویژگی جدیدی است که قبلاً ارسال کرده‌اید. برای استفاده از این مخزن، Cargo.toml خود را طوری ویرایش می‌کنیم که چنین باشد

    [package]
name = "my-library"
version = "0.1.0"

[dependencies]
uuid = "1.0.1"

[patch.crates-io]
uuid = { git = 'https://github.com/uuid-rs/uuid.git' }

    توجه کنید که وابستگی محلی ما به uuid به 1.0.1 به‌روز شده است، زیرا پس از انتشار crate همین را واقعاً لازم خواهیم داشت. اما این نسخه در crates.io وجود ندارد، پس آن را با بخش [patch] مانیفست فراهم می‌کنیم.

    حالا وقتی کتابخانهٔ ما ساخته شود، uuid را از مخزن git واکشی می‌کند و به‌جای تلاش برای دانلود یک نسخه از crates.io، به 1.0.1 درون مخزن حل می‌شود. وقتی 1.0.1 در crates.io منتشر شد، می‌توان بخش [patch] را حذف کرد.

    همچنین شایان ذکر است که [patch] به‌صورت تعدی‌یافته اعمال می‌شود. فرض کنید از my-library در یک بستهٔ بزرگ‌تر استفاده می‌کنید، مثلاً:

    [package]
name = "my-binary"
version = "0.1.0"

[dependencies]
my-library = { git = 'https://example.com/git/my-library' }
uuid = "1.0"

[patch.crates-io]
uuid = { git = 'https://github.com/uuid-rs/uuid.git' }

    به یاد داشته باشید که [patch] به‌صورت تعدی‌یافته قابل اعمال است اما فقط می‌تواند در سطح بالا تعریف شود، پس مصرف‌کنندگان my-library در صورت لزوم باید بخش [patch] را تکرار کنند. اما در اینجا crate جدید uuid هم برای وابستگی ما به uuid و هم برای وابستگی my-library -> uuid اعمال می‌شود. crate uuid برای کل این گراف crate به یک نسخه حل می‌شود، یعنی 1.0.1، و از مخزن git گرفته می‌شود.

    بازنویسی URL مخزن

    اگر وابستگی‌ای که می‌خواهید بازنویسی کنید از crates.io بارگذاری نمی‌شود، باید نحوهٔ استفاده از [patch] را کمی تغییر دهید. برای مثال، اگر وابستگی یک وابستگی git باشد، می‌توانید آن را با این به یک مسیر محلی بازنویسی کنید:

    [patch."https://github.com/your/repository"]
my-library = { path = "../my-library/path" }

    و تمام!

    پیش‌انتشار یک تغییر ناسازگار

    ببینیم چگونه با یک نسخهٔ major جدید از یک crate کار کنیم که معمولاً با تغییرات ناسازگار همراه است. با ادامهٔ همان crateهای قبلی، یعنی می‌خواهیم نسخهٔ 2.0.0 از crate uuid را ایجاد کنیم. پس از ارسال همهٔ تغییرات به بالادست، می‌توانیم مانیفست my-library را طوری به‌روز کنیم که چنین باشد:

    [dependencies]
uuid = "2.0"

[patch.crates-io]
uuid = { git = "https://github.com/uuid-rs/uuid.git", branch = "2.0.0" }

    و تمام! مانند مثال قبلی، نسخهٔ 2.0.0 واقعاً در crates.io وجود ندارد، اما با استفاده از بخش [patch] همچنان می‌توانیم آن را از طریق یک وابستگی git وارد کنیم. به‌عنوان یک تمرین فکری، بیایید دوباره به مانیفست my-binary از بالا نیز نگاهی بیندازیم:

    [package]
name = "my-binary"
version = "0.1.0"

[dependencies]
my-library = { git = 'https://example.com/git/my-library' }
uuid = "1.0"

[patch.crates-io]
uuid = { git = 'https://github.com/uuid-rs/uuid.git', branch = '2.0.0' }

    توجه کنید که این در واقع به دو نسخه از crate uuid حل می‌شود. crate my-binary همچنان از سری 1.x.y مربوط به crate uuid استفاده می‌کند، اما crate my-library از نسخهٔ 2.0.0 مربوط به uuid استفاده خواهد کرد. این کار به شما امکان می‌دهد تغییرات ناسازگار یک crate را به‌تدریج در یک گراف وابستگی پیاده کنید، بدون آنکه مجبور باشید همه‌چیز را یک‌جا به‌روز کنید.

    استفاده از [patch] با چند نسخه

    می‌توانید چند نسخه از یک crate را با کلید package که برای تغییر نام وابستگی‌ها به کار می‌رود، وصله کنید. برای مثال فرض کنید crate serde یک رفع اشکال دارد که می‌خواهیم در سری 1.* آن استفاده کنیم، اما می‌خواهیم نمونه‌سازی با نسخهٔ 2.0.0 از serde را هم که در مخزن git خود داریم امتحان کنیم. برای پیکربندی این کار چنین می‌کنیم:

    [patch.crates-io]
serde = { git = 'https://github.com/serde-rs/serde.git' }
serde2 = { git = 'https://github.com/example/serde.git', package = 'serde', branch = 'v2' }

    دستور اول serde = ... نشان می‌دهد که serde 1.* باید از مخزن git استفاده شود (و رفع اشکال موردنیاز ما را وارد کند) و دستور دوم serde2 = ... نشان می‌دهد که بستهٔ serde باید از شاخهٔ v2 مخزن https://github.com/example/serde نیز گرفته شود. در اینجا فرض می‌کنیم که Cargo.toml در آن شاخه نسخهٔ 2.0.0 را ذکر می‌کند.

    توجه کنید که هنگام استفاده از کلید package، شناسهٔ serde2 در اینجا در واقع نادیده گرفته می‌شود. ما فقط به یک نام یکتا نیاز داریم که با crateهای وصله‌شدهٔ دیگر تداخل نداشته باشد.

    بخش [patch]

    بخش [patch] در Cargo.toml را می‌توان برای بازنویسی وابستگی‌ها با نسخه‌های دیگر به کار برد. نحو آن شبیه بخش [dependencies] است:

    [patch.crates-io]
foo = { git = 'https://github.com/example/foo.git' }
bar = { path = 'my/local/bar' }

[dependencies.baz]
git = 'https://github.com/example/baz.git'

[patch.'https://github.com/example/baz']
baz = { git = 'https://github.com/example/patched-baz.git', branch = 'my-branch' }

    Note

    جدول [patch] را می‌توان به‌صورت یک گزینهٔ پیکربندی نیز مشخص کرد، مثلاً در فایل .cargo/config.toml یا یک گزینهٔ CLI مانند --config 'patch.crates-io.rand.path="rand"'. این می‌تواند برای تغییرات صرفاً محلی که نمی‌خواهید commit کنید، یا آزمایش موقت یک patch مفید باشد.

    جدول [patch] از زیرجدول‌های شبیه وابستگی تشکیل شده است. هر کلید پس از [patch] یا URL منبعی است که وصله می‌شود، یا نام یک رجیستری. از نام crates-io می‌توان برای بازنویسی رجیستری پیش‌فرض crates.io استفاده کرد. نخستین [patch] در مثال بالا بازنویسی crates.io را نشان می‌دهد و [patch] دوم بازنویسی یک منبع git را.

    هر ورودی در این جدول‌ها یک مشخصهٔ وابستگی عادی است، مانند آنچه در بخش [dependencies] مانیفست می‌آید. وابستگی‌های فهرست‌شده در بخش [patch] حل می‌شوند و برای وصله‌کردن منبع در URL مشخص‌شده به کار می‌روند. قطعهٔ مانیفست بالا منبع crates-io (یعنی خود crates.io) را با crateهای foo و bar وصله می‌کند. همچنین منبع https://github.com/example/baz را با شاخهٔ my-branch که از جای دیگری می‌آید وصله می‌کند.

    منابع را می‌توان با نسخه‌هایی از crateها که وجود ندارند وصله کرد و همچنین با نسخه‌هایی که از قبل وجود دارند. اگر یک منبع با نسخه‌ای از crate که از قبل در منبع وجود دارد وصله شود، crate اصلی منبع جایگزین می‌شود.

    Cargo فقط به تنظیمات patch در مانیفست Cargo.toml در ریشهٔ workspace نگاه می‌کند. تنظیمات patch تعریف‌شده در وابستگی‌ها نادیده گرفته می‌شوند.

    بخش [replace]

    Important

    [replace] منسوخ شده است. باید به‌جای آن از جدول [patch] استفاده کنید.

    این بخش از Cargo.toml را می‌توان برای بازنویسی وابستگی‌ها با نسخه‌های دیگر به کار برد. نحو آن شبیه بخش [dependencies] است:

    [replace]
"foo:0.1.0" = { git = 'https://github.com/example/foo.git' }
"bar:1.0.2" = { path = 'my/local/bar' }

    هر کلید در جدول [replace] یک مشخصهٔ شناسهٔ بسته است که امکان انتخاب دلخواه یک گره در گراف وابستگی برای بازنویسی را می‌دهد (شمارهٔ نسخهٔ ۳ بخشی لازم است). مقدار هر کلید همان نحو [dependencies] برای مشخص‌کردن وابستگی‌هاست، با این تفاوت که نمی‌توانید feature مشخص کنید. توجه کنید که وقتی یک crate بازنویسی می‌شود، نسخه‌ای که با آن بازنویسی می‌شود باید هم نام و هم نسخهٔ یکسان داشته باشد، اما می‌تواند از منبع دیگری (مثلاً git یا یک مسیر محلی) بیاید.

    Cargo فقط به تنظیمات replace در مانیفست Cargo.toml در ریشهٔ workspace نگاه می‌کند. تنظیمات replace تعریف‌شده در وابستگی‌ها نادیده گرفته می‌شوند.

    بازنویسی‌های paths

    گاهی فقط موقتاً روی یک crate کار می‌کنید و نمی‌خواهید مثل بخش [patch] بالا Cargo.toml را تغییر دهید. برای این مورد Cargo نسخهٔ بسیار محدودتری از بازنویسی ارائه می‌دهد به نام بازنویسی مسیر (path override).

    بازنویسی‌های مسیر به‌جای Cargo.toml از طریق .cargo/config.toml مشخص می‌شوند. درون .cargo/config.toml کلیدی به نام paths مشخص می‌کنید:

    paths = ["/path/to/uuid"]

    این آرایه باید با دایرکتوری‌هایی پر شود که شامل Cargo.toml هستند. در این نمونه فقط uuid را اضافه می‌کنیم، پس تنها همان بازنویسی می‌شود. این مسیر می‌تواند مطلق یا نسبی به دایرکتوری‌ای باشد که پوشهٔ .cargo را در بر دارد.

    بازنویسی‌های مسیر محدودتر از بخش [patch] هستند، از این جهت که نمی‌توانند ساختار گراف وابستگی را تغییر دهند. وقتی جایگزینی مسیر استفاده می‌شود، مجموعهٔ قبلی وابستگی‌ها باید دقیقاً با مشخصات جدید Cargo.toml مطابقت داشته باشد. برای مثال این یعنی نمی‌توان از بازنویسی مسیر برای آزمودن افزودن یک وابستگی به یک crate استفاده کرد. در آن موقعیت باید از [patch] استفاده کرد. در نتیجه، استفاده از بازنویسی مسیر معمولاً به رفع اشکال‌های سریع محدود می‌شود، نه تغییرات بزرگ‌تر.

    Note

    استفاده از پیکربندی محلی برای بازنویسی مسیرها فقط برای crateهایی کار می‌کند که در crates.io منتشر شده‌اند. نمی‌توانید از این قابلیت برای نشان‌دادن محل crateهای محلی منتشرنشده به Cargo استفاده کنید.
