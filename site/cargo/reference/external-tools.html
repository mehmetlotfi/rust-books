    ابزارهای خارجی

    یکی از اهداف Cargo، یکپارچه‌سازی ساده با ابزارهای شخص ثالث مانند IDEها و دیگر سامانه‌های ساخت است. برای آسان‌تر کردن این یکپارچه‌سازی، Cargo چند امکان در اختیار می‌گذارد:

    • فرمان cargo metadata که اطلاعات ساختار بسته و وابستگی‌ها را با قالب JSON تولید می‌کند،

    • پرچم --message-format که اطلاعاتی دربارهٔ یک ساخت مشخص تولید می‌کند، و

    • پشتیبانی از زیرفرمان‌های سفارشی.

    اطلاعات دربارهٔ ساختار بسته

    می‌توانید از فرمان cargo metadata برای دریافت اطلاعات دربارهٔ ساختار بسته و وابستگی‌ها استفاده کنید. برای جزئیات قالب خروجی، مستندات cargo metadata را ببینید.

    این قالب پایدار و نسخه‌دار است. هنگام فراخوانی cargo metadata باید پرچم --format-version را به‌صراحت بدهید تا از خطر ناسازگاری با نسخه‌های آینده جلوگیری شود.

    اگر از Rust استفاده می‌کنید، می‌توانید از crate با نام cargo_metadata برای تجزیهٔ خروجی بهره ببرید.

    پیام‌های JSON

    وقتی --message-format=json را می‌دهید، Cargo در طول ساخت، اطلاعات زیر را تولید می‌کند:

    • خطاها و هشدارهای کامپایلر،

    • artifactهای تولیدشده،

    • نتایج build scriptها (برای مثال، وابستگی‌های بومی).

    خروجی به stdout و با قالب «یک شیء JSON در هر خط» ارسال می‌شود. فیلد reason انواع مختلف پیام‌ها را از هم متمایز می‌کند. فیلد package_id شناسه‌ای یکتا برای ارجاع به بسته است و در بسیاری از فرمان‌ها به‌عنوان آرگومان --package نیز به کار می‌رود. گرامر این نحو را می‌توانید در فصل مشخصات شناسهٔ بسته بیابید.

    Note

    --message-format=json فقط خروجی Cargo و Rustc را کنترل می‌کند. این گزینه نمی‌تواند خروجی ابزارهای دیگر را کنترل کند، مثلاً cargo run --message-format=json، یا خروجی دلبخواه ماکروهای رویه‌ای. راه‌حل ممکن در این موارد این است که هر خط را فقط وقتی با { شروع می‌شود به‌عنوان JSON تفسیر کنید.

    گزینهٔ --message-format می‌تواند مقادیر قالب‌بندی اضافی نیز بپذیرد که شیوهٔ محاسبه و نمایش پیام‌های JSON را تغییر می‌دهند. برای جزئیات بیشتر، توضیح گزینهٔ --message-format را در مستندات فرمان build ببینید.

    اگر از Rust استفاده می‌کنید، می‌توانید از crate با نام cargo_metadata برای تجزیهٔ این پیام‌ها بهره ببرید.

    MSRV: برای اینکه package_id یک مشخصهٔ شناسهٔ بسته (Package ID Specification) باشد، نسخهٔ 1.77 لازم است. پیش از آن، این مقدار مبهم (opaque) بود.

    پیام‌های کامپایلر

    پیام «compiler-message» شامل خروجی کامپایلر، مانند هشدارها و خطاهاست. برای جزئیات قالب پیام rustc که در ساختار زیر جاسازی شده است، فصل JSON در rustc را ببینید:

    {
    /* The "reason" indicates the kind of message. */
    "reason": "compiler-message",
    /* The Package ID, a unique identifier for referring to the package. */
    "package_id": "file:///path/to/my-package#0.1.0",
    /* Absolute path to the package manifest. */
    "manifest_path": "/path/to/my-package/Cargo.toml",
    /* The Cargo target (lib, bin, example, etc.) that generated the message. */
    "target": {
        /* Array of target kinds.
           - lib targets list the `crate-type` values from the
             manifest such as "lib", "rlib", "dylib",
             "proc-macro", etc. (default ["lib"])
           - binary is ["bin"]
           - example is ["example"]
           - integration test is ["test"]
           - benchmark is ["bench"]
           - build script is ["custom-build"]
        */
        "kind": [
            "lib"
        ],
        /* Array of crate types.
           - lib and example libraries list the `crate-type` values
             from the manifest such as "lib", "rlib", "dylib",
             "proc-macro", etc. (default ["lib"])
           - all other target kinds are ["bin"]
        */
        "crate_types": [
            "lib"
        ],
        /* The name of the target.
           For lib targets, dashes will be replaced with underscores.
        */
        "name": "my_package",
        /* Absolute path to the root source file of the target. */
        "src_path": "/path/to/my-package/src/lib.rs",
        /* The Rust edition of the target.
           Defaults to the package edition.
        */
        "edition": "2018",
        /* Array of required features.
           This property is not included if no required features are set.
        */
        "required-features": ["feat1"],
        /* Whether the target should be documented by `cargo doc`. */
        "doc": true,
        /* Whether or not this target has doc tests enabled, and
           the target is compatible with doc testing.
        */
        "doctest": true
        /* Whether or not this target should be built and run with `--test`
        */
        "test": true
    },
    /* The message emitted by the compiler.

    See https://doc.rust-lang.org/rustc/json.html for details.
    */
    "message": {
        /* ... */
    }
}

    پیام‌های artifact

    برای هر مرحلهٔ کامپایل، یک پیام «compiler-artifact» با ساختار زیر صادر می‌شود:

    {
    /* The "reason" indicates the kind of message. */
    "reason": "compiler-artifact",
    /* The Package ID, a unique identifier for referring to the package. */
    "package_id": "file:///path/to/my-package#0.1.0",
    /* Absolute path to the package manifest. */
    "manifest_path": "/path/to/my-package/Cargo.toml",
    /* The Cargo target (lib, bin, example, etc.) that generated the artifacts.
       See the definition above for `compiler-message` for details.
    */
    "target": {
        "kind": [
            "lib"
        ],
        "crate_types": [
            "lib"
        ],
        "name": "my_package",
        "src_path": "/path/to/my-package/src/lib.rs",
        "edition": "2018",
        "doc": true,
        "doctest": true,
        "test": true
    },
    /* The profile indicates which compiler settings were used. */
    "profile": {
        /* The optimization level. */
        "opt_level": "0",
        /* The debug level, an integer of 0, 1, or 2, or a string
           "line-directives-only" or "line-tables-only". If `null`, it implies
           rustc's default of 0.
        */
        "debuginfo": 2,
        /* Whether or not debug assertions are enabled. */
        "debug_assertions": true,
        /* Whether or not overflow checks are enabled. */
        "overflow_checks": true,
        /* Whether or not the `--test` flag is used. */
        "test": false
    },
    /* Array of features enabled. */
    "features": ["feat1", "feat2"],
    /* Array of files generated by this step. */
    "filenames": [
        "/path/to/my-package/target/debug/libmy_package.rlib",
        "/path/to/my-package/target/debug/deps/libmy_package-be9f3faac0a26ef0.rmeta"
    ],
    /* A string of the path to the executable that was created, or null if
       this step did not generate an executable.
    */
    "executable": null,
    /* Whether or not this step was actually executed.
       When `true`, this means that the pre-existing artifacts were
       up-to-date, and `rustc` was not executed. When `false`, this means that
       `rustc` was run to generate the artifacts.
    */
    "fresh": true
}

    خروجی build script

    پیام «build-script-executed» شامل خروجی تجزیه‌شدهٔ یک build script است. توجه کنید که این پیام حتی وقتی build script اجرا نشود نیز صادر می‌شود؛ در این حالت مقدار ذخیره‌شدهٔ قبلی را نمایش می‌دهد. جزئیات بیشتر دربارهٔ خروجی build script را می‌توانید در فصل مربوط به build scriptها بیابید.

    {
    /* The "reason" indicates the kind of message. */
    "reason": "build-script-executed",
    /* The Package ID, a unique identifier for referring to the package. */
    "package_id": "file:///path/to/my-package#0.1.0",
    /* Array of libraries to link, as indicated by the `cargo::rustc-link-lib`
       instruction. Note that this may include a "KIND=" prefix in the string
       where KIND is the library kind.
    */
    "linked_libs": ["foo", "static=bar"],
    /* Array of paths to include in the library search path, as indicated by
       the `cargo::rustc-link-search` instruction. Note that this may include a
       "KIND=" prefix in the string where KIND is the library kind.
    */
    "linked_paths": ["/some/path", "native=/another/path"],
    /* Array of cfg values to enable, as indicated by the `cargo::rustc-cfg`
       instruction.
    */
    "cfgs": ["cfg1", "cfg2=\"string\""],
    /* Array of [KEY, VALUE] arrays of environment variables to set, as
       indicated by the `cargo::rustc-env` instruction.
    */
    "env": [
        ["SOME_KEY", "some value"],
        ["ANOTHER_KEY", "another value"]
    ],
    /* An absolute path which is used as a value of `OUT_DIR` environmental
       variable when compiling current package.
    */
    "out_dir": "/some/path/in/target/dir"
}

    پایان ساخت

    پیام «build-finished» در پایان ساخت صادر می‌شود.

    {
    /* The "reason" indicates the kind of message. */
    "reason": "build-finished",
    /* Whether or not the build finished successfully. */
    "success": true,
}

    این پیام می‌تواند به ابزارها کمک کند تا بدانند چه زمانی خواندن پیام‌های JSON را متوقف کنند. فرمان‌هایی مانند cargo test یا cargo run ممکن است پس از پایان ساخت خروجی بیشتری تولید کنند. این پیام به ابزار می‌فهماند که Cargo دیگر پیام JSON تولید نخواهد کرد، اما ممکن است پس از آن خروجی اضافی دیگری تولید شود (مانند خروجی برنامه‌ای که با cargo run اجرا می‌شود).

    Note

    پشتیبانی آزمایشی و مختص nightly برای خروجی JSON آزمون‌ها وجود دارد، بنابراین اگر این قابلیت فعال باشد، ممکن است پیام‌های JSON اختصاصی آزمون پس از پیام «build-finished» نیز دریافت شوند.

    زیرفرمان‌های سفارشی

    Cargo طوری طراحی شده است که بتوان بدون تغییر دادن خود Cargo، زیرفرمان‌های جدیدی به آن افزود. این کار با تبدیل فراخوانی cargo به شکل cargo (?<command>[^ ]+) به فراخوانی ابزار خارجی cargo-${command} انجام می‌شود. ابزار خارجی باید در یکی از پوشه‌های $PATH کاربر وجود داشته باشد.

    Note

    Cargo به‌طور پیش‌فرض ابزارهای خارجی موجود در $CARGO_HOME/bin را بر $PATH ترجیح می‌دهد. کاربران می‌توانند با افزودن $CARGO_HOME/bin به $PATH این اولویت را تغییر دهند.

    وقتی Cargo یک زیرفرمان سفارشی را فراخوانی می‌کند، آرگومان اول زیرفرمان، طبق معمول، نام فایل همان زیرفرمان سفارشی است. آرگومان دوم خود نام زیرفرمان است. برای مثال، هنگام فراخوانی cargo-${command}، آرگومان دوم ${command} خواهد بود. هر آرگومان اضافی در خط فرمان بدون تغییر منتقل می‌شود.

    Cargo همچنین می‌تواند خروجی راهنمای یک زیرفرمان سفارشی را با cargo help ${command} نمایش دهد. Cargo فرض می‌کند که اگر آرگومان سوم زیرفرمان --help باشد، آن زیرفرمان یک پیام راهنما چاپ خواهد کرد. بنابراین cargo help ${command} عملاً cargo-${command} ${command} --help را فراخوانی می‌کند.

    زیرفرمان‌های سفارشی می‌توانند با استفاده از متغیر محیطی CARGO دوباره Cargo را فراخوانی کنند. همچنین می‌توانند crate با نام cargo را به‌عنوان کتابخانه پیوند دهند، اما این رویکرد معایبی دارد:

    • Cargo به‌عنوان کتابخانه ناپایدار است: ممکن است API بدون اعلام منسوخ‌شدن تغییر کند
    • نسخه‌های کتابخانهٔ Cargo پیوندشده ممکن است با نسخهٔ فایل اجرایی Cargo متفاوت باشند

    در عوض توصیه می‌شود برای هدایت Cargo از رابط خط فرمان (CLI) استفاده شود. فرمان cargo metadata را می‌توان برای دریافت اطلاعات دربارهٔ پروژهٔ جاری به کار برد (crate با نام cargo_metadata یک رابط Rust برای این فرمان فراهم می‌کند).
