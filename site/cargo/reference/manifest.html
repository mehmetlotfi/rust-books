    قالب Manifest

    فایل Cargo.toml هر بسته، manifest آن بسته نامیده می‌شود. این فایل با قالب TOML نوشته می‌شود و شامل فراداده‌ای است که برای کامپایل بسته لازم است. برای جزئیات بیشتر دربارهٔ اینکه cargo چگونه فایل manifest را پیدا می‌کند، بخش cargo locate-project را ببینید.

    هر فایل manifest از بخش‌های زیر تشکیل می‌شود:

    • cargo-features — featureهای ناپایدار که فقط در nightly در دسترس‌اند.
    • [package] — یک بسته را تعریف می‌کند.
      • name — نام بسته.
      • version — نسخهٔ بسته.
      • authors — نویسندگان بسته.
      • edition — ویرایش Rust.
      • rust-version — حداقل نسخهٔ پشتیبانی‌شدهٔ Rust.
      • description — توضیحی دربارهٔ بسته.
      • documentation — URL مستندات بسته.
      • readme — مسیر فایل README بسته.
      • homepage — URL صفحهٔ اصلی بسته.
      • repository — URL مخزن سورس بسته.
      • license — مجوز بسته.
      • license-file — مسیر متن مجوز.
      • keywords — کلیدواژه‌های بسته.
      • categories — دسته‌بندی‌های بسته.
      • workspace — مسیر workspace بسته.
      • build — مسیر اسکریپت ساخت بسته.
      • links — نام کتابخانهٔ بومی که بسته با آن پیوند می‌خورد.
      • exclude — فایل‌هایی که هنگام انتشار کنار گذاشته می‌شوند.
      • include — فایل‌هایی که هنگام انتشار گنجانده می‌شوند.
      • publish — می‌تواند برای جلوگیری از انتشار بسته به کار رود.
      • metadata — تنظیمات اضافی برای ابزارهای خارجی.
      • default-run — فایل اجرایی پیش‌فرضی که cargo run اجرا می‌کند.
      • autolib — کشف خودکار کتابخانه را غیرفعال می‌کند.
      • autobins — کشف خودکار فایل‌های اجرایی را غیرفعال می‌کند.
      • autoexamples — کشف خودکار مثال‌ها را غیرفعال می‌کند.
      • autotests — کشف خودکار آزمون‌ها را غیرفعال می‌کند.
      • autobenches — کشف خودکار بنچمارک‌ها را غیرفعال می‌کند.
      • resolver — حل‌کنندهٔ وابستگی‌ای را که باید استفاده شود تعیین می‌کند.
    • جدول‌های هدف: (برای تنظیمات، پیکربندی را ببینید)
      • [lib] — تنظیمات هدف کتابخانه.
      • [[bin]] — تنظیمات هدف فایل اجرایی.
      • [[example]] — تنظیمات هدف مثال.
      • [[test]] — تنظیمات هدف آزمون.
      • [[bench]] — تنظیمات هدف بنچمارک.
    • جدول‌های وابستگی:
      • [dependencies] — وابستگی‌های کتابخانه‌ای بسته.
      • [dev-dependencies] — وابستگی‌های مثال‌ها، آزمون‌ها و بنچمارک‌ها.
      • [build-dependencies] — وابستگی‌های اسکریپت‌های ساخت.
      • [target] — وابستگی‌های مختص پلتفرم.
    • [badges] — نشان‌هایی (badge) که در یک رجیستری نمایش داده می‌شوند.
    • [features] — featureهای کامپایل شرطی.
    • [lints] — پیکربندی linterها برای این بسته.
    • [hints] — ارائهٔ راهنما (hint) برای کامپایل این بسته.
    • [patch] — بازنویسی وابستگی‌ها.
    • [replace] — بازنویسی وابستگی‌ها (منسوخ).
    • [profile] — تنظیمات و بهینه‌سازی‌های کامپایلر.
    • [workspace] — تعریف workspace.

    بخش [package]

    اولین بخش در Cargo.toml بخش [package] است.

    [package]
name = "hello_world" # the name of the package
version = "0.1.0"    # the current version, obeying semver

    تنها فیلدی که Cargo الزاماً می‌خواهد name است. اگر بسته را در یک رجیستری منتشر می‌کنید، ممکن است آن رجیستری فیلدهای اضافی دیگری هم بخواهد. برای الزامات انتشار در crates.io، یادداشت‌های زیر و فصل انتشار را ببینید.

    فیلد name

    نام بسته شناسه‌ای است که برای ارجاع به بسته به کار می‌رود. این نام هنگامی که بسته به‌عنوان وابستگی در بستهٔ دیگری فهرست می‌شود، و همچنین به‌عنوان نام پیش‌فرض هدف‌های lib و bin استنتاج‌شده استفاده می‌شود.

    نام فقط باید از نویسه‌های الفبایی‌عددی یا - یا _ تشکیل شده باشد و نمی‌تواند خالی باشد.

    توجه کنید که cargo new و cargo init محدودیت‌های اضافی‌ای بر نام بسته اعمال می‌کنند، مانند اینکه نام باید شناسهٔ معتبر Rust باشد و کلیدواژه نباشد. crates.io محدودیت‌های بیشتری هم اعمال می‌کند، از جمله:

    • فقط نویسه‌های ASCII مجاز هستند.
    • از نام‌های رزروشده استفاده نکنید.
    • از نام‌های ویژهٔ ویندوز مانند “nul” استفاده نکنید.
    • حداکثر طول نام ۶۴ نویسه است.

    فیلد version

    فیلد version طبق مشخصات SemVer قالب‌بندی می‌شود:

    نسخه‌ها باید سه بخش عددی داشته باشند: نسخهٔ اصلی (major)، نسخهٔ فرعی (minor) و نسخهٔ وصله (patch).

    پس از یک خط تیره می‌توان بخش پیش‌انتشار (pre-release) افزود، مانند 1.0.0-alpha. بخش پیش‌انتشار را می‌توان با نقطه جدا کرد تا مؤلفه‌های جداگانه از هم متمایز شوند. مؤلفه‌های عددی با مقایسهٔ عددی و بقیهٔ مؤلفه‌ها به‌صورت واژه‌نامه‌ای (lexicographic) مقایسه می‌شوند. برای مثال، 1.0.0-alpha.11 از 1.0.0-alpha.4 بزرگ‌تر است.

    پس از یک علامت جمع می‌توان بخش فراداده (metadata) افزود، مانند 1.0.0+21AF26D3. این بخش فقط جنبهٔ اطلاع‌رسانی دارد و Cargo عموماً آن را نادیده می‌گیرد.

    Cargo مفهوم نسخه‌گذاری معنایی را در خود جای داده است، بنابراین اگر چپ‌ترین مؤلفهٔ ناصفر از major/minor/patch دو نسخه یکسان باشد، آن دو نسخه سازگار به شمار می‌روند. برای اطلاعات بیشتر دربارهٔ اینکه Cargo چگونه از نسخه‌ها برای حل وابستگی‌ها استفاده می‌کند، فصل Resolver را ببینید.

    این فیلد اختیاری است و پیش‌فرض آن 0.0.0 است. این فیلد برای انتشار بسته‌ها الزامی است.

    MSRV: پیش از 1.75 این فیلد الزامی بود

    فیلد authors

    Important

    این فیلد منسوخ شده است.

    فیلد اختیاری authors در قالب یک آرایه، افراد یا سازمان‌هایی را فهرست می‌کند که «نویسندگان» بسته به شمار می‌روند. در انتهای هر ورودی نویسنده می‌توان یک نشانی ایمیل اختیاری را درون کروشهٔ زاویه‌ای (< و >) قرار داد.

    [package]
# ...
authors = ["Graydon Hoare", "Fnu Lnu <no-reply@rust-lang.org>"]

    این فیلد برای سازگاری با نسخه‌های قدیمی‌تر در فراداده‌های بسته و در متغیر محیطی CARGO_PKG_AUTHORS درون build.rs در دسترس قرار می‌گیرد.

    فیلد edition

    کلید edition کلیدی اختیاری است که تعیین می‌کند بستهٔ شما با کدام edition زبان Rust کامپایل شود. تنظیم کلید edition در [package] بر همهٔ هدف‌ها/crateهای بسته، از جمله مجموعه‌های آزمون، بنچمارک‌ها، فایل‌های اجرایی، مثال‌ها و غیره اثر می‌گذارد.

    [package]
# ...
edition = '2024'

    در بیشتر manifestها فیلد edition به‌طور خودکار توسط cargo new با جدیدترین edition پایدار پر می‌شود. در حال حاضر cargo new به‌طور پیش‌فرض manifestی با edition 2024 ایجاد می‌کند.

    اگر فیلد edition در Cargo.toml وجود نداشته باشد، برای سازگاری با نسخه‌های قدیمی‌تر فرض می‌شود که edition 2015 مورد نظر است. توجه کنید که همهٔ manifestهایی که با cargo new ایجاد شده‌اند از این حالت بازگشتی تاریخی استفاده نمی‌کنند، زیرا edition در آن‌ها به‌طور صریح روی مقداری جدیدتر تنظیم شده است.

    فیلد rust-version

    فیلد rust-version به cargo می‌گوید که بستهٔ شما از کدام نسخهٔ toolchain زبان Rust پشتیبانی می‌کند. برای جزئیات بیشتر فصل نسخهٔ Rust را ببینید.

    فیلد description

    توضیح (description) یک معرفی کوتاه دربارهٔ بسته است. crates.io آن را همراه با بستهٔ شما نمایش می‌دهد. این متن باید ساده (plain text) باشد، نه Markdown.

    [package]
# ...
description = "A short description of my package"

    Note

    (https://crates.io/) الزام می‌کند که description تنظیم شده باشد.

    فیلد documentation

    فیلد documentation یک URL به وب‌سایتی را مشخص می‌کند که مستندات crate را میزبانی می‌کند. اگر در فایل manifest هیچ URLای مشخص نشده باشد، crates.io پس از اینکه مستندات ساخته شد و در دسترس قرار گرفت، به‌طور خودکار crate شما را به صفحهٔ متناظر در docs.rs پیوند می‌دهد (به صف docs.rs نگاه کنید).

    [package]
# ...
documentation = "https://docs.rs/bitflags"

    فیلد readme

    فیلد readme باید مسیر فایلی در ریشهٔ بسته (نسبت به همین Cargo.toml) باشد که اطلاعات کلی دربارهٔ بسته را در بر دارد. این فایل هنگام انتشار به رجیستری منتقل می‌شود. crates.io آن را به‌صورت Markdown تفسیر می‌کند و در صفحهٔ crate نمایش می‌دهد.

    [package]
# ...
readme = "README.md"

    اگر برای این فیلد مقداری مشخص نشده باشد و فایلی با نام README.md، README.txt یا README در ریشهٔ بسته وجود داشته باشد، نام همان فایل استفاده خواهد شد. با تنظیم این فیلد روی false می‌توانید این رفتار را غیرفعال کنید. اگر فیلد روی true تنظیم شود، مقدار پیش‌فرض README.md در نظر گرفته می‌شود.

    فیلد homepage

    فیلد homepage باید URL سایتی باشد که صفحهٔ اصلی بستهٔ شماست.

    [package]
# ...
homepage = "https://serde.rs"

    فقط در صورتی باید برای homepage مقدار تعیین شود که برای crate یک وب‌سایت اختصاصی، غیر از مخزن سورس یا مستندات API، وجود داشته باشد. homepage را با مقادیر documentation یا repository تکراری نکنید.

    فیلد repository

    فیلد repository باید URL مخزن سورس بستهٔ شما باشد.

    [package]
# ...
repository = "https://github.com/rust-lang/cargo"

    فیلدهای license و license-file

    فیلد license نام مجوز نرم‌افزاری را که بسته تحت آن منتشر شده است در بر دارد. فیلد license-file مسیر فایلی را که متن مجوز در آن است (نسبت به همین Cargo.toml) در بر دارد.

    crates.io فیلد license را به‌عنوان عبارت مجوز SPDX 2.3 تفسیر می‌کند. نام باید یکی از مجوزهای شناخته‌شده در فهرست مجوزهای SPDX نسخهٔ 3.20 باشد. برای اطلاعات بیشتر سایت SPDX را ببینید.

    عبارت‌های مجوز SPDX از عملگرهای AND و OR برای ترکیب چند مجوز پشتیبانی می‌کنند.1

    [package]
# ...
license = "MIT OR Apache-2.0"

    استفاده از OR نشان می‌دهد که کاربر می‌تواند هر یک از دو مجوز را برگزیند. استفاده از AND نشان می‌دهد که کاربر باید هم‌زمان از هر دو مجوز پیروی کند. عملگر WITH مجوزی را نشان می‌دهد که استثنای ویژه‌ای دارد. چند نمونه:

    • MIT OR Apache-2.0
    • LGPL-2.1-only AND MIT AND BSD-2-Clause
    • GPL-2.0-or-later WITH Bison-exception-2.2

    اگر بسته از مجوزی غیراستاندارد استفاده می‌کند، می‌توان به‌جای فیلد license فیلد license-file را مشخص کرد.

    [package]
# ...
license-file = "LICENSE.txt"

    Note

    (https://crates.io/) الزام می‌کند که یکی از license یا license-file تنظیم شده باشد.

    فیلد keywords

    فیلد keywords آرایه‌ای از رشته‌هاست که این بسته را توصیف می‌کنند. این فیلد می‌تواند هنگام جست‌وجوی بسته در یک رجیستری کمک کند، و می‌توانید هر واژه‌ای را که به کسی در یافتن این crate کمک می‌کند انتخاب کنید.

    [package]
# ...
keywords = ["gamedev", "graphics"]

    Note

    (https://crates.io/) حداکثر ۵ کلیدواژه را مجاز می‌داند. هر کلیدواژه باید متن ASCII باشد، حداکثر ۲۰ نویسه داشته باشد، با یک نویسهٔ الفبایی‌عددی شروع شود و فقط شامل حروف، ارقام، _، - یا + باشد.

    فیلد categories

    فیلد categories آرایه‌ای از رشته‌هاست که دسته‌بندی‌های مربوط به این بسته را مشخص می‌کنند.

    categories = ["command-line-utilities", "development-tools::cargo-plugins"]

    Note

    (https://crates.io/) حداکثر ۵ دسته‌بندی را مجاز می‌داند. هر دسته‌بندی باید با یکی از رشته‌های موجود در https://crates.io/category_slugs مطابقت داشته باشد و این تطابق باید دقیق باشد.

    فیلد workspace

    فیلد workspace را می‌توان برای پیکربندی workspaceای به کار برد که این بسته عضوی از آن خواهد بود. اگر مشخص نشود، workspace به‌صورت اولین Cargo.toml حاوی [workspace] در مسیرهای بالاتر فایل‌سیستم استنتاج می‌شود. تنظیم این فیلد زمانی مفید است که عضو در زیرشاخه‌ای از ریشهٔ workspace قرار نداشته باشد.

    [package]
# ...
workspace = "path/to/workspace/root"

    اگر manifest از قبل جدول [workspace] را تعریف کرده باشد، این فیلد را نمی‌توان مشخص کرد. یعنی یک crate نمی‌تواند هم‌زمان crate ریشهٔ یک workspace (دارای [workspace]) و هم crate عضو workspace دیگری (دارای package.workspace) باشد.

    برای اطلاعات بیشتر فصل workspaceها را ببینید.

    فیلد build

    فیلد build فایلی را در ریشهٔ بسته مشخص می‌کند که یک اسکریپت ساخت برای ساخت کد بومی است. اطلاعات بیشتر را می‌توان در راهنمای اسکریپت ساخت یافت.

    [package]
# ...
build = "build.rs"

    مقدار پیش‌فرض "build.rs" است که اسکریپت را از فایلی به نام build.rs در ریشهٔ بسته بارگذاری می‌کند. برای تعیین مسیر فایلی دیگر از build = "custom_build_name.rs" و برای غیرفعال کردن تشخیص خودکار اسکریپت ساخت از build = false استفاده کنید.

    فیلد links

    فیلد links نام کتابخانهٔ بومی‌ای را مشخص می‌کند که با آن پیوند داده می‌شود. اطلاعات بیشتر را می‌توان در بخش links راهنمای اسکریپت ساخت یافت.

    برای مثال، crateای که با کتابخانهٔ بومی‌ای به نام “git2” (مثلاً libgit2.a در لینوکس) پیوند می‌خورد می‌تواند این را مشخص کند:

    [package]
# ...
links = "git2"

    فیلدهای exclude و include

    فیلدهای exclude و include را می‌توان برای تعیین صریح این به کار برد که هنگام بسته‌بندی یک پروژه برای انتشار و همچنین برای برخی انواع ردیابی تغییرات (که در ادامه توضیح داده می‌شود) کدام فایل‌ها گنجانده شوند. الگوهای مشخص‌شده در فیلد exclude مجموعه‌ای از فایل‌ها را که گنجانده نمی‌شوند معرفی می‌کنند، و الگوهای include فایل‌هایی را که صریحاً گنجانده می‌شوند مشخص می‌کنند.

    [package]
# ...
exclude = ["/ci", "images/", ".*"]

    [package]
# ...
include = ["/src", "COPYRIGHT", "/examples", "!/examples/big_example"]

    Note

    برای اطمینان از اینکه کدام فایل‌ها در بسته گنجانده خواهند شد، cargo package --list را اجرا کنید.

    اگر هیچ‌یک از دو فیلد مشخص نشده باشد، پیش‌فرض این است که همهٔ فایل‌های ریشهٔ بسته گنجانده شوند، به جز استثناهایی که در ادامه فهرست شده‌اند.

    اگر include مشخص نشده باشد، فایل‌های زیر کنار گذاشته می‌شوند:

    • اگر بسته در یک مخزن git نباشد، همهٔ فایل‌های «پنهان» که با نقطه شروع می‌شوند نادیده گرفته می‌شوند.
    • اگر بسته در یک مخزن git باشد، هر فایلی که قواعد gitignore مخزن و پیکربندی سراسری git آن را نادیده می‌گیرند، کنار گذاشته می‌شود.

    اگر include مشخص شده باشد، قواعد gitignore مخزن و پیکربندی سراسری git اعمال نمی‌شوند.

    صرف‌نظر از اینکه exclude یا include مشخص شده باشد، فایل‌های زیر همیشه کنار گذاشته می‌شوند:

    • هر زیربسته‌ای نادیده گرفته می‌شود (هر زیرشاخه‌ای که فایل Cargo.toml داشته باشد).
    • شاخه‌ای به نام target در ریشهٔ بسته نادیده گرفته می‌شود.

    فایل‌های زیر همیشه گنجانده می‌شوند:

    • فایل Cargo.toml خود بسته همیشه گنجانده می‌شود و لازم نیست در include فهرست شود.
    • یک Cargo.lock کمینه‌شده به‌طور خودکار گنجانده می‌شود. برای اطلاعات بیشتر cargo package را ببینید.
    • اگر license-file مشخص شده باشد، همیشه گنجانده می‌شود.

    این گزینه‌ها دوبه‌دو ناسازگارند؛ تنظیم include بر exclude غلبه می‌کند. اگر لازم است برای مجموعه‌ای از فایل‌های include استثناهایی داشته باشید، از عملگر ! که در ادامه توضیح داده شده است استفاده کنید.

    الگوها باید الگوهای به سبک gitignore باشند. به‌طور خلاصه:

    • foo با هر فایل یا شاخه‌ای که نامش foo باشد، در هر جای بسته، مطابقت دارد. این معادل الگوی **/foo است.
    • /foo فقط با فایل یا شاخه‌ای به نام foo در ریشهٔ بسته مطابقت دارد.
    • foo/ با هر شاخه‌ای به نام foo در هر جای بسته مطابقت دارد.
    • الگوهای glob رایج مانند *، ? و [] پشتیبانی می‌شوند:
      • * با صفر یا چند نویسه، به جز /، مطابقت دارد. برای مثال، *.html با هر فایل یا شاخه‌ای که پسوند .html داشته باشد، در هر جای بسته، مطابقت دارد.
      • ? با هر نویسه‌ای به جز / مطابقت دارد. برای مثال، foo? با food مطابقت دارد، اما با foo نه.
      • [] امکان مطابقت با بازه‌ای از نویسه‌ها را می‌دهد. برای مثال، [ab] با a یا b مطابقت دارد. [a-z] با حروف a تا z مطابقت دارد.
    • پیشوند **/ در هر شاخه‌ای مطابقت می‌دهد. برای مثال، **/foo/bar با فایل یا شاخهٔ bar در هر جایی که مستقیماً زیر شاخهٔ foo باشد مطابقت دارد.
    • پسوند /** با هر چیزی که درون آن است مطابقت دارد. برای مثال، foo/** با همهٔ فایل‌های درون شاخهٔ foo، از جمله همهٔ فایل‌های زیرشاخه‌های foo، مطابقت دارد.
    • /**/ با صفر یا چند شاخه مطابقت دارد. برای مثال، a/**/b با a/b، a/x/b، a/x/y/b و مانند آن‌ها مطابقت دارد.
    • پیشوند ! یک الگو را نفی می‌کند. برای مثال، الگوی src/*.rs همراه با !foo.rs با همهٔ فایل‌هایی که پسوند .rs دارند و درون شاخهٔ src هستند، به جز هر فایل با نام foo.rs، مطابقت دارد.

    فهرست include/exclude در برخی موقعیت‌ها برای ردیابی تغییرات نیز به کار می‌رود. برای هدف‌هایی که با rustdoc ساخته می‌شوند، از این فهرست برای تعیین فایل‌هایی که باید ردیابی شوند استفاده می‌شود تا مشخص شود هدف باید دوباره ساخته شود یا نه. اگر بسته اسکریپت ساختی داشته باشد که هیچ دستور rerun-if-*ای صادر نمی‌کند، از فهرست include/exclude برای ردیابی اینکه آیا اسکریپت ساخت باید دوباره اجرا شود یا نه استفاده می‌شود، در صورتی که هر یک از آن فایل‌ها تغییر کند.

    فیلد publish

    فیلد publish را می‌توان برای کنترل اینکه بسته در کدام رجیستری‌ها (با نام) منتشر شود به کار برد:

    [package]
# ...
publish = ["some-registry-name"]

    برای جلوگیری از انتشار اشتباهی بسته در یک رجیستری (مانند crates.io)، مثلاً برای خصوصی نگه داشتن یک بسته در یک شرکت، می‌توانید فیلد version را حذف کنید. اگر می‌خواهید صریح‌تر عمل کنید، می‌توانید انتشار را غیرفعال کنید:

    [package]
# ...
publish = false

    اگر آرایهٔ publish فقط یک رجیستری داشته باشد، دستور cargo publish هنگامی که پرچم --registry مشخص نشده باشد از همان رجیستری استفاده می‌کند.

    جدول metadata

    Cargo به‌طور پیش‌فرض دربارهٔ کلیدهای استفاده‌نشده در Cargo.toml هشدار می‌دهد تا به تشخیص غلط‌های تایپی و مانند آن کمک کند. اما جدول package.metadata کاملاً توسط Cargo نادیده گرفته می‌شود و دربارهٔ آن هشداری داده نمی‌شود. این بخش را می‌توان برای ابزارهایی به کار برد که می‌خواهند پیکربندی بسته را در Cargo.toml ذخیره کنند. برای مثال:

    [package]
name = "..."
# ...

# Metadata used when generating an Android APK, for example.
[package.metadata.android]
package-name = "my-awesome-android-app"
assets = "path/to/static"

    برای دانستن نحوهٔ استفاده از این فیلد باید به مستندات ابزار خود مراجعه کنید. برای پروژه‌های Rust که از جدول‌های package.metadata استفاده می‌کنند، این‌ها را ببینید:

    • docs.rs

    جدول مشابهی در سطح workspace در workspace.metadata وجود دارد. اگرچه cargo قالبی برای محتوای هیچ‌یک از این دو جدول مشخص نمی‌کند، پیشنهاد می‌شود ابزارهای خارجی از آن‌ها به شیوه‌ای یکدست استفاده کنند، مثلاً اگر داده‌ای در package.metadata وجود ندارد، به داده‌های workspace.metadata ارجاع دهند، البته اگر برای ابزار مورد نظر معنا داشته باشد.

    فیلد default-run

    فیلد default-run در بخش [package] فایل manifest را می‌توان برای تعیین فایل اجرایی پیش‌فرضی که cargo run انتخاب می‌کند به کار برد. برای مثال، وقتی هم src/bin/a.rs و هم src/bin/b.rs وجود دارد:

    [package]
default-run = "a"

    بخش [lints]

    سطح پیش‌فرض lintهای ابزارهای مختلف را با اختصاص دادن سطحی جدید به آن‌ها در یک جدول بازنویسی کنید، برای مثال:

    [lints.rust]
unsafe_code = "forbid"

    این مخفف عبارت زیر است:

    [lints.rust]
unsafe_code = { level = "forbid", priority = 0 }

    level با سطح‌های lint در rustc متناظر است:

    • forbid
    • deny
    • warn
    • allow

    priority یک عدد صحیح علامت‌دار است که کنترل می‌کند کدام lintها یا گروه‌های lint بر گروه‌های lint دیگر غلبه کنند:

    • اعداد کوچک‌تر (به‌ویژه منفی) اولویت پایین‌تری دارند، توسط اعداد بزرگ‌تر بازنویسی می‌شوند، و در خط فرمان ابزارهایی مانند rustc زودتر ظاهر می‌شوند

    برای دانستن اینکه یک lint مشخص زیر کدام جدول از [lints] قرار می‌گیرد، به بخش پیش از :: در نام lint نگاه کنید. اگر :: وجود نداشته باشد، ابزار rust است. برای مثال، هشدار دربارهٔ unsafe_code به‌صورت lints.rust.unsafe_code خواهد بود، اما lint مربوط به clippy::enum_glob_use به‌صورت lints.clippy.enum_glob_use خواهد بود.

    برای مثال:

    [lints.rust]
unsafe_code = "forbid"

[lints.clippy]
enum_glob_use = "deny"

[lints.cargo]
unused_dependencies = "deny"

    عموماً این تنظیمات فقط بر توسعهٔ محلی بستهٔ فعلی اثر می‌گذارند. Cargo آن‌ها را فقط بر بستهٔ فعلی اعمال می‌کند و نه بر وابستگی‌ها. در مورد بسته‌های وابسته به آن، Cargo با قابلیت‌هایی مانند --cap-lints lintهای وابستگی‌های غیر path را خاموش می‌کند.

    برای lintهای موجودی که خود Cargo تولید می‌کند، فصل lintها را نیز ببینید.

    بخش [hints]

    بخش [hints] امکان تعیین راهنماهایی (hint) برای کامپایل این بسته را فراهم می‌کند. Cargo به‌طور پیش‌فرض هنگام کامپایل این بسته به این راهنماها احترام می‌گذارد، هرچند بستهٔ سطح بالایی که ساخته می‌شود می‌تواند این مقادیر را از طریق سازوکار [profile] بازنویسی کند. راهنماها، طبق طراحی، همیشه برای Cargo بی‌خطر هستند که نادیده گرفته شوند؛ اگر Cargo با راهنمایی روبه‌رو شود که آن را نمی‌فهمد، یا راهنمایی که آن را می‌فهمد اما مقدارش را نمی‌فهمد، هشدار می‌دهد اما خطا نمی‌دهد. در نتیجه، تعیین راهنما در یک crate بر MSRV آن crate اثری ندارد.

    هر راهنما ممکن است یک feature gate ناپایدار مرتبط داشته باشد که برای اعمال پیکربندی‌ای که مشخص می‌کند باید آن را بدهید، اما اگر آن feature gate ناپایدار را مشخص نکنید، باز هم فقط یک هشدار دریافت می‌کنید، نه خطا.

    در حال حاضر هیچ راهنمای پایداری وجود ندارد. برای اطلاعات دربارهٔ یک راهنمای ناپایدار، مستندات hint-mostly-unused را ببینید.

    MSRV: از 1.90 رعایت می‌شود.

    بخش [badges]

    بخش [badges] برای تعیین نشان‌های وضعیتی است که می‌توانند هنگام انتشار بسته در وب‌سایت رجیستری نمایش داده شوند.

    Note

    (https://crates.io/) پیش‌تر نشان‌ها را کنار یک crate در وب‌سایت خود نمایش می‌داد، اما این قابلیت حذف شده است. بسته‌ها باید نشان‌ها را در فایل README خود قرار دهند که در crates.io نمایش داده می‌شود (به فیلد readme نگاه کنید).

    [badges]
# The `maintenance` table indicates the status of the maintenance of
# the crate. This may be used by a registry, but is currently not
# used by crates.io. See https://github.com/rust-lang/crates.io/issues/2437
# and https://github.com/rust-lang/crates.io/issues/2438 for more details.
#
# The `status` field is required. Available options are:
# - `actively-developed`: New features are being added and bugs are being fixed.
# - `passively-maintained`: There are no plans for new features, but the maintainer intends to
#   respond to issues that get filed.
# - `as-is`: The crate is feature complete, the maintainer does not intend to continue working on
#   it or providing support, but it works for the purposes it was designed for.
# - `experimental`: The author wants to share it with the community but is not intending to meet
#   anyone's particular use case.
# - `looking-for-maintainer`: The current maintainer would like to transfer the crate to someone
#   else.
# - `deprecated`: The maintainer does not recommend using this crate (the description of the crate
#   can describe why, there could be a better solution available or there could be problems with
#   the crate that the author does not want to fix).
# - `none`: Displays no badge on crates.io, since the maintainer has not chosen to specify
#   their intentions, potential crate users will need to investigate on their own.
maintenance = { status = "..." }
