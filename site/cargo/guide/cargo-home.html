    Cargo Home

    «Cargo home» به‌عنوان محل دانلود و کش منابع عمل می‌کند. هنگام ساخت یک crate، Cargo وابستگی‌های ساخت دانلودشده را در Cargo home ذخیره می‌کند. می‌توانید با تنظیم CARGO_HOME به‌عنوان متغیر محیطی، محل Cargo home را تغییر دهید. اگر درون crate خود به این مسیر نیاز دارید، crate با نام home یک API برای دریافت آن فراهم می‌کند. به‌طور پیش‌فرض، Cargo home در $HOME/.cargo/ قرار دارد.

    توجه داشته باشید که ساختار داخلی Cargo home پایدار (stable) نشده است و ممکن است در هر زمان تغییر کند.

    Cargo home از اجزای زیر تشکیل شده است:

    فایل‌ها:

    • config.toml فایل پیکربندی سراسری Cargo؛ مدخل config در مرجع را ببینید.

    • credentials.toml اطلاعات ورود خصوصی حاصل از cargo login برای ورود به یک registry.

    • .crates.toml، .crates2.json این فایل‌های پنهان شامل اطلاعات بسته‌های crateهایی هستند که با cargo install نصب شده‌اند. آن‌ها را دستی ویرایش نکنید!

    دایرکتوری‌ها:

    • bin دایرکتوری bin شامل فایل‌های اجرایی crateهایی است که با cargo install یا rustup نصب شده‌اند. برای اینکه بتوانید به این باینری‌ها دسترسی داشته باشید، مسیر این دایرکتوری را به متغیر محیطی $PATH خود اضافه کنید.

    • git منابع Git در اینجا ذخیره می‌شوند:

      • git/db وقتی یک crate به یک مخزن git وابسته باشد، Cargo آن مخزن را به‌صورت bare repo در این پوشه کلون می‌کند و در صورت نیاز به‌روزش می‌کند.

      • git/checkouts اگر از یک منبع git استفاده شود، commit موردنیاز مخزن از bare repo درون git/db به این پوشه checkout می‌شود. به این ترتیب فایل‌های واقعی موجود در مخزن، در commit مشخص‌شده برای آن وابستگی، در اختیار کامپایلر قرار می‌گیرند. امکان وجود چندین checkout از commitهای مختلف یک مخزن وجود دارد.

    • registry بسته‌ها و فرادادهٔ registryهای crate (مانند crates.io) در اینجا قرار دارند.

      • registry/index index یک مخزن git از نوع bare است که فرادادهٔ (نسخه‌ها، وابستگی‌ها و غیره) همهٔ crateهای موجود یک registry را در خود دارد.

      • registry/cache وابستگی‌های دانلودشده در cache ذخیره می‌شوند. crateها آرشیوهای فشردهٔ gzip هستند که با پسوند .crate نام‌گذاری می‌شوند.

      • registry/src اگر یک بسته به آرشیو .crate دانلودشده نیاز داشته باشد، آن آرشیو در پوشهٔ registry/src باز می‌شود که rustc فایل‌های .rs را در آنجا پیدا می‌کند.

    کش کردن Cargo home در CI

    برای جلوگیری از دانلود دوبارهٔ همهٔ وابستگی‌های crate در طول یکپارچه‌سازی مداوم، می‌توانید پوشهٔ $CARGO_HOME را کش کنید. با این حال، کش کردن کل پوشه اغلب کارآمد نیست، زیرا منابع دانلودشده را دو بار در خود دارد. اگر به crateای مانند serde 1.0.92 وابسته باشیم و کل $CARGO_HOME را کش کنیم، در واقع منابع را دو بار کش کرده‌ایم: یک بار serde-1.0.92.crate درون registry/cache و بار دیگر فایل‌های .rs استخراج‌شدهٔ serde درون registry/src. این کار می‌تواند ساخت را بی‌دلیل کند کند، چون دانلود، استخراج، فشرده‌سازی مجدد و بارگذاری دوبارهٔ کش روی سرورهای CI ممکن است مدتی طول بکشد.

    اگر می‌خواهید باینری‌هایی را که با cargo install نصب شده‌اند کش کنید، باید دایرکتوری bin/ و فایل‌های .crates.toml و .crates2.json را کش کنید.

    کش کردن فایل‌ها و پوشه‌های زیر در میان ساخت‌ها باید کافی باشد:

    • .crates.toml
    • .crates2.json
    • bin/
    • registry/index/
    • registry/cache/
    • git/db/

    Vendor کردن همهٔ وابستگی‌های یک پروژه

    زیردستور cargo vendor را ببینید.

    پاک کردن کش

    در تئوری، همیشه می‌توانید هر بخشی از کش را حذف کنید و Cargo تلاش خود را می‌کند تا در صورت نیاز یک crate به منابع، آن‌ها را بازیابی کند: یا با استخراج دوبارهٔ یک آرشیو، یا با checkout کردن یک bare repo، یا به‌سادگی با دانلود دوبارهٔ منابع از وب.

    همچنین، crate با نام cargo-cache یک ابزار CLI ساده فراهم می‌کند تا فقط بخش‌های انتخاب‌شده‌ای از کش را پاک کنید یا اندازهٔ اجزای آن را در خط فرمان خود ببینید.
