    شروع به کار

    یک CI ساده، پروژه‌های شما را می‌سازد و آزمون می‌کند:

    GitHub Actions

    برای آزمون بستهٔ خود در GitHub Actions، این یک نمونه فایل .github/workflows/ci.yml است:

    name: Cargo Build & Test

on:
  push:
  pull_request:

env:
  CARGO_TERM_COLOR: always

jobs:
  build_and_test:
    name: Rust project - latest
    runs-on: ubuntu-latest
    strategy:
      matrix:
        toolchain:
          - stable
          - beta
          - nightly
    steps:
      - uses: actions/checkout@v6
      - run: rustup update ${{ matrix.toolchain }} && rustup default ${{ matrix.toolchain }}
      - run: cargo build --verbose
      - run: cargo test --verbose

    این کار هر سه کانال انتشار را آزمون می‌کند (توجه کنید که شکست در هر نسخهٔ toolchain کل job را شکست می‌دهد). همچنین می‌توانید در رابط کاربری GitHub روی "Actions" > "new workflow" کلیک کنید و Rust را انتخاب کنید تا پیکربندی پیش‌فرض به مخزن شما اضافه شود. برای اطلاعات بیشتر مستندات GitHub Actions را ببینید.

    GitLab CI

    برای آزمون بستهٔ خود در GitLab CI، این یک نمونه فایل .gitlab-ci.yml است:

    stages:
  - build

rust-latest:
  stage: build
  image: rust:latest
  script:
    - cargo build --verbose
    - cargo test --verbose

rust-nightly:
  stage: build
  image: rustlang/rust:nightly
  script:
    - cargo build --verbose
    - cargo test --verbose
  allow_failure: true

    این کار روی کانال stable و کانال nightly آزمون می‌گیرد، اما هر خرابی در nightly کل ساخت شما را شکست نمی‌دهد. برای اطلاعات بیشتر لطفاً مستندات GitLab CI را ببینید.

    builds.sr.ht

    برای آزمون بستهٔ خود در sr.ht، این یک نمونه فایل .build.yml است. حتماً <your repo> و <your project> را به مخزنی که باید کلون شود و پوشه‌ای که در آن کلون شده است تغییر دهید.

    image: archlinux
packages:
  - rustup
sources:
  - <your repo>
tasks:
  - setup: |
      rustup toolchain install nightly stable
      cd <your project>/
      rustup run stable cargo fetch
  - stable: |
      rustup default stable
      cd <your project>/
      cargo build --verbose
      cargo test --verbose
  - nightly: |
      rustup default nightly
      cd <your project>/
      cargo build --verbose ||:
      cargo test --verbose  ||:
  - docs: |
      cd <your project>/
      rustup run stable cargo doc --no-deps
      rustup run nightly cargo doc --no-deps ||:

    این کار آزمون و ساخت مستندات را روی کانال stable و کانال nightly انجام می‌دهد، اما هر خرابی در nightly کل ساخت شما را شکست نمی‌دهد. برای اطلاعات بیشتر لطفاً مستندات builds.sr.ht را ببینید.

    CircleCI

    برای آزمون بستهٔ خود در CircleCI، این یک نمونه فایل .circleci/config.yml است:

    version: 2.1
jobs:
  build:
    docker:
      # check https://circleci.com/developer/images/image/cimg/rust#image-tags for latest
      - image: cimg/rust:1.77.2
    steps:
      - checkout
      - run: cargo test

    برای اجرای pipelineهای پیچیده‌تر، از جمله تشخیص آزمون‌های ناپایدار، کش کردن و مدیریت آرتیفکت‌ها، لطفاً مرجع پیکربندی CircleCI را ببینید.

    تأیید آخرین وابستگی‌ها

    هنگام مشخص کردن وابستگی‌ها در Cargo.toml، آن‌ها معمولاً با یک بازه از نسخه‌ها مطابقت دارند. آزمون کامل همهٔ ترکیب‌های نسخه دست‌وپاگیر خواهد بود. بررسی آخرین نسخه‌ها دست‌کم برای کاربرانی که cargo add یا cargo install را اجرا می‌کنند آزمون می‌گیرد.

    هنگام آزمون آخرین نسخه‌ها، برخی ملاحظات عبارت‌اند از:

    • به حداقل رساندن عوامل بیرونی که بر توسعهٔ محلی یا CI اثر می‌گذارند
    • نرخ انتشار وابستگی‌های جدید
    • سطح ریسکی که یک پروژه مایل به پذیرش آن است
    • هزینه‌های CI، از جمله هزینه‌های غیرمستقیم مانند اینکه یک سرویس CI سقفی برای تعداد runnerهای موازی داشته باشد و در هنگام رسیدن به آن سقف، jobهای جدید به‌صورت سریالی اجرا شوند.

    برخی راه‌حل‌های ممکن عبارت‌اند از:

    • ثبت نکردن Cargo.lock
      • بسته به سرعت PRها، ممکن است بسیاری از نسخه‌ها بدون آزمون بمانند
      • این کار به قیمت قطعی بودن (determinism) تمام می‌شود
    • داشتن یک job در CI که آخرین وابستگی‌ها را تأیید می‌کند اما آن را «ادامه در صورت شکست» علامت می‌زند
      • بسته به سرویس CI، شکست‌ها ممکن است واضح نباشند
      • بسته به سرعت PRها، ممکن است منابع بیش از حد لازم مصرف کند
    • داشتن یک job زمان‌بندی‌شدهٔ CI برای تأیید آخرین وابستگی‌ها
      • یک سرویس CI میزبانی‌شده ممکن است jobهای زمان‌بندی‌شده را برای مخزن‌هایی که مدتی است دست نخورده‌اند غیرفعال کند، که بر بسته‌هایی که به‌صورت منفعل نگهداری می‌شوند اثر می‌گذارد
      • بسته به سرویس CI، ممکن است اعلان‌ها به افرادی که می‌توانند برای رفع شکست اقدام کنند نرسند
      • اگر با نرخ انتشار وابستگی‌ها متوازن نشود، ممکن است نسخه‌های کافی را آزمون نکند یا آزمون‌های تکراری انجام دهد
    • به‌روزرسانی منظم وابستگی‌ها از طریق PRها، مانند Dependabot یا RenovateBot
      • می‌تواند وابستگی‌ها را در PR جداگانهٔ خودشان جدا کند یا همه را در یک PR واحد جمع کند
      • فقط از منابع لازم استفاده می‌کند
      • می‌توان بسامد را پیکربندی کرد تا میان منابع CI و پوشش نسخه‌های وابستگی توازن برقرار شود

    یک نمونه job در CI برای تأیید آخرین وابستگی‌ها با استفاده از GitHub Actions:

    jobs:
  latest_deps:
    name: Latest Dependencies
    runs-on: ubuntu-latest
    continue-on-error: true
    env:
      CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS: allow
    steps:
      - uses: actions/checkout@v6
      - run: rustup update stable && rustup default stable
      - run: cargo update --verbose
      - run: cargo build --verbose
      - run: cargo test --verbose

    نکته‌ها:

    • CARGO_RESOLVER_INCOMPATIBLE_RUST_VERSIONS تنظیم شده است تا اطمینان حاصل شود resolver به‌دلیل نسخهٔ Rust پروژهٔ شما، وابستگی‌های انتخاب‌شده را محدود نمی‌کند.

    برای پروژه‌هایی که ریسک بالاتری از شکست‌های مخصوص هر پلتفرم یا هر نسخهٔ Rust دارند، ممکن است بخواهید ترکیب‌های بیشتری آزمون شوند.

    تأیید rust-version

    هنگام انتشار بسته‌هایی که rust-version را مشخص می‌کنند، مهم است که درستی آن فیلد تأیید شود.

    برخی ابزارهای شخص ثالث که می‌توانند در این کار کمک کنند عبارت‌اند از:

    • cargo-msrv
    • cargo-hack

    یک نمونه از یکی از راه‌های انجام این کار با استفاده از GitHub Actions:

    jobs:
  msrv:
    runs-on: ubuntu-latest
    steps:
    - uses: actions/checkout@v6
    - uses: taiki-e/install-action@cargo-hack
    - run: cargo hack check --rust-version --workspace --all-targets --ignore-private

    این کار می‌کوشد میان دقت و زمان بازخورد تعادل برقرار کند:

    • از یک پلتفرم واحد استفاده می‌شود، چون بیشتر پروژه‌ها مستقل از پلتفرم هستند و به وابستگی‌های مخصوص پلتفرم اعتماد می‌شود که رفتار خود را تأیید کنند.
    • از cargo check استفاده می‌شود، چون بیشتر مشکلاتی که مشارکت‌کنندگان با آن‌ها روبه‌رو می‌شوند دردسترس بودن API است و نه رفتار.
    • بسته‌های منتشرنشده نادیده گرفته می‌شوند، چون فرض بر این است که فقط مصرف‌کنندگان پروژهٔ تأییدشده، از طریق یک registry، به rust-version اهمیت می‌دهند.

    بررسی هشدارها

    معمولاً پروژه‌ها می‌خواهند روی شاخه‌های رسمی «بدون هشدار» باشند، در حالی که برای توسعهٔ محلی سخت‌گیری کمتری دارند. می‌توان از build.warnings = "deny" استفاده کرد تا در صورت وجود هشدارها یک job در CI شکست بخورد.

    یک نمونه job در CI برای بررسی هشدارها با استفاده از GitHub Actions:

    jobs:
  warnings:
    runs-on: ubuntu-latest
    env:
      CARGO_BUILD_WARNINGS: deny
    steps:
      - uses: actions/checkout@v6
      - run: rustup update stable && rustup default stable
      - run: rustup component add clippy
      - run: cargo clippy --all-targets --all-features --keep-going

    ملاحظات:

    • CI ممکن است به‌دلیل نسخه‌های جدید toolchain شکست بخورد، چون ضمانت‌های سازگاری پیرامون هشدارها محدود است. پین کردن نسخهٔ toolchain را همراه با یک job خودکار که با هر انتشار جدید یک PR برای ارتقای toolchain می‌سازد در نظر بگیرید.
    • در انتخاب ترکیب‌های پلتفرم‌ها، featureها و ترکیب‌های بسته/هدف ساخت برای بررسی، میان جامعیت و زمان بازخورد توازن برقرار کنید
    • برخی سیستم‌های CI یکپارچگی مستقیم برای گزارش lintها دارند، مثلاً استفاده از clippy-sarif با GitHub

    اطمینان از به‌روز بودن lockfile

    داشتن یک lockfile قدیمی، مزایای commit کردن lockfile را از بین می‌برد.

    نمونه‌ای از یک job در CI برای بررسی lockfileهای قدیمی با استفاده از GitHub Actions:

    jobs:
  lockfile:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v6
      - run: rustup update stable && rustup default stable
      - run: cargo update --workspace --locked
