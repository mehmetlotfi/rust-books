    بهینه‌سازی عملکرد ساخت

    گزینه‌های پیکربندی Cargo و الگوهای سازمان‌دهی کد منبع می‌توانند با اولویت دادن به عملکرد ساخت نسبت به جنبه‌های دیگری که شاید برای شرایط شما اهمیت کمتری دارند، به بهبود عملکرد ساخت کمک کنند.

    همان‌طور که در بهینه‌سازی عملکرد زمان اجرا نیز چنین است، حتماً این تغییرات را با گردش‌کارهایی که واقعاً برایتان مهم هستند بسنجید؛ زیرا ما رهنمودهای کلی ارائه می‌دهیم و شرایط شما ممکن است متفاوت باشد، و امکان دارد برخی از این رویکردها در واقع عملکرد ساخت را در مورد استفادهٔ شما بدتر کنند.

    نمونه گردش‌کارهایی که باید در نظر بگیرید عبارت‌اند از:

    • بازخورد کامپایلر هنگام توسعه (cargo check پس از تغییر در کد)
    • بازخورد آزمون هنگام توسعه (cargo test پس از تغییر در کد)
    • ساخت‌های CI

    پیکربندی Cargo و کامپایلر

    Cargo از پیکربندی‌های پیش‌فرضی استفاده می‌کند که می‌کوشند میان جنبه‌های مختلفی از جمله قابلیت اشکال‌زدایی، عملکرد زمان اجرا، عملکرد ساخت، اندازهٔ باینری و موارد دیگر تعادل برقرار کنند. این بخش چند رویکرد برای تغییر این پیش‌فرض‌ها را شرح می‌دهد که برای به حداکثر رساندن عملکرد ساخت طراحی شده‌اند.

    مکان‌های رایج برای بازنویسی پیش‌فرض‌ها عبارت‌اند از:

    • فایل manifest با نام Cargo.toml
      • در دسترس همهٔ توسعه‌دهندگانی که در پروژهٔ شما مشارکت می‌کنند
      • پیکربندی‌های پشتیبانی‌شده در آن محدود است (برای گسترش این امر #12738 را ببینید)
    • فایل پیکربندی $WORKSPACE_ROOT/.cargo/config.toml
      • در دسترس همهٔ توسعه‌دهندگانی که در پروژهٔ شما مشارکت می‌کنند
      • برخلاف Cargo.toml، این فایل به این حساس است که cargo را از کدام پوشه فراخوانی می‌کنید (به #2930 نگاه کنید)
    • فایل پیکربندی $CARGO_HOME/.cargo/config.toml
      • برای اینکه هر توسعه‌دهنده پیش‌فرض‌های محیط توسعهٔ خود را کنترل کند

    کاهش مقدار اطلاعات اشکال‌زدایی تولیدشده

    توصیه: این را به Cargo.toml یا .cargo/config.toml خود اضافه کنید:

    [profile.dev]
debug = "line-tables-only"

[profile.dev.package."*"]
debug = false

[profile.debugging]
inherits = "dev"
debug = true

    این کار موارد زیر را انجام می‌دهد:

    • profile dev (پیش‌فرض دستورهای توسعه) را به این صورت تغییر می‌دهد:
      • اطلاعات اشکال‌زدایی اعضای workspace را به مقداری که برای backtraceهای مفید panic لازم است محدود می‌کند
      • از تولید هرگونه اطلاعات اشکال‌زدایی برای وابستگی‌ها پرهیز می‌کند
    • راهی اختیاری برای زمانی که با --profile debugging اشکال‌زدایی می‌کنید فراهم می‌کند

    Note: بازبینی مجدد profile dev در #15931 پیگیری می‌شود.

    مبادلات:

    • ✅ تولید کد سریع‌تر (cargo build)
    • ✅ زمان‌های لینک سریع‌تر
    • ✅ مصرف کمتر فضای دیسک توسط پوشهٔ target
    • ❌ برای داشتن تجربهٔ اشکال‌زدایی با کیفیت بالا، به ساخت کامل مجدد نیاز دارد

    استفاده از یک backend تولید کد جایگزین

    پیشنهاد:

    • مؤلفهٔ rustup مربوط به backend تولید کد Cranelift را نصب کنید 
      $ rustup component add rustc-codegen-cranelift-preview --toolchain nightly
    • این را به Cargo.toml یا .cargo/config.toml خود اضافه کنید: toml [profile.dev] codegen-backend = "cranelift" 
      [profile.dev]
codegen-backend = "cranelift"
    • Cargo را با -Z codegen-backend اجرا کنید یا قابلیت codegen-backend را در .cargo/config.toml فعال کنید.
      • این کار لازم است، چون این قابلیت در حال حاضر ناپایدار (unstable) است.

    این کار profile dev را طوری تغییر می‌دهد که برای تولید کد ماشین به‌جای backend پیش‌فرض LLVM، از backend تولید کد Cranelift استفاده کند. backend مربوط به Cranelift باید کد را سریع‌تر از LLVM تولید کند که باید به بهبود عملکرد ساخت بینجامد.

    مبادلات:

    • ✅ تولید کد سریع‌تر (cargo build)
    • ❌ نیاز به استفاده از Rust نسخهٔ nightly و یک قابلیت ناپایدار Cargo دارد
    • ❌ عملکرد زمان اجرای بدتر برای کد تولیدشده
      • بخش ساخت در cargo test را سریع‌تر می‌کند، اما ممکن است بخش اجرای آزمون‌های آن را طولانی‌تر کند
    • ❌ فقط برای هدف‌های معین در دسترس است
    • ❌ ممکن است از همهٔ قابلیت‌های Rust پشتیبانی نکند (مثلاً unwinding)

    فعال‌سازی frontend موازی آزمایشی

    توصیه: این را به .cargo/config.toml خود اضافه کنید:

    [build]
rustflags = "-Zthreads=8"

    این rustflags، frontend موازی کامپایلر Rust را فعال می‌کند و به آن می‌گوید از n نخ استفاده کند. مقدار n باید بر اساس تعداد هسته‌های موجود در سیستم شما انتخاب شود، هرچند بازده با افزایش آن کاهش می‌یابد. توصیه می‌کنیم حداکثر از 8 نخ استفاده کنید.

    مبادلات:

    • ✅ زمان‌های ساخت سریع‌تر (هم برای cargo check و هم برای cargo build)
    • ❌ نیاز به استفاده از Rust نسخهٔ nightly و یک قابلیت ناپایدار Rust دارد

    استفاده از یک لینکر جایگزین

    پیشنهاد: یک لینکر جایگزین مانند LLD، mold یا wild را نصب و پیکربندی کنید. برای مثال، برای پیکربندی mold در Linux می‌توانید این را به .cargo/config.toml خود اضافه کنید:

    [target.'cfg(target_os = "linux")']
# mold, if you have GCC 12+
rustflags = ["-C", "link-arg=-fuse-ld=mold"]

# mold, otherwise
linker = "clang"
rustflags = ["-C", "link-arg=-fuse-ld=/path/to/mold"]

    اگرچه وابستگی‌ها ممکن است به‌صورت موازی ساخته شوند، لینک کردن همهٔ وابستگی‌های شما یک‌جا و در پایان ساخت انجام می‌شود، که می‌تواند باعث شود لینک کردن بر زمان ساخت شما غالب شود، به‌ویژه در ساخت‌های مجدد افزایشی (incremental). اغلب لینکری که Rust استفاده می‌کند از قبل نسبتاً سریع است و سودی که از تعویض آن به دست می‌آید ممکن است ارزشش را نداشته باشد، اما همیشه چنین نیست. برای مثال، هدف‌های Linux به‌جز x86_64-unknown-linux-gnu همچنان از لینکر سیستمی Linux استفاده می‌کنند که کاملاً کند است (برای جزئیات بیشتر rust#39915 را ببینید).

    مبادلات:

    • ✅ زمان‌های لینک سریع‌تر
    • ❌ ممکن است همهٔ موارد استفاده را پشتیبانی نکند، به‌ویژه اگر به وابستگی‌های C یا C++ وابسته باشید

    تحلیل featureها برای کل workspace

    پیشنهاد: این را به .cargo/config.toml پروژهٔ خود اضافه کنید

    [resolver]
feature-unification = "workspace"

    هنگام فراخوانی cargo، featureها فعال می‌شوند و این بر اساس این است که کدام اعضای workspace را انتخاب کرده‌اید. با این حال، هنگام مشارکت در یک برنامه، ممکن است لازم باشد بسته‌های مختلف درون برنامه را بسازید و آزمون کنید، که می‌تواند باعث ساخت‌های مجدد غیرضروری شود، چون ممکن است برای وابستگی‌های مشترک مجموعه‌های مختلفی از featureها فعال شوند. با feature-unification، می‌توانید با اطمینان از فعال شدن مجموعهٔ یکسانی از featureهای وابستگی، صرف‌نظر از اینکه در حال حاضر کدام بسته را می‌سازید و آزمون می‌کنید، ساخت‌های وابستگی بیشتری را دوباره استفاده کنید.

    مبادلات:

    • ✅ ساخت‌های مجدد کمتر هنگام ساخت بسته‌های مختلف در یک workspace
    • ❌ نیاز به استفاده از Rust نسخهٔ nightly و یک قابلیت ناپایدار Cargo دارد
    • ❌ فعال کردن یک feature توسط یک بسته می‌تواند اشکالات بسته‌های دیگری را که باید آن را فعال کنند اما نمی‌کنند پنهان کند
    • ❌ اگر یکسان‌سازی featureها از طریق --workspace برای شما کار نکند، این روش هم کار نخواهد کرد

    کاهش کد ساخته‌شده

    حذف وابستگی‌های استفاده‌نشده

    cargo::unused_dependencies بیشتر وابستگی‌های استفاده‌نشده را با موارد مثبت کاذب اندک شناسایی می‌کند.

    برای هر چیز دیگر، نتایج پنهان cargo::unused_dependencies را به‌طور دوره‌ای بازبینی کنید:

    $ CARGO_LOG=cargo::diagnostics::rules::unused_dependencies=debug cargo check --workspace --all-targets

    این دستور وابستگی‌های بالقوه استفاده‌نشده را در موارد زیر نشان می‌دهد

    • وابستگی‌های registry و git
    • زمانی که package.rust-version شما برای استفاده از [lints.cargo] بسیار قدیمی است
    • زمانی که ممکن است از وابستگی شما شاید برای محدود کردن نسخهٔ یک وابستگی تعدی‌یافته استفاده شده باشد (به‌جای آن از [target."cfg(false)".dependencies] استفاده کنید)
    • زمانی که ممکن است از وابستگی شما شاید برای فعال کردن featureها روی یک وابستگی تعدی‌یافته استفاده شده باشد
    • [dev-dependencies] شما، چون هنوز راهی برای اطمینان از ساخته شدن همهٔ مصرف‌کنندگان آن‌ها وجود ندارد

    هنگام تغییر کد، ممکن است به‌آسانی از نظر دور بماند که یک وابستگی دیگر استفاده نمی‌شود و می‌توان آن را حذف کرد.

    مبادلات:

    • ✅ زمان‌های ساخت کامل و لینک سریع‌تر
    • ❌ شناسایی وابستگی‌های استفاده‌نشده از میان موارد مثبت کاذب به تلاش نیاز دارد

    حذف featureهای استفاده‌نشده از وابستگی‌ها

    توصیه: featureهای استفاده‌نشدهٔ وابستگی‌ها را برای حذف، به‌طور دوره‌ای با ابزارهای شخص ثالث مانند cargo-features-manager، cargo-unused-features بازبینی کنید.

    هنگام تغییر کد، ممکن است به‌آسانی از نظر دور بماند که یک feature از یک وابستگی دیگر استفاده نمی‌شود و می‌توان آن را حذف کرد. این کار می‌تواند تعداد وابستگی‌های تعدی‌یافته‌ای را که ساخته می‌شوند کاهش دهد یا مقدار کد درون یک crate را که ساخته می‌شود کم کند. هنگام حذف featureها باید احتیاط بیشتری کرد، زیرا ممکن است featureها برای رفتار یا تغییرات عملکردی مطلوب نیز استفاده شوند که همیشه از روی کامپایل یا آزمون کردن بدیهی نیست.

    مبادلات:

    • ✅ زمان‌های ساخت کامل و لینک سریع‌تر
    • ❌ ممکن است featureها را به‌اشتباه استفاده‌نشده علامت‌گذاری کند
