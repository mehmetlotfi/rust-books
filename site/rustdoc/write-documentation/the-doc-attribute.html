کتاب rustdocThe rustdoc Book

    attribute ـِ #[doc]

    attribute ـِ #[doc] به شما امکان می‌دهد جنبه‌های گوناگونی از نحوهٔ کار rustdoc را کنترل کنید.

    ابتدایی‌ترین کارکرد #[doc] مدیریت خودِ متن مستندات است. یعنی /// شکر نحوی برای #[doc] است (همان‌طور که //! برای #![doc] است). این یعنی این دو یکسان‌اند:

    /// This is a doc comment.
#[doc = r" This is a doc comment."]
fn f() {}

    (به فاصلهٔ ابتدای متن و رشتهٔ خام در نسخهٔ attribute توجه کنید.)

    در بیشتر موارد، استفاده از /// آسان‌تر از #[doc] است. یکی از مواردی که دومی راحت‌تر است، تولید مستندات درون ماکروهاست؛ گذرِ collapse-docs چند attribute ـِ #[doc] را در یک doc comment واحد ترکیب می‌کند و به شما اجازه می‌دهد کدی مانند این تولید کنید:

    #[doc = "This is"]
#[doc = " a "]
#[doc = "doc comment"]
fn f() {}

    که می‌تواند انعطاف‌پذیرتر به نظر برسد. توجه کنید که این کد، این را تولید می‌کند:

    #[doc = "This is\n a \ndoc comment"]
fn f() {}

    اما چون مستندات از طریق Markdown رندر می‌شوند، این خطوط جدید حذف می‌شوند.

    کاربرد دیگر، گنجاندن فایل‌های خارجی به‌عنوان مستندات است:

    #[doc = include_str!("../../README.md")]
fn f() {}

    attribute ـِ doc گزینه‌های بیشتری هم دارد! این گزینه‌ها به متن خروجی مربوط نمی‌شوند، بلکه به جنبه‌های گوناگون نمایش خروجی مربوط‌اند. ما آن‌ها را در زیر به دو نوع تقسیم کرده‌ایم: attributeهایی که در سطح crate مفیدند و آن‌هایی که در سطح آیتم مفیدند.

    در سطح crate

    این گزینه‌ها نحوهٔ ظاهر مستندات را در سطح crate کنترل می‌کنند.

    html_favicon_url

    این شکل از attribute ـِ doc به شما امکان می‌دهد favicon مستنداتتان را کنترل کنید.

    #![doc(html_favicon_url = "https://example.com/favicon.ico")]

    این کار <link rel="icon" href="{}"> را در مستندات شما قرار می‌دهد، که رشتهٔ مقدار attribute در جای {} می‌نشیند.

    اگر از این attribute استفاده نکنید، یک favicon پیش‌فرض به کار می‌رود.

    html_logo_url

    این شکل از attribute ـِ doc به شما امکان می‌دهد لوگوی بالا سمت چپ مستندات را کنترل کنید.

    #![doc(html_logo_url = "https://example.com/logo.jpg")]

    این کار <a href='../index.html'><img src='{}' alt='logo' width='100'></a> را در مستندات شما قرار می‌دهد، که رشتهٔ مقدار attribute در جای {} می‌نشیند.

    اگر از این attribute استفاده نکنید، هیچ لوگویی نخواهد بود.

    html_playground_url

    این شکل از attribute ـِ doc به شما امکان می‌دهد مشخص کنید دکمه‌های «run» در مثال‌های مستنداتتان درخواست‌هایشان را به کجا بفرستند.

    #![doc(html_playground_url = "https://playground.example.com/")]

    اکنون وقتی روی «run» کلیک می‌کنید، دکمه یک درخواست به این دامنه می‌فرستد. URL درخواست شامل ۳ پارامتر پرس‌وجو خواهد بود:

    1. code برای کد موجود در مستندات
    2. version برای کانال Rust، مثلاً nightly، که بر اساس این تعیین می‌شود که code شامل قابلیت‌های ناپایدار هست یا نه
    3. edition برای edition ـِ Rust، مثلاً 2024

    اگر از این attribute استفاده نکنید، هیچ دکمهٔ run وجود نخواهد داشت.

    issue_tracker_base_url

    این شکل از attribute ـِ doc عمدتاً فقط برای کتابخانهٔ استاندارد مفید است؛ وقتی یک feature ناپایدار است، باید یک شمارهٔ issue برای پیگیری آن feature داده شود. rustdoc از این شماره، به‌علاوهٔ URL پایه‌ای که در اینجا داده می‌شود، برای پیوند دادن به issue ـِ پیگیری استفاده می‌کند.

    #![doc(issue_tracker_base_url = "https://github.com/rust-lang/rust/issues/")]

    html_root_url

    مقدار attribute ـِ #[doc(html_root_url = "…")] نشانی URL را برای تولید پیوند به crateهای خارجی مشخص می‌کند. وقتی rustdoc باید پیوندی به یک آیتم در یک crate خارجی تولید کند، ابتدا بررسی می‌کند که آیا آن crate خارجی به‌صورت محلی روی دیسک مستندسازی شده است یا نه، و اگر شده باشد مستقیماً به آن پیوند می‌دهد. در غیر این صورت، در صورت وجود، از URL داده‌شده با پرچم خط فرمان --extern-html-root-url استفاده می‌کند. اگر آن هم در دسترس نباشد، از مقدار html_root_url در crate خارجی استفاده می‌کند، در صورتی که موجود باشد. اگر آن هم در دسترس نباشد، آیتم‌های خارجی پیوند داده نخواهند شد.

    #![doc(html_root_url = "https://docs.rs/serde/1.0")]

    html_no_source

    به‌طور پیش‌فرض، rustdoc کد منبع برنامهٔ شما را به همراه پیوندهایی به آن در مستندات می‌گنجاند. اما اگر این را بگنجانید:

    #![doc(html_no_source)]

    چنین نخواهد کرد.

    test(no_crate_inject)

    به‌طور پیش‌فرض، rustdoc به‌طور خودکار یک خط با extern crate my_crate; به هر doctest اضافه می‌کند. اما اگر این را بگنجانید:

    #![doc(test(no_crate_inject))]

    چنین نخواهد کرد.

    در سطح آیتم

    این شکل‌های attribute ـِ #[doc] روی آیتم‌های منفرد به کار می‌روند تا نحوهٔ مستندسازی آن‌ها را کنترل کنند.

    inline و no_inline

    این attributeها روی دستورهای use به کار می‌روند و کنترل می‌کنند که مستندات در کجا ظاهر شوند. برای مثال، این کد Rust را در نظر بگیرید:

    pub use bar::Bar;

/// bar docs
pub mod bar {
    /// the docs for Bar
    pub struct Bar;
}
fn main() {}

    مستندات یک بخش «Re-exports» تولید می‌کند و pub use bar::Bar; را نشان می‌دهد، که در آن Bar پیوندی به صفحهٔ خودش است.

    اگر خط use را این‌گونه تغییر دهیم:

    #[doc(inline)]
pub use bar::Bar;
pub mod bar { pub struct Bar; }
fn main() {}

    در عوض، Bar در بخش Structs ظاهر خواهد شد، درست مثل این‌که Bar در سطح بالا تعریف شده باشد، نه این‌که با pub use آورده شده باشد.

    بیایید مثال اولیه‌مان را با خصوصی کردن bar تغییر دهیم:

    pub use bar::Bar;

/// bar docs
mod bar {
    /// the docs for Bar
    pub struct Bar;
}
fn main() {}

    در اینجا، چون bar عمومی نیست، bar صفحهٔ مخصوص خودش را نخواهد داشت، پس جایی برای پیوند دادن وجود ندارد. rustdoc این تعریف‌ها را درون‌خط می‌کند و در نتیجه به همان حالت #[doc(inline)] بالا می‌رسیم؛ Bar در بخش Structs است، انگار که در سطح بالا تعریف شده باشد. اگر شکل no_inline این attribute را اضافه کنیم:

    #[doc(no_inline)]
pub use bar::Bar;

/// bar docs
mod bar {
    /// the docs for Bar
    pub struct Bar;
}
fn main() {}

    اکنون یک خط Re-exports خواهیم داشت و Bar به هیچ جا پیوند نخواهد داشت.

    یک حالت خاص: در Rust 2018 و جدیدتر، اگر یکی از وابستگی‌های خود را با pub use بیاورید، rustdoc آن را به‌صورت یک ماژول درون‌خط نمی‌کند مگر این‌که #[doc(inline)] را اضافه کنید.

    اگر می‌خواهید دربارهٔ قواعد درون‌خط شدن بیشتر بدانید، نگاهی به فصل re-exports بیندازید.

    hidden

    هر آیتمی که با #[doc(hidden)] علامت‌گذاری شده باشد در مستندات ظاهر نخواهد شد، مگر این‌که پرچم --document-hidden-items به کار رود.

    اطلاعات بیشتر را می‌توانید در فصل re-exports بیابید.

    alias

    این attribute یک نام مستعار را به نمایهٔ جستجو اضافه می‌کند.

    بیایید یک مثال بزنیم:

    #[doc(alias = "TheAlias")]
pub struct SomeType;

    پس اکنون، اگر «TheAlias» را در جستجو وارد کنید، SomeType نمایش داده می‌شود. البته اگر SomeType را وارد کنید، همان‌طور که انتظار می‌رود SomeType برمی‌گردد!

    مثال FFI

    این attribute به‌ویژه هنگام نوشتن binding برای یک کتابخانهٔ C مفید است. برای مثال، فرض کنید یک تابع C داریم که به این شکل است:

    int lib_name_do_something(Obj *obj);

    این تابع یک اشاره‌گر به نوع Obj می‌گیرد و یک عدد صحیح برمی‌گرداند. در Rust ممکن است این‌گونه نوشته شود:

    pub struct Obj {
    inner: *mut ffi::Obj,
}

impl Obj {
    pub fn do_something(&mut self) -> i32 {
        unsafe { ffi::lib_name_do_something(self.inner) }
    }
}

    این تابع برای استفادهٔ راحت‌تر به یک متد تبدیل شده است. اما اگر بخواهید معادل Rust برای lib_name_do_something را جستجو کنید، راهی برای این کار ندارید.

    برای دور زدن این محدودیت، کافی است #[doc(alias = "lib_name_do_something")] را روی متد do_something اضافه کنیم و مشکل حل می‌شود! اکنون کاربران می‌توانند مستقیماً در crate ما دنبال lib_name_do_something بگردند و Obj::do_something را پیدا کنند.

    test(attr(...))

    این شکل از اتریبیوت doc به شما امکان می‌دهد اتریبیوت‌های دلخواه را به همهٔ doctestهای خود اضافه کنید. برای مثال، اگر می‌خواهید doctestهایتان در صورت داشتن کد مرده (dead code) شکست بخورند، می‌توانید این را اضافه کنید:

    #![doc(test(attr(deny(dead_code))))]

mod my_mod {
    #![doc(test(attr(allow(dead_code))))] // but allow `dead_code` for this module
}

    attributeهای test(attr(..)) به فهرست attributeهای ماژول والد اضافه می‌شوند و فهرست فعلی attributeها را جایگزین نمی‌کنند. در مثال قبل، هر دو attribute حضور خواهند داشت:

    // For every doctest in `my_mod`

#![deny(dead_code)] // from the crate-root
#![allow(dead_code)] // from `my_mod`
