    چه چیزی بگنجانیم (و چه چیزی نه)

    گفتن این‌که هر چیزی در یک پروژه باید مستندسازی شود آسان است و بسیاری وقت‌ها درست هم هست، اما چگونه می‌توانیم به آنجا برسیم، و آیا چیزهایی هستند که جایی در مستندات ندارند؟

    در بالای فایل src/lib.rs یا main.rs در پروژهٔ باینری خود، attribute زیر را قرار دهید:

    #![warn(missing_docs)]

    اکنون cargo doc را اجرا کنید و خروجی را بررسی کنید. این یک نمونه است:

     Documenting docdemo v0.1.0 (/Users/username/docdemo)
warning: missing documentation for the crate
 --> src/main.rs:1:1
  |
1 | / #![warn(missing_docs)]
2 | |
3 | | fn main() {
4 | |     println!("Hello, world!");
5 | | }
  | |_^

note: the lint level is defined here
 --> src/main.rs:1:9
  |
1 | #![warn(missing_docs)]
  |         ^^^^^^^^^^^^

    Finished dev [unoptimized + debuginfo] target(s) in 2.96s

    به‌عنوان نویسندهٔ یک کتابخانه، افزودن lint ـِ #![deny(missing_docs)] راه بسیار خوبی است تا مطمئن شوید پروژه از مستندسازی خوب فاصله نمی‌گیرد، و #![warn(missing_docs)] راه مناسبی برای حرکت به سوی مستندات جامع است.

    lintهای بیشتری در فصل بعدی، Lintها، آمده‌اند.

    مثال‌ها

    البته این مثال عمداً ساده ساخته شده است، اما بخشی از قدرت مستندات در نشان دادن کدی است که دنبال کردنش آسان باشد، نه کدی که واقع‌گرایانه باشد. مستندات اغلب در مدیریت خطا میان‌بر می‌زنند، زیرا مثال‌ها می‌توانند با همهٔ تنظیمات لازم برای یک مثال ساده دنبال‌کردنشان پیچیده شود.

    Async نمونهٔ خوبی از این موضوع است. برای اجرای یک مثال async باید یک executor در دسترس باشد. مثال‌ها اغلب این بخش را کوتاه می‌کنند و به کاربران واگذار می‌کنند که بفهمند چگونه کد async را در runtime خودشان قرار دهند.

    ترجیح داده می‌شود در داخل یک مثال از unwrap() استفاده نشود، و اگر برخی از اجزای مدیریت خطا دنبال کردن مثال را بیش از حد دشوار می‌کنند، پنهان شوند.

    /// Example
/// ```rust
/// let fourtytwo = "42".parse::<u32>()?;
/// println!("{} + 10 = {}", fourtytwo, fourtytwo+10);
/// ```

    وقتی rustdoc این کد را در یک تابع main می‌پیچد، کامپایل نمی‌شود، زیرا صفت ParseIntError پیاده‌سازی نشده است. برای کمک به مخاطبانتان و هم به مجموعهٔ آزمون‌هایتان، این مثال به مقداری کد اضافی نیاز دارد:

    /// Example
/// ```rust
/// # fn main() -> Result<(), std::num::ParseIntError> {
/// let fortytwo = "42".parse::<u32>()?;
/// println!("{} + 10 = {}", fortytwo, fortytwo+10);
/// #     Ok(())
/// # }
/// ```

    مثال در صفحهٔ مستندات همان است، اما این اطلاعات اضافی برای هر کسی که بخواهد از crate شما استفاده کند در دسترس است. دربارهٔ آزمون‌ها در فصل بعدی، آزمون‌های مستندات، بیشتر می‌خوانید.

    چه چیزی را کنار بگذاریم

    برخی بخش‌های رابط عمومی شما ممکن است به‌طور پیش‌فرض در خروجی rustdoc گنجانده شوند. attribute ـِ #[doc(hidden)] می‌تواند جزئیات پیاده‌سازی را پنهان کند تا استفادهٔ اصطلاحی (idiomatic) از crate را تشویق کند.

    برای مثال، یک macro! داخلی که پیاده‌سازی crate را آسان‌تر می‌کند، وقتی در مستندات عمومی ظاهر شود می‌تواند برای کاربران به دردسر تبدیل شود. ممکن است یک نوع Error داخلی وجود داشته باشد و جزئیات impl باید پنهان شوند، همان‌طور که در API Guidelines شرح داده شده است.

    سفارشی‌سازی خروجی

    می‌توان یک فایل css سفارشی به rustdoc داد و مستندات را استایل‌دهی کرد.

    rustdoc --extend-css custom.css src/lib.rs

    یک نمونهٔ خوب از استفاده از این قابلیت برای ساخت یک تم تیره در این وبلاگ مستند شده است. فقط به یاد داشته باشید که تم تیره پیش‌تر در خروجی rustdoc گنجانده شده و با کلیک روی نماد چرخ‌دنده در بالا سمت راست در دسترس است. افزودن گزینه‌های بیشتر به تم‌ها به سادگی ساختن یک فایل .css برای تم سفارشی و استفاده از نحو زیر است:

    rustdoc --theme awesome.css src/lib.rs

    این یک نمونه از تمی جدید به نام Ayu است.
