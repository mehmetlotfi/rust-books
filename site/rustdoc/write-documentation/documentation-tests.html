    آزمون‌های مستندات (Documentation tests)

    rustdoc از اجرای مثال‌های مستندات شما به‌عنوان آزمون پشتیبانی می‌کند. این کار تضمین می‌کند که مثال‌های درون مستندات شما به‌روز و کارا هستند.

    ایدهٔ اصلی این است:

    /// # Examples
///
/// ```
/// let x = 5;
/// ```
fn f() {}

    در اینجا، سه backtick آغاز و پایان بلوک کد را مشخص می‌کنند. اگر این کد در فایلی به نام foo.rs باشد، اجرای rustdoc --test foo.rs این مثال را استخراج می‌کند و سپس آن را به‌عنوان یک آزمون اجرا می‌کند.

    لطفاً توجه کنید که به‌طور پیش‌فرض، اگر برای بلوک کد هیچ زبانی تعیین نشده باشد، rustdoc فرض می‌کند که کد Rust است. بنابراین این:

    ```rust
let x = 5;
```

    دقیقاً معادل این است:

    ```
let x = 5;
```

    با این حال نکات ظریفی وجود دارد! برای جزئیات بیشتر ادامه دهید.

    قبول یا رد شدن یک doctest

    مانند آزمون‌های واحد معمولی، doctestهای معمولی در صورتی «قبول» می‌شوند که کامپایل شوند و بدون panic اجرا شوند. بنابراین اگر می‌خواهید نشان دهید که یک محاسبه نتیجهٔ مشخصی می‌دهد، خانوادهٔ ماکروهای assert! درست مانند سایر کدهای Rust کار می‌کنند:

    let foo = "foo";
assert_eq!(foo, "foo");

    به این ترتیب، اگر محاسبه هر زمان چیز متفاوتی برگرداند، کد panic می‌کند و doctest شکست می‌خورد.

    پیش‌پردازش مثال‌ها

    در مثال بالا، چیز عجیبی می‌بینید: هیچ تابع main وجود ندارد! مجبور کردن شما به نوشتن main برای هر مثال، هر قدر هم کوچک باشد، اصطکاک ایجاد می‌کند و خروجی را شلوغ می‌کند. به همین دلیل rustdoc مثال‌های شما را پیش از اجرا اندکی پردازش می‌کند. این الگوریتم کاملی است که rustdoc برای پیش‌پردازش مثال‌ها به کار می‌برد:

    1. چند attribute ـِ allow رایج درج می‌شوند، از جمله unused_variables، unused_assignments، unused_mut، unused_attributes و dead_code. مثال‌های کوچک اغلب این lintها را فعال می‌کنند.
    2. هر attributeی که با #![doc(test(attr(...)))] مشخص شده باشد افزوده می‌شود.
    3. هر attribute ـِ #![foo] که در ابتدا آمده باشد به‌عنوان attribute سطح crate دست‌نخورده می‌ماند.
    4. اگر مثال شامل extern crate نباشد و #![doc(test(no_crate_inject))] مشخص نشده باشد، آنگاه extern crate <mycrate>; درج می‌شود (توجه کنید که #[macro_use] وجود ندارد).
    5. سرانجام، اگر مثال شامل fn main نباشد، بقیهٔ متن درون fn main() { your_code } پیچیده می‌شود.

    برای اطلاعات بیشتر دربارهٔ آن نکته در قاعدهٔ ۴، به «مستندسازی ماکروها» در ادامه مراجعه کنید.

    پنهان کردن بخش‌هایی از مثال

    گاهی به کد آماده‌سازی یا چیزهای دیگری نیاز دارید که حواس را از مثال شما پرت می‌کند، اما برای کار کردن آزمون‌ها مهم‌اند. بلوک مثالی را در نظر بگیرید که این شکل را دارد:

    /// ```
/// /// Some documentation.
/// # fn foo() {} // this function will be hidden
/// println!("Hello, World!");
/// ```
fn f() {}

    این‌گونه رندر می‌شود:

    /// Some documentation.
fn foo() {}
println!("Hello, World!");

    بله، درست است: می‌توانید خط‌هایی اضافه کنید که با # شروع می‌شوند و آن‌ها از خروجی پنهان می‌شوند، اما هنگام کامپایل کد شما به کار می‌روند. می‌توانید از این به نفع خود استفاده کنید. در این مورد، doc commentها باید روی نوعی تابع اعمال شوند، پس اگر بخواهم فقط یک doc comment را به شما نشان دهم، باید یک تعریف تابع کوچک زیر آن اضافه کنم. در عین حال، آن تابع فقط برای راضی کردن کامپایلر آنجاست، پس پنهان کردنش مثال را روشن‌تر می‌کند. می‌توانید از این تکنیک برای توضیح مثال‌های طولانی‌تر با جزئیات استفاده کنید، بی‌آن‌که آزمون‌پذیری مستنداتتان از بین برود.

    برای مثال، تصور کنید می‌خواهیم این کد را مستندسازی کنیم:

    let x = 5;
let y = 6;
println!("{}", x + y);

    ممکن است بخواهیم مستندات در نهایت این شکل را داشته باشند:

    ابتدا x را برابر پنج قرار می‌دهیم:

    let x = 5;
let y = 6;
println!("{}", x + y);

    سپس y را برابر شش قرار می‌دهیم:

    let x = 5;
let y = 6;
println!("{}", x + y);

    و در پایان، مجموع x و y را چاپ می‌کنیم:

    let x = 5;
let y = 6;
println!("{}", x + y);

    برای این‌که هر بلوک کد آزمون‌پذیر بماند، می‌خواهیم کل برنامه در هر بلوک باشد، اما نمی‌خواهیم خواننده هر بار همهٔ خطوط را ببیند. این چیزی است که در کد منبع خود می‌گذاریم:

    First, we set `x` to five:

```
let x = 5;
# let y = 6;
# println!("{}", x + y);
```

Next, we set `y` to six:

```
# let x = 5;
let y = 6;
# println!("{}", x + y);
```

Finally, we print the sum of `x` and `y`:

```
# let x = 5;
# let y = 6;
println!("{}", x + y);
```

    با تکرار همهٔ بخش‌های مثال، می‌توانید مطمئن شوید که مثال شما همچنان کامپایل می‌شود، در حالی که فقط بخش‌هایی را نشان می‌دهید که به آن قسمت از توضیحتان مربوط‌اند.

    می‌توان از پنهان شدن خط‌ها با # جلوگیری کرد، با استفاده از دو هش پشت‌سرهم ##. این کار فقط برای نخستین # لازم است که در غیر این صورت باعث پنهان شدن می‌شد. اگر یک رشتهٔ لیترال مانند زیر داشته باشیم که خطی دارد که با # شروع می‌شود:

    let s = "foo
# bar # baz";

    می‌توانیم با escape کردن # ابتدایی آن را مستندسازی کنیم:

    /// let s = "foo
/// ## bar # baz";

    این هم مثالی با یک قاعدهٔ ماکرو که با توکن‌هایی که با # شروع می‌شوند تطبیق می‌یابد:

    /// ```
/// macro_rules! ignore { (##tag) => {}; }
/// ignore! {
///     ###tag
/// }
/// ```
fn f() {}

    همان‌طور که می‌بینید، قاعده دو # انتظار دارد، پس هنگام فراخوانی آن باید یک # اضافه بنویسیم زیرا نخستین # به‌عنوان escape به کار می‌رود.

    استفاده از ? در آزمون‌های مستندات

    هنگام نوشتن یک مثال، گنجاندن مدیریت کامل خطا به‌ندرت مفید است، زیرا مقدار قابل‌توجهی کد تکراری (boilerplate) اضافه می‌کند. در عوض، ممکن است چنین چیزی بخواهید:

    /// ```
/// use std::io;
/// let mut input = String::new();
/// io::stdin().read_line(&mut input)?;
/// ```
fn f() {}

    مشکل این است که ? یک Result<T, E> برمی‌گرداند و تابع‌های آزمون چیزی برنمی‌گردانند، بنابراین این کد خطای ناسازگاری نوع‌ها می‌دهد.

    می‌توانید با افزودن دستی یک main که Result<T, E> برمی‌گرداند این محدودیت را دور بزنید، زیرا Result<T, E> صفت Termination را پیاده‌سازی می‌کند:

    /// A doc test using ?
///
/// ```
/// use std::io;
///
/// fn main() -> io::Result<()> {
///     let mut input = String::new();
///     io::stdin().read_line(&mut input)?;
///     Ok(())
/// }
/// ```
fn f() {}

    با کمک # از بخش بالا، به راه‌حلی می‌رسید که برای خواننده همان ایدهٔ اولیه به نظر می‌رسد اما با آزمون‌های مستندات کار می‌کند:

    /// ```
/// use std::io;
/// # fn main() -> io::Result<()> {
/// let mut input = String::new();
/// io::stdin().read_line(&mut input)?;
/// # Ok(())
/// # }
/// ```
fn f() {}

    از نسخهٔ 1.34.0 به بعد، می‌توان fn main() را هم حذف کرد، اما باید نوع خطا را مشخص کنید:

    /// ```
/// use std::io;
/// let mut input = String::new();
/// io::stdin().read_line(&mut input)?;
/// # Ok::<(), io::Error>(())
/// ```
fn f() {}

    این پیامد ناخوشایند آن است که عملگر ? یک تبدیل ضمنی اضافه می‌کند، پس استنتاج نوع شکست می‌خورد چون نوع یکتا نیست. لطفاً توجه کنید که باید (()) را پشت‌سرهم و بدون فاصلهٔ میانی بنویسید تا rustdoc بفهمد شما یک تابع ضمنی برگرداننده Result می‌خواهید.

    نمایش هشدارها در doctestها

    می‌توانید با اجرای rustdoc --test --test-args=--show-output (یا اگر از cargo استفاده می‌کنید، cargo test --doc -- --show-output) هشدارها را در doctestها نشان دهید. به‌طور پیش‌فرض، این کار همچنان هشدارهای unused را پنهان می‌کند، زیرا بسیاری از مثال‌ها از تابع‌های خصوصی استفاده می‌کنند؛ اگر می‌خواهید هشدارهای متغیرهای استفاده‌نشده یا کد مرده را ببینید، می‌توانید #![warn(unused)] را در بالای مثال خود اضافه کنید. همچنین می‌توانید برای فعال کردن هشدارها به‌صورت سراسری از #![doc(test(attr(warn(unused))))] در ریشهٔ crate استفاده کنید.

    مستندسازی ماکروها

    این مثالی از مستندسازی یک ماکرو است:

    /// Panic with a given message unless an expression evaluates to true.
///
/// # Examples
///
/// ```
/// # #[macro_use] extern crate foo;
/// # fn main() {
/// panic_unless!(1 + 1 == 2, “Math is broken.”);
/// # }
/// ```
///
/// ```should_panic
/// # #[macro_use] extern crate foo;
/// # fn main() {
/// panic_unless!(true == false, “I’m broken.”);
/// # }
/// ```
#[macro_export]
macro_rules! panic_unless {
    ($condition:expr, $($rest:expr),+) => ({ if ! $condition { panic!($($rest),+); } });
}
fn main() {}

    سه نکته را باید توجه کنید: باید خط extern crate خودمان را اضافه کنیم تا بتوانیم attribute ـِ #[macro_use] را بیفزاییم. دوم، باید main() خودمان را هم اضافه کنیم (به دلایلی که در بالا بحث شد). و سرانجام، استفادهٔ سنجیدهٔ # برای کامنت کردن آن دو مورد، تا در خروجی ظاهر نشوند.

    attributeها

    بلوک‌های کد را می‌توان با attributeهایی علامت‌گذاری کرد که به rustdoc می‌گویند آزمون را چگونه بسازد و تفسیر کند. این attributeها در خط آغازین، پس از حصار کد (code fence) می‌آیند. به همین دلیل، جایگاهشان را با رشته‌های زبان مانند rust یا text مشترک دارند. می‌توان چند attribute را با جدا کردن آن‌ها با ویرگول، فاصله یا tab ارائه کرد. همچنین می‌توانید توضیحاتی بنویسید که میان پرانتز (…) قرار می‌گیرند.

    همان‌طور که در مقدمهٔ ابتدای صفحه اشاره شد، مگر این‌که rust یا چیزی را مشخص کنید که attribute نیست (به‌جز custom)، بلوک کد کد منبع Rust فرض می‌شود (و به همین صورت syntax highlight می‌شود).

    البته اگر Markdown توسط ابزارهای دیگر هم مصرف می‌شود (مثلاً اگر درون یک README.md باشد که از طریق include_str گنجانده می‌شود)، می‌توانید rust را صریحاً اضافه کنید (مانند rust,ignore).

    ignore

    attribute ـِ ignore به rustdoc می‌گوید کد شما را نادیده بگیرد. این زمانی مفید است که می‌خواهید syntax highlighting مخصوص Rust را داشته باشید اما قطعه‌کد ناقص یا شبه‌کد است. رسم است دلیل نادیده گرفته شدن را در یک کامنت (…) بنویسید.

    /// ```ignore
/// fn foo() {
/// ```
///
/// ```ignore (needs extra dependency)
/// use dependency::functionality;
/// functionality();
/// ```
fn foo() {}

    توجه کنید که تقریباً هرگز این چیزی نیست که می‌خواهید، زیرا کلی‌ترین حالت است. در عوض، اگر کد نیست آن را با text علامت‌گذاری کنید، یا با استفاده از # مثالی کارا بسازید که فقط بخش مورد نظر شما را نشان دهد.

    should_panic

    should_panic به rustdoc می‌گوید که کد باید درست کامپایل شود اما هنگام اجرا panic کند. اگر کد panic نکند، آزمون شکست می‌خورد.

    /// ```should_panic
/// assert!(false);
/// ```
fn foo() {}

    no_run

    attribute ـِ no_run کد شما را کامپایل می‌کند اما اجرا نمی‌کند. این برای مثال‌هایی مانند «این‌گونه یک صفحهٔ وب را دریافت کنید» مهم است، که می‌خواهید مطمئن شوید کامپایل می‌شوند، اما ممکن است در یک محیط آزمون بدون دسترسی به شبکه اجرا شوند. این attribute همچنین برای نمایش قطعه‌کدهایی که می‌توانند باعث رفتار تعریف‌نشده (Undefined Behavior) شوند به کار می‌رود.

    /// ```no_run
/// loop {
///     println!("Hello, world");
/// }
/// ```
fn foo() {}

    compile_fail

    compile_fail به rustdoc می‌گوید که کامپایل باید شکست بخورد. اگر کامپایل شود، آزمون شکست می‌خورد.

    /// ```compile_fail
/// let x = 5;
/// x += 2; // shouldn't compile!
/// ```
fn foo() {}
    با این حال، لطفاً توجه کنید که کدی که با نسخهٔ فعلی Rust شکست می‌خورد، ممکن است در نسخه‌ای آینده کار کند، چون قابلیت‌های جدید افزوده می‌شوند!

    edition…

    edition2015، edition2018، edition2021 و edition2024 به rustdoc می‌گویند که نمونه‌کد باید با edition متناظر Rust کامپایل شود.

    /// Only runs on the 2018 edition.
///
/// ```edition2018
/// let result: Result<i32, ParseIntError> = try {
///     "1".parse::<i32>()?
///         + "2".parse::<i32>()?
///         + "3".parse::<i32>()?
/// };
/// ```
fn foo() {}

    standalone_crate

    از edition ـِ 2024 به بعد1، doctestهای سازگار پیش از اجرا در یکی ادغام می‌شوند. ما به دلایل کارایی doctestها را ترکیب می‌کنیم: کندترین بخش doctestها کامپایل آن‌هاست. ادغام همهٔ آن‌ها در یک فایل و کامپایل این فایل جدید و سپس اجرای doctestها بسیار سریع‌تر است. چه doctestها ادغام شوند چه نشوند، هر کدام در پردازهٔ جداگانهٔ خود اجرا می‌شوند.

    نمونه‌ای از زمان صرف‌شده هنگام اجرای doctestها:

    crate با نام sysinfo:

    wall-time duration: 4.59s
total compile time: 27.067s
total runtime: 3.969s

    کتابخانهٔ core در Rust:

    wall-time duration: 102s
total compile time: 775.204s
total runtime: 15.487s

    در برخی موارد، doctestها را نمی‌توان ادغام کرد. برای مثال، اگر این را داشته باشید:

    //! ```
//! let location = std::panic::Location::caller();
//! assert_eq!(location.line(), 4);
//! ```

    مشکل این کد آن است که اگر هر doctest دیگری را تغییر دهید، احتمالاً هنگام اجرای rustdoc --test می‌شکند و نگهداری آن را دشوار می‌کند.

    اینجاست که attribute ـِ standalone_crate وارد می‌شود: به rustdoc می‌گوید که یک doctest نباید با بقیه ادغام شود. پس کد قبلی باید از آن استفاده کند:

    //! ```standalone_crate
//! let location = std::panic::Location::caller();
//! assert_eq!(location.line(), 4);
//! ```

    در این حالت، این یعنی با افزودن/حذف doctestهای دیگر، اطلاعات شمارهٔ خط تغییر نخواهد کرد.

    ignore-…: نادیده گرفتن هدف‌ها

    attributeهایی که با ignore- شروع می‌شوند می‌توانند برای نادیده گرفتن doctestها در هدف‌های مشخص به کار روند. برای مثال، ignore-x86_64 از ساخت doctestها جلوگیری می‌کند هرگاه نام هدف شامل x86_64 باشد.

    /// ```ignore-x86_64
/// assert!(2 == 2);
/// ```
struct Foo;

    این doctest برای هدف‌هایی مانند x86_64-unknown-linux-gnu ساخته نخواهد شد.

    می‌توان چند attribute ـِ ignore را برای نادیده گرفتن چند هدف مشخص کرد:

    /// ```ignore-x86_64,ignore-windows
/// assert!(2 == 2);
/// ```
struct Foo;

    اگر می‌خواهید سازگاری با نسخه‌های قدیمی‌تر rustdoc را حفظ کنید، می‌توانید هم ignore و هم ignore- را مشخص کنید، مانند:

    /// ```ignore,ignore-x86_64
/// assert!(2 == 2);
/// ```
struct Foo;

    در نسخه‌های قدیمی‌تر، این روی همهٔ هدف‌ها نادیده گرفته می‌شود، اما از نسخهٔ 1.88.0 به بعد، ignore-x86_64 بر ignore غلبه می‌کند.

    {…} و custom: کلاس‌های CSS سفارشی برای بلوک‌های کد

    /// ```custom,{class=language-c}
/// int main(void) { return 0; }
/// ```
pub struct Bar;

    متن int main(void) { return 0; } بدون highlight در یک بلوک کد با کلاس language-c رندر می‌شود. برای مثال می‌توان از این برای highlight کردن زبان‌های دیگر از طریق کتابخانه‌های جاوااسکریپت استفاده کرد.

    بدون attribute ـِ custom، این به‌صورت یک مثال کد Rust با یک کلاس CSS اضافی language-C تولید می‌شد. بنابراین اگر به‌طور خاص نمی‌خواهید که مثال کد Rust باشد، فراموش نکنید attribute ـِ custom را اضافه کنید.

    شایان ذکر است که می‌توانید class= را با . جایگزین کنید تا همان نتیجه را بگیرید:

    /// ```custom,{.language-c}
/// int main(void) { return 0; }
/// ```
pub struct Bar;

    شایان ذکر است که rust و {.rust} / {class=rust} اثرهای متفاوتی دارند: rust نشان می‌دهد که این یک بلوک کد Rust است، در حالی که دو مورد دیگر یک کلاس CSS با نام «rust» به بلوک کد در HTML تولیدشده اضافه می‌کنند.

    همچنین می‌توانید از نقل‌قول دوتایی استفاده کنید:

    /// ```"not rust" {."hello everyone"}
/// int main(void) { return 0; }
/// ```
pub struct Bar;

    test_harness

    با اعمال test_harness، rustdoc هر تابع آزمونِ موجود را به‌جای تابع main (که ممکن است ضمنی باشد) اجرا می‌کند.

    //! ```test_harness
//! #[test]
//! #[should_panic]
//! fn abc() { assert!(false); }
//!
//! #[test]
//! fn xyz() { assert!(true); }
//! ```

    دربارهٔ تابع‌های آزمون می‌توانید در کتاب یا مرجع Rust بیشتر بخوانید.

    مرجع نحو

    نحو دقیق بلوک‌های کد، شامل حالت‌های مرزی، را می‌توانید در بخش Fenced Code Blocks از مشخصات CommonMark بیابید.

    Rustdoc بلوک‌های کد تورفته را هم به‌عنوان جایگزینی برای بلوک‌های کد محصور می‌پذیرد: به‌جای احاطه کردن کد خود با یک حصار کد (مثلاً سه backtick)، می‌توانید هر خط را با چهار فاصله یا بیشتر تورفته کنید.

        let foo = "foo";
    assert_eq!(foo, "foo");

    این‌ها نیز در مشخصات CommonMark، در بخش Indented Code Blocks، مستند شده‌اند.

    با این حال، ترجیح داده می‌شود به‌جای بلوک‌های کد تورفته از بلوک‌های کد محصور استفاده شود. نه‌تنها بلوک‌های کد محصور برای کد Rust اصطلاحی‌تر (idiomatic) شمرده می‌شوند، بلکه راهی برای استفاده از attributeهایی مانند ignore یا should_panic با بلوک‌های کد تورفته وجود ندارد.

    گنجاندن آیتم‌ها فقط هنگام جمع‌آوری doctestها

    آزمون‌های مستندات Rustdoc می‌توانند کارهایی بکنند که آزمون‌های واحد معمولی نمی‌توانند، بنابراین گاهی می‌تواند مفید باشد که doctestهای خود را با نمونه‌هایی گسترش دهید که در غیر این صورت نیازی نبود در مستندات باشند. برای این منظور، Rustdoc به شما اجازه می‌دهد برخی آیتم‌ها فقط هنگامی ظاهر شوند که doctestها را جمع‌آوری می‌کند، تا بتوانید از قابلیت doctest استفاده کنید بی‌آن‌که آزمون را مجبور به ظاهر شدن در مستندات کنید، یا مجبور شوید یک آیتم خصوصی دلخواه پیدا کنید تا آن را روی آن قرار دهید.

    هنگام کامپایل یک crate برای استفاده در doctestها (با گزینهٔ --test)، rustdoc مقدار #[cfg(doctest)] را تنظیم می‌کند. توجه کنید که آن‌ها همچنان فقط به آیتم‌های عمومی crate شما لینک می‌شوند؛ اگر لازم است آیتم‌های خصوصی را آزمون کنید، باید یک آزمون واحد بنویسید.

    در این مثال، doctestهایی اضافه می‌کنیم که می‌دانیم کامپایل نخواهند شد، تا بررسی کنیم که ساختار ما فقط می‌تواند داده‌های معتبر را بپذیرد:

    /// We have a struct here. Remember it doesn't accept negative numbers!
pub struct MyStruct(pub usize);

/// ```compile_fail
/// let x = my_crate::MyStruct(-5);
/// ```
#[cfg(doctest)]
pub struct MyStructOnlyTakesUsize;

    توجه کنید که ساختار MyStructOnlyTakesUsize در اینجا در واقع بخشی از API عمومی crate شما نیست. استفاده از #[cfg(doctest)] تضمین می‌کند که این ساختار فقط وقتی وجود دارد که rustdoc در حال جمع‌آوری doctestهاست. یعنی doctest آن هنگامی اجرا می‌شود که --test به rustdoc داده شود، اما از مستندات عمومی پنهان است.

    کاربرد ممکن دیگر #[cfg(doctest)] آزمودن doctestهایی است که در فایل README شما گنجانده شده‌اند، بی‌آن‌که آن را در مستندات اصلی خود بگنجانید. برای مثال، می‌توانید این را در lib.rs بنویسید تا README خود را به‌عنوان بخشی از doctestهایتان آزمون کنید:

    #[doc = include_str!("../README.md")]
#[cfg(doctest)]
pub struct ReadmeDoctests;

    این کار README شما را به‌عنوان مستندات روی ساختار پنهان ReadmeDoctests می‌گنجاند و سپس همراه با بقیهٔ doctestهای شما آزمون می‌شود.

    کنترل پوشه‌های کامپایل و اجرا

    به‌طور پیش‌فرض، rustdoc --test مثال‌های آزمون مستندات را از همان پوشهٔ کاری کامپایل و اجرا می‌کند. پوشهٔ کامپایل برای تشخیص‌های کامپایلر، ماکروی file!() و خروجی خودِ اجراکنندهٔ آزمون rustdoc به کار می‌رود، در حالی که پوشهٔ اجرا بر عملیات سیستم فایل درون مثال‌های آزمون مستندات اثر می‌گذارد، مانند std::fs::read_to_string.

    پرچم --test-run-directory اجازه می‌دهد پوشهٔ اجرا را جدا از پوشهٔ کامپایل کنترل کنید. این به‌ویژه در workspaceها مفید است، جایی که فراخوانی‌های کامپایلر و در نتیجه تشخیص‌ها باید نسبت به پوشهٔ workspace باشند، اما مثال‌های آزمون مستندات باید نسبت به پوشهٔ crate اجرا شوند.
