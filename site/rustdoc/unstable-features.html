    قابلیت‌های ناپایدار

    Rustdoc در حال توسعهٔ فعال است و مانند کامپایلر Rust، برخی قابلیت‌هایش فقط در نسخه‌های nightly در دسترس‌اند. برخی از این قابلیت‌ها جدیدند و پیش از آن‌که بتوانند در اختیار عموم قرار بگیرند به آزمون بیشتری نیاز دارند، و برخی به قابلیت‌های ناپایدار کامپایلر Rust وابسته‌اند. چند قابلیت در اینجا برای فعال شدن به یک attribute ـِ #![feature(...)] متناظر نیاز دارند و بنابراین در کتاب قابلیت‌های ناپایدار به‌طور کامل‌تری مستند شده‌اند. آن بخش‌ها در صورت نیاز به آنجا پیوند می‌دهند.

    قابلیت‌های مشروط به nightly

    این قابلیت‌ها فقط به یک ساخت nightly نیاز دارند. برخلاف سایر قابلیت‌های این صفحه، لازم نیست با یک پرچم خط فرمان یا یک attribute ـِ #![feature(...)] در crate شما «روشن» شوند. این موضوع می‌تواند باعث شود هنگام استفاده در نسخهٔ stable حالت‌های جایگزین ظریفی داشته باشند، پس مراقب باشید!

    شمارهٔ خطا برای doctestهای compile-fail

    همان‌طور که در فصل مربوط به آزمون‌های مستندات شرح داده شده، می‌توانید attribute ـِ compile_fail را به یک doctest اضافه کنید تا بگویید آزمون باید در کامپایل شکست بخورد. اما در nightly می‌توانید به‌طور اختیاری یک شمارهٔ خطا هم اضافه کنید تا بگویید یک doctest باید یک شمارهٔ خطای مشخص صادر کند:

    ```compile_fail,E0044
extern { fn some_func<T>(x: T); }
```

    این در فهرست خطاها (error index) به کار می‌رود تا اطمینان حاصل شود نمونه‌هایی که با یک شمارهٔ خطا متناظرند آن کد خطا را درست صادر می‌کنند. با این حال، تضمینی وجود ندارد که این کدهای خطا از نسخه‌ای به نسخهٔ دیگر تنها چیزی باشند که یک قطعه کد صادر می‌کند، بنابراین بعید است این قابلیت در آینده پایدار شود.

    تلاش برای استفاده از این شماره‌های خطا در نسخهٔ stable باعث می‌شود نمونه‌کد به‌عنوان متن ساده تفسیر شود.

    lint ـِ missing_doc_code_examples

    این lint در صورتی که یک آیتم در مستنداتش مثال کد نداشته باشد هشدار صادر می‌کند. می‌توان آن را با این روش فعال کرد:

    #![deny(rustdoc::missing_doc_code_examples)]

    این lint برای آیتم‌هایی که نمی‌توان از آن‌ها نمونه ساخت یا آن‌ها را فراخوانی کرد صادر نمی‌شود، مانند فیلدها، واریانت‌ها، ماژول‌ها، آیتم‌های وابستهٔ صفت/impl، بلوک‌های impl، staticها و ثابت‌ها. همچنین برای آیتم‌های خارجی، نام‌های مستعار، crateهای extern و importها صادر نمی‌شود.

    افزونه‌هایی برای attribute ـِ #[doc]

    این قابلیت‌ها با گسترش attribute ـِ #[doc] کار می‌کنند و بنابراین کامپایلر می‌تواند آن‌ها را بگیرد و با یک attribute ـِ #![feature(...)] در crate شما فعال شوند.

    افزودن صفت خود به پنجرهٔ «Notable traits»

    • issue پیگیری: #45040

    Rustdoc فهرستی از چند صفت نگه می‌دارد که برای نوع‌هایی که آن‌ها را پیاده‌سازی می‌کنند «بنیادین» تلقی می‌شوند. این صفت‌ها قرار است رابط اصلی پیاده‌سازهایشان باشند و اغلب بیشتر API قابل مستندسازی روی آن نوع‌ها را تشکیل می‌دهند. به همین دلیل، Rustdoc رصد می‌کند که یک نوع چه زمانی یکی از این صفت‌ها را پیاده‌سازی می‌کند و هنگامی که یک تابع یکی از این نوع‌ها را برمی‌گرداند، توجه ویژه‌ای به آن جلب می‌کند. این همان پنجرهٔ «Notable traits» است که به‌صورت یک دکمهٔ دایره‌ای i در کنار تابع در دسترس است و با کلیک روی آن پنجره نمایش داده می‌شود.

    در کتابخانهٔ استاندارد، برخی از صفت‌هایی که جزو این فهرست‌اند Iterator، Future، io::Read و io::Write هستند. با این حال، به‌جای پیاده‌سازی به‌صورت یک فهرست ثابت، این صفت‌ها یک attribute نشانگر ویژه دارند: #[doc(notable_trait)]. یعنی می‌توانید این attribute را روی صفت خودتان اعمال کنید تا در پنجرهٔ «Notable traits» در مستندات گنجانده شود.

    علاوه بر پنجرهٔ «Notable traits»، هر نوعی که یک صفت #[doc(notable_trait)] را پیاده‌سازی کند، یک نشان رنگی برای آن صفت در بالای صفحهٔ خود نشان می‌دهد تا هنگام مرور نوع، این رابطه به‌سادگی دیده شود.

    attribute ـِ #[doc(notable_trait)] در حال حاضر به feature gate ـِ #![feature(doc_notable_trait)] نیاز دارد. برای اطلاعات بیشتر، فصل مربوط به آن در کتاب قابلیت‌های ناپایدار و issue پیگیری آن را ببینید.

    کنار گذاشتن برخی وابستگی‌ها از مستندات

    • issue پیگیری: #44027

    کتابخانهٔ استاندارد از چند وابستگی استفاده می‌کند که آن‌ها نیز به نوبهٔ خود از چند نوع و صفت از کتابخانهٔ استاندارد استفاده می‌کنند. علاوه بر این، چند crate داخلی کامپایلر وجود دارند که جزو کتابخانهٔ استاندارد رسمی شمرده نمی‌شوند و در نتیجه گنجاندنشان در مستندات حواس‌پرتی ایجاد می‌کند. کنار گذاشتن مستندات crate آن‌ها کافی نیست، زیرا اطلاعات مربوط به پیاده‌سازی‌های صفت هم در صفحهٔ نوع و هم در صفحهٔ صفت ظاهر می‌شود، که ممکن است در crateهای متفاوتی باشند!

    برای جلوگیری از گنجانده شدن نوع‌های داخلی در مستندات، کتابخانهٔ استاندارد یک attribute به اعلان‌های extern crate آن‌ها اضافه می‌کند: #[doc(masked)]. این باعث می‌شود Rustdoc هنگام ساختن فهرست پیاده‌سازی‌های صفت، نوع‌های این crateها را «ماسک کند».

    attribute ـِ #[doc(masked)] برای استفادهٔ داخلی در نظر گرفته شده و به feature gate ـِ #![feature(doc_masked)] نیاز دارد. برای اطلاعات بیشتر، فصل مربوط به آن در کتاب قابلیت‌های ناپایدار و issue پیگیری آن را ببینید.

    مستندسازی نوع‌های اولیه

    این فقط برای استفادهٔ داخلی کامپایلر Rust است.

    از آنجا که نوع‌های اولیه (primitive) در کامپایلر تعریف می‌شوند، جایی برای متصل کردن attributeهای مستندات وجود ندارد. attribute ـِ #[rustc_doc_primitive = "..."] توسط کتابخانهٔ استاندارد به کار می‌رود تا راهی برای تولید مستندات نوع‌های اولیه فراهم کند و برای فعال شدن به #![feature(rustc_attrs)] نیاز دارد.

    مستندسازی کلیدواژه‌ها

    این برای استفادهٔ داخلی در کتابخانهٔ std است.

    کلیدواژه‌های Rust در کتابخانهٔ استاندارد مستند شده‌اند (برای نمونه match را جستجو کنید).

    برای این کار، از attribute ـِ #[doc(keyword = "...")] استفاده می‌شود. مثال:

    #![feature(rustdoc_internals)]
#![allow(internal_features)]

/// Some documentation about the keyword.
#[doc(keyword = "break")]
const _: () = ();

    مستندسازی attributeهای داخلی

    این برای استفادهٔ داخلی در کتابخانهٔ std است.

    attributeهای داخلی Rust در کتابخانهٔ استاندارد مستند شده‌اند (برای نمونه repr را جستجو کنید).

    برای این کار، از attribute ـِ #[doc(attribute = "...")] استفاده می‌شود. مثال:

    #![feature(rustdoc_internals)]
#![allow(internal_features)]

/// Some documentation about the attribute.
#[doc(attribute = "repr")]
const _: () = ();

    استفاده از لوگوی Rust به‌عنوان لوگوی crate

    این فقط برای استفادهٔ پروژهٔ رسمی Rust است.

    صفحه‌های داخلی Rustdoc مانند settings.html و scrape-examples-help.html لوگوی Rust را نشان می‌دهند. این لوگو به‌عنوان یک منبع ایستا ردیابی می‌شود. attribute ـِ #![doc(rust_logo)] باعث می‌شود همین منبع داخلی به‌عنوان لوگوی اصلی عمل کند.

    #![feature(rustdoc_internals)]
#![allow(internal_features)]
#![doc(rust_logo)]
//! This crate has the Rust(tm) branding on it.

    اثرات سایر قابلیت‌های nightly

    این قابلیت‌های فقط-nightly عمدتاً به Rustdoc مربوط نیستند، اما اثرات مناسبی بر مستندات تولیدشده دارند.

    نوع‌های fundamental

    علامت‌گذاری یک نوع با #[fundamental] عمدتاً بر قواعد انسجام (coherence) دربارهٔ نوع‌های جنریک اثر می‌گذارد، یعنی تغییر می‌دهد که آیا crateهای دیگر می‌توانند برای آن نوع پیاده‌سازی ارائه دهند یا نه. کتاب قابلیت‌های ناپایدار به اطلاعات بیشتر پیوند می‌دهد.

    برای مستندات، این یک اثر جانبی اضافی دارد: اگر یک متد روی F<T> (یا F<&T>) پیاده‌سازی شده باشد، که در آن F یک نوع fundamental است، آنگاه آن متد نه‌تنها در صفحهٔ F مستند می‌شود، بلکه در صفحهٔ T نیز مستند می‌شود. به‌گونه‌ای، این کار نوع را برای Rustdoc شفاف می‌کند. این به‌ویژه برای نوع‌هایی که مانند اشاره‌گرهای حاشیه‌نویسی‌شده کار می‌کنند، مانند Pin<&mut T>، مناسب است، زیرا تضمین می‌کند متدهایی که فقط از طریق آن اشاره‌گرهای حاشیه‌نویسی‌شده پیاده‌سازی شده‌اند همچنان با نوعی که روی آن عمل می‌کنند قابل یافتن باشند.

    اگر اثر قابلیت fundamental بر coherence مطلوب نیست، می‌توان چنین نوعی را فقط برای اهداف مستندسازی fundamental علامت زد، با معرفی یک feature سفارشی و محدود کردن استفاده از fundamental به زمانی که مستندات ساخته می‌شوند.

    آرگومان‌های ناپایدار خط فرمان

    این قابلیت‌ها با دادن یک پرچم خط فرمان به Rustdoc فعال می‌شوند، اما خود آن پرچم‌ها به‌عنوان ناپایدار علامت‌گذاری شده‌اند. برای استفاده از هر یک از این گزینه‌ها، علاوه بر پرچم مورد نظر، -Z unstable-options را نیز در خط فرمان به Rustdoc بدهید. برای انجام این کار از Cargo، می‌توانید از متغیر محیطی RUSTDOCFLAGS یا فرمان cargo rustdoc استفاده کنید.

    --write-doc-meta-dir و --read-doc-meta-dir

    این گزینه‌ها کنترل می‌کنند rustdoc با فایل‌هایی که داده‌های چند crate را ترکیب می‌کنند چگونه رفتار کند.

    به‌طور پیش‌فرض، rustdoc فراداده‌های مستندات را از خود پوشهٔ خروجی مستندات می‌خواند و با هم ادغام می‌کند. این در اسکریپت‌هایی که rustdoc را به‌صورت دستی فراخوانی می‌کنند بسیار آسان است، اما کند هم هست، زیرا برای هر crate کاری از مرتبهٔ O(crates) انجام می‌دهد، یعنی در مجموع کاری از مرتبهٔ O(crates2) انجام می‌دهد. وقتی --write-doc-meta-dir و/یا --read-doc-meta-dir داده شوند، این رفتار خاموش می‌شود.

    وقتی --write-doc-meta-dir داده شود، rustdoc فراداده‌های مشترک crate را در آن پوشه می‌نویسد. این یک حالت میانی است که در آن ممکن است برخی فایل‌ها را در پوشهٔ خروجی مستندات بنویسد، اما برخی قابلیت‌ها تا زمان نهایی شدن کار نخواهند کرد.

    وقتی --read-doc-meta-dir داده شود، rustdoc در حالت نهایی‌سازی (finalize) اجرا می‌شود. در این حالت هیچ کد منبع crate ای به rustdoc داده نمی‌شود. می‌توان چند --read-doc-meta-dir را به rustdoc داد، بنابراین سیستم ساخت شما می‌تواند در صورت لزوم وضعیت را بین چند پوشه تقسیم کند.

    --write-doc-meta-dir و --read-doc-meta-dir را نمی‌توان هر دو به یک فراخوانی rustdoc داد.

    $ rustdoc crate1.rs --out-dir=doc
$ cat doc/search.index/crateNames/*
rd_("fcrate1")
$ rustdoc crate2.rs --out-dir=doc
$ cat doc/search.index/crateNames/*
rd_("fcrate1fcrate2")

    برای به تعویق انداختن ادغام داده‌های مشترک تا پایان ساخت، تا فقط لازم باشد کاری از مرتبهٔ O(crates) انجام دهید، روی هر crate از --write-doc-meta-dir استفاده کنید و آخرین مورد از --read-doc-meta-dir استفاده خواهد کرد.

    می‌توانید از پوشه‌های فراداده جداگانه استفاده کنید:

    $ rustdoc +nightly crate1.rs --write-doc-meta-dir=crate1.d -Zunstable-options
$ cat doc/search.index/crateNames/*
cat: 'doc/search.index/crateNames/*': No such file or directory
$ rustdoc +nightly crate2.rs --write-doc-meta-dir=crate2.d -Zunstable-options
$ cat doc/search.index/crateNames/*
cat: 'doc/search.index/crateNames/*': No such file or directory
$ rustdoc +nightly --read-doc-meta-dir=crate1.d --read-doc-meta-dir=crate2.d -Zunstable-options
$ cat doc/search.index/crateNames/*
rd_("fcrate1fcrate2")

    یا می‌توانید یک پوشهٔ فراداده برای همهٔ crateها به کار ببرید:

    $ rustdoc +nightly crate1.rs --write-doc-meta-dir=meta.d -Zunstable-options
$ cat doc/search.index/crateNames/*
cat: 'doc/search.index/crateNames/*': No such file or directory
$ rustdoc +nightly crate2.rs --write-doc-meta-dir=meta.d -Zunstable-options
$ cat doc/search.index/crateNames/*
cat: 'doc/search.index/crateNames/*': No such file or directory
$ rustdoc +nightly --read-doc-meta-dir=meta.d -Zunstable-options
$ cat doc/search.index/crateNames/*
rd_("fcrate1fcrate2")

    --document-hidden-items: نمایش آیتم‌های #[doc(hidden)]

    به‌طور پیش‌فرض، rustdoc آیتم‌هایی را که با #[doc(hidden)] علامت‌گذاری شده‌اند مستندسازی نمی‌کند.

    --document-hidden-items باعث می‌شود همهٔ آیتم‌ها طوری مستندسازی شوند که انگار #[doc(hidden)] نداشتند، با این تفاوت که آیتم‌های پنهان با نماد 👻 نمایش داده می‌شوند.

    جدول زیر به‌طور کامل توضیح می‌دهد که با هر ترکیب از --document-hidden-items و --document-private-items کدام آیتم‌ها مستندسازی می‌شوند:

    پرچم‌های rustdocآیتم‌هایی که مستندسازی می‌شوند
    هیچ‌کدام از دو پرچمفقط آیتم‌های عمومی که پنهان نیستند
    فقط --document-hidden-itemsهمهٔ آیتم‌های عمومی
    فقط --document-private-itemsهمهٔ آیتم‌هایی که پنهان نیستند

    --markdown-before-content: گنجاندن Markdown رندرشده پیش از محتوا

    • issue پیگیری: #44027

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --markdown-before-content extra.md
$ rustdoc README.md -Z unstable-options --markdown-before-content extra.md

    درست مانند --html-before-content، این پرچم به شما اجازه می‌دهد محتوای اضافی را درون تگ <body> اما پیش از سایر محتوایی که rustdoc معمولاً در مستندات رندرشده تولید می‌کند درج کنید. با این حال، به‌جای درج مستقیم و عیناً فایل، rustdoc فایل‌ها را پیش از درج نتیجه در فایل از یک رندرکنندهٔ Markdown عبور می‌دهد.

    --markdown-after-content: گنجاندن Markdown رندرشده پس از محتوا

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --markdown-after-content extra.md
$ rustdoc README.md -Z unstable-options --markdown-after-content extra.md

    درست مانند --html-after-content، این پرچم به شما اجازه می‌دهد محتوای اضافی را پیش از تگ </body> اما پس از سایر محتوایی که rustdoc معمولاً در مستندات رندرشده تولید می‌کند درج کنید. با این حال، به‌جای درج مستقیم و عیناً فایل، rustdoc فایل‌ها را پیش از درج نتیجه در فایل از یک رندرکنندهٔ Markdown عبور می‌دهد.

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --playground-url https://play.rust-lang.org/

    هنگام رندر مستندات یک crate، این پرچم نشانی URL پایهٔ Rust Playground را می‌دهد تا برای تولید دکمه‌های Run به کار رود. برخلاف --markdown-playground-url، این آرگومان هم برای فایل‌های Markdown مستقل و هم برای crateهای Rust کار می‌کند. این پرچم همان اثری را دارد که افزودن #![doc(html_playground_url = "url")] به ریشهٔ crate شما دارد، همان‌طور که در فصل مربوط به attribute ـِ #[doc] اشاره شد. لطفاً توجه داشته باشید که Rust Playground رسمی در https://play.rust-lang.org همهٔ crateها را در دسترس ندارد، پس اگر مثال‌های شما به crate شما نیاز دارند، مطمئن شوید playground ای که می‌دهید crate شما را در دسترس دارد.

    اگر هنگام رندر یک فایل Markdown مستقل هر دوی --playground-url و --markdown-playground-url وجود داشته باشند، URL داده‌شده به --markdown-playground-url اولویت خواهد داشت. اگر هنگام رندر مستندات crate هر دوی --playground-url و #![doc(html_playground_url = "url")] وجود داشته باشند، attribute اولویت خواهد داشت.

    --sort-modules-by-appearance: کنترل نحوهٔ مرتب‌سازی آیتم‌ها در صفحه‌های ماژول

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --sort-modules-by-appearance

    معمولاً، وقتی rustdoc آیتم‌ها را در صفحه‌های ماژول چاپ می‌کند، آن‌ها را به ترتیب الفبایی مرتب می‌کند (با در نظر گرفتن مقداری ملاحظات برای پایداری آن‌ها و نام‌هایی که به عدد ختم می‌شوند). دادن این پرچم به rustdoc این مرتب‌سازی را غیرفعال می‌کند و به‌جای آن آیتم‌ها را به همان ترتیبی که در کد منبع ظاهر می‌شوند چاپ می‌کند.

    --show-type-layout: افزودن بخشی به مستندات هر نوع که چیدمان حافظهٔ آن را شرح می‌دهد

    • issue پیگیری: #113248

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --show-type-layout

    وقتی این پرچم داده شود، rustdoc بخشی با عنوان «Layout» در انتهای صفحهٔ مستندات هر نوع اضافه می‌کند که خلاصه‌ای از چیدمان حافظهٔ نوع را، آن‌گونه که rustc محاسبه کرده است، در بر می‌گیرد. برای مثال، rustdoc اندازهٔ بایتی را نشان می‌دهد که یک مقدار از آن نوع در حافظه اشغال می‌کند.

    توجه کنید که بیشتر اطلاعات چیدمان کاملاً ناپایدارند و حتی ممکن است میان کامپایل‌های مختلف متفاوت باشند.

    --resource-suffix: تغییر نام CSS/JavaScript در مستندات crate

    • issue پیگیری: #54765

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --resource-suffix suf

    هنگام رندر مستندات، rustdoc چند فایل CSS و JavaScript را به‌عنوان بخشی از خروجی می‌سازد. از آنجا که همهٔ این فایل‌ها از هر صفحه پیوند داده می‌شوند، اگر لازم باشد آن‌ها را به‌طور ویژه cache کنید، تغییر محل آن‌ها می‌تواند دست‌وپاگیر باشد. این پرچم نام همهٔ این فایل‌ها را در خروجی تغییر می‌دهد تا پسوند در نام فایل بیاید. برای مثال، با فرمان بالا light.css به light-suf.css تبدیل می‌شود.

    --extern-html-root-url: کنترل نحوهٔ پیوند rustdoc به crateهای غیرمحلی

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --extern-html-root-url some-crate=https://example.com/some-crate/1.0.1

    معمولاً، وقتی rustdoc می‌خواهد به یک نوع از crate دیگری پیوند دهد، در دو جا جستجو می‌کند: مستنداتی که از پیش در پوشهٔ خروجی وجود دارند، یا #![doc(doc_html_root)] تنظیم‌شده در crate دیگر. اما اگر بخواهید به مستنداتی پیوند دهید که در هیچ‌یک از آن دو جا وجود ندارند، می‌توانید از این پرچم‌ها برای کنترل این رفتار استفاده کنید. وقتی پرچم --extern-html-root-url با نامی مطابق با یکی از وابستگی‌های شما داده شود، rustdoc از آن URL برای آن مستندات استفاده می‌کند. به یاد داشته باشید که اگر آن مستندات در پوشهٔ خروجی وجود داشته باشند، همان مستندات محلی همچنان بر این پرچم اولویت خواهند داشت.

    نام‌های این پرچم ابتدا با نام‌هایی که در پرچم‌های --extern name= داده شده‌اند تطبیق داده می‌شوند، که امکان انتخاب میان چند crate هم‌نام را می‌دهد (مثلاً چند نسخهٔ یک crate). برای وابستگی‌های تراگذری که از طریق پرچم --extern بارگذاری نشده‌اند، تطبیق به استفاده از نام crate به‌تنهایی بازمی‌گردد، بدون توانایی تمایز میان چند crate هم‌نام.

    -Z force-unstable-if-unmarked

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z force-unstable-if-unmarked

    این یک پرچم داخلی برای کتابخانهٔ استاندارد و کامپایلر است که یک attribute ـِ #[unstable] را به هر crate وابسته‌ای که attribute پایداری دیگری ندارد اعمال می‌کند. این به rustdoc اجازه می‌دهد برای crateهای کامپایلر و کتابخانهٔ استاندارد مستندات تولید کند، زیرا یک آرگومان خط فرمان معادل هنگام ساخت آن crateها به rustc داده می‌شود.

    --index-page: فراهم کردن صفحهٔ فرود سطح بالا برای مستندات

    این قابلیت به شما امکان می‌دهد با یک فایل markdown مشخص یک صفحهٔ فهرست (index-page) تولید کنید. مثال خوبی از آن فهرست مستندات rust است.

    با این کار، صفحه‌ای خواهید داشت که می‌توانید در بالای crateهایتان تا هر اندازه که می‌خواهید سفارشی‌اش کنید.

    استفاده از گزینهٔ index-page گزینهٔ enable-index-page را نیز فعال می‌کند.

    --enable-index-page: تولید یک صفحهٔ فهرست پیش‌فرض برای مستندات

    این قابلیت امکان تولید یک صفحهٔ فهرست پیش‌فرض را می‌دهد که crateهای تولیدشده را فهرست می‌کند.

    --no-capture: غیرفعال کردن ثبت خروجی برای آزمون

    وقتی این پرچم همراه با --test به کار رود، خروجی (stdout و stderr) آزمون‌های شما توسط rustdoc ثبت نمی‌شود. در عوض، خروجی به ترمینال شما هدایت می‌شود، انگار فایل اجرایی آزمون را به‌صورت دستی اجرا کرده‌اید. این به‌ویژه برای اشکال‌زدایی آزمون‌هایتان مفید است!

    --check: فقط مستندات را بررسی می‌کند

    وقتی این پرچم داده شود، rustdoc کد شما را بررسی نوع (type check) و lint می‌کند، اما هیچ مستنداتی تولید نمی‌کند و doctestهای شما را اجرا نمی‌کند.

    استفاده از این پرچم به این شکل است:

    rustdoc -Z unstable-options --check src/lib.rs

    --static-root-path: کنترل نحوهٔ بارگذاری فایل‌های ایستا در خروجی HTML

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --static-root-path '/cache/'

    این پرچم کنترل می‌کند rustdoc در صفحه‌های HTML چگونه به فایل‌های ایستای خود پیوند دهد. اگر مستندات crateهای زیادی را که با همان نسخه از rustdoc تولید شده‌اند میزبانی می‌کنید، می‌توانید از این پرچم استفاده کنید تا فایل‌های CSS، JavaScript و فونت rustdoc را در یک مکان واحد cache کنید، به‌جای این‌که یک نسخه برای هر «ریشهٔ مستندات» (گروهی از مستندات crateها که در یک پوشهٔ خروجی تولید شده‌اند، مانند cargo doc) تکرار شود. فایل‌های مخصوص هر crate مانند نمایهٔ جستجو همچنان از ریشهٔ مستندات بارگذاری می‌شوند، اما هر چیزی که با --resource-suffix تغییر نام می‌دهد از مسیر داده‌شده بارگذاری خواهد شد.

    --persist-doctests: حفظ فایل‌های اجرایی doctest پس از اجرا

    • issue پیگیری: #56925

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs --test -Z unstable-options --persist-doctests target/rustdoctest

    این پرچم به شما اجازه می‌دهد فایل‌های اجرایی doctest را پس از کامپایل یا اجرا نگه دارید. معمولاً rustdoc یک doctest کامپایل‌شده را بلافاصله پس از آزمودن دور می‌اندازد، اما با این گزینه می‌توانید آن فایل‌های باینری را برای آزمون‌های بیشتر نگه دارید.

    --show-coverage: محاسبهٔ درصد آیتم‌های دارای مستندات

    • issue پیگیری: #58154

    استفاده از این پرچم به این شکل است:

    $ rustdoc src/lib.rs -Z unstable-options --show-coverage

    چیزی شبیه این تولید می‌کند:

    +-------------------------------------+------------+------------+------------+------------+
| File                                | Documented | Percentage |   Examples | Percentage |
+-------------------------------------+------------+------------+------------+------------+
| lib.rs                              |          4 |     100.0% |          1 |      25.0% |
+-------------------------------------+------------+------------+------------+------------+
| Total                               |          4 |     100.0% |          1 |      25.0% |
+-------------------------------------+------------+------------+------------+------------+

    اگر می‌خواهید تعیین کنید چند آیتم در crate شما مستندسازی شده‌اند، این پرچم را به rustdoc بدهید. وقتی این پرچم را دریافت کند، آیتم‌های عمومی crate شما را که مستندات دارند می‌شمارد و به‌جای تولید مستندات، تعداد و درصد را چاپ می‌کند.

    چند نکته دربارهٔ روشی که rustdoc در این معیار می‌شمارد:

    • Rustdoc فقط آیتم‌های crate شما را می‌شمارد (یعنی آیتم‌هایی که از crateهای دیگر بازصادر شده‌اند شمرده نمی‌شوند).
    • مستنداتی که مستقیماً روی بلوک‌های impl ذاتی نوشته شده‌اند شمرده نمی‌شوند، هرچند doc commentهای آن‌ها نمایش داده می‌شوند، زیرا الگوی رایج در کد Rust این است که همهٔ متدهای ذاتی را در یک بلوک impl بنویسند.
    • آیتم‌های درون پیاده‌سازی صفت شمرده نمی‌شوند، زیرا آن implها هر مستنداتی را از خود صفت به ارث می‌برند.
    • به‌طور پیش‌فرض فقط آیتم‌های عمومی شمرده می‌شوند. برای شمردن آیتم‌های خصوصی هم، همزمان --document-private-items را بدهید.

    آیتم‌های عمومی که مستندسازی نشده‌اند را می‌توان با lint داخلی missing_docs دید. آیتم‌های خصوصی که مستندسازی نشده‌اند را می‌توان با lint ـِ missing_docs_in_private_items در Clippy دید.

    محاسبهٔ مثال‌های کد از این قواعد پیروی می‌کند:

    1. این آیتم‌ها به‌طور پیش‌فرض محاسبه نمی‌شوند:
    • فیلد ساختار/union
    • واریانت شمارش
    • constant
    • static
    • typedef
    1. اگر یکی از آیتم‌های فهرست‌شده در بالا مثال کد داشته باشد، شمرده خواهد شد.

    اگر همراه با آن از گزینهٔ -o استفاده کنید، فایل را در پوشه‌ای با نام داده‌شده تولید می‌کند. برای مثال:

    rustdoc foo.rs --show-coverage -o doc

    یک foo.txt در پوشهٔ doc تولید می‌کند. اگر گزینهٔ -o داده نشود، خروجی روی stdout نمایش داده می‌شود.

    خروجی JSON

    وقتی --output-format json همراه با این گزینه به کار رود، اطلاعات coverage را در قالب JSON نمایش می‌دهد. برای مثال، این JSON مربوط به فایلی با یک آیتم مستندسازی‌شده و یک آیتم مستندسازی‌نشده است:

    /// This item has documentation
pub fn foo() {}

pub fn no_documentation() {}
    {"no_std.rs":{"total":3,"with_docs":1,"total_examples":3,"with_examples":0}}

    توجه کنید که آیتم سوم ریشهٔ crate است که در این مورد مستندسازی نشده است.

    اگر می‌خواهید به‌جای تولید یک فایل، خروجی JSON روی stdout نمایش داده شود، می‌توانید از -o - استفاده کنید.

    -w/--output-format: قالب خروجی

    json

    • issue پیگیری: #76578

    --output-format json مستندات را در قالب JSON آزمایشی تولید می‌کند.

    خروجی JSON برای crateهای toolchain (std، alloc، core، test و proc_macro) از طریق مؤلفهٔ rustup با نام rust-docs-json در دسترس است.

    rustup component add --toolchain nightly rust-docs-json

    سپس فایل‌های json در پوشهٔ share/doc/rust/json/ از پوشهٔ toolchain مربوط به rustup وجود خواهند داشت.

    همچنین می‌توان آن را با --show-coverage به کار برد. برای اطلاعات بیشتر، مستندات آن را ببینید.

    doctest

    • issue پیگیری: #134529

    --output-format doctest روی stdout یک JSON تولید می‌کند که اطلاعاتی دربارهٔ doctestهای crate داده‌شده به شما می‌دهد.

    می‌توانید این گزینه را این‌گونه به کار ببرید:

    rustdoc -Zunstable-options --output-format=doctest src/lib.rs

    برای این کد Rust:

    /// ```
/// #![allow(dead_code)]
/// let x = 12;
/// Ok(())
/// ```
pub trait Trait {}

    خروجی تولیدشده (قالب‌بندی‌شده) این‌گونه خواهد بود:

    {
  "format_version": 2,
  "doctests": [
    {
      "file": "src/lib.rs",
      "line": 1,
      "doctest_attributes": {
        "original": "",
        "should_panic": false,
        "no_run": false,
        "ignore": "None",
        "rust": true,
        "test_harness": false,
        "compile_fail": false,
        "standalone_crate": false,
        "error_codes": [],
        "edition": null,
        "added_css_classes": [],
        "unknown": []
      },
      "original_code": "#![allow(dead_code)]\nlet x = 12;\nOk(())",
      "doctest_code": {
        "crate_level": "#![allow(unused)]\n#![allow(dead_code)]\n\n",
        "code": "let x = 12;\nOk(())",
        "wrapper": {
          "before": "fn main() { fn _inner() -> core::result::Result<(), impl core::fmt::Debug> {\n",
          "after": "\n} _inner().unwrap() }",
          "returns_result": true
        }
      },
      "name": "src/lib.rs - (line 1)"
    }
  ]
}
    • format_version نسخهٔ فعلی JSON تولیدشده را به شما می‌دهد. اگر خروجی را به هر شکلی تغییر دهیم، این عدد افزایش می‌یابد.
    • doctests فهرست doctestهای موجود در crate را در بر دارد.
      • file مسیر فایلی است که doctest در آن قرار دارد.
      • line خطی است که doctest از آن شروع می‌شود (یعنی جایی که ``` در کد فعلی قرار دارد).
      • doctest_attributes اطلاعات محاسبه‌شده دربارهٔ attributeهای به‌کاررفته روی doctestها را در بر دارد. برای اطلاعات بیشتر دربارهٔ attributeهای doctest، اینجا را ببینید.
      • original_code کدی است که در کد منبع نوشته شده، پیش از آن‌که rustdoc آن را تغییر دهد.
      • doctest_code کدی است که rustdoc آن را تغییر داده و اجرا خواهد شد. اگر یک خطای نحوی مهلک وجود داشته باشد، این فیلد حضور نخواهد داشت.
        • crate_level کد سطح crate (مانند attributeها یا extern crate) است که در بالاترین سطح doctest تولیدشده افزوده خواهد شد.
        • code همان doctest «عریان» است، بدون چیزی از crate_level و محتوای wrapper.
        • wrapper کد اضافی‌ای را در بر دارد که پیش و پس از code افزوده خواهد شد.
          • returns_result یک مقدار بولی است. اگر true باشد، یعنی doctest یک نوع Result برمی‌گرداند.
      • name نامی است که rustdoc تولید کرده و این doctest را نمایندگی می‌کند.

    html

    --output-format html اثری ندارد، زیرا خروجی پیش‌فرض HTML است. این گزینه در نسخهٔ stable پذیرفته می‌شود، هرچند گزینه‌های دیگر این پرچم پذیرفته نمی‌شوند.

    --with-examples: گنجاندن مثال‌های استفاده از آیتم‌ها به‌عنوان مستندات

    • issue پیگیری: #88791

    این گزینه، همراه با --scrape-examples-target-crate و --scrape-examples-output-path، برای پیاده‌سازی قابلیت RFC #3123 به کار می‌رود. موارد استفاده از یک آیتم (در حال حاضر تابع‌ها / محل‌های فراخوانی) در یک crate و وابسته‌های معکوس آن پیدا می‌شوند و سپس این موارد استفاده به‌عنوان مستندات آن آیتم گنجانده می‌شوند. قرار است این قابلیت از طریق cargo doc --scrape-examples به کار رود، اما روند کار فقط با rustdoc به این شکل است:

    $ rustdoc examples/ex.rs -Z unstable-options \
    --extern foobar=target/deps/libfoobar.rmeta \
    --scrape-examples-target-crate foobar \
    --scrape-examples-output-path output.calls
$ rustdoc src/lib.rs -Z unstable-options --with-examples output.calls

    ابتدا باید کتابخانه بررسی (check) شود تا یک rmeta تولید شود. سپس یک وابستهٔ معکوس مانند examples/ex.rs به rustdoc داده می‌شود، همراه با crate هدفی که مستندسازی می‌شود (foobar) و مسیری برای نوشتن فراخوانی‌ها (output.calls). سپس فایل فراخوانی‌های تولیدشده را می‌توان از طریق --with-examples به مستندسازی بعدی foobar داد.

    دامنهٔ documentation

    rustdoc (و به‌تبع آن rustc) یک دامنهٔ بازنگاشت ویژه به نام documentation دارد که امکان بازنگاشت مسیرهای منبعی را می‌دهد که در مستندات تولیدشده ظاهر می‌شوند.

    می‌توان آن را با --remap-path-scope=documentation مشخص کرد.

    #[doc(cfg)] و #[doc(auto_cfg)]

    این قابلیت قصد دارد به کاربران rustdoc امکان دهد نشانگرهای بصری به مستندات رندرشده اضافه کنند تا مشخص شود یک آیتم تحت چه شرایطی در دسترس است (در حال حاضر از طریق این feature ناپایدار ممکن است: doc_cfg).

    هدفش این نیست که امکان دهد یک آیتم یکسان با cfgهای متفاوت بیش از یک بار در مستندات تولیدشده ظاهر شود.

    هدفش این نیست که آیتم‌هایی را که تحت پیکربندی فعلی غیرفعال هستند (یعنی «cfged out») مستندسازی کند.

    این قابلیت attributeهای زیر را اضافه می‌کند:

    • #[doc(auto_cfg)]/#[doc(auto_cfg = true)]/#[doc(auto_cfg = false)]
    • #[doc(cfg(...))]
    • #![doc(auto_cfg(hide(...)))] / #[doc(auto_cfg(show(...)))]

    همهٔ این attributeها را می‌توان به یک ماژول یا به ریشهٔ crate اضافه کرد و آیتم‌های فرزند آن‌ها را به ارث می‌برند، مگر این‌که attribute دیگری آن را بازنویسی کند. به همین دلیل attributeهای «مقابل» مانند auto_cfg(hide(...)) و auto_cfg(show(...)) فراهم شده‌اند: آن‌ها به یک آیتم فرزند اجازه می‌دهند والد خود را بازنویسی کند.

    #[doc(cfg(...))]

    این attribute قالبی استاندارد برای بازنویسی attributeهای #[cfg()] به‌منظور مستندسازی آیتم‌هایی که به‌صورت مشروط در دسترس‌اند فراهم می‌کند. مثال:

    // the "real" cfg condition
#[cfg(feature = "futures-io")]
// the `doc(cfg())` so it's displayed to the readers
#[doc(cfg(feature = "futures-io"))]
pub mod futures {}

    در مستندات این ماژول این را نمایش می‌دهد:

    This is supported on feature="futures-io" only.

    می‌توانید از آن برای نمایش اطلاعات در مستندات تولیدشده استفاده کنید، چه attribute ـِ #[cfg()] وجود داشته باشد چه نه:

    #[doc(cfg(feature = "futures-io"))]
pub mod futures {}

    دقیقاً مانند کد قبلی نمایش داده خواهد شد.

    این attribute همان نحو کامپایل شرطی را دارد، اما فقط باعث افزوده شدن مستندات می‌شود. یعنی #[doc(cfg(not(windows)))] باعث پنهان شدن مستندات شما روی هدف‌های غیر windows نخواهد شد، هرچند #[cfg(not(windows))] چنین می‌کند.

    اگر doc(auto_cfg) روی آیتم فعال باشد، doc(cfg) به هر حال آن را بازنویسی می‌کند، پس در دو مثال قبلی، حتی اگر feature ـِ doc(auto_cfg) فعال بود، باز هم همان چیز را نمایش می‌داد.

    این attribute روی ماژول‌ها و آیتم‌ها کار می‌کند.

    #[doc(auto_cfg(hide(...)))]

    این attribute برای جلوگیری از تولید برخی cfgها در نشانگرهای بصری به کار می‌رود. فقط روی #[doc(auto_cfg = true)] اعمال می‌شود، نه روی #[doc(cfg(...))]. پس در مثال قبلی:

    #[cfg(any(unix, feature = "futures-io"))]
pub mod futures {}

    این در حال حاضر هم unix و هم feature = "futures-io" را در مستندات نمایش می‌دهد که چندان خوب نیست. برای جلوگیری از نمایش داده شدن cfg ـِ unix در هر حالت، می‌توانید این attribute را در سطح ریشهٔ crate به کار ببرید:

    #![doc(auto_cfg(hide(unix)))]

    یا مستقیماً روی یک آیتم/ماژول مشخص، زیرا همهٔ نوادگان آیتم را پوشش می‌دهد:

    #[doc(auto_cfg(hide(unix)))]
#[cfg(any(unix, feature = "futures-io"))]
pub mod futures {
    // `futures` and all its descendants won't display "unix" in their cfgs.
}

    آنگاه cfg ـِ unix هرگز در مستندات نمایش داده نخواهد شد.

    نحو hide به این صورت است: می‌توانید هر تعداد نام cfg که می‌خواهید فهرست کنید:

    #[doc(auto_cfg(hide(feature, target_os)))]

    با مثال بالا، یعنی #[cfg(feature)] و #[cfg(target_os)] در مستندات نمایش داده نمی‌شوند. اما #[cfg(target_os = "linux)] یا #[cfg(feature = "something")] نمایش داده خواهند شد، زیرا فقط کلید بدون مقدار پنهان علامت‌گذاری شده است. اگر می‌خواهید برخی مقادیر را پنهان کنید، می‌توانید این کار را بکنید:

    #[doc(auto_cfg(hide(feature, target_os, values("something", "linux"))))]

    در این حالت، #[cfg(feature = "linux")]، #[cfg(feature = "something")]، #[cfg(target_os = "something")] و #[cfg(target_os = "linux")] پنهان خواهند شد. همهٔ کلیدهای فهرست‌شده تحت تأثیر values(...) قرار می‌گیرند. می‌توانید با داشتن دو hide آن‌ها را جدا کنید:

    #[doc(auto_cfg(
    hide(feature, values("something")),
    hide(target_os, values("linux")),
))]

    اکنون فقط #[cfg(feature = "something")] و #[cfg(target_os = "linux")] پنهان خواهند شد. اگر می‌خواهید یک کلید و همهٔ مقادیرش را پنهان کنید، می‌توانید از any() استفاده کنید:

    #[doc(auto_cfg(
    hide(feature, values(any())),
))]

    اگر می‌خواهید فقط وقتی مقداری وجود ندارد پنهان کنید، می‌توانید از none() استفاده کنید:

    #[doc(auto_cfg(
    hide(feature, values("something", none())),
))]

    پس اکنون، اگر می‌خواهید همهٔ مقادیر یک کلید را ممنوع کنید اما خود کلید را مجاز بدانید، می‌توانید این کار را بکنید:

    #[doc(auto_cfg(
    hide(feature, values(any())), // We completely hide "feature".
    show(feature), // We show again "feature" (but not any value).
))]

    در مثال قبلی، هم #[cfg(feature)] و هم #[cfg(feature = "something")] پنهان خواهند شد.

    Rustdoc در حال حاضر attributeهای test، doc و doctest را به‌طور پیش‌فرض پنهان می‌کند و این حق را برای خود محفوظ می‌دارد که فهرست attributeهای «پنهان به‌طور پیش‌فرض» را تغییر دهد.

    این attribute فقط فهرستی از شناسه‌ها و values() را می‌پذیرد. پس می‌توانید بنویسید:

    #[doc(auto_cfg(
    hide(unix, doctest),
    hide(feature, values("something")),
))]
#[doc(auto_cfg(hide()))]

    اما نمی‌توانید بنویسید:

    #[doc(auto_cfg(hide(not(unix))))]

    پس اگر از doc(auto_cfg(hide(unix))) استفاده کنیم، یعنی همهٔ اشاره‌ها به unix بدون مقدار را پنهان می‌کند:

    #[cfg(unix)] // nothing displayed
#[cfg(any(unix))] // nothing displayed
#[cfg(any(unix, windows))] // only `windows` displayed

    با این حال، فقط بر cfg ـِ unix اثر می‌گذارد، نه بر feature:

    #[cfg(feature = "unix")] // `feature = "unix"` is displayed

    استفاده از این attribute، اگر auto_cfg در این مکان غیرفعال شده بود، آن را دوباره فعال می‌کند:

    #[doc(auto_cfg = false)] // Disabling `auto_cfg`
pub fn foo() {}

    و استفاده از doc(auto_cfg) آن را دوباره فعال می‌کند:

    #[doc(auto_cfg = false)] // Disabling `auto_cfg`
pub mod module {
    #[doc(auto_cfg(hide(unix)))] // `auto_cfg` is re-enabled.
    pub fn foo() {}
}

    دلیل این رفتار آن است که doc(auto_cfg = ...) این قابلیت را فعال یا غیرفعال می‌کند، در حالی که doc(auto_cfg(...)) آن را بدون قید و شرط فعال می‌کند، و این باعث می‌شود نخستین attribute بی‌فایده شود، چون توسط doc(auto_cfg) بعدی بازنویسی خواهد شد.

    #[doc(auto_cfg(show(...)))]

    این attribute عکس #[doc(auto_cfg(hide(...)))] عمل می‌کند: اگر از #[doc(auto_cfg(hide(...)))] استفاده کرده‌اید و می‌خواهید اثر آن را روی یک آیتم و نوادگانش برگردانید، می‌توانید از #[doc(auto_cfg(show(...)))] استفاده کنید. فقط روی #[doc(auto_cfg = true)] اعمال می‌شود، نه روی #[doc(cfg(...))].

    همان قواعد نحوی #[doc(auto_cfg(hide(...)))] را دارد.

    برای مثال:

    #[doc(auto_cfg(hide(unix)))]
#[cfg(any(unix, feature = "futures-io"))]
pub mod futures {
    // `futures` and all its descendants won't display "unix" in their cfgs.
    #[doc(auto_cfg(show(unix)))]
    pub mod child {
        // `child` and all its descendants will display "unix" in their cfgs.
    }
}

    این attribute فقط فهرستی از شناسه‌ها یا آیتم‌های کلید/مقدار را می‌پذیرد. پس می‌توانید بنویسید:

    #[doc(auto_cfg(
    show(unix, doctest),
    show(feature, values("something")),
))]
#[doc(auto_cfg(show()))]

    اما نمی‌توانید بنویسید:

    #[doc(auto_cfg(show(not(unix))))]

    اگر auto_cfg(show(...)) و auto_cfg(hide(...)) برای نمایش/پنهان کردن یک cfg یکسان روی یک آیتم یکسان به کار روند، خطا صادر می‌شود. مثال:

    #[doc(auto_cfg(show(unix)))]
#[doc(auto_cfg(hide(unix)))] // Error!
pub fn foo() {}

    استفاده از این attribute، اگر auto_cfg در این مکان غیرفعال شده بود، آن را دوباره فعال می‌کند:

    #[doc(auto_cfg = false)] // Disabling `auto_cfg`
#[doc(auto_cfg(show(unix)))] // `auto_cfg` is re-enabled.
pub fn foo() {}

    #[doc(auto_cfg)/#[doc(auto_cfg = true)]/#[doc(auto_cfg = false)]

    به‌طور پیش‌فرض، #[doc(auto_cfg)] در سطح crate فعال است. وقتی فعال باشد، Rustdoc اطلاعات سازگاری cfg(...) را به‌طور خودکار نمایش می‌دهد، انگار همان #[doc(cfg(...))] مشخص شده بود.

    این attribute بر آیتمی که روی آن به کار می‌رود و نوادگان آن اثر می‌گذارد.

    پس اگر مثال قبلی را دوباره در نظر بگیریم:

    #[cfg(feature = "futures-io")]
pub mod futures {}

    نیازی نیست cfg را در یک doc(cfg()) «تکرار» کنید تا Rustdoc آن را نمایش دهد.

    در برخی موقعیت‌ها، قواعد دقیق کامپایل شرطی که برای پیاده‌سازی قابلیت به کار رفته‌اند ممکن است مستندات خوبی نباشند (برای مثال، فهرست پلتفرم‌های پشتیبانی‌شده ممکن است بسیار طولانی باشد و بهتر باشد در یک جا مستند شود). برای خاموش کردن آن، attribute ـِ #[doc(auto_cfg = false)] را روی آیتم اضافه کنید.

    اگر هیچ آرگومانی مشخص نشود (یعنی #[doc(auto_cfg)])، معادل نوشتن #[doc(auto_cfg = true)] است.

    وراثت

    Rustdoc attributeهای cfg را از ماژول‌های والد به فرزندانشان ادغام می‌کند. برای مثال، در این مورد، ماژول non_unix ماتریس سازگاری کامل ماژول را شرح می‌دهد، نه فقط اطلاعاتی را که مستقیماً به آن متصل است:

    #[doc(cfg(any(windows, unix)))]
pub mod desktop {
    #[doc(cfg(not(unix)))]
    pub mod non_unix {
        // ...
    }
}

    این کد این را نمایش می‌دهد:

    Available on (Windows or Unix) and non-Unix only.

    بازصادرها و درون‌خط شدن

    attributeهای cfg یک بازصادر هرگز با attributeهای آیتم(های) بازصادرشده ادغام نمی‌شوند، مگر این‌که بازصادر attribute ـِ #[doc(inline)] را داشته باشد. در این حالت، cfg آیتم بازصادرشده با cfg بازصادر ادغام خواهد شد.

    وقتی از «ادغام attributeها» صحبت می‌کنیم، منظورمان این است که اگر بازصادر #[cfg(unix)] داشته باشد و آیتم بازصادرشده #[cfg(feature = "foo")] داشته باشد، فقط cfg(unix) را روی بازصادر و فقط cfg(feature = "foo") را روی آیتم بازصادرشده خواهید دید، مگر این‌که بازصادر #[doc(inline)] داشته باشد، که در آن صورت فقط آیتم بازصادرشده را با هر دو cfg(unix) و cfg(feature = "foo") خواهید دید.

    مثال:

    #[doc(cfg(any(windows, unix)))]
pub mod desktop {
    #[doc(cfg(not(unix)))]
    pub mod non_unix {
        // code
    }
}

#[doc(cfg(target_os = "freebsd"))]
pub use desktop::non_unix as non_unix_desktop;
#[doc(cfg(target_os = "macos"))]
#[doc(inline)]
pub use desktop::non_unix as inlined_non_unix_desktop;

    در این مثال، non_unix_desktop فقط cfg(target_os = "freeebsd") را نمایش می‌دهد و هیچ cfg ای از desktop::non_unix نمایش نمی‌دهد.

    برعکس، inlined_non_unix_desktop cfgهای هر دو، بازصادر و آیتم بازصادرشده، را خواهد داشت.
