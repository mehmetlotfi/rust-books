    نحوهٔ نوشتن مستندات

    نوشتن مستندات خوب کاری طبیعی و آسان نیست. اهداف متضادی وجود دارند که نوشتن مستندات خوب را دشوار می‌کنند. این کار هم به تخصص در موضوع نیاز دارد و هم به نوشتن از دیدگاه یک تازه‌کار. به همین دلیل مستندات اغلب از جزئیات پیاده‌سازی سرسری می‌گذرند یا خواننده را با پرسش‌های بی‌پاسخ رها می‌کنند.

    چند اصل در مستندات Rust وجود دارد که می‌تواند هر کسی را در فرایند مستندسازی کتابخانه‌ها راهنمایی کند تا همه فرصت کافی برای استفاده از کد داشته باشند.

    این فصل نه‌تنها نحوهٔ نوشتن مستندات، بلکه به‌طور خاص نحوهٔ نوشتن مستندات خوب را پوشش می‌دهد. مهم است که تا جای ممکن واضح و تا حد امکان کامل باشید. به‌عنوان یک قاعدهٔ سرانگشتی: هرچه مستندات بیشتری برای crate خود بنویسید بهتر است. اگر یک آیتم عمومی است باید مستندسازی شود.

    شروع کار

    مستندسازی یک crate باید با مستندات صفحهٔ اول شروع شود. برای نمونه، مستندات سطح crate در hashbrown نقش crate را خلاصه می‌کند، پیوندهایی برای توضیح جزئیات فنی فراهم می‌کند و توضیح می‌دهد چرا می‌خواهید از این crate استفاده کنید.

    پس از معرفی crate، مهم است که صفحهٔ اول مثالی از نحوهٔ استفاده از crate در یک محیط واقعی ارائه دهد. در مثال به نقش کتابخانه پایبند بمانید، اما بدون میان‌بر این کار را بکنید تا به نفع کاربرانی باشد که ممکن است برای شروع، مثال را کپی و جایگذاری کنند.

    futures از توضیحات درون‌خطی (inline comments) استفاده می‌کند تا خط‌به‌خط پیچیدگی‌های استفاده از Future را توضیح دهد، چون نخستین مواجههٔ یک فرد با Future در Rust ممکن است همین مثال باشد.

    مستندات backtrace کل فرایند را گام‌به‌گام مرور می‌کند، تغییرات اعمال‌شده در فایل Cargo.toml و ارسال آرگومان‌های خط فرمان به کامپایلر را شرح می‌دهد و یک مثال سریع از backtrace در دنیای واقعی نشان می‌دهد.

    سرانجام، صفحهٔ اول می‌تواند به‌تدریج به یک مرجع جامع برای نحوهٔ استفاده از یک crate تبدیل شود، مانند regex. در این صفحهٔ اول، همهٔ الزامات شرح داده شده، موارد مرزی نشان داده شده و مثال‌های کاربردی ارائه شده‌اند. صفحهٔ اول سپس نحوهٔ استفاده از عبارت‌های باقاعده (regular expressions) را نشان می‌دهد و در پایان به ویژگی‌های (features) crate می‌پردازد.

    نگران مقایسهٔ crate خود، که تازه در ابتدای راه است، با crateهای پیشرفته‌تر نباشید. برای رساندن مستندات به چیزی صیقل‌یافته‌تر، به‌تدریج شروع کنید و یک مقدمه، مثال و featureها اضافه کنید. رم یک‌روزه ساخته نشد!

    چند خط نخست داخل lib.rs صفحهٔ اول را تشکیل می‌دهند و از قراردادی متفاوت با بقیهٔ مستندات rustdoc استفاده می‌کنند. خط‌ها باید با //! شروع شوند که مستندات سطح ماژول یا سطح crate را نشان می‌دهد. در اینجا یک مثال سریع از این تفاوت آمده است:

    //! Fast and easy queue abstraction.
//!
//! Provides an abstraction over a queue.  When the abstraction is used
//! there are these advantages:
//! - Fast
//! - [`Easy`]
//!
//! [`Easy`]: http://thatwaseasy.example.com

/// This module makes it easy.
pub mod easy {

    /// Use the abstraction function to do this specific thing.
    pub fn abstraction() {}

}

    در حالت ایده‌آل، این خط نخست مستندات جمله‌ای است بدون جزئیات بسیار فنی، اما با توصیفی خوب از اینکه این crate در کجای اکوسیستم Rust قرار می‌گیرد. کاربران باید پس از خواندن این خط بدانند که آیا این crate نیاز آن‌ها را برآورده می‌کند یا نه.

    مستندسازی اجزا

    چه ماژول باشد، چه ساختار، تابع یا ماکرو: API عمومی همهٔ کدها باید مستندات داشته باشد. به‌ندرت کسی از زیاد بودن مستندات شکایت می‌کند!

    توصیه می‌شود مستندات هر آیتم از این ساختار پایه پیروی کند:

    [short sentence explaining what it is]

[more detailed explanation]

[at least one code example that users can copy/paste to try it]

[even more advanced explanations if necessary]

    پیروی از این ساختار پایه هنگام نوشتن مستندات شما باید ساده باشد؛ هرچند ممکن است فکر کنید یک مثال کد بدیهی است، مثال‌ها واقعاً مهم‌اند زیرا می‌توانند به کاربران کمک کنند بفهمند یک آیتم چیست، چگونه استفاده می‌شود و برای چه هدفی وجود دارد.

    بیایید یک مثال از کتابخانهٔ استاندارد را با نگاه به تابع std::env::args() ببینیم:

    Returns the arguments which this program was started with (normally passed
via the command line).

The first element is traditionally the path of the executable, but it can be
set to arbitrary text, and may not even exist. This means this property should
not be relied upon for security purposes.

On Unix systems shell usually expands unquoted arguments with glob patterns
(such as `*` and `?`). On Windows this is not done, and such arguments are
passed as-is.

# Panics

The returned iterator will panic during iteration if any argument to the
process is not valid unicode. If this is not desired,
use the [`args_os`] function instead.

# Examples

```
use std::env;

// Prints each argument on a separate line
for argument in env::args() {
    println!("{argument}");
}
```

[`args_os`]: ./fn.args_os.html

    هر چیزی که پیش از نخستین خط خالی بیاید، برای توصیف آن جزء در جستجوها و مرورهای کلی ماژول دوباره استفاده می‌شود. برای مثال، تابع std::env::args() در بالا در مستندات ماژول std::env نمایش داده می‌شود. نگه داشتن خلاصه در یک خط روش خوبی است: نوشتن موجز یکی از اهداف مستندات خوب است.

    از آنجا که سیستم نوع در تعریف اینکه یک تابع چه نوع‌هایی می‌گیرد و برمی‌گرداند کار خوبی انجام می‌دهد، نوشتن صریح آن در مستندات فایده‌ای ندارد، به‌ویژه که rustdoc به همهٔ نوع‌های موجود در امضای تابع ابرپیوند اضافه می‌کند.

    در مثال بالا، یک بخش «Panics» توضیح می‌دهد که کد چه زمانی ممکن است ناگهان خارج شود، که می‌تواند به خواننده کمک کند از رسیدن به panic جلوگیری کند. اگر موارد مرزی کد شما قابل دستیابی و شناخته‌شده باشند، توصیه می‌شود هر بار یک بخش panic بنویسید.

    همان‌طور که می‌بینید، این مثال از ساختار شرح‌داده‌شده در بالا پیروی می‌کند: با یک جملهٔ کوتاه شروع می‌شود که توضیح می‌دهد تابع چه می‌کند، سپس اطلاعات بیشتری می‌دهد و در پایان یک مثال کد ارائه می‌کند.

    Markdown

    rustdoc از مشخصات Markdown در CommonMark استفاده می‌کند. ممکن است علاقه‌مند باشید نگاهی به وب‌سایت آن‌ها بیندازید تا ببینید چه کارهایی ممکن است:

    • مرجع سریع CommonMark
    • مشخصات فعلی

    علاوه بر نحو استاندارد CommonMark، rustdoc چند افزونه را پشتیبانی می‌کند:

    خط‌خورده (Strikethrough)

    می‌توان متن را با یک خط افقی در میانه‌اش نمایش داد، به این صورت که متن را از هر طرف با یک یا دو نویسهٔ مد (tilde) احاطه کنیم:

    An example of ~~strikethrough text~~. You can also use ~single tildes~.

    این مثال به این شکل رندر می‌شود:

    نمونه‌ای از ~~متن خط‌خورده~~. می‌توانید از ~یک tilde~ هم استفاده کنید.

    این بخش از افزونهٔ Strikethrough در GitHub پیروی می‌کند.

    پانوشت‌ها (Footnotes)

    یک پانوشت در متن یک پیوند شماره‌دار کوچک تولید می‌کند که با کلیک روی آن خواننده به متن پانوشت در پایین آیتم می‌رود. برچسب پانوشت شبیه ارجاع پیوند و با یک علامت کِرت (caret) در ابتدا نوشته می‌شود. متن پانوشت مانند تعریف ارجاع پیوند نوشته می‌شود، با متنی که پس از برچسب می‌آید. مثال:

    This is an example of a footnote[^note].

[^note]: This text is the contents of the footnote, which will be rendered
    towards the bottom.

    این مثال به این شکل رندر می‌شود:

    این نمونه‌ای از یک پانوشت است1.

    پانوشت‌ها به‌طور خودکار بر اساس ترتیبی که پانوشت‌ها نوشته شده‌اند شماره‌گذاری می‌شوند.

    جدول‌ها (Tables)

    جدول‌ها را می‌توان با خط عمودی و خط تیره برای کشیدن سطرها و ستون‌های جدول نوشت. این‌ها به جدول HTML هم‌شکل با آن‌ها ترجمه می‌شوند. مثال:

    | Header1 | Header2 |
|---------|---------|
| abc     | def     |

    این مثال مشابه این رندر می‌شود:

    Header1 | Header2 | Header2 |

    |———|———| abc | def | def |

    برای جزئیات بیشتر دربارهٔ نحو دقیق پشتیبانی‌شده، مشخصات افزونهٔ Tables در GitHub را ببینید.

    فهرست وظایف (Task lists)

    از فهرست‌های وظیفه می‌توان به‌عنوان یک چک‌لیست از آیتم‌هایی که انجام شده‌اند استفاده کرد. مثال:

    - [x] Complete task
- [ ] Incomplete task

    این به این شکل رندر می‌شود:

    • کار انجام‌شده
    • کار انجام‌نشده

    برای جزئیات بیشتر، مشخصات افزونهٔ فهرست وظایف را ببینید.

    علائم نگارشی هوشمند (Smart punctuation)

    برخی دنباله‌های علائم نگارشی ASCII به‌طور خودکار به نویسه‌های زیبای یونیکد تبدیل می‌شوند:

    دنبالهٔ ASCIIیونیکد
    --–
    ---—
    ...…
    "“ یا ”، بسته به زمینه
    '‘ یا ’، بسته به زمینه

    بنابراین نیازی نیست آن نویسه‌های یونیکد را دستی وارد کنید!

    افزودن بلوک هشدار

    اگر می‌خواهید یک هشدار یا یادداشت مشابه در مستندات برجسته شود، می‌توانید آن را این‌گونه احاطه کنید:

    /// documentation
///
/// <div class="warning">A big warning!</div>
///
/// more documentation

    توجه داشته باشید که اگر می‌خواهید markdown را درون تگ HTML بگذارید و به‌عنوان markdown تفسیر شود، باید میان تگ‌های HTML و محتوای markdown خود یک خط خالی داشته باشید. برای مثال اگر بخواهید از یک پیوند استفاده کنید:

    /// documentation
///
/// <div class="warning">
///
/// Go to [this link](https://rust-lang.org)!
///
/// </div>
///
/// more documentation
