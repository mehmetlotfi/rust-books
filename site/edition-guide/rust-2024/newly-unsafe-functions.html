    توابع unsafe

    خلاصه

    • توابع زیر اکنون به‌عنوان unsafe علامت‌گذاری شده‌اند:
      • std::env::set_var
      • std::env::remove_var
      • std::os::unix::process::CommandExt::before_exec

    جزئیات

    با گذشت زمان آشکار شده است که برخی توابع در کتابخانهٔ استاندارد باید به‌عنوان unsafe علامت‌گذاری می‌شدند. با این حال، افزودن unsafe به یک تابع می‌تواند یک تغییر ناسازگار (breaking change) باشد، چون لازم می‌کند کد موجود درون یک بلوک unsafe قرار گیرد. برای جلوگیری از این تغییر ناسازگار، این توابع از ویرایش 2024 به بعد به‌عنوان unsafe علامت‌گذاری می‌شوند، در حالی که در ویرایش‌های قبلی نیازی به unsafe ندارند.

    std::env::{set_var, remove_var}

    فراخوانی std::env::set_var یا std::env::remove_var در یک برنامهٔ چندنخی ممکن است به‌دلیل محدودیت‌های ایمنی نحوهٔ مدیریت محیط فرایند در برخی پلتفرم‌ها ناسالم (unsound) باشد. کتابخانهٔ استاندارد در ابتدا این‌ها را به‌عنوان توابع ایمن تعریف کرده بود، اما بعداً مشخص شد که این درست نبوده است.

    مهم است که اطمینان حاصل شود این توابع زمانی فراخوانی نمی‌شوند که ممکن است نخ دیگری در حال اجرا باشد. برای جزئیات بیشتر بخش ایمنی در مستندات تابع را ببینید.

    std::os::unix::process::CommandExt::before_exec

    تابع std::os::unix::process::CommandExt::before_exec تابعی مختص یونیکس است که راهی برای اجرای یک closure پیش از فراخوانی exec فراهم می‌کند. این تابع در نسخهٔ 1.37 منسوخ شد و با pre_exec جایگزین گردید که همان کار را انجام می‌دهد، اما به‌عنوان unsafe علامت‌گذاری شده است.

    با اینکه before_exec منسوخ شده است، از ویرایش 2024 به بعد اکنون به‌درستی به‌عنوان unsafe علامت‌گذاری شده است. این کار باید کمک کند هر کد قدیمی‌ای که هنوز به pre_exec مهاجرت نکرده است، به یک بلوک unsafe نیاز پیدا کند.

    الزامات ایمنی بسیار سخت‌گیرانه‌ای وجود دارد که closure مربوط به before_exec باید برآورده کند. برای جزئیات بیشتر بخش ایمنی را ببینید.

    مهاجرت

    برای اینکه کد شما در هر دو ویرایش 2021 و 2024 کامپایل شود، باید مطمئن شوید که این توابع فقط از درون بلوک‌های unsafe فراخوانی می‌شوند.

    ⚠ احتیاط: مهم است که فراخوانی‌های این توابع را به‌صورت دستی بررسی کنید و احتمالاً کد خود را طوری بازنویسی کنید که پیش‌شرط‌های آن توابع برآورده شوند. به‌ویژه، اگر ممکن است چند نخ در حال اجرا باشند، نباید set_var و remove_var فراخوانی شوند. ممکن است لازم باشد برای مدیریت مورد استفادهٔ خود از سازوکاری غیر از متغیرهای محیطی استفاده کنید.

    lint با نام deprecated_safe_2024 هر استفاده از این توابع را به‌طور خودکار طوری تغییر می‌دهد که درون یک بلوک unsafe قرار گیرد تا در هر دو ویرایش کامپایل شود. این lint بخشی از گروه lint با نام rust-2024-compatibility است که هنگام اجرای cargo fix --edition به‌طور خودکار اعمال می‌شود. برای مهاجرت کد خود به سازگاری با ویرایش Rust 2024، این دستور را اجرا کنید:

    cargo fix --edition

    برای مثال، این کد را تغییر می‌دهد:

    fn main() {
    std::env::set_var("FOO", "123");
}

    به این شکل تبدیل می‌شود:

    fn main() {
    // TODO: Audit that the environment access only happens in single-threaded code.
    unsafe { std::env::set_var("FOO", "123") };
}

    فقط توجه داشته باشید که این مهاجرت خودکار نمی‌تواند تأیید کند که این توابع به‌درستی استفاده می‌شوند. بازبینی دستی نحوهٔ استفاده از آن‌ها همچنان بر عهدهٔ شما است.

    همچنین می‌توانید lint را به‌صورت دستی فعال کنید تا جاهایی را که این توابع فراخوانی می‌شوند پیدا کنید:

    // Add this to the root of your crate to do a manual migration.
#![warn(deprecated_safe_2024)]
