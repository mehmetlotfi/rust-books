    تغییر در fallback نوع never

    خلاصه

    Note

    از Rust 1.100 به بعد، تغییراتی که پیش‌تر در این فصل مستند شده بودند دیگر مختص ویرایش نیستند.

    تبدیل‌های (coercion) نوع never (!) به هر نوع («never-to-any») اکنون در همهٔ ویرایش‌ها به‌جای نوع واحد (()) به نوع never (!) برمی‌گردند (fallback).

    lint با نام dependency_on_unit_never_type_fallback که مهاجرت را مدیریت می‌کرد نیز حذف شده است.

    توضیح تبدیل‌های «never-to-any» در ادامه برای اطلاع‌رسانی نگه داشته شده است.

    جزئیات

    وقتی کامپایلر مقداری از نوع ! (never) را در یک محل تبدیل می‌بیند، به‌طور ضمنی یک تبدیل درج می‌کند تا نوع‌یاب بتواند هر نوعی را استنباط کند:

    // This:
let x: u8 = panic!();

// ...is (essentially) turned by the compiler into:
let x: u8 = absurd(panic!());

// ...where `absurd` is the following function
// (it's sound because `!` always marks unreachable code):
fn absurd<T>(x: !) -> T { x }

    اگر نوع قابل استنباط نباشد، این می‌تواند به خطاهای کامپایل منجر شود:

    fn absurd<T>(x: !) -> T { x }
// This:
{ panic!() };

// ...gets turned into this:
{ absurd(panic!()) }; //~ ERROR can't infer the type of `absurd`

    برای جلوگیری از چنین خطاهایی، کامپایلر به خاطر می‌سپارد که فراخوانی‌های absurd را کجا درج کرده است و اگر نتواند نوع را استنباط کند، به‌جای آن از نوع جایگزین (fallback) استفاده می‌کند:

    fn absurd<T>(x: !) -> T { x }
type Fallback = /* An arbitrarily selected type! */ !;
{ absurd::<Fallback>(panic!()) }

    این همان چیزی است که با نام «fallback نوع never» شناخته می‌شود.

    از نظر تاریخی، نوع جایگزین () (واحد) بوده است. این باعث می‌شد ! حتی وقتی کامپایلر بدون fallback نوع () را استنباط نمی‌کرد، خودبه‌خود به () تبدیل شود. این موضوع گیج‌کننده بود و مانع پایدارسازی نوع ! شده است.

    در همهٔ ویرایش‌ها، نوع جایگزین اکنون ! است. این باعث می‌شود همه‌چیز شهودی‌تر کار کند. اکنون وقتی ! را عبور می‌دهید و دلیلی برای تبدیل آن به چیز دیگری وجود ندارد، به‌صورت ! باقی می‌ماند.

    در برخی موارد ممکن است کد شما به این وابسته باشد که نوع جایگزین () است، بنابراین این تغییر می‌تواند باعث خطاهای کامپایل یا تغییر در رفتار شود.

    مهاجرت

    Note

    مهاجرت دیگر کاربرد ندارد، زیرا نوع never اکنون در همهٔ ویرایش‌ها به ! برمی‌گردد. اطلاعات مربوط به بازنویسی کدی که فرض می‌کرد fallback به () است، در ادامه حفظ شده است تا اگر کد قدیمی‌ای دارید که باید به‌روزرسانی شود از آن استفاده کنید.

    برای به‌روزرسانی کدی که fallback به () را فرض می‌کرد، اصلاح خودکاری وجود ندارد.

    اصلاح دستی این است که نوع را به‌صراحت مشخص کنید تا نوع جایگزین به کار نرود. متأسفانه ممکن است دیدن اینکه کدام نوع باید مشخص شود ساده نباشد.

    یکی از رایج‌ترین الگوهایی که با این تغییر می‌شکنند، استفاده از f()?; است که در آن f نسبت به بخش Ok نوع بازگشتی جنریک است:

    fn outer<T>(x: T) -> Result<T, ()> {
fn f<T: Default>() -> Result<T, ()> {
    Ok(T::default())
}

f()?;
Ok(x)
}

    ممکن است فکر کنید که در این مثال نوع T قابل استنباط نیست. با این حال، به‌دلیل باز شدن (desugaring) فعلی عملگر ?، اکنون به‌صورت ! استنباط می‌شود (در حالی که در نسخه‌های قبلی Rust به‌صورت () استنباط می‌شد).

    برای رفع مشکل باید نوع T را به‌صراحت مشخص کنید:

    fn outer<T>(x: T) -> Result<T, ()> {
fn f<T: Default>() -> Result<T, ()> {
    Ok(T::default())
}
f::<()>()?;
// ...or:
() = f()?;
Ok(x)
}

    مورد نسبتاً رایج دیگر، panic کردن در یک closure است:

    trait Unit {}
impl Unit for () {}

fn run<R: Unit>(f: impl FnOnce() -> R) {
    f();
}

run(|| panic!());

    پیش‌تر ! حاصل از panic! به () تبدیل می‌شد که Unit را پیاده‌سازی می‌کند. اما اکنون ! به‌صورت ! باقی می‌ماند، بنابراین این کد شکست می‌خورد، چون ! صفت Unit را پیاده‌سازی نمی‌کند. برای رفع این مشکل می‌توانید نوع بازگشتی closure را مشخص کنید:

    trait Unit {}
impl Unit for () {}

fn run<R: Unit>(f: impl FnOnce() -> R) {
    f();
}
run(|| -> () { panic!() });

    موردی مشابه f()? را می‌توان هنگام استفاده از عبارتی با نوع ! در یک شاخه و تابعی با نوع بازگشتی بدون قید در شاخهٔ دیگر دید:

    if true {
    Default::default()
} else {
    return
};

    پیش‌تر () به‌عنوان نوع بازگشتی Default::default() استنباط می‌شد، چون ! حاصل از return به‌اشتباه به () تبدیل می‌شد. اکنون به‌جای آن ! استنباط می‌شود که باعث می‌شود این کد کامپایل نشود، چون ! صفت Default را پیاده‌سازی نمی‌کند.

    دوباره، این مشکل را می‌توان با مشخص کردن صریح نوع رفع کرد:

    () = if true {
    Default::default()
} else {
    return
};

// ...or:

if true {
    <() as Default>::default()
} else {
    return
};
