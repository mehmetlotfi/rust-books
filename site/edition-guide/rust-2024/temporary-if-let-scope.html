    دامنهٔ مقدار موقت در if let

    خلاصه

    • در یک عبارت if let $pat = $expr { .. } else { .. }، مقادیر موقتی که از ارزیابی $expr تولید می‌شوند پیش از ورود برنامه به شاخهٔ else از بین می‌روند (drop می‌شوند)، نه پس از آن.

    جزئیات

    ویرایش 2024 دامنهٔ drop شدن مقادیر موقت را در عبارت مورد تطبیق (scrutinee)1 یک عبارت if let تغییر می‌دهد. هدف این است که رفتار احتمالاً غیرمنتظره‌ای که از زنده ماندن بیش‌ازحد مقدار موقت ناشی می‌شود، کاهش یابد.

    پیش از 2024، مقادیر موقت می‌توانستند فراتر از خود عبارت if let ادامه یابند. برای مثال:

    // Before 2024
use std::sync::RwLock;

fn f(value: &RwLock<Option<bool>>) {
    if let Some(x) = *value.read().unwrap() {
        println!("value is {x}");
    } else {
        let mut v = value.write().unwrap();
        if v.is_none() {
            *v = Some(true);
        }
    }
    // <--- Read lock is dropped here in 2021
}

    در این مثال، قفل خواندن موقتی که با فراخوانی value.read() تولید می‌شود تا پس از عبارت if let (یعنی پس از بلوک else) drop نمی‌شود. در حالتی که بلوک else اجرا شود، این موضوع هنگام تلاش برای گرفتن قفل نوشتن باعث بن‌بست (deadlock) می‌شود.

    ویرایش 2024 طول عمر مقادیر موقت را تا لحظه‌ای کوتاه می‌کند که بلوک then به‌طور کامل ارزیابی شده یا کنترل برنامه وارد بلوک else شده باشد.

    // Starting with 2024
use std::sync::RwLock;

fn f(value: &RwLock<Option<bool>>) {
    if let Some(x) = *value.read().unwrap() {
        println!("value is {x}");
    }
    // <--- Read lock is dropped here in 2024
    else {
        let mut v = value.write().unwrap();
        if v.is_none() {
            *v = Some(true);
        }
    }
}

    برای اطلاعات بیشتر دربارهٔ نحوهٔ گسترش دامنهٔ مقادیر موقت، قواعد دامنهٔ مقدار موقت را ببینید. برای تغییری مشابه که روی عبارت‌های انتهایی (tail expression) اعمال شده است، فصل دامنهٔ مقدار موقت عبارت انتهایی را ببینید.

    مهاجرت

    بازنویسی if let با match همیشه ایمن است. مقادیر موقت عبارت مورد تطبیق در match تا بعد از پایان عبارت match (معمولاً تا پایان دستور) ادامه می‌یابند، که با رفتار if let در 2021 یکسان است.

    وقتی به‌خاطر این تغییر مشکلی در طول عمر پیش می‌آید، یا lint با نام if_let_rescope تشخیص می‌دهد که از عبارت مورد تطبیق (scrutinee) در if let یک مقدار موقت با destructor سفارشی و غیرپیش‌پاافتادهٔ Drop تولید شده است، این lint یک اصلاح پیشنهاد می‌کند. برای مثال، اگر پیشنهاد cargo fix پذیرفته شود، مثال قبلی می‌تواند به شکل زیر بازنویسی شود:

    use std::sync::RwLock;
fn f(value: &RwLock<Option<bool>>) {
    match *value.read().unwrap() {
        Some(x) => {
            println!("value is {x}");
        }
        _ => {
            let mut s = value.write().unwrap();
            if s.is_none() {
                *s = Some(true);
            }
        }
    }
    // <--- Read lock is dropped here in both 2021 and 2024
}

    در این مثال خاص، به دلیل بن‌بستی که پیش‌تر گفته شد، احتمالاً این چیزی نیست که می‌خواهید! با این حال، برخی سناریوها ممکن است فرض کنند که مقادیر موقت تا پس از بند else نگه داشته می‌شوند، و در این صورت ممکن است بخواهید رفتار قدیمی را حفظ کنید.

    lint با نام if_let_rescope بخشی از گروه lint با نام rust-2024-compatibility است که در مهاجرت خودکار ویرایش گنجانده شده است. برای اینکه کد خود را با ویرایش Rust 2024 سازگار کنید، این دستور را اجرا کنید:

    cargo fix --edition

    پس از مهاجرت، توصیه می‌شود همهٔ تغییرات if let به match را مرور کنید و تصمیم بگیرید که از نظر زمان drop شدن مقادیر موقت، چه رفتاری لازم دارید. اگر به این نتیجه رسیدید که تغییر ضروری نیست، می‌توانید آن را به if let بازگردانید.

    اگر می‌خواهید بدون انجام مهاجرت ویرایش، این هشدارها را به‌صورت دستی بررسی کنید، می‌توانید lint را به این شکل فعال کنید:

    // Add this to the root of your crate to do a manual migration.
#![warn(if_let_rescope)]
