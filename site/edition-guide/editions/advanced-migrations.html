    راهبردهای پیشرفتهٔ مهاجرت

    مهاجرت‌ها چگونه کار می‌کنند

    دستور cargo fix --edition با اجرای معادل cargo check روی پروژهٔ شما کار می‌کند، با lintهای ویژه‌ای که فعال شده‌اند و کدی را تشخیص می‌دهند که ممکن است در ویرایش بعدی کامپایل نشود. این lintها شامل دستورالعمل‌هایی دربارهٔ چگونگی تغییر کد برای سازگار شدن آن با هر دو ویرایش فعلی و بعدی هستند. cargo fix این تغییرات را روی کد منبع اعمال می‌کند و سپس دوباره cargo check را اجرا می‌کند تا بررسی کند اصلاحات کار می‌کنند. اگر اصلاحات شکست بخورند، تغییرات را برمی‌گرداند و یک هشدار نمایش می‌دهد.

    تغییر کد به‌گونه‌ای که هم‌زمان با ویرایش فعلی و بعدی سازگار باشد، مهاجرت تدریجی کد را آسان‌تر می‌کند. اگر مهاجرت خودکار کاملاً موفق نشود یا به کمک دستی نیاز داشته باشد، می‌توانید پیش از تغییر Cargo.toml برای استفاده از ویرایش بعدی، در حالی که روی ویرایش اصلی باقی مانده‌اید به‌صورت تکرارشونده کار کنید.

    lintهایی که cargo fix --edition اعمال می‌کند بخشی از یک گروه lint هستند. برای مثال، هنگام مهاجرت از 2018 به 2021، Cargo برای اصلاح کد از گروه lint با نام rust-2021-compatibility استفاده می‌کند. برای نکاتی دربارهٔ استفاده از lintهای منفرد برای کمک به مهاجرت، بخش مهاجرت جزئی را در ادامه ببینید.

    cargo fix ممکن است cargo check را چندین بار اجرا کند. برای مثال، پس از اعمال یک مجموعه اصلاحات، ممکن است هشدارهای جدیدی ایجاد شوند که به اصلاحات بیشتری نیاز دارند. Cargo این کار را تکرار می‌کند تا دیگر هشدار جدیدی تولید نشود.

    مهاجرت پیکربندی‌های متعدد

    cargo fix در هر لحظه فقط با یک پیکربندی کار می‌کند. اگر از featureهای Cargo یا کامپایل شرطی استفاده می‌کنید، ممکن است لازم باشد cargo fix را چندین بار با پرچم‌های مختلف اجرا کنید.

    برای مثال، اگر کدی دارید که از attributeهای #[cfg] برای گنجاندن کدهای متفاوت برای پلتفرم‌های مختلف استفاده می‌کند، ممکن است لازم باشد cargo fix را با گزینهٔ --target اجرا کنید تا برای هدف‌های مختلف اصلاح شود. اگر امکان کامپایل متقابل (cross-compiling) ندارید، ممکن است لازم باشد کد خود را بین ماشین‌ها جابه‌جا کنید.

    به همین ترتیب، اگر روی featureهای Cargo شرط‌هایی دارید، مانند #[cfg(feature = "my-optional-thing")]، توصیه می‌شود از پرچم --all-features استفاده کنید تا cargo fix بتواند همهٔ کدهای پشت آن feature gateها را مهاجرت دهد. اگر می‌خواهید کد feature را به‌صورت جداگانه مهاجرت دهید، می‌توانید از پرچم --features برای مهاجرت یکی‌یکی استفاده کنید.

    مهاجرت یک پروژه یا workspace بزرگ

    اگر هنگام مهاجرت با مشکل روبه‌رو شدید، می‌توانید یک پروژهٔ بزرگ را به‌صورت تدریجی مهاجرت دهید تا فرایند آسان‌تر شود.

    در یک workspace در Cargo، هر بسته ویرایش خودش را تعریف می‌کند، بنابراین فرایند به‌طور طبیعی شامل مهاجرت یک بسته در هر مرحله است.

    در داخل یک بستهٔ Cargo، می‌توانید یا کل بسته را یک‌جا مهاجرت دهید، یا هدف‌های Cargo را یکی‌یکی مهاجرت دهید. برای مثال، اگر چند باینری، آزمون و مثال دارید، می‌توانید با پرچم‌های انتخاب هدف خاص در cargo fix --edition فقط همان یک هدف را مهاجرت دهید. به‌طور پیش‌فرض، cargo fix از --all-targets استفاده می‌کند.

    برای موارد پیشرفته‌تر، می‌توانید ویرایش هر هدف را به‌طور جداگانه در Cargo.toml این‌گونه مشخص کنید:

    [[bin]]
name = "my-binary"
edition = "2018"

    معمولاً این کار لازم نیست، اما اگر اهداف زیادی دارید و مهاجرت همهٔ آن‌ها با هم دشوار است، یک گزینه است.

    مهاجرت جزئی با کد خراب

    گاهی اصلاحاتی که کامپایلر پیشنهاد می‌دهد ممکن است کار نکنند. وقتی این اتفاق می‌افتد، Cargo هشداری گزارش می‌کند که نشان می‌دهد چه رخ داده و خطا چه بوده است. با این حال، به‌طور پیش‌فرض تغییراتی را که اعمال کرده بود به‌طور خودکار برمی‌گرداند. نگه داشتن کد در حالت خراب و رفع دستی مشکل می‌تواند مفید باشد. ممکن است برخی از اصلاحات درست بوده باشند، و اصلاح خراب ممکن است تقریباً درست باشد و فقط به اصلاحات جزئی نیاز داشته باشد.

    در این وضعیت، از گزینهٔ --broken-code در cargo fix استفاده کنید تا به Cargo بگویید تغییرات را برنگرداند. سپس می‌توانید خطا را به‌صورت دستی بررسی کنید و ببینید برای رفع آن چه لازم است.

    راه دیگر برای مهاجرت تدریجی یک پروژه، اعمال اصلاحات منفرد به‌صورت جداگانه و یکی‌یکی است. می‌توانید این کار را با افزودن lintهای منفرد به‌عنوان هشدار انجام دهید و سپس یا cargo fix را (بدون پرچم --edition) اجرا کنید یا از ویرایشگر یا IDE خود برای اعمال پیشنهادهایش استفاده کنید، اگر از «Quick Fix» پشتیبانی می‌کند.

    برای مثال، ویرایش ۲۰۱۸ از lint با نام keyword-idents برای اصلاح کلیدواژه‌های متعارض استفاده می‌کند. می‌توانید #![warn(keyword_idents)] را به بالای هر crate اضافه کنید (مثلاً بالای src/lib.rs یا src/main.rs). سپس اجرای cargo fix فقط پیشنهادهای مربوط به آن lint را اعمال می‌کند.

    فهرست lintهای فعال برای هر ویرایش را می‌توانید در صفحهٔ گروه lint ببینید، یا دستور rustc -Whelp را اجرا کنید.

    مهاجرت ماکروها

    برخی ماکروها ممکن است برای سازگار شدن با ویرایش بعدی به کار دستی نیاز داشته باشند. برای مثال، cargo fix --edition ممکن است نتواند ماکرویی را که سینتکسی تولید می‌کند که در ویرایش بعدی کار نمی‌کند، به‌طور خودکار اصلاح کند.

    این موضوع ممکن است هم برای ماکروهای proc و هم برای ماکروهای به سبک macro_rules مشکل‌ساز باشد. ماکروهای macro_rules گاهی در صورتی که ماکرو در همان crate استفاده شود می‌توانند به‌طور خودکار به‌روزرسانی شوند، اما چند وضعیت وجود دارد که نمی‌شود. ماکروهای proc در حالت کلی اصلاً به‌طور خودکار قابل اصلاح نیستند.

    برای مثال، اگر crate‌ای را که شامل این ماکروی (ساختگی) foo است از 2015 به 2018 مهاجرت دهیم، foo به‌طور خودکار اصلاح نخواهد شد.

    #[macro_export]
macro_rules! foo {
    () => {
        let dyn = 1;
        println!("it is {}", dyn);
    };
}

    وقتی این ماکرو در یک crate مربوط به 2015 تعریف شده باشد، به‌دلیل بهداشت ماکرو (macro hygiene، که در ادامه بحث می‌شود) می‌توان آن را از crate هر ویرایش دیگری استفاده کرد. در 2015، dyn یک شناسهٔ معمولی است و بدون محدودیت قابل استفاده است.

    اما در 2018، dyn دیگر شناسهٔ معتبری نیست. هنگام استفاده از cargo fix --edition برای مهاجرت به 2018، Cargo اصلاً هیچ هشدار یا خطایی نمایش نمی‌دهد. با این حال، foo هنگام فراخوانی از هر crate کار نخواهد کرد.

    اگر ماکرو دارید، توصیه می‌شود مطمئن شوید آزمون‌هایی دارید که سینتکس ماکرو را کاملاً پوشش می‌دهند. همچنین ممکن است بخواهید ماکروها را با وارد کردن و استفاده از آن‌ها در crateهایی از ویرایش‌های مختلف آزمایش کنید، تا مطمئن شوید همه‌جا درست کار می‌کنند. اگر به مشکل برخوردید، باید فصل‌های این راهنما را بخوانید تا بفهمید چگونه می‌توان کد را طوری تغییر داد که در همهٔ ویرایش‌ها کار کند.

    بهداشت ماکرو (Macro hygiene)

    ماکروها از سیستمی به نام «بهداشت ویرایش» (edition hygiene) استفاده می‌کنند که در آن توکن‌های داخل یک ماکرو با ویرایشی که از آن می‌آیند علامت‌گذاری می‌شوند. این امکان را می‌دهد که ماکروهای خارجی از crateهایی با ویرایش‌های مختلف فراخوانی شوند، بدون اینکه نگران ویرایشی باشیم که از آن فراخوانی می‌شود.

    بیایید نگاه دقیق‌تری به مثال بالا بیندازیم که یک ماکروی macro_rules را با استفاده از dyn به‌عنوان شناسه تعریف می‌کند. اگر آن ماکرو در یک crate با ویرایش 2015 تعریف شده باشد، آن ماکرو درست کار می‌کند، حتی اگر از یک crate مربوط به 2018 فراخوانی شود که در آن dyn یک کلیدواژه است و در حالت عادی این یک خطای سینتکسی می‌بود. توکن‌های let dyn = 1; به‌عنوان توکن‌های 2015 علامت‌گذاری شده‌اند و کامپایلر این را در هر جایی که آن کد گسترش یابد به یاد خواهد داشت. تجزیه‌گر (parser) به ویرایش توکن‌ها نگاه می‌کند تا بداند چگونه آن را تفسیر کند.

    مشکل زمانی پیش می‌آید که ویرایش را در crate‌ای که ماکرو در آن تعریف شده به 2018 تغییر می‌دهیم. اکنون آن توکن‌ها با ویرایش 2018 برچسب‌گذاری می‌شوند و تجزیهٔ آن‌ها شکست می‌خورد. با این حال، چون هرگز ماکرو را از crate خودمان فراخوانی نکردیم، cargo fix --edition هرگز فرصتی نداشت ماکرو را بررسی و اصلاح کند.

    آزمون‌های مستندات

    در حال حاضر، cargo fix نمی‌تواند آزمون‌های مستندات را به‌روزرسانی کند. پس از به‌روزرسانی ویرایش در Cargo.toml، باید cargo test را اجرا کنید تا مطمئن شوید همه‌چیز هنوز درست کار می‌کند. اگر آزمون‌های مستندات شما از سینتکسی استفاده می‌کنند که در ویرایش جدید پشتیبانی نمی‌شود، باید آن‌ها را به‌صورت دستی به‌روزرسانی کنید.

    در موارد نادر، می‌توانید ویرایش را برای هر آزمون به‌صورت دستی تنظیم کنید. برای مثال، می‌توانید از حاشیه‌نویسی edition2018 روی سه بک‌تیک استفاده کنید تا به rustdoc بگویید از کدام ویرایش استفاده کند.

    کد تولیدشده

    حوزهٔ دیگری که اصلاحات خودکار نمی‌توانند در آن اعمال شوند، زمانی است که اسکریپت ساختی دارید که در زمان کامپایل کد Rust تولید می‌کند (برای مثال، تولید کد را ببینید). در این وضعیت، اگر در نهایت کدی داشته باشید که در ویرایش بعدی کار نمی‌کند، باید اسکریپت ساخت را به‌صورت دستی تغییر دهید تا کدی سازگار تولید کند.

    مهاجرت پروژه‌هایی که از Cargo استفاده نمی‌کنند

    اگر پروژهٔ شما از Cargo به‌عنوان سیستم ساخت استفاده نمی‌کند، ممکن است همچنان بتوانید از lintهای خودکار برای کمک به مهاجرت به ویرایش بعدی استفاده کنید. می‌توانید lintهای مهاجرت را همان‌گونه که در بالا توضیح داده شد با فعال کردن گروه lint مناسب فعال کنید. برای مثال، می‌توانید از attribute با نام #![warn(rust_2021_compatibility)] یا پرچم CLI با نام -Wrust-2021-compatibility یا --force-warns=rust-2021-compatibility استفاده کنید.

    گام بعدی اعمال آن lintها روی کد شماست. چند گزینه در اینجا وجود دارد:

    • هشدارها را به‌صورت دستی بخوانید و پیشنهادهای کامپایلر را اعمال کنید.
    • از ویرایشگر یا IDE‌ای استفاده کنید که از اعمال خودکار پیشنهادها پشتیبانی می‌کند. برای مثال، Visual Studio Code همراه با افزونهٔ Rust Analyzer امکان استفاده از پیوندهای «Quick Fix» را برای اعمال خودکار پیشنهادها دارد. بسیاری از ویرایشگرها و IDEهای دیگر قابلیت مشابهی دارند.
    • یک ابزار مهاجرت با استفاده از کتابخانهٔ rustfix بنویسید. این کتابخانه‌ای است که Cargo در داخل خود برای گرفتن پیام‌های JSON از کامپایلر و تغییر کد منبع استفاده می‌کند. برای نمونه‌هایی از نحوهٔ استفاده از این کتابخانه، پوشهٔ examples را ببینید.

    نوشتن کد idiomatic در یک ویرایش جدید

    ویرایش‌ها فقط دربارهٔ قابلیت‌های جدید و حذف قابلیت‌های قدیمی نیستند. در هر زبان برنامه‌نویسی، اصطلاحات رایج (idiom) با گذشت زمان تغییر می‌کنند و Rust هم استثنا نیست. درحالی که کد قدیمی همچنان کامپایل می‌شود، ممکن است امروز با اصطلاحات رایج متفاوتی نوشته شود.

    برای مثال، در Rust 2015 باید crateهای خارجی با extern crate این‌گونه فهرست شوند:

    // src/lib.rs
extern crate rand;

    در Rust 2018، گنجاندن این آیتم‌ها دیگر ضروری نیست.

    cargo fix گزینهٔ --edition-idioms را دارد تا برخی از این اصطلاحات را به‌طور خودکار به سینتکس جدید منتقل کند.

    هشدار: مشخص است که «lintهای اصطلاحات رایج» (idiom lints) فعلی مشکلاتی دارند. ممکن است پیشنهادهای نادرستی بدهند که کامپایل نمی‌شوند. lintهای فعلی عبارت‌اند از:

    • ویرایش 2018: * unused-extern-crates * explicit-outlives-requirements
      • unused-extern-crates
      • explicit-outlives-requirements
    • ویرایش 2021 هیچ lint اصطلاحات رایجی ندارد.

    دستورالعمل‌های زیر فقط برای افراد ماجراجویی توصیه می‌شوند که حاضرند چند باگ کامپایلر/Cargo را پشت سر بگذارند! اگر به مشکل برخوردید، می‌توانید گزینهٔ --broken-code را که در بالا توضیح داده شد امتحان کنید تا تا حد ممکن پیشرفت کنید و سپس مشکلات باقی‌مانده را به‌صورت دستی حل کنید.

    با این مقدمه، می‌توانیم به Cargo دستور دهیم که قطعه کد ما را این‌گونه اصلاح کند:

    cargo fix --edition-idioms

    پس از آن، خط extern crate rand; در src/lib.rs حذف خواهد شد.

    اکنون کد ما idiomatic‌تر شده است و لازم نبود کد خود را به‌صورت دستی اصلاح کنیم!
