راهنمای ویرایش‌های RustThe Edition Guide

    انتقال یک پروژهٔ موجود به یک ویرایش جدید

    Rust ابزارهایی دارد که یک پروژه را به‌طور خودکار از یک ویرایش به ویرایش بعدی منتقل می‌کنند. این ابزار کد منبع شما را به‌روزرسانی می‌کند تا با ویرایش بعدی سازگار شود. به‌طور خلاصه، مراحل به‌روزرسانی به ویرایش بعدی عبارت‌اند از:

    1. برای به‌روزرسانی وابستگی‌هایتان به آخرین نسخه‌ها، cargo update را اجرا کنید.
    2. cargo fix --edition را اجرا کنید.
    3. فایل Cargo.toml را ویرایش کنید و فیلد edition را روی ویرایش بعدی تنظیم کنید، برای مثال edition = "2024"
    4. برای اطمینان از درستی اصلاحات، cargo build یا cargo test را اجرا کنید.
    5. برای قالب‌بندی مجدد پروژه، cargo fmt را اجرا کنید.

    بخش‌های بعدی به جزئیات این مراحل و برخی مشکلاتی که ممکن است در طول مسیر با آن‌ها روبه‌رو شوید می‌پردازند.

    هدف ما این است که مهاجرت به ویرایش‌های جدید تا حد ممکن تجربه‌ای روان باشد. اگر ارتقا به آخرین ویرایش برای شما دشوار است، آن را یک باگ می‌دانیم. اگر در این فرایند با مشکلی روبه‌رو شدید، لطفاً یک گزارش باگ ثبت کنید. سپاسگزاریم!

    شروع مهاجرت

    به‌عنوان مثال، بیایید انتقال از ویرایش 2015 به ویرایش 2018 را بررسی کنیم. مراحل هنگام انتقال به ویرایش‌های دیگر مانند 2021 نیز اساساً یکسان است.

    فرض کنید crate‌ای داریم که این کد را در src/lib.rs دارد:

    trait Foo {
    fn foo(&self, i32);
}

    این کد از یک پارامتر بی‌نام استفاده می‌کند، یعنی همان i32. این کار در Rust 2018 پشتیبانی نمی‌شود، و بنابراین این کد کامپایل نمی‌شود. بیایید این کد را به‌روز کنیم!

    به‌روزرسانی وابستگی‌هایتان

    پیش از شروع، توصیه می‌شود وابستگی‌هایتان را به‌روزرسانی کنید. برخی وابستگی‌ها، به‌ویژه برخی proc-macroها یا وابستگی‌هایی که در زمان ساخت تولید کد انجام می‌دهند، ممکن است با ویرایش‌های جدیدتر مشکل سازگاری داشته باشند. ممکن است از آخرین باری که به‌روزرسانی کرده‌اید نسخه‌های جدیدی منتشر شده باشند که این مشکلات را رفع می‌کنند. دستور زیر را اجرا کنید:

    cargo update

    پس از به‌روزرسانی، ممکن است بخواهید آزمون‌های خود را اجرا کنید تا مطمئن شوید همه‌چیز درست کار می‌کند. اگر از ابزار مدیریت کد منبع مانند git استفاده می‌کنید، شاید بخواهید این تغییرات را جداگانه commit کنید تا commitها از هم تفکیک منطقی داشته باشند.

    به‌روزرسانی کد برای سازگاری با ویرایش جدید

    ممکن است کد شما از قابلیت‌هایی استفاده کند که با ویرایش جدید ناسازگارند، یا استفاده نکند. برای کمک به انتقال به ویرایش بعدی، Cargo زیردستور cargo fix را دارد که کد منبع شما را به‌طور خودکار به‌روزرسانی می‌کند. برای شروع، بیایید آن را اجرا کنیم:

    cargo fix --edition

    این دستور کد شما را بررسی می‌کند و هر مشکلی را که بتواند به‌طور خودکار رفع می‌کند. بیایید دوباره به src/lib.rs نگاه کنیم:

    trait Foo {
    fn foo(&self, _: i32);
}

    کد ما بازنویسی شده است تا برای آن مقدار i32 یک نام پارامتر معرفی کند. در این مورد، چون نامی نداشت، cargo fix آن را با _ جایگزین می‌کند، که برای متغیرهای استفاده‌نشده یک قرارداد رایج است.

    cargo fix همیشه نمی‌تواند کد شما را به‌طور خودکار اصلاح کند. اگر cargo fix نتواند چیزی را اصلاح کند، هشداری را که نمی‌تواند رفع کند در کنسول چاپ می‌کند. اگر یکی از این هشدارها را دیدید، باید کد خود را به‌صورت دستی به‌روزرسانی کنید. برای اطلاعات بیشتر دربارهٔ کار با فرایند مهاجرت، فصل راهبردهای پیشرفتهٔ مهاجرت را ببینید و فصل‌های این راهنما را بخوانید که توضیح می‌دهند چه تغییراتی لازم است. اگر مشکلی دارید، لطفاً از انجمن کاربران کمک بگیرید.

    فعال‌سازی ویرایش جدید برای استفاده از قابلیت‌های جدید

    برای استفاده از برخی قابلیت‌های جدید، باید صراحتاً ویرایش جدید را فعال کنید. وقتی آماده ادامه بودید، فایل Cargo.toml خود را تغییر دهید و جفت کلید/مقدار edition جدید را اضافه کنید. برای مثال:

    [package]
name = "foo"
version = "0.1.0"
edition = "2018"

    اگر کلید edition وجود نداشته باشد، Cargo به‌طور پیش‌فرض Rust 2015 را در نظر می‌گیرد. اما در این مورد، ما 2018 را انتخاب کرده‌ایم و بنابراین کد ما با Rust 2018 کامپایل خواهد شد!

    آزمایش کد در ویرایش جدید

    گام بعدی آزمایش پروژهٔ شما روی ویرایش جدید است. آزمون‌های پروژه را اجرا کنید تا مطمئن شوید همه‌چیز هنوز کار می‌کند، مثلاً با اجرای cargo test. اگر هشدارهای جدیدی صادر شد، شاید بخواهید دوباره cargo fix را (بدون پرچم --edition) اجرا کنید تا پیشنهادهای کامپایلر اعمال شوند.

    در این مرحله، ممکن است هنوز لازم باشد برخی تغییرات را به‌صورت دستی انجام دهید. برای مثال، مهاجرت خودکار doctestها را به‌روزرسانی نمی‌کند، و تولید کد در زمان ساخت یا ماکروها ممکن است به به‌روزرسانی دستی نیاز داشته باشند. برای اطلاعات بیشتر فصل مهاجرت‌های پیشرفته را ببینید.

    تبریک! کد شما اکنون هم در Rust 2015 و هم در Rust 2018 معتبر است!

    قالب‌بندی مجدد با rustfmt

    اگر از rustfmt برای نگهداری خودکار قالب‌بندی پروژه استفاده می‌کنید، باید قالب‌بندی مجدد با قوانین قالب‌بندی جدید ویرایش جدید را در نظر بگیرید.

    پیش از قالب‌بندی مجدد، اگر از ابزار مدیریت کد منبع مانند git استفاده می‌کنید، شاید بخواهید همهٔ تغییراتی را که تا این لحظه انجام داده‌اید قبل از این گام commit کنید. گذاشتن تغییرات قالب‌بندی در یک commit جداگانه می‌تواند مفید باشد، چون می‌توانید ببینید کدام تغییرات صرفاً قالب‌بندی هستند و کدام تغییرات کد دیگرند، و همچنین احتمالاً می‌توانید تغییرات قالب‌بندی را در git blame نادیده بگیرید.

    cargo fmt

    برای اطلاعات بیشتر، فصل ویرایش‌های سبک را ببینید.

    مهاجرت به یک ویرایش ناپایدار

    پس از انتشار یک ویرایش، تقریباً یک بازهٔ سه‌ساله تا ویرایش بعدی وجود دارد. در این بازه، ممکن است قابلیت‌های جدیدی به ویرایش بعدی اضافه شوند که فقط روی کانال nightly در دسترس خواهند بود. اگر می‌خواهید پیش از stable شدن این قابلیت‌ها در آزمایش آن‌ها کمک کنید، می‌توانید از کانال nightly برای امتحان کردنشان استفاده کنید.

    مراحل تقریباً شبیه کانال stable است:

    1. جدیدترین نسخهٔ nightly را نصب کنید: rustup update nightly.
    2. cargo +nightly fix --edition را اجرا کنید.
    3. فایل Cargo.toml را ویرایش کنید و cargo-features = ["edition20xx"] را در بالای آن (بالاتر از [package]) قرار دهید، و فیلد edition را طوری تغییر دهید که edition = "20xx" باشد، که در آن 20xx ویرایشی است که به آن ارتقا می‌دهید.
    4. cargo +nightly check را اجرا کنید تا مطمئن شوید اکنون در ویرایش جدید کار می‌کند.

    ⚠ احتیاط: ممکن است برای قابلیت‌هایی که در ویرایش بعدی پیاده‌سازی شده‌اند، مهاجرت خودکار با cargo fix پیاده‌سازی نشده باشد، و خود قابلیت‌ها نیز ممکن است کامل نشده باشند. در صورت امکان، این راهنما باید اطلاعاتی دربارهٔ اینکه کدام قابلیت‌ها روی nightly پیاده‌سازی شده‌اند، همراه با اطلاعات بیشتر دربارهٔ وضعیت آن‌ها داشته باشد. چند ماه پیش از stable شدن ویرایش، همهٔ قابلیت‌های جدید باید کاملاً پیاده‌سازی شده باشند و وبلاگ Rust فراخوانی برای آزمایش اعلام خواهد کرد.
