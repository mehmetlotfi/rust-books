    افزوده‌ها به prelude

    خلاصه

    • صفت‌های TryInto، TryFrom و FromIterator اکنون بخشی از prelude هستند.
    • این ممکن است فراخوانی متدهای صفت را مبهم کند و باعث شود برخی کدها کامپایل نشوند.

    جزئیات

    prelude کتابخانهٔ استاندارد ماژولی است که شامل هر چیزی است که به‌طور خودکار در هر ماژول وارد می‌شود. این ماژول آیتم‌های پرکاربردی مانند Option، Vec، drop و Clone را در خود دارد.

    کامپایلر Rust به آیتم‌هایی که به‌صورت دستی وارد شده‌اند نسبت به آیتم‌های prelude اولویت می‌دهد، تا اطمینان یابد افزودن چیزی به prelude هیچ کد موجودی را خراب نخواهد کرد. برای مثال، اگر crate یا ماژولی به نام example داشته باشید که شامل pub struct Option; است، آنگاه use example::*; باعث می‌شود Option بدون ابهام به آنی که در example است اشاره کند و نه به آنی که در کتابخانهٔ استاندارد است.

    با این حال، افزودن یک صفت به prelude می‌تواند کد موجود را به شکلی ظریف خراب کند. برای مثال، فراخوانی x.try_into() که از یک صفت MyTryInto می‌آید ممکن است در صورتی که TryInto از std نیز وارد شده باشد کامپایل نشود، زیرا فراخوانی try_into اکنون مبهم است و می‌تواند از هر یک از دو صفت باشد. به همین دلیل است که TryInto را تاکنون به prelude اضافه نکرده‌ایم، چون کدهای زیادی به این شکل خراب می‌شدند.

    به‌عنوان راه‌حل، Rust 2021 از یک prelude جدید استفاده خواهد کرد. این prelude با prelude فعلی یکسان است، به‌جز سه افزودهٔ جدید:

    • std::convert::TryInto
    • std::convert::TryFrom
    • std::iter::FromIterator

    مسئلهٔ پیگیری را می‌توانید اینجا ببینید.

    مهاجرت

    به‌عنوان بخشی از ویرایش 2021، یک lint مهاجرت با نام rust_2021_prelude_collisions اضافه شده است تا به مهاجرت خودکار کدهای Rust 2018 به Rust 2021 کمک کند.

    برای مهاجرت کد خود به سازگاری با ویرایش Rust 2021، این دستور را اجرا کنید:

    cargo fix --edition

    این lint مواردی را شناسایی می‌کند که در آن‌ها تابع‌ها یا متدهایی فراخوانی می‌شوند که نامی یکسان با متدهای تعریف‌شده در یکی از صفت‌های جدید prelude دارند. در برخی موارد، ممکن است فراخوانی‌های شما را به شیوه‌های گوناگون بازنویسی کند تا اطمینان یابد همچنان همان تابعی را فراخوانی می‌کنید که قبلاً فراخوانی می‌کردید.

    اگر می‌خواهید کد خود را به‌صورت دستی مهاجرت دهید یا بهتر بفهمید cargo fix چه می‌کند، در ادامه موقعیت‌هایی را که مهاجرت لازم است همراه با یک نمونهٔ مخالف از زمانی که لازم نیست، شرح داده‌ایم.

    مهاجرت لازم است

    متدهای صفت متعارض

    وقتی دو صفت که در دامنه هستند نام متد یکسانی داشته باشند، مشخص نیست کدام متد صفت باید استفاده شود. برای مثال:

    trait MyTrait<A> {
  // This name is the same as the `from_iter` method on the `FromIterator` trait from `std`.  
  fn from_iter(x: Option<A>);
}

impl<T> MyTrait<()> for Vec<T> {
  fn from_iter(_: Option<()>) {}
}

fn main() {
  // Vec<T> implements both `std::iter::FromIterator` and `MyTrait` 
  // If both traits are in scope (as would be the case in Rust 2021),
  // then it becomes ambiguous which `from_iter` method to call
  <Vec<i32>>::from_iter(None);
}

    می‌توانیم این را با استفاده از سینتکس کاملاً مشخص‌شده (fully qualified) رفع کنیم:

    fn main() {
  // Now it is clear which trait method we're referring to
  <Vec<i32> as MyTrait<()>>::from_iter(None);
}

    متدهای ذاتی روی شیءهای dyn Trait

    برخی کاربران متدهایی را روی یک مقدار dyn Trait فراخوانی می‌کنند که نام متد با یکی از صفت‌های جدید prelude همپوشانی دارد:

    mod submodule {
  pub trait MyTrait {
    // This has the same name as `TryInto::try_into`
    fn try_into(&self) -> Result<u32, ()>;
  }
}

// `MyTrait` isn't in scope here and can only be referred to through the path `submodule::MyTrait`
fn bar(f: Box<dyn submodule::MyTrait>) {
  // If `std::convert::TryInto` is in scope (as would be the case in Rust 2021),
  // then it becomes ambiguous which `try_into` method to call
  f.try_into();
}

    برخلاف متدهای ارسال ایستا، فراخوانی یک متد صفت روی یک شیء صفت لازم نمی‌کند که صفت در دامنه باشد. کد بالا تا زمانی که هیچ صفتی با نام متد متعارض در دامنه نباشد، کار می‌کند. وقتی صفت TryInto در دامنه باشد (که در Rust 2021 چنین است)، این موضوع ابهام ایجاد می‌کند. آیا فراخوانی باید به MyTrait::try_into باشد یا std::convert::TryInto::try_into؟

    در این موارد، می‌توانیم با افزودن dereferenceهای اضافی یا روشن کردن نوع گیرندهٔ متد به شکل دیگری، این مشکل را رفع کنیم. این کار تضمین می‌کند که متد dyn Trait انتخاب می‌شود و نه متدهای صفت prelude. برای مثال، تبدیل f.try_into() بالا به (&*f).try_into() تضمین می‌کند که try_into را روی dyn MyTrait فراخوانی می‌کنیم، که فقط می‌تواند به متد MyTrait::try_into اشاره کند.

    مهاجرت لازم نیست

    متدهای ذاتی

    بسیاری از نوع‌ها متدهای ذاتی (inherent) خود را با نامی یکسان با یک متد صفت تعریف می‌کنند. برای نمونه، در ادامه ساختار MyStruct متد from_iter را پیاده‌سازی می‌کند که نامش با متد صفت FromIterator در کتابخانهٔ استاندارد یکسان است:

    use std::iter::IntoIterator;

struct MyStruct {
  data: Vec<u32>
}

impl MyStruct {
  // This has the same name as `std::iter::FromIterator::from_iter`
  fn from_iter(iter: impl IntoIterator<Item = u32>) -> Self {
    Self {
      data: iter.into_iter().collect()
    }
  }
}

impl std::iter::FromIterator<u32> for MyStruct {
    fn from_iter<I: IntoIterator<Item = u32>>(iter: I) -> Self {
      Self {
        data: iter.into_iter().collect()
      }
    }
}

    متدهای ذاتی همیشه بر متدهای صفت اولویت دارند، بنابراین نیازی به هیچ مهاجرتی نیست.

    مرجع پیاده‌سازی

    این lint هنگام تعیین اینکه آیا معرفی ویرایش 2021 به یک پایگاه کد باعث تعارض در تفکیک نام می‌شود (و در نتیجه کد را پس از تغییر ویرایش خراب می‌کند) باید چند عامل را در نظر بگیرد. این عوامل عبارت‌اند از:

    • آیا فراخوانی یک فراخوانی کاملاً مشخص‌شده (fully-qualified) است یا از نحو فراخوانی متد با نقطه استفاده می‌کند؟
      • این موضوع بر نحوهٔ تفکیک نام به‌دلیل ارجاع خودکار و غیرارجاع‌دهی خودکار در سینتکس فراخوانی متد تأثیر می‌گذارد. ارجاع/غیرارجاع‌دهی دستی امکان تعیین اولویت را در مورد سینتکس فراخوانی متد با نقطه فراهم می‌کند، در حالی که فراخوانی کاملاً مشخص‌شده نیازمند تعیین نوع و نام صفت در مسیر متد است (مثلاً <Type as Trait>::method)
    • آیا این یک متد ذاتی است یا یک متد trait؟
      • متدهای ذاتی که self می‌گیرند بر TryInto::try_into اولویت خواهند داشت، چون متدهای ذاتی بر متدهای صفت اولویت دارند، اما متدهای ذاتی که &self یا &mut self می‌گیرند اولویت نخواهند داشت، زیرا نیازمند ارجاع خودکار هستند (در حالی که TryInto::try_into چنین نیازی ندارد، چون self می‌گیرد)
    • آیا منشأ این متد core/std است؟ (چون صفت‌ها نمی‌توانند با خودشان تعارض داشته باشند)
    • آیا نوع داده‌شده صفتی را که ممکن است با آن تعارض داشته باشد پیاده‌سازی کرده است؟
    • آیا متد از طریق ارسال پویا فراخوانی می‌شود؟ (یعنی آیا نوع self برابر dyn Trait است)
      • اگر چنین باشد، واردسازی صفت‌ها بر تفکیک نام تأثیری ندارد و نیازی به اجرای lint مهاجرت نیست
