    حل‌کنندهٔ پیش‌فرض feature در Cargo

    خلاصه

    • edition = "2021" به‌طور ضمنی resolver = "2" را در Cargo.toml اعمال می‌کند.

    جزئیات

    از Rust 1.51.0 به بعد، Cargo از یک حل‌کنندهٔ جدید feature پشتیبانی اختیاری دارد که با نوشتن resolver = "2" در Cargo.toml فعال می‌شود.

    از Rust 2021 به بعد، این حل‌کننده پیش‌فرض خواهد بود. یعنی نوشتن edition = "2021" در Cargo.toml به‌طور ضمنی resolver = "2" را نیز اعمال می‌کند.

    حل‌کننده (resolver) یک تنظیم سراسری برای یک workspace است و این تنظیم در وابستگی‌ها نادیده گرفته می‌شود. این تنظیم فقط برای بستهٔ سطح بالای workspace اعمال می‌شود. اگر از یک workspace مجازی استفاده می‌کنید و می‌خواهید حل‌کنندهٔ جدید را فعال کنید، همچنان باید فیلد resolver را در تعریف [workspace] به‌صراحت تنظیم کنید.

    حل‌کنندهٔ جدید feature دیگر همهٔ featureهای درخواست‌شده را برای crateهایی که به چند روش مختلف به آن‌ها وابستگی وجود دارد با هم ادغام نمی‌کند. برای جزئیات بیشتر اعلان انتشار Rust 1.51 را ببینید.

    مهاجرت

    ابزار مهاجرت خودکاری برای به‌روزرسانی به حل‌کنندهٔ جدید وجود ندارد. برای بیشتر پروژه‌ها، این به‌روزرسانی معمولاً تغییر کمی ایجاد می‌کند یا اصلاً تغییری ایجاد نمی‌کند.

    هنگام به‌روزرسانی با cargo fix --edition، اگر حل‌کنندهٔ جدید وابستگی‌ها را با featureهای متفاوتی بسازد، Cargo گزارشی نمایش می‌دهد. این گزارش ممکن است چیزی شبیه این باشد:

    توجه: تغییر به ویرایش 2021 استفادهٔ حل‌کنندهٔ feature نسخهٔ 2 را در Cargo فعال می‌کند. این ممکن است باعث شود برخی وابستگی‌ها با featureهای کمتری نسبت به قبل ساخته شوند. اطلاعات بیشتر دربارهٔ تغییرات حل‌کننده را می‌توانید در https://doc.rust-lang.org/nightly/edition-guide/rust-2021/default-cargo-resolver.html بیابید
    هنگام ساخت وابستگی‌های زیر، featureهای مشخص‌شده دیگر استفاده نخواهند شد:

      bstr v0.2.16: default, lazy_static, regex-automata, unicode
  libz-sys v1.1.3 (as host dependency): libc

    این گزارش به شما اطلاع می‌دهد که برخی وابستگی‌ها دیگر با featureهای مشخص‌شده ساخته نخواهند شد.

    خطاهای ساخت

    ممکن است در برخی شرایط، پروژهٔ شما پس از این تغییر به‌درستی ساخته نشود. اگر اعلان یک وابستگی در یک بسته فرض کند که featureهای مشخصی در بستهٔ دیگری فعال هستند و آن featureها اکنون غیرفعال شده باشند، ممکن است کامپایل با شکست مواجه شود.

    برای مثال، فرض کنید وابستگی‌ای مانند این داریم:

    # Cargo.toml

[dependencies]
bstr = { version = "0.2.16", default-features = false }
# ...

    و جایی در درخت وابستگی‌های ما، بستهٔ دیگری این را دارد:

    # Another package's Cargo.toml

[build-dependencies]
bstr = "0.2.16"

    در بستهٔ ما، از متد words_with_breaks از bstr استفاده می‌کردیم که نیازمند فعال بودن feature با نام “unicode” در bstr است. این کار تاکنون درست عمل می‌کرد، چون Cargo featureهای bstr را بین آن دو بسته یکپارچه می‌کرد. اما پس از به‌روزرسانی به Rust 2021، حل‌کنندهٔ جدید bstr را دو بار می‌سازد: یک بار با featureهای پیش‌فرض (به‌عنوان وابستگی ساخت) و یک بار بدون هیچ feature (به‌عنوان وابستگی عادی ما). از آنجا که bstr اکنون بدون feature با نام “unicode” ساخته می‌شود، متد words_with_breaks وجود ندارد و ساخت با خطایی مبنی بر نبودن این متد شکست می‌خورد.

    راه‌حل این است که مطمئن شوید وابستگی با featureهایی اعلان شده که واقعاً از آن‌ها استفاده می‌کنید. برای مثال:

    [dependencies]
bstr = { version = "0.2.16", default-features = false, features = ["unicode"] }

    در برخی موارد، ممکن است مشکل از یک وابستگی شخص ثالث باشد که کنترل مستقیمی روی آن ندارید. می‌توانید ارسال یک وصله (patch) به آن پروژه را برای اعلان مجموعهٔ درست featureها در وابستگی مشکل‌ساز در نظر بگیرید. یا می‌توانید از داخل فایل Cargo.toml خودتان featureهایی را به هر وابستگی اضافه کنید. برای مثال، اگر اعلان bstr در مثال بالا در یک وابستگی شخص ثالث انجام شده باشد، می‌توانید اعلان درست وابستگی را در پروژهٔ خودتان کپی کنید. featureها تا زمانی که با قوانین یکپارچه‌سازی حل‌کنندهٔ جدید مطابقت داشته باشند، یکپارچه خواهند شد. این قوانین عبارت‌اند از:

    • featureهای فعال‌شده روی وابستگی‌های مختص یک پلتفرم، برای اهدافی که در حال حاضر ساخته نمی‌شوند، نادیده گرفته می‌شوند.
    • وابستگی‌های ساخت (build-dependencies) و proc-macroها featureها را با وابستگی‌های عادی به اشتراک نمی‌گذارند.
    • وابستگی‌های توسعه (dev-dependencies) featureها را فعال نمی‌کنند، مگر اینکه هدفی که نیاز به آن‌ها دارد (مانند آزمون‌ها یا مثال‌ها) ساخته شود.

    یک مثال واقعی استفاده از diesel و diesel_migrations است. این بسته‌ها پشتیبانی از پایگاه داده را فراهم می‌کنند و پایگاه داده با یک feature انتخاب می‌شود، مثلاً به این شکل:

    [dependencies]
diesel = { version = "1.4.7", features = ["postgres"] }
diesel_migrations = "1.4.0"

    مشکل این است که diesel_migrations یک proc-macro داخلی دارد که خودش به diesel وابسته است، و این proc-macro فرض می‌کند نسخهٔ خودش از diesel همان featureهایی را دارد که در بقیهٔ گراف وابستگی‌ها فعال است. پس از به‌روزرسانی به حل‌کنندهٔ جدید، ساخت شکست می‌خورد، زیرا اکنون دو نسخه از diesel وجود دارد و نسخه‌ای که برای proc-macro ساخته شده feature با نام “postgres” را ندارد.

    یک راه‌حل این است که diesel را با featureهای لازم به‌عنوان وابستگی ساخت اضافه کنید، برای مثال:

    [build-dependencies]
diesel = { version = "1.4.7", features = ["postgres"] }

    این کار باعث می‌شود Cargo، feature با نام “postgres” را برای وابستگی‌های میزبان (proc-macroها و وابستگی‌های ساخت) اضافه کند. اکنون proc-macro مربوط به diesel_migrations نیز feature با نام “postgres” را فعال خواهد داشت و به‌درستی ساخته می‌شود.

    نسخهٔ 2.0 از diesel (که در حال حاضر در دست توسعه است) این مشکل را ندارد، زیرا ساختار آن طوری بازطراحی شده که این نیاز وابستگی را نداشته باشد.

    کاوش featureها

    دستور cargo tree برای کمک به مهاجرت به حل‌کنندهٔ جدید بهبودهای قابل‌توجهی داشته است. می‌توان از cargo tree برای کاوش گراف وابستگی‌ها و دیدن اینکه کدام featureها فعال می‌شوند و مهم‌تر از آن، چرا فعال می‌شوند، استفاده کرد.

    یک گزینه استفاده از پرچم --duplicates (به‌اختصار -d) است که به شما می‌گوید چه زمانی یک بسته چندین بار ساخته می‌شود. با در نظر گرفتن مثال bstr از بالا، ممکن است چیزی شبیه این ببینیم:

    > cargo tree -d
bstr v0.2.16
└── foo v0.1.0 (/MyProjects/foo)

bstr v0.2.16
[build-dependencies]
└── bar v0.1.0
    └── foo v0.1.0 (/MyProjects/foo)

    این خروجی به ما می‌گوید که bstr دو بار ساخته شده است و در هر دو مورد زنجیرهٔ وابستگی‌هایی را که به گنجانده شدن آن منجر شده‌اند نشان می‌دهد.

    با پرچم -f می‌توانید چاپ کنید که هر بسته از کدام featureها استفاده می‌کند، مانند این:

    cargo tree -f '{p} {f}'

    این به Cargo می‌گوید «قالب» خروجی را تغییر دهد، به‌طوری که هم بسته و هم featureهای فعال آن را چاپ کند.

    همچنین می‌توانید از پرچم -e استفاده کنید تا مشخص کنید کدام «یال‌ها» (edges) نمایش داده شوند. برای مثال، cargo tree -e features میان هر وابستگی نشان می‌دهد که هر وابستگی چه featureهایی را اضافه می‌کند. این گزینه همراه با پرچم -i که برای «وارونه کردن» درخت به کار می‌رود مفیدتر می‌شود. این کار به شما اجازه می‌دهد ببینید featureها چگونه به یک وابستگی مشخص جریان می‌یابند. برای مثال، فرض کنید گراف وابستگی‌ها بزرگ است و دقیقاً نمی‌دانیم چه کسی به bstr وابسته است؛ دستور زیر آن را نشان می‌دهد:

    > cargo tree -e features -i bstr
bstr v0.2.16
├── bstr feature "default"
│   [build-dependencies]
│   └── bar v0.1.0
│       └── bar feature "default"
│           └── foo v0.1.0 (/MyProjects/foo)
├── bstr feature "lazy_static"
│   └── bstr feature "unicode"
│       └── bstr feature "default" (*)
├── bstr feature "regex-automata"
│   └── bstr feature "unicode" (*)
├── bstr feature "std"
│   └── bstr feature "default" (*)
└── bstr feature "unicode" (*)

    این بخش از خروجی نشان می‌دهد که پروژهٔ foo با feature با نام “default” به bar وابسته است. سپس bar به‌عنوان وابستگی ساخت با feature با نام “default” به bstr وابسته است. همچنین می‌بینیم که feature با نام “default” در bstr، feature با نام “unicode” را (در کنار featureهای دیگر) فعال می‌کند.
