    تغییرات در مسیرها و سامانهٔ ماژول

    خلاصه

    • مسیرها در اعلان‌های use اکنون مانند سایر مسیرها عمل می‌کنند.
    • مسیرهایی که با :: شروع می‌شوند اکنون باید به یک crate خارجی ارجاع دهند.
    • مسیرها در اصلاح‌کننده‌های دید pub(in path) اکنون باید با crate، self یا super شروع شوند.

    انگیزه

    سامانهٔ ماژول اغلب یکی از دشوارترین بخش‌ها برای تازه‌واردان Rust است. البته هر کسی چیزهایی دارد که تسلط بر آن‌ها زمان می‌برد، اما برای گیج‌کننده بودن آن برای بسیاری از افراد یک علت ریشه‌ای وجود دارد: با اینکه قواعد ساده و یکدستی سامانهٔ ماژول را تعریف می‌کنند، پیامدهای این قواعد می‌توانند ناهماهنگ، خلاف شهود و مرموز به نظر برسند.

    به همین دلیل، ویرایش 2018 زبان Rust چند ویژگی تازه برای سامانهٔ ماژول معرفی می‌کند، اما در نهایت این ویژگی‌ها سامانهٔ ماژول را ساده‌تر می‌کنند تا روشن‌تر باشد که چه اتفاقی در جریان است.

    خلاصهٔ کوتاه آن‌ها از این قرار است:

    • extern crate در ۹۹٪ موارد دیگر لازم نیست.
    • کلیدواژهٔ crate به crate فعلی اشاره می‌کند.
    • مسیرها می‌توانند با نام یک crate شروع شوند، حتی در زیرماژول‌ها.
    • مسیرهایی که با :: شروع می‌شوند باید به یک crate خارجی ارجاع دهند.
    • یک فایل foo.rs و یک زیردایرکتوری foo/ می‌توانند هم‌زمان وجود داشته باشند؛ هنگام قرار دادن زیرماژول‌ها در یک زیردایرکتوری دیگر به mod.rs نیازی نیست.
    • مسیرها در اعلان‌های use مانند سایر مسیرها عمل می‌کنند.

    وقتی به این شکل بیان شوند ممکن است قواعدی جدید و دلبخواهی به نظر برسند، اما مدل ذهنی در مجموع به‌طور قابل‌توجهی ساده‌تر شده است. برای جزئیات بیشتر ادامه را بخوانید!

    جزئیات بیشتر

    بیایید هر ویژگی تازه را به‌ترتیب بررسی کنیم.

    دیگر نیازی به extern crate نیست

    این یکی کاملاً سر راست است: دیگر لازم نیست برای وارد کردن یک crate به پروژه‌تان extern crate بنویسید. پیش از این:

    // Rust 2015

extern crate futures;

mod submodule {
    use futures::Future;
}

    پس از آن:

    // Rust 2018

mod submodule {
    use futures::Future;
}

    اکنون برای افزودن یک crate تازه به پروژه، کافی است آن را به فایل Cargo.toml اضافه کنید و مرحلهٔ دومی وجود ندارد. اگر از Cargo استفاده نمی‌کنید، از پیش مجبور بودید پرچم‌های --extern را به rustc بدهید تا مکان crateهای خارجی را بداند، پس در این مورد هم همان کاری را که می‌کردید ادامه می‌دهید.

    یک استثنا

    یک استثنا برای این قاعده وجود دارد و آن crateهای «sysroot» هستند. اینها crateهایی هستند که همراه خود Rust توزیع می‌شوند.

    معمولاً فقط در موقعیت‌های بسیار تخصصی به این crateها نیاز است. از نسخهٔ 1.41 به بعد، rustc پرچم --extern=CRATE_NAME را می‌پذیرد که نام crate داده‌شده را به شیوه‌ای شبیه به extern crate به‌طور خودکار اضافه می‌کند. ابزارهای ساخت می‌توانند از این قابلیت برای تزریق crateهای sysroot به prelude آن crate استفاده کنند. Cargo راه عمومی‌ای برای بیان این کار ندارد، هرچند آن را برای crateهای proc_macro به کار می‌برد.

    نمونه‌هایی از مواردی که در آن‌ها باید crateهای sysroot را صریحاً وارد کرد:

    • std: معمولاً این کار لازم نیست، چون std به‌طور خودکار وارد می‌شود، مگر اینکه crate با #![no_std] علامت‌گذاری شده باشد.
    • core: معمولاً این کار لازم نیست، چون core به‌طور خودکار وارد می‌شود، مگر اینکه crate با #![no_core] علامت‌گذاری شده باشد. برای مثال، برخی از crateهای داخلی که خود کتابخانهٔ استاندارد از آن‌ها استفاده می‌کند به این نیاز دارند.
    • proc_macro: از نسخهٔ 1.42 به بعد، اگر crate یک proc-macro باشد، Cargo آن را به‌طور خودکار وارد می‌کند. اگر بخواهید از نسخه‌های قدیمی‌تر پشتیبانی کنید، یا از ابزار ساخت دیگری استفاده کنید که پرچم‌های --extern مناسب را به rustc نمی‌دهد، به extern crate proc_macro; نیاز خواهید داشت.
    • alloc: آیتم‌های crate با نام alloc معمولاً از طریق re-exportها در crate با نام std در دسترس‌اند. اگر با یک crate از نوع no_std کار می‌کنید که از تخصیص حافظه پشتیبانی می‌کند، ممکن است لازم باشد alloc را صریحاً وارد کنید.
    • test: این فقط در کانال nightly در دسترس است و معمولاً تنها برای پشتیبانی ناپایدار از benchmark استفاده می‌شود.

    ماکروها

    یکی دیگر از کاربردهای extern crate وارد کردن ماکروها بود؛ این دیگر لازم نیست. ماکروها را می‌توان مانند هر آیتم دیگری با use وارد کرد. برای مثال، این کاربرد extern crate:

    #[macro_use]
extern crate bar;

fn main() {
    baz!();
}

    را می‌توان به چیزی شبیه زیر تغییر داد:

    use bar::baz;

fn main() {
    baz!();
}

    تغییر نام crateها

    اگر از as برای تغییر نام crate خود به این شکل استفاده کرده‌اید:

    extern crate futures as f;

use f::Future;

    آنگاه حذف تنهای خط extern crate کار نمی‌کند. باید این کار را انجام دهید:

    use futures as f;

use self::f::Future;

    این تغییر باید در هر ماژولی که از f استفاده می‌کند انجام شود.

    کلیدواژهٔ crate به crate فعلی اشاره می‌کند

    در اعلان‌های use و در سایر کدها می‌توانید با پیشوند crate:: به ریشهٔ crate فعلی اشاره کنید. برای مثال، crate::foo::bar از هر جای دیگر همان crate، همیشه به نام bar درون ماژول foo اشاره می‌کند.

    پیشوند :: پیش از این یا به ریشهٔ crate اشاره می‌کرد یا به یک crate خارجی؛ اکنون بدون ابهام به یک crate خارجی اشاره می‌کند. برای مثال، ::foo::bar همیشه به نام bar درون crate خارجی foo اشاره می‌کند.

    مسیرهای crate خارجی

    پیش‌تر، برای استفاده از یک crate خارجی در یک ماژول بدون import با use، لازم بود مسیر با :: شروع شود.

    // Rust 2015

extern crate chrono;

fn foo() {
    // this works in the crate root
    let x = chrono::Utc::now();
}

mod submodule {
    fn function() {
        // but in a submodule it requires a leading :: if not imported with `use`
        let x = ::chrono::Utc::now();
    }
}

    اکنون نام crateهای خارجی در کل crate، از جمله زیرماژول‌ها، در scope قرار دارند.

    // Rust 2018

fn foo() {
    // this works in the crate root
    let x = chrono::Utc::now();
}

mod submodule {
    fn function() {
        // crates may be referenced directly, even in submodules
        let x = chrono::Utc::now();
    }
}

    اگر یک ماژول یا آیتم محلی با همان نام یک crate خارجی داشته باشید، مسیری که با آن نام شروع شود به ماژول یا آیتم محلی اشاره می‌کند. برای ارجاع صریح به crate خارجی، از شکل ::name استفاده کنید.

    دیگر نیازی به mod.rs نیست

    در Rust 2015، اگر یک زیرماژول داشته باشید:

    // This `mod` declaration looks for the `foo` module in
// `foo.rs` or `foo/mod.rs`.
mod foo;

    می‌تواند در foo.rs یا foo/mod.rs قرار بگیرد. اگر خودش زیرماژول داشته باشد، باید foo/mod.rs باشد. بنابراین زیرماژول bar از foo در foo/bar.rs قرار می‌گیرد.

    در Rust 2018 این محدودیت که ماژولی دارای زیرماژول باید mod.rs نام داشته باشد برداشته شده است. foo.rs می‌تواند همان foo.rs باشد و زیرماژول همچنان foo/bar.rs است. این کار نام ویژه را حذف می‌کند و اگر در ویرایشگر خود فایل‌های زیادی باز داشته باشید، می‌توانید نام آن‌ها را به‌روشنی ببینید، به‌جای اینکه تعداد زیادی زبانه با نام mod.rs داشته باشید.

    Rust 2015 Rust 2018 
    .
├── lib.rs
└── foo/
    ├── mod.rs
    └── bar.rs

    .
├── lib.rs
├── foo.rs
└── foo/
    └── bar.rs

    مسیرهای use

    Rust 2018 در مقایسه با Rust 2015 مدیریت مسیرها را ساده و یکپارچه می‌کند. در Rust 2015 مسیرها در اعلان‌های use با جاهای دیگر متفاوت عمل می‌کردند. به‌طور خاص، مسیرها در اعلان‌های use همیشه از ریشهٔ crate شروع می‌شدند، در حالی که مسیرها در سایر کدها به‌طور ضمنی از scope فعلی شروع می‌شدند. این تفاوت‌ها در ماژول سطح بالا هیچ تأثیری نداشتند، که یعنی همه‌چیز ساده به نظر می‌رسید تا زمانی که روی پروژه‌ای به اندازه‌ای بزرگ کار کنید که زیرماژول داشته باشد.

    در Rust 2018 مسیرها در اعلان‌های use و در سایر کدها یکسان عمل می‌کنند، هم در ماژول سطح بالا و هم در هر زیرماژول. می‌توانید از یک مسیر نسبی از scope فعلی، مسیری که از نام یک crate خارجی شروع می‌شود، یا مسیری که با ::، crate، super یا self شروع می‌شود استفاده کنید.

    کدی که این‌گونه بود:

    // Rust 2015

extern crate futures;

use futures::Future;

mod foo {
    pub struct Bar;
}

use foo::Bar;

fn my_poll() -> futures::Poll { ... }

enum SomeEnum {
    V1(usize),
    V2(String),
}

fn func() {
    let five = std::sync::Arc::new(5);
    use SomeEnum::*;
    match ... {
        V1(i) => { ... }
        V2(s) => { ... }
    }
}

    در Rust 2018 دقیقاً به همین شکل خواهد بود، با این تفاوت که می‌توانید خط extern crate را حذف کنید:

    // Rust 2018

use futures::Future;

mod foo {
    pub struct Bar;
}

use foo::Bar;

fn my_poll() -> futures::Poll { ... }

enum SomeEnum {
    V1(usize),
    V2(String),
}

fn func() {
    let five = std::sync::Arc::new(5);
    use SomeEnum::*;
    match ... {
        V1(i) => { ... }
        V2(s) => { ... }
    }
}

    همین کد در یک زیرماژول هم بدون هیچ تغییری کار می‌کند:

    // Rust 2018

mod submodule {
    use futures::Future;

    mod foo {
        pub struct Bar;
    }

    use foo::Bar;

    fn my_poll() -> futures::Poll { ... }

    enum SomeEnum {
        V1(usize),
        V2(String),
    }

    fn func() {
        let five = std::sync::Arc::new(5);
        use SomeEnum::*;
        match ... {
            V1(i) => { ... }
            V2(s) => { ... }
        }
    }
}

    این کار جابه‌جا کردن کد در یک پروژه را آسان می‌کند و از افزودن پیچیدگی اضافی به پروژه‌های چندماژولی جلوگیری می‌کند.
