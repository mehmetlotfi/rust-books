    خلاصه

    معرفی یک زبان خاص‌دامنه (domain-specific language) شبیه عبارت‌های منظم (regular expressions) که امکان توصیف lintها را با استفاده از الگوهای درخت نحو فراهم می‌کند.

    انگیزه

    یافتن بخش‌هایی از یک درخت نحو (AST، HIR و …) که ویژگی‌های مشخصی دارند (مثلاً «یک if که یک بلوک به‌عنوان شرط دارد») هنگام نوشتن lintها کار اصلی است. برای lintهای غیرپیش‌پاافتاده، اغلب به تطبیق الگوی تودرتوی گره‌های AST / HIR نیاز دارد. برای مثال، آزمودن اینکه یک عبارت یک لیترال بولی است بررسی‌های زیر را لازم دارد:

    if let ast::ExprKind::Lit(lit) = &expr.node {
    if let ast::LitKind::Bool(_) = &lit.node {
        ...
    }
}

    نوشتن این نوع کد تطبیق به‌سرعت به کاری پیچیده تبدیل می‌شود و کد حاصل اغلب درک‌کردنش دشوار است. کد زیر نسخهٔ ساده‌شدهٔ تطبیق الگوی لازم برای lint ‏collapsible_if را نشان می‌دهد:

    // simplified version of the collapsible_if lint
if let ast::ExprKind::If(check, then, None) = &expr.node {
    if then.stmts.len() == 1 {
        if let ast::StmtKind::Expr(inner) | ast::StmtKind::Semi(inner) = &then.stmts[0].node {
            if let ast::ExprKind::If(check_inner, content, None) = &inner.node {
                ...
            }
        }
    }
}

    ماکروی if_chain می‌تواند با مسطح کردن دستورهای if تودرتو خوانایی را بهبود دهد، اما کد حاصل هنوز خواندنش بسیار دشوار است:

    // simplified version of the collapsible_if lint
if_chain! {
    if let ast::ExprKind::If(check, then, None) = &expr.node;
    if then.stmts.len() == 1;
    if let ast::StmtKind::Expr(inner) | ast::StmtKind::Semi(inner) = &then.stmts[0].node;
    if let ast::ExprKind::If(check_inner, content, None) = &inner.node;
    then {
        ...
    }
}

    کد بالا عبارت‌های if را تطبیق می‌دهد که فقط شامل یک عبارت if دیگر هستند (که هیچ‌یک از دو if شاخهٔ else ندارند). توضیح اینکه lint چه کاری می‌کند آسان است، اما دیدن آن از روی نمونه‌کدهای بالا دشوار است.

    با توجه به انگیزهٔ بالا، نخستین هدف این RFC ساده‌سازی نوشتن و خواندن lintها است.

    بخش دوم انگیزه، وابستگی clippy به ساختارهای دادهٔ ناپایدار داخلی کامپایلر است. lintهای Clippy در حال حاضر بر پایهٔ AST / HIR کامپایلر نوشته می‌شوند، که یعنی حتی تغییرات کوچک در این ساختارهای داده ممکن است تعداد زیادی lint را خراب کند. هدف دوم این RFC مستقل کردن lintها از ساختارهای دادهٔ AST / HIR کامپایلر است.

    رویکرد

    به نظر می‌رسد بخش زیادی از پیچیدگی نوشتن lintها در حال حاضر از این می‌آید که باید منطق تطبیق را به‌صورت دستی پیاده‌سازی کنیم (نمونه‌کدهای بالا را ببینید). این سبکی دستوری (imperative) است که توصیف می‌کند چگونه یک گرهٔ درخت نحو را تطبیق دهیم، به‌جای اینکه به‌صورت اعلانی (declarative) مشخص کند چه چیزی باید تطبیق داده شود. در حوزه‌های دیگر، استفاده از الگوهای اعلانی برای توصیف اطلاعات مطلوب و واگذاشتن تطبیق واقعی به پیاده‌سازی رایج است. یک نمونهٔ شناخته‌شده از این رویکرد عبارت‌های منظم هستند. به‌جای نوشتن کدی که دنباله‌های کاراکتری مشخصی را تشخیص دهد، می‌توان یک الگوی جستجو را با یک زبان خاص‌دامنه توصیف کرد و با آن الگو دنبال تطبیق‌ها گشت. مزیت استفاده از یک زبان اعلانی خاص‌دامنه این است که دامنهٔ محدود آن (مثلاً تطبیق دنباله‌های کاراکتری در مورد عبارت‌های منظم) اجازه می‌دهد موجودیت‌های آن دامنه به شیوه‌ای بسیار طبیعی و گویا بیان شوند.

    عبارت‌های منظم برای جستجوی الگو در دنباله‌های کاراکتری تخت بسیار مفیدند، اما به‌آسانی نمی‌توان آن‌ها را روی ساختارهای دادهٔ سلسله‌مراتبی مانند درخت‌های نحو به کار برد. بنابراین این RFC یک سامانهٔ تطبیق الگو پیشنهاد می‌کند که از عبارت‌های منظم الهام گرفته و برای درخت‌های نحو سلسله‌مراتبی طراحی شده است.

    توضیح در سطح راهنما

    این پیشنهاد یک ماکروی pattern! اضافه می‌کند که می‌توان با آن یک الگوی درخت نحو را برای جستجو مشخص کرد. یک الگوی ساده در زیر نشان داده شده است:

    pattern!{
    my_pattern: Expr =
        Lit(Bool(false))
}

    این فراخوانی ماکرو الگویی به نام my_pattern تعریف می‌کند که می‌توان آن را با یک گرهٔ درخت نحو از نوع Expr تطبیق داد. الگوی واقعی (در اینجا Lit(Bool(false))) تعیین می‌کند کدام درخت‌های نحو با الگو تطبیق پیدا می‌کنند. این الگو با عبارت‌هایی تطبیق پیدا می‌کند که لیترال بولی با مقدار false هستند.

    سپس می‌توان از الگو برای پیاده‌سازی lintها به این روش استفاده کرد:

    ...

impl EarlyLintPass for MyAwesomeLint {
    fn check_expr(&mut self, cx: &EarlyContext, expr: &syntax::ast::Expr) {

        if my_pattern(expr).is_some() {
            cx.span_lint(
                MY_AWESOME_LINT,
                expr.span,
                "This is a match for a simple pattern. Well done!",
            );
        }

    }
}

    فراخوانی ماکروی pattern! به تابعی به نام my_pattern گسترش می‌یابد که یک عبارت درخت نحو را به‌عنوان آرگومان می‌گیرد و یک Option برمی‌گرداند که نشان می‌دهد آیا الگو تطبیق پیدا کرده است یا نه.

    Note

    نکته: نوع نتیجه در بخشی بعدتر با جزئیات بیشتر توضیح داده شده است. فعلاً همین‌قدر کافی است که بدانیم اگر الگو تطبیق پیدا کند نتیجه Some است و در غیر این صورت None.

    نحو الگو

    مثال‌های زیر نحو الگو را نشان می‌دهند:

    هر چیز (_)

    ساده‌ترین الگو، الگوی «هر چیز» است. با هر چیزی تطبیق پیدا می‌کند و بنابراین شبیه * در regex است.

    pattern!{
    // matches any expression
    my_pattern: Expr =
        _
}

    گره (<node-name>(<args>))

    گره‌ها برای تطبیق یک حالت مشخص از یک گرهٔ AST به کار می‌روند. هر گره یک نام و تعدادی آرگومان دارد که به نوع گره بستگی دارد. برای مثال، گرهٔ Lit یک آرگومان دارد که نوع لیترال را توصیف می‌کند. به‌عنوان مثالی دیگر، گرهٔ If سه آرگومان دارد که شرط if، بلوک then و بلوک else را توصیف می‌کنند.

    pattern!{
    // matches any expression that is a literal
    my_pattern: Expr =
        Lit(_)
}

pattern!{
    // matches any expression that is a boolean literal
    my_pattern: Expr =
        Lit(Bool(_))
}

pattern!{
    // matches if expressions that have a boolean literal in their condition
    // Note: The `_?` syntax here means that the else branch is optional and can be anything.
    //       This is discussed in more detail in the section `Repetition`.
    my_pattern: Expr =
        If( Lit(Bool(_)) , _, _?)
}

    لیترال (<lit>)

    یک الگو می‌تواند لیترال‌های Rust را هم در بر داشته باشد. این لیترال‌ها با خودشان تطبیق پیدا می‌کنند.

    pattern!{
    // matches the boolean literal false
    my_pattern: Expr =
        Lit(Bool(false))
}

pattern!{
    // matches the character literal 'x'
    my_pattern: Expr =
        Lit(Char('x'))
}

    انتخاب‌ها (a | b)

    pattern!{
    // matches if the literal is a boolean or integer literal
    my_pattern: Lit =
        Bool(_) | Int(_)
}

pattern!{
    // matches if the expression is a char literal with value 'x' or 'y'
    my_pattern: Expr =
        Lit( Char('x' | 'y') )
}

    تهی (())

    الگوی تهی یک دنبالهٔ خالی یا حالت None از یک مقدار اختیاری را نشان می‌دهد.

    pattern!{
    // matches if the expression is an empty array
    my_pattern: Expr =
        Array( () )
}

pattern!{
    // matches if expressions that don't have an else clause
    my_pattern: Expr =
        If(_, _, ())
}

    دنباله (<a> <b>)

    pattern!{
    // matches the array [true, false]
    my_pattern: Expr =
        Array( Lit(Bool(true)) Lit(Bool(false)) )
}

    تکرار (<a>*, <a>+, <a>?, <a>{n}, <a>{n,m}, <a>{n,})

    عناصر را می‌توان تکرار کرد. نحو تعیین تکرارها با نحو regex یکسان است.

    pattern!{
    // matches arrays that contain 2 'x's as their last or second-last elements
    // Examples:
    //     ['x', 'x']                         match
    //     ['x', 'x', 'y']                    match
    //     ['a', 'b', 'c', 'x', 'x', 'y']     match
    //     ['x', 'x', 'y', 'z']               no match
    my_pattern: Expr =
        Array( _* Lit(Char('x')){2} _? )
}

pattern!{
    // matches if expressions that **may or may not** have an else block
    // Attn: `If(_, _, _)` matches only ifs that **have** an else block
    //
    //              | if with else block | if without else block
    // If(_, _, _)  |       match        |       no match
    // If(_, _, _?) |       match        |        match
    // If(_, _, ()) |      no match      |        match
    my_pattern: Expr =
        If(_, _, _?)
}

    زیرتطبیق نام‌دار (<a>#<name>)

    pattern!{
    // matches character literals and gives the literal the name foo
    my_pattern: Expr =
        Lit(Char(_)#foo)
}

pattern!{
    // matches character literals and gives the char the name bar
    my_pattern: Expr =
        Lit(Char(_#bar))
}

pattern!{
    // matches character literals and gives the expression the name baz
    my_pattern: Expr =
        Lit(Char(_))#baz
}

    دلیل استفاده از زیرتطبیق‌های نام‌دار در بخش نوع نتیجه توضیح داده شده است.

    نوع نتیجه

    بسیاری از lintها به بررسی‌هایی نیاز دارند که فراتر از چیزی است که نحو الگوی توصیف‌شده در بالا می‌تواند بیان کند. برای مثال، یک lint ممکن است بخواهد بررسی کند آیا یک گره در نتیجهٔ گسترش ماکرو ساخته شده است یا اینکه بالای یک گره هیچ توضیحی (comment) وجود ندارد. مثال دیگر lintی است که می‌خواهد دو گره را که مقدار یکسانی دارند تطبیق دهد (مانند آنچه lintهایی مثل almost_swapped لازم دارند). به‌جای اینکه به کاربران اجازه دهد این بررسی‌ها را مستقیماً در الگو بنویسند (که ممکن است خواندن الگوها را دشوار کند)، راه‌حل پیشنهادی به کاربران اجازه می‌دهد به بخش‌هایی از یک عبارت الگو نام بدهند. هنگام تطبیق یک الگو با یک گرهٔ درخت نحو، مقدار بازگشتی شامل ارجاع به همهٔ گره‌هایی خواهد بود که با این زیرالگوهای نام‌دار تطبیق پیدا کرده‌اند. این شبیه گروه‌های ضبط (capture groups) در عبارت‌های منظم است.

    برای مثال، با توجه به الگوی زیر

    pattern!{
    // matches character literals
    my_pattern: Expr =
        Lit(Char(_#val_inner)#val)#val_outer
}

    می‌توان به این روش به گره‌هایی که با زیرالگوها تطبیق پیدا کرده‌اند ارجاع گرفت:

    ...
fn check_expr(expr: &syntax::ast::Expr) {
    if let Some(result) = my_pattern(expr) {
        result.val_inner  // type: &char
        result.val        // type: &syntax::ast::Lit
        result.val_outer  // type: &syntax::ast::Expr
    }
}

    نوع‌های درون ساختار result به الگو بستگی دارند. برای مثال، الگوی زیر

    pattern!{
    // matches arrays of character literals
    my_pattern_seq: Expr =
        Array( Lit(_)*#foo )
}

    با آرایه‌هایی تطبیق پیدا می‌کند که از هر تعداد عبارت لیترال تشکیل شده‌اند. چون این عبارت‌ها foo نام دارند، ساختار نتیجه یک ویژگی foo دارد که برداری از عبارت‌هاست:

    ...
if let Some(result) = my_pattern_seq(expr) {
    result.foo        // type: Vec<&syntax::ast::Expr>
}

    نوع نتیجهٔ دیگر زمانی پیش می‌آید که یک نام فقط در یکی از شاخه‌های یک انتخاب تعریف شده باشد:

    pattern!{
    // matches if expression is a boolean or integer literal
    my_pattern_alt: Expr =
        Lit( Bool(_#bar) | Int(_) )
}

    در الگوی بالا، نام bar فقط زمانی تعریف می‌شود که الگو با یک لیترال بولی تطبیق پیدا کند. اگر با لیترال صحیح تطبیق پیدا کند، نام تنظیم نمی‌شود. برای رعایت این موضوع، ویژگی bar در ساختار نتیجه از نوع اختیاری (option) است:

    ...
if let Some(result) = my_pattern_alt(expr) {
    result.bar        // type: Option<&bool>
}

    همچنین می‌توان یک نام را در چند شاخهٔ انتخاب به کار برد، به شرط آنکه نوع‌های سازگار داشته باشند:

    pattern!{
    // matches if expression is a boolean or integer literal
    my_pattern_mult: Expr =
        Lit(_#baz) | Array( Lit(_#baz) )
}
...
if let Some(result) = my_pattern_mult(expr) {
    result.baz        // type: &syntax::ast::Lit
}

    زیرتطبیق‌های نام‌دار یک فضای نام تخت هستند و این عمدی است. در مثال بالا، دو زیرساختار متفاوت به یک نام تخت اختصاص داده شده‌اند. انتظار دارم برای بیشتر lintها یک فضای نام تخت کافی باشد و کار کردن با آن از فضای نام سلسله‌مراتبی آسان‌تر باشد.

    دو مرحله

    با استفاده از زیرالگوهای نام‌دار، کاربران می‌توانند lintها را در دو مرحله بنویسند. نخست، یک انتخاب درشت از تطبیق‌های ممکن با نحو الگو تولید می‌شود. در مرحلهٔ دوم، ارجاع‌های زیرالگوهای نام‌دار را می‌توان برای انجام آزمون‌های بیشتر به کار برد، مانند تأیید اینکه یک گره در نتیجهٔ گسترش ماکرو ساخته نشده است.

    پیاده‌سازی lintهای Clippy با استفاده از الگوها

    به‌عنوان یک مثال «دنیای واقعی»، lint ‏collapsible_if را با استفاده از الگوها دوباره پیاده‌سازی کردم. کد را می‌توان اینجا یافت. نسخهٔ مبتنی بر الگو همهٔ آزمون‌هایی را که برای collapsible_if نوشته شده بود با موفقیت می‌گذراند.

    توضیح در سطح مرجع

    نمای کلی

    نمودار زیر وابستگی‌های میان بخش‌های اصلی راه‌حل پیشنهادی را نشان می‌دهد:

                              Pattern syntax
                                |
                                |  parsing / lowering
                                v
                           PatternTree
                                ^
                                |
                                |
                          IsMatch trait
                                |
                                |
             +---------------+-----------+---------+
             |               |           |         |
             v               v           v         v
        syntax::ast     rustc::hir      syn       ...

    نحو الگوی توصیف‌شده در بخش پیشین تجزیه / پایین‌آوری (lowering) می‌شود و به ساختار دادهٔ موسوم به PatternTree تبدیل می‌شود که یک الگوی معتبر درخت نحو را نشان می‌دهد. تطبیق یک PatternTree با یک درخت نحو واقعی (مثلاً AST / HIR زبان Rust یا AST کتابخانهٔ syn و …) با استفاده از صفت IsMatch انجام می‌شود.

    PatternTree و صفت IsMatch در بخش‌های بعدی با جزئیات بیشتر معرفی می‌شوند.

    PatternTree

    ساختار دادهٔ اصلی این RFC PatternTree است.

    این ساختار دادهٔ شبیه AST / HIR زبان Rust است، اما با تفاوت‌های زیر:

    • PatternTree اطلاعات تجزیه مانند Spanها را شامل نمی‌شود
    • PatternTree می‌تواند حالت‌های جایگزین، دنباله‌ها و اختیاری‌ها را نشان دهد

    کد زیر نسخهٔ ساده‌شدهٔ PatternTree فعلی را نشان می‌دهد:

    Note

    نکته: پیاده‌سازی فعلی را می‌توان اینجا یافت.

    pub enum Expr {
    Lit(Alt<Lit>),
    Array(Seq<Expr>),
    Block_(Alt<BlockType>),
    If(Alt<Expr>, Alt<BlockType>, Opt<Expr>),
    IfLet(
        Alt<BlockType>,
        Opt<Expr>,
    ),
}

pub enum Lit {
    Char(Alt<char>),
    Bool(Alt<bool>),
    Int(Alt<u128>),
}

pub enum Stmt {
    Expr(Alt<Expr>),
    Semi(Alt<Expr>),
}

pub enum BlockType {
    Block(Seq<Stmt>),
}

    ساختارهای Alt، Seq و Opt به این شکل هستند:

    Note

    نکته: پیاده‌سازی فعلی را می‌توان اینجا یافت.

    pub enum Alt<T> {
    Any,
    Elmt(Box<T>),
    Alt(Box<Self>, Box<Self>),
    Named(Box<Self>, ...)
}

pub enum Opt<T> {
    Any,  // anything, but not None
    Elmt(Box<T>),
    None,
    Alt(Box<Self>, Box<Self>),
    Named(Box<Self>, ...)
}

pub enum Seq<T> {
    Any,
    Empty,
    Elmt(Box<T>),
    Repeat(Box<Self>, RepeatRange),
    Seq(Box<Self>, Box<Self>),
    Alt(Box<Self>, Box<Self>),
    Named(Box<Self>, ...)
}

pub struct RepeatRange {
    pub start: usize,
    pub end: Option<usize>  // exclusive
}

    تجزیه / پایین‌آوری

    ورودی یک فراخوانی ماکروی pattern! ابتدا به یک ParseTree تجزیه می‌شود و سپس به یک PatternTree پایین‌آورده می‌شود.

    الگوهای معتبر به تعریف‌های PatternTree بستگی دارند. برای مثال، الگوی Lit(Bool(_)*) معتبر نیست، چون نوع پارامتر حالت Lit از شمارش Expr برابر Any<Lit> است و بنابراین از تکرار (*) پشتیبانی نمی‌کند. به‌عنوان مثالی دیگر، Array( Lit(_)* ) الگویی معتبر است، چون پارامتر Array از نوع Seq<Expr> است که دنباله‌ها و تکرارها را مجاز می‌کند.

    Note

    نکته: نام‌ها در نحو الگو با حالت‌های شمارش PatternTree متناظرند. برای مثال، Lit در الگوی بالا به حالت Lit از شمارش Expr (یعنی Expr::Lit) اشاره دارد، نه شمارش Lit.

    صفت IsMatch

    نحو الگو و PatternTree از پیاده‌سازی‌های مشخص درخت نحو (AST / HIR زبان Rust، syn و …) مستقل هستند. با نگاه به مثال‌های مختلف الگو در بخش‌های پیشین می‌توان دید که الگوها هیچ اطلاعاتی مختص یک پیاده‌سازی مشخص از درخت نحو در بر ندارند. در مقابل، lintهای Clippy در حال حاضر با گره‌های درخت نحو AST / HIR تطبیق می‌دهند و بنابراین مستقیماً به پیاده‌سازی آن‌ها وابسته‌اند.

    پیوند میان PatternTree و پیاده‌سازی‌های مشخص درخت نحو، صفت IsMatch است. این صفت تعریف می‌کند چگونه گره‌های PatternTree را با گره‌های مشخص درخت نحو تطبیق دهیم. پیاده‌سازی ساده‌شده‌ای از صفت IsMatch در زیر نشان داده شده است:

    pub trait IsMatch<O> {
    fn is_match(&self, other: &'o O) -> bool;
}

    این صفت باید روی هر شمارش از PatternTree پیاده‌سازی شود (برای نوع‌های متناظر درخت نحو). برای مثال، پیاده‌سازی IsMatch برای تطبیق ast::LitKind با شمارش Lit در PatternTree ممکن است به این شکل باشد:

    impl IsMatch<ast::LitKind> for Lit {
    fn is_match(&self, other: &ast::LitKind) -> bool {
        match (self, other) {
            (Lit::Char(i), ast::LitKind::Char(j)) => i.is_match(j),
            (Lit::Bool(i), ast::LitKind::Bool(j)) => i.is_match(j),
            (Lit::Int(i), ast::LitKind::Int(j, _)) => i.is_match(j),
            _ => false,
        }
    }
}

    همهٔ پیاده‌سازی‌های IsMatch برای تطبیق PatternTree فعلی با syntax::ast را می‌توان اینجا یافت.

    معایب

    کارایی

    کد تطبیق الگو در حال حاضر برای کارایی بهینه نشده است، بنابراین ممکن است از کد تطبیق دست‌نویس کندتر باشد. افزون بر این، رویکرد دو مرحله‌ای (ابتدا تطبیق با الگوی درشت و سپس بررسی ویژگی‌های اضافی) ممکن است از روش فعلی، یعنی بررسی ساختار و ویژگی‌های اضافی در یک گذر، کندتر باشد. برای مثال، lint زیر

    pattern!{
    pat_if_without_else: Expr =
        If(
            _,
            Block(
                Expr( If(_, _, ())#inner )
                | Semi( If(_, _, ())#inner )
            )#then,
            ()
        )
}
...
fn check_expr(&mut self, cx: &EarlyContext<'_>, expr: &ast::Expr) {
    if let Some(result) = pat_if_without_else(expr) {
        if !block_starts_with_comment(cx, result.then) {
            ...
        }
}

    ابتدا با الگو تطبیق می‌دهد و سپس بررسی می‌کند که بلوک then با یک comment شروع نشده باشد. با رویکرد فعلی clippy می‌توان این شرط‌ها را زودتر بررسی کرد:

    fn check_expr(&mut self, cx: &EarlyContext<'_>, expr: &ast::Expr) {
    if_chain! {
        if let ast::ExprKind::If(ref check, ref then, None) = expr.node;
        if !block_starts_with_comment(cx, then);
        if let Some(inner) = expr_block(then);
        if let ast::ExprKind::If(ref check_inner, ref content, None) = inner.node;
        then {
            ...
        }
    }
}

    اینکه این موضوع به افت کارایی منجر شود یا نه به الگوهای واقعی بستگی دارد. اگر معلوم شد مشکل‌ساز است، الگوریتم‌های تطبیق الگو را می‌توان گسترش داد تا «فیلتر کردن زودهنگام» ممکن شود (بخش فیلتر کردن زودهنگام در امکانات آینده را ببینید).

    با این حال، هیچ محدودیت مفهومی‌ای دربارهٔ کارایی تطبیق الگو نمی‌بینم.

    کاربردپذیری

    حتی اگر انتظار داشته باشم بسیاری از lintها را بتوان با نحو الگوی پیشنهادی نوشت، بعید است همهٔ lintها را بتوان با الگوها بیان کرد. گمان می‌کنم همچنان lintهایی خواهند بود که باید با نوشتن کد تطبیق الگوی سفارشی پیاده‌سازی شوند. این به ترکیبی در کدبیس clippy می‌انجامد که در آن برخی lintها با الگوها پیاده‌سازی شده‌اند و برخی نه. این ناهمگونی ممکن است یک عیب به حساب بیاید.

    منطق و جایگزین‌ها

    مشخص کردن lintها با الگوهای درخت نحو در مقایسه با رویکرد فعلی نوشتن دستی کد تطبیق، چند مزیت دارد. نخست، الگوهای درخت نحو به کاربران اجازه می‌دهند الگوها را به شیوه‌ای ساده و گویا توصیف کنند. این نوشتن lintهای جدید را هم برای تازه‌کارها و هم برای متخصصان آسان‌تر می‌کند و همچنین خواندن / تغییر lintهای موجود را ساده‌تر می‌کند.

    مزیت دیگر این است که lintها از پیاده‌سازی‌های مشخص درخت نحو (مثلاً AST / HIR و …) مستقل می‌شوند. وقتی این پیاده‌سازی‌های درخت نحو تغییر می‌کنند، فقط پیاده‌سازی‌های صفت IsMatch باید اصلاح شوند و lintهای موجود می‌توانند بدون تغییر بمانند. این همچنین یعنی اگر پیاده‌سازی‌های صفت IsMatch در کامپایلر ادغام شوند، به‌روزرسانی پیاده‌سازی‌های IsMatch برای کامپایل موفق کامپایلر الزامی خواهد بود. این می‌تواند تعداد دفعاتی را که Clippy به‌خاطر تغییرات کامپایلر خراب می‌شود کاهش دهد. مزیت دیگر استقلال الگو این است که تبدیل یک lint از نوع EarlyLintPass به LatePassLint به بازنویسی کل کد تطبیق الگو نیاز ندارد. در واقع، ممکن است الگو بدون هیچ تغییری کاملاً خوب کار کند.

    جایگزین‌ها

    نحو الگوی شبیه Rust

    نحو الگوی پیشنهادی از کاربران می‌خواهد ساختار PatternTree (که بسیار شبیه ساختار AST / HIR است) و همچنین نحو الگو را بدانند. یک جایگزین، معرفی نحو الگویی است که شبیه نحو واقعی Rust باشد (احتمالاً مانند ماکروی quote!). برای مثال، الگویی که عبارت‌های if با false در شرط را تطبیق می‌دهد می‌تواند این شکلی باشد:

    if false {
    #[*]
}

    مشکلات

    گسترش نحو Rust (که خودش کاملاً پیچیده است) با نحو اضافی لازم برای مشخص کردن الگوها (انتخاب‌ها، دنباله‌ها، تکرارها، زیرتطبیق‌های نام‌دار و …) ممکن است خواندن را دشوار و تجزیهٔ درست را واقعاً سخت کند.

    برای مثال، الگویی که یک عملیات دودویی با 0 در دو طرف را تطبیق می‌دهد ممکن است این شکلی باشد:

    0 #[*:BinOpKind] 0

    حالا این مثال کمی پیچیده‌تر را در نظر بگیرید:

    1 + 0 #[*:BinOpKind] 0

    تجزیه‌گر باید تقدم #[*:BinOpKind] را بداند، چون بر ساختار AST حاصل اثر می‌گذارد. 1 + 0 + 0 به‌صورت (1 + 0) + 0 تجزیه می‌شود، در حالی که 1 + 0 * 0 به‌صورت 1 + (0 * 0) تجزیه می‌شود. چون الگو می‌تواند هر BinOpKind باشد، تقدم را نمی‌توان از پیش دانست.

    مثال دیگری از مشکل، زیرتطبیق‌های نام‌دار است. به این الگو نگاه کنید:

    fn test() {
    1 #foo
}

    #foo به کدام گره اشاره دارد؟ int، ast::Lit، ast::Expr یا ast::Stmt؟ نام‌گذاری زیرالگوها در نحوی شبیه Rust دشوار است، چون بسیاری از گره‌های AST عنصر نحوی‌ای ندارند که بتوان برچسب نام را روی آن گذاشت. در این موارد، تنها گزینهٔ معقول این است که برچسب نام به بیرونی‌ترین گره (در مثال بالا ast::Stmt) اختصاص یابد، چون اطلاعات همهٔ گره‌های فرزند را می‌توان از طریق بیرونی‌ترین گره به دست آورد. مشکل این کار آن خواهد بود که دسترسی به گره‌های درونی (مانند ast::Lit) دوباره به تطبیق الگوی دستی نیاز خواهد داشت.

    به‌طور کلی، نحو Rust ساختار کد را به‌صورت ضمنی در بر دارد. این ساختار هنگام تجزیه بازسازی می‌شود (مثلاً عملیات دودویی با تقدم عملگرها و چپ‌به‌راست بازسازی می‌شوند) و یکی از دلایل پیچیده بودن تجزیه است. مزیت این رویکرد آن است که نوشتن کد برای کاربران ساده‌تر می‌شود.

    هنگام نوشتن الگوهای درخت نحو، هر عنصر از سلسله‌مراتب ممکن است جایگزین‌ها، تکرارها و غیره داشته باشد. رعایت این موضوع و در عین حال حفظ نحوی انسان‌پسند که ساختار را به‌صورت ضمنی در بر دارد، واقعاً پیچیده، اگر نگوییم غیرممکن، به نظر می‌رسد.

    توسعهٔ چنین نحوی همچنین نیازمند نگهداری یک تجزیه‌گر سفارشی است که دست‌کم به پیچیدگی خود تجزیه‌گر Rust باشد. افزون بر این، تغییرات آیندهٔ نحو Rust ممکن است با چنین نحوی ناسازگار باشند.

    در مجموع، فکر می‌کنم توسعهٔ چنین نحوی پیچیدگی زیادی برای حل یک مشکل نسبتاً کوچک وارد می‌کند.

    مسئلهٔ ناآشنا بودن کاربران با ساختار PatternTree را می‌توان با ابزاری حل کرد که با گرفتن یک برنامهٔ Rust، الگویی تولید کند که فقط با همان برنامه تطبیق پیدا کند (شبیه lint ‏author در Clippy).

    برای برخی موارد ساده (مانند نخستین مثال بالا)، شاید بتوان با موفقیت نحو Rust و نحو الگو را ترکیب کرد. این حوزه را می‌توان در یک توسعهٔ آینده بیشتر کاوید.

    پیشینه

    نحو الگو به‌شدت از عبارت‌های منظم (تکرارها، جایگزین‌ها، دنباله‌ها و …) الهام گرفته است.

    تا آنجا که تاکنون دیده‌ام، دیگر linterها هم lintهایی پیاده‌سازی می‌کنند که مستقیماً روی ساختارهای دادهٔ درخت نحو کار می‌کنند، درست مثل Clippy در حال حاضر. بنابراین نحو الگو را جدید می‌دانم، اما لطفاً اگر اشتباه می‌کنم اصلاحم کنید.

    پرسش‌های حل‌نشده

    چگونه چند تطبیق را مدیریت کنیم؟

    هنگام تطبیق یک گرهٔ درخت نحو با یک الگو، ممکن است چند روش برای تطبیق الگو وجود داشته باشد. یک مثال ساده از این وضعیت، الگوی زیر است:

    pattern!{
    my_pattern: Expr =
        Array( _* Lit(_)+#literals)
}

    این الگو با آرایه‌هایی تطبیق پیدا می‌کند که دست‌کم با یک لیترال پایان می‌یابند. حالا با آرایهٔ [x, 1, 2]، آیا 1 باید جزو بخش _* تطبیق داده شود یا جزو بخش Lit(_)+ الگو؟ این تفاوت مهم است، چون زیرتطبیق نام‌دار #literals بسته به نحوهٔ تطبیق الگو ۱ یا ۲ عنصر خواهد داشت. در عبارت‌های منظم، این مشکل با تطبیق «حریصانه» (greedy) به‌صورت پیش‌فرض و تطبیق «غیرحریصانه» (non-greedy) به‌صورت اختیاری حل می‌شود.

    هنوز زیاد به این موضوع نپرداخته‌ام، چون نمی‌دانم برای بیشتر lintها چقدر اهمیت دارد. پیاده‌سازی فعلی فقط نخستین تطبیقی را که پیدا کند برمی‌گرداند.

    امکانات آینده

    پیاده‌سازی بقیهٔ نحو Rust

    پروژهٔ فعلی فقط بخش کوچکی از نحو Rust را پیاده‌سازی می‌کند. در آینده باید این به‌تدریج به نحو بیشتری گسترش یابد تا پیاده‌سازی lintهای بیشتر ممکن شود. پیاده‌سازی بخش بیشتری از نحو Rust نیازمند گسترش پیاده‌سازی‌های PatternTree و IsMatch است، اما باید نسبتاً سرراست باشد.

    فیلتر کردن زودهنگام

    همان‌طور که در بخش معایب/کارایی توضیح داده شد، امکان انجام بررسی‌های اضافی در حین تطبیق الگو ممکن است سودمند باشد.

    الگوی زیر نشان می‌دهد این کار چه شکلی می‌تواند داشته باشد:

    pattern!{
    pat_if_without_else: Expr =
        If(
            _,
            Block(
                Expr( If(_, _, ())#inner )
                | Semi( If(_, _, ())#inner )
            )#then,
            ()
        )
    where
        !in_macro(#then.span);
}

    تفاوت آن با فیلتر کردن دو مرحله‌ای پیشنهادی فعلی این است که با فیلتر کردن زودهنگام، شرط (در اینجا !in_macro(#then.span)) به محض تطبیق Block(_)#then ارزیابی می‌شود.

    ایدهٔ دیگر در این زمینه، معرفی نحوی برای ارجاع‌های برگشتی (backreference) است. از آن‌ها می‌توان برای الزام اینکه چند بخش از یک الگو باید با مقدار یکسانی تطبیق پیدا کنند استفاده کرد. برای مثال، lint ‏assign_op_pattern که دنبال a = a op b می‌گردد و تغییر آن به a op= b را توصیه می‌کند، لازم دارد که هر دو رخداد a یکسان باشند. با استفاده از =#... به‌عنوان نحو ارجاع‌های برگشتی، lint را می‌توان به این شکل پیاده‌سازی کرد:

    pattern!{
    assign_op_pattern: Expr =
        Assign(_#target, Binary(_, =#target, _)
}

    تطبیق نوادگان

    بسیاری از lintها در حال حاضر بازدیدکننده‌های (visitor) سفارشی پیاده‌سازی می‌کنند که بررسی می‌کنند آیا زیردرختی (که ممکن است فرزند مستقیم نباشد) از گرهٔ جاری ویژگی‌هایی دارد یا نه. این را با نحو الگوی پیشنهادی نمی‌توان بیان کرد. گسترش نحو الگو برای امکان‌دادن به الگوهایی مانند «تابعی که دست‌کم دو دستور return دارد» می‌تواند افزودنی کاربردی باشد.

    عملگر نقیض برای انتخاب‌ها

    برای الگوهایی مانند «لیترالی که لیترال بولی نیست»، در حال حاضر باید همهٔ جایگزین‌ها به‌جز حالت بولی را فهرست کرد. معرفی عملگر نقیضی که اجازه دهد Lit(!Bool(_)) نوشته شود ایدهٔ خوبی به نظر می‌رسد. این الگو معادل Lit( Char(_) | Int(_) ) خواهد بود (با توجه به اینکه در حال حاضر فقط سه نوع لیترال پیاده‌سازی شده است).

    ترکیب تابعی

    الگوها در حال حاضر هیچ مفهومی از ترکیب (composition) ندارند. این به تکرار در درون الگوها منجر می‌شود. برای مثال، یکی از الگوهای collapsible-if در حال حاضر باید به این شکل نوشته شود:

    pattern!{
    pat_if_else: Expr =
        If(
            _,
            _,
            Block_(
                Block(
                    Expr((If(_, _, _?) | IfLet(_, _?))#else_) |
                    Semi((If(_, _, _?) | IfLet(_, _?))#else_)
                )#block_inner
            )#block
        ) |
        IfLet(
            _,
            Block_(
                Block(
                    Expr((If(_, _, _?) | IfLet(_, _?))#else_) |
                    Semi((If(_, _, _?) | IfLet(_, _?))#else_)
                )#block_inner
            )#block
        )
}

    اگر الگوها از تعریف توابعی از زیرالگوها پشتیبانی می‌کردند، کد را می‌شد به این شکل ساده کرد:

    pattern!{
    fn expr_or_semi(expr: Expr) -> Stmt {
        Expr(expr) | Semi(expr)
    }
    fn if_or_if_let(then: Block, else: Opt<Expr>) -> Expr {
        If(_, then, else) | IfLet(then, else)
    }
    pat_if_else: Expr =
        if_or_if_let(
            _,
            Block_(
                Block(
                    expr_or_semi( if_or_if_let(_, _?)#else_ )
                )#block_inner
            )#block
        )
}

    افزون بر این، الگوهای رایجی مانند expr_or_semi را می‌توان میان lintهای مختلف به اشتراک گذاشت.

    نویسندهٔ الگوی Clippy

    بهبود دیگر می‌تواند ساخت ابزاری باشد که با گرفتن نحو معتبر Rust، الگویی تولید کند که دقیقاً با همین نحو تطبیق پیدا کند. این کار شروع نوشتن یک الگو را آسان‌تر می‌کند. کاربر می‌تواند به الگوهای تولیدشده برای چند نمونه‌کد Rust نگاه کند و از آن اطلاعات برای نوشتن الگویی استفاده کند که با همهٔ آن‌ها تطبیق پیدا کند.

    این شبیه lint ‏author در clippy است.

    پشتیبانی از نحوهای دیگر

    بیشتر سامانهٔ پیشنهادی مستقل از زبان است. برای مثال، نحو الگو را می‌توان برای توصیف الگوها در زبان‌های برنامه‌نویسی دیگر هم به کار برد.

    برای پشتیبانی از نحو زبان‌های دیگر، باید PatternTree دیگری پیاده‌سازی کرد که AST آن زبان‌ها را به‌قدر کافی توصیف کند، و IsMatch را برای این PatternTree و AST آن زبان‌ها پیاده‌سازی کرد.

    یکی از جنبه‌های این کار آن است که حتی می‌توان lintهایی نوشت که روی خود نحو الگو کار کنند. برای مثال، هنگام نوشتن الگوی زیر

    pattern!{
    my_pattern: Expr =
        Array( Lit(Bool(false)) Lit(Bool(false)) )
}

    یک lint که روی AST نحو الگو کار می‌کند می‌تواند پیشنهاد کند به‌جای آن از این الگو استفاده شود:

    pattern!{
    my_pattern: Expr =
        Array( Lit(Bool(false)){2} )
}

    در آینده، Clippy می‌تواند از این سامانه برای فراهم کردن lint برای نحوهای سفارشی، مانند آنچه در ماکروها یافت می‌شود، نیز استفاده کند.
