    افزودن یک lint جدید

    احتمالاً به این دلیل اینجا هستید که می‌خواهید یک lint جدید به Clippy اضافه کنید. اگر این نخستین بار است که در Clippy مشارکت می‌کنید، این سند شما را گام‌به‌گام در ساخت یک lint نمونه از صفر راهنمایی می‌کند.

    برای شروع، lintی می‌سازیم که تابع‌هایی با نام foo را شناسایی می‌کند، چون به‌وضوح نامی غیرتوصیفی است.

    آماده‌سازی

    مستندات مبانی را ببینید.

    شروع کار

    هنگام ساخت یک lint جدید، مقداری کد boilerplate باید آماده شود. خوشبختانه می‌توانید با ابزارهای توسعهٔ Clippy این کار را به آن‌ها بسپارید. ما lint جدید خود را foo_functions نام‌گذاری می‌کنیم (نام lintها معمولاً به‌صورت snake case نوشته می‌شود) و به اطلاعات نوع نیازی نداریم، بنابراین از نوع early pass خواهد بود (در این مورد در ادامه بیشتر می‌گوییم). اگر مطمئن نیستید نامی که انتخاب کرده‌اید با lint مناسب است، به رهنمودهای نام‌گذاری lint ما نگاهی بیندازید.

    تعریف lint ما

    برای شروع، دو راه برای تعریف lint ما وجود دارد.

    مستقل

    دستور: cargo dev new_lint --name=foo_functions --pass=early --category=pedantic (اگر category داده نشود، پیش‌فرض آن nursery است)

    این دستور یک فایل جدید با نام clippy_lints/src/foo_functions.rs می‌سازد و همچنین lint را ثبت می‌کند.

    نوع مشخص

    دستور: cargo dev new_lint --name=foo_functions --type=functions --category=pedantic

    این دستور یک فایل جدید با نام clippy_lints/src/{type}/foo_functions.rs می‌سازد.

    توجه کنید که این دستور به‌جای --pass پرچم --type دارد. برخلاف تعریف مستقل، این lint به معنای سنتی ثبت نمی‌شود. در عوض، lint خود را از داخل lint pass مربوط به آن نوع فراخوانی می‌کنید که در clippy_lints/src/{type}/mod.rs قرار دارد.

    «نوع» (type) فقط نام یک پوشه در clippy_lints/src است، مانند functions در دستور نمونه. این پوشه‌ها گروه‌بندی‌هایی از lintها با رفتارهای مشترک هستند، بنابراین اگر lint شما در یکی از آن‌ها می‌گنجد، بهتر است آن را به همان نوع اضافه کنید.

    محل آزمون‌ها

    هر دو دستور یک فایل با نام tests/ui/foo_functions.rs می‌سازند. برای lintهای cargo، به‌طور پیش‌فرض دو سلسله‌مراتب پروژه (fail/pass) در tests/ui-cargo ساخته می‌شود.

    در ادامه این فایل‌ها را باز می‌کنیم و lint خود را اضافه می‌کنیم!

    آزمایش

    بیایید ابتدا چند آزمون بنویسیم که بتوانیم هنگام تکرار و پیشرفت روی lint اجرایشان کنیم.

    Clippy برای آزمایش از آزمون‌های UI استفاده می‌کند. آزمون‌های UI بررسی می‌کنند که خروجی Clippy دقیقاً همان چیزی باشد که انتظار می‌رود. هر آزمون فقط یک فایل ساده از Rust است که کدی را که می‌خواهیم بررسی کنیم در خود دارد. خروجی Clippy با یک فایل .stderr مقایسه می‌شود. توجه کنید که لازم نیست این فایل را خودتان بسازید؛ تولید فایل‌های .stderr را در ادامه توضیح می‌دهیم.

    کار را با باز کردن فایل آزمونی که در tests/ui/foo_functions.rs ساخته شده است شروع می‌کنیم.

    فایل را با چند نمونه به‌روز کنید تا شروع کنیم:

    #![allow(unused)]
#![warn(clippy::foo_functions)]

// Impl methods
struct A;
impl A {
    pub fn fo(&self) {}
    pub fn foo(&self) {}
    //~^ foo_functions
    pub fn food(&self) {}
}

// Default trait methods
trait B {
    fn fo(&self) {}
    fn foo(&self) {}
    //~^ foo_functions
    fn food(&self) {}
}

// Plain functions
fn fo() {}
fn foo() {}
//~^ foo_functions
fn food() {}

fn main() {
    // We also don't want to lint method calls
    foo();
    let a = A;
    a.foo();
}

    توجه کنید که ما کامنت‌های حاشیه‌نویسی‌ای با نام lint خود اضافه می‌کنیم تا خط‌هایی را که انتظار خطا در آن‌ها داریم علامت بزنیم. جز در موارد بسیار خاص (//@check-pass)، برای اینکه یک فایل آزمون پذیرفته شود، باید دست‌کم یک نشانگر خطا در آن وجود داشته باشد.

    وقتی lint را پیاده‌سازی کردیم، می‌توانیم TESTNAME=foo_functions cargo uibless را اجرا کنیم تا فایل .stderr تولید شود. اگر lint ما از پیشنهادهای ساخت‌یافته استفاده کند، این دستور فایل .fixed متناظر را نیز تولید می‌کند.

    تا زمانی که مشغول پیاده‌سازی lint هستیم، می‌توانیم آزمون UI را مرتب اجرا کنیم. این کار به ما امکان می‌دهد با بررسی فایل .stderr که در هر اجرای آزمون به‌روز می‌شود، ببینیم خروجی به آنچه می‌خواهیم نزدیک می‌شود یا نه.

    وقتی lint را پیاده‌سازی کردیم، اجرای TESTNAME=foo_functions cargo uitest باید به‌تنهایی موفق شود. هنگام commit کردن lint، باید فایل‌های .stderr تولیدشده و در صورت وجود، فایل‌های .fixed را نیز commit کنیم. به‌طور کلی باید فقط فایل‌هایی را commit کنید که cargo bless برای همان lintی که در حال ساخت یا ویرایش آن هستید تغییر داده است.

    Note

    توجه: می‌توانید با تعیین فهرستی از نام‌ها که با ویرگول جدا شده‌اند، چند فایل آزمون را با هم اجرا کنید: TESTNAME=foo_functions,test2,test3.

    lintهای cargo

    برای lintهای cargo، روند آزمایش از این جهت فرق دارد که ما به فایل مانیفست Cargo.toml علاقه‌مندیم. همچنین به یک crate کمینه نیاز داریم که با آن مانیفست مرتبط باشد.

    اگر نام lint جدید ما مثلاً foo_categories باشد، پس از اجرای cargo dev new_lint --name=foo_categories --type=cargo --category=cargo به‌طور پیش‌فرض دو crate جدید را می‌یابیم که هر کدام فایل مانیفست خود را دارند:

    • tests/ui-cargo/foo_categories/fail/Cargo.toml: این فایل باید باعث شود lint جدید خطا صادر کند.
    • tests/ui-cargo/foo_categories/pass/Cargo.toml: این فایل نباید lint را فعال کند.

    اگر به موارد بیشتری نیاز دارید، می‌توانید یکی از این crateها را (در foo_categories) کپی کنید و نام آن را تغییر دهید.

    روند تولید فایل .stderr یکسان است و قرار دادن متغیر TESTNAME پیش از cargo uitest نیز کار می‌کند.

    آزمون‌های Rustfix

    اگر lintی که روی آن کار می‌کنید از پیشنهادهای ساخت‌یافته استفاده می‌کند، آزمون با اجرای rustfix برای آن آزمون، یک فایل .fixed می‌سازد. Rustfix پیشنهادهای lint را روی کد فایل آزمون اعمال می‌کند و نتیجه را با محتوای یک فایل .fixed مقایسه می‌کند.

    از cargo bless استفاده کنید تا فایل .fixed هنگام اجرای آزمون‌ها به‌طور خودکار تولید شود.

    آزمایش دستی

    اگر چند println! اضافه کرده باشید و خروجی مجموعه آزمون‌ها ناخوانا شده باشد، آزمایش دستی روی یک فایل نمونه می‌تواند مفید باشد. برای امتحان Clippy با تغییرات محلی خود، دستور زیر را از پوشهٔ Clippy اجرا کنید:

    cargo dev lint input.rs

    برای اجرای Clippy روی یک پروژهٔ موجود، به‌جای یک فایل تکی، می‌توانید از این دستور استفاده کنید

    cargo dev lint /path/to/project

    یا یک toolchain از rustup راه‌اندازی کنید که به باینری‌های محلی Clippy اشاره کند

    cargo dev setup toolchain

# Then in `/path/to/project` you can run
cargo +clippy clippy

    اعلام lint

    بیایید با باز کردن فایل جدیدی که در crate ‏clippy_lints در clippy_lints/src/foo_functions.rs ساخته شده است شروع کنیم. این همان crate ای است که همهٔ کد lintها در آن قرار دارد. این فایل از پیش چند چیز اولیه را که به آن‌ها نیاز داریم import کرده است:

    use rustc_lint::{EarlyLintPass, EarlyContext};
use rustc_session::declare_lint_pass;
use rustc_ast::ast::*;

    گام بعدی به‌روز کردن اعلام lint است. lintها با ماکروی declare_clippy_lint! اعلام می‌شوند و ما فقط باید اعلام تولیدشدهٔ خودکار را به‌روز کنیم تا توضیح واقعی داشته باشد، چیزی شبیه این:

    declare_clippy_lint! {
    /// ### What it does
    ///
    /// ### Why is this bad?
    ///
    /// ### Example
    /// ```rust
    /// // example code
    /// ```
    #[clippy::version = "1.29.0"]
    pub FOO_FUNCTIONS,
    pedantic,
    "function named `foo`, which is not a descriptive name"
}
    • بخشی از خط‌ها که با /// شروع می‌شوند، بخش مستندات lint را تشکیل می‌دهند. این سبک پیش‌فرض مستندسازی است و به این شکل نمایش داده می‌شود. برای رندر کردن و باز کردن این مستندات به‌صورت محلی در مرورگر، cargo dev serve را اجرا کنید.
    • attribute ‏#[clippy::version] به‌عنوان بخشی از مستندات lint نمایش داده می‌شود. مقدار آن باید نسخهٔ فعلی Rust باشد که lint در آن توسعه داده می‌شود؛ می‌توانید آن را با اجرای rustc -vV در پوشهٔ rust-clippy به دست آورید. نسخه زیر release فهرست شده است. (نسخه را بدون پسوند -nightly به کار ببرید.)
    • FOO_FUNCTIONS نام lint ما است. هنگام نام‌گذاری lint خود حتماً رهنمودهای نام‌گذاری lint را رعایت کنید. به‌طور خلاصه، نام باید چیزی را که بررسی می‌شود بیان کند و هنگام استفاده با allow/warn/deny خوب خوانده شود.
    • pedantic سطح lint را روی Allow تنظیم می‌کند. نگاشت دقیق را می‌توانید اینجا بیابید
    • بخش آخر باید متنی باشد که توضیح دهد دقیقاً چه چیزی در کد نادرست است

    بقیهٔ این فایل شامل یک پیاده‌سازی خالی برای lint pass ما است که در این مورد EarlyLintPass است و باید این شکل را داشته باشد:

    // clippy_lints/src/foo_functions.rs

// .. imports and lint declaration ..

declare_lint_pass!(FooFunctions => [FOO_FUNCTIONS]);

impl EarlyLintPass for FooFunctions {}

    ثبت lint

    هنگام استفاده از cargo dev new_lint، lint به‌طور خودکار ثبت می‌شود و کار دیگری لازم نیست.

    وقتی lint جدید را دستی اعلام می‌کنید و از cargo dev update_lints استفاده می‌شود، ممکن است لازم باشد lint pass را دستی ثبت کنید؛ برای این کار یک ورودی به فراخوانی ماکروی early_lint_methods! در clippy_lints/src/lib.rs و در محل نشانگر // add early passes here اضافه کنید:

    FooFunctions: foo_functions::FooFunctions = foo_functions::FooFunctions,

    همان‌طور که انتظار می‌رود، یک ماکروی متناظر late_lint_methods! نیز وجود دارد. بدون یک ورودی در یکی از early_lint_methods! یا late_lint_methods!، lint pass مورد نظر اجرا نخواهد شد.

    یکی از دلایلی که cargo dev update_lints این گام را خودکار نمی‌کند این است که چند lint می‌توانند از یک lint pass مشترک استفاده کنند، بنابراین ممکن است هنگام افزودن یک lint جدید، ثبت lint pass پیش‌تر انجام شده باشد. دلیل دیگر خودکار نبودن این گام این است که ترتیب فهرست شدن passها ترتیب واقعی اجرای آن‌ها را تعیین می‌کند و این به نوبهٔ خود بر ترتیب خروجی lintهای صادرشده اثر می‌گذارد.

    lint passها

    نوشتن lintی که فقط نام یک تابع را بررسی می‌کند به این معناست که فقط با AST سروکار داریم و اصلاً لازم نیست با سامانهٔ نوع کار کنیم. این خوب است، زیرا نوشتن این lint خاص را ساده‌تر می‌کند.

    این تصمیم را باید برای هر lint جدید Clippy بگیریم. در نهایت به انتخاب بین EarlyLintPass و LateLintPass برمی‌گردد.

    EarlyLintPass پیش از بررسی نوع و lowering به HIR اجرا می‌شود، در حالی که LateLintPass پس از این مراحل اجرا می‌شود و به اطلاعات نوع دسترسی می‌دهد. دستور cargo dev new_lint به‌طور پیش‌فرض LateLintPass را که توصیه می‌شود انتخاب می‌کند، اما اگر lint شما فقط به تحلیل در سطح AST نیاز دارد، می‌توانید --pass=early را مشخص کنید.

    از آنجا که برای بررسی نام تابع به اطلاعات نوع نیازی نداریم، هنگام اجرای خودکارسازی lint جدید از --pass=early استفاده کردیم و همهٔ importها بر همین اساس اضافه شدند.

    صدور یک lint

    با آماده بودن آزمون‌های UI و اعلام lint، می‌توانیم کار روی پیاده‌سازی منطق lint را شروع کنیم.

    بیایید با پیاده‌سازی EarlyLintPass برای FooFunctions خود شروع کنیم:

    impl EarlyLintPass for FooFunctions {
    fn check_fn(&mut self, cx: &EarlyContext<'_>, fn_kind: FnKind<'_>, span: Span, _: NodeId) {
        // TODO: Emit lint here
    }
}

    ما متد check_fn را از صفت EarlyLintPass پیاده‌سازی می‌کنیم. این متد به ما دسترسی به اطلاعات گوناگونی دربارهٔ تابعی می‌دهد که در حال بررسی است. در بخش بعد بیشتر دربارهٔ آن می‌گوییم. فعلاً نگران جزئیات نباشیم و ابتدا lint خود را برای هر تعریف تابع صادر کنیم.

    بسته به اینکه پیام lint خود را چقدر پیچیده بخواهیم، می‌توانیم از میان طیف گسترده‌ای از تابع‌های صدور lint انتخاب کنیم. همهٔ آن‌ها در clippy_utils/src/diagnostics.rs قرار دارند.

    در این مورد span_lint_and_help مناسب‌ترین به نظر می‌رسد. این تابع به ما اجازه می‌دهد یک پیام راهنمای اضافی ارائه کنیم و ما واقعاً نمی‌توانیم نام بهتری را به‌طور خودکار پیشنهاد دهیم. این‌طور به نظر می‌رسد:

    impl EarlyLintPass for FooFunctions {
    fn check_fn(&mut self, cx: &EarlyContext<'_>, fn_kind: FnKind<'_>, span: Span, _: NodeId) {
        span_lint_and_help(
            cx,
            FOO_FUNCTIONS,
            span,
            "function named `foo`",
            None,
            "consider using a more meaningful name"
        );
    }
}

    اکنون اجرای آزمون UI ما باید خروجی‌ای تولید کند که پیام lint را در خود دارد.

    طبق rustc-dev-guide، متن باید عینی و بی‌پیرایه باشد و، مگر اینکه چند جمله لازم باشد، از حروف بزرگ و نقطه پرهیز کند. وقتی کد یا یک شناسه باید در پیام یا برچسب بیاید، باید داخل علامت‌های گراو (backtick) تکی قرار گیرد: `.

    افزودن منطق lint

    نوشتن منطق lint شما به احتمال زیاد با مثال ما تفاوت خواهد داشت، بنابراین این بخش نسبتاً کوتاه نگه داشته شده است.

    استفاده از متد check_fn ما را به FnKind دسترسی می‌دهد که دارای واریانت FnKind::Fn است. این واریانت از طریق یک Ident به نام تابع/متد دسترسی می‌دهد.

    با این امکان می‌توانیم متد check_fn خود را به این شکل گسترش دهیم:

    impl EarlyLintPass for FooFunctions {
    fn check_fn(&mut self, cx: &EarlyContext<'_>, fn_kind: FnKind<'_>, span: Span, _: NodeId) {
        if is_foo_fn(fn_kind) {
            span_lint_and_help(
                cx,
                FOO_FUNCTIONS,
                span,
                "function named `foo`",
                None,
                "consider using a more meaningful name"
            );
        }
    }
}

    ما شرط lint را از صدور lint جدا می‌کنیم، چون این کار خواندن کد را کمی آسان‌تر می‌کند. در برخی موارد این جداسازی همچنین امکان می‌دهد برای تابع جداشده چند آزمون واحد (در مقابل صرفاً آزمون‌های UI) بنویسیم.

    در مثال ما، is_foo_fn به این شکل است:

    // use statements, impl EarlyLintPass, check_fn, ..

fn is_foo_fn(fn_kind: FnKind<'_>) -> bool {
    match fn_kind {
        FnKind::Fn(_, _, Fn { ident, .. }) => {
            // check if `fn` name is `foo`
            ident.name.as_str() == "foo"
        }
        // ignore closures
        FnKind::Closure(..) => false
    }
}

    اکنون باید مجموعهٔ کامل آزمون‌ها را نیز با cargo test اجرا کنیم. در این مرحله اجرای cargo test باید خروجی مورد انتظار را تولید کند. به یاد داشته باشید cargo bless را اجرا کنید تا فایل .stderr به‌روز شود.

    cargo test (در مقابل cargo uitest) همچنین تضمین می‌کند که پیاده‌سازی lint ما خودش هیچ‌یک از lintهای Clippy را نقض نمی‌کند.

    پیاده‌سازی lint همین بود. اکنون اجرای cargo test باید موفق شود.

    تعیین حداقل نسخهٔ پشتیبانی‌شدهٔ Rust (MSRV) برای lint

    گاهی یک lint پیشنهادهایی می‌دهد که به نسخهٔ مشخصی از Rust نیاز دارند. برای مثال، lint ‏manual_strip استفاده از str::strip_prefix و str::strip_suffix را پیشنهاد می‌کند که فقط پس از Rust 1.45 در دسترس هستند. در چنین مواردی باید مطمئن شوید MSRV پیکربندی‌شده برای پروژه بزرگ‌تر یا مساوی MSRV قابلیت مورد نیاز Rust است. اگر در یک پیشنهاد چند قابلیت به کار رفته است، MSRVی را انتخاب کنید که همهٔ آن‌ها را پشتیبانی کند.

    ابتدا یک نام مستعار MSRV برای قابلیت مورد نیاز در clippy_utils::msrvs اضافه کنید. بعداً می‌توان به آن مثلاً با msrvs::STR_STRIP_PREFIX دسترسی داشت.

    msrv_aliases! {
    ..
    1,45,0 { STR_STRIP_PREFIX }
}

    برای دسترسی به MSRV پیکربندی‌شدهٔ پروژه، باید در ساختار LintPass یک فیلد msrv و یک سازنده برای مقداردهی اولیهٔ آن فیلد داشته باشید. مقدار msrv در clippy_lints/lib.rs به سازنده داده می‌شود.

    pub struct ManualStrip {
    msrv: Msrv,
}

impl ManualStrip {
    pub fn new(conf: &'static Conf) -> Self {
        Self { msrv: conf.msrv.into() }
    }
}

    سپس می‌توان MSRV پروژه را در LintPass با استفاده از متد Msrv::meets با MSRV قابلیت مقایسه کرد.

    if !self.msrv.meets(cx, msrvs::STR_STRIP_PREFIX) {
    return;
}

    نکتهٔ مهم این است که اگر crate دارای attribute به نام clippy::msrv باشد، فراخوانی Msrv::meets نسبتاً پرهزینه است؛ بنابراین معمولاً باید MSRV را در انتهای یک زنجیرهٔ if let و پس از بررسی‌های دیگری که زودتر ارزیابی را متوقف می‌کنند (short-circuit) بررسی کنید.

    lint passهای early باید به‌جای آن از MsrvStack همراه با extract_msrv_attr!() استفاده کنند.

    وقتی msrv به lint اضافه شد، باید یک مورد آزمون مرتبط به فایل آزمون lint اضافه شود، که در این مثال tests/ui/manual_strip.rs است. این فایل باید یک مورد برای نسخه‌ای پایین‌تر از MSRV و یک مورد با همان محتوا اما برای خود نسخهٔ MSRV داشته باشد.

    ...

#[clippy::msrv = "1.44"]
fn msrv_1_44() {
    /* something that would trigger the lint */
}

#[clippy::msrv = "1.45"]
fn msrv_1_45() {
    /* something that would trigger the lint */
}

    به‌عنوان گام آخر، lint باید به مستندات lint اضافه شود. این کار در clippy_config/src/conf.rs انجام می‌شود:

    define_Conf! {
    #[lints(
        allow_attributes,
        allow_attributes_without_reason,
        ..
        <the newly added lint name>,
        ..
        unused_trait_names,
        use_self,
    )]
    msrv: Msrv = Msrv::default(),
    ...
}

    سپس مستندات کتاب را همان‌طور که در افزودن پیکربندی به یک lint توضیح داده شده است به‌روز کنید.

    Tip

    توجه داشته باشید که آیتم‌های کتابخانهٔ استاندارد معمولاً دو تاریخ پایداری دارند: یکی برای حالت عادی و دیگری برای زمینه‌های const. برای مثال، str::split_at در Rust 1.4 پایدار شد و در نسخهٔ 1.86 در const پایدار شد.

    برای رفع این مشکل، clippy_utils::is_in_const_context(cx) را همراه با بررسی‌های MSRV به کار ببرید. اگر MSRV پیشنهادها میان std و core متفاوت باشد، ممکن است clippy_utils::std_or_core(cx) نیز لازم شود. برای آزمودن پیشنهادها، یک تابع const را پیش از MSRV و پس از آن با #[clippy::msrv] علامت‌گذاری کنید.

    lint مربوط به author

    اگر در پیاده‌سازی lint خود مشکل دارید، یک lint داخلی با نام author نیز وجود دارد که کد Clippy را برای شناسایی الگوی مشکل‌دار تولید می‌کند. این lint برای همهٔ نحو Rust کار نمی‌کند، اما می‌تواند نقطهٔ شروع خوبی به دست دهد.

    سریع‌ترین راه استفاده از آن، Rust playground: play.rust-lang.org است. کدی را که می‌خواهید lint کنید در ویرایشگر قرار دهید و attribute ‏#[clippy::author] را بالای آیتم اضافه کنید. سپس Clippy را از طریق Tools -> Clippy اجرا کنید و باید کد تولیدشده را در خروجی زیر ببینید.

    اینجا یک نمونه روی playground وجود دارد.

    اگر دستور با موفقیت اجرا شد، می‌توانید کد را به جایی که lint خود را پیاده‌سازی می‌کنید کپی کنید.

    lint چاپ HIR

    برای پیاده‌سازی یک lint، مفید است ابتدا بازنمایی داخلی‌ای را که rustc استفاده می‌کند بشناسید. Clippy دارای attribute ‏#[clippy::dump] است که بازنمایی میانی سطح بالا (HIR) آیتم، دستور یا عبارتی را که attribute به آن متصل شده است چاپ می‌کند. برای متصل کردن attribute به عبارت‌ها اغلب باید #![feature(stmt_expr_attributes)] را فعال کنید.

    اینجا می‌توانید یک نمونه بیابید؛ فقط Tools را انتخاب کنید و Clippy را اجرا کنید.

    مستندات

    آخرین کار پیش از ارسال PR، افزودن مقداری مستندات به اعلام lint ما است.

    لطفاً lint خود را با یک doc comment مشابه زیر مستند کنید:

    declare_clippy_lint! {
    /// ### What it does
    /// Checks for ... (describe what the lint matches).
    ///
    /// ### Why is this bad?
    /// Supply the reason for linting the code.
    ///
    /// ### Example
    ///
    /// ```rust,ignore
    /// // A short example of code that triggers the lint
    /// ```
    ///
    /// Use instead:
    /// ```rust,ignore
    /// // A short example of improved code that doesn't trigger the lint
    /// ```
    #[clippy::version = "1.29.0"]
    pub FOO_FUNCTIONS,
    pedantic,
    "function named `foo`, which is not a descriptive name"
}

    اگر lint در گروه restriction است، چون چیزهایی را lint می‌کند که لزوماً «بد» نیستند و بیشتر انتخابی سبکی هستند، عنوان بخش «Why is this bad?» را با «Why restrict this?» جایگزین کنید تا از نوشتن عبارتی مانند «Why is this bad? It isn’t, but …» پرهیز شود.

    وقتی lint شما merge شود، این مستندات در فهرست lintها نمایش داده خواهد شد.

    اجرای rustfmt

    Rustfmt ابزاری برای قالب‌بندی کد Rust مطابق رهنمودهای سبک است. کد شما باید پیش از merge شدن PR با rustfmt قالب‌بندی شده باشد. Clippy در CI از rustfmt نسخهٔ nightly استفاده می‌کند.

    می‌توان آن را از طریق rustup نصب کرد:

    rustup component add rustfmt --toolchain=nightly

    از cargo dev fmt برای قالب‌بندی کل کدبیس استفاده کنید. مطمئن شوید rustfmt برای toolchain نسخهٔ nightly نصب شده است.

    اشکال‌زدایی

    اگر می‌خواهید بخش‌هایی از پیاده‌سازی lint خود را اشکال‌زدایی کنید، می‌توانید از ماکروی dbg! در هر جای کد استفاده کنید. در این صورت اجرای آزمون‌ها باید خروجی اشکال‌زدایی را در بخش stdout شامل شود.

    lintهای متعارض

    چند lint وجود دارند که با یک الگوی واحد سروکار دارند اما رویکردهای متفاوتی پیشنهاد می‌دهند. به عبارت دیگر، برخی lintها ممکن است تغییراتی را پیشنهاد دهند که در جهت مخالف چیزی است که lintهای دیگر پیش‌تر برای همان کد پیشنهاد کرده‌اند و در نتیجه تشخیص‌های متعارض ایجاد شود.

    وقتی lintی می‌سازید که به چنین وضعیتی می‌رسد، توصیه می‌شود از نکات زیر برای راهنمایی در دسته‌بندی پیروی کنید:

    • تنها موردی که این lintها باید در یک دسته باشند این است که آن دسته restriction باشد. برای مثال، semicolon_inside_block و semicolon_outside_block.
    • در همهٔ موارد دیگر، باید در دسته‌های متفاوت با سطوح مجاز بودن متفاوت قرار گیرند. برای مثال، implicit_return (restriction، allow) و needless_return (style، warn).

    برای lintهایی که در دسته‌های متفاوت هستند، همچنین توصیه می‌شود دست‌کم یکی از آن‌ها در دستهٔ restriction باشد. دلیلش این است که گروه restriction تنها گروهی است که توصیه نمی‌کنیم کل مجموعهٔ آن فعال شود و در عوض lintها را از میان آن‌ها دستچین می‌کنیم.

    چک‌لیست PR

    پیش از ارسال PR مطمئن شوید همهٔ الزامات پایه را رعایت کرده‌اید:

    • [ ] از قراردادهای نام‌گذاری lint پیروی کرده‌ام
    • [ ] آزمون‌های UI موفق اضافه کرده‌ام (از جمله فایل .stderr که commit شده است)
    • [ ] cargo test به‌صورت محلی موفق می‌شود
    • [ ] cargo dev update_lints را اجرا کرده‌ام
    • [ ] مستندات lint را اضافه کرده‌ام
    • [ ] cargo dev fmt را اجرا کرده‌ام

    افزودن پیکربندی به یک lint

    Clippy از پیکربندی مقادیر lintها با استفاده از یک فایل clippy.toml پشتیبانی می‌کند که جست‌وجوی آن در این مکان‌ها انجام می‌شود:

    1. پوشه‌ای که متغیر محیطی CLIPPY_CONF_DIR مشخص می‌کند، یا
    2. پوشه‌ای که متغیر محیطی CARGO_MANIFEST_DIR مشخص می‌کند، یا
    3. پوشهٔ جاری.

    افزودن پیکربندی به یک lint می‌تواند برای آستانه‌ها یا محدود کردن رفتاری مفید باشد که برای برخی کاربران هشدار اشتباه به‌شمار می‌آید. افزودن پیکربندی در گام‌های زیر انجام می‌شود:

    1. افزودن یک ورودی پیکربندی جدید به clippy_config::conf به این شکل:

      /// Lint: LINT_NAME.
///
/// <The configuration field doc comment>
(configuration_ident: Type = DefaultValue),

      doc comment به‌طور خودکار به مستندات lintهای فهرست‌شده اضافه می‌شود. مقدار پیش‌فرض با استفاده از پیاده‌سازی Debug نوع مربوطه قالب‌بندی می‌شود.

    2. افزودن مقدار پیکربندی به struct پیاده‌سازی lint:

      1. افزودن مقدار پیکربندی به ساختار پیاده‌سازی lint: 1. این کار ابتدا نیازمند تعریف یک ساختار پیاده‌سازی lint است. ساختارهای پیاده‌سازی lint معمولاً با ماکروی declare_lint_pass! تولید می‌شوند. این ساختار باید دستی تعریف شود تا نوعی فراداده به آن اضافه شود: ```rust // Generated struct definition declare_lint_pass!(StructName => [ LINT_NAME ]);

        // Generated struct definition
declare_lint_pass!(StructName => [
    LINT_NAME
]);

// New manual definition struct
pub struct StructName {}

impl_lint_pass!(StructName => [
    LINT_NAME
]);

      2. سپس مقدار پیکربندی و یک متد سازندهٔ متناظر را به این شکل اضافه کنید:

        pub struct StructName {
    configuration_ident: Type,
}

// ...

impl StructName {
    pub fn new(conf: &'static Conf) -> Self {
        Self {
            configuration_ident: conf.configuration_ident,
        }
    }
}

    3. ارسال مقدار پیکربندی به ساختار پیاده‌سازی lint:

      ابتدا محل ساخت struct را در فایل lib مربوط به clippy_lints بیابید. مقدار پیکربندی اکنون در یک مقدار محلی clone یا copy می‌شود و سپس به این شکل به struct پیاده‌سازی ارسال می‌شود:

      // Default generated registration:
store.register_*_pass(|| box module::StructName);

// New registration with configuration value
store.register_*_pass(move || box module::StructName::new(conf));

      تبریک، کار تقریباً تمام است. اکنون می‌توان به مقدار پیکربندی در کد lint از طریق self.configuration_ident دسترسی داشت.

    4. افزودن آزمون‌ها:

      1. مقدار پیکربندی‌شدهٔ پیش‌فرض را می‌توان مانند هر lint معمولی در tests/ui آزمود.
      2. خود پیکربندی به‌طور جداگانه در tests/ui-toml آزموده می‌شود. کافی است یک زیرپوشهٔ جدید با نامی مناسب اضافه کنید. این پوشه شامل یک فایل clippy.toml با مقدار پیکربندی و یک فایل rust است که باید توسط Clippy lint شود. آزمون را در غیر این صورت می‌توان طبق معمول نوشت.

    5. به‌روز کردن پیکربندی lint

      دستور cargo bless --test config-metadata را اجرا کنید تا تغییرات مستندات کتاب تولید شود.

    • rustc-dev-guide بسیاری از مفاهیم داخلی کامپایلر را توضیح می‌دهد
    • مستندات rustc نسخهٔ nightly که در سراسر این راهنما به آن لینک داده شده است
