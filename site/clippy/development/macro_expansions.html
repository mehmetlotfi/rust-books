کتاب ClippyThe Clippy Book

    مواجهه با ماکروها و گسترش‌ها

    گاهی هنگام کار با Clippy ممکن است با گسترش ماکروهای Rust روبه‌رو شویم. گسترش ماکروها به اندازهٔ انبساط جهان ما شگفت‌انگیز و عمیق نیست، اما قطعاً می‌تواند به دنیای منظم کد و منطق آشوب بیاورد.

    قاعدهٔ سرانگشتی این است که هنگام کار با Clippy باید کدی را که گسترش ماکرو دارد نادیده بگیریم، زیرا چنین کدی ممکن است به شیوه‌هایی پویا باشد که پیش‌بینی آن‌ها برای ما دشوار یا غیرممکن است.

    مثبت‌های کاذب

    منظور دقیق ما از پویا به شیوه‌هایی که پیش‌بینی‌شان دشوار است چیست؟

    ماکروها در سطح EarlyLintPass گسترش داده می‌شوند، یعنی درخت نحو انتزاعی (AST) به‌جای ماکروها تولید می‌شود. این یعنی کدی که در Clippy با آن کار می‌کنیم از پیش گسترش یافته است.

    اگر lint جدیدی بنویسیم، این امکان وجود دارد که lint در کدی که ماکرو تولید کرده است فعال شود. از آنجا که این کد گسترش‌یافتهٔ ماکرو را کاربر ماکرو ننوشته، بلکه در واقع نویسندهٔ ماکرو نوشته است، کاربر نمی‌تواند و نباید مسئول رفع مشکلی باشد که باعث فعال شدن lint می‌شود.

    علاوه بر این، Span در یک ماکرو را نویسندهٔ ماکرو می‌تواند تغییر دهد. بنابراین باید از هر بررسی lint که به خط‌ها یا ستون‌ها مربوط باشد پرهیز کرد، زیرا ممکن است هر زمان تغییر کنند و به اطلاعاتی نامطمئن یا نادرست تبدیل شوند.

    به دلیل این رفتارهای پیش‌بینی‌ناپذیر یا ناپایدار، گسترش ماکرو را اغلب نباید بخشی از API پایدار دانست. به همین دلیل است که بیشتر lintها، پیش از ارائهٔ پیشنهاد به کاربر نهایی، بررسی می‌کنند که داخل یک ماکرو هستند یا نه تا از مثبت‌های کاذب جلوگیری کنند.

    چگونه با ماکروها کار کنیم

    چند تابع برای کار با ماکروها در دسترس هستند.

    متد Span::from_expansion

    می‌توانیم از متد from_expansion یک span استفاده کنیم که تشخیص می‌دهد span از گسترش ماکرو یا desugaring آمده است یا نه. این یکی از رایج‌ترین گام‌های نخست در یک lint است:

    if expr.span.from_expansion() {
    // We most likely want to ignore it.
    return;
}

    متد Span::ctxt

    زمینهٔ (context) یک span که متد ctxt آن را می‌دهد و SyntaxContext برمی‌گرداند، نشان می‌دهد که span از گسترش ماکرو آمده است یا نه و اگر آمده است، کدام فراخوانی ماکرو این span را گسترش داده است.

    گاهی بررسی برابر بودن زمینهٔ دو span مفید است. برای مثال، فرض کنید خطی از کد داریم که به 1 + 0 گسترش می‌یابد:

    // The following code expands to `1 + 0` for both `EarlyLintPass` and `LateLintPass`
1 + mac!()

    با فرض اینکه عبارت 1 را در متغیری به نام left و عبارت 0/mac!() را در متغیری به نام right جمع‌آوری کنیم، می‌توانیم زمینهٔ آن‌ها را ساده مقایسه کنیم. اگر زمینه متفاوت باشد، به احتمال زیاد با یک گسترش ماکرو سروکار داریم و باید آن را نادیده بگیریم:

    if left.span.ctxt() != right.span.ctxt() {
    // The code author most likely cannot modify this expression
    return;
}

    نکته: کدی که از گسترش نیامده باشد در زمینهٔ «ریشه» (root) است. بنابراین می‌توان فرض کرد هر spanی که from_expansion آن false برگرداند، زمینهٔ یکسانی دارد. به همین دلیل، استفاده از span.from_expansion() اغلب کافی است.

    کمی عمیق‌تر که برویم، در یک عبارت ساده مانند a == b، a و b زمینهٔ یکسانی دارند. اما در یک macro_rules! با a == $b، ‏$b به عبارتی گسترش می‌یابد که زمینه‌ای متفاوت از a دارد.

    به ماکروی m زیر نگاه کنید:

    macro_rules! m {
    ($a:expr, $b:expr) => {
        if $a.is_some() {
            $b;
        }
    }
}

let x: Option<u32> = Some(42);
m!(x, x.unwrap());

    اگر خط m!(x, x.unwrap()); گسترش داده شود، دو عبارت گسترش‌یافته خواهیم داشت:

    • x.is_some() (از خط $a.is_some() در ماکروی m)
    • x.unwrap() (متناظر با $b در ماکروی m)

    فرض کنید span عبارت x.is_some() با متغیر x_is_some_span و span عبارت x.unwrap() با متغیر x_unwrap_span مرتبط باشد؛ می‌توانیم فرض کنیم که این دو span زمینهٔ یکسانی ندارند:

    // x.is_some() is from inside the macro
// x.unwrap() is from outside the macro
assert_ne!(x_is_some_span.ctxt(), x_unwrap_span.ctxt());

    تابع in_external_macro

    Span متدی (in_external_macro) فراهم می‌کند که می‌تواند تشخیص دهد span داده‌شده از ماکرویی آمده است که در یک crate خارجی تعریف شده است.

    بنابراین اگر واقعاً بخواهیم یک lint جدید با کد تولیدشده توسط ماکرو کار کند، این خط دفاعی بعدی برای پرهیز از ماکروهایی است که داخل crate جاری تعریف نشده‌اند، زیرا درست نیست که Clippy کدی را lint کند که کاربر نمی‌تواند آن را تغییر دهد.

    برای مثال، فرض کنید کد زیر را Clippy در حال بررسی است:

    #[macro_use]
extern crate a_foreign_crate_with_macros;

// `foo` macro is defined in `a_foreign_crate_with_macros`
foo!("bar");

    همچنین فرض کنید برای فراخوانی ماکروی foo متغیر متناظر foo_span را به دست آورده‌ایم؛ می‌توانیم تصمیم بگیریم اگر in_external_macro مقدار true برگرداند، lint نکنیم (توجه کنید که cx می‌تواند EarlyContext یا LateContext باشد):

    if foo_span.in_external_macro(cx.sess().source_map()) {
    // We should ignore macro from a foreign crate.
    return;
}

    تابع is_from_proc_macro

    یکی از نقاط رایج سردرگمی، وجود is_from_proc_macro است و اینکه با دیگر تابع‌های in_external_macro/from_expansion چه فرقی دارد.

    اگرچه in_external_macro و from_expansion هر دو برای تشخیص کد گسترش‌یافته از ماکروهای تعریفی (declarative) (یعنی macro_rules! و ماکروهای 2.0) کاملاً خوب کار می‌کنند، تشخیص کدی که ماکروی proc تولید کرده است کمی دشوارتر است، زیرا ماکروهای proc می‌توانند (و اغلب هم می‌کنند) span توکن‌های بازگشتی را آزادانه دستکاری کنند.

    در عمل، این کار اغلب با استفاده از quote::quote_spanned! و یک span از توکن‌های ورودی انجام می‌شود.

    در این موارد، هیچ راه قابل اتکایی برای کامپایلر (و ابزارهایی مانند Clippy) وجود ندارد که کدی را که از چنین ماکروی procای می‌آید از کدی که کاربر مستقیماً نوشته است تشخیص دهد، و in_external_macro مقدار false برمی‌گرداند.

    این معمولاً برای کامپایلر مشکلی نیست و حتی به نویسندگان ماکروی proc کمک می‌کند پیام‌های خطای بهتری بسازند، چون امکان می‌دهد بخش‌هایی از گسترش را به بخش‌هایی از ورودی ماکرو مرتبط کنند و به کامپایلر اجازه می‌دهد در صورت بروز خطای کامپایل، کاربر را به کد مربوط راهنمایی کند.

    اما برای Clippy این ناخوشایند است، چون بیشتر اوقات نمی‌خواهیم کد تولیدشده توسط ماکروی proc را lint کنیم و این وضعیت تشخیص اینکه چه کدی از ماکروی proc است و چه کدی نیست را غیرممکن می‌کند.

    Note

    نکته: این موضوع به‌طور خاص فقط زمانی مشکل است که یک ماکروی proc صراحتاً span را برابر با span ورودی قرار دهد.

    برای مثال، روش‌های رایج دیگر ساخت TokenStream، مانند "fn foo() {...}".parse::<TokenStream>()، span هر توکن را برابر با Span::call_site() قرار می‌دهند، که از قبل span را به‌عنوان آمده از یک ماکروی proc علامت‌گذاری می‌کند و متدهای معمول span مشکلی در تشخیص آن به‌عنوان span ماکرو ندارند.

    به همین دلیل Clippy تابع is_from_proc_macro مخصوص خود را دارد که با بررسی اینکه متن منبع در span داده‌شده با گره AST داده‌شده هم‌خوان است یا نه، سعی می‌کند تقریب بزند که span از یک ماکروی proc آمده است یا نه.

    این تابع معمولاً همراه با دیگر توابع span ماکرویی که ذکر شد به کار می‌رود، اما معمولاً بسیار دیرتر در زنجیرهٔ شرط‌ها فراخوانی می‌شود، چون کمی سنگین‌تر از بیشتر شرط‌های دیگر است، تا شرط‌های ارزان‌تر دیگر سریع‌تر شکست بخورند. برای مثال، lint ‏borrow_deref_ref:

    impl<'tcx> LateLintPass<'tcx> for BorrowDerefRef {
    fn check_expr(&mut self, cx: &LateContext<'tcx>, e: &rustc_hir::Expr<'tcx>) {
        if let ... = ...
            && ...
            && !e.span.from_expansion()
            && ...
            && ...
            && !is_from_proc_macro(cx, e)
            && ...
        {
            ...
        }
    }
}

    آزمودن lintها با گسترش ماکرو

    برای آزمودن اینکه همهٔ این موارد در lint شما درست مدیریت می‌شوند، یک crate کمکی جانبی داریم که ماکروهای گوناگونی ارائه می‌دهد و آزمون‌ها به این شکل از آن استفاده می‌کنند:

    //@aux-build:proc_macros.rs

extern crate proc_macros;

fn main() {
    proc_macros::external!{ code_that_should_trigger_your_lint }
    proc_macros::with_span!{ span code_that_should_trigger_your_lint }
}

    این دو حالت را آزمایش می‌کند:

    • proc_macros::external! یک ماکروی proc ساده است که توکن‌های ورودی را با span ماکرو بازمی‌گرداند: این حالت معمول و رایجی را نشان می‌دهد که یک ماکروی خارجی به کدی گسترش می‌یابد که lint شما را فعال می‌کند، و in_external_macro و Span::from_expansion آن را درست مدیریت می‌کنند.

    • proc_macros::with_span! توکن‌های ورودی را از توکن دوم به بعد با span توکن اول بازمی‌گرداند: اینجا جایی است که دیگر توابع شکست می‌خورند و به is_from_proc_macro نیاز است.
