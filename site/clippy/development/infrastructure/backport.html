    بک‌پورت تغییرات

    گاهی لازم است تغییرات به نسخهٔ beta از Clippy بک‌پورت (backport) شوند. بک‌پورت در Clippy نادر است و باید توسط تیم Clippy تأیید شود. برای مثال، اگر یک ICE حیاتی رفع شده باشد یا یک lint تا حدی خراب باشد که پیش از رسیدن به stable باید غیرفعال شود، بک‌پورت انجام می‌شود.

    Note

    توجه: اگر فکر می‌کنید یک PR باید بک‌پورت شود، می‌توانید آن را با برچسب beta-nominated علامت‌گذاری کنید. این کار باید پیش از پنجشنبهٔ هفتهٔ قبل از انتشار انجام شود.

    فیلتر کردن PRهایی که باید بک‌پورت شوند

    نخست، همهٔ PRهای برچسب‌خورده را با این فیلتر پیدا کنید.

    سپس، هر PR را جداگانه بررسی کنید. چند مورد برای بررسی وجود دارد. این موارد نیاز به توضیح دارند و کاملاً ذهنی هستند. قضاوت درست لازم است.

    1. آیا ارزش بک‌پورت کردن این اصلاح را دارد؟

      این کاملاً ذهنی است. اصلاح یک ICE معمولاً ارزشش را دارد. انتقال یک lint به گروهی با سطح پایین‌تر (از warn به allow-by-default) نیز معمولاً چنین است. اصلاح یک FP (مثبت کاذب) معمولاً نه (به‌تنهایی). اگر به هر حال بک‌پورت انجام شود، اصلاح‌های FP نیز ممکن است گنجانده شوند. اگر PR تغییرات زیادی دارد، بک‌پورت‌ها را باید با دقت بیشتری بررسی کرد.

    2. آیا مشکلی که PR برطرف کرده است از پیش در beta وجود دارد؟

      ممکن است مشکلی که PR برطرف کرده است هنوز به شاخهٔ beta مخزن Rust نرسیده باشد. اگر چنین باشد و اصلاح از پیش با مخزن Rust همگام شده باشد، لازم نیست اصلاح بک‌پورت شود، چون همراه با کامیتی که مشکل را ایجاد کرده به stable خواهد رسید. اگر PR اصلاح هنوز همگام نشده است، آن PR یا باید به شاخهٔ master مخزن Rust یا در چرخهٔ بک‌پورت بعدی به beta «بک‌پورت» شود.

    3. پیش از انتقال به beta مطمئن شوید اصلاح روی master است

      اصلاح باید از پیش با شاخهٔ master مخزن Rust همگام شده باشد. در غیر این صورت، beta بعدی دوباره این اصلاح را نخواهد داشت. اگر هنوز در master نیست، احتمالاً نباید بک‌پورت شود. اگر بک‌پورت واقعاً مهم است، ابتدا یک همگام‌سازی خارج از چرخه انجام دهید. با این حال، این همگام‌سازی خارج از چرخه باید کوچک باشد، چون تغییرات آن بدون آنکه ابتدا در nightly آزموده شوند مستقیماً وارد beta می‌شوند.

    آماده‌سازی

    Note

    توجه: همهٔ دستورهای این فصل در clone مخزن Rust اجرا می‌شوند.

    دستورالعمل‌های تعریف remoteها را دنبال کنید تا remote با نام clippy-upstream را در مخزن Rust تعریف کنید.

    پس از آن، remote را با دستور زیر دریافت (fetch) کنید

    git fetch clippy-upstream master

    سپس به شاخهٔ beta بروید:

    git switch beta
git fetch upstream
git reset --hard upstream/beta

    بک‌پورت کردن تغییرات

    وقتی یک PR با صف ادغام (merge queue) گیت‌هاب ادغام می‌شود، PR با پیام زیر بسته می‌شود

    <PR title> (#<PR number>)

    این کامیت باید بک‌پورت شود. برای این کار، <sha1> آن کامیت را پیدا کنید و دستور زیر را در clone مخزن Rust اجرا کنید:

    git cherry-pick -m 1 `<sha1>`

    این کار را برای همهٔ PRهایی که باید بک‌پورت شوند انجام دهید.

    باز کردن PR در مخزن Rust

    سپس، PR مربوط به بک‌پورت را باز کنید. مطمئن شوید PR به سمت شاخهٔ beta باز می‌شود و نه شاخهٔ master. توضیح PR باید چیزی شبیه این باشد:

    [beta] Clippy backports

r? @Mark-Simulacrum

Backports:
- <Link to the Clippy PR>
- ...

<Short summary of what is backported and why>

    Mark عضو تیم انتشار (release) است و در نهایت او باید پیش از شاخه‌سازی یک نسخهٔ جدید beta، PR را ادغام کند. او را تگ کنید تا بک‌پورت را رسیدگی کند. سپس، همهٔ بک‌پورت‌ها را فهرست کنید و یک خلاصهٔ کوتاه بنویسید که چه چیزی بک‌پورت شده و چرا ارزش بک‌پورت کردن آن را دارد.

    تغییر برچسب PRهای بک‌پورت‌شده

    وقتی یک PR به Rust beta بک‌پورت می‌شود، آن را با برچسب beta-accepted علامت‌گذاری کنید. این برچسب هنگام نوشتن changelog در نظر گرفته می‌شود.
