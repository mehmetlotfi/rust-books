    آزمون‌نویسی

    توسعهٔ lintها برای Clippy یک فرایند توسعهٔ آزمون‌محور (TDD) است، زیرا نخستین کار ما پیش از پیاده‌سازی هر منطقی برای یک lint جدید، نوشتن چند نمونه آزمون است.

    توسعهٔ lintها همراه با آزمون‌ها

    وقتی Clippy را توسعه می‌دهیم، وارد قلمرویی پیچیده و پرآشوب می‌شویم که پر از مشکلات برنامه‌نویسی، خطاهای سبکی، کد نامنطقی و بی‌توجهی به قراردادهاست. آزمون‌ها نخستین لایهٔ نظمی هستند که می‌توانیم برای تعیین اینکه یک lint جدید کِی و کجا باید فعال شود یا نشود، از آن بهره ببریم.

    افزون بر این، نوشتن آزمون‌ها در ابتدا به توسعه‌دهندگان Clippy کمک می‌کند برای نخستین نسخه و بهبودهای بعدی یک lint تعادلی بیابند. با داشتن نمونه‌آزمون‌ها، لازم نیست نگران پیچیده‌سازی بیش‌ازحد یک lint در نسخهٔ اول یا از قلم افتادن برخی حالت‌های مرزی بدیهی آن باشیم. این رویکرد ما را قادر می‌سازد هر lint را به‌صورت تکرارشونده بهبود دهیم.

    آزمون‌های UI در Clippy

    ما برای آزمون در Clippy از آزمون‌های UI استفاده می‌کنیم. این آزمون‌های UI بررسی می‌کنند که خروجی Clippy دقیقاً همان چیزی باشد که انتظار داریم. هر آزمون فقط یک فایل ساده از Rust است که کدی را که می‌خواهیم بررسی کنیم در خود دارد.

    خروجی Clippy با یک فایل .stderr مقایسه می‌شود. توجه کنید که لازم نیست این فایل را خودتان بسازید. تولید فایل‌های .stderr را با دستور cargo bless (که بعداً خواهیم دید) انجام می‌دهیم.

    نوشتن نمونه‌آزمون‌ها

    حالا بیایید دربارهٔ چند آزمون برای lint خیالی foo_functions خود فکر کنیم. کار را با باز کردن فایل آزمون tests/ui/foo_functions.rs که توسط cargo dev new_lint ساخته شده است آغاز می‌کنیم.

    برای شروع، فایل را با چند مثال به‌روز کنید:

    #![warn(clippy::foo_functions)] // < Add this, so the lint is guaranteed to be enabled in this file

// Impl methods
struct A;
impl A {
    pub fn fo(&self) {}
    pub fn foo(&self) {}
    //~^ foo_functions
    pub fn food(&self) {}
}

// Default trait methods
trait B {
    fn fo(&self) {}
    fn foo(&self) {}
    //~^ foo_functions
    fn food(&self) {}
}

// Plain functions
fn fo() {}
fn foo() {}
//~^ foo_functions
fn food() {}

fn main() {
    // We also don't want to lint method calls
    foo();
    let a = A;
    a.foo();
}

    بدون منطق واقعی lint که هنگام دیدن نام تابع foo آن lint را صادر کند، این آزمون شکست می‌خورد، زیرا انتظار داریم در خط‌هایی که با //~^ foo_functions علامت‌گذاری شده‌اند خطا داشته باشیم. با این حال، اکنون می‌توانیم آزمون را با دستور زیر اجرا کنیم:

    $ TESTNAME=foo_functions cargo uitest

    Clippy کامپایل می‌شود و با شکایت از اینکه هیچ خطایی دریافت نکرده شکست می‌خورد:

    این طبیعی است. بالاخره ما مقداری کد Rust نوشته‌ایم، اما هنوز واقعاً هیچ منطقی برای تشخیص توابع foo و صدور lint در Clippy پیاده‌سازی نکرده‌ایم.

    با پیاده‌سازی تدریجی منطق lint، این دستور اجرای آزمون UI را مرتب اجرا می‌کنیم. Clippy شروع به نمایش اطلاعاتی می‌کند که به ما اجازه می‌دهد بررسی کنیم آیا خروجی دارد به چیزی که می‌خواهیم تبدیل می‌شود.

    توجه: می‌توانید با تعیین یک فهرست جداشده با ویرگول، چند فایل آزمون را اجرا کنید: TESTNAME=foo_functions,bar_methods,baz_structs.

    cargo bless

    وقتی از خروجی راضی شدیم، باید این دستور را اجرا کنیم تا فایل .stderr را برای lint خود تولید یا به‌روز کنیم:

    $ TESTNAME=foo_functions cargo uibless

    این دستور پیشنهادها و اصلاح‌های صادرشدهٔ lint را در فایل .stderr می‌نویسد، همراه با دلیل lint، اصلاح‌های پیشنهادی، شمارهٔ خط‌ها و غیره.

    پس از آن، اجرای TESTNAME=foo_functions cargo uitest باید موفق باشد. وقتی lint خود را کامیت می‌کنیم، باید فایل‌های .stderr تولیدشده را هم کامیت کنیم.

    به‌طور کلی، باید فقط فایل‌هایی را کامیت کنید که cargo bless برای lint مشخصی که در حال ساخت یا ویرایش آن هستید تغییر داده است.

    Note

    توجه: اگر فایل‌های .stderr و .fixed تولیدشده خالی باشند، باید حذف شوند.

    آزمون‌های toml

    برخی lintها را می‌توان از طریق فایل clippy.toml پیکربندی کرد. آن مقادیر پیکربندی در tests/ui-toml آزموده می‌شوند.

    برای افزودن یک آزمون جدید در آنجا، یک پوشهٔ جدید بسازید و این فایل‌ها را اضافه کنید:

    • clippy.toml: مقدار پیکربندی‌ای را که می‌خواهید بیازمایید اینجا بگذارید.
    • lint_name.rs: فایل آزمونی که کد آزمایشی را در آن می‌گذارید و باید بسته به پیکربندی تنظیم‌شده در فایل clippy.toml رفتار متفاوتی از lint ببیند.

    فایل‌های احتمالی .stderr و .fixed را باز هم می‌توان با cargo bless تولید کرد.

    lintهای Cargo

    فرایند آزمون برای lintهای Cargo متفاوت است، چون اینجا به فایل مانیفست Cargo.toml علاقه‌مندیم. در این حالت به یک crate کمینه نیز نیاز داریم که به آن مانیفست مرتبط باشد. این آزمون‌ها در tests/ui-cargo تولید می‌شوند.

    تصور کنید یک lint نمونهٔ جدید به نام foo_categories داریم؛ می‌توانیم این دستور را اجرا کنیم:

    $ cargo dev new_lint --name=foo_categories --pass=late --category=cargo

    پس از اجرای cargo dev new_lint، به‌طور پیش‌فرض دو crate جدید می‌یابیم که هر کدام مانیفست خود را دارند:

    • tests/ui-cargo/foo_categories/fail/Cargo.toml: این فایل باید باعث شود lint جدید خطا صادر کند.
    • tests/ui-cargo/foo_categories/pass/Cargo.toml: این فایل نباید lint را فعال کند.

    اگر به حالت‌های بیشتری نیاز دارید، می‌توانید یکی از آن crateها (زیر foo_categories) را کپی کنید و نامش را تغییر دهید.

    فرایند تولید فایل .stderr مانند lintهای دیگر است و گذاشتن متغیر TESTNAME پیش از cargo uitest برای lintهای Cargo هم کار می‌کند.

    آزمون‌های Rustfix

    اگر lintی که روی آن کار می‌کنید از پیشنهادهای ساختاریافته استفاده می‌کند، rustfix پیشنهادهای lint را روی کد فایل آزمون اعمال می‌کند و نتیجه را با محتوای یک فایل .fixed مقایسه می‌کند.

    پیشنهادهای ساختاریافته به کاربر می‌گویند چگونه کدی را که با span_lint_and_sugg lint شده است اصلاح یا بازنویسی کند.

    اگر از span_lint_and_sugg برای تولید پیشنهاد استفاده شود، اما همهٔ پیشنهادها به کد معتبر نرسند، می‌توانید با گذاشتن نظر //@no-rustfix در بالای فایل آزمون، از اجرای rustfix روی آن فایل جلوگیری کنید.

    دربارهٔ پیشنهادها در فصل بعدی به‌طور عمیق‌تر صحبت خواهیم کرد.

    برای تولید خودکار فایل .fixed پس از اجرای آزمون‌ها از cargo bless استفاده کنید.

    آزمون دستی

    آزمودن دستی روی یک فایل نمونه می‌تواند مفید باشد، اگر چند println! اضافه کرده‌اید و خروجی مجموعه آزمون ناخوانا شده است.

    برای امتحان Clippy با تغییرات محلی خود، دستور زیر را از ریشهٔ نسخهٔ کاری اجرا کنید.

    $ cargo dev lint input.rs
