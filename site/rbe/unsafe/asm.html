Rust با مثالRust By Example

    اسمبلی درون‌خطی

    Rust از طریق ماکروی asm! از اسمبلی درون‌خطی پشتیبانی می‌کند. با آن می‌توان اسمبلی دست‌نویس را در خروجی اسمبلی کامپایلر گنجاند. معمولاً نیازی به این کار نیست، اما گاهی کارایی یا زمان‌بندی موردنیاز از راه دیگری به‌دست نمی‌آید. دسترسی به امکانات سطح‌پایین سخت‌افزار، مثلاً در کد هسته، نیز ممکن است این قابلیت را لازم کند.

    نکته: مثال‌ها با اسمبلی x86/x86-64 نوشته شده‌اند، اما معماری‌های دیگر نیز پشتیبانی می‌شوند.

    اسمبلی درون‌خطی در حال حاضر روی معماری‌های زیر پشتیبانی می‌شود:

    • x86 و x86-64
    • ARM
    • AArch64
    • RISC-V

    استفادهٔ پایه

    با ساده‌ترین مثال ممکن شروع کنیم:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

unsafe {
    asm!("nop");
}
}

    این کد یک دستورالعمل NOP (بدون عملیات) به اسمبلی تولیدشده توسط کامپایلر اضافه می‌کند. توجه کنید که همهٔ فراخوانی‌های asm! باید درون یک بلوک unsafe باشند، زیرا می‌توانند دستورالعمل‌های دلخواه درج کنند و ناورداهای گوناگونی را نقض کنند. دستورالعمل‌هایی که باید درج شوند، به‌صورت یک لیترال رشته‌ای در آرگومان اول ماکروی asm! فهرست می‌شوند.

    ورودی‌ها و خروجی‌ها

    افزودن دستوری که کاری نمی‌کند چندان جذاب نیست؛ بیایید روی داده عمل کنیم:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let x: u64;
unsafe {
    asm!("mov {}, 5", out(reg) x);
}
assert_eq!(x, 5);
}

    این کد مقدار 5 را در متغیر x از نوع u64 می‌نویسد. رشتهٔ مشخص‌کنندهٔ دستورها در واقع رشتهٔ قالب است و از قواعد رشته‌های قالب Rust پیروی می‌کند. آرگومان‌های درج‌شده در قالب کمی متفاوت‌اند. نخست باید ورودی یا خروجی‌بودن متغیر را مشخص کنیم؛ اینجا با out آن را خروجی اعلام کرده‌ایم. نوع ثبات مورد انتظار را نیز تعیین می‌کنیم؛ reg یعنی یک ثبات همه‌منظورهٔ دلخواه. کامپایلر ثبات مناسبی را در قالب قرار می‌دهد و پس از پایان اسمبلی، مقدار متغیر را از آن می‌خواند.

    مثال دیگری را ببینیم که ورودی نیز دارد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let i: u64 = 3;
let o: u64;
unsafe {
    asm!(
        "mov {0}, {1}",
        "add {0}, 5",
        out(reg) o,
        in(reg) i,
    );
}
assert_eq!(o, 8);
}

    این کد 5 را به ورودی i می‌افزاید و نتیجه را در o می‌نویسد. ابتدا مقدار i را در خروجی کپی و سپس 5 را به آن اضافه می‌کند.

    این مثال چند نکته را نشان می‌دهد:

    نخست، asm! چند آرگومان رشتهٔ قالب می‌پذیرد و هرکدام مانند یک خط جداگانهٔ اسمبلی رفتار می‌کنند؛ گویی با خط جدید به هم پیوسته‌اند. این ویژگی قالب‌بندی اسمبلی را آسان می‌کند.

    دوم، ورودی‌ها با in به‌جای out اعلان می‌شوند.

    سوم، مانند هر رشتهٔ قالب می‌توان شماره یا نام آرگومان را مشخص کرد. این قابلیت در اسمبلی درون‌خطی بسیار مفید است، چون آرگومان‌ها اغلب چند بار استفاده می‌شوند. در اسمبلی پیچیده، نام‌گذاری خوانایی را بهتر می‌کند و اجازه می‌دهد بدون تغییر ترتیب آرگومان‌ها، دستورها را جابه‌جا کنید.

    می‌توانیم مثال را بیشتر بهبود دهیم و دستور mov را حذف کنیم:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut x: u64 = 3;
unsafe {
    asm!("add {0}, 5", inout(reg) x);
}
assert_eq!(x, 8);
}

    inout آرگومانی را مشخص می‌کند که هم ورودی و هم خروجی است. برخلاف اعلان جداگانهٔ ورودی و خروجی، تضمین می‌کند هر دو به یک ثبات اختصاص یابند.

    همچنین می‌توان برای بخش‌های ورودی و خروجی عملوند inout متغیرهای متفاوتی تعیین کرد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let x: u64 = 3;
let y: u64;
unsafe {
    asm!("add {0}, 5", inout(reg) x => y);
}
assert_eq!(y, 8);
}

    عملوندهای خروجی دیرهنگام

    کامپایلر Rust در تخصیص عملوندها محافظه‌کار است. فرض می‌شود out هر لحظه ممکن است نوشته شود، پس نمی‌تواند مکانش را با آرگومان دیگری مشترک کند. برای کارایی بهینه باید کمترین تعداد ثبات را مصرف کرد تا پیرامون بلوک اسمبلی ذخیره و بازیابی نشوند. مشخص‌کنندهٔ lateout برای خروجی‌ای است که فقط پس از مصرف همهٔ ورودی‌ها نوشته می‌شود؛ گونهٔ inlateout نیز وجود دارد.

    مثالی که در حالت release یا بهینه‌شده نمی‌توان از inlateout استفاده کرد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut a: u64 = 4;
let b: u64 = 4;
let c: u64 = 4;
unsafe {
    asm!(
        "add {0}, {1}",
        "add {0}, {2}",
        inout(reg) a,
        in(reg) b,
        in(reg) c,
    );
}
assert_eq!(a, 12);
}

    در حالت‌های بهینه‌نشده (مثلاً حالت Debug)، جایگزین‌کردن inout(reg) a با inlateout(reg) a در مثال بالا همچنان می‌تواند نتیجهٔ مورد انتظار را بدهد. اما در حالت release یا سایر حالت‌های بهینه‌شده، استفاده از inlateout(reg) a می‌تواند به‌جای آن به مقدار نهایی a = 16 منجر شود و باعث شکست assertion شود.

    زیرا در حالت بهینه کامپایلر می‌تواند برای b و c یک ثبات بگذارد، چون مقدارشان یکسان است. با inlateout، ممکن است a و c نیز یک ثبات بگیرند و نخستین add بارگذاری اولیهٔ c را بازنویسی کند. در مقابل، inout(reg) a ثبات جداگانه‌ای برای a تضمین می‌کند.

    اما مثال زیر می‌تواند از inlateout استفاده کند، چون خروجی فقط پس از خواندن همهٔ ثبات‌های ورودی تغییر می‌کند:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut a: u64 = 4;
let b: u64 = 4;
unsafe {
    asm!("add {0}, {1}", inlateout(reg) a, in(reg) b);
}
assert_eq!(a, 8);
}

    همان‌طور که می‌بینید، حتی اگر a و b به یک ثبات اختصاص یابند این قطعه درست کار می‌کند.

    عملوندهای ثبات صریح

    برخی دستورها می‌خواهند عملوند در ثبات مشخصی باشد. ازاین‌رو اسمبلی درون‌خطی Rust قیدهای دقیق‌تری فراهم می‌کند. reg عموماً روی هر معماری موجود است، اما ثبات صریح به معماری وابستگی زیادی دارد؛ مثلاً در x86 می‌توان ثبات‌های همه‌منظورهٔ eax، ebx، ecx، edx، ebp، esi و edi را با نامشان مشخص کرد.

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let cmd = 0xd1;
unsafe {
    asm!("out 0x64, eax", in("eax") cmd);
}
}

    در این مثال دستور out محتوای cmd را به درگاه 0x64 می‌فرستد. چون out فقط eax و زیرثبات‌هایش را می‌پذیرد، باید قید eax را به‌کار ببریم.

    نکته: برخلاف دیگر عملوندها، ثبات صریح را نمی‌توان با {} در رشتهٔ قالب آورد و باید نام ثبات را مستقیم نوشت. همچنین باید پس از همهٔ نوع‌های دیگر، در انتهای فهرست عملوندها بیاید.

    این مثال از دستور mul در x86 استفاده می‌کند:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

fn mul(a: u64, b: u64) -> u128 {
    let lo: u64;
    let hi: u64;

    unsafe {
        asm!(
            // The x86 mul instruction takes rax as an implicit input and writes
            // the 128-bit result of the multiplication to rax:rdx.
            "mul {}",
            in(reg) a,
            inlateout("rax") b => lo,
            lateout("rdx") hi
        );
    }

    ((hi as u128) << 64) + lo as u128
}
}

    دستور mul دو ورودی ۶۴ بیتی را با نتیجهٔ ۱۲۸ بیتی ضرب می‌کند. تنها عملوند صریح ثباتی است که از a پر می‌شود. عملوند دوم ضمنی و الزاماً rax است که از b پر می‌شود. ۶۴ بیت پایین نتیجه در rax و سپس lo، و ۶۴ بیت بالا در rdx و سپس hi قرار می‌گیرد.

    ثبات‌های تخریب‌شده

    اسمبلی درون‌خطی اغلب وضعیتی را تغییر می‌دهد که به‌عنوان خروجی لازم نیست؛ یا ثباتی موقت مصرف می‌شود یا دستورها وضعیتی را تغییر می‌دهند که دیگر بررسی نمی‌کنیم. به این وضعیت «تخریب‌شده» می‌گویند. باید کامپایلر را آگاه کنیم، چون شاید لازم باشد آن را پیرامون بلوک اسمبلی ذخیره و بازیابی کند.

    use std::arch::asm;

#[cfg(target_arch = "x86_64")]
fn main() {
    // three entries of four bytes each
    let mut name_buf = [0_u8; 12];
    // String is stored as ascii in ebx, edx, ecx in order
    // Because ebx is reserved, the asm needs to preserve the value of it.
    // So we push and pop it around the main asm.
    // 64 bit mode on 64 bit processors does not allow pushing/popping of
    // 32 bit registers (like ebx), so we have to use the extended rbx register instead.

    unsafe {
        asm!(
            "push rbx",
            "cpuid",
            "mov [rdi], ebx",
            "mov [rdi + 4], edx",
            "mov [rdi + 8], ecx",
            "pop rbx",
            // We use a pointer to an array for storing the values to simplify
            // the Rust code at the cost of a couple more asm instructions
            // This is more explicit with how the asm works however, as opposed
            // to explicit register outputs such as `out("ecx") val`
            // The *pointer itself* is only an input even though it's written behind
            in("rdi") name_buf.as_mut_ptr(),
            // select cpuid 0, also specify eax as clobbered
            inout("eax") 0 => _,
            // cpuid clobbers these registers too
            out("ecx") _,
            out("edx") _,
        );
    }

    let name = core::str::from_utf8(&name_buf).unwrap();
    println!("CPU Manufacturer ID: {}", name);
}

#[cfg(not(target_arch = "x86_64"))]
fn main() {}

    در مثال بالا، دستور cpuid شناسهٔ سازندهٔ پردازنده را می‌خواند. این دستور بیشترین آرگومان پشتیبانی‌شدهٔ cpuid را در eax و بایت‌های ASCII شناسهٔ سازنده را به‌ترتیب در ebx، edx و ecx می‌نویسد.

    با اینکه eax خوانده نمی‌شود، باید تغییرش را به کامپایلر بگوییم تا مقدار پیش از اسمبلی را در صورت نیاز حفظ کند. آن را خروجی با _ به‌جای نام متغیر اعلان می‌کنیم؛ یعنی مقدار خروجی دور انداخته شود.

    این کد محدودیت ثبات رزروشدهٔ ebx در LLVM را نیز دور می‌زند. LLVM کنترل کامل آن را برای خود می‌داند و پیش از خروج از بلوک باید به حالت اصلی بازگردد؛ بنابراین جز وقتی کامپایلر آن را برای کلاس عمومی مانند in(reg) برگزیند، ورودی یا خروجی نمی‌شود. پس عملوندهای reg در حضور ثبات رزروشده خطرناکند، زیرا اشتراک ثبات می‌تواند ناخواسته ورودی یا خروجی را خراب کند.

    برای دور زدن این مشکل، از rdi برای نگه‌داشتن اشاره‌گر به آرایهٔ خروجی استفاده می‌کنیم، ebx را با push ذخیره می‌کنیم، درون بلوک asm از ebx می‌خوانیم و در آرایه می‌نویسیم و سپس ebx را با pop به حالت اولیه‌اش بازمی‌گردانیم. push و pop از نسخهٔ کامل ۶۴ بیتی ثبات یعنی rbx استفاده می‌کنند تا اطمینان حاصل شود که کل ثبات ذخیره می‌شود. روی هدف‌های ۳۲ بیتی، کد به‌جای آن در push/pop از ebx استفاده می‌کند.

    این روش را می‌توان با کلاس ثبات عمومی برای گرفتن یک ثبات موقت در اسمبلی نیز به‌کار برد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

// Multiply x by 6 using shifts and adds
let mut x: u64 = 4;
unsafe {
    asm!(
        "mov {tmp}, {x}",
        "shl {tmp}, 1",
        "shl {x}, 2",
        "add {x}, {tmp}",
        x = inout(reg) x,
        tmp = out(reg) _,
    );
}
assert_eq!(x, 4 * 6);
}

    عملوندهای نماد و تخریب‌های ABI

    به‌طور پیش‌فرض، asm! فرض می‌کند که محتوای هر ثباتی که به‌عنوان خروجی مشخص نشده باشد توسط کد اسمبلی حفظ می‌شود. آرگومان clobber_abi در asm! به کامپایلر می‌گوید که عملوندهای clobber لازم را مطابق ABI قرارداد فراخوانی داده‌شده به‌طور خودکار درج کند: هر ثباتی که در آن ABI به‌طور کامل حفظ نمی‌شود، clobber‌شده تلقی می‌شود. می‌توان چند آرگومان clobber_abi ارائه کرد و همهٔ clobberهای تمام ABIهای مشخص‌شده درج می‌شوند.

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

extern "C" fn foo(arg: i32) -> i32 {
    println!("arg = {}", arg);
    arg * 2
}

fn call_foo(arg: i32) -> i32 {
    unsafe {
        let result;
        asm!(
            "call {}",
            // Function pointer to call
            in(reg) foo,
            // 1st argument in rdi
            in("rdi") arg,
            // Return value in rax
            out("rax") result,
            // Mark all registers which are not preserved by the "C" calling
            // convention as clobbered.
            clobber_abi("C"),
        );
        result
    }
}
}

    اصلاح‌کننده‌های قالب ثبات

    گاهی باید شیوهٔ قالب‌بندی نام ثبات در رشتهٔ قالب را دقیق کنترل کرد؛ به‌ویژه وقتی زبان اسمبلی برای یک ثبات چند نام دارد که هرکدام نمایی از بخشی از آن‌اند، مانند ۳۲ بیت پایین ثبات ۶۴ بیتی.

    کامپایلر به‌طور پیش‌فرض نام اندازهٔ کامل ثبات را برمی‌گزیند؛ مانند rax در x86-64 و eax در x86.

    با اصلاح‌کننده‌های عملوند رشتهٔ قالب، همانند رشته‌های قالب معمولی، می‌توان این پیش‌فرض را تغییر داد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut x: u16 = 0xab;

unsafe {
    asm!("mov {0:h}, {0:l}", inout(reg_abcd) x);
}

assert_eq!(x, 0xabab);
}

    در این مثال کلاس reg_abcd تخصیص‌دهنده را به چهار ثبات قدیمی x86 یعنی ax، bx، cx و dx محدود می‌کند که دو بایت نخستشان جداگانه قابل آدرس‌دهی‌اند.

    فرض کنید تخصیص‌دهنده x را در ax قرار داده است. اصلاح‌کنندهٔ h نام بایت بالا و l نام بایت پایین را تولید می‌کند؛ پس کد به mov ah, al گسترش می‌یابد و بایت پایین را در بایت بالا کپی می‌کند.

    اگر نوع کوچک‌تری مانند u16 را بدون اصلاح‌کننده به‌کار ببرید، کامپایلر هشدار می‌دهد و اصلاح‌کنندهٔ درست را پیشنهاد می‌کند.

    عملوندهای نشانی حافظه

    گاهی دستور اسمبلی عملوند را از طریق نشانی یا مکان حافظه می‌خواهد. باید نحو نشانی حافظهٔ معماری هدف را دستی به‌کار ببرید. مثلاً در نحو Intel روی x86/x86_64، ورودی و خروجی را در [] بگذارید تا عملوند حافظه باشد:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

fn load_fpu_control_word(control: u16) {
    unsafe {
        asm!("fldcw [{}]", in(reg) &control, options(nostack));
    }
}
}

    برچسب‌ها

    استفادهٔ دوباره از برچسب نام‌دار، محلی یا غیرمحلی، ممکن است خطای اسمبلر یا پیونددهنده و رفتارهای عجیب ایجاد کند. این تکرار به چند شکل رخ می‌دهد:

    • صریح: استفادهٔ چندباره از یک برچسب در یک بلوک asm! یا بلوک‌های مختلف.
    • ضمنی از راه درون‌خطی‌سازی: کامپایلر می‌تواند چند نسخه از بلوک asm! بسازد، مثلاً وقتی تابع در چند محل درون‌خطی شود.
    • ضمنی از راه LTO: ممکن است کد crateهای دیگر در همان واحد تولید کد قرار گیرد و برچسب‌های دلخواه را وارد کند.

    در نتیجه، درون کد اسمبلی درون‌خطی فقط باید از برچسب‌های محلی عددی اسمبلر GNU استفاده کنید. تعریف نمادها در کد اسمبلی ممکن است به‌دلیل تعریف‌های تکراری نماد به خطاهای اسمبلر و/یا لینکر منجر شود.

    علاوه بر این، در x86 هنگام استفاده از نحو پیش‌فرض Intel، به‌دلیل یک باگ LLVM نباید از برچسب‌هایی استفاده کنید که فقط از رقم‌های 0 و 1 ساخته شده‌اند، مانند 0، 11 یا 101010، چون ممکن است در نهایت به‌عنوان مقدار دودویی تفسیر شوند. استفاده از options(att_syntax) هر ابهامی را از میان می‌برد، اما بر نحو کل بلوک asm! اثر می‌گذارد. (برای اطلاعات بیشتر دربارهٔ options، گزینه‌ها را در ادامه ببینید.)

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut a = 0;
unsafe {
    asm!(
        "mov {0}, 10",
        "2:",
        "sub {0}, 1",
        "cmp {0}, 3",
        "jle 2f",
        "jmp 2b",
        "2:",
        "add {0}, 2",
        out(reg) a
    );
}
assert_eq!(a, 5);
}

    این کد مقدار ثبات {0} را از ۱۰ تا ۳ کم می‌کند، سپس ۲ می‌افزاید و در a ذخیره می‌کند.

    این مثال چند نکته را نشان می‌دهد:

    • نخست، یک عدد را می‌توان چند بار به‌عنوان برچسب در همان بلوک به‌کار برد.
    • دوم اینکه، وقتی یک برچسب عددی به‌عنوان ارجاع استفاده می‌شود (مثلاً به‌عنوان عملوند یک دستورالعمل)، باید پسوندهای «b» («backward»، یعنی رو به عقب) یا «f» («forward»، یعنی رو به جلو) به برچسب عددی اضافه شود. در این صورت به نزدیک‌ترین برچسبی اشاره می‌کند که با این عدد در آن جهت تعریف شده است.

    گزینه‌ها

    بلوک اسمبلی درون‌خطی به‌طور پیش‌فرض مانند فراخوانی تابع خارجی FFI با قرارداد سفارشی رفتار می‌کند: ممکن است حافظه را بخواند یا بنویسد و اثر جانبی قابل مشاهده داشته باشد. در بسیاری موارد بهتر است اطلاعات بیشتری از عملکرد واقعی کد به کامپایلر بدهیم تا بهتر بهینه‌سازی کند.

    مثال قبلی دستور add را در نظر بگیریم:

    #[cfg(target_arch = "x86_64")] {
use std::arch::asm;

let mut a: u64 = 4;
let b: u64 = 4;
unsafe {
    asm!(
        "add {0}, {1}",
        inlateout(reg) a, in(reg) b,
        options(pure, nomem, nostack),
    );
}
assert_eq!(a, 8);
}

    گزینه‌ها را می‌توان به‌عنوان آخرین آرگومان اختیاری asm! داد. اینجا سه گزینه داریم:

    • pure یعنی کد اثر جانبی قابل مشاهده ندارد و خروجی فقط به ورودی‌ها وابسته است؛ بهینه‌ساز می‌تواند آن را کمتر اجرا یا کاملاً حذف کند.
    • nomem یعنی کد حافظه را نمی‌خواند و نمی‌نویسد. در حالت عادی کامپایلر دسترسی اسمبلی به هر نشانی قابل دسترس را فرض می‌کند.
    • nostack یعنی کد داده‌ای روی پشته push نمی‌کند؛ در نتیجه بهینه‌سازی‌هایی مانند ناحیهٔ قرمز پشته در x86-64 ممکن می‌شوند.

    این گزینه‌ها به کامپایلر اجازه می‌دهند کدی را که از asm! استفاده می‌کند بهتر بهینه کند؛ مثلاً با حذف بلوک‌های asm! خالص (pure) که خروجی‌هایشان لازم نیست.

    برای فهرست کامل گزینه‌ها و اثرشان، مرجع را ببینید.
